# HWP3 내장 OLE 참조명을 외부 파일로 오분류 — 테스트가 오분류를 제도화한 사례

> 작성일: 2026-07-26 (#3363)
> 성격: 기술 결함 + **프로세스 실패 사례**. 유사 상황에서 같은 사슬이 반복되는 것을
> 막기 위해 결함의 해부와 해독 절차를 함께 보존한다.

## 현상

`samples/SO-SUEOP.hwp`(HWP 3.0) 1쪽의 글맵시가 rhwp에서 표시되지 않았다. 파서는
그림 레코드에서 읽은 `00000000.OOO`를 **외부 이미지 파일명**으로 취급했고
(`external_path` 노출, `populate_external_images_from_dir()` / studio 사이드카 주입
경로), 배포판·확장에서는 옆에 놓아줄 파일이 없어 이미지가 비었다.

## 확정된 원인

이름은 파일이 아니라 **내부 참조명**이었다. 스펙(`mydocs/tech/한글문서파일구조3.0.md`)
3중 실측:

- 표 44 offset 74 그림 종류 = **1 (OLE Object)** — 원시 바이트 실측
- 12.1절: "그림 코드에는 **이름만 존재**, 실데이터는 모든 OLE를 하나의 스토리지로
  모아 **추가 정보 블록**(id=2, 표 82)에 저장" — 압축 해제 본문에서 CFB 스토리지
  실재, root 서브 스토리지명 = `00000000.OOO`
- 한컴 변환 `SO-SUEOP.hwpx`의 `BinData/ole1.ole` = 그 서브 스토리지의 root 승격
  재포장(스트림 md5 완전 동일)

파서의 추가 정보 블록 순회는 id=1(포함 그림)·id=3(하이퍼링크)만 처리하고 **id=2를
미처리**해서, pic_type=1 BinData가 payload 없는 Link로 남아 외부 경로로 오노출됐다.

## 오분류가 제도화된 사슬 (프로세스 실패의 해부)

1. **표면 증거의 함정**: "파일명처럼 생긴 문자열" + 스펙 표 44 필드명("그림 파일
   이름")만 보고 외부 파일로 해석. 12.1절을 읽지 않았다.
2. **워크어라운드의 자기강화**: 수동 추출된 `samples/00000000.OOO`(PNG)가 옆에
   놓이자 외부 파일 이론이 "실측 green"이 됐다. 출처 불명 보조 파일이 증거 노릇을
   했다.
3. **테스트가 환각을 고정**: `tests/issue_1692.rs`가 "external_path는
   00000000.OOO여야 한다 + 사이드카가 로드되어야 한다"를 단언 — 오분류가 회귀
   테스트의 보호를 받는 공식 동작이 됐고, 올바른 수정(#3363)이 들어가자 이
   테스트가 저항했다.
4. **증축 관성**: #3313에서 주입 후 뷰 갱신 배선, 프로덕션 사이드카 공급 UX
   설계안까지 오분류 위에 계층이 쌓였다. 작업지시자의 "내부에 포함된 것 아닌가"
   확인이 없었다면 존재할 필요 없는 기능이 계속 양산될 참이었다.

## 대응 (#3363, PR #3378)

- 추가 정보 블록 id=2 파싱: `extract_ole_payloads()` — 서브 스토리지 root 승격
  재포장(한컴 동형), ext "ole" BinData 주입. wasm에서는 `cfb::create()`가
  `SystemTime::now()`로 panic하므로 자체 `mini_cfb` 사용.
- payload 확보 그림만 `Picture → ShapeObject::Ole` 변환(기존 OLE preview·선택 경로
  상속).
- OlePres000이 EMF가 아닌 **표준 WMF**인 경우 추출(`preview_wmf`) + OLE 폴백
  WMF→SVG 분기.
- 부수 발견: WMF `META_POLYPOLYGON`을 윤곽별 `<polygon>`으로 분리 방출해 글자
  폐영역('ㅇ'·'ㅂ')이 검게 채워지던 구멍 소실 — 단일 `<path>` 서브패스 병합으로
  정정.
- `issue_1692` 단언을 "내장 OLE 렌더·사이드카 불요" 기준으로 교체. 스펙 문서
  표 44 아래 보완 주석 기록.

## 검증

```bash
cargo test --profile release-test --lib parser::hwp3::tests::task3363_hwp3_embedded_ole_payload_extraction
cargo test --profile release-test --test issue_1692

```

## 환각 대응 방법 요약 (작업지시자 정리, 2026-07-26)

HWP 3.0 해석 작업에서 이런 환각을 끊는 표준 절차 두 단계:

1. **HWP 3.0 스펙 문서의 비정확성을 인지한다.** 스펙 문구를 유일 근거로 배선하지
   않는다. 실증된 어긋남: 표 13 offset 181 "1=있음"(한컴 실동작은 선 없음, #3303),
   offset 182 선 연결 극성 반대(#3303), 표 44 "그림 파일 이름"(pic_type=1/2에서는
   외부 파일이 아니라 내부 참조명, #3363). 어긋남을 발견하면 해당 표 아래 보완
   주석으로 즉시 기록한다.
2. **한컴 에디터로 같은 HWP 3.0 문서를 HWPX로 변환한 대조본을 확보해 둘을
   비교한다.** 한컴의 변환 결과가 스펙 문구보다 우선하는 실동작 권위다 —
   #3303은 `paraPr/border`(4방향 NONE + connect=1)로, #3363은 `BinData/ole1.ole`
   (재포장 CFB, 스트림 md5 동일)로 각각 목표 구조가 확정됐다. 기계화 수단은
   `rhwp ir-diff <hwpx> <hwp>`이되, 비교 항목 밖 필드(문단 border_fill 등)는
   XML/바이너리 수동 대조가 필요하다(#3303 당시 ir-diff 사각지대).

## 재발 방지 절차 (같은 부류의 작업에서)

1. 파서에 **외부 자원 의존**(사이드카/링크/경로)을 도입·확장하기 전에: 스펙 해당 절
   정독 + 원시 바이트 + 한컴 실동작(UI/변환본) 3중 교차검증. "파일명이 보인다"는
   증거가 아니다.
2. 동작을 고정하는 테스트에는 근거(스펙 절/한컴 실측)를 주석으로 남긴다.
   워크어라운드를 단언하는 테스트는 워크어라운드임을 명시한다. **기존 테스트가
   수정에 저항하면 "테스트가 정답인가, 과거 믿음의 스냅샷인가"를 먼저 묻는다.**
3. `samples/`의 출처 불명 보조 파일은 이론의 증거로 삼지 말고 출처부터 추적한다.
