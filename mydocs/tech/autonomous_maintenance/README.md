# 자율 유지보수 문서 지도

`mydocs/tech/autonomous_maintenance/` 는 **rhwp 의 일상 정비를 에이전트가 맡을 때
필요한 규약**을 다룬다. 코드가 무엇을 하는가가 아니라, **여러 에이전트 세션이 한
저장소를 동시에 고칠 때 무엇이 깨지고 무엇으로 막는가**가 이 축의 주제다.

로드맵상의 위치는 [#3907](https://github.com/edwardkim/rhwp/issues/3907) **J 그룹
(R91~R100, 자율 유지보수 — 엔드게임)** 이다. 이 축은 그 그룹의 상세를 담고, #3907 은
조망만 한다.

---

## 0. 이 축이 왜 생겼는가

다른 축(`agent_security/`·`agent_runtime/`)은 **rhwp 가 에이전트에게 무엇을 주는가**를
다룬다. 이 축은 방향이 반대다 — **에이전트가 rhwp 를 고칠 때 무엇을 지켜야 하는가**다.

그 구분이 필요해진 계기는 실측이다. 2026-08-03 하루에 **같은 계정의 병렬 세션이 같은
이슈를 각자 작업해 중복 PR 이 두 번** 났다(#3902/#3903, #3897/#3904). 한 번은 우연이지만
두 번은 구조다. 그리고 그 구조를 막는 규약은 **이미 저장소에 있었는데 쓰이지 않았다**
(`../../manual/memory/feedback_assign_issue_before_work.md`, 2026-04-23 사건에서 도출).

> 규약이 문서로 있는데 안 지켜졌다면 그건 규약의 문제다 — 어디에 있는지 모르거나,
> 왜 있는지 모르거나, 지키는 비용이 어기는 비용보다 커 보이거나 셋 중 하나다.
> 이 축은 **사건을 먼저 적고 규칙을 그 뒤에 적는다.** 규칙만 남으면 왜 그런지 잊힌다.

## 1. 읽는 순서

**실측 등급 2편이 이 축의 본체**다. 사건이 실제로 났고 해법이 실증된 것만 규약으로
고정했다.

| 순서 | 문서 | 언제 읽나 | R | 등급 |
| --- | --- | --- | --- | --- |
| 1 | [병렬 세션 규약](parallel_session_protocol.md) | **이슈에 착수하기 직전. 실무 진입점** | R93 | 실측 |
| 2 | [선등재 패턴](pre_registration_pattern.md) | 열린 PR 과 같은 표·목록을 건드릴 때 | R92 | 실측 |

그 아래는 **설계 문서**다. 전부 `[가설]` 등급이고, 각 문서가 스스로 그 사실을 첫 문단에
못박는다 — "이렇게 하면 된다"가 아니라 **"이렇게 하려면 무엇이 필요한가"** 를 적는다.
읽는 순서는 없다. 해당 주제를 착수할 때 그 문서만 본다.

| 문서 | 주제 | R | 등급 |
| --- | --- | --- | --- |

| [드리프트 자동 감지](drift_detection.md) | 감지 → 이슈 자동 기안(사람 승인 게이트) | R95 | 가설 |

> [!NOTE]
> 이 표는 **2026-08-04 기준**이다. 이 축은 여러 세션이 동시에 채우고 있어(그 자체가
> [병렬 세션 규약](parallel_session_protocol.md)의 대상이다) 파일이 더 늘 수 있다.
> §5 의 R91~R100 표가 전체 현황이고, 목록에 없는 파일이 디렉터리에 있으면 이 표가
> 낡은 것이다.

### 1-1. 30초 요약 — 지금 이슈 하나를 집으려는 에이전트에게

전부 읽을 시간이 없다면 이것만 한다. 근거는 [병렬 세션 규약](parallel_session_protocol.md) §5.

```bash
# ① 잠금 확인 — 출력이 비면 미착수
gh issue view <n> --repo edwardkim/rhwp --json assignees -q '.assignees[].login'

# ② 비었으면 즉시 할당 (조사보다 먼저, 브랜치보다 먼저)
gh issue edit <n> --repo edwardkim/rhwp --add-assignee @me

# ③ 같은 이슈의 열린 PR — --limit 을 반드시 명시한다
gh pr list --repo edwardkim/rhwp --state open --limit 100 --search "<n>"

# ④ 내 열린 PR 잔량 — 10건 내외
gh pr list --repo edwardkim/rhwp --author @me --state open --limit 100 --json number -q length
```

**assignee 가 이미 있으면 착수하지 않는다.** 같은 계정이 걸려 있어도 마찬가지다 —
같은 계정의 다른 세션이 잡고 있다는 뜻이고, 그게 정확히 2026-08-03 사고의 형태다.

### 1-2. 두 문서가 각각 무엇에 답하는가

| 질문 | 답하는 문서 |
|---|---|

## 2. 이 축이 고정하는 계약

네 가지가 이 축 전체를 관통한다. 개별 문서의 결론은 모두 여기서 파생된다.

### ① 착수는 선언이다 — 잠그지 않으면 겹친다

GitHub 이슈는 기본적으로 **"누구든 가져갈 수 있는 오픈 타스크"** 로 읽힌다. 세션이
"아무도 안 하고 있다"를 확인할 방법은 이슈 본문뿐인데, 이슈 본문은 누가 착수했는지
말해 주지 않는다. `assignee` 가 그 자리를 채우라고 있는 필드다.

2026-08-03 두 사고 모두 **대상 이슈에 `assignee` 가 비어 있었다**(2026-08-04 재확인:
`gh issue view 3884/3885 --json assignees` → 둘 다 `[]`). **잠금 기제가 없어서가 아니라
쓰지 않아서 났다.**

### ② 감지는 기계, 판정은 사람

"열린 PR 이 몇 건인가"·"이 이슈에 assignee 가 있는가"는 `gh` 한 줄이다. 반면
**"이 PR 이 저 PR 과 같은 일인가"** 는 기계가 판정하기 어렵다. 파일 겹침은 신호이지
증거가 아니다 — 같은 파일을 다른 이유로 고칠 수 있다.

그래서 이 축의 자동화는 **차단이 아니라 경고**를 목표로 한다. 오탐으로 정상 작업을
막는 검사기는 곧 우회당하고, 우회당하는 검사기는 없느니만 못하다.

### ③ 충돌은 피하는 게 아니라 **미리 접합**한다

병렬 PR 이 같은 표·목록·매니페스트를 건드리면 나중 것이 반드시 충돌한다. 특히
**완전성 가드**(표에 없는 항목을 패닉으로 알리는 종류)가 있으면 더 나쁘다 — 한쪽이
머지되는 순간 다른 쪽이 깨진다.

[선등재 패턴](pre_registration_pattern.md)이 그 해법이고, #3903↔#3808 에서 실증됐다.
**어느 쪽이 먼저 머지돼도 후속 수정이 없다.**

### ④ 볼륨 캡은 리뷰어 부하가 근거다

`../../manual/agent_surface_playbook.md` §2-7 이 **"열린 PR 은 10건 이내를 유지한다"** 로
못박고, [#3796](https://github.com/edwardkim/rhwp/issues/3796) §6 이 같은 문장을
`2026-07-22 에 113건까지 불어나 30건이 일괄 close 됐다` 는 근거와 함께 반복한다.

캡은 기여자 편의를 위한 숫자가 아니다. **유입 속도가 검토 속도를 앞지르면 큐가
자산이 아니라 부채가 된다.** 근거와 계산은 [병렬 세션 규약](parallel_session_protocol.md)
§7 에 있다.

### 3-2. PR 개설 볼륨

`gh pr list --repo edwardkim/rhwp --author kevin9327 --state all --limit 500 --json number,createdAt`
로 전량을 받아 `createdAt` 날짜별로 센 값이다(2026-08-04 실행, 500건 수신, 번호 범위
#2467~#3908).

| 날짜 | 개설 | 그중 머지 |
|---|---|---|
| 2026-07-29 | 11 | 6 |
| 2026-07-30 | 17 | 0 |
| 2026-08-01 | **48** | 0 |
| 2026-08-02 | 18 | 0 |
| 2026-08-03 | 28 | 0 |

측정 시점의 **열린 PR 은 9건**(#3808·#3886·#3887·#3889·#3897·#3898·#3899·#3903·#3908)
으로 캡 안이다. **개설 속도가 캡을 넘는 것과 큐 잔량이 캡을 넘는 것은 다른 문제**이며,
지금 문제는 전자다 — 사흘간 94건을 열고 머지가 0건이다.

> [!WARNING]
> [#3914](https://github.com/edwardkim/rhwp/issues/3914) §4 와 #3907 코멘트는 08-01 을
> **14건**으로 적었다. 위 실측은 **48건**이다. `28 + 18 + 14 = 60` 이 정확히 떨어지므로
> **최신 60건만 조회해 가장 오래된 날이 잘린 것**으로 보인다 — 다만 이는 산술적으로
> 정합할 뿐 원 명령을 복원해 확인한 것은 아니라 **확인되지 않음**으로 남긴다.
> 같은 부류의 사고 선례가 있다: `../../orders/20260722.md` §"PR 메타데이터 일괄 지정" —
> `gh pr list` 기본 limit 이 30 이라 조회가 잘린 채 완료 보고가 나갔다.
> **`gh pr list`·`gh issue list` 는 항상 `--limit` 을 명시한다.**

### 3-3. 2026-07-22 큐 폭주 이력

`../../orders/20260722.md` §"대량 PR 유입 대응 체계 착수" 가 원 기록이다.

- 5일간 300건 가까이 유입(07-19 77 · 07-20 62 · 07-21 48 · 07-22 100+)
- 열린 PR 이 한때 **113건**, 대부분 한 사람 것
- 품질이 아니라 속도가 문제였다 — 처리 완료 195건 중 **171건(88%)이 실제 반영**, 순수 반려 24건
- B단계에서 `mergeable=CONFLICTING` **30건을 리베이스 안내와 함께 close**(잔량 122 → 92)

[#3719](https://github.com/edwardkim/rhwp/issues/3719) §7 이 같은 사건을
`메인테이너가 열린 PR 폭주로 30건을 일괄 close 하며 동시 열린 PR 을 10건 내외로 요청했습니다`
로 요약하고, 2026-08-01 21시 기준 16건(초과 상태)을 함께 기록한다.

**등급과 문서 유무는 다른 축이다.** R94~R97 은 문서가 있어도 등급은 `[가설]` 그대로다 —
설계 문서가 있다고 근거가 생기지는 않는다. 문서가 등급을 올리려면 **실측이 그 문서
안에 들어와야** 한다(#3907 운영 규칙 1: *"착수는 단계가 아니라 근거가 결정한다"*).

### 5-1. 무엇이 확보되면 등급이 오르는가

착수 조건을 명시해 둔다 — "언젠가 하자"는 로드맵이 아니라 대기열 청소다. R94~R97 은
각 문서가 자체 착수 조건을 담으므로 여기서는 **문서가 없는 항목**만 적는다.

| # | 승격에 필요한 근거 | 지금 없는 것 |
|---|---|---|
| R91 | autofix 봇의 red→green 게이트 로그와 볼륨 캡 준수 실적이 **저장소 안에서** 재현 가능해야 한다 | 증거가 포크에 있어 이 저장소에서 대조할 수 없다 |
| R98 | 문서 링크 검사(`../../manual/markdown_link_check_guide.md`)가 이미 있다. 필요한 것은 **자동 PR 이 볼륨 캡을 넘기지 않는다**는 설계 | 캡과의 상호작용 미설계 |
| R99 | 사람/에이전트 분담선을 **실측으로** 그어야 한다 — 에이전트가 **틀린** 사례 목록이 근거다 | 사례 수집은 이 축이 시작했다(§3-1 의 중복 PR 2건, §3-2 의 볼륨 캡 위반, [README](README.md) §3-2 의 측정 절단) |
| R100 | "유효 PR"의 정의, "매뉴얼 없이"의 경계(`llms.txt` 는 매뉴얼인가 표면인가), **30분이라는 숫자의 근거**, 측정 방법 | 넷 다 미정 |

> [!NOTE]
> R100 의 "30분"은 #3907 의 목표 문장에서 왔고, **그 숫자의 산출 근거는 확인되지 않음**이다.
> 실험을 설계할 때 임의 숫자면 임의라고 적는다.

**R99 를 쓸 때 억지로 좋게 쓰지 않는다.** 분담선의 근거는 에이전트가 잘한 것뿐 아니라
**틀린 것**이다. 이 축이 실측으로 확보한 오류 목록만 해도 셋이다 — 같은 이슈에 중복
PR 2건, 사흘간 94건 개설·머지 0건, 볼륨 수치를 절단된 조회로 보고. 이 목록이 짧아지면
분담선을 다시 그을 근거가 생기고, 길어지면 그 자체가 판정이다.

## 6. 이 축의 문서 규율

`../agent_security/threat_model.md` 의 규율을 그대로 승계한다.

1. **모든 주장에 근거를 단다** — PR·이슈 번호, `파일:줄`, 또는 재현 명령과 그 출력.
2. **근거를 대지 못하는 항목은 "확인되지 않음"으로 적는다.** 추측을 사실처럼 적은
   운영 문서는 반년 뒤 거짓말이 된다.
3. **사건을 규칙보다 먼저 적는다.** 규칙만 남으면 왜 그런지 잊히고, 잊힌 규칙은
   비용으로만 보여서 다시 어겨진다(2026-04-23 → 2026-08-03 이 그 증명이다).
4. **개인 식별자·로컬 경로를 쓰지 않는다.** 저장소 루트는 `<저장소>` 로 적는다.
5. **날짜를 붙인 실측은 재현 명령을 함께 적는다.** 명령이 없으면 다음 사람은 그 숫자를
   갱신할 수 없고, 갱신되지 않는 숫자는 곧 틀린 숫자가 된다.
