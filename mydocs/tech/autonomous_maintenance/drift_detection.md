# 드리프트 자동 감지 → 이슈 자동 기안 (R95)

> 로드맵 [#3907](https://github.com/edwardkim/rhwp/issues/3907) J그룹 **R95** 의 설계 문서다.
> R95 의 등급은 `[가설]` 이다 — **구현이 없고, 착수 승인도 없다.**
> 이 문서는 "이렇게 하면 된다"를 말하지 않는다. **"이렇게 하려면 무엇이 필요한가"** 를 말한다.

## 0. 이 문서가 주장하는 것과 주장하지 않는 것

이 저장소의 서술 규약을 이 문서 자신에게도 적용한다. 아래 표가 그 선언이다.

| 절 | 등급 | 내용 |
|---|---|---|
| 1 | 정의 | 드리프트의 정의. 이 문서가 만든 용어 경계다 |
| 2 | **실측** | 이 저장소에서 실제로 난 드리프트 8종. 전부 2026-08-04 devel 워크트리와 GitHub API 로 재현했다 |
| 3 | **실측** | 이미 있는 자동화 전수. 파일 수·트리거·cron 을 직접 세었다 |

검증 전 구현 금지"다. 이 문서는 그 **설계 검증 자료**이며, 착수 판단은 사람이 한다.

## 1. 드리프트란 무엇인가

### 1.1 정의

> **드리프트** = 저장소 안의 **두 진술이 같은 사실을 다르게 말하는 상태**.
> 두 진술 모두 어느 시점에는 참이었고, 한쪽만 갱신되어 어긋났다.

이 정의에는 세 부분이 있고, 셋 다 필요하다.

1. **두 진술이 있다.** 한 곳에만 있는 사실은 드리프트가 될 수 없다. 드리프트는 항상 **쌍**이다.
2. **같은 사실을 가리킨다.** 서로 다른 것을 말하는 두 문장은 그냥 다른 문장이다.
3. **어긋나 있다.** 그리고 **어느 쪽이 옳은지는 감지기가 결정하지 않는다** — 감지기는 어긋남만
   보고한다. 이 구분이 6절 승인 게이트 논증의 뿌리다.

### 1.2 드리프트가 아닌 것

경계를 흐리면 감지기가 헛울린다. 다음은 드리프트가 아니다.

| 아닌 것 | 왜 아닌가 | 담당 |
|---|---|---|
| **버그** | 진술이 하나뿐이다. 코드가 의도대로 안 도는 것이지, 두 문장이 어긋난 게 아니다 | 테스트·CI |
| **미구현** | 계획과 현실의 차이는 정상이다. `[가설]` 항목이 구현 안 된 것은 드리프트가 아니라 **설계대로**다 | 로드맵 |
| **의도적 예외** | `capabilities` 가 MCP 도구를 갖지 않는 것은 사유와 함께 계약 테스트에 명시돼 있다 (`tests/cli_json_contract.rs`, `capabilities_mcp_covers_every_json_command`) | 허용목록 |
| **진행 중 작업** | 열린 PR 안의 미완성 상태 | 리뷰 |

세 번째 줄이 특히 중요하다. **의도적 예외를 드리프트로 신고하는 감지기는 곧 무시당한다.**
그래서 감지기는 예외 목록을 **자기 안에 베끼지 않고** 계약 테스트에서 읽어야 한다 —
`agent_preflight.py` 의 `load_allowlist()` 가 이미 그렇게 하고, 그 이유를 코드 주석에
적어 두었다("베낀 목록은 언젠가 원본과 어긋나고, 어긋나면 이 선검사가 실제 가드와 다른 말을 한다").

### 1.3 왜 별도의 이름이 필요한가

드리프트는 **어느 한 커밋도 잘못하지 않았는데 생긴다.** 커밋 A 가 코드를 6종으로 늘리고,
커밋 B 가 문서를 안 고쳤다면, A 도 B 도 각자의 리뷰를 통과한다. 어긋남은 **두 커밋 사이의
공백**에서 태어나므로, 어떤 단일 PR 의 리뷰로도 잡히지 않는다.

그래서 드리프트는 **상시 감시**의 대상이지 **PR 검사**의 대상이 아니다. 4절의 경계가 여기서 나온다.

## 2. 실측 드리프트 대장

전부 2026-08-04 에 `devel` 기준 워크트리와 GitHub API 로 직접 재현했다.

### D1. 자기서술 ↔ 실물 — 선언한 플래그·명령이 CLI 에 없다

**부류.** `capabilities` 가 선언한 것과 CLI 가 실제로 받는 것의 어긋남.

**현재 상태: 0건.** 이건 이미 막혀 있다.

```
$ py tools/agent_preflight.py --bin target/release/rhwp.exe
  통과   선언 flags 실재 (103개 플래그)
  통과   capabilities ↔ --help 상호 커버 (61개 명령)
  통과   --json 명령 ↔ MCP 도구 커버
```

**그러나 반쪽이다.** `check_declared_flags_real()` 은 "선언했는데 CLI 가 거부하는" 방향만 본다.
**반대 방향 — CLI 가 받는데 선언에 없는 플래그 — 은 검사하지 않는다.** #3884 G1 이 잡은
`bench`·`dump`·`diag` 의 미지 플래그 침묵 무시가 이 방향의 사고였고, 그 수정 PR
[#3897](https://github.com/edwardkim/rhwp/pull/3897) 은 2026-08-04 현재 **열려 있다**.

**왜 눈에 안 띄었나.** 선언→실물 방향은 에이전트가 호출하다 실패하므로 시끄럽다.
실물→선언 방향은 **아무도 안 부르므로 조용하다.**

### D2. 봉투 ↔ `recordFields` — #3882 T1 이 통과한 구멍

**부류.** 명령이 실제로 내보내는 JSON 키 집합과 `capabilities` 의 `recordFields` 선언의 어긋남.

**실측.** `recordFields` 를 검사하는 계약 테스트는 있지만 **명령별 개별 검사**다.

```
$ grep -rn "recordFields" tests/*.rs
tests/capabilities_schema_contract.rs:408
tests/digest_macro_contract.rs:196,200
tests/digest_v2_contract.rs:336,338,341
tests/envelope_integrity_contract.rs:142,144,150
tests/ir_schema_contract.rs:268
tests/render_diff_json_contract.rs:510,511,612,615,616
```

`digest`·`info`·`render-diff` 는 자기 필드를 지키지만, **전수 대조는 없다.** 그래서
snake_case 가 하나 섞여도 통과했다 — [#3882](https://github.com/edwardkim/rhwp/pull/3882) T1 이
그 사례다. 전수 대조를 본체로 승격하는 작업은 [#3903](https://github.com/edwardkim/rhwp/pull/3903)
인데, **이 PR 도 2026-08-04 현재 열려 있다.**

`render_diff_json_contract.rs:615` 는 이 부류의 **모범 형태**다.

```rust
assert_eq!(
    tool["outputFields"], entry["recordFields"],
    "MCP 출력 필드와 capabilities recordFields 가 어긋납니다"
);
```

두 선언을 직접 대조한다. 문제는 **이게 한 명령에만 있다**는 것이다.

**왜 눈에 안 띄었나.** 봉투 필드가 하나 빠져도 JSON 은 여전히 유효하다. 소비자가 그 필드를
읽을 때 `undefined` 가 되고, 정적 매핑 바인딩(파이썬 dataclass·TS 타입)에서는 **필드가 조용히
사라진다.** [#3886](https://github.com/edwardkim/rhwp/issues/3886) 의 "L1 의 구멍이 L3 를 막는다"가
정확히 이 경로다.

### D3. 문서 ↔ 코드 — 문서가 말하는 개수와 실물 개수

**실측.** 재현 가능하다.

```
$ grep -n "3종" mydocs/tech/agent_security/README.md
62:> **현재 `rhwp edit`의 하위 명령은 `fill-fields`·`replace-text`·`set-cell` 3종뿐이다**

$ ./target/release/rhwp.exe edit --help
오류: 알 수 없는 edit 하위 명령 - --help
사용법: rhwp edit <fill-fields|replace-text|set-cell|insert-image|redact|sanitize> ...
```

**문서 3종, 실물 6종.** `insert-image`·`redact`·`sanitize` 가 문서에 없다. 그중 `redact` 는
**개인정보 마스킹 명령**이다 — 보안 축 문서가 보안 명령을 빠뜨렸다.

이 드리프트는 #3886 이 이미 지적했다("보안 축 문서가 하루 만에 낡았다"). **지적된 지 하루가
지난 지금도 문서는 그대로다.** 이것 자체가 R95 의 존재 이유다: 사람이 알아채도 고쳐지지
않는다면, 알아채는 것만으로는 부족하다.

**왜 눈에 안 띄었나.** 링크 검사기는 이걸 못 잡는다. 링크는 멀쩡하다. 메타데이터 검사기도
못 잡는다. front matter 는 완전하다. **"3종"은 그냥 산문이다.**

**22행이 "머지된 PR" 근거를 갖지 못했다.** 그중 참조 PR 이 지금도 **열려 있는** 것이 6행이다.

### D6. 메타데이터 규약 ↔ 실물

**실측.** 검사기를 지금 돌리면 실패한다.


### D7. 바이너리 ↔ 소스 — 감지기 자신의 함정

**실측.** 이 문서를 쓰는 동안 실제로 걸렸다.

만약 R95 의 감지기가 이 바이너리를 물고 돌았다면 **"R31·R32·R33 이 실은 미구현"이라는 이슈
3건을 기안했을 것이다. 전부 오탐이다.** 7절이 이 함정을 다룬다.

### D8. 문서가 인용한 수치 ↔ 현재 수치

**실측.** #3886 이 정리한 표가 그대로 이 부류다.

| | #3719 스냅샷(08-01) | #3886 실측(08-03) | 이 문서 실측(08-04, 스테일 바이너리) |
|---|---:|---:|---:|

**이틀 만에 스냅샷이 낡았다.** 문제는 수치가 변한 게 아니라 **문서가 그 수치를 "현재"로
서술한다**는 것이다. `mydocs/tech/README.md` 의 `last_verified` 는 `2026-07-19` 인데, 그 사이
명령이 54→61 로 늘었다.

**보조 실측**: `mydocs/{manual,tech,troubleshootings}` 의 마크다운 475편 중 `last_verified` 가
2026-06 이전인 문서는 **0건**이다. 즉 이 저장소의 문제는 "아무도 안 본 낡은 문서"가 아니라
**"본 지 얼마 안 됐는데 그 사이 세상이 바뀐 문서"** 다. 감지 전략이 달라진다 —
날짜만으로는 못 잡는다. [자기 치유 문서](self_healing_docs.md) §3 이 이 갈래를 다룬다.

## 3. 이미 있는 자동화 — 전수

R95 를 설계하기 전에 **이미 도는 것**을 세어야 한다. 없는 것을 만들기 전에 있는 것을 알아야
겹치지 않는다.

### 3.1 GitHub Actions 워크플로 — 14개 (12개가 아니다)

`.github/workflows/*.yml` 파일 수 실측 = **14**.

| 파일 | 트리거 | 하는 일 | 드리프트 감지와의 관계 |
|---|---|---|---|
| `ci.yml` | push(main·devel·태그) / PR | 본체 CI. preflight 분류 → 샤드 테스트 → lint(fmt·clippy·WASM) → 프런트엔드 게이트 | **계약 테스트를 여기서 돌린다.** 드리프트 방지의 주력 |
| `build-nextest-archives.yml` | `workflow_call` | nextest 아카이브 빌드(빌더별 라벨) | 인프라 |
| `run-nextest-archives.yml` | `workflow_call` | 아카이브 실행 | 인프라 |
| `codeql.yml` | push·PR + **cron 매주 월 06:00 UTC** | 정적 보안 분석 | 코드 결함. 드리프트 아님 |
| `render-diff.yml` | PR(렌더 경로 변경 시) | 렌더 시각 회귀 diff | 픽셀 회귀 |
| `full-renderer-sweep.yml` | `workflow_dispatch` | 전 코퍼스 렌더 스윕 | 수동 |

### 3.4 `close-issues-on-devel-push.yml` — 이 저장소가 정의한 "착지"

이 워크플로는 D4 를 이해하는 열쇠다. 핵심 한 줄:

```js
if (pr.base.ref !== 'devel' || !pr.merged_at) {
  core.info(`Skip PR #${prNumber}: base=${pr.base.ref}, merged_at=${pr.merged_at}`);
  return texts;
}
```

**저장소의 자동화는 `merged_at != null` 을 착지의 정의로 쓴다.**

그런데 실측하면 그 정의가 이 저장소의 실제 착지 경로와 맞지 않는다.

```
$ gh pr view <n> --json state,mergedAt,mergeCommit
#3882 CLOSED  null  null
#3795 CLOSED  null  null
#3867 CLOSED  null  null
#3836 CLOSED  null  null
#3832 CLOSED  null  null
#3838 CLOSED  null  null
```

여섯 건 다 `mergedAt: null` 인데, **그 PR 들이 넣은 산출물은 devel 에 있다** —
`tools/agent_preflight.py`(#3795)가 워크트리에 존재하고, `explain`·`export-agent-manifest`
(#3832·#3843)가 `src/main.rs` 에 있다.

커밋 동일성도 없다.

```
$ gh api repos/edwardkim/rhwp/compare/devel...<PR head sha>
#3832 → diverged ahead_by=4  behind_by=199
#3882 → diverged ahead_by=1  behind_by=109
#3795 → diverged ahead_by=1  behind_by=312
```

`ahead_by > 0` 이므로 PR 의 커밋 자체는 devel 에 없다. 내용은 재적용됐고 SHA 는 달라졌다.

**결론(실측):** 이 저장소에서 **PR 상태는 착지의 신호가 아니다.** `merged_at` 도, 커밋 도달성도
쓸 수 없다. 유일하게 믿을 수 있는 신호는 **산출물 실재**다.

**확인되지 않음:** 왜 이 경로로 착지하는지(메인테이너의 로컬 적용 방식인지, 다른 규약인지)는
확인하지 못했다. R95·R94 설계는 **이유를 몰라도 성립해야 한다** — 그래서 산출물 기준을 쓴다.

### 3.5 이미 있는 드리프트 가드의 모범 — 생성 타입 최신 검사

`node-binding.yml` 머리말이 R95 가 따라야 할 형태를 이미 보여준다.

> 4. 생성 타입 최신 검사 — 스키마가 바뀌었는데 커밋된 타입이 옛것이면 실패시킨다.

이것이 **드리프트 감지의 정석**이다. 두 진술(`src/capabilities_schema.rs` ↔ 커밋된 `.d.ts`)을
잡고, 한쪽에서 다른 쪽을 **재생성해서 비교**한다. 재생성 가능한 쌍은 이렇게 하면 오탐이 0이다.

R95 의 감지 대상 대부분은 **재생성이 불가능한 쌍**이다 — 산문 문서를 코드에서 재생성할 수는
없다. 그래서 5절의 설계가 필요하다.

## 4. `agent_preflight.py` 와의 경계

**요청받은 핵심 설계 판단이다.** 두 도구가 겹치면 하나는 죽는다.

### 4.1 preflight 가 지금 검사하는 것 — 실측 10종

```
$ py tools/agent_preflight.py --bin target/release/rhwp.exe
```

### 4.2 두 도구는 **시간축이 다르다**

| | `agent_preflight.py` | R95 드리프트 감지 |
|---|---|---|
| **언제** | 사람/에이전트가 커밋·푸시 **직전** | 상시(주기 실행) |
| **무엇을 본다** | **내가 방금 바꾼 것** | **저장소 전체의 현재 상태** |
| **입력 범위** | `git diff` 로 좁힌다 | 전수 |
| **실패의 뜻** | "이 커밋을 내지 마라" | "여기 어긋난 게 있다" |
| **누가 받는다** | 지금 작업 중인 사람 | 나중에 볼 사람(이슈) |
| **비용 제약** | **1초**(그래서 `--static-only` 가 있다) | 몇 분 써도 된다 |
| **오탐의 대가** | 작업을 막는다 → 즉시 무시당한다 | 이슈 소음 → 서서히 무시당한다 |

**시간축이 다르므로 같은 검사를 양쪽에 둬도 중복이 아니다.** 다만 **구현을 두 벌 두면**
그 둘이 서로 드리프트한다(1.2 의 교훈). 그래서 경계는 "검사 항목"이 아니라 **"코드 소유권"**
으로 그어야 한다.

### 4.3 preflight 가 **구조적으로** 못 잡는 것

이게 R95 의 고유 영역이다.

1. **아무도 커밋하지 않을 때 자라는 어긋남.** preflight 는 커밋이 있어야 돈다. D3(문서 3종 vs
   실물 6종)는 `edit` 하위를 늘린 커밋에서 태어났지만, 그 커밋의 preflight 는 **문서를 보지
   않는다** — 검사 5~9 는 바이너리만 본다.
2. **`git diff` 밖의 것.** preflight 는 변경 파일만 훑는다(검사 2·3·4). 안 바뀐 문서가 낡는
   것은 정의상 범위 밖이다.
3. **저장소 밖의 사실.** D4 는 GitHub API 를 물어봐야 안다. preflight 는 네트워크를 안 쓴다
   (그게 1초 예산의 근거다).
4. **자기 자신의 입력이 낡은 것.** D7. preflight 는 주어진 바이너리를 **신뢰**한다.
   실측대로 스테일 바이너리로 8검사 전부 통과했다.

### 4.4 경계 규칙 — 제안

> **P1. 검사 로직의 소유는 한 곳이다.**
> 드리프트 판정 함수는 `tools/agent_preflight.py` 가 소유하고, R95 감지기는 **그것을 import
> 해서 전수 모드로 부른다.** 반대는 안 된다 — preflight 는 의존성 0이어야 하고 1초 안에 끝나야
> 한다. 두 벌 구현은 금지다(1.2·`load_allowlist()` 의 교훈).
>
> **P2. 시간축으로 나눈다.**
> - preflight: **변경분** · **로컬** · **차단**
> - R95: **전수** · **네트워크 허용** · **비차단(보고)**
>
> **P3. R95 는 preflight 를 차단 게이트로 쓰지 않는다.**
> R95 가 실패했다고 PR 이 막히면 안 된다. 드리프트는 누가 지금 만든 게 아니다 — 지금
> 커밋하는 사람에게 남의 빚을 물리면 그 사람은 감지기를 끈다.
>
> **P4. 새 검사는 preflight 에 먼저 넣고, 전수가 필요할 때만 R95 로 올린다.**
> 순서를 거꾸로 하면 커밋 전에 못 잡는 검사가 늘어난다.
>
> **P5. R95 의 검사 대상 중 preflight 에 이미 있는 것(5~9)은 R95 가 다시 구현하지 않는다.**
> R95 는 그 다섯을 **주기적으로 부르는 쪽**만 담당한다.

## 5. 감지기 설계 — 드리프트별

각 항목에 **① 기계 감지 ② 오탐 위험 ③ 감지 후 행동** 셋을 붙인다.
③ 의 값은 `자동수정` / `이슈기안` / `보고만` 셋 중 하나이고, 그 판단 근거는 6절이다.

### D1. 자기서술 ↔ 실물 (양방향)

**① 감지.** 선언→실물은 preflight 검사 9 재사용. 실물→선언은 새로 필요하다:
`--help` 출력과 각 하위 명령의 usage 문자열에서 플래그 토큰을 뽑아 `capabilities` 의
`flags` 배열과 대칭차를 낸다. usage 문자열은 이미 기계 판독 가능한 형태다 —
`rhwp edit` 이 `<fill-fields|replace-text|set-cell|insert-image|redact|sanitize>` 를 내뱉는다.

**② 오탐.** (a) 숨긴 명령·플래그 — `HELP_HIDDEN` 허용목록을 계약 테스트에서 읽어야 한다
(preflight 의 `load_allowlist()` 그대로). (b) 진단 명령 부류 — R8(#3884 G2)이 "밖" 부류를
정의하기 전에는 `dump-*`·`hwp5-*` 계열을 어떻게 셀지 답이 없다. **R8 미정 상태에서 이
감지기를 켜면 40행 가까이 헛울린다.** 그러므로 **R8 이 선행 조건**이다.

**③ 행동.** `이슈기안`. 어느 쪽이 옳은지(선언을 지울지 CLI 를 고칠지)는 사람 판단이다.

### D2. 봉투 ↔ `recordFields`

**① 감지.** 대표 문서로 각 `--json` 명령을 1회 실행 → 봉투의 최상위 키 집합 수집 →
`capabilities` 의 `recordFields` 와 대칭차. `render_diff_json_contract.rs:615` 의 형태를
31개 `--json` 명령 전체로 넓힌 것이다.

**② 오탐.** **높다.** (a) **조건부 필드** — `edit` 의 `recordFields` 34개는 하위 명령별로
쓰이는 것이 다르다. `fill-fields` 실행 봉투에 `redactedCount` 가 없는 건 정상이다.
(b) **입력 의존 필드** — `warnings` 는 경고가 있어야 나온다. (c) **대표 문서 선택** —
어떤 샘플을 쓰냐로 결과가 바뀐다.

→ **단방향만 켠다.** "봉투에 있는데 `recordFields` 에 없다"만 실패로 본다. 반대 방향
("선언했는데 이번 실행에 안 나왔다")은 정상 케이스가 너무 많다.

**③ 행동.** `이슈기안`. 다만 #3903 이 착지하면 이 감지는 **계약 테스트로 내려가야 한다** —
CI 가 매 PR 마다 잡는 게 주기 실행보다 낫다. R95 는 #3903 착지 전까지의 **임시 그물**이다.

### D3. 문서 ↔ 코드 (개수·목록 주장)

**이 부류가 가장 어렵고 가장 가치가 크다.** 링크 검사로도 메타데이터 검사로도 안 잡힌다.

**① 감지 — 세 가지 후보.**

**(가) 산문 패턴 매칭.** `N종`·`N개`·`N가지` 를 정규식으로 찾아 근처 코드 심볼과 대조.
→ **버린다.** "3종"이 무엇의 3종인지 기계가 모른다. 오탐이 압도적이다.

**(나) 백틱 목록 대조.** 문서 안의 백틱 식별자를 뽑아 CLI 표면 사전(61명령 · 103플래그 ·
하위 명령 목록)과 대조. 문서가 존재하지 않는 명령을 말하면 **잡힌다.** 하지만 D3 은
**빠뜨린** 사고다 — 없는 걸 말한 게 아니라 있는 걸 안 말했다. **(나)는 D3 을 못 잡는다.**

**(다) 문서에 기계 검증 가능한 주장을 심는다.** 산문 옆에 검증 지시를 놓는다.

````markdown
<!-- verify: cli-subcommands edit == fill-fields,replace-text,set-cell,insert-image,redact,sanitize -->
> 현재 `rhwp edit` 의 하위 명령은 6종이다.
````

감지기는 주석만 읽고, `rhwp edit` 의 usage 를 파싱해 목록을 비교한다. 산문은 읽지 않는다.

**(다)를 제안한다.** 근거는 **이 저장소에 이미 선례가 있다**는 것이다 —
`scripts/check_markdown_links.py` 는 `mydocs/manual/agent_capability_registry.md` 의 표를
파싱해 ID 형식(`CAP-<N>`/`LEGACY-<9자리>`)·중복·진입점 실파일 해석을 검증한다
(`collect_capability_registry_errors()`, `check_markdown_links.py:382`). **구조화된 주장은
이미 기계가 검증하고 있다.** (다)는 그 범위를 표에서 주석으로 넓히는 것뿐이다.

**② 오탐.** (다)의 오탐은 **원리적으로 낮다** — 검증 지시가 명시적이기 때문이다. 대신
**미탐이 크다**: 주석이 없는 문서는 안 본다. 그래서 (다)는 **커버리지 지표**가 필요하다
(몇 개 문서가 검증 주장을 갖는가). 상세는 [자기 치유 문서](self_healing_docs.md) §3.

**③ 행동.** 주장 형태에 따라 갈린다 — 6.4 판정표 참조. `== 목록` 형 불일치는 조건부
`자동수정` 후보, 그 외는 `이슈기안`.

### D4. 로드맵 ↔ 착지

**① 감지.** #3907 본문 파싱 → `[완료]` 행의 **완료 증거** 검증. 증거를 무엇으로 볼지가
설계의 전부이며, 3.4 의 실측 때문에 PR 상태는 쓸 수 없다.
정의와 검증 절차는 [진행률 기계 산출](progress_machine_readable.md) 이 canonical 이다.

**② 오탐.** 지금 형식 그대로는 **22/28 이 실패로 뜬다.** 그중 몇이 진짜인지는 증거 정의를
바꿔야 갈린다. **정의를 고치기 전에 감지기를 켜면 안 된다.**

**③ 행동.** `보고만`(대시보드). 로드맵 본문을 기계가 고치는 것은 금지 — 6.3 참조.

### D5. 문서 ↔ 권위표

**① 감지.** `mydocs/tech/` 하위 디렉터리와 `mydocs/tech/README.md` 의 링크 집합을 대조.
2절의 실측이 그 자체로 감지기 프로토타입이다(디렉터리 10개, 미등재 3개).

**② 오탐.** **낮다.** 다만 (a) 의도적 비등재(`archive/` 같은 보존 영역)와 (b) 신규 축의
등재 PR 이 아직 안 났을 때의 시차를 구분해야 한다. → 유예 기간(예: 생성 후 7일)을 둔다.

**③ 행동.** `이슈기안`. 표의 어느 행에 어떤 문구로 넣을지는 사람 판단이다.

### D6. 메타데이터 규약

**① 감지.** `scripts/check_document_metadata.py` 를 그대로 부른다. **새로 만들 것이 없다.**

**② 오탐.** 없다. 결정론적이다.

**③ 행동.** 갈린다. `last_verified` 형식 오류처럼 **정답이 하나뿐인 것**은 `자동수정` 후보.
`kind: contract` 처럼 **규약을 넓힐지 문서를 고칠지 판단이 필요한 것**은 `이슈기안`.

### D7. 감지기 입력의 최신성

**① 감지.** 감지기 시작 시 자기 입력을 먼저 검증한다. 7.3 의 계약 참조.

**② 오탐.** 해당 없음(자기 진단).

**③ 행동.** **감지기를 중단한다.** 이슈를 기안하지 않는다. 낡은 입력으로 낸 결론은
전부 무효다.

### D8. 문서의 수치 주장

**① 감지.** D3 (다)의 특수형. `<!-- verify: count commands == 61 -->` 처럼 숫자 주장을 심는다.

**② 오탐.** 낮음. 단, **셈의 정의**를 문서와 감지기가 공유해야 한다 — "명령 61개"가 숨김
명령을 포함하는지 같은 것. 정의가 다르면 영원히 어긋난다. → 셈 함수는 감지기가 소유하고,
문서는 그 함수 이름을 지시한다(숫자를 세는 법을 문서에 적지 않는다).

**③ 행동.** 숫자 하나 갱신은 `자동수정` 후보(6.2 조건 충족 시).

## 6. 자동 수정인가, 이슈 기안인가

R95 는 제목부터 **"이슈 자동 기안(사람 승인 게이트)"** 이라고 못박는다. 왜 그런지 논증한다.

### 6.1 게이트가 필요한 세 가지 이유

**(1) 감지기는 어느 쪽이 옳은지 모른다.**

1.1 의 정의로 돌아가자. 드리프트는 **두 진술의 어긋남**이다. 감지기가 아는 것은 "다르다"
뿐이다. D3 을 보자 — 문서 3종, 실물 6종. 자동 수정기는 문서를 6종으로 고칠 것이다.
**그런데 그게 옳은 수정인가?** `sanitize` 가 실은 실험적 명령이라 문서에서 일부러 뺐다면?
감지기는 그 의도를 모른다. 실물이 항상 옳다는 가정은 **"코드가 곧 사양"** 이라는
가정이고, 이 저장소는 그 반대를 택했다 — `hwp_spec_errata.md` 가 그 증거다.

**(2) 자동 수정은 드리프트를 지우면서 그 흔적도 지운다.**

D3 의 진짜 정보는 "문서가 틀렸다"가 아니라 **"보안 축 문서가 보안 명령 `redact` 를 몰랐다"**
이다. 자동 PR 이 조용히 숫자를 3→6 으로 바꾸면 그 정보가 사라진다. #3886 은 이 드리프트를
**"보안 축 문서가 하루 만에 낡았다"** 라는 판단으로 기록했고, 그 판단이 R95 를 낳았다.
**증거를 지우는 자동화는 다음 R95 를 못 낳는다.**

**(3) 이 저장소의 병목은 감지가 아니라 큐다.**

메모리에 기록된 사고: 2026-07-22 열린 PR 113건 폭주 후 메인테이너가 30건을 일괄 close 하고
리베이스+reopen 을 요구했다. #3719 §7·#3796 §6 이 **"열린 PR 10건 내외"** 를 못박은 것도
같은 맥락이고, #3907 운영 규칙 2 가 **"이 지도는 큐를 늘리는 면허가 아니다"** 라고 다시 못박는다.

즉 **PR 을 자동으로 만드는 것은 이 저장소에서 비용이지 이익이 아니다.** 드리프트 12건을
감지해 PR 12건을 열면 캡을 그날로 깬다. `pr_triage.sh` 가 존재하는 이유가 바로 그 부담이다.

이 세 번째 논거가 가장 무겁다. 앞의 둘은 "자동 수정을 정교하게 하면" 완화되지만,
**세 번째는 자동 수정이 정교할수록 악화된다.**

### 6.2 그래도 자동 수정이 안전한 경우 — 조건 셋을 **동시에** 충족할 때

> **C1. 정답이 유일하고 기계가 계산할 수 있다.**
> `last_verified: 2026-8-4` → `2026-08-04`. 판단이 없다.
>
> **C2. 되돌리기가 무료다.**
> 한 줄 diff. 잘못돼도 revert 비용이 리뷰 비용보다 작다.
>
> **C3. 수정이 사실을 만들지 않고 표기만 고친다.**
> 형식·링크·경로처럼 **의미를 바꾸지 않는** 수정.

셋 다 만족하는 실제 예:

- `last_verified` 날짜 **형식** 오류(D6 의 세 번째 유형)
- 파일이 옮겨져 깨진 상대 링크에서 redirect stub 의 `canonical:` 을 따라간 경로로 치환
  (`check_markdown_links.py` 가 이미 redirect 매핑을 안다)
- 코드펜스 안 명령줄의 **경로만** 바뀐 경우

셋 중 **하나라도** 안 되면 `이슈기안`이다.

### 6.3 자동 수정이 명백히 위험한 경우

| 대상 | 왜 위험한가 |
|---|---|
| **로드맵 이슈 본문**(D4) | 진행률은 **평가**다. 기계가 `[완료]`↔`[이슈]` 를 뒤집으면 사람의 판단 기록을 덮어쓴다. #3907 운영 규칙 1 이 "완료 표기는 머지 링크와 함께만"이라고 한 것은 **사람이 링크를 붙이라**는 뜻이다 |
| **보안 문서**(D3 의 `agent_security/`) | 문서가 실물보다 **좁게** 쓰인 게 의도일 수 있다. 자동으로 넓히면 검증 안 된 명령을 보안 계약에 등재한다 |
| **계약 테스트 허용목록** | 허용목록에 항목을 자동 추가하면 **가드를 자동으로 약화**시킨다. 감지기가 자기를 무력화하는 경로다 |
| **`capabilities` 선언** | 선언은 외부 계약이다. 스키마 버전 규약(#3808·#3691)의 대상이므로 minor/major 판단이 필요하다 |
| **수치 주장 중 "몇 개인가"가 논쟁적인 것**(D8) | 5절 D8 ②의 셈 정의 문제 |

### 6.4 판정표

| 드리프트 | C1 유일 | C2 무료 | C3 표기만 | 판정 |
|---|:---:|:---:|:---:|---|
| D6 `last_verified` 형식 | ○ | ○ | ○ | **자동수정** |
| D6 `canonical` 누락 | ✕(무엇을 넣을지 판단) | ○ | ✕ | 이슈기안 |
| D6 미허용 `kind` | ✕(규약 vs 문서) | ○ | ✕ | 이슈기안 |
| 깨진 링크(redirect 존재) | ○ | ○ | ○ | **자동수정** |
| 깨진 링크(대상 소실) | ✕ | ○ | ✕ | 이슈기안 |
| D8 숫자 주장(셈 함수 지정) | ○ | ○ | ○ | **자동수정** |
| D3 목록 주장 `== 목록` | ○ | ○ | ✕(의미가 바뀐다) | 이슈기안 |
| D5 권위표 미등재 | ✕ | ○ | ✕ | 이슈기안 |
| D1 자기서술 어긋남 | ✕ | ✕ | ✕ | 이슈기안 |
| D2 봉투 어긋남 | ✕ | ✕ | ✕ | 이슈기안 |
| D4 로드맵 | ✕ | ✕ | ✕ | **보고만** |

**자동수정 3종은 전부 형식이다.** 사실을 만드는 자동 수정은 하나도 없다. 이것이
"승인 게이트"의 실질적 의미다.

### 6.5 게이트 통과 뒤의 형태 — 제안

자동 수정 3종도 **바로 devel 에 푸시하지 않는다.** 형태는 다음 중 하나여야 한다.

- **초안 PR(draft)** 로 열고, 라벨 `autofix/format` 을 단다. 캡 계산에서 draft 를 뺄지는
  사람이 정한다(확인되지 않음 — #3719 §7 의 "10건 내외"가 draft 를 포함하는지 불명).
- 또는 **주 1회 묶음 PR** 로 형식 수정을 합친다. 12건이 PR 12개가 아니라 1개가 된다.

후자를 제안한다. 3.1 에서 본 대로 이 저장소의 상시 자동화(`cache-generation-sweep`)도
**"매일 몰아서 정리"** 형태다. 같은 리듬을 따르는 것이 운영 부담이 적다.

## 7. 감지기 자신의 신뢰성

### 7.1 헛울리는 검사기는 없느니만 못하다

이 문장은 이 저장소가 이미 코드 주석으로 적어 둔 원칙이다
(`agent_preflight.py`, `load_allowlist()` docstring):

> 헛울리는 검사기는 곧 무시당하고, 무시당하는 검사기는 없느니만 못하다.

R95 는 **이슈를 만든다.** 헛울리면 사람이 이슈를 닫는 노동이 생긴다. preflight 의
오탐보다 비싸다. 그래서 R95 의 기본값은 **보수적**이어야 한다 — 애매하면 침묵.

### 7.2 스테일 입력 함정 — 실측

D7 이 그것이다. 다시 강조할 값어치가 있다:

- preflight 는 **2026-08-03 빌드 바이너리로 8검사 전부 통과**했다.
- 같은 시점 `src/main.rs` 에는 그 바이너리가 모르는 명령 2개(`explain`·`export-agent-manifest`)와
  플래그 1개(`capabilities --search`)가 있었다.

**preflight 는 "바이너리가 자기 자신과 일관된가"를 검사한다.** 자기 일관성은 낡아도 유지된다.
R95 가 같은 입력으로 돈다면 R31·R32·R33 을 "미구현"으로 기안했을 것이다 — 세 건 모두 오탐.

### 7.3 감지기의 자기 진단 계약 — 제안

> **S1. 입력 신선도를 먼저 검사하고, 실패하면 **아무것도 기안하지 않고** 종료한다.**
> 최소 조건: 바이너리 mtime 이 `src/**` 최신 mtime 보다 새롭다. 더 강한 조건:
> `rhwp --version` 의 커밋 해시가 `HEAD` 와 같다(**현재 `rhwp --version` 이 커밋 해시를
> 내는지 확인되지 않음** — 실측 출력은 `rhwp v0.8.2` 뿐이다. 필요하면 선행 작업이다).
>
> **S2. 검사 불능과 통과를 절대 섞지 않는다.**
> preflight 가 `rustfmt` 에서 배운 교훈이다 — "실패를 통과로 오독한 사고가 두 번 있었다"
> (`check_fmt()` docstring). R95 는 `건너뜀` 을 별도 상태로 보고하고, 건너뛴 검사가 있으면
> 리포트 머리에 그 수를 적는다.
>
> **S3. 감지기의 감지 근거를 이슈 본문에 그대로 싣는다.**
> "문서가 3종이라 함 / 실물 6종" 이 아니라 **재현 명령과 그 출력**을 싣는다.
> 사람이 5초 안에 오탐 여부를 판정할 수 있어야 한다.
>
> **S4. 감지기는 자기 오탐률을 기록한다.**
> 기안한 이슈 중 `invalid`·`wontfix` 로 닫힌 비율. **이 비율이 임계를 넘으면 감지기를 끈다.**
> 임계값은 확인되지 않음 — 운영 데이터가 있어야 정한다.

## 8. 운영 설계 — 제안

### 8.1 실행 주기

| 감지 | 주기 | 근거 |
|---|---|---|
| D6 메타데이터 · D5 권위표 · 링크 | **문서 변경 PR 마다** | 가볍다(실측 481문서 수 초). 3.3 의 덩어리를 여기서 가른다 |
| D1·D2 표면 드리프트 | **devel push 마다**(빌드가 이미 있을 때) | 바이너리가 신선하다 |
| D3·D8 문서↔코드 주장 | **주 1회** | 주장 주석이 붙은 문서만 보므로 싸다 |
| D4 로드맵 | **주 1회** | 네트워크 왕복 100회+ |

**3.3 의 `paths-ignore` 를 건드리는 방법**: `ci.yml` 을 고치지 말고 **문서 전용 워크플로를
새로 만든다.** 기존 CI 의 트리거를 넓히면 무거운 잡이 딸려 온다. (확인되지 않음: 메인테이너가
새 워크플로 추가를 선호하는지 기존 잡 확장을 선호하는지.)

### 8.2 볼륨 캡 — 강제여야 한다

R91(autofix 봇 상시화)이 **"볼륨 캡 자동 준수"** 를 등급 `[실측]` 로 달고 있다. R95 도 같은
제약을 받는다.

> **V1. 한 주기에 새로 여는 이슈 상한 = 3.**
> **V2. 열린 자동 기안 이슈가 5건을 넘으면 새로 열지 않는다.** 리포트만 남긴다.
> **V3. 자동 수정 PR 은 묶음 1건.**(6.5)
> **V4. 상한에 걸려 못 낸 것은 버리지 않고 다음 주기 큐에 남긴다.** 우선순위는
> "새로 생긴 것" > "오래된 것" — 새 드리프트는 원인 커밋을 아직 찾을 수 있다.

### 8.3 중복 기안 방지

같은 드리프트로 매주 이슈가 열리면 감지기는 그날로 끝난다.

> **U1. 드리프트마다 안정 키를 만든다.** 예: `drift:D3:mydocs/tech/agent_security/README.md:edit-subcommands`.
> **U2. 이슈 본문에 그 키를 `<!-- drift-key: ... -->` 로 심는다.**
> **U3. 기안 전 열린·닫힌 이슈를 그 키로 검색한다.** 있으면 새로 열지 않는다.
> **U4. 닫힌 이슈의 키가 다시 감지되면** 새 이슈가 아니라 **재발**로 보고한다 —
> 재발은 그 자체가 정보다(가드가 없다는 뜻).

`close-issues-on-devel-push.yml` 의 `closingIssueRef` 정규식이 보여주듯 이 저장소는 이미
이슈 참조를 기계 파싱한다. U2 의 주석 키는 그 관행의 연장이다.

### 8.4 기안 이슈 본문 형식 — 제안

```markdown
<!-- drift-key: D3:mydocs/tech/agent_security/README.md:edit-subcommands -->

## 무엇이 어긋났나

- 문서: `mydocs/tech/agent_security/README.md:62` — "`rhwp edit` 의 하위 명령은 … 3종뿐이다"
- 실물: 6종 (`fill-fields`·`replace-text`·`set-cell`·`insert-image`·`redact`·`sanitize`)

## 재현

    $ ./target/release/rhwp edit --help
    사용법: rhwp edit <fill-fields|replace-text|set-cell|insert-image|redact|sanitize> …

## 감지기가 판단하지 않은 것

**어느 쪽이 옳은지.** 문서를 6종으로 고칠 수도, 세 명령이 보안 계약에서 의도적으로
제외됐다면 그 사유를 문서에 적을 수도 있다. 판단은 사람이 한다.

## 감지 근거

- 감지기: `drift/doc_claims`  · 주기 실행 2026-08-11
- 입력 신선도: 바이너리 `<sha>` == HEAD `<sha>` ✓
```

**"감지기가 판단하지 않은 것" 절이 핵심이다.** 이 절이 있으면 이슈를 받는 사람이 자동
기안임을 알고, 기계가 결론을 내지 않았음을 안다.

## 9. 단계적 도입안 — 제안

R95 를 한 번에 켜지 않는다. 각 단계는 **앞 단계의 오탐률이 확인된 뒤**에만 간다.

| 단계 | 범위 | 선행 조건 | 산출 |
|---|---|---|---|
| **0** | 이 문서 + [진행률](progress_machine_readable.md) + [자기 치유](self_healing_docs.md) | — | 설계 검증 자료 |
| **1** | D6·링크·D5 를 **문서 변경 PR 게이트**로 | 없음(검사기 3종 이미 있음) | 3.3 의 구멍이 닫힌다 |
| **2** | D4 **보고만** — 대시보드 1장 | 완료 정의 확정(진행률 문서 §2) | #3907 의 22행 오탐/실탐 판별 |
| **3** | D3·D8 주장 주석 — **주장 심기부터** | 주석 문법 확정 | 커버리지 지표 |
| **4** | D1·D2 상시화 | **R8 판정**(진단 명령 부류) · #3903 착지 | 표면 상시 그물 |
| **5** | 자동 수정 3종 묶음 PR | 1~4 의 오탐률 실측 | R96(야간 정비)의 재료 |

**단계 4 는 R8 에 막혀 있다.** 이건 결함이 아니라 **의존성**이다 — #3907 운영 규칙 3 이
말한 "단계 번호는 의존성 순서지 일정이 아니다"가 그대로 적용된다.

## 10. 확인되지 않음 / 미해결

정확히 적는다. 아래는 **모른다**.

1. **메인테이너의 착지 경로.** 3.4 에서 PR 이 `mergedAt: null` 인 채 산출물만 devel 에 있는
   것을 실측했지만, **왜 그런지는 모른다.** R94·R95 설계는 이유를 몰라도 성립하도록 짰지만,
   이유를 알면 더 단순해질 수 있다.
2. **`rhwp --version` 이 커밋 해시를 내는가.** 실측 출력은 `rhwp v0.8.2` 뿐이었다.
   7.3 S1 의 강한 조건은 이것에 달려 있다.
3. **자동 기안 이슈가 열린 PR 캡에 포함되는가.** #3719 §7 의 "10건 내외"는 PR 기준이고
   이슈는 언급이 없다. 8.2 V2 의 상한 5는 **임의로 정한 값**이다.
4. **오탐률 임계.** 7.3 S4 의 "감지기를 끄는" 기준값을 정할 데이터가 없다.
5. **주장 주석 문법.** 5절 D3 (다)의 `<!-- verify: ... -->` 는 **이 문서의 제안**이며
   합의된 것이 아니다. 문법 확정은 [자기 치유 문서](self_healing_docs.md) 와 함께 해야 한다.
6. **워크플로 추가 vs 기존 잡 확장.** 8.1 참조.
7. **D2 대표 문서 선택 규약.** 어떤 샘플로 봉투를 뽑을지 정해야 결정론이 된다.
   `samples/` 의 어느 문서가 각 명령의 대표인지 매핑이 없다.
8. **R8 의 판정.** 진단 명령을 자기서술에 등재할지 "밖" 부류로 정의할지가 안 정해졌고,
   그것이 D1 전수 감지의 오탐률을 좌우한다.
