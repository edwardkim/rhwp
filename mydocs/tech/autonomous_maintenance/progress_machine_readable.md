# 진행률 기계 산출 — 등급 태그 파싱에서 대시보드까지 (R94)

> 로드맵 [#3907](https://github.com/edwardkim/rhwp/issues/3907) J그룹 **R94** 의 설계 문서다.
> R94 의 등급은 `[가설]` 이다 — **구현이 없다.**
> 이 문서는 "이렇게 하면 된다"가 아니라 **"이렇게 하려면 무엇이 필요한가"** 를 적는다.

## 0. 이 문서의 등급 선언

| 절 | 등급 | 내용 |
|---|---|---|
| 1 | **실측** | 문제의 출발점. 세 출처가 다른 값을 말한 이력과 지금 #3907 안의 재발 |
| 2 | **실측** | 현재 형식이 파싱 가능한지 **직접 파서를 써서 돌린 결과** |

| 4 | **제안** | 증거 문법. 합의된 것이 아니다 |

## 1. 문제의 출발점 — 진행률이 세 곳에서 다른 값을 말한다

### 1.1 #3886 의 지적

[#3886](https://github.com/edwardkim/rhwp/issues/3886) 이 D3 으로 정리한 문장 그대로다.

> **"진행률의 유일 기준"이 셋** — #3608 체크박스(비관) vs #3719 §8 ✅(낙관) vs 실측.
> M2 는 참인데 M4 는 거짓이다

그리고 그 옆에 더 무거운 한 줄이 있다.

> **열린 PR 을 "착지"로 계산** — #3869 §0(하필 "과장하지 않기 위해" 절)·#3828·#3608
> **세 코멘트에서 반복**됐다. #3719 §2 가 금지한 바로 그 합산이다.

**세 코멘트에서 반복됐다**는 부분이 핵심이다. 한 번의 실수가 아니라 **형식이 유도하는 오류**다.
사람이 손으로 체크박스를 칠 때, "PR 을 냈다"와 "착지했다"를 가르는 것은 오직 기억뿐이다.

### 1.2 같은 오류가 #3907 안에서 재발했다 — 실측

2026-08-04 에 #3907 본문을 파싱해 `[완료]` 28행의 참조를 전부 GitHub API 로 조회했다.

| 행 | 지도의 주장 | 참조 상태(2026-08-04) |
|---|---|---|
| R4 | `[완료]` bench·dump·diag 미지 플래그 침묵 무시 제거 — #3884→#3897 | #3884 issue **open** · #3897 PR **open** |
| R5 | `[완료]` 표지 누락 봉투 5건 봉합 — #3885→#3903 | #3885 issue **open** · #3903 PR **open** |
| R6 | `[완료]` recordFields↔실물 전수 대조 본체 승격 — #3903 | #3903 PR **open** |
| R32 | `[완료]` export-agent-manifest + planSchema 접합 — #3843·#3808 | #3808 PR **open** |
| R34 | `[완료]` 레시피 1~6 + 3(마스킹) — #3835·#3898 | #3898 PR **open** |
| R81 | `[완료]` planSchema 공개 계약 — #3808 | #3808 PR **open** |

**#3886 이 지적한 그 오류가, #3886 을 읽고 만든 지도 안에서 여섯 번 났다.**

이것은 사람의 부주의가 아니다. **지도를 쓰는 시점과 PR 이 착지하는 시점이 다르고, 그
시차를 기억으로 메우게 하는 형식**이 문제다. 사람이 더 조심해서 해결될 문제였다면
#3886 을 쓴 사람이 다음 날 같은 실수를 하지 않았을 것이다.

### 1.3 그래서 R94 가 필요하다

R94 의 목적은 **진행률을 더 정확히 세는 것이 아니다.** 목적은 **틀린 진행률을 사람이
쓸 수 없게 만드는 것**이다. 즉 산출이 아니라 **검증**이 본질이다.

## 2. 지금 형식이 파싱 가능한가 — 실측

**추측하지 않고 파서를 써서 돌렸다.**

### 2.1 파서

```python
ROW = re.compile(r"^\|\s*(R\d+)\s*\|\s*\[([^\]]+)\]\s*\|\s*(.*?)\s*\|\s*$")
ISSUE = re.compile(r"#(\d+)")
```

`gh issue view 3907 --json body -q .body` 로 받은 본문(168줄)에 그대로 적용했다.

### 2.2 결과 — **파싱된다**

```
파싱된 행: 100
R 번호 범위: 1 ~ 100 | 결번: []
중복: []
등급 분포: {'완료': 28, '이슈': 8, '가설': 50, '문서': 7, '실측': 7}
참조 없는 행: 49건 (R9 R10 R19 R20 R25 R26 R27 R28 R29 R30 R39 R40 …)
```

| 판정 | 결과 |
|---|---|
| 100행 전부 인식 | **○** |
| R1~R100 결번 | **0** |
| 중복 R 번호 | **0** |
| 등급 태그 추출 | **○** (5종) |
| 이슈·PR 참조 추출 | **○** (51행에서) |

**결론: 현재 형식은 이미 파싱 가능하다.** R94 의 어려움은 파싱이 아니다.

### 2.3 그런데 등급 합계가 헤더와 어떻게 맞는지는 **문서에 없다**

헤더는 이렇게 말한다.

> 현재 위치: **100단계 중 완료·운영 35 / 진행·추적 15 / 가설 50.**

파싱 결과와 맞춰 보면:

```
완료 28 + 실측  7 = 35   → "완료·운영"
이슈  8 + 문서  7 = 15   → "진행·추적"
가설 50           = 50   → "가설"
```

**숫자는 맞다.** 하지만 **이 묶음 규칙이 어디에도 적혀 있지 않다.** 헤더의 증거 등급 설명은
5종을 개별로만 정의한다.

> 증거 등급: `[완료]` 머지 실적 / `[실측]` 측정 존재 / `[문서]` 설계 문서 존재 /
> `[이슈]` 추적 중 / `[가설]` 근거 확보가 선행 조건.

즉 **집계 축(3종)과 등급 축(5종)이 따로 놀고, 둘을 잇는 사상(寫像)은 사람 머릿속에만 있다.**
이 상태에서 누가 등급 하나를 고치면 헤더의 3개 숫자를 손으로 다시 계산해야 하고,
그 계산은 검증되지 않는다. **이것 자체가 드리프트 발생원**이다
([드리프트 자동 감지](drift_detection.md) D8 부류).

### 2.4 파싱은 되는데 **깨지기 쉬운** 지점 — 실측 기반

지금 통과한다고 앞으로도 통과하는 것은 아니다. 실제 본문을 보며 확인한 취약점:

| # | 취약점 | 왜 깨지나 | 지금 상태 |
|---|---|---|---|
| F1 | `[완료]` 뒤에 괄호 URL 이 붙어 Markdown 링크가 되면 | 등급 정규식 `[^\]]+` 는 여전히 맞지만 셀에 괄호 잔여물이 남는다. 잔여물 검사가 없다 | 발생 안 함 |
| F2 | 내용 셀 안의 `\|` | 표 셀에 파이프가 들어가면 행 정규식의 마지막 `\|` 앵커가 어긋난다 | 발생 안 함 |
| F3 | 등급 어휘가 통제되지 않음 | 누가 `[진행]` 을 새로 쓰면 파서는 조용히 새 등급으로 받는다. **통제 어휘 선언이 본문에 기계 판독 형태로 없다** | **위험** |
| F4 | 표 밖에 R 행을 쓰면 | 목록 형태로 쓰면 누락 | 발생 안 함 |
| F5 | 증거 표기가 자유 산문 | `—`·`→`·`·`·"계열"·"포크 실증분" 이 섞인다. **49행은 `#` 참조가 아예 없다** | **위험** |

F3·F5 가 실질 위험이다. **F5 가 R94 설계의 중심 문제다** — 5절.

## 3. 등급의 정의 — "완료"는 무엇인가

### 3.1 후보 셋과 각각의 실패

**(가) "PR 을 열었다".** #3886 이 세 코멘트에서 반복됐다고 지적한 것이 이것이다.
1.2 에서 #3907 안의 재발 6건을 실측했다. **명백히 틀렸다.** 열린 PR 은 리뷰에서 뒤집힐 수 있다.

**(나) "PR 이 머지됐다".** #3907 헤더가 채택한 정의다("`[완료]` 머지 실적", "완료 표기는
머지 링크와 함께만"). **이 저장소에서는 기계로 판정할 수 없다.**

실측 근거:

```
$ gh pr view <n> --json state,mergedAt,mergeCommit
#3882 CLOSED  null  null
#3795 CLOSED  null  null
#3867 CLOSED  null  null
#3836 CLOSED  null  null
#3832 CLOSED  null  null
#3838 CLOSED  null  null
```

여섯 건 다 `mergedAt: null` 이다. 그런데 **그 PR 들의 산출물은 devel 에 있다**:

```
$ grep -n '"explain"\|"export-agent-manifest"' src/main.rs
279:  Some("export-agent-manifest") => exit_with(cmd_export_agent_manifest(&args[2..])),
340:  Some("explain") => exit_with(explain_document(&args[2..])),

$ ls tools/agent_preflight.py      # #3795 의 산출물
tools/agent_preflight.py
```

커밋 동일성도 없다:

```
$ gh api repos/edwardkim/rhwp/compare/devel...<PR head>
#3832 → diverged ahead_by=4  behind_by=199
#3882 → diverged ahead_by=1  behind_by=109
#3795 → diverged ahead_by=1  behind_by=312
```

`ahead_by > 0` 이므로 PR 의 커밋은 devel 에 없다. **내용은 재적용됐고 SHA 는 달라졌다.**

저장소의 자동화도 이 정의를 쓰지만 그래서 발동하지 않는다 —
`.github/workflows/close-issues-on-devel-push.yml` 는 `!pr.merged_at` 이면 skip 한다.
#3884·#3885·#3787·#3793·#3828 이 산출물 착지 후에도 open 인 이유가 이것이다.

**따라서 (나)를 기계 판정에 쓰면 22/28 이 거짓 실패로 뜬다.** 실제로 그 값을 측정했다(5.2).

**(다) "산출물이 devel 에 실재한다".** 남는 것은 이것뿐이고, **실측 가능하다.**
`explain` 이 CLI 에 있는가? `tools/agent_preflight.py` 가 있는가? 계약 테스트가 있는가?
전부 저장소와 바이너리에 물어보면 답이 나온다.

### 3.2 제안하는 정의

> **`[완료]`** = 그 항목이 주장하는 **산출물이 `devel` 에 실재하고, 그 실재를 기계로 확인하는
> 증거 토큰이 행에 붙어 있다.**
>
> - PR 이 열려 있든 닫혔든 머지됐든 **상관없다.**
> - 이력 링크(`#N`)는 **사람이 읽을 맥락**이지 증거가 아니다.
> - 증거가 없으면 `[완료]` 를 쓸 수 없다. 증거를 못 만들면 그 항목은 `[실측]` 이하다.

나머지 등급도 같은 방식으로 조인다.

| 등급 | 정의(제안) | 필요 증거 | 반례 |
|---|---|---|---|
| `[완료]` | 산출물이 devel 에 실재 | `bin:` `file:` `test:` 중 1+ , **전부 통과** | PR 만 열린 상태 |
| `[실측]` | 측정이 존재하고 재현 가능 | `측정:` 또는 `doc:` 1+ | "해 봤다"는 기억 |
| `[문서]` | 설계 문서가 저장소에 있음 | `doc:` 1+ (실파일) | 이슈 코멘트만 |
| `[이슈]` | 추적 이슈가 **열려 있음** | `#N` 1+ 이고 그 이슈 open | 닫힌 이슈 참조 |
| `[가설]` | 근거 확보가 선행 조건 | **증거 토큰 금지** | 증거가 있는데 가설로 둠 |

마지막 줄이 흥미롭다. `[가설]` 에 증거가 붙어 있으면 **등급이 낮게 잘못 매겨진 것**이다.
검증기는 이것도 잡아야 한다 — **지도가 비관 방향으로 틀린 것도 틀린 것**이다.

### 3.3 집계 축을 유도값으로 만든다

2.3 의 사상(寫像)을 본문에 기계 판독 가능하게 선언한다.

```
<!-- roadmap-grades
완료·운영 = 완료, 실측
진행·추적 = 이슈, 문서
가설      = 가설
-->
```

효과 셋:
1. F3(통제 어휘 부재)이 해결된다 — 선언에 없는 등급이 나오면 실패.
2. 헤더의 3개 숫자를 손으로 계산하지 않는다. 검증기가 계산해 대조한다.
3. 묶음 규칙이 바뀌면 한 곳만 고친다.

## 4. 증거 문법 — 제안

### 4.1 설계 제약

- **사람이 손으로 쓸 수 있어야 한다.** 메인테이너가 이슈를 손으로 편집한다.
- **이슈 본문이 단일 출처여야 한다.** 저장소 파일로 옮기면 이슈와 파일이 드리프트한다 —
  없애려는 병을 새로 만드는 꼴이다.
- **기존 표를 파괴하지 않아야 한다.** 100행을 한 번에 다시 쓰는 것은 비현실적이고,
  #3907 운영 규칙 4("중복 서술하지 않는다")와도 어긋난다.
- **점진 도입이 가능해야 한다.** 증거 없는 행이 49개다. 한 번에 다 채울 수 없다.

### 4.2 문법

내용 셀 끝에 ` — 증거: <토큰>[·<토큰>]*` 를 붙인다. 지금 행들이 이미 ` — #2707→#2711·#3221`
로 끝나므로 **표기 관성이 유지된다.**

```
| R33 | [완료] | `rhwp explain` 결정론적 자기서술 — 증거: bin:`explain --help`·이력:#3832 |
```

| 토큰 | 뜻 | 검증 방법 |
|---|---|---|
| `bin:`<명령줄>`` | CLI 표면 실재 | 백틱 안 인자로 `rhwp` 를 부르고 **"알 수 없는 명령/옵션"이 안 나오면** 통과 |
| `file:<경로>` | 파일 실재 | `Path.exists()` |
| `test:<함수명>` | 계약 테스트 실재 | `grep -rn "fn <함수명>" tests/` 1건 이상 |
| `doc:<경로>` | 문서 실재 | 파일 실재 + front matter `status: active` |
| `측정:<경로>` | 측정 산출물 실재 | 파일 실재 |
| `이력:#N` | 사람용 맥락 | **검증하지 않는다** |

`이력:` 접두어가 이 설계의 핵심이다. **이슈·PR 번호를 증거에서 명시적으로 강등한다.**
1.2 의 여섯 건은 `#3897`·`#3903` 을 증거로 읽었기 때문에 났다. 문법이 그것을 이력으로
강등하면 **`[완료]` 를 쓰려면 반드시 산출물을 가리켜야 한다.**

### 4.3 `bin:` 판정을 왜 "exit 0" 이 아니라 "미지 명령 아님" 으로 하는가

`agent_preflight.py` 의 `check_declared_flags_real()` 이 이미 겪은 함정이다. 그 주석을 그대로
따른다 — 판정은 **stderr 만** 보고, 종료 코드 0 이면 무조건 통과로 본다. 인자 없이 부른
명령은 정상적으로 usage error(exit 2)를 내므로, exit 코드만 보면 멀쩡한 명령이 미구현으로
신고된다. 실측 오탐 2건이 그 방식에서 나왔다.

### 4.4 대안 검토 — 저장소 파일을 단일 출처로 두면 안 되는가

가장 자연스러운 대안은 `mydocs/tech/autonomous_maintenance/roadmap.yaml` 같은 구조화 파일을
만들고 이슈 본문을 거기서 생성하는 것이다. 검토했고, **채택하지 않는다.**

| 항목 | 이슈 본문 SSOT | 저장소 파일 SSOT |
|---|---|---|
| 사람이 고치는 비용 | 이슈 편집 1회 | 브랜치→PR→리뷰→착지 |
| 기계가 읽는 비용 | `gh issue view --json body` 1회 | 파일 읽기 |
| **드리프트 표면** | **없음**(원본이 하나) | 이슈 본문 ↔ 파일. **새 드리프트를 만든다** |
| 이력 | 이슈 편집 이력(열람 불편) | git log(우수) |
| 리뷰 | 없음 | PR 리뷰 |
| CI 검증 | 별도 워크플로 필요 | PR 마다 자동 |

**세 번째 줄이 결정적이다.** R94 는 "같은 사실을 말하는 출처가 셋"이라는 문제를 풀려고
있다(1.1). 그 해법이 **네 번째 출처를 만드는 것**이면 자기모순이다.

생성기를 두어 "파일→이슈 본문" 단방향으로 강제하면 이론상 드리프트가 없다. 그러나
**메인테이너가 이슈를 손으로 편집하는 순간 역방향이 생긴다.** 편집을 금지할 수는 없다 —
#3907 은 메인테이너의 조망 문서다.

다만 **파생 산출물은 저장소에 둔다**(6.3 의 주간 스냅샷). 스냅샷은 원본이 아니라 사진이므로
드리프트 대상이 아니다. 사진이 낡는 것은 "스냅샷 나이" 지표로 관리한다(6.2 (5)).

### 4.5 점진 도입 — 미증거 행을 실패로 보지 않는다

증거 토큰이 **없는** `[완료]` 행은 처음에는 `미검증` 으로 분류하고 실패로 세지 않는다.
대신 대시보드에 **미검증 비율**을 크게 띄운다(6.3). 실패로 세면 첫날부터 22건이 빨간불이라
아무도 안 본다 — [드리프트 자동 감지](drift_detection.md) §7.1 의 "헛울리는 검사기는
없느니만 못하다"가 여기에도 적용된다.

## 5. 자동 검증 — 실측한 것과 제안하는 것

### 5.1 검증기가 해야 할 판정

| # | 규칙 | 실패의 뜻 |
|---|---|---|
| V1 | R1~R100 결번·중복 없음 | 표가 깨졌다 |
| V2 | 등급이 `<!-- roadmap-grades -->` 선언 어휘 안 | 미승인 등급 |
| V3 | `[완료]`·`[실측]`·`[문서]` 행의 증거 토큰이 **전부 통과** | 지도가 낙관 방향으로 틀림 |
| V4 | `[이슈]` 행의 `#N` 이 **열려 있음** | 닫힌 이슈를 추적 중이라 함 |
| V5 | `[가설]` 행에 증거 토큰 **없음** | 지도가 비관 방향으로 틀림 |
| V6 | 헤더 집계 숫자 = 파싱 집계 | 손계산이 낡음 |
| V7 | 미검증(`증거:` 없는 `[완료]`) 비율 보고 | 실패 아님. 지표 |

**V5 가 이 설계의 정직도 장치다.** 진행률 검증기가 "덜 됐다"만 잡으면 사람은 등급을 낮춰
검증을 피한다. 양방향이어야 회피가 불가능하다.

### 5.2 실측 — 지금 형식에 (나) 정의로 검증기를 돌리면

3.1(나)의 "머지된 PR" 정의로 검증기 원형을 만들어 실제로 돌렸다.

```
[완료] 행 중 머지 근거를 못 찾은 것: 22건
 - R2  #3787=issue/open   #3804=PR/closed(merged_at=null)
 - R3  #3882=PR/closed(merged_at=null)
 - R4  #3884=issue/open   #3897=PR/open
 - R5  #3885=issue/open   #3903=PR/open
 - R6  #3903=PR/open
 - R11 #3795=PR/closed(merged_at=null)
 - R13 #3867=PR/closed(merged_at=null)
 …
 - R51 참조 0건
 - R62 참조 0건
```

**28행 중 22행 실패.** 그런데 이 22건은 성격이 다른 셋이 섞여 있다.

| 유형 | 건수(대략) | 진짜 문제인가 |
|---|---:|---|
| PR 이 지금도 **열려 있음** (R4·R5·R6·R32·R34·R81) | 6 | **그렇다.** 1.2 의 재발 |
| PR 이 닫혔고 `mergedAt: null` 인데 **산출물은 있음** | 14 | **아니다. 검증기 정의가 틀렸다** |
| 참조 자체가 없음 (R51·R62) | 2 | 판정 불가 |

**두 번째 유형이 22건 중 14건이다.** 즉 (나) 정의를 쓰면 **오탐이 실탐의 두 배**다.
이것이 3.2 에서 산출물 기준을 택한 실측 근거다.

### 5.3 이 실측이 주는 더 큰 교훈

> **검증기를 만들기 전에 정의를 고쳐야 한다.**

정의가 틀린 검증기는 정확히 22건을 빨갛게 칠하고, 그중 14건이 오탐이면 사람은
**나머지 8건도 안 본다.** #3886 이 지적한 문제를 고치려다 더 나쁜 상태를 만든다.

[드리프트 자동 감지](drift_detection.md) §9 의 단계표가 R94 를 **2단계(보고만)** 에 두고
"완료 정의 확정"을 선행 조건으로 건 이유가 이것이다.

### 5.4 어디서 도는가 — 제안

| 실행 위치 | 장점 | 단점 |
|---|---|---|
| **GitHub Actions 주 1회 cron** | 이슈 편집을 놓치지 않음 | 저장소에 cron 이 2개뿐이라 새 워크플로 필요 |
| `issues` 이벤트(edited) | 즉시 | #3907 만 걸러야 함. 편집이 잦으면 소음 |
| 로컬 스크립트 | 지금 당장 가능 | 아무도 안 부른다(`check_document_metadata.py` 의 전철) |

**주 1회 cron 을 제안한다.** 근거: 이 저장소의 유일한 상시 정비 자동화
(`cache-generation-sweep.yml`)도 같은 형태이고, 그 워크플로 머리말이 "devel push 마다 돌
필요가 없다"는 판단을 명시한다. 진행률도 마찬가지다 — 시간 단위로 바뀌지 않는다.

**검증 실패를 어떻게 알리는가**: 이슈에 코멘트를 자동으로 다는 것은 **하지 않는다.**
#3907 은 조망 이슈이고 코멘트 소음이 쌓이면 읽히지 않는다. 대신 **워크플로 job 을 실패시키고
요약을 job summary 에 쓴다.** (확인되지 않음: 메인테이너가 어느 통지 경로를 선호하는지.)

### 5.5 검증기는 무엇을 **하지 않는가**

- **이슈 본문을 고치지 않는다.** 등급은 평가이고 평가는 사람이 한다
  ([드리프트 자동 감지](drift_detection.md) §6.3).
- **등급을 추천하지 않는다.** "R47 은 `[완료]` 여야 합니다" 같은 말을 하지 않는다.
  증거가 통과하는지 아닌지만 말한다.
- **새 R 항목을 만들지 않는다.** 로드맵의 범위는 사람이 정한다.

## 6. 대시보드 — 무엇을 보여줘야 유용한가

### 6.1 보여주면 **안 되는** 것부터

> **큰 퍼센트 하나.** "로드맵 35% 완료."

이것이 정확히 #3886 이 지적한 낙관 편향의 형태다. 단일 숫자는 (a) 어느 정의로 셌는지
숨기고, (b) 미검증 행을 완료 쪽에 흡수하고, (c) R100 과 R51 을 같은 무게로 센다.

**퍼센트를 낼 거면 반드시 분모의 정의와 미검증 수를 같은 크기로 옆에 붙인다.**

### 6.2 보여줘야 할 것

**(1) 등급 분포 + 검증 상태 교차표.** 대시보드의 본체다.

```
           검증통과   검증실패   미검증   합
완료          6          6        16      28
실측          -          -         7       7
문서          4          0         3       7
이슈          5          3         0       8
가설          -          -        50      50
```

(위 숫자는 **형식 예시**다. 실측값이 아니다 — 증거 토큰이 아직 없어서 채울 수 없다.)

이 표 하나가 "얼마나 됐나"와 **"얼마나 확인됐나"** 를 동시에 말한다. 후자가 R94 의 고유
기여다. 지금까지 어떤 출처도 후자를 말하지 않았다.

**(2) 그룹(A~J)별 상태.** #3907 은 이미 A~J 로 나뉘어 있다. 그룹별 등급 분포를 보면
**어느 층이 막혀 있는지**가 보인다. #3886 의 "L1 의 구멍이 L3 를 막는다"를 매주 재확인하는
장치다.

**(3) 선행 조건 그래프.** 본문에 이미 의존이 적혀 있다.

- R9 "R8 판정 뒤"
- R53 "R8 부류 판정 뒤"
- R18 "수집 기준·라이선스 선행"
- R78 "보안 축(R14~15) 선행"
- R30 "권위표 등재"

이것들은 지금 **산문**이다. 기계가 읽으려면 `선행:R8` 같은 토큰이 필요하다(4.2 문법의 확장).
그러면 **"지금 착수 가능한 `[가설]` 항목"** 을 계산할 수 있다 — 선행 조건이 전부
`[완료]` 인 가설 행들. #3907 운영 규칙 1("착수는 단계가 아니라 근거가 결정한다")을
기계가 집행하는 형태다.

**(4) 변화 로그.** 주 1회 스냅샷을 저장하고 **등급이 바뀐 행만** 보여준다.
"이번 주에 R7 이 `[이슈]`→`[완료]`". 100행을 매주 다시 읽게 하지 않는다.

**(5) 정직도 지표 3개.**

| 지표 | 정의 | 왜 |
|---|---|---|
| **미검증률** | 증거 토큰 없는 행 / 전체 | 낮을수록 지도를 믿을 수 있다 |
| **역방향 오류** | V5 위반 수(가설인데 증거 있음) | 비관 편향도 오류다 |
| **스냅샷 나이** | 마지막 검증 실행 이후 경과일 | 대시보드 자신이 낡는 것을 막는다 |

세 번째가 특히 필요하다. 대시보드는 **자기가 드리프트할 수 있는 문서**다
([드리프트 자동 감지](drift_detection.md) D8).

### 6.3 형태

| 후보 | 평 |
|---|---|
| **이슈 본문 상단 자동 갱신 블록** | 단일 출처 원칙에 맞지만 **기계가 이슈를 고치게 된다**(5.5 위반) |
| **job summary** | 구현 비용 0. 검색이 안 되고 보존이 안 됨 |
| **저장소 안 Markdown 스냅샷** (`mydocs/metrics/roadmap/YYYY-MM-DD.md`) | 이력이 남고 diff 로 변화가 보임. `mydocs/metrics/` 관행이 이미 있다 |
| GitHub Pages | 보기 좋지만 배포 경로(`deploy-pages.yml`)가 main 기준이라 지연 |

**job summary(즉시) + 저장소 스냅샷(주간)** 조합을 제안한다. 스냅샷이 (4) 변화 로그의
재료가 된다. `mydocs/metrics/` 에 날짜 디렉터리로 쌓는 기존 관행을 그대로 쓴다.

### 6.4 스냅샷 문서의 뼈대 — 형식 예시

```markdown
---
kind: snapshot
status: active
canonical: mydocs/tech/autonomous_maintenance/progress_machine_readable.md
last_verified: <실행일>
---

# 로드맵 #3907 진행 스냅샷 — <실행일>

검증기 `<커밋 SHA>` · 입력 신선도 ✓ · 건너뛴 검사 0건

## 1. 등급 × 검증 상태
<교차표>

## 2. 이번 주 변화
| 행 | 이전 | 현재 | 근거 |

## 3. 검증 실패
| 행 | 등급 | 실패한 증거 토큰 | 실행 출력 |

## 4. 착수 가능한 [가설] 항목
선행 조건이 전부 통과한 행

## 5. 정직도
미검증률 · 역방향 오류 · 스냅샷 나이
```

`kind: snapshot` 은 `scripts/check_document_metadata.py` 의 `ALLOWED_KINDS` 에 이미 있는
값이다. **새 규약을 만들지 않고 기존 어휘로 들어간다** — 그러지 않으면 이 문서 자신이
[드리프트 자동 감지](drift_detection.md) D6 의 사례가 된다(`kind: contract` 처럼).

§3 의 "실행 출력" 열이 중요하다. 실패를 숫자로만 보고하면 사람이 재현하러 가야 한다.
출력을 함께 실으면 **5초 안에 오탐 판정**이 된다 —
[드리프트 자동 감지](drift_detection.md) §7.3 S3 과 같은 원칙이다.

## 7. 도입 순서 — 제안

| 단계 | 하는 일 | 선행 | 통과 판정 |
|---|---|---|---|
| **P0** | 이 문서 | — | — |
| **P1** | **정의 확정** — 3.2 를 #3907 헤더에 반영. `<!-- roadmap-grades -->` 선언 추가 | 사람 승인 | 헤더가 산출물 기준을 말한다 |

| **P4** | V3·V4·V5 켜기 | P3 에서 미검증률 < 임계 | 실패가 전부 실탐 |

**P1 이 가장 어렵고 가장 중요하다.** 코드가 아니라 합의다. 5.3 이 그 이유다.

이유가 여기 있다: 자율 정비는 **무엇이 됐는지 기계가 아는 것**에서 시작한다.

## 8. 확인되지 않음

1. **왜 PR 이 `mergedAt: null` 로 착지하는가.** 3.1(나)에서 실측했지만 원인은 모른다.
   이 설계는 원인을 몰라도 성립하도록 산출물 기준을 택했다.
2. **메인테이너가 `증거:` 문법을 받아들일지.** 4.2 는 제안이고 합의가 아니다. 100행 중
   28행만 손대는 점진 도입을 전제로 했지만, 그마저도 사람 노동이다.
3. **미검증률 임계.** P4 진입 조건의 숫자를 정할 데이터가 없다.
4. **통지 경로.** 5.4 참조.
5. **`bin:` 토큰의 실행 환경.** CI 에서 릴리스 바이너리를 빌드하면 6분+가 든다.
   기존 CI 산출물을 재사용할 수 있는지 확인하지 않았다.
6. **선행 조건 토큰의 문법.** 6.2(3)의 `선행:R8` 은 이 문서의 제안이며, 본문 산문을
   토큰으로 옮기는 작업의 비용을 산정하지 않았다.
7. **#3608·#3719 §8 과의 관계.** #3907 운영 규칙 4 는 상세의 canonical 이 각 참조 이슈라고
   한다. **R94 검증기가 #3608 체크박스도 검증할지는 정해지지 않았다.** 세 출처의 값이
   달랐다는 것이 문제의 출발점이었으므로, #3907 만 검증하면 나머지 둘은 그대로 남는다.
   이것이 이 설계의 **가장 큰 미해결**이다.
