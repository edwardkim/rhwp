# 엔드게임 판정 기준 — R99·R100

로드맵 [#3907](https://github.com/edwardkim/rhwp/issues/3907) 의 **R99·R100** 설계 문서이자
**자율 유지보수 축(R91~R100)의 결론**이다. 둘 다 등급은 **[가설]** 이고, 이 문서는
그 등급을 올리지 않는다.

R100 은 로드맵 100단계 중 하나가 아니다. **나머지 99개가 사실인지 판정하는 실험**이다.
#3907 의 목표 문장이 그렇게 쓰여 있다:

> **"새로 온 에이전트가 매뉴얼 없이 30분 안에 첫 유효 기여를 만들고, 도구의 일상 정비를
> 에이전트가 맡는 문서 엔진"** (R100 이 그 판정 실험이다)

앞 절반이 R100, 뒤 절반이 R99 다. 이 문서는 앞 절반을 **실험으로 설계**하고,
뒤 절반의 **분담선을 실측으로 긋는다.**

증거 표기는 [야간 자율 정비 사이클](nightly_cycle.md) §0 과 같다 —
**[실측] [기록] [설계] [미확인]**.

# 제1부. R100 — 판정 실험

## 1. 이 문장이 실험이 되려면

목표 문장은 지금 상태로는 실험이 아니다. 네 단어가 전부 정의되지 않았다.

| 단어 | 정의되지 않은 것 |
| --- | --- |
| **새로 온 에이전트** | 무엇을 모르는 상태인가. 어떻게 보장하나 |
| **매뉴얼 없이** | `llms.txt`·`AGENTS.md` 는 매뉴얼인가 아닌가 |
| **30분** | 무엇부터 무엇까지. 왜 30분인가 |
| **첫 유효 기여** | 열린 PR? CI 통과? 머지? |

정의를 안 하면 실험은 **항상 통과하거나 항상 실패한다.** 어느 쪽이든 아무것도
알려 주지 않는다. §2~§5 가 이 넷을 하나씩 좁힌다.

그리고 실험이려면 **반증 조건**이 있어야 한다. "통과했다"만 정의하고 "실패했다"를
정의하지 않으면 그건 시연이지 실험이 아니다. §7 이 그걸 다룬다.

## 2. "신규 에이전트"의 조건

### 2.1 무지를 어떻게 보장하나 — 오염 경로 4개

| 경로 | 무엇 | 통제 가능? |
| --- | --- | --- |
| **C1. 사전학습 오염** | 모델 가중치가 이미 이 저장소를 봤다 | **통제 불가** |
| C2. 세션 맥락 | 같은 세션에서 앞서 이 저장소를 다뤘다 | 통제 가능 — 새 세션 |
| C3. 사람 조력 | 실행자가 힌트를 준다 | 통제 가능 — 대화 로그 보존 |
| C4. 반복 학습 | 같은 실험을 두 번째 돌린다 | 통제 가능 — 회차 기록 |

### 2.2 C1 이 이 실험의 근본 약점이다

**[기록]** `edwardkim/rhwp` 는 공개 저장소다. 그러므로 어떤 모델의 사전학습 데이터에
이 저장소의 코드·문서·이슈가 들어 있을 수 있다.

**[미확인]** 실제로 들어 있는지, 어느 모델에 얼마나 들어 있는지 **확인할 방법이 없다.**
모델 제공자가 학습 데이터를 공개하지 않고, 저장소 쪽에서 검증할 수단도 없다.

이걸 숨기지 않는다. **C1 이 통제 불가라는 것은 R100 의 결과 해석을 제한한다.**

- 통과했을 때: "저장소가 잘 가르쳤다" 와 "모델이 이미 알고 있었다" 를 **구분할 수 없다.**
- 실패했을 때: 이건 깨끗하다. 이미 알고 있었어도 실패했다면 저장소 쪽 문제가 맞다.

즉 **R100 은 비대칭 실험이다. 실패는 강한 증거이고 통과는 약한 증거다.**
이걸 인정하고 설계하는 것과, 모르는 척 "통과했으니 목표 달성"이라고 쓰는 것은 다르다.

### 2.3 그래서 무지를 가정하지 말고 행동을 측정한다

**[설계]** C1 을 못 없애므로, 대신 **저장소 밖 지식을 썼는지 흔적을 남긴다.**

| 기록 항목 | 무엇을 알려 주나 |
| --- | --- |
| 첫 5회 도구 호출의 대상 파일 | 진입점을 **찾았나** 아니면 **알고 있었나**. `llms.txt` 를 읽고 간 것과 바로 `src/main.rs` 를 연 것은 다르다 |
| 읽은 파일 전체 목록 + 순서 | 안내를 따라간 경로가 재구성된다 |
| 저장소에 없는 사실을 쓴 순간 | 예: 파일을 안 읽고 명령 플래그를 정확히 씀 |
| 막힌 지점과 푼 방법 | 저장소가 답을 줬나, 아니면 추측했나 |

**[설계]** 그리고 판정에 이 조항을 넣는다:

> 저장소를 읽지 않고 저장소 특유의 사실을 사용한 흔적이 있으면, 그 회차는
> **통과로 세지 않는다.** 무효로 세지도 않는다 — **"C1 오염 의심"으로 따로 센다.**

억지로 깨끗한 척하지 않는 것이 이 조항의 목적이다.

### 2.4 나머지 세 경로

**[설계]**

- **C2**: 새 세션·빈 맥락에서 시작한다. 이전 대화 요약을 주입하지 않는다.
- **C3**: 사람은 **과제 문장 하나**만 준다(§6.2). 그 뒤로는 답하지 않는다.
  막혀도 답하지 않는다. 막혀서 실패하는 것이 이 실험의 관측값이다.
- **C4**: 회차를 기록한다. 2회차부터는 **같은 과제를 쓰지 않는다.**
  같은 과제를 다시 쓰면 그건 저장소가 아니라 실행자의 학습을 재는 것이다.

## 3. "유효 PR"의 정의

### 3.1 후보 사다리

| 후보 | 기준 | 문제 |
| --- | --- | --- |
| V1 | PR 이 **열렸다** | 너무 약하다 (§3.2) |
| V2 | **CI 가 초록** | 이 저장소에서 오해를 만든다 (§3.3) |
| V3 | **리뷰어가 승인** | 사람 일정에 묶인다 |
| V4 | **머지됐다** | 기여자가 통제 못 한다 (§3.4) |

### 3.2 V1 이 안 되는 이유 — 실측 반례

**[기록]** PR #3753 과 #3754 는 둘 다 제목이 `... (최초 결함 주장 철회)` 로 끝난다.
열렸고, 형식을 갖췄고, 테스트가 붙어 있었다. 그런데 **주장한 결함이 존재하지 않았다.**

- #3753: quick-xml 의 `From` 구현이 이미 이스케이프하고 있었다
- #3754: `HmlRectangle` 이 이미 `i32` 였다

두 건 다 **FIXME 주석과 타입 추론을 근거로 결함을 주장**했다가, 호출 경로와 선언을
끝까지 따라가고 나서 철회했다.

> **"PR 을 열었다"가 기준이면 오탐도 통과한다.** 그러면 실험은 통과하는데 목표 문장은
> 여전히 거짓이다. 신규 에이전트가 30분 만에 만들 수 있는 가장 쉬운 산출물이
> 정확히 **그럴듯한 오탐**이기 때문이다.

### 3.3 V2 가 오해를 만드는 이유 — 실측

**[실측]** `.github/workflows/ci.yml` 의 `preflight` job 에는 `Detect review-only fast pass`
단계가 있고, `isAllowedReviewPath()` 는 `mydocs/` 로 시작하는 모든 파일을 허용한다.
`mydocs-only` 로 판정되면 본 검사가 빠른 통과로 처리된다.

**[실측]** 그리고 `ci.yml` 의 `paths-ignore` 에는 `mydocs/**`·`docs/**`·`*.md` 가 있다.

**결과**: 문서 PR 은 **CI 를 통과한 게 아니라 CI 가 안 돈 것**이다.
신규 에이전트가 30분 안에 낼 확률이 가장 높은 것이 문서 PR 이므로, 이 구멍은
가설이 아니라 **실험 설계의 실제 결함**이다.

> **[설계] V2 를 쓰려면 "CI 초록"이 아니라 "이 PR 에서 실제로 돈 검사가 초록"으로
> 적어야 한다.** 그리고 **돈 검사가 0개면 V2 를 충족하지 못한 것으로 센다.**

### 3.4 V4 가 안 되는 이유 — 실측

**[실측]** `kevin9327` 의 PR 60건(`--state all`) 중 `mergedAt` 이 null 이 아닌 것은
**0건**이다.

**[실측]** 그런데 그 내용은 `devel` 에 들어와 있다. 예: PR #3882 ↔ 커밋
`fix(envelope): info 가 건너뛴 것을 숨기고, structure 에 snake_case 가 섞여 있다 (#3880 T1·T3)`.

**[실측]** 지금 열린 PR 중 #3912 의 제목이
`Kevin PR 9건 누적 통합: CLI 계약·agent 문서·provenance` 다.

**[실측]** `devel` 최근 100커밋에 `Merge pull request #3895 from edwardkim/review/kevin9327-20260803`
같은 통합 머지가 실측된다.

해석: **머지는 기여자가 통제하는 사건이 아니다.** 메인테이너가 여러 건을 모아
자기 브랜치에서 통합한 뒤 원본을 닫는다. (제목 일치에 근거한 해석이며 커밋 단위
확정 대조는 안 했다 **[미확인]**.)

> **V4 를 기준으로 삼으면 R100 은 신규 에이전트의 능력이 아니라 메인테이너의 일정을
> 측정한다.** 30분 안에 머지되는 일은 이 저장소에서 일어나지 않는다.

### 3.5 권고 정의

**[설계]** V1~V4 중 하나를 고르는 대신 **세 요소의 논리곱**으로 정의한다.

> **유효 기여 = (E1) ∧ (E2) ∧ (E3)**
>
> - **E1. 대응**: 저장소에 이미 존재하는 이슈 하나, 또는 저장소에 있는 검사 도구가
>   보고한 실패 하나에 대응한다. **에이전트가 스스로 발굴한 문제는 이 실험에서
>   유효로 세지 않는다** — §3.2 의 오탐 위험을 실험 밖으로 밀어내기 위해서다.
> - **E2. 기계 검증**: 이 PR 의 변경으로 **실제로 돌아간** 검사가 있고 그것이 초록이다.
>   돈 검사가 0개면 불충족(§3.3).
> - **E3. 범위 판정**: 리뷰어가 "범위 밖" 또는 "오탐"으로 판정하지 않는다.
>   **승인은 요구하지 않는다** — 승인은 사람 일정이고 30분 안에 안 온다.

E3 은 30분 안에 못 정한다. 그래서 **[설계]** 판정을 두 단계로 나눈다.

| 단계 | 언제 | 무엇을 확정 |
| --- | --- | --- |
| **1차** | PR 생성 즉시 | E1·E2 — 자동 판정 가능 |
| **2차** | 리뷰 후(며칠 뒤) | E3 — 사람 판정 |

**시간 측정은 1차까지**만 한다. 2차는 **그 회차를 무효화할 수 있는 사후 조건**이다.
즉 30분 안에 1차를 통과해도, 나중에 오탐으로 판정되면 **그 회차는 실패로 뒤집힌다.**

이 사후 뒤집기 조항이 §3.2 의 반례를 실험에 반영하는 방법이다.

### 3.6 E1 이 실험 범위를 좁힌다는 것을 인정한다

E1 은 "스스로 발굴한 문제는 세지 않는다"고 못박는다. 이건 목표 문장의
"첫 유효 기여"보다 **좁다.** 자율적으로 문제를 찾아내는 것이야말로 값진 기여인데
그걸 뺐다.

뺀 이유는 §3.2 하나다. **오탐과 발굴을 30분 안에 구분할 방법이 없다.**
구분하려면 사람이 검증해야 하고, 그건 30분을 넘긴다.

> **[설계] 그래서 R100 은 "에이전트가 유용한가"를 재는 실험이 아니다.
> "저장소가 스스로를 설명하는가"를 재는 실험이다.** 목표 문장을 이 범위로 읽어야
> 실험 결과가 무언가를 뜻한다.

## 4. "매뉴얼 없이"의 경계

### 4.1 후보들의 실측 크기

**[실측]** 저장소 루트의 진입 문서들:

| 파일 | 줄 수 |
| --- | --- |
| `AGENTS.md` | 38 |
| `llms.txt` | 43 |
| `CLAUDE.md` | 41 |
| `CONTRIBUTING.md` | 378 |
| `README.md` | 546 |

**[실측]** `llms.txt` 43줄의 내용은 거의 전부 **링크 목록**이다 — 지식 지도, CLI 매뉴얼,
MCP 가이드, 레시피 6편, 실패 사전 등으로 나간다.

**[실측]** `AGENTS.md` 38줄도 마찬가지로 "문서 로딩 순서" 8단계를 링크로 지시한다.

### 4.2 구분 원칙과 그것이 무너지는 지점

**[설계]** 그럴듯한 구분: **사람에게 읽히려고 쓰인 것 = 매뉴얼 / 기계가 한 왕복에
소비하는 것 = 표면.** 이 기준이면 `llms.txt` 는 표면, `CONTRIBUTING.md` 는 매뉴얼이다.

**이 구분은 한 홉에서 무너진다.** `llms.txt` 는 링크 목록이고, 링크 끝은 매뉴얼이다.
`llms.txt` 를 읽는 것을 허용하면 `mydocs/manual/cli_commands.md` 를 읽는 것도 허용된다.
읽지 말라고 하면 `llms.txt` 는 아무 쓸모가 없다.

### 4.3 그래서 다르게 좁힌다

**[설계]** "매뉴얼 없이"를 **파일의 성질**이 아니라 **정보의 출처**로 정의한다.

> **"매뉴얼 없이" = 사람이 대화로 주는 안내가 0 이다.**
> **저장소 안의 파일은 전부 읽어도 된다.**

근거:

1. **경계가 명확하다.** 대화 로그에 있느냐 없느냐로 판정된다. 파일은 논쟁이 없다.
2. **재고 싶은 것과 일치한다.** 재고 싶은 것은 "문서가 적은가"가 아니라
   **"저장소가 스스로 가르치는가"** 다. 문서가 많아도 찾을 수 있으면 성공이다.
3. **[기록]** 이 저장소의 실제 투자 방향과 맞는다 — `llms.txt`, `capabilities --search`(#3836),
   `export-agent-manifest`(#3843), `rhwp explain`(#3832), 레시피 6편(#3835·#3898)은
   전부 **"문서를 줄인다"가 아니라 "찾을 수 있게 한다"** 쪽 투자다.

### 4.4 그러면 이 실험이 재는 것

이 정의를 채택하면 R100 이 재는 것이 바뀐다.

- ~~"문서 없이도 되는가"~~
- **"저장소에 있는 것만으로 첫 기여에 도달하는 경로가 존재하고, 그 경로를 찾을 수
  있는가"**

**이 차이를 목표 문장에 반영해야 한다.** 반영하지 않으면 통과했을 때 잘못된
자랑을 하게 된다.

### 4.5 그래도 남는 회색지대

**[설계]** 아래는 판정을 미리 적어 둔다.

| 대상 | 허용? | 이유 |
| --- | --- | --- |
| 저장소 안 모든 파일 | 허용 | §4.3 |
| `gh issue view` 로 이슈 읽기 | 허용 | 이슈는 저장소의 일부이고 E1 이 이슈를 전제한다 |
| 웹 검색 | **불허** | 저장소 밖이고, 검색 결과에 이 저장소가 나오면 C1 오염과 구분 불가 |
| 다른 에이전트에게 묻기 | **불허** | 사람 안내 0 조항의 우회다 |
| 과제 문장 자체 | 허용 (§6.2 의 고정 문장만) | 이게 유일한 사람 입력이다 |
| 실행 환경 문서(예: 이 PC 빌드 함정) | **불허** | 저장소 밖 지식. 그리고 §5.3 의 편향과 직결된다 |

## 5. 30분의 근거

### 5.1 근거는 없다

**[실측]** #3907 본문 전체를 읽었다. **30분이라는 숫자의 도출 과정이 어디에도 없다.**
목표 문장에 그냥 들어 있다.

> **30분은 임의 숫자다.** 이 문서는 그것을 임의라고 적는다.

### 5.2 임의여도 쓸 데는 있다 — 절대 임계가 아니라 추세

**[설계]** 30분을 **합격선**으로 쓰면 아무 뜻이 없다. **기준선**으로 쓰면 뜻이 생긴다.

- 1회차 측정값이 기준선이 된다. 그게 47분이든 12분이든.
- 이후 개선의 의미는 **기준선 대비 변화**다.
- 30분은 그 위에 그어 놓은 **목표선**이고, 목표선은 근거가 없어도 방향을 준다.

**[설계]** 그래서 판정 문장을 이렇게 쓴다: "30분 안에 됐다/안 됐다" 가 아니라
**"N분 걸렸고, 시간의 M%가 어디에 갔다"**. 두 번째가 실제로 행동을 바꾼다.

### 5.3 30분이 숨기고 있는 편향 — 빌드

**[기록]** `tools/agent_preflight.py` 헤더에 실측이 적혀 있다: 가드가 한 번에 하나씩만
드러나 **빌드만 18분**을 쓴 적이 있고, 한 번의 `cargo build` 를 **6분**으로 적는다.

**[실측]** `.github/workflows/ci.yml` 의 아카이브 빌드 job 은 `timeout-minutes: 30`,
`full-renderer-sweep` 는 60 이다. 러너에서도 이 규모다.

산수는 단순하다.

| 트랙 | 30분 안에 가능한가 |
| --- | --- |
| 문서·계약 문서 PR | 가능 |
| 코드 수정 + 빌드 1회 + 테스트 | 빌드만 6분 **[기록]**. 빠듯하지만 가능 |
| 코드 수정 + 빌드 3회(가드 순차 실패) | **불가능** — 빌드만 18분 **[기록]** |
| 첫 빌드(의존성 컴파일 포함) | **불가능** — 시간 미측정이나 6분보다 훨씬 크다 **[미확인]** |

> **[설계] 결론: 30분 상한은 사실상 "문서·계약 PR 만 허용한다"는 뜻이다.**
> 이건 실험 설계의 **숨은 편향**이고, 명시하지 않으면 결과를 오독하게 된다.
> "신규 에이전트가 30분에 기여했다"가 실제로는 "문서 PR 을 냈다"일 수 있다.

### 5.4 그래서 트랙을 나눈다

**[설계]**

| 트랙 | 상한 | 무엇을 재나 |
| --- | --- | --- |
| **T-문서** | 30분 (벽시계) | 저장소가 자기를 설명하는가 |
| **T-코드** | 30분 (**빌드·CI 대기 제외한 순작업**) + 벽시계 별도 기록 | 코드 기여 경로가 열려 있는가 |

T-코드에서 빌드 시간을 빼는 것은 **저장소가 통제하지 못하는 변수**이기 때문이다.
다만 빼면 무엇을 재는지가 바뀌므로 **두 숫자를 다 기록한다**(§6.4).

**두 트랙은 별개 실험이다.** T-문서 통과가 T-코드 통과를 뜻하지 않는다.
목표 문장이 어느 쪽을 뜻했는지는 **[미확인]** 이다.

## 6. 측정 방법

### 6.1 시작 시각(t0) — 후보와 판정

| 후보 | 문제 |
| --- | --- |
| 세션 시작 | 환경 준비·인증이 포함된다. 저장소가 통제 못 한다 |
| 첫 도구 호출 | 위와 같음 (첫 호출이 환경 확인일 수 있다) |
| clone 완료 | 네트워크 속도가 섞인다 |
| **저장소 파일·이슈에 대한 첫 접근** | ← **권고** |

**[설계] t0 = 저장소 내용에 대한 첫 접근** (첫 파일 읽기 또는 첫 `gh issue view`).
근거: 그 앞은 전부 환경이고, 실험이 재려는 것은 **저장소**다.

### 6.2 사람이 주는 유일한 입력

**[설계]** 고정 문장 하나. 회차마다 바꾸지 않는다.

> 이 저장소에 기여하라. 열려 있는 이슈 하나를 골라 PR 을 하나 열어라.
> 질문에는 답하지 않는다.

이 문장에 **저장소 이름 외의 정보를 넣지 않는다.** "먼저 `llms.txt` 를 읽어라"를
넣는 순간 그게 매뉴얼이 되고 §4.3 위반이다.

### 6.3 종료 시각(t1)

**[설계] t1 = PR 생성 API 가 반환한 시각.**

근거: **[실측]** `gh pr list --json createdAt` 이 서버 기록을 준다.
실행자가 조작할 수 없고, 사후에 재확인된다. 자가 보고 시각과 달리 검증 가능하다.

### 6.4 기록 양식

**[설계]** 회차마다 아래를 남긴다. 하나라도 비면 그 회차는 **측정 실패**로 센다.

| 필드 | 예 |
| --- | --- |
| 회차 / 트랙 | 1회차 / T-문서 |
| 실행 모델·환경 | (기록만. 비교 목적 아님) |
| t0 / t1 (UTC) | 저장소 첫 접근 / PR createdAt |
| **벽시계 소요** | t1 − t0 |
| **순작업 소요** | 벽시계 − (빌드 + CI 대기 + 네트워크 대기) |
| 읽은 파일 목록 + 순서 | §2.3 |
| 첫 5회 도구 호출 | §2.3 |
| 막힌 지점 / 푼 방법 | 저장소가 답을 줬나 |
| 고른 이슈 번호 | E1 |
| 이 PR 에서 **실제로 돈 검사** | E2. 0개면 불충족 |
| C1 오염 의심 여부 | §2.3 |
| 1차 판정 (E1·E2) | 즉시 |
| 2차 판정 (E3) | 리뷰 후. **뒤집힐 수 있다** |

### 6.5 무엇을 재지 않는가

**[설계]** 아래는 재지 않는다. 재면 실험이 다른 것이 된다.

- **모델 간 비교** — 이 실험은 저장소를 재지 모델을 재지 않는다
- **PR 품질 점수** — E3 이 이분법(범위 밖/오탐인가 아닌가)인 이유다
- **토큰·비용** — 별개 지표다. [야간 사이클](nightly_cycle.md) 소관에 가깝다

## 7. 판정과 그 뒤

### 7.1 통과의 뜻과 한계

**[설계]** 판정 문장:

> **N회차 중 K회가 1차·2차 판정을 모두 통과했다. 벽시계 중앙값은 X분이다.**

**n=1 은 통과가 아니다.** 한 번 됐다는 것은 그 회차의 과제가 쉬웠다는 뜻일 수도 있다.
**[설계]** 최소 회차를 정하되, 그 숫자의 근거도 없다는 것을 적는다 —
**3회 중 2회**를 제안한다 **[근거 없음]**.

그리고 §2.2 대로, 통과는 **약한 증거**다. C1 을 배제하지 못했기 때문이다.

### 7.2 실패의 뜻 — 이쪽이 값지다

실패는 강한 증거다. 그리고 **어디서 실패했는지가 다음 작업 목록이 된다.**

**[설계]** 실패 지점을 이 분류로 기록한다:

| 실패 지점 | 뜻하는 것 | 그러면 다음은 |
| --- | --- | --- |
| 진입점을 못 찾음 | `llms.txt`·`AGENTS.md` 가 진입 역할을 못 한다 | 표면 문제 (로드맵 D 트랙) |
| 이슈는 골랐는데 무엇을 고쳐야 할지 모름 | 이슈와 코드 사이 다리가 없다 | 지식 지도·레시피 |
| 고쳤는데 검증을 못 함 | 검증 절차가 안 보인다 | 선검사·가드 문서화 |
| 검증했는데 PR 규약에서 막힘 | 기여 절차 문서 | CONTRIBUTING·PR 템플릿 |
| 시간 초과(빌드) | §5.3 의 편향이 현실화 | 트랙 분리로 다시 잼 |
| 오탐을 냄 | §3.2 재현 | **가장 중요한 실패** — 저장소가 "확인하는 법"을 안 가르쳤다 |

마지막 행이 이 축 전체와 이어진다. §제2부에서 다룬다.

### 7.3 아직 정하지 못한 것

**[미확인]** 이 실험 설계에서 답을 못 낸 지점들이다. 실험 전에 사람이 정해야 한다.

| # | 미정 지점 | 왜 지금 못 정하나 |
| --- | --- | --- |
| M1 | 목표 문장이 T-문서인가 T-코드인가 | #3907 에 근거가 없다 |
| M2 | 최소 회차와 통과 비율 (3중 2?) | 임의 숫자다 |
| M3 | 과제 이슈를 실행자가 고르나 에이전트가 고르나 | 고르는 능력도 재고 싶지만 그러면 난이도 통제가 안 된다 |
| M4 | 2차 판정을 누가 하나 | 메인테이너 시간이 든다. 동의가 필요하다 |
| M5 | 실패 회차의 PR 을 어떻게 처리하나 | 실험 산물이 큐를 먹는다 — [볼륨 캡](nightly_cycle.md) §5.1 과 충돌 |
| M6 | 몇 번 실패하면 실험 자체를 접나 | 무한 재시도는 실험이 아니라 훈련이다 |

**M5 가 실무적으로 가장 급하다.** **[실측]** 지금 저장소 전체 열린 PR 은 14건이고
그중 10건이 한 계정이다. 실험 PR 을 3건 더 얹으면 캡을 정면으로 위반한다.
**[설계]** 실험은 **캡에 자리가 있을 때만** 돌린다. 실험이 규약보다 위에 있지 않다.

# 제2부. R99 — 에이전트 유지보수 모드

## 8. 선언이 무슨 뜻이고 무슨 뜻이 아닌가

R99 는 "사람은 판단·방향, 에이전트는 실행 상시"를 **선언**하는 단계다.
선언은 능력이 아니라 **약속**이므로, 지킬 수 없는 것을 선언하면 그냥 거짓말이 된다.

**[설계]** 뜻하는 것 / 뜻하지 않는 것:

| 뜻한다 | 뜻하지 않는다 |
| --- | --- |
| 반복·전수·재현 작업의 기본 수행자가 에이전트다 | 사람이 코드를 안 본다 |
| 사람의 시간은 판단에 쓰인다 | 사람이 적게 일한다 |
| 에이전트 산출물이 정상 경로로 들어온다 | 검수 없이 들어온다 |
| 정비가 사람 일정에 안 묶인다 | 정비가 무인이다 |

## 9. 분담선의 근거 — 실측 대비

분담선을 원리로 정하면 틀린다. **오늘까지 실제로 무엇이 잘됐고 무엇이 틀렸는지**로
정한다. 억지로 좋게 쓰지 않는다.

### 9.1 에이전트가 잘한 것

| 잘한 것 | 근거 |
| --- | --- |
| **실측 재현** | **[기록]** #3905 — 두 exit 0 이 편집 하나를 무신호로 지우는 경합 유실을 재현했다. 재현 없이는 아무도 못 믿을 주장이었다 |
| **오탐을 실측으로 좁힘** | **[기록]** #3809 은닉 텍스트 탐지에서 오탐 31,946건 → 0. #3807 인젝션 신호 351개 표본 오탐 0. #3811 유니코드 기만 348개 오탐 0 |
| **전수 조사** | **[기록]** #3903 recordFields ↔ 실물 전수 대조로 즉시 28건 회수. #3838 프로필 등재 누락 14건. #3839 `--password` 선언하고 못 여는 명령 7건 |
| **회귀 가드** | **[기록]** #3867 악성 코퍼스 스위트가 samples/ 에서 **진짜** 은닉 텍스트 2건을 찾았다 |
| **문서 볼륨** | **[기록]** #3889 에이전트 가이드 577줄 → 4,487줄(×7.8) |
| **red→green 실증** | **[기록]** #3875 WMF 음수 카운트 패닉 — 실패 재현 후 수정 |

공통점: **범위가 정해져 있고, 답이 데이터 안에 있고, 지루하다.**
"61개 명령의 recordFields 를 실물과 하나씩 대조하라"는 사람이 하기 싫은 일이고
에이전트가 잘하는 일이다.

### 9.2 에이전트가 틀린 것

| 틀린 것 | 근거 |
| --- | --- |
| **없는 결함을 로드맵에 적음** | **[기록]** #3753·#3754 — 선검사 오탐을 실측 없이 옮겼다. FIXME 주석과 타입 추론을 근거로 삼았고, 호출 경로·선언을 끝까지 안 봤다. 둘 다 최초 주장 철회 |
| **종료 코드를 파이프에 가려진 채 읽음** | **[기록]** 파이프 뒤의 `$?` 는 마지막 명령의 것이다. 실패를 성공으로 읽었다 |
| **같은 축 문서를 이중으로 만듦** | **[기록]** 축 문서 세트가 겹쳐 생성됨 |
| **중복 PR 2건** | **[기록]** #3914 — #3902/#3903(4분 차), #3897/#3904(35분 차). 두 번째는 **같은 두 파일을 서로 다른 테스트 이름으로** 고쳤고, 둘 다 완주해 검증까지 마친 뒤에야 드러났다 |
| **볼륨 캡 위반** | **[실측]** 08-01 14건 · 08-02 18건 · 08-03 28건 개설. 캡은 "열린 PR 10건 내외" **[기록]** #3719 §7·#3796 §6. **[실측]** 현재 전체 열린 PR 14 중 10이 한 계정(71%) |

공통점 — 이쪽이 분담선의 진짜 근거다:

1. **존재/부재 판정에서 틀린다.** "이 결함이 있다"는 반례로만 확정되는데, 정황(주석·타입)에
   설득당했다. 전수 조사에서는 강하고 **존재 증명에서는 약하다.**
2. **자기 상태를 못 본다.** 캡 위반도 중복 PR 도 "다른 세션이 무엇을 하고 있나"와
   "내가 큐를 얼마나 먹고 있나"를 **안 보고** 생긴 일이다. 문서 안의 사실은 잘 읽고
   **자기가 만든 상태**는 안 읽는다.
3. **판정 도구를 잘못 읽는다.** 종료 코드 오독은 능력이 아니라 **규율**의 문제다.
   그리고 무인 루프에서는 이게 안전 장치를 통째로 무력화한다
   ([nightly_cycle.md](nightly_cycle.md) §5.2).
4. **양이 질을 밀어낸다.** 28건/일은 생산성이 아니라 **리뷰 부하의 이전**이다.
   그리고 그 결과 **[실측]** `mergedAt` 이 아니라 통합 배치(#3912)로 소비된다.

### 9.3 그래서 분담선은 여기다

> **에이전트는 "전수·재현·반복"에 강하고, "존재/부재 판정·우선순위·자기 상태 인식"에
> 약하다. 분담선은 능력이 아니라 이 약점을 따라 긋는다.**

**[설계]** 작업 유형별 분담:

| 작업 | 누가 | 근거 (§9.1/§9.2 항목) |
| --- | --- | --- |

### 9.4 "상시"의 조건

"에이전트가 실행을 상시 맡는다"는 **감독 없이 돈다**는 뜻이 아니다.

**[설계]** 상시가 되려면 셋이 필요하다.

1. **되돌릴 수 있다** — [nightly_cycle.md](nightly_cycle.md) §5.4
2. **멈출 수 있다** — 같은 문서 §5.2·P7. 끄는 법이 없는 자동화는 켜지 않는다
3. **자기 상태를 본다** — 캡 조회를 **매번** 한다. §9.2 의 약점 2 에 대한 직접 대응

3번이 R91(autofix 봇의 볼륨 캡 자동 준수)·R92(선등재)·R93(착수=할당)이 존재하는 이유다.
**셋 다 에이전트의 능력을 늘리는 장치가 아니라 자기 상태를 강제로 보게 만드는 장치다.**

## 10. 분담선이 지켜지는지 어떻게 아나

**[설계]** 선언만 하고 안 재면 선언은 장식이다. 위반 신호를 측정 가능한 것으로 적는다.

| # | 신호 | 재는 법 | 위반 방향 |
| --- | --- | --- | --- |
| G1 | 열린 PR 이 캡을 넘는다 | `gh pr list --state open --limit 500` (**`--limit` 필수** — **[기록]** `pr_triage.sh` 가 기본 30 절단을 경고) | 에이전트가 우선순위를 침범 |
| G2 | 철회된 결함 주장 건수 | 제목에 "철회" / 리뷰에서 오탐 판정 | 존재 판정을 에이전트가 함 |
| G3 | 중복 PR 발생 | 같은 이슈에 PR 2건 | 자기 상태 미인식 |
| G4 | 사람 검수 없이 들어간 계약 변경 | `capabilities` diff vs 승인 기록 ([release_notes_automation.md](release_notes_automation.md) §4) | 계약을 에이전트가 바꿈 |
| G5 | 한 계정의 큐 점유율 | 열린 PR 중 비율. **[실측] 지금 71%** | 부하 이전 |

**[실측] G5 는 지금 이미 나쁜 값이다.** 즉 R99 를 오늘 선언하면 그 선언은
**선언 시점부터 위반 상태**다.

## 11. 선언의 전제조건

**[설계]** 아래가 갖춰지기 전에는 R99 를 선언하지 않는다. 선언은 마지막에 한다.

| # | 조건 | 현재 |
| --- | --- | --- |
| D1 | 착수=할당 규약 확정 | **[기록]** #3914 제안됨. 확정 **[미확인]** |
| D2 | 캡이 자동으로 지켜진다 | **[실측] 안 지켜진다** — 71% |
| D3 | 야간 사이클의 정지·되돌리기가 리허설됨 | **없음** ([nightly_cycle.md](nightly_cycle.md) P5) |
| D4 | 계약 변경 감지가 돈다 | **[설계]** — R7·R8 선행 ([release_notes_automation.md](release_notes_automation.md) §4.5) |
| D5 | G1~G5 지표가 실제로 수집됨 | **없음** |
| D6 | R100 이 최소 1회 측정됨 | **없음** |

**D6 을 넣은 이유**: R99 는 "에이전트가 일상 정비를 맡는다"는 선언이고, R100 은
"에이전트가 이 저장소에서 일할 수 있다"는 판정이다. **판정 전에 선언하면 순서가
거꾸로다.**

## 13. 이 축의 한 줄

> **자율 유지보수 축의 결론은 "할 수 있다"가 아니라 "무엇이 없어서 아직 못 한다"다.**

그리고 없는 것 대부분은 기능이 아니다.

- 캡을 지키는 것은 **기능이 아니라 규율**이다 — **[실측]** 71%
- 결함 판정을 사람에게 두는 것은 **기능이 아니라 경계**다 — **[기록]** #3753·#3754
- 끄는 법을 문서화하는 것은 **기능이 아니라 대비**다 — **[기록]** 113건 사고

R91~R98 이 다 되어도 R99 는 이 셋이 서면 선언되고, 안 서면 선언되지 않는다.
**그리고 R100 은 그 선언이 사실인지 재는 유일한 장치다.**
