# 병렬 세션 규약 — 착수 = 할당

> 같은 계정의 여러 에이전트 세션이 한 저장소를 동시에 고친다. 2026-08-03 **하루에
> 중복 PR 사고가 두 번** 났다. 이 문서는 그 두 사건을 사례로 보존하고, 다시 나지
> 않게 하는 규약을 확정한다.
>
> 로드맵상 [#3907](https://github.com/edwardkim/rhwp/issues/3907) **R93**, 확정 이슈는
> [#3914](https://github.com/edwardkim/rhwp/issues/3914).
> 축 지도는 [README](README.md), 접합 기법은 [선등재 패턴](pre_registration_pattern.md).

이 문서의 모든 주장에는 PR·이슈 번호, `파일:줄`, 또는 재현 명령이 붙는다. 근거를
대지 못하는 항목은 **"확인되지 않음"** 으로 적었다(§11 에 모아 두었다).

## 0. 한 줄 요약

**이슈에 `assignee` 를 걸지 않으면 두 세션이 같은 것을 집는다.** GitHub 에 잠금 기제가
없는 게 아니라 **쓰지 않았다.** 착수 전 30초짜리 확인 세 줄이 사고 두 건과 빌드·테스트
사이클 한 벌을 아꼈을 것이다.

```bash
gh issue view <n> --repo edwardkim/rhwp --json assignees -q '.assignees[].login'
gh pr list --repo edwardkim/rhwp --state open --limit 100 --search "<n>"
gh issue edit <n> --repo edwardkim/rhwp --add-assignee @me   # 권한 있는 계정만 성공
gh issue comment <n> --repo edwardkim/rhwp --body "착수합니다 — <범위>"  # 외부 기여자의 잠금은 이것
```

### 2-3. 어떻게 발견됐나

**기계가 잡은 게 아니다.** 두 번째 PR 을 올린 세션이 개설 직후 열린 PR 목록을 보다가
같은 이슈 번호를 발견했다. 발견 시각 15:22:46 은 두 번째 PR 개설(15:20:54)의 **2분 뒤**다.

`../../manual/agent_surface_playbook.md` §2-5 가 못박은 **누적 머지 충돌검사**
(`upstream/devel` 에서 임시 브랜치를 만들어 열린 PR 브랜치 전부를 순차 merge)를
돌렸다면 이 겹침은 **확실히** 드러났을 것이다. 그러나 그 단계는 절차상 **PR 직전**에
있다 — 즉 **두 세션 모두 작업을 끝낸 뒤**다. 검사로는 늦다.

### 2-4. 어떻게 정리됐나 — 닫는 쪽이 남긴 것

#3902 를 닫으며 남긴 코멘트가 이 저장소의 **중복 판정 선례**다. 원문 구조를 그대로 옮긴다.

> #3903 과 중복이라 닫습니다 — 같은 이슈(#3885)를 병렬로 작업했습니다.
> **#3903 이 이 PR 을 완전히 포함하고, 더 낫습니다.**

| 항목 | #3902 | #3903 |
|---|---|---|
| `marked()` 부착 | 4곳 | **7곳** |
| 출처 지도 선언 | `findings[].raw`, `removed[].before` | 위 + **`findings[].masked`** |
| 계약 테스트 | 가드 2개 | 가드 4중 확장 + `tests/redact_sanitize_contract.rs` |

닫는 쪽은 **자기가 놓친 것을 구체적으로 적었다**:

> 특히 `findings[].masked` 를 제가 놓쳤습니다. 마스킹 결과도 영숫자만 가려질 뿐
> **하이픈·`@`·점 같은 구조 문자와 자릿수가 원문에서 옵니다.** 문서 파생이 맞고,
> #3903 이 보수적으로 선언한 쪽이 옳습니다.

그리고 **남는 쪽에 없는 산출물을 인계**했다:

> 저장소 규약은 이슈등록 → 분석 → 코드변경 → **처리결과문서** → PR 순서입니다.
> #3903 에는 `mydocs/report/` 산출물이 없습니다. 이 PR 의
> `mydocs/report/task_m100_3885_report.md` 를 그대로 가져다 쓰시면 됩니다
> (브랜치 `task/3885-envelope-provenance-marker`, 커밋 `e54f16e14`).

**이것이 좋은 선례인 이유**는 세 가지다.

1. **판정 근거를 표로 남겼다** — 다음 사람이 같은 판단을 다시 하지 않아도 된다.
2. **닫는 쪽이 이긴 항목을 인정했다** — "내가 놓친 것"을 적었다. 자존심 관리가 아니라
   기록이다. 놓친 이유(`masked` 도 구조 문자가 원문 유래)가 적혀 있어야 그 판단이
   다음에 재사용된다.
3. **버려지는 산출물을 인계했다** — 닫힌 PR 의 브랜치·커밋 해시를 명시해서, 남는 쪽이
   `git cherry-pick e54f16e14` 로 회수할 수 있게 했다. **중복 작업의 잔여 가치는
   0 이 아니다.**

### 3-4. 두 근인 분석이 서로 달랐다 — 중복의 유일한 이득

기록해 둘 만한 부수 사실이 있다. 두 PR 의 **근인 서술이 달랐다.**

- **#3897**: 표면 동작을 `before → after` 표로 6행 고정(예: `dump <문서> --bogus-flag`

- **#3904**: 삼킴 지점을 코드 위치로 셋 분해 — `dump_controls` 의 `_ => { i += 1; }`,

가치는 아니라는 뜻이고**, 그래서 §6 의 "닫는 쪽이 남겨야 할 것"이 필요하다.

## 4. 왜 났는가 — 구조

### 4-1. 이슈는 "누가 하고 있는지"를 말하지 않는다

GitHub 이슈의 기본 해석은 **"누구든 가져갈 수 있는 오픈 타스크"** 다. 세션이
"아무도 안 하고 있다"를 확인할 방법은 이슈 본문뿐인데, 이슈 본문은 착수 여부를
담지 않는다. 특히 이 저장소의 이슈는 **실측 근거를 상세히 담은 긴 문서**라서, 읽는
쪽에서 보면 "잘 정의된 미착수 작업"으로 보인다 — 정확히 집어가고 싶은 모양이다.

### 4-2. 잠금 기제는 있다. 쓰지 않았다

`assignee` 가 그 자리다. 2026-08-04 재확인:

```console
$ gh issue view 3884 --repo edwardkim/rhwp --json assignees
{"assignees":[]}
$ gh issue view 3885 --repo edwardkim/rhwp --json assignees
{"assignees":[]}
```

**두 사고 모두, 사고 다음 날까지도 비어 있다.** 사고 뒤에도 채워지지 않았다는 것은
"깜빡했다"가 아니라 **절차에 그 단계가 없다**는 뜻이다.

### 4-3. 같은 계정이라 외부 신호가 없다

외부 기여자끼리라면 GitHub 이 최소한의 신호를 준다 — 다른 사람의 브랜치, 다른 아바타,
알림. **같은 계정의 병렬 세션은 그 신호가 전부 같다.** 브랜치 접두사만 달랐다
(`wip/` vs `task/`), 그리고 그건 신호가 아니라 관습이다.

### 4-4. 규약은 이미 있었다 — 2026-04-23 의 재발

이 저장소에는 **정확히 이 규약이 이미 문서로 있다.**

`../../manual/memory/feedback_assign_issue_before_work.md`:

> 이슈 착수 결정 → 브랜치 생성 전 **반드시** 해당 이슈에 assignee 를 지정.
> GitHub 이슈는 기본적으로 "누구든 가져갈 수 있는 오픈 타스크" 로 해석되기 때문.
>
> **Why:** 2026-04-23 이슈 #259 (HY 폰트 매핑) 을 내부 작업하기로 하고 `local/task259`
> 브랜치에서 진행했으나 **이슈에 assignee 를 지정하지 않음**. 외부 기여자가 같은 이슈를
> 보고 합리적으로 "assignee 없음 = 오픈 타스크" 로 판단하여 PR #264 로 5-Stage 완주
> 해결. […] 기여자의 몇 시간 노력이 증발.

그리고 그 문서가 **일차/이차 방어선까지 구분**해 뒀다:

> 기존 메모리 `feedback_check_open_prs_first.md` 는 "열린 PR 확인" 자체는 여전히
> 유효하지만, **assign 이 일차 방어선**. PR 확인은 이차 방어선.

**규약이 없어서 난 사고가 아니다.** 도달하지 않아서 난 사고다. 두 메모 문서 모두
`status: historical` 이고 `mydocs/manual/memory/` 아래에 있어, 표면 작업의 실무 진입점인
`../../manual/agent_surface_playbook.md` 절차 §2 에는 **그 단계가 없다** — §2 는
`1. 이슈 등록 → 2. red 계약 테스트 → 3. 구현 → …` 로 시작하고 **할당 단계가 빠져 있다.**

이것이 이 문서가 필요한 진짜 이유다. **규약을 새로 만드는 게 아니라, 실무 절차의
1단계로 끌어올리는 것이다.**

### 4-5. 비용 — 무엇이 실제로 낭비됐나

"중복 PR 한 건"으로 세면 비용을 과소평가한다. 낭비는 네 층에 걸쳐 있다.

| 층 | 사고 1 (#3902) | 사고 2 (#3904) |
|---|---|---|
| **조사** | #3885 의 봉투 4건을 코드로 재확인, 가드가 못 잡은 경로 분석 | `dump_controls`·`diag_document`·`bench::run` 세 곳의 삼킴 지점 특정 |
| **구현** | +204/-5 (4파일) | +186/-0 (4파일) |
| **검증** | `rustfmt` 확인. `cargo test` 는 이 PC 링커 손상으로 못 돌림 | 계약 테스트 4조합 설계. 같은 이유로 못 돌림 |
| **문서** | 처리결과문서 +89줄 | 처리결과문서 +58줄 |
| **리뷰** | 메인테이너가 **어느 쪽을 볼지 판단**해야 한다 | 〃 |

마지막 줄이 캡(§8)과 이어지는 지점이다. #3904 의 닫는 코멘트가 정확히 적었다 —
*"같은 이슈를 두 번 고치면 리뷰가 두 배로 들고, 메인테이너가 어느 쪽을 봐야 하는지
판단해야 합니다."* **중복 PR 은 큐를 2건 늘리면서 처리량은 1건도 늘리지 않는다.**

빌드 비용은 이 저장소 기준 낮지 않다.
[#3796](https://github.com/edwardkim/rhwp/issues/3796) §1 이 실측으로 적는다 —
드리프트 가드 3연속 실패 사례에서 **릴리스 빌드 3회 18분**, 공유 워크트리 충돌로
**콜드 빌드 8분**.

> [!NOTE]
> 두 사고 모두 PR 본문이 *"이 PC 는 MSVC 링커(`dbghelp.lib`) 손상으로 `cargo test` 가
> 아예 돌지 않아 CI 가 유일한 판정자"* 라고 적었다. **CI 가 판정자면 중복의 비용에
> CI 러너 시간이 더해진다.** 이 저장소의 테스트는 8샤드로 나뉘어 있고
> `../../orders/20260803.md` 가 8단계 CI **17분 37초**를 기록한다.

### 4-6. 안 걸렸다면 — 두 사고 모두 나중에 반드시 드러났다

두 사고 다 소스 파일이 겹쳤다(§2-2·§3-2). 그래서 늦게라도 드러났을 것이고,
드러나는 지점이 어디였을지가 규약 설계의 근거가 된다.

| 발견 지점 | 시점 | 이미 지출된 비용 |
|---|---|---|
| **착수 전 assignee 확인** | 조사 전 | 0 |
| **착수 전 열린 PR 확인** | 조사 전 | 0 |
| 개설 직후 큐 훑기 (실제 사고 1) | PR 개설 직후 | 조사+구현+검증 한 벌 |
| 완주 후 큐 훑기 (실제 사고 2) | PR 개설 직후 | 조사+구현+검증+문서 한 벌 |
| 누적 머지 충돌검사 (playbook §2-5) | PR 직전 | 〃 |
| CI 리베이스 실패 | 머지 시도 | 〃 + CI 왕복 |
| 메인테이너 리뷰 | 리뷰 | 〃 + 리뷰어 시간 |

**규약이 착수 시점에 있어야 하는 이유가 이 표다.** 아래로 갈수록 지출이 커지고,
playbook §2-5 조차 이미 "한 벌"을 지출한 뒤다.

## 5. 규약 — 착수 전 3단계

절차의 canonical 은 `../../manual/agent_surface_playbook.md` §2 이고, 이 절은 그 §2 의
**0단계를 신설**하는 제안이다.

### 5-0. 순서가 중요하다

```
[신설] 0. 잠금 확인·할당  ← 조사보다 먼저
        1. 이슈 등록
        2. red 계약 테스트
        3. 구현
        …
```

**할당은 조사보다 먼저 한다.** 조사에도 시간이 든다 — 사고 2 의 두 PR 은 각자
`dump_controls`·`diag_document`·`bench::run` 세 곳을 읽고 근인을 세웠다. 그 조사 시간
동안 상대가 이미 작업 중이었다.

### 5-1. ① 이슈 잠금 확인 → 비었으면 즉시 할당

```bash
# 확인 — 출력이 비어 있으면 미착수
gh issue view <n> --repo edwardkim/rhwp --json assignees -q '.assignees[].login'

# 비었으면 즉시 (브랜치 생성 전)
gh issue edit <n> --repo edwardkim/rhwp --add-assignee @me
```

> [!IMPORTANT]
> **실측(2026-08-06): 외부 기여자 계정은 assignee 편집이 거부된다.** #3914·#3884·#3627
> 세 이슈에 `gh issue edit <n> --add-assignee kevin9327` 을 실행한 결과 세 건 모두
> `failed to update 1 issue` — GitHub 는 collaborator(또는 해당 이슈에 assignable 한
> 계정)만 지정을 허용한다. 명령 자체는 실행되므로 `gh` 의 projectCards 문제(아래 NOTE)와는
> 별개다. 따라서 잠금 매체는 계정 권한에 따라 갈린다:
>
> | 계정 | 1차 잠금 매체 |
> |---|---|
> | 메인테이너·collaborator | `assignee` 지정 |
> | **외부 기여자(병렬 세션 포함)** | **이슈 착수 코멘트** — `"착수합니다 — <범위>"` 형식, 범위를 반드시 적는다(§10-3 부분 잠금 겸용) |
>
> 착수 전 확인도 두 매체를 다 본다 — assignee 가 비어 있어도 **착수 코멘트가 있으면
> 선점된 것**이다. 이 실측으로 §11 의 미확인 4번이 해소됐다.

**assignee(또는 착수 코멘트)가 이미 있으면 착수하지 않는다.** 같은 계정이 이미 걸려
있어도 마찬가지다 — 같은 계정의 다른 세션이 잡고 있다는 뜻이기 때문이고, 그게 정확히
이 사고의 형태다.

**작업을 접거나 미루면 즉시 해제한다.** 걸어 놓고 안 하는 것은 큐를 막는다.

```bash
gh issue edit <n> --repo edwardkim/rhwp --remove-assignee @me
```

> [!NOTE]
> `gh pr edit` 는 **이 저장소에서 작동하지 않는다** — 내부적으로 projectCards 를
> 조회하는데 Projects classic 지원 종료로 오류가 난다(`../../orders/20260722.md`
> §"PR 메타데이터 일괄 지정"). 우회는 REST API 직접 호출
> (`gh api -X PATCH repos/edwardkim/rhwp/issues/{n}`, `.../assignees`,
> `.../requested_reviewers`). **`gh issue edit` 가 같은 제약을 받는지는 확인되지 않음**
> — 실패하면 같은 REST 우회를 쓴다.

### 5-2. ② 열린 PR 확인 (이차 방어선)

```bash
gh pr list --repo edwardkim/rhwp --state open --limit 100 --search "<이슈번호>"
```

**이슈 assignee 가 비어 있어도 PR 이 이미 열려 있을 수 있다.** 사고 2 가 정확히
그 경우다 — #3897 이 35분 먼저 열려 있었고 이슈는 비어 있었다.

> [!IMPORTANT]
> **`--limit` 을 항상 명시한다.** `gh pr list`·`gh issue list` 의 기본 limit 은 30 이라
> 조회 자체가 잘린다. 이 저장소는 그것으로 실사고를 냈다 —
> `../../orders/20260722.md`: *"처음에 30건만 처리하고 완료로 보고하는 사고가 있었다.
> `gh pr list` 기본 limit 이 30 이라 조회 자체가 잘렸다."*
> [README](README.md) §3-2 의 볼륨 수치 불일치도 같은 부류로 보인다.

### 5-3. ③ 겹치는 열린 PR 의 접합면 확인

이슈가 다르더라도 **같은 파일·같은 표를 건드리면 충돌한다.** 착수 전에 접합면을 보고,
겹치면 [선등재 패턴](pre_registration_pattern.md)을 쓸 수 있는지 판단한다.

```bash
# 열린 PR 이 건드리는 파일 전부
for n in $(gh pr list --repo edwardkim/rhwp --state open --limit 100 --json number -q '.[].number'); do
  gh pr view "$n" --repo edwardkim/rhwp --json files -q '.files[].path' | sed "s|^|#$n |"
done | sort -k2
```

겹치는 파일이 있으면 세 선택지가 있고, 순서가 있다.

1. **선등재로 접합** — 상대 PR 이 추가할 항목을 미리 등재해 두어 어느 쪽이 먼저
   머지돼도 후속 수정이 없게 한다. 성립 조건은 [선등재 패턴](pre_registration_pattern.md) §5.
2. **적층(stacking)** — 베이스 PR 을 본문에 명시하고 그 위에서 딴다.
   `../../manual/agent_surface_playbook.md` §2-5 의 지시다. 다만
   [#3719](https://github.com/edwardkim/rhwp/issues/3719) §7 이 **5단 체인의 직렬 의존**을
   리스크로 못박았다 — 맨 아래가 막히면 위 전부가 대기한다. **체인은 3단 이하.**
   [#3796](https://github.com/edwardkim/rhwp/issues/3796) §6 은 더 강하게 *"브랜치는 항상
   `upstream/devel` 기준. 적층 금지"* 라고 적는다. **두 문서가 어긋난다 — 어느 쪽이
   현행인지는 확인되지 않음**(§11).
3. **순서 대기** — 상대가 머지될 때까지 이슈로만 예약한다.
   [#3719](https://github.com/edwardkim/rhwp/issues/3719) §7 권고가 이것이다:
   *"신규 PR 을 잠시 멈추고 머지·리베이스에 집중 — 슬롯이 빌 때까지 다음 조각은
   이슈로만 예약"*.

### 5-4. 워크트리 격리는 별개 문제다

[#3796](https://github.com/edwardkim/rhwp/issues/3796) §6 이 *"조각마다 전용 워크트리.
공유 트리에서 두 작업이 `src/main.rs` 를 건드리면 반드시 깨진다"* 로 못박는다. 같은
문서 §1 이 그 비용을 실측으로 적는다(R4: 콜드 빌드 8분).

**워크트리 격리는 두 세션이 서로의 컴파일을 깨지 않게 한다. 같은 일을 두 번 하는 것은
막지 못한다.** 사고 1·2 는 브랜치가 각각 달랐고(따라서 워크트리도 별개였을 가능성이
높다) 그래도 났다. 두 방어는 층이 다르다 — 격리는 **작업 중** 간섭, 할당은 **착수 시점**
중복을 막는다.

## 6. 중복이 드러났을 때 — 판정 기준

### 6-1. 나중 것이 이기는 게 아니다

사고 1 에서 나중에 열린 #3903 이 남았고, 사고 2 에서 먼저 열린 #3897 이 남았다.
**시간 순서는 기준이 아니다.**

#3902 가 실제로 쓴 문장이 기준이다 — *"#3903 이 이 PR 을 **완전히 포함**하고, 더
낫습니다."* 판정은 **포함 관계**로 내렸다.

### 6-2. 판정 우선순위

[#3914](https://github.com/edwardkim/rhwp/issues/3914) §3 이 제안한 순서를 그대로 채택하고,
두 사고에 역으로 대입해 검증한다.

| 순위 | 기준 | 무엇을 보는가 |
|---|---|---|
| 1 | **범위 포함** | 한쪽의 수정 지점 집합이 다른 쪽을 진부분집합으로 포함하는가 |
| 2 | **검증 깊이** | red→green 실증이 있는가, 회귀 가드를 남기는가, 인접 스위트 무회귀를 봤는가 |
| 3 | **접합 비용** | 다른 열린 PR 과의 충돌이 적은 쪽, 선등재·적층이 이미 된 쪽 |

**사고 1 대입**: 1순위에서 결판났다. `marked()` 부착 4곳 ⊂ 7곳, 지도 선언
`{raw, before}` ⊂ `{raw, masked, before}`. 2순위도 같은 방향이었다 — #3903 은
`src` 만 devel 로 원복한 RED 를 실측했다(`provenance_contract` 4종 실패, 그중 2종은
**기존 가드가 레시피 추가만으로 물기 시작한 것**). #3902 는 *"새 가드의 red→green 을
로컬에서 보이지 못했습니다"* 라고 스스로 적었다.

**사고 2 대입**: 1순위 — `+250/-10`(#3897) vs `+186/-0`(#3904), 거부 지점이 더 많고
실패 경로 stdout 처리(G1)까지 함께 다룬다. 다만 **완전한 포함은 아니었다** — #3904 의
근인 서술 3분해와 "G1·G2 는 하나의 근인" 판정은 #3897 에 없다(§3-4). 즉 사고 2 는
**1순위로 결판나지 않는 사례**였고, 그래서 §6-3 의 인계가 더 중요했다.

### 6-3. 판정 기준에 **넣지 않는** 것

- **개설 시각** — 먼저 연 쪽이 이긴다는 규칙은 "일단 열고 보자"를 유도한다.
  큐 볼륨 문제(§7)를 악화시킨다.
- **줄 수** — `+409` 가 `+85` 보다 낫다는 보장은 없다. 사고 1 에서 줄 수와 판정이
  같은 방향이었던 것은 **결과지 근거가 아니다.**
- **작성자 선호·세션 순서** — 같은 계정이라 구분 자체가 없다.

### 6-4. 판정이 안 서면 — 합치지 말고 물어본다

두 PR 이 서로를 포함하지 않고 검증 깊이도 비슷하면, **한쪽을 골라 나머지를 급히
이식하지 않는다.** 급조한 합본은 어느 쪽의 검증도 물려받지 못한다. 이슈에 두 PR 의
범위 비교표를 올리고 메인테이너 판단을 요청한다 — **리뷰어 부하를 줄이는 게 목적인데
판단을 떠넘기는 것 아니냐**는 반론이 있을 수 있지만, 잘못 합친 PR 의 리뷰 비용이 더 크다.

## 7. 닫는 쪽이 남겨야 할 것

#3902 의 닫는 코멘트가 선례다(§2-4). 최소 네 가지를 남긴다.

### 7-1. 범위 비교표

**항목 단위로** 적는다. "더 낫다"는 판정이 아니라 서술이다.

```markdown
| | 이 PR | #<남는 PR> |
|---|---|---|
| <수정 지점 수> | 4곳 | **7곳** |
| <선언·계약> | A, B | 위 + **C** |
| <검증> | 가드 2개 | 가드 4중 + 별도 계약 파일 |
```

### 7-2. 판정 근거 한 문장

어느 기준(§6-2)으로 결판났는지 명시한다. "포함 관계"인지 "검증 깊이"인지 적어야
다음 사람이 같은 판단을 재사용한다.

### 7-3. 닫는 쪽에만 있는 산출물의 인계 — **브랜치와 커밋 해시까지**

이게 가장 자주 빠진다. 두 사고 모두 **닫히는 쪽에만 처리결과문서가 있었다.**

| 사고 | 닫힌 PR | 닫힌 쪽에만 있던 산출물 | 인계 방법 명시 |
|---|---|---|---|
| 1 | #3902 | `mydocs/report/task_m100_3885_report.md` (+89) | 브랜치 `task/3885-envelope-provenance-marker`, 커밋 `e54f16e14` |
| 2 | #3904 | `mydocs/report/task_m100_3884_report.md` (+58) | 브랜치 `task/3884-unknown-flag-rejection`, 커밋 `d0a1dc360` |

저장소 규약은 **이슈등록 → 분석 → 코드변경 → 처리결과문서 → PR** 순서다. 남는 쪽에
처리결과문서가 없으면 그 PR 은 규약 미충족 상태로 남는다. **닫는다고 산출물이
사라지면 안 된다** — 브랜치·커밋을 적어 두면 `git cherry-pick <해시>` 로 회수된다.

> [!WARNING]
> 닫힌 PR 의 브랜치는 정리(삭제) 대상이다. **인계 커밋 해시를 코멘트에 적기 전에는
> 브랜치를 지우지 않는다.** 2026-08-04 기준 두 인계 커밋(`e54f16e14`·`d0a1dc360`)이
> 아직 접근 가능한지는 **확인되지 않음**(§11).

### 7-4. 자기가 놓친 것

#3902 는 `findings[].masked` 를 놓친 이유까지 적었다 — *"마스킹 결과도 영숫자만
가려질 뿐 하이픈·`@`·점 같은 구조 문자와 자릿수가 원문에서 옵니다."*

**놓친 항목만 적으면 목록이고, 놓친 이유까지 적으면 지식이다.** 이 한 문장이
"마스킹된 값도 문서 파생"이라는 판정을 다음 작업에 그대로 옮겨 준다.

### 8-2. 왜 10인가 — 리뷰어 부하

캡의 근거는 기여자 편의가 아니다. `../../orders/20260722.md` 가 폭주 당시를 기록한다.

- 5일간 300건 가까이 유입(07-19 **77** · 07-20 **62** · 07-21 **48** · 07-22 **100+**)
- 열린 PR 이 한때 **113건**, 대부분 한 사람 것
- **품질이 아니라 속도가 문제였다**: *"기여의 질이 문제가 아니다. 처리 완료 195건 중
  171건(88%)이 실제 반영됐고 순수 반려는 24건뿐이다. **유입 속도가 검토 속도를
  앞지르는 것이 문제**"*

**10 이라는 숫자 자체의 산출 근거(리뷰 처리량 실측 등)는 확인되지 않음.** 메인테이너
요청값이고, 이 문서는 그것을 규약으로 승계한다. 숫자를 바꾸려면 처리량 실측이 선행해야 한다.

### 8-3. 넘으면 무슨 일이 생기나 — 실측 3가지

`../../orders/20260722.md` 와 [#3719](https://github.com/edwardkim/rhwp/issues/3719) §7 에서.

1. **충돌 대량 발생 → 일괄 close.** `mergeable=CONFLICTING` **30건**을 리베이스 안내와
   함께 close 했다(잔량 122 → 92). 방침은 *"반려 PR 은 close 하고 기여자가 reopen 하게
   한다"* — *"열린 채로 두면 검토 가능한 것과 구분되지 않는데, 닫아 두면 리베이스가
   끝난 것부터 순서대로 다시 올라와 양쪽 진행이 분명해진다."*
   **큐가 길면 그 자체로 리베이스 노동을 생산한다** — 축 하나에서 *"17건 중 14건이 같은
   `mod.rs` 를 건드려 오래된 순서로 cherry-pick 해도 8건만 적용되고 9건이 충돌했다."*
2. **처리가 축 단위 배치로 바뀐다.** 개별 리뷰가 불가능해져 분류 도구(`pr_triage.sh`)와
   축 단위 통합 PR 로 전환됐다. **개별 PR 의 리뷰 품질이 배치 품질로 대체된다.**
3. **적층 체인의 직렬 의존.** #3719 §7 이 **5단 체인**(#3698 → #3701 → #3705 → #3710 →
   #3716)을 리스크로 기록한다 — 맨 아래가 막히면 위 4건이 전부 대기. **체인 길이 3단 이하.**

부수 효과 하나 더: 큐가 길면 **급한 수정이 뒤에서 대기한다.** #3719 §7 리스크 3 —
*"신규 기능 PR 이 안전 수정 PR 보다 앞에 쌓이면, 정작 급한 버그 수정이 뒤에서 대기한다."*

### 8-5. 기계로 강제할 수 있는가

**할 수 있는 것 — 감지.**

```bash
# 잔량
gh pr list --repo edwardkim/rhwp --author @me --state open --limit 100 --json number -q 'length'

# 최근 7일 유입 / 그중 머지
gh pr list --repo edwardkim/rhwp --state all --limit 500 \
  --search "author:@me created:>=$(date -d '7 days ago' +%F)" --json number,mergedAt \
  -q '[length, ([.[] | select(.mergedAt)] | length)] | @tsv'
```

`tools/agent_preflight.py` 가 붙일 자리다. 이 스크립트는 이미 **"모든 검사를 한 번에
돌리고 실패를 전부 모아서 보고"** 하는 구조(`Report.fail/ok/skip`)이고, 종료 코드
계약(0 통과 / 1 실패 / 2 사용법 오류)을 가진다. 캡 검사는 다음 성질을 가져야 한다.

- **경고(`skip`/soft fail)이지 차단이 아니다.** 캡은 "10건 내외"이지 하드 리밋이 아니다.
- **네트워크가 없으면 조용히 건너뛴다.** 현재 검사들은 전부 로컬(바이너리·소스)이라
  `gh` 의존은 새 축이다. 네트워크 실패로 선검사가 통째로 빨개지면 곧 우회당한다.
- **`--limit` 을 명시한다**(§5-2).

**할 수 없는 것 — 판정.** *"이 PR 이 저 PR 과 같은 일인가"* 는 기계가 어렵다.
파일 겹침은 **신호이지 증거가 아니다** — 같은 파일을 다른 이유로 고칠 수 있다.
`src/main.rs` 는 15,000줄이 넘고 이 저장소의 거의 모든 표면 작업이 그 파일을 건드린다.
겹침으로 자동 차단하면 오탐이 정상 작업을 막는다.

**그래서 감지는 기계, 판정은 사람이다. 자동 차단이 아니라 경고가 맞다.**

**중복 감지의 유일한 고신뢰 신호는 이슈 번호다.** PR 본문의 `#<번호>`·`Closes #<번호>` 는
기계가 정확히 읽는다. 이것은 겹침 추정이 아니라 **양쪽이 스스로 선언한 대상**이다.

```bash
# 같은 이슈를 대상으로 하는 열린 PR 이 둘 이상인지
gh pr list --repo edwardkim/rhwp --state open --limit 100 --json number,body \
  -q '[.[] | {n:.number, i:[(.body|scan("#[0-9]{3,5}"))]}]'
```

이 검사는 **오탐이 거의 없고**(선언 기반) **사고 두 건을 모두 잡았을 것이다** —
#3902/#3903 은 둘 다 본문에 `#3885`, #3897/#3904 는 둘 다 `#3884` 를 적었다.

### 8-6. 선검사의 큐 규율 검사 (구현)

`tools/agent_preflight.py` 는 이미 `Report.fail/ok/skip` 로 **모든 실패를 모아 한 번에
보고**하고 종료 코드 계약(0 통과 / 1 실패 / 2 사용법 오류)을 가진다. 큐 검사는 그
구조에 얹되 성질이 달라야 한다 — **기존 검사는 전부 로컬(소스·바이너리)이고 이것만
네트워크에 의존한다.**

| 성질 | 기존 검사 | 큐 검사 |
|---|---|---|
| 의존 | 소스 파일 · 빌드된 바이너리 | `gh` + 네트워크 + 인증 |
| 실패 의미 | 계약 위반 (고쳐야 함) | 규율 이탈 (판단 필요) |
| 실패 처리 | `rep.fail` (종료 코드 1) | **`rep.skip` 또는 경고 전용** |
| 네트워크 없음 | 해당 없음 | **조용히 건너뛴다** |

세 번째 줄이 핵심이다. `load_allowlist` 의 주석이 이 스크립트의 설계 철학을 적는다 —
*"헛울리는 검사기는 곧 무시당하고, 무시당하는 검사기는 없느니만 못하다."*
네트워크 실패로 선검사 전체가 빨개지면 다음 사람은 `--static-only` 로 우회하고,
그러면 **로컬 검사까지 함께 꺼진다.**

검사 항목은 셋으로 충분하다.

1. **잔량** — 열린 PR 수가 10을 넘으면 경고. 넘긴 건수와 함께 보고.
2. **동일 이슈 중복** — 열린 PR 본문의 `#<번호>` 를 모아 2건 이상 겹치는 이슈 보고.
   §8-5 의 고신뢰 신호다.
3. **미할당 착수** — 현재 브랜치 이름에서 이슈 번호를 뽑을 수 있으면
   (`task/<n>-…`·`wip/fix-<n>-…` 관습이 있다) 그 이슈의 assignee 가 비었는지 확인.
   **두 사고의 브랜치 이름 넷 모두 이 패턴을 만족한다** —
   `task/3885-envelope-provenance-marker` · `wip/fix-3885-provenance` ·
   `wip/fix-3884-flags` · `task/3884-unknown-flag-rejection`.

3번이 특히 값싸다. 브랜치 이름은 로컬에서 읽고, 확인은 `gh issue view` 한 번이다.

> [!NOTE]
> [#4106](https://github.com/edwardkim/rhwp/pull/4106)이 이 형태를
> `tools/agent_preflight.py::check_queue_discipline()`으로 구현했다. 잔량·선언 기반
> 중복·브랜치 잠금을 모두 경고 전용으로 보고하고, `gh` 부재·미인증·조회 실패는
> 조용히 건너뛴다. 외부 기여자의 잠금 코멘트는 `착수합니다 — <범위>` 형식만 인정해
> 회고의 단어 하나가 잠금으로 오인되지 않게 한다.

## 10. 이 규약이 못 막는 것

과장은 운영 문서의 가장 흔한 실패다. **하지 못하는 일**을 명시한다.

### 10-1. 이슈 없이 시작하는 작업

두 사고는 이슈가 있었기에 잠글 대상이 있었다. **이슈 없이 브랜치부터 파는 작업은
이 규약의 사각이다.** 저장소 규약(이슈등록 → 분석 → 코드변경 → 처리결과문서 → PR)이
이슈를 먼저 만들게 하므로 원칙적으로는 없어야 하지만, 규약이 지켜진다는 가정 자체가
이 문서가 부정하는 것이다.

### 10-2. 이슈가 다른데 같은 코드를 고치는 경우

`src/main.rs` 처럼 넓은 파일은 이슈가 달라도 겹친다. 이건 **중복이 아니라 충돌**이고,
다른 도구(누적 머지 검사·선등재·적층)의 몫이다.

### 10-3. 이슈 하나를 여럿이 쪼개는 경우

#3884 는 G1~G4 로 쪼개져 있었고 두 PR 이 각각 "G1·G2(최소)·G3" 와 "G1·G2" 를 집었다.
**부분 집합끼리도 겹친다.** assignee 는 이슈 단위라 이 입도를 표현하지 못한다.
해법 후보는 이슈 코멘트로 착수 범위를 선언하는 것인데, **실증되지 않았다**(§11).

### 10-4. 잠금의 방치

걸어 놓고 안 하면 큐를 막는다. 만료 규칙(예: N일 무활동이면 자동 해제)이 필요한데
**이 저장소에 그런 규칙은 없다** — 확인되지 않음.
