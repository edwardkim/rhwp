## 1. "자기 치유"란 무엇을 치유하는가

R98 의 문장은 "자기 치유 문서(깨진 링크·메타 자동 PR)"다. 괄호 안의 둘은 **가장 쉬운 둘**이고,
정작 이 저장소를 실제로 아프게 한 것은 셋째다.

### 1.1 세 층

| 층 | 무엇이 낡나 | 지금 잡히나 | 예 |
|---|---|---|---|
| **L1 링크** | 문서가 가리키는 경로 | **잡힌다** — `check_markdown_links.py` | 파일 이동 후 상대 링크 |
| **L2 메타데이터** | front matter 4필드 | **잡힌다** — `check_document_metadata.py` | `kind: contract`(미허용 값) |
| **L3 사실** | 산문이 말하는 내용 | **안 잡힌다** | "`edit` 하위는 3종" (실물 6종) |

**L1·L2 는 검사기가 이미 있다. 없는 것은 "돌게 하는 것"이다**(2.3).
**L3 는 검사기 자체가 없다.** 5절이 그것을 설계한다.

### 1.2 왜 L3 가 본체인가

L1 이 깨지면 클릭했을 때 404 가 난다 — **읽는 사람이 즉시 안다.**
L2 가 깨지면 문서 분류가 흐트러진다 — **불편하지만 오해를 낳지는 않는다.**
L3 가 깨지면 **읽는 사람이 틀린 사실을 참으로 받아들인다.** 그리고 그 사람이 에이전트라면
틀린 사실대로 행동한다.

실제 사례가 있다. `mydocs/tech/agent_security/README.md:62` 는 이렇게 말한다.

> **현재 `rhwp edit`의 하위 명령은 `fill-fields`·`replace-text`·`set-cell` 3종뿐이다**

실물은 6종이다.

```
$ ./target/release/rhwp edit --help
사용법: rhwp edit <fill-fields|replace-text|set-cell|insert-image|redact|sanitize> …
```

빠진 셋 중 하나가 **`redact`(개인정보 마스킹)** 다. **보안 축 문서가 보안 명령을 모른다.**
이 문서를 근거로 보안 검토를 한 에이전트는 `redact` 를 검토 대상에서 뺀다.

[#3886](https://github.com/edwardkim/rhwp/issues/3886) 이 2026-08-03 에 이미 지적했다
("보안 축 문서가 하루 만에 낡았다"). **2026-08-04 현재 문서는 그대로다.** 사람이 알아채는
것만으로는 고쳐지지 않는다는 증거다.

### 1.3 "치유"의 범위 — 무엇을 안 하는가

- **문서를 새로 쓰지 않는다.** 없는 문서를 기계가 만들지 않는다.
- **문서의 판단을 바꾸지 않는다.** "이 설계가 옳다"는 문장은 치유 대상이 아니다.
- **사실의 옳고 그름을 정하지 않는다.** 문서와 코드가 다를 때 **어느 쪽이 옳은지는
  기계가 모른다** — [드리프트 자동 감지](drift_detection.md) §6.1 의 논증이 그대로 적용된다.

즉 자기 치유는 **"기계가 계산할 수 있는 정답이 하나뿐인 것"만** 고친다. 6절이 그 경계다.

## 2. 지금 있는 것 — 실측

### 2.1 `scripts/check_markdown_links.py` (585줄)

**하는 일 — 전수:**

1. **내부 상대 링크 해석.** 인라인 링크(`INLINE_LINK_RE`)와 참조 링크(`REFERENCE_LINK_RE`)
   양쪽. 코드펜스 안은 건너뛴다(`FENCE_RE`).
2. **금지 경로 참조 검출.** `--forbid-path` 로 지정한 옛 경로를 새로 참조하면 실패.

4. **변경분 한정 검사.** `--changed-from <ref>` 로 merge-base 이후 변경 문서만.
5. **capability 등록부 형식 검증.** `mydocs/manual/agent_capability_registry.md` 의 표를
   파싱해 열 구성·ID 형식(`CAP-<N>`/`LEGACY-<9자리 SHA>`)·슬러그 형식·상태 어휘·중복·
   진입점 실파일 해석을 본다(`collect_capability_registry_errors()`, 파일 382행부터).

## 3. 층 1 — 깨진 링크

### 3.1 현재 상태: 0건

2.1 의 실측이다. **R98 의 링크 문제는 "지금 깨져 있다"가 아니라 "언제든 깨질 수 있고
아무도 모른다"** 이다. 2.3 이 그 이유다.

### 3.2 검사기가 구조적으로 못 보는 것

코드를 읽어 확인했다.

| 대상 | 상태 | 근거 |
|---|---|---|
| 외부 URL(`https://…`) | **안 봄** | `resolve_local_destination()` 이 `scheme`/`netloc` 있으면 `None` |
| 문서 내 앵커(`#절-제목`) | **안 봄** | 경로가 비면 `None` 반환. `urlsplit` 의 `fragment` 는 쓰지 않는다 |
| 코드펜스 안 경로 | **안 봄**(의도) | `FENCE_RE` 로 건너뜀 |
| 기본 범위 밖 문서 | **안 봄** | `DEFAULT_PATHS` 9경로 |

**앵커가 가장 위험하다.** 이 저장소의 문서는 절 참조가 많고(`#3719 §8`·`§6.6` 같은 표기),
Markdown 앵커 링크로도 쓴다. 절 제목이 바뀌면 링크는 **깨진 채로 조용히 산다** —
GitHub 은 없는 앵커로 가면 문서 맨 위를 보여줄 뿐 오류를 내지 않는다.

**외부 URL 은 일부러 안 보는 게 맞다.** 네트워크 검사는 느리고, 실패가 상대 서버 사정일 수
있고, CI 를 불안정하게 만든다. 다만 **GitHub 이슈·PR 링크는 예외 후보**다 —
`gh api` 로 확인 가능하고, 이 저장소 문서는 `#N` 참조에 크게 의존한다.

### 3.3 자동 수정 가능성

| 상황 | 정답이 유일한가 | 판정 |
|---|---|---|
| 대상이 redirect stub 으로 이동됨 | **○** — stub 의 `canonical:` 이 답을 준다 | **자동수정** |
| 대상 파일이 이름만 바뀜(내용 동일) | △ — 후보가 여럿일 수 있다 | 이슈기안 |
| 대상이 삭제됨 | ✕ | 이슈기안 |
| 앵커가 깨짐 | △ — 절 제목이 바뀐 것인지 삭제인지 모름 | 이슈기안 |

**첫 줄만 자동 수정한다.** 근거: `redirect_mapping()` 이 이미 옛경로→새경로 사상을
계산한다. 치환 결과가 유일하고, diff 가 한 줄이고, 의미가 변하지 않는다 —
[드리프트 자동 감지](drift_detection.md) §6.2 의 C1·C2·C3 를 동시에 만족한다.

## 4. 층 2 — 낡은 메타데이터

### 4.1 `last_verified` 로 낡은 문서를 찾을 수 있는가 — **거의 못 찾는다**

가장 먼저 떠오르는 방법은 "`last_verified` 가 N일보다 오래된 문서"다. 실측하면 무력하다.

```
$ grep -rl "^last_verified: 202[0-5]\|^last_verified: 2026-0[1-5]" \
    mydocs/manual mydocs/tech mydocs/troubleshootings --include=*.md | wc -l
0
```

**2026-06 이전인 문서가 0건이다.**

`mydocs/tech` 의 분포를 보면 이유가 보인다.

```
44  2026-07-17
31  2026-07-16
25  2026-08-03
14  2026-08-02
 4  2026-07-19
 …
```

**이 저장소의 문제는 "몇 년째 방치된 문서"가 아니다.** 문제는 **"본 지 2주 됐는데 그 사이
명령이 54→61 로 늘어난 문서"** 다. `mydocs/tech/README.md` 의 `last_verified` 가
`2026-07-19` 인데, [#3886](https://github.com/edwardkim/rhwp/issues/3886) 이 08-03 에 잰
표면은 명령 61 · `--json` 31 이다.

> **날짜만으로는 못 잡는다.** 필요한 것은 **"마지막 검증 이후 그 문서가 서술하는 대상이
> 바뀌었는가"** 다.

### 4.2 그래서 필요한 것 — 문서→대상 매핑

front matter 에 필드 하나를 더하는 것을 **제안**한다.

```yaml
---
kind: canonical
status: active
canonical: mydocs/tech/agent_security/README.md
last_verified: 2026-08-02
verifies:                       # 제안 — 이 문서가 서술하는 대상
  - src/main.rs
  - tests/hidden_text_contract.rs
---
```

그러면 감지가 결정론적이 된다.

> `verifies` 의 어느 경로든 **마지막 변경일이 `last_verified` 보다 나중**이면
> **"검증 필요"** 로 보고한다.

**오탐 위험.** `src/main.rs` 는 거의 매일 바뀐다. 그러면 그 문서는 매일 "검증 필요"가 된다 —
[드리프트 자동 감지](drift_detection.md) §7.1 의 헛울림이다. 완화 후보 셋:

1. **경로를 좁힌다.** 파일이 아니라 심볼·절 단위로. (기계 판정이 어려워진다)
2. **보고만 하고 이슈를 안 만든다.** 대시보드의 "검증 필요 문서 N편" 지표로만.
3. **L3 주장으로 대체한다.** 5절이 이것을 택한다.

**3번을 제안한다.** `verifies` 는 "이 문서가 낡았을 수 있다"만 말하지만, L3 주장은
**"이 문장이 틀렸다"** 를 말한다. 후자가 훨씬 유용하다.

즉 `verifies` 는 **L3 주장을 심지 못한 문서를 위한 차선책**으로 둔다. 필수가 아니라 선택.

### 4.3 지금 잡히는 것과 그 처리

2.2 의 오류 3건을 예로 판정한다.

| 오류 | 정답이 유일한가 | 판정 |
|---|---|---|
| `last_verified` **형식** 오류(`2026-8-4`) | ○ | **자동수정** |
| `canonical` **누락** | ✕ — 어느 문서를 권위로 둘지 판단 | 이슈기안 |
| 미허용 `kind: contract` | ✕ — **규약을 넓힐지 문서를 고칠지** | 이슈기안 |

세 번째가 흥미롭다. `kind: contract` 는 오타가 아니라 **의미 있는 분류 시도**로 보인다
(`envelope_provenance.md` 는 실제로 계약 문서다). 자동 수정기가 이걸 `reference` 로 바꾸면
**정보를 잃는다.** 옳은 처리는 "`ALLOWED_KINDS` 에 `contract` 를 추가할 것인가"를 **사람에게
묻는 것**이다.

## 5. 층 3 — 낡은 사실

**여기가 본체다.** 링크 검사로도 메타데이터 검사로도 안 잡힌다.

### 5.1 왜 어려운가

`agent_security/README.md:62` 의 "3종뿐이다"는 **완벽한 문서**다.

- 링크: 없음 → 링크 검사 통과
- front matter: 4필드 완비, `last_verified: 2026-08-02`(이틀 전) → 메타데이터 검사 통과
- 문법: 정상

**모든 검사를 통과하면서 틀렸다.** 산문이기 때문이다.

### 5.2 후보 세 가지와 판정

**(가) 산문 패턴 매칭.** `N종`·`N개`·`N가지` 를 정규식으로 찾아 근처 코드 심볼과 대조.

→ **버린다.** "3종"이 무엇의 3종인지 기계가 모른다. 이 저장소 문서에는 "표 3종"·"경로 3종"·
"가드 4중"이 산더미다. 오탐이 압도적이고, 오탐이 압도적인 검사기는 꺼진다.

**(나) 백틱 식별자 대조.** 문서 안 백틱 토큰을 CLI 표면 사전(명령 61 · 플래그 103 ·
하위 명령 목록)과 대조해 **없는 것을 말하면** 실패.

→ **부분 채택.** 유용하지만 D3 을 못 잡는다. D3 은 **빠뜨린** 사고다 — 없는 걸 말한 게
아니라 있는 걸 안 말했다. (나)는 "존재하지 않는 명령을 문서가 말함"만 잡는다.

**(다) 문서에 기계 검증 가능한 주장을 심는다.** 산문 옆에 검증 지시를 놓는다.

````markdown
<!-- verify: cli.subcommands(edit) == fill-fields,replace-text,set-cell,insert-image,redact,sanitize -->
> 현재 `rhwp edit` 의 하위 명령은 6종이다.
````

검사기는 **주석만 읽는다.** 산문은 읽지 않는다.

→ **채택.** 근거는 **이미 선례가 있다**는 것이다(2.1 의 5번). `check_markdown_links.py` 는
`agent_capability_registry.md` 의 표를 파싱해 ID 형식·중복·진입점 실파일 해석을 검증한다.
**구조화된 주장은 이 저장소에서 이미 기계가 검증한다.** (다)는 그 형식을 표에서 주석으로
일반화한 것이다.

### 5.3 주장 문법 — 제안

```
<!-- verify: <provider>(<인자>) <연산> <기대값> -->
```

| provider | 무엇을 계산하나 | 계산 주체 |
|---|---|---|
| `cli.commands()` | `capabilities` 의 명령 이름 집합 | 검사기 |
| `cli.subcommands(<명령>)` | usage 문자열의 `<a\|b\|c>` 파싱 | 검사기 |
| `cli.flags(<명령>)` | `capabilities` 의 `flags` 배열 | 검사기 |
| `cli.recordFields(<명령>)` | `capabilities` 의 `recordFields` | 검사기 |
| `mcp.tools()` | `capabilities --mcp` 의 도구 이름 | 검사기 |
| `fs.exists(<경로>)` | 파일 실재 | 검사기 |
| `test.exists(<함수명>)` | `tests/` 안 `fn <함수명>` | 검사기 |
| `wf.exists(<파일명>)` | `.github/workflows/` 안 파일 | 검사기 |

| 연산 | 뜻 | 실패 판정 |
|---|---|---|
| `==` | 집합이 정확히 같다 | 대칭차가 있으면 실패 |
| `>=` | 기대값이 계산값의 부분집합 | 기대값에만 있는 원소가 있으면 실패 |
| `count ==` | 원소 수가 같다 | 다르면 실패 |
| `exists` | 참이다 | 거짓이면 실패 |

예:

```markdown
<!-- verify: cli.subcommands(edit) == fill-fields,replace-text,set-cell,insert-image,redact,sanitize -->
<!-- verify: cli.commands() count == 61 -->
<!-- verify: cli.subcommands(inspect) == hidden-text,injection,unicode -->
<!-- verify: fs.exists(tools/agent_preflight.py) -->
<!-- verify: test.exists(capabilities_mcp_covers_every_json_command) -->
```

### 5.4 설계 원칙 넷

> **A1. 셈의 정의는 provider 가 소유한다. 문서는 소유하지 않는다.**
> "명령 61개"가 숨김 명령을 포함하는지 같은 정의는 **검사기 코드 한 곳**에 있어야 한다.
> 문서가 각자 세는 법을 적으면 문서 100편이 각자 다르게 센다.
>
> **A2. 주장은 산문 바로 위에 둔다.**
> 문서 맨 위에 몰아 두면 산문을 고칠 때 주장을 안 본다. 붙어 있어야 같이 고쳐진다.
>
> **A3. 주장이 실패하면 산문이 틀렸다고 단정하지 않는다.**
> `cli.subcommands(edit)` 가 6종인데 주장이 3종이면, **주장이 낡은 것일 수도 있고 실물이
> 잘못 늘어난 것일 수도 있다.** 6절이 이 갈래를 다룬다.
>
> **A4. 주장 없는 문서를 실패로 세지 않는다.**
> 481편에 주장을 한 번에 심을 수 없다. 대신 **커버리지 지표**를 낸다(5.6).

### 5.5 어디에 먼저 심는가 — 우선순위

전 문서에 심는 것은 비현실적이다. 순서는 **"틀렸을 때 피해가 큰 순"** 이다.

| 순위 | 대상 | 왜 |
|---|---|---|
| 1 | `mydocs/tech/agent_security/**` | 에이전트가 보안 판단의 근거로 쓴다. **실제 사고가 난 곳**(1.2) |
| 2 | `mydocs/manual/cli_commands.md` 계열 | 에이전트가 호출을 여기서 배운다 |
| 3 | `mydocs/tech/agent_runtime/**` · `bindings/**` | 봉투·계약 서술 |
| 4 | `mydocs/tech/README.md` 권위표 | 지도가 틀리면 전부 틀린다 |
| 5 | `README.md`·`AGENTS.md` 온보딩 절 | 첫인상 |

1·2 는 **`--json` 표면을 서술하므로 provider 가 이미 있다**(`capabilities`).
심는 비용이 가장 낮고 가치가 가장 크다.

### 5.6 커버리지 지표

주장 기반 검사의 약점은 **미탐**이다 — 주장이 없으면 안 본다. 그래서 지표가 필요하다.

| 지표 | 정의 |
|---|---|
| **주장 보유율** | 주장 1개 이상 가진 문서 / 대상 문서 |
| **주장 밀도** | 주장 수 / 문서 (우선순위 1·2 구간만) |
| **주장 실패율** | 실패한 주장 / 전체 주장 |

**주장 실패율이 0 으로 오래 유지되면 경계해야 한다** — 주장이 너무 느슨하다는 뜻일 수 있다.
`fs.exists()` 만 잔뜩 심으면 실패율은 영원히 0이다.

### 5.7 (나)를 부분 채택하는 지점

5.2 (나)는 D3 을 못 잡지만 **다른 것을 잡는다**: 문서가 존재하지 않는 명령·플래그를 말하는 경우.
이것은 에이전트를 직접 오작동시킨다(문서대로 호출 → usage error). 그리고 주장 주석 없이도
**전 문서에 적용 가능**하다.

**단, 오탐이 많다.** 백틱은 명령 이름 말고도 온갖 것에 쓰인다. 완화안:

- **whitelist 방식이 아니라 blacklist 방식으로 본다** — "`rhwp <토큰>` 형태로 쓰였는데
  그 토큰이 명령 목록에 없다"만 잡는다. `rhwp` 접두가 있어야 한다.
- 코드펜스 **안**도 본다(링크 검사와 반대). 명령 예시는 대개 펜스 안에 있다.

이 좁힌 형태라면 오탐이 낮을 것으로 보인다. **확인되지 않음 — 실제로 재어 보지 않았다.**

## 6. 자동 PR 의 범위 — 어디까지 기계고 어디부터 사람인가

### 6.1 판정 기준

[드리프트 자동 감지](drift_detection.md) §6.2 의 조건 셋을 그대로 승계한다.
**셋을 동시에** 만족할 때만 자동 수정한다.

> **C1** 정답이 유일하고 기계가 계산할 수 있다
> **C2** 되돌리기가 무료다(한 줄 diff)
> **C3** 표기만 고치고 의미를 바꾸지 않는다

### 6.2 층별 판정표

| 대상 | C1 | C2 | C3 | 판정 |
|---|:-:|:-:|:-:|---|
| L1 깨진 링크 — redirect stub 존재 | ○ | ○ | ○ | **자동수정** |
| L1 깨진 링크 — 대상 소실 | ✕ | ○ | ✕ | 이슈기안 |
| L1 깨진 앵커 | ✕ | ○ | ✕ | 이슈기안 |
| L2 `last_verified` 형식 오류 | ○ | ○ | ○ | **자동수정** |
| L2 `last_verified` **갱신**(날짜를 오늘로) | ✕ | ○ | ✕ | **금지** — 6.4 |
| L2 `canonical` 누락 | ✕ | ○ | ✕ | 이슈기안 |
| L2 미허용 `kind` | ✕ | ○ | ✕ | 이슈기안 |
| L3 `count ==` 숫자 하나 | ○ | ○ | △ | 조건부 자동수정 — 6.3 |
| L3 `==` 목록 불일치 | ○ | ○ | **✕** | 이슈기안 |
| L3 `fs.exists` 실패 | ✕ | ✕ | ✕ | 이슈기안 |
| 권위표 미등재 문서 | ✕ | ○ | ✕ | 이슈기안 |

### 6.3 `L3 count ==` 가 조건부인 이유

"명령 54개"를 "61개"로 바꾸는 것은 C1·C2 를 만족한다. C3 이 애매하다 —
**숫자를 바꾸면 주변 산문이 거짓이 될 수 있다.**

> "명령 54개 중 21개가 `--json` 을 지원해 **약 40%** 다."

`54→61` 만 고치면 "약 40%"가 틀린다(31/61 ≈ 51%). **자동 수정기는 그 문장을 읽지 못한다.**

완화안: 주장 주석에 **영향 범위**를 적게 한다.

```markdown
<!-- verify: cli.commands() count == 61 · scope: 이 문단 -->
```

`scope` 가 선언된 주장만 자동 수정한다. 선언이 없으면 이슈기안. **선언 책임을 문서 저자에게
둔다** — 저자만이 그 숫자가 어디까지 파급되는지 안다.

### 6.4 자동 PR 이 **절대** 건드리지 않는 것

| 대상 | 왜 |
|---|---|
| **`last_verified` 를 오늘로 갱신** | `last_verified` 의 정의는 "역할·canonical 관계를 마지막으로 **확인한** 날짜"(`CONTRIBUTING.md:323`)다. 기계가 날짜만 올리면 **확인하지 않고 확인했다고 적는 것**이다. 이 문서 전체를 무의미하게 만드는 단 하나의 수정이다 |
| **산문 문장 재작성** | L3 주장이 실패했을 때 문장을 다시 쓰는 것은 저술이다 |
| **보안 문서의 범위 확대**(`agent_security/**`) | 문서가 실물보다 좁게 쓰인 게 의도일 수 있다. 자동으로 넓히면 검증 안 된 명령을 보안 계약에 등재한다 |
| **`ALLOWED_KINDS` 등 통제 어휘 확장** | 규약을 자동으로 넓히면 검사기가 스스로를 무력화한다 |
| **권위표(`mydocs/tech/README.md`) 행 추가** | 어느 주제 아래 어떤 문구로 넣을지가 편집 판단이다 |
| **redirect stub 생성** | 문서 이동은 사람의 결정이다 |

**첫 줄이 가장 중요하다.** `last_verified` 자동 갱신은 유혹적이고(대시보드가 예뻐진다)
치명적이다. 이 축 전체가 "문서가 실물과 맞는가"를 묻는데, 그 질문의 답을 기계가 위조하게 된다.

### 6.5 자동 PR 의 형태

- **묶음 1건.** 층 1·2·3 의 자동 수정을 **주 1회 한 PR** 로 합친다.
  근거: 열린 PR 캡 10건(#3719 §7·#3796 §6)이 이 저장소의 제약이고,
  #3907 운영 규칙 2 가 "이 지도는 큐를 늘리는 면허가 아니다"라고 못박는다.
  드리프트 12건에 PR 12개를 열면 그날로 캡을 깬다.
- **라벨** `autofix/docs`.
- **본문에 반드시 싣는 것**: 각 수정의 (a) 원인 주장·검사, (b) 재현 출력,
  (c) **기계가 판단하지 않은 것**.
- **초안(draft)으로 연다.** 사람이 열어 보고 ready 로 올린다.

### 6.6 이슈 기안 쪽 — 중복 방지

[드리프트 자동 감지](drift_detection.md) §8.3 의 `drift-key` 규약을 공유한다.
문서 축의 키 형태:

```
doc:L3:mydocs/tech/agent_security/README.md:cli.subcommands(edit)
```

같은 키의 이슈가 열려 있으면 새로 열지 않는다. 닫힌 키가 다시 감지되면 **재발**로 보고한다 —
재발은 가드가 없다는 뜻이므로 그 자체가 정보다.

## 7. 이 축의 자기 적용

이 문서와 형제 문서들도 같은 규칙을 받는다. 자기 적용을 안 하는 규약은 곧 무시된다.

- 이 축의 문서는 **front matter 4필드 완비**(`kind: canonical`·`status: active`·`canonical`·
  `last_verified: 2026-08-04`). `kind` 는 `ALLOWED_KINDS` 안의 값만 쓴다 — 4.3 의
  `kind: contract` 사례를 반복하지 않는다.
- 이 축의 문서가 인용한 **모든 수치는 실측 명령과 함께** 적었다. 명령이 없는 수치는 없다.
- **아직 심지 않은 것**: 이 문서들에 5.3 의 `<!-- verify: -->` 주석을 심지 않았다.
  **문법이 확정되지 않았기 때문**이다. 확정되지 않은 문법을 먼저 뿌리면 나중에 481편을
  다시 고쳐야 한다. 8절 P2 가 그 순서다.
- **이 문서가 인용한 사실 중 가장 빨리 낡을 것**: 명령 61 · MCP 도구 39 · `--json` 31 ·
  `edit` 하위 6종. 이들은 전부 5.3 의 provider 로 검증 가능한 형태로 적었다.

4. **앵커 검사의 비용.** 3.2 에서 앵커가 가장 위험하다고 봤지만, 절 제목→앵커 slug 변환
   규칙(GitHub 방언)을 정확히 구현하는 비용을 산정하지 않았다.
5. **GitHub `#N` 참조 검증을 켤지.** 3.2 참조. 네트워크 왕복이 늘고 rate limit 이 걸린다.
6. **`verifies:` front matter 필드의 필요성.** 4.2 에서 차선책으로 남겼지만, L3 주장이
   충분히 퍼지면 불필요할 수 있다. 성급히 필드를 늘리면 그 필드가 낡는다.
7. **자동 PR 이 열린 PR 캡에 포함되는가.** #3719 §7 의 "10건 내외"가 draft·autofix 를
   포함하는지 불명.
8. **`scope:` 선언의 실효성.** 6.3 의 완화안이 실제로 저자에게 부담이 되지 않는지 모른다.
