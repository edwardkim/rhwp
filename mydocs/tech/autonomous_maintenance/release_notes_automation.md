# 릴리스 노트 자동 작성 — 무엇까지 기계가 쓸 수 있나

로드맵 [#3907](https://github.com/edwardkim/rhwp/issues/3907) **R97** 의 설계 문서다.
R97 의 등급은 **[가설]** 이고 이 문서는 그 등급을 올리지 않는다. 여기 적힌 자동화는
**구현된 적 없다.**

이 문서의 결론을 먼저 적는다.

> **릴리스 노트 전체를 기계가 쓸 수는 없다. 기계가 쓸 수 있는 것은 "무엇이 바뀌었나"의
> 절반과 "계약이 깨졌나"의 전부다. "왜"는 못 쓴다.** 그리고 이 저장소에는 "왜"를
> 끌어올 원천(커밋→PR 역참조)이 **구조적으로 끊겨 있다**(§5.2).

증거 표기는 [야간 자율 정비 사이클](nightly_cycle.md) §0 과 같다 —
**[실측] [기록] [설계] [미확인]**.

## 1. 지금은 어떻게 만들어지는가

자동화 설계 전에 **대체하려는 대상**을 실측한다.

### 1.1 CHANGELOG.md — 손으로 쓴다

**[실측]** `CHANGELOG.md` 의 `## [Unreleased]` 섹션은 **비어 있다**. 즉 항목이 개발
중에 누적되지 않고 **릴리스 시점에 한꺼번에 작성**된다.

**[실측]** v0.8.1 항목의 섹션 어휘:

```
### 렌더 정정
### CLI — 계약 정합
### CLI — 신규 기능
### studio
### 의존성
### 알려진 문제
```

v0.8.2 는 여기에 `### 확장 인쇄 복구` 가 추가된다 — **섹션 이름이 릴리스마다 다르다.**
고정 템플릿이 아니라 **그 릴리스의 이야기에 맞춰 짓는다.**

### 1.2 GitHub 릴리스 본문 — CHANGELOG 를 다듬어 다시 쓴다

**[실측]** `gh api repos/edwardkim/rhwp/releases` 로 최근 5건을 봤다.

| 태그 | 발행 | 본문 길이 |
| --- | --- | --- |
| v0.8.2 | 2026-07-26 | 840자 |
| v0.8.1 | 2026-07-26 | 1,998자 |
| v0.8.0 | 2026-07-25 | 1,383자 |
| v0.7.19 | 2026-07-17 | 953자 |
| v0.7.18 | 2026-07-10 | 1,030자 |

**[실측]** `.github/release.yml` **이 없다.** GitHub 의 자동 릴리스 노트 생성
설정이 없다는 뜻이다. 본문에도 자동 생성 산물인 `## What's Changed` /
`**Full Changelog**` 블록이 없다. **전부 사람이 쓴 산문**이다.

**[실측]** v0.8.2 본문은 CHANGELOG 항목을 **경어체로 바꾸고** 끝에 CHANGELOG 링크를
붙인 형태다. 즉 원천은 하나(CHANGELOG)이고 릴리스 본문은 그 파생이다.

### 1.3 그래서 자동화의 목표물은 무엇인가

**[설계]** 대체 대상은 GitHub 릴리스 본문이 아니라 **CHANGELOG 항목**이다.
릴리스 본문은 그 파생이므로 원천이 좋아지면 따라온다.

## 2. 근거로 쓸 수 있는 것 — 저널·diff 실측

### 2.1 커밋 메시지 — 규약 준수율은 높다

**[실측]** `gh api "repos/edwardkim/rhwp/commits?sha=devel&per_page=100"` 로
`devel` 최근 **100커밋**의 제목을 뽑았다.

| 구분 | 건수 |
| --- | --- |
| 전체 | 100 |
| 머지 커밋 (`Merge ...`) | **19** |
| 비-머지 커밋 | **81** |
| 그중 `type:` / `type(scope):` 접두가 있는 것 | **79** |
| 한글 접두(`문서:`)를 쓴 것 | **2** |
| 접두가 아예 없는 것 | **0** |

**[실측]** 타입 분포(비-머지 81건):

| 타입 | 건수 | 비율 |
| --- | --- | --- |
| `docs` | **32** | 39.5% |
| `fix` | 16 | 19.8% |
| `ci` | 10 | 12.3% |
| `test` | 8 | 9.9% |
| `feat` | 5 | 6.2% |
| `style` | 3 | 3.7% |
| `explain` | 3 | 3.7% |
| `poc` | 2 | 2.5% |
| `문서` | 2 | 2.5% |

두 가지가 눈에 띈다.

1. **어휘가 표준 밖으로 확장돼 있다** — `explain`·`poc` 는 Conventional Commits 의
   표준 타입이 아니다. 그리고 한글 접두가 2건 섞여 있다. 기계가 접두를 파싱하려면
   **이 저장소의 실제 어휘**를 써야지 표준 목록을 가져오면 5건을 놓친다.
2. **최다 타입이 `docs`(39.5%)** 다. 그리고 `docs` 는 릴리스 노트에 **들어가면 안 되는**
   것이 대부분이다. 즉 커밋의 40%는 자동 분류의 첫 관문에서 버려야 한다.

### 2.2 이슈 참조 — 절반이 없다

**[실측]** 비-머지 81건 중 제목에 `#숫자` 가 있는 것은 **32건(39.5%)** 이다.

나머지 49건은 제목만 보고는 어느 이슈 소관인지 알 수 없다. 본문에 있을 수는 있으나
**확인하지 않았다 [미확인]**.

이 숫자가 뜻하는 것: **"이슈 번호로 항목을 묶는다"는 전략은 60%에서 실패한다.**

## 3. 사용자가 보는 변화 vs 내부 리팩터 — 기계가 가를 수 있나

이게 R97 의 핵심 질문이다. 답은 **"접두 하나로는 못 가른다"** 이고, 근거는 반례다.

### 3.1 접두가 배신하는 실측 반례

**[실측]** 위 100건에서 뽑은 실제 제목들이다.

| 커밋 제목 | 접두가 시키는 분류 | 실제 |
| --- | --- | --- |
| `fix(preflight): 선언 flags 검사가 스키마 출력 명령을 스스로 미구현으로 신고한다` | 버그 수정 → 노트에 넣음 | **기여자 도구 내부.** 사용자 무영향 |
| `fix(build/#3890): rhwp-subsecond 를 feature 로 분기 — --workspace 빌드 복구` | 버그 수정 → 넣음 | **빌드 구성.** 사용자 무영향 |
| `ci(#3890): 가드를 워크스페이스 전체로 확장 — #3664 의 -p 제약 해소` | CI → 버림 | 기여자에게는 의미 있음 |
| `docs(M18~M20): 바인딩 동등성 계약 4편 — Python·Node 표류 20건` | 문서 → 버림 | **"표류 20건"은 사용자 영향 사실**이 문서 안에 있다는 뜻 |
| `test(#3891): C ABI 표면 계약 가드 + C# 래퍼 rhwp_read_text 표류 정정` | 테스트 → 버림 | 제목 뒤쪽에 **정정**이 들어 있다 |
| `style(security): 악성 코퍼스 회귀 테스트 rustfmt 포맷 정리` | 스타일 → 버림 | 맞다. 버리는 게 옳다 |

마지막 한 줄만 접두와 실제가 맞는다. **접두의 정확도는 이 표본에서 6분의 1이다.**
(표본 6건은 내가 눈으로 고른 것이고 무작위가 아니다 — **접두가 배신하는 사례를
찾으려고 고른 것**이므로 이 비율을 일반 정확도로 읽으면 안 된다 **[편향 있음]**.)

### 3.2 그럼 무엇에 의존하나 — 신호 3개

**[설계]** 접두 하나 대신 신호 셋을 합성한다. 신호마다 **누가 만들었나**가 다르고,
그게 신뢰도를 정한다.

| 신호 | 누가 만드나 | 신뢰도 | 무엇을 말해 주나 |
| --- | --- | --- | --- |
| **S1. 접두** | 사람이 손으로 | 낮음 — 사람이 잘못 붙일 수 있고 어휘가 흔들린다(§2.1) | 의도 |
| **S2. 변경 경로** | 기계가 안다(diff) | **높음** — 틀릴 수 없다 | 어느 계층인가 |
| **S3. 계약 diff** | 기계가 실행해서 얻는다(§4) | **가장 높음** — 자기증명적 | 소비자가 깨지나 |

**S2 가 S1 보다 강한 이유**: 접두는 선언이고 경로는 사실이다. 선언과 사실이 다르면
사실을 믿는다. 이건 이 저장소가 이미 다른 데서 쓰는 원칙이다 — **[기록]**
자기서술 드리프트 가드(#3838·#3903 계열)가 하는 일이 정확히 "선언과 실물 대조"다.

**[실측]** 경로 → 계층 매핑의 재료도 이미 있다. `scripts/pr_triage.sh` 의 `axis_of()`
함수가 경로를 축으로 접는 표를 갖고 있다(`src/parser/hwpx/*` → hwpx,
`rhwp-studio/*` → studio, `tests/*` → test 등). **[설계]** 릴리스 노트용 분류는 이
표를 재사용하되 목적이 다르므로 다시 접는다.

**[설계]** 사용자 가시성 판정표:

| 경로 | 기본 판정 |
| --- | --- |
| `src/**` (파서·직렬화·렌더·모델) | **가시** — 출력이 바뀐다 |
| `src/main.rs`, CLI 표면 | **가시** — 명령·플래그·봉투 |
| `rhwp-studio/**`, `rhwp-chrome/**`, `npm/**` | **가시** — 별도 섹션 |
| `bindings/**` | **가시** — 단, 해당 바인딩 소비자만 |
| `tests/**` | 비가시 (예외: 계약 테스트가 바뀌면 §4 로 넘긴다) |
| `mydocs/**`, `docs/**`, `*.md` | 비가시 |
| `.github/**`, `tools/**`, `scripts/**` | 비가시 |
| `Cargo.toml`, `Cargo.lock` | **의존성 섹션** — 실측대로 CHANGELOG 에 그 섹션이 있다 |

**[설계]** 그리고 **S3 이 S1·S2 를 이긴다.** 계약이 바뀌었으면 경로가 무엇이든
접두가 무엇이든 릴리스 노트에 들어간다. 이유는 §4.

### 3.3 합성 규칙

**[설계]**

```
if S3 가 변화를 보고했다      → 반드시 포함, "계약 변경" 섹션 (사람 검토 필수)
elif S2 가 비가시 계층         → 제외 (단 목록에는 남긴다)
elif S2 가 가시 계층           → 포함 후보. 섹션은 S2 가, 성격은 S1 이 정한다
else                           → 미분류로 사람에게 넘긴다
```

**마지막 줄이 중요하다.** 애매한 것을 추측으로 채우지 않는다. 이건 이 저장소의
기존 원칙과 같다 — **[기록]** `extract-data` 는 "애매하면 추정하지 않고 null"
(PR #3806)을 계약으로 삼는다. 같은 규율을 여기에도 적용한다.

## 4. 계약 변경은 특별 취급한다

### 4.1 왜 특별한가

일반 변경은 사용자가 못 보고 넘어가도 손해가 작다. **계약 변경은 소비자를 깨뜨린다.**
그리고 이 저장소의 1급 소비자는 사람이 아니라 에이전트다 — **[기록]** `llms.txt` 가
"AI 에이전트가 1급 소비자다"라고 선언한다. 에이전트는 릴리스 노트를 안 읽고
**봉투를 파싱한다.** 봉투가 조용히 바뀌면 조용히 깨진다.

### 4.2 무엇이 계약인가 — `capabilities` 실측

**[실측]** 빌드된 `rhwp` (v0.8.2) 의 `capabilities` 출력 구조:

| 항목 | 값 |
| --- | --- |
| 최상위 키 | `batch`, `commands`, `exitCodes`, `formats`, `jsonContract`, `schemaVersion`, `tool`, `untrustedContent`, `untrustedFields`, `version` (10개) |
| `schemaVersion` | `1.0` |
| `version` | `0.8.2` |
| `commands` | **61개** |
| 카테고리 분포 | query 8 · export 18 · edit 3 · serve 1 · batch 1 · diagnostic 25 · internal 5 |
| `exitCodes` | `0`~`4` (5개) |
| `jsonContract` 하위 키 | `failure`, `provenance`, `schemaPolicy`, `stdout`, `textSecurity` |
| 모든 명령의 `recordFields` 합 | **278개** (명령 간 중복 포함) |

**[실측]** 명령 하나의 모양:

```json
{"batch": true, "category": "query", "flags": ["--json"], "json": true,
 "name": "info",
 "recordFields": ["schemaVersion","source","format","sizeBytes","version",
                  "sections","pageCount","paraCount","fonts","title"],
 "summary": "문서 메타(포맷·버전·페이지/문단 수·폰트·제목) 표시"}
```

**즉 계약의 기계 가독 사본이 이미 있다.** R97 자동화가 새로 만들 것이 아니라
**이미 있는 것을 릴리스 간에 대조**하면 된다.

### 4.3 릴리스 간 대조는 실행 가능한가

**[실측]** 릴리스 자산이 붙어 있다. v0.8.2 의 자산 목록:

```
rhwp-v0.8.2-linux-x86_64.tar.gz
rhwp-v0.8.2-macos-aarch64.tar.gz
rhwp-v0.8.2-macos-x86_64.tar.gz
rhwp-v0.8.2-windows-x86_64.zip
SHA256SUMS.txt
```

**[기록]** 이 자산은 `.github/workflows/release-binary.yml` 이 태그 `v*` push 에
자동 생성한다(4플랫폼 matrix).

따라서 **[설계]** 절차는 이렇다:

```
1. 직전 릴리스 자산에서 rhwp 바이너리를 받는다   (SHA256SUMS 로 검증)
2. old_caps = <직전 바이너리> capabilities
3. new_caps = <이번 빌드>     capabilities
4. 두 JSON 을 구조 대조한다
```

**[미확인]** 이 절차를 실제로 돌려 보지 않았다. 자산 이름과 워크플로 존재는 실측이지만,
**과거 릴리스 바이너리가 `capabilities` 를 지금과 같은 모양으로 뱉는지는 확인하지
않았다.** 특히 `capabilities` 자체가 릴리스를 거치며 진화했다면(#3357·#3329 계열
**[기록]**) 대조기는 **자기가 대조하려는 스키마의 변화**를 먼저 다뤄야 한다.

### 4.4 대조 항목과 파괴성 판정

**[설계]**

| 대조 항목 | 추가 | 삭제 | 값 변경 |
| --- | --- | --- | --- |
| `commands[].name` | additive | **breaking** | — |
| `commands[].flags[]` | additive | **breaking** | — |
| `commands[].recordFields[]` | **주의**(§아래) | **breaking** | — |
| `commands[].category` | — | — | **주의** — 소비자가 카테고리로 라우팅하면 깨진다 |
| `commands[].batch` / `.json` | additive | **breaking** | **breaking** |
| `exitCodes` 키 | additive | **breaking** | **breaking** — 같은 코드의 뜻이 바뀌는 것이 가장 위험하다 |
| `jsonContract.*` | additive | **breaking** | **breaking** |
| `untrustedContent` / `untrustedFields` | **주의** | **breaking** | **주의** |
| `schemaVersion` | — | — | 이 값이 **판정 결과와 일치하는지 교차 검증** |
| `formats` | additive | **breaking** | — |

**`recordFields` 추가를 "주의"로 두는 이유**: 봉투에 필드가 느는 것은 보통 안전하지만,
**엄격 파서**(미지 필드를 거부하는 소비자)는 깨진다. 그리고 이 저장소는 그런 엄격함을
스스로도 쓴다 — **[기록]** PR #3358 "ingest 미지 필드 거부 — 침묵 유실 대신 즉시 실패".
자기가 엄격하면서 소비자에게는 관대하길 기대할 수 없다.

**`schemaVersion` 교차 검증이 진짜 산출물이다.** 대조기가 breaking 을 찾았는데
`schemaVersion` 이 그대로면, 그건 릴리스 노트 문제가 아니라 **계약 위반**이다.
**[설계]** 이때 자동화의 출력은 릴리스 노트 항목이 아니라 **릴리스 차단 신호**다.
이 규약의 상위 근거는 **[기록]** planSchema 의 minor/major 진화 규약(#3808)과
`irSchemaVersion` 규약(#3691)이다. 같은 원칙을 `capabilities` 에 적용한다.

### 4.5 이 자동화의 선행 조건

**[실측]** `capabilities` 는 61개 명령을 서술한다. 그런데 **[기록]** 로드맵 R7·R8 은
아직 열려 있다 — `edit`·`inspect` 하위 명령이 자기서술에 등재되지 않았고(#3884 G4),
진단 명령 부류 판정이 미결이다(#3884 G2).

> **자기서술에 없는 표면은 대조에도 안 잡힌다.**

즉 §4 의 자동화는 **커버리지가 자기서술 커버리지와 정확히 같다.** 이건 한계가 아니라
**의존**이다. R97 을 R7·R8 보다 먼저 켜면, 대조기가 "변화 없음"이라고 보고하는데
실제로는 하위 명령 계약이 바뀌어 있는 상황이 생긴다. **거짓 안심은 안 하느니만 못하다.**

**[설계] 결론: R97 의 계약 대조는 R7·R8 이 닫힌 뒤에 켠다.**

## 5. 기계가 못 쓰는 것 — "왜"

### 5.1 "왜"는 diff 에 없다

**[실측]** v0.8.2 릴리스 본문의 한 항목:

> 인쇄 미리보기 문서(`print.html`)가 확장 빌드 산출물에 포함되지 않았습니다.
> v0.8.0 에서 인쇄 경로가 도입될 때 빌드 복사 목록에 빠진 것이 원인입니다 (#3433).

이 문장에서 diff 로 얻을 수 있는 것은 **"복사 목록에 `print.html` 이 추가됨"** 뿐이다.
나머지 전부 — 언제 빠졌는지, 왜 빠졌는지, 어느 버전부터 영향인지 — 는 **사람의 조사
결과**다. 그리고 릴리스 노트에서 사용자에게 실제로 쓸모 있는 부분은 그쪽이다.

**[실측]** 같은 릴리스의 `### 알려진 문제` 섹션은 **실패하는 E2E 테스트 2건**을 적고
"근인은 미진단 상태입니다"라고 밝힌다. 이건 diff 가 아니라 **CI 결과 + 판단**이다.
diff 에는 원천이 아예 없다.

### 5.2 PR 본문에서 뽑을 수 있나 — 이 저장소에서는 원칙적으로 어렵다

일반적인 저장소라면 답은 "그렇다"다. 머지 커밋이 `(#1234)` 를 달고 있으면
PR 본문을 API 로 끌어와 "왜"를 뽑을 수 있다. **이 저장소는 그 경로가 끊겨 있다.**

**[실측]** `kevin9327` 의 PR 60건을 `--state all` 로 조회했을 때
**`mergedAt` 이 null 이 아닌 것은 0건**이다.

**[실측]** 그런데 같은 내용이 `devel` 커밋에 들어와 있다:

| 닫힌 PR (mergedAt=null) | devel 커밋 제목 |
| --- | --- |
| #3882 | `fix(envelope): info 가 건너뛴 것을 숨기고, structure 에 snake_case 가 섞여 있다 (#3880 T1·T3)` |
| #3875 | `fix(wmf): POLYLINE/POLYGON 의 음수 NumberOfPoints 가 capacity overflow 패닉` |
| #3877 | `docs(M21): 퍼징 운영 문서 4편 — 인프라는 있는데 아무도 안 돌리고 있었다` |

**[실측]** 그리고 지금 열린 PR 중 #3912 의 제목이
`Kevin PR 9건 누적 통합: CLI 계약·agent 문서·provenance` 다.

**해석**: 기여 PR 은 머지 버튼이 아니라 **메인테이너의 통합 브랜치**를 거쳐 들어온다
(`Merge pull request #3895 from edwardkim/review/kevin9327-20260803` 같은 머지 커밋이
실측된다). 그 결과:

- 커밋 제목의 `(#3880)` 은 **이슈** 번호이지 PR 번호가 아니다.
- 따라서 **커밋 → 원 PR 역참조가 없다.**
- 즉 "커밋에서 PR 을 찾아 본문의 '왜'를 뽑는다"는 표준 경로가 **이 저장소에서는
  기본적으로 성립하지 않는다.**

(제목 일치와 통합 PR 제목에 근거한 해석이다. 커밋 단위로 원 PR 을 확정 대조하지는
않았다 **[미확인]**.)

### 5.3 그래도 뽑고 싶다면 — 필요한 것

**[설계]** 두 갈래뿐이다.

| 갈래 | 무엇이 필요한가 | 비용 |
| --- | --- | --- |
| **A. 통합 커밋에 원 PR 을 적는다** | 통합 시 커밋 trailer 추가 — 예: `Origin-PR: #3882` | 메인테이너 절차 변경. **사람의 습관을 바꾸는 비용** |
| **B. 이슈를 경유한다** | 커밋 제목의 `(#3880)` → 이슈 본문에서 "왜"를 뽑는다 | 절차 변경 없음. 대신 **[실측] 제목에 이슈 참조가 있는 커밋은 39.5%뿐** |

B 는 절반 이상에서 실패하고, A 는 사람의 절차를 바꿔야 한다.
**어느 쪽도 공짜가 아니다.** 그리고 이건 R97 이 스스로 해결할 수 없다 —
**릴리스 노트 자동화의 성패가 커밋 규약에 달려 있다**는 뜻이고, 그게 이 절의 결론이다.

**[설계]** B 를 쓰더라도 이슈 본문을 그대로 붙이면 안 된다. 이슈는 조사 과정이고
릴리스 노트는 결론이다. 기계가 이슈에서 뽑을 수 있는 것은 **인용 후보**까지이고
**고르는 것은 사람**이다.

## 6. 그래서 무엇을 자동화하나 — 3층 산출물

**[설계]** 자동화의 산출물을 하나의 완성된 노트로 잡지 않는다. 층을 나눈다.

### L1. 기계 사실 (100% 자동, 사람 편집 불필요)

| 산출 | 원천 | 신뢰도 |
| --- | --- | --- |
| **계약 diff 표** (§4.4) | `capabilities` 릴리스 간 대조 | 자기증명적 |
| `schemaVersion` 정합 판정 | 위 대조 결과 vs 선언값 | 자기증명적 |
| **의존성 bump 목록** | `Cargo.lock` diff | 기계적. **[실측]** CHANGELOG 에 이미 `### 의존성` 섹션이 있어 형식이 정해져 있다 |
| **커밋 분류 원장** | 100건 전수 + S1·S2 신호 | 분류는 제안, 원장 자체는 사실 |
| 통계 (커밋 수·타입 분포·기여자) | 커밋 조회 | 사실 |

L1 은 **사실이므로 검수가 필요 없다.** 다만 §4.5 대로 **커버리지가 자기서술
커버리지에 묶여 있다** — 그래서 L1 산출물에는 항상 *무엇을 못 봤는지*를 같이 적는다.

### L2. 초안 (자동 생성, 사람 편집 전제)

- 섹션별 항목 초안 — §3.3 합성 규칙의 출력
- "포함 후보" 와 "제외" 두 목록을 **둘 다** 낸다. 제외 목록이 없으면 사람이
  놓친 것을 확인할 방법이 없다
- **미분류** 목록 — 애매한 것을 여기 모은다. 추측으로 분류하지 않는다

### L3. 사람만 (기계는 자리만 만든다)

| 항목 | 왜 사람인가 |
| --- | --- |
| **왜** — 근인·경위 | §5.1. diff 에 원천이 없다 |
| 릴리스 요약 한 문단 | v0.8.2 의 "핫픽스입니다. v0.8.0 부터 영향받았습니다" 같은 판단 **[실측]** |
| **영향 범위** 서술 | "어느 버전부터 영향" 은 조사 결과다 |
| `### 알려진 문제` | §5.1. CI 결과 + 미진단 판단 |
| 업그레이드 안내 | 계약 diff 가 breaking 을 보고했을 때 **무엇을 어떻게 고쳐야 하는지** |
| 섹션 이름 짓기 | **[실측]** 릴리스마다 다르다. 그 릴리스의 이야기를 아는 사람이 짓는다 |

**[설계]** 자동화의 성공 기준은 "노트를 다 썼다"가 아니라
**"사람이 L3 에만 시간을 쓴다"** 이다.

### 6.1 언제 어디서 도나

**[설계]** 태그를 밀 때 도는 것은 **늦다**. 태그 시점에 breaking 을 발견하면
릴리스를 되돌려야 한다.

| 시점 | 무엇을 | 왜 그때인가 |
| --- | --- | --- |
| **PR 마다** | 계약 diff 만 (직전 릴리스 기준) | 깨뜨린 PR 을 그 자리에서 안다. **[기록]** 이 저장소가 이미 쓰는 방식 — 자기서술 가드가 PR 단위로 돈다 |
| **야간 사이클** | 누적 계약 diff + 커밋 원장 갱신 | 릴리스 직전에 몰리지 않게. [nightly_cycle.md](nightly_cycle.md) §2.3 의 대안 C 검토와 같은 이유 |
| **릴리스 준비** | L1 확정 + L2 초안 생성 | 사람이 L3 을 쓰기 시작하는 시점 |
| **태그 push** | 아무것도 새로 판정하지 않는다 | 이미 확정된 것을 붙일 뿐. 여기서 처음 알면 늦다 |

**[설계]** 그리고 이 파이프라인은 **`release-binary.yml` 을 건드리지 않는다.**
그 워크플로는 바이너리를 만드는 일만 하고, 노트는 별개 산출물이다.
한 워크플로가 두 일을 하면 하나가 실패할 때 나머지도 막힌다.

### 6.2 언어

**[실측]** `CHANGELOG.md` 와 `CHANGELOG_EN.md` 가 둘 다 있고, 릴리스 본문 말미가
두 파일을 모두 링크한다.

**[미확인]** 영문판이 어떻게 유지되는지는 확인하지 않았다(U4).

**[설계]** 그래도 원칙은 정할 수 있다. **L1 은 언어 중립**이다 — 계약 diff 표는
필드 이름과 기호이지 산문이 아니다. 즉 자동화는 **한 번 만들어 두 언어에 쓴다.**
번역 비용이 드는 것은 L2·L3 이고, 그건 사람 몫이다. 자동화가 영문 산문을 생성해
두 파일이 서로 어긋나기 시작하면, 그 순간부터 **CHANGELOG 자체가 드리프트 대상**이
된다.

## 7. 수용 기준과 반증 조건

**[설계]** 이 자동화가 쓸모 있다고 말하려면 아래가 관측돼야 한다.

| # | 기준 | 재는 법 |
| --- | --- | --- |
| A1 | 계약 diff 가 **사람이 놓친 breaking 을 최소 1건** 잡는다 | 릴리스 회고에서 대조 |
| A2 | L1 산출물에 사람이 손대지 않는다 | 편집 diff 가 0 |
| A3 | L2 초안의 **제외 판정**이 뒤집히는 비율이 20% 미만 | 사람이 되살린 항목 수 / 제외 수. 20%의 근거는 없다 **[근거 없음]** |
| A4 | 릴리스 준비 시간이 준다 | 준비 시작~발행 벽시계 |

**반증 조건 [설계]**: A3 이 50%를 넘으면 §3.3 의 합성 규칙이 틀린 것이다.
그때는 규칙을 고치는 게 아니라 **L2 를 끄고 L1 만 남긴다** — 사실은 여전히 쓸모 있고
잘못된 분류는 검수 비용을 늘리기만 한다.

이 문서가 근거를 대지 못한 것들이다. 채우기 전에는 설계를 구현으로 옮기지 않는다.

| # | 무엇 |
| --- | --- |
| U1 | **과거 릴리스 바이너리가 지금과 같은 `capabilities` 모양을 내는지** — §4.3. 대조기의 전제인데 실행 검증 안 함 |
| U2 | 커밋 → 원 PR 매핑이 실제로 몇 % 복원 가능한지 — §5.2 는 제목 일치에 근거한 해석이다 |
| U3 | 커밋 **본문**(제목이 아니라)에 이슈 참조가 얼마나 있는지 — 제목만 실측했다 |
| U4 | `CHANGELOG_EN.md` 가 어떻게 유지되는지 — 존재는 확인했으나 동기화 방식은 안 봤다 |
| U5 | 릴리스 본문과 CHANGELOG 사이에 자동 변환이 있는지 — 손으로 다듬은 것으로 **보이지만** 확인 안 함 |
| U6 | `docs` 39.5% 중 릴리스 노트에 실제로 들어가야 할 비율 — 세지 않았다 |
