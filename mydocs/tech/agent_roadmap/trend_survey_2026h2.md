# 2026 하반기 에이전트 도구 동향 조사 — 로드맵 실공백 선별 (제안)

**질문**: 2026 하반기 시점의 에이전트 도구 동향에 비추어, R1~R100 로드맵에
**실제로 비어 있는** 표면이 무엇인가.

이 문서는 **제안**이다 — 어떤 항목도 로드맵 등급을 올리지 않고, 채택·번호
부여·트랙 편입 여부는 전부 메인테이너 몫이다(트랙 K 제안 PR #4211 과 같은
성격). 조사 시점은 2026-08-08 이고, 아래 출처의 접속일도 별도 표기가 없으면
같은 날이다.

## 선별 기준 (이 문서의 본체)

동향 하나가 제안이 되려면 다섯 관문을 전부 지나야 한다. 하나라도 걸리면
§6 제외 목록에 사유와 함께 남긴다 — **막 더하지 않는다.**

1. **출처 실재** — 동향 서술 전부에 URL+날짜가 붙는다. 출처 없는 동향은
   서술 자체를 하지 않는다.
2. **3판정 통과** — 로드맵 전 트랙·열린 PR 과 대조해 **이미 있음 / 부분 /
   공백**을 먼저 판정하고, 공백(또는 공백이 명확한 부분)만 제안한다.
   이미 있는 표면의 재제안은 드리프트 표면을 만든다(같은 목표의 두 번호가
   서로 갈라진다).
3. **논지 직접 기여** — "세계 1등 HWP 편집기·뷰어·에이전트 도구" 논지에
   직접 닿아야 한다. 경쟁 우위는 실명 비교가 아니라 원리로만 서술한다:
   기계가 검증 가능한 계약, 자기서술, 성공률의 실측 공표.
4. **착수 게이트 서술 가능** — 시작 전에 확보할 근거·판단을 지금 적을 수
   없으면 제안이 아니라 소망이다.
5. **캡 8** — 제안은 최대 8건. 이번 조사는 4건에서 멈춘다 — 기준 3·4를
   지나는 후보가 그만큼이었다.

## 1. 동향 5축 (실조사)

### 축 1 — 에이전트용 도구 설계 모범

Anthropic 의 도구 설계 가이드가 이 축의 1차 출처다: 도구는 API 래퍼가 아니라
고임팩트 워크플로를 겨눈 통합 표면이어야 하고, 응답은 페이지네이션·필터·절단
기본값으로 토큰 효율을 지키며, **오류 메시지는 불투명한 코드가 아니라 "무엇이
왜 틀렸고 다음에 무엇을 하라"는 행동 가능 서술**이어야 한다. 도구 개선은
감이 아니라 평가(held-out 태스크의 에이전트 성공률)로 닫는다.

- Anthropic, *Writing effective tools for agents* (2025-09-11):
  <https://www.anthropic.com/engineering/writing-tools-for-agents>
- 해설·확장 논의 (2025-11-05): <https://tianpan.co/blog/2025-11-05-writing-tools-for-agents>

**rhwp 함의** — 통합 표면(digest·batch·scan)·절단 규약(S7)·자기서술은 이미
같은 방향이다. 갈리는 곳은 오류 쪽이다: MCP 오류에는 `nextCall` 이 있지만
CLI 실패 봉투는 stderr 산문에 머문다(§2 대조표, §5 T4).

### 축 2 — "실패할 수 없는 도구"

두 갈래가 뚜렷하다. ① **입력 쪽**: constrained decoding(구조화 출력 강제)이
런타임 표준 계층으로 내려앉아, 도구 인자의 스키마 위반 자체가 클라이언트
측에서 사라지는 추세다 — 도구 제공자의 몫은 스키마를 기계가 읽게 공표하는
것까지다. ② **부작용 쪽**: 파괴 작업에는 dry-run·승인 게이트·멱등성 키를,
선언에는 도구별 안전 힌트를 다는 것이 관례가 됐다 — MCP 스펙은 이를
`annotations`(readOnlyHint·destructiveHint·idempotentHint·openWorldHint)로
표준화했고, "힌트는 신뢰 경계가 아니다(신뢰 못 할 서버가 거짓 선언 가능)"는
주의까지 스펙 본문에 있다.

- 구조화 출력 벤치마크 (arXiv 2025-01): <https://arxiv.org/html/2501.10868v1>
- 문법 제약 생성 해설 (2026-04-16):
  <https://tianpan.co/blog/2026-04-16-grammar-constrained-generation-output-reliability>
- MCP tool annotations (스펙 개정판 2025-06-18):
  <https://modelcontextprotocol.io/specification/2025-06-18/server/tools>
- 멱등 도구 설계 관례 (2026): <https://www.agentpatterns.ai/agent-design/idempotent-agent-operations/>,
  <https://www.digitalapplied.com/blog/agent-rollback-checkpoint-patterns-2026-engineering-reference>

**rhwp 함의** — dry-run(redact·run 계열)·CAS(R22~R24 설계)·원자적 쓰기·스키마
공표(planSchema R81)는 이미 있거나 트랙에 있다. 없는 것은 **MCP 도구
주석**이다: `src/mcp_serve.rs` 에 annotations/Hint 문자열이 0건(2026-08-08
grep 실측) — 16종 도구 중 무엇이 읽기전용이고 무엇이 파일을 바꾸는지를
클라이언트가 기계로 읽을 자리가 비어 있다(§5 T3).

### 축 3 — 자기수정 루프

"에이전트의 자기 판단을 믿지 말고 독립 검증기를 루프에 넣어라"가 2026 년
문헌의 합의다. 검증기 주도 self-healing 이 의미적 침묵 실패를 0%로 내린
반면 비검증 경로는 13~17%의 침묵 실패를 남겼다는 실측이 있고, 자기 저작
검증(자기가 만든 기준으로 자기를 채점)은 신뢰할 수 없다는 반대편 실증도
나왔다. 요지는 하나다 — **판정은 산문이 아니라 실행(종료 코드·스키마 검사·
재독 대조)이어야 한다.**

- 검증기 주도 self-healing (arXiv 2026-06): <https://arxiv.org/pdf/2606.01416>
- 자기 저작 검증의 비신뢰성 (arXiv 2026-07): <https://arxiv.org/html/2607.24300v1>

**rhwp 함의** — 이 축은 rhwp 가 동향을 따라가는 것이 아니라 동향이 rhwp 의
기존 선택을 확인한다: 독립 `verify` 게이트(#4186·#4192), 편집 축 `--verify`
재독 대조, render-diff 회귀 게이트(#4200), red→green 종료 코드로 PR 여부를
정하는 봇(R91). 새 항목 불요 — §2 대조표에 "이미 있음"으로 기록한다.

서버는 `PROTOCOL_VERSION = "2025-06-18"` 단일 지원으로 고정돼 있고
(`src/mcp_serve.rs:24·32` 실측), R74 계약 테스트는 확정판이 바꾼 `-32002`

지침과 이미 정합이다 — 손수 구현이 방향을 미리 맞춘 사례로 기록해 둔다.

### 축 5 — 평가·벤치마크

에이전트 도구의 품질 주장이 "태스크 성공률 실측"으로 수렴하고 있다.
τ-bench(2024-06)가 도구·에이전트·사용자 상호작용의 성공률 벤치마크를
표준화했고 τ²-bench 가 이중 통제로 확장했다. MCP 축에서는 서버 33종·도구
188종·질의 600건 규모의 MCP-AgentBench, Scale 의 MCP-Atlas 리더보드
(2026-04 개정: 도구 호출 예산 100회제)가 "도구 제공자의 표면 위에서
에이전트 성공률을 재는" 형식을 굳혔다. Anthropic 가이드(축 1)도 도구
개선의 판정을 held-out 평가 성공률로 두라고 못박는다.

- τ-bench (arXiv 2024-06): <https://arxiv.org/pdf/2406.12045> ·
  τ²-bench: <https://github.com/sierra-research/tau2-bench>
- MCP-Atlas (2026-04 개정): <https://labs.scale.com/leaderboard/mcp_atlas>
- MCP 평가 하니스 해설 (2026): <https://futureagi.com/blog/step-by-step-guide-mcp-evaluation-2026/> ·
  <https://www.confident-ai.com/blog/llm-agent-evaluation-complete-guide>

**rhwp 함의** — 로드맵에 성능 회귀(R54)·생태계 지표(R90)·온보딩 판정
실험(R100)은 있지만, **"표준 HWP 작업 N종을 에이전트가 몇 % 성공하는가"를
재는 태스크 벤치마크는 어느 트랙에도 없다**(§5 T2). 세계 1등 논지를 실명
비교 없이 실증하는 수단이 정확히 이 형식이다 — 자기 표면 위의 성공률을
재현 가능하게 공표하는 것.

## 3. 선별 제안 (4건)

T 번호는 이 문서 안의 후보 명칭일 뿐 로드맵 번호가 아니다 — 채택 시 번호·
트랙 배치는 메인테이너가 정한다. 형식은 README 여섯 칸 중 다섯을 쓴다
(등급은 부여하지 않는다).

### T1 MCP 스펙 개정 추종 대장

- **무엇** — MCP 개정판(2025-11-25·2026-07-28 확정판)별 변경 항목 × rhwp
  현행 표면의 전수 대조표를 만들고, 항목마다 이행/유예/불요 판정과 근거를
  기록하는 추종 대장을 세운다.
- **왜 (출처)** — 확정판(2026-07-28)이 코어를 stateless 로 바꾸고 rhwp 가
  계약 테스트로 고정한 표면을 직접 건드린다: initialize 핸드셰이크 제거,
  리소스 부재 `-32002` → `-32602`(#4116 이 고정한 값), Tasks 확장 이관,
  Roots·Sampling·Logging 폐기 예고
  (<https://modelcontextprotocol.io/specification/2026-07-28/changelog>).
  서버는 `2025-06-18` 단일 지원(`src/mcp_serve.rs:24·32` 실측)이라, 추종
  판정 없이는 "손수 구현이 스펙 유지보수를 떠안는다"(R75 의 자인)의 대가가
  침묵 속에 쌓인다.
- **기존 항목과의 관계** — R75(rmcp 교환비, #4206 의 D-41 '미도입 유지'
  제안)의 **입력**이다: 개정마다 손수 이행 비용이 대장에 수치로 쌓이면
  R75 재평가가 감이 아니라 데이터 위에서 돈다. R71~R74 계약 테스트가 이행
  대상 목록의 원천이고, 새 표면 제안이 아니라 판정 절차 제안이다.
- **착수 게이트** — ① 확정판 원문 전수 검토(변경 항목 목록화 — 요약 기사
  아니라 스펙 changelog 기준). ② 추종 범위 판단(메인테이너): 구식 개정판
  유지 지원을 언제까지 무엇으로 할지 — 클라이언트 생태계의 확정판 채택
  속도 실측이 판단 재료다.
- **DoD** — 대장 문서 1편: 개정 항목 × 현행 표면 대조 전수, 항목별 판정
  (이행/유예/불요+근거), `SUPPORTED_PROTOCOL_VERSIONS` 갱신 여부 결정 기록.
  이후 개정판 공개 시 대장 갱신이 절차로 남는다.

### T2 에이전트 태스크 벤치마크 스위트

- **무엇** — 표준 HWP 작업 N종(서식 채움·표 CSV 왕복·마스킹·대량 추출·
  안전 점검 등)을 태스크 정의 + 기계 판정 오라클로 고정하고, 에이전트가
  rhwp 표면만으로 각 태스크를 완주하는 성공률을 재는 하니스를 만든다.
- **왜 (출처)** — 도구 품질 주장의 통화가 태스크 성공률 실측으로 수렴했다:
  τ-bench(<https://arxiv.org/pdf/2406.12045>, 2024-06)·MCP-Atlas
  (<https://labs.scale.com/leaderboard/mcp_atlas>, 2026-04 개정)·Anthropic
  가이드의 held-out 평가 권고(2025-09-11). "세계 1등 HWP 에이전트 도구"
  논지를 실명 비교 없이 실증하는 수단이 정확히 이 형식이다 — 자기 표면
  위의 성공률을 재현 가능하게 공표하고, 하락을 회귀로 잡는다.
- **기존 항목과의 관계** — R100(30분 온보딩 실험)과 판정이 다르다: R100 은
  "처음 온 에이전트가 길을 찾는가", T2 는 "찾은 에이전트가 작업을 몇 %
  완주하는가". R54(성능 회귀)와도 다르다 — 속도가 아니라 성공률이다.
  재사용만 한다: 태스크 원천은 agent_task_playbook 8시나리오·공무원 업무
  21행, 판정 오라클은 verify `--expect`(#4186·#4192)·render-diff(#4200),
  코퍼스 발견은 scan(#4217). 성공률 수치는 R90 생태계 지표·R59 대시보드의
  자연 입력이 된다.
- **착수 게이트** — ① 태스크 선정 기준 합의: verify 로 기계 판정 가능한
  작업만 1차 편입(판정을 LLM 심판에 맡기면 축 3의 자기 저작 검증 함정을
  다시 밟는다). ② 실행 주체·비용 판단(메인테이너): 어떤 에이전트로 몇 회
  돌릴지 — CI 상시인지 릴리스 단위인지가 비용을 정한다.
- **DoD** — 태스크 N종 정의·오라클·재현 절차가 저장소에 있고, 최초 성공률
  실측 1회가 공표되며, 재실행이 같은 판정 기준으로 도는 것을 실증한다.

### T3 MCP 도구 주석(annotations) 선언

- **무엇** — 16종 MCP 도구 전부에 스펙 표준 `annotations`(readOnlyHint·
  destructiveHint·idempotentHint·openWorldHint)를 선언하고,
  `mcp_tool_definitions()` 단일 출처(R71)에 편입해 capabilities 파리티
  계약 테스트로 고정한다.
- **왜 (출처)** — 파괴 작업 선언 힌트는 MCP 스펙 표준 표면이고
  (<https://modelcontextprotocol.io/specification/2025-06-18/server/tools>),
  클라이언트들이 승인 게이트·자동 실행 판단의 입력으로 읽는 관례가 굳었다
  (축 2 출처). 현행 서버에는 annotations 선언이 0건이다(2026-08-08 grep
  실측) — 읽기전용 조회(`hwp_info` 류)와 파일을 바꾸는 편집(`hwp_doc_save`
  류)이 클라이언트에게 같은 얼굴로 보인다.
- **기존 항목과의 관계** — 새 능력이 아니라 기존 도구의 자기서술 1필드
  확장이다: R71 의 단일 출처 원칙·R6 의 선언↔실물 대조 공리를 그대로
  따른다. 트랙 B 의 "선언을 믿지 않는다"와도 정합 — 스펙 자신이 "힌트는
  신뢰 경계가 아니다"를 명시하므로, 주석은 게이트의 입력이지 보안 경계가
  아니라는 해석 규약을 함께 문서화한다.
- **착수 게이트** — 도구별 주석 값 실측 분류표: 무엇이 디스크를 바꾸고
  무엇이 멱등인지를 코드 경로로 확인해 채운다(추정 선언 금지 — 선언↔실물
  괴리를 새로 만들면 R5 의 재판이다).
- **DoD** — 전 도구 주석 선언 + "선언 값 ↔ 실제 부작용" 대조 계약 테스트
  (읽기전용 선언 도구가 파일시스템을 건드리면 red) + 해석 규약 문서화.
- **주의** — T1 과 접속: 확정판(2026-07-28)에서 annotations 표면이 어떻게
  움직였는지 T1 대장에서 먼저 확인하고 그 개정판 기준으로 선언한다.

### T4 실패 봉투 수복 힌트 일반화

- **무엇** — CLI 실패 경로(exit 1/2/3)의 봉투·stderr 에 MCP `nextCall` 과
  같은 어휘의 구조화 수복 힌트(다음 호출·왜)를 싣는 것을, 실패 부류별로
  선별 확장한다.
- **왜 (출처)** — "오류 메시지가 수복 루프의 수렴을 정한다"가 축 1 의 핵심
  권고이고(Anthropic 2025-09-11), 축 3 의 검증기 문헌도 실패 신호의 행동
  가능성이 self-healing 성공률을 가른다고 본다(arXiv 2606.01416). rhwp 는
  이 설계를 MCP 오류 8사이트(R72 `nextCall`)와 R22 설계(`preconditionFailed`
  +`nextCall`)에 이미 갖고 있으나 CLI 실패 봉투 일반에는 없다 —
  `nextCall` 방출부가 `src/mcp_serve.rs` 뿐임을 grep 으로 실측했다.
- **기존 항목과의 관계** — R72 의 일반화이자 R22 어휘의 선반영이다: CLI 와
  MCP·계획 거부가 같은 `nextCall` 모양을 쓰면 소비자가 한 어휘로 수복
  루프를 짠다. R4 의 실패 3면 계약(exit 2·stdout 0 B·stderr 명시) 위에
  얹는 확장이라 기존 계약을 깨지 않는다. 실패 사전
  (agent_troubleshooting_guide)의 증상→처방 지식이 힌트 내용의 원천이다.
- **착수 게이트** — ① 실패 부류 분류: 다음 행동이 **결정론적으로** 정해지는
  부류만 힌트 대상으로 선별(정해지지 않는 부류에 힌트를 지어내면 R72 가
  임계 밖 침묵으로 지켜온 "오제안 0" 원칙이 깨진다). ② 힌트의 자리 판단:
  exit 2(stdout 0 B 계약)에서는 stderr 에 실을지, 봉투를 내는 실패(run
  계열 exit 1/3)에서는 봉투 필드로 실을지 — R4 계약과의 정합 설계.
- **DoD** — 선별된 실패 부류 N종이 구조화 수복 힌트를 싣고, 힌트의
  `nextCall.name` 실존(호출부 책임)이 R72 와 같은 계약 테스트로 고정되며,
  오제안 0 원칙(대상 밖 부류는 침묵)이 테스트로 남는다.
