# 트랙 G — 바인딩·플랫폼 (R61~R70)

> **v0.8.4 정책 변경:** 이 문서는 Python·Node 바인딩과 신규 배포 채널을 검토하던
> 당시의 로드맵 근거로 보존한다. 해당 구현·테스트·공식 패키지는 #4655에서 철회됐으며,
> 현재 지원 표면으로 해석하지 않는다. 재도입은 안전 검증과 메인테이너의 명시적 채택이
> 선행돼야 한다.

**질문**: 다른 언어·플랫폼에서도 같은 계약인가 — 봉투·종료 코드·출처 표지가 언어
경계를 넘어도 같은 뜻인가.

바인딩은 본체 자기서술의 **첫 소비자**다(`test_envelope_parity.py` 머리말: 선언과
실제 봉투가 어긋나면 선언을 읽고 만든 코드가 실행 시점에 깨진다). 그래서 이
트랙의 질문은 "다른 언어에서도 도는가"가 아니라 "**같은 계약인가**"다. 파이썬
dataclass 매핑(R62)이 그 재사용의 바닥이고, WASM(R64~R65)이 플랫폼 경계를
시험한다. WASM 에서 배운 것 하나가 이 트랙의 태도를 요약한다 — **막힌 건 기능이
아니라 크레이트 경계였다.** 계약을 언어마다 다시 쓰지 않고 본체 것을 재사용하는
것(R68)이 표류를 막는 유일한 구조다.

## R61 Python·Node 표류 20건 해소 `[문서]`

- **한 줄** — 파이썬·노드 바인딩이 본체 계약에서 벌어진 표류 20건을 좁힌다.
- **지금** — #3879 에 표류 20건이 문서화돼 있고, 그중 **치명 3건은 실행으로 재현
  확인**됐다(선언과 실물이 갈려 바인딩 코드가 실행 시점에 깨지는 부류). 설계
  문서가 존재한다.
- **설계** — 표류 각 건에 수정 우선순위를 매기되 치명 3건을 먼저 닫는다. 바인딩은
  본체 계약을 **재생산하지 않고 재사용**하는 방향으로 좁힌다(R68 적합성 스위트가
  그 재사용 기구).
- **착수 게이트** — 표류 20건의 수정 우선순위 확정(치명 3건 선행). #3879 이 목록은
  주지만 순서는 아직.
- **DoD** — 치명 3건이 회귀 테스트로 닫히고, 나머지 17건이 우선순위대로 소진되며,
  각 건이 R68 스위트에 편입된다.
- **의존** — R62(바인딩 공통 기반), R68(재사용 기구).

## R62 파이썬 봉투→dataclass 기계 매핑 `[완료]`

- **한 줄** — `capabilities` 의 `recordFields` 선언에서 파이썬 dataclass 를 기계적으로
  얻는다.
- **지금** — M18 계열(#3691·#3692)이 바인딩 공통 기반을 놨고, 그 위에서 봉투 필드가
  dataclass 로 매핑된다. `mydocs/tech/agent_runtime/envelope_parity.md` 가
  봉투↔바인딩 정합의 원천 문서다.
- **설계(보장)** — 선언(`recordFields`)이 타입의 **단일 출처**다 — 손으로 dataclass 를
  쓰지 않으므로 선언과 타입이 구조적으로 어긋날 수 없다. 봉투는 `schemaVersion` 을
  싣고, 바인딩은 `SUPPORTED_SCHEMA_VERSION` 과 대조해 진화를 따라간다
  (`test_every_envelope_carries_schema_version`).
- **DoD** — 달성. 재발 방지는 R68 전수 스위트·R70 자동 생성 CI.
- **의존** — 없음(바인딩 축의 바닥).

## R63 PyPI/npm 릴리스 파이프라인 `[가설]`

- **한 줄** — 파이썬·노드 바인딩을 서명과 함께 PyPI·npm 으로 배포한다.
- **지금** — 없음. #4655에서 v0.8.2 이후 추가된 파이썬·Node 바인딩 코드와 공개
  레지스트리 배포 경로를 공식 업스트림 표면에서 함께 철회했다. 수요 실측(2026-08-09,
  #4327): #227 이 PyO3+PyPI 배포를 제안했고 그
  제안자가 서드파티 파이썬 바인딩을 직접 만들었으며, 루트 README 스스로 "PyPI
  배포 전"을 안내했다. 철회 전 파이썬 래퍼는 실행 바이너리를 `RHWP_BIN`으로
  요구했다 — 향후 재검토한다면 **휠에 플랫폼 바이너리를 동봉하는 파이프라인**이 이
  단계의 실체다([user_demand_survey_2026h2.md](user_demand_survey_2026h2.md)
  §4·§5 P1). 철회된 `@rhwp/node`도 같은 모양이었다 — 웹 축의
  `@rhwp/core`·`@rhwp/editor` 는 이미 npm 배포 중이라, 배포 격차는 에이전트 축에만
  남아 있다.
- **설계** — 트랙 D R38(바이너리 배포)·R67(버전 정책, 이 트랙)과 **같은 서명 인프라를
  공유**한다 — 바인딩 릴리스가 별도 서명 체계를 새로 세우면 신뢰 뿌리가 갈린다.
  버전은 R67 이 정하는 semver×스키마 규약을 따른다.
- **착수 게이트** — R67(버전 정책, 이 트랙)이 확정될 것 + 트랙 D R38 의 서명 인프라가
  존재할 것(같은 인프라 재사용, 새로 세우지 않음).
- **DoD** — 태그 하나로 서명된 바인딩이 PyPI·npm 에 올라가고, 설치본이 본체 버전과
  스키마 버전을 자기서술한다.
- **의존** — 트랙 G R67, 트랙 D R38.

## R64 WASM 에이전트 표면 `[문서]`

- **한 줄** — rhwp 의 에이전트 표면(명령·봉투·자기서술)을 WASM 으로 그대로 노출한다.
- **지금** — 설계 문서 존재: #3873·#3876 → `mydocs/tech/wasm_agent_surface/`
  (`README`·`self_description`·`zero_install_onboarding`)와 `mydocs/tech/agent_runtime/`.
  핵심 진단은 **"막힌 건 기능이 아니라 크레이트 경계였다"** — WASM 이 못 되던
  이유가 표면 설계가 아니라 크레이트 의존 구조라는 것.
- **설계** — 크레이트 경계 리팩터로 에이전트 표면을 WASM 대상에서 컴파일 가능한
  크레이트로 분리하고, 같은 봉투·같은 자기서술을 브라우저에서 낸다. 표면 명세는
  `agent_runtime/surface_spec.md`, 무설치 온보딩은
  `wasm_agent_surface/zero_install_onboarding.md` 가 이미 스케치돼 있다.
- **착수 게이트** — 크레이트 경계 리팩터의 **범위 승인**(어느 크레이트를 어떻게
  가를지 — 메인테이너 판단). 기능 추가가 아니라 경계 이동이라 승인이 선행이다.
- **DoD** — WASM 빌드가 CLI 와 동일한 `capabilities`·봉투를 내고, 파리티 테스트가
  두 표면에 같이 돈다.
- **의존** — 없음(경계 리팩터 자체가 이 단계).

## R65 브라우저 내 에이전트 데모 `[가설]`

- **한 줄** — 브라우저 안에서 에이전트가 WASM rhwp 를 MCP 브리지로 부르는 데모.
- **지금** — 설계만 존재: #3873 의 `browser_bridge` 설계
  (`mydocs/tech/wasm_agent_surface/browser_bridge.md`). 구현은 R64 크레이트 경계
  해소에 막혀 있다.
- **설계** — WASM 표면(R64) + MCP 브리지로 브라우저 안 에이전트가 문서를 열고
  편집·검사한다. 브리지는 무상태 도구부터 — 세션은 R57 안전성 감사 뒤로 미룬다.
- **착수 게이트** — R64 크레이트 경계 해소가 **머지**될 것. 그 전에는 브라우저에서
  부를 표면 자체가 없다.
- **DoD** — 브라우저 데모에서 에이전트가 실문서를 열어 봉투를 받고 편집을 반영하는
  것을 재현.
- **의존** — R64.

## R66 C-ABI/FFI 판단 `[가설]`

- **한 줄** — 파이썬·노드·WASM 밖의 언어에서 rhwp 를 부르는 C-ABI/FFI 표면을 낼지
  정한다.
- **지금** — 없음, 그리고 **수요 근거가 없다.** 현재 바인딩(파이썬·노드)과 WASM 이
  주요 소비 경로를 덮는다.
- **설계** — 미정(선행 근거: 파이썬·노드·WASM 밖에서 rhwp 를 부르려는 실제 요청이
  없다). C-ABI 는 안정성·수명 계약을 새로 들이므로, 실수요 없이는 유지비만 남는다.
- **착수 게이트** — C-ABI/FFI 를 요구하는 실제 사용처 1건 이상(예: Go·C++ 통합
  요청). 없으면 만들지 않는다.
- **DoD** — 판정이 문서화된다(만들면 안정 ABI 계약 + 스위트, 안 만들면 사유).
  "부류 없음"보다 판정이 낫다.
- **의존** — 없음.

## R67 버전 정책 canonical `[가설]`

- **한 줄** — semver(릴리스)와 스키마 버전(계약)의 이중 규약을 단일 정책으로 못
  박는다.
- **지금** — 스키마 버전이 **축마다 따로 굴러간다**(실측): `irSchemaVersion = "1.0"`
  (`src/ir_schema.rs`), `capabilitiesSchemaVersion = "1.1"`(`src/capabilities_schema.rs`),
  그리고 봉투 최상위 `schemaVersion = "1.0"`(바인딩이 `SUPPORTED_SCHEMA_VERSION` 으로
  대조). **capabilities 가 이미 1.1 로 앞서 나가 있다는 것 자체가 "각자 굴러감"의
  증거**다 — 이들 사이의 관계(무엇이 오르면 무엇이 따라 오르는가)를 규정한 정책은
  없다. (별도 `planSchemaVersion` 필드는 실측되지 않는다 — 계획도 봉투 최상위
  `schemaVersion` 을 탄다.)
- **설계** — 릴리스 semver × 스키마 버전의 이중 규약을 명문화한다: 어느 버전이
  하위호환을 보장하고, 스키마 bump 가 semver 에 어떻게 반영되는지. 트랙 I R83
  (스키마 레지스트리 단일 출처)이 이 버전들의 등록처가 되므로 **함께 설계**한다 —
  정책과 등록처는 한 몸이라 따로 세우면 또 갈린다.
- **착수 게이트** — 트랙 I R83(스키마 레지스트리)과 공동 설계 진입.
- **DoD** — 버전 정책이 canonical 문서로 서고, 각 스키마 버전이 레지스트리에서
  정책대로 검증된다.
- **의존** — 트랙 I R83.

## R68 바인딩 적합성 스위트 `[가설]`

- **한 줄** — 바인딩이 본체 계약 테스트를 **재사용**해 전수로 검증받는다.
- **지금** — #4655 철회로 공식 바인딩 적합성 스위트는 없다. 철회 전 파이썬
  `test_envelope_parity.py`의
  `test_declared_fields_actually_appear` 는 **대표 4개**(`info`·`export-text`·
  `fields`·`export-structure`)만 대조한다(docstring 이 "전 명령을 도는 대신 대표를
  고른 이유"를 밝힘). 본체는 이미 R6 에서 전수
  (`declared_record_fields_actually_appear_in_envelopes`)로 올라갔고, 바인딩 쪽은
  철회 당시까지 대표 표본에 머물렀다.
- **설계** — 본체 R6 전수 대조를 바인딩에서도 재사용하는 기구를 만든다: 계약
  테스트를 바인딩이 **베끼지 않고** 본체 오라클을 그대로 돌리게 한다. 그러면 R61 의
  표류 20건도 이 스위트 안에서 회귀로 고정된다.
- **착수 게이트** — R6 이 본체에 자리잡았을 것(완료) + **바인딩이 본체 계약 테스트를
  재사용하는 기구** 설계(베끼기가 아니라 재사용 — 베끼면 또 표류한다).
- **DoD** — 바인딩 스위트가 본체 recordFields 를 전수로 대조하고, 대표 표본 4개
  한계가 사라진다.
- **의존** — 트랙 A R6(완료), R61(표류 목록).

## R69 예제 실측 유지 체계 `[실측]`

- **한 줄** — 문서에 실린 예제가 깨진 채로 남지 않게 실행으로 검증한다.
- **지금** — #4655 철회로 공식 파이썬 예제와 그 실행 테스트는 없다. 철회 전에는
  예제 **01~09(9편)**가 존재했고(`bindings/python/examples/`
  `01_read_document`…`09_convert_audit`), `test_examples.py` 가 전 예제를 glob 으로
  잡아 ① 컴파일 ② docstring 실행법(`python examples/…`) ③ 인자 없이 부르면 exit 2
  (06 예외)를 검사하고, 01·02·03·05·06 은 실물 문서로 통합 실행까지 본다.
- **설계** — 예제는 "도는 문서"다: 깨진 예제는 문서 없는 것보다 나쁘다는 전제
  (`test_examples.py` 머리말)로, 새 예제는 같은 3검사 + 필요 시 통합 실행을
  자동으로 받는다.
- **착수 게이트** — 예제 드리프트 감지를 CI 게이트로 강제할지 판단 — 검사 본체는
  존재하나 CI 에서 red 를 내는 게이트로 걸려 있는지 확인이 선행.
- **DoD** — 예제 하나를 깨뜨린 가짜 브랜치가 CI 에서 red 가 되고, 예제 추가가
  자동으로 3검사를 받는다.
- **의존** — R62(바인딩 기반).

## R70 타입 정의 자동 생성 CI `[가설]`

- **한 줄** — 봉투 선언에서 타입 정의(파이썬 stub·노드 `d.ts`)를 자동 생성하고
  드리프트 0 을 CI 로 강제한다.
- **지금** — 없음. #4655 철회 전 R62가 dataclass 매핑을 놨으나, 그 생성을 CI에서
  돌려 **커밋된 타입과 선언의 드리프트를 0으로 막는 게이트**는 없었다.
- **설계** — 타입 생성기(`recordFields`→타입)를 CI 에서 돌려 산출물을 커밋본과
  대조: 다르면 red. R68 적합성 스위트가 "런타임 봉투↔선언"을 보고, R70 이 "정적
  타입↔선언"을 봐서 두 방향을 다 닫는다.
- **착수 게이트** — R68 적합성 스위트가 있을 것 + **타입 생성기의 존재 확인**
  (R62 매핑이 재실행 가능한 생성기인지, 일회성 산출인지 실측).
- **DoD** — 선언을 바꾸고 타입을 재생성하지 않은 가짜 브랜치가 CI 에서 드리프트
  게이트로 red 가 된다.
- **의존** — R62, R68.
