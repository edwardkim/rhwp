# 트랙 F — 대량·성능 (R51~R60)

**질문**: 규모에서 버티는가 — 문서 수·문서 크기·반복 호출이 커져도 계약과 성능이
무너지지 않는가.

규모는 주장이 가장 값싸고 반증이 가장 비싼 축이다 — "빠르다"·"큰 문서도 된다"는
측정 없이는 공수표다. 그래서 이 트랙의 두 기둥은 둘 다 수치다: batch(R51)가 문서
수 축을, 세션(R52)이 반복 호출 축을 각각 실측으로 세웠다. 나머지(R53~R60)는
대부분 **"어디서 깨지는지를 아직 안 재본 표면"**이고, 그래서 착수 게이트가
하나같이 "먼저 측정하라"로 수렴한다. bench 스스로가 밝히듯 절대 수치는 머신
의존이므로, 이 트랙에서 숫자는 항상 상대·재현 형태로만 계약이 된다.

## R51 batch 9 하위 명령 + 파일당 병렬 `[완료]`

- **한 줄** — 한 번의 호출로 폴더 전체를 9개 축 중 하나로 처리하고, 파일마다
  스레드를 태운다.
- **지금** — batch 하위 9종: `export-text`·`info`·`export-structure`·
  `export-tables`·`fields`·`search`·`extract-data`·`convert`·`fill`. 각 축은 단건
  명령과 같은 봉투를 파일당 NDJSON 한 줄로 내고, 축 전체 규약은 `capabilities` 의
  `BatchAxisContract`(`subcommands`·`flags`·`input`·`output`·`mcp`)로 자기서술된다.
  실측: 문서 271건을 3.0초에 — 파일당 스레드 병렬(측정 환경 threads=32,
  `--threads` 로 상한). 입력은 stdin 한 줄당 경로 하나.
- **설계(보장)** — 병렬은 **파일 경계에서만** 걸린다 — 한 문서 안에서 상태를
  공유하지 않으므로 경합이 구조적으로 없다. 오류도 데이터다: 실패한 파일은
  스트림을 끊지 않고 `batch` 오류 레코드로 실리며, R6 이 이 오류 레코드의 필드까지
  recordFields 전수 대조에 넣었다.
- **DoD** — 달성. 회귀 가드: `tests/batch_axes_contract.rs`·`batch_fill_contract.rs`·
  `batch_extract_data_contract.rs`.
- **의존** — 없음(대량 축의 바닥).

## R52 세션 경로 ×120.6 벤치 `[실측]`

- **한 줄** — 문서를 한 번 열어두고 여러 편집을 세션으로 흘리면, 무상태 호출 대비
  호출당 시간이 두 자릿수 배로 줄어든다.
- **지금** — #3624 실측: 무상태 경로가 호출당 82.1ms(매번 파싱·구성·직렬화),
  세션 경로가 호출당 0.68ms — **×120.6**. 세션은 `mcp-serve` 프로세스 메모리 안의
  문서 핸들을 재사용하므로 파싱이 첫 open 한 번으로 끝난다.
- **설계** — 이 수치는 "세션이 왜 있는가"의 정량 근거다. 무상태 도구와 세션 도구는
  매니페스트에서 층이 갈려 있고(`test_session_tools_are_not_duplicated_in_stateless_manifest`),
  섞이면 소비자가 비용 모델을 오판한다 — 그래서 수치는 계약(층 분리)과 짝으로만
  뜻이 있다.
- **DoD** — 달성(재현 절차가 #3624 에 있다).
- **의존** — 세션 기구(트랙 C 세션 수명·동시성, 트랙 H MCP 서버와 공유).

## R53 bench --json 계약 `[가설]`

- **한 줄** — `bench` 의 **성공** 출력에 기계가 읽는 봉투 계약을 준다.
- **지금** — R4(#3897)가 고친 것은 **실패 경로의 stdout 오염**뿐이다 — 수정 전
  `bench <문서> --json` 은 `--json` 을 파일 이름으로 접어 exit 1 + 배너 섞인 반쪽
  출력을 냈고, 지금은 전건 실패 시 산출물을 아예 안 낸다. 하지만 **성공 봉투
  계약은 아직 없다** — bench 는 `capabilities` 에 `json`·`recordFields` 를 선언하지
  않는 회색지대(트랙 A R8) 안에 있다.
- **설계** — 봉투 스케치: `{schemaVersion, samples[], metric, unit, note}`. bench
  출력이 스스로 밝히는 규약("절대 수치는 머신 의존, 상대·재현 지표로 해석")을
  봉투에도 명문화한다(수치 옆에 해석 표지). recordFields·출처 스윕·R6 전수 대조에
  편입.
- **착수 게이트** — 트랙 A R8(진단 명령 부류 판정)이 (a)안(자기서술 등재)으로
  갈릴 것. (b)안(자기서술 밖 부류)이면 bench 는 봉투 계약 대상이 아니므로 이
  단계는 접는다.
- **DoD** — `bench --json` 이 계약 봉투를 내고 capabilities 에 선언되며, 드리프트
  가드 시야에 든다.
- **의존** — 트랙 A R8·R4, R52(측정 대상).

## R54 성능 회귀 CI 게이트 `[가설]`

- **한 줄** — bench 기준선과 대조해 성능이 뒷걸음치면 CI 가 막는다.
- **지금** — 없음. bench 는 수치를 내지만 그 수치를 **기준선으로 고정해 회귀를
  판정하는 층이 없다**. 그리고 bench 스스로가 "절대 수치는 머신 의존"이라
  밝히므로, 순진하게 절대값을 비교하면 CI 러너 변동에 오탐이 터진다.
- **설계** — 두 층으로 가른다: ① 기계 계약 봉투(R53)로 수치를 파싱한다. ② 기준선
  안정화 — 절대 임계가 아니라 상대 지표(같은 러너에서 직전 대비 비율)나 통계적
  밴드로 회귀를 정의한다. 축적된 기준선 데이터가 R59 대시보드로 이어진다.
- **착수 게이트** — R53(기계 계약 봉투)이 있을 것 + **측정 환경 변동성을 흡수하는
  방법**이 설계로 확정될 것(무엇을 기준선으로, 어떤 밴드로 회귀를 판정하는지). 이
  답 없이는 러너 노이즈에 우는 오탐 게이트가 된다.
- **DoD** — 성능을 의도적으로 퇴화시킨 가짜 브랜치가 회귀 게이트 1개로 red 가
  되고, 러너 노이즈로는 red 가 되지 않음을 실증.
- **의존** — R52·R53.

## R55 대형 문서 상한 실측·한계 공표 `[실측]`

- **한 줄** — 수백 MB·만 쪽 규모에서 어디가 먼저 깨지는지 측정하고 한계를 공표한다.
- **지금** — [`tools/scale_ladder.py`](../../../tools/scale_ladder.py)(합성 HWPX
  생성기+실측 러너, commit `837a8d19f`)와
  [`mydocs/report/scale_ladder_r1_20260808.md`](../../report/scale_ladder_r1_20260808.md)
  (1차 실측 보고서)로 착지했다. 문단 축은 50,000 문단(3,572쪽 상당, XML 20MB)까지
  `info`·`export-text`·`export-structure` 전부 exit 0, 상한 미발견. 첫 실패 지점은
  `export-pdf` × 문단 5,000(358쪽) — 120초 타임아웃(시간 벽, 72쪽/76.9초는 통과).
  표 축의 메모리 급증 지점은 `export-pdf` × 5,000행 — RSS 가 1,000→5,000행 사이
  261MB→1,415MB 로 ×5.4 뛰었다(시간 93초는 통과, 메모리만 급증).

  **2차(실물 축)** — [`tools/scale_ladder_real.py`](../../../tools/scale_ladder_real.py)
  (실물 코퍼스 사다리+반복·분산+실물 증폭)와
  [`mydocs/tech/large_document_limits.md`](../large_document_limits.md)(한계 공표
  문서)가 1차의 미측정 3건(합성 아닌 실물·분산·입력 상한 근거)을 메웠다. 총 196회
  실행에서 **크래시·OOM·`error` 0건**, 실패 모드는 오직 시간. `samples/` 실물
  전 구간(68KB~13.0MB)에서 파싱 계열 4종 벽 없음(최악 13.0MB·383쪽 문서의
  `export-text` 1.4초). 실물 본문을 32배로 불린 **12,039쪽**(section XML 248MB)
  문서도 `info` 16.3초·`export-structure` 16.2초·`export-tables` 17.2초로 완주하고,
  최대 RSS 950MB(RAM 16GB의 6%)라 **메모리가 제약이 된 지점이 없다**. 60초를 넘긴
  칸은 단 하나 — `export-text` × 12,039쪽 = 173초(6,023쪽은 54초로 통과). **이 명령만
  초선형**이다: 내용 ×31.5 에 시간 ×95.5, 나머지 셋은 ×26~29 로 선형. 렌더 계열은
  훨씬 앞: **실물 13.0MB·383쪽 문서에서 `export-pdf` 180초 타임아웃**(같은 문서를
  파싱 계열은 1.4초 이내에 끝낸다, **130배 격차**) — 1차가 합성으로 본 "첫 실패
  지점 = `export-pdf`, 실패 모드 = 시간"이 실물에서 재현됐다. 부수 소득: **파일
  바이트는 비용을 예측하지 못한다**(2.2MB 문서 60ms vs 0.12MB 문서 149ms)와
  **최대 RSS ≈ 압축 해제 section XML × 3.8~4.2배** 경험칙.
- **설계(달성)** — 규모 사다리(문단 축 1,000~50,000·표 축 100~5,000행)로 명령별
  첫 실패 지점과 실패 모드(타임아웃·메모리 급증)를 기록해 표로 공표했다. 2차는
  같은 축을 실물 코퍼스·실물 증폭·반복 3회로 다시 세우고, 판정을
  `ok`/`slow`/`error`/`crash`/`timeout` 5종으로 갈라 실패 모드를 뭉개지 않았다.
- **착수 게이트** — (없음 — 실측 완료.)
- **DoD** — 명령별 첫 실패 지점·실패 모드는 **달성**(위 표·보고서, 2차에서 실물로
  재확인). "그 지점이 회귀 가드로 고정된다"는 **여전히 미달성** — 1·2차 모두
  측정과 공표까지다. `[완료]` 승급은 그 회귀 가드가 CI 에 붙은 뒤.
- **미측정(2차 기준)** — 수백 MB **파일 바이트** 급 입력(HWPX 압축 때문에 증폭으로도
  24.8MB 가 최대), HWP(CFB) 축의 대형 한계, 메모리 벽 자체, `export-text` 초선형의
  원인, 세션·WASM 표면의 규모 거동. 전건이 한계 공표 문서 §13 에 열거돼 있다.
- **의존** — 없음(실측이 선행).

## R56 스트리밍 export(NDJSON 페이지 단위) `[가설]`

- **한 줄** — 단일 대형 문서의 export 를 통째로 메모리에 쌓지 않고 페이지(또는
  레코드) 단위로 흘린다.
- **지금** — batch 는 이미 **파일당** NDJSON 스트림이다. **단일 문서 하나의 대형
  export**(예: 만 쪽 문서의 `export-text`·`export-structure`)는 전체를 구성해 한
  봉투로 낸다. R55 실측(`mydocs/report/scale_ladder_r1_20260808.md`)이 이 게이트에
  답한다: 문단 축 5만 개(3,572쪽 상당, XML 20MB)까지 `info`·`export-text`·
  `export-structure` 전부 벽 없음(최대 10.7초/260MB) — **현재 실측 범위 안에서는
  스트리밍이 필요하다는 근거가 나오지 않았다.** 다만 보고서 자신이 R56 판정을
  명시적으로 범위 밖(§1 "안 하는 것")이라 밝혔고, 합성 문서라 실물 "수백 MB"급은
  아직 미검증(§8)이라 게이트가 형식적으로 닫히진 않았다.

  **R55 2차([`large_document_limits.md`](../large_document_limits.md) §11)가 이
  게이트에 답했다 — 그리고 답이 R56 의 처방과 어긋난다.** ① 벽은 **관측됐다**:
  실물 본문을 불린 문서에서 `export-text` × 12,039쪽 = 173초(6,023쪽은 54초로 통과)
  이고 **이 명령만** 초선형(내용 ×31.5 ↔ 시간 ×95.5, 나머지 셋은 ×26~29)이다.
  ② 그러나 **벽의 종류가 시간이지 메모리가 아니다**: 같은 12,039쪽에서 최대 RSS
  851MB(RAM 의 5%), 봉투 20.4MB. R56 의 전제("통째로 메모리에 쌓지 않는다")가
  겨냥하는 메모리 벽은 **관측되지 않았고**, 스트리밍은 총 CPU 를 줄이지 않으므로
  173초를 짧게 만들지 못한다.
- **설계** — batch 의 NDJSON 규약을 단일 문서 안으로 끌어와 페이지·레코드 경계에서
  한 줄씩 방출. 절단·부분 실패 표지는 S7·batch 오류 레코드 규약을 재사용. R55 데이터가
  가리키는 방향대로면, 착수 자체가 "현재 상한 안에서 멀쩡한 것에 복잡도만 추가"할
  위험이 있다 — 시간 벽에 스트리밍을 처방하는 것은 처방이 틀린 것이다.
- **착수 게이트** — 원래 문구("실물 대형 문서에서 벽이 관측될 것")는 R55 2차로
  **충족**됐으나, 관측된 벽이 시간이라 **처방이 맞지 않는다**. 데이터가 지지하는
  다음 게이트는 둘로 좁혀진다: ① **`export-text` 초선형의 원인 규명 후에도 시간
  벽이 남을 것**(단 간 배증 계수가 ×2.01→×3.20 으로 자라 지수가 1.6~1.7 대다.
  원인을 고치면 벽 자체가 사라질 수 있다 — 그게 먼저다),
  ② **첫 레코드까지의 지연이 소비자에게 문제라는 근거**(173초 뒤 한 덩어리 vs 1초
  만에 첫 쪽 — 이 축은 R55 2차가 **재지 않았다**).
- **DoD** — 지정 크기 이상 문서에서 export 가 상수 메모리로 완주하고, 스트림
  중단·재개·절단 표지가 계약으로 관측된다.
- **의존** — R55.

## R57 멀티스레드 세션 안전성 감사 `[가설]`

- **한 줄** — 세션 핸들을 여러 스레드가 만질 때의 안전성을 감사하고 계약으로 못
  박는다.
- **지금** — batch 의 병렬은 파일 경계라 세션과 무관하다(무상태). 세션은
  `mcp-serve` 프로세스 메모리 안의 핸들인데, **동시 접근 모델이 명문화돼 있지
  않다** — 트랙 C(MCP 세션 동시성)가 여는 질문과 같은 뿌리다.
- **설계** — 미정(선행 근거: 세션 핸들의 현재 스레드 안전성 현황 실측이 없다).
  감사 결과가 (a) 단일 스레드 강제, (b) 핸들별 락, (c) 불변 스냅샷 중 무엇을
  계약으로 세울지 정한다.
- **착수 게이트** — 트랙 C R28(MCP 세션 동시성)의 모델 확정 + 세션 핸들 스레드
  안전성 현황 실측.
- **DoD** — 세션 동시 접근의 허용/불허가 계약으로 선언되고, 위반이 테스트로 잡힌다.
- **의존** — R52, 트랙 C R28.

## R58 파싱 캐시 계층 `[가설]`

- **한 줄** — 같은 문서의 반복 파싱을 캐시로 건너뛴다.
- **지금** — 없음. 세션(R52)이 이미 "한 번 열고 재사용"으로 반복 파싱을 없애므로,
  **별도 캐시 계층이 실제로 필요한 워크로드가 있는지 근거가 없다**.

  R55 2차([`large_document_limits.md`](../large_document_limits.md) §11)가 **비용의
  크기만** 확정했다: 같은 문서를 3회 콜드 실행한 전 구간에서 회차 간 단조 감소가
  없다(13.0MB 실물 `info` 421ms ±15%, 12,039쪽 문서 `info` 16,315ms ±4%) —
  **OS 페이지 캐시가 데워져도 비용이 안 줄어든다** = 파싱은 I/O 바운드가 아니라
  CPU 바운드다. 따라서 파일 수준 캐시는 무의미하고, 캐시를 만든다면 **IR 수준**
  이어야 한다는 것까지가 데이터가 말하는 전부다.
- **설계** — 미정(선행 근거: 반복 파싱이 병목인 워크로드 실측이 없다). 캐시는
  무효화·정합성 비용을 새로 들이므로, 세션으로 안 풀리는 반복 파싱 패턴이
  실증되기 전에는 복잡도만 추가한다.
- **착수 게이트** — 반복 파싱이 실측 병목인 워크로드 근거 1건 이상(세션으로 해소
  불가한 경우). **여전히 미충족** — R55 2차는 재파싱 비용의 절대값만 쟀고,
  세션으로 해소되지 않는 워크로드를 제시하지 못했다. 다음 실측 후보는
  "`batch` 를 서로 다른 축으로 N회 돌릴 때의 총 재파싱 비용"(아직 **가설**이다).
- **DoD** — 캐시 적중이 대상 워크로드에서 측정 가능한 이득을 내고, 무효화 정합성이
  테스트로 고정된다.
- **의존** — R52(세션이 대안이므로 필요성 판정의 기준선).

## R60 자원 상한 옵션(--max-mem/--timeout) 계약화 `[가설]`

- **한 줄** — 명령이 쓰는 메모리·시간에 호출자가 상한을 걸고, 상한 도달이 봉투에
  드러나게 한다.
- **지금** — **없음, 그리고 이건 S7 과 다른 축이다(중복 확인 결과).**
  `agent_boundary_contract.md` S7("자원 한계")은 **출력** 컨텍스트(문자·매치 수)
  상한만 계약화했고, 같은 문서가 "파일 산출 크기·페이지 수·**메모리 상한은 다루지
  않는다**", "핸들 개수 상한·메모리 상한은 없다"고 못 박는다. 즉 `--max-mem`·
  `--timeout` 은 S7 의 중복이 아니라 S7 이 명시적으로 비워 둔 칸이다.

  **R55 의존분은 해소됐다** —
  [`large_document_limits.md`](../large_document_limits.md) §9·§10 이 숫자를 줬다:
  ① 시간 축 — 60초는 `export-text` 약 6,000쪽 / 나머지 파싱 계열 12,000쪽 초과 /
  `export-pdf` 실물 약 80~200쪽(두 경계 모두 구간 사이를 안 재서 폭으로 적었다).
  ② 메모리 축 — **최대 RSS ≈ 압축 해제 section XML × 3.8~4.2배**(×8·×16·×32 3점에서
  일관)라, 상한을 사후 감지가 아니라 **입력에서 사전 추정·거부**로 구현할 수 있다.
  ③ **바이트 축은 잘못된 축이다** — 파일 바이트가 비용을 예측하지 못하고(2.2MB
  문서 60ms vs 0.12MB 문서 149ms), 내용이 ×31.5 자라는 동안 파일은 ×2.87 만 자란다.
  진행 중인 서비스 계층 작업(`src/service/open.rs`, **미머지**)이 제안한
  `DEFAULT_MAX_BYTES = 256 MiB` 는 이 실측 기준으로 **보호도 제한도 못 하는 자리
  표시자**로 판정됐다(근거는 같은 문서 §10.1).
- **설계** — S7 의 어휘·표지 규약(상한 도달은 **반드시 봉투에 드러난다**, 기본값
  무제한)을 그대로 새 축(메모리·시간)에 확장한다. 상한 초과 시 부분 산출 여부·표지를
  S7 과 같은 모양으로 맞춰 두 축이 한 어휘를 쓰게 한다. 자원 축은 **바이트가 아니라
  압축 해제 바이트**에 걸어야 한다(§10.2).
- **착수 게이트** — S7 과의 정합 설계 확정(같은 어휘·같은 표지 규약을 쓰되 두 축이
  충돌하지 않게) + 메모리·시간 상한을 거는 실행 기구(프로세스 수준 제한)의 실현
  가능성 확인. **둘 다 여전히 미확인** — R55 2차는 상한의 *값*을 줬을 뿐 *기구*는
  다루지 않았고, 12,039쪽에서도 최대 RSS 950MB 라 **메모리 벽 자체를 못 봤으므로
  `--max-mem` 기본값의 근거는 없다**.
- **DoD** — `--max-mem`·`--timeout` 초과가 정의된 종료 코드 + 봉투 표지로
  관측되고, `agent_boundary_contract` 에 S7 과 나란히 등재된다.
- **의존** — 트랙 B(경계 무결 계약 S7), R55(어느 상한이 현실적인지 실측).
