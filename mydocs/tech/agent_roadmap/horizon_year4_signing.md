## 1. 질문 — 무결의 다음은 귀속이다

계보(3년)는 세 가지를 증명한다: 작업이 사실이고(영수증), 재현되며(감사·deep),
역사가 이어졌고 사후에 안 바뀌었다(해시 체인). 그러나 **"누가 했나"** 는 한
글자도 증명하지 못한다. 캡슐은 익명이다.

익명 무결의 한계는 유통에서 드러난다:

- **분쟁**: 재현 실패 캡슐이 나왔을 때, 어느 에이전트(누구의 운영 주체)의
  산출인지 다툴 근거가 없다.
- **선별**: "우리 조직 키로 서명된 산출물만 반입"이라는 가장 기초적인 정책
  (6년 축)을 세울 토대가 없다.
- **위장**: 캡슐 형식은 공개 규약이므로 누구나 "남의 작업처럼 보이는" 캡슐을
  만들 수 있다 — 무결 검증은 통과한다. 귀속 없는 무결은 위장에 무방비다.

한 줄 정의: **서명 축은 "이 캡슐을 이 키의 소유자가 봉인했다"를 오프라인
검증 가능하게 만든다.**

## 2. 설계

### 2.1 서명 대상 — 파일 바이트, 정규화 아님

두 가지 선택지가 있다:

| 방식 | 장점 | 단점 |
|---|---|---|
| 정규화(canonical JSON) 서명 | 재직렬화·포맷 변경에 내성 | 정규화 규칙 자체가 공격면·구현 분기 (JSON 정규화의 역사는 사고의 역사다) |
| **파일 바이트 서명 (채택)** | 구현 단순·검증 단순·기존 해시 체인과 동형 | 파일을 재직렬화하면 서명이 깨진다 |

채택 근거: 계보 축 전체가 이미 **파일 바이트 해시** 위에 서 있다(부모 링크가
파일 SHA-256). 서명도 같은 대상을 봉인해야 두 체계가 어긋나지 않는다.
"캡슐 파일은 발급 후 불변"은 이미 계보의 전제이므로 새 제약이 아니다 —
재직렬화 금지를 규약으로 명문화한다.

### 2.2 봉인 형식 — 분리 서명(sidecar)

서명을 캡슐 **안에** 넣으면 "서명 필드를 제외한 바이트"라는 정규화 문제가
되돌아온다. 채택: **분리 서명 파일** `<캡슐>.sig.json`:

```json
{
  "schemaVersion": "1.0",
  "kind": "capsuleSignature",
  "capsuleSha256": "9f2c…",
  "alg": "ed25519",
  "keyId": "org.example/agent-7#2026",
  "signature": "base64…",
  "signedAt": "2026-08-10T12:00:00Z"
}
```

- `signature` = Ed25519(개인키, 캡슐 파일 바이트). `capsuleSha256` 은 어느
  파일에 대한 서명인지의 자기서술(검증 시 실물 대조).
- `signedAt` 은 **주장이지 증명이 아니다** — 서명 시점의 증명은 5년 축(앵커)의
  몫임을 처음부터 명시한다. 이 분리가 4년/5년 축의 경계선이다.
- Ed25519 채택 근거: 결정론 서명(같은 입력 → 같은 서명 — 이 로드맵의 결정론
  문화와 정합), 키·서명이 짧고, 구현이 보편적이다. `alg` 필드로 후속 알고리즘
  여지는 남긴다.

### 2.3 키 등록부(keyring)와 폐기

```json
{
  "schemaVersion": "1.0",
  "kind": "keyring",
  "keys": [
    { "keyId": "org.example/agent-7#2026", "publicKey": "base64…",
      "owner": "표기용 문자열", "validFrom": "2026-01-01", "validUntil": null,
      "revoked": null }
  ]
}
```

- `keyId` 는 "소유 주체/용도#세대" 관례 — 키 회전 시 세대만 올린다.
- **폐기는 삭제가 아니라 기록이다**: `revoked: {"at": "…", "reason": "…"}`.
  폐기된 키의 과거 서명은 "폐기 이전 발급분"으로 판정이 갈려야 하는데, 서명
  시점 증명이 없는 4년 축 단독으로는 **폐기 시점 이전/이후를 구분할 수 없다**
  — 정직하게: 4년 축 단독의 폐기 판정은 "이 키는 현재 폐기됨" 경고까지고,
  시점 구분은 5년 축(앵커된 서명)이 완성한다.
- 키 등록부 자체의 신뢰 뿌리는 **도구 밖**이다(조직이 어떤 keyring 파일을
  믿을지는 거버넌스 문제). 도구는 "주어진 keyring 기준 판정"까지만 한다 —
  신뢰 뿌리를 도구가 가진 척하지 않는다.

### 2.4 CLI 확장

```text
rhwp replay --plan-json … --capsule c.json --sign-key key.pem
  → c.json + c.json.sig.json 발급 (키 없으면 서명 없이 — 하위호환)

rhwp lineage head.json --keyring keyring.json [--deep] [--json]
  → 링크마다 4번째 판정 축 signerOk 추가:
    null  = 서명 파일 없음 (keyring 미지정 시 항상 null — 판정 축 자체가 꺼짐)
    true  = 서명 유효 + keyId 가 keyring 에 있고 미폐기
    false = 서명 무효 / 미등록 키 / 폐기 키
rhwp verify-signature c.json --keyring keyring.json   # 단건 검증(스크립트용)
```

- 봉투 확장: `links[].signerOk`, `links[].keyId` (없으면 null). 기존 소비자는
  새 필드를 무시하면 되므로 스키마 부 버전 상향(1.x)으로 충분하다.
- exit 규약 불변: 서명 실패도 "깨진 계보"(exit 3)의 한 사유다 — 단, `--keyring`
  을 준 경우에만. 주지 않으면 서명은 판정에 개입하지 않는다(opt-in — 기존
  파이프라인 무파손).

### 2.5 등재 부담 (실측 기반 견적)

3년 축 실측: 신설 명령 1개 = **7표면**(capabilities·MCP·help·프로필 + node
래퍼·지식지도 사전·출처 지도/스윕). 이 축은 명령 신설 1(verify-signature) +
기존 명령 플래그 확장 2(replay·lineage) → 7표면 1회 + 플래그 등재 2회 예상.
구현 착수 시 이 견적을 stage 문서에서 실측으로 대체한다.

## 3. 위협 모델

| # | 공격 | 판정 | 비고 |
|---|---|---|---|
| S1 | 캡슐 변조 후 재서명 (키 미보유) | `signature` 검증 실패 → signerOk false | 서명의 존재 이유 |
| S2 | 위장 발급 (남의 작업인 척) | 서명 강제 정책(6년) 하에서 미서명/미등록 키 → 반입 거부 | 4년 축 단독은 "정책 없이 자발 서명"까지 |
| S3 | 키 유출 후 위조 서명 | **못 잡는다** — 폐기 기록 이후의 신규 검증만 false. 유출~폐기 사이 발급분은 5년 축(앵커 시점)과 결합해야 소급 판정 가능 | 정직 조항 |
| S4 | signedAt 거짓 기재 | **못 잡는다** — 주장 필드임을 명시 (§2.2). 시점 증명은 5년 축 | 경계선 명시 |
| S5 | keyring 바꿔치기 | 도구 밖 (신뢰 뿌리 거버넌스) — keyring 파일 자체를 서명·앵커 대상으로 삼는 재귀 적용은 5·6년 축에서 | |

## 4. 단계와 DoD

| 단계 | 내용 | DoD |
|---|---|---|
| Y4-M1 | sig.json 발급·단건 검증 | 서명→검증 왕복 + 1바이트 변조 검출 + 결정론(같은 키·같은 캡슐 → 같은 서명) 테스트 |
| Y4-M2 | keyring·폐기 | 미등록/폐기 키 false + 폐기 기록 후 경고 판정 테스트 |
| Y4-M3 | lineage signerOk 통합 | 2링크 체인에서 한 링크만 서명 무효 → brokenAt 그 링크 + opt-in 무파손(–keyring 없이 기존 테스트 전건 green) |
| Y4-M4 | 등재 7표면+가드 | 3년 축과 동일 게이트 전건 green |

## 5. 정직 조항

- 이 문서는 설계이지 구현이 아니다. 서명 라이브러리 선정(ed25519 크레이트
  의존성 추가)은 저장소 의존성 정책 검토가 선행돼야 한다 — M1 착수 시 논의.
- 4년 축 단독으로는 S3·S4 를 못 잡는다. "서명은 귀속을, 앵커는 시점을" —
  두 축이 합쳐져야 폐기 소급 판정이 완성된다는 것이 사다리의 설계 의도다.
