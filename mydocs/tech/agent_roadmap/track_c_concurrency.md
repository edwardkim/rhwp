# 트랙 C — 동시성·협업 (R21~R30)

**질문**: 에이전트 여럿이 같은 문서를 안전하게 다루는가.

이 트랙의 원점은 #3905 하나다 — 두 에이전트가 같은 기준본에서 서로 다른 편집을
하면, 둘 다 성공(exit 0)을 보고하는데 나중 쓴 쪽이 먼저 쓴 편집을 무신호로 덮는
경합 유실이 실측됐다. 해법은 한 축으로 모인다: **계획을 만든 시점의 상태 지문을
봉인하고, 실행 입장에서 대조해 낡은 기준의 실행을 거부한다**(CAS,
compare-and-swap). 잠금 데몬도 전송 프로토콜도 아니다 — 도구는 무상태로 남고,
상태는 지문이 되어 봉투에 실린다. R21 이 문제를 못 박았고, R22 가 그 대조의 최소
구현이며, R23~R30 이 그 위에 지문 체인·단발 CAS·인계·협업 계약을 쌓는다. 이
트랙이 명시적으로 거부하는 것은 끝의 **비목표** 절이 이유와 함께 적는다.

## R21 경합 유실 재현 `[실측]`

- **한 줄** — 두 에이전트의 동시 편집이 무신호로 유실되는 경합을 재현해 못 박는다.
- **지금** — #3905(이 트랙의 원점). 실측: 같은 기준본에서 두 에이전트가
  `fill-fields` 로 각각 다른 필드를 채워 같은 출력 파일에 쓰면, 둘 다 exit 0 +
  `filledCount:1` 을 보고한다 — 그런데 나중에 쓴 쪽이 이겨 먼저 쓴 편집은 흔적 없이
  사라진다. 어느 봉투에도 "네 기준 상태가 이미 낡았다"는 신호가 없다.
  `atomic_file::write_atomically` 는 **쓰기 원자성**(반쯤 쓰인 파일이 안 생김)을
  보장할 뿐 **의미 동시성**(남의 편집을 덮는가)을 보장하지 않는다 — 이 둘을 혼동한
  것이 문제의 뿌리다.
- **설계(보장)** — 재현 케이스가 경합 유실을 결정적으로 드러낸다: 두 봉투 모두
  성공을 보고하는데 디스크 결과는 하나만 남는다. 이 재현이 R22 이하 전 단계의 착수
  근거다.
- **착수 게이트** — 없음(재현은 이미 확보; 이 재현 자체가 트랙의 착수 근거다).
- **DoD** — 달성: 경합 유실이 재현 가능한 실측으로 고정됐다.
- **의존** — 없음(트랙의 원점). `fill-fields`·`atomic_file` 은 기존 표면.

## R22 계획서 preconditions.inputSha256 (CAS) `[문서]`

- **한 줄** — 계획을 만든 시점의 입력 지문을 계획서에 봉인하고, 실행기가 입장에서
  대조해 낡은 기준의 실행을 거부한다(CAS).
- **지금** — #3905 M1. R21 이 드러낸 유실을 막는 최소 장치다: 계획서에
  `preconditions.inputSha256` 을 실어 "이 계획은 이 지문의 입력을 전제한다"를
  선언하고, 실행기가 실제 입력의 지문과 대조한다.
- **설계** — 불일치는 **거부이지 건너뜀이 아니다**: 실행 0건·디스크 무변경·저널에
  `preconditionFailed{expected, actual}` + `nextCall`(재계획 힌트). `--dry-run` 도
  같은 대조를 한다 — 선검증이 곧 실행 경로라는 #3719 §6-8 원칙(dry-run 과 실행이
  같은 판정을 내야 한다)을 지킨다. 구현은 작다: `run_plan_engine` 입구에서 해시
  1회. 선택 필드라 `planSchemaVersion` 은 minor 증가(기존 계획서는 필드 없이도
  유효).
- **착수 게이트** — 판단 3개가 선행한다. ① 종료 코드: 대조 실패를 기존 단언 실패
  (exit 3)에 편입할지, 신설 코드를 둘지. ② 지문 대상: 파일 바이트 sha256 인지 IR
  지문(같은 내용의 다른 바이트를 같게 볼지)인지. ③ preconditions 위치: 계획서
  본문에 둘지 CLI 플래그로 뺄지. 셋 다 이후 단계(R23 지문 대상, R24 플래그, R26
  거부 저널)의 모양을 좌우한다.
- **DoD** — 낡은 기준의 계획이 exit(판정된 코드) + 디스크 무변경 + `preconditionFailed`
  저널로 거부되는 것을 red→green 으로 실증. capabilities 에 preconditions 선언 등재.
- **의존** — R21.

## R23 저널 지문 체인 `[문서]`

- **한 줄** — 저널에 `inputSha256`/`outputSha256` 을 실어, 저널만 이어 붙이면
  "누가 어떤 상태에서 무엇을 바꿨나"가 재구성되게 한다.
- **지금** — #3905. R22 가 입력 지문을 계획서에 봉인한다면, R23 은 그 지문을 실행
  결과 저널에도 남긴다 — 앞 저널의 output 이 뒤 저널의 input 과 이어지면 편집
  사슬이 검증 가능해진다.
- **설계** — 도구는 지문만 낸다. 저널을 이어 붙여 누적 이력으로 만드는 것은 호출자
  몫이다(무상태 CLI 철학 — 도구가 상태를 들고 있지 않는다). input/output 지문은
  R22 와 같은 해시 함수를 써야 사슬이 성립한다.
- **착수 게이트** — R22 의 지문 대상 판정(파일 sha256 vs IR 지문)이 먼저다. 저널이
  R22 와 다른 해시를 쓰면 계획서 지문과 저널 지문이 안 이어져 사슬 자체가 끊긴다.
- **DoD** — 연속 실행의 저널에서 앞의 `outputSha256` = 뒤의 `inputSha256` 이
  성립함을 검사로 고정하고, 불연속(끼어든 편집)을 저널만으로 탐지할 수 있음을 실증.
- **의존** — R22(같은 지문 대상·해시 함수).

## R24 단발 edit --expect-sha256 `[문서]`

- **한 줄** — `run` 계획서 밖의 단발 `edit` 명령에도 `--expect-sha256` 으로 CAS 를
  건다.
- **지금** — #3905. R22 의 CAS 는 계획서(run) 경로에만 있다. 그러나 에이전트가
  계획 없이 단발 `edit` 로 바로 쓰는 경로도 흔하고, 거기에는 아직 낡은 기준 방어가
  없다.
- **설계** — R22 의 의미론을 단발 명령으로 이식한다: `--expect-sha256 <지문>` 을
  주면 실행 전 대조하고, 불일치면 R22 와 같은 거부 3면(실행 0·디스크 무변경·저널).
  새 의미론이 아니라 같은 의미론의 다른 진입점이라 설계 위험이 낮다.
- **착수 게이트** — R22 가 자리 잡은 뒤. 거부 3면과 종료 코드가 R22 에서 확정돼야
  그대로 이식할 수 있다 — R22 전에 하면 두 경로의 CAS 의미가 갈린다.
- **DoD** — `edit ... --expect-sha256` 이 불일치 기준에서 R22 와 동일한 거부를 내는
  것을 실증하고, capabilities 에 플래그 등재.
- **의존** — R22(이식할 의미론의 원본).

## R25 인계 레시피(07) `[가설]`

- **한 줄** — `digest` + fields + 지문을 조합해, 다음 에이전트를 1 왕복으로
  부트스트랩하는 인계 레시피(07).
- **지금** — 미착수. 인계는 지금 여러 왕복이 든다(문서 요약 따로, 필드 상태 따로,
  기준 지문 따로). 이것을 한 번의 호출 조합으로 묶어 "다음 에이전트가 받는 첫
  봉투"를 표준화하려는 것이다.
- **설계** — 새 명령을 만들지 않는다. 기존 표면(`digest` 요약 + `fill-fields` 상태
  + R22/R23 의 지문)을 레시피 문서로 조합해 먼저 검증한다 — 조합으로 되면 새 명령이
  불필요하고, 안 되는 부분만 명령 후보가 된다.
- **착수 게이트** — R22·R23 머지. 지문이 봉투에 실려야(R22 계획서·R23 저널) 인계
  봉투에 기준 상태를 담을 수 있고, 그 전에는 레시피가 "낡을 수 있는 상태"를 그대로
  넘겨 R21 유실을 인계 단계로 옮길 뿐이다.
- **DoD** — 인계 레시피 07 이 등재되고, 두 에이전트 순차 인계에서 뒤 에이전트가 1
  왕복으로 문서·필드·기준 지문을 받는 것을 실측.
- **의존** — R22·R23.

## R26 재계획 루프 규약 `[가설]`

- **한 줄** — CAS 거부 후 재계획 루프를 규약화한다 — `nextCall` 힌트를 표준화하되
  재시도 상한을 넣어 무한 재계획을 막는다.
- **지금** — 미착수. R22 는 거부 시 저널에 `nextCall` 을 남기지만, 소비자가 그것을
  받아 어떻게 재계획하고 언제 포기하는지는 규약이 없다. 규약 없이 두면 두 에이전트가
  서로의 편집에 계속 튕겨 무한 재계획(livelock)에 빠질 수 있다.
- **설계** — 미정(선행 근거 필요). 뼈대만: `nextCall` 의 필드(무엇을 다시 읽고
  무엇을 다시 계획할지)를 표준화하고, 재시도 상한(N회 후 사람에게 에스컬레이션)을
  규약에 못 박는다. 상한 값과 에스컬레이션 신호의 모양이 미검증이다.
- **착수 게이트** — R22 의 거부 저널 모양(`preconditionFailed` + `nextCall` 필드)이
  확정돼야 그 위에 루프 규약을 얹는다. 거부 저널이 흔들리면 규약이 겨눌 대상이 없다.
- **DoD** — 재계획 루프 규약이 문서화되고, 두 에이전트 경합에서 상한 내 수렴 또는
  상한 초과 시 에스컬레이션이 실증된다.
- **의존** — R22(거부 저널 형태).

## R27 다문서 계획 원자성 `[가설]`

- **한 줄** — 여러 문서를 건드리는 계획을 전부-또는-전무(all-or-nothing)로
  실행한다 — 하나라도 대조 실패면 전체가 디스크에 안 닿는다.
- **지금** — 미착수. R22 의 CAS 는 단일 입력 기준이다. 계획이 문서 A·B 를 함께
  바꾸는데 A 는 최신이고 B 가 낡았다면, 원자성 없이는 A 만 쓰이고 B 는 거부돼 문서
  집합이 반쯤 갱신된 모순 상태가 된다.
- **설계** — 미정(선행 근거 필요). 핵심 난점은 롤백이다: 무상태 CLI 가 다문서 쓰기
  도중 실패했을 때 이미 쓴 파일을 어떻게 무변경으로 되돌리는가(임시 산출 후 일괄
  커밋? 전 대조 후 전 쓰기?). 이 방법이 실측으로 서기 전에는 "전부-또는-전무"가
  구호에 그친다.
- **착수 게이트** — 두 선행. ① 단문서 CAS(R22)가 안정될 것. ② 다문서 실패 롤백
  설계 — 디스크 무변경을 실제로 보장하는 방법이 실측될 것(부분 쓰기 후 크래시
  시나리오 포함).
- **DoD** — 다문서 계획에서 일부 대조 실패 시 어떤 문서도 변경되지 않음을 크래시
  주입 테스트로 실증.
- **의존** — R22.

## R28 MCP 세션 동시성 `[가설]`

- **한 줄** — MCP 서버가 여러 세션을 동시에 열 때, 세션별 핸들을 격리하고 세션
  간에는 기준 지문을 공유해 경합을 CAS 로 잡는다.
- **지금** — 미착수. 트랙 H 에서 rhwp 가 MCP 서버가 되면 한 프로세스가 여러
  에이전트 세션을 동시에 든다 — CLI 의 프로세스 격리가 사라지므로, R21 의 경합이
  프로세스 내부로 들어온다.
- **설계** — 미정(선행 근거 필요). 방향만: 세션 핸들은 서로의 상태를 못 보게
  격리하되, 같은 문서를 겨눈 쓰기는 R22 의 지문 대조를 세션 경계에서도 적용한다.
  MCP 세션 수명·핸들 모델(트랙 H)이 서기 전에는 격리 단위 자체가 미정이다.
- **착수 게이트** — 두 선행. ① R22 의 CAS 의미론 확정. ② MCP 세션 표면(트랙 H)의
  안정 — 세션·핸들이 무엇인지가 정의돼야 "세션 간 공유"의 대상이 생긴다.
- **DoD** — 두 MCP 세션이 같은 문서를 동시 편집할 때 CLI 경로와 동일하게 뒤 쓰기가
  CAS 로 거부됨을 실증.
- **의존** — R22, 트랙 H(MCP 세션 표면).

## R29 협업 레시피(08) `[가설]`

- **한 줄** — 계획자·실행자·검증자 세 역할이 하나의 문서를 나눠 다루는 협업
  레시피(08)를 실측한다.
- **지금** — 미착수. R25 가 두 에이전트의 순차 인계라면, R29 는 세 역할이 각자 다른
  명령 표면(계획 생성 / `run` 실행 / `verify` 검증)을 맡아 협업하는 흐름이다.
- **설계** — 미정(선행 근거 필요). 인계 레시피(R25)가 실측으로 선 다음, 거기에 역할
  분리를 얹어 계획자가 계획서(+preconditions)를 만들고, 실행자가 CAS 로 실행하고,
  검증자가 저널 지문 체인(R23)으로 결과를 확인하는 3역 흐름을 레시피로 조립한다.
- **착수 게이트** — R25 인계 레시피가 검증된 뒤. 2역(인계)이 안 서면 3역(협업)은 더
  못 선다.
- **DoD** — 협업 레시피 08 이 등재되고, 3역이 한 문서를 경합 없이 갱신하는 것을
  실측(각 역할의 봉투가 다음 역할의 입력으로 이어짐).
- **의존** — R25.

## R30 협업 계약 canonical 문서 1편 `[가설]`

- **한 줄** — 동시성·협업 계약을 mydocs/tech 의 agent_architecture 축에 canonical
  문서 1편(권위표)으로 등재한다.
- **지금** — 미착수. 지금 계약은 #3905 이슈와 개별 PR 에 흩어져 있어, 새 에이전트가
  "여럿이 안전하게 협업하는 규약"을 한 곳에서 읽을 수 없다.
- **설계** — 미정(선행 근거 필요). CAS(R22)·지문 체인(R23)·단발 CAS(R24)·재계획
  규약(R26) 중 실제로 머지된 것들을 권위표로 묶는다. 아직 실물이 없는 조항을 문서가
  앞서 규정하면 소설이 되므로, 문서는 머지를 뒤따른다.
- **착수 게이트** — R22~R26 중 최소 2개가 머지될 것(문서화할 실물이 존재해야 한다).
  이 지도의 규칙 2·5(완료는 머지 링크와 함께, 원천이 이긴다)를 그대로 따른다.
- **DoD** — 협업 계약 canonical 문서가 agent_architecture 축에 등재되고, 트랙 C 의
  머지된 단계들이 그 권위표에서 단일 출처로 참조된다.
- **의존** — R22~R26 중 최소 2개.

## 비목표

이 트랙이 명시적으로 **하지 않는** 것과 그 이유다 — 경계를 적어 두지 않으면
동시성 요구가 자연히 이 방향으로 새기 때문이다.

- **잠금 데몬 / 리스(lease) 서버** — 상주 프로세스가 문서 잠금을 관리하는 방식은
  rhwp 의 **무상태 CLI 철학과 정면으로 상충한다.** 도구는 상태를 들고 있지 않고 매
  호출이 자기완결적이다. 동시성은 상주 잠금이 아니라 지문 대조(CAS)로 푼다 —
  상태를 서버에 두는 대신, 지문을 봉투에 실어 호출자가 나른다.
- **에이전트 간 메시지 브로커 · 직접 전송 프로토콜** — rhwp 는 여러 에이전트가
  함께 쓰는 **공유 작업면이지 전송 계층이 아니다.** 협업은 같은 문서·같은 저널을
  통해 간접적으로 일어나지, A 가 B 에게 직접 보내는 채널을 도구가 제공하지 않는다.
  전송이 필요하면 그것은 호출자(오케스트레이터)의 몫이다.
- **압축 · 은닉 채널** — 봉투에 정보를 은닉하거나 압축해 실어 나르는 채널은 **L2
  신뢰 축(트랙 B)과 정면으로 상충한다.** 우리는 문서 안의 은닉을 **탐지하는** 쪽이다
  (S10·악성 코퍼스 R13). 도구가 스스로 은닉 채널을 만들면 그 탐지의 근거가 무너진다.
