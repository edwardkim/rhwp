# 참조 조회 — "어느 문서가 이 서식을 인용하나" (M25)

> 로드맵 [#3608](https://github.com/edwardkim/rhwp/issues/3608) M25 의 셋째 항목 —
> "참조 조회(어느 문서가 이 서식을 인용하나)".
> 이 문서는 **설계**다. 여기 나오는 도구·필드는 아직 구현되어 있지 않다.
> 디렉터리 개요는 [README](README.md).

## 0. 이 문서가 정하는 것

LSP 의 "Find All References" 는 심볼 하나를 잡고 그것을 쓰는 곳을 전부 찾는다. 문서
세계로 옮기면 "이 서식을 인용하는 문서를 찾아라" 가 된다.

**먼저 답할 것은 설계가 아니라 사실이다 — HWP 에 그런 링크가 실제로 있는가.**
이 문서는 `src/` 를 훑어 연결 고리 후보를 전수 조사하고(§2), 저장소 `samples/` 353건에서
실측하고(§3), 결론을 낸다(§4). 링크가 없으면 무엇으로 근사할 수 있는지(§5)와 그 근사가
무엇을 틀리는지(§6)를 적는다.

**결론을 먼저 적는다.**

> **HWP 문서에는 "다른 HWP 문서를 인용한다"는 링크가 사실상 없다.** 하이퍼링크 필드는
> 임의 문자열을 담을 수 있어 이론상 파일 경로를 넣을 수 있지만, **353건 코퍼스에서
> 문서 파일을 가리키는 링크는 0건**이었다. 참조 그래프는 **문서 안**에서만 완결된다
> (하이퍼링크 → 책갈피, 상호참조 → 책갈피). 문서 **사이**의 관계는 링크가 아니라
> **닮음**으로만 근사할 수 있다.

---

## 1. 질문을 먼저 쪼갠다

"어느 문서가 이 서식을 인용하나" 는 한 문장이지만 셋으로 갈린다. 답이 서로 다르다.

| 해석 | 뜻 | 답 |
|---|---|---|
| **Q1. 명시적 링크** | 문서 B 안에 "서식 A" 를 가리키는 링크가 박혀 있다 | **없다** (§2·§3) |
| **Q2. 유래** | 문서 B 가 서식 A 를 열어 채운 결과물이다 | 링크로는 알 수 없다. **닮음으로 근사**(§5) |
| **Q3. 문서 내부 참조** | 문서 A 안에서 "표 3 참조" 가 어느 표를 가리키나 | **가능하다** — 상호참조·책갈피가 IR 에 있다(§2.2) |

M25 가 말하는 것은 Q2 이고, 현실적으로 답할 수 있는 것도 Q2(근사)와 Q3(정확)이다.
Q3 은 이미 재료가 다 있으나 **CLI·MCP 표면이 없다**(§2.2) — 가장 작은 작업이면서
확실히 정확한 답을 주는 축이다.

## 2. 연결 고리 전수 조사 (코드)

`src/model/` 과 `src/parser/` 에서 "다른 파일·다른 위치를 가리키는 값"을 담을 수 있는
자리를 전부 찾았다.

### 2.1 필드(Field) 계열

IR 의 `Field` 는 타입과 **명령 문자열** 하나를 가진다(`src/model/control.rs:254-258`,
`pub command: String` — 주석에 "누름틀: 안내문, 하이퍼링크: URL 등"). 타입은 15종이다
(`src/model/control.rs:425-441`, 매핑은 `src/parser/control.rs:60-76`).

| 필드 타입 | 무엇을 가리키나 | 문서 간 참조인가 |
|---|---|---|
| `Hyperlink` (`%hlk`) | `command` 에 대상 문자열. 형식은 `대상;옵션;옵션;옵션;` | **가능성만** — 실측 0건(§3.2) |
| `CrossRef` (상호참조) | `command` 에 `?#<책갈피id>` 또는 `?<책갈피 이름>` | **아니다** — 같은 문서 안 |
| `Bookmark` | 참조의 **대상** 쪽 | 아니다 |
| `MailMerge` | 메일머지 자리표시자 | **아니다** — 타입만 있고 데이터 원본 이름을 담는 자리가 IR 에 없다 |
| `Path` | 문서 **자기** 파일 경로를 본문에 찍는 필드 | 아니다 |
| `TableOfContents` | 목차 | 아니다(같은 문서) |
| 나머지(`Date`·`DocDate`·`Formula`·`Summary`·`UserInfo`·`Memo`·`PrivateInfoSecurity`·`ClickHere`·`Unknown`) | — | 아니다 |

`Hyperlink` 구조체 자체(`src/model/control.rs:174-179`, `url`·`text`)도 있지만, HWP5
경로에서 실제로 값이 실리는 곳은 `Field.command` 다 — `fields --json` 이 `command` 를
그대로 낸다(`src/main.rs:12875`).

### 2.2 책갈피 — 참조의 대상 쪽

`Control::Bookmark { name }`(`src/model/control.rs:167-170`)이 IR 에 있고, 조회 API 도
있다 — `get_bookmarks_native`(`src/document_core/queries/bookmark_query.rs:21`).

**그런데 CLI 에도 MCP 에도 노출되어 있지 않다.** `wasm_api` 에만 있다
(`src/wasm_api.rs:7534`, `get_bookmarks`). 즉 지금 에이전트는 `?#653826223` 이라는
**참조를 볼 수는 있어도 그것이 가리키는 곳을 볼 수 없다.** 문서 내부 참조 그래프(Q3)를
닫으려면 이 한 표면만 열면 된다.

### 2.3 BinData — 외부 파일 참조는 **실존한다**

```rust
pub struct BinData {
    …
    /// 연결 파일 절대 경로 (LINK 타입)
    pub abs_path: Option<String>,
    /// 연결 파일 상대 경로 (LINK 타입)
    pub rel_path: Option<String>,
    …
}
pub enum BinDataType { Link /*외부 파일 참조*/, Embedding, Storage }
```
(`src/model/bin_data.rs:5-36`)

파서가 LINK 타입에서 두 경로를 읽는다(`src/parser/doc_info.rs:252-256`), 그리고 그림
컨트롤의 `image_attr.external_path` 로 옮겨 붙인다(`src/parser/mod.rs:910-940`).

**이것은 진짜 문서→외부 파일 참조다.** 다만 가리키는 것은 **그림·OLE 페이로드**이지
다른 HWP 문서가 아니다. OLE 개체도 별도 링크 필드 없이 `bin_data_id` 로 BinData 를
가리킬 뿐이다(`src/model/shape.rs:828-848`) — 그 BinData 가 LINK 타입이면 경로가 딸린다.

### 2.4 문서 요약 정보·기타

`DocInfo`/요약정보에 "이 문서의 원본 서식" 같은 항목은 **없다**. HWP 5.0 스펙에 그런
필드가 있는지는 이 조사 범위 밖이며 **확인되지 않음** — 다만 rhwp IR 에는 없다.

## 3. 실측 — 코퍼스 353건 스캔

### 3.1 방법

```bash
ls samples/*.hwp samples/*.hwpx | rhwp batch fields --json --threads 8
```

- 대상: 저장소 `samples/` 의 `.hwp`/`.hwpx` **353건** (합계 296.3 MB, 중앙값 54 KB).
- 결과: **350건 파싱 성공, 3건 오류**(오류 레코드로 스트림에 남는다).
- 소요: 1스레드 17.1초 / 8스레드 6.3초(문서당 48.5 ms).
- NDJSON 을 Python 으로 집계.

### 3.2 필드 타입 분포

| 필드 타입 | 총 개수 | 보유 문서 수 |
|---|---:|---:|
| `ClickHere`(누름틀) | 3,614 | 30 |
| `Hyperlink` | 567 | 25 |
| `CrossRef` | 316 | 6 |
| `Formula` | 27 | 10 |
| `Bookmark` | 24 | 7 |
| `Unknown` | 2 | 1 |

`MailMerge`·`Path`·`TableOfContents`·`Summary`·`UserInfo` 는 **0건**이다.

### 3.3 하이퍼링크가 실제로 가리키는 것

567건의 `command` 첫 필드(`;` 앞)를 스킴별로 분류했다.

| 대상 | 건수 | 예 |
|---|---:|---|
| 문서 **내부** 책갈피 (`?#숫자`, `?이름`) | **319** | `?#968516013`, `?Action.Run` |
| `javascript:` | 199 | `javascript\:\` |
| `https:` | 25 | `https\://apply.lh.or.kr` |
| `http:` | 17 | `http\://www.korean.go.kr)` |
| 기타 | 6 | |
| `mailto:` | 1 | |
| **`file:` 또는 `.hwp` 경로** | **0** | — |

고유 대상은 230종이었고, **그중 파일 경로처럼 보이는 것은 하나도 없었다**(`.hwp` 포함,
`file:` 시작, UNC `\\`, 드라이브 문자 `X:` 를 전부 검사).

`CrossRef` 316건도 전부 `?#<숫자>` 또는 `?<같은 문서의 문자열>` 형태였다 —
예: `hwpspec.hwp` 의 `?#1428148037;0;1;1;0;`, `hwpctl_ParameterSetID_Item_v1.2.hwp` 의
`?※ 대각선의 형태;6;1;1;0;`.

### 3.4 BinData LINK 보유 문서

`rhwp info` 의 BinData 목록(`src/main.rs:7572-7594`)을 353건에 돌려 `Link` 항목을 세었다.

| 문서 | LINK 항목 수 |
|---|---:|
| `hwp3-sample10.hwp` | 3 |
| `hwp3-sample10-hwp5.hwp` | 3 |
| `hwp3-sample10-hwpx.hwpx` | 3 |
| `issue1891_external_bindata_link.hwpx` | 1 |
| **합계** | **4문서 / 353** |

전부 그림 링크이며, HWP 문서를 가리키는 것은 없다.

## 4. 결론 — 링크는 없다

| 질문 | 답 | 근거 |
|---|---|---|
| HWP 에 "다른 문서를 인용한다"는 전용 구조가 있나 | **없다** | §2 전수 조사 |
| 하이퍼링크에 파일 경로를 넣을 수는 있나 | 형식상 가능(임의 문자열) | `Field.command` 는 자유 문자열 |
| 실제 문서들이 그렇게 쓰나 | **아니다 — 353건에 0건** | §3.3 |
| 문서 **내부** 참조 그래프는 만들 수 있나 | **그렇다** | 하이퍼링크 319 + 상호참조 316 이 책갈피를 가리킨다 |
| 문서 내부 참조의 **대상**을 조회할 표면이 있나 | **없다**(WASM 전용) | §2.2 |

**따라서 "어느 문서가 이 서식을 인용하나"에 링크로 답하는 기능은 만들 수 없다.**
만들면 언제나 빈 결과를 내는 도구가 되고, 그것은 에이전트에게 "인용하는 문서가 없다"는
**틀린 확신**을 준다 — 있지도 않은 것을 있는 것처럼 만드는 부류의 실패다.

## 5. 그러면 무엇으로 근사하나

Q2(유래)는 닮음으로만 답할 수 있다. 세 후보를 재료 유무 기준으로 비교한다.

### 5.1 후보 A — 누름틀 이름 집합 유사도

서식은 **누름틀 이름 집합**으로 자기를 드러낸다. 채워진 산출물도 이름은 그대로 남는다
(값만 채워진다). 재료는 이미 있다 — `fields --json` / `hwp_doc_fields`.

판정식은 Jaccard:  `J(A,B) = |이름(A) ∩ 이름(B)| / |이름(A) ∪ 이름(B)|`

**실측** — 누름틀을 2종 이상 가진 22문서의 모든 쌍(88쌍이 J>0):

| J | 쌍 | 무엇인가 |
|---:|---|---|
| 1.000 | `2025 행정업무운영 편람(최종).hwp` ↔ `.hwpx` (각 49종) | 같은 문서의 포맷 변환본 |
| 1.000 | `20250130-hongbo.hwp` ↔ `-no.hwp` ↔ `_saved.hwp` ↔ `honbo-save.hwp` (각 12종) | 같은 서식의 저장 변주 |
| 1.000 | `field-01.hwp` ↔ `field-01-memo.hwp` (각 7종) | 같은 서식 |
| 0.903 | `76076_regulatory_analysis.hwp`(143종) ↔ `80168_…`(150종), 교집합 139 | **같은 규제영향분석서 계열** |
| 0.884 | `80168_…` ↔ `issue1891_external_bindata_link.hwpx`(142종) | 같은 계열(파일 이름만 다름) |
| 0.667 | `76076_…` ↔ `86712_…`(202종) | 같은 계열, 항목 수 차이 |
| 0.443 | `80168_…` ↔ `80250_…`(104종) | 같은 계열의 **축약판** |
| 0.917 | `20250130-hongbo.hwp` ↔ `table-vpos-01.hwp` | **보도자료 서식 계열** — 이름은 다르지만 같은 서식에서 나왔다 |
| 0.259 | 편람 ↔ `issue2083_hide_fill_page.hwpx` (교집합 15) | 결재란 이름(`*검토1`·`*협조1` …)만 겹침 |
| 0.211~0.263 | 여러 쌍 (교집합 4~5) | `제목`·`기관명` 같은 **범용 이름**만 겹침 = 잡음 바닥 |

읽는 법이 분명하다. **J ≥ 0.6 은 같은 서식 계열**이었고, **J ≤ 0.3 은 범용 이름
몇 개가 겹친 잡음**이었다(그 구간 55쌍). 0.3~0.6 사이는 이 표본에 두 쌍뿐이라
경계값을 정할 근거가 부족하다 — **임계값을 도구가 정하지 않고 값을 그대로 내는** 이유다.

### 5.2 후보 B — 구조 지문(해시)

이름이 아니라 **모양**으로 잡는 방법이다. 후보 성분: 구역 수, 구역별 문단 수, 표의
행×열 격자 형태, 누름틀 개수와 순서, 쪽 크기·여백.

- 재료는 있다 — `export-structure`, `export-tables`, `info`(구역·문단·쪽 수).
- 해시 도구도 있다 — blake3 가 이미 의존성이고 자원 키에 쓰인다
  (`src/paint/resources.rs:14`, `:62`, `:236`). 진단 축은 레코드 페이로드 해시를
  `blake3:` 접두로 낸다(`src/diagnostics/hwp5_inventory.rs:351`).
- **약점**: 채우면 모양이 변한다. 값이 길어 줄이 늘면 문단 수·쪽 수가 달라진다. 즉
  구조 지문은 **채우기 전후로 안 맞을 수 있다** — 서식↔산출물을 잇는 데는 A 보다 약하다.
- **강점**: 누름틀이 아예 없는 서식(표만 있는 양식)에서는 A 가 못 하는 일을 한다.

### 5.3 후보 C — `ir-diff` 를 판정기로

`rhwp ir-diff A B --json` 이 이미 있다. 비교 항목은 text·char_count·char_offsets·
char_shapes·line_segs·controls·ParaShape·TabDef, 표·그림 속성까지다(`--help`).
차이가 있으면 exit 3.

- **강점**: 가장 정밀하다.
- **약점**: 두 문서를 **모두 파싱**해야 한다. N 건 후보 대조는 O(N) 번의 전체 파싱이다
  (문서당 48.5 ms, 353건이면 17초 — §3.1). 그리고 결과가 "같다/다르다" 에 가까워
  **닮음의 정도**를 주지 않는다.
- **적합한 자리**: A 로 후보를 좁힌 뒤 **최종 확인**.

### 5.4 권고 — A 를 1차, C 를 확인, B 는 보조

```
1차 필터   누름틀 이름 집합 Jaccard (fields --json 만 있으면 된다, 문서당 48.5 ms)
        ↓  J 값을 그대로 낸다 — 임계값은 호출자가 정한다
2차 확인   ir-diff 로 최종 대조 (후보가 소수로 줄었을 때만)
보조      누름틀이 없는 서식에서는 구조 지문
```

## 6. 이 근사가 무엇을 틀리는가

정직하게 적어야 도구가 오용되지 않는다.

| 성격 | 사례(실측) | 뜻 |
|---|---|---|
| **오탐 — "같은 계열"과 "인용"은 다르다** | `20250130-hongbo.hwp` ↔ `table-vpos-01.hwp` J=0.917 | 둘 다 같은 보도자료 서식에서 나왔지만, **한쪽이 다른 쪽을 인용한 것은 아니다.** 방향이 없다 |
| **오탐 — 범용 이름** | 교집합이 `제목`·`기관명` 5개뿐인 쌍이 J=0.263 | 서로 무관한 서식이 흔한 이름 몇 개로 겹친다 |
| **미탐 — 이름을 바꾼 파생** | (표본 없음) | 서식을 복사해 누름틀 이름을 손보면 J 가 떨어진다 |
| **미탐 — 누름틀 없는 서식** | 353건 중 누름틀 보유는 **30건뿐** | 대다수 문서는 A 로 아무것도 못 한다 |
| **동률 문제** | 규제영향분석서 5건이 서로 0.62~0.90 | "원본이 누구인가" 를 정하지 못한다. 방향은 이름 집합이 **더 큰 쪽이 원본**이라는 식의 휴리스틱뿐이고, 근거가 약하다 |

> **그래서 도구는 "인용한다" 고 말하면 안 된다.** 낼 수 있는 것은 `similarity` 라는
> 숫자와 그 근거(교집합 크기·양쪽 이름 수)뿐이다. 판단은 호출자가 한다 — 판정을
> 데이터로 내는 것은 이 저장소 세션 봉투의 일관된 태도다
> (`hwp_doc_save` 의 `verify`, `src/mcp_serve.rs:1394-1405`).

## 7. 보안 경계 — 문서가 가리킨 경로를 따라가지 않는다

참조 조회는 **문서 안의 문자열을 경로로 해석**하고 싶어지는 기능이다. 그 순간
경계 계약과 정면으로 만난다.

[S5](../agent_boundary_contract.md#s5--경로는-문서-내용에서-파생되지-않는다) 는 **산출**
경로가 문서 내용에서 나오지 않음을 보장한다. 참조 조회가 만드는 것은 **입력** 경로다 —
계약이 아직 다루지 않은 방향이고, 위험은 더 크다.

- `BinData` 의 `abs_path` 는 공격자가 정할 수 있는 문자열이다(§2.3). 그것을 열면
  임의 파일 읽기가 된다.
- 하이퍼링크 `command` 도 마찬가지다. 실측에서는 `http`/`https`/`javascript:` 가
  나왔지만(§3.3), 만들려면 무엇이든 넣을 수 있다.
- `javascript:` 199건이 이미 코퍼스에 있다는 사실 자체가 **문서에 실행 의도 문자열이
  흔하다**는 증거다.

**규칙:**

1. 참조 조회는 **가리키는 값을 보고**할 뿐 **열지 않는다.**
2. 대조 대상 문서 집합은 **호출자가 준 목록**(또는 워크스페이스 구성원)에서만 온다 —
   문서가 지목한 경로로 집합을 넓히지 않는다.
3. 보고되는 링크 문자열은 다른 문서 유래 텍스트와 같이 **비신뢰 표시**를 달고 나간다.
   `info` 봉투가 `untrustedContent`·`untrustedFields` 를 다는 것과 같은 방식이다
   (실측: `rhwp info --json` 이 `"untrustedContent":true,"untrustedFields":["title","fonts[]"]`
   를 낸다 — `src/provenance.rs`).

배경은 [에이전트 보안 문서 지도](../agent_security/README.md)와
[위협 모델](../agent_security/threat_model.md)에 있다.

## 8. 계약 제안

설계이며 구현이 아니다. 셋으로 나뉘고, **위에서부터 작고 확실하다.**

### 8.1 (작고 확실) 문서 내부 참조 그래프 — Q3

```
hwp_doc_references { docId }
→ { schemaVersion, docId,
    bookmarks: [ { name, section, paragraph } ],
    references: [ { kind: "hyperlink"|"crossref", target, resolved: <bool>,
                    section, paragraph } ],
    danglingCount: <n> }
```

- 재료가 전부 있다. 필요한 것은 `get_bookmarks_native` 를 MCP 로 여는 것뿐(§2.2).
- `resolved:false`(끊어진 참조)는 문서 품질 점검의 실질적 산출이다 — 상호참조 316건을
  가진 `hwpspec.hwp` 같은 문서에서 바로 값이 난다.
- `target` 은 §7-3 에 따라 비신뢰 표시를 단다.

### 8.2 (근사) 서식 닮음 — Q2

```
hwp_similar_forms { docId, candidates: [path…] | wsId, minSimilarity? }
→ { schemaVersion, docId, method: "fieldNameJaccard",
    results: [ { path|docId, similarity, sharedCount, aCount, bCount } ],
    note: "이름 집합 닮음이며 인용 관계가 아니다" }
```

- `candidates` 는 **호출자가 준다**(§7-2).
- `similarity` 는 값만 낸다. 임계값을 도구가 정하지 않는다(§5.1).
- `method` 를 봉투에 박아 나중에 다른 방법이 추가돼도 소비자가 구별할 수 있게 한다.

### 8.3 (하지 않음) 역방향 색인

"이 서식을 쓰는 문서 목록"을 서버가 미리 만들어 두는 것. **하지 않는다** — 색인 대상
집합을 서버가 정하게 되고(§7-2 위반), 무효화 문제가 [파일 감시](incremental_reparse.md)
전체를 색인에도 다시 요구한다. 워크스페이스 구성원(수십 건) 안에서는 색인 없이 전수
비교로 충분하다(문서당 48.5 ms).

## 9. 무엇을 하지 않는가

1. **링크 기반 "인용" 도구** — 링크가 없다(§4). 언제나 빈 결과를 내는 도구는 만들지 않는다.
2. **문서가 가리킨 경로를 여는 기능** — §7.
3. **유사도 임계값 내장** — 판정은 호출자 몫(§5.1, §6).
4. **전역 역방향 색인** — §8.3.
5. **`MailMerge` 데이터 원본 추적** — IR 에 원본 이름을 담는 자리가 없고 코퍼스에 0건이다(§2.1, §3.2).

## 10. 확인되지 않음

- HWP 5.0 **스펙**에 문서 간 링크를 담는 구조가 있는지 — rhwp IR 에는 없다는 것만
  확인했다. 스펙 원문 대조는 하지 않았다(§2.4).
- 한글에서 "다른 문서로 하이퍼링크" 를 만들면 `command` 가 어떤 형태로 저장되는지 —
  한컴오피스가 이 PC 에 없어 만들어 보지 못했다. 파싱 쪽은 자유 문자열이므로 읽히기는
  할 것으로 보이나 **형식은 미확인**.
- J 의 0.3~0.6 구간 성격 — 표본이 두 쌍뿐이라 판단 근거가 없다(§5.1).
- 구조 지문(후보 B)의 실제 판별력 — 설계만 했고 실측하지 않았다.
- 353건 중 누름틀 보유 30건이라는 비율이 **실무 문서 분포를 대표하는지** — `samples/`
  는 회귀 테스트용으로 모인 집합이라 편향이 있다.

## 11. 검증 계획

1. `references_envelope_lists_bookmarks_and_targets` — 상호참조를 가진 고정 표본
   (`hwpspec.hwp`, 316건 중 일부)에서 참조 개수와 해소 여부가 재현된다.
2. `dangling_reference_is_reported_not_error` — 끊어진 참조는 `isError:false` + 계수.
3. `similarity_is_symmetric_and_bounded` — `J(A,B) == J(B,A)`, `0 ≤ J ≤ 1`,
   자기 자신은 1.0.
4. `similarity_matches_measured_baseline` — 규제영향분석서 계열의 J 값이 이 문서
   §5.1 표와 일치한다(회귀 기준선).
5. `reference_targets_are_marked_untrusted` — 봉투의 링크 문자열이 비신뢰 표시를 단다(§7-3).
6. `candidates_come_only_from_caller` — 문서 내용에 경로를 심어 두고 호출해도 그 경로는
   후보 집합에 들어가지 않는다(§7-2). `tests/boundary_integrity_contract.rs` 의 S5
   테스트와 같은 형태.
