# 파일 감시와 증분 재파싱 (M25)

> 로드맵 [#3608](https://github.com/edwardkim/rhwp/issues/3608) M25 의 첫 항목 —
> "장수명 서버 모드 확장: 파일 감시 + 증분 재파싱".
> 이 문서는 **설계**다. 여기 나오는 도구·필드는 아직 구현되어 있지 않다.
> 디렉터리 개요는 [README](README.md).

## 0. 이 문서가 정하는 것

`mcp-serve` 는 문서를 파싱해 `docId` 로 들고 있다. 그 문서의 **원본 파일이 디스크에서
바뀌면 무슨 일이 벌어져야 하는가** — 이 문서가 답하는 질문은 그것 하나다.

세 가지를 갈라 정한다.

1. **무엇이 증분으로 가능하고 무엇이 불가능한가** — HWP 포맷 구조에서 나오는 답.
2. **그래서 감시는 무엇을 위한 것인가** — 속도가 아니라면 무엇인가.
3. **파일 감시의 함정** — 저장 중간 상태, 임시 파일, 원자 교체, 플랫폼 잠금.

**결론을 먼저 적는다.** 편집 델타 기반의 증분 재파싱은 HWP 에서 **성립하지 않는다.**
파일이 바뀌면 통째로 다시 읽는 것이 답이다. 그럼에도 파일 감시에는 값이 있는데, 그 값은
**빨라지는 것이 아니라 틀린 답을 멈추는 것**이다(§5).

## 1. 출발점 — 현재 세션 모델

| 사실 | 근거 |
|---|---|
| `hwp_open` 은 `std::fs::read(path)` 로 **파일 전체**를 메모리에 올린 뒤 `HwpDocument::from_bytes` 로 파싱한다 | `src/mcp_serve.rs:680-695` |
| 핸들 구조체는 `doc` / `source_is_hwpx` / `size_bytes` / `detected_format` 네 필드다 — **경로도, mtime 도, 해시도 없다** | `src/mcp_serve.rs:41-49` |
| 응답 봉투에 `source: path` 를 싣지만 서버 상태에는 남기지 않는다 | `src/mcp_serve.rs:712-720` |
| 핸들은 프로세스가 사는 동안 유지되고 TTL 이 없다 | [S8](../agent_boundary_contract.md#s8--핸들-무결성) |
| 서버 루프는 stdin 한 줄을 블로킹으로 읽어 응답 한 줄을 쓴다 — 요청이 없으면 아무 코드도 돌지 않는다 | `src/mcp_serve.rs:116-227` |
| `initialize` 응답이 `resources` 의 `subscribe`·`listChanged` 를 **명시적 미지원**으로 선언한다 | `src/mcp_serve.rs:189-191` |

여기서 이미 하나가 확정된다. **파일 감시를 붙이려면 핸들에 원본 경로를 먼저 넣어야
한다.** 지금 구조로는 서버가 "이 `docId` 가 어느 파일에서 왔는지"를 모른다 — 재읽기도,
중복 제거도, 변경 감지도 전부 이 한 필드가 없어 막혀 있다. 이것은 세 M25 항목이 공유하는
선행 조건이다([워크스페이스 핸들 §2](workspace_handles.md#2-지금-있는-것--docid-하나--문서-하나)).

## 2. 실측 — 재파싱은 얼마나 비싼가

증분이 얼마를 아끼는지 판단하려면 **전체 재파싱 비용**을 알아야 한다.

### 2.1 측정 방법

- 환경: Windows 11, `<저장소>/target/release/rhwp.exe`
  (v0.8.2 릴리스 빌드), 저장소 `samples/`.
- 무상태 CLI: bash 에서 `date +%s%N` 으로 감싸 7회 반복, 밀리초 정수.
- 세션: Python `subprocess` 로 `rhwp mcp-serve` 를 실제 stdio 구동하고
  `time.perf_counter()` 로 **요청 write → 응답 readline** 왕복을 잰다. 순수 함수 벤치가
  아니라 JSON-RPC 왕복을 포함한 값이다(공개 벤치와 같은 방식 —
  [bench_session_vs_stateless](../../report/bench_session_vs_stateless/README.md)).
- RSS 는 `Get-Process -Id <pid>` 의 `WorkingSet64`.

### 2.2 프로세스 기동 오버헤드

```
rhwp --version ×7 : 89 92 106 89 95 100 99 ms   (중앙값 95 ms)
```

이 PC 에서는 **실행 파일을 띄우는 것만으로 95 ms** 다. 무상태 CLI 호출은 문서 크기와
무관하게 이 값을 매번 문다. (절대값은 머신 의존이며, 백신 실시간 검사 등이 섞인
값이다 — 비율만 계약으로 쓴다.)

### 2.3 무상태 `info --json` (기동 포함)

| 문서 | 크기 | 쪽/구역/문단 | 7회 (ms) | 중앙값 |
|---|---:|---|---|---:|
| `2025 행정업무운영 편람(최종).hwp` | 10,687,488 B | 393쪽 / 14구역 / 2,618문단 | 229 222 231 226 225 225 227 | **226** |
| `2025 행정업무운영 편람(최종).hwpx` | 13,639,865 B | 387쪽 | 304 301 295 288 295 287 287 | **295** |
| `exam_kor.hwp` | 10,418,688 B | 20쪽 | 142 136 142 137 136 136 137 | **137** |

크기가 같아도(10.6 MB vs 10.4 MB) 비용이 226 ms 대 137 ms 로 갈린다. **바이트 수가 아니라
문단·쪽 수가 비용을 정한다** — `exam_kor` 는 대부분이 이미지 바이트다.

### 2.4 세션 `hwp_open` (기동 제외, 왕복 포함)

| 문서 | 크기 | 쪽 | `hwp_open` |
|---|---:|---:|---:|
| 편람 `.hwp` | 10.6 MB | 393 | 131.6 ms / 126.5 ms |
| 편람 `.hwpx` | 13.6 MB | 387 | 194.7 ms |
| `exam_kor.hwp` | 10.4 MB | 20 | 29.7 ms |
| 정책연구 중간진도보고서 `.hwp` | 7.1 MB | 225 | 173.9 ms |
| `issue2083_hide_fill_page.hwpx` | 203 KB | — | 4.81 ms (20회 평균) |
| `20250130-hongbo.hwp` | 628 KB | — | 1.79 ms (20회 평균) |
| `form-01.hwp` | 18 KB | — | 0.49 ms (20회 평균) |

`226 − 131.6 ≈ 95` — 무상태와 세션의 차이는 정확히 프로세스 기동값이다. 파싱 자체가
느린 것이 아니라 **매번 새로 여는 것**이 느리다.

### 2.5 열어 둔 뒤의 조회 비용 (재파싱 없음)

편람 `.hwp` 핸들 기준:

| 호출 | 비용 |
|---|---:|
| `hwp_doc_info` | 0.67 ~ 1.93 ms |
| `hwp_doc_search`(maxMatches=5) | 0.60 ~ 4.09 ms |
| `hwp_doc_fields` | 0.25 ~ 4.22 ms |
| `hwp_doc_render_page`(SVG 716,593 B) | 3.2 ms |
| `hwp_doc_text`(page=3) | 0.5 ms |
| `hwp_doc_text`(전체 393쪽, maxChars=2000) | **374.4 ms** |

마지막 줄은 예외이자 경고다. `hwp_doc_text` 는 페이지를 생략하면 전 쪽을 순회하므로
(`src/mcp_serve.rs:837`, `None => (0..page_count).collect()`) **여는 것보다 비싸다.**
`maxChars` 는 봉투를 자를 뿐 추출 자체를 줄이지 않는다(`src/mcp_serve.rs:848`,
`crate::truncate_page_texts` 는 이미 뽑은 텍스트를 자른다). 감시·증분과는 별개의 공백이라
여기서는 사실만 기록한다.

### 2.6 파싱 비용과 조판 비용의 분해

전체를 파싱·조판이라고 뭉뚱그리면 "증분이 무엇을 아끼는가"를 못 따진다. 편집 API 로
구역을 dirty 로 만든 뒤의 **재조판만** 재서 갈랐다.

| 호출 | 결과 | 비용 |
|---|---|---:|
| `hwp_doc_replace_text`(없는 문자열) | `replacedCount=0`, 재조판 없음 | 4.2 / 4.5 / 4.9 ms |
| `hwp_doc_replace_text`("행정업무"→동일) | 241건, 여러 구역 dirty | 54.1 / 54.6 / 56.9 ms |
| `hwp_doc_replace_text`("의"→동일) | 4,357건, 전 구역 dirty, `changedPages` 355쪽 | 68.9 ms |
| 파일 읽기(페이지 캐시 적중, 10.2 MB) | — | 3.1 ms |

0건 갈래(4.5 ms)는 **전수 grep 만** 한 값이다(`src/mcp_serve.rs:1055`, `doc.grep`). 전 구역
갈래에서 그만큼을 빼면 **전 구역 재조판 ≈ 64 ms**.

```
hwp_open(126 ms) ≈ 읽기(3 ms) + 파싱·compose(≈59 ms) + 최초 조판(≈64 ms)
```

즉 **비용은 파싱과 조판이 대략 반반**이다.

> **이 분해의 한계.** 68.9 ms 안에는 4,357회의 문자열 치환과 그에 따른 문단 recompose 가
> 함께 들어 있다. 따라서 64 ms 는 **순수 재조판의 상한**이고, 파싱 몫 59 ms 는 그만큼
> **하한**이다. "반반"은 자릿수 판단으로만 쓰고, 정밀한 분해가 필요하면 코어에 계측을
> 넣어 다시 재야 한다.

그리고 조판 쪽은 **이미 증분이다** —
`DocumentCore` 는 구역별 dirty 비트를 들고 dirty 구역만 재처리한다
(`src/document_core/queries/rendering.rs:3878-3884`, `:4023`,
`recompose_section` `:3380-3403`). 최초 로드에서 전 구역이 dirty 로 시작하므로
(`src/document_core/commands/document.rs:179`) 첫 조판만 전량이고, 이후 편집은
바뀐 구역만 다시 짠다.

> **이미 있는 증분을 다시 만들지 말 것.** M25 가 얹을 것은 조판 증분이 아니다.
> 조판 증분은 편집 경로에서 이미 동작하고 있고, 세션 편집 도구가 `repaginate_if_needed()`
> 로 그것을 호출한다(`src/mcp_serve.rs:1073`, `:1331`).

## 3. LSP 의 증분과 HWP 의 증분은 같은 문제가 아니다

LSP 의 `textDocument/didChange` 는 **에디터가 보낸 편집 델타**(범위 + 새 텍스트)를 받는다.
서버는 원본을 다시 읽지 않고, 그 범위만 다시 렉싱·파싱한다. 성립 조건이 셋이다.

1. 문서가 **텍스트**다 — 오프셋으로 범위를 말할 수 있다.
2. 변경을 **에디터가 알려준다** — 서버가 파일을 다시 읽는 것이 아니다.
3. 문법이 **국소적**이다 — 한 줄 변경이 파일 전체 구조를 흔들지 않는다.

HWP 에서 셋 다 성립하지 않는다.

### 3.1 문서가 바이너리 컨테이너다

- **HWP5** 는 CFB(복합 파일) 컨테이너다. `FileHeader` / `DocInfo` / `BodyText/Section{i}` /
  `BinData/*` 가 각각 스트림이고, 스트림 내용은 대개 zlib deflate 압축이다
  (`src/parser/mod.rs:183-184`, `:263-310`). 바이트 오프셋 하나가 문단 하나에 대응하지
  않는다 — 압축이 그 대응을 지운다.
- **HWPX** 는 ZIP 이다. `Contents/section0.xml`, `Contents/section1.xml` … 이 구역별로
  나뉘어 있다(`src/parser/hwpx/content.rs:242-243`). 겉보기에는 XML 이지만, ZIP 의
  중앙 디렉터리가 **파일 끝**에 있어 부분 읽기의 진입점이 되지 못한다(§4.2 실측).

### 3.2 변경을 알려주는 주체가 없다

한글(한컴오피스)은 rhwp 에게 편집 델타를 보내지 않는다. 저장 버튼을 누르면 **완성된 새
파일**이 디스크에 나타날 뿐이다. 그 순간 서버가 아는 것은 "파일이 달라졌다"가 전부이고,
**무엇이 달라졌는지는 다시 파싱해야만 알 수 있다.** 이 한 문장이 증분 재파싱을 무너뜨린다.

### 3.3 무엇이 국소적이고 무엇이 아닌가

| 대상 | 국소적인가 | 근거 |
|---|---|---|
| 본문 구역 파싱 | **부분적으로 그렇다** — 구역이 CFB 스트림 / ZIP 엔트리로 이미 분리 | `src/parser/mod.rs:580-600` (`parse_sections_strict` 가 구역별 루프), `src/parser/hwpx/content.rs:242` |
| `DocInfo` (글꼴·글자모양·문단모양·BinData 목록) | **아니다** — 전 구역이 인덱스로 참조하는 공유 테이블 | `src/parser/mod.rs:306` 앞뒤(3단계 DocInfo → 4단계 구역) |
| 조판 | **그렇다** — 이미 구역 dirty 단위 증분 | `rendering.rs:3878-3884` |
| 쪽 번호 | **아니다** — 앞 구역이 한 줄 늘면 뒤 구역 쪽 번호가 전부 밀린다 | `changedPages` 계약이 이 성질 위에 있다(`src/mcp_serve.rs:1003-1018`) |

### 3.4 그래서 "구역만 다시 파싱"은 왜 실익이 없는가

이론상으로는 가능하다 — 구역 3만 바뀌었다면 구역 3 스트림만 풀어 다시 읽으면 된다.
실제로 막는 것은 셋이다.

1. **어느 구역이 바뀌었는지 알려면 이미 다 읽어야 한다.** 압축 스트림의 바이트가
   달라졌다는 것과 IR 이 달라졌다는 것은 다른 말이다(같은 내용도 압축기 설정이 바뀌면
   다른 바이트가 된다). 스트림 바이트 해시로 걸러 낼 수는 있지만, 그러려면 컨테이너를
   열어 전 스트림을 훑어야 한다 — 그 비용이 이미 파싱의 상당 부분이다.
2. **`DocInfo` 가 공유 테이블이다.** 사용자가 글자 색 하나만 바꿔도 `CharShape` 테이블이
   재배치될 수 있고, 그러면 전 구역의 인덱스 해석이 달라진다. 구역만 갈아 끼우면
   IR 이 조용히 어긋난다 — **조용히 틀리는 부류**라 가장 나쁘다.
3. **아껴 봐야 절반의 일부다.** §2.6 에서 파싱은 전체의 약 절반(≈59 ms/126 ms)이고,
   그중 구역 파싱만 골라 아끼는 것이므로 상한이 수십 ms다. 그 대가로 얻는 것은
   "IR 이 어긋날 수 있는 새 경로"다. **값이 위험보다 작다.**

> **결정 — 파일이 바뀌면 통째로 다시 읽는다.** 구역 단위 부분 재파싱은 M25 범위에서
> 기각한다. 재파싱 비용은 이미 대형 문서에서 130~195 ms 수준이고, 이는 사람의 저장
> 동작 뒤에 한 번 무는 비용으로 충분히 작다.

## 4. 파일 감시의 함정

감시를 붙이겠다고 결정하면 실제 난점은 성능이 아니라 **언제 읽을 것인가**다. 아래는 전부
이 저장소 코드 또는 이 PC 실측에서 나온 것이다.

### 4.1 저장 중간 상태 — 절반 쓰인 파일

수정 알림은 **쓰기가 끝나기 전에** 온다. 그 순간 읽으면 무엇이 나오는가 — 실측했다.

| 입력 | 결과 | 종료 코드 |
|---|---|---:|
| 편람 `.hwp` 앞 50% | `표준 CFB 파서 실패: DIFAT refers to sector 20872, but sector count is only 10436` → lenient 재시도 → `헤더 오류: HWP 시그니처가 일치하지 않습니다` | 1 |
| 편람 `.hwp` 앞 99% | 같은 형태로 실패 | 1 |
| 0 바이트 | `지원하지 않는 포맷입니다: 빈 파일. 오류코드: EMPTY_FILE` | 1 |
| 편람 `.hwpx` 앞 50% / 99% | `ZIP 오류: invalid Zip archive: Could not find EOCD` | 1 |

**좋은 소식이다.** 잘린 파일은 *조용히 절반짜리 IR* 이 되지 않고 **소리 내어 실패**한다.
CFB 는 DIFAT 섹터 수가 안 맞아서, ZIP 은 EOCD(중앙 디렉터리 끝 레코드)가 파일 끝에 있어서
그렇다. 즉 감시자가 실수로 중간 상태를 읽어도 **손상된 상태로 핸들이 갱신되는 일은 없다.**

그렇다고 읽어도 된다는 뜻은 아니다. 실패도 비용이고(대형 파일이면 읽기 + 컨테이너 열기까지
간다), 무엇보다 **실패를 어떻게 보고할지**가 계약이 된다(§6.3).

### 4.2 임시 파일과 원자 교체

rhwp 자신이 원자 교체로 쓴다. 감시자가 이 패턴을 모르면 자기 산출물에 반응한다.

- `write_atomically` 는 형제 임시 파일을 만들고 `sync_all` 후 `rename` 한다
  (`src/atomic_file.rs:5-24`).
- 임시 이름은 `.rhwp-hml-{pid}.{nonce}.{attempt}.tmp` (`src/atomic_file.rs:33-40`).
- 사용처는 `src/main.rs:11089`, `:14590`, `:15062`.

따라서 감시자가 폴더 단위로 보면 **한 번의 저장이 최소 세 이벤트**로 온다: 임시 파일 생성 →
(여러 번의) 수정 → 대상 경로로 rename. 반응해야 할 것은 **rename 이 끝난 뒤의 대상 경로**
하나뿐이다.

> **비대칭 주의.** 세션 저장(`hwp_doc_save`)은 원자 교체를 쓰지 않고
> `std::fs::write(output, &bytes)` 로 직접 쓴다(`src/mcp_serve.rs:1391`). 즉 세션이 만든
> 산출물은 **잘린 중간 상태가 관측 가능한 시간창**을 가진다. 감시와 세션 저장이 같은
> 폴더에서 만나면 이 창이 그대로 함정이 된다. (이 비대칭 자체가 별도 공백이다 —
> 감시 설계와 무관하게 정합을 맞출 값이 있다.)

한글이 저장할 때 어떤 임시 파일·교체 패턴을 쓰는지는 **확인되지 않음** — 이 PC 에
한컴오피스가 설치되어 있지 않아 실측하지 못했다. 설계는 "임시 파일 + rename" 과
"제자리 덮어쓰기" **둘 다 올 수 있다**는 전제로 세운다.

### 4.3 Windows 공유 위반 (실측)

저장 중인 파일이 배타 잠금되어 있으면 rename 이 아니라 **읽기 자체**가 실패한다.

```console
$ # 다른 프로세스가 GENERIC_WRITE·공유 0 으로 연 파일
$ rhwp info --json locked.hwp
오류: 파일을 읽을 수 없습니다 - locked.hwp: 다른 프로세스가 파일을 사용 중이기 때문에
프로세스가 액세스 할 수 없습니다. (os error 32)
exit 1
```

`os error 32`(ERROR_SHARING_VIOLATION)는 **일시적**이다 — 잠금이 풀리면 성공한다. 감시
설계에서 이 오류만은 "실패"가 아니라 "아직"으로 취급해야 한다. 다른 오류(시그니처 불일치,
EMPTY_FILE)와 같은 갈래로 뭉개면 **정상 저장이 영구 실패로 보고된다.**

POSIX 에서는 같은 상황이 잠금이 아니라 절단된 읽기로 나타난다(§4.1). 즉 **플랫폼마다
실패 모양이 다르다** — 이것이 "일정 시간 조용해질 때까지 기다린다"(디바운스)가 플랫폼
공통의 유일한 방어인 이유다.

### 4.4 감시 수단 — 의존성이 없다

`Cargo.toml` 의 `[dependencies]` 에 `notify` 계열 크레이트가 **없다**. 파일 감시를 넣으려면
둘 중 하나다.

| 방식 | 장점 | 비용 |
|---|---|---|
| 새 의존성(`notify` 등) | OS 네이티브 알림, 저지연 | 의존성 추가. `mcp_serve` 는 WASM 에 포함되지 않으므로(`src/mcp_serve.rs:16-17`) `#[cfg(not(target_arch = "wasm32"))]` 로 가둘 수는 있다 |
| 폴링(mtime + 크기, 또는 내용 해시) | 의존성 0, 동작이 뻔함, 플랫폼 차이 없음 | 주기만큼 지연. 대형 파일 해시는 비쌈 |

`mcp-serve` 모듈의 설계 원칙이 "의존성은 추가하지 않는다"임을 모듈 주석이 명시한다
(`src/mcp_serve.rs:16-17`). **폴링을 기본으로 제안한다** — 감시 대상이 열린 핸들 수(수십)
수준이고, `mtime`+`len` 비교는 `fs::metadata` 두 필드 읽기라 비용이 무시할 만하다.
내용 해시(blake3 는 이미 의존성이다 — `src/paint/resources.rs:14`, `:62`)는 mtime 이
믿기 어려운 환경의 **옵트인**으로 남긴다.

> **mtime 만으로는 부족한 경우가 있다.** 같은 초에 두 번 저장되거나(해상도), 복원 도구가
> mtime 을 보존하며 내용을 바꾸는 경우다. 그래서 기본 판정은 `(mtime, len)` **쌍**이고,
> 둘 다 같은데 내용이 다른 경우는 이 설계가 놓치는 것으로 **명시**한다(§8).

### 4.5 디바운스와 이벤트 폭풍

한 번의 저장이 여러 이벤트로 오고(§4.2), 잘린 상태가 관측 가능하며(§4.1), 잠금이
걸릴 수 있다(§4.3). 세 함정의 공통 해법은 하나다 — **마지막 변화 관측 후 일정 시간
정지했을 때에만 상태를 바꾼다.**

- 기본 정지 시간은 **보수적으로 크게**(수백 ms 수준) 잡는다. 이 축의 비용은 지연이고,
  지연은 잘못된 재로딩보다 싸다.
- `os error 32` 는 정지 타이머를 **되돌린다**(아직 쓰는 중이라는 신호다).
- 이 값은 계약이 아니라 조정 가능한 상수로 둔다 — 이 문서가 특정 밀리초를 못 박지 않는
  이유는, 저장 소요가 파일 크기와 저장 주체에 따라 달라지고 그 분포를 실측하지 못했기
  때문이다(**확인되지 않음**).

## 5. 그래서 감시는 무엇을 위한 것인가

증분 재파싱이 없다면 감시의 값은 속도가 아니다. **캐시 무효화 시점을 아는 것**이다.
지금 벌어질 수 있는 일을 그대로 적으면 값이 분명해진다.

### 5.1 지금 일어나는 일 — 조용한 스테일

```
에이전트                        디스크                         핸들 doc-1
  hwp_open("보고서.hwp")  →     v1 읽음                    →   v1 IR
                                사용자가 한글로 편집·저장  →   (그대로 v1)
  hwp_doc_search(...)     →                                →   v1 결과를 성공으로 반환
  hwp_doc_fill_fields(...)→                                →   v1 IR 에 누적
  hwp_doc_save("보고서.hwp")                               →   v2 를 v1+편집 으로 덮어씀
```

마지막 줄이 **사용자의 편집을 소리 없이 지운다.** 그리고 그 전 두 줄은 옛 문서를 근거로
`isError: false` 를 돌려준다 — 에이전트에게는 성공으로 보인다. 이것이 감시가 막아야 할
것이고, "속도"가 아니라 **정확성** 축이다.

### 5.2 무효화가 주는 것 — 세 단계

| 단계 | 서버가 하는 일 | 값 |
|---|---|---|
| 감지 | `(mtime, len)` 이 열 때와 다르다는 것을 안다 | 스테일을 **말할 수 있게** 된다 |
| 표시 | 이후 응답 봉투에 스테일 표식을 싣는다 | 에이전트가 판단할 재료를 얻는다 |
| 재적재 | 명시 요청이 오면 통째로 다시 읽고 새 리비전을 준다 | 되돌아갈 길이 생긴다 |

세 단계는 **분리 가능**하고, 값의 대부분은 첫 두 단계에 있다. 재적재는 편집 누적이 있는
핸들에서 **되돌릴 수 없는 손실**(누적된 편집 폐기)을 만들 수 있으므로 자동이어서는 안 된다.

### 5.3 자동 재로딩을 하지 않는 이유

세션 편집 도구(`hwp_doc_fill_fields`·`replace_text`·`set_cell`)는 디스크에 쓰지 않고
**핸들의 IR 에 누적**한다(`src/mcp_serve.rs:1020-1021`, `:1229-1233`). `hwp_doc_save` 만이
기록 지점이다. 따라서 자동 재로딩은 곧 **누적된 편집의 무단 폐기**다. 그것을 성공 응답
사이에 조용히 끼워 넣는 것은 에이전트 표면에서 가장 피해야 할 부류다.

## 6. 계약 제안

아래는 설계이며 구현이 아니다. 형태는 기존 세션 도구 계약을 그대로 따른다.

### 6.1 핸들에 추가할 상태

```
SessionDoc {
    doc, source_is_hwpx, size_bytes, detected_format,   // 지금 있는 것
    source_path: PathBuf,        // 신규 — 감시·중복제거·재적재의 선행 조건
    source_mtime: Option<SystemTime>,   // 신규 — 열 때 찍은 값
    source_len: u64,             // 신규 — mtime 과 쌍으로 판정
    revision: u64,               // 신규 — 재적재·편집마다 증가
}
```

`revision` 은 **단조 증가**이고 `docId` 는 바뀌지 않는다. 핸들 번호 재사용이 ABA 를
만든다는 [S8 부록 5번](../agent_boundary_contract.md#부록--이-계약을-깨뜨리는-변경)과
같은 이유로, 재적재에 **새 `docId` 를 발급하지 않는다**(옛 번호가 되살아나지도, 같은
번호가 다른 문서를 가리키지도 않게 하려면 리비전이 옳은 축이다).

### 6.2 봉투에 추가할 필드

모든 세션 도구 응답에 다음을 싣는다. 기존 필드는 건드리지 않으므로 하위호환이다.

| 필드 | 값 | 뜻 |
|---|---|---|
| `revision` | 정수 | 이 응답이 근거한 핸들 리비전 |
| `sourceChanged` | `true`/`false`/`null` | 원본이 열 때와 달라졌는가. `null` 은 **판정 불가**(파일이 사라졌거나 metadata 를 못 읽음) |

`sourceChanged: true` 는 **오류가 아니다.** `isError` 는 그대로 `false` 이고, 판정은
데이터로 낸다 — `hwp_doc_save` 의 `verify` 가 취한 것과 같은 태도다
(`src/mcp_serve.rs:1394-1405`). 다만 `hwp_doc_save` 만은 예외를 둘 값이 있다(§6.4).

### 6.3 새 도구 2종

```
hwp_doc_check_source { docId }
  → { docId, revision, sourceChanged, reason }
     reason: "unchanged" | "mtime" | "size" | "missing" | "locked" | "unreadable"

hwp_doc_reload { docId, discardEdits: bool }
  → { docId, revision, reloaded: true, discardedEdits: <bool> }
```

- `hwp_doc_check_source` 는 **파일을 읽지 않는다** — `metadata` 만 본다. 그래서 싸고,
  대형 문서에서도 상수 시간이다.
- `hwp_doc_reload` 는 통째로 다시 읽는다(§3 결론). 누적 편집이 있는데
  `discardEdits: false` 면 **거부**하고 `nextCall` 로 교정을 동봉한다 —
  기존 죽은 핸들 갈래와 같은 형태다(`src/mcp_serve.rs:806-812`).
- `reason: "locked"` 는 §4.3 의 `os error 32` 전용 갈래다. "아직"과 "틀렸다"를
  같은 문자열로 뭉개지 않는다.

### 6.4 감시 모드는 옵트인

```
rhwp mcp-serve --watch[=poll-ms]
```

- 기본은 **꺼짐**. 켜지 않으면 지금 동작 그대로다(회귀 0).
- 켜면 폴링 스레드가 열린 핸들의 `(mtime, len)` 을 주기적으로 확인해 `sourceChanged` 를
  갱신한다. **재적재는 절대 자동으로 하지 않는다**(§5.3).
- 켠 상태에서 `hwp_doc_save` 가 **원본 경로를 대상으로** 호출되고 `sourceChanged` 가
  `true` 이면 거부한다 — §5.1 의 손실 시나리오가 정확히 이 지점이다. 다른 경로로
  저장하는 것은 막지 않는다.

### 6.5 MCP 알림을 쓰지 않는 이유

MCP 에는 서버→클라이언트 알림이 있고, `initialize` 응답에서 이 서버는 `resources` 의
`subscribe`·`listChanged` 를 **미지원으로 선언**한다(`src/mcp_serve.rs:189-191`). 감시를
알림으로 밀어 올리는 설계도 가능하지만 이 문서는 채택하지 않는다.

1. **문서는 리소스로 노출되어 있지 않다.** `resources/list` 가 내는 것은 저장소 문서
   3종과 자기서술 매니페스트뿐이다(`src/mcp_serve.rs:294-348`). 열린 HWP 문서는 리소스가
   아니라 도구 핸들이므로 `notifications/resources/updated` 의 대상이 아니다.
2. **서버 루프가 알림을 밀 구조가 아니다.** `run()` 은 stdin 을 블로킹으로 읽는 단일
   스레드이고(`src/mcp_serve.rs:116`), 핸들 테이블은 지역 `&mut` 다(`:114`). 알림을
   보내려면 테이블을 공유 잠금 뒤로 옮기고 stdout 쓰기를 조율해야 한다 — 감시 하나를
   위해 서버 구조 전체를 바꾸는 비용이다.
3. **끌어가는 쪽이 안전하다.** 스테일 표식은 **다음 도구 호출의 봉투**에 실리면 충분하다.
   에이전트는 어차피 도구를 호출해야 무엇이든 하고, 그 호출이 판정을 실어 준다.

폴링 스레드조차 쓰지 않고 **도구 호출 시점에 `metadata` 를 확인하는** 더 작은 설계도
성립한다(§9 대안 A). 어느 쪽이든 알림 표면은 건드리지 않는다.

## 7. 무엇을 하지 않는가

1. **구역 단위 부분 재파싱** — §3.4 에서 기각.
2. **편집 델타 수신 API** — 델타를 보낼 주체가 없다(§3.2).
3. **자동 재로딩** — 누적 편집을 조용히 버린다(§5.3).
4. **MCP 알림 표면 확장** — §6.5.
5. **핸들 번호 재발급** — S8 의 ABA 금지와 정면 충돌한다(§6.1).
6. **감시를 기본 켜기** — 종전 동작이 조용히 달라진다. 기본 무제한·기본 꺼짐은
   [자원 한계 계약 S7](../agent_boundary_contract.md#s7--자원-한계-컨텍스트-범람-방어)이
   세운 태도와 같은 방향이다.

## 8. 이 설계가 놓치는 것 (명시)

- `(mtime, len)` 이 **둘 다 같은데 내용이 다른** 변경은 감지하지 못한다. 내용 해시
  옵트인으로만 덮인다.
- 파일이 **삭제 후 같은 경로에 재생성**된 경우, mtime 이 커졌으므로 변경으로 잡히지만
  "같은 문서의 새 판"인지 "다른 문서"인지는 구별하지 못한다.
- **심볼릭 링크·네트워크 드라이브**에서의 mtime 신뢰도는 **확인되지 않음**.
- 한글(한컴오피스)의 실제 저장 패턴(임시 파일 유무, 잠금 유지 시간)은 **확인되지 않음**
  — 이 PC 에 설치되어 있지 않다(§4.2).
- 디바운스 기본값의 근거가 될 **저장 소요 시간 분포**는 실측하지 못했다 —
  **확인되지 않음**(§4.5).

## 9. 검토한 대안

| 대안 | 내용 | 판단 |
|---|---|---|
| A. 감시 스레드 없이 **호출 시 확인** | 세션 도구 진입에서 `fs::metadata` 를 보고 `sourceChanged` 를 채운다 | **유력**. 스레드·의존성·공유 잠금이 전부 없어진다. 대가는 "호출이 없으면 모른다" 인데, §6.5-3 대로 그것으로 충분하다. 구현 시 이쪽을 먼저 시도할 것 |
| B. `notify` 크레이트 + OS 알림 | 저지연, 폴더 단위 감시 | 의존성 추가 + §4.2 임시 파일 필터 부담. 값 대비 크다 |
| C. 원본을 열 때 통째로 복사해 스냅숏 고정 | 스테일 자체가 사라진다 | 대형 문서 메모리 2배. 그리고 "사용자 편집을 못 본다"는 문제는 그대로 |
| D. 재적재 시 IR 차이를 계산해 편집 재적용 | 누적 편집을 살린다 | 3-way 병합이다. 문서 IR 병합은 별도 축의 큰 문제이고, 잘못 병합하면 조용히 틀린다 |

## 10. 검증 계획

구현이 붙는다면 계약 테스트로 다음을 못 박는다(기존 `tests/mcp_session_*_contract.rs` 와
같은 방식).

1. `source_unchanged_reports_false` — 열고 아무것도 안 했을 때 `sourceChanged: false`.
2. `touched_source_is_detected` — 파일을 덮어쓴 뒤 `sourceChanged: true`, `reason: "mtime"`.
3. `truncated_source_is_not_loaded` — 잘린 파일로 `hwp_doc_reload` 하면 실패하고
   **핸들은 옛 IR 을 유지**한다(§4.1 이 보장하는 성질을 계약으로 고정).
4. `locked_source_reports_locked_not_error` — `os error 32` 는 `reason: "locked"` 로
   보고되고 `unreadable` 과 갈린다(§4.3).
5. `reload_refuses_to_discard_edits_silently` — 편집 누적 상태에서 `discardEdits:false`
   재적재는 `isError: true` + `nextCall`.
6. `reload_keeps_doc_id_and_bumps_revision` — `docId` 불변, `revision` 증가(S8 ABA 금지).
7. `watch_is_off_by_default` — `--watch` 없이 뜬 서버의 봉투는 종전과 동일.

시각 검증은 필요 없다(렌더 산출물이 바뀌지 않는다). 성능 회귀 가드는 `hwp_doc_check_source`
가 **파일을 읽지 않는다**는 것만 확인하면 충분하다 — 대형 문서에서 상수 시간이어야 한다.
