# 다문서 워크스페이스 핸들 (M25)

> 로드맵 [#3608](https://github.com/edwardkim/rhwp/issues/3608) M25 의 둘째 항목 —
> "다문서 워크스페이스 핸들(프로젝트 단위 세션)".
> 이 문서는 **설계**다. 여기 나오는 도구·필드는 아직 구현되어 있지 않다.
> 디렉터리 개요는 [README](README.md).

## 0. 이 문서가 정하는 것

지금 `docId` 하나는 문서 하나다. "프로젝트 단위 세션"이 필요하다면, 먼저 **프로젝트가
무엇인지**를 정해야 한다. 폴더인가, 서식 하나와 데이터 여럿인가, 사람이 고른 파일 묶음인가.

이 문서는 **실제 사용 시나리오에서 출발**해 그 답을 고르고(§3~§4), **메모리 예산**을
실측으로 세우고(§5), 계약을 제안한다(§6). 기존 핸들 계약과 충돌하는 지점은 §7 에서
따로 다룬다.

**결론을 먼저 적는다.** 워크스페이스는 폴더가 아니라 **역할이 붙은 명시적 핸들 집합**이다.
그리고 M25 에서 가장 값이 큰 것은 다문서 조회가 아니라 **서식 하나를 한 번만 파싱해
N 번 재사용하는 것**이다 — 지금 `batch fill` 은 행마다 서식을 다시 파싱한다(§3.1, 실측
10.6 MB 서식에서 **137 ms/행**).

## 1. 지금 있는 것 — 세션 도구 12종

| 도구 | 성격 | 워크스페이스가 더해야 할 것 |
|---|---|---|
| `hwp_open` | 경로 → `docId` | 같은 경로를 두 번 열면 **두 벌**이 생긴다(§5.3). 워크스페이스 소속·중복 제거 |
| `hwp_close` | 핸들 해제 | 묶음 단위 해제 |
| `hwp_doc_info` | 메타 조회 | 묶음 요약(문서 수·총 쪽·총 메모리) |
| `hwp_doc_text` | 페이지 텍스트 | 없음(문서 단위가 맞다) |
| `hwp_doc_search` | 문자열 검색 | **묶음 전체 검색** — 지금은 N 번 호출하고 결과를 에이전트가 합쳐야 한다 |
| `hwp_doc_fields` | 누름틀 조사 | **묶음 전체 필드 목록**과 이름 교집합 |

| `hwp_doc_render_page` | 쪽 SVG | 없음 |
| `hwp_doc_replace_text` | IR 누적 치환 | 묶음 일괄 치환(각 문서의 `changedPages` 를 한 봉투로) |
| `hwp_doc_set_cell` | IR 누적 셀 기록 | 없음 |
| `hwp_doc_fill_fields` | IR 누적 누름틀 채움 | **원본 복구(fork)** — §3.1 이 걸리는 지점 |
| `hwp_doc_save` | 형식 보존 저장 | 묶음 저장 + 산출 이름 규칙 |

목록의 근거는 `src/mcp_serve.rs:617-633`(`is_session_tool`)와
`src/mcp_serve.rs:398-550`(`served_tools`)이며, 실제 `tools/list` 를 stdio 로 받아
확인했다(프로필 미지정) — **총 51종 = 무상태 39종 + 세션 12종**.

## 2. 지금 있는 것 — `docId` 하나 = 문서 하나

| 사실 | 근거 |
|---|---|
| 핸들 테이블은 `HashMap<String, SessionDoc>` + 단조 증가 `next_id` | `src/mcp_serve.rs:51-64` |
| `SessionDoc` 은 `doc`/`source_is_hwpx`/`size_bytes`/`detected_format` — **경로 없음** | `src/mcp_serve.rs:41-49` |
| `hwp_open` 은 중복 검사를 하지 않는다. 같은 파일을 두 번 열면 IR 두 벌 | `src/mcp_serve.rs:676-721` |
| `hwp_close` 는 맵에서 항목만 지운다. 번호는 재사용하지 않는다 | `src/mcp_serve.rs:1423` |
| TTL·개수 상한·메모리 상한 없음 | [S8](../agent_boundary_contract.md#s8--핸들-무결성) |
| 핸들 테이블은 `run()` 지역 변수라 다른 스레드가 볼 수 없다 | `src/mcp_serve.rs:114` |

**문서 사이의 관계를 표현하는 자리가 서버에 없다.** 지금 그 관계는 전부 에이전트의
컨텍스트에 있다 — 어느 `docId` 가 서식이고 어느 것이 데이터인지, 어느 것들이 한 묶음인지.
컨텍스트가 잘리면 그 지도도 함께 사라진다.

## 3. 실사용 시나리오에서 출발

### 3.1 메일머지 — 서식 1 + 데이터 N행

가장 흔하고, 지금 가장 비싼 축이다. 이미 전용 명령이 있다.

```
rhwp batch fill --form <서식> --data <행.jsonl|행.csv> --out-dir <폴더> --json
```

**구현은 행마다 서식을 다시 읽고 다시 파싱한다.** `batch_fill_record_inner` 가
`fill_fields_core(form, …)` 를 호출하고(`src/main.rs:6198`), 그 함수는 진입에서
`fs::read(file_path)` + `HwpDocument::from_bytes` 를 한다(`src/main.rs:13976-13986`).

실측(프로세스 **내부** 계측, `--threads 1 --dry-run`):

| 서식 | 1행 | 5행 | 20행 | 50행 | 한계비용 |
|---|---:|---:|---:|---:|---:|
| `issue2083_hide_fill_page.hwpx` (203 KB, 누름틀 24종) | 6 ms | 27 ms | 108 ms | 250 ms | **≈5.0 ms/행** |

| 서식 | 1행 | 3행 | 6행 | 한계비용 |
|---|---:|---:|---:|---:|
| `2025 행정업무운영 편람(최종).hwp` (10.6 MB, 누름틀 150개·49종) | 133 ms | 410 ms | 819 ms | **≈137 ms/행** |

한계비용이 `hwp_open` 비용(각각 4.8 ms, 126 ms)과 **거의 같다** — 행마다 전체 재파싱을
한다는 것이 그대로 보인다. 100행이면 대형 서식에서 13.7초가 파싱에만 간다.

**세션으로 옮기면 왜 안 되는가.** 지금 세션 편집은 핸들의 IR 에 **누적**한다
(`src/mcp_serve.rs:510` 도구 설명의 "여러 번 호출하면 누적된다", 구현은 `:1234-1351`).
1행을 채우고 저장한 뒤
2행을 채우면 1행 값이 남은 채로 덮인다. 즉 세션으로 메일머지를 하려면 **원본 상태로
되돌리는 수단**이 필요하다.

> **그 수단은 코어에 이미 있다.** `save_snapshot_native` / `restore_snapshot_native`
> (`src/document_core/commands/document.rs:1637-1691`)가 undo/redo 용으로 존재하며,
> `Document::clone()` 으로 스냅숏을 뜨고 복원 시 스타일 재해소·compose·전 구역
> 재조판까지 한다. 상한은 100개(`:1646`). **WASM 에만 노출**되어 있고
> (`src/wasm_api.rs:5901-5914`) CLI·MCP 표면에는 없다.

복원 비용은 코드상 "clone + compose + 전 구역 조판"이므로
[증분 재파싱 §2.6](incremental_reparse.md#26-파싱-비용과-조판-비용의-분해)
의 조판 몫(편람 기준 ≈64 ms)에 가깝고 파싱 몫(≈59 ms)과 I/O(3 ms)를 아낀다 —
**정확한 수치는 표면이 없어 실측하지 못했다(확인되지 않음).** 소형 서식(203 KB)에서는
전체 재파싱이 5 ms 라 이득이 작고, 대형 서식에서 커진다.

### 3.2 보고서 묶음 — 여러 문서를 함께 본다

"3분기 보고서 12건에서 '안전관리' 가 나오는 곳을 전부 찾아라", "이 12건의 표 첫 행을
비교하라" 같은 작업이다.

현재 최선은 둘 중 하나다.

| 경로 | 비용 | 한계 |
|---|---|---|
| `batch search --query …` (무상태) | 문서당 재파싱 1회. 353건 코퍼스 전수 `batch fields --json` 실측: **1스레드 17.1 s / 8스레드 6.3 s**(문서당 48.5 ms) | 한 번 훑고 IR 을 버린다. 두 번째 질문에 같은 값을 다시 문다 |
| `hwp_open` ×N 후 `hwp_doc_search` ×N | 두 번째 질문부터 sub-ms | 묶음 개념이 없어 **에이전트가 `docId` 지도를 들고 있어야** 한다. 결과 합치기도 에이전트 몫 |

실측(세션, 4개 문서를 순서대로 열기):

| 문서 | 크기 | `hwp_open` | RSS 증가 |
|---|---:|---:|---:|
| 편람 `.hwp` | 10.6 MB | 131.6 ms | +39.3 MB |
| 편람 `.hwpx` | 13.6 MB | 194.7 ms | +38.2 MB |
| `exam_kor.hwp` | 10.4 MB | 29.7 ms | +14.1 MB |
| 정책연구 중간진도보고서 | 7.1 MB | 173.9 ms | +21.8 MB |
| **합계** | 41.7 MB | **530 ms** | **+113.4 MB** |

즉 대형 문서 4건을 함께 들고 있는 것은 **0.5초·113 MB** 다. 이 정도면 충분히 현실적이다 —
문제는 비용이 아니라 **묶음을 표현할 자리가 없다**는 것.

### 3.3 서식 일괄 점검 — 폴더 전체를 훑는다

"이 폴더의 서식들이 채워야 할 누름틀 이름이 서로 같은가", "빈 칸이 남은 문서는 어느
것인가" 같은 감사 작업이다.

여기서는 **워크스페이스가 답이 아니다.** 저장소 `samples/` 를 재료로 규모를 재면:

```
353건, 합계 296.3 MB, 평균 860 KB, 중앙값 54 KB, 최대 13.0 MB
```

IR 배율(§5)을 보수적으로 3배만 잡아도 전건 상주는 **≈900 MB** 다. 일회성 훑기에 그
메모리를 태울 이유가 없고, 이미 `batch` 축이 스트리밍 NDJSON 으로 이 일을 한다
(문서당 48.5 ms, 8스레드로 353건 6.3초).

> **경계 결정 — 전건 스캔은 `batch`, 반복 접근은 워크스페이스.** 한 번 보고 버릴
> 것이면 상주시키지 않는다. 워크스페이스는 "같은 문서에 여러 질문을 던지는" 축이다.

## 4. 워크스페이스란 무엇인가 — 후보와 결정

### 4.1 후보 3안

| 안 | 정의 | 장점 | 문제 |
|---|---|---|---|
| **A. 폴더** | `hwp_workspace_open{ dir }` — 폴더 안의 문서를 전부 연다 | 사람이 말하기 쉽다 | 폴더 크기를 서버가 통제하지 못한다(§3.3 의 296 MB). 하위 폴더·확장자 필터 등 정책이 계속 늘어난다. 무엇보다 **경로 확장을 서버가 결정**하게 되어 자원 상한 계약이 흔들린다 |
| **B. 명시적 집합** | `hwp_workspace_create{}` → `hwp_workspace_add{ wsId, docId }` | 서버는 받은 것만 안다. 상한이 자연스럽다 | 문서 사이의 **역할**을 표현하지 못한다 — 어느 것이 서식이고 어느 것이 산출인가 |
| **C. 역할 있는 집합** | B + 각 항목에 역할(`template`/`source`/`output`) | 메일머지·비교·감사가 전부 표현된다 | 역할 어휘를 정해야 한다. 잘못 고르면 나중에 못 바꾼다 |

### 4.2 결정 — C(역할 있는 명시적 집합)

근거는 셋이다.

1. **A 는 경로 정책을 서버로 끌어온다.** 어떤 문서를 열지는 호출자가 정하는 것이
   [경로 계약 S5](../agent_boundary_contract.md#s5--경로는-문서-내용에서-파생되지-않는다)의
   태도와 같다 — 서버는 받은 경로만 다룬다. 폴더 확장이 필요하면 그것은 클라이언트가
   `hwp_open` 을 N 번 부르는 것으로 충분하다.
2. **역할이 없으면 §3.1 이 안 풀린다.** 메일머지는 "서식 하나가 특별하다"는 사실
   자체가 정보다. 역할이 없으면 어느 핸들에서 fork 해야 하는지 서버가 모른다.
3. **역할은 최소로 시작할 수 있다.** `template` 하나만 있어도 §3.1 이 풀리고,
   나머지는 붙이지 않아도 된다. 어휘를 늘리는 것은 나중에 되지만 줄이는 것은 안 되므로,
   **처음에는 `template` 과 `member` 둘만** 둔다.

## 5. 메모리 예산

### 5.1 측정 방법

`rhwp mcp-serve` 를 stdio 로 띄우고 `hwp_open` 사이사이에 `Get-Process -Id <pid>` 의
`WorkingSet64` 를 읽었다. 프로세스 전체 RSS 라 할당자 단편화·페이지 캐시 효과를 포함하며,
**IR 자체의 정확한 크기가 아니라 상한에 가까운 관측값**이다.

### 5.2 문서당 RSS (실측)

| 문서 | 파일 크기 | 문서당 RSS | 배율 |
|---|---:|---:|---:|
| `form-01.hwp` (20개 평균) | 18 KB | 0.13 MB | 7.4× |
| `issue2083_hide_fill_page.hwpx` (20개 평균) | 203 KB | 0.94 MB | 4.7× |
| `20250130-hongbo.hwp` (20개 평균) | 628 KB | 1.01 MB | 1.7× |
| 정책연구 중간진도보고서 `.hwp` | 7.1 MB | 21.8 MB | 3.1× |
| `exam_kor.hwp` | 10.4 MB | 14.1 MB | 1.4× |
| 편람 `.hwp` | 10.6 MB | 39.3 MB | 3.7× |
| 편람 `.hwpx` | 13.6 MB | 38.2 MB | 2.8× |

- 기준 RSS(문서 0개): **6.3 ~ 7.8 MB**
- 소형 서식 60개 동시 보유: **49.5 MB**
- 대형 문서 4개 + 편람 사본 4개(8핸들): **269.1 MB**

**배율은 1.4× ~ 7.4× 로 넓다.** 작은 파일일수록 고정 오버헤드(스타일 테이블·조판 구조)가
상대적으로 커서 배율이 높고, 이미지가 큰 비중인 문서(`exam_kor`)는 낮다. **예산은
"파일 크기 × 4" 를 기본 추정으로 쓰고, 실제 값은 봉투로 보고**하는 편이 정직하다(§6.3).

### 5.3 중복 제거가 없다 (실측)

같은 경로를 4번 열면:

```
dup open #1: 128.7 ms  RSS 156.7 MB
dup open #2: 122.8 ms  RSS 194.4 MB
dup open #3: 161.5 ms  RSS 232.1 MB
dup open #4: 149.0 ms  RSS 269.1 MB
→ 4핸들 close 후 RSS 123.8 MB
```

매번 **전체 파싱 비용과 전체 메모리**를 다시 문다(+37 MB/회). 닫으면 정상적으로
반환된다(269.1 → 123.8 MB) — 누수는 없다.

경로 기반 중복 제거는 워크스페이스가 자연스럽게 얻는 이득이다. 다만 **공유는 편집과
충돌**한다 — 같은 IR 을 두 핸들이 가리키는데 한쪽이 편집하면 다른 쪽이 조용히 바뀐다.
그래서 **읽기 전용으로 열린 핸들끼리만 공유**하고, 첫 편집에서 분리하는(copy-on-write)
설계가 아니면 중복 제거를 하지 않는 편이 낫다. 이 문서는 **중복 제거를 M25 범위에서
제외**하고, 대신 `hwp_workspace_add` 가 같은 경로를 두 번 받으면 **경고를 봉투에 싣는**
것으로 그친다.

### 5.4 상한 정책

[S8](../agent_boundary_contract.md#s8--핸들-무결성) 이 "개수 상한·메모리 상한은 없다" 를
현재 상태로 못박아 두었다. 워크스페이스는 **상한을 만들 좋은 자리**지만, 기본값을 유한하게
잡으면 종전 호출이 조용히 실패한다 —
[S7](../agent_boundary_contract.md#s7--자원-한계-컨텍스트-범람-방어) 이 "기본은 무제한,
상한은 옵트인, 절단은 봉투에 드러난다" 로 정한 태도와 같다.

- 기본: 상한 없음(종전과 동일).
- 옵트인: `rhwp mcp-serve --max-open-bytes <N>` / `--max-open-docs <N>`.
- 초과 시: **조용히 축출하지 않는다.** `hwp_open`/`hwp_workspace_add` 가 `isError: true`
  로 거절하고, 어느 한계에 걸렸는지와 현재 사용량을 싣는다. LRU 축출은 "핸들이 살아 있다"
  는 계약을 깨므로 채택하지 않는다.

## 6. 계약 제안

설계이며 구현이 아니다.

### 6.1 서버 상태

```
Workspaces {
    map: HashMap<String, Workspace>,   // "ws-1", "ws-2", …
    next_id: u64,                      // 단조 증가, 재사용 없음
}
Workspace {
    members: Vec<(String /*docId*/, Role)>,   // 삽입 순서 보존
    label: Option<String>,                    // 호출자가 준 이름(선택)
}
enum Role { Template, Member }
```

`docId` 는 지금과 같이 전역이다. 워크스페이스는 **`docId` 를 담을 뿐 새 주소 공간을
만들지 않는다** — 세션 도구 12종이 그대로 동작해야 하기 때문이다.

### 6.2 도구

| 도구 | 인자 | 하는 일 |
|---|---|---|
| `hwp_workspace_create` | `{ label? }` | `wsId` 발급 |
| `hwp_workspace_add` | `{ wsId, docId, role? }` | 소속 등록. `role` 기본 `member` |
| `hwp_workspace_remove` | `{ wsId, docId }` | 소속 해제(핸들은 살아 있다) |
| `hwp_workspace_info` | `{ wsId }` | 구성원 목록 + 문서별 쪽수·추정 메모리 합계 |
| `hwp_workspace_close` | `{ wsId, closeDocs? }` | 묶음 해제. `closeDocs:true` 면 구성원 핸들도 닫는다 |
| `hwp_workspace_search` | `{ wsId, query, caseSensitive?, maxMatches? }` | 구성원 전체 검색. 봉투는 `hwp_doc_search` 와 **동형**이고 매치마다 `docId` 가 붙는다 |
| `hwp_workspace_fields` | `{ wsId }` | 구성원 전체 누름틀 + 이름 교집합/차집합 |
| `hwp_doc_fork` | `{ docId }` | 핸들 복제 → 새 `docId`. **§3.1 메일머지의 핵심** |

`hwp_doc_fork` 만은 워크스페이스와 독립적으로도 값이 있다(스냅숏 코어를 MCP 로 여는 것).
구현이 붙는다면 이것을 **먼저** 하는 것이 옳다 — 작고, 코어가 이미 있고
(`document.rs:1637-1691`), 가장 큰 실측 이득(137 ms/행 → 파싱 몫 제거)을 낸다.

### 6.3 봉투

기존 세션 봉투 어휘를 그대로 쓴다(`schemaVersion`·`docId`·판정은 데이터).

```json
{ "schemaVersion": "1.0", "wsId": "ws-1", "label": "3분기 보고서",
  "docCount": 12, "totalPages": 418,
  "estimatedBytes": 128974848,
  "members": [ { "docId": "doc-3", "role": "template", "pageCount": 54 }, … ],
  "warnings": [ { "kind": "duplicatePath", "docIds": ["doc-3","doc-7"] } ] }
```

`estimatedBytes` 는 **추정**이라고 이름에 박는다 — §5.2 의 배율이 1.4×~7.4× 로 넓어서
정확한 값을 약속할 수 없다. 근거는 `size_bytes`(핸들이 이미 들고 있다,
`src/mcp_serve.rs:46-47`) × 계수이며, 계수의 출처를 이 문서로 링크한다.

### 6.4 검색 봉투의 동형성

`hwp_workspace_search` 는 반드시 `crate::search_json_value` 를 재사용해야 한다
(`src/mcp_serve.rs:1000` 이 세션 검색에서 하는 것과 같이). 주소 어휘
(`matches[].section/paragraph/page/context`)가 갈라지면 소비자가 같은 코드로 못 읽는다.
묶음 판은 각 매치에 `docId` 한 필드만 더한다.

## 7. 기존 계약과의 충돌 검토

| 계약 | 워크스페이스의 영향 | 처리 |
|---|---|---|
| [S8](../agent_boundary_contract.md#s8--핸들-무결성) — 없는 핸들은 조용히 성공하지 않는다 | `wsId` 가 새 핸들 종류로 늘어난다 | 같은 규약 적용: 없는 `wsId` 는 `isError:true` + `nextCall`(→`hwp_workspace_create`) |
| S8 — 닫은 번호 재사용 금지(ABA) | `wsId` 도 단조 증가 | `next_id` 를 `docId` 와 같은 방식으로 |
| S8 — TTL 없음 | 묶음이 오래 살면 메모리가 오래 잡힌다 | §5.4 옵트인 상한. TTL 은 여전히 도입하지 않는다 |
| [S7](../agent_boundary_contract.md#s7--자원-한계-컨텍스트-범람-방어) — 기본 무제한, 절단은 봉투에 | 묶음 검색은 결과가 N배로 커진다 | `maxMatches` 를 묶음 전체 기준으로 적용하고 `truncated`·`omittedCount`·`totalMatchCount` 를 **묶음 총량**으로 낸다 |
| [S5](../agent_boundary_contract.md#s5--경로는-문서-내용에서-파생되지-않는다) — 경로는 문서 내용에서 나오지 않는다 | 폴더 안(A)이었다면 위험했을 지점 | §4.2 에서 A 를 기각했으므로 서버가 경로를 만들지 않는다 |
| 직무 프로필(`--profile`) | 새 도구가 프로필 필터를 통과해야 한다 | `agent_profiles` 의 `session_tools` 목록에 이름 단위로 등록. 목록과 호출이 **같은 판정 함수**를 쓰는 규약 유지(`src/mcp_serve.rs:569-576`) |

## 8. `batch` 축과의 경계

두 축을 섞으면 둘 다 나빠진다. 경계를 문장으로 못박는다.

| | `batch` | 워크스페이스 |
|---|---|---|
| 문서 수명 | 한 건 처리 후 버림 | 명시적으로 닫을 때까지 유지 |
| 적합한 질문 | "전건에 한 번씩" | "같은 문서들에 여러 번" |
| 메모리 | 동시 처리 스레드 수만큼만 | 구성원 전체 |
| 출력 | NDJSON 스트림 | 한 봉투 |
| 병렬 | `--threads` | 없음(단일 스레드 서버) |

`batch fill` 만은 예외적으로 애매하다 — 겉보기는 batch 지만 **서식 하나가 N 번 반복
사용**되므로 워크스페이스의 fork 가 정확히 맞는 축이다(§3.1). 이 문서는 `batch fill` 을
없애자고 제안하지 않는다. `hwp_doc_fork` 가 생기면 `batch fill` 내부가 그것을
쓰도록 바꾸는 것이 더 작은 변경이고, CLI 계약은 그대로 유지된다.

## 9. 무엇을 하지 않는가

1. **폴더 워크스페이스** — §4.2 에서 기각.
2. **IR 공유(중복 제거)** — 편집과 충돌한다(§5.3). copy-on-write 없이는 하지 않는다.
3. **LRU 자동 축출** — 핸들이 살아 있다는 계약을 깬다(§5.4).
4. **워크스페이스 단위 저장 트랜잭션**("전부 저장하거나 전부 안 하거나") — 부분 실패
   시 되돌리려면 이미 쓴 파일을 지워야 하고, 그것은 파괴적 연산이다. 묶음 저장은
   **행마다 레코드**를 내는 `batch` 규약을 따른다.
5. **새 주소 공간** — `wsId:docId` 같은 복합 주소를 만들지 않는다. 세션 도구 12종이
   그대로 도는 것이 하위호환의 전부다.
6. **다중 클라이언트 격리** — stdio 전제 밖이다(S8).

---

## 10. 확인되지 않음

- `restore_snapshot_native` 의 실제 복원 비용 — MCP·CLI 표면이 없어 실측 불가(§3.1).
  코드상 "clone + 스타일 재해소 + compose + 전 구역 조판"이므로 조판 몫에 가깝다는
  **추정**만 적었다.
- `Document::clone()` 의 메모리 배수 — 스냅숏 하나가 원본 IR 만큼 늘 것으로 보이나
  실측하지 못했다. 대형 문서 fork 의 메모리 영향은 미지수다.
- RSS 배율 1.4×~7.4× 의 **분포** — 7개 표본으로 잡은 범위이고, 문서 종류별 예측식은
  세우지 못했다.
- 묶음 검색을 단일 스레드로 도는 것이 실용적인 규모의 상한 — 구성원 12건·418쪽 정도는
  개별 검색 비용(0.6~4.1 ms)의 합으로 추정되나 실측하지 않았다.

## 11. 검증 계획

계약 테스트로 다음을 못 박는다(`tests/mcp_session_*_contract.rs` 와 같은 방식).

1. `unknown_workspace_never_succeeds_quietly` — 없는 `wsId`·빈 문자열·형태 오류가 전부
   `isError:true` + `nextCall`.
2. `workspace_ids_are_not_recycled` — 닫고 다시 만들면 다른 번호(S8 ABA).
3. `workspace_search_envelope_is_isomorphic` — `hwp_workspace_search` 의 매치 객체가
   `hwp_doc_search` 와 **키 집합이 같고** `docId` 만 추가된다.
4. `workspace_limits_are_opt_in` — 옵션 없이 뜬 서버는 종전대로 무제한.
5. `fork_gives_independent_ir` — fork 한 핸들을 편집해도 원본 핸들의 조회 결과가 변하지
   않는다(양방향).
6. `fork_preserves_source_format` — fork 한 핸들의 `hwp_doc_save` 가 원본과 같은 형식
   보존 규칙을 따른다(`src/mcp_serve.rs:1376-1383`).
7. `duplicate_path_is_warned_not_rejected` — 같은 경로 두 핸들을 한 묶음에 넣으면
   경고만 싣고 성공한다.

성능 회귀 가드로는 **`batch fill` 이 fork 로 바뀐 뒤 행당 비용이 파싱 비용 아래로
떨어지는 것**을 재현 스크립트로 남긴다 — 이 문서 §3.1 의 표가 그 기준선이다.
