# 문서 에이전트 런타임 (Document Agent Runtime, DAR) — 아키텍처 척추

rhwp 를 "에이전트 도구가 딸린 문서 엔진"에서 **검증 가능하고 안전하며 채점 가능한
범용 문서 에이전트 런타임**으로 진화시키는 단일 아키텍처다. 열두 개의 층을 따로
쌓지 않는다 — 하나의 구조이고, 이 문서가 그 척추다.

## 설계 원칙: 결정적 코어, 지능은 가장자리에

신뢰 코어에 들어가는 것: 파싱 · IR · 선택 · 변경 · 검증 · 렌더 · diff · 트랜잭션 ·
롤백 · 출처 · 서명 · 정책 집행 · 능력 검증 · 벤치마크 채점.

에이전트(LLM)가 하는 것: 계획 · 자연어 해석 · 도구 선택 · 변경 제안 · 실패 진단 ·
전략 수립 · 재시도.

**에이전트는 결정적 검증과 정책 집행을 우회할 수 없다.** LLM 이 없어도 시스템은
쓸 수 있어야 하고, 결정적 연산은 결정적으로 남아야 한다.

## 이 아키텍처가 새로 만드는 것은 생각보다 적다

솔직한 실측이 설계의 출발점이다. `rhwp capabilities` 가 광고하는 89개 명령을 훑으면
**런타임의 절반 이상이 이미 구현되어 있다.** 없는 것은 대개 기능이 아니라 **이름**이다
— 조각들이 스스로를 하나의 시스템이라고 부르지 않는다.

| # | 층 | 상태 | 근거 (실측) |
|---|---|---|---|
| 1 | 문서 에이전트 프로토콜 (DAP) | **빠짐** | 봉투마다 `schemaVersion` 은 있으나 요청·트랜잭션 신원과 안정 오류 코드를 묶는 프로토콜 이름이 없다 → [DAP/1.0](document_agent_protocol.md) |
| 2 | 문서 트랜잭션 프로토콜 (DATP) | **실질 있음·이름 없음** | `run`(선언적 계획·정적 선검증·원자 실행·저널) + `replay`(입력·계획·산출 3해시 영수증, `--expect-output-sha256` 제3자 재현, 불일치 exit 3) → [DATP/1.0](document_transaction_protocol.md) 이 이를 형식화 |
| 3 | 샌드박스·정책 엔진 | **부분** | 능력 축소(MCP 프로필) + DATP 참조 드라이버의 COMMIT 전 집행(`tools/dar/transaction.py commit --policy`: `admissionPolicy` 서술 → 위반은 4000 으로 커밋 차단, 통과분은 `policySha256` 을 영수증에 기록). `rhwp run`(러스트 본체) 에는 아직 미결속 |
| 4 | 능력 등록부 | **있음** | `capabilities`·`export-agent-manifest`·[capability 카탈로그](../../manual/agent_capability_registry.md) |
| 5 | 문서 에이전트 벤치마크 | **부분** | `gym/` 과제 팩·`tools/agent_bench` 존재. 표준 점수 계약 미정 |
| 6 | 문서 컴파일러 / IR | **있음** | 전 포맷 파서가 공통 `Document` IR 반환([parser_architecture](../parser_architecture.md)), `export-ir-schema` 로 자기서술 |
| 7 | 자가치유 에이전트 | **부분** | 트리아지·요청 큐·회귀 폐회로가 제안됨(#4894·#4901·#4906). 런타임 편입은 미정 |
| 8 | 에이전트 메모리 | **빠짐** | 세션 도구(`mcp-serve`)는 재파싱을 피하지만 작업 간 기억이 아니다 |
| 9 | 출처·영수증·계보·감사 | **있음(강함)** | `replay --capsule`·`lineage`·`anchor`·`audit`·`settle`·`conformance`, [AWS/1.0](agent_work_standard.md) 5단 표준 |
| 10 | MCP 통합 | **있음** | `mcp-serve` 세션·무상태 도구, `capabilities --mcp` 가 도구 정의의 단일 출처 |
| 11 | 하니스 통합 | **부분** | `.claude/` 에이전트·Skill, `.agents/` — 런타임 계약과의 접합은 미정 |
| 12 | 보안·주입·비신뢰 문서 격리 | **있음** | `inspect`(은닉·주입·유니코드)·`threat-scan`·출처 표지(`untrustedContent`/`untrustedFields`)·`export-provenance-map` |

**따라서 이 아키텍처의 1차 작업은 발명이 아니라 결속이다.** 있는 것을 프로토콜로
묶어 이름을 주고(1·2), 없는 것(3·8)을 그 위에 얹고, 부분인 것(5·7·11)을 계약에
맞춘다. 없는 것을 있다고 적지 않고, 있는 것을 새로 만들지 않는다.

## 층 사이의 관계

```
        [에이전트 — 계획·해석·진단·재시도]        지능은 가장자리
                     │  DAP/1.0 봉투만으로 대화
─────────────────────┼──────────────────────────  신뢰 경계
   DAP/1.0 (1)  요청·신원·신뢰수준·정책·결과·오류
        │
   DATP/1.0 (2) BEGIN…COMMIT/ROLLBACK 상태기계
        │            └ 정책 (3) 이 COMMIT 전 게이트
        ├─ IR (6) · 능력 (4) · 보안 (12)          결정적 코어
        └─ 영수증·계보·감사 (9) ← 모든 트랜잭션이 남긴다
                     │
        벤치마크 (5) 가 이 전부를 점수화 · 메모리 (8) 가 작업을 잇는다
```

## 진행 순서와 판정

각 층은 **문서 두 정본(사람·기계) + 준수 검사기**를 갖는다. 검사기 없는 층은
"설계했다"고 말하지 않는다 — [AWS/1.0](agent_work_standard.md) 과 같은 규율이다(SWS/1.0 은 PR #4904 로 제안 중).

1. **DAP/1.0 · DATP/1.0** — 프로토콜 정의 + `tools/dar/conformance.py` 실측 판정
2. **정책 엔진(3)** — 정책 서술·해시·COMMIT 전 집행
3. **메모리(8)** — 트랜잭션 간 지속 상태, 영수증 계보에 접합
4. **벤치마크(5)·하니스(11)** — 점수 계약과 접합 계약

현 단계는 1이다. `tools/dar/conformance.py` 는 rhwp 가 두 프로토콜을 **실제로**
어디까지 만족하는지 실행해서 판정하고, 미달 항목이 곧 다음 구현 목록이 된다 —
아키텍처 문서가 희망이 아니라 반증 가능한 진술이 되게 하는 장치다.
