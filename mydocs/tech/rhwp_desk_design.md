# rhwp-desk — HWP 문서를 위한 Windows 상주 에이전트 워크벤치 설계

## 0. 한 줄 정의

**rhwp-desk는 "문서를 여는 앱"이 아니라 "문서 일을 시키는 앱"이다.** 사용자는
자연어로 지시하고, 로컬 LLM 어댑터가 계획을 세우고, rhwp 엔진의 결정론적
도구들이 실행·검증하며, 모든 산출에 영수증이 남는다. 문서 바이트는 사용자가
허락하지 않는 한 기계 밖으로 나가지 않는다.

## 1. 왜 데스크톱인가 — 웹(studio)·CLI가 못 채우는 세 가지

rhwp에는 이미 세 개의 소비 표면이 있다: CLI(자동화), `mcp-serve`(에이전트
호스트 연동), rhwp-studio(브라우저 편집기). 그런데 실제 HWP 사용자의 주류
환경 — 행정기관·학교·기업의 Windows PC — 에서는 셋 다 진입 장벽이 있다.

1. **문서 반출 금지.** 공공·기업 문서는 외부 서버 업로드가 금지인 경우가
   많다. 클라우드 LLM 채팅창에 문서를 붙여 넣는 순간 규정 위반이다.
   데스크톱 앱은 파싱·렌더·검증을 전부 로컬에서 수행하고, LLM에는
   **표지된 발췌만** 보내거나(§6), 로컬 모델로 완전 오프라인 동작한다.
2. **파일이 삶의 단위다.** HWP 사용자는 탐색기에서 더블클릭으로 산다.
   `.hwp`/`.hwpx` 파일 연결, 우클릭 "rhwp-desk로 검증", 드래그앤드롭이
   있어야 도구가 일상에 들어간다. CLI와 웹은 이 자리에 못 들어간다.
3. **긴 작업의 거처.** "이 폴더 400개 문서 전부 검증해줘" 같은 작업은
   브라우저 탭이 아니라 트레이에 상주하며 진행률을 보여주는 프로세스가
   맞다. batch·gym·repair_loop 같은 기존 장기 실행 자산의 자연스러운 UI다.

## 2. 무엇을 새로 만들고, 무엇을 재사용하는가 (자산 매핑표)

설계 원칙은 이 저장소의 관례 그대로다 — **재구현 금지, 승격과 배선만.**
새로 짓는 것은 셸·어댑터·대화 UI 세 조각뿐이다.

| 계층 | 필요한 것 | 이미 있는 자산 | 신축 여부 |
|---|---|---|---|
| 문서 엔진 | 파싱·렌더·편집·변환 | rhwp 코어(HWP/HWPX/HWP3/HML → 공통 IR) | 없음 |
| 뷰어/편집 UI | 페이지 렌더·편집 화면 | **rhwp-studio**(TS+Vite, WASM) — 셸의 WebView에 그대로 탑재 | 없음 |
| 도구 표면 | 에이전트가 부를 88개 명령 | `mcp-serve`(무상태 66 + 세션 16+) — 셸이 사이드카로 띄우고 stdio로 연결 | 없음 |
| 계획 실행 | Plan→Act→Verify 원자 실행 | `run` 계획서 엔진(선검증·CAS·저널 지문 체인 R22/R23) | 없음 |
| 재시도 | 실패 진단→수리→재검증 | `tools/repair_loop`(진전 판정·loop detection) | 없음 |
| 외부 위임 | 전문 에이전트에 task 위임 | `tools/handoff`(#4949: sandbox·3겹 검증·retry→fallback) | 없음 |
| 검증 | 편집 후 무결 확인 | `verify --expect-*`·`edit --verify`·`render-diff`·`layout-anomaly` | 없음 |
| 안전 | 정책·주입 방어·출처 표지 | `policy_gate`·`inspect injection/hidden-text/unicode`·provenance | 없음 |
| 회계 | 작업 증명 | `replay --capsule`·`lineage`·`audit` | 없음 |
| 문서 생성 | 명세→문서 | `scaffold`(표 병합·서식 스택 #3~#9) | 없음 |
| **셸** | 창·트레이·파일연결·업데이트 | — | **신축 ①** |
| **LLM 어댑터** | 계획 수립 두뇌 연결 | — | **신축 ②** |
| **대화 UI** | 채팅 패널 + 승인 카드 + 영수증 뷰 | — | **신축 ③** |

## 3. 셸 선택 — Tauri (근거와 반례)

**Tauri 2.x를 채택한다.** 근거:

- 백엔드가 Rust다. rhwp 코어를 **같은 프로세스에 링크**할 수 있어(FFI 없이
  crate 의존) 뷰어 렌더 경로에서 IPC 왕복이 사라진다. CLI를 서브프로세스로
  부르는 것은 도구 호출 경로에만 남긴다(§4).
- WebView2는 Windows 10/11에 기본 탑재라 런타임 동봉이 필요 없다.
  설치 용량이 수 MB대(대안인 크로미엄 동봉형은 100MB+).
- rhwp-studio가 이미 웹 기술이므로 프런트엔드를 그대로 가져온다.

반례 검토: (a) 크로미엄 동봉형 — studio 재사용은 동일하게 가능하나 용량·
메모리에서 열세고 Rust 코어 직링크가 안 된다. (b) 네이티브(WinUI/egui) —
studio를 버리고 UI를 다시 짓는 것이라 "재구현 금지" 원칙 위반. (c) PWA —
파일 연결·트레이·오프라인 LLM이 안 된다.

## 4. 아키텍처 — 5층과 두 개의 실행 경로

```
┌─────────────────────────────────────────────────────┐
│  UI (WebView2)                                       │
│  ├─ 문서 뷰(rhwp-studio 재사용)                       │
│  ├─ 대화 패널(신축 ③)                                │
│  └─ 승인 카드·영수증 뷰·작업 큐(신축 ③)               │
├─────────────────────────────────────────────────────┤
│  Agent Runtime (Rust, Tauri 백엔드 안)                │
│  ├─ LLM 어댑터(신축 ②): 계획 수립·다음 행동 선택      │
│  ├─ 계획 실행기: run 계획서 엔진 호출                  │
│  ├─ 재시도: repair_loop 호출                          │
│  └─ 위임: handoff 오케스트레이터 호출                  │
├─────────────────────────────────────────────────────┤
│  Tool Layer                                          │
│  ├─ 빠른 경로: rhwp 코어 crate 직호출(렌더·조회)       │
│  └─ 계약 경로: rhwp.exe 서브프로세스(편집·검증·저널)   │
├─────────────────────────────────────────────────────┤
│  Safety: policy_gate·provenance·inspect 3축·sandbox  │
├─────────────────────────────────────────────────────┤
│  Observability: NDJSON 저널·capsule·lineage          │
└─────────────────────────────────────────────────────┘
```

**두 실행 경로의 구분이 이 설계의 심장이다.**

- **빠른 경로(직링크)**: 페이지 렌더, 구조 트리, 검색 등 **읽기 전용** 조회.
  studio가 이미 WASM으로 하는 일을 데스크톱에선 네이티브 속도로 한다.
- **계약 경로(서브프로세스)**: 문서를 **바꾸는** 모든 일은 반드시 `rhwp.exe`
  CLI를 거친다. 이유는 성능이 아니라 **계약**이다 — CLI 봉투(exit 0/1/2/3,
  provenance 표지, 저널 지문 체인)가 곧 검증 가능성의 원천이고, 데스크톱
  앱이 그걸 우회하는 순간 "에이전트가 한 일을 증명한다"는 축이 무너진다.
  또한 앱과 CLI가 같은 저널 형식을 쓰므로 앱에서 한 작업을 CI·다른
  에이전트가 `replay`로 재현 검증할 수 있다.

## 5. LLM 어댑터 — BYO-두뇌, 두뇌 없이도 동작

어댑터는 trait 하나다:

```rust
trait Planner {
    /// 대화 맥락 + 도구 목록(capabilities --mcp 그대로) → 다음 행동
    fn next_action(&self, ctx: &Context) -> PlannerAction;
}
enum PlannerAction { CallTool(ToolCall), Ask(String), Done(Summary) }
```

- **구현 1: OpenAI 호환 HTTP** — 사용자가 키를 넣는 클라우드 모델(또는
  같은 API 형태를 쓰는 사내 게이트웨이). tool-use 스키마는
  `capabilities --mcp`가 **이미 만들어 주는 것을 그대로** 넘긴다 — 도구
  정의의 단일 출처 계약을 데스크톱에서도 유지.
- **구현 2: 로컬 HTTP** — 사용자가 로컬에 띄운 OpenAI 호환 서버(형태만
  맞으면 무엇이든). 완전 오프라인 모드의 기반.
- **구현 3: NoPlanner** — LLM 없음. 이때 rhwp-desk는 "결정론 모드"로
  동작한다: 뷰어 + 명령 팔레트(모든 CLI 명령의 GUI 폼) + batch 러너.
  **LLM이 없어도 유용한 도구여야 한다**는 것이 이 저장소의 확립된 방향
  ("llm은 판단이고 얘 없이도 가능해야" — 도구만으로 완결)과 일치한다.

계획 수립만 LLM이 하고, 실행·검증·재시도·회계는 전부 기존 결정론 자산이
한다. LLM이 틀려도 문서가 깨질 수 없는 구조가 목표다(§6).

## 6. 보안 모델 — 세 개의 경계

1. **문서 경계**: 문서 바이트는 기본적으로 LLM에 보내지 않는다. LLM에는
   (a) 구조 요약(`export-structure`), (b) 사용자가 명시 선택한 발췌,
   (c) 도구 봉투의 메타데이터만 간다. 문서 파생 텍스트가 갈 때는
   provenance 표지(`untrustedContent`)를 프롬프트 경계 표지(nonce)와 함께
   싣는다 — `envelope_provenance.md`의 주입 방어 수칙 그대로.
2. **행동 경계**: 문서를 바꾸는 도구 호출은 **승인 카드**를 거친다.
   카드에는 dry-run 미리보기(`run --dry-run`의 preview[])와 변경 좌표
   (docdiff `NodePath`)가 뜬다. "이 세션에서 같은 종류 자동 승인" 옵션은
   policy_gate 문법으로 저장된다(eq/in/gte/lte, default-deny).
3. **위임 경계**: 외부 에이전트 위임은 handoff(#4949)의 sandbox 그대로 —
   inputs/ 사본만 노출, out/만 수거, 경계 위반 시 exit 4 무재시도.

네트워크 정책은 3단: **오프라인**(어댑터 자체 비활성) / **로컬만**(로컬
호스트 외 차단) / **허용 목록**(사용자가 등록한 엔드포인트만). 기본값은
로컬만.

## 7. 대화 UI — 채팅이 아니라 작업대

채팅 패널은 있지만, 중심은 **작업 카드 스트림**이다:

- 도구 호출 1건 = 카드 1장(명령·인자·봉투 요약·exit code·소요).
- 편집 카드에는 전/후 렌더 썸네일(render-diff)과 변경 좌표가 붙는다.
- 검증 실패 카드에는 repair_loop의 진단 분류와 다음 시도가 이어진다.
- 작업이 끝나면 **영수증 카드**(capsule 해시)가 닫는다 — 클릭하면
  `replay` 재현 명령을 복사할 수 있다.

이 UI는 "AI가 뭘 했는지 모르겠다"는 데스크톱 에이전트 공통 불신을
rhwp의 회계 자산으로 정면 돌파하는 자리다. 카드 스트림은 NDJSON 저널의
1:1 렌더일 뿐이며, UI가 저널에 없는 것을 지어내 보여주지 않는다.

## 8. Windows 통합

- **파일 연결**: `.hwp`/`.hwpx` 열기(뷰어), 우클릭 확장 메뉴 "검증"(inspect
  3축+layout-anomaly 리포트), "텍스트 추출", "PDF로".
- **트레이 상주**: batch/gym/장기 검증의 진행률. 완료 토스트.
- **패키징**: 1차 **portable .exe**(설치 불요 — 기관 PC에서 관리자 권한
  없이 실행 가능, 이 사용자층에 결정적), 2차 MSIX(스토어·자동 업데이트).
  MSIX는 가상화된 파일시스템 특이사항이 있으므로(런타임 쓰기 경로를
  AppData로 통일) portable을 기준 삼는다.
- **업데이트**: portable은 앱 내 알림+수동 교체, MSIX는 스토어 채널.

## 9. 단계별 로드맵 (각 단계가 독립 출시 가능)

| 단계 | 내용 | 재사용 | 신축 | 출시 기준 |
|---|---|---|---|---|
| **M0 뷰어** | 셸+파일연결+studio 뷰 탑재+우클릭 검증 | studio·inspect·layout-anomaly | 셸 ① | .hwp 더블클릭→1초 내 첫 페이지 |
| **M1 결정론 작업대** | 명령 팔레트(전 CLI GUI 폼)+batch 러너+영수증 뷰 | capabilities(폼 자동 생성)·batch·replay | UI ③ 일부 | LLM 없이 서식 채우기·표 왕복·검증 완주 |
| **M2 에이전트** | 대화 패널+Planner 어댑터+승인 카드+repair 루프 | run·repair_loop·policy_gate | 어댑터 ② + UI ③ | "이 서식 채워서 검증까지"를 자연어로 완주 |
| **M3 위임·스킬** | handoff GUI·CAP 등록부 스킬 브라우저 | handoff·capability_registry | 얇은 배선 | 외부 에이전트 위임 1건을 카드로 추적 |

M1이 이 설계의 승부수다 — **LLM 이전에 이미 팔리는 도구**가 되고, M2는
그 위에 두뇌만 얹는다. `capabilities` JSON에서 GUI 폼을 자동 생성하므로
명령이 늘 때 데스크톱 코드는 안 바뀐다(자기서술 계약의 데스크톱 확장).

## 10. 저장소 배치와 경계

- 신규 crate `rhwp-desk/`(Tauri 앱, 워크스페이스 멤버) + `rhwp-desk/ui/`
  (studio에서 분기하지 않고 **studio를 의존으로 임포트** — 뷰 컴포넌트만
  가져오고 편집기 전체를 포크하지 않는다).
- rhwp 코어에 요구하는 변경: **없음이 목표.** 유일한 후보는 `capabilities`
  JSON에 GUI 힌트 필드(선택, 예: 파일 픽커 여부)를 얹는 것인데, 이것도
  recordFields 확장 규약(SWEEP_EXEMPT·지식지도 §2-2 등재)을 따르는 별도
  PR로 분리한다.
- CI: 데스크톱 빌드는 별도 워크플로(기존 CI에 무영향), 도구 계약 회귀는
  기존 계약 테스트가 이미 지킨다.

## 11. 리스크와 반론

| 리스크 | 대응 |
|---|---|
| WebView2 미설치(구형 Win10) | 부트스트래퍼가 Evergreen 설치 안내. 기관망 차단 시 오프라인 설치본 동봉 옵션 |
| studio가 데스크톱 임베드를 전제하지 않음 | M0에서 뷰 전용 서브셋만 임베드해 결합면 최소화. 편집 UI 통합은 M2 이후 별도 판단 |
| LLM 어댑터의 프롬프트 주입 | 문서 파생 텍스트는 전부 표지+nonce 경계(§6). inspect injection 사전 스캔을 파이프라인에 상시 배선 |
| 장기 실행 중 크래시 | 모든 작업이 저널 우선 기록(journal-first)이라 재시작 후 이어가기 가능 — run 저널·handoff 저널 재사용 |
| 유지보수 표면 증가 | 신축 3조각(셸·어댑터·대화 UI)만 데스크톱 소유. 나머지는 기존 계약 테스트가 지키는 자산의 소비자일 뿐 |

## 12. 이 설계가 여는 것

CLI(자동화)·mcp-serve(에이전트 호스트)·studio(브라우저)·**desk(일반
사용자·기관 PC)** — 네 표면이 전부 같은 엔진, 같은 봉투 계약, 같은 저널을
쓴다. desk는 rhwp의 "에이전트가 1급 소비자"(llms.txt) 선언을 **사람이 쓰는
제품**으로 뒤집어 보여주는 표면이며, 도구가 늘수록(자기서술 계약) UI가
공짜로 넓어지는 구조다.
