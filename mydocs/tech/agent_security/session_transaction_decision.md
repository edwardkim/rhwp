# `hwp_doc_transaction` 별도 도구 판정 기록

## 문서 정보

| 항목 | 내용 |
|------|------|
| 계기 | #3719 §3-3 "세션 도구 남은 공백 4" — "다건 원자 적용 (L4 계획 실행기가 상위 호환으로
       대체 가능 → §6 에서 판정)", §6 "판정 대기 2건" 중 하나 |
| 판정 | 별도 `hwp_doc_transaction` MCP 세션 도구를 **신설하지 않는다. L4 계획 실행기(`rhwp run` /
       `hwp_run_plan`)가 상위 호환이 맞다** |
| 근거 | 계획 실행기가 이미 "여러 step 선검증 → 원자 적용 → 단일 저장" 계약을 제공하고 있고,
       세션 트랜잭션이 추가로 필요할 만한 시나리오(세션 상태를 넘나드는 트랜잭션, 다중 문서
       메모리상 원자성)를 검토했으나 계획 실행기로 표현 불가능한 실제 요구를 찾지 못함 |

## 1. `rhwp run` / `cmd_run_plan` 이 실제로 하는 것

`src/main.rs` 의 `cmd_run_plan()`(13210행)과 그 본체 `run_plan_engine()`(13341행)을 확인했다.

### 1-1. 계획 입력 계약

- `cmd_run_plan` 은 계획 JSON 을 파일(`plan_path`) 또는 `--plan-json` 인라인 문자열로 받는다
  (13211-13252행). CLI `--dry-run` 플래그는 계획서의 `dryRun` 필드를 덮어쓴다(13262-13266행) —
  "의도의 단일 출처는 계획서"라는 주석이 13260행에 명시되어 있고, 이 덕분에 MCP `hwp_run_plan`
  은 별도 인자 추가 없이 같은 계약을 얻는다(13261행 주석).

### 1-2. 실행 계약 — 선검증 → 원자 적용 → 단일 저장

`run_plan_engine()` 을 그대로 추적하면:

1. **입력은 파일 경로다.** `plan["input"]`(13364행)을 `fs::read`(13380행)로 읽고
   `HwpDocument::from_bytes`(13384행)로 **매 실행마다 새로 파싱**한다. 즉 계획 실행기는
   기존 `hwp_open` 세션 핸들을 재사용하지 않고, 항상 디스크의 원본 파일에서 시작한다.
2. **정적 선검증(0 실행)** — 13389-13409행: 전체 필드 이름/개수를 한 번 순회해 모으고
   (`name_counts`, `name_locs`), `fill_fields`/`replace_text`/`set_checkbox`/`set_cell` 각
   step 을 실제 실행 전에 검사해 위반을 `invalid[]` 에 **전부** 모은다(두더지잡기 방지,
   13389행 주석). 위반이 있으면 exit 2, **출력 파일을 만들지 않는다**(§3-4 DoD, "선검증 실패가
   출력 파일 부재로 증명됨").
3. **원자 적용** — 선검증을 통과한 step 들을 인메모리 `doc`(`HwpDocument`, 13384행에서 로드한
   그 인스턴스)에 순서대로 적용한다. 중간에 실패하면 디스크는 그대로다(자연 트랜잭션).
4. **사후 단언 → 단 1회 저장** — `assertions.verify`(13374행 `assert_verify`),
   `assertions.notFoundEmpty`(13376행)를 확인한 뒤에만 `output` 경로에 저장한다. 실패 시 exit 3,
   저장 없음.
5. **저널** — step 별 결과 + `verify` + (§3-4 문서상) `changedPages` 를 반환한다.

이것이 로드맵 §3-4 가 요약한 "정적 선검증(실행 0) → 원자 실행(인메모리) → 사후 단언 → 단 한 번
저장" 계약과 코드 상 정확히 일치함을 확인했다.

## 2. "상위 호환"이 실제로 맞는지 — 계획 실행기로 표현 불가능한 시나리오가 있는가

로드맵이 제시한 두 후보를 검토했다.

### 2-1. 세션 상태를 넘나드는 트랜잭션

- 계획 실행기는 **입력을 항상 파일 경로에서 새로 읽는다**(13380-13384행). 이미 `hwp_open` 으로
  열어 두고 몇 차례 `hwp_doc_fill_fields` 등으로 메모리상 IR 을 변경해 둔 **살아 있는 세션**을
  계획 실행기가 이어받아 트랜잭션을 계속하는 경로는 없다 — 세션의 미저장 편집은 계획 실행기
  입장에서 보이지 않는다(디스크에 없으므로).
- 다만 이 격차가 실사용 문제가 되려면 "세션으로 일부 편집 → 그 미저장 상태 위에 추가로 여러
  step 을 원자적으로 얹고 싶다"는 워크플로가 있어야 한다. 그런데 세션 편집 도구들 자체가 이미
  step 단위로 즉시 반영되고 즉시 판정을 반환하므로(예: `replace_text` 의 치환 건수,
  `mcp_serve.rs` 세션 편집 도구 목록 12행 주석), "여러 step 을 모아 한 번에 원자 적용"하고
  싶다면 애초에 세션 편집을 부분적으로 시작하지 않고 **계획서 하나로 처음부터 표현**하면 된다.
  즉 "세션 상태를 넘나드는 트랜잭션"이 필요해지는 것은 에이전트가 계획 실행기 대신 세션 도구로
  작업을 시작한 경우뿐이며, 이는 도구 설계의 공백이라기보다 **사용 패턴 선택의 문제**다.
- 결론: 이론적으로는 존재하는 격차이지만, 계획서로 처음부터 작업을 표현하면 발생하지 않는
  격차이므로 별도 도구가 필요할 만큼의 실사용 근거는 없다(확인되지 않음: 세션을 먼저 시작한 뒤
  중간에 원자적 다건 적용이 필요해진 실제 요청 사례).

### 2-2. 파일이 아니라 메모리상 여러 문서에 걸친 원자성

- 계획 스키마(`plan["input"]`, `plan["output"]`, 13364-13369행)는 **단일 입력·단일 출력** 만
  받는다. §3-4 "v2 공백" 목록(로드맵 원문)에도 "다중 문서(input 배열·문서 간 전사)"가 **아직
  미착수**로 명시되어 있다 — 이는 계획 실행기 자체가 이미 인지하고 있는 v2 로드맵 항목이지,
  `hwp_doc_transaction` 이 채울 별개의 공백이 아니다.
- 즉 "여러 문서에 걸친 원자성"이 필요하다면, 그 확장은 **계획 스키마의 v2(다중 문서 input)**
  로 흡수되는 것이 맞다 — 세션 트랜잭션 도구를 별도로 만들어 이 문제를 풀 필요가 없다. 세션
  도구는 애초에 한 번에 하나의 `docId` 핸들만 다루므로(`hwp_open` → 단일 `docId`), 세션
  트랜잭션 도구를 만들어도 "여러 문서에 걸친 원자성" 문제는 자동으로 풀리지 않는다 — 여러
  `docId` 를 트랜잭션 인자로 받는 새 설계가 필요해지는데, 이는 계획 스키마의 다중 문서 확장과
  본질적으로 같은 설계 문제를 세션 계층에서 다시 푸는 것이다(불변식 §4-3 "새 로직 금지"에 저촉
  소지).

### 결론

두 후보 시나리오 모두, 별도의 `hwp_doc_transaction` 세션 도구가 아니라 (a) "계획서로 작업을
처음부터 표현" 하는 사용 패턴, 또는 (b) 계획 실행기 자체의 v2 확장(다중 문서 input)으로
흡수되는 것이 맞다. **계획 실행기로 표현 불가능하면서 세션 트랜잭션 도구로만 풀리는 실제
시나리오는 찾지 못했다.**

## 3. 판정

**`hwp_doc_transaction` 은 만들지 않는다. L4 계획 실행기가 상위 호환이 맞다는 로드맵의 가설을
확정한다.**

- 계획 실행기는 이미 "선검증 → 원자 적용 → 단일 저장"을 코드로 구현·테스트하고 있다
  (`src/main.rs:13341-13500`대, §3-4 DoD "4 action + 2 assertion 이 red→green 계약으로 고정").
- 세션 도구가 커버하지 못하는 두 격차(세션 상태 이어받기, 다중 문서)는 각각 (a) 사용 패턴
  선택으로 회피 가능하거나 (b) 계획 실행기 자체의 이미 계획된 v2 확장 범위이지, 세션 계층에
  중복 구현할 이유가 아니다.
- §6 "판정 대기 2건" 중 `hwp_doc_transaction` 항목은 본 문서로 **종결**한다: "계획이 상위
  호환이면 세션 트랜잭션은 불필요"라는 로드맵 원문의 조건이 §1~2 의 코드 추적으로 충족되었다.

## 4. 재검토 조건

다음 신호가 실제로 관측되면 재검토한다:

- 계획 실행기 v2 의 "다중 문서 input" 이 착수된 뒤에도, 세션 핸들 기반으로만 표현 가능한
  원자성 요구(예: 이미 열려 있는 여러 `docId` 사이의 트랜잭션)가 이슈로 접수될 때
- "세션으로 시작한 작업을 계획서로 전환하는 비용이 실제로 에이전트 워크플로를 막는다"는
  실측 보고가 나올 때(현재는 이런 보고가 없음 — 확인되지 않음)
