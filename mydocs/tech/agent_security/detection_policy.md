# 탐지·오탐 정책 — 여섯 가지 결정과 그 근거

이 문서는 **rhwp 가 문서에서 무엇을 탐지하고, 탐지한 것을 어떻게 다루는가**에 대한 결정과
근거를 보존한다.

아래 여섯 결정은 전부 **6개월 뒤 다시 논쟁이 된다.** "왜 그냥 지우지 않느냐", "왜 더 많이
잡지 않느냐", "요즘은 작은 모델로 판정하면 되지 않느냐" — 전부 합리적인 질문이고, 근거가
남아 있지 않으면 그때 뒤집힌다. 뒤집는 것 자체는 문제가 아니다. **근거를 모른 채 뒤집는
것**이 문제다. 그래서 결론이 아니라 논증을 남긴다.

> **구현 상태** — 결정 ①②④⑤⑥은 이미 코드에 있다(`textSecurity`, #3707).
> `untrustedContent`·`injectionSignals`·`hiddenText` 는
> [#3787](https://github.com/edwardkim/rhwp/issues/3787)로 **구현 중이며 아직 머지되지
> 않았다** — 이 문서가 그 구현의 계약이다. 각 절에서 **[현재]** / **[설계]** 로 구분한다.

## ① 지우지 않고 표시한다

**결정** — rhwp 는 문서에서 위험 신호를 찾으면 **봉투에 표시**한다. 문자열을 고치거나
지우거나 정규화하지 않는다.

### 왜 정화(sanitize)가 아닌가

#### 근거 1 — 조용한 정화는 그것대로 거짓말이다

이것이 다른 어떤 근거보다 먼저 온다.

사용자가 `export-text` 결과를 읽을 때, 그는 **문서를 읽었다고 믿는다.** rhwp 가 조용히
`U+202E` 를 걷어내고 키릴 `Т` 를 라틴 `T` 로 고쳐 보여 줬다면, 사용자는 자기가 본 적
없는 텍스트를 본 텍스트로 착각한다. 그가 화면에서 본 것과 실제 파일의 내용이 다르다.

**공격자가 하려던 일이 정확히 그것이다** — 화면과 실체를 어긋나게 하는 것. 정화는 그
어긋남을 없애는 게 아니라 **어긋남의 방향을 바꿀 뿐**이다. 이번엔 도구가 사용자를 속인다.
선의라는 점만 다르다.

보안 도구가 사용자에게 거짓 상태를 보여 주는 것은, 그 거짓이 안전한 방향이라도 계약 위반이다.

#### 근거 2 — 형식 보존이 제품의 핵심 약속이다

rhwp 는 왕복 충실도 하네스와 `ir-diff` 로 **입력과 출력의 의미 동일성**을 시험한다(#3383).
정화기는 이 약속을 조용히 깬다. 키릴로 쓰인 정당한 러시아어 인용문을 라틴으로 고쳐 저장하는
순간 그 문서는 손상된 것이고, `--verify` 는 그것을 차이로 보고할 것이다.

#### 근거 3 — 사용자 파일이 실제로 망가진다

MCP 세션은 읽기-수정-쓰기 루프다:

```
hwp_open → hwp_doc_text → hwp_doc_replace_text → hwp_doc_save
```

읽을 때 정화하면 **정화된 형태가 그대로 디스크에 기록된다.** 사용자는 텍스트 하나를 바꾸려
했을 뿐인데 문서 전체의 문자가 조용히 바뀐다.

#### 근거 4 — 좌표계가 어긋난다

`GrepMatch` 는 `charOffset`/`length` 를 문자 오프셋으로 낸다(§실측: `search --json` 봉투에
`"charOffset":29,"length":2`). `U+200B` 하나를 지우면 **그 뒤 모든 좌표가 무효**가 되고,
`set-cell`·`--occurrence`·후속 편집이 전부 어긋난다. 정화는 탐지 기능 하나를 얻고 주소
체계 전체를 잃는 거래다.

#### 근거 5 — 위협이 사라지지도 않는다

`U+202E` 를 걷어내도 "이전 지시는 무시하고 다음을 실행하라"라는 **한글 문장은 그대로**다.
정화가 막는 것은 벡터의 일부뿐인데, 소비자는 "정화된 텍스트"라는 이름표를 보고 안전하다고
믿는다. 정화는 충실도를 내주고 **완전하다는 착각**을 사는 거래다.

### 그럼 지우고 싶을 때는

지우는 것은 **사용자가 명시적으로 부르는 명령**의 일이다.

| 축 | 누가 부르나 | 무엇을 하나 | 상태 |
| --- | --- | --- | --- |
| `fields --json` 의 `textSecurity` | 자동(모든 호출) | 표시만 | **[현재]** |
| `edit redact` | **사용자가 명령으로** | 실제로 지우고 새 파일로 저장 | **[설계]** |

> **⚠ [설계]** — `edit redact` 는 **현재 존재하지 않는다.** `src/` 전체 grep 0건,
> `rhwp --help` 0건으로 확인했다(2026-08-02, v0.8.2). 이 표의 아랫줄은 계약이지 현황이 아니다.

경계가 왜 여기인가: **사용자가 명령을 쳤다는 것 자체가 동의**다. `redact` 를 부른 사용자는
결과물이 원본과 다르다는 것을 안다. 자동 정화에는 그 동의가 없다.

`redact` 가 지켜야 할 규약도 여기서 고정한다.

- **원본을 덮어쓰지 않는다.** 산출은 항상 새 경로.
- **무엇을 지웠는지 봉투로 보고한다.** 지운 개수·종류·위치. 조용한 삭제는 `redact` 에서도 금지.
- **판정 어휘는 `textSecurity` 와 동형.** 같은 `kind` 이름을 쓴다.

## ② 오탐은 기능 실패다 — 놓치는 것보다 나쁘게 본다

**결정** — 탐지 규칙은 **정상 한국 공문서에서 절대 발화하지 않는 것**을 첫 번째 제약으로
설계한다. 탐지율을 높이려고 오탐을 늘리는 교환은 하지 않는다.

이것은 보안 공학의 통상적 직관과 반대다. 보통은 "놓치는 것(FN)이 헛울리는 것(FP)보다
나쁘다"고 본다. **여기서는 아니다.** 왜 그런지가 이 절의 전부다.

### 논증 1 — 이 방어의 최종 실행자는 사람이다

`textSecurity` 는 **스스로 아무것도 막지 않는다.** 실측이 이를 못박는다:

```json
{"ambiguous":[],"changedPages":null,
 "confusable":[{"lookalikes":["Тotal"],"name":"Total","note":"…"}],
 "dryRun":true,"filled":[{"name":"Total","occurrence":0,"value":"999"}],
 "filledCount":1,"notFound":[],"schemaVersion":"1.0","source":"…/probe-cyr.hwpx"}
```

`filledCount: 1`, `notFound: []` — 성공 봉투다. `run --json` 은 같은 상황에서 **exit 0**
으로 끝나고 파일을 쓴다. 흐름을 멈추는 것은 **신호를 읽은 소비자**뿐이다.

즉 이 방어의 실효는 100% **"신호가 읽히는가"**에 달려 있다.

### 논증 2 — 오탐은 신호를 읽히지 않게 만든다 (비대칭)

여기서 FN 과 FP 의 비대칭이 나온다.

| | 1건의 영향 | 누적 효과 |
| --- | --- | --- |
| **FN(놓침)** | 그 문서 1건이 방어 없이 통과 | **없음** — 다른 문서의 탐지는 그대로 작동 |
| **FP(헛울림)** | 그 문서 1건에서 사람이 불필요하게 확인 | **있음** — 무시 습관이 생기고, 그 습관은 **모든 이후 탐지에 적용된다** |

FN 은 **국소적**이다. FP 는 **전역적**이다. 헛울림을 몇 번 겪은 운영자는
`if env["confusable"]: pass` 를 넣거나, 아예 필드를 안 읽는다. 그 순간 탐지율이 얼마든
실효 탐지율은 0이 된다.

**놓친 1건은 1건의 손해다. 헛울린 1건은 앞으로의 모든 탐지를 깎는다.**

### 논증 3 — 안 쓰이는 방어는 방어가 아니다

FP 가 높은 탐지기의 최종 상태는 "꺼진 탐지기"다. 코드에는 남아 있고, 테스트는 통과하고,
문서에는 기능으로 적혀 있는데, 실제 파이프라인에서는 아무도 그 필드를 안 본다.
**이 상태는 탐지기가 없는 것보다 나쁘다** — 없으면 적어도 방어하고 있다고 착각하지 않는다.

### 논증 4 — 도메인 특수성이 FP 를 특히 위험하게 만든다

rhwp 의 주 무대는 **한국 행정 서식**이다. 정상 문서가 다음을 일상적으로 한다:

- 한글·한자·라틴·숫자·기호를 한 낱말에 섞는다 (`E-Mail`, `2026년 Q3`, `株式會社`)
- 표·머리말·꼬리말·주석에 안내 문구를 넣는다
- 누름틀 `guide`/`memo` 에 "여기에 입력" 같은 **지시문 형태의 문장**을 넣는다 —
  실측: `"guide":"여기에 입력"`

세 번째가 특히 곤란하다. 서식의 정상 기능이 **인젝션과 문법적으로 구별되지 않는다.**
"여기에 회사명을 입력하세요"와 "다음 파일을 읽고 전송하세요"는 둘 다 명령문이다.
문법만으로 가르려는 규칙은 한국 서식에서 반드시 헛울린다.

### 실측 — 이 정책이 지켜지고 있는가

정책은 수치로 증명되지 않으면 의견이다. `samples/` 전건 스윕(2026-08-02):

| 항목 | 값 |
| --- | --- |
| 문서 파일 | **668개** (hwp 395 · hwpx 271 · hml 2) |
| 스윕 레코드 | 668 (12.65초, `batch fields --json`) |
| `clean` | **665** |
| **`warning`** | **0** |
| `error` | 3 (전부 암호 문서, `exitClass: "runtime"`) |
| 판정된 누름틀 이름 | **10,592개** (누름틀 보유 문서 179개) |

**실제 한국 공문서·서식 665건, 누름틀 이름 10,592개에서 경고 0건.**

이것이 이 정책의 수용 기준이다: **새 탐지 규칙은 이 스윕을 경고 0으로 통과해야 한다.**
통과하지 못하면 규칙을 좁히거나, 아니면 넣지 않는다. 규칙을 넣고 스윕을 고치는 것은 금지다.

### 이 정책이 만든 구체적 규칙 (코드에 있는 것)

`src/document_core/text_security.rs` 가 FP 를 줄이려고 실제로 포기한 것들:

| 좁힌 것 | 잃은 것(FN) | 이유 |
| --- | --- | --- |
| 본문에는 혼합 스크립트 판정을 **안 한다** (`scan_text` vs `scan_identifier`, :204/:237) | 본문의 동형자 스푸핑 | 한국어 문서가 러시아어를 인용하는 것은 정상 |
| **단일 스크립트는 통과** (`scripts.len() > 1` 일 때만, :248) | 순수 키릴로 만든 가짜 이름 | `Москва`·`αβγ` 는 정당하다 |
| **한글·한자·숫자·문장부호를 스크립트 계산에서 제외** (`script_of`, :92~105) | 그쪽 축의 스푸핑 | 세는 순간 한국어 문서 전부가 발화한다 |
| **같은 이름의 단순 반복은 제외** (`members.len() > 1` 이 서로 다른 이름 기준, :364) | — | 기존 `ambiguous` 판정의 몫 (중복 신호 금지) |
| 동형자 표를 **~50항목**으로 제한 (`confusable_to_latin`, :111~182) | 저빈도 동형자 | 표를 넓히는 것보다 정확히 유지하는 편이 FP 를 막는다 |

각 줄의 왼쪽이 이 정책의 대가이고, 오른쪽이 그 값이다. **이 표를 보고도 왼쪽을 넓히고
싶다면, 먼저 665건 스윕을 통과시켜라.**

## ③ LLM 판정을 넣지 않는다

**결정** — rhwp 코드에 언어 모델 호출·소형 분류 모델·임베딩을 넣지 않는다. 탐지는
**결정론적 규칙**만 쓴다.

### 논증 1 — 순환성: LLM 으로 LLM 공격을 막는다는 것

이것이 가장 중요한 근거다.

간접 프롬프트 인젝션은 **"모델이 데이터를 지시로 오인하는 것"**이다. 이를 판정하려고
모델을 하나 더 두면, **그 판정 모델도 같은 입력을 읽는다.** 같은 취약점을 가진 부품을
방어선으로 세우는 셈이다.

공격자에게는 표적이 하나 늘 뿐이고, 오히려 더 쉽다 — 판정 모델은 보통 더 작고, 컨텍스트가
짧고, "이 텍스트가 인젝션인가?"라는 **고정된 프롬프트**를 쓴다. 프롬프트가 고정이면
공격자는 그것에 맞춰 최적화할 수 있다.

더 나쁜 것은 **판정 모델이 뚫렸을 때 아무 흔적이 없다는 점**이다. 규칙 기반 탐지기는
"이 규칙이 이 문자열에 안 걸렸다"를 사후에 재현할 수 있다. 모델은 "그때 그 판정이 왜
clean 이었는지"를 재현할 수 없다.

### 논증 2 — 재현성이 계약이다

rhwp 의 봉투는 **계약**이고 계약 테스트로 고정된다(`tests/` 416개 파일). 계약은 같은
입력에 같은 출력을 요구한다.

| 항목 | 규칙 기반 | 모델 기반 |
| --- | --- | --- |
| 같은 입력 → 같은 출력 | 보장 | 온도·버전·양자화에 따라 변동 |
| 회귀 시험 | 가능 | 임계값 튜닝 게임이 된다 |
| CI 결정성 | 보장 | 플래키 |
| "왜 이 판정인가" | 코드 줄 번호 | 설명 불가 |

`textSecurity` 처럼 **봉투에 실리는 필드**는 소비자가 분기 조건으로 쓴다(§소비자 가이드
§3.4). 분기 조건이 비결정적이면 소비자 코드도 비결정적이 된다.

### 논증 3 — 오프라인 동작이 제품 요구다

rhwp 는 **네트워크 없이 동작한다.** 행정망·폐쇄망·CI 컨테이너·브라우저 WASM 이 전부
실사용 환경이다. 모델 호출은 이 중 어느 것도 만족하지 못한다:

- 원격 API: 네트워크 필요 + **문서 내용이 외부로 나간다** — 그 자체가 새 유출 경로다
- 로컬 모델: 산출물 크기·메모리·CPU. `[lib] crate-type = ["rlib", "cdylib"]` 이므로
  **브라우저 뷰어 WASM 에 그대로 실린다**

### 논증 4 — 의존성 정책과 충돌한다

이 저장소는 이미 **UTS #39 전체 표(728KB + 515KB)조차 거부했다**(#3707). 이유는 WASM
산출물에 그대로 실리기 때문이다. 데이터 표 1MB 를 거부한 저장소에 모델을 넣는 것은
일관되지 않는다.

실제로 `Cargo.toml` 직접 의존성에는 **정규식 엔진조차 없다**(2026-08-02 실측;
`Cargo.lock` 에는 전이 의존으로 존재).

### 반론 처리 — "그럼 자연어 인젝션은 어떻게 잡나"

**완전히는 못 잡는다.** 그것이 정직한 답이다. 규칙으로 잡을 수 있는 것은 자연어 판정이
아니라 **구조적 신호**다:

- 사람이 볼 수 없는 위치·서식에 텍스트가 있다 (`hiddenText` **[설계]**)
- 문서 텍스트가 도구·에이전트 어휘를 담는다 (`injectionSignals` **[설계]**, ⑤ 참조)
- 코드포인트 층위의 기만 (`textSecurity` **[현재]**)

그리고 못 잡는 부분은 **소비자 쪽 권한 축소**가 받는다([소비 에이전트
가이드](consumer_guide.md) §3.5 B1). 탐지가 완전하지 않다는 전제 위에 설계를 세우는 것이,
탐지가 완전한 척하는 것보다 안전하다.

## ④ 부분 목록 금지 — `null` 의 의미

**결정** — 목록형 판정 필드는 **완전하거나 `null`**이다. 확신이 없으면 항목을 빼는 것이
아니라 필드 전체를 `null` 로 내린다.

### 기존 규약과의 연결

이것은 새 규칙이 아니라 rhwp 가 이미 채택한 규약의 보안 축 적용이다.

| 선례 | 규약 | 출처 |
| --- | --- | --- |
| `changedPages` | 문단→페이지 매핑을 확정할 수 없으면 `null`("전체를 보라"). **부분 목록 금지** | P3, [경량 에이전트 내성](../weak_agent_proofing.md) §4 |
| `verify` | `--verify` 미지정 시 `null`. 판정 불가와 판정 통과를 구별 | #3596 |
| `nextCall`·`didYouMean` | 확신 없는 제안은 **필드 생략**(오제안 0) | P1·P4 |
| `textSecurity` 부재 | "깨끗함"이 아니라 **"검사하지 않음"** | #3707, `src/main.rs:4794`~`4796` |
| `title` | 추출 실패 시 `None`(JSON null) | `src/main.rs:4866`~`4868` |

`changedPages` 의 실측 확인 — 같은 명령에서 두 값을 다 봤다:

```json
"changedPages": null      // edit fill-fields --dry-run (레이아웃 재계산 없음)
"changedPages": [0]       // run --json (실제 저장 경로)
```

### 왜 부분 목록이 `null` 보다 나쁜가

| | 소비자가 읽는 뜻 | 실제 | 결과 |
| --- | --- | --- | --- |
| **부분 목록** | "이게 전부다" | 일부만 | **거짓 통과** — 빠진 항목은 검사되지 않고 통과 |
| **`null`** | "모른다" | 모른다 | 보수적 처리(전수 확인·사람 확인) |

부분 목록은 **정밀한 척하는 것**이고, 정밀한 척은 소비자에게 "나머지는 안전"이라는 잘못된
결론을 준다. `null` 은 아무 정보도 안 주지만 **거짓 정보도 안 준다.**

보안 축에서 이 차이는 특히 크다. `hiddenText: []`("은닉 텍스트 없음")와
`hiddenText: null`("검사 못 함")은 소비자 코드에서 **완전히 다른 분기**여야 한다.
전자는 진행, 후자는 사람 확인이다. 검사에 실패했는데 `[]` 를 내면 그 문서는 은닉 검사를
통과한 것으로 기록된다.

### 세 상태를 구별한다

| 값 | 뜻 | 소비자 |
| --- | --- | --- |
| `[...]` (원소 있음) | 검사했고 발견했다 | 처리 |
| `[]` (빈 배열) | 검사했고 없다 | 진행 |
| `null` | **검사하지 못했다** | 보수적 처리 |
| 키 자체 없음 | **이 바이너리는 검사 기능이 없다** | `capabilities` 확인 |

네 상태 중 두 개(`[]` 와 `null`)를 뭉개는 것이 가장 흔한 구현 실수다. 계약 테스트가
이 둘을 각각 고정해야 한다.

### 적용 — 각 필드

| 필드 | 완전할 수 있나 | `null` 조건 | 상태 |
| --- | --- | --- | --- |
| `textSecurity.findings` | **예** — 이름 집합이 유한하고 전수 검사한다 | 없음(항상 배열) | **[현재]** |
| `confusable` | **예** — 같은 근거 | 없음(항상 배열, 실측 `[]` 확인) | **[현재]** |
| `hiddenText` | 조건부 | 서식 정보를 못 읽는 경로 | **[설계]** |
| `injectionSignals` | 아니오 — 자연어다 | **완전성을 주장하지 않는다**(⑤) | **[설계]** |

`injectionSignals` 가 예외인 이유가 중요하다. 이 필드는 **"발견한 것"의 목록이지 "전부"의
목록이 아니다.** 그래서 `[]` 를 "인젝션 없음"으로 읽으면 안 되고, 이 사실을 필드 이름과
문서로 못박아야 한다 — `signals`(신호)이지 `verdict`(판정)이 아닌 이유다.

## ⑤ 신뢰도 등급 기준 — **[설계]**

> **⚠ [설계]** — `injectionSignals` 는 #3787 로 설계됐고 **아직 머지되지 않았다.**
> 아래 등급 체계는 계약이며, v0.8.2 봉투에는 이 필드가 없다.

**결정** — `high`/`medium`/`low` 는 **객관적으로 판정 가능한 규칙**으로 나눈다.
"수상함의 정도"가 아니다.

### 왜 규칙이어야 하나

등급은 소비자 코드의 **분기 조건**이다([소비 에이전트 가이드](consumer_guide.md) §3.2 —
high 는 중단, medium 은 읽기 전용 강등, low 는 진행). 분기 조건이 "느낌"이면:

- 같은 문서가 버전마다 다른 등급을 받는다 → 계약 테스트 불가
- 어떤 규칙 때문에 high 가 됐는지 설명할 수 없다 → 오탐 조사 불가
- 등급 기준이 조용히 표류한다 → 소비자 코드가 조용히 무력화된다

### 등급 정의 — 축이 아니라 **조합의 개수**

느낌을 배제하는 방법: 등급을 **"몇 개의 독립 축이 동시에 발화했는가"**로 정의한다.
개별 축의 "심각도"를 매기지 않는다 — 그 순간 느낌이 들어온다.

**축(signal axis)** — 각각 독립적으로 판정 가능하고, 각각 정상 문서에서 발생 가능하다.

| 축 | 판정 내용 | 정상 문서에서도 나오나 |
| --- | --- | --- |
| **A. 은닉** | 사람이 볼 수 없는 위치·서식의 텍스트 | 예 (흰 배경 흰 글자 실수, 화면 밖 잔여 개체) |
| **B. 지시 형태** | 명령문 + 대상 지정 어휘의 동시 출현 | 예 (`guide`: "여기에 입력") |
| **C. 도구·에이전트 어휘** | `AI`·`assistant`·도구 이름·`시스템`·`이전 지시` 등 | 드묾 |
| **D. 코드포인트 기만** | bidi·제로폭·동형자 (`textSecurity` 재사용) | 드묾 |
| **E. 외부 지시** | URL·경로·전송 대상이 지시문과 같은 문단에 | 예 (안내문에 홈페이지 주소) |

**등급 규칙**

| 등급 | 규칙 | 근거 |
| --- | --- | --- |
| **`high`** | **A(은닉) ∧ (B ∨ C)** — 사람이 못 보는 곳에 지시문 형태가 있다 | 은닉의 유일한 목적이 "사람 눈을 피하는 것"이다. 지시문을 숨길 정상적 이유가 없다 |
| **`medium`** | **서로 다른 축 2개 이상** (high 조건 미충족) | 축 하나는 우연일 수 있다. 둘이 겹칠 확률은 급감한다 |
| **`low`** | **축 1개** | 보고하되 흐름은 막지 않는다 |
| **(미발화)** | 축 0개 | `injectionSignals` 를 내지 않는다 |

이 규칙의 성질:

- **재현 가능** — 같은 문서는 항상 같은 등급. 각 축이 결정론적이므로.
- **설명 가능** — 봉투에 발화한 축을 함께 싣는다. `"axes": ["A", "C"]` 형태로.
- **조정 가능** — 오탐이 나오면 **축의 판정 규칙**을 좁히지, 등급 임계값을 만지지 않는다.
  임계값 튜닝은 근거 없는 조정의 온상이다.
- **A 가 특별한 이유가 근거로 남는다** — high 를 "A ∧ (B∨C)"로 정의한 것은 A 를 심각도가
  높은 축으로 봐서가 아니라, **A 에 정당한 이유가 없기 때문**이다.

### 등급이 하지 않는 것

| 하지 않는 것 | 이유 |
| --- | --- |
| 점수(0~100)를 내지 않는다 | 임계값이 감으로 정해지고, 소수점이 정밀도의 착각을 만든다 |
| "안전함"을 선언하지 않는다 | 미발화는 "신호 없음"이지 "안전"이 아니다(④의 `signals` vs `verdict`) |
| 문서를 차단하지 않는다 | 판단은 소비자가 한다(①) |
| 등급으로 정화 수준을 정하지 않는다 | 정화 자체를 안 한다(①) |

### 계약 테스트가 고정해야 하는 것

- `injection_signals_high_requires_hidden_axis` — A 없이 high 가 나오지 않는다
- `injection_signals_level_is_deterministic` — 같은 파일 10회 호출 시 등급 동일
- `injection_signals_reports_axes` — 등급과 함께 발화 축이 실린다
- `injection_signals_absent_on_sample_corpus` — `samples/` 665건에서 high 0건(②의 스윕 확장)

## ⑥ 성능 제약 — 탐지기 자체가 DoS 표면이다

**결정** — 탐지는 문서 크기에 **선형**이어야 한다. ReDoS 를 성립시키는 형태의 정규식을
쓰지 않는다.

### 왜 이것이 보안 정책인가

성능은 보통 품질 항목이지 보안 항목이 아니다. 여기서는 다르다.

**탐지기의 입력은 공격자가 완전히 통제하는 데이터다.** 이 축의 전제 자체가 그렇다 —
공격자가 만든 `.hwp` 가 rhwp 에 들어온다. 탐지기가 어떤 입력에서 초선형으로 느려진다면,
공격자는 **그 입력을 정확히 만들 수 있다.**

그러면 이런 일이 생긴다:

```
공격자가 만든 문서 → rhwp 가 탐지 시도 → 탐지기가 멈춤
                                          ↓
                          MCP 서버 응답 없음 / 배치 파이프라인 정지
```

**보안 기능을 추가했더니 새 취약점이 생긴 것이다.** 게다가 이 DoS 는 탐지기가 없었으면
존재하지 않았다. 방어를 추가하는 행위가 순 위험을 늘리는 경우이고, 그런 방어는 넣지
않는 편이 낫다.

배치 축에서 특히 심하다 — `batch fields --json` 은 한 프로세스로 전건을 돌린다(실측:
668건 12.65초). 파일 하나가 탐지기를 멈추면 **그 배치 전체가 멈춘다.** 스레드 풀에
같은 문서가 여러 개 들어오면 프로세스가 통째로 죽는다.

### 규칙

| # | 규칙 | 이유 |
| --- | --- | --- |
| P1 | **역추적 정규식 금지** | ReDoS. 중첩 수량자(`(a+)+`)·교대 반복은 지수 시간 |
| P2 | **단일 패스 스캔 우선** | `chars()` 한 번으로 판정할 수 있으면 그렇게 한다 |
| P3 | **입력 길이에 상한을 두지 않는다** | 상한은 "긴 문서는 검사 안 함"이라 우회가 자명하다. 대신 알고리즘을 선형으로 |
| P4 | **할당은 입력 크기에 비례** | 문자당 여러 벡터를 만들지 않는다 |
| P5 | **초선형 경로는 문서화 + 실측** | 없앨 수 없으면 최소한 **알려진 상태**로 둔다 |

**P1 이 현재 무료로 지켜지는 이유** — `Cargo.toml` 직접 의존성에 **정규식 엔진이 없다**
(2026-08-02 실측). `text_security` 는 `match` 와 범위 비교만 쓴다. 즉 현재 ReDoS 표면이
구조적으로 0이다. **이 상태를 유지하는 것이 P1 의 실질**이고, 정규식 크레이트를 직접
의존성에 넣자는 제안은 이 절을 근거로 검토돼야 한다.

### 현재 구현의 복잡도 — 실측과 정직한 예외

| 함수 | 복잡도 | 근거 |
| --- | --- | --- |
| `scan_text` (:204) | **O(n)** — `chars()` 단일 패스 | 문자당 상수 비교 3회 |
| `scan_identifier` (:237) | O(n·s), s=스크립트 3종 | 실질 O(n) |
| `compose_hangul` (:283) | **O(n)** — 인덱스 전진, 되돌아가지 않음 | 산술 조합, 표 조회 없음 |
| `confusable_skeleton` (:327) | **O(n)** | filter → compose → map → lowercase |
| `confusable_collisions` (:348) | **O(k²·m)** ← **선형이 아니다** | k=이름 수, m=골격 길이 |

**마지막 줄이 이 규칙의 정직한 예외다.** 코드가 이렇다:

```rust
for name in names {
    let skel = confusable_skeleton(name);
    match groups.iter_mut().find(|(s, _)| *s == skel) { … }   // groups 선형 탐색
}
```

이름마다 `groups` 를 선형 탐색한다. 모든 이름의 골격이 서로 다르면 `groups` 가 k 까지
자라므로 총 비교 횟수는 **O(k²)**이다.

**실측으로 경계를 확인했다** (2026-08-02, v0.8.2):

| 문서 | 누름틀 수 | 크기 | `fields --json` 전체 |
| --- | --- | --- | --- |
| `samples/80168_regulatory_analysis.hwp` | **1,070** (코퍼스 최대) | 218KB | **0.409초** |
| `samples/2025 행정업무운영 편람(최종).hwp` | 0 | 10.7MB | **0.465초** |

누름틀 1,070개(≈57만 회 골격 비교)에서 **탐지 비용이 파싱 비용에 묻힌다.** 두 번째 줄이
대조군이다 — 누름틀 0개인 50배 큰 문서가 오히려 더 걸린다. 즉 현재 코퍼스 규모에서
O(k²) 는 관측되지 않는다.

**그럼에도 이것을 기록하는 이유**: 누름틀 수 k 는 **문서가 정한다.** 공격자가 k=100,000 인
문서를 만들면 100억 회 비교가 된다. 현재 이것이 실제 위험이 아닌 이유는 파서가 그런
문서를 만들기 전에 다른 한계에 부딪히기 때문이지, **알고리즘이 안전해서가 아니다.**

| 항목 | 내용 |
| --- | --- |
| 상태 | **알려진 초선형 경로**(P5) |
| 현재 위험 | 낮음 — 실측 코퍼스 최대 k=1,070 에서 관측 불가 |
| 해소 방법 | `groups` 를 `HashMap<String, Vec<String>>` 으로 → O(k·m) |
| 착수 조건 | k 가 큰 실제 문서가 관측되거나, 이 경로를 겨냥한 코퍼스가 추가될 때 |

이 항목은 [악성 코퍼스](test_corpus.md)에 **자원 소모 벡터**로 등록한다 — 코퍼스가
"많은 누름틀" 표본을 합성해 시간 상한 시험을 걸면 회귀가 자동으로 잡힌다.

### 새 규칙을 추가할 때의 관문

- [ ] 최악 입력에서의 복잡도를 **적었다** (O 표기 + 무엇이 n 인가)
- [ ] 초선형이면 **왜 허용하는지**와 **해소 방법**을 적었다 (P5)
- [ ] 정규식을 썼다면 역추적이 없음을 논증했다 (P1)
- [ ] 코퍼스 최대 규모 표본에서 실측 시간을 기록했다
- [ ] 자원 소모 표본이 [코퍼스](test_corpus.md)에 추가됐다

---

## 정책 변경 절차

이 여섯 결정을 뒤집으려면:

1. **어느 논증이 틀렸는지 지목한다.** "요즘은 다르다"는 지목이 아니다.
2. **②의 665건 스윕을 통과시킨다.** 탐지를 넓히는 변경은 특히.
3. **⑥의 복잡도 관문을 통과한다.**
4. **[악성 코퍼스](test_corpus.md)에 양성·음성 표본을 함께 추가한다.**
5. 결정 표와 해당 절을 갱신하고, `last_verified` 를 올린다.

절차를 어긴 정책 변경은 되돌린다 —
[에이전트 표면 플레이북](../../manual/agent_surface_playbook.md)의 규약과 같다.
