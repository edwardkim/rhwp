# `hwp_doc_verify` 별도 도구 판정 기록

## 문서 정보

| 항목 | 내용 |
|------|------|
| 계기 | #3719 §3-3 "세션 도구 남은 공백 4" — `hwp_doc_verify` 재검토 지시 |
| 판정 | 별도 `hwp_doc_verify` MCP 세션 도구를 **신설하지 않는다** |
| 근거 | `hwp_doc_save{verify:true}`(#3702, PR #3705)가 이미 저장 시점 자기검증을 제공하고,
       "저장 없이 세션 상태만 검증"하는 실제 사용 시나리오를 찾지 못함 |

## 1. `hwp_doc_save{verify}`가 정확히 무엇을 검증하는가

`src/mcp_serve.rs` 의 `session_save()` (도구명 `hwp_doc_save`) 를 확인했다.

- 도구 선언(`src/mcp_serve.rs:521-528`):
  ```
  521:        "name": "hwp_doc_save",
  ...
  528:                "verify": { "type": "boolean", "description": "true 면 저장본 재파싱 IR 자기검증(verify 필드)" }
  ```
- 실행 경로(`src/mcp_serve.rs:1387-1405`):
  1. 살아 있는 세션 IR(`sd.doc`)을 스냅숏하여 바이트로 직렬화한다(`crate::edit_serialize_snapshot`, 1387행).
  2. 그 바이트를 `output` 경로에 실제로 `fs::write` 한다(1391행) — **디스크 쓰기가 먼저 일어난다**.
  3. `verify:true` 인 경우에만 `crate::edit_verify_report(&sd.doc, &bytes, false)` 를 호출한다(1401행).
     이 함수는 방금 쓴 `bytes`(저장된 산출물)를 **재파싱**하여 나온 IR 을, 저장 전
     살아 있던 `sd.doc`(세션 IR)과 대조한다. 즉 비교 대상은:
     - **"편집 전후"가 아니라 "직렬화 전 세션 IR" ↔ "직렬화 후 저장 바이트를 재파싱한 IR"**
     - 왕복(round-trip) 손실을 잡는 계약이지, 사용자의 편집 의도가 맞는지를 검증하는 게 아니다.
  4. 판정은 산문이 아니라 `verify` 필드에 데이터로 실린다(1406-1416행, 불변식 §4-2 "판정은 데이터").
     `verify:false`(기본값)면 `verify` 필드는 `null` 이고 저장은 그대로 성공 처리된다.

핵심: **이 계약은 저장 동작에 종속되어 있다.** `bytes` 자체가 `session_save` 내부에서만
만들어지므로, "저장하지 않고 검증만" 은 현재 함수 경계상 성립하지 않는다 — 저장이 곧
검증 입력의 출처다.

## 2. 별도 `hwp_doc_verify` 가 필요한 실제 시나리오가 있는가

로드맵이 제시한 두 후보 시나리오를 검토했다.

### 시나리오 A — "저장 없이 지금 세션 상태가 유효한가만 확인"

- `edit_verify_report(doc, bytes, ..)` 의 시그니처(`src/main.rs` 내 `edit_verify_report` 정의,
  `.agentwt/decision-docs` 워크트리 `grep -rn "fn edit_verify_report"` 로 확인 가능)는 **직렬화된
  바이트**를 두 번째 인자로 요구한다. "세션 상태만" 검증한다는 것은 세션 IR 을 세션 IR 자신과
  비교하는 것이므로 항상 항등(자기 자신과 동일)이라 의미 있는 판정이 나오지 않는다.
- 즉 "유효성"을 검증하려면 반드시 **직렬화 → 재파싱** 왕복이 있어야 하고, 그 직렬화 산출물은
  이미 `hwp_doc_save{verify:true}` 가 스냅숏 경로(`edit_serialize_snapshot`, 1387행)로 만들고 있다.
  디스크에 쓰지 않고 스냅숏만 만들어 검증하는 "verify-only, no write" 변형은 이론상 가능하지만,
  그 경우에도 대조 대상은 여전히 "지금 세션 IR" 대 "그 세션 IR 을 직렬화·재파싱한 것" 뿐이다 —
  **저장 여부와 무관하게 로직이 같다.** 저장을 생략해서 얻는 이득은 디스크 I/O 1회 절감뿐이며,
  이는 별도 도구 신설을 정당화할 만큼의 실사용 압박으로 보이지 않는다(§3 참고).

### 시나리오 B — "특정 편집 단계마다 검증하고 싶은 경우"

- 세션 편집 도구들(`hwp_doc_fill_fields`/`hwp_doc_replace_text`/`hwp_doc_set_cell`, `mcp_serve.rs:12`
  주석 "세션 편집(`hwp_doc_fill_fields`/`hwp_doc_save`, #3598)")은 모두 **메모리상의 세션 IR 을
  즉시 갱신**하고 반환값에 해당 편집이 적용됐는지 여부를 이미 담아 돌려준다(예: `replace_text` 는
  치환 건수를, `set_cell` 은 이전 값을 응답에 싣는다 — L5 불변식 "판정은 데이터"). 편집 도구 자체가
  "이 호출이 성공했는가"의 판정을 이미 반환하므로, 그 위에 별도의 "지금까지의 누적 편집이 유효한가"
  검증을 추가로 두는 것은 **L4 계획 실행기가 이미 제공하는 계약과 중복**된다 — 계획 실행기는
  `assertions.verify` 로 "전체 편집 묶음 완료 후 1회" 검증을 지원한다(§3-4, `run_plan_engine`,
  `src/main.rs:13374`의 `assert_verify`). 세션 경로에서 "편집 단계마다" 검증하고 싶다면, 그 요구
  자체가 "여러 step 을 원자적으로 묶어 마지막에 한 번 검증"이라는 계획 실행기의 설계와 동형이다 —
  세션 도구를 여러 번 호출하며 매번 별도 verify 를 부르는 패턴은 계획 실행기가 이미 대체 가능한
  워크플로다.

### 결론

두 시나리오 모두 (a) 기존 `hwp_doc_save{verify}` 로 충분히 커버되거나, (b) L4 계획 실행기의
`assertions.verify` 로 이미 대체 가능하다. **"저장 없이 검증만 하고 싶다"는 요구가 실사용에서
나온 증거를 찾지 못했다** — 로드맵 문서(#3719)·이슈 트래커·기존 PR 스레드 어디에도 그런 요청 사례가
확인되지 않는다(확인되지 않음: 별도 사용자/에이전트 요청 이력).

## 3. 판정

**별도 `hwp_doc_verify` 도구는 만들지 않는다.**

- `hwp_doc_save{verify:true}` 가 L5-P2 계약(#3702, PR #3705)을 이미 세션 경로에 배선해 두었고
  (`src/mcp_serve.rs:1394-1405`), 이는 로드맵 §3-3 이 스스로 명시한 "선점" 상태와 일치한다.
- "저장 없이 검증만"이라는 요구가 성립하려면 그래도 직렬화 왕복이 필요해 로직 이득이 없고,
  "편집 단계마다 검증"이라는 요구는 L4 계획 실행기의 설계와 겹친다.
- 불변식 §4-3 "새 로직 금지" — 상위 층은 검증된 코어 함수를 재사용해야 하는데, `hwp_doc_verify`
  를 새로 만들면 `edit_verify_report` 호출부가 두 곳(저장 경로 + 신규 도구)으로 갈라져
  판정 로직이 이원화될 위험이 있다. 현재 상태(저장에 종속)가 이 불변식에 더 부합한다.

## 4. 재검토 조건

다음 신호가 실제로 관측되면 재검토한다:

- 세션 편집 워크플로에서 "저장 직전 매번 verify 를 걸었더니 저장 I/O 비용이 체감될 만큼 크다"는
  실측 보고가 나올 때 (현재는 verify 자체가 이미 옵트인이라 비용은 사용자가 선택한다)
- 계획 실행기(L4)로 표현할 수 없는 대화형·장기 세션 워크플로가 실제로 등장해, "여러 세션 호출
  사이사이 확정 없이 유효성만 반복 확인"하는 수요가 이슈로 접수될 때
