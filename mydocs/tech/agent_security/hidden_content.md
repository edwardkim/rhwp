# 은닉 콘텐츠 — 사람은 못 보는데 에이전트는 읽는 텍스트

> 위협 ID 는 [위협 모델](threat_model.md)의 **T2(은닉 텍스트)** · **T4(표면마다 다른
> 문서)** 를 따른다. 여기 실린 신호가 실제 규칙이 되는 과정은
> [탐지·오탐 정책](detection_policy.md), 벡터의 내용물은
> [간접 프롬프트 인젝션](indirect_prompt_injection.md), 구현 이슈는
> [#3787](https://github.com/edwardkim/rhwp/issues/3787).
>
> 모든 주장에 코드 경로(`파일:줄`) 또는 실제 명령 출력을 붙였다. 근거를 대지 못한
> 항목은 **"확인되지 않음"** 으로 남겼다.

---

## 0. 이 문서의 논지

### 0.1 은닉이 가장 악질인 이유

간접 인젝션의 다른 벡터에는 **최후의 방어선**이 하나 남아 있다. 사용자가 문서를
열어 본다는 것. 본문에 대놓고 "이전 지시를 무시하고…"라고 적혀 있으면 사람이 본다.

은닉은 그 방어선을 없앤다.

> 사용자가 문서를 연다 → 이상 없다 → 에이전트에게 넘긴다 → **에이전트는 다른 걸 읽는다.**

사용자는 자기가 검토한 문서와 에이전트가 처리한 문서가 같다고 믿는다. 실제로는
다르다. 그리고 사용자는 그 차이를 **끝까지 모른다** — 결과가 이상해도 원인을 찾을
곳이 없다. 자기가 읽은 문서에는 그런 내용이 없으니까.

### 0.2 그리고 rhwp 만 이걸 잡을 수 있다

평범한 텍스트 추출기는 **흰 글씨인지 모른다.** 글자를 꺼내는 것과 그 글자가
화면에서 보이는지 판정하는 것은 다른 일이다. 후자는 **조판·서식 엔진**이 있어야
한다.

| 도구 부류 | 글자를 꺼낸다 | 색을 안다 | 좌표를 안다 | 겹침을 안다 | 은닉 판정 |
| --- | --- | --- | --- | --- | --- |
| 텍스트 추출기 (문자열 스캔) | ○ | × | × | × | **불가** |
| 포맷 파서 (IR 까지) | ○ | ○ | × | × | 부분 |
| **조판 엔진 (rhwp)** | ○ | ○ | ○ | ○ | **가능** |

rhwp 는 파서와 렌더러를 둘 다 갖는다. `CharShape` 에서 색과 크기를 알고
(`src/model/style.rs:100`~), 레이아웃 결과에서 **실제로 어디에 놓였는지**를 안다
(`export-render-tree`). 이 조합은 rhwp 의 우연한 부산물이 아니라 **구조적 우위**다.
문서를 정확히 그릴 수 있는 프로그램만이 "이건 안 보인다"를 말할 자격이 있다.

이 우위를 쓰지 않으면 rhwp 는 그냥 정확한 배달부다([간접 인젝션](indirect_prompt_injection.md) §1).

### 0.3 그러나 자격이 곧 능력은 아니다

§3 부터 실측으로 보이겠지만, **지금 그 정보를 봉투로 꺼내는 표면이 없다.**
`export-render-tree` 는 좌표를 주지만 색이 없고, 색을 주는 CLI 표면은 아예 없다.
"할 수 있다"와 "하고 있다"는 다르다. 이 문서는 그 간격도 함께 적는다.

## 1. 두 개의 눈 — 무엇이 어긋나는가

같은 파일을 두 갈래로 본다.

| | **사람의 눈** | **에이전트의 눈** |
| --- | --- | --- |
| 경로 | `export-svg` / `export-pdf` / `hwp_doc_render_page` / 한컴 오피스 | `export-text` / `digest` / `export-markdown` / `fields` |
| 거치는 것 | 조판 → 색 합성 → 래스터 | 문자 열거 |
| 색을 반영하는가 | **한다** | 안 한다 |
| 좌표를 반영하는가 | **한다** | 안 한다 |
| 가려짐을 반영하는가 | **한다** | 안 한다 |
| 각주·필드 메모 | 위치에 따라 다름 | **전부 평탄화** |

**은닉이란 이 두 눈의 차이를 공격자가 조종하는 것**이다. 그러므로 탐지의 정의도
여기서 나온다: *렌더 결과에 기여하지 않는데 텍스트 축에는 실리는 문자열.*

### 1.1 실측 — 차이는 이미 존재한다

특별한 조작 없이도 두 눈은 이미 다르다.

```bash
# 각주에만 있는 낱말
./target/release/rhwp.exe search      "samples/2010-01-06.hwp" "임대료" --json  # matchCount 0
./target/release/rhwp.exe export-text "samples/2010-01-06.hwp" -p 0 --json     # 각주 전문 포함
./target/release/rhwp.exe digest      "samples/2010-01-06.hwp" --json          # excerpt 에 각주 전문 포함
```

`export-text -p 0` 결과의 말미에는 각주 본문이 그대로 붙는다
(`… ․세외수입 : 임대료, 이자수입, 수수료, … / 5) 순 융 자 : 융자지출 - 융자회수`).
같은 문자열을 `search` 로는 **한 건도** 찾을 수 없다.

→ **검사한 표면과 소비한 표면이 다르면 검사는 무효다.** 이 원칙이 이 문서 전체를
관통한다.

## 2. 어디를 봐야 하나 — 구현자가 가장 많이 헤매는 지점

**이 절을 먼저 읽지 않으면 구현이 반드시 막힌다.**

### 2.1 render tree 에는 색이 없다

`export-render-tree` 의 JSON 노드는 다음 키만 갖는다. 직렬화 코드를 직접 확인했다
(`src/renderer/render_tree.rs:186`~`268`, `write_json`).

```
{ "type", "bbox": {x, y, w, h}, "children": [...] }
```

노드 종류별 추가 키는 다음이 전부다.

| 노드 | 추가 키 | 코드 |
| --- | --- | --- |
| `TextRun` | `text`, `pi`, (선택) `displayText` | `render_tree.rs:204`~`219` |
| `TextLine` | `pi` | `render_tree.rs:200` |
| `Table` | `rows`, `cols`, `pi`, `ci` | `render_tree.rs:221` |
| `Cell` | `row`, `col` | `render_tree.rs:234` |
| `Column` | `col` | `render_tree.rs:196` |

실제 산출물로도 교차 확인했다.

```bash
./target/release/rhwp.exe export-render-tree "samples/2010-01-06.hwp" -p 0 -o out/
# 전 노드 키 합집합:
#   bbox, children, ci, col, cols, h, pi, row, rows, text, type, w, x, y
```

**색·글자크기·투명도·z-order 가 전부 없다.** `Image` 노드는 `bbox` 만 갖고
`Rect`·`Line` 도 마찬가지다. 렌더 트리는 **레이아웃 시각 분석용**으로 설계됐고
(`--help`: "페이지별 render tree bbox JSON을 내보내기 (레이아웃 시각 분석용)")
페인트 속성은 애초에 대상이 아니었다.

### 2.2 그러므로 판정은 두 축으로 갈라진다

| 판정할 것 | 봐야 할 곳 | 못 보는 곳 |
| --- | --- | --- |
| 글자색 · 음영 · 글자 크기 | **`CharShape`** (`src/model/style.rs:100`~) | render tree |
| 좌표 · 페이지 이탈 · bbox 겹침 | **render tree `bbox`** | CharShape |
| 배경색 | `BorderFill`(`style.rs:459`) → `Fill`(`style.rs:607`) → `SolidFill.background_color`(`style.rs:635`) | 둘 다 직접은 아님 |
| 그리는 순서 | `CommonObjAttr.z_order`(`src/model/shape.rs:45`) | render tree JSON |

**색 판정은 CharShape, 좌표 판정만 bbox.** 두 축을 한 자료구조에서 얻으려다
막히는 것이 이 영역의 첫 함정이다. 둘을 잇는 열쇠는 `TextRun.pi`(문단 인덱스)이며,
문단 → 문자 모양 매핑은 IR 쪽에서 따로 해소해야 한다.

### 2.3 CharShape 에 실제로 있는 것

`src/model/style.rs:100` `pub struct CharShape` 에서 이 문서에 필요한 필드만 추린다.

| 필드 | 타입 | 주석에 적힌 범위 | 쓰임 |
| --- | --- | --- | --- |
| `text_color` | `ColorRef` | — | 글자 색 |
| `shade_color` | `ColorRef` | — | 글자 음영 색 |
| `underline_color`·`strike_color`·`shadow_color` | `ColorRef` | — | 부수 요소 색 |
| `base_size` | `i32` | HWPUNIT, 0pt~4096pt | 기준 크기 |
| `relative_sizes` | `[u8; 7]` | 언어별 10 %~250 % | 상대 크기 |
| `ratios` | `[u8; 7]` | 50 %~200 % | 장평 |
| `border_fill_id` | `u16` | — | 글자 테두리/배경 ID |

### 2.4 `ColorRef` 의 표현 — 여기서 "auto/inherit" 질문이 갈린다

```rust
/// RGB 색상 값 (0x00BBGGRR 형식)
pub type ColorRef = u32;                 // src/model/mod.rs:31
```

값의 의미는 파서에서 확정된다(`src/parser/hwpx/utils.rs:89`~).

| 원본 | 저장값 | 의미 |
| --- | --- | --- |
| `#FFFFFF` | `0x00FFFFFF` | 불투명 흰색 |
| `#000000` | `0x00000000` | 불투명 검정 |
| `"none"` 또는 빈 문자열 | `0xFFFFFFFF` | **투명/없음** (`utils.rs:90`~`92`) |
| `#AARRGGBB` | `0xAABBGGRR` | 알파 보존 |

상위(알파) 바이트가 0 이 아니면 "채우기 없음"으로 읽는다
(`utils.rs:197` 테스트: `#FF000000` → 상위 바이트 비제로 → 채우기 없음).

**결론: rhwp 는 "흰색"과 "지정 없음"을 구별할 수 있다.** `0x00FFFFFF` 와
`0xFFFFFFFF` 는 다른 값이다. 그러나 **구별할 수 있다는 것과 상속을 해소했다는 것은
다르다.** `0xFFFFFFFF`(없음)인 `CharShape` 가 실제로 화면에 어떤 색으로 그려지는지는
상위 스타일에서 내려온다 — 그 해소 경로가 전 경우에 대해 검증됐는지는
**확인되지 않음**이다. 그래서 §5.1 은 "지정 없음"을 배경과 같다고 단정하지 않는다.

### 2.5 `relative_sizes` — 코디네이터 전제와 실제 구현이 다르다

스펙 수준에서 실효 글자 크기는 `base_size × relative_size / 100` 이다. **그러나
rhwp 렌더러는 이 곱을 하지 않는다.**

```rust
// src/renderer/style_resolver.rs:339-341
fn resolve_single_char_style(cs: &CharShape, doc_info: &DocInfo, dpi: f64) -> ResolvedCharStyle {
    // base_size는 HWPUNIT 단위
    let font_size = hwpunit_to_px(cs.base_size, dpi);
```

같은 함수가 `ratios`(장평)와 `spacings`(자간)는 반영하지만
(`style_resolver.rs:350`~`356`), `relative_sizes` 는 읽지 않는다. 전수 확인:

```
src/ 전체에서 relative_sizes 를 참조하는 곳
  파서   : doc_info.rs:542(HWP5) · hwpx/header.rs:675-681 · hml/reader.rs:637
  모델   : style.rs:110 · 170(PartialEq) · 743 · 845
  직렬화 : serializer/doc_info/tests.rs:189
  편집   : document_core/commands/formatting.rs (JSON 통과)
  렌더러 : 없음
```

**즉 `relative_sizes` 는 왕복 보존만 되고 조판에 반영되지 않는다.** 이 사실이
탐지에 갖는 의미는 둘이다.

1. `relative_sizes = 10` 으로 글자를 10 % 로 줄인 문서는 **한컴에서는 작게 보이고
   rhwp 렌더에서는 원래 크기로 보인다.** rhwp 의 렌더 결과를 사람 눈의 기준으로
   삼는 판정은 이 경우 어긋난다.
2. 그러므로 `relative_sizes` 기반 판정은 **렌더 트리와 대조할 수 없고** CharShape
   값만으로 해야 한다. 대조 불가는 곧 오탐 위험이다.

단위 관계는 다음과 같다.

```
HWPUNIT_PER_INCH = 7200.0            // src/renderer/mod.rs:633
font_size_px = base_size * dpi / 7200
1 pt = 100 HWPUNIT                   // style_resolver.rs:1022 주석 "24pt = 2400 HWPUNIT"
```

## 3. 은닉 수단 카탈로그

각 수단을 **수단 / 사람이 보는 것 / 추출기가 읽는 것 / 탐지 근거 / 현재 상태**로 적는다.

공격 예시는 개념 수준으로만 적는다 — 어떤 속성을 어떤 값으로 두면 성립하는지까지는
적되, 그대로 열면 되는 파일을 만들어 주지는 않는다. 실제 표본은
[악성 코퍼스](test_corpus.md)가 픽스처로 관리한다.

---

### H1 — 글자색 == 배경색

| | |
| --- | --- |
| **수단** | `charPr@textColor` 를 배경과 같은 값으로. 흰 종이 위 흰 글씨가 전형 |
| **사람이 보는 것** | 아무것도 없다. 빈 줄로 보인다 |
| **추출기가 읽는 것** | 문자열 전문. `export-text`·`digest`·`markdown` 모두 그대로 |
| **탐지 근거** | `CharShape.text_color`(`style.rs`) vs 배경. HWPX 매핑은 `parser/hwpx/header.rs:595` `b"textColor" => cs.text_color = parse_color(&attr)` |
| **현재 상태** | 판정 가능하나 **봉투로 꺼내는 표면 없음** |

**심는 법**: 글자 모양 하나를 흰색으로 정의하고 그 모양을 문단에 건다. 워드프로세서
UI 만으로 가능하며 특수 도구가 필요 없다. 문서 끝의 빈 페이지, 표 아래 여백처럼
사람이 스크롤을 멈추지 않는 곳에 놓는다.

**왜 잘 통하는가**: 검토자는 **보이는 것**을 검토한다. 인쇄해도 안 나온다. PDF 로
바꿔도 안 보인다(글자는 남지만 흰색이다). 사용자가 할 수 있는 모든 육안 검증을
통과한다.

**탐지의 실측 — 여기가 이 항목의 핵심이다**

```bash
# samples/*.hwpx 60건의 header.xml 안 <hh:charPr> 전수
# → charPr 4,298개
```

| 관측 | 값 |
| --- | --- |
| `textColor="#FFFFFF"` 인 charPr | **56개** |
| 그 charPr 이 있는 문서 | **11개 / 60 (18.3 %)** |
| 그중 `shadeColor` 값 | **전부 `"none"` (56/56)** |
| 그 charPr 의 `borderFillIDRef` | 대부분 보유 (예: `id="5" height="1000" textColor="#FFFFFF" shadeColor="none" … borderFillIDRef="3"`) |

**정상 문서 5건 중 1건에 흰 글자 정의가 있다.** 어두운 표 머리행에 흰 글씨를 쓰는
것은 한국 공문서 표의 표준 스타일이다. 즉:

> **"흰 글씨" 단독으로는 규칙을 만들 수 없다. 18.3 % 오탐이다.**

배경을 알아야 한다. 그리고 배경은 `shade_color` 에 없다(전부 `none`). 실제 배경은
`borderFillIDRef` → `BorderFill.fill.solid.background_color`(`style.rs:635`)와
셀·문단·개체·쪽 배경에 흩어져 있다. 판정 규칙은 **글자색 == 유효 배경색**이지
**글자색 == 흰색**이 아니다. 유효 배경의 해소는 §5.1 의 한계로 이어진다.

---

### H2 — 극소·0 크기 글자

| | |
| --- | --- |
| **수단** | `charPr@height`(→ `CharShape.base_size`)를 아주 작게. 또는 `relSz`(→ `relative_sizes`)를 최소값으로 |
| **사람이 보는 것** | 점 하나 또는 아무것도 아닌 얼룩 |
| **추출기가 읽는 것** | 문자열 전문. 크기는 텍스트 축에 전혀 반영되지 않는다 |
| **탐지 근거** | `CharShape.base_size` (HWPUNIT). HWPX 매핑 `parser/hwpx/header.rs:594` `b"height" => cs.base_size = parse_i32(&attr)` |
| **현재 상태** | 판정 가능·오탐 낮음. **단 `relative_sizes` 경로는 렌더와 대조 불가**(§2.5) |

**심는 법**: 글자 모양의 크기를 최소로 두고 그 모양으로 한 문단을 쓴다. 줄 간격까지
줄이면 한 줄의 흔적조차 남지 않는다.

**왜 잘 통하는가**: H1 과 같은 이유에 하나가 더 붙는다 — **확대해도 잘 안 보인다.**
흰 글씨는 드래그 선택하면 반전돼 드러나지만, 0.1pt 글자는 선택해도 여전히 점이다.

**탐지의 실측**

같은 60개 HWPX / 4,298 charPr 의 `height`(HWPUNIT) 분포:

| 통계 | 값 | 환산 |
| --- | --- | --- |
| 최소 | **100** | 1 pt |
| 1 퍼센타일 | 200 | 2 pt |
| 중앙값 | 1,000 | 10 pt |
| 최대 | 58,000 | 580 pt |
| **100 미만** | **0건 (0.0 %)** | — |

정상 문서에서 관측된 최소 글자는 정확히 **1pt** 이고, 그 아래는 한 건도 없다.
→ `base_size < 100`(1pt 미만)은 **이 코퍼스에서 오탐 0** 인 임계값이다.
`base_size ≤ 200`(2pt 이하)까지 넓히면 정상 1pt 사용을 건드린다.

`relative_sizes` 는 다르다. 같은 코퍼스에서 **100 이외의 값이 한 건도 없다
(0건 / 0.0 %)**. 오탐은 0 이지만 정탐 근거도 없다 — 이 축은 "이론적으로 가능하고
실측 기준선이 0" 인 상태다. 게다가 렌더러가 안 읽으므로(§2.5) 렌더 대조로 확증할
수도 없다. **낮은 신뢰도로만 쓸 수 있다.**

### H3 — 쪽 경계 밖 배치

| | |
| --- | --- |
| **수단** | 개체(글상자·그림)를 음수 좌표나 용지 밖으로 이동 |
| **사람이 보는 것** | 없다. 화면·인쇄 모두 잘린다 |
| **추출기가 읽는 것** | 개체 안 텍스트 전문 |
| **탐지 근거** | render tree `bbox` vs `Page` 노드 `bbox`. **좌표는 여기서만 나온다**(§2.1) |
| **현재 상태** | 판정 가능. **임계값 설정이 전부** |

**심는 법**: 개체 위치를 쪽 기준·음수 오프셋으로 준다. `treat_as_char`(글자처럼
취급)를 끄면 개체는 본문 흐름과 독립적으로 배치되므로 임의 좌표가 가능하다
(`CommonObjAttr.treat_as_char`, `src/model/shape.rs`).

**왜 잘 통하는가**: 편집기에서 스크롤해도 용지 밖은 회색 여백이라 눈에 안 띈다.
개체 목록을 열어 하나씩 확인하지 않는 한 존재 자체를 모른다.

**탐지의 실측 — 임계값이 없으면 무너진다**

```bash
# samples 앞 30건의 0쪽 render tree, 총 26개 문서 / 8,227개 노드
# Page 노드의 bbox 를 용지로 삼아 자식 노드 bbox 를 비교
```

| 판정 기준 | 적중 노드 | 적중 문서 | 비율 |
| --- | --- | --- | --- |
| bbox 가 용지를 **0.5pt 넘게 벗어남** | 36 | 23 | **88.5 %** |
| bbox 가 용지와 **전혀 겹치지 않음** (완전 이탈) | **0** | **0** | **0.0 %** |

**"경계를 벗어남"으로 규칙을 만들면 정상 문서 9건 중 8건이 걸린다.** 벗어난 36건은
`TextRun` 31 · `Image` 5 이며, 전부 10pt 이상 삐져나오지만 **용지와는 겹친다** —
표가 오른쪽 여백을 넘거나 그림이 아래쪽으로 흐른 정상적 조판이다.

반면 **완전 이탈은 0건**이다. 이것이 임계값의 실측 답이다.

> 판정은 "벗어남"이 아니라 **"교차 없음"** 이어야 한다.

주의: 폭·높이가 0 인 노드(줄·빈 런)가 있으므로 **면적 교차로 판정하면 안 된다.**
면적으로 재면 322개 노드 / 22개 문서가 "완전 이탈"로 잘못 잡힌다(직접 겪었다).
**구간 겹침**으로 판정해야 한다.

### H4 — 다른 개체에 가려짐 (z-order)

| | |
| --- | --- |
| **수단** | 텍스트 개체를 놓고 그 위에 불투명한 개체·그림을 덮는다 |
| **사람이 보는 것** | 위에 있는 개체만 |
| **추출기가 읽는 것** | 아래 텍스트도 전문 |
| **탐지 근거** | bbox 겹침 + 그리는 순서. **그런데 순서가 render tree JSON 에 없다** |
| **현재 상태** | **부분적** — 겹침은 알 수 있고 위아래는 간접 추론만 |

**심는 법**: 텍스트를 담은 개체 위에 같은 크기의 채워진 사각형이나 그림을 겹치고
z-order 를 위로 올린다. `TextWrap` 을 `InFrontOfText`/`BehindText` 로 조합하면
본문과의 관계까지 조종할 수 있다(`src/model/shape.rs:193`~`201`).

**왜 잘 통하는가**: 화면에서 완전히 정상으로 보인다. 그림 한 장이 있을 뿐이다.
그림을 옮겨 보지 않는 한 아래에 무엇이 있는지 알 방법이 없다.

**탐지 근거의 정확한 상태**

- 모델에는 있다: `CommonObjAttr.z_order: i32` (`src/model/shape.rs:45`)
- 레이아웃이 쓴다: `src/renderer/layout.rs:1630` 이 `common.z_order` 로 정렬하고,
  회귀 테스트가 순서를 못박는다 — `tests.rs:1905`
  `task1197_paper_nodes_sort_by_plane_z_order_and_stable_index`,
  단언 문구는 "BehindText는 z-order/stable 순서로 먼저, flow, InFrontOfText 순으로
  정렬"(`src/renderer/layout/tests.rs:1929`)
- **render tree JSON 에는 없다**(§2.1 전수 확인)

따라서 JSON 소비자가 쓸 수 있는 정보는 **형제 노드의 배열 순서**뿐이다. 위 테스트가
보증하는 정렬 규약 덕분에 순서는 그리는 순서를 반영하지만, 이건 **간접 추론**이지
명시적 z 값이 아니다. 그리고 결정적으로:

> **덮는 개체가 불투명한지 알 수 없다.** `Fill.alpha`(`style.rs:617`,
> "0=완전투명/미설정, 255=불투명")와 `FillType`(`style.rs:622`)은 IR 에 있으나
> render tree 에는 없다. 반투명 도형은 아래 글자를 가리지 않는다.

→ bbox 겹침만으로 "가려짐"을 선언하면 오탐이 크다. 표 위의 투명 도형, 배경 무늬,
워터마크가 전부 걸린다. **이 항목은 현재 신뢰할 만한 자동 판정 대상이 아니다.**

### H5 — 숨김 속성 개체

| | |
| --- | --- |
| **수단** | 개체에 "숨김" 속성을 주어 화면에서 제외 |
| **사람이 보는 것** | (해당한다면) 없다 |
| **추출기가 읽는 것** | (해당한다면) 전문 |
| **탐지 근거** | **확인되지 않음** |
| **현재 상태** | **판정 불가** |

`CommonObjAttr`(`src/model/shape.rs:30`~)를 전부 읽었다. 필드는
`ctrl_id`·`attr`·`vertical_offset`·`horizontal_offset`·`width`·`height`·`z_order`·
`margin`·`instance_id`·`prevent_page_break`·`treat_as_char`·`flow_with_text`·
`allow_overlap`·`affect_line_spacing` 등이며, **가시성 플래그가 없다.**

`src/model/` 전체에서 `visible` 필드는 단 하나, 차트 범례의
`Legend.visible`(`src/model/shape.rs:746`)뿐이다. 개체 일반의 숨김 속성이 아니다.

정리:

- HWP/HWPX 포맷 자체에 개체 숨김 속성이 있는지 — **확인되지 않음**
- 있다면 `CommonObjAttr.attr` 비트 어딘가에 있을 수 있으나, 어느 비트인지 —
  **확인되지 않음**
- 현재 rhwp IR 로는 **판정 불가**. 못 잡는다.

추측으로 비트 번호를 적지 않는다. 근거 없는 비트 번호는 반년 뒤 잘못된 구현의
원인이 된다.

### H6 — 각주·미주 (본문만 보는 사람은 놓친다)

| | |
| --- | --- |
| **수단** | 페이로드를 각주·미주 본문에 넣는다 |
| **사람이 보는 것** | 쪽 아래 작은 글씨. **읽지 않는다** |
| **추출기가 읽는 것** | 본문과 **구별 없이** 같은 문자열에 이어붙는다 |
| **탐지 근거** | 렌더 트리에 `FootnoteArea`·`FnMarker` 노드가 있다 |
| **현재 상태** | **표면 간 비대칭이 실측됨. 구조적 문제** |

**심는 법**: 각주를 하나 달고 본문에 지시를 쓴다. 서식 조작이 전혀 필요 없다 —
**정상 기능만 쓴다.** 여기에 H1(흰 글씨)이나 H2(극소 글자)를 겹치면 각주 영역
자체가 시각적으로 사라진다.

**왜 잘 통하는가**: 이건 은닉이라기보다 **주의력 공격**이다. 각주는 "읽지 않아도
되는 것"이라는 사회적 합의가 있다. 사용자는 각주를 보고도 검토했다고 생각한다.
그리고 §1.1 에서 잰 것처럼 **검사 도구도 각주를 안 본다.**

**실측된 비대칭**

| 표면 | 각주 텍스트 | 근거 |
| --- | --- | --- |
| `export-text` | **포함** | `samples/2010-01-06.hwp -p 0` 결과 말미에 각주 5개 전문 |
| `digest` | **포함** | `excerpt` 에 동일 문자열 |
| `search` | **미포함** | `"임대료"` → `matchCount: 0` |
| `export-render-tree` | 별도 노드 | `FootnoteArea` → `TextRun` |

대조군: `"통합재정수지"`(본문) 12건, `"자본지출"`(본문+각주) 6건 — `search` 는
정상 동작 중이며 각주만 범위 밖이다.

이 비대칭이 만드는 실패 시나리오는 명확하다. 방어자가 `search` 로 의심 문자열을
훑어 "깨끗함"을 확인하고 `export-text` 로 모델에 넘긴다. 검사는 통과하고 페이로드는
전달된다.

`search` 가 각주를 제외하는 것이 의도인지 결함인지는 **확인되지 않음** — 코드
주석에서 근거를 못 찾았다. 다만 **보안 관점의 요구는 분명하다**: 어떤 표면이 무엇을
포함하는지 봉투가 밝혀야 한다.

### H7 — 누름틀 안내문·메모 (화면과 봉투가 다른 문서를 준다)

코디네이터의 질문("화면엔 채워진 값, 내부엔 다른 값?")에 실측으로 답한다.

`samples/field-01-memo.hwp` 로 두 표면을 나란히 봤다.

```bash
./target/release/rhwp.exe export-text "samples/field-01-memo.hwp" --json
# 0쪽 텍스트: "… 회사명\t\t: 여기에 입력 / 작성자\t\t: 여기에 입력 …"

./target/release/rhwp.exe fields "samples/field-01-memo.hwp" --json
# fieldCount 11, 첫 필드:
#   "name":"회사명", "guide":"여기에 입력", "value":"",
#   "memo":"회사명은 회사이름입니다. 반드시 거래업체 등록된 정식 명칭을 사용해야 합니다.",
#   "command":"Clickhere:set:92:Direction:wstring:6:여기에 입력 HelpState:wstring:43:회사명은 …"
```

| 값 | 화면에 보이는가 | `export-text` | `fields --json` |
| --- | --- | --- | --- |
| `value` (현재값) | 채워졌으면 보인다 | 포함 | 포함 |
| `guide` (안내문 / `Direction`) | 비었을 때 보인다 | **포함** | 포함 |
| `memo` (지시문 / `HelpState`) | **보이지 않는다** | **미포함** | **포함** |
| `command` (원문) | 보이지 않는다 | 미포함 | **포함** |

**확정된 사실**: `memo`(`HelpState`)는 쪽 위에 렌더되지 않는데 `fields --json` 봉투에는
전문이 실린다. 한컴에서는 커서가 누름틀에 들어갈 때만 보조 표시로 나타난다.
문서를 훑어본 사용자는 이 문자열을 **한 번도 보지 않는다.**

그리고 실측된 `memo` 값은 `"반드시 … 사용해야 합니다"` — **당위 명령형**이다.
정상 문서에서도 이 칸은 원래 지시를 담는다. 즉 이 칸에 들어간 인젝션은 어투상
정상값과 구별되지 않는다([간접 인젝션](indirect_prompt_injection.md) V4·V8).

`command` 필드는 더하다. `Direction`·`HelpState` 를 담은 한컴 원문 문자열이 그대로
봉투에 들어간다(`src/model/control.rs:299`~`301` 의 형식 주석). 파싱된 값과 원문이
**둘 다** 컨텍스트에 실린다.

**부분적으로만 확인된 것 — 화면값과 내부값의 불일치**

`src/model/control.rs` `Field::guide_residue` 주석이 관련 사실을 기록한다.

> 한컴은 미기입 누름틀(`dirty="0"`)의 안내문을 **파일에는 본문 run 으로 유지**하고
> 렌더·인쇄에서만 구분 취급한다. rhwp 는 편집 IR 을 빈 필드로 정규화하므로,
> 저장에서 이 잔재를 되살리지 않으면 파일 차원에서 텍스트가 영구 소실된다.

즉 **파일에는 있는데 값 API 는 빈 값을 주는** 문자열이 존재한다. 이것은 "화면값 ≠
내부값"의 한 방향(파일에 더 있음)을 확인해 준다.

그러나 반대 방향 — **화면에는 값 A 가 보이는데 내부·봉투에는 다른 값 B 가 있는
누름틀** — 은 **확인되지 않음**이다. 만들어 확인하지 못했고, 코드에서 그런 분기를
찾지 못했다. 추측으로 적지 않는다.

## 4. 실측 기준선 — 한 표로

이 문서에서 잰 값의 요약. 재현 절차는 각 항목에 있다.

| 신호 | 코퍼스 | 정상 문서 적중 | 판정 |
| --- | --- | --- | --- |
| 흰 글자색 정의 존재 | HWPX 60건 / charPr 4,298 | **11건 (18.3 %)** | 단독 사용 불가 |
| `base_size < 100` (1pt 미만) | 동일 | **0건 (0.0 %)** | 사용 가능 |
| `relative_sizes ≠ 100` | 동일 | **0건 (0.0 %)** | 정탐 근거 없음, 낮은 신뢰도 |
| bbox 가 용지를 0.5pt 초과 이탈 | 문서 26 / 노드 8,227 | **23건 (88.5 %)** | 사용 불가 |
| bbox 가 용지와 교차 없음 | 동일 | **0건 (0.0 %)** | 사용 가능 |
| 각주 텍스트 존재 | — | 사실상 전건 | 신호 아님. **표면 표시**의 문제 |
| 누름틀 `memo` 비어 있지 않음 | — | 흔함 (정상 서식의 기본 기능) | 신호 아님. **표시 대상** |

**패턴이 보인다.** 은닉 신호는 대부분 "존재 여부"로는 못 쓰고 **"정상 범위를 벗어난
정도"** 로만 쓸 수 있다. 그리고 정상 범위는 코퍼스에서 재야 알 수 있다.

## 5. 탐지의 한계 — 못 잡는 것을 못 잡는다고 적는다

과장은 보안 문서의 가장 흔한 실패다([README](README.md) "보장하지 않는 것").

### 5.1 배경을 모르면 색 판정은 성립하지 않는다

**흰 글씨라도 배경이 어두우면 보인다.** 그리고 §H1 실측대로 이건 예외가 아니라
**정상 문서 18.3 %** 의 일상이다.

유효 배경을 알려면 여러 층을 합성해야 한다.

| 층 | 어디에 있나 |
| --- | --- |
| 글자 배경 | `CharShape.border_fill_id` → `BorderFill.fill`(`style.rs:471`) |
| 글자 음영 | `CharShape.shade_color` — 실측상 흰 글자 56건 전부 `none` |
| 표 셀 채우기 | 셀의 `BorderFill` |
| 문단 배경 | 문단 모양 쪽 |
| 개체 채우기 | 개체의 `Fill`(`FillType`·`alpha`, `style.rs:607`~`619`) |
| 쪽 배경 | `PageBackground` 노드 (render tree 에 `PageBg` 로 나오나 색은 없다) |

이 합성은 **조판 엔진이 실제로 그릴 때 하는 일**이다. 지금 그 결과를 문자 단위로
꺼내는 경로가 없다. 그래서:

- **잡지 않는 케이스**: 배경 층을 확정할 수 없는 문자. 특히 개체 안 텍스트,
  중첩 표 안 셀, 배경 그림 위 텍스트.
- 판정 가능한 범위는 **배경 층이 단일하고 확정적인 경우**(쪽 배경 = 기본 흰색,
  글자·문단·셀 배경 모두 미지정)로 좁혀야 한다.

### 5.2 "지정 없음"을 배경과 같다고 단정하지 않는다

§2.4 대로 `0xFFFFFFFF`(투명/없음)와 `0x00FFFFFF`(흰색)는 구별된다. 그러나 "없음"인
글자가 실제로 무슨 색으로 그려지는지는 상속 해소의 결과이고, 그 해소가 모든 경로에서
검증됐는지는 **확인되지 않음**이다.

→ **`text_color` 가 "없음"인 문자는 판정하지 않는다.** 판정 불가를 "깨끗함"으로
보고하지 않는다. 이 원칙은 저장소에 선례가 있다 — `capabilities` 의
`jsonContract.textSecurity` 선언 주석(`src/main.rs:1577`~`1579`):

> 이 키가 있으면 바이너리가 검사한다는 뜻이다 — **키가 없으면 '깨끗함'이 아니라
> '검사하지 않음'으로 읽어야 한다.**

### 5.3 렌더러가 안 읽는 속성은 렌더로 확증할 수 없다

`relative_sizes`(§2.5)가 그렇다. CharShape 값과 rhwp 렌더 결과가 어긋나므로,
"렌더에 안 보이는데 텍스트에는 있다"는 판정 논리를 이 축에 적용할 수 없다.
값만 보고 신고할 수는 있으나 **확증은 불가**다.

### 5.4 불투명도를 모르면 가려짐을 판정할 수 없다

§H4. `Fill.alpha`·`FillType` 이 render tree 에 없어서, bbox 겹침이 실제 가림인지
반투명 통과인지 구별할 수 없다. **가려짐 판정은 현재 신뢰할 수 없다.**

### 5.5 포맷에 있는지도 모르는 것은 판정 대상이 아니다

§H5(숨김 속성 개체). IR 에 필드가 없고 포맷 지원 여부도 확인하지 못했다.
**못 잡는다.**

### 5.6 은닉이 아닌 은닉

각주(H6)와 누름틀 메모(H7)는 **정상 기능**이다. 서식 조작이 없다. "이 문서에는
각주가 있다"는 신호가 될 수 없다 — 거의 모든 공문서에 각주가 있다.

이 축에서 rhwp 가 할 수 있는 일은 탐지가 아니라 **표시**다. 어느 문자열이 본문에서
왔고 어느 것이 각주·메모·필드에서 왔는지 봉투가 밝히면, 소비자가 신뢰 등급을 나눌
수 있다([README](README.md) 계약 ②). 이건 규칙 문제가 아니라 **봉투 스키마 문제**다.

## 6. 구현 노트 (#3787 을 여는 사람에게)

실측하면서 확인한, 구현 전에 알아야 할 사실들.

| # | 사실 | 근거 |
| --- | --- | --- |
| 1 | **render tree 에 색이 없다.** 색 판정을 render tree 로 하려다 막힌다 | `render_tree.rs:186`~`268` |
| 2 | 색은 `CharShape`, 좌표는 `bbox`. 잇는 열쇠는 `TextRun.pi` | §2.2 |
| 3 | **CharShape 를 노출하는 CLI·MCP 표면이 없다.** 실측한 38종 도구 어디에도 색·크기가 없다. 신규 표면이 필요하다 | `tools/list` 실측, `--help` 전수 |
| 4 | 배경은 `CharShape.border_fill_id` → `BorderFill.fill.solid.background_color` 로 갈 수 있다. 이 경로는 존재한다 | `style.rs:459`·`607`·`635` |
| 5 | `shade_color` 는 배경이 아니다. 실측상 흰 글자 56건 전부 `none` | §H1 |
| 6 | bbox 판정은 **면적이 아니라 구간 겹침**으로. 0폭/0높이 노드가 있다 | §H3 |
| 7 | `relative_sizes` 는 렌더러가 안 읽는다. 렌더 대조 불가 | §2.5 |
| 8 | 신호는 **보고만** 한다. 문서를 고치지 않는다 | `text_security.rs` 모듈 주석 "보고만 하고 절대 변형하지 않는다" |
| 9 | 새 의존성을 더하지 않는 선례가 있다 (WASM 크기) | `text_security.rs` "왜 의존성을 더하지 않는가" |
| 10 | 판정 불가는 "깨끗함"이 아니다. 봉투가 검사 여부를 밝혀야 한다 | `main.rs:1577` |

기존 `textSecurity` 봉투(`main.rs:4797` `text_security_value`)가 이 축의 형태
선례다: `status: "clean" | "warning"`, `findings[].{kind, scope, note}`,
`policy: "보고 전용"`. 은닉 신호도 같은 형태를 따르는 편이 소비자에게 일관된다.

## 7. 확인되지 않음

| 항목 | 상태 |
| --- | --- |
| HWP/HWPX 포맷의 **개체 숨김 속성** 존재 여부와 비트 위치 | 확인되지 않음. IR 에 필드 없음 |
| 화면에는 값 A, 봉투에는 값 B 인 **누름틀** 성립 여부 | 확인되지 않음. 반대 방향(`guide_residue`)만 확인 |
| `search` 가 각주를 제외하는 것이 의도인지 결함인지 | 확인되지 않음. 사실만 실측 |
| `export-markdown`·`export-doclang` 의 각주 포함 여부 | 확인되지 않음. `export-text`·`digest` 만 실측 |
| `text_color` 가 "없음"일 때의 상속 해소 경로 전수 | 확인되지 않음 |
| HWP5(바이너리) 경로의 흰 글자 기준선 | 확인되지 않음. HWPX 60건만 측정 (헤더 XML 직접 판독이 가능해서) |
| 각 은닉 수단의 실제 **재현율** | 확인되지 않음. 오탐률만 측정. 정탐 측정은 [악성 코퍼스](test_corpus.md)의 몫 |
| `relative_sizes` 를 실제로 쓰는 문서의 존재 | 확인되지 않음. 60건에서 0건 |
