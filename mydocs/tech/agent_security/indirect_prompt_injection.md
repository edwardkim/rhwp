# 간접 프롬프트 인젝션 — 벡터 카탈로그

> 이 문서는 **문서가 에이전트에게 말을 거는 경로**를 벡터 단위로 분해한다.
> 위협 ID 는 [위협 모델](threat_model.md)의 T1~T8 을 그대로 쓰고, 표면 전수는
> [공격 표면](attack_surface.md), 규칙의 신뢰도 등급 확정은
> [탐지·오탐 정책](detection_policy.md)에 있다. 구현 이슈는
> [#3787](https://github.com/edwardkim/rhwp/issues/3787).
>
> 모든 기술 주장에 코드 경로(`파일:줄`) 또는 실제 명령 출력을 붙였다.
> 근거를 대지 못한 항목은 **"확인되지 않음"** 으로 남겼다.

---

## 0. 공격 예시의 수위 — 이 문서가 지키는 선

방어 규칙을 만들려면 벡터가 **어떤 모양인지** 알아야 한다. 그러나 그대로 복사해
쓸 수 있는 완성 문자열을 나열하면 이 문서는 카탈로그가 아니라 공격 키트가 된다.

그래서 이 문서는 다음 규칙을 지킨다.

| 적는다 | 적지 않는다 |
| --- | --- |
| 벡터의 **구조** (어떤 성분이 어떤 순서로 결합하면 성립하는가) | 성분이 전부 채워진 완성 문장 |
| 탐지에 필요한 **앵커 토큰** (`SYSTEM:`, `hwp_` 접두사 등 — 규칙에 직접 들어갈 문자열) | 앵커 뒤에 붙는 설득 본문 |
| 실제 코퍼스에서 잰 **오탐률** | 특정 모델을 뚫었다는 성공률 주장 |
| 왜 속는지에 대한 **메커니즘 설명** | 특정 에이전트 제품을 겨냥한 튜닝 |

예시가 필요한 곳에는 `<역할표지>`, `<명령형 문장>`, `<도구이름>` 같은 자리표시자를
쓴다. 자리표시자를 채우는 일은 독자의 몫이고, 그건 이미 공격자가 아는 일이다.
방어자에게 필요한 것은 **앵커와 결합 규칙**이지 완성품이 아니다.

실제 악성 표본은 코드로만 존재해야 한다 — [악성 코퍼스](test_corpus.md)가 계약
테스트 픽스처로 관리하는 이유다.

## 1. 직접 인젝션과 간접 인젝션은 다른 문제다

이 구분을 세우지 않으면 나머지가 전부 흐려진다.

| | **직접 인젝션** | **간접 인젝션** |
| --- | --- | --- |
| 텍스트가 들어오는 곳 | 사용자가 프롬프트에 직접 입력 | 도구가 가져온 데이터 안 |
| 사용자의 인지 | **안다.** 자기가 썼다 | **모른다.** 문서를 열어봤을 뿐이다 |
| 공격자와 사용자의 관계 | 같은 사람 (사용자가 자기 에이전트를 조작) | **다른 사람.** 사용자는 피해자다 |
| 피해 방향 | 사용자가 자기 정책을 우회 | 제3자가 사용자의 권한을 훔쳐 씀 |
| 방어 지점 | 프롬프트 입력단 | **도구 출력 경계** ← rhwp 가 여기 있다 |
| 사용자 동의 | 있다 (본인이 원함) | **없다** |

직접 인젝션은 사용자가 자기 에이전트의 가드레일을 넘으려는 시도다. 나쁘든 아니든
**사용자 본인의 선택**이다. 간접 인젝션은 다르다. 민원인이 올린 서식, 웹에서 받은
공고문, 상대 기관이 보낸 붙임 파일 — 그 안에 있는 문장이 사용자의 에이전트를
움직인다. 사용자는 문서를 열어 "이상 없네" 하고 넘겼을 뿐이다.

**rhwp 는 후자의 통로다.** rhwp 의 일은 문서 안의 글자를 정확하게 꺼내 주는 것이고,
그 정확함이 곧 공격자의 전달 보장이 된다. 파서가 정확할수록 페이로드도 정확하게
배달된다. 이건 버그가 아니라 rhwp 가 하는 일 자체이며, 그래서 **탐지는 파싱을
고치는 것이 아니라 봉투에 표시를 다는 방식**이어야 한다
([README](README.md) 계약 ①).

### 1.1 왜 "도구 출력"이라는 사실이 방어를 어렵게 만드는가

에이전트 컨텍스트 안에서 도구 결과는 **검증된 사실**의 지위를 갖는다. 사용자 발화는
"요청"이고, 모델 출력은 "추론"이고, 도구 출력은 "관측"이다. 이 위계는 에이전트가
환각을 줄이도록 설계된 것인데, 간접 인젝션은 정확히 그 위계를 탄다.

`{"pages":[{"text":"…"}]}` 안의 문자열은 rhwp 가 만든 것이 아니라 문서가 준 것이다.
그러나 봉투 어디에도 "이 필드는 신뢰할 수 없는 출처"라는 표시가 없다면, 그 구분은
**모델의 판단력에만** 남는다. 판단력은 컨텍스트가 길어질수록 무너진다
([weak_agent_proofing.md](../weak_agent_proofing.md) F5).

봉투가 출처를 밝혀야 한다는 계약 ②가 여기서 나온다.

## 2. 반출 표면 — 무엇이 문서 문자열을 컨텍스트로 옮기는가

MCP 도구 전수를 실측했다.

```bash
# initialize → notifications/initialized → tools/list 를 stdio 로 투입
printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize",…}' \
              '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
              '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' \
  | ./target/release/rhwp.exe mcp-serve
# → tools 배열 길이 38 (rhwp v0.8.2)
```

**38종.** 이 중 문서 문자열을 그대로 에이전트 컨텍스트로 옮기는 도구는 다음과 같다.

| MCP 도구 | CLI | 반출되는 문서 유래 문자열 | 비고 |
| --- | --- | --- | --- |
| `hwp_export_text` | `export-text` | 본문 전문 (쪽 단위) | 가장 넓은 통로 |
| `hwp_digest` | `digest` | 발췌 + 개요 제목 + `nextStep` | 초소형 모델 진입점 |
| `hwp_export_markdown` | `export-markdown` | 본문 전문 (Markdown) | 도구 설명이 "LLM 컨텍스트 입력용"이라 밝힌다 |
| `hwp_export_structure` | `export-structure` | 개요·조문 제목 트리 | 제목만이라 짧다 = 희석이 없다 |
| `hwp_export_tables` | `export-tables` | 표 셀 전문 | 격자 좌표까지 |
| `hwp_search` / `hwp_batch_search` | `search` / `batch search` | 매치 주변 문자열 | 각주 미포함 (§2.1) |
| `hwp_fields` | `fields` | 필드 `name`·`guide`·`memo`·`value` | `memo` 는 화면에 없다 ([hidden_content.md](hidden_content.md) H7) |
| `hwp_export_doclang` | `export-doclang` | 본문 의미 XML | "다운스트림 AI 파이프라인 입력용" |
| `hwp_info` | `info` | 제목·저자 등 메타 | 짧지만 앞쪽에 놓인다 |
| `hwp_doc_text`·`hwp_doc_search`·`hwp_doc_tables`·`hwp_doc_fields` | — | 위와 같음 (세션판) | 핸들 유지 |
| `hwp_batch` | `batch` | 위 축들의 NDJSON 스트림 | 문서 N건이 한 컨텍스트로 |
| `hwp_ir_diff` | `ir-diff` | 차이 항목의 텍스트 조각 | 차이 근처만 |
| — | `export-render-tree` | `TextRun.text` | JSON 노드에 텍스트가 실린다 |

반대편, **에이전트가 디스크·문서를 바꾸는 도구**는 다음과 같다. 인젝션의 목표는
결국 이쪽을 부르게 만드는 것이다.

| MCP 도구 | 효과 |
| --- | --- |
| `hwp_fill_fields`·`hwp_replace_text`·`hwp_set_cell`·`hwp_set_checkbox` | 문서 내용 변경 + 파일 쓰기 |
| `hwp_batch_fill` | 한 번에 N건 생성 |
| `hwp_run_plan` | 선언 계획을 원자 실행 (§3.7) |
| `hwp_doc_replace_text`·`hwp_doc_set_cell`·`hwp_doc_fill_fields` | 세션 메모리 변경 |
| `hwp_doc_save` | 세션 상태를 디스크로 |
| `hwp_convert_hwpx`·`hwp_convert_hwp5`·`hwp_split_document`·`hwp_build_from_ingest`·`hwp_export_*` | 산출물 파일 생성 |

### 2.1 실측 — 표면마다 문서가 다르다

같은 파일인데 표면마다 에이전트가 보는 내용이 다르다. 실측했다.

```bash
# 각주에만 있는 낱말로 두 표면을 비교
./rhwp.exe search "samples/2010-01-06.hwp" "임대료" --json   # → matchCount 0
./rhwp.exe export-text "samples/2010-01-06.hwp" -p 0 --json  # → 본문 말미에 각주 전문 포함
./rhwp.exe digest "samples/2010-01-06.hwp" --json            # → excerpt 에 각주 전문 포함
```

| 낱말 | 위치 | `search` | `export-text` | `digest` |
| --- | --- | --- | --- | --- |
| `임대료` | 각주에만 | **0건** | 포함 | 포함 |
| `자본지출` | 본문 표 + 각주 | 6건 | 포함 | 포함 |
| `통합재정수지` | 본문 | 12건 | 포함 | 포함 |

**`search` 로 문서를 검사한 사람은 각주에 심긴 페이로드를 못 본다. 그런데
`export-text`·`digest` 는 그 페이로드를 모델에 넘긴다.** 이 비대칭은 T4(표면마다
다른 문서)의 실증이며, "검사한 표면과 소비한 표면이 다르면 검사는 무효"라는 원칙의
근거다. 자세한 은닉 경로는 [hidden_content.md](hidden_content.md) H6.

### 2.2 rhwp 자신은 반출 채널이 아니다

실측한 38종 도구 중 **네트워크로 데이터를 보내는 도구는 없다.** 전부 로컬 파일
입출력이다. 이것은 중요한 한계선이다.

- 반출 유도(§3.5)가 성공하려면 **에이전트의 다른 도구**(HTTP·메일·셸)가 필요하다.
- 즉 rhwp 는 **지시의 출처**이지 **전송의 수단**이 아니다.
- 그러나 rhwp 가 파일을 쓴다는 사실은 여전히 남는다. 공유 폴더·동기화 폴더에
  산출물을 떨어뜨리는 것은 네트워크 없이도 성립하는 반출이다(T5 경로 주입).

## 3. 벡터 카탈로그

각 벡터를 네 항목으로 적는다.

1. **심는 법** — 실제 .hwp/.hwpx 에서 가능한 방법
2. **반출 경로** — 어떤 명령이 이것을 컨텍스트로 옮기는가
3. **왜 속는가** — 이 항목이 빠지면 카탈로그가 아니라 나열이다
4. **탐지와 오탐** — 결정론적 규칙으로 잡히는가, 정상 문서에서 헛울리는가

오탐률은 §4 의 실측 코퍼스(117 문서 / 7,293,169자)에서 잰 값이다.

---

### V1 — 역할 위장 (role impersonation)

대화 역할 표지를 본문에 심어, 문서 텍스트가 **대화 기록의 일부**인 것처럼 보이게 한다.

**① 심는 법**
평범한 본문 문단이면 된다. 서식도 필요 없다. 줄 첫머리에 `SYSTEM:` `Assistant:`
`<|im_start|>` `[INST]` `<<SYS>>` 같은 표지를 놓고, 그 아래에 지시문을 잇는다.
[은닉 수단](hidden_content.md)과 결합하면 사람 눈에는 아무것도 안 보인다.

**② 반출 경로**
`export-text` · `export-markdown` · `digest` · `export-doclang` — 줄바꿈을 보존하는
모든 텍스트 축. Markdown 축이 특히 위험하다: 도구 설명이 스스로 "LLM 컨텍스트
입력용"이라고 밝히므로 소비자가 그 출력을 프롬프트에 그대로 이어붙일 확률이 높다.

**③ 왜 속는가**
에이전트의 컨텍스트는 **평평한 토큰 열**이다. "여기부터는 도구 결과"라는 경계는
호스트가 프롬프트로 그려 넣은 관습일 뿐, 모델 내부에 구조적 장벽이 있는 것이 아니다.
훈련 데이터에서 `SYSTEM:` 은 **가장 권위 있는 발화의 표지**로 반복 학습됐다. 그래서
도구 결과 안의 `SYSTEM:` 은 "누가 말했나"라는 물음을 만들지 않고 "무엇을
지시했나"로 바로 넘어간다. 위계를 존중하도록 훈련된 것이 그대로 취약점이 된다.

**④ 탐지와 오탐**
표지 문자열이 유한하고 짧아서 결정론적 규칙으로 잡힌다. 다만 **어떻게 좁히느냐가
전부**다. 실측(117 문서):

| 규칙 변형 | 오탐 문서 | 오탐률 |
| --- | --- | --- |
| A. 줄머리 `system\|assistant\|user` + `:` | 6 | **5.1 %** |
| B. 역할 표지가 **줄에 단독**으로 놓임 | 0 | **0.0 %** |
| C. 서로 다른 역할 라벨이 한 문서에 **2종 이상** | 0 | **0.0 %** |
| D. 한국어 역할 표지(`시스템:` `어시스턴트:`) | 0 | **0.0 %** |

A 의 오탐 6건은 추측이 아니라 실물이다. `samples/hwp3-sample10-hwp5.hwp` 에는
데이터베이스 로그가 붙어 있고 그 안에 `SYSTEM:  insert into test values` 가 있다.
**Oracle 의 SYSTEM 계정 이름**이지 역할 표지가 아니다. 기술 문서·전산 매뉴얼·감사
보고서에 SQL 덤프를 붙이는 것은 한국 공문서에서 드물지 않다.

→ 규칙 A 는 **낮은 신뢰도**, B·C·D 는 **높은 신뢰도**로 나눈다. 등급의 확정은
[detection_policy.md](detection_policy.md).

### V2 — 지시 무효화 (instruction override)

앞선 모든 지시를 무효로 선언하고 새 지시로 갈아탄다. 가장 오래되고 가장 유명한 형태다.

**① 심는 법**
V1 과 같다. 본문 한 문단. "이전 지시를 무시하고 <명령형 문장>" 구조이며, 한국어·
영어·혼합 모두 성립한다. 실무에서는 V1 과 붙어 다닌다 — 역할을 세운 뒤 그 역할의
권위로 무효화를 선언하는 편이 단독보다 강하다.

**② 반출 경로**
V1 과 동일. 추가로 `export-tables` — 표 셀 안의 긴 문장은 사람이 잘 읽지 않는다.

**③ 왜 속는가**
"최신 지시가 우선"은 대화형 모델의 **정상 동작**이다. 사용자가 마음을 바꾸면
따라야 하니까. 문제는 모델이 "최신"을 **토큰 순서**로 재는데, 도구 결과는 항상
시스템 프롬프트보다 뒤에 온다는 점이다. 도구 결과 안의 무효화 선언은 구조적으로
"더 최신"이다. 게다가 컨텍스트가 길어지면 초기 계획이 밀려나
([weak_agent_proofing.md](../weak_agent_proofing.md) F5) 대조할 원본 자체가 흐려진다.

**④ 탐지와 오탐**
**낱말 단위로는 절대 안 된다.** 실측:

| 토큰 | 등장 문서 | 비율 | 총 출현 |
| --- | --- | --- | --- |
| `무시` | 16 | **13.7 %** | 25 |
| `지시` | 12 | 10.3 % | 181 |
| `확인` | 60 | **51.3 %** | 1,614 |
| `반드시` | 38 | 32.5 % | 285 |

`무시`만으로 규칙을 만들면 **정상 공문서 7건 중 1건**이 걸린다. "법령의 취지를
무시한 처분", "소수점 이하는 무시한다" — 전부 정상 문장이다.

**대상 + 동작이 인접해야 한다.** `(이전|앞|위)의? (모든)? (지시|명령|지침|안내)`
뒤 12자 이내에 `(무시|무효|취소)` 가 오는 형태로 좁히면:

| 좁힌 규칙 | 오탐 문서 | 오탐률 |
| --- | --- | --- |
| 한국어 인접 무효화 | 0 | **0.0 %** |
| `ignore (all) previous/prior/above instructions` | 0 | **0.0 %** |

인접 조건이 오탐률을 13.7 % → 0.0 % 로 떨어뜨린다. 이것이 "규칙을 어디까지
좁혀야 하는가"에 대한 실측 답이다.

### V3 — 도구 지시 (tool-name injection)

본문에 **실존하는 MCP 도구 이름**과 명령형을 함께 심어, 특정 도구 호출을 유도한다.

**① 심는 법**
`tools/list` 로 얻은 이름을 그대로 쓴다. 공개 저장소이므로 공격자도 안다.
실측된 38종 중 부작용이 있는 이름이 표적이다:
`hwp_doc_save` · `hwp_run_plan` · `hwp_replace_text` · `hwp_fill_fields` ·
`hwp_set_cell` · `hwp_batch_fill` · `hwp_split_document` · `hwp_convert_hwp5`.
인자 이름까지 함께 심으면 유도력이 오른다 — 실측한 스키마상
`hwp_doc_save` 는 `docId`·`output`·`verify`, `hwp_run_plan` 은 `plan` 을 받는다.

**② 반출 경로**
텍스트 축 전부. 그러나 이 벡터가 특히 잘 먹히는 곳은 **짧은 봉투**다:
`export-structure`(제목만), `search`(매치 주변만), `fields`(필드 값만). 긴 본문에
섞이면 희석되지만, 제목 하나가 통째로 도구 지시면 희석이 없다.

**③ 왜 속는가**
에이전트의 최대 실패 유형 중 하나가 **없는 이름 환각**이다
([weak_agent_proofing.md](../weak_agent_proofing.md) F1). 그래서 에이전트는 "존재가
확인된 도구 이름"에 강하게 끌린다. 본문에 있는 `hwp_doc_save` 는 자기 `tool_defs`
와 정확히 일치하므로 **환각이 아니라는 확인**으로 읽힌다. 이름이 맞으면 의도도
맞을 것이라는 비약이 여기서 일어난다.

거기에 rhwp 봉투가 원래부터 **다음 호출을 안내하는 필드**를 갖는다는 사실이
겹친다. `digest --json` 의 실측 출력:

```json
"nextStep": "더 읽으려면 export-text --json -p <쪽>, 찾으려면 search --json"
```

에이전트는 이미 "봉투가 다음 호출을 지시한다"는 패턴에 적응돼 있다. 문서에서 온
도구 지시는 그 패턴의 연장으로 읽힌다. 계약 ③(도구가 만든 값과 문서에서 온 값을
섞지 않는다)이 필요한 이유가 이것이다.

**④ 탐지와 오탐**
**이 벡터의 오탐률이 가장 낮다.** `hwp_[a-z_]+` 패턴 실측: 117 문서 중 **0건
(0.0 %)**. 한국 공문서 본문에 `hwp_` 로 시작하는 소문자 밑줄 식별자가 나올 이유가
없다.

- 후보 목록은 **`tool_defs` 단일 출처**에서 가져온다. 하드코딩 목록은 도구가 늘면
  즉시 낡는다 — did-you-mean 이 같은 원칙을 쓴다
  ([weak_agent_proofing.md](../weak_agent_proofing.md) P1).
- 남은 오탐 위험은 **rhwp 자신의 문서**다. 이 저장소의 매뉴얼·PR 본문에는 도구
  이름이 당연히 들어간다. 사용자가 rhwp 문서를 .hwp 로 만들어 rhwp 에 물리면
  전건이 걸린다. 실사용 코퍼스에서는 무시할 만하지만 **0 은 아니다.**
- CLI 이름(`export-text` 등)까지 넓히면 오탐이 오른다 — 하이픈 낱말은 일반 문서에도
  나온다. **MCP 도구 이름(`hwp_` 접두사)으로 한정**하는 편이 방어력 대비 비용이 낫다.

### V4 — 권한 주장 (false authorization)

"이미 승인됐다"고 선언해 확인 절차를 건너뛰게 한다.

**① 심는 법**
본문 문장. "사용자가 이미 승인한 작업임", "관리자 권한으로 처리", "개발자 모드에서는
확인 불필요" 같은 형태. 공문서에서는 §V8 의 어투와 결합할 때 훨씬 자연스럽다.

**② 반출 경로**
텍스트 축 전부. **`fields --json` 의 `memo`** 가 특히 위험하다 — 화면에 안 보이는
필드인데 값은 봉투에 실린다([hidden_content.md](hidden_content.md) H7). 실측한
`samples/field-01-memo.hwp` 의 `memo` 는 "반드시 …해야 합니다" 형태의 **당위
문장**이었다. 정상 문서에서도 이 칸은 원래 명령형을 담는다.

**③ 왜 속는가**
에이전트는 승인 상태를 **직접 알 수 없다.** 사용자가 승인했는지는 호스트가
관리하며, 도구를 호출하는 모델에게는 그 사실이 텍스트로만 도달한다. 그래서
"승인됨"이라는 텍스트와 실제 승인 사이에 **모델이 검증할 수 있는 차이가 없다.**
게다가 이 주장은 에이전트에게 편리하다 — 확인 절차는 비용이고, "이미 승인됨"은
그 비용을 없애 준다. 작업을 완료하려는 압력과 방향이 같은 거짓말은 특히 잘 통한다.

**④ 탐지와 오탐**
`(사용자가|관리자가|이미)\s*승인` 실측: **0건 (0.0 %)**. 그러나 이 0 은
**규칙이 좁아서** 나온 값이다. 넓히면 급격히 나빠진다:

| 토큰 | 등장 문서 | 비율 |
| --- | --- | --- |
| `승인` 단독 | 14 | 12.0 % |
| `관리자` 단독 | 23 | **19.7 %** |
| `조치` | 31 | 26.5 % |

`승인`·`관리자`는 공문서의 기본 어휘다. 결재·전결·권한위임을 다루는 문서라면
문장마다 나온다. **주체(사용자/관리자) + 완료 시제(이미/했음) + 대상(이 작업/요청)의
3요소가 한 문장에 모일 때만** 신호로 삼아야 한다. 요소 하나로는 잡을 수 없다.

### V5 — 반출 유도 (exfiltration lure)

본문에 목적지(URL·메일 주소·경로)와 전송 명령형을 함께 놓아, 에이전트가 다른 도구로
데이터를 밖으로 보내게 한다.

**① 심는 법**
목적지 + 명령형 + 대상 지정. 목적지는 본문·하이퍼링크 필드·각주 어디든 놓을 수 있다.
대상은 보통 "이 문서 전문" 또는 "방금 읽은 내용"처럼 **에이전트의 현재 컨텍스트를
가리키는 말**로 지정된다.

**② 반출 경로**
텍스트 축 전부 + `fields`(하이퍼링크 필드의 `command` 에 URL 이 그대로 들어간다 —
`src/model/control.rs:258` 주석: "필드 이름/명령 (누름틀: 안내문, 하이퍼링크: URL 등)").

**③ 왜 속는가**
**rhwp 도구만으로는 성립하지 않는다**(§2.2). 성립하려면 에이전트가 HTTP·메일·셸
도구를 함께 갖고 있어야 한다. 실무 에이전트는 대개 갖고 있다. 그때 모델이 보는
장면은 이렇다: 신뢰된 도구 결과 안에 구체적 목적지와 구체적 동작이 있고, 자기
도구 목록에는 그 동작을 수행할 도구가 실제로 있다. **요청과 능력이 맞아떨어지면
"할 수 있으니 하라는 뜻"이라는 해석이 자연스럽다.**

네트워크가 없어도 성립하는 변종이 있다. rhwp 는 파일을 쓴다 — 산출 경로를 문서가
정하게 만들면(T5) 공유 폴더·동기화 폴더가 채널이 된다. 이 경우 rhwp **단독으로**
반출이 완성된다.

**④ 탐지와 오탐**
- URL 단독은 **신호가 아니다.** 실측: 117 문서 중 **21건(17.9 %)** 에 URL 이 있다
  (총 76개). 정부 문서의 정상 인용이다 — `corpus.korean.go.kr`,
  `stdict.korean.go.kr` 같은 공공 도메인.
- `(전송|발송|업로드|전달)` + 명령형 어미 인접 규칙 실측: **0건 (0.0 %)**.
- 그래서 규칙은 **목적지 × 전송 동사 × 명령형**의 결합이어야 한다. 단일 요소는
  전부 높은 오탐을 갖는다.
- **못 잡는 것**: 목적지가 문서 안에 없고 "평소 쓰던 주소로"처럼 지시대명사로만
  지정되면 결정론적 규칙으로 잡을 수 없다. 이 한계는 명시한다.

### V6 — 경계 위조 (delimiter forgery)

컨텍스트 구분자를 흉내 내, 문서 텍스트가 **끝났다고** 믿게 만든다.

**① 심는 법**
코드펜스(` ``` `), 수평선(`---`), 유사 태그(`</system>`, `</document>`,
`<END_OF_DOCUMENT>`), JSON 닫는 괄호열. .hwp 본문은 임의 문자열을 담을 수 있으므로
전부 그대로 심긴다. 문단 구분·표 구분은 텍스트 축에서 개행 문자로 평탄화되므로,
**구분자처럼 생긴 줄과 실제 구분자를 구별할 정보가 봉투에 남지 않는다.**

**② 반출 경로**
`export-markdown` 이 최악이다. Markdown 산출물을 프롬프트에 이어붙이는 순간 문서
안의 코드펜스와 호스트가 만든 코드펜스가 **같은 층위**에 놓인다.
`export-text` 도 다르지 않다 — 소비자가 텍스트를 삼중 따옴표로 감싸 프롬프트에
넣는 관행이 흔하다.

**③ 왜 속는가**
경계는 **합의된 관습**이지 강제되는 구조가 아니다. 호스트가 "```로 감싼 부분이
데이터"라고 프롬프트에 적어도, 데이터 안의 ```가 그 규칙을 깨는 것을 막을 방법이
프롬프트 층위에는 없다. 모델은 가장 가까운 닫는 구분자에서 문맥이 끝났다고 읽고,
그 뒤 텍스트를 **자기 층위의 발화**로 취급한다. HTML 이 아니라 프롬프트라서 파서가
없다 — 이스케이프할 곳이 없다는 뜻이다.

**④ 탐지와 오탐**
- `</system>` `<|im_end|>` `[/INST]` 류 실측: **0건 (0.0 %)**. 한국 공문서에 나올
  이유가 없다.
- **코드펜스와 `---` 는 다르다.** 이 둘은 정상 문서에도 흔하다. 특히 `---` 는
  구분선·서명란·표 대체로 쓰인다. 이 둘만으로는 신호로 쓸 수 없다.
- 실용적 판정선: **LLM 전용 구분자**(`<|…|>`, `[INST]`, `<<SYS>>`, `</system>`)만
  높은 신뢰도로 잡고, 범용 구분자(``` , `---`)는 **다른 벡터와 동시 발생할 때만**
  가중치로 쓴다.
- 근본 해법은 탐지가 아니라 **봉투 설계**다. 문서 유래 문자열이 JSON 문자열 값
  안에 있는 한 구분자는 데이터로 남는다 — 소비자가 그 값을 꺼내 평문으로
  이어붙이는 순간 무너진다. 이 책임 이전을
  [consumer_guide.md](consumer_guide.md)가 명시해야 한다.

### V7 — 다단 유인 (multi-stage lure)

1단계는 무해해 보이고, 2단계에서 발현한다.

**① 심는 법**
세 가지 결합 방식이 있다.

| 방식 | 1단계 | 2단계 |
| --- | --- | --- |
| **문서 간** | 문서 A 가 "붙임 문서 B 를 함께 처리하라" | 문서 B 에 페이로드 |
| **표면 간** | `export-text` 에는 정상 | `fields` 의 `memo` 또는 각주에 페이로드 (§2.1 비대칭) |
| **시간차** | 지금 만든 산출물은 정상 | 그 산출물을 나중에 다시 읽을 때 발현 |

**② 반출 경로 — plan runner 가 특히 위험하다**
`rhwp run <계획.json>` / `hwp_run_plan` 은 선언 계획을 정적 선검증 후 원자 실행한다
(`--help` 실측: "전 step 을 정적 선검증(불가 시 실행 0·exit 2)하고 인메모리로 원자
실행해 단언(verify) 통과 시에만 단 한 번 저장"). 계약 자체는 견고하다 — 실패 시
디스크 무변경이다.

위험은 다른 곳에 있다. **계획서를 누가 쓰느냐**다.

- 계획서가 사람이 쓴 것이면 안전하다. 계획서가 **문서를 읽은 에이전트가 쓴 것**이면,
  문서 내용이 계획서 내용을 결정한다.
- `run --json` 봉투는 `steps` · `verify` · `invalid` · `changedPages` 를 담고
  (`src/main.rs:958`), 실행 결과가 **저널**로 돌아온다. 저널은 다음 판단의 입력이다.
  1단계에서 심은 텍스트가 산출물에 들어가면, 그 산출물을 검증하려고 다시 읽는
  순간이 2단계다.
- 원자성은 **한 계획 안**에서만 보장된다. 계획 A 의 산출물을 계획 B 가 읽는
  연쇄에는 원자성이 없다.

**③ 왜 속는가**
에이전트의 안전 판단은 대체로 **호출 단위**다. 각 호출이 무해하면 통과한다.
그러나 위험은 호출들의 **조합**에 있다. "문서를 읽는다"(무해) + "계획을
작성한다"(무해) + "계획을 실행한다"(무해) = 문서가 시킨 편집. 어느 단계에도
멈출 이유가 없다.

여기에 F5(장기 계획 붕괴)가 겹친다. 2단계에 도달했을 때 1단계의 원본 지시는 이미
컨텍스트 뒤편이고, 눈앞에는 방금 읽은 문서 텍스트가 있다.

**④ 탐지와 오탐**
- **단일 문서 정적 검사로는 원리적으로 못 잡는다.** 1단계는 정말로 무해하기
  때문이다. 이건 규칙을 잘 만들면 되는 문제가 아니라 **탐지 범위 밖**이다.
  못 잡는다고 적는 것이 정직하다.
- 잡을 수 있는 것은 **연쇄의 흔적**이다: 계획서의 `find`/`replace`/`text` 값이
  방금 읽은 문서 문자열과 일치하는가. 이건 탐지가 아니라 **출처 추적**이며
  계약 ③의 확장이다.
- 오탐 위험이 크다 — 정상 작업은 원래 문서에서 읽은 값을 문서에 쓴다(연도 갱신,
  기관명 정정). 그래서 이 신호는 **차단이 아니라 표시**로만 쓸 수 있다.
- 현재 구현된 유일한 관련 신호는 `run --json` 의 `steps[].confusable`
  (`src/main.rs:1584` 자기서술)이다. 이름 혼동만 잡고 출처 추적은 없다 —
  **확인되지 않음**이 아니라 **미구현**이다.

### V8 — 한국어 공문 어투 위장 (Korean official-document register)

**이 문서의 독자적 가치가 여기 있다.** 영어 규칙만으로는 이 벡터가 잡히지 않는다.

rhwp 의 주 사용처는 한국 공문서다. 공문서에는 **지시를 담는 정형 어투가 이미
존재한다.** 공격자는 새 문법을 만들 필요가 없다 — 문서 종류가 원래 갖고 있는 어투를
쓰면 된다.

**① 심는 법**
공문 서식의 정상 구성요소 자리에 지시를 넣는다.

| 자리 | 정상 용법 | 위장 가능성 |
| --- | --- | --- |
| `붙임` 항목 | 첨부 목록 | 첨부 대신 처리 지시 |
| `위와 같이 … 하시기 바랍니다` | 시행문 맺음 | 맺음 형식에 얹은 명령 |
| `조치사항` / `협조요청` 절 | 수신처 조치 | 수신처를 "처리 시스템"으로 지칭 |
| 표의 `비고`·`참고사항` 칸 | 부기 | 사람이 잘 안 읽는 칸 |
| `※` 각주 표기 | 단서 | 단서 형식의 지시 |

핵심은 **명령형이 문서의 정상 성분**이라는 점이다. 시행문은 원래 남에게 무엇을
하라고 적는 글이다.

**② 반출 경로**
텍스트 축 전부. `export-structure` 는 `붙임`·`조치사항` 같은 **절 제목을 트리로
올려** 주므로 위장 절이 구조적으로 강조된다. `digest --sections` 도 마찬가지로
절 제목을 앞세운다.

**③ 왜 속는가**
세 겹이다.

1. **어투가 진짜다.** V1·V2 처럼 이질적 표지를 심을 필요가 없다. 문장이 문서
   전체와 이질감 없이 붙는다 — 사람 검토자도 위화감을 못 느낀다.
2. **행위 주체가 모호하다.** 한국어 공문은 주어를 잘 생략한다.
   "확인 후 회신하시기 바랍니다"의 주어는 수신 기관인데, 문서를 읽고 있는 것이
   에이전트일 때 **"수신자 = 나"** 로 해석될 여지가 문법적으로 열려 있다. 영어
   `you` 처럼 지시 대상을 못 박는 대명사가 없다.
3. **에이전트에게 이 문서의 목적은 "처리"다.** 사용자가 "이 공문 처리해 줘"라고
   시켰다면, 문서 안의 조치사항은 **작업 명세서**로 읽히는 것이 자연스럽다.
   사용자 지시와 문서 지시의 경계가 의미상 흐려진다. 이 흐림은 다른 벡터에는
   없는, 이 벡터만의 성질이다.

**④ 탐지와 오탐 — 여기가 가장 어렵다**

정상 공문서에서 이 토큰들이 얼마나 흔한지 실측했다(117 문서 / 7,293,169자):

| 토큰 | 등장 문서 | 비율 | 총 출현 |
| --- | --- | --- | --- |
| `시행` | 60 | **51.3 %** | 1,727 |
| `확인` | 60 | **51.3 %** | 1,614 |
| `반드시` | 38 | 32.5 % | 285 |
| `참고` | 32 | 27.4 % | 249 |
| `조치` | 31 | 26.5 % | 515 |
| `요청` | 26 | 22.2 % | 328 |
| `바랍니다` | 25 | 21.4 % | 109 |
| `제출` | 20 | 17.1 % | 609 |
| `붙임` | 17 | **14.5 %** | 133 |
| `협조` | 16 | 13.7 % | 311 |
| `하시기 바랍니다` | 14 | 12.0 % | 43 |
| `승인` | 14 | 12.0 % | 212 |
| `위와 같이` | 12 | 10.3 % | 66 |
| `아래와 같이` | 10 | 8.5 % | 47 |

**절반 이상의 문서가 `시행`·`확인`을 담는다.** 공문 어투 토큰을 신호로 쓰는 것은
"공문서인가?"를 묻는 것과 같다 — 전부 공문서다. 이 축에서는 **어투 자체가 신호가
될 수 없다.**

그러면 무엇이 신호인가. 어투가 아니라 **대상**이다.

| 판정 축 | 근거 |
| --- | --- |
| **수신자가 사람이 아니다** | `(AI\|에이전트\|어시스턴트\|모델\|시스템)` 이 명령형의 대상으로 지목됨. 실측 오탐 **0건(0.0 %)** — 단 `시스템` 단독은 26.5 %(31 문서, 2,764회)이므로 **명령형 어미와 인접할 때만** |
| **동작이 문서 처리가 아니다** | 공문의 정상 동작은 회신·제출·공람·보고. 파일 쓰기·전송·도구 호출은 공문 어휘가 아니다 |
| **다른 벡터와 동시 발생** | 공문 어투 + `hwp_` 도구 이름, 공문 어투 + 은닉 서식 |

즉 **한국어 벡터는 단독 규칙으로 잡지 않는다.** 어투는 배경이고, 판정은 "그
명령형의 대상이 누구인가"에서 갈린다. 영어 규칙 집합에는 이 판정축이 아예 없다 —
`ignore previous instructions` 만 찾으면 공문 어투 위장은 **한 건도** 안 걸린다
(실측: 영어 무효화 패턴 0건).

**남는 한계 — 정직하게**

- "붙임 문서를 열어 처리하라"는 문장은 **정상 지시와 공격이 구별되지 않는다.**
  실제 공문은 늘 그렇게 쓴다. 이 경우는 못 잡는다.
- 수신자를 명시하지 않은 명령형(주어 생략)은 판정축 ①이 작동하지 않는다.
  한국어 공문의 **기본 문형**이 이것이므로, 이 벡터의 상당 부분이
  **탐지 범위 밖**에 남는다.
- 이 한계를 좁히려 규칙을 넓히면 위 표의 오탐률로 즉시 돌아간다. 계약 ④
  ("오탐은 기능 실패다")에 따라 **넓히지 않는다.**

## 4. 오탐 실측의 방법과 재현

위 수치는 추정이 아니라 이 저장소 샘플로 잰 값이다.

```bash
# 대상: samples/ 의 .hwp/.hwpx 앞 120건
ls samples/*.hwp samples/*.hwpx | head -120 > list.txt
cat list.txt | ./target/release/rhwp.exe batch export-text --json --threads 8 > batch.ndjson
# 결과: 성공 117건 / 오류 3건 / 총 7,293,169자
# NDJSON 레코드: {"pageCount","schemaVersion","source","text"}
```

이후 각 레코드의 `text` 에 규칙 후보를 적용해 **문서 단위 적중률**을 셌다.

### 4.1 요약 — 넓은 규칙 vs 좁힌 규칙

| 규칙 | 오탐 문서 | 오탐률 | 등급 후보 |
| --- | --- | --- | --- |
| `무시` 낱말 | 16 | 13.7 % | 사용 불가 |
| 줄머리 역할 표지 (변형 A) | 6 | 5.1 % | 낮음 |
| URL 존재 | 21 | 17.9 % | 사용 불가 |
| 역할 표지 단독 줄 (변형 B) | 0 | 0.0 % | 높음 |
| 역할 라벨 2종 이상 (변형 C) | 0 | 0.0 % | 높음 |
| 한국어 역할 표지 (변형 D) | 0 | 0.0 % | 높음 |
| 한국어 인접 무효화 | 0 | 0.0 % | 높음 |
| 영어 무효화 정형구 | 0 | 0.0 % | 높음 |
| LLM 전용 구분자 | 0 | 0.0 % | 높음 |
| `hwp_` 도구 이름 | 0 | 0.0 % | 높음 |
| 권한 주장 3요소 결합 | 0 | 0.0 % | 높음 |
| 전송 동사 + 명령형 | 0 | 0.0 % | 높음 |
| AI 수신자 지목 + 명령형 | 0 | 0.0 % | 높음 |

### 4.2 이 실측이 증명하지 못하는 것

- **재현율은 재지 않았다.** 오탐률만 쟀다. 좁힌 규칙이 실제 공격을 얼마나 잡는지는
  악성 표본이 있어야 알 수 있다 — [test_corpus.md](test_corpus.md)의 몫이다.
- **표본 편향.** `samples/` 는 렌더링 회귀를 잡으려고 모은 코퍼스다. 공문서가 많지만
  시험지·교재·기술 문서도 섞여 있다. 순수 행정 공문 코퍼스에서는 §V8 표의 비율이
  **더 올라갈** 가능성이 높다.
- **117건은 통계적으로 작다.** 0.0 % 는 "이 표본에서 0건"이지 "오탐 없음"이 아니다.
  0 건과 낮은 확률을 혼동하면 안 된다.

### 4.3 왜 신뢰도를 나누는가

오탐률이 0.0 % 인 규칙과 13.7 % 인 규칙을 같은 `warning` 으로 내보내면, 소비자는
곧 전체를 무시하게 된다. 이미 저장소 안에 같은 취지의 계약 테스트가 있다
(`tests/fields_json_contract.rs:259` 주석: "에이전트는 곧 textSecurity 를 무시하게
된다 — 없느니만 못한 상태다").

등급의 정의·임계값·봉투 표현은 [detection_policy.md](detection_policy.md)에서
확정한다. 이 문서는 **각 벡터의 오탐 실측치**를 그 입력으로 제공할 뿐이다.

## 6. 확인되지 않음

근거를 대지 못한 항목을 명시한다. 추측으로 채우지 않았다.

| 항목 | 상태 |
| --- | --- |
| 각 벡터가 실제 에이전트를 뚫는 **성공률** | 확인되지 않음 — 모델·호스트마다 다르고 이 저장소에서 측정할 수단이 없다 |
| `export-markdown`·`export-doclang` 이 각주를 포함하는지 | 확인되지 않음 — `export-text`·`digest` 만 실측했다 |
| `search` 가 각주를 제외하는 것이 **의도인지 결함인지** | 확인되지 않음 — 실측으로 사실만 확인했고 설계 의도는 코드 주석에서 못 찾았다 |
| 표 셀 안 텍스트가 `export-text` 에서 본문과 구별되는지 | 확인되지 않음 |
| V7 시간차 변종이 실제 파이프라인에서 성립한 사례 | 확인되지 않음 — 구조적 가능성만 서술했다 |
| 순수 행정 공문 코퍼스에서의 §V8 오탐률 | 확인되지 않음 — `samples/` 는 렌더링 회귀용 혼합 코퍼스다 |
