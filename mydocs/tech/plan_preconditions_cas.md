# 계획서 전제 계약 — `preconditions.inputSha256` (CAS)

**한 줄**: 계획을 만든 시점의 입력 지문을 계획서에 봉인하고, 실행기가 입구에서
대조해 **낡은 기준의 실행을 거부한다**. 잠금도 데몬도 아니고, 해시 하나다.

원점은 #3905(로드맵 트랙 C R21 `[실측]`)다 — 두 에이전트가 같은 기준본에서 서로
다른 필드를 채워 같은 출력에 쓰면 **둘 다 exit 0 + `filledCount:1` 을 보고하는데
나중 쓴 쪽이 먼저 쓴 편집을 흔적 없이 덮는다.** 어느 봉투에도 "네 기준이 이미
낡았다"는 신호가 없다. `atomic_file::write_atomically` 는 **쓰기 원자성**(반쯤 쓰인
파일이 안 생김)을 보장할 뿐 **의미 동시성**(남의 편집을 덮는가)을 보장하지
않는다 — 이 둘의 혼동이 문제의 뿌리였다.

이 문서는 그 차단기의 계약을 적는다. 로드맵 상 R22 이고, R23(저널 지문 체인)·
R24(단발 `--expect-sha256`)·R26(재계획 루프)이 이 계약 위에 얹힌다.

## 1. 계약 — 계획서 쪽

계획서 본문의 **선택 필드**다. 없으면 CAS 이전과 완전히 같게 동작한다(하위 호환).

```json
{
  "planVersion": "1.0",
  "input": "계약서.hwp",
  "output": "계약서_기입.hwp",
  "preconditions": { "inputSha256": "9658a0…(64자리 16진)" },
  "steps": [ … ]
}
```

- `preconditions` 는 **객체**여야 하고, 있으면 `inputSha256` **하나만** 갖는다.
  값은 64자리 16진(대소문자 무관, 앞뒤 공백 허용)이다.
- 형식 위반은 CAS 판정이 아니라 **사용법 오류(exit 2)** 다 — 계획서가 문법을
  어긴 것이지, 문서가 바뀐 것이 아니다. 키가 있는데 타입이 틀린 경우를 "전제
  없음"으로 낮추면 CAS 경계가 fail-open 되므로, 생략만 허용하고 명시된 값은
  반드시 검사한다.
- `planSchemaVersion` 은 **1.2**(minor). 계획서 **문법**은 1.1 이후 그대로라 기존
  계획서는 무수정으로 유효하다 — 1.2 가 바꾼 것은 아래 §2 의 거부 계약이다.

## 2. 계약 — 실행기 쪽 (거부 3면)

실행기 입구에서 실제 입력 파일 바이트의 sha256 을 **1회** 계산해 대조한다.
불일치는 **거부이지 건너뜀이 아니다.**

| 면 | 보장 |
|---|---|
| 실행 0건 | step 은 하나도 적용되지 않는다. 저널에 `steps` 자체가 없다 |
| 디스크 무변경 | 출력 파일이 생기지 않고, 제자리 편집(input == output)이면 원본이 **한 바이트도** 바뀌지 않는다 |
| 저널 | `preconditionFailed{kind,expected,actual}` + `nextCall` + `invalid: []`, **exit 3** |

```json
{
  "schemaVersion": "1.0",
  "planVersion": "1.0",
  "input": "계약서.hwp",
  "output": "계약서_기입.hwp",
  "invalid": [],
  "preconditionFailed": {
    "kind": "inputSha256",
    "expected": "0000…0000",
    "actual": "9658a0…d66d"
  },
  "nextCall": {
    "name": "run",
    "arguments": ["--plan-json", "{…기대 해시를 actual 로 갈아 끼운 계획…}",
                  "--dry-run", "--json"],
    "why": "계획 수립 후 입력 문서가 바뀌었습니다. 같은 의도를 새 지문으로 다시 선검증하세요 — …"
  },
  "error": "입력 문서가 계획의 기대 해시와 다릅니다 — …"
}
```

`invalid` 가 **비어 있는 것이 계약의 일부**다. "invalid 가 비어 있지 않으면 정적
선검증 위반 = exit 2" 는 소비자가 이미 쓰고 있는 불변식이고, CAS 는 그 축이
아니다 — 계획은 문법도 의미도 옳았고 틀린 것은 세상 쪽이다.

대조는 **두 번** 일어난다: 파싱 전 입구에서 한 번, 저장 직전에 다시 한 번. 사이에
낀 편집을 저장 직전 재대조가 잡는다(같은 입력 경로를 겨눈 rhwp writer 사이의
read-check-write 경계는 파일 잠금으로 직렬화된다 — CAS 를 선언한 계획만 이 잠금을
든다).

## 3. `--dry-run` 도 같은 판정을 낸다 — 이 계층의 심장

CAS 대조는 dry-run 분기보다 **앞**에 있다. 따라서 `--dry-run` 과 실행은 같은 종료
코드와 같은 `preconditionFailed`·`nextCall` 을 낸다(거부 봉투는 `dryRun` 표지를
싣지 않는다 — 두 경로의 판정이 구별 불가능해야 한다는 것이 요구 자체다).

이유는 #3719 §6-8 의 원칙이다: **선검증이 곧 실행 경로다.** 예행이 통과했는데
실행이 거부되는 도구를 에이전트는 신뢰할 수 없고, 그 순간 안전 계층 전체가
장식이 된다. 계약 테스트 `dry_run_reaches_the_same_cas_verdict_as_execution` 이
두 호출의 종료 코드와 판정 객체가 **같음**을 고정한다.

## 4. `nextCall` — 재계획 힌트는 실행 가능해야 한다

`nextCall` 은 설명문이 아니라 **그대로 argv 로 이어 붙여 부를 수 있는 호출**이다:
`name` 은 실존 명령, `arguments` 는 그 뒤에 붙일 argv 조각이다(MCP 오류 봉투 R72·
CLI `수복:` 줄과 같은 어휘).

CAS 거부에서 오는 것은 **기대 해시를 실제 해시로 갈아 끼운 같은 계획을 `--dry-run`
으로 재선검증하는 호출**이다. 이 한 수가 재계획 루프의 분기점이 된다:

- **통과(exit 0, `dryRun:true`)** — step 이 바뀐 문서에서도 여전히 성립한다.
  `--dry-run` 만 빼고 그대로 다시 부르면 된다.
- **`invalid[]`(exit 2)** — 남의 편집이 이 계획이 겨눈 자리를 무너뜨렸다. 진짜
  재계획(문서를 다시 읽고 의도를 다시 세움)이 필요하다.

해시를 갈아 끼운 계획을 실어 보내는 것이 CAS 를 무력화하는 것처럼 보일 수 있으나
그렇지 않다 — 힌트는 **선검증(`--dry-run`)** 을 지목하고, 디스크에 닿는 재실행은
소비자의 명시적 다음 결정으로 남는다. 상한(무한 재계획 방지)과 에스컬레이션 신호는
R26 소관이며 이 문서의 범위 밖이다.

## 5. 판단 3개와 그 답의 근거

트랙 C 문서가 R22 의 착수 게이트로 못 박은 판단 셋이다. 셋 다 이후 단계의 모양을
좌우하므로 근거를 남긴다.

### ① 종료 코드 — 신설하지 않고 **exit 3** 에 편입

#2707 계약이 이미 "3 = 판정"이다(`--verify` IR 차이, `ir-diff`, `replay` 재현
불일치, `audit` 불일치, 그리고 계획서 `assertions.verify` 실패). CAS 불일치는
런타임 실패도 사용법 오류도 아니라 **판정**이므로 의미가 정확히 맞고, 에이전트의
분기표를 늘리지 않는다.

**이 판단은 이미 착지한 코드를 고친다.** #4378 은 R22(계획서 경로)를 exit 2 로,
R24(`edit … --expect-sha256`)를 exit 3 으로 서로 다르게 냈다 — 트랙 C 문서가 R24
착수 게이트에서 경고한 바로 그 상태("R22 전에 하면 두 경로의 CAS 의미가 갈린다")다.
같은 사실에 두 코드를 내면 소비자는 진입점마다 다른 분기를 써야 한다. 여기서
**진입점과 무관하게 하나**로 맞춘다: 두 경로 모두 exit 3 + 같은
`preconditionFailed{kind,expected,actual}` 모양.

### ② 지문 대상 — **파일 바이트 sha256**

실행기 입구에서 해시 1회로 끝나 구현이 작다. 그리고 `replay` 영수증의
`inputSha256` 과 **같은 단위**라 계보가 이어진다 — 영수증·감사(`audit`)·계보
(`lineage`) 축이 이미 파일 바이트 해시로 서 있으므로, 여기서 IR 지문을 쓰면 같은
문서에 두 개의 "지문"이 생기고 R23 의 저널 체인이 어느 쪽으로도 이어지지 않는다.

"같은 내용의 다른 바이트를 같게 보고 싶다"는 요구는 실재하지만(재저장·정규화),
그것은 R23 소관이다. 이 단계가 먼저 서야 그 위에서 지문 대상을 넓힐 수 있다.

### ③ `preconditions` 위치 — **계획서 본문의 선택 필드**

계획을 만든 시점의 전제는 **계획의 일부**다. 플래그로 빼면 계획서만 넘겨받은
제3자(인계받은 다른 에이전트, 저장된 계획을 재실행하는 CI)가 전제를 잃고, 그
순간 CAS 는 "부르는 사람이 기억하고 있어야 하는 것"으로 격하된다. 무상태 CLI 는
상태를 봉투에 실어 호출자가 나르는 설계이고, 계획서가 곧 그 봉투다.

단발 경로에도 같은 의미론이 필요하다는 요구는 R24 가 `--expect-sha256` 플래그로
이미 이식했다 — 둘은 배타가 아니라 **상보적**이다(계획 있는 경로는 본문, 계획
없는 경로는 플래그).

## 6. 자기서술 등재

지도에 없는 필드는 에이전트에게 없는 것과 같다. 세 곳에 등재한다.

| 자리 | 내용 |
|---|---|
| `export-plan-schema` (`$defs.Preconditions`) | 계획을 **쓰는** 쪽의 정답지 — 필드 형식과 거부 계약 |
| `capabilities` (`run`) | `summary` 에 CAS 선언, `recordFields` 에 `preconditionFailed`·`nextCall` |
| [지식지도 §2-2](../manual/agent_knowledge_map.md) | 봉투 필드 사전 — 두 필드의 뜻과 `null` 의 뜻 |

`provenance_contract` 의 `declared_record_fields_actually_appear_in_envelopes` 가
"선언한 필드가 실물 봉투에 실제로 나타나는가"를 전수 대조하므로, 스윕에 **CAS 거부
레시피(exit 3)** 를 넣어 허용목록 없이 실물로 통과시킨다.

## 7. R23·R24 로의 확장 경로

- **R23 저널 지문 체인** — 이 단계가 고정한 지문 대상(파일 바이트 sha256)을 실행
  **결과** 저널에도 싣는다. 앞 저널의 `outputSha256` 이 뒤 저널의 `inputSha256`
  과 이어지면 편집 사슬이 검증 가능해진다. 같은 해시 함수를 써야 사슬이 성립한다.
- **R24 단발 CAS** — `edit … --expect-sha256` 은 이미 착지했고, 이 PR 이 두 경로의
  종료 코드·판정 객체를 하나로 맞췄다. 남은 것은 `replace-text` 밖 `edit` 하위
  명령으로의 배선 확장이다.
- **R26 재계획 루프 규약** — 이 문서 §4 의 `nextCall` 이 그 규약이 겨눌 대상이다.
  재시도 상한과 에스컬레이션 신호는 거기서 정한다.

## 8. 비범위

- **잠금 데몬 / 리스 서버** — 무상태 CLI 철학과 정면으로 상충한다. 여기서 쓰는
  파일 잠금은 한 번의 read-check-write 구간을 직렬화하는 것이지, 문서 소유권을
  들고 있는 상주 상태가 아니다.
- **다문서 원자성** — 계획이 문서 A·B 를 함께 바꾸는데 한쪽만 낡은 경우의
  전부-또는-전무는 R27 소관이다. 이 단계의 CAS 는 단일 입력 기준이다.
- **IR 지문·정규화 비교** — ② 참조. R23.
- **재시도 상한·에스컬레이션** — R26.
- **MCP 세션 간 지문 공유** — R28(트랙 H 의 세션 표면이 서야 격리 단위가 정해진다).
