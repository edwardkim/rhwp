## 목표·범위

제목·본문 표 공동 앵커 개선을 수용할 수 있도록, 확인한 비본문 제어 경계와 부족한 검증을 한 단위로 보완한다.
다른 문서의 기존 조판 차이까지 수정 범위를 확장하지 않는다.

1. 공통 `stored_inline_host_has_separate_float_frame`의 Header/Footer 분류를
   `prepare_coanchored_first_line`과 일치시킨다. [한 파일 보정 초안](assets/pr9042/proposed-header-footer.patch)은
   승인 후 적용했다. Native 선행 검증에서 빈 머리말·꼬리말을 포함한 5종 모두 독립 PDF와 같은 2쪽이다.
   최종 fresh WASM·전체 검증은 계속한다. 문서 ID·특정 높이·px 보정은 추가하지 않는다.
2. 원 사례, 무변경 저장, 빈 머리말·꼬리말, 한컴 재저장 대조군에서 제목·본문·다음 표의 쪽 소속,
   순서·겹침·내용 보존을 실제 Native/fresh WASM과 저장·재열기로 확인한다.
3. 중첩 TAC tail 변경은 원 기여를 보존하며 실제 발동 입력·독립 한컴 Print와 비적용 대조군을 보강한다.
   기존 #8187 마지막 행 계약과 #8682 보호를 추적하고, 시작/끝 컷·요구 높이·예약·fit 실패 시 이월·배치를
   실제 관련 경로에서 확인한다. 자료 미확보를 완료로 처리하거나 임의로 기능을 제거하지 않는다.
   실제 한컴 저장본에서 내용과 칸·자식 상자 높이가 정확히 같아야 한다는 기존 가정의 오류를 확인했다.
   칸의 최소 선언과 실제 상자를 구분하고, 여백·저장 줄 폭·되감기 없는 문단 사다리의 포함 관계로 보완했다.
   한 문단·바깥 여백·두 문단의 실제 저장본 전 6쪽 Native가 모두 100.00%다.
   [입력·독립 Print·수정 전후 TSV](assets/pr9042/native-nested-validation/README.md)를 보존했다.
4. 검증한 경계는 정식 suite의 관계형 회귀에 반영한다. 기존 원 사례 검사의 유효한 내용 보호는 유지하고,
   신규 파일 첫머리는 최종 양쪽 전쪽 측정 뒤 실제 수치·시각·증거로 보완한다.

## 독립 근거·소비 지점

빈 머리말·꼬리말·무변경 직렬화의 Windows 한컴 Print는 모두 2쪽이고 두 쪽 RGB도 같다.
반면 후보 Native는 Header 또는 Footer가 있으면 3쪽이다.
공통 host 판정의 비본문 제어 수용 결과가 `from_stored_inline_host`의 frame 생성 여부를 바꾸며,
새 whole-fit 경로가 그 frame을 `record_paragraph_float_placement`와 `place_table_with_text`에 전달한다.
보정 후에도 후속 원점 선택·상한 적용과 실제 paint가 같은 결과를 소비하는지 추적한다.

## 추가 승인: 원 합성본의 저장 줄 정합

2026-11-13 메인테이너는 기존 차이 예외 대신 원 합성본의 저장 줄 처리 보완을 승인했다.
현재 제품 범위에는 이 보완도 포함하며 원격 처리 승인은 별도다.

- 현재 글자모양은 650 HU인데 저장 줄은 800·1100·1900 HU다. 본문의 고정 간격은 저장 3114 HU, 실제 전진 1557 HU인데 기존 줄 사다리는 약 1539~1540 HU로 전진한다. 실제 한컴 재저장본은 명목 높이 650·기준선 553·전진 1557 HU다.
- 기존 `stored_text_metrics`의 렌더 전용 사본에서 셀 전체의 높이·기준선·누적 원점을 함께 산출한다. 가시 글자와 빈 문단 모두 유지한다. 원본 IR·원본 저장 값은 수정하지 않는다.
- 적용은 실제 BodyText 바이트가 `RhwpLineSegTags`에 인증된 rhwp 관리 구역이다. 이름·파일 ID·한컴 metadata로 판정하지 않는다. 인증은 캐시 값의 의미적 정확성 증거로 승격하지 않는다. 정상 한컴 저장본과 인증되지 않은 구역은 기존 계약을 유지한다.
- 단순 한 줄 텍스트 셀에서 현재 글자 높이와 문단 전진이 함께 불일치할 때만 재계산한다. 정상 큰 strut, 현재 간격과 맞는 저장 캐시, 개체·장식·다중 줄·문단 경계 간격·쪽 되감김은 이 단순 줄 사다리의 증명이 아니므로 기존 경로를 유지한다.
- 생산: `stored_text_metrics::owned_cell_with_current_metrics` → `compute_render_normalized_with_storage`의 기존 렌더 사본 → pagination/height measurer/paint의 동일 문단·셀. `register_rendered_text_partitions_with_storage`가 원본/현재 프레임의 변경을 함께 등록한다. 후속 원점·clamp·table row-fit은 실제 원본 실행으로 추가 확인한다.
- 원본과 같은 글자·문단 스타일을 적용한 독립 선행 투영 대조군은 Mac Print 전 2쪽 Native 100.00%다. 이것은 변경한 입력의 진단이며, 실제 원본을 새 코드에서 실행한 결과를 대신하지 않는다.

최종 원본 Native/fresh WASM·저장 재열기, 정상 한컴 대조군·인증 불일치 대조군, 전체 필수 게이트를 마친 후 완료로 판정한다.

## 저장 경계에서 같은 캐시 발행

원본을 새 코드에서 직접 실행한 Native 두 쪽은 100.00%다. 다만 화면용 투영만 적용하면 HWPX 저장 뒤 과거 캐시가 다시 살아나 94.20%/96.08%와 괘선 겹침이 재발했다. 쪽수 2→2만으로 저장 통과를 판정하지 않는다.

동일한 `owned_cell_with_current_metrics` 생산자를 저장용 `ManagedCellsForExport` 범위에서도 호출한다. 원본 section의 실제 바이트 인증을 확인한 뒤 저장 사본에만 현재 캐시를 반영하고, 이후 표 높이·쪽 경계·포맷 lowering을 적용한다. HWP 직접 저장·공통 bounded snapshot·HWPX의 모든 공개 저장 진입점이 이를 소비한다. 일반 렌더 호환 투영 전체를 직렬화하지 않으며 live IR은 보존한다.

최종 공개 저장 API의 재열기 관계 검사, Native/fresh WASM의 실제 저장 출력과 정상 대조군을 추가 검증한다.

## 실제 셀 편집 후 저장 경계

원본과 현재 캐시로 저장한 대조군 모두 공개 `insertTextInCell`로 Body 뒤에 X를 추가하면 화면은 2쪽이지만 HWP/HWPX 저장·재열기는 3쪽이다. 내용은 모두 유지된다. 현재 캐시 대조군의 표 선언은 61,220 HU인데 저장 사본만 61,786 HU로 커진다. 셀 선언은 그대로다. 화면에서 사용한 끝 행의 물리 프레임과 저장용 원시 측정 합이 다르다.

같은 수행 범위에서 관리 캐시의 편집 인계와 공통 행 프레임 소비를 보완한다. 편집 전후 전체 줄·셀 포함, 두 형식의 반복 저장, 내용 보존과 실제 한컴 Print를 확인한 뒤 전체 필수 검증을 완료한다. 무편집 시각 통과와 위 3쪽 경계를 구분하며 미해결 상태로 제출하지 않는다.


### 편집 직후 프레임과 저장 프레임의 연결

원시 행 측정은 61,786 HU이며, 실제 수용한 마지막 행의 빈 밴드를 닫으면 원래 표의 61,220 HU다. 편집 세션이라는 전역 상태만으로 닫힌 행 계산을 배제하면, 줄바꿈이 그대로인 글자 추가에도 format 높이가 달라져 공동 앵커의 whole-fit 경로가 탈락한다. 이때 편집 직후 본문 표가 바깥 위 여백 283 HU만큼 위로 이동한다. 저장·재열기만 비교하면 놓치는 경계다.

생산과 소비는 `fit_measured_table_declared_tail_to_declared_height_with_storage` → format의 행·전체 높이 → 공동 앵커의 fit·예약·실제 배치이며, 저장 높이 writeback도 같은 helper를 소비한다. 원래 저장 host가 별도의 inline/float 프레임을 입증하고 해당 표의 실제 수직 줄 프레임이 유지될 때 적용한다. 줄 재배치·내용 하한·span·되감김이 허용하지 않으면 기존 성장·분할 경로를 유지한다. 전역 height measurer를 바꾸지 않는다.

독립 한컴 2020 Print를 확보한 글자 추가 사례의 저장·재열기 Native 전 2쪽은 100.00%다. 편집 직후 Native 화면, fresh WASM과 반복 저장은 이 연결 보정 후 다시 실행하며, 아래 결과가 완료되기 전에는 이 경계를 완료로 판정하지 않는다.


제목의 `prepare_coanchored_first_line`도 미변경 제목과 유효한 저장 줄을 확인하면서 세션 전체 편집 플래그만으로 원점을 버렸다. 호출한 표의 실제 재배치·확장, 제목 셀 dirty, 저장 줄·선언 높이·fit 검사는 유지하고 전역 편집 플래그만 제외했다. 제목의 수용 원점 → float 원점 → 최종 paint까지 같은 원점을 소비함을 실행으로 확인했다.


### 최신 후보의 Native 확인

`1506a1c34672931c4f5aa5cb6363fba776225949`를 실제로 다시 컴파일한 Native에서 글자 추가 직후 전 2쪽 raw는 모두 100.00%다. 같은 공개 HWP/HWPX 저장 API로 두 번씩 저장·재열어도 2쪽이며, live/저장 재열기 두 PNG는 RGB가 같다. 384 DPI의 독립 Print/Native 재출력으로 마지막 줄의 잉크와 괘선을 확대 판독했다. 96 DPI의 1px 격자 차이와 실제 줄 겹침을 구분하며, 문자의 하강부가 칸 경계를 넘지 않는다. fresh 최적화 WASM과 필수 전체 게이트는 진행 중이다.

비교용 최신 devel을 공용 target에서 빌드한 뒤 후보 Cargo가 잘못 fresh로 판정한 첫 산출물은 base와 해시가 같고 실제 원본이 3쪽이었다. 이 실행은 검증 결과에서 제외했다. 캐시 전체를 지우지 않고 루트 crate의 소스 mtime만 갱신해 실제 재컴파일했으며, 후보 hash `b3d7aecccf0277dd4cc8d4e36b9f23c3ddb3f61f3d0aae28e13e72f746e1f411`과 base hash `8357360d647419607558d3253cd26a9f698dc68cfa3a466f3e515379b41cc49f`를 구분한다. Git 내용은 바꾸지 않았다.

## 최신 devel #9054와의 저장 계약 통합

`959300e66c`는 삭제한 그림만 HWPX에서 제거하고 원본 미참조 자원·그림 글머리표를 유지하는 #8941과, 빈 문단의 정렬 캐럿을 복원하는 #8944를 포함한다. `document.rs` 한 곳의 충돌은 캐시 투영과 자원 pruning을 모두 같은 `with_hwpx_export_document`의 소비 사본에 적용해 해결했다. 검증용 예상 문서도 같은 사본을 소비하며 live IR은 바꾸지 않는다. 새 base의 3개 검사 모듈과 브라우저 공개 API의 그림 삭제·두 번 저장·클립보드/스냅샷 복원·원본 자원/그림 글머리표 보존·정렬 캐럿을 추가 확인한다. 기존 22종·40쪽씩과 보호 3,542쪽·편람·전체 필수 게이트는 이 최종 제품에서 다시 검증한다.
