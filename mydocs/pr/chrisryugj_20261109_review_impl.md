## 실행으로 재현한 새 누락

HWP3 공식 설명본 [27-byte 셀 구조](../tech/한글문서파일구조3.0.md#106-표텍스트박스수식버튼하이퍼텍스트-10)에 따라 셀 위치·크기, 표 정보의 word 셀 개수, 각 셀의 고유 ASCII 문단을 넣은 합성 입력이다. 실제 한컴 생성본·Print 시각 증거와 구분한다. 각 셀은 서로 겹치지 않는 같은 2열 격자이고 모든 입력은 두 parser에서 정상 열렸다. Native binary source·hash를 고정해 같은 입력을 비교했다.

| 입력 | base 셀 수 | 후보 셀 수 | 후보에서 사라진 내용 |
| --- | ---: | ---: | --- |
| 2행×2열 | 4 | 4 | 없음 |
| 2,048행×2열 | 4,096 | 4,096 | 없음 |
| 2,049행×2열 | 4,098 | 4,097 | R2048C1 |
| 2,050행×2열 | 4,100 | 4,098 | R2048C1, R2049C1 |

2,049행 입력 SHA-256 `4f884e6b53dd0fff0103b48b836d429eb5a9f8d747587ad854f50c2fc803dcf3` (1,354,226 bytes), 2,050행 `c927fff59a9049ece02a26d5ac98d137d8e7aa6e86e9ef1eaebb0fe21518c127` (1,354,886 bytes). 진단 입력·생성 스크립트·raw dump는 로컬 `output/pr-review/chrisryugj-20261109/`에 있다. 정식 수용 증거가 되기 전의 진단 자료이며 원본 Hancom Print로 표현하지 않는다.

원인 경로는 `hwp3_next_cell_starts`의 `.take(2048)` → 실제 오른쪽 이웃이 있는데 None → c2를 표 오른쪽 끝으로 대체 → 왼쪽 셀이 두 칸을 점유 → 뒤의 기존 겹침 해소가 오른쪽 셀을 중복으로 버리는 순서다. 2048은 문서 구조의 끝이 아니라 검사한 후보 수이며, 이 둘을 같은 상태로 처리한 것이 누락 원인이다.

## 제안하는 제한 보정과 완료 조건

1. HWP3의 공통 이웃 탐색만 보정한다. 축별 시작 좌표와 반대 축 구간을 index로 구성해 실제 겹치는 이웃을 찾는다. 선형 탐색 상한을 단순 제거해 O(n²)로 바꾸거나 2048 뒤를 None으로 처리하지 않는다. 좌표군의 구간 합집합을 가진 검색 tree 등으로 O(n log n) 구성·O(log² n) 질의를 사용하고 메모리/연산 경계를 기록한다. 두 축이 같은 구현을 사용하게 한다.
2. 원 기여의 시작 변 기반 격자·한컴 네 표 개선을 보존하며 기존 parsing·Storage 자원 한도·동일 입력의 내용 순서를 유지한다. 데이터 손실을 숨기거나 문서 ID·행 수 전용 예외를 넣지 않는다.
3. 작은 정상·2048 경계·연산량 대조를 실제 parser에서 먼저 확인한다. 셀의 내용 보존·소유·겹침 관계를 검사하고 helper만 통과한 것으로 끝내지 않는다.
4. 두 테스트 파일의 현행 증거 주석·검증 근거를 실제 측정 후 보완한다. SO-SUEOP 46쪽·sample16 64쪽·table-cell-order 1쪽의 Native/fresh WASM 전쪽 TSV, 독립 Print·원 글꼴 공급, 직접 확대 판독과 base 대비 하락을 확인한다. 미달·쪽수 불일치는 완료로 처리하지 않는다.
5. 새 source/test 보정에는 Rust lint 전체·집중·release-test 전체·Native 공식·최적화 fresh WASM과 편람 gate 등 적용 필수 검증을 수행한다. 기존 녹색 원 CI를 새 보정 head의 검증으로 재사용하지 않는다. 원 head의 기여 이력은 보존한다.
