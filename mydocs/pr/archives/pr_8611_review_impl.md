## R30 선행 분석 — 유효한 0번 머리 글자 모양 참조

R29는 괄호의 영문 슬롯 소유를 고쳤지만 전 94쪽의 Native/fresh WASM 최저가 모두
98.93%이며, 고정 base 대비 93쪽에서 이 작업의 0.1%p 조건을 넘겨 낮다. 90% 하한을
넘었다는 이유로 수용하지 않고 고비용 전체 회귀·편람 후속 실행을 중지했다.

원본 바이트의 BULLET은 `attr=0x8`, 거리 20%, `char_shape_id=0`, 문자 U+F09F다.
0번 글자 모양은 1400HU·#000080·양각이며 본문 10번 모양은 1300HU·#000099다.
구역 1 문단 63의 PARA_CHAR_SHAPE는 `(0,10)` 한 항목뿐이다. 끝 글자 모양을
상속한 결과가 14pt라는 해석도 성립하지 않는다. 독립 Print는 약 14.04pt의
#000080·흰색·회색 층을 가진 마커를 출력한다.

기존 `marker_char_style`과 `nominal_marker_size`는 ID 0을 참조 없음으로 취급해
마커·예약 영역·거리 기준을 모두 본문의 13pt에서 얻는다. 이 조건은 통합 PR #7568의
`731de9e1b4bb946d76f35108ed7e186ebe4ebecb`에서 들어왔으며, 당시 별도 글자 모양을
참조하는 마커의 크기 분리는 맞지만 0번과 본문 모양이 다를 수 없다는 가정은 틀리다.
사양 표 39는 글자 모양 ID 참조를 정의하며 0을 예약값으로 정하지 않는다.

같은 0번 모양을 새 ID로 복제해 참조 주소만 바꾼 진단 HWPX 쌍에서도 본문 시작이
1.6 CSSpx 달라졌다. 독립 Print 5쪽과의 진단 값은 99.96933% → 100%다. 이는 rhwp가
직렬화한 진단 쌍이므로 원본 HWP의 최종 측정으로 바꾸지 않는다. 실제 원본은 그대로
새 Native/fresh WASM으로 다시 측정한다.

보정은 0번을 포함한 유효 참조를 공통 마커 스타일·예약 영역에서 함께 소비하는 것이다.
참조가 없는 합성 HWP3 개요와 편집 API의 기본 목록은 생성 단계에서 기존 센티널
`u32::MAX`를 명시해 본문 추종을 보존한다. 파일의 실제 0번 참조와 합성 기본값을
소비 지점의 휴리스틱으로 구분하지 않는다. 같은 모양의 ID 별칭 불변성·원본 크기와
꾸밈·명시적 참조 없음 반례를 글꼴 설치와 무관한 관계 검사로 보호한다.

수정 전 최소 글꼴 Rust 회귀 3건은 **2 FAIL / 정상 대조 1 PASS / exit 100**이다.
0번 참조의 크기·색·양각과 동일 모양 ID 별칭의 배치를 실제로 검출했고, 명시적 참조 없음
대조군은 통과했다. 보정본의 집중 검사·실제 영향 쪽·전쪽 및 필수 전체 검증은 별도로 진행한다.

## R32 선행 분석 — 표시 투영 전 Wingdings 글리프 소유

R31의 원본 고사성어 전 94쪽은 Native 최저 99.98%, fresh WASM 최저 98.63%다.

두 경로를 합쳐 통과로 쓰지 않는다. 실제 공급 목록은 같아도 자동으로 선택한 프로그램은

정정한다. 비교 기준이나 설치 글꼴을 바꾸어 차이를 숨기지 않는다.

원본 BULLET U+F09F는 기존 공통 투영표가 Wingdings의 원으로 해석하는 문자다.
그러나 `bullet_marker_text`에서 곧바로 Unicode U+2022로 바꾸면서 원본 주소를 잃는다.
이후 `marker_text_width`와 TextRun이 서로 다른 대체 프로그램의 U+2022 폭·윤곽을
소비한다. WASM에서는 1em 폭의 다른 원이 선택되며, 양각 경로는 일반 글자 경로의
폭 맞춤도 거치지 않는다. 실제 Canvas 명령의 글꼴·전진·변환과 같은 쪽 Native를 대조했다.

독립 Print 5쪽의 Wingdings-Regular subset(xref 36, glyph 3)은 UPEM 2048,
전진 937, 실제 윤곽 경계 `(173,444)..(765,1036)`인 원이다. 중심은 `(469,740)`,
반지름은 296이다. 첫 원점 95.04pt와 약 14.04pt 크기도 원본 스타일·배치와 일치한다.
이것은 원 glyph의 em 단위 계약이며 문서별 좌표 보정이나 화면에서 역산한 픽셀 핀이 아니다.

보정 경로는 원 PUA 보존 → 기존 일대일 표시 투영의 원본 메트릭 → 공통 em 윤곽 →
Native·Canvas·SVG의 현재 원점과 효과 pass다. Unicode U+2022 자체와 다른 미확인 PUA는
기존 글꼴 경로를 유지한다. 원본의 크기·장평·색·양각을 그대로 소비하고 입력·PDF는 바꾸지 않는다.
새 후보의 영향 쪽 직접 판독과 전쪽 TSV, 기존 정상 대조군 및 최소 글꼴 회귀로 검증한 뒤
최종 판단한다. 이 절의 선행 분석만으로 보정 성공이나 승인을 주장하지 않는다.


## R33 원 기호 소유 보정의 전쪽 검증과 회귀 고정

제품 source `ef77d740e1da7c9eaeb908ac3bd653a9670b312a`에서 같은 고사성어 원본과
기존 독립 한컴 2020 Print PDF를 전 94쪽 비교했다. 두 backend 모두 PDF와 쪽수가

본문을 확대 대조했다. 기호의 크기와 양각을 복원했으며 본문의 줄 소속·원점·내용 순서는
유지된다. 획 두께와 서브픽셀 래스터 차이는 남아 있어 픽셀 동일로 표현하지 않는다.

- [전체 Native TSV](../assets/planet6897_20261106/pr8611/r33-source-symbol/native.tsv)
- [전체 fresh WASM TSV](../assets/planet6897_20261106/pr8611/r33-source-symbol/wasm.tsv)

실제 공유 결과의 소비 경로는 원 PUA 보존 → 암묵적 기호 프로그램의 전진·윤곽 →
줄의 마커 배치 → Native Skia/SVG/Canvas의 실제 paint다. 같은 원본 5쪽의 실제 SVG를

대체 증거로 사용하지 않는다. 글꼴 프로그램은 임시 output에서만 사용하고 재배포하지 않았다.

회귀는 설치된 OTF에 의존하지 않는다. 원본을 읽는 공개 DocumentCore 관계 검사 3건은
원 PUA·독립 메트릭 소유, 표시 대체 설정 불변성, 일반 Unicode bullet 대조군을 검사하며

검사 1건, 총 6건이 통과했다. 새 검사는 누락 face와 저장소 소유 fixture face, 두 크기·장평에서
실제 잉크가 독립 Print의 em 윤곽을 따르는지 확인한다. 페이지 절대 배치 좌표를 고정하지 않는다.

실제 fresh WASM·Chrome의 Canvas 회귀는 원본 기호의 source·전진과 실제 남색 잉크를
대조한다. 새 검사는 수정 전 R31 WASM에서 원 PUA가 Unicode bullet로 바뀐 결함을
검출해 실패했고, R33 WASM에서 통과했다. 기존 Canvas 글꼴 CI 집계의 import에 연결했으며
workflow의 새 job이나 개별 호출은 추가하지 않았다. 같은 집계 14건이 모두 통과했다.
검사 개발 중 드러난 상대 baseline 및 공개 JSON/HWPUNIT 양자화의 차이는 검사 좌표계를
바로잡아 처리했고, 제품을 검사 기대값에 맞춰 변경하지 않았다.

현재 단계는 원 기호 보정의 완료 증거다. 전 27건 최종 판정은 남은 전체 Rust·lint·원본 및
보호 문서 Native/fresh WASM 검증과 새 base 보존 대조를 모두 완료한 뒤 별도로 갱신한다.


## R34 선행 분석 — 원 HFT의 굵은 CFF 윤곽 소비

보호 입력 `samples/hwp3-sample16-hwp5.hwpx`의 기존 독립 2024 Print를 대조했다.
R33 WASM 40쪽 raw 99.96%, 51쪽 99.90%는 기존 100.00%보다 낮다. 이 값은 R28과
R31에서도 동일했으므로 R33 원 기호 보정이 새로 만든 차이로 분류하지 않는다. Native의
같은 쪽은 100.00%다. 40쪽의 굵은 전각 한점과 51쪽의 굵은 빈 원에서 차이를 확인했다.

원본의 HFT 한양신명조에 대해 실제 등록한 CFF는 독립 PDF와 같은 윤곽을 갖는다.
PDF 51쪽 Type3 T9 glyph2는 bbox (189,36)..(812,662), UPEM1000, 20/1000 굵기
stroke다. 설치된 원 HFT 대응 CFF의 U+25CB도 같은 bbox다. 글꼴 파일은 배포하지 않는다.
문서별 크기나 좌표를 보정할 필요가 없다.

현재 `HftOutlineFonts::faux_bold_glyph`는 TrueType 보관소만 조회한다. 실제 등록한 원 CFF는
보통 HFT 글자에서 소비되지만 굵은 글자는 그 윤곽을 찾지 못해 Canvas 글자 painter로
돌아간다. 같은 공개 등록 API와 저장소 소유 합성 CFF, 공개 굵기 편집 API를 사용한
브라우저 반례에서 이 경로 미소비를 재현했다. 원본의 실제 굵기 해석도 별도로 assertion한다.

보정은 Print/high-quality에서 등록·검증된 원 HFT CFF의 단일 글리프 윤곽을 기존
fill+stroke 소비 경로에 제공한다. 전진·원점·장평·굵기 합성 규칙을 새로 만들지 않는다.
미등록·결측 glyph, 명시적 기울임, 옛한글 전용 face 및 Screen은 기존 선택을 유지한다.
먼저 작은 실제 Canvas 반례와 40·51쪽을 확인하고, 전체 WASM과 기존 보호 기준을 다시
대조한다. 아래 보정의 실제 통과와 최종 판정은 후속 검증 결과로 기록한다.


### 원 해결 이력의 Git 대조 정정

[PR #8397](https://github.com/edwardkim/rhwp/pull/8397)의 실제 통합은
`99a176b7cb34fde54454c03433baa1382b2de9fa`다. 그 안의 선행 commit
`730759eb2c`(합성 굵기에서 분리 OTF 글리프 보존)는 **Native Skia font_lookup**에서
합성 굵기의 후보 face를 유지한 수정이다. 현재도 같은 경로가 남아 있다. 그 수정을
WASM CFF 굵기 소비까지 구현한 것으로 설명하지 않는다.

후속 [PR #8583](https://github.com/edwardkim/rhwp/pull/8583)의 `96827b3acc`는
Print TTF 대체 윤곽 보관소를 추가했고, [이슈 #8430](https://github.com/edwardkim/rhwp/issues/8430)의
해결 commit `14ae66657fdc6aed96c3b3b31367f4765688bb88`는 이 보관소를 사용하는
WASM 합성 굵기 path를 추가했다. 후자의 실제 diff와 설명은 보통 굵기 TTF의 선택·윤곽과
0.02em fill+stroke를 근거로 한다. 원 HFT CFF의 보통 글자용 윤곽 보관소와는 다르다.

따라서 현재 보정은 원 PR #8397의 Native OTF 선택을 되돌리는 수정이 아니다. 이미 공급된
원 CFF가 굵은 글자에서도 기존 fill+stroke 경로에 도달하도록 누락된 소비를 연결한다.
새 반례는 수정 전 R33 WASM에서 실제 굵기 해석·원 CFF 등록을 확인한 뒤 glyph painter
되돌아감으로 실패했다. 새 제품 결과는 실제 WASM 빌드와 원본 40·51쪽으로 별도 확인한다.

R34의 첫 사전 fmt 검사는 아직 suite에 등록되지 않은 새 회귀 파일의 서식을 발견했다.
저장소 루트의 cargo fmt만으로 해당 원본 파일이 포맷되었다고 판단한 것이 잘못이었다.
원본을 rustfmt로 직접 보정하고 준비된 검증 suite에서 fmt를 재검증한다. 제품 보정의
실행 결과와 서식 보정을 구분하며 이 단계에서 통과하지 않은 gate를 완료로 표시하지 않는다.


## R34 실제 검증 완료 범위

원 HFT 대응 OTF의 CFF 굵기 경로를 실제 최적화 WASM에서 확인했다. 원래 TTF 합성 굵기와
새 CFF 경로, Screen·옛한글 대조군은 3개 집중 브라우저 검사에서 통과했고, 기존 CI 집계에
연결한 실제 Canvas 글꼴 검사 16건도 통과했다. 새로운 원 CFF 검사는 소유 fixture를 명시적인
source family에 연결하고 실제 공개 편집 API로 굵기를 설정한다. SVG의 해당 글자 stroke로
합성 굵기 경계에 진입했는지 확인하며, 페이지 테두리의 stroke를 근거로 삼지 않는다.

추가 보호 대조군인 sample16 HWPX는 같은 독립 2024 Print와 Native/fresh WASM 모두64쪽이
일치한다. 전쪽 최저는 Native100.00%/WASM99.99%이고, 기존 기준64행의 표시값 하락은0행이다.
지적한40·51쪽은 양쪽100.00%다. 이는 원 PR의 다른 문서 주장에 대한 증거와 구분한다.
[전체 TSV·같은 쪽 review/overlay·재현 조건](../assets/planet6897_20261106/protected-r34/sample16-hwpx/README.md).

제품 source는99f1340628이며 이후 검사 assertion과 문서를 보완한 commit은 실제 제품 실행과
구분한다. 전27 PR 최종 판정은 남은 전체 WASM·Rust·lint 완료 후 갱신한다.

## R36 전체 회귀의 구두점 공통 원인 분석

R36 전체 실행의 실패 다수는 같은 원인으로 묶였다. `5de92ecc46`이 실제 한자 뒤 괄호를
보정하면서 기존 `ascii_punctuation::uses_latin_slot` 조건을 지우고 모든 ASCII 구두점에
영문 슬롯을 지정했다. 이는 원 주장의 한자→괄호 경계보다 넓은 변경이다.
한글·영문 슬롯의 실제 프로그램·속성이 같던 글줄도 분할하고, HWP3에서 한글 프로그램이
괄호를 가진 경우까지 영문 공급으로 바꾼다. 하나의 run을 찾던 검사 실패와 실제 프로그램
소유 계약의 실패를 구분하며, 이 결과만으로 기존 기대값을 일괄 변경하지 않는다.

선행 `9b1c31ec03`·`11cc64a443`와 R28 제품 `b6c02c1946`의 조건을 대조했다.
`ResolvedCharStyle::ascii_punct_latin_slot` 문서에는 HFT의 확정 영문 프로그램과
일반 한글 TTF의 구두점 계약이 구별되어 있고, HWP3의 공개 CFF 반례도 한국어 프로그램의
실제 cmap 결측과 영문 프로그램의 hit가 있을 때만 공급을 옮긴다. 해당 정확한 검사는
유지한다. 원래 source 프로그램·꾸밈 조건을 복구하고, 한자 뒤 ASCII 구두점은 공통
`punctuation_slots::slot`에서 앞 한자와 영문 슬롯을 구분한다. 측정과 구성 run이 같은
선택을 소비하며 HWP3의 독립 계약은 그대로 둔다.

실물 고사성어 5쪽의 `江湖煙波(강호연파)`와 기존 HWP3 공급 대조, 이번 전체 실패 묶음을
집중 실행한다. R33 전쪽 Native/fresh WASM·원 보호 PR의 기준과 대조하기 전에는
이 보정의 시각 완료나 최종 승인을 선언하지 않는다. run 분할 가정뿐 아니라 줄·글자
소유, 전진, 쪽수·본문 보존·겹침의 정확한 기존 검사는 유지한다.

### 기존 검사의 정확한 보호 범위 유지

R36은 전체 12,850건 실행을 마쳤고 12,807 PASS / 43 FAIL / 기존 skipped 45건,
exit 100이었다. 표·수식 정상 출력 대신 실패 기대값을 넓히지 않고 공통 ASCII 소유를
보정한다. 앞서 `ce9e186c04`에서 바꾼 issue265 HWP3 제목의 독립 괄호 run 기대는
과도한 슬롯 변경의 결과를 수용했던 부분이므로 원 검사를 복원한다. 원문 주소로
자연 글리프를 선택하는 개선과 독립 Print 좌표·저장 바이트 보존 검사는 유지한다.

자동 BULLET의 U+F09F 보존은 별도의 정확한 source 프로그램 보정이다. 기존 #7379
합성 예산 반례의 본문 비교 helper는 표시 문자 `•`를 지워 마커를 구분했으므로
원본 주소 `char_start`가 있는 run만 IR 본문과 비교하도록 고친다. 원본 본문 기대값,
표 분할·셀/문단별 내용 순서·행 소속·캡션과 후속 내용 검사는 그대로 유지한다.
자동 마커 자체의 원 주소·전진·일반 Unicode 대조는 기존 implicit Wingdings 검사에서
계속 보호한다. 실물 정책연구 215쪽의 미해결 조판을 해결했다고 주장하지 않는다.
