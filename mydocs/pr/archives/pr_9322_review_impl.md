# PR #9322 보완 근거와 #9280 검토에서 확인한 인접 기호

## HWPX를 저장한 뒤의 문자

기여자가 제시한 기호 15개는 버전별로 올바르게 저장된다. Windows 한컴 2020과 2024가 만든 HWPX, 기여자의 macOS 한컴 HWPX와 문자 및 굵은 B의 UTF-16 시작 위치가 모두 일치한다. Windows 한컴 2020으로 원본 HWP와 후보가 저장한 HWPX를 각각 열어 인쇄했을 때 두 버전 모두 96 dpi 전쪽 RGB 픽셀이 같았다. [문자·서식 30행](../assets/pr9280/symbols.tsv) · [한컴 실행 근거](../assets/pr9280/hancom-jobs.tsv)

5.0.1.6의 저장본을 rhwp로 다시 열면 `export-text --json`에서 아래 네 문자가 다른 문자로 나온다. 메인테이너가 한컴에서 직접 저장한 HWPX를 기존 devel에서도 열어 같은 결과를 얻었다. 특히 `U+A832` 줄에서 제품은 이중 가로선을 그리며 Windows 한컴 Print와 모양이 다르다. 이번 PR이 새로 만든 회귀로 분류할 근거는 없다. [1쪽 비교 이미지](../assets/pr9280/modern-native-review.png)

| HWPX 원문 | rhwp 추출 |
| --- | --- |
| U+A807 | U+252C ┬ |
| U+A80E | U+2518 ┘ |
| U+A810 | U+2502 │ |
| U+A832 | U+2550 ═ |

HWPX writer는 원본 포맷과 파일 버전을 확인한다. 반면 표시·추출이 호출하는 `hancom_symbol_display_key(ch)`는 문자 값만 입력받아 BMP를 다시 Plane 15 키로 바꾼다. 이 경로는 최신 devel에도 있다. 기존 구형 HWP와 실제 보충 PUA의 선 기호는 계속 보호해야 한다. ## 원 표본 주변에서 추가로 확인한 네 문자

공개 HWP 두 개의 첫 기호 문단에 일반 편집 API로 여덟 기호와 ASCII 표식을 넣고 HWP로 저장했다. 두 파일의 FileHeader는 각각 5.0.1.5와 5.0.1.6이다. 5.0.1.5에서는 U+A805·U+A809·U+A847·U+A849 네 문자를 Windows 한컴 2020과 2024 모두 U+F0805·U+F0809·U+F0847·U+F0849로 저장했다. 후보는 원래 BMP로 남겼고 `export-hwpx --verify --verify-pages`를 통과했다. 5.0.1.6은 여덟 문자 전부 두 한컴 버전과 같았다. 네 문자는 원 PR이 검증 대상으로 명시한 15종 밖의 기존 누락이다. [기호별 대조](../assets/pr9280/neighbors.tsv) · [5.0.1.5 입력](../assets/pr9280/neighbors-v5.hwp) · [5.0.1.6 입력](../assets/pr9280/neighbors-v6.hwp)

## 메인테이너 보완안

1. 현대 HWP5·HWPX의 본문 BMP와 구형 HWP5의 선 기호를 구분하는 근거를 공통 표시·추출 경로에 전달한다. 실제 Plane 15 문자, 글자 겹침과 구형 문서의 표시 의미는 대조군으로 검사한다.
2. 인접 네 문자는 독립 저장본이 일치한 값만 구형 본문 변환표에 보완한다. 다른 코드의 의미 또는 BMP 구간 전체의 대응은 추정할 수 없다.
3. 원 15종과 인접 대조군으로 저장·재열기, 추출, 서식·줄 경계, Native·fresh WASM 직접 표시를 재검증한다. 표시 코드 변경 시 편람과 특별 보호 문서의 쪽별 하한 및 전체 필수 검증을 적용한다.

원 기여의 저장 수정은 독립 인쇄까지 확인했다. 기존 표시 문제와 추가 네 문자를 이 PR에서 메인테이너가 함께 맡는 것은 별도 작업 범위다.

## 인접 기호 대조에서 확인한 현대 문서의 결합 부호

메인테이너 보완 후보에서 현대 문자의 잘못된 괘선과 구형 인접 기호 변환을 고쳤다. 원본·인접 기호·기존 #5800 대조군을 HWPX로 저장해 Windows 한컴 2020에서 다시 인쇄한 여섯 쪽은 모두 해당 원본 Print와 96 dpi RGB 픽셀이 동일하다. [재인쇄 결과](../assets/pr9280/hancom-reprint.tsv)

Windows Print에는 이 영역에 사용한 함초롬바탕이 포함되어 있다. 현대 인접 대조군의 첫 줄에서 실로티 나그리 결합 부호 U+A806은 라틴 B 뒤에 놓여 있다. 결합 대상인 같은 문자 체계의 기본 글자는 없다. 한컴 PDF의 그리기 순서는 B, 점선 원 U+25CC, U+A806이다. 독립 PDF상의 점선 원 시작점은 107.9pt, 다음 라틴 C의 시작점은 113.0pt다. 원은 본문에 저장된 문자가 아니다. 원 기여와 최신 devel, 메인테이너 후보의 Native는 이 원을 그리지 않는다. 후보의 인접 대조군 전쪽 raw는 99.38%다. [동일 영역 3배 확대](../assets/pr9280/isolated-combining-mark.png)

같은 글꼴을 별도 HarfBuzz로 셰이핑했다. 문자 체계의 시작에서 단독 U+A806을 전달하면 점선 원과 부호가 나온다. 실로티 나그리 기본 글자 U+A807 다음에 붙이면 원이 생기지 않는다. 저장·추출 의미와 다음 글자의 배치 원점을 유지하면서, 화면과 인쇄가 단독 부호와 정상 결합을 구별하는지를 검증할 수 있다. 앞서 확인한 현대 문자 네 개와 구형 인접 기호 네 개 중에는 이 현대 결합 부호가 없다.

작업지시자가 이 표시 문제도 보완하도록 승인했다. 공개 현대 HWP의 본문을 편집해 세 문서를 만들고 Windows 한컴 2020에서 각각 한 쪽씩 직접 인쇄했다. 30개 문단의 원문과 PDF 그리기 순서, 각 글자의 가로 원점을 대조했다. 일반 공백과 줄바꿈 없는 공백 뒤에는 원이 생긴다. 기본 글자나 직접 입력한 점선 원 뒤에 붙은 첫 부호는 그대로 결합하고, 다음 부호에만 새 원이 생긴다. 한컴은 점선 원을 그린 다음에도 뒤 라틴 글자의 조판 위치를 보존한다. [한컴 원문·인쇄 문자·좌표 30행](../assets/pr9280/syloti-hancom.tsv) · [Microsoft의 결합 대상이 없는 부호 처리 규칙](https://learn.microsoft.com/en-us/typography/script-development/use#defective-clusters)

문서 모델의 문자·커서 위치를 유지한 채 공통 그리기 단계에서 결합 대상을 판정한다. 기존 조판의 문자 시작 위치를 사용하고, 추가 원의 전진폭은 같은 실로티 나그리 구간을 그릴 때만 반영한다. HWP와 HWPX 각각에서 저장 본문, 실제 표시 순서, 뒤 글자 위치를 비교한다.

## 구현과 독립 대조

구형 HWP 본문의 변환은 파일 버전과 문자 소유 경로를 확인한다. HWPX 본문의 현대 유니코드, 실제 보충 사설 문자, 글자 겹침을 각각 검사했다. 한컴 2020·2024가 저장한 인접 네 문자의 대응을 구형 변환표에 추가했다. 두 형식으로 저장·재열기한 결과 및 본문과 서식 경계의 대조를 보존했다. [저장 XML 32개 비교](../assets/pr9280/save-xml.tsv) · [한컴 재인쇄 9개 비교](../assets/pr9280/hancom-reprint.tsv)

단독 U+A806의 원은 공통 paint에서만 만든다. 같은 문단·셀의 직전 글자가 다른 run에 있어도 원래 조판 위치와 편집 인덱스를 사용한다. 원이 앞에 직접 입력된 경우, 실로티 나그리 기본 글자, 반복 부호, 폭 없는 연결자·비연결자를 독립 Print에 대조했다. 30조합을 HWP·HWPX로 각각 열어 확인한 결과 표시 순서 60개가 모두 한컴과 일치했고 다음 C의 조판 위치도 60개 모두 보완 전과 같았다. [문자별 전후 대조](../assets/pr9280/syloti-display.tsv) · [편집·저장 13개 상태](../assets/pr9280/syloti-edit.json)

Studio에서는 CanvasKit이 문자 조형이 필요한 run을 건너뛰어 레이어에 남아 있는 원과 부호가 화면에서 사라졌다. 가로쓰기 실로티 나그리 run은 준비된 실제 글꼴로 SkParagraph를 실행한다. 글리프의 결합 오프셋은 그 결과에서, 클러스터 시작 위치는 레이어 좌표에서 읽는다. 글꼴의 굵기·기울임과 그리기 효과에도 같은 글리프를 쓴다. U+A832는 주어진 Windows 글꼴 모두에 없어서 실제 한컴도 누락 글리프의 윤곽을 그린다. CanvasKit에서도 각 후보의 실제 문자 지원을 먼저 검사하고, 없을 때는 실제 윤곽이 있는 누락 글리프를 원래 위치에 그린다. [실제 조형 경로](../../../rhwp-studio/src/view/canvaskit/positioned-syloti-text.ts) · [글꼴별 실측](../assets/pr9280/font-metrics.tsv)

줄 바꿈 없는 공백 자체의 폭 차이는 별도의 대조군으로 확인했다. 결합 부호가 없는 U+00A0 뒤 C는 96 dpi에서 한컴 117.376px, 기존 devel과 보완본 모두 120.053px다. 단독 부호 처리의 적용 조건과 무관하게 재현된다. [공백 8조합의 독립 좌표](../assets/pr9280/space-control.tsv)

현대 원본의 U+A832에는 글꼴의 누락 표시가 그려졌지만 그 오른쪽 선이 다음 B와 겹쳤다. Windows 한컴 2020 Print에서 굴림의 글리프 0과 B의 원점 차이는 96 dpi에서 13.43px다. 보완 전 Native의 공통 줄 배치는 이 기호에 6.7px를 배정했다. 같은 함초롬바탕 문서에 U+A830부터 U+A839까지 각각 A와 B 사이에 입력해 다시 인쇄했다. 열 문자 모두 굴림의 글리프 0으로 그려졌고, 전진폭은 인쇄 글자 크기와 같았다. 글꼴에 실제로 있는 실로티 나그리 문자와 빈 사각형 U+25A1은 각자의 글리프와 폭을 사용했다. 공통 줄 측정에서 실제 문자 공급을 먼저 해소하고, 확인된 결측에서만 누락 글리프의 전진을 사용한다. [수정 전 Studio와 한컴 인쇄 확대](../assets/pr9280/studio-missing-sign.png)

Windows 한컴 2020에서 같은 10pt 기호를 425.2pt 폭의 문단에 반복 입력해 줄 경계를 확인했다. 42개까지는 원점 사이가 약 10pt이고, 43개부터는 한 줄의 마지막 윤곽까지 들어오도록 간격이 좁아진다. 84개와 85개는 한 줄에 남고 86개는 85개와 1개로 나뉜다. 줄 나눔에도 누락 글리프의 자연 전진폭을 사용한 중간 후보에서는 #5800 원본의 84개가 42개씩 갈라져 뒤 문단까지 내려갔다. 줄을 나눌 때의 원문 문자 칸과 그 줄에 실제 그리는 글리프의 전진폭을 구분해 짧은 원본과 긴 원본을 함께 검사한다. [독립 인쇄의 문단별 글자 수·줄 경계·가로 원점](../assets/pr9280/indic-line-breaks.tsv)

## 최종 표시와 검증 도구 확인

제품 커밋 `9595602fe1`의 Native와 최적화한 WASM에서 짧은 원본의 U+A832와 B는 각각 독립된 윤곽으로 보인다. 같은 커밋에서 #5800의 84개 기호와 뒤 문단도 독립 인쇄와 같은 줄에 배치됐다. 글꼴 공급 계약도 별도로 확인했다. 폭 0.75em인 검증용 글리프를 원 문서의 글꼴로 지정하면 수정 전후 모두 96 dpi에서 10.0px를 소비했다. 원본 폭 보존 옵션을 켜고 그리기용 글꼴만 공급한 HCR 문서에서는 원본의 줄 배치가 적용됐다. [짧은 줄 비교](../assets/pr9280/indic-short-comparison.png) · [84개 기호 비교](../assets/pr9280/indic-long-comparison.png)

11개 독립 인쇄본을 쪽수 검증에 등록하는 과정에서 pypdfium2의 문자 범위 조회가 긴 미수록 글리프 문서에서 재귀 한도에 도달했다. 이 문서는 한 쪽이며 PDFium의 문자 인덱스가 2,677개다. 문자 범위 조회가 실패할 때 같은 PDFium의 전체 쪽 텍스트 조회를 사용하도록 보완했다. 등록된 38개 고유 PDF의 1,449쪽에서 대조한 결과, 기존 방식으로 읽힌 1,448쪽의 텍스트와 SHA-256이 일치했다. 나머지 한 쪽의 텍스트는 비어 있고 기호 윤곽과 줄별 개수는 직접 인쇄본에 보존돼 있다. 11개 검증용 HWP 모두 등록한 인쇄본과 실제 쪽수가 일치했다.
