## #8232 추가 조사 — 우선 좌표 검사 40파일의 단언·호출과 현재 Print 근거

전수 조사는 계속 진행 중이며 제품·테스트 수정, `issue_8232` 이름 변경 및 PR 제출은 아직 없습니다. 고정 head는 `238de6de41a208648f4ade6b494fe433a81c1fce`입니다.

### 파일 태그를 실제 함수·helper 판정으로 내렸습니다

기존 부동소수 상수 조사에서 우선 확인한 **40파일·81함수/helper**의 실제 단언·상수·호출 문맥을 대조했습니다. 그중 14그룹은 해당 국소 단언이 원본 HU·실제 포함·원문/소유·CLI 실행 계약이고, 67그룹은 절대 위치·고정 selector·독립 쪽수/내용 대응의 추가 근거가 필요합니다. **67은 확정 위반 수가 아닙니다.** 공용 helper가 올바른 ±2px 비교를 한다는 사실만으로 모든 caller의 페이지별 자격이 입증되지는 않습니다.

확인한 구분 사례:

- footer-logo 검사는 x에 `1.5pt=2 CSS px`, y에는 `3pt=4 CSS px`를 허용합니다. 단위 표기만 보고 둘 다 ±2px인 것으로 세지 않습니다.
- 같은 머리말·제목 검사 안에서도 완료된 쪽과 98% 미만인 쪽이 섞여 있습니다. 쪽별로 자격을 확인합니다.
- 원본 셀의 마지막 빈 줄 1000HU·여백141HU·그림 offset에서 **실제 셀 끝을 기준으로 유도한 관계**의 0.1px와, 실물 페이지 y를 0.1px로 고정하는 단언을 구분했습니다.
- 그림을 고정 x/y/폭/높이로 찾은 뒤 포함·개수를 검사하는 경우도 selector 자체를 심사합니다. 원문·개체 ID·표/셀/문단 소속으로 대상을 확인해야 합니다.
- source 내부에서 실물 입력을 직접 사용하는 추가 65그룹도 읽었습니다. 쿼리 경로 parity·원본 바이트/구조 보존과, 고정115쪽·편집 후 증가≤2 같은 별도 검증 전제를 구분했습니다. 이 목적 분류를 전체 테스트 품질의 완료 판정으로 쓰지 않습니다.

### `hy-001`의 글꼴과 배치 차이도 분리했습니다

앞선 로고 간격 대조에 대해 PDF 내부 정보도 추가로 확인했습니다. 2020 engine으로 출력한 HWP의 본문 font descriptor는 Gulim이고, 2024 engine의 HWPX 및 기존 PDF에서는 CP949 이름의 휴먼명조가 관측됩니다. 이 정보만으로 HWP 원본의 실제 글꼴 선택 원인을 단정하지 않습니다.

HWPX의 본문 PDF subset에서는 **비어 있지 않은 157글리프 모두** 로컬 휴먼명조와 정규화 윤곽·advance가 일치했습니다. subset에 Unicode cmap이 없어 문자별 매핑을 입증한 것은 아니며, 이것만으로 Native가 선택한 typeface를 확인했다고 주장하지도 않습니다. 프로그램 바이트 hash 동일성과 subset 윤곽/advance 대응은 구분합니다. 추출 프로그램은 로컬 ignored output에만 보관합니다.

추가로 현재 source의 Native renderer에서 실제 font decision trace를 실행했습니다. 두 입력 모두 2쪽 본문123문자와 로고 줄 공백54자의 요청/선택은 휴먼명조이며, HCI Poppy 요청9문자는 Palatino Linotype으로 선택됐습니다. 각 입력258문자 전체를 제한 누락 없이 관측했고, Canvas2D/CanvasKit은 이 Native 관측의 지원 범위가 아니므로 확인했다고 세지 않습니다. 따라서 HWP PDF의 Gulim 차이를 현재 Native가 휴먼명조를 찾지 못한 현상으로 단정할 수 없습니다. HWP 원본 선언도 휴먼명조를 참조합니다. 한컴 2020 worker의 실제 선택 원인은 별도 확인이 필요하고, 공통 로고 간격의 강제 폭 배분은 계속 구분합니다.

HWPX도 같은 로고 간격 차이를 보이므로 이를 본문 글꼴 차이 하나로 설명하지 않습니다. 원본 로고 줄은 두 TAC 그림, 사이 공백54자, 음수 자간과 `horzsize=47372HU`를 가집니다. 현재 `textbox_tac_space_advance_override`는 저장 폭에서 두 그림 폭을 뺀 나머지를 공백에 전부 배분합니다. 두 그림과 공백의 사용 폭을 저장 폭으로 가득 채우는 이 계산과 실제 Print의 사용 끝점을 대조하고 있습니다. 문서별 오프셋이나 기대값 완화로 처리하지 않습니다.
