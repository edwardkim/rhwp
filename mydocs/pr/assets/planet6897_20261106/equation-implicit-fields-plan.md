# 생략된 수식 필드와 셀 프레임의 후속 분석 계획

## 범위와 독립 근거

R12의 빈 꼬리 일괄 이월은 반례로 기각하고, 제품은 `048f44da99`를 유지한다.
27개 원 PR의 통합·최종 리뷰 범위와 모든 기존 검증 게이트는 줄이지 않는다.
report-628의 수식 네 개와 같은 원본의 영향 쪽 16·18·120·122·123·124·125쪽이
직접 보정 대상이다. report-838 및 기존 보호 문서는 대조군으로 유지한다.

공식 HWP5 사양 설명본 표 105의 수식 속성·문자 크기·기준선·선택적 버전/글꼴 필드와
원본 레코드를 대조한다. 이 원본은 파일 버전 5.0.0.0이며 네 EQEDIT 모두 버전과 글꼴
문자열이 생략돼 있다. BaseUnit은 1100, 선언 높이는 10570 HU, 기준선 값은 9다.
수식 스크립트는 명시적 빈 행과 아래첨자를 포함한다. Instance ID나 문서별 수치로
표시 세대를 추정하지 않는다.

원본 한컴 별도 저장 관찰 job `28113bb8-bd43-4ec4-995f-4293d559f4e4`에서는 글꼴이
HYhwpEQ, 높이 10560 HU, 기준선 54로 발행됐지만 수식 호스트의 저장 줄은 그대로였다.
이 관측만으로 생략 필드의 기본값을 현대 버전으로 바꾸거나 모든 캐시를 무효화하지 않는다.

현재 소비 경로는 `parse_equation_control → Equation → document_script::parse /
EqLayout::for_equation → flow_metrics_hwp → composer의 수식 소유 행 갱신 →
셀 높이·인라인 원점 → paint_parts::layout_for_paint → Native/Canvas`다.
빈 글꼴은 현재 HYhwpEQ 분기에 들어가지 않는다. HYhwpEQ만 명시한 진단도 16·120쪽을
후퇴시켰고, 현대 버전을 함께 명시한 진단도 개선되지 않았다. 글꼴명 또는 버전 분기
하나만 바꾸는 것으로 원인 해결을 대신하지 않는다.

## 작은 독립 관찰

원본에서 앞서 RHWP로 내보낸 모델 진단 HWPX를 사용해, 서로 다른 수식 두 개를 담은
표 호스트만 남긴 수동 축약 HWPX를 만들었다. 수식 스크립트·BaseUnit·선언 크기·기준선·
버전/글꼴 생략·표/문자/문단 속성은 유지하고, 모든 저장 LineSeg를 제거했다.
이 파일은 수동 진단 자료이며 기존 저장 정보 수용 조건을 완화하는 근거로 쓰지 않는다.

- 생성 경로: ignored `output/pr-review/planet6897-integration-20261106/`의
  `prepare-equation-implicit-minimal.py`와 `equation-implicit-fields-minimal-source.json`.
- 이 HWPX는 MCP가 생성한 파일이 아니다. MCP에는 실제 한컴 2020의 Print PDF와
  별도 HWP 저장 관찰을 각각 요청했다.
- Print job: `89e4bbcb-51ac-4b97-b36d-38951d710ebd`.
- HWP 저장 job: `407e4fbe-e564-4fa3-8005-42e02e1f6d79`.
- 요청 시점 상태는 queued다. 성공·실패·출력 메타데이터는 실제 status와 다운로드 후 확인한다.
  `--target pdf`만으로 Print를 입증하지 않으며 engine·제품 빌드·PrintMethod 0·1-up을 확인한다.
- 정식 report-628 HWP·독립 PDF를 다시 만들거나 이 진단 출력으로 교체하지 않는다.

### 실제 관찰과 진단 입력의 한계

위 두 job은 실제 한컴 2020 `11.0.0.9136`에서 성공했다. 진단 PDF는 1쪽이며
`pdf_print_method=0`, `hancom2020_pdf_driver_one_up`을 확인했다. 별도 저장 HWP의
두 수식은 글꼴 HYhwpEQ를 명시했지만 높이 10570 HU·기준선 9를 유지했다.
이는 전체 HWP 원본의 별도 저장 관찰(높이 10560·기준선 54)과 다르다.

기존 정식 Print 18쪽의 PDF object 129에서 BaseFont의 원시 CP949 이름은
`한양신명조`다. PDF 텍스트 연산의 `보험자수` 네 글자가 이 글꼴을 실제 선택함을 확인했다.
HWPX 경유 진단 Print의 수식 한글은 Haansoft Batang이다. 원본은 글자 크기 92인 인쇄
좌표계에서 `보→험→자→수`의 x 전진이 94이고, HWPX 경유 진단은 같은 크기에서
한글 전진이 85다. 이 인쇄 좌표를 출력 px 보정 상수로 사용하지 않는다.

현재 Native Skia와 Canvas의 수식 한글 기본 family는 공통
`CJK_EQUATION_FONT_FAMILY`의 Haansoft Batang이다. 따라서 생략 필드가 있는 원본의
표시 프로그램과 HWPX의 명시/빈 속성 기본값을 같은 계약으로 취급하면 안 된다.
이 차이가 수식·셀 프레임 차이 전체의 원인인지, 그 일부인지는 아직 별도로 입증해야 한다.
PDF 글꼴 프로그램 바이트를 저장소나 배포물에 추가하지 않았다.

원본 HWP 레코드로 직접 축약한 시도는 구역 수 불일치, 한컴의 손상/변조 경고 또는 CFB
구조 사전 검사로 거절됐다. 이 입력들에서는 한컴 Print·수용된 저장본을 얻지 못했으므로
정상 한컴 문서나 시각 근거로 사용하지 않는다. HWPX 경유 진단도 Native 59.62%여서
새 회귀 fixture로 등록하지 않는다. 실패한 진단을 독립 기준으로 승격하지 않는다.

직접 축약의 형식 차이를 더해 원인을 흐리지 않도록, 변경하지 않은 전체 HWP 원본을
한컴 2020 HWPX로 저장하는 job `0dc804e7-be50-4e79-8817-5514b8692c21`을 시작했다.
이는 PDF 재출력 요청이 아니다. 실제 결과에서 수식·셀·호스트 줄 속성을 읽고 비교한다.

새 저장본에서 두 수식의 의미 속성·행 상자·표 높이와 실제 Print의 같은 영역을 대조한다.
수동 HWPX의 값, 한컴이 새로 발행한 저장값, 실제 독립 출력의 관측값을 구분한다.
정상 생성본·크기/구조 대조군에서 확인한 공통 계약을 확보한 뒤에만 제품 보정을 정한다.

## 구현·검증 조건

표시 내부 기준선과 바깥 호스트 기준선, 줄의 점유와 마지막 잉크를 구분한다. 새 분기가
필요하면 파일의 생략 필드 의미·표시 세대 계약과 적용/비적용 반례를 먼저 입증한다.
한 helper 뒤에서 별도 원점·높이로 덮어쓰는 경로도 확인하고 공통 결과를 소비하게 한다.
목표 두 쪽에 맞춘 이월이나 수치 보정으로 다른 페이지를 바꾸지 않는다.

보정 후 같은 정식 원본·기존 Print의 영향 쪽을 먼저 판독한다. 방향이 맞으면 전 195쪽과
대조군 전 109쪽, fresh WASM, 보호 PR #8389/#8397, 편람 gate와 최종 회귀·lint·Studio를
검증한다. 미달 원본의 회귀 기대값·golden은 먼저 갱신하지 않는다. 실제로 90% 이상과
확대 판독을 완료한 뒤 독립 관계 기대값에 따라 필요한 회귀만 추가/수정한다.

## 전체 저장 관찰 완료와 호스트 앞 공백

전체 원본의 한컴 2020 HWPX 저장 job `0dc804e7-be50-4e79-8817-5514b8692c21`은
성공했다. 산출물 SHA-256은 `ec5e19d434cd6d23ae0f95edd51d2a35d5caa5b0521865407e2e13e483ce3c5e`이며,
수식 네 개의 글꼴 HYhwpEQ·기준선 54·높이 10560 HU·폭 38728/36449 HU를 확인했다.
호스트/셀의 저장 LineSeg는 원본과 같은 값이므로 별도 저장값을 정상 배치 결과로 재인용하지 않는다.

18쪽 두 번째 수식 호스트에는 첫 문단의 공백 다섯 개와 다음 문단의 수식 앞 공백 일곱 개가
실제로 존재한다. 원본 문단 속성은 각각 180%·200% 줄 간격이다. R11 공통 전진 추적에서
휴먼명조 공백 하나의 최종 전진은 492 HU다. 따라서 두 번째 수식의 원 저장 폭
32884 HU와 일곱 공백·좌우 여백 112 HU의 합 36440 HU는 가용 39516 HU에 들어간다.
한컴 별도 저장에서 발행한 자연 폭 36449 HU를 같은 계산에 넣으면 40005 HU여서 넘친다.

이는 수식의 자연 폭 갱신이 앞 공백의 줄 나눔과 빈 줄 점유를 바꿀 수 있다는 원인 가설이다.
200%×1100 HU의 빈 줄 전진은 2200 HU다. 독립 Print와의 표 높이 차이를 이 상수로
직접 더하지 않고, 실제 공통 줄 구성에서 같은 줄/다음 줄 소유가 달라지는지 확인한다.
첫 번째 수식도 앞 공백과 자연 폭의 합이 가용 폭을 넘으므로, 두 호스트의 기존 셀 높이와
줄 구성 차이를 함께 검증해야 한다. 저장 수식 값만 덮어쓰거나 빈 줄을 무조건 추가하지 않는다.
추적 원본은 ignored output의 `report628-p18-host-prefix-trace.json`에 있다.

## 한컴의 빈 행·아래첨자·글자 크기 대조 관찰

전체 정상 HWP 사본에서 네 수식의 스크립트·BaseUnit만 바꾼 원인 분리용 입력 두 개를
만들었다. 원본의 버전/글꼴 필드 생략과 나머지 내용은 유지했다. 정식 원본·PDF를
대체하지 않는다. 실제 한컴 2020 11.0.0.9136이 두 입력 모두 수용했으며 PrintMethod 0·
1-up PDF와 별도 HWPX 저장을 얻었다.

| 조합 | BaseUnit | 한컴 저장 자연 높이 | 기준선 | 관측 |
| --- | ---: | ---: | ---: | --- |
| `가나` | 1000 / 2000 | 1200 / 2400 | 84% | 독립 글자 줄 1.2em |
| `가나 = x_{year}` | 1000 / 2000 | 1400 / 2800 | 72% | 아래첨자가 논리 하강부를 확장 |
| 같은 식 두 행 | 1000 / 2000 | 2600 / 5200 | 58% | 한 행 전진 1.2em, 마지막 하강부 보존 |
| 두 행 사이 빈 행 하나 | 1000 / 2000 | 3800 / 7600 | 58% | 빈 행도 같은 1.2em 전진 |

원본 PDF의 한글 대체 프로그램은 한양신명조다. Print의 가→나 전진은 명목 10pt에서
인쇄 좌표 85/86, 20pt에서 171이고, 행 피치는 각각 100과 200이다. 빈 행이 하나 있으면
가시 행의 기준선 차이는 각각 200과 400이다. 원점의 정수 반올림과 글자 크기를 구분한다.
수학 본체와 아래첨자는 원본 Type3 프로그램을 사용한다. 생략된 HWP5 필드와 HWPX에
명시한 HYhwpEQ를 같은 입력 계약으로 취급하지 않는다.

Print job은 `d23971e5-0cf9-424e-9f3e-5beda67bd6c8`,
`63b7a1ab-4e8a-4f03-8038-d1eef3b3c9b6`, HWPX 저장 job은
`ba8ab96c-5eea-49e0-9b24-514adababd03`, `ed76c6da-7b37-43b3-b12b-e135997c3591`이다.
ignored output의 `equation-implicit-controls*-source.json`, `*-saved-frames.json`,
PDF 연산자 관찰 파일에 실제 입력·산출물 SHA와 읽은 속성을 기록한다. 새 PDF에는 공백이
들어간 BaseFont 이름을 MuPDF가 해석하지 못하는 부분이 있어 전 문서 텍스트 추출을
근거로 사용하지 않는다. 의도한 한글 글꼴의 ToUnicode와 실제 텍스트 연산자·원점만 대조했다.
정상 전쪽 시각 통과나 새 회귀 fixture로 승격하지 않았다.

구현에서는 파서가 실제로 읽은 HWP5 선택 문자열 생략을 보존해 명시된 빈 HWPX 속성과
구분한다. 해당 표시 계약의 논리 글줄·아래첨자·명시적 빈 행을 공통 EqLayout 결과로
생산하고 flow 폭/높이/기준선과 paint가 함께 소비하게 한다. 정상 명시 face와 현대 버전,
미확인 복합 구조의 저장 프레임은 기존 계약을 유지한다. 앞 공백의 줄 나눔은 같은 자연
폭을 기존 composer가 소비하게 하며 특정 문서의 빈 줄 높이를 직접 더하지 않는다.

## R17 실패와 공통 표시·간격 소비 보정

R17 Native 빌드는 성공했지만 영향 7쪽은 모두 90% 미만이다. 18쪽 review에서 한글이
없고 아래첨자·연산자만 남았다. 설치 HY Sinmyeongjo의 Regular 프로그램은 HGSMJ(한글),
ENSMJ(영문), FLSMJ(기호) 등으로 분리되어 있다. 첫 family의 첫 프로그램만 고르는
HancomGlyphs paint는 한글 cmap을 보장하지 않는다. 기호용 FLSMJ를 명시 공급한 실험도
한글을 복원하지 못했다. 본문이 사용하는 계열 후보·문자 coverage 선택 결과를 소비하고
원본의 논리 전진과 shear는 유지한다. 새 글꼴 파일은 배포하지 않는다.

평가결과서 원본 첫 제목의 문단 앞 간격은 1,000 HWPUNIT다. 기존 측정은 이를 예약하지만
paint의 reflow_spacing은 SectionDef 등 배치 상자가 없는 컨트롤도 일괄 제외하여 0으로
다시 처리한다. source→typeset/paragraph/format→reflow_spacing→paragraph_layout의
같은 간격 소비를 확인했다. 셀 경로가 이미 쓰는 control_is_width_neutral_marker로 소유를
판정해 배치 상자가 없는 메타데이터와 표·그림 등 개체 호스트를 구분한다. 저장 LineSeg가
있는 문단과 별도 상자를 소유하는 컨트롤은 이 재조판 간격 경로에 넣지 않는다.

두 공통 경로를 함께 수정한 뒤 수식 영향 7쪽과 평가결과서 2쪽을 먼저 실제 비교한다.
원본·Print·측정 임계값·회귀 기대값은 바꾸지 않는다. 방향 확인 전 전체 빌드·전쪽 반복을
늘리지 않으며 Native 개선 뒤 fresh WASM과 최종 필수 검증을 완료한다.

### R18 결과와 실제 설치 프로그램 진단

Native 평가결과서 2쪽은 최저 93.90%→97.02%로 개선됐고 제목 원점이 Print와 맞았다.
수식 7쪽은 변화가 없었다. 실제 Skia FontMgr의 두 이름 모두 7개 style 프로그램 중 한글
coverage는 별도 HGSMJ에만 있었다. 공통 후보 연결 뒤에도 새 이름 체인에 CSS용 따옴표를
넣으면 내부의 원시 family 이름과 다르다. 내부 체인은 따옴표 없는 실제 가족 이름으로
전달하고, SVG/Canvas의 CSS 문자열 해석과 Native의 원시 이름을 구분한다.

원본 Print 18쪽의 아래첨자 r→등호 전진은 44 인쇄 단위, r→합 기호 전진은 31 단위다.
글리프 자신의 전진과 첨자의 꼬리 여백을 제외하면 등호에는 앞 여백이 있고 합 기호에는
추가 앞 여백이 없다. 현재 항 파서는 `[첨자, Row(등호, 다음 첨자), Row(합 기호, ...)]`를
만든다. 투명 Row의 첫 연산자가 행 첫 항으로 취급되어 등호 앞 여백이 빠졌다.
명시 Group·첨자 소유는 유지한 채 투명 항 Row의 문맥을 공유한다. 기존 명시 face 계약은
유지하고, 생략 필드 세대의 합 기호에는 첨자의 꼬리 여백을 중복 가산하지 않는다.
이 기대는 PDF 원시 Tf/Tm·Type3 전진과 두 크기 Print 관찰을 근거로 한다.

R18의 Native 후보 빌드는 exit 0, 수식 시각 검증은 exit 1이었다. 회귀 기대값을 바꾸지
않았다. 원본과 PDF를 새로 만들지 않고 다음 후보의 실제 방향을 다시 확인한다.

### 브라우저 CanvasKit 소비 경로의 별도 확인

새 구형 수식의 HancomGlyphs는 한양신명조 등의 선언 family chain과 scalar별
고정 전진을 발행한다. Native는 문자 coverage를 확인하지만 CanvasKit의 기존
분기는 family chain 전체로 한 face를 조회해 어느 한 글자가 없으면 런 전체를
거절한다. host 준비도 chain 전체의 단일 이름을 조회해 분할 프로그램을 누락한다.
Canvas2D Visual Sweep 통과만으로 이 CanvasKit 경로를 입증하지 않는다.

공통 local-fonts의 resolveRendererLocalFontCandidates와 CSS family parser를
준비·paint가 같이 사용한다. 같은 family/style의 실제 분할 프로그램을 준비하고
scalar별 coverage를 사전 검사한 뒤 producer의 positions·baselineShift·shears를
그대로 재생한다. 모든 문자가 준비되기 전에는 일부만 그리지 않으며 임의 기본
글꼴·고정 좌표 보정을 추가하지 않는다. 이 경로의 portable mock 진단과 실제
CanvasKit 브라우저 실행을 구분해 확인한다. 정식 렌더 회귀 추가는 전쪽 Native/
fresh WASM 90% 선행 조건 이후 진행한다.

브라우저 보정의 기본 확인: 기존 host-font-provider·declared FontGlyph Node 검사는
exit0이며, tsc --noEmit는 nullable 보조 face를 걸러내는 보정 후 exit0이다.
ignored output의 positioned-equation-contract-probe는 6/6건 통과했다. 첫 진단의
provider mock에서 필수 subscribe를 빠뜨려 host가 활성화되지 않았던 오류를 고쳐
재실행했다. 이는 제품의 오류로 분류하거나 기대값을 완화한 것이 아니다.

실제 CanvasKit WASM 엔진에도 현재 시스템의 ENSMJ/HGSMJ/FLSMJ 프로그램을 공급해
`보험자수x=1`을 실행했다. 첫 영문 프로그램에 한글 glyph ID0이 있음을 확인했고,
동일한 위치 배열에서 한글·영문 프로그램 선택과 paint 성공·PNG 생성을 확인했다.
이 설치 프로그램을 저장소에 복사하거나 배포하지 않는다. 이 진단은 실제 API 소비
증거이며 독립 Print의 전쪽 시각 검증 또는 fresh rhwp WASM의 최종 브라우저 검증을
대체하지 않는다. 새 정식 렌더 회귀는 선행 시각 조건 완료 후 등록한다.
