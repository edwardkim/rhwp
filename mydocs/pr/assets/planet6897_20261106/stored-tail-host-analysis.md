# 표 뒤에 저장된 빈 호스트 줄의 프레임

2026-11-06, 기반 `0c3278967f`와 base `45684640be5eddcf5972b063260250345b34d928`에서
[628 보고서 원본·Print](pr8642/report-628-print-reference.md)를 보정했다.
96 DPI, compat2022, 설치된 시스템 글꼴과 정식 웹 공급 경로를 사용했다.
원본·독립 Print PDF는 변경하지 않았다.

## 원본의 두 닫힌 구간

원시 CFB의 `BodyText/Section3`과 해당 PARA_LINE_SEG를 직접 읽어 모델 진단과 대조했다.

| 대상 | 앞 문단의 저장 끝 | 표 본체와 위·아래 여백 | 빈 호스트 줄 위치 | 다음 문단 위치 |
| --- | --- | --- | --- | --- |
| 59쪽 표, 문단 160 | `3960 + 1100 + 880 = 5940` | `49585 + 283 + 283 = 50151` | `5940 + 50151 = 56091` | `56091 + 1150 + 920 = 58161` |
| 143쪽 표, 문단 842 | `0 + 1150 + 920 = 2070` | `13386 + 283 + 283 = 13952` | `2070 + 13952 = 16022` | `16022 + 1150 + 920 = 18092` |

모든 수치는 원본 HWPUNIT다. 이 호스트의 저장 위치는 표 앞이 아니라 표 외곽 뒤다.
조판의 현재 pen과 뒤 문단의 끝은 이미 맞았지만 paint 원점에서 위 바깥 여백 283 HU가 빠졌다.
현재 pen에서 표 윗변을 잡아야 하며 저장 호스트 vpos를 표 앞의 원점으로 읽으면 안 된다.

## 공통 생산과 실제 소비

선행 `d5f49fb4b7`(#7620)은 통째로 들어가는 표도 바깥 여백을 보존했고,
`dbf0107c9d`(#8149)는 원본 원점·간격을 인증한 경우에 같은 상자를 소비한다.
기존의 표 앞 호스트·저장 단 프레임·분할 계약은 유지한다.

- `ParagraphFloatPlacement::from_stored_tail_host`는 위의 두 닫힌 구간과 현재 측정 높이를
  확인해 현재 pen에서의 `table_top`과 호스트 줄을 포함한 `occupied_bottom`을 함께 생산한다.
- `typeset/table/block/entry.rs`는 기존 whole-fit 판정과 실제 예산을 통과한 경우에만 이
  결과를 발행한다. 기존에 인증한 프레임은 우선하며 분할을 억지로 통째 배치하지 않는다.
- `place_table_with_text`는 같은 `occupied_bottom`까지 전진한다. 빈 호스트 줄을 다시 더하지 않는다.
- `layout_table_control_block`·`layout_table`은 같은 `table_top`을 최종 원점으로 소비한다.

가시 호스트, 편집·합성·없는 저장 줄, 별도 흐름 개체가 있는 앞 문단, 다른 상대 기준,
측정 높이가 증가한 표, 닫히지 않는 간격은 수용하지 않는다. 표 앞 호스트는 첫 등식이
성립하지 않는다. 문서 ID·행열 수·높이 임계값으로 분기하지 않았다.
