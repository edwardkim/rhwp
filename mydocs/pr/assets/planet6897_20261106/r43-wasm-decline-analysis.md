# R43 새 base 대비 WASM 하락의 원인 분석

검토 기준은 base `5077b216cbc51d2046da07350de562f6f521a7c1`, 후보
`0261687265f3a10a64e51809d006b2305a36d950`이다. 사용자 지정 허용폭 0.1%p를 적용한다.
Native 73조합에서는 허용폭 초과 하락이 없지만, WASM 원 PR군 56조합에서는 5쪽이 해당한다.
기존 허용폭이나 TSV를 변경하지 않는다.

## 실제 글꼴 요청과 원점 대조

정책연구 신청서의 2020·2024 Print 대조에서 각각 0.24·0.25%p 하락했다.
실제 Canvas 호출을 기록한 진단 PNG는 공식 후보 PNG와 RGBA가 같았다.
제목은 합성 굵기 윤곽 경로가 아니라 기존 `fillText`를 사용하며, 같은 글꼴 descriptor와
같은 공급 바이트에서도 첫 글자 원점이 base 292.920에서 후보 298.493으로 바뀌었다.

선행 메인터너 보정 `2135140180`은 미분류 원본 슬롯의 실제 TrueType 전진을 요청한다.
Native 공급자는 실제 프로그램의 family(name ID 1·16·21) 또는 PostScript 이름을 확인한다.
반면 WASM 공급 목록은 표시용 full name(ID 4)도 검색 이름으로 포함하므로,
`나눔고딕 Bold`를 보통 family의 원본 전진으로 수용했다. 해당 프로그램의 실제 family는
`NanumGothic`·`나눔고딕`, PostScript 이름은 `NanumGothicBold`이며 요청과 다르다.
Native는 이 프로그램을 원본 전진으로 수용하지 않아 같은 하락이 없다.

소비 경로는 `native_otf_font_requests → prepare_native_otf_fonts_multiple_with →
register_otf_for_source → uses_original_truetype → char_width_decision`이다.
보정은 공급자를 신뢰하기 전에 공통 DocumentCore 경계에서 원본 family 소유를 확인한다.
표시용 별칭과 fallback은 계속 사용할 수 있지만 다른 프로그램의 전진을 원본으로 인증하지 않는다.
저장소 소유 공개 글꼴로 family·PostScript 양성 대조와 full-name·다른 family·fallback 반례를
확인한다. 원 HFT 표시 프로그램의 기존 별칭 계약은 유지한다.

## 나머지 세 쪽

법제 중간보고 5·10쪽과 심판 보고 49쪽은 실제 경로와 독립 PDF를 추가 대조 중이다.
앞 두 쪽의 원본 휴먼명조 굵은 글자에는 윤곽 fill+stroke가 적용된다. 이 사실만으로
합성 굵기를 제거하거나 모든 선의 최소 폭을 변경하지 않는다. PDF의 글꼴·선 폭·변환과
실제 paint를 대조하여 원인을 확정한 뒤 보정한다. 아직 전체 해결이나 제출 가능으로 판정하지 않는다.

진단과 재검증 로그는 `output/pr-review/planet6897-integration-20261106/logs/`에 두며,
공식 새 source의 측정값과 일치 여부를 확인하기 전 진단 출력을 제출 증적으로 승격하지 않는다.


## 법제 보고서 두 쪽의 동일 반례

전체 픽셀을 확인한 결과 두 쪽의 미일치 94픽셀은 제목의 「·」에만 모였다.
공급된 휴먼명조는 한글 CFF와 같은 family의 TTF 동반 face를 함께 사용한다.
CFF에는 「·」가 없고 TTF에는 있다. 그러나 불완전한 coverage에서는 뒤 family가
선택되어 합성 굵기의 윤곽으로 대체됐다. CFF가 소유한 글자는 기존 경로를 유지하고,
등록된 CFF가 소유하지 않는 글자는 실제 CSS 사다리를 아는 Canvas에 맡긴다.
명시 원 TTF 별칭의 우선권은 유지한다. 공개 CFF·TTF를 공급한 실제 브라우저 반례는
수정 전 `분리 CFF의 누락 글리프는 동반 face를 아는 Canvas에 맡겨야 한다`로 실패했다.

선 폭을 0.02em으로만 그린 별도 원인 분리 진단은 이 두 쪽의 94픽셀을 해결하지 못했다.
PDFium AGG의 `RasterizeStroke`도 실제 최소 장치 폭을 적용함을 공식 구현에서 확인했다.
따라서 인쇄 합성 굵기의 최소 선 폭은 변경하지 않는다. 보고서 49쪽은 계속 별도로 분석한다.
공식 구현 참조: https://pdfium.googlesource.com/pdfium/+/refs/heads/main/core/fxge/agg/cfx_agg_devicedriver.cpp


## 심판 보고서 49쪽의 중복 소비

원본 326번 문단은 TAC 표 뒤에 독립된 공백 줄을 저장한다. 다음 327번 문단은
`3. 한국과 일본의 현황비교` 제목이다. 기존 Native에서도 같은 제목이 아래로 밀려 있지만
새 WASM의 올바른 굵기 윤곽이 이 기존 배치 오차를 더 드러냈다. 굵기를 가늘게 해서
점수만 되돌리는 대신 문단 끝의 간격 소유를 보정한다.

실제 `RHWP_DEBUG_TAC_CURSOR` 기록에서 Table 항목은 `393.9 → 574.6`, 뒤
PartialParagraph 항목은 `574.6 → 611.9`로 전진한다. 두 항목이 모두 동일한 문단 아래
간격 13.333px를 더한다. 이는 원본 단위를 환산한 진단 관측이며 구현의 고정 보정값이 아니다.
수용 측에서는 뒤 줄을 방출했고, paint의 `tac_text_tail_spacing_after`는 보이는 글자가
없다는 이유로 소유를 인정하지 않았다. 기존 partial 경로는 독립 저장 줄을 이미 보존하므로
가시성 판단과 실제 물리 줄 소유가 갈린다.

보정 경로는 수용한 `Table → PartialParagraph` 항목 → 독립 저장 꼬리 판정 →
Table에서 아래 간격 보류 → 꼬리 줄 배치 → 마지막 항목에서 한 번 소비다.
독립 저장 줄 판정은 기존 partial 경로의 로직을 작은 공통 helper로 옮겨 재사용한다.
표와 같은 줄의 공백 캐리어, 저장 정보가 없는 임의 공백은 독립 꼬리로 승격하지 않는다.
새 관계형 계약은 같은 문단의 가시 Footer를 같은 길이의 공백으로 바꾸고, 아래 간격을
변경해도 자기 꼬리가 움직이지 않으며 다음 문단만 원본 간격만큼 이동하는지 검사한다.
기존 가시 꼬리·혼합 표/도형의 간격 검사를 함께 실행한다.


## 첫 보정의 집중 검증

최소 공개 글꼴 환경에서 `native_pua_host_font_protocol` 18건이 실제 통과했다.
새 원본 family 소유 반례는 보정 전 1건 실패, 보정 후 통과했으며 기존 프로토콜도 유지했다.
분리 CFF 동반 face 반례는 기존 026 WASM에서 실제 실패했다. 수정한 source의 새 WASM
빌드·브라우저 통과·실물 5쪽 및 전쪽 재측정은 아직 완료하지 않았으므로 이 커밋을 제출 가능
판정으로 사용하지 않는다. 기존 전체 Rust 12,910건은 026 source의 결과로 보존한다.


## 공백 꼬리 반례와 적용

첫 합성 입력에서는 새 뒤 문단의 문자·서식 정보가 빠져 `Following`이 방출되지 않았다.
그 실행은 제품 결함의 검출 증거로 쓰지 않는다. 문단 생성 API와 글자 모양으로 입력을
보완한 뒤 실제 실패를 확인했다. 수정 전 꼬리/뒤 문단 y는 아래 간격 0·600·1200 HU에서
각각 `(219.36,232.6933)`, `(227.36,248.6933)`, `(235.36,264.6933)`이었다.
자기 꼬리가 움직이고 뒤 문단이 간격의 두 배만큼 이동하는 결함이다. 이 수치는 진단 관측이며
새 assertion은 이 좌표를 고정하지 않고 원본 간격의 변화량과 줄 소유를 검사한다.
공통 보정은 별도의 문서 식별자나 px 보정값 없이 독립 저장 꼬리 판정을 재사용한다.
다음 단계에서 새 source의 집중 회귀·fresh WASM·실물 하락 5쪽을 검증한다.
