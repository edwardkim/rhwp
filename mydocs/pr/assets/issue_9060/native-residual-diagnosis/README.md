# Native 2·5·12쪽의 잔여 차이 원인

> 이 문서는 당시 단계의 분석 기록이다. 최종 결과와 대표 증적은 [검증 기록](../verification-record.md)과 [최종 대상 증적](../final/main/README.md)을 따른다. 원시 로그·중간 분석 JSON·중간 PNG는 제출에서 제외했다.

2026-11-14 검토. 세 쪽 모두 100.00%가 불가능한 상태는 아니다. 원본 조판을 유지한
분리 진단에서 **2·5·12쪽 모두 2px raw 실루엣 100.00%, 미대응 0개**를 확인했다.
이 폴더는 원인 분석 자료다. 제품 코드의 보정 완료나 최종 전쪽 TSV로 대신하지 않는다.
이후의 실제 코드 보정과 제품 출력은 [Native 제품 보정 단계](../native-print-stage/README.md)에 있다.

## 같은 입력의 분리 대조

입력·독립 한컴 Print PDF의 SHA와 producer는 [실행 기록](../verification-record.md)에 있다.
Print profile, 2022 호환 조판, 96 DPI, 기존 2px raw 지표를 유지했다. PDF를 재산출하거나
비교 영역·마스크·임계값·원점·글자 크기·장평·전진 폭을 바꾸지 않았다.

| Native 조건 | 2쪽 | 5쪽 | 12쪽 |
| --- | ---: | ---: | ---: |
| 현재 제품 | 99.98% / 20개 | 99.98% / 17개 | 99.72% / 219개 |
| 맑은 고딕 6.68만 명시 공급, 제품 재생 유지 | 99.98% | 99.98% | 99.72% |
| 글자 기하 재생만 분리 적용, 기존 글꼴 | 100.00% / 0개 | 100.00% / 0개 | 99.99% / 8개 |
| 글자 기하 재생과 PDF에 맞는 6.68 프로그램 공급 | **100.00% / 0개** | **100.00% / 0개** | **100.00% / 0개** |

퍼센트 뒤의 개수는 색상 경계 보정 전 미대응 내용 픽셀 수다. 100.00%는 위 raw 지표의
값이며 엄격한 RGB 픽셀 동일성을 뜻하지 않는다. 설치 글꼴 파일은 이 폴더에 포함하지 않는다.

## 첫 번째 원인: Native의 글자 재생 정책

현재 `PageLayerTree::preserves_raster_text_geometry()`는 명시적인 이전 인쇄 세대에서
false를 반환한다. `skia/cache.rs`가 이 값을 전달하고, `text_replay/fonts.rs`의
`preserve_geometry`와 `draw_positioned_cluster`가 실제로 소비한다. 기하 경로는 힌팅과
baseline snap을 끄고 단색 SFNT의 단일 문자 윤곽을 같은 원점에 재생한다. 기존 경로는
`canvas.draw_str`를 사용한다. 본 실험은 이 설정 묶음의 차이를 입증하며 힌팅과 glyph cache의
기여도를 각각 따로 측정한 것으로 표현하지 않는다.

현재 Native의 잔여 차이는 주로 맑은 고딕 본문의 `기·준·및·받` 등의 획이다. 5쪽에서
사용자가 지적한 첫 본문 줄은 이미 미대응 0개이며 나머지 17개는 표의 다른 글자에 있다.
원본 문단·표 분할이나 첫 줄의 위치를 다시 옮겨 해결할 문제가 아니다.

[진단 코드](../verification-record.md)는 2022 호환에서 만든 실제 페이지의 root·스타일·
좌표·자원을 유지한 채 글자 재생 정책을 분리한다. 자원을 바꾼 뒤 layer JSON 전체가
`rasterTextGeometry` 한 값 외에는 같다는 assertion을 통과해야 렌더링한다.
제품의 세대 선택이나 제출용 `--compat` 값을 바꾸어 얻은 수치가 아니다.

## 두 번째 원인: 맑은 고딕의 숫자 윤곽 버전

PDF의 `/F9`는 `INPILL+MalgunGothic`, CIDToGIDMap은 Identity다. PDF의 ToUnicode와
내장 FontFile2를 읽고 CID에 해당하는 glyf 좌표·contour·flag·hmtx를 로컬 프로그램과 직접
대조했다. 추출한 사설 글꼴 프로그램을 파일이나 배포물로 추가하지 않았다.

설치된 6.50과 Windows의 6.68은 비교한 한글 `기·준·및·받·항`의 윤곽과 전진 폭이 모두
PDF와 같다. 반면 숫자 `1·4·6`은 6.50의 윤곽이 PDF와 다르고 6.68의 윤곽은 같다.
전진 폭은 두 버전 모두 같으므로 폭 보정으로 대체하면 안 된다.
[글리프별 실제 대조](../verification-record.md)를 따른다.

글자 재생 정책만 분리했을 때 12쪽에 남은 8개는 숫자와 `항` 주변의 획 끝에 있다.
같은 기하 재생에서 6.68을 명시 공급하자 그 8개도 없어졌다. 따라서 글꼴 버전만 바꾼
첫 대조의 수치가 같았다는 이유로 글꼴의 영향을 없다고 판정할 수 없다.

## 기존 해결 PR과 제품 반영의 경계

글자 기하 재생의 선행 근거는 [#8153 글리프 정밀도 분석](../../../../plans/issue_8153_print_glyph_precision_20261027.md),
이전 인쇄 세대를 구분한 이유는 [#8389 리베이스 후 기존 Print 보존 분석](../../../../plans/issue_8153_rebase_legacy_print_text_20261030.md)에 있다.
공통 경로를 무조건 전환하면 이때 보호한 이전 인쇄 세대의 출력도 바뀔 수 있다.
HWP 사양은 이 저수준 힌팅 방식을 강제하지 않는다. 특정 문서·쪽·글꼴 이름에 따른
제품 예외나 좌표 보정을 추가하지 않는다.

현재 제품 코드와 상위 폴더의 최종 제출용 TSV는 그대로다. 이 분석의 100%를 제품의 최종
결과로 옮겨 적지 않는다. 실제 공통 경로를 보정한다면 정상 대조군과 정본 보호 대상의
하락 여부를 재검증해야 하며, 그 완료 전에는 보정 완료나 PR 승인으로 판정하지 않는다.
