# #7203 — 저장 사다리 되감김 경계의 조각 컷이 마지막 줄의 줄간격을 요구했다

`#7203` 네 갈래 중 **조각 컷** 갈래의 구현·검증 기록이다. 앞선 PR #7221 이 같은 이슈의
**페인트 원점** 갈래를 닫았고, 이 문서는 그 위에서 컷을 다룬다.

- 재현물: `samples/hwpctl_API_v2.4.hwp` (저장소 기존 샘플)
- 정본: `pdf/hwpctl_API_v2.4-hwp-2020.pdf` (한/글 engine 2020, 105쪽)
- base: `fcbd00e0f` (upstream/devel) + PR #7221 의 커밋

## 1. 증상

쪼개지는 빈-host 자리차지 표(1×1 `RowBreak`)의 **첫 조각이 셀 줄 하나를 잃는다.**

`hwpctl_API_v2.4.hwp` 52쪽(0-based 51) `Example` 코드 상자에서 정본은 세 줄
(빈 줄 + 코드 두 줄)을 담는데 rhwp 는 두 줄만 담았다. 잃은 줄이 뒤로 밀리면서, 허용치가
없는 조건(`#7035`)에서는 **두 줄짜리 고아 쪽**이 생겨 총쪽수가 105 에서 106 이 됐다.

## 2. 근인 — 예산이 그 줄의 **줄간격**까지 요구했다

컷 예산 분해(`RHWP_TABLE_DRIFT=1`, `RHWP_DIAG_6368=1`):

```text
  TABLE_SPLIT_AVAIL  pi=1274  table_avail=876.9  cur_h=809.3  host_before=3.8
                              page_avail=63.8
  DIAG_6368 cap-cut  j=2  h=42.67  u_h=21.33  avail=63.68  over=0.32
```

세 유닛의 전진값 합은 `3 × 21.33 = 64.00` 이고 예산은 `63.68` 이다 — **0.32px** 초과로
마지막 줄이 거부됐다. 초과분의 정체는 **마지막 줄의 줄간격**(`600 HU = 8.0px`)이다.
조각 상자는 그 줄의 줄 높이에서 끝나고 뒤따르는 줄간격은 다음 쪽의 것이므로, 그 항은
쪽 예산에 들어가지 않는다.

### 문서 자신이 그 값을 적어 뒀다

문단 1274 의 칸(`pad=(510,510,141,141)`) 줄 사다리는 `0 · 1600 · 3200` 뒤 `0` 으로
되감긴다(`p[2].ls[1]`). 즉 저장본이 **세 줄 뒤**를 물리 쪽 경계로 지목한다. 그리고 표의
선언 높이 `common.height = 4482 HU` 는 그 세 줄을 **줄간격 트림과 함께** 담은 상자와
정확히 같다.

```text
  pad 141 + 1600 + 1600 + lh 1000 + pad 141 = 4482 HU   = 선언 높이 · 정본 상자
  pad 141 + 1600 + 1600 + 1600    + pad 141 = 5082 HU   = 트림 없이 요구한 값
```

### 정본도 같은 말을 한다

`pdf/hwpctl_API_v2.4-hwp-2020.pdf` 52쪽(0-based 51)의 조각 상자 괘선과 글자 줄:

```text
  상자 윗변  940.73      아랫변 1000.51      높이 59.78px = 4482 HU
  글자 줄    964.91 · 986.19                 (빈 첫 줄은 글자가 없다)
```

## 3. 같은 트림이 이미 있었고, 게이트가 이 경우를 뺐다

`table_layout.rs` 의 `native_multirow_saved_reset_trailing_trim`(`#3931`)이 **같은 규칙**을
이미 구현한다 — *"저장 reset 직전 마지막 가시 줄의 trailing 공백을 물리 쪽 경계에서
제외"*. 그 helper 는 두 조건으로 이 경우를 뺀다.

| 게이트 | 문단 1274 |
| --- | --- |
| `table.row_count <= 1` → 0 | 1행 표라 즉시 제외 |
| `next_unit.para_idx > previous_unit.para_idx` | 되감김이 **같은 문단 안**(2 → 2)이라 제외 |

즉 기존 트림은 **문단 경계** reset 만 본다. 한/글은 문단 중간에서도 쪽을 넘긴다
(`ls[i].vpos > 0` → `ls[i+1].vpos = 0`). 수정은 그 경계에도 같은 계약을 준다.
문단이 끝나지 않으므로 `spacing_after` 는 더하지 않고 **줄간격만** 트림한다.

### 되감김 하나만으로는 부족했다 — 실측으로 확인했다

처음 구현은 조건을 "문단 안 사다리 되감김"까지만 요구했다. 전체 회귀에서 **8건이 깨졌다.**

```text
  oracle_page_count_baseline  partition 1 · 7 · 12      (쪽수 정답지 드리프트)
  body_overflow_baseline      partition 3               (본문 넘침 증가)
  issue_3931_keeps_pr4763_hwp_page_count_contract
  issue_1891_hwp5_origin_hwpx_export_reparse_keeps_page_count
  issue_3820_hwp5_qa_rowbreak_tail_reduces_page_count
  issue_1686_hwp_matches_pdf_page_count_and_page5_boundary
```

문단 안 되감김은 **물리 쪽 프레임**일 수도, 공간이 남은 **로컬 재시작**일 수도 있다
(기계 문서의 촘촘한 리셋 — `#1658` 낭비 쪽 회귀의 근거이며, `is_stored_frame_rewind` 가
본문 절반 바닥 검사로 막으려는 바로 그 무리다). 넓은 규칙은 그 둘을 섞었다.

둘을 가르는 것은 **문서 자신**이다. 위 §2 의 동일성을 조건으로 세웠다 — 트림을 적용한
조각 상자가 저장 `common.height` 와 같을 때만 그 되감김을 쪽 프레임으로 인정한다.

```rust
  fragment_box = consumed_before + (last_unit_height - trim) + pad_top + pad_bottom
  |fragment_box - hwpunit_to_px(table.common.height)| <= 0.5   // 아니면 트림 0
```

이 동일성은 컷이 **첫 조각**일 때만 성립하므로(누적값이 셀 시작부터여야 한다) 이어받는
조각에는 저절로 적용되지 않는다. 좁힘 뒤 위 8건은 전부 통과하며, 목표 사례의 출력은
넓은 규칙과 **한 픽셀도 다르지 않다**(표 상자 280개 전수 동일).

### 왜 `stored_frame_break_before` 를 쓰지 않았는가

이 유닛의 `stored_frame_break_before` 는 `false` 다. `is_stored_frame_rewind` 가 셀-로컬
사다리를 **본문 절반**(438.44px)이라는 절대 바닥과 견주기 때문이다 — 이 칸은 본문 바닥
근처에서 시작해 첫 프레임이 56px 밖에 안 되므로 그 검사를 통과할 수 없다. `cell_units`
는 쪽 위치를 모르는 캐시라 그 검사를 쪽 상대로 바꾸는 것은 이 PR 범위를 넘는다
(`#7203` 에 남겼다). 트림은 쪽 위치가 필요 없는 신호(사다리 되감김)만 쓴다.

## 5. 유닛 보존과 뒤 내용 — 표 상자 전수 대조

문서의 `Table` 노드 **280개** 중 움직인 것은 4개뿐이며, 모두 이 경계와 그 뒤다.

| 쪽(1-based) | 문단 | 수정 전 (y, h) | 수정 후 (y, h) | 뜻 |
| ---: | ---: | --- | --- | --- |
| 52 | 1274 | 941.70, 46.70 | 941.70, **62.60** | 첫 조각이 유닛 하나를 얻었다 |
| 53 | 1274 | 136.00, 336.03 | 136.00, **314.70** | 이어받는 조각이 같은 유닛만큼 줄었다 (−21.33) |
| 53 | 1281 | 618.00, 24.90 | **596.60**, 24.90 | 뒤 내용이 유닛 하나만큼 올라왔다 |
| 53 | 1296 | 938.13, 81.09 | **916.80**, 81.09 | 같음 — 그리고 넘침이 사라졌다 |

마지막 행이 중요하다. 수정 전 문단 1296 의 표는 하단 `1019.22` 로 본문 바닥 `1009.15` 를
**10.05px 넘었다**. 수정 후 `997.89` 로 본문 안에 들어온다.

글자 위치도 정본과 맞는다.

```text
  정본      964.91 · 986.19
  수정 후   964.90 · 986.30      (차 −0.01 · +0.11)
```

## 6. 반례 — 이미 맞던 경계는 움직이지 않는다

같은 문서 문단 1342 도 같은 종류의 되감김 경계를 가진 분할 자리차지 표다
(셀 `p[1].ls[11]` 에서 `vpos = 0`). 그 표는 예산이 넉넉해 트림 없이도 이미 그 경계를
맞추고 있었다.

```text
  DIAG_SCAN CUT_TRY  budget=278.4  consumed_h=256.0  end_cut=[12]      (12유닛 = 256.0px)
```

수정 후에도 `(731.80, 260.00)` / `(136.00, 145.30)` 그대로다 — 트림은 예산이 줄간격만큼
모자란 경우에만 발화한다.

## 9. 잠그지 않은 것 — `#7203` 에 남는다

- **조각 상자의 아래변.** 수정 후 `1004.30`, 정본 환산 `1001.48` — 2.8px 낮다. 컷과 글자
  위치는 트림을 소비하지만 상자 **높이 계산**(`row_block_content_height`)은 아직 아니다.
  같은 문서에서 조판이 보고하는 조각 소비도 `67.8`(트림 없는 값)로 남아 있다.
- **조판 원점과 페인트 원점의 3.64px 차이.** 이 형상에서 조판은 흐름 누적값
  (`cur_h 809.3`)으로, 페인트는 저장 사다리(`941.70 − om`)로 원점을 잡는다. 시험 구현으로
  조판을 페인트 원점에 맞춰 봤을 때 예산은 `63.8 → 67.4` 로 고쳐졌지만 이 문서의 출력은
  **한 픽셀도 바뀌지 않았다**(표 상자 280개 전수 동일). 출력으로 입증되지 않으므로 이 PR 에
  넣지 않았다.
- **비분할 경로**(`fragment_outer_top_px = 0`)와 `is_stored_frame_rewind` 의 절대 바닥 검사.
