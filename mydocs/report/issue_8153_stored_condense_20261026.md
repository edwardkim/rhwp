# #8153 저장 줄의 공백 압축 구현과 검증 기록

브랜치: `task/8153-handbook-raw100`. [구현 계획](../plans/issue_8153_stored_condense_20261026.md)의
공통 원인과 독립 Print 근거를 따른다. 두 원본과 기존 기준 PDF를 그대로 사용한다.

## 구현

LEFT/RIGHT/CENTER 문단의 줄이 원본 공백 최소값의 예산으로 수용되면 내부 ASCII 공백에만 압축을 배정한다.
`composer::condense_space_savings_px`는 기존 HU 단위 줄 수용 예산을 재사용한다.
`CondensePlan`은 선두 공백·말미 구분 공백·nbSpace·원자적 필드를 제외하고 run별 원본
공백 폭에 비례해 같은 예산을 소비한다. 공백 최소값이 없거나 예산이 부족한 줄과
Justify/Split의 기존 계약은 이 새 배정의 적용 대상이 아니다.

공통 결과는 `TextStyle.space_compression`으로 전달한다. 문자 폭의 최종 결정은 원 글자·
자간 측정 뒤에 해당 ASCII 공백의 전진만 줄인다. exact/unrounded 폭과 glyph positions가
같은 결정을 소비한다. 인라인 경계의 `for_text_fragment`도 원문 scalar 범위를 이어받는다.
실제 run의 positions를 게시하므로 Native/Canvas가 별도 글꼴 측정으로 압축을 잃지 않는다.
정렬 기준 폭은 같은 계획의 실제 소비량을 사용한다. 문서 IR·글꼴·저장 줄 소속은 바꾸지 않는다.

## 현재 검증 상태

- 최초 구현 `1a22f15c6cddecc85b0cbc2946425cc01d4cdf9e`의 Native 빌드는
  `release-test`, `native-skia`, 공유 `target/pr-review`, jobs 8로 9분 38초에 통과했다.
  실제 출력 검증과 최종 필수 테스트는 아직 완료하지 않았다.
- 기존 producer `5bcb654516968c64d5c3910aeb556fe5e3eebe72`에서 두 원본의
  긴 줄 `관` 전진은 10.759259259259252px, 같은 글자모양의 짧은 줄은 11.04px였다.
  최종 관계형 검사 원문으로 두 원본 모두 동일한 전진 차이에 따른 FAIL을 다시 확인했다.
  검사 SHA-256은 `669b58af6d783d959fa9185ffe598d15d3eedebc627ae840c90ab8bb57058252`다.
- 최초 구현의 집중 검사에서 선두 공백 run 분할 뒤에도 이전 run 수로 만든
  `unjustified_leading_spaces` 배열을 사용해 인덱스 오류가 발생했다. 기존 fragment 검사와
  새 공백 검사에서 확인했다. 실제 배치 run 분할을 확정한 뒤 같은 소유 배열을 생성하도록
  생산 순서를 수정한다. 범위 밖 인덱스의 값을 임의로 0으로 대신하지 않는다.
  최초 빌드·실패 로그와 producer는 보존하고 수정한 새 source에서 다시 빌드·검증한다.
- 기존 fresh WASM 표준 최적화가 사용하는 고정 checkout과 공유 target을 보존한다.
  최적화 종료·산출물 동결을 확인한 뒤에 Native 컴파일을 시작했다. 표준 최적화 WASM
  `5bcb654516`의 실제 공통 기호 검사 API와 Canvas 폰트 등록에서 빈 기호의 후속 글꼴
  선택을 확인했고, 두 문서 집중 102쪽에서 200쪽만 125→14픽셀로 개선됐다. 다른 쪽은
  기존 결과와 같다. 이는 공백 압축 보정 전 기호 복구의 증거이며 새 구현의 증거와 구분한다.
- 두 원본 200쪽과 정상 대조군의 직접 출력·기존 #7418/#7702 검사, 전쪽 TSV 및 최종
  필수 검증은 계속 수행한다. 현재 기록은 시각 개선 완료나 PR 준비 완료 판정이 아니다.

## 마지막 줄의 Justify 계약 재사용

소유 배열을 정정한 `7e8e5e9e02`는 12분 27초에 빌드됐고, 집중 60건이 모두 통과했다.
동일 원본 Native 집중 102조건에서 두 형식의 116쪽은 미대응 1→0, 200쪽은 14→0,
328쪽은 21→0픽셀로 개선됐다. 116·200쪽의 Print/수정 전/후 PNG를 직접 확대 판독했고,
진단 대상 글자·공백 원점과 독립 PDF의 최대 차이는 각각 약0.10px·0.30px였다.

반면 두 형식의 148쪽은 172→190, 327쪽은 9→24픽셀로 하락했다. 전체 확대를 보류하고
해당 줄의 원본·Print를 먼저 조사했다. 문단은 Justify인데 `needs_justify`가 거짓인
마지막 줄을 LEFT 문단과 같은 원본 condense 계약으로 처리한 것이 원인이다.
각 문서 ID를 조건으로 좁히지 않고 문단 정렬과 실제 여백 부호를 구별한다.

기존 `848df0676f`와 `task_m100_7642_stage3720.md`의 공통 Justify 압축을 재사용한다.
마지막 줄도 음수 여백에서는 20% 공백 한계와 잔여 글자 사이 압축을 소비하며, 양수 여백은
늘리지 않는다. `justification_spacing::measure`에서 측정한 말미 공백·signed 자간을 포함한
동일한 여백을 계약 선택과 기존 압축 helper가 사용한다. 선택한 run 분할과 소유 배열을 실제
배치에도 전달한다. Split·탭·억제 셀·양수 여백의 기존 계약은 유지한다.

새 `issue_8153_justified_final_line_compression.rs`의 독립 Print 전진 구간 검사 4건을
고정된 `7e8e5e9e02`에서 각각 실행해 전부 FAIL을 확인했다. 검사 SHA-256은
`bd90b2a2d082138cf8d93e9a4fe37410c53608e0c033789f42f24293eec29742`다.
`d394351f0fb4c037f793080cf4b23f6121ea1ffc`는 Native 빌드 6분 42초와 집중 검사
64건을 모두 통과했다. 두 형식의 집중 102조건에서 116·200·300·328쪽은 미대응
0픽셀이다. 148쪽은 172→102픽셀로 개선됐고, 327쪽은 기존 9픽셀로 돌아왔다.
64건 통과를 전쪽 검증이나 최종 완료로 대신하지 않는다.

반면 두 형식의 80·85·86·87쪽은 각각 49·46·46·38픽셀 늘었다. 증가 영역은
서명 표 안의 날짜 줄이다. 실제 원본은 JUSTIFY·condense70·8pt이며 날짜의 숫자
전진은 수정 전 5.150833px, 수정 후 5.534545px다. 독립 Print의 전진은 약
5.4404~5.6001px로 수정 후가 맞지만, 같은 줄의 원점은 약 3.8px 오른쪽이다.
날짜 문자열·숫자·문서 ID로 압축을 예외 처리하거나 올바른 전진을 되돌리지 않는다.

80쪽의 서명 표에서 date 셀 시작 전 원본 폭의 합은 23,456HU=312.746667px인데
현재 셀 시작은 표 기준 316.52px다. 차이 283HU=3.773333px는 해당 행의 원본
셀 폭 합과 공통 표 폭의 차이와 같다. 이는 글꼴이나 날짜 전용 문제가 아니라
행 경계 생산을 먼저 확인할 근거다. 독립 Print를 원본·셀 구획과 대조하고, 셀 본문과
테두리가 함께 소비하는 공통 원인 보정 후 집중·전쪽 Native/fresh WASM을 재검증한다.

별도로 기호 복구 producer `5bcb654516`의 표준 최적화 WASM 전 766쪽도 완료했다.
HWPX/HWP 모두 200쪽에서만 111픽셀씩 개선됐고 다른 쪽은 기존과 같다. 최저값은 각각
99.25665%, 미대응 0픽셀 쪽은 292·295쪽이며 전쪽 100%는 아직 아니다.

실행 로그·중간 JSON·이미지는 ignored
`output/pr-review/issue8153-handbook-raw100-20261022/`에 기록한다.
`upstream/devel` 동기화·원격 게시·PR 생성은 하지 않는다.

## 후속 행 프레임 보정의 집중 재현

날짜 줄의 원점 차이를 보호하는 `issue_8153_row_cell_frame_ownership.rs`를 추가했다.
같은 두 원본 80·85·86·87쪽에서 고유 날짜 내용·셀 포함 관계와 독립 96dpi Print의
첫 숫자 원점(±2px)을 확인한다. 말미 구분 공백 전체 bbox와 실제 마지막 글자의 포함을
구별한다. 검사 SHA-256은
`e56bc02215800614639e71a2c36f0db83b90f5ed5c9a27da0da66aadd3fd4040`이며,
고정된 `d394351f0f` 라이브러리에서 두 원본 모두 원점 assertion으로 FAIL을 확인했다.
초기 검사 작성의 컴파일 오류와 초안도 ignored output에 보존하며 최종 실패 증거와 구분한다.

[행 경계 계획](../plans/issue_8153_stored_cell_width_20261024.md)에 따라 모델의
HU 단위 행 프레임 생산을 측정의 문단 폭과 실제 셀·괘선의 행별 geometry에 연결했다.
실제 셀 전체 폭을 가상 열의 부동소수 합으로 다시 정하지 않는다. 수평선도 획의 상·하
소유를 따라 좌표 행을 선택한다. 이 단계의 구현은 아직 빌드·집중 검증 전이며,
기존 보조 폭 복구·부분 가로선과 전쪽 영향은 실제 실행 후 판정한다.

`52aa554548cfab831d18abbedd1c6164112910f9`의 빌드는 11분 58초에 완료됐고,
집중 68건이 모두 통과했다. 새 날짜 원점 검사 두 건과 #5590·#5720도 통과했다.
실제 Native 정상 대조에서 form-002의 10쪽 구성과 부분 가로선 182.5px가 유지됐고,
#5720은 1쪽을 유지했다. 영향 102조건은 같은 고정 producer에서 별도로 비교한다.

별도 추가한 정상 대조 35쪽은 두 원본 모두 기존 raw100에서 99.40602%, 미대응
795픽셀로 하락했다. 이쪽 표의 셀 간격은 255HU이고 병합 셀의 물리 폭에는 span
내부의 간격도 들어간다. 최초 행 프레임이 이를 빼서 앞 행의 2열 병합 셀과 다음 행의
단일 셀 두 개가 같은 걸침 셀 시작점을 다르게 계산했다. 원본 11,070HU와 내부 간격
255HU를 함께 점유해야 한다. 문서 ID·간격 상수로 좁히지 않고 기존
`inner_cell_spacing_hu`를 재사용한다.

새 `issue_8153_spaced_merged_frame.rs`는 같은 두 원본 35쪽에서 걸침 셀과 다음 행
이웃 셀 사이의 원본 간격·세로 포함 관계를 검사한다. SHA-256은
`a6403a7d5614a02c5b20c12d7e61b4f1a423b434ec973df43d210300de752c87`이며
고정된 `52aa554548`에서 두 건 모두 실제 FAIL이다. 진단용 작은 모델 계약도 같은 원인을
FAIL로 확인했고 보정 후 PASS지만, 실제 문서·새 Native/fresh WASM 통과를 대신하지 않는다.
원본의 모든 값과 기존 기준 PDF를 유지하고 재빌드·재검증한다.

행 coverage 예약도 원본 grid 상한 안에서 제한하고 잘못된 span·폭을 완결 행으로
승격하지 않는다. 동일 획의 좌표 소유는 셀 방문 순서가 아닌 아래 셀 상단의 기존
우선순위를 따른다. 아래 획이 없는 form-002 부분 가로선은 위 셀 하단 소유를 유지한다.
