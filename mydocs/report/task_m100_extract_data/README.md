# #3719 §6-10 처리 기록 — `extract-data` (행정문서 구조화 공통 프리미티브)

## 문제

에이전트가 행정문서에서 "언제·얼마·몇 개"를 뽑으려면 지금까지 `export-text` 로 평문을
뽑아 밖에서 정규식을 돌리는 수밖에 없었다. 그러면 값은 얻지만 **주소가 소멸한다** —
"이 금액이 몇 쪽 어느 문단에 있는가"에 답할 수 없어 근거 제시도 검증도 불가능하다.
rhwp 는 조판 엔진을 갖고 있어 쪽까지 답할 수 있는 유일한 도구인데, 그 출구가 값에
대해서는 없었다. `search`(#3283)가 **검색어**에 대해 연 출구를 **데이터 값**에 대해 연다.

두 번째 문제는 정규화다. 밖에서 돌리는 정규식은 `'26.8.2` 를 만나면 2026년으로
추정하거나 조용히 버린다. 추정한 값은 옳은 값과 구별되지 않는다 — 에이전트가 틀린
날짜로 계약서를 채우면 그건 사고다.

## 구현

- 신규 코어 질의 `DocumentCore::extract_data(&self, kinds) -> Vec<DataItem>`
  ([extract_data.rs](../../../src/document_core/queries/extract_data.rs)):
  - 본문 + 표 셀 + 글상자를 순회하며 값마다 (구역·문단·**쪽**·문자 오프셋)을 붙인다.
    페이지 인덱스는 `grep` 의 `build_paragraph_page_index`·`build_table_row_page_index`
    를 **재사용**한다(`pub(crate)` 승격 2줄) — "몇 쪽"의 정의가 두 개면 두 명령이 서로
    다른 답을 한다. 분할 표는 그 행이 실제로 렌더되는 쪽을 쓴다(#3403 규약 그대로).
  - 표 셀·글상자 값에는 `cell`/`textbox` 좌표가 붙는다(`grep` 의 `CellRef`/`TextBoxRef`
    재사용 — 주소 어휘를 복제하지 않는다).
  - 종류 판정은 **항상 전 종류로** 하고 `--kind` 필터는 마지막에 건다. 필터에 따라
    구간 경계가 달라지면 `--kind amount` 가 날짜 안의 숫자를 금액으로 다시 읽는다.
- CLI `rhwp extract-data <파일> [--kind date|amount|number|all] [--limit N] [--json]`
  + capabilities 등재 + `--help` + MCP 도구 `hwp_extract_data`(+ `--password-stdin`)
  + `데이터분석` 역할 프로필 등재.

### 인식 규칙은 상상이 아니라 실물에서 왔다

`samples/` 의 실제 정부 문서를 `export-text --json` 으로 뽑아 표기를 세어 본 뒤 규칙을
짰다. 규칙마다 근거 문서가 있다.

| 실물 표기 | 출처 | 처리 |
|---|---|---|
| `1949. 7. 15.` (점 구분) | 행정업무운영 편람 466건 | `1949-07-15` |
| `2026. 1.` (연·월) | 기부·답례품 보고서 양식의 **유일한 날짜** | 부분 날짜 `2026-01` |
| `’26. 1.` (둥근 어깨점) | 행정업무운영 편람 | `null` (세기 미상) |
| `금113,560원` (접두 `금`, 공백 없음) | 행정업무운영 편람 56쪽 | `113560` |
| `금일십일만삼천오백육십원` (한글 수사) | 같은 문단, 바로 옆 | `null` |
| `21,345천원` · `3,180백만원` | 편람 / 국립국어원 업무계획 | 단위 배수 반영 |
| `12.03억원` · `2.15백만원` (소수 + 배수) | 국립국어원 업무계획 | 정수 연산으로 정확히 |
| `62.9%` · `210mm` · `2,106개소` | 편람 / 업무계획 | 단위를 `unit` 으로 분리 |

### 모름을 보존하는 규약

`normalized` 는 날짜면 ISO-8601 문자열, 금액·수량이면 숫자다. **정규화할 수 없으면
`null` 이고 `raw` 만 믿을 수 있다.** 키 자체를 지우지 않는 이유는, 키가 없으면 소비자가
"뽑히지 않음"과 "값을 모름"을 구별할 수 없기 때문이다.

`null` 로 남기는 경우 (전부 계약 테스트로 고정):

1. **두 자리 연도** — `'26.8.2` · `‘26. 8. 2.` · `’26. 1.`. 세기를 추정하면 100년이 틀린다.
2. **한글 수사 금액** — `일금 백이십삼만원` · `금일십일만삼천오백육십원`.
3. **한자·갖은자 수사 금액** — `金壹百貳拾參萬圓` · `一金 百二十三萬圓`.
   (2·3은 만 단위 자리 올림 규칙을 반만 구현하면 조용히 틀린 금액이 나오므로 v1 범위 밖)
4. **배수가 정수로 떨어지지 않는 금액** — `1,234.56원`. 반올림하지 않는다.
5. **연·월만 있는 날짜** — 일(日)은 `null` 이 아니라 **부분 날짜**(`2026-01`)로 표현한다.
   없는 날을 1일로 채우면 조용히 틀린 값이 되고, 버리면 그 문서의 유일한 날짜가 사라진다.

### 값을 지어내느니 인식 자체를 포기한 형태와 그 이유

| 형태 | 왜 뽑지 않는가 |
|---|---|
| `20260802` | 구분자가 없어 일반 정수와 구별되지 않는다 |
| `8/2` · `8. 2.` | 연도가 없어 어느 해인지 모르고 분수·번호와 겹친다 |
| `26. 8. 2.` | 어깨점 없는 두 자리 연도는 번호 매김과 구별되지 않는다 |
| `(1,234,567)원` | 회계의 괄호 음수는 `(3)원칙` 같은 번호 매김과 구별할 수 없다. 한국 행정문서의 음수 표기는 `△` 이지 괄호가 아니다. 부호를 지어내는 대신 그 형태를 통째로 포기한다 (단위가 괄호 **안**이면 부연 표기이므로 `(1,234,567원)` 은 양수로 뽑는다) |
| `▲12.3%` · `▼` | 화살표의 증가/감소 의미가 문서마다 뒤집힌다 — 부호로 읽으면 절반이 틀린다. 화살표를 무시하고 양수로 뽑는다 |
| `$1,234` · `€` · `¥` · `USD 1,234` | 외화는 소수 단위(센트)와 환율 맥락이 필요하다. `currency:"KRW"` 로 표시하면 통화가 틀린 값이 된다 |
| `2천억원` | 곱셈형 복합 수사(2천 × 억)는 만 단위 곱셈 규칙이 필요하다. 반만 구현하면 조용히 틀린다 |
| `3만 5억원` | 자릿수가 뒤집힌 표기는 수사가 아니다 — 합산하지 않는다 |
| `3억` · `5만` (`원` 없음) | 금액인지 수량인지 문맥이 있어야 안다 |
| 단위 없는 맨 숫자 | 표 하나가 수백 건의 잡음이 된다 |
| `제3조` · `제137호` · `3차` | 개수가 아니라 번호(서수)다 |
| `표 3 개요` 의 `개` | 띄어 쓴 한글 단위는 낱말 첫 글자를 단위로 오인한다 (기호·라틴 단위는 `3.5 %` 처럼 공백 하나를 허용) |
| `- 1,234,567원` (글머리표) | 글머리표는 뒤에 공백이 온다 — 붙여쓰기 규칙 하나로 마이너스와 갈린다 |
| `3-5개` 의 하이픈 | 앞 글자가 숫자면 범위 표기다 |
| `14:30` · 전화번호 · 사업자번호 | 값의 종류가 다르다 — 별도 축이 필요하다 |

### ReDoS 가 원천적으로 없다

정규식을 쓰지 않는다. 문자 슬라이스를 왼쪽에서 오른쪽으로 **한 번** 훑으며 각 위치에서
고정 길이 후보만 시도하고, 인식한 구간은 통째로 건너뛴다. 되추적이 없으므로 중첩 수량자로
인한 파국적 backtracking 자체가 존재할 수 없고, 숫자 열 한가운데에서 다시 시작하지 않으므로
`1111…1` 같은 입력에서도 입력 길이에 선형이다(단위 테스트 `long_digit_runs_do_not_blow_up`
가 20만 자 입력을 2초 상한으로 감시). 복합 금액 마디 반복도 자릿수 단위 개수로 상한이 있다.

## 실측 ([evidence.txt](evidence.txt) 원문)

전부 라이브 실행이다. 인용한 표기는 전부 실제 정부 문서에 있는 것이다.

| 문서 | 결과 |
|---|---|
| `2025 행정업무운영 편람(최종).hwp` (393쪽·10MB) | **717건** — date 466 · amount 10 · number 241 |
| `2025년 기부·답례품 실적 지자체 보고서_양식.hwpx` | 2건 — `2026. 1.` → `2026-01`(1쪽), `17개` → 17(16쪽) |
| `2022년 국립국어원 업무계획.hwp` | amount 65건 — `3,180백만원`→3180000000, `12.03억원`→1203000000, `2.15백만원`→2150000 |

1. **값과 주소가 한 몸이다.** `금113,560원` → 113560, 구역2·문단351·**56쪽**·오프셋 5.
2. **모름이 보존된다.** 바로 같은 문단(오프셋 15)의 `금일십일만삼천오백육십원` 은
   `normalized: null` 이다 — 아라비아 숫자 쪽에서 값을 베껴 오지 않는다.
3. **두 자리 연도는 추정하지 않는다.** 편람의 date 466건 중 `normalized: null` 은
   `’26. 1.` **단 1건**이고, 나머지 465건은 전부 ISO-8601 이다.
4. **없는 날을 채우지 않는다.** 기부·답례품 양식의 유일한 날짜 `2026. 1.` 은
   `2026-01-01` 이 아니라 부분 날짜 `2026-01` 이다.
5. **`--limit` 이 총량을 숨기지 않는다.** `--limit 3` → `itemCount:3`,
   `totalItemCount:717`, `truncated:true`, `counts` 는 절단 전 값.
6. **`--kind` 가 경계 판정을 바꾸지 않는다.** `--kind date|amount|number` 각각의
   `counts` 가 `--kind all` 의 해당 값(466·10·241)과 정확히 일치한다.
7. **실패 경로 stdout 0바이트.** 없는 파일 exit 1 · 경로 없음 exit 2 ·
   `--kind 치즈` exit 2, 셋 다 stdout 0바이트.
8. **성능** — 393쪽·10MB 문서 전량 추출이 파싱 포함 **226·252·338ms**
   (`search` 의 215ms 와 같은 자릿수. 페이지 인덱스를 한 번만 만들어 재사용한다).

## 남은 것 (의도적으로 v1 범위 밖)

- **한글·한자 수사 금액의 값 정규화** — 지금은 인식만 하고 `normalized: null` 이다.
  만 단위 자리 올림(`이천삼백만` = 2300 × 10⁴)과 곱셈형(`2천억`)을 함께 다루는 수사
  파서가 필요하다. 반만 구현하면 조용히 틀린 금액이 나오므로 통째로 미룬다.
- **곱셈형 복합 금액**(`2천억원`) — 위와 같은 이유로 **인식 자체를 하지 않는다**.
  잘못된 값 대신 아무 값도 내지 않는 쪽을 골랐다.
- **외화** — `currency` 축은 봉투에 열어 뒀지만 v1 은 `KRW` 전용이다. USD/EUR/JPY 는
  소수 단위(센트)와 환율 맥락이 필요하고, 금액 `normalized` 의 정수 계약도 함께 봐야 한다.
- **다른 값 종류** — 시각(`14:30`)·기간(`2026. 1. ~ 12.`)·전화번호·사업자번호는
  날짜/금액/수량 어디에도 속하지 않는다. 종류를 늘리려면 `--kind` 어휘와 함께 봐야 한다.
- **머리말/꼬리말·각주/미주** — 순회 범위가 본문·표 셀·글상자다(`grep` 과 같은 사각지대).
  재귀 확장은 `fields` 의 `collect_fields_from_paragraph` 와 같은 문제라 함께 처리해야 한다.
- **`batch extract-data`** — 아카이브 일괄 추출 축은 붙이지 않았다. `batch` 서브커맨드
  목록과 MCP `hwp_batch` 스키마를 같이 늘려야 해서 별도 이슈가 맞다.
- **수량 단위는 화이트리스트다** — 목록에 없는 단위는 잡히지 않는다. 개방형(임의 한글
  1~2글자)으로 바꾸면 조사·어미까지 단위로 먹어 잡음이 폭증하므로, 실측 문서에서
  관측된 표기만 늘린다.
