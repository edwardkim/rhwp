- Issue: [#3591](https://github.com/edwardkim/rhwp/issues/3591) (M100) / 브랜치 `local/task3591`

- 단계 기록: `mydocs/working/task_m100_3591_stage1-3.md`

## 근인

`virtual-scroll.ts` `applyHorizontalPanSpace()` 가 콘텐츠 좌우에 **창 폭 100%** 씩 팬
여백을 붙였다(`totalWidth = base + viewportWidth × 2`). 실측(창 1229, SO-SUEOP):
833.7 + 2458 = 3291.7px — **스크롤 영역의 75%가 빈 공간**. 창 폭 비례라 4K 최대화 시
총 8500px 중 내용이 10% 미만이 된다. 화면 폭(`screen.width`)은 수식에 개입하지 않는다
(실측 역산 확인) — 4K 가 문제였던 것은 큰 화면에서 창을 크게 쓰기 때문이다.

파생 증상 두 가지가 같은 뿌리에서 나왔다.

- 콘텐츠가 항상 창보다 넓어 브라우저 자연 중앙 정렬이 무력화되고, 수평 배치를
  `scrollLeft` 가 전담하는데 줌 완료 후 중앙 수렴 규칙이 없어 앵커 잔류가 줌 비례로
  증폭(복귀 구간 47.5→403.5px, 그리드 진입 −546px).
- [#3377](https://github.com/edwardkim/rhwp/issues/3377)(해결됨)의 좌표 stale 도 같은
  설계에서 파생됐다 — CSS 자기 중앙 정렬이 불가능해 명시 left 에 의존한 구조.

## 수정 (rhwp-studio, Rust/WASM 비접촉)

```
pan = (그리드) ? 0
    : (콘텐츠폭 <= 창폭) ? 0
    : clamp(창폭 × 0.25, 80, 240)
```

1. `horizontalPanSpace()` 신설 + 상수 `PAN_SPACE_RATIO/MIN/MAX`. 팬 0 이면 단일 열은
   CSS 중앙 정렬(`left:50%`)이 회복되고 `totalWidth` 도 base 그대로다.
2. **그리드 예외**: `layoutGrid` base 가 `max(gridWidth + marginLeft*2, viewportWidth)` 라
   항상 창 폭 이상이어서 팬 조건이 경계에서 참이 됐다. 그리드 첫 진입(zoom 0.5)에서만
   스크롤 여지 482px 이 생겨 문서가 밀리던 결함 — 실환경 2차 판정에서 발견해 정정.
3. **앵커 오버슈트 정정**: 팬이 얇아지자 줌 앵커 계산이 스크롤 범위를 넘는 것이
   드러났다(632 vs 최대 550). 종전엔 두꺼운 팬이 흡수했다. `CanvasView.clampScrollLeft()`
   추가로 계산 단계에서 가둔다.

## 교훈

- **측정식도 검증 대상이다**: Stage 2 의 −7.5px 잔차는 하니스가 뷰포트 중앙을
  `getBoundingClientRect().width`(세로 스크롤바 포함)로 잰 아티팩트였다. 스크롤바 폭의
  절반이 그대로 나온 것이고, 실제 표시 영역(`clientWidth`) 기준으로는 1.0px 였다.
  작업지시자 육안 판정이 맞았고 계측이 틀렸다 — 코드 수정 대상 없음으로 종결.
- **정적 측정은 동적 결함을 못 본다**: 정지 상태만 재던 하니스는 그리드 진입 결함을
  놓쳤고, 실환경 시각 판정이 잡았다. 자동 계측과 사람 판정은 대체 관계가 아니다.
- 얇아진 여백이 종전에 가려져 있던 오버슈트를 드러냈다 — 완충재를 줄이면 숨은 계약
  위반이 노출된다.

## 범위 밖

배치의 의도된 설계다. 셀 내부 중앙 정렬로 바꾸려면 별도 이슈로 다룬다.
