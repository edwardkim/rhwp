# #7170 — HWP3 차례의 탭 채움(점선)이 저장본에서 사라진다

표본은 `1170000-200500003_D0150004-1-001_독일의 법령체계와 입법심사기준(최종본).hwp`
(264쪽, HWP3, 인라인 탭 112개)다. 정본은 **한글 자신의 HWP5 변환본** — 같은 원본을
한글 2024 로 열어 `SaveAs(..., "HWP")` 한 파일이다.

## 근인 — 파서가 읽고 버리던 6바이트

HWP3 은 인라인 탭을 8바이트로 저장하고 그 안에 **탭 폭과 점끌기 여부**를 담는다
(스펙 `한글문서파일구조3.0.md` §10.5 표 39).

```text
  offset 0: hchar(=9)   여는 코드
  offset 2: hunit       탭 폭
  offset 4: word        점끌기 여부
  offset 6: hchar(=9)   닫는 코드
```

HWP5 도 같은 정보를 본문 안 8코드유닛 탭 확장에 싣는다. 종전 파서는 저 6바이트를
`buf` 로 읽어 놓고 **하나도 쓰지 않았다.** 그래서 HWP3 에서 온 문단은 저장본에서 탭
폭 0 · 채움 없음이 됐고, 한글은 문단 `TabDef` 가 아니라 이 인라인 값으로 점선을
그리므로 차례가 빈칸이 된다.

이슈 본문은 폭을 "조판 결과라 파서 단독으로 만들 수 없다"고 봤다. **원본이 이미
갖고 있었다** — 아래처럼 정본과 바이트 단위로 같아진다.

## 저장 바이트 — 탭 확장 112개

정본 확장의 형상은 `[폭_lo, 폭_hi, 0x0003, 0, 0, 0, 0x0009]` 이고, 폭 112개가 모두
4의 배수다. HWP3 hunit 에 4를 곱한 값과 맞는다(HWPUNIT 환산).

| | 탭 확장 | 폭이 0 인 것 | `ext[2]` |
| --- | ---: | ---: | --- |
| 한글 정본 | 112 | 0 | 전부 `0x0003` |
| 수정 전 | 112 | **112** | 전부 `0x0000` |
| 수정 후 | 112 | 0 | 전부 `0x0003` |

수정 후 **112/112 가 정본과 완전히 일치**한다(폭·`ext[2]` 모두).

## 한글이 그린 PDF — 점이 정본과 같아진다

세 파일을 한글 2024 로 열어 PDF 로 저장하고 텍스트를 뽑았다.

| | 쪽 | 글자 | 점(U+00B7) |
| --- | ---: | ---: | ---: |
| 한글 정본 | 264 | 248,006 | **9,189** |
| 수정 전 | 273 | 239,649 | **0** |
| 수정 후 | 273 | 248,839 | **9,189** |

늘어난 글자를 멀티셋으로 가르면 정확히 `·`(U+00B7) 9,189개다 — 정본과 수정 전의
차이와 **같은 값**이다.

```text
  수정 후 - 수정 전   '·' x 9,189
  정본    - 수정 전   '·' x 9,189
```

남은 정본 대비 차이(`)` 231 · `-` 69 · 공백)는 각각 #7174 와 하이픈 축이며 이
수정의 범위가 아니다. 쪽수는 273 으로 그대로다 — 조판을 건드리지 않는다.

## 폭과 채움이 둘 다 빈 탭은 싣지 않는다 (#1892 계약)

HWP3 탭 중에는 폭도 채움도 0 인 것이 있다. 그 확장을 그대로 실으면 직렬화기의
**"데이터 없음" 마커**(`[0, …, 0, 0x0009]`)와 글자 그대로 같아진다. HWP5 파서는 그
마커를 일부러 IR 에 싣지 않으므로(#1892), 재파스에서 확장 하나가 사라지고 **뒤 탭의
확장이 순번으로 밀린다** — 직렬화는 `	` 순번으로 확장을 꺼낸다.

처음 구현은 이 갈래를 놓쳐 `issue_1892` 계약 둘을 깼다.

```text
  issue_1892_null_tab_extension_marker_not_parsed_into_ir      FAIL
  issue_1892_hwp3_tab_roundtrip_render_is_self_consistent      FAIL
```

표본 `samples/issue1892_hwp3_tab_roundtrip.hwp` 의 탭 8개가 `(폭 0, 채움 0) x 5` ·
`(4000, 0) x 2` · `(8000, 0) x 1` 로 **섞여 있다.** 그래서 그런 탭이 하나라도 있는
문단은 통째로 싣지 않고 종전 동작을 유지한다 — 한 문단 안에서 일부만 싣는 절충은
순번 계약을 깬다. 가드를 넣은 뒤 두 계약이 모두 복구된다.

코퍼스 HWP3 38건의 탭 138개는 **전부 폭이 0 이 아니라** 이 갈래를 타지 않는다.
가드 전후로 저장 바이트가 같다(아래 수치는 가드를 포함한 최종 head 실측이다).

## 폭발반경 — 코퍼스 HWP3 38건 전수

수정 전후 바이너리로 38건을 각각 `convert` 해 저장본 레코드를 직접 비교했다(COM 불필요).

| | 결과 |
| --- | --- |
| 탭이 있는 문서 | **4 / 38** (탭 138개) |
| 폭이 0 이 아닌 탭 | `0` → **138** |
| 채움 분포(수정 후) | 점선 112 · 없음 26 |
| 탭 **개수**가 바뀐 문서 | 0 — 비어 있던 데이터만 채운다 |

채움이 두 값으로 갈리는 것이 중요하다. HWP3 의 `점끌기 여부` 를 무시하고 전부 점선으로
칠하면 점끌기를 끈 탭 26개가 없던 점선을 얻는다.

## 범위 밖

- `ext[2]` 고바이트(탭 종류)는 정본이 `0`(미지정)을 쓰므로 채우지 않는다 — 종류는
  문단 `TabDef` 가 정한다.
- 우리 렌더러가 인라인 탭 채움으로 점선을 그리지 않는 **읽기 쪽** 축.
- 표본의 쪽수 격차(264 대 273) — #7172 등 별개 축.
