## 1. 결론과 결정 요청

**제품 `rhwp`와 보조 실행 파일 25개를 Cargo 패키지 경계로 분리하는 방향을 권고한다.**
보조 도구는 같은 저장소의 선택형 개발 도구로 유지한다. Gym 폴더로 옮기거나 삭제하지 않는다.
그 뒤 확인된 복제만 공통화한다. 처음부터 명령 통합·공개 API 재설계까지 묶지 않는다.

분석에서 제시한 권고 방향은 다음과 같다. 이번 타스크의 구현 지시가 아니다.

> 별도 개발 도구 패키지로 제품의 기본 빌드·소스 설치 경계를 명확히 한다.
> 기존 실행 이름과 명령 계약은 유지한다. 먼저 패키지 분리를 구현하고 검증한 뒤,
> 중복 제거는 아래 우선순위에 따라 선택한다.

이 보고서 승인은 분석 결과와 방향에 대한 승인이다. 실제 파일 이동·Cargo/test/CI 수정은
최신 devel을 확인하고 구체적인 수행계획을 승인받은 뒤 시작한다. 이번에 새 하위 이슈를
만들거나 배포 채널을 추가하지 않았다. #7001 종료와 후속 구현 완료도 서로 구분한다.

## 3. 왜 이렇게 되었는가

1. `rhwp-agent`는 #3918에서 main/Cargo 수정 경합을 피하는 별도 실험 실행 파일로 출발했다.
   이후 scan·verify를 본 CLI로 승격했지만 양쪽 handler가 남아 서로 다른 계약으로 발전했다.
2. q 도구들은 공개 조회 API의 노출과 폰트 계측 등에 사용되었다. 묶음별 봉투 복제와
   대량 probe 코드의 축소 이력이 함께 남아 있다. 모두 불필요한 임시 파일인 것은 아니다.
3. `src/agent`는 다른 계보의 공개 DSEL 선택자 라이브러리다. rhwp-agent 실행 파일의
   공통 라이브러리가 아니며, 주석의 8층 커널 구상 전체가 구현된 상태도 아니다.
4. #5511은 main의 기능군 분리를 수행했지만 service 계층 전환까지 완료했다고 선언하지 않았다.
   현재 중복 전체를 그 리팩토링의 회귀라고 단정할 근거는 없다.

커밋·기존 보고서 연결은 Stage 1의 4절에 있다. **독립적으로 기능을 추가하기 쉬운 구조에 비해
승격 이후의 소유권·호환 계약·설치 경계 정리가 뒤따르지 않은 것**을 구조적 원인으로 해석한다.
이는 관측된 계보에 대한 분석이며, 기여자가 남겨 둔 이유나 외부 사용 부재를 추정한 사실은 아니다.

## 4. 역할별 권고 위치

| 현재 대상 | 권고 소유권·위치 | 보존할 것 |
| --- | --- | --- |
| `src/main.rs`, `src/cli` | 제품 CLI 유지 | 기존 102개 명령과 MCP·batch 등의 호출 계약 |
| `src/agent` | 제품 공개 라이브러리 유지 | DSEL API 경로·선택 의미·오류·자원 제한. 실제 구현과 미래 설명만 구분 |
| `src/bin/rhwp-agent` | 선택형 개발 도구 패키지 | 80개 명령과 `rhwp-agent` 실행 이름 |
| `src/bin/rhwp-q-*` | 같은 개발 도구 패키지 | 23개 실행 이름, 조회 의미, 폰트 scripts·계약 테스트 |
| `src/tools/font_metric_gen.rs` | 같은 개발 도구 패키지 | 메트릭 생성 명령·입출력. 이동을 이유로 생성 데이터를 재작성하지 않음 |
| `gym/` | 선택형 평가 도구 유지 | 과제·채점·기준 풀이·리더보드. 제품이 Gym 파일을 필요로 하지 않음 |

권고 구조의 예시이며 아직 생성한 경로가 아니다.

```text
rhwp 루트 패키지
├─ src/main.rs, src/cli/      제품 실행 어댑터
└─ src/lib.rs, src/agent/    제품 API와 공개 선택자
tools/rhwp-devtools/         별도 Cargo 패키지, 배포하지 않는 개발 도구
├─ agent/                   기존 rhwp-agent 진입점·모듈
├─ queries/                 기존 rhwp-q-* 진입점·모듈
└─ font-metric-gen/          폰트 메트릭 생성기
gym/                        제품을 호출하는 선택적 평가 도구
```

`bin`은 실행 타깃 소스라는 Cargo 관례이지 컴파일된 파일이 들어 있다는 뜻은 아니다.
다만 이 프로젝트에서는 역할이 드러나는 위 경로와 명시적 `[[bin]]` 등록을 권고한다.
이름 변경만으로 제품에서 제외되었다고 판단하지 않는다.

의존 방향은 **개발 도구 → 제품 API**, **Gym → 제품 CLI/API**다.
제품이 개발 도구 패키지나 Gym에 의존하는 역방향을 만들지 않는다.
개발 CLI 봉투를 `src/agent`에 넣거나 Gym이 소비한다는 이유로 제품의 replay/audit 등을
Gym 전용 구현으로 옮기는 안은 제외한다.

## 5. 구조 대안 비교

| 대안 | 얻는 효과 | 비용·주의점 | 판정 |
| --- | --- | --- | --- |
| 경로만 tools로 이동, 같은 패키지 bin 유지 | 폴더 역할 명확화 | 기본 설치·타깃 소유권은 그대로. 보조 25개가 제품과 계속 묶임 | 목적 달성 부족 |
| 같은 패키지에서 개발 feature로 bin 선택 | 기본 제품 선택과 선택형 도구를 구분 가능 | required-features와 자동 탐색, 테스트 feature 조합을 함께 관리해야 함. 기능을 끄고 테스트까지 사라지는 위험 | 대안으로 가능하나 비권고 |
| 별도 workspace 개발 도구 패키지 | 제품과 개발 실행 타깃의 소유권·설치 경계를 분리 | 테스트의 실행 파일 공급과 상대 경로 이관 필요. workspace CI에서는 계속 검증 | **권고** |

권고 패키지는 `publish = false`, `autobins = false`와 25개 명시 타깃을 전제로 설계한다.
루트도 자동 탐색에 의한 재유입을 막고 제품 bin을 명시한다. 새 패키지는 `tools/` 아래
workspace member로 등록하되 기본 멤버에 포함하지 않는 방향이다. 현 기본 멤버의 `crates/*`
아래에 만들면 의도와 달리 기본 빌드에 다시 들어갈 수 있다.
멤버 선택 규칙은 [Cargo workspace 정본](https://doc.rust-lang.org/cargo/reference/workspaces.html#package-selection)을
확인했다(2026-09-11 조회).

이는 패키지 분리 방향이지 이 Cargo 설정만으로 이관이 완성된다는 뜻은 아니다.
직접 의존 crate, native/WASM cfg, include 경로, build-time 환경 변수와 생성 테스트의 소유권을
후속 수행계획에서 명시해야 한다. 루트 dependency를 근거 없이 함께 삭제하지 않는다.

## 6. 실제 구현은 어떤 순서로 할 것인가

세 작업 단위로 한정한다. **첫 구현 범위는 R1만 권고**하며, R2·R3 완료를 R1의 종료 조건으로
연결하지 않는다. 모든 명령을 합칠 때까지 계속되는 리팩토링으로 만들지 않는다.

| 순서 | 범위·목적 | 완료 판정 | 하지 않는 일 |
| --- | --- | --- | --- |
| R1 — 실행 타깃 경계 | 보조 25개를 선택형 패키지로 이관. 호출 scripts·테스트·사용 문서를 함께 맞춤 | 제품 기본 bin 1개, 도구 25개 명시 선택, 기존 호출 계약 및 전체 필수 검증 통과 | handler 의미 변경, 실행 이름 삭제, Gym 변경 |
| R2 — 확정 복제 제거 | q-more/q-pack 봉투를 도구명을 받는 개발 도구 내부 helper로 공통화 | 각 tool/command/출처 표지·stdout 오류·exit 유지, 두 도구 계약 통과 | 서로 다른 volume-probe 계산 통합, agent 봉투까지 일괄 통합 |
| R3 — 공통 처리의 소유권 정리 | scan의 수집·정렬·형식 분류, explore의 DocFacts 집계만 후보 | loader·출력·MCP 도구 목록 정책은 어댑터에 남고 공통 처리 전후 계약 일치 | verify/search 통합, 전 CLI service 계층 재작성 |

R1은 의미 변경이 없는 이관으로 제한하지만 단순 `mv` 작업은 아니다. 구현 전에 기존 바이너리와
입력의 출처를 고정하고 변경 범위의 계약 검증을 준비한다. 등록 명령·타깃 수, 출력 필드·종료 코드,
폰트 계측의 동일 스냅샷 사용이 유지되어야 한다. 새 코드의 출력을 그대로 정답으로 삼지 않는다.

현재 계약 테스트는 루트 패키지의 `CARGO_BIN_EXE_rhwp-agent` 및 q 실행 이름,
`CARGO_MANIFEST_DIR` 기준 샘플 경로에 의존한다. 타깃만 옮기면 이 연결이 깨진다.
후속 계획은 **새 패키지 소유 계약 테스트로 옮길지, 별도 빌드한 실행 파일을 명시적으로 공급할지**
하나를 정하고 generated suite 정책과 함께 검증해야 한다. fixture가 없다고 조용히 return하거나
테스트를 비활성화해서 통과시키지 않는다. 제품/도구를 교차 비교하는 테스트도 누락하지 않는다.

R3에서는 파일시스템·프로세스 처리를 WASM 공통 라이브러리로 밀어 넣지 않는다.
DocFacts처럼 제품의 기존 공통 코어에 자연스럽게 속하는 계산은 그곳을 우선한다.
scan의 host 전용 공유가 별도 crate·역방향 의존까지 요구한다면 그 비용을 먼저 비교하고,
적은 중복을 없애기 위해 거대한 새 계층을 도입하지 않는다. 이 지점은 구현 전 설계 확인 대상이다.

## 7. 당장 합치거나 삭제하지 않을 것

- **verify**: 옵션 반복·형식 검사만 실행할 때의 파싱 여부·field 존재 검사·검색 방식·JSON이 다르다.
  main이 전역 암호 로더를 우회하는 정적 불일치도 확인했다. 암호 문서 재현 전 확정 버그로
  확대하지 않으며, 오류 보정이 필요하면 호환 리팩토링과 구분해 승인을 받는다.
- **search 3종**: 구조 검색·렌더된 페이지 문자열·공개 API 검색의 범위와 주소 단위가 다르다.
  byte offset과 문자 위치를 같은 값처럼 합치지 않는다.
- **structure**: 코어를 이미 공유한다. 서로 다른 출력 어댑터 자체를 중복 오류로 보지 않는다.
- **volume-probe**: more/pack의 seed, 문자/byte 길이, 셀 순회 계산이 다르다. 장기 필요성은 미확정이다.
  pack의 현 타입 검사만으로 수치 동등성이 증명되지 않는다. 현 계약을 유지하며 필요성 결정 전 삭제하지 않는다.
- **DSEL 공개 API**: 내부 소비자 미검출은 외부 사용 부재의 증거가 아니다. 실행 CLI와 이름을
  통일하려고 공개 경로를 바꾸지 않는다. 8층 구상과 실제 1층 구현의 문서 구분을 우선한다.

보호 불변식은 알려진 오류를 영구 보존하는 규칙이 아니다. **구조 변경과 동작 변경을 구분하여
어떤 계약을 바꿨는지 검토 가능하게 하는 경계**다.

| 경계 | 현재 근거 | R1에서 확보할 상태 |
| --- | --- | --- |
| 제품 release archive | workflow의 `--bin rhwp`, 확인한 Linux archive는 제품 1개 | 현 배포 파일 구성을 유지. 새 개발 도구 배포 채널 없음 |
| 루트 소스 설치 | Cargo 규칙·metadata상 기본 bin 26개, 실제 설치는 미실행 | 기본 제품만 설치, 개발 도구는 명시적 별도 선택 |
| 개발 기본 빌드 | 보조 bin이 루트 패키지에 속함 | 선택하지 않은 도구가 제품 기본 타깃에 섞이지 않음 |
| workspace CI | workspace build·all-target Clippy가 도구를 포함 | 새 member도 계속 검증. 테스트 누락으로 시간 절감하지 않음 |
| 제품 WASM | 개발 CLI helper를 필수 의존으로 만들면 경계 훼손 가능 | 제품이 Gym·개발 패키지 없이 기존 WASM 구성을 유지 |

설치 규칙의 확인 출처는 Stage 2의 7절 및
[Cargo 공식 설치 문서](https://doc.rust-lang.org/cargo/commands/cargo-install.html)다.
`default-run`은 설치 대상 제한이 아니다. 또한 `publish = false`는 registry 발행 금지이며
workspace 빌드 제외를 뜻하지 않는다. R1으로 모든 CI 시간이 줄어든다고 약속하지 않는다.
`publish`의 의미는 [Cargo manifest 정본](https://doc.rust-lang.org/cargo/reference/manifest.html#the-publish-field)을
확인했다(2026-09-11 조회).

25개 도구의 기본 선택을 분리해도 루트의 공통 의존성 비용이 자동으로 사라지는 것은 아니다.
빌드 시간·메모리·배포 용량 절감률은 이번에 측정하지 않았다. 실제 개선 비용 비교는 같은
toolchain·features·캐시 조건에서 변경 전후를 측정해야 한다.

향후 구현 검증은 [로컬 검증 정본 4.3](../manual/pr_review/local_validation.md)의
Rust lint 전체 묶음과 변경 범위별 회귀 게이트를 따른다. focused 테스트만으로 완료하지 않는다.
Cargo/workspace 변경에 따른 실행 타깃 목록·테스트 목록 대조, scripts의 실제 실행 경로,
제품 설치 smoke test와 Docker WASM 검증을 함께 설계한다. CI 운영 변경이 필요할 때만
[GitHub 운영 정본](../manual/github_operations.md)에 따라 처리한다.
일반 PR에 Gym 전건 평가나 Gym release gate를 다시 붙이지 않는다.

  `git diff --check` 통과. 제품 기준 대비 tracked 변경은 mydocs뿐이며 새 파일도 이 보고서 하나다.

## 10. 용어 미주

- **CLI — Command-Line Interface**: 명령줄에서 인자를 받아 실행하고 결과·종료 코드를 내는 인터페이스.
- **API — Application Programming Interface**: 다른 프로그램이 호출하는 공개 기능의 약속.
- **DSEL**: 소스가 “문서 선택자 언어”로 소개하는 공개 모듈의 명칭. 영문 약어 확장은
  확인되지 않아 임의로 부여하지 않는다. 문서 노드 선택자이지 rhwp-agent 실행 파일 전체가 아니다.
- **Cargo package / workspace**: 함께 빌드되는 타깃의 패키지 / 여러 패키지를 관리하는 작업 공간.
- **bin target**: 컴파일할 실행 프로그램의 진입점. 폴더의 모든 파일이 별도 실행 타깃인 것은 아니다.
- **adapter / contract**: 입력·출력을 코어에 연결하는 부분 / 인자·결과·주소·실패 방식의 약속.
- **JSON envelope**: 결과 데이터 바깥의 tool·command·출처 등 공통 메타데이터 묶음.
- **DocFacts**: explore가 행동 메뉴를 만드는 데 사용하는 문서 특성 집계 구조.
- **CI — Continuous Integration**: 변경 통합 시 빌드·테스트 등을 자동으로 확인하는 절차.
- **WASM — WebAssembly**: 브라우저 등에서 실행하는 바이너리 명령 형식. native CLI 빌드와 구분한다.
- **golden / smoke test**: 독립적으로 확정한 기대값 / 설치·실행의 기본 동작을 확인하는 짧은 검사.
