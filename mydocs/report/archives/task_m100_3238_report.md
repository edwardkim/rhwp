## 1. 문제

수만 건 HWP 아카이브(검색/RAG 인덱싱이 실수요)를 다루는 방법이 "파일마다 프로세스
하나"뿐이었다. 셸 병렬화(`xargs -P`)는 실측 1.5배에 그쳤고, 사전 검증 과정에서 그
원인이 프로세스 기동이 아니라 **극단 파일 1건이 병렬 막차(makespan)를 지배**하고
파일 간 병렬의 이득을 프로세스 모델이 살리지 못하는 데 있음이 드러났다
(#3238 사전 검증 코멘트 — 가설 수정 2건).

## 2. 분석 — 설계 결정

### 2.1 한계 재정렬 버퍼(bounded reorder buffer) 스트리밍

청크 배리어 방식(청크 단위 병렬→정렬→방출)과 비교해 스트리밍을 택했다.

| | 청크 배리어 | 한계 재정렬 버퍼 (채택) |
|---|---|---|
| 첫 레코드 지연 | 첫 청크 완료까지 대기 | 첫 파일 완료 즉시 |
| 유휴 | 청크마다 최장 파일 대기 누적 | 최장 파일 1회 |
| 순서/메모리 | 보장/청크 크기 | 보장/cap(threads×8) |

교착 안전 논증: 완료-미방출 레코드가 cap 을 넘으면 워커가 대기(역압)하되, **방출
차례(next_emit) 레코드는 cap 무관 삽입**할 수 있다. 방출자가 기다리는 레코드의
생산자는 절대 블록되지 않으므로 시스템은 항상 전진한다.

구현 중 실측으로 잡은 함정: 레코드당 `notify_all` 은 대기 워커 전원을 헛깨우는
thundering herd 로 수 초를 잃는다(271건 실측). 방출자가 **연속 레코드를 한 번의
락으로 일괄 드레인하고 notify 는 배치당 1회**로 확정했다. `notify_one` 은 대기자
조건이 인덱스별로 달라(escape 조건) 엔드게임 교착 위험이 있어 의도적으로 배제했다.

### 2.2 견고성 — 신뢰 불가 대량 코퍼스 전제

- **panic 격리**: 한 건의 파서 panic 을 `catch_unwind` 로 해당 파일의 `error`
  레코드에 격리한다. 10만 건 배치가 1건 때문에 죽으면 안 된다.
- **부분 실패 = 실패**: 건별 실패는 레코드로 스트림을 계속하되 최종 종료 코드 1 (#2707).
- **broken pipe**: 소비자가 파이프를 끊으면(`| head` 등) abort 플래그로 신규 수주를
  멈추고 워커를 정리한 뒤 1 로 끝난다 — 실동작 확인.
- 신규 의존성 없음(`std::thread::scope`).

### 2.3 `batch info` — 에이전트의 첫 질문

에이전트가 아카이브를 만나면 첫 작업은 본문 추출이 아니라 **선별**이다(무슨 파일이,
몇 페이지, 어떤 포맷인가). `batch info --json` 은 `info --json` 과 같은 스키마
(`info_json_value()` 공유)를 NDJSON 으로 스트림해, 단건/배치를 같은 소비 코드로 읽는다.

## 3. 실측 (32코어[16물리] Windows, 저장소 samples 271건, 릴리스 빌드)

| 측정 | 값 |
|---|---|
| `batch info` — 전체 271건 메타데이터 스윕 | **3.0s** |
| `batch export-text` — 270건(극단 합성 1건 제외) | **7.0s** (파일당 프로세스 순차 45.1s 대비 **6.4배**) |
| 동일 — 1,350건(코퍼스 5×) | 27.8s — 지속 48.6건/s |
| 극단 합성 1건(`issue2063_huge_cellbreak_table.hwp`, 단독 57.5s) 포함 271건 | 67.4s — makespan 은 최장 파일이 바닥 |

균질 워크로드(동일 파일 256벌) 강스케일링: T=1: 79.6s → T=8: 17.7s → T=32: 13.5s.
**8~16스레드에서 포화(~6배)** — 원인은 미확정(할당 경합 추정)이며, 본 골격과 무관한
엔진 수준 병렬 효율 주제라 재현 스크립트와 함께 후속 이슈로 분리 예정. 여기가 풀리면
같은 골격에서 배수가 한 번 더 뛴다.
