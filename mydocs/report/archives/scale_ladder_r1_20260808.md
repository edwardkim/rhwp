# R55 대형 문서 규모 사다리 1차 실측 보고서 (2026-08-08)

- 로드맵: `mydocs/tech/agent_roadmap/track_f_scale_perf.md` — R55 "대형 문서 상한
  실측·한계 공표" `[가설]`
- 도구: `tools/scale_ladder.py` (이번 브랜치에서 신규 — 합성 HWPX 생성기 + 실측 러너)
- 원시 데이터: 러너가 출력한 TSV (본문 표에 전량 전재)

## 1. 범위 — 1차가 하는 것 / 안 하는 것

R55 의 착수 게이트는 "규모 사다리 코퍼스(대형 합성 문서 생성기)가 선행 준비물 —
없으면 그것부터"다. 이 1차는 그 선행 준비물(생성기)과 **대표 명령 4종 × 사다리
실측 + 한계 공표**까지만 착지한다.

- **하는 것** — 문단 축(1k·5k·20k·50k)·표 축(5열×100·1k·5k행) 합성 코퍼스 생성,
  대표 명령 4종(`info`·`export-text`·`export-structure`·`export-pdf`) 실측,
  첫 실패 지점·급증 지점·안전 영역 공표.
- **안 하는 것(후속)** — 전 명령 전수(`export-svg`·`export-hwpx`·`search` 등),
  실패 지점의 회귀 가드 고정(R55 DoD 후반), 수백 MB 급 실물 밀도 사다리,
  `--text-as-paths` 메모리 절감 실측, R56(스트리밍 export) 게이트 판정.

## 2. 방법

- 합성 HWPX: 저장소 fixture 관례(`tools/make_issue3765_fixture.py` 등)대로
  `samples/tac-host-spacing.hwpx` 를 껍데기로 쓰고 `Contents/section0.xml` 만
  갈아 끼운다. 문단 축은 한·영 혼합 ~150자 문단을 N 개 복제, 표 축은 5열 × N행
  단일 표(짧은 셀 텍스트) 1개.
- 명령별 측정: 프로세스 스폰 포함 벽시계 ms, 최대 RSS(Windows
  `PeakWorkingSetSize` — 정확값), exit code. 명령당 타임아웃 120초.
- 사다리 원칙: 한 단에서 타임아웃/실패한 명령은 더 큰 단에서 건너뛴다(skipped).
- 각 단 **1회 실행**(콜드, 순차) — 편차·워밍업은 이번에 재지 않았다.
- `info`·`export-text`·`export-structure` 는 `--json`(stdout 봉투)로,
  `export-pdf` 는 실제 산출 파일 생성으로 측정(레이아웃+렌더 경로).

## 5. 판독 — 첫 실패 지점과 급증 지점

1. **파싱 계열 3종(`info`·`export-text`·`export-structure`)은 이 사다리 안에서
   벽이 없다.** 50,000 문단(3,572쪽 상당, XML 20MB)까지 전부 exit 0, 최악
   10.7초 / 260MB. 단 간 증가가 대체로 선형이다(예: info 86→315→1,482→4,370ms,
   문단 ×5·×4·×2.5 에 시간 ×3.7·×4.7·×2.9).
2. **첫 실패 지점은 `export-pdf` × 문단 5,000(358쪽) — 실패 모드는 시간이다.**
   72쪽(1,000문단)은 76.9초에 완주(쪽당 ~1.07초, PDF 2.4MB·72쪽 확인). 358쪽은
   같은 비례로 ~380초 상당이라 120초 안에 끝나지 않았다. 타임아웃 시점까지
   메모리는 문제가 아니었다(1,000문단 성공 시 피크 119MB).
3. **메모리 급증 지점은 `export-pdf` × 표 5,000행 — 피크 1,415MB.** 시간(93초)은
   통과했지만 RSS 가 한 단 사이(1,000→5,000행)에 261MB→1.4GB 로 ×5.4 뛰었다.
   같은 배율이면 다음 단(1만 행대)에서 수 GB — 시간보다 메모리가 먼저 벽이 되는
   축이다.
4. **표 축의 쪽 분할 관찰** — 합성 5,000행 표를 `info` 가 pageCount=2 로 보고하고
   PDF 도 2쪽으로 렌더된다(내부 page 객체 수로 확인). `treatAsChar=1` 단일 거대
   표가 쪽 분할되지 않는 것으로 보인다. 이 1차에서는 원인을 파지 않았다 — 표 축
   수치는 **표 파싱·렌더 비용의 사다리로만 유효**하고, 대형 표의 쪽 분할 동작
   실측은 실물 표 문서로 후속에서 봐야 한다.

## 8. 정직성 단서 — 이 수치가 말하지 않는 것

- **합성 문서는 실물 공공문서가 아니다.** 같은 문장의 반복이라 zip 압축률이
  비정상적으로 높고(50,000문단: zip 434KB vs XML 20.1MB), 이미지·수식·개체·
  다중 구역이 없고 폰트도 1종이다. "수백 MB" 실물급 입력의 실측은 아직 아니다 —
  R55 의 "수백 MB·만 쪽" 문장 중 이번에 실증한 것은 **만 쪽 상당(3,572쪽)의 문단
  규모**까지다.
- **linesegarray 를 넣지 않았다.** 레이아웃 엔진이 전부 재계산하는 경로를 쟀다.
  한컴이 저장한 실물(lineseg 있음)과 코스트 프로파일이 다를 수 있다.
- **각 단 1회 실행이다.** 편차·캐시 워밍업을 재지 않았고, 콜드 스타트(프로세스
  스폰·폰트 로드)가 포함된다. 예열 스모크(50문단)에서 export-pdf 가 3.3초였던
  것으로 보아 고정 오버헤드가 ~3초 수준 있으나 이번에 분리하지 않았다.
- **타임아웃 120초는 러너의 설정이지 도구의 한계가 아니다.** 358쪽 PDF 는 더
  기다리면 끝날 수도 있다 — "120초 안에 못 끝난다"까지만이 이번 실측의 주장이다.
