## 환경 제약이 범위를 정했다

현재 개발 환경(Linux)에 Swift·.NET 툴체인이 없다. 이슈가 제시한 3단계 중 최소
(소스 가드)만 채택했다 — **검증할 수 없는 것을 CI 에 넣지 않는다.** 넣어도 "동작한다"고
말할 근거가 없고, 러너에서 처음 도는 것을 확인 없이 배포하는 셈이 된다.

## 검출한 표류 — C# 의 `rhwp_read_text` 누락

시간순 실측으로 **의도적 제외가 아님**을 확정했다.

| 시점 | 사건 |
|---|---|
| 2026-05-04 | C# 래퍼 도입(`dcd33bd52`) — 당시 `rhwp_read_text` 없음 |
| 이후 | Rust 에 `rhwp_read_text` 추가 |
| 2026-05-13 | **Swift 만** 반영(`75d76f854`, `readText` 공개 API) |

C# 만 갱신되지 않았다. 예외 등재가 아니라 정정이 답이므로 `ReadText` 공개 메서드와
`[DllImport]` 를 추가했다.

**이것은 선언 누락이 아니라 기능 격차였다** — C# 사용자는 파일로 내보내지 않고 텍스트만
읽는 경로를 쓸 수 없었다. 정정으로 두 래퍼의 공개 API 가 3개로 대칭이 됐다.

## 설계 — 인자 "개수"만 비교하는 이유

같은 것을 세 표기로 쓴다:

| Rust | C | C# |
|---|---|---|
| `*const c_char` | `const char *` | `byte[]` |
| `*mut c_char` | `char *` | `IntPtr` |

타입 문자열을 그대로 맞추려 들면 공백·별표 위치 차이로 오탐이 난다. **이름과 인자
개수**가 어긋나는 것이 실제로 터지는 표류다.

### 가드 자체의 오탐을 먼저 잡았다

첫 구현이 "Rust 4 vs C 헤더 3"을 보고했는데, **Rust 의 후행 콤마**(`page: i32,\n)`)를
인자로 세는 내 버그였다. 고치지 않았다면 진짜 결함(`rhwp_read_text`)이 오탐 속에
묻혔을 것이다. **계측을 신뢰하기 전에 계측을 검증해야 한다.**

## red-check — 3축 전부 검출

| 흔든 지점 | 결과 |
|---|---|
| C# 선언 제거 | 2건 실패 |
| C 헤더에서 함수 제거 | 검출 |

세 번째가 이 가드의 본래 목적이다. #3664 에서 `rhwp_string_free` 를 `unsafe` 로
바꿨을 때 **래퍼 영향을 코드 판독으로만 확인**했는데, 이제 권위가 바뀌면 두 소비자가
자동으로 잡힌다.

## 파싱 실패는 조용히 통과하지 않는다

세 파서 모두 결과가 비면 `assert!` 로 실패한다. 선언 형식이 바뀌어 가드가 아무것도
못 읽으면 **통과가 아니라 실패**다 — #3664 형(가드가 죽은 채 초록) 함정 차단.
