## 브라우저 기준선

각 조건을 별도 브라우저 컨텍스트에서 실행했다. 실제 파일 입력에 저장소의 합성 1쪽 HWP를 전달하고, 성공 상태가 상태 표시줄에 기록된 순간 연결된 페이지 캔버스를 셌다. 이벤트는 첫 CanvasView.loadDocument의 첫 metrics 준비에서 microtask로 한 번 전달했다. 공식 v0.9.0 Chrome 배포본은 로컬 HTTP로 제공하면서 최초 로드 진입점에 계측 훅을 넣었다. devel과 수정본은 해당 소스로 빌드한 Web WASM과 Studio 개발 서버에서 실행했다.

| --- | ---: | ---: |
| v0.9.0 | 1 | 0 |
| 기준 devel | 1 | 0 |
| 수정본 | 1 | 1 |

## 구현과 회귀

CanvasView는 같은 문서에서 먼저 시작한 metrics 응답이 지연돼도 현재 렌더러가 준비되면 최초 페이지를 구성한다. 첫 화면의 복구 작업이 끝나고 보이는 페이지의 캔버스를 확인한 뒤 로드 완료를 알린다. 새 열기가 시작되면 이전 열기의 진행 및 성공 상태 갱신을 취소한다.

`rhwp-studio/e2e/initial-page-render-issue9164.test.mjs`는 기존 합성 HWP·HWPX 두 개를 사용한다. 입력 채널에서 시작해 성공 표시 시점의 현재 파일, 문서 세대별 완료 통지 횟수, 첫 캔버스의 잉크를 검사한다. 비교용 픽셀 서명은 같은 실행의 정상 열기에서 얻는다.

| 브라우저 검증 | 결과 |
| --- | --- |
| loadingdone 단일·연속 발생 | 정상 열기와 같은 첫 쪽. 연속 발생은 오래된 준비 응답을 풀기 전에 완료 |
| 실제 WOFF2 응답 지연 | Chromium이 발생시킨 loadingdone 확인 후 정상 열기와 같은 첫 쪽 |
| 호스트 글꼴 공급자 변경 | 빈 합성 카탈로그로 갱신 후 정상 열기와 같은 첫 쪽 |
| 최초 metrics 준비 예외 | rendererPreparationFailed 대체 경로로 복구, 성공 시점에 본문 잉크 확인 |
| 동일 이름·바이트 재열기 | 새 문서 세대의 완료 통지 1회, 정상 열기와 같은 첫 쪽 |
| HWP 준비 중 HWPX로 교체 | HWPX 완료 후 HWP 준비를 풀어도 HWP 성공 표시 0회, HWPX 첫 쪽의 픽셀 서명 유지 |
| 복구할 수 없는 첫 paint 실패 | 상태 표시줄에 오류 표시, 해당 파일 성공 표시 0회 |

구현 커밋에서 TypeScript 검사, Studio 단위 테스트 2,807개(실패·건너뜀 0개), E2E 목록 검사(195개)와 diff 공백 검사를 통과했다. 단위 테스트는 새 Node WASM 바인딩을 공급해 두 WASM 왕복 검사까지 실행했다. 브라우저 E2E는 개발 서버를 실행한 뒤 Studio 디렉터리에서 `VITE_URL=<서버 주소> node e2e/initial-page-render-issue9164.test.mjs --mode=headless`로 재실행할 수 있다.

실제 사용자 환경에서 자연 발생한 이벤트의 순서는 확인되지 않았다.

## Firefox 다운로드 자동 열기

macOS의 Firefox 160.0.1을 headless로 실행했다. 매회 독립 프로필에 확장을 임시 설치한 뒤 HTTP 페이지의 다운로드 링크를 클릭했다. 서버가 확장자 없는 URL에서 합성 HWP를 attachment로 응답했다. 매회 Firefox 다운로드 기록에서 31,744바이트 완료를 확인하고, 확장이 자동 생성한 moz-extension 뷰어 탭에서 성공 상태와 캔버스를 읽었다.

| 최초 열기 조건 | 공식 Firefox 확장 v0.9.0 | 수정 브랜치 Firefox 확장 |
| --- | --- | --- |
| 계측 훅·이벤트 주입 없이 각 3회 | 3회 모두 1페이지 완료 표시, 캔버스 0개 | 3회 모두 1페이지 완료 표시, 캔버스 1개와 본문 잉크 확인 |
| 위 실행 중 각 2회에서 2초 후 재확인 | 캔버스 0개 유지 | 캔버스 1개 유지 |
| 최초 metrics 준비 중 loadingdone 주입 각 1회 | 캔버스 0개 | 캔버스 1개와 본문 잉크 확인 |

별도로 v0.9.0에 관측 훅을 추가한 1회에서는 최초 metrics 준비 도중 Firefox의 신뢰된 loadingdone이 발생했고 본문이 표시됐다. 자연 재현에 성공한 세 실행에는 해당 훅이 없어 그 순간의 내부 순서를 단정할 수 없다.

## 최신 devel에 통합한 뒤의 검증

기준 `1695089d21`에 포함된 #9168의 3쪽 합성 표 셀 입력을 기준과 후보에서 같은 release WASM으로 실행했다. 입력 20회 동안 페이지 트리 조회는 양쪽 모두 공급자 미연결 0회, 빈 카탈로그 0회, 글꼴 공급 20회였다. 세 조건에서 조판 해시, 편집 결과, 커서, 최종 쪽수가 일치했다. 최초 시도의 dev WASM은 기준 자체에서 글꼴 공급 시 준비 40회로 원 검사의 20회 조건을 벗어나 원 PR이 사용한 release 조건으로 양쪽을 대조했다.

리베이스 후 TypeScript 검사, Studio 단위 검사 2,808개(실패·건너뜀 0개), E2E 목록 검사 196개 및 #9164 브라우저 회귀를 통과했다. Firefox 확장을 다시 빌드해 합성 파일을 다운로드했을 때 별도 이벤트 주입 없이 첫 화면에 본문이 표시됐고 2초 뒤에도 유지됐다. 제출 전 본인 열린 PR은 0건이었고 최신 devel과 후보의 병합 시뮬레이션은 충돌 없이 끝났다.
