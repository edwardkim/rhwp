## 피드백

> 하이퍼 워터폴 규칙을 준수해서 이슈를 먼저 등록하고 현재 작업을 소분해서 문서를 추가한 후 PR을
> 등록하는 게 좋을까?

작업지시자는 구현 결과만 남기지 말고, 이슈를 작업 좌표로 삼아 조사·구현·검증을 단계화하고 PR 전에
문서 계보를 복구하도록 지시했다.

## 누락된 게이트

[`docs_and_git_workflow.md`의 Issue Workflow](../manual/codex/docs_and_git_workflow.md#issue-workflow)와
대조하면 다음 순서가 누락됐다.

| 절차 | 실제 상태 |
| --- | --- |
| 동일 증상 이슈 검색·이슈 등록 | 구현 뒤 수행 |
| assignee 지정 | #6112 등록 시 수행 |
| 이슈 번호 기반 브랜치 | 구현 뒤 이름 정리 |
| 수행 계획서·구현 계획서 | 구현 뒤 사후 재구성 |
| 계획 승인 | 구현 전에는 받지 못함 |
| 단계별 구현·보고·승인 | 단일 구현 commit 뒤 사후 재구성 |
| 최종 보고 | PR 전 복구 |

## 원인

사용자의 `그렇게 진행해줘`를 기능 구현 승인으로만 해석하고, 저장소의 이슈 기반 작업 절차를 먼저
적용하지 않았다. 관련 문서를 읽고 기존 자산과 코드를 조사했지만, 그 조사 결과를 이슈와 계획 승인
게이트로 외부화하기 전에 구현으로 넘어갔다.

기능 범위가 기존 커맨드에 버튼·단축키를 연결하는 작은 작업이라는 사실도 절차 생략 근거가 될 수
없다. canonical 워크플로에는 변경 규모에 따른 이슈·계획 면제 조항이 없다.

## 영향

- 작업 번호가 없어 계획·테스트·커밋을 GitHub에서 한 좌표로 추적할 수 없었다.
- 기본값을 신규 사용자만 바꿀지 모든 사용자에게 강제할지 계획 검토에서 확인할 기회를 줄였다.
- 버튼 위치와 서식 도구 상자 소형화의 비범위 판정을 구현 전에 승인받지 못했다.
- 구현 commit 하나에 실패 계약, 제품 변경과 검증 결과가 함께 묶여 단계 경계가 사라졌다.

## 복구

1. 열린 이슈를 증상·단축키·커맨드 이름으로 검색하고, 닫힌 선행 #5738만 있음을 확인했다.
2. 후속 이슈 #6112를 등록하고 `postmelee` 담당·`enhancement` 라벨을 확인했다.
3. 브랜치를 `codex/issue-6112-toolbox-collapse`로 변경했다.
4. 수행·구현 계획, 3단계 보고, 최종 보고와 오늘할일을 추가했다.
5. 각 문서에 사후 재구성임을 명시하고 구현 commit을 재작성하지 않았다.
6. 문서 검토 승인 뒤에만 PR 준비·등록으로 이동한다.

## 재발 방지

- rhwp의 코드 변경 요청을 받으면 첫 쓰기 전에 `Issue Workflow`를 체크한다.
- 이슈가 없으면 동일 증상 검색 → 등록·할당 → 브랜치 → 계획 문서 → 승인 순서를 먼저 밟는다.
- `진행해줘`는 현재 제시한 단계의 승인으로만 해석하고 이후 PR·CI·merge 게이트를 포괄한다고
  간주하지 않는다.
- 구현이 먼저 생겼다면 계획을 과거형으로 꾸미거나 커밋을 인위적으로 분할하지 않고, 사후 재구성
  고지·원인·실제 증적·다음 유효 게이트를 기록한다.
