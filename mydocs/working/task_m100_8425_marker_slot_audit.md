# 이슈 #8425 — 기본 개요 번호의 영역과 글리프 폭 대조

2026-11-05 KST. 기존 통합 대상 [PR #8433](https://github.com/edwardkim/rhwp/pull/8433)의
주장 쪽을 직접 판독한 결과다. 새 PR 접수나 원격 변경은 하지 않았다.

## 원 해결 PR과 원본

원 PR 본문을 다시 확인했다. 작성자는 `default_outline_numbering()`에 본문과의 거리
50%, 자동 내어쓰기, 너비 보정 0을 합성했다. 주 회귀 대상은
`samples/task3307/issue3307_outline_number.hwpx` 7쪽이다. 이 입력의 실제 개선과 별도로,
기여자가 제공한 수준 1~7 탐침도 독립 한컴 2020·2024 Print와 대조했다.

원본 탐침 HWPX는 번호 정의가 없으며 제목의 `charPrIDRef=2`는 12pt·굵게,
문단의 `heading`은 OUTLINE·idRef 0이다. 문단 들여쓰기는 0이다. 이 문서는 엔진이
만든 합성 탐침이므로 정상 저장본과 구분하며, 독립 Print의 실제 좌표를 구현과
독립적인 관측값으로만 사용한다. PDF를 새로 출력하거나 원본을 수정하지 않았다.

## 관측과 사양

[HWP5 사양 표 40](../tech/한글문서파일형식_5.0_revision1.3.md#표-40-문단-머리-정보-속성)의
bit 2는 번호 너비를 실제 인스턴스 문자열 너비로 정할지를 나타낸다. 현재 합성 속성은
bit 3만 켜며 bit 2는 꺼져 있다. 그런데 `list_marker_geometry_for`는 이 비트를
읽지 않고 ASCII 번호의 `marker_text_width`를 항상 사용한다.

두 한컴 PDF의 실제 문자 원점을 추출했다. 긴 번호가 별도 PDF 텍스트 블록으로
나뉘는 경우에도 같은 기준선의 번호 문자를 찾아 내용이 `1.`의 수준별 반복인지
검증하고 본문과 연결했다. 실제 공백 bbox를 번호 글리프 폭으로 오인하지 않는다.
제목 본문 시작은 번호 시작에서 각각 약 1.5em, 2.5em, …, 7.5em이다. 두 엔진은
같다. 현재 Native의 시작점은 1수준에서 약 2.07 CSSpx, 7수준에서 약 14.51 CSSpx
왼쪽이다. 이 수치는 수정 상수나 고정 회귀 기대값이 아니라 결함의 진단 관측이다.

[원본·PDF 해시와 수준별 실제 관측](../pr/assets/planet6897_20261103/pr_8433/marker-slot-diagnostic.json)을
보존했다. 사용한 Native 트리는 전쪽 TSV와 같은 `4b149b6cdf` 캡처다. 새 제품의
재출력으로 표시하지 않는다. 보조 `rhwp-q font-trace`는 backend paint를 지원하지
않는다고 명시하므로 그 결과만으로 실제 Bold 면 선택이나 획 차이의 원인을 확정하지 않는다.

## 다음 검증과 현재 판정

실제 번호 폭과 예약 영역을 분리하는 공통 규칙을 먼저 확인한다. 기본 개요만의 근거를
명시적 번호 정의·글머리표 전체에 자동 적용하지 않는다. 한 자리·여러 자리 번호,
수준 경로·정렬·너비 보정과 실제 너비 비트가 켜진 반례를 기존 독립 자료에서 대조한다.
측정·줄 나눔과 최종 배치가 같은 번호 영역 결과를 소비하도록 수정해야 하며, 현재
7쪽 정상 대조군과 보호 대상 PR #8389·#8397의 표시값을 떨어뜨리면 안 된다.

탐침 1쪽의 raw가 90%를 넘었다는 이유로 제목 시작점 차이를 정상으로 판정하지 않는다.
이 기록 시점에는 해당 공통 구현을 수정하지 않았으며 최종 수용 판정은 대기다.
