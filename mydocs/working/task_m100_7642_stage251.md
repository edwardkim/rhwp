# 작은 확장 둥근 괄호의 글꼴 행렬과 채움 윤곽

Issue: #7642

## 독립 Print 근거

Stage241의 24개 독립 수식 입력은 한컴 MCP 저장·Print를 마친 HWP와 PDF다.
PDF의 ToUnicode는 기본 둥근 괄호 E044/E045를 가리키며 출력 연산자의
`Tf`와 `Tz`를 읽으면 세로·가로 em이 분리된다. 예를 들어 900HU의
`LEFT ( a _n RIGHT )`에서 본체 높이는 1078HU이고 세로 em은 약
14.38944px, 가로 em은 약 12.15129px다. 정상 크기의 괄호는 양쪽 em이
약 11.991px다. 이 값은 PDF 출력 격자의 반올림을 포함한다.

PyMuPDF의 span size는 가로·세로 크기의 결합값이므로 이를 세로 em으로
간주하지 않는다. 앞서 추정만 했던 크기를 원래 PDF 출력 연산자와 대조했다.
PDF 원문·명령·측정 JSON은 ignored `stage241-small-delimiter-diagnostic`에
있으며 기준 HWP/PDF를 바꾸거나 사설 글꼴 윤곽을 복제하지 않는다.

## 생산과 소비

현재 layout은 큰 괄호에 공개 MATH 부품의 채움 윤곽을 발행하지만 작은
확장 괄호에는 윤곽을 발행하지 않아 backend의 선 경로를 사용한다.
같은 source face의 작은 확장 괄호도 기존 Latin Modern Math 기본 괄호
채움 윤곽을 사용한다. 정상 가로 em을 유지하고 세로 em을 본체 높이에
맞춰 이미 확인한 잉크 bbox 프레임에 중앙 배치한다. 실물 문서 ID·px 위치·
점수 임계값에 따른 분기는 넣지 않는다. 큰 괄호 조립과 일반 글리프 경로는
기존 소비 계약을 따른다.

`delimiter_outline`이 같은 윤곽을 layout에 저장하고 SVG와 Canvas가
이를 소비한다. Native math8·24개 진단·기존 수식 대조군을 한 빌드로 먼저
확인하며, 이후 fresh WASM·직접 판독을 확인한다. 미달이면 이 후보를
시각 개선 완료로 보고하지 않는다. 새 관계 회귀 추가는 선행 gate 이후다.
