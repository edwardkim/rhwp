# #7642 Stage 166 — DYAD 최종 윤곽 표시의 관계 검사

## 독립 근거와 선행 조건

Stage 165의 같은 공개 원본과 한컴 2020 Print를 Native/fresh WASM으로 각각
전체 1쪽 비교했다. 원본 최저 98.50470%, 최소 대조군 99.17678%이며 큰 보기
예약 높이와 본문 간격을 확대 판독했다. 소스는 `c7472832df262ec48c639f35b29301ad9365c4a8`다.
새 저장 예약 영역 검사는 수정 후 실제 nextest PASS, 수정 전 같은 검사도 의도한 예약 영역 assertion으로 실제 FAIL을 확인했다.

기존 `issue_7593_print_placement`의 두 검사는 SVG `<text>`로 AB를 찾고
`<line>`으로 장식 폭을 찾는다. 현재 공개 윤곽 글리프와 장식은 `<path>`로
표시되므로 요소 이름에 의존하는 검사를 재검토한다. 실제 배치 결함과 표시
요소 종류의 변경을 구분하고, 새 이름의 검사로 독립 Print의 의미를 보존한다.

## 검사 항목과 출력 경로

- RenderTree의 수식 script·셀/문단 소유로 실제 대상을 선택한다. 고정 px 영역으로
  선택하지 않는다. 측정 트리의 실제 문자 순서·정체와 출력 보존을 함께 확인한다.
- 실제 최종 Print SVG를 usvg로 읽어 조상 변환이 적용된 표시 윤곽을 대조한다.
  대상 수식의 점유 상자와 실제 경로의 포함 관계로 내용을 찾아, 발문/보기의
  같은 BaseUnit은 다른 예약 폭에서도 같은 paint 폭인지 검사한다.
- 보기 ㄴ의 표시 잉크는 뒤 본문보다 위에 있어야 하며 수식→본문이 겹치지
  않아야 한다. 기존 저장 예약 영역·기준선 비율의 새 검사는 별도로 유지한다.
- 두 기존 검사는 새 함수명과 파일로 이관한다. 나머지 소유·탭·관계 기호 검사는
  유지한다. SVG 해시·절대 px 위치·새 골든 완화로 실패를 숨기지 않는다.
- 하나의 공용 target에서 수정 전 검사가 끝난 뒤 새 검사 묶음을 한 번에 실행한다.
  최종 전체 회귀·Native/WASM·lint·최신 devel 동기화와 PR은 아직 남아 있다.

## 결과

같은 표시 구현을 소비하는 7개 실제 nextest 검사를 모두 통과했다.
새 함수명은 `equal_base_units_keep_equal_final_dyad_ink_with_different_reservations`와
`tall_dyad_final_ink_stays_above_the_following_owned_cell_text`다. 기존 두 검사의
문자/정체·최종 paint 폭·보기 본문의 관계를 보존하고, 실제 최종 SVG를 읽어
문단/셀 소유에 따른 상자의 표시 잉크를 검사한다. 고정 px 영역이나 좌표 기대값을
추가하지 않았다. SVG 윤곽을 읽는 usvg의 f32 연산 오차는 상대 비율에서만 처리한다.
구현 소스는 바뀌지 않았으며 Stage 165 Native/fresh WASM 검증과 동일한 소스
해시를 다시 확인했다. 전체 테스트나 전체 제출 범위의 완료를 뜻하지 않는다.


수정 전 worktree의 예약 영역 검사는 의도한 원인으로 FAIL했고 Stage 165 문서에
수정 후 PASS와 같은 검사 해시를 연결했다. 현재 두 윤곽 검사와 나머지 소유·탭·
관계 기호, 저장 예약 영역을 합한 7건의 집중 묶음을 실행한다.
첫 실행은 6 PASS / 예약 영역 1 FAIL이었다. 수정 전 worktree 빌드 직후 공용
release-test target을 재사용한 실행이므로 현재 source 재컴파일을 확인한다.
소스 내용을 바꾸지 않고 수식 모듈의 mtime만 갱신했으며 Cargo fingerprint 로그가
현재 소스의 dependency library 재컴파일을 확인했다. 첫 실패 로그와 모든 기대값은
그대로 보존한다. 현재 소스의 실제 재컴파일 뒤 동일한 7건이 모두 PASS했다. 소스 내용·입력·
기대값·검사 SHA는 바뀌지 않았다. 따라서 첫 실행을 현재 코드의 회귀로 보고
기대값을 수정하지 않았다. 별도 worktree의 비교 빌드 뒤 공용 산출물을 쓸 때는
소스 해시뿐 아니라 실제 재컴파일 또는 실행 산출물의 출처도 확인해야 한다.
첫 시도는 `stage166-dyad-focused-first-attempt/`, 확인 실행은
`stage166-dyad-focused/receipt.json`과 `nextest.log`에 보존한다.

시험지 경계 추적에서는 현재 단의 첫 미주 pi=493의 저장 원점이 직전 pi=492의
줄 끝보다 앞인 것을 확인했다. 이는 기존 `endnote_column_starts_at_stored_break`
계약으로 저장 단 시작에 해당하지만, 내부 컷의 전체 fit 수용·취소 경로는 그
계약을 소비하지 않는다. 다음 보정은 편집 후 재조판과 유효한 저장 단 소속을
구분하는 공통 경계를 대상으로 분석한다. 원본 HWPX의 경계 정보 손실도 별도다.
현재 `SO-SUEOP.hwpx`는 원본에서 문단 마지막 0 패턴이 발견되지 않아 오래된
주석의 아티팩트 사례와 같은 입력이라고 추정하지 않는다. 합성 기대값만으로
정상 저장 LineSeg의 단 소속을 덮어쓰지 않는다.


전체 대상 목록의 HWPX 21개 원본 해시를 대조한 읽기 전용 조사에서 12개 입력의
미주 문단 마지막 0이 현재 파서의 비영 되감김 검사를 통과하지 못하는 패턴임을
확인했다. `stage166-full-hwpx-terminal-note-reset-audit.json`에 원본 위치와 저장
사다리를 보존했다. 이 12개 모두가 실제 결함이라는 판정은 아니며 독립 Print와
짝 입력을 계속 대조한다. 문서 ID 예외 대신 저장 분할의 유효성 계약을 확인한다.
