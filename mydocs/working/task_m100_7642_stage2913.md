# #7642 표 오프셋 실패의 정확한 입력·독립 Print 확보

Issue: #7642

## 정확한 원 회귀 입력

#5566 실패 검사가 만드는 HWPX 두 개를 다시 만들거나 근사하지 않았다.
현재 자동 수집 suite를 nextest 목록에서 찾아 정확한 테스트 한 개를 실행하고,
원래 생성기가 파일을 닫은 직후·지우기 전에 자기 PID의 두 임시 파일만 복사했다.
검사 소스·파라미터와 생성기를 변경하지 않았다. source는6052118a3c이며
입력 원본 `samples/hwp_table_test-m.hwp` SHA-256은
`3b060970d3762a981948cc408edcfb5ba7af037781419142c658318d9c6dfc8c`다.

| 보존 입력 | 바이트 | SHA-256 |
| --- | ---: | --- |
| voff0.hwpx | 14176 | `40ad1749c9b7f2e8686f2ced5b7c497a51206bb3f593f255019cfb557411b119` |
| voff1904.hwpx | 14182 | `014004a52c1ff60b262a795121f274189d3a00534b3ce5dd77b50262ffcd9fcf` |

원래 검사는 같은 증상의 종료 코드101을 재현했다. 최초 시도는 파생 suite 번호를
이전 번호로 가정해0건 실행했으므로 재현이나 통과로 세지 않는다. 자동 수집
후 실제 모듈 소속과 nextest의 해당 case `filter-match=matches`를 확인해 고쳤다.
전역 `test-count`는 필터 뒤 실행 수가 아니므로 그것으로 한 건 실행을 단정하지 않는다.
이전 시도의 로그도 stage2910에 분리 보존했다.

## 독립 한컴 Print

두 입력을 변형하지 않고 MCP `start → status → download`로 PDF 출력했다.
engine2020, 실제 한컴11.0.0.9136, `pdf_print_method=0`,
`pdf_output_mode=hancom2020_pdf_driver_one_up`을 결과에서 확인했다.
각 PDF는3쪽이다. 인증 정보는 기록하지 않는다.

입력은 ignored stage2910, PDF·metadata·Print 증거는 ignored stage2911에
있다. 아직 시각 자격이 없는 진단 입력이라 임시 파일을 루트에 추가하지 않았다.
수용 근거로 확정할 때에는 같은 바이트의 입력과 PDF를 정식 fixture로 옮긴다.

## 관측과 검사 전제 구분

독립 Print에서 첫 표의 위쪽 선은216.843→235.902pt로 내려가고, 뒤의
`□ 셀 편집(테두리, 배경, 대각선)`도382.382→401.441pt로 내려간다.
차이는약19.059pt, 즉 입력1904HU에 대응한다. 앵커 제목의 줄은 같은 위치다.

현재 Native의 첫 표 위쪽은251.0→276.4px다. 다음 `TextLine`을 잡는 기존
검사의349.8→247.2는 뒤 본문이 아니라 표와 같은 **문단3의 앵커 제목**이다.
실제 뒤 본문의 문단4도396.2→308.0으로 올라가므로 검사 선택 오류만 있는
것은 아니다. 원문 소유로 검사를 고치기 전에 실제 앵커·흐름 출력을 보정해야 한다.

표의 선언 높이는7126HU, 현재 실제 높이는95px다. Print의 첫 표도 위·아래
선 차이약71.202pt, 즉약94.94px이므로 표 높이를 임의로 늘려 해결하지 않는다.
첫 표 원점과 앵커 줄의 순서·점유를 생산/소비 경로에서 추적한다.

stage2912에서 Native/fresh WASM 모두 각3쪽을 직접 산출했다.

| 입력 | Native p1/p2/p3 raw | fresh WASM 최저 raw |
| --- | --- | ---: |
| voff0 | 45.42732 / 37.21762 / 17.56084% | 17.59733% |
| voff1904 | 50.25074 / 37.21762 / 17.56084% | 17.59733% |

90% 미달이므로 이 검사의 기대값이나 baseline을 갱신하지 않았다. 전체 쪽수가
같다는 이유로 통과시키거나 원문과 가까운 다른 샘플의 점수를 대신 쓰지 않는다.
캡처 runner의 초기 입력 키 오류는 측정 전 실행 실패이며 별도 보존 후 고쳤다.

## 다음 원인 추적의 경계

`layout.rs`의 `para_start_y/para_y_for_table` → Square 앵커 선택 →
`layout_table/compute_table_y_position`과 실제 host 줄 방출을 연결한다.
`ctx.paragraph_float_placements`의 확정 배치 소비 경로와 별도 fallback도
함께 본다. 기존 #5566의 양수 offset 분기만 바꾸거나 좌표를 clamp하지 않는다.
원문 제어 위치 앞의 가시 텍스트·유효한 저장 줄·재조판을 구분하고 실제 줄
구성 결과를 측정과 배치가 함께 소비하는지 확인한다. 오른쪽 어울림 다줄,
빈 host와 이미 반영한 #7969 대조군의 보존도 계속 검증한다.

이 단계는 원인 확정이나 구현 완료가 아니다. 정식102문서 Native는 전쪽90%
이상으로 종료했지만, 새 진단 두 입력·남은12회귀·devel 하락·최종 WASM 및
전체 Rust/lint는 별도로 남아 있다. PR을 만들지 않았다.
