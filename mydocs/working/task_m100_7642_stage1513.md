# Issue #7642: HWP3 제목의 원문 공백과 위치 축 조사

## 현재 관측과 독립 근거

생산 코드는 `c239bf118`, PDF 래스터 정책을 포함한 검증 head는
`63a1c13b2`다. `63985edd8`의 전체 회귀는 실행 중이므로 이 단계에서는
추적된 Rust 소스·검사·fixture를 변경하지 않았다. 전체 실행은 이후
10,435 통과·15 실패로 종료했고 소스 해시 유지도 확인했다.

`stage1508-hwp3-current-qualification/receipt.json`에서
`samples/hwp3-sample16.hwp`의 전 64쪽을 원본의 독립 Print PDF와 대조했다.
Native 최저는 92.25853%, fresh WASM 최저는 95.76171%이고 쪽수 차이는 없다.
3쪽은 각각 99.60810%, 99.58123%다. 이 수치만으로 완료 판정을 내리지 않았다.
확대 판독에서 첫 제목의 번호 뒤 공백이 누락된 것을 확인했다.

독립 PDF는 `pdf/issue7642-hwp3-original-print/hwp3-sample16-2020.pdf`다.
SHA-256은 `f1f2e6dd265d098ea468bae14b44e98a1609dd7eba293f91d73ba16704be73c5`다.
원본 hchar와 Print 양쪽에 `1. 추진목적`의 공백이 존재한다.
보정 전 파싱 결과는 `1.추진목적`이다. PDF의 번호 기준선은 CSS 96dpi에서 y=159.199992이며,
제목 본문 시작은 x=109.919993이다.

ignored 증적 루트는
`output/pr-review/issue7642/failed-inputs-20261008/stage15-current-validation/`이다.
`stage1512-hwp3-heading-details/`의 원문 hchar·PDF 문자 원점 JSON과
Native/Print 확대 PNG를 연결했다. 원문 압축 본문의 두 일치 구간은
`31 00 2e 00 20 00`으로 시작하며, hchar를 조합형으로 읽으면
`1. 추진목적`이다. 이 바이트 조사를 전체 HWP3 재파싱 증거로 대신하지 않는다.

## 생산과 소비 경로

`src/parser/hwp3/mod.rs::parse_paragraph_list_inner`는 원문 문자·제어 슬롯과
글자모양 위치를 읽은 뒤, 새번호·쪽번호 위치 컨트롤이 있는 짧은 제목에
장식을 합성한다. 이때 `filter(!is_whitespace)`가 원문 내부 공백까지 지우고,
문자 원점·글자모양 축을 합성 장식 기준으로 다시 만든다.

그 뒤 `fixup_hwp3_heading_decoration`은 장식을 제거한 문자열만 대입한다.
이미 사라진 내부 공백은 복원되지 않고, 문자 축은 합성 장식 기준으로 남는다.
공통 스타일 해소·글줄 측정·최종 TextRun은 이 변형된 문단을 소비한다.
현재 덤프의 가시 문자열은 6자지만 `char_count`는 53이다.

수정 방향은 원문에 없는 장식을 만들었다 지우는 가정을 제거하는 것이다.
독립 Print나 정상 저장본에 없는 공백·보정 좌표를 새로 주입하지 않는다.
원래 문자·컨트롤·글자모양과 저장 줄의 위치 축을 함께 보존한 출력으로 확인한다.
실제 원문에 장식 문자가 있는 입력과 다른 쪽번호 컨트롤 조합도 구분해야 한다.
전체 회귀와 배포 문서의 집중 검사를 종료한 뒤, 원문에 없는 장식을 합성하는
블록과 문자열만 다시 제거하던 후처리를 함께 제거했다. 원문 공백을 따로
추측해 넣거나 문자 원점을 보정하지 않는다. HWP3 일반 파서가 이미 읽은
문자·제어 슬롯·글자모양·줄 정보를 그대로 다음 단계에 전달한다.
다른 HWP3 입력의 실제 장식 문자열도 제어 조합으로 임의 삭제하지 않는다.
기존 장식 검사에는 의도를 설명하는 주석만 정정했고 기대값은 바꾸지 않았다.
아래 Native 재검증과 확대 판독을 완료했으며, fresh WASM은 별도 검증한다.

## 회귀 검토의 경계

기존 `sample16_hwp3_page3_heading_positions_follow_hancom_grid`는 HWP3 원본에
다른 저장 모드의 y=337.2/749.2를 적용한다. 독립 원본 Print의 두 번호 기준선은
y=359.039998/771.199951이다. 올바른 원본과 전체 시각 검증을 확보한 뒤,
새 이름의 검사에서 원본 문단 소유·제목과 후속 본문의 순서·내용 보존을 보호한다.
첫 제목의 알려진 공백 차이를 해소하기 전에는 3쪽을 완료 페이지로 취급하거나
그 페이지의 새 ±2px 좌표 검사를 등록하지 않는다.

6쪽 수식은 `stage1511-hwp3-equation-read/`에서 Native/fresh WASM/Print를
같은 페이지로 다시 출력했다. 전체 페이지와 확대 수식을 직접 대조했으며,
수식의 폭과 장식 간격 차이는 별도로 남아 있다. TextLine 조상 유무만으로
독립 수식의 의미를 판정하는 기존 검사를 즉시 뒤집지 않는다. 원본 Equation의
소유·본문 추출 순서·누락·중복과 실제 Print 배치를 함께 확인한 뒤 처리한다.

전체 회귀 종료 후의 실패 목록, 메타파일 별도 대조와 devel 대비 하락 페이지는
이 제목 조사와 구분한다. 이 단계는 전체 검증 완료나 PR 준비 완료가 아니다.

## 보정 후 Native와 원문 축 대조

`stage1520-current-native.json`의 Native 빌드는 종료 코드 0, 287.811초다.
빌드 잡은 8개이고 공용 `target/pr-review`를 사용했다. 생산 소스 해시 유지가 true다.
검증용 CLI SHA-256은
`0f21ce5dc4b0b13fd8de6bef9266be52d7c19d2bf5214b487fa35b441d45032c`다.
빌드 당시 부모 `c2c10df9b`와 작업 트리 diff·파일별 해시는 원래 기록대로 보존한다.

`stage1523-hwp3-native-qualification/receipt.json`은 같은 원본·Print·96dpi·none으로
전 64쪽을 다시 측정했다. 쪽수가 같고 최저 92.25853%, 미달·누락 0쪽이다.
변경된 3쪽은 **99.60810% → 99.94303%**이며 다른 63쪽의 수치는 동일하다.
`stage1523-hwp3-before-after.json`의 Decimal 비교에서 0.01%p 이상 하락은 없다.
기준 devel 대비 원래 목록 전체의 하락 문제를 이 결과로 해소했다고 주장하지 않는다.

새 3쪽 review와 `stage1523-hwp3-heading-review.png`를 같은 배율로 직접 읽었다.
번호 뒤 작성 공백과 제목 원점, 점선 박스 위의 간격을 독립 Print와 확인했다.
원본에 없는 장식과 제어 자리 문자가 가시 글자로 나오지 않는다.
2·6·19쪽도 별도로 출력했으며, 6쪽 수식의 기존 폭·장식 차이는 해결 범위에 넣지 않는다.

별도 파서 진단 `stage1525-hwp3-source-snapshot/receipt.json`은 samples의 HWP3 원본
27개를 전후 보존 라이브러리로 읽었다. 암호 입력 한 개는 양쪽 모두 같은 오류여서
비교 불가로 남겼다. 나머지 26개 중 25개는 문단 트리와 글자모양이 동일하다.
변경은 sample16의 구역 0·문단 70 하나뿐이며 `text`·`char_offsets`·`char_count`만
달라졌다. 글자모양 풀과 저장 줄은 동일하다. 이 대조는 문단 트리와 글자모양의
진단이며 전체 문서의 시각 일치로 승격하지 않는다.

보정 후 제목은 `1. 추진목적` 7자와 원래 세 제어 슬롯을 보존한다.
문자 배열은 10개이고 공통 IR의 문자 수는 `7 + 3×8 + 종결자 1 = 32`다.
종전 합성 장식 축 53을 가시 문자열 6자에 잘못 붙이던 상태와 구분한다.
진단 첫 시도는 Section의 Serialize 미지원으로 컴파일하지 못했다. 문단 트리와
글자모양만 명시적으로 수집하도록 고친 뒤 양쪽 컴파일·파싱 종료 코드 0을 확인했다.
초기 빌드 실패를 제품 결함 재현으로 세지 않았다.

sample10의 별도 원본 Print도 MCP 2020에 요청했으나, 위 대조에서 해당 문서의
문단·글자모양은 전후 동일하다. 이 요청의 성공이나 시각 검증을 미리 주장하지 않는다.
새 정식 회귀 등록은 새 생산 소스의 fresh WASM 전쪽 측정과 직접 판독 뒤에 진행한다.
