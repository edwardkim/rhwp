# #7642 남은 수학 간격과 출력 경로별 하락의 독립 근거 확인

Issue: #7642

## 기준과 원인 범위

기준 제품은 `85542514a`, 비교 devel은 `4662c069e`다. 26개 문서의 전쪽 90% 조건은
양쪽에서 통과했지만 Native 3쪽·fresh WASM 5쪽에 devel 대비 0.01%p 이상 하락이 남았다.
수학 2022년 9월 8쪽의 콜론은 본문·첨자 기준선이 아닌 기호와 전진폭 경로를 먼저 확인한다.
Print의 HyhwpEQ PUA U+E04F와 현재 Latin Modern Math 콜론을 같은 기호로 가정하지 않는다.

콜론 진단 HWPX는 수동 편집 전에 있던 양수 개체 크기와 LineSeg를 유지했고, 한컴 SaveAs도
그 크기를 바꾸지 않았다. 이를 정상 한컴 생성본이나 새 회귀의 근거로 사용하지 않는다.
정상 한컴 편집 API의 EquationCreate로 새 HWP를 만들고, 저장 속성과 독립 Print를 확인한다.

## 실행 순서

1. Windows 검증 호스트의 기존 HWP 프로세스와 작업 경로를 확인한다. 비어 있는 자기 COM
   문서에서 두 수식 face·두 크기·콜론 문맥 대조군을 생성한다. 기존 사용자 문서는 수정하지 않는다.
2. 실제 EquationCreate 요청·결과, 정상 저장 HWP의 개체 수·글꼴·크기·LineSeg를 기록한다.
   원격 임시 경로는 파일을 회수한 뒤 자기 프로세스 종료와 용도를 확인하고 삭제한다.
3. 해당 저장 제품에 맞는 MCP engine으로 PDF를 Print 출력한다. 실제 제품·Print mode·입력/PDF
   SHA와 전체 쪽수를 보존한다. 원본 시험지의 Print를 대조군 결과로 바꾸어 보고하지 않는다.
4. 기준 제품의 Native/fresh WASM 전쪽 TSV를 산출하고 콜론의 단독·이항·첨자 뒤·괄호 뒤
   전진과 자동 간격을 독립 Print에서 측정한다. 차이가 남으면 원래 시험지의 같은 영역과 함께 분석한다.
5. 첨자 대조군과 WASM의 언어·과학·자간 대조군 하락도 같은 base/head/Print로 직접 확인한다.
   여러 하락의 원인을 분석한 뒤 일반 규칙으로 묶어 수정하고, 같은 source를 한 번씩 빌드한다.

생산된 진단 자료는 우선 ignored output 또는 진단 PDF 경로에만 둔다. 전쪽 양쪽 90% 및
직접 판독 전에는 정식 fixture·golden을 추가하지 않는다. 기존 기대값이나 허용치를 완화하지 않는다.

## 정상 생성본에서 확인한 콜론 계약과 구현

1826단계 Windows의 정상 EquationCreate 64개를 HWP로 저장했다. 실제 제품은
Hancom 11.0.0.9136이며 1828단계에서 같은 2020 engine의 Print method 0으로
8쪽 PDF를 출력했다. 수동 캐시를 남긴 이전 진단은 근거에서 제외했다.
새 저장본의 콜론은 실제 PDF에서 두 face 모두 U+E04F로 확인됐다.

설치 HYHWPEQ.TTF의 UPM 1024에서 E04F 전진은 283이다. Windows GDI에서도
HancomEQN·HyhwpEQ 각각 논리 크기 2..128의 짝수 64개 전체에서 E04F와 E052의
전진이 같다. glyph 모양·baseline과 수학 쉼표의 별도 간격은 공유하지 않는다.
정상 HY 저장본 `a:b`의 폭은 900HU에서 1428HU, 1200HU에서 1929HU다.
각각 두 피연산자·콜론의 논리 전진과 양쪽 0.21em 간격으로 설명된다.
첨자 뒤에는 기존 관계 기호의 0.3em 경계를 적용하며, 문맥 없는 단독·끝·연속 콜론은
기존 행 경계 규칙에 따라 불필요한 자동 간격을 예약하지 않는다.

생산 경로는 원본 colon Symbol → Hancom glyph run의 실제 E04F·논리 전진 →
공통 row_children의 앞뒤 문맥 간격 → Native·Canvas·SVG가 소비하는 같은 layout이다.
일반 수학 face의 문자 출력은 기존 경로를 사용한다. 문서·좌표별 분기는 넣지 않는다.

한컴 2020은 두 요청 face에 같은 개체 캐시 폭을 저장했으나 실제 Print face는 각각
HancomEQN·HyhwpEQ다. 이 캐시만으로 두 face의 영문자 자연 폭까지 같다고 가정하지 않는다.
새 회귀의 기대값은 확인한 실제 glyph·HY 전진·문맥 간격과 독립 Print에서 정한다.
수정 뒤 같은 source를 Native/fresh WASM으로 고정해 새 8쪽·원본 수학 전체23쪽과
기존 정상 operator 대조군을 비교하고 확대 판독한다. 현재는 구현·검증 진행 중이다.

### HY 수학 쉼표의 동일한 원인

원본 수학 8쪽의 `rm A( sqrt {5} ,~0,~0)`는 쉼표 두 개를 일반 Symbol로 남겨
뒤의 0이 독립 Print보다 약 2.37 CSS px 오른쪽에 있었다. 실제 Print의 쉼표는
HyhwpEQ U+E052다. 정상 저장 구조 대조군의 `sum _{i=1}^{n} y _{i,G}`도
두 face·600/900/1200/1800HU에서 같은 glyph와 뒤 0.07em 간격을 출력한다.
전진과 뒤 간격은 fontsize에 비례하며 작은 첨자에도 같은 논리 격자를 소비한다.

현재 공통 glyph 측정은 HancomEQN에서만 쉼표를 허용한다. HY의 쉼표도 원본 face의
glyph·전진을 전달하고 확인한 뒤 간격을 함께 예약한다. HancomEQN의 기존 별도 왼쪽
문맥 간격과 일반 수학 face는 변경하지 않는다. 콜론과 쉼표의 실제 baseline 이동도
기존 공통 glyph 결과에서 소비한다. 그리스 기호의 별도 공공 대체 glyph 경로는 이번
수정에 포함하지 않았으며, 설치 face와의 차이를 별도 분석 자료에 남겼다.

1837 Native·1838 fresh WASM은 콜론만 반영한 중간 생산자다. WASM 중단을 검토한
시점에 이미 exit0으로 완료되어 실제 중단은 없었다. 이 생산자로 쉼표 보정까지
검증했다고 보고하지 않는다. 쉼표와 포맷까지 고정한 source를 다시 순차 빌드한다.

## 현재 구현의 검증과 남은 차이

1848단계 Native와 1849단계 fresh WASM은 콜론·쉼표 보정 및 포맷을 포함한 같은
제품 source hash를 사용했다. 양쪽 빌드는 exit 0이고 빌드 전후 source 변경이 없다.
공용 `target/pr-review`에서 Native → WASM 순서로 빌드 잡 8개를 사용했다.
중간 1837/1838 생산자는 콜론만 포함하므로 최종 쉼표 검증으로 재인용하지 않는다.

1850단계 Native는 27개 문서·204쪽 전쪽 측정을 마쳤다. 최저값은 90.83624%이며
90% 미만·누락 쪽과 독립 PDF의 쪽수 차이는 없다. 1851단계 fresh WASM의 같은
27개 문서 대기열은 실행 중이다. 아래 핵심 4개 입력의 전쪽 측정은 양쪽 모두 끝났다.
이 표를 전체 74개 문서·전체 Rust gate 완료로 확대하지 않는다.

| 입력 | 쪽수 | Native 최저 | fresh WASM 최저 |
| --- | ---: | ---: | ---: |
| 이번 EquationCreate 콜론 진단 | 8 | 98.07932% | 98.14792% |
| 원본 `3-09월_교육_통합_2022.hwp` | 23 | 90.83624% | 91.14385% |
| 기존 정상 저장 수식 구조 대조군 | 16 | 98.89532% | 99.24621% |
| 기존 연산자·첨자 저장 대조군 | 8 | 99.11894% | 99.10760% |

원본 수학 8쪽의 Native는 수정 전 98.08528%에서 98.46641%, fresh WASM은
98.08769%에서 98.46582%로 개선됐다. 다만 고정 devel의 같은 쪽은 각각
98.71823%·98.51684%여서 0.01%p 하락 재검토 조건은 아직 해소되지 않았다.
평균 개선이나 98% 통과로 이를 면제하지 않는다.

기존 인라인 개체·캡션·문단 외곽·수식 크기 보호·연산자·수식 구조 회귀는
1864단계에서 **36 PASS / 0 FAIL**이다. 새 회귀 36개를 만든 것이 아니다.
동일 원본 8쪽에서 두 콜론과 좌표식의 두 쉼표를 확인한 1867단계 진단은
같은 진단 source로 수정 전 **0 PASS / 3 FAIL**, 수정 후 **3 PASS / 0 FAIL**이다.
양쪽 모두 컴파일은 성공했다. 진단은 정식 회귀 추가나 전체 Rust gate를 대신하지 않는다.
수정한 네 Rust 파일의 `rustfmt --check`와 `git diff --check`도 통과했다.

### 보존 입력과 직접 판독

[한컴 생성 HWP](../../pdf/issue7642-colon-authored-20261016/colon-authored.hwp)와

같은 경로에 보존한다. HWP는 26,112바이트이며 SHA-256은
`0d40330e345bc9f69f614d04f3d6c199c0173969817d95c37ea69cef43ffb965`다.
PDF SHA-256은 `16754e31b377e4ca7c19a1167d2aaf8d6b2d780761466a28a56638440873a668`다.
이 자료는 생성·Print 동작과 현재의 남은 차이를 재현하는 진단 증거다.
자동 수집 corpus·정식 회귀 fixture·golden에는 등록하지 않았다.

7쪽 HY 수식의 콜론·아래/위첨자·뒤 항을 같은 배율로 대조했고, 7쪽은 양쪽
100%다. 단독·앞뒤 문맥의 콜론도 같은 glyph 원점을 사용한다. 다음 확대 그림과 실제
standalone overlay를 함께 확인했다. 실루엣 100%를 픽셀·수식 전체의 완전 동일로 쓰지 않는다.

진단의 HancomEQN 3쪽 복합식은 점수가 98% 이상이어도 일부 영문·항 간격 차이가 보인다.
EquationCreate는 두 요청 face에 같은 캐시 폭을 저장했으나 실제 Print face는 다르다.
2020에서 요청한 새 face의 편집·메트릭 계약이 무엇인지 아직 확정하지 않았다.
저장 폭으로 생성 세대를 추측하는 분기나 골든 갱신을 넣지 않고, 새 관계형 회귀 초안도
ignored output에만 두었다. 이 진단을 한컴 2020의 HancomEQN 전체 호환 완료로 보고하지 않는다.

원본 8쪽 분홍 상자에는 수식과 별개의 실제 차이가 있다. HWP 원본의 선 속성 하위
6비트는 `10`, 폭은 425 HU다. HWPX의 대응 속성도 `THICK_SLIM`이다. Print는
굵은 외곽선·빈 간격·가는 안쪽 선을 출력하지만 `drawing_to_shape_style`에서 복합 선
종류가 유실되어 현재는 폭 5.6667 CSS px인 단선이다. 1858/1866단계에 독립 PDF의
경계와 원본 속성을 기록했다. 일반적인 복합 사각형 테두리의 공통 결과를 마련한 뒤
이 쪽을 다시 판독해야 한다. 이 결함을 점수 통과로 면제하지 않는다.
