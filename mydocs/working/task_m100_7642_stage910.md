# 단계 910 Canvas 공급 이름과 실제 program의 일치

Issue: #7642. renderer 후보 1caab356fe1f72755a716fb316b6e66eab687191.

## 실제 검출과 수정

Native #5821은 Print와 대응한 원 face로 아래 문장 굵기를 표시했지만 WASM은 얇은 폴백을 계속 썼다. catalogue의 source SHA와 load 성공만으로 실제 사용을 판정하지 않았다. 같은 원본 program의 advance를 독립 측정하여 요청 family에서 19.621948px, 별도 원 이름 등록에서 21.328125px를 관측했다. FontFace 생성에 JSON 문자열의 따옴표를 포함한 이름을 넘긴 것이 공급 이름과 Canvas의 요청 이름을 갈라놓았다.

`registerCanvasFont`는 원본 family 문자열과 program bytes를 FontFace에 전달한다. Canvas 요청 family, weight와 style을 보존하며 글리프·배치·좌표를 바꾸지 않는다. 실제 공급은 서버가 같은 해시의 바이트만 반환한 뒤 이 함수를 호출한다. 별도 허용 목록 밖의 파일 요청과 변경한 program은 기존 계약대로 실패한다.

## 독립 검사와 결과

- 자체 fixture `RHWPHostFixture-Regular.ttf`의 A는 hmtx advance 900 / unitsPerEm 1000이다. 브라우저 검사는 실제 그리기의 자연 advance/font_size 비율을 원본 0.9와 대조한다. 화면 위치를 px로 고정하지 않는다. 이름·공백·한국어 별칭을 포함한다.
- 올바른 원본 기대값을 사용한 단계 902 수정 전 검사는 0.607999420으로 실패했고, 원 이름을 전달한 단계 904/908은 통과했다. 최초 단계 901의 임시 기대값 오류와 단계 903의 잘못된 CSS escape 시도는 결함 검출 근거로 사용하지 않는다.
- CI가 이미 실행하는 PNG server 검사에는 이름·원본 bytes·weight/style 보존을 포함했다. 직접 브라우저 검사와 server 검사 합계 6건을 실행해 6건 모두 통과했으며 skip은 없었다.
- 단계 909의 #5821 전체 1쪽은 Native 99.98879%, fresh WASM 100.00000%다. 새 대표 review에서 제목·본문·아래 문장의 face·굵기·간격을 Print와 직접 대조했다. 기존 sqrt 장평 크기 검사를 교정할 선행 근거로 연결한다.

WASM은 1caab356f의 fresh dev snapshot이며 최종 동일 release 전쪽 비교를 대체하지 않는다. helper 수정 후의 비교 helper SHA는 실행 manifest에 남는다. Linux와 Windows 원 face의 버전 차이는 ignored 진단 경로에서 공급했고 font 바이너리는 커밋하지 않았다.

68쪽 캡션 보정의 Native 진단은 99.69631%로 개선됐다. 새 WASM과 122쪽 전체 검증, 목차 3쪽 보정, 55문서 전쪽의 최신 base 비교와 전체 Rust/lint 검증은 아직 완료되지 않았다. 현재 gate 상태에서 PR은 만들지 않는다.
