# 이슈 #8532 — 앞 조각의 표 아래 외곽 높이 대조

2026-11-05 KST. PR #8547을 포함한 기존 39개 PR 통합 검토 범위다. 새 PR을 접수하거나
새 이슈를 등록하지 않았다. 아래 원인 분석 뒤 공통 물리 프레임 소비 경로를 보정 중이다.
기존 회귀의 내용·쪽수 기대값은 바꾸지 않았다.

## 독립 관측과 원 해결 PR

[원 PR #8547](https://github.com/edwardkim/rhwp/pull/8547)의 원 head는
`802078a02454a66ef3dc917d6ba2c6461709dcd5`, 제품 커밋은
`38ed5b5c4a4fc8e1a11dbdad2071c71302c7f531`이다. 현재 적용 제품 커밋은
`a6f332bf20a5baaaae5e2b430bd7a5414f7ddafb`다. 원 PR 전체 본문·diff를 다시 읽었다.
원 작성자는 3쪽의 남은 차이가 표 아래 경계임을 이미 공개했다. 현재 통합에서 새로
발생한 차이라고 단정하지 않는다. 4~6쪽이 뒤로 밀리는 문제를 해결한 범위와 구분한다.

같은 HWP·독립 한컴 Print의 기존 Native/fresh WASM 3·4쪽 review와 overlay를 직접
대조했다. 3쪽 위생 앞 조각과 4쪽 이어받는 내용의 소유·순서는 맞지만 3쪽 마지막 행의
아래 외곽은 다르다. 기존 96 DPI 원본 PNG의 마지막 두 긴 가로선은 Native y=996/1013,
Print y=996/1025다. 아래 선만 12 CSSpx 차이가 난다. 이 값은 진단 관측이며 98% 미만인
3쪽에 새 절대 px 회귀를 추가한 것이 아니다.

[원본 레코드·페이지 항목·PNG 관측](../pr/assets/planet6897_20261103/intermediate-evidence-summary.md)을
같이 보존한다. 입력 SHA는 `797268d10fc7605ae5e0e299e9fb386ea6c204f35ef4c4879bb611e66ef4545a`다.
원본 CFB를 직접 해제해 읽었으며 엔진의 HWPX 재저장본을 근거로 사용하지 않았다.

## 원본 저장값과 현재 소비 경로

원본의 0기준 38행은 col 0이 rowspan 2·높이 6126HU, 나머지 네 칸은 rowspan 1·높이
3063HU다. col 3/4는 위생사·영양사 두 문단의 저장 vpos가 모두 0이며, 각 줄 높이는
1000HU·줄간격 500HU다. col 1은 위생 한 줄·간격 400HU다. 패딩 원값은 네 방향
141HU이고, 개별 여백 지정 여부와 표 기본 패딩의 적용을 구분해야 한다.

최신 제품의 `dump-pages --json --compat 2022 -p 2`는 실제 3쪽을 반환했다. partialTable은
startRow=21, endRow=39, startCut=[1,1,1,1], endCut=[1,1,1,1,1,0,0,0,0]다.
페이지 usedHeight는 920.5733333333335px, 본문 높이는 933.5333333333334px다.
기존 캡처 render tree에서 38행의 다섯 Cell은 y=998.0·height=17.1px로 기록돼 있다.

생산·소비 연결은 다음 순서로 계속 대조한다.

1. `BlockCutQuery::allows_split`의 저장 되감김 수용: 내용 컷을 받는 조건이다. 물리 밴드의
   최종 높이를 이 조건 하나에서 정하지 않는다.
2. `RowBlockQuery::row_cut_base_height` → `row_block_cut_physical_height` 또는
   `row_block_cut_row_content_height` → `fragment_extent`의 요구·예약 높이.
3. `layout/table_partial.rs`의 끝 행 override·행별 높이와 최종 셀/외곽 배치. 같은 helper
   호출 뒤 다른 분기가 값을 덮어쓰는지도 추적해야 한다.
4. 4쪽의 이어받는 내용·기존 100% 출력 보존. 앞 조각의 비어 있는 물리 밴드를 내용 소비로
   차감하면 다음 조각이 줄거나 소유가 달라질 수 있으므로 확인 없이 보정하지 않는다.

원본 높이 3063HU를 그대로 강제하거나 남은 본문 높이까지 무조건 늘리는 방식은 아직
독립 계약으로 입증되지 않았다. 실제 물리 프레임 규칙과 정상 대조군을 확인한 뒤 공통
생산 결과로 수정하고, 측정·예약·배치가 같은 결과를 소비하도록 해야 한다. 점수 통과나
작성자가 남은 차이를 공개했다는 사실만으로 해결 완료를 선언하지 않는다.

## 공통 소비 경로 보정과 검증 계획

`RHWP_DIAG_SCAN=1`의 실제 실행은 원본에서 인증한 다음 조각의 하단 932.2px가
`fragment/budget.rs`에 도달하지만 `stored_body_closing_fragment_extent`가 블록 컷을
일괄 제외하는 것을 확인했다. 그 결과 3쪽은 내용 높이 868.2px와 반복 머리행
52.373333px만 점유하고, 원본 물리 하단까지의 빈 띠는 최종 행에 전달되지 않는다.

일반 행의 기존 종료 프레임 계산을 유지하면서, 블록 소유 순서의 컷을 별도로 인증한다.
실제 수용 범위 뒤의 행은 미소비 컷 0을 유지하고, 완료한 칸은 내용 종료로, 미완료 칸은
공통 `cell_units`가 인증한 `page_frame_reset_before`로 확인한다. 원본 일반 글줄·유효한
저장 프레임에만 적용하며 재조판·개체 문단에는 적용하지 않는다. 원본 프레임 하단과
이미 수용한 앞 행 상자로 마지막 행 높이를 함께 계산해 기존 PageItem의 높이와 paint가
소비하게 한다. 새 문서 식별자나 출력 차이 12px를 분기·상수로 넣지 않는다.

먼저 같은 Native 출력에서 전 6쪽 TSV, 3쪽 외곽과 4~6쪽의 내용·줄 소속 보존을 확인한다.
이후 fresh WASM의 같은 범위와 기존 정상 병합 경계 대조군을 실행한다. 새 관계형 회귀는
이 검증이 완료된 뒤에 등록하며, 현재 진행 중인 과거 base의 WASM 대조는 중복 실행하지 않는다.
결과가 없으므로 아직 보정 성공·최종 승인으로 판정하지 않는다.

### 첫 보정 후보의 실행 결과와 추가 인증 경로

첫 Native 후보는 `release-test` 빌드를 완료했다. 실행 래퍼가 컴파일 완료 뒤 종료 기록을
남기지 않아 같은 소스의 캐시 빌드를 다시 실행하고 exit 0을 확인했다. 제품 해시와 소스
파일 해시는 `output/pr-review/planet6897-20261103/logs/8532-closing-frame-product.json`에
기록했다. 그 후보의 실제 `dump-pages`는 3쪽 높이 920.573333px가 그대로임을 확인했다.
따라서 첫 후보를 시각 개선 성공으로 판정하지 않는다.

원본 본문 닫힘을 예산에서 이미 인증했어도 일반 행 경로가 요구하는 별도 inset 전달이
없으면 방출에서 일괄 제외된다. 병합 블록에는 원본 호스트·선언 상자를 대조하는 기존
`original_body_closed_table_frame` 인증도 허용하되, 위의 컷별 일반 글줄 인증과 실제
수용 높이·예산 검사는 유지하는 두 번째 후보를 빌드 중이다. 디버그 출력은 인증 여부와
입력 inset·종료선을 구분한다. 이 후보도 아직 실제 출력·WASM 검증을 완료하지 않았다.

### 두 번째 후보의 실행 결과와 공통 결과 전달

두 번째 Native 빌드도 exit 0이다. 실제 진단은 3쪽에 `inset=None`, 원본 호스트의
본문 닫힘 인증 `source=true`, 방출에 전달된 `bottom=None`을 함께 기록했다. 예산의
`accepted_frame_bottom=932.2`는 내용 스캔의 상한으로 사용됐지만 `FragmentBudget`의
`source_frame_bottom`에는 일반 글줄 프레임 경로의 이전 값 None만 들어갔다. 따라서
두 번째 후보도 같은 920.573333px를 내며 개선되지 않았다.

세 번째 후보는 `FragmentBudget`에 실제 수용한 `accepted_frame_bottom`을 먼저 싣고,
없을 때만 기존 `source_frame_bottom`을 보존한다. 방출은 원본 호스트 인증을 따로
다시 계산하지 않고 이 공통 결과를 소비한다. 끝 컷의 인증도 원본 일반 글줄과 실제
유닛 재시작을 확인하며, 일반 행 전용 전체 표 프레임 분류를 병합 블록에 강제하지 않는다.
내용 컷·미수용 뒤 행의 컷 0과 기존 이어받기 소유는 그대로 보존한다.

세 번째 후보의 빌드·실제 출력은 현재 진행 중이다. 앞의 두 후보는 성공한 보정으로
합산하지 않는다. 전쪽 Native/fresh WASM, 정상 대조군과 필수 회귀 검증 전에는 PR을
제출하거나 승인하지 않는다.

## 세 번째 후보의 실제 전쪽 검증

제품 커밋 `e61ed1ca7329d3dacffc9c7fc76e602f30f43f66`의 Native 빌드와 최적화한 fresh
WASM 빌드가 모두 exit 0으로 종료됐다. 실제 소스 파일 해시와 제품 해시를 연결했다.
독립 Print PDF를 재출력하지 않고 같은 6쪽으로 비교했다. Native 최저 99.85%, WASM
최저 99.87%이며 3쪽은 각각 97.95%·97.98%에서 100.00%로 올랐다. 나머지 쪽의
표시값은 유지됐다. 양쪽 3·4쪽 review와 별도 overlay를 직접 읽어 아래 외곽과 다음
조각 영양사·뒤 행의 보존을 확인했다. 원본 내용 컷·쪽수는 동일하고 점유 높이만
932.2px로 바뀌었다. 이 값은 실제 실행 관측이며 새 절대 좌표 기대값이 아니다.
