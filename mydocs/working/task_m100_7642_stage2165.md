# #7642 fresh WASM의 WMF 글꼴 공급 상한 오류 보정

## 실행으로 확인한 실패

source `84fa650793`의 stage2151 fresh WASM 자체는 exit 0으로 빌드됐다.
그러나 stage2154의 정상 WMF 64쪽 입력 세 항목은 캡처 도중 메타파일 글꼴의
64MiB 총 바이트 상한을 초과했다. 이를 성공·90% 미달 페이지로 분류하지 않고
`measurement_failed`로 남겼다. Native의 동일 입력 전쪽 최저 95.03221%를
WASM 결과로 복사하지 않는다.

Sweep은 Canvas에 필요한 family를 공급할 때 catalog의 모든 굵기·스타일을
등록한다. 이를 WMF 세션에도 그대로 복제해, 실제 요청이 400·700뿐인데
Noto CJK의 Black·Light 등을 함께 공급했다. 상한을 늘리는 대신 같은 catalog에서
WMF가 요청한 style·weight에 맞는 face만 paint 세션에 전달한다. Canvas에 대한
기존 전체 공급은 보존한다. 별칭·fallback 사다리와 실제 SFNT 바이트도 유지한다.

## 독립 선택 계약과 검사

`fontdb 0.23`의 실제 `find_best_match`를 확인하고 style 우선순위, 400↔500,
가는 쪽/굵은 쪽 탐색 순서와 가장 먼저 등록된 동률 후보를 따른다. 문서·글꼴별
예외를 만들지 않는다. 요청 400·700에서 미사용 일곱 굵기를 제외하는 경계,
없는 style의 대체, 별칭·없는 family를 새 Node 검사 네 개로 검증했다.

기존 실제 브라우저 검사는 FontFace 적재가 끝난 같은 바이트를 별도 WMF 세션에
전달하고 선택하지 않은 900 face는 복제하지 않는 assertion을 보완했다.
stage2165의 Node/브라우저 검사 총 일곱 개가 PASS(exit 0)다. 실제 Canvas의
advance·glyph 계약과 Chrome 시작 실패 뒤 프로필 정리도 포함한다.

## 정상 문서의 실제 진단 캡처

stage2166은 고정 84fa650793 package에 이 선택 로직의 별도 draft를 공급했다.
정상 저장본 HWPX 35쪽의 캡처가 성공했고 같은 독립 PDF·Cairo 정책의 raw
실루엣은 98.52195%다. 새 review·standalone overlay를 함께 열었다.
그림의 큰 배경 차이는 줄었으나 본문 굵기·괘선과 그림 내부 미세 차이가 남는다.
이는 한 페이지 진단이며 전쪽 통과, 이번 종횡비 보정의 검증, 완료 페이지나
px 핀 추가 판정이 아니다.

이전 queue는 stage2167에서 실제 캡처 자식이 없는 경계에 종료했다.
Native 61개 완료 항목과 WASM 7개 완료 항목 및 미완료 항목의 증거를 보존하고,
`interrupted_for_verified_correction`으로 구분했다. 출력 공백·관찰 timeout을
실패로 추정해 재시작한 것이 아니다. 종횡비 보정과 새 글꼴 선택을 적용한
전체 재검증으로 이어간다. TSV·로그·JSON은 Git에 포함하지 않는다.

## Rust 선행 gate

stage2164는 종횡비 보정을 포함한 `6b363c39ed02403c3e787b13af7bdf4e98968f67`의
Rust source·tests/cases 해시를 고정했다. prepare, format, Native Clippy,
WASM32 Clippy, workspace build, workspace all-target Clippy, 최신 base를 명시한
manifest·source unit-tier 검사 여덟 단계가 모두 exit 0으로 끝났다.
이번 JS 공급 선택은 Rust 파일을 바꾸지 않았다. stage2168 Native와 이어지는
stage2169 fresh WASM은 그 동일한 Rust source에서 실제로 다시 빌드한다.
전체 Rust 회귀·새 시각 증적은 이 lint 묶음과 별개로 아직 미완료다.

## 실제 Studio 글꼴 세션의 실행 경계

stage2177은 Vite로 실제 `MetafileFontSession`·host provider를 묶고 브라우저에서
고정 84fa650793 WASM과 정상 HWPX를 연결했다. 설치된 실제 GulimChe 프로그램
한 개와 두 별칭을 공급한 뒤 35쪽의 3898×2853 PNG를 확인했다. 같은 준비
세대의 재호출에서 host read 횟수가 두 번 그대로였고, bytes를 기다리는 중
문서를 교체하면 이전 소유자에게 등록하지 않았다. provider 해제도 확인했다.

`OutputDevice`는 원본 WMF key로 재조회하지 않고 PNG bytes를 직접 싣는 기존
공통 JSON 계약이다. 처음 관측 코드가 모든 PNG에 source key가 있다고 가정한
stage2175 실패는 제품 결함으로 분류하지 않는다. 실제 `paint/json.rs` 계약을
읽어 원본 key와 직접 전달을 구분한 검사로 수정하고 통과했다. 그 앞 stage2174의
esbuild 미설치 실패도 렌더링 실행으로 세지 않는다. 별도 설치 없이 현재 Vite를
사용했다. 원본 font bytes를 저장소나 문서에 추가하지 않았다.

이 결과는 새 클래스의 실제 host·WASM 연결과 비동기 소유권 경계 증거다.
전체 Studio 화면·CanvasKit·종횡비 보정 후 package의 완료 증거를 대신하지 않는다.
