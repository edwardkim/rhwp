# Issue #7642 단계 823: 캡션이 있는 공동 앵커의 실행 경로 확인

## 검증 기준과 관측

코드 후보는 `35ccddcff4f9f40d1c0ca7712bae3c2dc7b8bcda`, 비교 base는 `a5e88ad682c805e1d845502ddc9521b94ea8eccd`다. 단계 812에서 Native 빌드와 합성 그라데이션 검사 1건을 통과했다. 단계 813의 fresh WASM 빌드는 exit 0, 소스 해시 불변, 루트 pkg와 Studio public의 JS·WASM SHA-256 일치로 완료됐다. 단계 819·820에서 같은 입력과 Print PDF의 Native·WASM 전쪽 검증을 시작했다. 기존 801·802의 후보는 `099ae279f`이므로 최신 후보의 완료 증거로 바꾸어 보고하지 않는다.

HWPML 37쪽은 Native 70.71239%, 38쪽은 48.94542%다. 같은 원본 문단 2.238은 하나의 저장 줄에서 TAC 표와 양수 오프셋 부동 표를 소유한다. 부동 표의 아래 캡션도 원본에 존재한다. 독립 Print PDF의 해당 표 상단은 약 649.85px이며, 기존 Native의 표 상단은 본문 원점 103.56px와 조각 원점 669.40px의 합이다. 이 좌표는 원인 진단용이며 회귀 기대값으로 추가하지 않는다.

## 생산 값에서 최종 배치까지

`controls/paragraph_flow.rs`가 포맷·사전 수용 뒤 문단 시작을 한 번 캡처하고 `controls/flow_table.rs`를 통해 표 배치에 전달한다. 실제 GDB 관측에서 문단 시작은 두 표 모두 417.733333px였으며, 앞 TAC 표를 배치한 뒤 현재 흐름만 540.160000px로 전진했다. `strict_following_plain_text_fit`은 false였다. 따라서 `prepare_flow_table_anchor`의 strict 경로가 이 입력의 앵커를 덮어쓴다는 초기 추정은 적용되지 않는다.

`table/continuation/fragment/coanchored_origin.rs`의 실제 조회는 첫 조각, 동일 물리 frame, 원본 저장 줄, 이미 배치한 같은 줄의 TAC 형제를 확인한다. 그러나 모든 캡션을 거절하는 조건에서 원점을 반환하지 않았다. GDB로 이 반환 위치와 아래 캡션을 확인했다. 이후 `fragment/budget.rs`의 되감김 표 폴백이 현재 흐름에 문단 오프셋을 더해 669.40px를 선택했고, 컷은 12행에서 끝났다. 이 컷과 원점이 emit·partial paint로 전달되어 다음 쪽의 행 시작도 달라졌다.

아래 캡션은 줄 앞의 원점이 아니라 마지막 조각의 종료 공간이다. 기존 budget·emit이 `caption_overhead`와 마지막 아래 캡션을 계상하므로 공동 앵커 조회에서 아래 캡션만 허용한다. 위·옆 캡션, 이어받기, 다른 물리 frame, 다른 줄의 형제, 편집·재조판 경로는 기존 인증 범위를 유지한다. 문서 ID나 관측 좌표로 분기하지 않는다.

## 검증과 남은 범위

진단 로그는 ignored `output/pr-review/issue7642/failed-inputs-20261008/stage15-current-validation/`의 단계 817·818·821에 보존한다. 수정 후보의 빌드, 영향 쪽 Print 대조, Native·fresh WASM 전쪽 확인과 일반 공동 앵커 대조군 검증이 필요하다. HWPML 3·57·68쪽의 글꼴·표 원점 차이와 그림 마커의 확대 판독 차이도 아직 해결 완료가 아니다. 해당 원본 전쪽이 90% 이상이 되기 전 새 실물 회귀·golden을 추가하지 않는다.
