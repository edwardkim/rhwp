# #7642 WMF의 공통 장치 합성 진단

## 실제 원본과 독립 출력

stage2124는 고정 Native `rhwp-stage2102-palette-delimiter-current`로
`samples/hwp3-sample16-hwp5.hwpx` 35쪽을 Print·2024로 실제 SVG 출력했다.
producer source는 `aae3ea1b26006f2b7dc4b0ead2f8a65640fff9aa`다.
그림의 변환 SVG SHA-256은
`8fcdb24e0e43ce1249beab8de1eab890f241a28446186ed3e601c926e9bd47f4`다.
비교 원본은 `pdf/issue7642-sample16-print-refresh-20261012/`의
`hwp3-sample16-hwp5-hwpx-2024.pdf` 35쪽, image xref 464, 4561×2853이다.

단독 WMF의 합성을 보기 위해 librsvg 2.58.0으로 같은 자원 치수에 렌더했다.
원래 SVG와 도형 crispEdges·문자 optimizeSpeed 진단을 각각 실행했다.
이것은 제품 Native/WASM 재생이나 96DPI 전쪽 Visual Sweep이 아니다.
기존 gate·DPI·판정 정책을 바꾸지 않으며 이 진단을 완료 점수로 쓰지 않는다.

## 확인한 범위

- 전체 합성 RGB는 원래 SVG에서 230,792색, crispEdges 진단에서도 215,456색이다.
  원본의 도형 fill 목록이나 개별 DIB 팔레트 수만으로 최종 팔레트를 정할 수 없다.
- 같은 자원 치수의 독립 PDF와 RGB 평균 성분 오차는 기본 합성 13.3627,
  bitmap 전달식을 합성 뒤 적용한 진단 12.7582다. crispEdges는 각각 13.4098,
  12.8184다. 개선 일부는 있으나 큰 잔여 차이가 있어 단순 전역 색 보정의 완료
  근거가 아니다. 정확한 RGB 비율도 약 57%이며 페이지 실루엣 점수와 구분한다.
- 원본 WMF의 445개 text가 요구하는 서로 다른 문자 122개는 실제 설치된
  GulimChe Regular에 모두 있다. bold 요청도 같은 실제 파일로 해석된다.
  파일·SHA·cmap 대조는 ignored font-coverage.json에 있다. glyph 존재는 bold 재생,
  문자 원점·간격 또는 Native/브라우저의 실제 face 선택을 입증하지 않는다.
- 작성한 cardinality WMF 대조 입력의 8개 WMF는 같은 Native SVG export에서
  변환 SVG 대신 `image/x-wmf` payload로 나갔다. 독립 한컴 Print의 관측값과
  RHWP 재생 성공을 분리한다. 왜 변환되지 않았는지는 별도 실패 원인을 확인해야
  하며 이 입력을 완료 회귀나 팔레트 분기의 제품 증거로 쓰지 않는다.

## 실제 소비 경로와 다음 검증

현재 `paint::metafile::image_payload`는 Print 장치 원점을 EMF에만 전달하고,
WMF는 image_resolver → SVGPlayer 변환 → 각 backend의 SVG 그림 재생으로 간다.
bitmap palette 보정은 별도의 BMP/PNG 경로다. WMF의 전체 합성·팔레트·문자
선택은 그 경로에 연결되어 있지 않다. helper 이름이나 RGB 진단만으로 공통
출력이 구현됐다고 판정하지 않는다.

공통 WMF 장치 출력을 만들려면 crop·fill·변환을 포함한 전체 자원 크기, clip·
덮어쓰기 이후의 실제 색, DIB 보간과 벡터·문자 재생, 사용한 실제 font bytes를
한 결과에 반영해야 한다. 출력 장치·글꼴 세대가 다른 결과를 원본 이미지 키로
재조회하는 캐시와 혼합해서도 안 된다. 브라우저 canvas의 글꼴 등록만으로 SVG
이미지 내부 글꼴까지 공급됐다고 추정하지 않는다.

ignored stage2124·stage2126에 실제 명령·자원·source hash·RGB 진단 receipt를
보존했다. 기존 35쪽의 미달은 해소되지 않았고, 새 제품 구현이나 시각 통과,
회귀 등록 완료를 주장하지 않는다. 두 palette bitmap 입력의 새 정식 검사는
[stage2122](task_m100_7642_stage2122.md)의 별도 검증 범위다.

## 작성 입력의 잘못된 객체 선택 분리와 대조군 재산출

stage2135는 실제 새로 빌드한 library의 공개 WMFConverter를 직접 호출했다.
기존 cardinality 입력 8개 모두 `UnexpectedGraphicsObject: Graphics Object is null`
오류였다. 작성 helper는 pen을 만들기 전에 `META_SELECTOBJECT 0x8008`을 발행했다.
[MS-WMF의 ObjectIndex 계약](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wmf/59b4b6f3-40db-4685-8eda-3be3e4196fb2)은
메타파일이 정의한 객체 테이블을 가리킨다. EMF의 stock object 가정을 이 입력의
WMF 수용 근거로 쓰지 않는다. 이 실패 때문에 실제 정상 WMF의 조건을 완화하지 않는다.

stage2136은 별도 입력에서 `META_CREATEPENINDIRECT(PS_NULL)`을 명시적으로
만들고 object 0으로 선택했다. brush는 object 1로 분리했으며 header의 객체 수와
기록 크기도 함께 갱신했다. 원래 입력·PDF는 그대로 보존했다. 별도 입력 8개 모두
실제 converter의 SVG 생성이 성공했다. 이것도 한컴 저장본이 아닌 작성한 진단이다.

stage2137은 그 **새 입력 자체**를 MCP `target=pdf`, `engine=2024`, PrintMethod 0으로
출력했다. job `0c6a279c-bf34-44a5-9052-8514f75dfe65`, 실제 제품 13.0.0.3901,
출력 모드 `frame_print_to_pdf_ex_one_up`을 확인했다. 독립 PDF는 1쪽이다.

stage2139에서 같은 고정 producer·공식 Cairo 96DPI로 전체 1쪽을 실제 출력했다.
Native raw 98.89893%, fresh WASM raw 98.84372%, 양쪽/PDF 쪽수 1이다.
stage2140의 양쪽 review·standalone overlay를 직접 판독했다. 그림 수와 배치는
보존되지만 벡터 격자의 선명도와 계조 차이가 남아 있다. **98% 이상이어도 이
알려진 차이를 정상 golden이나 좌표 핀으로 고정하지 않는다.** 새 두 파일은
독립 근거를 보존하는 진단 자료이며 제품의 WMF 완료 fixture로 등록하지 않는다.

[Win32 Rectangle의 독립 계약](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-rectangle)에
PS_NULL pen의 사각형 폭·높이가 각각 1 device pixel 작다는 규칙이 있다. 화면 px
상수를 임의로 빼는 것과 구분해 실제 600DPI 장치·변환을 확인해야 한다. 그러나
미달 정상 원본 35쪽의 SVG에는 그 조건을 직접 충족하는 사각형이 없으므로 이
대조군의 규칙 하나로 기존 미달 원인이 해결됐다고 주장하지 않는다.

실행한 ignored 사본과 커밋할 두 파일의 SHA·크기가 같은지 확인하고
committed-copy-provenance.json에 연결했다. 명령·TSV·중간 JSON·변환 SVG·PNG는
stage2135~2140의 ignored output에만 보존한다.
