# #7642 Stage 160 — 선언 셀 프레임의 안 여백과 실제 행 소유 대조

Issue: #7642

## 구현 전 근거

실패한 #7362/#7390 입력은 HWP가 아니라 정식 HWPX
`samples/issue2006/1790387_prep_final_report.hwpx`다. 저장 정보는 한컴 2024
13.0.0.564이며 같은 원본의 독립 기준은
`pdf/issue2006/1790387_prep_final_report-2024.pdf`다. 두 파일 SHA-256은 각각
`c68baed24096386f9041930d24d39409b61ac99463bf04dfd242440dfdeb739f`,
`04b95a6e41420fb45934ce2ee5abd8cf6dac4ce12fd47977dacbe7fca28018a8`이다.

Stage 159 Native로 67~70쪽을 비교하면 98.83194 / 96.76802 / 70.71660 /
35.27534%다. 2022 기본 프로필과 2024 프로필 모두 69쪽에서 같은 잘못된 통째
배치를 한다. 실제 38행 높이는 957.3px이며 선언 개체는 809.3px다.
`DIAG_FIT`는 실제 높이가 안 들어가는데 `declared=true`로 수용한 것을 확인했다.
본문 94.5~1020.5에 표 155.2~1112.5를 그려 하단이 약 92px 넘는다.

선언을 신뢰하는 검사는 셀의 저장 줄 아래끝만 검사하고 유효 안 여백을 빠뜨렸다.
실제 첫 열 일반 행은 `hasMargin=0`, 셀 저장 높이 1280HU, 저장 줄 높이 1000HU다.
셀 고유 140HU 대신 표 기본 위·아래 425HU가 적용되어 필요한 물리 높이는
1850HU다. 한컴 PDF의 행 피치도 이에 해당한다. 저장 글줄이 들어간다는 사실만으로
셀의 전체 점유가 선언 상자 안에 있다고 판정하면 안 된다.

## 생산·소비와 수정 범위

`Cell::effective_padding → 저장 줄 끝 + 유효 위·아래 여백 → 선언 셀 프레임 유효성
→ query_whole_table_fit의 선언 수용 → 블록 표의 행 스캐너 → 같은 조각의 실제 paint`
를 대조한다. 선언 상자에 안 여백 포함 저장 내용이 들어가는 경우만 선언 수용의
근거로 사용한다. 선언·측정 중 큰 값을 일괄 선택하거나 출력의 하단을 숨기지 않는다.
조회 helper를 작은 `typeset/stored_table_frame.rs` 모듈로 분리해 안 여백 출처와
검사 근거를 함께 유지한다. 행 형상 조회는 이어받기의 예산·컷 검사에도 사용되므로
typeset의 기존 조회 이름으로 공유한다. 행 형상 조회 자체의 의미는 변경하지 않는다.

## 검증 계획

같은 Native 빌드에서 PrEP의 67~70쪽과 140쪽 전체를 대조하고 69→70의 행 소유,
선행 본문·캡션, 후속 내용·각주 보존을 확인한다. 정상 저장 선언 프레임 대조군은
#2097의 원본 및 독립 재저장 표를 사용하며 입력과 Print를 바꾸지 않는다.
수정 전·후의 정확한 기존 관계 검사는 유지한다. 원본의 Native/fresh WASM 전체
90%와 확대 판독 전에는 새 회귀나 기대값 교정을 추가하지 않는다.

Stage 159 fresh WASM 64쪽의 환경 실패는 실제 공간 부족이었다. 같은 package로
재실행 중이며 이 작업의 source 해시 검사가 끝날 때까지 Rust는 변경하지 않는다.
이전 소스 전체 55문서 WASM도 같은 공간 부족으로 종료된 것을 실제 traceback과
controller PID 소멸로 확인했다. 해당 중간 SVG 약 6.40GiB를 정리하고 PNG·TSV·로그를
보존했다. 그 진단을 최종 코드의 55문서 통과로 보고하지 않는다.

이후 이전 소스 `01dc6dee46eb0e0efeb474e4386799c34cf584dd`의 Native 전체
55문서·853쪽이 완료됐다. 49문서는 전쪽 90% 이상이며 6문서는 미달이다.
9월 시험지 HWP/HWPX 및 격자 변형 4문서는 10~11쪽, 11월 구분선위0·미주사이20·
구분선아래2 HWP/HWPX는 12~17쪽에서 미달이다. 9월 HWP를 Stage 159의 동일한
입력·PDF로 다시 출력해 10쪽 35.35162%, 11쪽 63.01163%를 확인했다.
10쪽 Print 맨 위의 이전 문항 꼬리가 Native에서는 앞쪽에 들어가고 이후 내용이
위로 당겨진다. 이 쪽 소유 차이는 수식 모양 개선과 구분해 계속 보정한다.

PrEP 68쪽도 96.76802%만으로 완료 판정하지 않는다. Print에는 세 줄인 표 앞
마지막 문단이 Native에는 네 줄 배치되어 69쪽 선행 본문·표 원점에 영향을 준다.
원래 예약한 각주 경계와 실제 수용 분기를 확인하기 위해 기존
`RHWP_DIAG_SPLIT_BUDGET`에 각 후보 줄의 실제 예산·각주 예약·수용 근거를 함께
출력한다. 이 진단 자체는 수용 조건이나 테스트 기대값을 바꾸지 않는다.

`upstream/devel`을 다시 fetch했고 기준 SHA는
`bfa28a77a2714482f647ee6a7b9aa7f7876d8404`로 유지됐다. 현재 브랜치가 이미 이 기준을
포함하며 뒤처진 commit은 0개다. 소스 검증 중 새 rebase를 실행하지 않았다.

유효 위·아래 안 여백을 포함했다. 초기 분리의 이어받기 import 누락은 공통
조회 경로를 유지하도록 고쳤다. 행 형상 조회의 의미와 기존 컷 계약은 유지한다.

`stage160-native-realign-build.json`에 명령·소스 해시·binary SHA를 보존한다.
