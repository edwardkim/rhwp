WASM 빌드는 각각 exit 0으로 끝났다. 양쪽 시각 검증과 Rust 회귀는 아직

## 공간 정리

종료된 Snap Chromium 검증 프로필 9개는 삭제 직전 소유·inode·하위 파일
시각·잠금 PID·프로세스 참조를 재확인해 삭제했다. 할당 크기
2,962,558,976바이트를 정리했으며 정확한 경로와 전후 여유 공간은
`stage2802-closed-chromium-cleanup.json`에 있다.

사용자가 지정한 `target/pr-review/debug/incremental`은 캐시 330개,
약 16.67GiB다. 가장 최근 캐시도 마지막 사용 후 11시간 이상 지났다.
WASM producer가 끝나고 Cargo 계열이 모두 유휴임을 확인한 뒤 stage2804에서
캐시 하위 경로 330개를 삭제했다. 할당 크기 17,900,785,664바이트를 정리했다.
각 경로의 소유·inode·최근 변경·프로세스 참조와 삭제 결과를 기록했다. 정리
전후 파일시스템 여유는 9,712,803,840/26,446,807,040바이트이며, 다른 작업의
동시 쓰기가 있으므로 이 차이를 삭제한 캐시 크기와 동일시하지 않는다.
후속 Rust 컨트롤러 두 개만 정리 동안 대기시켰다가 재개했으며 실행 중인
컴파일러는 중지하지 않았다.

`target/pr-review/release-test/incremental`에는 캐시 하위 경로가 없다.
`release-test`의 deps·fingerprint·빌드 산출물·실행 파일은 후속 회귀 검증에
재사용하므로 보존한다. 공유 target 전체를 삭제하거나 초기화하지 않는다.

## 합성 굵기의 실제 소비 경로 진단

stage2808에서 같은 후보의 direct PDF를 PDFium으로 출력한 50쪽 raw는
99.99123%였다. 같은 source의 Native Skia PNG 99.17636%와 다르므로,
윤곽선 기하만 보고 Native raster 소비까지 일치한다고 가정하지 않는다.
RHWP PDF는 진단 산출물이며 독립 한컴 PDF나 Native gate를 대체하지 않는다.

stage2810은 원 한컴 PDF의 복제본에서 `2 Tr` 직후의 획 너비 명령 25개만
변경했다. 변경 없는 직렬화 대조군은 원 PDF와 픽셀이 완전히 같다.
획 너비를 각각 원래의 0.05배·0.5배로 줄여도 96DPI 출력은 원본과 픽셀이
완전히 같았고, 4배로 늘리면 10,631픽셀이 달라졌다. 원 PDF의 바이트와
SHA는 유지했다. 이 복제본들은 새 기준 자료나 최종 gate 증거가 아니다.

PDFium main의 AGG `RasterizeStroke`와 Skia `SetupStrokePaint`에는 장치
단위에서의 최소 획 처리와 fill/stroke 소비가 있다. 소스 snapshot과 해시는
stage2809에 보존했다. main과 설치된 PDFium의 정확한 revision이 같다는
주장은 하지 않으며, 위 실행은 설치 binary에서 관측한 별도 증거다.
이 장치 단위 raster 처리와 원문 조판 좌표·em 획 너비를 구분해 검토한다.
후속 수정은 vector 출력의 원래 em 획, 서로 다른 DPI, 회전·장평, 정적
picture 캐시의 기록/재생까지 확인해야 한다. 문서별 수치 보정으로 대체하지 않는다.
