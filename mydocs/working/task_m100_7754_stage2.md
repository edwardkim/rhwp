## 독립 근거와 수정 전 관측

시작 base는 `d7b5286cbf6401678a70eed3d66236a68dd2a72c`다. 같은 원본의 Native 전쪽
46쪽과 독립 한컴 2024 Print 46쪽을 비교했다. HWP·HWPX 각각 5쪽 94.60%이며,
HWP는 35쪽 96.34%·42쪽 96.20%, HWPX는 35쪽 96.34%·42쪽 96.66%다.
새로 확보한 HWP Print와 기존 HWPX Print도 5쪽의 본문 줄 경계를 동일하게 출력했다.
fresh WASM 전쪽 측정은 진행 중이며 아직 이 수치를 WASM 결과로 표시하지 않는다.

원본 HWPX `Contents/section1.xml`의 문단 11은 어울림 표 `[A]`와 본문을 함께 소유한다.
한컴 저장본의 LineSeg 시작은 0·52·96·139·185·227이고, 별도 개체의 8단위 원문 슬롯을
포함한다. Native는 저장 경계에 따라 첫 줄을 `미지의 `에서 끝낸다. 같은 소스의 독립 Print는
첫 줄 끝에 `세`를 포함하고 다음 줄을 `계에`부터 시작한다. 뒤 줄도 서로 다른 문자 경계를
갖는다. Native·PDF의 같은 페이지 review를 직접 열어 이 차이를 확인했다.

본문 글자모양 74는 원본 TTF `KoPubWorld바탕체 Light`, 위첨자 97은 원본 TTF
`학교안심 포스터 B`다. 원본의 문서 대체 선언은 각각 HCR Batang이다. 현재 설치 프로그램과
PDF의 KoPubWorldBatangLight·HakgyoansimPosterB도 확인했다. HFT OTF를 이 두 TTF의
대용으로 공급하지 않는다. TTF → TTC의 해당 face → OTF(CFF) 선택 순서는 그대로 둔다.

## 원인과 소비 경로

`inline_flow::plan_square_table_host`는 실제 표 바깥여백·현재 측정 높이로 배제 프레임을
만들고 공통 composer에서 현재 줄 구성을 계산한다. 그러나 새 줄과 저장 줄의 수·가로 원점·폭이
같으면 `None`을 반환하는 분기가 문자 소속의 시작을 비교하지 않는다. 동일한 가로 상자라도
문자가 다음 줄로 이동한 계획은 저장 줄과 동등하지 않다. 원본 줄의 유효성을 전면 완화하거나
문서 ID·임의 좌표 조건을 추가하지 않고 이 동등성 판정을 바로잡는다.

생산 결과는 `plan_square_table_host`의 `text_rows`이며
`typeset/controls/paragraph_flow.rs`가 fit 전에 `use_square_host_plan`에 전달한다.
이 소비 경로의 fit 높이·본문 줄 배치·표 원점과 뒤 문단 전진까지 새 줄 구성이 유지되는지
실제 출력에서 확인한다. 함수 이름이 같다는 이유만으로 배치까지 공유했다고 판정하지 않는다.

기존 `inline_flow.rs`는 이미 1,505줄이다. 이번 수정은 해당 분기의 동등성 비교에 원문 문자
시작을 포함하는 최소 변경으로 제한한다. 1,000줄 원칙을 맞추기 위한 무관한 파일 분할을 섞지
않으며, 새 진단·회귀·기록 파일은 1,000줄 이내로 유지한다.

## 35쪽의 전폭·배제 프레임 소유 보정

문단 3.8의 마지막 두 저장 줄은 `850 + 36568 = 37418HU`다. 이는 실제 단 폭 38268HU에서
문단의 왼·오른 여백 각 850HU를 뺀 `ParagraphBox::body_for_style`의 `850..37418`과 같다.
그림 옆 7개 줄도 이 문단 상자 안의 좁은 구간이며 저장 `column_start`는 이미 단 기준이다.
첫 줄의 독립 Print 끝 글자 `보`는 x=374.08..386.01px다. 현재 Native는 시작이 오른쪽으로
밀리는 동시에 가로 여백을 다시 차감해 줄 끝도 약 11.33px 일찍 닫는다.

원본 저장값은 `composer/stored_lines_runs.inc.rs`에서 ComposedLine의 `column_start`와
`segment_width`로 보존된다. 줄 높이·기준선·간격을 쓰는 측정 경로는 이 줄 구성과 저장
메트릭을 유지한다. 실제 배치는 `paragraph_layout.rs`의 저장 세그먼트 선택 후
`effective_col_x = column.x + column_start`로 원점을 소비하지만, 뒤의 일반 문단 여백
분기에서 같은 여백을 다시 더하고 폭에서도 뺐다. 이중 소비가 마지막 원점·폭을 바꾼다.

기존 #7548의 전폭 줄 비교를 `stored_wrap_frame.rs`로 옮겨 재사용한다. 현재 실제 문단
상자와 원본 전폭 줄의 양 끝이 정확히 같고 현재 줄이 그 안에 들어가는 경우만, 해당 저장
구간을 완성된 단 기준 프레임으로 소비한다. 문단 여백은 이미 소비됐으며 별도 줄 들여쓰기는
한 번 적용한다. 같은 cs 수치만으로 인증하지 않고 셀·글상자·명시 wrap-anchor 경로도
변경하지 않는다. 기존 #6706/#8191의 TAC 소유 인증·장식 도형 반례는 그대로 유지한다.

기존 13,000줄 이상의 `paragraph_layout.rs`에서는 전폭 줄 helper를 분리하고 소비 분기만
연결한다. 새 helper는 1,000줄 이내다. 원본 전폭 구간이 문단 상자와 다른 경우·일정한 줄 폭만
있는 경우·편집 후 저장 캐시를 근거로 이 계약을 적용하지 않는다. 실제 후보 출력과 정상
대조군은 빌드 종료 후 확인하며, 아직 이 보정의 성공으로 기록하지 않는다.

## 복학원서의 PCX Print 코덱 계약

#7756의 작은 로고는 PCX 1-bit/1-plane이며 palette 0은 검정, 1은 흰색이다. Native가
디코딩한 유효 그림이며 잘못된 좌표나 불투명도 때문에 PDF와 다른 것은 아니다.
같은 원본의 한컴 2020 Hancom PDF driver Print와 2024 PrintToPDFEx는 로고를 출력하지
않고 JPG 워터마크만 내장한다. 이 결과를 독립 인쇄의 코드 경로 차이로 분리해 확인했다.

진단 HWPX는 원본의 문단·LineSeg·그림 프레임·글꼴 선언을 그대로 유지하고 image1의
코덱만 바꿨다. 원 PCX, 같은 픽셀의 8-bit palette PCX는 모두 로고가 인쇄되지 않았다.
PNG 96 DPI·PNG 300 DPI는 모두 401×458 픽셀 로고를 같은 Print 사각형
`57.57,39.56..115.26,105.36pt`에 내장했다. 출력 4건은 한컴 2024 13.0.0.3901의
같은 Print 경로이며 쪽수는 각각 1이다. DPI·배치 변경을 원인으로 주장하지 않는다.
입력·PDF·job·실제 결과는 ignored `output/pr-review/issue7754-nine/bokhak-codec/`에 있다.

공통 Print의 Picture 코덱 지원 판정에 PCX를 반영한다. 편집 출력의 PCX 디코딩, 원본 자원,
그림의 조판 상자와 흐름 점유는 유지한다. bitmap fill은 Picture와 다른 계약이므로 이번
근거로 적용하지 않는다. SVG와 공통 Paint가 같은 Print 지원 술어를 소비하며 backend마다
문서별 로고를 숨기지 않는다. PCX 비트 깊이 두 대조군과 PNG의 실제 인쇄가 적용·비적용
근거다. 보정 후 원본 전쪽 Native/fresh WASM·워터마크와 후속 본문의 직접 판독은 남아 있다.


## 분리된 원본 HFT 프로그램의 실제 조회 별칭

#7755의 3쪽은 정상 배율 한컴 2020 Print에서도 Native raw 96.04%였다. 원본
`양재 본목각M`을 Native가 선택했으나 실제 canonical family는 영문 부분 프로그램의
`YJ Bonmoggak M`이었다. 새 OTF의 영문 부분 `YJENBMGM.otf`와 한글 부분
`YJHGBMGM.otf`는 서로 다른 영문 family를 갖고, 둘 다 SFNT name 1/16의 한국어 family
`양재 본목각M`을 선언한다. 영문 프로그램에는 한글 글리프가 없고 한글 프로그램에는
해당 원본 한글 글리프가 있다. 다른 family를 같은 원본으로 추정한 별칭은 아니다.

`lookup_font_name_in_environment`는 HFT의 임의 조판 별칭을 실제 주 프로그램 앞에 넣지
않도록 막는다. 이 보호는 유지한다. 유효한 프로그램 SHA가 있는 실제 조회 이름을 주
프로그램 다음의 glyph fallback으로 보존해, 같은 원본의 분리된 프로그램에 도달하게 한다.
같은 원본 TTF → TTC face → OTF의 형식 선택은 변경하지 않는다.

생산 코드 수정 전 같은 Native 바이너리·원본·Print·96 DPI에서 자동 선택 환경을 고정해
대조했다. 고정 환경은 96.04%, 같은 실제 조회 이름만 glyph fallback에 보존한 환경은
96.40%였다. 연구진 소제목의 잘못된 돋움이 원본 목각 글리프로 바뀌는 것을 직접 판독했다.
3쪽의 남은 차이까지 해결하거나 98% 조건을 충족했다고 주장하지 않는다.
진단의 환경 JSON·TSV·PNG는 ignored `market-yj-alias/`에 보존한다.

## 시장구조조사 전쪽 대조와 빈 줄의 실제 소속

## 네 번째 고정 소스 검증의 중간 결과

## 명시된 HWPUNIT과 fallback의 CHAR 표지를 분리한 한컴 입증

셀 폭 5곳만 변경한 Print와 layoutCompatibility만 변경한 Print는 원본 구판 배치와 같다.
들여쓰기 단위·값 36곳만 현재 exporter 값으로 바꾼 Print에서만 27·53쪽의 내용 소속이
현재 exporter 배치로 바뀐다. 세 독립 job은 각각
`196dcb51-c7fd-4d07-afba-788cb29e1773`, `f4d33064-5a16-4a8f-980f-075fb184df10`,
`ca613e35-4401-422e-93ad-c6f03be97d7e`이며 입력별 SHA·PDF·본문 원점은
`regulatory-resave/isolated-xml-print-matrix.json`에 보존했다.

실제 패키지 version.xml도 확인했다. 86712는 xmlVersion 1.5이고 header의 version만 1.2다.
80168 대조군은 패키지 xmlVersion도 1.2다. 헤더 판본만 보고 전역 반감 규칙을 바꿀 수 없다.
두 원본을 한컴 2020·2024에서 각각 HWP로 저장해 DocInfo tag 25의 원본 값을 읽었다.
86712 문단모양 24·34·35·40·43의 intent는 두 제품 모두 case×2이며,
80168의 34·35·43은 두 제품 모두 기존 case 값 그대로다. 저장 중 자원 중복 제거가 있으므로
전체 ID의 개수 통계나 뒤쪽 ID의 단순 대응을 독립 매핑 근거로 사용하지 않는다.
`regulatory-resave/unit-boundary-matrix.json`은 진단 원자료이며 해당 ID·원본 속성을 직접 대조했다.

공식 로컬 Core 스키마의 HWPValue는 값과 단위를 함께 정의하고 unit의 기본값을 HWPUNIT으로
명시한다. 현재 파서의 case 파싱은 CHAR 표지를 먼저 보존하지만, 이후
`exact_value_from_default`가 홀수 fallback을 정밀도 값으로 재채택하면서 명시 HWPUNIT도
CHAR 저장값으로 바꾼다. 선택한 case의 선언 단위를 보존하고 fallback이 그 표지를 덮어쓰지
않게 공통 margin 해소를 보정한다. fixed lineSpacing의 별도 정밀도 복원과 패키지 판본의
기존 단위 처리는 유지한다. #3368 → #6875 → #7545 → #7816의 선행 계약을 대조했다.

소스 7의 실제 Native 빌드는 exit 0이고 SHA는
`89254cbba9084435ca05bf775e0578fee7a2a17399b364e5be567d7a38ab502c`다.
수동 Print와 시장구조조사 3쪽 raw는 99.37%로 개선됐다. 남은 raw 미대응은 소제목의 41픽셀이다.
제목의 공백과 이름·KDI는 모두 2px raw 범위에 들어왔다. fresh WASM·전쪽 통과로 확대하지 않는다.


명시 단위에 맞춰 default 값만 바꾼 진단 사본을 따로 인쇄했다. job
`a9b180a4-c75e-4a5e-a692-6a2d641ace86`, 한컴 2024 Print이며 원본 구판 PDF와
96DPI 전64쪽의 래스터 바이트가 모두 같다. 이는 fallback의 홀수 표지를 case의 명시
HWPUNIT에 재주입하면 안 된다는 독립 근거다. 반면 같은 사본을 현재 Native로 렌더하면
52쪽 둘째 줄의 x는 146.9 → 89.8px로 올바르게 바뀌지만 저장 textpos 경계는 그대로여서
53쪽 최저 19.46%가 남는다. 파서의 단위 보정만으로 해결 완료라 판정하지 않는다.
한컴이 직접 재저장한 HWP의 Native는 52쪽 99.98·53쪽 100.00%지만 27–29쪽은 아직 미달이다.
재저장 HWP는 진단 자료이며 정식 구판 HWPX 입력의 검증을 대체하지 않는다.

기존 `stored_margin_context`는 이전 여백을 현재 raw 값의 2배로 추정한다. #7765에서는
fallback의 실제 CHAR 저장값이 있으므로 그 값을 파싱 출처로 보존한다. 기존의 모든 줄 경계
재현 인증은 유지하면서 이전 스타일 생성만 실제 출처를 우선 사용하게 한다. 생산 연결은
`parse_para_shape_switch`의 case와 fallback → ParaShape의 읽기 전용 원본 여백 출처 →
`previous_margin_styles_with_storage` → `project_body/project_cell`의 줄 전체 인증 →
`normalize_flow_with_storage`의 새 줄·누적 전진 → 공통 측정·배치다. 새 원본별 조건이나 px
보정값을 넣지 않는다. 인증에 실패하면 캐시를 임의로 삭제하지 않고 원인 추적을 계속한다.

거대 기존 모듈의 수정은 현재 파서·모델 필드와 기존 이전 스타일 해소 지점으로 제한한다.
새 독립 거대 파일이나 호출 지점별 중복 보정을 만들지 않는다. 저장 단위 판본 처리,
fixed lineSpacing의 별도 정밀도 복원, 정상 CHAR writer 계약은 유지한다. 새 회귀 검사는
정식 원본의 Native/fresh WASM 98% 이상·독립 확대 판독 후에만 작성한다.

## 선언 단위·캐시 후보의 실제 실패
