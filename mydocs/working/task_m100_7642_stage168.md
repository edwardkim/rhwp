# #7642 Stage 168 — 미주 0 원점의 연속줄과 저장 되감김 구분

## 원본과 독립 근거

Stage 167의 9월 HWP 전체 23쪽은 22쪽이 90% 이상이며, 기존 4쪽 78.47295%가
남는다. 같은 역할의 HWPX 첫 12쪽은 10쪽 35.26860%, 11쪽 62.88459%가 남는다.
원문과 한컴 Print에 대응한 입력을 유지하며 서로 다른 파일의 점수를 대신하지 않는다.

9월 원본 HWPX의 문7 마지막 미주 문단은 저장 사다리
`30144, 33034, 35924, 38814, 0`이다. HWP 짝도 마지막 0을 그대로 보존한다.
독립 Print는 이 마지막 수식 줄을 다음 쪽에 둔다. 파서는 HWPX의 마지막 0을
41336으로 덮어쓰며 실제 조판이 써야 할 단 경계를 지운다.

이전 주석이 인용한 아티팩트를 원본에서 다시 확인했다.
`SO-SUEOP.hwpx` 미주 161의 실제 저장 사다리는 **0, 0**이다. 정상 연속줄을
0으로 저장한 경우로, archived Task 1692 Stage 5의 복원 근거다. 양수에서 0으로
되감기는 저장 사다리와 같은 패턴이 아니다. GitHub issue 1692 제목/본문만으로
좌표 계약을 추정하지 않고 실제 작업 기록과 원본 XML을 읽었다.

## 구현 방향

- 미주에서는 원래 양수 줄에서 0으로 되감기는 유효한 저장 단/쪽 신호를 보존한다.
  0,0처럼 한 번도 양수 원점에 도달하지 않은 연속줄 아티팩트의 복원은 유지한다.
- 소스 태그·문자 분할·보호된 HWP5-origin 경로와 기존 각주 계약을 확인한다.
  특정 문서 ID, 미주 번호, 줄 개수나 위치 임계값으로 구별하지 않는다.
- 큰 section 파서에 분기와 큰 함수를 계속 쌓지 않고 관련 사다리 helper를 작은
  모듈로 이동한다. Native/fresh WASM이 같은 파싱 결과와 Stage 167의 공통 컷
  조회를 소비한다. parser 결과 → 줄 투영 → fit/컷 수용 → 실제 배치를 대조한다.
- 4쪽 본문 배치도 별도 원인으로 유지한다. HWPX 짝의 원문은 일부 수식 값이
  달라 HWP 원본의 PDF를 대신할 수 없다. 동일 입력/Print와 source before/head의
  비교로 표 이후 오른쪽 단의 줄/문단 원점·높이 전진을 추적한다.

## 반례와 검증

0,0 연속줄, 양수→0 실제 경계, 0 아닌 값들 사이의 기존 되감김, 각주와 HWP5
보호된 저장본, 편집/합성 줄을 분리한다. 정식 새 렌더링 회귀는 관련 원본의
전체 Native/fresh WASM 90% 이상과 확대 판독 뒤에 추가한다. 먼저 실제 원본
전체 TSV·대표 PNG와 parser 데이터 대조로 보정 방향을 확인한다. 새 함수명으로
내용 소속·보존·순서를 검사하고 px 기대값으로 배치를 고정하지 않는다.

## 결과

Stage 167 HWPX 전체 23쪽 비교가 끝났다. 10·11쪽만 90% 미만이고 나머지
21쪽은 90% 이상이다. actual 쪽수 23과 소스 해시 일치를 확인했다.

파서 사다리 수용 helper를 `note_line_positions.rs`로 이동하고 미주의
양수→0 실제 되감김을 보존하도록 구현했다. 기존 HWP5-origin·각주 보호,
비영 되감김과 전 줄 0 연속줄 복원 경로를 유지한다. 소스 문자 분할과 태그의
유효성을 확인하며 문서 ID/줄 개수/높이 임계값으로 선택하지 않는다.
이 단계의 새 빌드와 독립 출력/전체 회귀 검증은 미완료다. 최종 55개/853쪽, 추가
64쪽과 실패 원본, Rust/lint·최신 devel 동기화와 PR/CI/후속 처리는 계속 남는다.

## 첫 재검증 결과

새 Native 빌드는 exit 0, 소스 해시 일치다. 실제 컴파일된 파서 진단에서
SO 미주 161의 전 줄 0 연속줄은 0,1200으로 복원되고, 9월 미주 7의
30144/33034/35924/38814/0 되감김은 그대로 보존됐다.

9월 HWPX 첫 12쪽은 모두 90% 이상이며 최저 96.65213%다. 10쪽은
35.26860%→98.92453%, 11쪽은 62.88459%→98.82582%로 개선됐다. 새 전체
review PNG를 `mydocs/pr/assets/issue7642-note-origin-20261012/`에 보존했다.
내용의 단 소속은 확인했으며 fresh WASM·수식 미세 확대와 나머지 11쪽은 진행 중이다.

WASM 검증의 대용량 Native 글꼴 정책 중간 SVG도 전체 글꼴 바이트 공급과
원본 SVG 복원 해시·기존 Unicode 검사 결과를 보존하며 제한하도록 ignored
helper를 준비했다. 동일 DYAD WASM package의 기존/새 래스터 PNG 바이트가
같고, 점수 98.50470%와 검사 글꼴 4개가 같다. 전체 원문 쪽수와 WASM 소유는
실제 WASM export만 사용한다. 이 작은 동등성 확인을 새 WASM 원본 통과로
대신하지 않는다. code source와 canonical 점수·래스터 backend는 바꾸지 않았다.

## Native 전체 및 공백 원본 재검증

9월 HWPX 전체 23쪽 Native가 완료됐다. 쪽수 23/23, 최저 91.85820%,
90% 미만 0쪽, 소스 해시 유지 true다. fresh WASM 빌드는 exit 0이며
소스 해시 유지와 Studio JS/WASM 해시 동기화를 확인했다. 실제 WASM 23쪽
시각 검증은 계속 실행 중이다. 빌드 성공으로 이 입력의 WASM 통과를 선언하지 않는다.

고정폭 공백 회귀의 원본 30307을 별도로 전체 비교했다. Native/fresh WASM
각 13/13쪽, 최저 93.19077%, 미달 0쪽이다. 대표 PNG와 실제 글꼴 공급의
남은 차이는 `mydocs/pr/assets/issue7642-figure-space-source-20261012/`에 기록했다.
선택 실패를 px 기준으로 우회하지 않고 원문 문단 소속의 런과 내용 보존을
검사하는 새 이름의 관계형 검사를 검토한다. 현재 정식 검사 추가/변경은 미완료다.

종료된 Stage164 PrEP WASM 묶음에 반복 보존된 전체 SVG 692개를 해시 기록
후 정리했다. 약 9.10GB를 확보했으며 원본 HWP/HWPX/PDF, 전쪽 TSV/PNG/로그/
render tree와 최저 쪽을 포함한 대표 원문 SVG 8쪽은 보존했다. 사용 중인 경로가
아님을 열린 파일 핸들로 확인했다. 공용 Cargo 산출물은 삭제하지 않았다.

`upstream/devel`을 다시 fetch했으며 SHA는 기존 `bfa28a77a2714482f647ee6a7b9aa7f7876d8404`
와 같고 현재 HEAD에 포함돼 있다. 실행 중인 생산 소스를 바꾸지 않았다.

## fresh WASM 전체 완료

9월 HWPX의 실제 fresh WASM 전체 23쪽도 완료됐다. 쪽수 23/23, 최저
91.85820%, 90% 미만 0쪽, source hash 유지 true, exit 0이다. 1096.705초다.
Native와 WASM의 별도 manifest/TSV를 확인했으며 대표와 수식 확대의 판독은
별도로 유지한다. 이 결과를 남은 HWP 4쪽이나 전체 55개 통과로 대신하지 않는다.

## 확대 판독의 보류 항목

전체 점수 통과 뒤 실제 Native/fresh WASM 11쪽을 같은 영역에서 확대했다.
큰 괄호 뒤 첨자 2가 독립 Print보다 낮으므로 이 수식의 배치는 미충족으로
유지한다. 기호가 존재한다는 앞 기록을 정확한 첨자 위치의 증거로 사용하지
않는다. 해당 원본 script와 script 부착 기준을 추적하며 새 회귀의 선행 판독과
최종 제출/승인을 보류한다. 다음 표 진입 간격 보정의 빌드/검증은 별도로 진행한다.
