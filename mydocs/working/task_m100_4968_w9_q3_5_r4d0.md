## 1. 결론

`TextRunNode`에 optional `layout_positions` 계약과 공통 검증·fallback accessor를 추가했다. 모든 기존
producer는 명시적으로 `None`을 사용하므로 이번 절편만으로 layout이나 backend 동작은 바뀌지 않는다.
K1 producer와 backend 소비 전환은 R4D-1·R4D-2의 승인 경계로 남겼다.

K0 보호 불변식은 다음 두 층에서 확인했다.

1. unit contract에서 `None`은 JSON에서 완전히 생략되고 `Some`만 `layout_positions`를 직렬화한다.
2. 새 native release와 R4C 때 보존한 Docker WASM 산출물을 교차 실행한 결과 normalized layer-tree와 선택
   9개 run positions가 같고 SVG가 byte-for-byte 같았다. 새 필드는 K0 `textRunFields`에 나타나지 않았다.

따라서 R4D-0은 공통 전달 그릇만 만들었으며 기존 K0 paint 출력에는 positions payload를 노출하지 않는다.

## 2. 구현 범위

### 2.1 optional positions 계약

`src/renderer/render_tree.rs`의 `TextRunNode`에 다음 필드를 추가했다.

```rust
#[serde(skip_serializing_if = "Option::is_none")]
pub layout_positions: Option<Vec<f64>>,
```

- 의미: 실제 replay 문자열 Unicode scalar N개에 대한 run-relative N+1 경계값
- K0·미지원·검증 실패: `None`
- K1 exact pair 적용 결과: 후속 producer가 `Some`을 게시
- font bytes·경로·family provenance·원문 복제: 저장하지 않음

기존 제품·unit·integration literal에는 모두 `layout_positions: None`을 명시했다. 새 integration source나
generated suite·manifest는 source 변경에 포함하지 않았다.

### 2.2 검증과 fail-closed

`validated_layout_positions_for(replay_text)`는 다음 조건을 모두 만족할 때만 값을 빌려준다.

- replay scalar 수 + 1과 positions 길이가 같음
- 최대 4,096 scalar / 4,097 positions
- 첫 값이 `0.0`
- 전항 finite·non-negative·monotonic

`replay_positions_for(replay_text)`는 검증된 값을 우선하되, 필드 부재·문자 수 불일치·NaN·역행·상한 초과
시 기존 `compute_char_positions`를 실행한다. display projection 등으로 source와 replay 문자열 길이가 달라도
부분 K1을 남기지 않고 run 전체를 K0로 닫는다.

### 2.3 이번 절편에서 하지 않은 일

- `Some(layout_positions)`을 만드는 제품 producer 없음
- SVG·Canvas2D·HTML·Skia·paint JSON·CanvasKit consumer 전환 없음
- line boundary·bbox·다음 run x 변경 없음
- source lookup·shaping·font fallback 변경 없음
- `LineSeg` validity 판정 변경 없음

이는 미완 구현의 은폐가 아니라 R4D-0의 의도된 승인 경계다. producer를 먼저 열면 소비 backend가 서로 다른
좌표를 사용할 수 있으므로 공통 계약과 K0 무변화를 먼저 고정했다.
