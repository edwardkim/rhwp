# #7642 HancomEQN의 측정과 실제 표시 face 연결

Issue: #7642

## 구현 전 근거와 범위

PrEP 원본 HWPX와 한컴 재저장 HWP의 수식 12개는 글꼴·크기·폭·높이·기준선이 같다.
독립 Print는 HancomEQN을 사용하지만 현재 paint는 Latin Modern Math와 일반 첨자 70%를 쓴다.
정상 저장 정보를 무효로 분류하거나 HYhwpEQ로 치환할 근거가 없다.

로컬 XML 진단 64개를 한컴 2024에서 Print했다. 두 face, 6/9/12/18pt의 아래첨자는
모두 68%이고, 본체와 첨자의 기준선 차이는 약 1/4em이다. 설치 글꼴과 Print subset의
38개 윤곽은 같지만 HancomEQN의 hint 프로그램은 다르다. 따라서 원시 hmtx에 단순
비례만 적용하지 않는다. 실제 Windows GDI의 선택 face와 논리 글자 크기별 전진폭을
읽고 Print에서 관측한 원점과 대조한다. 글꼴 바이트·윤곽은 커밋하지 않는다.

원본의 font → EqLayout의 face 선택·전진·첨자 크기 → LayoutBox의 글리프 런 →
SVG/Canvas2D/Native Skia/paint JSON → Studio의 host face 요청·CanvasKit 표시까지 연결한다.
같은 런이 실제 family를 보존해야 한다. 선형 글줄의 자연 크기와 복합 수식의 저장 폭
스케일은 구분하며, HY 전용 분수·장식 프레임을 다른 face에 적용하지 않는다.

이번 보정은 실제 face, 전진폭, 첨자의 크기·기준선과 검증된 연산자 간격을 함께 다룬다.
기본 EqLayout·다른 글꼴·기존 HY 경로와 보호된 크기는 대조군으로 유지한다.
Hat·분수·큰 연산자의 남은 차이는 별도 직접 판독으로 확인하며 이 변경만으로 완료라 하지 않는다.

## 검증 계획과 현재 판정

고정 target/pr-review, 빌드 잡 8개를 사용한다. 먼저 Native 진단과 원본 영향 페이지를
Print와 비교한 뒤 fresh WASM과 전체 PrEP를 확인한다. 새 실물 회귀는 양쪽 전쪽 90%
선행 조건과 직접 판독을 충족한 뒤 추가한다. 수정 전후의 같은 assertion으로 검출을 확인한다.

구현과 새 출력 검증을 진행 중이며 PR 준비 완료가 아니다.
ignored 증거 루트는 `output/pr-review/issue7642/failed-inputs-20261008/stage15-current-validation/`이며,
1584 원본/저장본 비교, 1585 Print와 trace, 1586 실제 face·윤곽·GDI 확인,
1587 GDI 전진폭 자료에 연결한다. 인증 정보는 보존하지 않는다.

Windows PowerShell에서 실제 GDI face 선택과 논리 크기 2..128의 짝수 크기별 148개
글리프 전진폭을 읽었다. 서버·글꼴 파일을 변경하거나 글꼴 파일을 복사하지 않았다.
원본과 다른 숫자표가 아니라 글꼴의 기기 메트릭이다. 6/9/12/18pt의 대·소문자
40개 Print 원점과 누적 전진을 대조한 최대 오차는 0.14541 CSS px이다.
큰 크기는 같은 cmap/hmtx의 논리 격자 환산으로 처리한다.

호스트 face의 중첩·혼합·기본값 요청 계약 13/13과 Studio TypeScript 검사는 통과했다.
배치 회귀·시각 통과를 대신하는 결과는 아니다.

## 첫 Native 실행과 빌드 의존성 확인

1588 Native 빌드 자체는 exit 0이며 269.97초 걸렸다. 1589에서 33쪽은
97.80292→98.50405%로 개선됐다. 그러나 수식이 없는 차트 26·27쪽도 달라져 27쪽이
89.91062%가 됐다. 이 상태의 WASM 빌드는 시작하지 않았다.

1589 결과를 완료 증거로 사용하지 않고 원인을 확인했다. 1591의 각 바이너리 3회 출력은
반복마다 PNG 해시가 같았다. 비결정성 문제가 아니었다. 1592에서 연결된 OOXML 차트
라이브러리는 현재 소스의 `sysClr/lastClr` 사례를 `Unspecified`로 반환했고, 정상 기대값인
`Solid { rgb: 1193046, width_emu: None }`와 달랐다. base worktree에서 빌드한 동일 경로의
산출물을 Cargo가 현재 소스보다 새롭다는 이유로 fresh 재사용한 것을 빌드 JSON·dep-info와
파일 시각으로 확인했다. 소스 SHA만 확인한 이전 binding으로 이 의존성까지 입증할 수 없었다.

실행 중인 Cargo/Rust 작업이 없는 것을 확인하고, base와 내용이 다른 차트 parser 파일의
mtime만 갱신했다. 바이트·Git diff는 유지했고 공유 target의 파일을 삭제하지 않았다.
새 빌드에서 해당 dependency가 실제 재컴파일됐는지와 같은 독립 사례의 반환값을 확인하고,
Native 전체 PrEP를 다시 검증한다. 아래첨자 1/4em 계약도 확인한 단일 글자 줄에만 적용하며,
분수 같은 복합 본체는 기존 배치를 유지한다.

## 보정된 의존성과 현재 결과

1593 빌드는 현재 checkout의 차트 dependency를 `fresh: false`로 재컴파일했다.
1592의 같은 독립 XML 사례가 기대한 Solid 색을 반환하는 것도 실제 연결한 라이브러리에서
확인했다. 1595 fresh WASM 로그도 현재 경로의 차트 crate 재컴파일을 기록한다.
공유 target은 그대로 재사용했다. 첫 1588 바이너리는 올바른 dependency를 사용한
제품 검증으로 인정하지 않고 1592 감사 결과에 무효화를 기록했다.

1593 Native와 1595 fresh WASM은 같은 제품 소스 1,602개 해시로 연결됐다.
Studio의 JS/WASM 동기화도 확인했다. 1594/1599에서 원본 PrEP와 독립 Print 140쪽의

## 남은 구조 보정의 독립 자료

1598은 로컬 XML 진단 입력 128개를 한컴 2024에서 HWP로 저장하고 별도 Print PDF로
출력한 자료다. MCP가 HWPX를 산출한 것이 아니다. 원본 PrEP의 검증 결과와도 구분한다.
HWP job `b6550187-1ade-439e-bbef-94f7f39c7dd2`, Print job
`64235c43-aae6-4268-8ac2-2be5d8352581`과 결과 해시는 ignored 1598 receipt에 있다.
두 face의 대응 64개 높이·기준선은 전부 같았고 실제 설치 글꼴의 hhea/OS2 세로 메트릭도
같았다. 서로 다른 전진폭을 유지하면서 공통 구조 프레임을 조사할 근거다.

이 진단 저장본에는 원시 LineSeg가 없다. 1605 raw parser로 메타데이터와 실제 줄 소유를
분리해서 확인했다. Native/fresh WASM 16쪽 최저 22.45847/22.87469%이고, 1~5쪽은
98% 이상이지만 뒤쪽은 실제 줄 배치부터 다르다. 원본/Print와 실패 증거를 로컬에 보존하며
공식 fixture·활성 회귀로 추가하지 않는다. 생성 입력이라는 이유로 결함을 면제하지 않는다.

이번 단계에서는 새 렌더링 회귀를 추가하지 않았다. 남은 구조·확대 차이를 보정한 뒤
새 이름의 관계 검사와 조건을 충족한 완료 페이지의 좌표 검사를 추가한다.
전체 기존 범위의 최신 devel 비교·나머지 실패 원본·전체 Rust 등 최종 게이트는 미완료이며,
PR 생성·승인·통합 완료가 아니다.
