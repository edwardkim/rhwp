# Task #524 Stage 1 — 진단·재현

## 요약

**가설 B (페이지 1 우측 단 누적 높이 inflation) 확정.** 페이지네이션의 `current_height`가 HWP의 vpos 기반 실제 사용 높이보다 **약 59 px 더 누적**되어, 페이지 1 우측 단의 잔여 공간을 잘못 계산. 결과적으로 문제 6의 보기/답지(126.2 px) 가 페이지 2로 spill.

가설 A (`[쪽나누기]`의 컬럼 인식 누락)는 **별도 수정 불필요**. B를 정정하면 [쪽나누기]는 자연스럽게 페이지 2 좌측에 도달하므로 (페이지 1 우측 단 끝 + 페이지 break = 페이지 2 좌측 단 시작) 의도된 위치에 안착.

## 1. 측정 데이터

### 페이지 1 단 1 (우측, 2단 레이아웃)

| 지표 | 값 |

### vpos 기반 실제 종료점 계산

`pi=29` (페이지 1 단 1 마지막 항목): `"  (가)(다)에 대한 설명으로 옳은 것만을 <보기>에서 있는 대로 고른 것은? [3점]"`

```
ls[0]: vpos=75232, lh=1150
ls[1]: vpos=76842, lh=1150
[PS] spacing: after=1000 line=140/Percent
```

- 마지막 줄 bottom HWP = 76842 + 1150 = **77992 HU**
- HWP→px 변환: 77992 / 75 = 1039.9 px
- `+ spacing_after` 1000 HU = +13.3 px
- **vpos 기반 종료점 = 1053.2 px** (단 시작 기준)

알고리즘은 1112.6 px로 계산 → 59.4 px 추가 누적.

`h 합 + 갭 합` = 766.5 + 137.3 = 903.8 px → 단 시작점에서 누적된 콘텐츠 높이.

알고리즘 `used` = 1112.6 px → +208.8 px 추가 누적 (어디서?). 가능성:
1. **그림 tac=false (pi=21 ci=0)** — block image with text wrap. 38.4 px 갭이 여기서 발생. 알고리즘이 이미지 높이를 두 번 가산할 가능성.
2. **수식 다발 (pi=27의 9개 수식, pi=18의 7개 수식)** — 인라인 수식 다발이 누적 높이 계산을 부풀릴 가능성.
3. **trailing line_spacing 처리** — `paginate_text_lines` 의 trailing ls 제거 로직(`engine.rs:611-661`)이 일부 항목에서만 작동.

## 3. 가설 A 재검토

`[쪽나누기]` 처리 (`process_page_break` → `force_new_page`):
- B가 정정되면, 문제 6의 보기/답지가 페이지 1 우측 단에 안착.
