## 5. C — 이 방법으로는 측정 불가

`표1 [구역0:문단4]` 78행×5열, 셀 296개(78×5=390 → 병합 94개). 방문 셀 296 = info 296.
78행 전부 "복원" 되지만 **합계가 한글 5582.10 vs rhwp 4870.33 으로 −711.76px 벌어진다** —
복원값이 표를 한 번씩 덮지 못한다는 증거다.

원인은 복원 휴리스틱의 전제 붕괴다. 행높이를 "그 행에서 시작하는 셀들의 최소 높이" 로
잡는데, 이는 그 행에 rowspan=1 셀이 하나라도 있어야 성립한다. C 의 row 11 은 시작 셀이
전부 세로 병합이라 최소값이 671.36px 이고, 이는 rhwp row 11–17 의 합(671.3)과 같다.
따라서 C 의 큰 diff 10건 중 다수는 실측 차이가 아니라 **병합 잔재**다.

이슈 본문의 "한글 ≈24.3px vs 재합성 37.76px" 는 이번 실행으로 확인하지 못했다.
**후속**: rowspan 을 COM 에서 직접 읽거나(셀 ParameterSet), 셀별 (시작행, 높이) 집합에서
행높이를 연립으로 푸는 복원기가 필요하다. 합계 일치가 그 검증 게이트다.

## 6. 좌표계 — 러너북 정정

`--table-index`(한글 HeadCtrl 순번)와 `--pi`(rhwp 문단 인덱스)는 다르며, **HeadCtrl 순번은
문서 순서와 어긋난다**(중첩 표가 끼어든다). 실측으로 확정한 규칙:

> **한글 tbl 앵커 `GetAnchorPos(0)` 의 `List==0` 일 때 그 `Para` 값 == rhwp TABLE_DRIFT 의 `pi`.**

76076 상위 60개 표 기준 36 OK / 4 MISMATCH / 20 미해당(중첩 또는 drift 없음)으로 검증.
이 규칙을 도구에 넣어 `--pi` 하나로 양쪽을 같은 좌표에서 고르게 했다. `--table-index` 는
레거시 경로로만 남긴다.

MISMATCH 4건(pi 36/197/202/370)은 전부 **1×1 래퍼 표 안에 중첩 표**가 든 형태다.
한글은 바깥 표 1행을 보고, rhwp 는 같은 pi 로 안쪽 표(3/3/2/3행)를 보고한다 —
**중첩 표에 바깥 문단 pi 를 붙여 pi 가 충돌한다.** 도구는 info 행수 ≠ drift 행수인 표를
건너뛴다(B 에서 9개).

러너북 좌표 정정:

| | 러너북 | 실제 |
|---|---|---|
| A | `--table-index 0 --pi 0` | 맞음 |
| B | `--table-index 3 --pi 10` | **pi 10 은 존재하지 않음** — `--all` 로 대체 |
| C | `--table-index 0 --pi 0` | **`--pi 4`** (문서에 표 1개, 문단4) |
| D | `--table-index 63 --pi 763` | pi 763 맞음 |

## 7. 오라클 결함 3건 (수선함)

1. **표 진입 실패** — `SetPosBySet`+`FindCtrl` 은 표 앵커와 같은 문단에 누름틀(`%clk`)이나
   그림(`gso`)이 있으면 표가 아니라 그쪽을 잡는다. 36404953 은 `tbl@(0,0,16)` 옆에
   `%clk@(0,0,24)` 가 있어 FindCtrl 이 몇 번을 호출해도 `%clk` 만 반환하고 A 가 통째로
   실패했다. pyhwpx 의 `get_into_nth_table` 도 같은 경로라 함께 깨진다.
   → `hwp.select_ctrl(ctrl)` 로 컨트롤 객체를 직접 선택.
2. **침묵 폴백** — `--pi` 가 아무것도 못 맞히면 조용히 옛 `cut_rows=[...]` 표기의 **첫 줄**로
   폴백했다. 현행 바이너리에도 `cut_rows` 가 13개 남아 있어서, B 의 `--pi 10`(없는 pi)이
   **전혀 다른 표(pi 13, 31행)** 의 값으로 그럴듯한 대조표를 찍었다. n/a 보다 나쁜 실패다.
   → `--pi` 가 없으면 사용 가능한 pi 목록과 함께 죽는다.
3. **병합 셀을 행으로 셈** — `TableLowerCell` 순회는 세로 병합 셀을 한 행으로 세어
   병합 구간 합을 한 행 값으로 낸다(C: 실제 78행인데 31스텝, D: 75행인데 10스텝).
   → `goto_addr` 로 전 셀을 훑어 행별 최소 높이를 취한다. 방문 셀 수가 `rhwp info` 의
   셀 개수와 일치하는지, 복원 합이 rhwp 합과 맞는지가 검증 게이트다(A·D 통과, C 실패).

부수: 스윕 중 한컴이 죽는 경우(`RPC 서버를 사용할 수 없습니다`)가 있어 부분 결과를 살려
반환하도록 했다. 직전 실행의 COM 서버 잔재가 원인이면 `taskkill /F /IM Hwp.exe` 후 재시도로 풀린다.

## 9. 리눅스 후속 검증 (2026-08-13) — 8절의 판단 재료가 뒤집힘

Windows 측정 뒤 리눅스에서 5×2 축을 파다, **COM 행높이와 실제 조판·렌더가 이 문서에서
어긋난다**는 것이 드러났다. 4절의 "형태별 상수 결함 2건"은 렌더에 나타나지 않는다.

### 9.1 5×2 (+6.4px) — 렌더는 일치

`pi=71` 표를 한컴 2024 PDF(`samples/issue1891/76076_regulatory_analysis-2024.pdf`)의
가로 괘선으로 직접 측정했다. 텍스트 앵커(`경쟁영향평가점검항목`)로 같은 표임을 먼저 고정했다.

| | 행 피치 | 합 |
|---|---|---:|
| 한컴 PDF 괘선 | 34.85 / 31.00 / 31.01 / 31.16 / 31.01 | 159.03 |
| rhwp `mt_row_heights` | 34.85 / 31.08 / 31.08 / 31.08 / 31.08 | 159.17 |

차 **+0.14px**. COM 이 보고한 +6.4px 는 렌더에 없다.

### 9.2 1×1 (+3.8px) — 흐름은 이미 정확하고, 그 표는 무테두리

```
Table pi=160 ci=0  1x1  635.0x17.3px  wrap=TopAndBottom tac=false
```

- 표시/흐름 크기가 **선언 17.3px** 이다 — COM 17.4px 와 같다. 조판은 이미 한컴 정합.
- 21.09px 는 `mt_row_heights`(측정 경로)에만 있는 값이다.
- **누적 없음**: p17 에서 이 표 2개 아래 텍스트의 rhwp↔한컴 y 차가
  +0.6 / −0.5 / −0.6 / −0.6 / −0.5px 로 일정하고 쪽 꼬리(`-17-`)도 +0.4px.
  표당 3.8px 이 흐름에 들어갔다면 7.4px 이 누적돼야 한다.
- 그 자리에 **한컴 괘선이 없다** — 테두리 없는 레이아웃 표라 화면에 그려지는 것이 없다.

### 9.3 그래서 B 의 +163.8px 는 렌더 오차가 아니다

- 누적의 46%인 두 형태가 렌더에 나타나지 않는다.
- 76076 은 이미 82쪽 = 한컴 2024 PDF 82쪽이고, 82쪽 텍스트 매칭의 y 중앙 편차는
  상단 +0.16 / 중간 −1.86 / 하단 −1.74px 다.
- `mt_row_heights`(측정 중간값) ≠ 조판·렌더 값이며, 3-sum 오라클은 전자를 잰다.
  #2148 이 필요로 하는 것은 후자다.

### 9.4 방법론 정정 2건

1. **PDF 괘선은 테두리 있는 표만 잰다.** 무테두리 1×1 표는 측정 불가이고, 인접 표의 괘선을
   잘못 집으면 그럴듯한 오답이 나온다(첫 시도에서 23.17px 을 그렇게 얻었다).
   쪽·표 동일성은 **텍스트 앵커로 먼저 고정**한다.
2. **3절의 "PDF 괘선 = COM 실측" 은 범위를 좁혀야 한다** — 선언==렌더인 표에서만 성립한다.
   D 에서 둘이 맞은 것은 그 표가 그런 형상이었기 때문이다.

### 9.5 #2148 결론 (8절 대체)

- 원 재현 A: 완전 일치 — 클램프 불필요
- B 코호트: **렌더 기준 정합** — 측정 경로의 누적은 조판에 영향 없음
- 1×1 축: 8절이 지목한 `#1891 게이트의 비용`은 **비용 자체가 렌더에 없다**. 흐름이 이미
  선언을 쓰므로 게이트를 건드릴 이유가 없다
- **비사선 NO_LS 클램프는 착수 근거가 없다**

측정 경로와 조판 경로가 갈리는 것 자체는 별개 관심사다 — 진단이 프로덕션과 다른 값을
말하는 축(#4628)에 가깝다.
