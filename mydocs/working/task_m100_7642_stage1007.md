# 단계 1007 저장 쪽 경계의 실제 소유와 WMF 글꼴 이름 대조

Issue: #7642.

## 구현 전 원인 추적과 검증 계획

tracked visibility HWPX는 동일 원본과 독립 한컴 Print 6쪽에 대해 고정 base `a5e88ad682c805e1d845502ddc9521b94ea8eccd`는 6쪽, 현재 코드는 7쪽이다. 처음 다섯 쪽의 내용 분포는 같고 마지막 예산 표만 다음 쪽으로 밀렸다. 단계1003~1005의 실제 흐름 추적에서 6쪽은 재조판 문단93만 소비했는데, 문단94의 저장 되감김 판정은 이전 쪽의 문단92 저장 끝을 현재 흐름 끝과 대조했다. 숫자 일치가 같은 물리 쪽 소유를 입증하지 못한다.

공통 생산 경로는 저장 문단 끝 → `stored_rewind_boundary_matches_current_flow` → `stored_page_boundary_invalidated_by_reflow` 및 `whole_fit`의 덜 찬 쪽 경계 → 실제 쪽 분리다. 두 소비 지점에 현재 물리 frame의 `PageItem`을 전달하고, 저장 끝의 원본 소유 문단이 현재 frame에 포함될 때만 기존 위치 허용치를 적용한다. 명시적 쪽 나누기·충분히 찬 쪽의 기존 경계는 바꾸지 않는다. 같은 frame에서 저장 소유를 실제 소비한 정상 되감김은 유지해야 한다. 기존 #5169의 정확한 6쪽 검사를 바꾸지 않고 #6761·#7333·#6132 관련 경계 검사도 함께 실행한다. 부분 문단·표 소유는 기존 `PageItem`의 소유 인덱스를 사용하며, 단순 좌표 겹침으로 소유를 추측하지 않는다.

별도 WMF 경로에서는 본문이 쓰는 설치 글꼴 별칭을 SVG 그림만 누락했다. HWP3 sample16 18쪽의 그림 SVG는 `굴림체` 다음에 다른 family fallback을 넣지만, 실제 시스템의 해당 글꼴 family는 `GulimChe`다. 본문 renderer의 기존 설치 별칭 표를 WMF SVG 직렬화에서도 재사용한다. `LOGFONT` face → 원래 이름과 설치 별칭 → SVG font-family → Native/브라우저 glyph 선택 경로를 대조한다. 원래 이름·크기·굵기·문자열·그림 좌표와 일반 fallback 순서는 보존한다. 별칭이 없는 face는 그대로 둔다. 공개 WMF 재생 경로에 합성 글꼴 이름/문자 보존 계약을 추가하되 실물 시각 통과로 표현하지 않는다.

두 원인을 묶어 보정한 뒤 공유 target, 빌드 잡8로 한 번 빌드하고 관련 검사를 묶어서 확인한다. 이후 실제 원본의 전쪽 Native/fresh WASM TSV와 직접 확대 판독을 다시 수행한다. 새 실물 회귀 또는 기존 기대값 갱신은 전쪽 90% 이상 증거를 갖춘 뒤에만 처리한다. 최종 release WASM·전체 회귀·lint·base 하락 비교는 별도로 남아 있다.

## 수정 전 재현과 준비 검사

단계1008은 `a15420ceb`의 실제 공개 경로에 새 글꼴 이름 계약만 가져와 실행했다. 4건 중 별칭이 없는 Arial 대조군 1건은 통과했고, GulimChe 누락 1건 및 기존 #5169 6쪽 검사 2건은 각각 누락된 family와 실제 7/기대 6쪽으로 실패했다. 빌드 실패를 결함 검출로 계산하지 않았다.

초기 기본 작업 트리의 `cargo fmt --all`은 오래된 generated suite가 이미 제거된 파일을 참조해 실패했다. 원본 테스트를 되돌리거나 generated suite를 PR에 넣지 않고 review worktree에서 manifest를 준비했다. 이후 정식 fmt check는 새 테스트의 공백·줄바꿈 2곳을 검출해 실패했고, `c11717fe0`에서 포맷을 바로잡았다. 이 준비 실패를 검사 통과로 보고하지 않는다. 단계1009에서 fmt를 다시 통과하고 Native 빌드를 3분 55초에 완료했으며 관련 검사 묶음을 실행 중이다.

단계1007 시작 전에 upstream/devel을 다시 fetch한 결과 기준은 `a5e88ad682c805e1d845502ddc9521b94ea8eccd`로 같아 리베이스하지 않았다. 제출 직전에는 다시 확인한다.

별도 배포 문서의 파란 표 머리행은 아직 원인 미확정이다. 단계1010의 실제 parser dump에는 셀 border-fill 4~6이 Gradient로 남아 있다. 공개 셀 속성 API의 `fillType: none`은 해당 API가 gradient를 표현하지 않기 때문이며, 원본이 채우기 없음을 입증하지 않는다. 원본 이진 gradient는 흰색/연한 파랑, step255, 중심50, alpha0이다. 독립 Print의 흰 배경과 차이가 있으므로 점수 통과만으로 완료 처리하지 않는다. 이 조사에서 표 배경이나 gradient를 일괄 제거하지 않았다.

## 관련 검증 실행 결과

단계1009의 코드 `c11717fe0` 에서 관련 32건이 모두 통과했다. 실행 1.452초, 실패 0건이다. WMF 공유·원래 clip·글꼴 이름 계약 2건, Native mask 계약, 기존 #5169의 6쪽·내용 보존, #6761 정상/불일치 저장 경계, #7333 그림/표 경계, #6132 전체 구성을 포함한다. 기존의 정확한 6쪽 기대값은 바꾸지 않았다. 전체 회귀나 전쪽 Visual Sweep 완료는 아니다. 6개 문서 전체의 Native 재출력과 새 개발 WASM package 검증을 단계1011~1013에서 계속한다.

단계1012의 Native 전쪽 결과는 보고서 1쪽 96.80142%, HWP5 sample16 64쪽 최저 91.96350%, tracked visibility HWPX 6쪽 최저 90.28596%로 쪽수가 맞고 모두 90% 이상이다. tracked visibility의 실제 7→6쪽 회귀를 보정했다.
