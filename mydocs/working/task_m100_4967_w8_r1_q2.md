## 1. Q2 질문과 결론

Q1은 `문체부 바탕체`가 runtime에서도 unresolved이며 첫 divergence가 `layout-name`임을 확인했다. Q2는
그 이름을 가상으로 `MBatang`에 연결했을 때 현행 generated metric 또는 exact `MT.TTF hmtx`가 실제 조판
폭을 개선하는지 묻는다.

결론은 `no-change`다. name relation은 metric match metadata를 만들지만 공개 fixture의 base/final advance를
한 건도 바꾸지 않는다. exact source를 적용해도 같다. layout 이득이 없으므로 제품 alias를 추가하지 않고
W8-R1-Q3에도 진입하지 않는다.

## 3. exact source와 exhaustive domain

exact `MT.TTF`는 UPEM 1,000, cmap 2,356개다. layout-bearing codepoint는 Hangul 2,350개와 space 1개이고,
현행 entry와 advance mismatch가 0이다. 나머지 cmap 5개는 layout glyph 비교에서 제외한 control codepoint다.

| 영역 | current raw face | virtual `MBatang` | exact source |
| --- | ---: | ---: | ---: |
| Hangul | heuristic 1,000 | metric 1,000 | cmap 보유 2,350자 모두 1,000 |
| space | heuristic 500 | metric half-space 500 | 500 |
| 그 밖의 문자 | heuristic | metric miss 후 같은 heuristic | source miss면 virtual 결과 보존 |

generated metric은 exact cmap에 없는 Hangul 8,822자에도 1,000을 반환한다. 따라서 advance compatibility는
font identity·glyph identity나 source-exact lineage를 뜻하지 않는다.

이 비교는 특정 fixture나 private cohort보다 넓은 전체 layout-bearing 문자 영역을 닫는다. base advance가
같으면 ratio, letter spacing, justification additive spacing과 negative clamp의 결정 함수도 같은 값을 낸다.
그러므로 Q0의 22문서를 다시 열어 문자 목록을 만들 필요가 없고 bounded cohort 재parse는 0이다.
