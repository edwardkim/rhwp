## 결론

Rust selector는 이제 D3-C target의 두 leaf를 `CanvasKit`과 `CanvasKitBrowser`에서만
`verticalGlyphRun`으로 선택한다. Native Skia·SVG·Canvas2D는 기존 `TextRun` fallback을 유지한다. 허용은
backend 이름 하나가 아니라 provenance·variant·writing mode·orientation·direction·shape engine·portable
font 진단의 전체 tuple을 현재 객체의 capability로 판정한다.

bounded provenance가 붙은 run은 tuple 일부를 horizontal 값으로 바꿔도 일반 horizontal lane으로 우회하지
못한다. exact tuple이 아니면 writing-mode와 vertical-orientation authority가 닫힌 것으로 판정해 fallback한다.
generic vertical run의 기존 guard도 그대로 유지된다.

## 1. red-first

D3-C target 계약을 다음 기대값으로 먼저 바꿨다.

- CanvasKit·CanvasKitBrowser: leaf 2개 모두 `verticalGlyphRun`
- Native Skia·SVG·Canvas2D: leaf 2개 모두 `TextRun`
- wrong provenance·variant, sideways, horizontal tuple, glyph transform: 전부 `TextRun`

구현 전 첫 실행은 CanvasKit target이 여전히 fallback을 선택한 지점에서 실패했다. bounded helper 구현 뒤 같은
계약은 통과했다. Rust와 Studio 양쪽 문자열만 검사하는 기존 D4 source red는 Studio가 아직 닫혀 있으므로
의도대로 red를 유지한다.

## 2. 허용 tuple

다음 조건을 모두 만족해야 두 CanvasKit backend의 pending reason을 해제한다.

1. `boundedVerticalHwp5TableCellV1` + `verticalGlyphRun` + one-part non-fallback variant
2. run·shape key 모두 `vertical-rl`, orientation `vertical-upright`, transform 없음
3. run·shape key 모두 `ltr`, bidi 0
4. `rustybuzz-q4-vertical-v1`, fallback policy `none`
5. variation·synthetic style 없음
6. variant와 diagnostics 모두 exact, portable·strict, mismatch/missing/fallback-font 0
7. vertical resource requirement 세 개가 정확히 존재

그 뒤에도 기존 glyph count·position·advance·paint·font resource·digest·face·finite 상한 검사는 전부 실행된다.
