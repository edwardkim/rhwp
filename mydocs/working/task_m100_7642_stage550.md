# Issue #7642 단계 550: 동일 face 부분 글꼴의 cmap 누락 보정

- 수정 전 고정 source는 `e6c4d315b9`, 현재 리베이스 기준은 `d070e76ea5`다. 명령 helper 3건의 집중 회귀는 stage545에서 실제 실행 후 통과했다. 기대 문자열·장식 개수·내용 소유 검사를 완화하지 않았다.
- Native SVG가 공급한 `HyhwpEQ` 파일의 SHA-256은 `b37ad1f81dc6cd870569b8d7f368a2927874a8b6f0343a237c7d127209909e78`다. 이 파일에는 이탤릭 PUA는 있지만 `sqrt`와 피연산자의 정체 ASCII cmap가 없다. 시스템에는 부분 글꼴과 완전한 같은 regular face가 함께 등록되어 있었다. fontdb의 이름 조회만으로 부분 파일을 먼저 선택해 브라우저가 누락된 글자를 다른 face로 그렸다.
- 공식 설치 파일 `HYHWPEQ.TTF`는 SHA-256 `a3a3cd992a89ac38e7707b58143ebdb1da9511d3c462f019cda7f92c30467807`이며 해당 문자를 모두 공급한다. stage549의 진단에서 같은 입력·Print·Native binary에 이 설치 디렉터리만 명시해 출력했을 때 정체 획·세리프가 복구되었다. 전1쪽 일치율은 98.69218%다. 이 경로 지정은 원인 분리용 진단이며 운영 설정이나 font 예외가 아니다.
- 수정은 시스템 family 조회 결과와 실제 SVG 사용 문자의 cmap를 함께 확인한다. 선호 파일이 모두 공급하면 기존 순서를 유지한다. 누락되면 같은 family·굵기·style·stretch의 완전한 설치 face를 찾는다. 다른 face나 italic으로 바꾸지 않는다. 완전한 대안이 없으면 기존 파일을 유지해 기존 fallback 계약을 보존한다. 문서 ID·폰트명 전용 예외·좌표 보정은 추가하지 않았다.
- 소비 경로는 수식 SVG의 실제 문자 수집 → `generate_font_style`의 Full/Subset 파일 선택 → 시스템 face의 cmap 확인 → 같은 문자를 포함한 font bytes 전송 → 브라우저 출력이다. 글리프 배치·문자 내용·원본·Print PDF는 변경하지 않았다. 원본에 내장된 글꼴을 대체하는 경로도 변경하지 않았다.
- 자원 계약 검사는 프로젝트가 직접 생성한 `RHWPHostFixture-Regular.ttf`의 `A` cmap만 제거한 부분 대조군을 사용한다. 같은 regular의 전체 공급과 이미 공급되는 문자의 우선순위, italic·가짜 bold 거절을 검사한다. 사설 한컴 폰트는 커밋하지 않는다. 새 문서 배치 회귀로 합성 글꼴을 사용하는 것은 아니다.
- source unit 정책 검사는 신규 `cfg(test)` module을 금지해 최초 배치를 거절했다. 정책을 유지하고 검사를 `tests/cases/issue_7642_same_family_font_coverage.rs`로 옮겼다. 기존 사례와 같은 방식으로 생산 코드 모듈을 연결하며, 해당 원본만 module 통합 대상으로 등록했다. 새 standalone target이나 generated 파일을 커밋하지 않는다.
- 새 source의 Native/fresh WASM 출력·시각 확대 판독·lint·회귀 검증은 아직 미실행이다. stage549의 진단을 새 코드 head의 통과로 대신하지 않는다. 기존 55개 원본의 고정 source 검증도 계속 보존한다.
- HWP3 후보 stage535의 선택 1·3·33·64쪽은 각각 52.74476%, 90.86551%, 99.53366%, 97.97455%다. 33쪽의 빈 호스트 쪽 소속은 개선됐지만 1쪽은 미달이다. 후보는 현재 브랜치에 통합하지 않았다. 추가 dump에서 측정은 0번 문단의 42.7을 보존하는 반면 실제 배치가 다음 문단을 더 일찍 시작함을 확인했다. 측정 뒤 paint의 별도 원점·advance 분기를 추적 중이며 대표 쪽의 통과를 전64쪽 통과로 쓰지 않는다.
