# #7642 PDF 축소의 균일 RGB 손실을 독립 재현

## 측정과 해석

원본·기준 PDF와 RHWP 출력은 바꾸지 않았다. `a6a095c25f` Native 6쪽의 동일 PNG를
canonical Poppler PDF PNG와 비교하면 raw 89.06661%, 같은 PDF의 MuPDF raster에서는
98.15071%, PDFium에서는 98.21221%였다. 뒤의 두 값은 진단이며 정식 통과로 쓰지 않는다.

원본 PNG와 PDF의 1201×657 그림 자원에는 넓은 RGB 232 면이 있고,
Poppler의 `pdfimages -png`로 자원만 디코드해도 232가 유지된다.
JPEG 자원을 새 PDF에 그대로 옮겨도 축소 후 차이가 반복되어 본문·수식·다른 개체와 분리됐다.
처음 만든 64×64 상수 면의 확대 계약에서는 손실이 없어 JPEG decoder 결함으로
단정하지 않았다. 이어 실제 1201×657 원본 격자와 153.038×83.668pt 분수 배치의
독립 Flate RGB PDF로 축소 계약을 확인했다.

| 원본 RGB | Poppler 축소 | MuPDF 축소 | PDFium 축소 |
|---:|---:|---:|---:|
|0|0|0|0|
|64|63|64|64|
|128|127|128|128|
|192|191|192|192|
|231|230|231|231|
|232|231|232|232|
|233|232|233|233|
|255|254|255|255|

입력은 JPEG가 아닌 lossless RGB 상수 면이다. 같은 값으로만 된 내부 영역은 가중 평균
축소에서도 같은 값을 유지해야 한다. 특정 문서·임계값만 겨냥한 색 보정이 아니라
PDF raster의 균일색 보존 계약을 독립적으로 재현했다. 현재 raw 내용 경계가 231/232
사이에 있어 1단계 차이가 큰 수치 차이로 드러난다. 마스크나 원본을 바꾸지 않는다.

## 진행 상태

- `197f88e079a6cf823a73197b98c5337954e801f1`의 문단 앵커 보정은 별도 source다.
  고정 review worktree에서 stage2063 Native → 기존 마스크 검사 → stage2065 fresh WASM을
  공용 target으로 순차 빌드하며 stage2066에서 전쪽 재검증한다.
- 앞 source `a6a095c25f`의 Native·기존 마스크 2건·fresh WASM은 exit 0이다.
  해당 source의 전쪽과 새 source의 실행을 구분한다.
- 최신 devel `fe5725dc38`의 Native 55문서 queue는 종료됐고 fresh WASM queue는 진행 중이다.
  쪽수 불일치·측정 실패도 있어 55문서 통과라는 뜻이 아니다.
- stage2057의 앞 후보 부분 대조 96쪽에는 Native 10월 7·8쪽, 11월 9·15쪽 등
  0.01%p 이상 하락이 있다. 새 앵커 보정과 검증기 원인 확인 후 재대조해야 한다.
  이전 base의 전체 문서 최저값이 낮다는 이유로 개별 쪽의 하락을 상쇄하지 않는다.

PDF raster 교체는 아직 구현하지 않았다. 균일색·분수 축소·독립 Print 선의 검사와
provenance를 마련하고 양쪽 source의 전쪽을 같은 renderer로 다시 산출해야 한다.
기존 producer SHA·PNG 바이트가 확인되면 RHWP 재출력과 PDF 재출력은 분리해 재사용한다.
raw 수식·90%·98%·0.01%p 기준을 그대로 유지하며 새 진단 값으로 승인하지 않는다.
남은 WMF 색 전달·수식/간격 직접 판독·기존 Rust 실패와 최종 lint도 해결 전이다.

## 추가 실행 결과

`197f88e079` Native 빌드와 기존 마스크 2건이 exit 0이다. 10월 원본 HWP 8쪽은
89.97725%에서 98.02262%로 높아졌고 그림이 소유 줄과 맞는 위치로 돌아왔다.
stage2072의 공식 review·standalone overlay를 직접 열어 함께 제시했다.
6쪽은 canonical Poppler 기준 89.06661%이므로 문서 전체 통과가 아니며,
같은 source의 fresh WASM이 진행 중이라 98% 양쪽 조건의 px 회귀 자격도 아직 없다.

같은 Poppler의 Cairo 출력인 `pdftocairo -r 96 -png`도 stage2071 상수 면을
0·64·128·192·231·232·233·255 그대로 유지했다. 결과는 `cairo-contract.json`에 있다.
따라서 PDFium Python 의존성을 새로 넣지 않고도 기존 poppler-utils의 Cairo backend를
검토할 수 있다. 아직 Visual Sweep의 canonical 명령·provenance·테스트·문서는
바꾸지 않았다. 도입 시 전체/선택 쪽수와 분수 축소의 실제 상수 면 보존을 검사하고,
같은 renderer로 base/head를 재계산해야 한다. 원본 PNG·PDF와 raw 판정식은 유지한다.
