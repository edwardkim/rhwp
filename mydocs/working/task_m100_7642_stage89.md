## 생산 결과와 실제 소비 경로

1. `height_measurer.rs::measure_table_impl`은 실제 내용과 셀 행 선언에서 높이를
   구한다. 진단 `RHWP_DIAG_ROWH`에서 미주19의 모든 셀이 선언 안에 들어간다.
2. `notes/endnotes/flow_table.rs`가 이 측정을 미주 원장에 넣고 일반 표 format과
   block 경로로 방출한다.
3. `typeset/table.rs::fit_measured_for_host`는 빈 TopAndBottom 호스트도 개체 선언
   높이로 비례 조정하여 행별 저장 선언을 다시 키운다.
4. `layout/table_layout.rs::fit_row_heights_to_common_height`는 실제 paint에서
   개체 선언의 잔여를 마지막 행에 더한다. 같은 helper 결과를 소비한 것이 아니다.
5. `layout.rs`의 개체 원점 선택과 뒤 글줄의 `HeightCursor::vpos_adjust`가
   바깥 위·아래 여백, 저장 후속 줄 원점, 표의 실제 끝을 각각 소비한다.
   행 높이만 바꿔 뒤의 저장 원점 선택을 그대로 두어서는 해결을 입증할 수 없다.
6. `notes/endnotes/measure.rs`가 최종 layout 경로를 scratch로 재생하고,
   `paragraph/reflow_fit.rs::query_reflowed_endnote_new_head_fit`가 앞 미주의
   점유 끝과 미주 간격으로 문20 제목 수용 여부를 판정한다.

현재 Print는 문20 제목을 앞 단 하단에 남기며 본문은 다음 단에서 시작한다.
이전 Native는 제목까지 다음 단으로 넘긴다. 제목에 추가 허용치를 주거나
원점을 clamp하여 숨기지 않고 표·후속 줄이 소비하는 공통 프레임을 고친다.

## 구현·검증 계획

- 원본 저장 행이 실제 내용을 모두 담고 있고 개체 선언만 더 큰 경우의 행
  프레임을 공통 결과로 보존한다. 측정과 format·paint에서 다른 비율 조정을
  하지 않는다. 보호 크기·실제 행 성장·분할 프레임·저장 줄이 없는 재조판은
  자기 계약을 유지하며 판별 근거를 코드와 대조한다.
- 같은 프레임의 바깥 여백·실제 표 원점·점유 끝과 후속 줄의 시작을 fit과
  최종 배치가 함께 소비하게 한다. 다단 미주에서도 현재 단 원점으로 표현하며
  저장 좌표나 앞 단의 임시 원점을 다른 단에 이식하지 않는다.
- 네 실패 원본을 같은 Print PDF로 재검증하고 제목의 단 소속·후속 문단과
  표·그림의 누락·겹침·이월을 직접 판독한다. 90% 미만인 다른 선택 쪽의
  원인도 수용·예약·배치 경로에서 확인한다.
- 현재 변수·NOT·그리스·기존 미주 경계를 정상 대조군으로 유지한다.
  실제 행 성장 및 개체 높이가 필요한 표도 대조해 행 선언 보존을 일반화한다.
- 관련 모든 쪽의 Native/fresh WASM 90% 이상과 확대 판독을 확인한 뒤
  관계형 회귀를 추가·변경한다. 전체 원본 55개/853쪽과 기존 91파일,
  #1139 전체 함수의 범위를 유지한다. 전체 게이트·PR은 아직 완료하지 않았다.

## 저장 프레임의 닫힘과 추가 실패 범위

원본 HWPX와 원본 HWP의 RHWP 파싱·직렬화 진단을 각각 읽어 미주19의
표 앵커 10177HU, 다음 문단 원점 14514HU를 확인했다.
`10177 + 3771 + 283 + 283 = 14514`로 원본 바깥 상자가 정확히 닫힌다.
행 선언 합 3546HU를 사용하는 본체의 바깥 상자는 14289HU에서 닫힌다.
따라서 차이는 화면 위치 상수가 아닌 본체의 225HU다.
`all20-independent-source-frame-closure.json`에 두 입력 해시와 계산을 보존했다.

실제 측정 로그의 18개 셀은 모두 선언과 요구가 일치하며 내용이 자라지 않았다.
format은 비례 배분으로 세 행을 모두 늘리고 paint는 마지막 행을 늘린다.
기존 `stored_empty_control_table_frame`의 닫힘 검증을 재사용한 뒤 실제 본체와
현재 단 원점으로 프레임을 투영하는 후보를 ignored output에 준비했다.
후속 줄의 저장 기준도 동일한 확정 원점을 이어받도록 소비 경로를 검토한다.
표 높이만 바꾼 상태를 해결로 판정하지 않는다.

Native 선택 쪽 결과가 끝난 두 원본의 판정은 다음과 같다.

| 입력 | 13쪽 | 16쪽 | 17쪽 | 19쪽 | 20쪽 | 21쪽 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `미주사이20/구분선아래2.hwp` | 65.98698% | 53.79032% | 48.83636% | 98.41256% | 98.05970% | 97.53137% |
| 같은 `.hwpx` | 65.98698% | 53.79032% | 48.83636% | 59.81066% | 28.96275% | 40.53802% |

두 문서 모두 실제 22쪽으로 기준 PDF와 쪽수가 같다. HWPX 20쪽은 앞 문항의
풀이가 다음 쪽에 남아 문23 이하와 오른쪽 그림·본문이 밀린다. HWP의 16/17쪽도
단 이월의 내용과 시작 줄 차이가 이어진다. 세 쪽의 새 review PNG를 직접 열어
확인했으며, 첫 표 경계의 보정이 이 차이까지 해소하는지 수정 후 다시 확인한다.
HWP의 뒤쪽 통과를 HWPX의 증거로 대신하지 않는다.

## 공통 후보 적용

Stage 88의 fresh WASM 빌드는 exit 0으로 종료했고 소요 시간은 1292.16초다.
고정 패키지의 JS/WASM 해시와 Studio public의 일치를 확인한 뒤 이 후보를 적용했다.
Stage 88의 선택 쪽 WASM은 그 고정 패키지로 계속 검증하며 이후 코드 결과와 구분한다.

`table_row_frame`은 실제 측정과 원본 행 선언이 일치하는 저장 표의 본체를
보존하고, 원본 바깥 상자의 닫힘 검증을 재사용해 후속 줄 원점을 투영한다.
format의 균등 확대와 paint의 마지막 행 확대는 같은 판별 결과로 건너뛴다.
미주 흐름 표가 현재 단에 통째 방출된 경우만 본체·바깥 여백·후속 줄의 프레임을
공유 원장에 넣는다. 분할·이월된 조각의 소유 원점은 기존 표 경로에 남긴다.

후속 문단은 앞 항목이 실제 Table이고 같은 소유자의 바로 다음 문단에서
시작할 때 그 확정 원점을 소비한다. 기존 완성 미주 경계와 함께
`HeightCursor::owned_paragraph_origin`으로 연결해 저장 vpos 기준도 같은
원점으로 재연결한다. 뒤에서 오래된 좌표로 다시 덮어쓰지 않게 한다.

교정된 source `9605623089dd2540e63abc3782efa129351a2fc3`에서 fmt,
Native Clippy, WASM Clippy, Skia check가 모두 exit 0으로 종료했다.
`stage89-table-row-frame-type-checks.json`에 실행 명령과 source 파일 해시를
보존했다. 실제 재출력과 전체 검증은 아직 미완료이며, 정식 회귀·기대값은
바꾸지 않았다. 이 네 결과를 workspace 전체 lint나 전체 회귀의 통과로
대신하지 않는다.

첫 Native Clippy는 새 원점 필드의 section cursor 초기화와 단위 변환 함수
import 누락으로 실패했다. 두 연결을 교정하고 기존 실패 receipt·로그를
`stage89-*-attempt1`에 보존했다. 이 컴파일 실패는 조판 결함의 수정 전 FAIL
증거로 세지 않는다. 교정된 source에서 lint 묶음을 다시 실행한다.
Stage 88의 fresh WASM이 생성한 Canvas `lineJoin`·`miterLimit` import도
`rhwp-studio/public/rhwp.js`에 함께 보존한다.

## 선택 쪽 검증의 반복 조판 비용

기존 Native 검증은 선택 쪽마다 render tree를 산출하면서 같은 문서를 반복
조판했다. 검증용 ignored adapter에서 tree 전체를 한 번 산출한 뒤 선택 쪽만
기존 비교 입력에 복사한다. SVG 렌더, PDF 래스터, 실루엣 계산과 gate는
정본 도구를 그대로 사용한다. `scripts/visual_sweep.py`는 수정하지 않았다.

Stage 88의 고정 Native 실행 파일과 원본 all-20에서 13·16·17·19·20·21쪽의
개별 산출 tree와 한 번에 산출한 tree의 SHA-256 및 JSON이 모두 같음을
실제로 확인했다. `stage89-tree-batch-equivalence/receipt.json`에 그 결과와
명령을 보존했다. 이는 산출 방법의 동일성 근거이며 현재 후보의 시각 통과
근거가 아니다. 새 후보는 별도로 다시 렌더한다.

현재 후보의 선택 검증은 네 실패 원본을 먼저 처리하고 변수·미주 대조군을
포함한 37개 입력·97개 선택 쪽을 유지한다. 준비 스크립트의 변수 대조군
경로 오기를 실행 전에 교정했다. 실제 원본 전체 55개·853쪽과 기존 91개
테스트 파일의 범위는 줄이지 않는다.
