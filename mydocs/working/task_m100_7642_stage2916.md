# #7642 저장된 표 전용 줄의 앵커와 물리 점유 계획

Issue: #7642. 수정 전 생산 소스는0a6ada2b이며 현재 문서 head는bb5af07013이다.

## 독립 저장 정보에서 확인한 규칙

정확한 #5566 생성 입력을 그대로 Print한 PDF는 stage2911에 유지한다. 별도로
같은 입력을 한컴2020에서 HWP로 저장해 **메타데이터 검사만** 수행했다.
stage2915의 저장 HWP를 `rhwp export-hwpx --verify`로 읽기 전용 조사했으며,
두 건 모두 재파싱 검증 종료 코드0이다. 첫 시도의 `convert`는 HWP 출력 전용
명령이라 확장자 오류로 거부됐고 산출물이 없었다. PDF를 RHWP로 만든 것은 아니다.

| 저장 줄 | 원래 입력 vpos | 한컴 저장 vpos(offset0) | 한컴 저장 vpos(offset1904) |
| --- | ---: | ---: | ---: |
| 문단3 제목 textpos0 | 8620 | 8620 | 8620 |
| 문단3 표 슬롯 textpos7 | 11500 | 19192 | 21096 |
| 뒤 본문 문단4 | 20572 | 28264 | 30168 |

제목 줄은 높이1800·뒤 간격1080HU를 가진다. 표 슬롯 줄은 높이7692·뒤 간격
1080HU를 가진다. 표 자체7126HU와 위아래 바깥 여백283HU씩의 합이7692HU다.
한컴 저장본에서도 이 물리 슬롯 높이는 유지된다. 가시 문자열이 없다는 이유로
빈 줄의 점유를24px 글자 높이로 다시 만들거나 삭제하면 안 된다.

표의 앵커는 앞 제목 줄의 끝이다. 표 슬롯의 최종 텍스트 줄은 어울림 배제 영역
뒤로 이동한다. 따라서 최종 슬롯 줄 vpos를 표의 원점으로 다시 쓰면 표 높이를
두 번 전진한다. 같은 물리 프레임이 앞 제목 줄, 표·바깥여백의 배제 영역,
표 슬롯 줄의 높이·뒤 간격을 순서대로 확정해야 한다. 이 결과가 독립 Print의
표 시작과 뒤 본문의 움직임을 함께 설명한다.

## 변경할 생산·소비 연결

`inline_flow::plan_square_table_host`는 현재 원본 저장 줄을 지우고 표를 문단
시작에 놓은 뒤 문자열만 재채움한다. 저장 표 전용 줄이 있는 경우에는 원문
제어 위치·앞 텍스트 줄·슬롯 높이를 먼저 검증하고 `LayoutFrame`에서 한 번
계획한다. 문서 ID·고정 px·특정 offset 값으로 대상을 고르지 않는다.

해당 계획의 줄·끝 높이·표 원점·배제 영역은 기존 경로를 공유한다.

1. `FormattedParagraph::use_square_host_plan`: 같은 줄 메트릭과 요구 높이.
2. typeset의 `record_square_host_flow`: 같은 점유 끝·배제 영역·표 배치 기록.
3. layout의 해당 plan 소비: 같은 본문 줄과 `paragraph_float_placements`의
   표 원점을 사용하고 legacy fallback에서 다시 앵커를 선택하지 않는다.

기존 오른쪽 다줄 어울림, 원문 저장 폭이 현재 단과 다른 경우, 빈 host,
실제 표 성장, 복수 흐름 개체 등은 이 저장 슬롯 계약으로 입증되지 않는다.
새 경로를 적용하지 않고 기존 소유자가 처리한다. 적용 경계는 원문의 한 흐름
표가 마지막 저장 줄을 소유하고, 앞 가시 줄과 실제 폭·측정 높이가 일치하는
경우다. 원문 슬롯이 아직 배제 전 원점이거나 이미 배제 후 원점인지도 같은
프레임 결과로 대조한다. 앞 텍스트 줄을 새 배제 영역이 이동시키면 수용하지 않는다.

## 검증 계획과 현재 상태

Native 빌드 잡8개·공용 target/pr-review로 정확한 두 입력의3쪽을 먼저 대조한다.
본문·표 순서와 마지막 쪽 제목 소속을 직접 판독하고, #7969 대조군과 정상
저장 슬롯·오른쪽 어울림 경계를 확인한다. 방향이 맞은 뒤 fresh WASM과 전쪽
base 비교를 이어간다. 새 정식 회귀는 두 원본의 전쪽90% 및 확대 판독 전에는
등록하지 않는다. 현재는 계획과 독립 근거이며 구현·통과를 미리 선언하지 않는다.
