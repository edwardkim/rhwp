# 단계 1106 PUA 표시와 원본 문자 경계의 공통 폭

Issue: #7642. 수정 전 source는 `39f6c3456`이며 기준 devel은 `a5e88ad682c805e1d845502ddc9521b94ea8eccd`다.

## 실행으로 확인한 원인

단계1095의 집중65건은 통과했고 Native11문서245쪽 측정도 끝났다. HWP3 19쪽88.60821%, HWPX25쪽89.98669%가 미달이다. 마지막 음수 자간을 보정했다고 시각 검증 완료로 기록하지 않는다.

HWPX25쪽 문단474의 원본은 `U+F03C5` 체크박스로 시작한다. 독립 Print의 해당 글꼴은 Haansoft Batang이며 글리프 advance는1024/1024em이다. 현재 표시 경로는 이미 검증된 공통 PUA 표에 따라 `□`를 출력한다. 그러나 scalar 측정은 원시 PUA를 표에서 못 찾아 반각으로 재며, 같은 원본 기호 런의 공개 charX 끝15.4와 실제 bbox23.0이 갈린다. 공개 API 후보 `verified_pua_marker_character_boundaries_cover_the_emitted_run`은 단계1105에서 이 원인으로 FAIL했다. 고정 좌표의 기대값이 아니라 같은 방출 런의 문자 경계와 점유 관계를 검사했다. 후보는 아직 review worktree에만 있다.

실제 Native 글꼴 선택도 관측했다. 한글741자는 설치 휴먼명조, 영문90자는 설치 Palatino Linotype을 사용한다. PDF의 휴먼명조179개 고유 글리프와 설치 HMKMM.TTF는 em512·advance·분해한 윤곽 명령이 모두 같다(단계1098). 글꼴이 설치되지 않았다는 가정으로 줄 나눔 차이를 면제하지 않는다. 로드 시 생성한 줄과 같은 줄간격160%를 공개 API로 다시 적용한 줄은 모두 UTF-16 시작0/48/92로 같았다. 캐시 재사용만의 결함이라는 가설은 이 실행으로 확인되지 않았다.

## 수정 범위와 소비

공통 paint의 기존 PUA 정규화·검증된 표시 표·일반 텍스트 표시 여부에서 정확히 한 scalar로 대응하는 값을 읽는다. 이 대응만 공통 `char_width_decision`에 전달한다. 원문·UTF-16 소유·문자 수를 바꾸지 않고 문자별 전진만 실제 표시와 같게 만든다. 숨기는 filler, 여러 scalar로 확장되는 표기, 글자겹침 숫자, 미등록 PUA, 옛한글의 별도 cluster 계약은 기존 경로를 유지한다. 새 기호 매핑이나 글꼴 치환 표는 추가하지 않는다.

소비 경로는 `공통 PUA 표시 투영 → char_width_decision → unrounded token 폭/Frame fit 및 공개 charX → 런 bbox/Native·WASM paint`다. 표시 후 다음 본문을 따로 이동하거나 원시 문자열의 길이를 줄여 맞추지 않는다. 기존 문자 경계와 표면 표를 유지한 채 측정의 가정을 수정한다.

## 검증

공개 문자 경계 후보의 수정 전 FAIL/수정 후 결과와 기존 집중 대조군, HWP3/HWP5/HWPX 및 실제 실패 입력11문서245쪽을 한 번에 대조한다. 이후 전체55문서853쪽 Native/fresh WASM과 실제 base 비교·전체 회귀·lint가 남는다. 원본의90% 미달이 해소되기 전에 새 실물 회귀나 baseline을 정식 추가하지 않는다.

MCP의 추가 합성 Print job `a2492590-4fec-4e6d-9cd9-45fdda8e328c`는 별도 대기 중이다. 요청은 PDF/engine2020/Print이며 HWPX 저장 변환으로 대신하지 않았다. 원래 두 독립 Print는 현재 원인 분석에 계속 사용한다.
