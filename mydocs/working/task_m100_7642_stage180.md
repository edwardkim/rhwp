# #7642 Stage 180 — 수식 줄의 페이지 경계 예약 검증

Issue: #7642

## 근거와 계획

Stage 179 원 카탈로그 18쪽 Print에는 `DMATRIX{ROOT 2 & 0 # 0 & ROOT 3}`이 맨 위에 있고 Native에는 17쪽 마지막에 있다. 마지막 줄의 표시 상자만 수용하는 경우와 추가 leading까지 수용하는 경우를 구분한다. 현재 관측은 원인 확정이 아니며 상수나 문서 ID로 페이지를 밀지 않는다.

독립 한컴 정상 저장본의 구역·스타일을 재사용해 `x` 다음에 같은 DMATRIX를 둔 최소 문서를 만든다. 본문 예산을 낮음 / 표시 상자만 fit / 전체 전진 fit의 세 범위로 바꾸고, 원래 용지와 나머지 설정은 보존한다. 저장 수식 크기·baseline·LineSeg를 직접 맞추지 않고 한컴 2020의 정상 저장과 Print로 재발행한다. 입력 생성 경로·세 예산·출력 job 및 SHA를 기록한다. 이 문서는 페이지 경계 가설을 판별하는 진단 입력이며 정식 회귀 fixture가 아니다.

실제 경로는 `composition의 수식 줄 상자·간격 → height_measurer의 line_heights/line_spacings·total_height → pagination의 전체 문단 fit와 줄 분할/overflow → format_paragraph의 실제 전진`을 추적한다. 높이·예산·소유를 같은 결과로 소비하는지 확인한다. 독립 Print가 마지막 leading을 어떻게 취급하는지 확인하기 전에는 구현을 변경하지 않는다. 앞뒤 수식의 누락·중복과 쪽 소속을 함께 판독한다. 사전 테스트와 후속 빌드는 고정 `/home/tsjang/rhwp/target/pr-review`만 사용한다.

## 독립 Print와 Native 페이지 소속 결과

정상 입력 low / middle / high의 본문 예산은 각각 5700 / 6225 / 6750 HWPUNIT이다. 실제 한컴 2020 Print의 쪽수는 2 / 1 / 1, 코드 `785c2821c7276a506b635e16e6c5b53c3daf53ce` Native render tree도 2 / 1 / 1이다. 첫 수식의 상자·줄간격 다음에 DMATRIX를 배치했으며 세 예산에서 두 수식의 소속은 일치한다. 마지막 leading 가설은 이 대조군에서 입증되지 않았으므로 pagination에 보정을 넣지 않는다. 실제 시각 90%는 아직 측정하지 않았고 관계형 정식 회귀도 추가하지 않았다. 입력·정상 저장 HWP·독립 Print PDF와 job/SHA는 `pdf/issue7642-page-budget-diagnostic/README.md`에 보존했다.

입력 작성 도구의 ZIP metadata 재사용 오류로 첫 middle 작업이 실패했다. metadata를 복사하여 출력하고 모든 CRC를 확인한 뒤 middle과 미실행 high만 재산출했다. 성공한 low 입력 SHA는 그대로이고 해당 remote job은 반복하지 않았다. 작성 도구 실패를 엔진 회귀 재현으로 보고하지 않는다.

원 카탈로그의 14쪽 확대에서는 긴 EQALIGN 왼쪽 항 폭에 따라 짧은 앞 행의 원점도 밀리는 차이를 확인했다. 현재 `layout_aligned_rows`의 최대 왼쪽 폭 소비를 독립 Print의 행별 정렬 원점과 대조한다. 이것과 누적 줄 높이를 분리해 추적하며, 원인 확정 전에는 구현·기대값을 바꾸지 않는다. Stage 179의 fresh WASM 빌드·전체 36쪽 TSV는 계속 진행 중이다.
