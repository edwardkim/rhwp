# Issue #7642 단계 628: 한점 리더의 원본 기호 슬롯 복원

- source `0083c6a01dfc7eb2d63ff688c9048c3b64402fee`의 월간 수출입 원본 Native 전19쪽은 최저86.62049%, 미달은6쪽이다. 같은 원본/독립 engine2020 PDF의 stage610/616 결과를 사용했고 review를 직접 표시했다.
- 6쪽 문단111 첫 하이픈/단어가 Print보다 오른쪽으로 밀린 현상에서 앞 공백 정렬 배분을 먼저 의심했으나, 구분점의 원래 폭 누락을 확인했다. 앞 공백 제외나 정렬 slack 공식을 변경하지 않는다.
- Native 첫 줄의 U+2024 점→다음 글자 전진은7.92pt이고 Print는15.84pt다. PDF 기호 font `T24`는 Type3, FontMatrix0.001, Widths[1000], ToUnicode U+2024이며 원래1em 전진이다. 고유 폰트 바이트·윤곽선은 코드에 넣지 않았다.
- 원본 HWP DocInfo에서 charshape259/260/326의 한글 슬롯은 휴먼명조(type1), 기호 슬롯5는 한양신명조(type2)임을 확인했다. 실제 Trace는 U+2024를 한글 슬롯0으로 보내며 휴먼명조의 `characterMatch=miss`, `heuristicHalfwidth`를 소비했다. PDF는 원본 HFT 기호로 출력한다.
- `detect_lang_category`의 기존 주석도 U+2024의 기호 슬롯 근거를 기록했지만 match에 해당 글자가 없었다. U+2024만 슬롯5로 복원했다. 굽은 따옴표의 영문 슬롯, 다른 구두점/한글·ASCII/공백, HFT 대체·fallback 계약은 유지한다.
- 분류 → stored/reflow run의 `lang_index` → 해당 슬롯 face·ratio·spacing·HFT 전각 표식 → 공통 폭/정렬 → 실제 glyph/advance의 경로를 대조했다. 문서 ID·고정 위치·폭 수치나 글꼴 이름으로 예외를 추가하지 않았다. 새 source의 전19쪽 Native/fresh WASM·확대 판독과 기호 슬롯이 다른 정상 대조군은 아직 미검증이다.
- 진단 데이터는 ignored stage623~627의 원본 문단 dump·SVG/PDF 원점·PDF Widths/ToUnicode·font trace·raw charshape 슬롯에 보존했다. 기존 정확한 FontTrace 기대값을 갱신하지 않았고 source4533 기반 q 진단과 source0083의 실제 렌더 결과를 구분한다.
