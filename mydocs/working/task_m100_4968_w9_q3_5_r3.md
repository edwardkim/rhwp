## 1. 결론

Q2 capability boundary에서 이미 생성·검증하던 synthetic GPOS face를 1,236 bytes의
`RHWPExactKerningSmoke.ttf`로 materialize했다. fixture는 원본 glyph와 metadata로 구성되고 저장소 MIT
라이선스를 적용한다. 생성기, 인접 라이선스 문서, 고정 SHA-256으로 provenance를 재현할 수 있다.

동일 integration 원본의 target-neutral test를 native와 Node wasm-bindgen runner에서 실제 실행했다. 두
환경은 같은 fixture bytes, exact handle, borrowed provider, `KerningSourceSession`, pair engine을 사용하며
`AV To WA HH`에 동일한 -120 design units를 냈다.

Noto Sans KR 2.52 MiB face는 Q2의 실제 OpenType truth와 digest 증거로 유지한다. 새 자동 parity fixture는
Noto를 제품 core에 등록하거나 이름으로 선택하지 않는다. Docker WASM은 R2와 byte-exact이며 fixture 이름과
SHA도 binary에 존재하지 않는다.

고정 fontTools 환경으로 재현할 수 있으며 현재 환경의 재생성도 같은 SHA를 냈다.

## 3. native/WASM 동일 경계

기존 `tests/cases/issue_4968_kerning_capability_provider.rs`에 target-neutral test 하나를 추가했다.

1. 추적 fixture bytes에서 exact source handle을 식별한다.
2. expected size와 SHA-256을 확인한다.
3. borrowed provider를 `KerningSourceSession`에 연결한다.
4. capability가 `gpos-kern`인지 확인한다.
5. 같은 pair engine으로 `AV To WA HH` 후보를 계산한다.
6. 합계 -120 DU와 fallback 부재를 확인한다.

native에서는 표준 `#[test]`, wasm32에서는 `#[wasm_bindgen_test]`로 같은 함수 본문을 실행한다. target별 font
선택이나 pair 상수 분기는 없다. 이 단계는 host가 제공한 exact bytes를 R1/R2 계약으로 소비할 수 있음을
검증하지만, 아직 제품 font registry나 measurement positions에는 연결하지 않는다.

## 4. fixture CI 생명주기

새 생성기 변경이 unclassified full fallback에 의존하지 않도록 다음 세 경로를 동기화했다.

- `scripts/ci-impact-classifier.cjs` render tool 분류
- `scripts/ci-impact-policy.cjs` Render Diff trigger 정본

첫 정책 검사에서 policy와 workflow trigger 불일치를 잡았고, 실제 workflow path를 추가한 후 관련 Node 정책
검사 65건이 전항 통과했다. generator만 바뀔 때 Rust lane을 과도하게 켜지 않고 render/native 검증을
선택하는 기존 fixture generator 정책을 그대로 따른다. 추적 TTF 자체가 바뀌면 기존 font fixture 규칙에 따라
Rust와 render/native 검증을 모두 수행한다.
