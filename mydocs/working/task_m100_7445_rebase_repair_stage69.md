# Stage69: 비정수 그림 축소의 원본 면적 소유 복구

Issue: #7445. 기존 frozen inventory의 로드맵(item32), PrEP(item25), RowBreak(item55/56)만 검증했다. 새 HWP 보정 대상을 추가하지 않았다. 부모 HEAD는 `65fdd7926795f09d3b5b388a75d40e9186bbc242`다.

## 원인과 공통 소비

`PagePaintContext::image_frame`이 발행한 최종 그림 사각형은 독립 Print의 사각형과 대응했다. 로드맵 153쪽은 Native `121.374723,146.559673,558.739501,430.089510px`, PDF `91.031,109.920~510.086,432.487pt`다. 원본 BMP와 PDF의 DCT 자원은 같은 1000×514 그림이지만 압축 색상 차이가 있다. 같은 원본을 engine2020/timeout1800/Print0으로 다시 인쇄한 독립 302쪽에서도 153쪽 content stream·JPEG bytes·사각형이 같았다. 기준 PDF를 교체하지 않았다.

문제는 공통 `prepare_bitmap`의 불투명 Print 축소가 원본 픽셀을 바닥 정수 경계 한 구간에만 배정하던 것이다. 장치 픽셀이 원본 픽셀의 일부를 덮는 경우 경계의 기여가 빠져 가는 선과 점의 농도가 달라졌다. 두 축의 교차 면적을 공통 정수 격자의 비율로 적분하고 축별 양자화를 같은 순서로 적용한다. 가중치 목록을 대량 저장하지 않는 순회자로 바꿔 큰 그림의 임시 할당도 줄였다.

`최종 paint 사각형 → bitmap_raster → Skia/WebCanvas/CanvasKit의 1:1 재생` 소비를 유지한다. source/layout/paint 좌표, JPEG bytes, 글꼴, 색상 임계값, DPI, 마스크를 바꾸지 않았다. 투명 premultiplied 적분·HighQuality·crop·rotation·nearest 및 한컴2024 장치 재구성 경로도 변경하지 않았다. 이 범위의 실제 대조는 아래 기존 그림 회귀로 확인했다.

## 진단 한계와 실패 보존

기존 합성 C352/C354/C356을 canonical PDFium으로 다시 산출했다. Native는 각각 93.60106 → 100%, 99.94993 → 94.57727%, 34.61881 → 42.89522%다. C354 하락과 C356 미달이 남아 있어 세 대조군 전체 통과로 주장하지 않는다. 고정 devel Native에서도 같은 세 입력을 다시 산출해 91.58691/98.85995/33.33810%를 확인했다. C354는 devel 대비 **4.28268%p 하락**하므로 새 2%p 기준으로 재검토 대상이며, 로드맵의 개선으로 상쇄하지 않는다. C356의 첫 그림 회색 행은 면적 적분과 대응하지만 다른 소수 원점의 캔버스 투영은 추가 진단 대상이다. 이 합성 입력을 새 완료 회귀 fixture로 등록하지 않았다. JPEG q41·PDF 자원·반올림 경계·필터 교체 그림은 ignored 진단이며 제품이나 기준으로 사용하지 않았다.

제가 빌드 완료 전에 집중 드라이버를 호출한 실행은 `nativeSha256` 미완성으로 캡처 전에 실패했다. 빌드 성공·해시 고정 뒤 다시 실행했다. 임시 진단의 PDF 단일 쪽 이름과 상대 부모 경로 오류도 정정했고 실패를 통과로 인용하지 않았다. 제품 소스에 임시 eprintln이나 테스트 전용 API를 추가하지 않았다.
