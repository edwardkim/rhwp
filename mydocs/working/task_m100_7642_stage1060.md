# 단계 1060 인라인 표 뒤 문단 위 간격의 소유

Issue: #7642. 이전 생산 source는 `80e557f46a9a2a56038dc57b7572612f9dbe795d`다.

## 근거와 실제 경로

HWP3 sample16 35쪽 캡션 문단602의 괘선은 독립 Print와 맞지만 후속 표603만 약 7.4px 위다. 원본 위 간격은 흐름 단위 568HU이며 한컴 저장본도 같은 줄 시작11128HU를 보존한다. 독립 Print의 표603 윗변은225.673px, Native는218.3px다. 점수83.01067%로 미달이며 실물 회귀 기대값을 갱신하지 않는다.

실제 소비 경로는 `host_spacing::resolve.before` → typeset 표 전체 예산 → FullParagraph의 인라인 캡션 배치 결과 → `prev_tac_seg_applied` → `layout_table_item`의 before 분기다. typeset는 위 간격을 포함해 표 끝을 계산하지만, 인라인 캡션은 실제 저장 원점을 적용하지 않은 계산 줄 끝을 반환하면서도 `applied_tac_segment=true`를 반환한다. 다음 표는 이 값을 저장 원점이 이미 소비됐다는 의미로 읽어 자기 위 간격을 생략한다. 실제 paint 종료와 typeset 종료도568HU만큼 갈라진다.

수정은 인라인 계산 줄 끝과 실제 저장 사다리 원점 적용을 구별한다. 저장 target을 수용한 분기에서만 해당 플래그를 반환한다. 포맷·문서명·문단 번호 조건을 추가하지 않는다. 저장 사다리에서 확정한 기존 원점 계약은 유지하고, 일반 계산 끝 뒤의 다음 문단은 자기 before를 소비한다.

## 반례와 수정 전 실행

기존 합성 HWP3 빌더로 작은 인라인 캡션과 뒤의 블록 표를 구성했다. 뒤 문단의 원본 위 간격만0→100/1800인치로 바꾸면 앞 캡션·뒤 표 높이·내용은 유지되고 뒤 표의 원점만 그 간격만큼 이동해야 한다. 새 함수명 `inline_caption_preserves_the_following_table_paragraphs_own_spacing`으로 내용 보존·같은 쪽 소속·상대 이동을 검사한다. 실물 문서의 절대 픽셀 좌표를 고정하지 않는다.

정상 수정 전 실행은 실제 두 경우 모두 BODY y=29.3333으로 같아 의도한 원인으로 실패했다. 최초 작업 경로 착오로0건 선택된 실행은 재현 증거가 아니며 같은 로그를 정상 실행으로 교체했다. source80e의 `stage1060-inline-before-test.log`에 실제1건 FAIL이 있다. 수정 후 공개 배치 경로 검사와 같은 원본 전쪽 sweep을 수행한 뒤 판정한다. 원본35쪽이 아직 미달이므로 실물 golden·새 px 핀은 추가하지 않는다.

원인 플래그는 upstream의 `7eddd19da6`(#6101)에서 도입됐다. 그 수정의 실제 대조군인 `issue_6101_block_tac_table_text_order`도 이번 검사에 포함한다. 계산 줄 끝 뒤 문단 위 간격을 소비하는 경로와 실제 저장 target을 수용하는 기존 경로를 구분해 확인한다.

## 실제 검증 결과와 합성 입력 정정

source `bc66c8a88392550330fb45421e3061dc725c2b8c`의 Native 전쪽 재산출(단계1062)은 HWP3 35쪽을83.01067→92.22059%로 개선했다. 전체64쪽의 미달은19쪽88.56619% 한 쪽이며, 새35쪽 review를 직접 열어 캡션·본문 표의 원점과 그림 상단을 대조했다. 그림 내부 글꼴의 차이는 남아 있으며 전체 완료를 의미하지 않는다. 나머지5개 대조군의 Native 최저값은 유지됐다.

단계1061은63건 중62건 통과, 새 합성1건 실패였다. 이 입력은 기존 parser 전용 빌더의0 크기 용지를 그대로 사용해 의도한 인라인/블록 경계를 구성하지 못했다. 테스트를 약화하지 않고 유효한 원본 용지 크기와 블록 너비를 주고, parser가 실제 before를 읽었는지도 확인하도록 정정했다. 정정 입력은 현재 공개 배치 경로에서 통과했다. 기존 #6101 두 대조군은 원래63건 실행에서도 모두 통과했다.

수정 전 재현도 정정한 동일 입력으로 다시 확인했다. 단계1067은 source80e와bc66의 불변 Native 바이너리로 같은 두 합성 HWP3를 직접 출력했다. before=0/100(1/1800인치)에서 source80e의 BODY y는 둘 다29.3, bc66은29.3→34.7이며 캡션·표 높이·내용은 보존됐다. CLI JSON의0.1 반올림과 별도로 정식 검사는 실제 RenderNode의 원본 단위 환산 관계를 검사한다. 이 실행은 실물 문서의 시각 통과 증거가 아니다. 초기0 크기 합성의 FAIL을 의도한 결함 재현으로 사용하지 않고 `stage1067-caption-cli-before-after.json`으로 대체한다.
