# 이슈 #7642 — 근호와 함수 간격의 독립 진단

시작 커밋: `5de3d6e62df047d24f9fc55a270da292c2c130f3`.
현재 커밋의 전체 nextest와 Native52는 실행 중이며 소스를 유지한다.

## 확대 판독과 구현 가정

Nov 21쪽의 Native 일치율은 94.94393%지만 직접 확대에서 근호의 갈고리·
기울기와 일부 함수 간격이 독립 Print와 다르다. 높은 페이지 점수로 이 차이를
면제하지 않는다. 현재 `layout_sqrt`는 HYhwpEQ의 근호 폭을 1em으로 놓고,
SVG/Canvas는 같은 상수 비율의 V 경로를 각자 다시 만든다. 이 값과 경로가
한컴의 근호 크기·몸체 높이별 구성에 대응하는지 독립 근거로 확인한다.

## 진단과 소비 경로 계획

1. 이미 검증한 진단 입력의 문서 설정을 재사용하되 script·크기를 명시하고
   수식 프레임/기준선/줄 캐시는 비운 HWPX를 만든다. 한컴 2020에서 정상 HWP로
   재생성한 뒤 그 HWP를 PrintMethod 0으로 출력한다. 생성 입력 HWPX와 정상
   저장 HWP, 대응 Print PDF의 역할과 변경 절차를 구분한다.
2. 숫자·단어 몸체, 분수/첨자 몸체, 근 지수, 중첩 근호와 함수/괄호 간격을
   9/18pt에서 대조한다. 원본 Nov의 Print는 그대로 유지하고 진단 통과를
   원본 전쪽 통과로 사용하지 않는다.
3. `layout_sqrt`의 몸체 원점/점유 폭/기준선 → inline 흐름의 소비 →
   SVG/Canvas의 실제 근호 경로·본문 원점을 추적한다. 출력 backend가 같은
   결과 뒤에서 다시 계산하거나 덮어쓰는지 확인한다. 본문을 고정 px로 밀거나
   원본 저장 폭에 맞춰 글자를 장평 조정하지 않는다.
4. 현재 커밋의 회귀가 종료된 뒤 근거가 확인된 일반 규칙을 구현한다.
   작은 영향 쪽과 반례의 직접 Print 대조를 먼저 수행하고, 변경 뒤 전체
   Native/fresh WASM과 실패 회귀를 검증한다. 90%와 확대 판독 선행 조건을
   만족하기 전 테스트 기대값·golden·baseline을 바꾸지 않는다.

로그·TSV·JSON·진단 스크립트·nextrun은 ignored output에만 보존한다.
수식 관련 실패는 모두 현재 브랜치에서 보정하며 테스트 제거·새 이슈 이관으로
해소하지 않는다. PR·CI·merge와 최종 판정은 아직 완료하지 않았다.

## 독립 저장·Print와 실제 판독

28개 수식을 한컴 2020에서 정상 저장했다. Save job은
`3433b894-34b0-4b13-991d-96c23d744623`, Print job은
`3d78bd35-8978-4c1e-bba4-88c4eab6a0a6`이다. 실제 제품
11.0.0.9136, PrintMethod 0 / `hancom2020_pdf_driver_one_up`, 전체 1쪽이다.
생성 입력 HWPX·정상 HWP·Print PDF는 `pdf/issue7642-radical-function-contract/`에
같은 stem으로 보존한다. 템플릿의 용지 설정을 유지했고 PDF는 728×1031pt다.
입력 ZIP에는 폰트 파일이나 BinData가 없다.

| 9pt 표현 | 독립 저장 폭/높이 (HU) | Native 자연 폭/높이 (HU) |
|---|---:|---:|
| `sqrt3` | 1503 / 1035 | 1440 / 1080 |
| `sqrt{1234}` | 2853 / 1035 | 2790 / 1080 |
| `sqrt{{a} over {b}}` | 1953 / 2205 | 1890 / 2310 |
| `root 3 of x` | 1578 / 1035 | 2865 / 1080 |
| `cos theta` | 1875 / 900 | 1661 / 900 |
| `cos(theta)` | 2751 / 900 | 2411 / 900 |

자연 폭 진단은 앞 단계의 고정 실행 파일을 재사용했다. 수식 소스가 현재
커밋과 동일하다는 근거와 이전 빌드 출처를 구분해 기록했다. 현재 커밋의
고정 Native로 실제 전체 페이지를 비교한 결과는 별도로 기록했다.

Native sweep는 전체 1쪽 **91.64639%**, 쪽수 일치·누락 없음, exit 0이다.
그러나 새 review와 3배 확대에서 한컴의 3제곱근이 RHWP에서는
`sqrt3` 뒤 `of x`로 출력되는 **내용 결함**을 직접 확인했다.
함수의 간격·근호 기울기/갈고리도 다르다. 점수의 `passed`를 이 결함의
해결·신규 회귀 등록·최종 승인으로 해석하지 않는다.

`parse_sqrt`는 묶인 지수 뒤 `of`만 인식하고 단일 숫자 지수 뒤 `of`는
인식하지 않는다. 단일 원자 지수와 실제 피연산자의 소속을 보존하는 일반
문법 보정이 필요하다. 함수 이름은 현재 Latin Modern의 합산 폭을 소비하며
한컴의 정체 글자 전진을 소비하는 일반 텍스트와 갈린다. 원본 AST 역할을
보존하면서 측정과 paint가 같은 글자 원점을 소비하도록 연결해야 한다.

Print의 글자 변환에는 `Tz`도 있으므로 font size만 보고 근호가 가로까지
확대됐다고 판단하지 않는다. 실제 스트림의 수평 배율을 별도 JSON으로
보존했다. 사설 글꼴의 바이트·윤곽을 저장소에 복사하지 않고 메트릭·출력
관측과 표시 글리프의 선택을 구분한다. 소스 변경은 아직 하지 않았다.

## 크기별 정체 글자와 간격의 원인 분리

9/18pt에서 unhinted hmtx의 단순 반올림은 함수 캐시 6건 중 3건만
일치했다. 같은 설치 글꼴의 FreeType hinted 전진으로는 6건 모두 일치했다.
이를 다른 크기의 근거로 확장하지 않고 정체 ASCII 52자 및 함수 3종을
6–24pt 14개 크기, 총 98개 수식으로 다시 정상 Save/Print했다.

- Save: `0956fee9-71ef-42c7-98bd-95f35cbecf59`
- Print: `7471328e-d996-4de1-9bb8-7e92286772e0`
- 실제 제품 11.0.0.9136, method 0 / one-up, 전체 3쪽
- 입력·정상 HWP·Print PDF: `pdf/issue7642-roman-function-advance/`

일반 ppem의 FreeType 합산은 정체 단어 56건 중 27건만 일치했다.
한컴의 같은 논리 크기에 대응하는 짝수 ppem에서는 54건이 일치했다.
13/14pt의 x/y는 FreeType과 한컴의 전진이 다르므로 실제 Print의 문자
원점 차이와 정상 캐시의 마지막 글자 점유를 직접 측정했다. 이 결과로
동일 논리 크기의 전진이 같은지 확인했다. 논리 글꼴의 전진 메트릭이며
실물 문단 좌표를 고정하는 회귀 기대값이 아니다.

새 캐시의 `cos(theta)`에서 괄호 전진과 operand 간격을 분리한 결과
14/14 크기에서 같은 간격 계약이 일치했다. `cos rm(angle ADO)`는
함수·정체 글자·각 기호의 전진과 닫는 operand 간격을 별도로 소비한다.
함수 뒤 직접 여는 괄호, 그리스 변수 뒤 닫는 괄호의 operand 역할도
같은 AST 경계에서 검증해야 한다. 한컴과 다른 FreeType 값을 그대로
원본 정답으로 쓰거나 그 차이를 px 위치 보정으로 숨기지 않는다.

현재 소스의 전체 nextest가 최종 exit 100으로 종료됐다.
**10,430 PASS / 110 FAIL / 50 SKIP**, 컴파일 오류 없음이다.
기존 실패 90건 중 6건은 통과했고 새 실패는 26건이며 84건은 유지됐다.
검증 소스 `5de3d6e62`와 진단 커밋 `8c7ba758f`의 Rust/test는 동일하다.
실패 원문·함수·원본 매핑과 변화는 ignored `stage25-failure-*.json`에
보존했다. 현재 110건 모두 이 브랜치에서 보정하며 삭제·이관으로 처리하지 않는다.
