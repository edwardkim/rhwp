# #7642 Stage 165 — DYAD 예약 프레임과 표시 글리프의 계약 분리

## 확인한 실패와 독립 근거

Stage 164의 저장 각주 축 보정과 새 관계형 검사는 완료됐으며, PrEP 전체
140쪽 Native/fresh WASM은 모두 최저 91.75234%다. 이번 단계는 #7593 원본의
별도 미세 배치 결함과 시험지 6개 입력의 페이지 차이를 계속 다룬다.

`samples/issue7593/repro-equation-issue7593.hwpx`와 동일 입력의 독립 한컴 2020
Print `pdf/issue7593/repro-equation-issue7593-hwpx-2020.pdf`를 대조했다.
Native/fresh WASM 점수는 각각 91.61325%지만 보기 ㄴ의 큰 수식 예약 영역과
뒤 본문 간격이 다르다. source의 `dyad{rm AB}`는 BaseUnit 1100 HU, 저장 높이
2580 HU, baseline 85%다. Print는 큰 예약 영역의 위쪽에 수식을 표시하고 뒤
본문을 낮은 기준선에 둔다. 현재 흐름 높이는 18px로 재발행되어 이 공간이 줄었다.
수치는 진단 관측이며 보정 상수·회귀 기대 위치로 사용하지 않는다.

## 공통 결과의 생산과 소비

1. `equation/mod.rs::flow_metrics_hwp`는 저장 크기가 없는 수식을 먼저 구성하고,
   그 외 일반 수식의 캐시 재발행 여부를 `normalized_simple_math_metrics`에서 정한다.
2. `logical_font_frame::frame_with_style`는 표시와 무캐시 구성에도 사용하는
   BAR/VEC/DYAD의 논리 메트릭을 제공한다. 이 helper의 지원 범위가 넓어졌다는
   이유로 모든 큰 저장 예약 영역을 낡은 캐시로 판단하면 안 된다.
3. `composer/equation_line_metrics.rs`는 재발행한 높이·기준선을 실제 글줄에
   소비한다. 이어받기와 저장 축 투영도 줄 전진의 차이를 사용한다.
4. `inline_baseline_px`와 각 배치 경로는 같은 흐름 메트릭으로 수식·본문 원점을
   정한다. `layout_for_paint`의 기존 DYAD 글자 줄 계약은 예약 영역 안의 자연
   glyph 원점을 보존한다. SVG·Skia·Canvas도 그 결과를 소비한다.

현재 측정의 재발행과 DYAD paint의 예약 영역 보존 계약이 충돌한다. 이미
존재하는 의미 분류 `dyad_font_line`을 흐름의 수용에도 사용해 같은 계약을
적용한다. 문서 ID·높이 비율·특정 수치로 대상을 선택하지 않는다.

## 구현과 반례 검증

- 같은 글자 크기의 DYAD 행은 유효한 저장 예약 영역을 유지한다. 원래 없는
  캐시를 구성하는 경로, 보호된 크기, 압축된 작은 프레임은 각각 기존 계약을 따른다.
- 복합 첨자·분수·크기 변경·다줄·CJK 혼재는 기존 DYAD 글자 줄 분류의 대상이
  아니다. 독립 근거 없이 이들의 수용 조건을 바꾸지 않는다.
- #7593 원본의 큰/작은 DYAD 영역을 같은 배율로 비교하고, 최소 입력을 대조군으로
  사용한다. Native/fresh WASM 전체 TSV와 변경 영역 확대 판독을 새로 수행한다.
- glyph가 `<text>`에서 윤곽 경로로 바뀐 기존 검사 실패와 실제 배치 결함을
  구분한다. 출력 보정과 관련 전쪽 90% 확인 전에 기대값·golden을 갱신하지 않는다.
- 시험지 미달 6개 입력의 변경 영역과 페이지 내용·분할을 같은 Print로 추적한다.
  이 수정이 해당 미달까지 해결했다고 추정하지 않고 실제 결과로 다음 원인을 정한다.
- 새 관계형 검사, 기존 실패의 보정과 최종 전체 Rust/lint/정책 검사, 최신 devel
  동기화, 전체 대상의 최신 시각 검증과 PR/CI/후속 처리는 계속 남아 있다.

## 결과

Native 빌드와 원본·최소 대조군 전체 1쪽 검증을 완료했다. 원본은
91.61325% → **98.50470%**, 최소 대조군은 **99.17678%**다. 소스 해시 일치와
독립 기준 PDF·입력 해시를 확인했다. 새 전체 review 및 같은 배율의 보기 확대
비교를 `mydocs/pr/assets/issue7642-dyad-frame-20261012/`에 보존했다.
fresh WASM도 원본 **98.50470%**, 최소 대조군 **99.17678%**로 완료됐다.
실제 WASM 출력과 전체 쪽수·소스 해시·Studio 동기화를 확인했다.
새 이름 `saved_dyad_reservation_keeps_the_cell_text_below_the_visible_math`의
관계형 검사를 `tests/cases/issue_7642_dyad_saved_reservation.rs`에 추가하고 실제
nextest **1개 PASS**를 확인했다. 독립 원본의 저장 예약 높이와 기준선 비율,
셀·문단 소유, 수식→본문 비겹침을 검사한다. 고정 절대 px 위치를 쓰지 않는다.
수정 전 `4bf6ca10edccd50459edc30758bf3eccbb59e8fd`에서도 동일한 Rust 검사를
실행해 예약 영역 보존 assertion의 **1개 FAIL**을 확인했다. 수정 후 **1개 PASS**와
테스트 SHA-256 `675a61308bf51aca7c0500d8b33ccc2e0776f184ee21085e39377cd07b620eeb`가
일치한다. 컴파일 실패나 다른 검사를 결함 재현으로 세지 않았다. 종료된 전용
worktree만 제거했으며 영수증·로그와 공용 target 캐시는 보존했다.

시험지의 별도 원인 추적에서 문7 미주 마지막 문단의 마지막 저장 줄을 확인했다.
원본 HWPX는 `vertpos=0`으로 다음 단을 시작하지만 파싱된 문서는 앞줄의 전진에
이어지는 `41336`으로 바뀐다. `normalize_hwpx_note_line_vpos`는 0이 아닌 값 사이의
되감김만 보존하고 마지막 0을 연속줄 아티팩트로 정규화한다. 원본 Print의 다음 쪽
첫 줄은 이 마지막 수식인데 현재 출력에서는 앞쪽에 남는다. 이는 독립 원본과
파싱 결과의 관측이며, HWP 짝과 기존 연속줄 대조군을 확인하기 전 전체 0 보존을
구현하거나 원인 해결로 선언하지 않는다.

같은 HWP 짝의 동일 미주 문단도 대조했다. HWP 파싱은 마지막 `vpos=0`을
보존하지만 현재 HWP 출력도 같은 페이지 배치에서 미달한다. 따라서 HWPX 파서의
경계 변경만 고쳐 두 형식 전체의 문제가 해결된다고 주장할 수 없다. 공통 미주
조판의 내부 되감김 수용·실제 fit 재생 이후 컷 제거 경로까지 추적한다.


HWP 미주 조판의 실제 디버그 재생에서는 문7 마지막 문단에 내부 되감김을
인식해도 전체 문단의 실제 점유가 가용 높이에 들어간다는 판정으로 전체를 앞
단에 남기는 경로를 확인했다. `paragraph.rs`의 `render_fits_whole`과
`whole_internal_rewind_fits` 이후 컷 제거가 저장 단 소속을 바꿀 수 있다.
진단은 `stage165-september-hwp-q7-flow-debug.log`에 보존했다. 독립 Print와
같은 저장 단 시작을 사용하는지, 편집 후 재조판과 구별하는지 추가 확인해야 하며
이 관측만으로 공통 경로 수정을 완료했다고 선언하지 않는다.
