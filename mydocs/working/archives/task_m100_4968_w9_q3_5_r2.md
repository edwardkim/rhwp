## 1. 결론

R1의 payload-free `ExactFontSourceHandle`을 한 번의 layout/reflow 동안 소비하는
`KerningSourceSession`을 도입했다. session은 exact handle별로 provider 조회, source SHA-256 대사,
kerning capability parse와 `KerningPairEngine` 준비를 최초 한 번만 수행하고 이후 요청에는 같은 결과를
재사용한다.

cache는 성공만 저장하지 않는다. source unavailable·identity mismatch·malformed/unsupported face도
fail-closed 결과로 저장한다. 따라서 같은 layout session 중 host font registry가 바뀌어도 앞 문단과 뒷 문단이
서로 다른 source 판단을 사용하는 비결정성이 생기지 않는다. registry 변경을 반영하려면 새 session을 만든다.

R2는 실제 document/native/WASM provider를 제품 measurement에 연결하지 않았고 positions를 수정하지 않는다.
Docker WASM은 Q3-4/R1과 동일한 8,978,378 bytes와 동일 SHA-256이다.

## 2. 소유권과 cache 경계

### 2.1 source 소유권

- document embedded font, native selected font, WASM host registry가 font bytes를 소유한다.
- `KerningSourceSession`은 provider를 layout session 수명 동안 빌린다.
- prepared `rustybuzz::Face`도 provider bytes를 같은 수명으로만 빌린다.
- `TextStyle`, handle, trace, cache key에는 bytes·path·font family·원문을 넣지 않는다.

### 2.2 최초 준비

1. provider에 exact handle을 한 번 조회한다.
2. 32 MiB source 상한, face index, byte length, SHA-256을 대사한다.
3. 검증된 source를 다시 hashing하지 않고 SFNT capability를 판정한다.
4. 지원 face만 bounded pair engine으로 준비한다.
5. capability·engine 또는 구조화된 실패 결과를 exact handle key로 보존한다.

독립 호출용 기존 `prepare_kerning_pair_engine`의 재대사 계약은 유지했다. session 내부에서만 이미 검증된
source 경로를 사용하므로 두 번째 session 요청에서 provider·SHA·SFNT parse가 반복되지 않는다.

### 2.3 fail-closed

provider가 없거나 반환 source가 handle과 다르면 engine을 노출하지 않는다. unsupported/malformed source와
shaping 준비 실패도 같은 원칙으로 닫는다. cache hit trace는 `cacheHit: true`만 달라지며 최초 판단의 capability와
reason을 그대로 유지한다.

현재 R2에는 segment 순회나 layout commit이 없다. 따라서 기존 4,096 code point/glyph, 4,095 pair 상한은
Q3-4 run gate에 그대로 있고, 256 segment 상한은 실제 segment measurement를 도입하는 R4에서 실행 경로와 함께
적용한다.

## 3. 회귀 검증

기존 `tests/cases/issue_4968_kerning_capability_provider.rs` 원본에 두 회귀를 추가했다. 별도 integration
source는 만들지 않았다.

- 성공 handle을 두 번 준비해 provider 호출 횟수가 1회인지 확인
- cache된 engine의 `AV To WA HH` 결과가 기존과 같은 -94 design units인지 확인
- source unavailable과 byte-length mismatch를 두 번 요청해 실패도 1회만 조회되고 cache되는지 확인
- 실패 handle에서 engine이 노출되지 않는지 확인
- session trace에 bytes, path, text, fontFamily가 없는지 확인

## 5. 보호 불변식 판정

- K0 및 현재 제품 layout: 변경 없음
- exact source: family 추정 없이 handle identity로만 대사
- source payload: core·style·trace·cache key에 복제하지 않음
- bounded font: 32 MiB 초과 source는 engine 진입 전 차단
- deterministic session: 성공과 실패를 모두 exact handle별로 고정
- backend 책임: positions 재생만 하며 R2에서 재-shaping 연결 없음
- WASM bundle: Q3-4/R1과 byte-exact
