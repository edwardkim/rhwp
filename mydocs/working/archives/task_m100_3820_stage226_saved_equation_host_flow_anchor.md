# Stage 226 - 저장 수식 host 흐름 앵커 복원

## 목적

`issue2006/1790387_prep_final_report.hwpx`의 마지막 1쪽 차이를 고정 여백이 아닌
원본 HWPX의 저장 VPOS 흐름으로 제거한다.

## 관측

- 최신 HWP 2020 MCP 기준 PDF는 140쪽이다.
- Stage 225 후 rhwp는 141쪽이며, 원본 19쪽의 `pi=328`, `pi=329` 수식 문단이
  실제 다음 문단 VPOS보다 각각 약 23px, 37px 더 많은 흐름 높이를 소비한다.
- 두 문단의 다음 source VPOS는 같은 물리 쪽 본문 안의 양수 좌표이고, `pi=330`은
  원본에서 그 쪽 하단에 함께 배치된다. rhwp에서는 `pi=330`만 다음 쪽으로 이월된다.
- 파싱 덤프에서 두 문단은 모두 `treat_as_char=true`인 수식 control 세 개로만 구성된다.
  일반 문단 조판 경로를 타므로 표 전용 조판 경로에 보정하면 실행되지 않는다.

## 수정

- HWPX 저장 조판, 단일 컬럼, 마지막 실제 저장 LineSeg를 가진 수식 전용 문단으로 대상을 제한했다.
  문단의 텍스트 버퍼가 수식 자리표시자만 담는 저장 형식도 같은 수식 host로 취급한다.
- 마지막 host VPOS와 다음 문단 VPOS가 같은 본문 영역에서 증가할 때, 측정 조판이
  다음 source 앵커를 넘긴 경우에만 `current_height`를 그 앵커까지 되돌린다.
- 표, 도형, 물리 쪽 리셋과 음수/본문 밖 좌표는 모두 제외하고 synthetic LineSeg는
  source 앵커 선택에서만 제외한다.

## 결과

- 기존 핀 실행에서 실제 쪽수는 140쪽으로 확인됐다.
- 최신 HWP 2020 MCP PDF
  `pdf/issue2006/1790387_prep_final_report-hwp2020-20260814.pdf`의 140쪽과 일치한다.
- 이전 한글 2022 PDF의 146쪽은 다른 폰트 환경 산출물이므로 테스트 정본을 2020 MCP
  기준 140쪽으로 교체한다.

## 검증 계획

1. `issue_2006_1790387_prep_pagination_pin`의 실제 쪽수가 HWP 2020 MCP 기준 140쪽인지 확인한다.
2. 저장 RowBreak 및 HWP/HWPX 383쪽 fixture를 다시 실행해 회귀가 없는지 확인한다.
3. 최종 전체 회귀 뒤 MCP 2020 PDF와 해당 페이지 raster를 비교하고 증적을 보관한다.
