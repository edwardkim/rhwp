## 1. 결론

R4A의 목표였던 `(char_shape_id, language_index) → exact source handle → provider → layout
session` 경로를 제품 owner에 연결했다. family 이름으로 font를 다시 찾지 않으며, source bytes와 face index는
`LayoutEngine`의 bounded registry가 소유한다.

임베디드 font는 문서에서 실제 text run이 참조한 slot만 기존 BinData/face-index 해소 경로로 등록한다. 임베디드
source가 없는 일반 문서는 문단 순회 자체를 생략한다. native host와 WASM host는 같은 core API에 확정 slot,
bytes, face index를 전달한다.

R4A는 source owner와 수명만 마련한다. 기존 width, line break, char positions, paint positions에는 kerning
delta를 적용하지 않았고 K0 SVG byte identity를 native와 실제 Node/WASM 양쪽에서 확인했다.

## 2. 구현

### 2.1 bounded exact source registry

`src/renderer/kerning.rs`에 다음 계약을 추가했다.

- `ExactFontSlot { char_shape_id, language_index }`
- `ExactFontSourceRegistry`
- 구조화된 등록 결과와 오류
- 동일 slot/source 재등록은 멱등
- 동일 slot의 다른 source 덮어쓰기는 `slot-conflict`로 fail-closed
- 여러 slot이 같은 handle을 쓰면 source bytes는 한 번만 소유
- registry가 `ExactFontSourceProvider`를 구현해 R2 `KerningSourceSession`이 직접 빌림

상한은 다음과 같다.

| 항목 | 상한 |
|---|---:|
| source 하나 | 32 MiB |
| registry 누적 source bytes | 64 MiB |
| exact face/source | 256 |
| slot | 4,096 |
| 문서 slot 탐색 깊이 | 128 |
| 문서 slot 탐색 work units | 1,000,000 |

face parser나 `rustybuzz::Face`는 registry에 저장하지 않는다. session이 registry를 빌리는 동안에만 face를
만들어 self-reference, leaked bytes, global/thread-local 상태를 피했다. `DocumentCore: Send` 계약도 유지된다.

### 2.2 문서 임베디드 source 선등록

초기 load와 문서 전체 교체·snapshot 복원·blank template 생성에서 파생 상태를 만들기 전에 embedded exact
source registry를 재구성한다.

- 본문, 표 셀, 글상자, 캡션, 머리말/꼬리말, 각주/미주, master page, field memo의 실제 composed run을 순회
- 사용하지 않는 embedded BinData는 load하지 않음
- primary embedded face를 먼저 해소하고, 불가하면 embedded substitute face 사용
- 기존 `32 MiB/font`, `64 MiB cumulative` bounded loader와 TTC face-index resolver 재사용
- 손상·상한 초과·미해소 source는 문서 open을 실패시키지 않고 해당 slot을 미등록 상태로 둠
- embedded source 자체가 없는 문서는 O(font face count) 확인 뒤 즉시 종료

paint/lowering의 기존 page-local embedded loader는 R4A에서 바꾸지 않았다. R4A registry가 layout source를
소유하므로 embedded 문서의 최악 resident memory는 registry 64 MiB와 page lowering 64 MiB가 겹칠 수 있다.
R4D에서 backend가 registry/저장 positions를 단일 소비할 때 중복 load 제거를 검토해야 한다. 지금 단계에서는
paint source를 바꿔 K0 출력 경로를 흔드는 것보다 bounded 중복을 명시적으로 남기는 쪽을 선택했다.

### 2.3 native/WASM 공통 host API

`DocumentCore::register_exact_font_source_native`와 WASM
`HwpDocument.registerExactFontSource`를 추가했다.

입력은 `charShapeId`, `languageIndex`, `Uint8Array/font bytes`, `faceIndex`이며 family 이름이나 host path를 받지
않는다. 반환 JSON은 payload 없는 handle(SHA-256, byte length, face index), 등록 상태, bounded registry
회계만 담는다.

새 source 등록은 layout/page tree/측정 파생 캐시를 무효화하고 즉시 재페이지네이션한다. 동일 source의 멱등
재등록은 불필요한 재페이지네이션을 하지 않는다. 문서를 통째로 교체하면 이전 문서 또는 host의 slot binding을
지운 뒤 새 문서의 embedded source로 다시 만든다.

## 5. 남은 경계와 다음 단계

R4A registry와 session은 준비됐지만 measurement 함수는 아직 이를 소비하지 않는다. 따라서 현재 결과만으로
kerning이 화면 조판에 적용됐다고 주장하지 않는다.

다음 승인 경계인 R4B에서는 한 layout/reflow 진입에서 registry를 빌린 `KerningSourceSession`을 만들고,
기존 base char positions와 exact pair candidate를 owned `KerningRunMeasurement` 하나로 합쳐야 한다. K0 또는
source 부재 시 기존 positions를 그대로 반환하는 것이 첫 진입 게이트다.
