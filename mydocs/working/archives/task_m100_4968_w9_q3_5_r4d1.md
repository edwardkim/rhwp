## 1. 결론

`layout_composed_paragraph` 호출 한 번에 `KerningLayoutSession` 하나를 열고, 최종 emitted `TextRunNode`만
K1 positions를 게시하도록 연결했다. 각 run은 `(char_style_id, lang_index)` exact slot과 최종 `TextStyle`을
사용하며, `PairAdjusted`일 때만 `layout_positions=Some`이 된다.

positions의 마지막 값은 해당 TextRun bbox 폭과 다음 run x advance의 단일 정답으로 사용한다. body,
fresh table-cell, fresh text-box의 공개 exact-font fixture에서 이 계약을 page tree로 직접 확인했다.

각주·TAC로 분할되는 run은 whole-run pair를 적용하지 않는다. 실제로 방출되는 각 텍스트 조각을 같은 session에서
따로 측정하므로 marker/control 경계를 가로지르는 pair delta가 남지 않는다. 탭·강제 줄바꿈·CharOverlap처럼
현재 replay 계약을 온전히 만족하지 않는 특수 run은 K1을 추정하지 않고 K0로 닫는다.

## 2. 구현

### 2.1 문단 단위 session

`layout_composed_paragraph` 진입 시 exact font registry generation을 고정한 session 하나를 만들고 모든 줄의
`emit_line_runs`에 mutable borrow로 전달한다.

```text
layout_composed_paragraph
  -> one KerningLayoutSession
     -> line 0 final runs
     -> line 1 final runs
     -> ...
```

따라서 같은 문단 안에서 run마다 registry snapshot이나 face parse cache를 새로 만들지 않는다. exact source가
없는 slot은 base positions 계산 전에 즉시 K0로 반환한다.

### 2.2 최종 run producer

공통 helper `emitted_run_layout_positions`는 다음 순서만 허용한다.

1. K1 eligibility와 exact slot 존재 확인
2. 최종 replay text와 정렬·배분까지 반영된 `TextStyle`로 base positions 계산
3. 줄-말미 공백에 잘못 배정된 `extra_word_spacing` 회수
4. 동일 session의 exact pair measurement 실행
5. `PairAdjusted`에서만 owned positions 게시
6. positions 마지막 값을 bbox 폭과 다음 x advance에 사용

K0, source 부재, no-pair, identity mismatch, malformed source는 기존 `fallback_width`와 `None`을 그대로 쓴다.
부분 적용 상태는 만들지 않는다.

### 2.3 경계별 처리

- composed run·언어 slot 경계: 각 run을 독립 측정
- 물리적 줄 경계: 각 줄의 emitted run을 독립 측정
- 각주/미주 marker: marker 앞뒤 텍스트 조각을 각각 측정
- TAC image/table/equation/form: TAC 앞뒤 텍스트 조각을 각각 측정
- display text: 분할되지 않은 visible replay 문자열 기준 positions
- 탭·개행·CharOverlap: 이번 절편에서는 K0 fail-closed
- 줄-말미 공백: 배분 여분 회수 뒤 pair delta 적용

일반 unsplit run의 선행 공백 배경·글자 테두리 폭과 RangeTag highlight도 가능한 경우 같은 positions range를
읽는다. 각주·TAC 분할 run의 backend 장식·control sidecar 정합은 모든 visual consumer를 함께 전환하는
R4D-2에서 닫는다.

### 3.4 R4D-0 대비 조판 성능

#### 측정 경계

빌드·테스트 하네스 시간 대신 공개 `DocumentCore::build_page_render_tree(0)`의 cold tree 생성을 직접
측정했다. 이 API는 page-tree cache를 통하지 않으므로 각 iteration이 실제 조판 producer를 다시 실행한다.

- 기준선: `9a6b09cb8` R4D-0
- 후보: 위 기준선 + 현재 R4D-1 source diff
  (`2478ba762fc0a9c9961724c9698ea04688b3f8224e7deb1dfac801c8f4559eb1`)
- 빌드: `cargo build --locked --release --bin r4d1_perf_probe`
  (`lto=true`, `codegen-units=1`)
- 호스트: WSL2 Linux 6.6.114.1, Intel Core i9-9900KF, Rust 1.93.1
- 고정 CPU: `taskset -c 4`
- 입력: 문단당 `AV` 40쌍(80 scalar), 동일 char shape·page geometry
- K0: `kerning=true`지만 exact source를 등록하지 않은 기존 fallback 조판
- K1: 같은 slot에 `RHWPExactKerningSmoke.ttf`를 등록한 exact 조판
- 문서 준비·폰트 등록·warm-up은 측정에서 제외
- R4D-0/R4D-1 프로세스 순서를 매 trial마다 뒤집어 한쪽에만 열·순간 부하가 몰리지 않게 함

아래 시간은 독립 프로세스별 iteration 중앙값을 다시 중앙값으로 모은 값이다. 16·128문단은 각 5개
프로세스 × 30회, 64문단은 7개 프로세스 × 40회다.

| 경로 | 문단 | TextRun | R4D-0 중앙값 | R4D-1 중앙값 | 변화 |
|---|---:|---:|---:|---:|---:|
| K0 | 16 | 32 | 1.280 ms | 1.301 ms | +1.6% |
| K0 | 64 | 128 | 5.131 ms | 5.151 ms | +0.4% |
| K0 | 128 | 256 | 10.322 ms | 10.432 ms | +1.1% |
| K1 | 16 | 32 | 14.881 ms | 15.409 ms | +3.5% |
| K1 | 64 | 128 | 60.058 ms | 61.932 ms | +3.1% |
| K1 | 128 | 256 | 119.743 ms | 123.497 ms | +3.1% |

K0 128문단 값은 변동을 줄이기 위해 별도로 20개 프로세스 × 60회로 확대 측정한 값이다. 같은 조건의
추가 10개 프로세스 측정에서는 중앙값 변화 +0.6%, p95 변화 -0.2%였으므로 K0 tail 증가가 일관되게
관측되지는 않았다. 반면 K1 p95 변화는 16·64·128문단에서 각각 +0.7%, +1.6%, +0.4%였고 중앙값은
세 크기 모두 약 +3%로 같은 방향이었다.

#### 메모리·바이너리 크기

64문단 K1 후보는 128개 TextRun 중 64개에 3,264개의 `f64` position을 게시했다. position 값 자체의
owned heap payload는 26,112 bytes(25.5 KiB)다. 5개 독립 프로세스의 GNU time peak RSS는 K0에서
두 버전 모두 중앙값 7,296 KiB였고, K1은 두 버전 모두 7,936~8,064 KiB 범위였다. Linux RSS의 page
단위와 allocator 변동이 25.5 KiB보다 커서 이 probe로는 별도의 peak RSS 증가를 분리하지 못했다.

동일 probe native release 바이너리는 8,419,672 bytes에서 8,428,504 bytes로 8,832 bytes(+0.10%)
증가했다. 이는 native 단일 probe의 참고치이며 WASM bundle 크기 판정은 아니다.

#### 판정

- K0 산출물은 동일하지만 실행비용까지 완전한 zero-cost는 아니다. 빈 registry에서도 문단 session 생성과
  emitted run별 eligibility/source-handle 조기 판정이 추가되어 중앙값 기준 약 +0.4~1.1%가 관측됐다
  (16문단의 짧은 1.3 ms 구간은 +1.6%).
- K1의 약 +3.1% 중앙값 증가는 R4C의 line-boundary exact shaping 뒤 최종 emitted run positions를 한 번 더
  계산하고 `Vec<f64>`로 소유하는 R4D-1 고유 비용이다. 문단 수를 8배로 늘려도 비율이 약 3%로 유지되어
  이 probe에서는 초선형 폭증이 없다.
- 프로젝트에 아직 이 경로의 정식 성능 허용 상한이 없으므로 수치만으로 `통과`를 선언하지 않는다. 이
  결과는 메인테이너가 R4D-1을 수용하거나 K0 optional-session fast path를 먼저 요구할 수 있는 승인 근거다.
- R4D-2는 이 positions를 backend가 그대로 소비해야 한다. backend별 재-shaping을 추가하면 이번 +3% 경계가
  다시 누적되므로 성능 보호 불변식 위반으로 본다. R4D-2 완료 시 backend replay·WASM payload 비용을 별도로
  다시 측정한다.

## 4. 검증 중 발견하고 정정한 사항

### 4.1 tuple helper의 `?` 사용

첫 compile에서 tuple 반환 helper에 `?`를 쓴 타입 오류가 1건 발생했다. 명시적 `let Some(...) else`로 바꿔
fail-closed 반환을 분명히 했고 이후 all-target check를 통과했다.

### 4.2 source-side test 증가 차단

경계 검증 2건을 잠시 source `#[cfg(test)]`에 두었으나 unit-tier가 총량 증가를 즉시 차단했다
(`4226 > 4225`). 해당 module을 전부 제거하고 기존 #4968 integration source로 검증을 이동했다. 최종 source
unit 총량은 기존 4,224건으로 유지되며 generated inventory는 제출하지 않는다.

### 4.3 root Cargo registry 오염 복구

review registry 동기화 명령 1회가 잘못된 working directory에서 실행되어 root `Cargo.toml`에 예외 target 4줄을
추가했다. 즉시 그 4줄만 제거하고 새 detached review worktree에서 prepare/sync/check를 다시 수행했다. 최종 root
`Cargo.toml`은 변경되지 않았고 source 후보에는 generated suite·manifest·target registry가 없다.
