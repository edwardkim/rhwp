## 1. 절편 목적

메인테이너가 승인한 효율 전환을 저장소의 재현 가능한 실행 절차로 고정했다. 제품 코드는
변경하지 않고, 24개 절편의 실측 속도와 현재 `main.rs` 책임 지도를 이용해 단일 handler
절편을 기능군 배치로 교체했다.

## 2. 효율 평가

- 시작 42,370줄에서 현재 38,561줄로 3,809줄 감소했다.
- 1,200줄 목표까지 필요한 총 감소의 9.3%를 완료했고 37,361줄이 남았다.
- 최상위 함수는 351개에서 310개로 줄었지만 편집 handler 92개는 아직 root에 있다.
- 최상위 query 명령 19개와 `inspect` 하위 명령 4개가 새 모듈 경로를 사용한다.
- `HwpDocument` 직접 참조 42개와 `rhwp::service` 참조 0개는 Stage 3 대상이라 변하지 않았다.

지금까지의 이동 평균을 그대로 적용한 약 190개 절편은 예측값이 아니라 단일 handler 절차가
지속 불가능함을 나타내는 역산값이다.

## 3. 확정한 절차

새 실행계획은 16개 기능군을 query/output, metadata/protocol, command 세 wave로 나눈다.
하나의 승인 배치 안에서 필요한 계약 보강과 handler 이동을 분리 커밋으로 수행하고, focused
검증은 각 커밋에, 전체 회귀는 배치 최종 HEAD에 한 번 적용한다.

승인과 보고는 배치 시작·종료에 유지한다. 계약 차이, 내부 계층 동작 변경, 순환 의존, 새 모듈
1,200줄 초과, CC>25 함수 단순 이전, 동시 PR 경로 중첩은 즉시 중단 조건이다. 따라서 효율
전환은 품질 관문이나 메인테이너 통제권을 낮추지 않는다.

상세 순서와 종료 조건은
[`task_m100_5511_stage2_batch_plan.md`](../../plans/archives/task_m100_5511_stage2_batch_plan.md)에
기록했다.

## 4. 다음 실행 배치

첫 배치 Q1은 `thumbnail`의 preview output 경계를 다룬다.

1. 파일 출력 바이트·format·MIME·크기와 입력 불변성을 고정한다.
2. base64·data URI decoding 결과가 실제 내장 미리보기와 같은지 확인한다.
3. 기본 출력 경로 생성과 저장 실패의 부작용·종료 코드를 고정한다.
4. query가 아니라 `cli/outputs/preview.rs` 또는 동등한 부작용 명시 모듈이 맞는지 판정한다.
5. 계약이 확보되면 별도 승인 절편을 만들지 않고 같은 배치에서 handler를 이동한다.

CQRS 소유권을 확정할 수 없거나 현재 동작을 정상 규약으로 고정하기 어려우면 이동하지 않고
메인테이너에게 판정을 요청한다.

## 5. 검증 범위

이번 절편은 수행계획과 작업 보고만 바꾸며 Rust·Cargo·workflow·제품 동작을 변경하지 않는다.
따라서 `git diff --check`와 변경 문서 링크 검사를 적용한다. 전체 Cargo 회귀는 다음 제품 코드
배치의 최종 HEAD에서 실행한다.

## 6. 원격 위험

절편 시작 시 `origin/devel`과 `upstream/devel`은 `1a6ce79fd`로 같고 작업 브랜치는 56커밋
앞, 0커밋 뒤였다. 최신 base와 merge-tree는 충돌 없이 생성됐다. 열린 PR과 변경 경로는 보고서
커밋 직전에 다시 확인한 결과 12개였고, task branch와 이번 문서 경로의 교집합은 모두 0개였다.

절편 중 #5565가 새로 열리고 head도 `a1b1e827`로 갱신됐으며 #5548 head는 `0a334bd3`으로
바뀌었다. 보고서 커밋 뒤 최종 재확인에서는 #5564 head도 `de0ce108`로 갱신됐다. 세 head를
실제로 fetch해 각 시점의 현재 HEAD와 가상 병합했고 모두 충돌 없이 tree를 생성했다. 동일
계획·보고 경로 또는 다음 Q1의 source·test 경로가 이후 겹치면 Q1을 시작하지 않는다.

이 문서 커밋과 원격 재검증 뒤 첫 기능군 배치 착수는 메인테이너의 별도 승인을 기다린다.
