# Task #3927 Stage 1 — sec 보강 후 잔여 발산 좌표 확정

프로브 3종(DIAG_FIT·DIAG_PRESPLIT·DIAG_SPLITSCAN)에 `sec` 필드 추가(동작 불변).
pi 충돌 없이 구역 10(질의·답변)만 분리 관측 가능해졌다.

## 발산 지점 — pi=23 이 쪽을 새로 시작한다

| | 한컴(저장 vpos) | rhwp |
|---|---|---|
| 쪽 시작 문단 | 0,2,6,10,13,15,18,**21**,**24**,26,29,32 | 14,18,**23**,**24**,30,… |
| pi=22 | 52.0px (21 과 같은 쪽) | cur_h 52.0 ✓ 동일 |
| **pi=23** | **324.7px (같은 쪽 계속)** | **cur_h=0.0 — 새 쪽** ✗ |
| pi=24 | 159.5 (되감김 → 새 쪽) | cur_h=0.0 ✓ 동일 |

즉 **한컴은 pi=21·22·23 을 한 쪽에 담고 rhwp 는 23 을 다음 쪽으로 밀어 +1쪽**.

## 근인 수치

```
TABLE_DRIFT pi=22: table_total=300.2  cur_h=52.0  → 배치 후 cur_h=352.2
TABLE_DRIFT pi=23: table_total=557.8  cur_h=352.2 avail=740.8
                   352.2 + 557.8 = 910.0 > 740.8  (초과 169.2px)
DIAG_FIT   pi=23: plain=false 로 fit 실패 → 이월(cur_h=0.0 에서 재배치)
```

한컴 오라클: pi=23 의 저장 vpos=324.7px, 다음 문단(24) vpos=159.5px 로 **되감김** —
한컴은 pi=23 표를 324.7 에서 시작해 **쪽 경계에서 분할**하고 꼬리를 다음 쪽 0~159.5 에
뒀다. rhwp 는 통짜 이월했다.

**#3674 축 B(되감김 형상)와 같은 계열**이나, 그 수정은 `declared_overflows_current`
경로를 겨눴고 여기는 **plain fit 실패 → 일반 이월** 경로다. 즉 되감김 증거를 쓰는
지점이 하나 더 필요하다(#3931 의 무증거 일반화와도 다름 — 여기엔 증거가 있다).

## Stage 1 정정 — "한컴이 분할했다"는 해석은 틀렸다

이월 지점 프로브(DIAG_ADV A/B/C)로 pi=23 은 **지점 C = `declared_overflows_current`
분기**(#3674 pi=14 와 동일 분기)에서 이월됨을 특정했다. 그 지점의 입력:

```
DECL_DEFER? pi=23 cur_h=352.2 declared=402.5 avail=740.8
            saved=Some((324.7, 719.1)) bottom_fits=false splits_here=false
```

**저장 하단 719.1px < 가용 740.8px** — 즉 한컴은 이 표를 **그 쪽에 통째로 넣었다.**
분할이 아니다. pi=24 의 되감김은 24 자신이 새 쪽에서 시작한다는 뜻일 뿐이다.

### 진짜 근인 — 표 높이 과대측정

| | 값 |
|---|---|
| 한컴 선언 기반 표 세로폭 | 719.1 − 324.7 = **394.4px** |
| rhwp 실측 `table_total` | **557.8px** |
| 과대 비율 | **1.41배 (+163px)** |

표가 163px 크게 계산되니 `352.2 + 557.8 = 910 > 740.8` 로 넘쳐 이월된다. 한컴 값
(394.4)이면 `352.2 + 394.4 = 746.6` 로 여전히 5.8px 초과이나, 그 정도는 관용치·
호스트 간격 처리로 흡수될 여지가 있다 — **분할 진입 문턱이 아니라 측정 정합이
1순위**다.

**#3674 7보에서 `issue_3738` fixture 를 두고 도달했던 결론과 같은 형태**:
"증거는 참인데 행높이 과대측정이 실행을 깨뜨린다". 이번엔 편람 자체에서 같은 축이
드러났다 — 즉 이 문서의 잔여 발산도 **#3931(측정 정합 선결)** 과 한 뿌리다.

## Stage 1 재정정 (2보) — 저장값은 스냅샷, 실물 오라클로 재측정

1보의 "선언 394.4px 가 정답"이라는 판단도 **부정확**했다. 저장 셀 h·행 높이는
편집기 저장 시점 스냅샷이고 한컴은 조판 때 내용에 맞춰 재계산한다(메모리:
한컴 LINE_SEG 자동 재계산). 실제로:

- 셀[11], r=4, 선언 h=2949HU(**39.3px**)인데 저장 LINE_SEG 는 **16줄**(p0 12 + p1 4,
  줄 간격 24.5px = 392px)을 담고 있다 — 선언 높이로는 내용이 들어갈 수 없다.
- 한컴 PDF 실물(p287) 육안: Q11 답변 12줄이 **전부 보인다** → 한컴도 행을 키운다.

**따라서 rhwp 가 행4 를 422.5px 로 키우는 동작 자체는 옳다.**

### 실물 오라클 — PDF bbox 실측

| | 값 |
|---|---|
| 한컴 Q11 블록 세로(PDF p287, 96dpi 환산) | **378.0px** |
| rhwp `eff_h` | **549.8px** |
| 과대 | **+171.8px (1.45배)** |

행별 대조에서 **행 4 하나가 원인**임은 유효하다(다른 5행은 저장값과 ±0.5px 일치):

| 행 | 저장(px) | rhwp(px) |
|---|---|---|
| 0·2·3·5 | 12.5 / 20.2 / 13.3 / 32.9 | 12.5 / 20.2 / 13.3 / 32.9 ✓ |
| 1 | 31.3 | 48.4 (+17.1) |
| **4** | 74.4 | **422.5** |

행 4 는 내용 재계산 대상이라 저장값 비교가 무의미하고, 실물 기준 과대는 **총
171.8px**. 즉 "행4 를 키우는 것"은 맞고 **얼마나 키우는가**가 틀렸다 — 줄 수(16)는
저장과 일치하므로 **줄당 높이 또는 셀 패딩** 축이 남는다.
