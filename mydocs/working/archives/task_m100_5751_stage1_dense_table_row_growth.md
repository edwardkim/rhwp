# #5751 조밀 표 행이 내용에 맞춰 안 늘어나는 #501 가드 오발동

Issue: #5751

## 재현

`korea_downloads/교육부/156505020_[교육부 04-27(수) 조간보도자료](../별첨) 2024학년도
대입전형시행계획 주요사항.hwp` 마지막 쪽(33쪽) 표에서 셀 글자가 아래 괘선을 넘어
다음 행 위에 그려진다. 데이터 행 전부가 그렇다.

`export-svg` 33쪽 실측:

```
행 y=359.19  h=21.09  아래 괘선=380.28 | 글줄 baseline 381.47 (행 위로부터 22.28px)
                                        → 괘선 아래로 +1.19px, 글자 몸통이 아래 행에 얹힌다
```

## 원인 — 같은 가드가 두 곳에서 다른 기준으로 살아 있었다

`#501` 은 "안 여백이 셀 선언 높이를 넘는 비정상 저장값" 을 막는 한컴 방어 로직
모방인데, 그 발동 기준이 측정과 렌더에서 갈려 있었다.

| | 파일 | 임계 | 동작 |
| --- | --- | --- | --- |
| 측정 | `height_measurer.rs:1668` | `total_pad > cell_h * 0.5` | 행 높이를 선언 높이로 clamp |
| 렌더 | `layout/table_layout.rs:3960` | `total_v_pad >= cell_h` | padding 을 `cell_h*0.5` 로 비례 축소 |

이 문서의 데이터 셀은 `pad=1,132 HU(15.09px)`, `cell_h=1,582 HU(21.09px)` 라
**측정 기준만 넘는다**. 그래서 측정은 행을 21.09px 로 묶어 두는데 렌더는 표 기본
여백 566 HU 를 그대로 써서, 글자가 `566 + 1,105(baseline) = 22.28px` 자리에 놓이고
21.09px 짜리 행을 넘어간다.

여백 566 HU(2mm)는 표 기본값이고 비정상인 쪽은 **선언 높이** 다 — 판정이 뒤집혀
있었다.

### 같은 문서 안에 통제군이 있다

같은 구역의 표 `pi=4`(203행)는 선언 높이가 넉넉해 가드를 타지 않고, 행 높이가
이미 한글과 같은 32.43px 다. 문제의 표 `pi=8`(201행)만 21.09px 로 눌렸다.

## 보정

발동 기준을 `Cell::vertical_padding_is_abnormal` 하나로 모아 측정과 렌더가 같은
값을 보게 했다. 기준은 렌더 쪽(= 셀 높이 자체를 넘을 때)을 채택했다 — `#1785` 의
`use_cell_padding_axis` 를 단일 출처로 모은 것과 같은 결이다.

`#501` 이 겨냥한 진짜 비정상 셀(mel-001 p2 셀[21]: 여백 3,400 HU > 셀 1,280 HU)은
그대로 걸리고, 여백이 셀 높이의 절반~1배인 정상 조밀 표만 가드에서 풀린다.

## 이 이슈에 귀속하지 않는 축 — 가로 용지 RowBreak bleed

표적 문서의 쪽수는 수정 뒤에도 33 그대로다(한글 43). 이슈 코멘트의 판단대로 쪽
회계는 별개 축이고, 원인을 특정했다.

`typeset.rs:23374`

```rust
const LANDSCAPE_ROWBREAK_SHORT_ROW_TOLERANCE_PX: f64 = 260.0;
let landscape_rowbreak_bleed = st.layout.body_area.height < 700.0;   // 이 문서 604.8 → 참
```

가로 용지 RowBreak 연속 조각에서 `consumed` 가 가용 높이를 260px 넘길 때까지 행을
계속 얹는다. 32.43px 행이면 8행이 더 들어간다.

**가드를 안 타는 통제군 `pi=4` 가 오늘 이미 그 상태다** — 쪽마다 26행을 그려 본문
하한(699.3px)을 215px, 용지(793.7px)를 121px 넘긴다.

```
수정 전 render_tree_015~022:  Table pi=4 bottom = 914.7   (본문 하한 699.3, 용지 793.7)
수정 후 render_tree_025~032:  Table pi=8 bottom = 935.9   (같은 형태로 합류)
```

이 상수는 `git log -S` 로 task #1672 "행정업무 편람 페이지 과대 분할 완화"(416쪽
→ 383쪽) 단일 문서 캘리브임이 확인된다. 그 문서는 bleed 가 없으면 **과분할**(416 >
383)이고 이 문서는 bleed 때문에 **과적재**(33 < 43)라 오차 방향이 반대다 — 상수를
좁히면 `#1672` 골든이 크게 되돌아간다. 별개 근본 원인이므로 별도 이슈로 분리한다.

## 기존 계약 갱신 — 편람 문서 쪽수

`samples/2025 행정업무운영 편람(최종).hwp` 는 이 정정으로 표 67개 중 43개가 각 1행씩
늘어(총 46행) 쪽수가 383 → 385 가 된다. 세 단정을 갱신했다.

| 위치 | 종전 | 갱신 |
| --- | --- | --- |
| `tests/issue_3931_declared_rowbreak.rs` (native HWP) | 383 | 385 |
| `tests/issue_3930_hwpx_hwp_save_layout.rs` `issue_3820_…` (native HWP) | 383 | 385 |
| `tests/issue_3930_hwpx_hwp_save_layout.rs` 왕복 | `reloaded == source` | `reloaded == 384`, `source == 383` |

`tests/issue_3931_declared_rowbreak.rs` 의 HWPX 단정(383)은 불변이다.

383 은 `#4763` 이 **한컴 2020** PDF 에 맞춘 값이다(모듈 주석 명시). 같은 파일을 한글
**2022** COM 으로 열면 `.hwp`·`.hwpx` 모두 **384쪽** 이라, 383 도 385 도 2022 정답이
아니고 오차 크기는 1 로 같다. 이 문서에서 rhwp 자신의 측정↔렌더 정합은 좋아진다 —
`TABLE_CUT_DRIFT` 어긋난 표 13 → 10개, `|diff|` 합계 113.7 → 57.9px.

세 번째는 고정값이 아니라 왕복 일관성 불변식이었다. 한글 2022 가 두 형식 모두 384 인데
정정 뒤 **저장 HWP 경로가 384 로 정답에 도달**했고 HWPX 원본 경로만 383 에 남아 등식이
깨졌다. 등식을 유지하면 정확해진 쪽을 되돌리라는 요구가 되고 등식을 지우면 회귀 탐지력이
사라지므로, 양쪽을 오라클 기준값과 함께 각각 고정했다. 남은 HWPX −1 격차는 HWP5/HWPX
조판 비대칭 축이라 별도 이슈로 추적한다.

변경 파일 LF 사본에 `rustfmt --check` 를 돌리고 전체 fmt 는 CI 에 의존했다.

### 환경 기록

`#5672` 가 추가한 `src/bin/rhwp-q-more/gen/` 자동 생성 소스 89만 줄(`s00.rs`~`s49.rs`)은
