## 1. 결론

Q3-3은 Q3-1의 문서 kerning 의도와 Q3-2의 exact-font capability를 결합해 pair engine에 진입해도 되는
run인지 판정한다. 판정값은 `not-requested`, `eligible`, `fail-closed`다. 여기서 `eligible`은 kerning이
적용됐다는 뜻이 아니다. 후속 pair engine이 실제 glyph identity·cluster와 adjustment를 비교한 뒤에만 최종
disposition인 `applied` 또는 `no-pair-adjustment`를 만들 수 있다.

run 입력은 code point 4,096개까지만 허용하고 판정을 위해 최대 4,097개까지만 순회한다. glyph는 4,096개,
인접 candidate pair는 4,095개로 제한한다. 상한 초과나 unsupported capability는 pair 값을 추정하지 않고
현행 advance를 유지하는 `fail-closed`로 닫는다.

## 2. 판정 계약

| request | capability·run 상태 | gate | fallback reason |
| --- | --- | --- | --- |
| disabled | 무관 | `not-requested` | 없음 |
| enabled | code point 4,096 초과 | `fail-closed` | `run-code-point-limit-exceeded` |
| enabled | glyph 4,096 초과 | `fail-closed` | `run-glyph-limit-exceeded` |
| enabled | unsupported capability | `fail-closed` | Q3-2의 구조화된 이유를 보존 |
| enabled | 지원 capability, 상한 이내 | `eligible` | 없음 |

상한이 동시에 초과되면 code point를 먼저 보고한 뒤 glyph를 판정한다. 이는 결정적 진단 우선순위일 뿐 다른
초과를 숨기지 않는다. trace에는 각각의 `limitExceeded` boolean이 함께 남는다.

## 3. bounded trace

`KerningRunGateDecision`은 다음 정보만 직렬화한다.

- request, capability, gate, fallback reason
- exact source SHA-256, byte 수, face index, units-per-em
- 상한으로 clamp한 code point·glyph 수와 각 초과 여부
- 최대 4,095로 제한한 candidate pair 수

원문 text, 문서 경로, font bytes는 trace에 넣지 않는다. 50,000자를 더 붙인 공격성 입력도 code point
4,096, glyph 4,096, candidate pair 4,095로 기록되고 `fail-closed`한다. pair별 trace 레코드는 아직 생성하지
않는다. Q1의 run trace record 4,096 상한은 후속 pair engine이 레코드 배열을 도입하는 절편에서 적용한다.
