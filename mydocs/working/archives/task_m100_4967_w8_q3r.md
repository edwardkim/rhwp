# Task M100 #4967 Stage W8-Q3R — same-snapshot evidence query

- **계획**: [`task_m100_4967.md`](../../plans/archives/task_m100_4967.md)
- **선행 판정**: [`task_m100_4967_w8_q3.md`](task_m100_4967_w8_q3.md)
- **권한 경계**: 읽기 전용 query 보강, 제품 font 정책 변경 없음

## 1. 수정 이유

Q3은 `export-render-tree`, `rhwp-q-text-layout`, Font Decision Trace를 각각 실행했다. 각 도구가 별도로
페이지 tree를 만들기 때문에 2문서의 run set이 달라졌고 target 4,397자를 actual frame에 결합하지 못했다.
독립 결과를 더 정교한 휴리스틱으로 이어 붙이는 것은 원인을 해결하지 않는다.

## 2. 승인된 수정 계약

한 번 만든 `PageRenderTree`를 다음 세 증거가 함께 소비한다.

```text
one build_page_tree(page)
  -> existing font decision trace records
  -> TextLine frame/context + exact run-index membership
  -> stored-row cache disposition or fail-closed unmodelled reason
```

기존 `get_font_decision_trace_native`의 JSON과 hash는 호환성을 유지한다. 새 결합 query는 분석용 read-only
surface이며 문서 IR, pagination, metric DB, registry, fallback, paint와 supply를 변경하지 않는다.

## 3. 판정 의미

- `admitted`: 현행 cache key가 actual frame의 physical-row geometry를 정확히 재현했다.
- `rejected`: 현행 frame이 source stored row를 재현하지 못해 fresh partition이 필요하다.
- `unmodelled`: wrap·legacy·source mapping 등 필요한 frame provenance를 query가 온전히 소유하지 못한다.
- `notApplicable`: authoritative stored row가 없는 fresh 또는 synthetic lane이다.

`unmodelled`을 `rejected`나 `admitted`로 바꾸어 세지 않는다. 이 구분은 HWP/HWPX 버전이 아니라 현재
문단과 frame의 기능 탐지 결과다.

## 4. 검증·중단선

- 쪽당 page-tree build 1회
- 기존 trace canonical output·hash 불변
- trace record와 TextLine run-index join 누락 0
- `maxCharacters` 4,096 상한 유지
- 공개 fixture로 disposition 각 경계 검증
- private source·경로·본문·식별 hash와 font bytes tracked output 0
- 동일 6문서만 제한 재실행, 10k 전수·Hyper-V 0

actual frame provenance를 안전하게 복원하지 못하거나 기존 trace 호환성이 깨지면 구현을 넓히지 않고 다시
`blocked`로 보고한다.

## 5. 구현·계약 검증 결과

새 `get_font_layout_evidence_native`와 `rhwp-q-font-layout-evidence`는 쪽당 page tree를 한 번 만든 뒤 기존
Font Decision Trace, TextLine frame/context, exact run-index membership와 stored-row disposition을 함께 낸다.
기존 trace 계산은 이미 만든 tree를 받는 내부 함수로 분리했으며 standalone trace의 JSON 값·hash와 결합
query 안의 trace가 의미상 동일한지 공개 fixture에서 확인했다. standalone API의 직렬화 결과도 기존 회귀
테스트로 그대로 고정했다.

| 공개 계약 | 결과 |
| --- | ---: |
| page tree build | 쪽당 1 |
| unframed run | 0 |
| trace run ↔ line membership | 전건 1:1 |
| `admitted` fixture | `field-01.hwp` |
| `rejected` fixture | `rowbreak-problem-pages.hwp` |
| `unmodelled` fixture | legacy `hwp3-sample16.hwp` |
| 기존 trace 상한 | 4,096 유지 |

## 6. 동일 6문서 제한 재판정

Q0의 같은 6문서·534쪽만 다시 읽었다. 10k 전수·Hyper-V·제품 source 변경은 0이다. 이전 Q3에서 독립 query
사이의 run set 차이로 frame을 잇지 못했던 4,397자는 0으로 해소됐고, target line은 1,930개에서 2,043개로
완전 결합됐다.

| cache disposition | target 문자 | target 줄 |
| --- | ---: | ---: |
| `admitted` | 15,788 | 706 |
| `rejected` | 10,187 | 316 |
| `unmodelled` | 18,142 | 1,021 |

metric-capacity projection은 overflow 제거 217줄, slack 증가 114줄을 보였지만 회귀도 5줄이었다. 회귀 5줄은
`admitted` 4줄, `rejected` 1줄이며 `unmodelled` 추정에 기대지 않는다. 특히 Q3의 표 셀 target 9자
`+144 HWPUNIT = +1.92px` overflow 신규 사례는 정확한 cache key를 통과한 `admitted` 줄로 확인됐다.

문서 분류는 `unmodelled` 4건, `worsened` 2건이다. 개선 줄이 있더라도 같은 문서 안의 modelled 회귀를
평균으로 상쇄하지 않는다.

## 7. 판정

rank 8 일괄 exact metric 교정은 `no-change`다. 미해석 18,142자는 후보를 승인할 때라면 차단 사유지만,
이미 현행 cache policy가 소유한 줄에서 회귀 5건이 증명됐으므로 후보 기각에는 추가 해석이 필요하지 않다.
따라서 W8-Q4로 진행하지 않고 제품 metric DB·registry·fallback·paint·supply를 그대로 둔다.

```text
sameSnapshot=true
pageTreeBuildsPerPage=1
unframedTargetCharacters=0
decisiveModelledRegressionLines=5
status=no-change
productMutationAuthorized=false
fullCorpusPass=false
hyperVOracleRerun=false
```

## 8. push-preflight 계수기 격리 정정

Q5 보고서 승인 뒤 기본 병렬 `regression_suite_009`를 실행하자 same-snapshot test의 process-global
`PAGE_TREE_BUILDS`가 같은 binary에서 동시에 실행된 다른 테스트의 build까지 세어 기대 1, 관찰 4로
실패했다. 해당 테스트 단독 실행과 140건 직렬 실행은 통과했으므로 제품 query의 다중 build가 아니라
검증 계수기 격리 결함이다.

기존 전용 프로세스 성능 가드가 사용하는 전역 counter는 그대로 두고 current-thread page-tree counter를
추가했다. #4967 계약은 다른 스레드에서 실제 page tree를 한 번 만든 뒤 현재 스레드 count가 0인 것을
확인하고, same-snapshot query 뒤 정확히 1이 되는 것을 판정한다. query JSON과 제품 font·layout 동작에는
변화가 없다.

fresh `--prepare` 뒤 정식 배치는 `regression_suite_008`이며 기본 병렬 3회 420/420과 직렬 140/140을
통과했다. 기존 process-global 성능 가드 4건, Python 17/17, Clippy, manifest·문서·fmt 검사와 Docker
WASM 5분 56초도 통과했고 `pkg` 추적 delta는 0이다.
