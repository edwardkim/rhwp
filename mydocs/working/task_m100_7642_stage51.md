# 이슈 #7642 Stage 51 — 저장 경계의 미주 표 점유 측정

Issue: #7642

## 독립 출력과 최초 차이

시작 source는 `abb84dd63f1bb773f79297058b6961dd08189570`이다.
2024년 9월 구분선 아래/위 20 HWPX의 독립 한컴 Print 13쪽에는 문20의
증감표가 오른쪽 단 하단에 있다. Native는 표를 14쪽 왼쪽 단으로 이월한다.
13쪽 실루엣은 95.55843%지만 이 배치 결함을 면제하지 않는다. 뒤 14/19쪽은
35.79448% / 33.74395%다. 같은 HWP도 같은 후속 차이를 보인다.

원본 본문 문단 180의 Endnote 내부 문단 5가 이 표를 소유한다. 저장 줄의
vertical_pos는 0으로 되감겼고 앞 내부 문단은 6953에서 시작한다. 표는
treat_as_char이고 명시적 단 나눔이 없다. 저장 줄 높이는 5509 HWPUNIT이나,
실제 표·행·여백의 점유는 렌더 경로에서 확인해야 한다.

## 원인 추적과 수정 계약

실행 로그는 `paragraph.rs`의 저장 되감김 처리에서 단 이월을 확인했다.
앞 문단의 실제 흐름 끝은 단 원점 기준 약 925.3, 가용 높이는 1001.56이다.
`local_rewind_tail_fits`는 이미 등록한 현재 문단에도 future가 있는 측정을
호출한다. 이 경로는 표·float가 있으면 지원 문맥 부족으로 `None`을 반환하고,
빈 measured_tables를 전달한다. 결과적으로 표의 실제 fit을 확인하지 못한다.

현재 문단의 fit은 future 생성 없이 최종 방출과 같은 항목을 후보로 추가하고,
현재 단의 inline 계획·원본 소유·실제 measured_tables를 유지하는 공통
배치 측정을 소비하도록 수정한다. `endnote_paragraph_items`가 일반 문단의
FullParagraph와 빈 표 문단의 Table, 부속 Shape를 원래 순서로 발행하며
실제 emit과 scratch 측정이 이 결과를 함께 소비한다. 명시적 단 나눔·keep_with_next는 유지한다.
측정 실패를 통과로 처리하거나 표 높이를 고정 수치로 줄이지 않는다.
현재 후보가 별도 PageItem이나 float 예약을 필요로 하면, 아직 그 계획을
발행하기 전이므로 이 조회로 fit을 선언하지 않는다. TAC 표·그림·도형과
텍스트는 방출 항목 내부의 실제 배치로 확인한다. 기존 단에 이미 등록된
개체의 계획은 공통 측정에 그대로 전달한다.

소비 경로는 `원본 표 → 공통 방출 항목 → 현재 단 + 후보 → 공통 단 배치의
점유 끝 → 저장 되감김 이월 판정 → 최종 단 배치`다. 실제 측정의 fit과
최종 배치가 같은 소유·원점·표 높이를 소비하는지 실행으로 확인한다.

## 검증 계획과 현재 판정

HWP/HWPX 13/14/19쪽의 새 Native와 fresh WASM을 독립 Print와 비교한다.
13쪽 표의 위치·행 보존과 다음 쪽 첫 문단을 직접 판독하고, 전체 문서 TSV는
후속 검증에서 다시 산출한다. 2022 HWPX 18/19쪽과 2023 HWP/HWPX 19쪽,
2024년 11월 미주 변형을 정상 대조군으로 유지한다.

현재는 원인 분석·수정 준비 단계다. 전체 문서 90%와 확대 판독 전에는
회귀 기대값이나 px 선택자를 변경하지 않으며 완료로 판정하지 않는다.

## 반례와 구현 진행

11월 구분선 없음 HWPX의 13쪽은 63.65353%다. 원본 문단 162의 미주 19
내부 문단 3은 글자처럼 취급하지 않는 3행 RowBreak 표다. Print는 앞 단의
하단에 첫 두 행, 다음 단 상단에 마지막 행을 둔다. Native는 전체 표를 다음
단으로 옮긴다. 이 후보는 별도 표 조판·행 분할이 필요하며 현재 inline fit
조회로 수용하지 않는다. 행 분할 경로의 독립 후속 보정이 필요하다.

초기 연결의 Native 빌드는 580.56초, exit 0이었다. 이후 실제 emitter에서
빈 표 문단이 Table 항목으로 나가는 것을 확인해 공통 항목 생산 결과를
추가했다. 초기 빌드의 frozen binary·source 해시·로그를 별도 이름으로
보존했고 최종 연결 뒤 다시 빌드한다. 초기 빌드를 최종 구현 검증으로
인용하지 않는다. 테스트 기대값·baseline·fixture는 변경하지 않았다.

이전 source `abb84dd63f1b`의 fresh WASM 빌드는 905.01초, exit 0이었다.
HWP/HWPX 8쪽은 각각 98.33020% / 98.33234%이며 Native와 선택 6쪽의
PNG 해시가 같다. 이는 앞선 그림 보정의 증거이며 현재 표 이월 수정의
fresh WASM 증거로 재사용하지 않는다.

## 첫 최종 연결의 검증과 남은 생산 지점

source `70de3f2004b17070febf5907383352f6c8a1e350`의 Native 빌드는
584.28초, exit 0이었다. frozen binary SHA-256은
`37231d91f15660016398b5bd91bcf05a1c7d3d96c132071ae94528893e4938c5`다.
포맷 검사 40.91초·Native Clippy 115.47초 모두 exit 0이다.
2022 HWPX 18/19쪽과 2023 HWP/HWPX 19쪽의 대조군 수치는 유지된다.

그러나 9월 HWP/HWPX 13쪽은 95.55843%로 표가 여전히 다음 쪽에 있다.

실제 표·글줄 점유를 소비자에게 게시하지 않는다. Root의 항목 진입이 지운
content/flow-line 결과가 NaN으로 남아 fit 조회가 측정 불가로 판단한다.

TAC 표의 실제 배치가 흐름 끝·표/본문 내용 끝·줄 상자 끝을 공통 결과로
반환하게 보정한다. 후행 줄간격/문단 간격은 흐름 전진에만 포함한다.
Root는 이 결과를 최종 y와 다음 문단의 점유 소비자 모두에 전달한다.
기존 공백 캐리어의 페인트 원점 변위는 내용의 물리 경계에 남기고 논리
흐름·줄 상자만 기존 문단 흐름 원점으로 옮긴다. 별도 고정 높이·clamp로
fit을 통과시키지 않는다. 수정 뒤 같은 원본·Print·선택 페이지를 다시 검증한다.


## 실제 점유 생산 결과의 검증과 페이지 문맥 누락

source `1af0ae1790578ad04a0530cbb1d398e58255ded2`의 Native 빌드는
381.97초, exit 0이었다. frozen binary SHA-256은
`adc8d6d1ff16e1e244aa1b7f6d432d1622768c101cd087144f8b453e5aa56b3e`다.
포맷 검사 19.36초·Native Clippy 69.95초 모두 exit 0이다.
8개 문서의 선택 16쪽 검증은 종료했고 11쪽이 90% 이상, 5쪽이 미달이다.
전체 페이지 통과나 최신 fresh WASM 검증으로 보고하지 않는다.

9월 구분선 아래/위 20 HWP/HWPX 13쪽은 98.15044%, 19쪽은
97.76191%다. TAC 표는 Print와 같이 13쪽에 남는다. 14쪽은
70.45700%로 여전히 미달이다. 2022 HWPX 18/19쪽과 2023 HWP/HWPX
19쪽의 대조군 수치는 유지됐다. 11월 변형의 non-TAC 표 분할과 9월
미주 사이 20의 후속 배치 차이도 아직 남아 있다.

14쪽에서 최초로 다른 흐름은 원본 본문 문단 180의 미주 20 내부 문단 7,
가상 문단 741이다. 이 빈 non-TAC 그림 host를 scratch는 흐름 전진 없이
측정하고 실제 paint는 저장 줄 예약을 소비한다. 이후 문단 742부터
두 출력의 흐름이 달라져, 미주 21 내부 문단 10을 scratch만 왼쪽 단에
수용한다. 독립 Print는 이 문단을 오른쪽 단의 첫 줄에 둔다.

`para_has_visible_textless_float_shape_item`은 현재 단뿐 아니라 전달된
`PageContent.column_contents`의 Shape 소유를 확인한다. 측정 caller는
현재 단을 별도 인자로 전달하면서 페이지에는 flush 전의 단들만 둔다.
최종 paint는 `flush_column`이 게시한 현재 단을 페이지에서 확인한다.
따라서 같은 host가 서로 다른 분기로 간다. 진단 수치 차이를 고정 높이로
더하는 대신 scratch도 `flush_column`과 같이 현재 단과 후보 항목을
페이지에 게시해 동일한 소유·저장 줄 예약 판정을 소비하도록 수정한다.

소비 경로는 `공통 방출 항목 → 단 + 페이지의 Shape 소유 → 빈 host 판정 →
저장 줄 예약 → 단 fit → 최종 paint`다. 다른 완료 단과 zone 문맥은 보존한다.
수정 뒤 첫 차이의 scratch/실제 원점 일치와 HWP/HWPX 13/14/19쪽,
앞선 대조군을 함께 재검증한다. 회귀 기대값·baseline은 변경하지 않았다.
