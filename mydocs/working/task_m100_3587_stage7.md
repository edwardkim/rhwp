## 1차 검증과 추가로 드러난 결함

제품 `a2bb90745`에서 표 순서 검사 3건과 기존 #3587/#1686/#6795를 합한

같은 제품의 Docker WASM을 실제 Studio에서 새로 수신했음을 SHA-256
`bc676a407be914f56c9def0fc2b7d7c15199358cd5fc9e0d8d31597ce24aae42`로 확인했다.
원본·한컴 cp01/cp02·native 반복 저장본을 각각 새 문서로 열고, 원형 본문 표 6번째 셀을
마우스로 선택하여 Enter 15회를 입력했다. 원형 서명 표가 다음 사본 뒤로 밀리는 순서는
복구됐지만, 한컴 복사본의 다음 제목/본문 표가 겹쳤다.

cp01의 4쪽에서 다음 묶음 제목 표는 y=270.2px, 높이=87.0px인데 본문 표는

### 추가 원인과 수정

#2813의 저장 앵커 기반 통째 배치 구제가 작동했다. `RHWP_DIAG_2813`으로
pi13/ci1의 `verdict=true`를 확인했다. 기존 #6795 보호는 **같은 문단의 연속 조각**만
검사했으므로, 앞 문단의 표가 늘어난 연속 쪽에서는 뒤 문단의 저장 좌표를 잘못 신뢰했다.

테스트 `8989cb9f3`에서 표 쌍의 외곽 영역 겹침 검사를 추가하자 2 PASS / 1 FAIL이다.
실패는 cp01 4쪽의 이전 서명 표와 다음 본문 표가 710.6×2.9px 겹치는 지점부터 검출됐다.
로그: `output/3587/b3/reedit-geometry-red-targeted.log`.

제품 `a6ac61b67`은 이 쪽에 연속 표 조각이 있으면 소유 문단에 관계없이 저장 앵커의
통째 배치 구제를 거부한다. 표 크기·offset·명시적 쪽나누기는 바꾸지 않고 기존 잔여 공간
판정 및 이월 경로로 처리했다. 재검증은 2 PASS / 1 FAIL이었다. cp02의 다음 쪽에는
앞 표가 **통째로 이월**되어 연속 조각 표시가 없었고, 다시 뒤 묶음의 통째 배치 구제가
발동했다. 이 중간 수정만으로 완료하지 않는다.

제품 `c9ee96527`은 저장 배치 구제에도 `현재 소비 높이 + 표 선언 높이 ≤ 가용 높이`를
필수로 한다. 저장 구제의 역할을 셀 실측 팽창의 보완으로 한정하고, 이미 소비된 공간을
되감아 뒤 표를 강제로 넣지 않으려 했지만 **보호 테스트 실패로 기각했다**.
집중 검증에서 #2813 정상 서식이 2→3쪽으로 과분할됐다. 현재 소비 높이에는 이미 앞 표의
셀 실측 팽창이 포함되어 있어 이를 저장 frame 적합성 조건으로 사용할 수 없었다.

제품 `0d49f516b`은 이 단순 잔여 공간 조건을 제거하고,
`host 시작점 + 선언된 스택 전체 높이 ≤ 저장 앵커 줄 시작점`으로 바꿨다.
이는 같은 host 내부의 셀 실측 팽창과, 앞 문단이 밀어낸 host 원점 이동을 구분한다.
해당 제품의 집중 검증을 별도로 수행한다.
