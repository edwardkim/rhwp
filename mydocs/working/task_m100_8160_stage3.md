# #8160 단계 3: 2020 WMF의 공통 장치 재생

## 시작 상태와 완료 조건

작업 브랜치는 `task/8160-sample16-raw100`이고 source head는
`f3408d9cc16a8fac9092946f52d898250b7a3f16`이다. 단계 2의 제품 변경은 모두 일반
커밋으로 고정했다. 원본 BCP 두 줄을 숨기던 예외도 `f0f434b8f`에서 제거했다.
기존 잘못된 한 줄 기대값은 아직 바꾸지 않았다. 세 문서의 전쪽 Native와 fresh 표준
최적화 WASM 384쪽 raw 100%·양방향 미대응 0 확인 뒤에 회귀를 정정·통합한다.

Native 후보 29는 190/192쪽, 같은 source의 표준 WASM은 184/192쪽 raw 100%다.
38쪽 HFT 잉크 폭과 39쪽 JPEG 디코드 보정 뒤 후보 30을 clean worktree에서 표준 release로
빌드 중이다. 빌드·최적화·전쪽의 실제 종료를 확인하며 진단 그림으로 제품 완료를 대신하지 않는다.

## 원인과 독립 근거

- WMF 안의 고색수 불투명 사진도 일반 Print 그림과 같은 폭 의존 JPEG 전달을 사용한다.
  반복 자원은 문서의 첫 사용 품질을 공유한다. 순서를 뒤집은 독립 표본도 확인했다.
- PDFium은 내부 사진을 최종 장치 사각형에서 면적/선형 표본화한다. 그림 전체를 SVG의
  원본 격자에서 한 번 래스터화해 축소하면 사진 경계와 벡터 글자의 장치 위상을 잃는다.
- 비트맵 패턴 마스크는 개체별 원본 격자에서 합성한다. 벡터 형제와 글자를 함께 그
  격자에 고정하지 않는다. 기존 PNG/SVG crop·그림 효과·모델의 내용과 소유는 보존한다.
- 원본 WMF의 Polygon 뒤에서 PDF writer의 숫자 직렬화가 6자리에서 3자리로 바뀌고
  다음 그림에도 유지된다. 독립 Polygon 전/후/중간 배치 12개로 재현했다.
- GDI의 기본 폭은 실제 공급 SFNT의 평균 폭과 장치 배율에서 반올림된다. 합성 굵기는
  실제 일반 face를 쓰는 경우의 별도 폭이다. 원본 Dx와 실현 폭이 같으면 기본 glyph
  전진을 내보내고, 다르면 정규화 폭과 Dx 차이를 PDF text adjustment로 직렬화한다.
  특정 글자·문서 ID·쪽수·좌표 상수로 이 조건을 대신하지 않는다.

별도 `wmf-size-dx-independent.hwpx`는 12개 크기·두 굵기·세 Dx와 역순 대조를 갖는
2쪽 입력이다. 새 MCP 2020 job `72d98e4e-0f97-4de2-841b-7fc617d3a3d1`은 실제
11.0.0.9136·Print method 0·`hancom2020_pdf_driver_one_up`으로 성공했다. GDI 평균 폭
반올림은 win10-ted의 메모리 DC와 Hancom PDF 정보 DC에서도 읽기 전용으로 대조했다.
실행 중인 GUI를 열거나 로컬 PDF 변환으로 기준을 대체하지 않았다.

독립 표본의 간격을 대조 중이며 정규화 1/1000em 경계의 차이까지 기록한다. 원본에서
만든 별도 재생 진단은 18·35쪽 그림 영역 양방향 미대응 0이며 확대 판독을 완료했다.
이 진단은 제품 renderer에 아직 연결하지 않았으므로 190/192 결과에 합산하지 않는다.

## 구현 순서와 소비 경로

1. WMF 변환기는 opt-in source 계약으로 창·원본 LOGFONT·레코드 순서를 보존한다.
   일반 변환과 저장 원본을 바꾸지 않는다.
2. 문서의 source 사용 순서로 자원 전달 품질과 직렬화 상태를 공통 생산한다. 요청한
   페이지의 순서나 프로세스 전역 mutable 상태로 첫 사용을 정하지 않는다.
3. 공통 Print producer가 실제 공급 글꼴·GDI 프레임·자원 전달을 소비해 글자 윤곽과
   내부 그림의 재생 자료를 마련한다. 글꼴이 없거나 증명하지 않은 변환은 기존 경로로 보존한다.
4. Native·Canvas2D·CanvasKit은 최종 장치 변환만 공통 재생기에 전달한다. 사진의
   디코드는 각 host의 실제 codec을 사용하고 프레임·표본·합성은 공통 결과를 소비한다.
   배율 변경과 비동기 최초 로드도 확인한다. 96dpi의 완성 PNG만 만들어 확대하지 않는다.
5. 경계 진단 뒤 전쪽 Native와 fresh 표준 최적화 WASM을 다시 실행한다. 결과가 모두
   100%일 때 기존 검사 감사·정정·병합과 전쪽 회귀 등록 단계로 넘어간다.

공유 Cargo target의 후보 30 빌드가 끝날 때까지 다른 Cargo 명령을 병렬 실행하지 않는다.
기존 산출물·사용자 변경·다른 PR의 정오표·브랜치 정책 문서는 수정하지 않는다.

## 후보 30의 실제 전쪽 결과

clean `f3408d9cc16a8fac9092946f52d898250b7a3f16`의 표준 release 빌드는 exit 0,
1,811.784초다. 실제 rlib+cdylib·manifest LTO·wasm-opt `-O`와 package/public 해시
일치를 확인했다. HWPX·2024 HWP의 WASM 64쪽씩은 모두 raw 100%이고 양방향 미대응 0이다.
2022는 61/64쪽이며 18쪽 15/6, 35쪽 0/67, 38쪽 4/5픽셀이 남는다(후보/참조 방향).
정수 미대응 재계산에서도 같은 결과다. 세 전쪽 실행은 exit 0(106.28/95.81/66.61초)이다.
완료 쪽은 189/192이며 `candidate30-standard-wasm.json`에 source·package·입력/PDF와
실제 실행을 연결했다. Native 29의 190/192와 서로 다른 source 신원을 섞어 최종 완료로
판정하지 않는다. 2022의 38쪽은 같은 HFT 잉크 계약의 공급 경계를 추가 확인한다.

## 원본 계약 전달의 첫 구현과 검증

`SVGPlayer::with_source_contract` opt-in은 요소를 그릴 때의 원본 창·LOGFONT의
높이/폭/각도/굵기/italic·map mode·글자 정렬·선행 Polygon 사건을 메타데이터로 보존한다.
그림 전체에는 마지막 source 창과 Polygon 유무를 보존한다. DC Save/Restore가 이 source
사건의 순서를 되돌리지 않으며, 실제 숫자 반올림은 여기서 수행하지 않는다. 기본 변환에는
메타데이터가 없고 새 2020 consumer 연결은 아직 진행 전이다.

현재 제품의 WMF 모듈을 별도 rustc 진단에 직접 포함해 69개 WMF를 대조했다. 성공한
67개는 계약 메타데이터를 제거한 SVG가 기본 출력과 바이트 단위로 같고 1,039개 text의
원본 속성이 보존된다. Polygon 전/후/중간의 독립 12개는 각각 0/0·1/1·0/1 사건을
보존한다. 나머지 2개는 새 크기 표본의 stock font 선택을 기존 변환기가 지원하지 않는
같은 오류를 양쪽 모두 반환한다. 이를 성공으로 세지 않는다. 이 진단은 실제 WMF 모듈을
컴파일하지만 이미지 디코드·family alias는 진단 adapter이므로 정식 빌드로 대신하지 않는다.
최종 source의 Native lib Clippy는 exit 0(1분 27초), WASM lib Clippy는 exit 0(1분 39초)다.
새 회귀 등록·기대값 변경은 없다. 세부 값은 `wmf-source-replay-contract.json`에 기록한다.

GDI 폭 진단은 실제 공급 SFNT의 `xAvgCharWidth`와 hmtx를 사용한다. 평균 폭을 장치에서
반올림한 뒤 glyph 폭과 합성 굵기를 실현하고, 원본 Dx가 실현 폭과 같은 경우와 다른 경우를
구분한다. 이 분기로 원본 35쪽의 첫 글자만 간격이 달랐던 이유를 설명한다. 독립 크기 표본의
정규화 경계 일부에는 1/1000em 차이가 남아 수치가 완전히 같다고 주장하지 않는다.
현재 원본 18·35쪽의 별도 진단은 이 일반 계산과 장치 행렬을 소비해 미대응 0이지만,
아직 제품 전체의 성공으로 합산하지 않는다. 추가 글꼴·배치와 정규화 경계를 확인한다.

## HFT 전용 잉크 예외를 명시적인 glyph 폭 계약으로 통합

2022의 Poppy FACE_NAME 원본은 `alt_type=1`·대체 Batang이다. 원본 HWPX의 같은 이름은
`alt_type=2`다. 2022의 TextStyle은 실제로 `source_font_is_hft=false`,
`fixed_glyph_advances=false`이므로 후보 30의 HFT 전용 잉크 조건에는 들어가지 않는다.
2022 38쪽의 같은 프로그램 공급·잉크 보존 브라우저 진단도 양방향 미대응 0을 확인했다.
이 선언을 HFT로 바꾸거나 같은 이름의 모든 TTF를 HFT로 간주하지 않는다.

Native는 PR #7941의 실제 통합 `84764fa21c96cd5f8a0e158658e4162a4fb3ce9e`부터
명시적인 `fixed_glyph_advances`만 폭을 맞춘다. PR 본문·원 head
`554021bee72b8b5cf30deec20c8ac5a9b15e54c0`·실제 Native 호출 경로를 다시 읽었다.
기존 helper 주석이 참조한 #2189는 실제로 조판의 자간 스필오버 수정
`b85f8533d`·통합 `04201feb0`이며, 일반 글자의 잉크를 전진 안에 축소할 근거가 아니다.
원 이슈와 완료 보고서도 대조했다. 음수 간격·명시적 폭 맞춤의 기존 분기는 유지한다.

같은 명시적 요청을 공통 `canvas_cluster_fit_scale`의 진입 조건으로 옮기고, 이번 작업에서
추가한 HFT registry 한정 예외 두 개를 제거했다. 글꼴 공급·저장 유형·원점·다음 글자 전진은
바꾸지 않는다. 이 수정의 최적화 WASM 전쪽과 정상 대조군은 다음 후보에서 확인한다.
기존 회귀검사와 기대값은 아직 변경하지 않았다.

이 공통 조건의 Native lib Clippy는 exit 0(1분 27초), WASM lib Clippy도 exit 0
(1분 31초)다. 현재 제품의 fresh 표준 WASM 결과는 아직 후보 30이므로 이 lint와
브라우저 원인 진단으로 새 source의 전쪽 완료를 주장하지 않는다.
