### #7833 짧은 그림 줄의 HWPX 캐럿·그림 원점

### 계산 분할 표 뒤 앞 간격의 소유와 독립 반례

기존 실제 저장본의 `split_float_successor_spacing_before`는 저장 사다리로만 앞 간격
흡수를 판단했다. 그러나 공개 API에서 생성한 계산 빈 호스트도 이어받기 조각은 단 위끝을
공유한다. 실제 소비 경로는 `PartialTable(is_continuation) → place_fitted_paragraph →
split_float_successor_spacing_before → record_float_pushed_line_spacing → layout의
float_pushed_line_spacings`다. 측정 전진과 실제 문단 배치가 이 확정 앞 간격을 함께 쓴다.

3556에서 같은 공개 입력에 applyParaFormat(spacingBefore=0/30000)을 적용하고 각각
HWP/HWPX로 내보냈다. 유효 앞 간격은 0/200CSSpx다. MCP2020 11.x PrintMethod0의
독립 0간격 출력은 2쪽 다음 문단 y310.7180이며, 200간격 HWP 출력은 y332.2944다.
단 위끝132.2667 + 200이 표 점유 끝310.7467보다 큰 경우에는 그 차이만 더하는
`max(단 위끝 + 앞 간격, 조각 점유 끝)` 계약과 일치한다. 앞 간격을 무조건 0으로
만드는 보정은 이 반례를 위반한다. 실제 작업·SHA는 3557, 벡터 text span은 3559다.

계산 빈 호스트인 경우 기존 공통 앞 간격 함수를 사용하도록 연결했다. 실제 저장 줄의
유효성 조건은 유지한다. 문서명·행 수·20px를 구현 조건으로 추가하지 않는다. 일반 통째
표는 호출 대상이 아니며 기존 한컴 저장본도 기존 저장 사다리 계약을 유지한다. Native224
빌드는 실행 중인 fresh062가 종료된 뒤 공용 target에서 순차 수행한다. 기존 36개 및
0/200 앞 간격 반례, 관련 표·캐럿 검사를 재검증하며 기대값은 유지한다.

3556 생성 스크립트 첫 실행의 fromBytes API 이름 오류는 new HwpDocument로 수정해
실제 입력을 다시 생성했다. 자료 생성 실패를 제품 실패나 통과 증거로 세지 않았다.

700CSSpx 앞 간격의 추가 HWP/HWPX 반례는 원 엔진에서 3쪽이지만 독립 Print는 2쪽이다
(3564~3566). 다음 문단의 PDF 상단은 2쪽831.7486이다. 배치 뒤 흡수만으로는 이 잘못된
fit을 고칠 수 없다. 계산 분할 표 뒤의 남은 앞 간격을 fit 전에 현재 단의 기존
`float_pushed_line_spacings`에 확정하고, `spacing::confirmed_format`이 그 값을 읽어
fit·빈 문단·전진·넘침·분할의 같은 높이 뷰를 만든다. paint도 같은 단 기록을 받는다.
단 전환은 기존 기록을 비우므로 줄 분할은 새 단에서 원래 fmt를 다시 읽는다. 기존
저장 사다리의 늦은 간격 흡수는 그대로 유지하며 계산 경로만 이중 적용을 피한다.
