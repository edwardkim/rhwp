# 단계 1199 실제 프로그램 굵기와 시스템 합성 굵기의 분리

Issue: #7642. 검증 기준 `463c48cc228170b576c832591b76826116e86a49`, 선행 구현 `cac7fcf3929f569dd00d951940c72570402a92d9`.

## 완료한 실행과 판독

단계 1193 Native 빌드는 공용 `target/pr-review`, 빌드 잡 8개로 성공했다. 같은 산출물에 정식 `verified_justification_edge_spaces` 3개 검사를 연결해 모두 통과했다. 전체 Rust 회귀의 통과를 뜻하지 않는다.

독립 Print와 같은 범위로 다시 출력한 HWPX의 24쪽은 96.14841%에서 **99.90857%**, 25쪽은 92.01111%에서 **99.93384%**가 됐다. 각 review PNG를 직접 열어 본문·보기 표·다음 제목의 줄 소속을 대조했다. `응용프로그램,`이 앞줄 끝에 포함되고 `정보시스템`이 다음 줄에서 분리되지 않아 Print와 대응한다. 원문 PUA와 UTF-16 위치는 보존하고 1:1 표시 문자의 폭을 측정 경로 전체에 소비시킨 효과다. 나머지 64쪽과 fresh WASM은 별도 실행 중이며 이 두 페이지로 전체 완료를 선언하지 않는다.

같은 비교에서 주거 계약서와 사회 시험지는 PNG SHA까지 수정 전후 같았다. 합성 굵기 분기가 실제로 적용되지 않았다는 반증이다. 단계 1195는 `FontMgr::match_family_style`이 Gulim·HYgtrE·휴먼명조의 Bold 요청에 weight 700을 반환하지만 **동일 프로그램의 OS/2 usWeightClass는 400**임을 관측했다. 단계 1197의 같은 문자·같은 원점 진단에서 이 시스템 Typeface는 `Font::set_embolden(false)`로도 가상 굵기가 해제되지 않았다. 원래 SFNT를 다시 열면 weight 400으로 확인된다.

## 보정 경로와 적용 경계

시스템의 요청 weight를 실제 Bold face의 증거로 사용하지 않는다. 실제 프로그램의 OS/2와 활성 `wght` 축으로 판정하고 같은 SFNT·TTC index·가변 축을 재적재한다. 시스템이 덧붙인 가상 굵기만 제거한 뒤 기존 독립 Print의 가운데 정렬 fill+stroke 0.02em 계약을 적용한다. 위치·전진폭·원본 속성·장평은 그대로 소비한다. 최종 `draw_text_pass`의 fill 분기에 연결하고 명시적 outline pass는 유지한다.

실제 Bold와 활성 Bold 축은 재적재하지 않는다. 근거가 없는 프로그램도 추정해서 변경하지 않는다. DejaVu Sans와 Liberation Serif의 실제 Bold·Bold Italic은 단계 1199 프로그램 진단에서 적용 제외가 확인됐다. 가변 축의 실제 렌더 대조는 아직 미검증이다. 재적재 전후 slant가 다른 시스템 가상 기울임은 각도 근거 없이 바꾸지 않고 기존 paint를 유지한다. 가족 이름이나 문서 ID로 대상 서체를 정하지 않는다. 같은 Typeface의 프로그램 판정은 캐시해 매 글자마다 파일을 복제하지 않는다.

## 전쪽 기준 비교의 현황

이전 runtime `fa56a97f683fb7ca690ae6a155bf1902bcfc9406`의 고정 Chrome fresh WASM 71개 문서·1110쪽 큐가 종료됐다. 원래 요청한 **55개 문서·853쪽은 모두 90% 이상**이다. 그러나 실제 devel과 같은 조건에서 비교 가능한 938쪽 중 WASM 44쪽이 Decimal 기준 0.01%p 이상 하락했다. Native의 선행 하락은 61쪽이다. 두 결과는 새 구현 전체의 최종 결과가 아니며, 이 하락을 보정해야 제출할 수 있다.

base에서 쪽수가 다른 4개 입력은 대응을 임의로 만들지 않아 비교 불가로 유지했다. `sample16-hwp5`·`additional-1`은 65/64쪽, `all-16`·`all-17`은 23/22쪽이다. 현재의 90% 통과, 평균 상승 또는 다른 페이지 개선으로 이를 통과 처리하지 않는다.

실행 명령·전체 TSV·입력/PDF/producer SHA·PNG·브라우저 SHA는 ignored `output/pr-review/issue7642/failed-inputs-20261008/stage15-current-validation/`의 단계 1193·1194·1195·1197·1198·1200에 보존한다. 새 Native paint 보정의 빌드·영향 쪽 재출력과 fresh WASM 전쪽 검증은 완료 후 연결한다. PR 생성·push·CI·merge는 아직 수행하지 않았다.

## 안내 표의 별도 배치 원인

주거 계약서 2쪽의 같은 좌표 밴드를 진단하자 본문은 base 99.44692% / 후보 99.53031%, 아래 서명 표는 99.07746% / 99.06092%였다. **특약 안내 표 밴드가 97.27282% / 57.41755%**로 큰 하락을 소유한다. 이는 원인 분리용 crop이며 전쪽 gate를 대신하지 않는다. 같은 배율의 base/head/Print crop을 직접 열었다.

공개 render tree에서 호스트 문단 33의 안내 표 원점은 base y=519.5, 후보 y=515.0이다. 앞 문단 32와 뒤 문단 35의 글줄 위치는 같고, 안내 표와 셀 내부 글줄 전체만 약 4.5px 올라갔다. 원본 저장 줄의 `vertical_pos=35986`, `line_height=10402`는 표 선언 높이 10122와 상하 바깥여백 140+140을 소유한다. 앞줄의 후행 간격 332HU 및 다음 호스트 앞 간격과의 연결을 실제 수용·배치 경로에서 추적한다. 이 별도 배치 결함을 굵기 보정으로 해결했다고 보고하지 않는다.

선행 fresh WASM 빌드 단계 1196은 release 최적화까지 14분 37초에 성공했다. 원본 source 해시 불변과 root pkg / Studio public의 JS·WASM 해시 일치를 확인했다. source는 cac7fcf이며 이후 Native 전용 수정의 최종 WASM 완료 증거로 대체하지 않는다. 영향 쪽 fresh WASM 비교는 단계 1201에서 진행 중이다.
