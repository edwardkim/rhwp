# 단계 1192 실제 글꼴 프로그램과 합성 굵기 인쇄 계약

Issue: #7642. 기준 `463c48cc228170b576c832591b76826116e86a49`, 수정 전 구현 `4e0ad27591b69cde76dadedc7cbf2910f01fbf57`.

## 독립 근거와 배제한 가정

주거 계약서 2쪽은 전쪽 90%를 통과해도 기준 대비 약 6.72%p 하락했다. 같은 원문/독립 Print에서 공개 문자 원점 1054개를 대응한 진단은 현재 가로 위치가 대체로 기준과 같거나 더 가깝다는 것을 보였다. 이는 실제 raster gate를 대신하지 않으며, 위치를 과거 값으로 되돌릴 근거가 아니다.

실제 Skia trace는 표시 프로그램 Gulim의 선택을 관측했다. 독립 PDF의 TrueType subset과 설치된 Gulim의 한글 175개 `(Unicode, GID)` 쌍에서 분해한 정규화 윤곽선이 모두 같았다. `fpgm`·`prep`·`cvt `의 해시도 같다. 글꼴 결측이나 다른 glyph 프로그램, 임베디드 bitmap strike로 단정할 근거는 없다. 다른 설치 face HYGulim은 이 175쌍 중 16개만 같은 윤곽선이다. 같은 연도·버전 문자열만으로 둘을 같은 프로그램으로 취급하지 않는다.

원본 Print의 굵은 Gulim은 같은 regular glyph를 fill과 stroke로 출력한다. PDF 원시 연산은 `88 Tf`, `2 Tr`, `1.760 w`, CTM 0.120이다. **stroke/글자 크기 = 0.02em**이며, 추출 API가 보고한 `linewidth`를 변환 없이 화면 px로 사용하지 않는다. Skia의 기존 `Font::set_embolden(true)`는 이 가운데 정렬된 fill+stroke 계약과 다른 합성 방식이다.

## 보정 경로와 반례

`CharShape.bold → TextStyle.bold → 실제 Typeface weight 확인 → Skia draw_text_pass의 최종 glyph paint`를 추적한다. 실제 bold face가 없는 regular 프로그램의 **fill** 출력만 같은 glyph에 0.02em stroke를 함께 그린다. 글자 위치·레이아웃 전진·원본 bold 속성·폰트 선택은 보존한다. 실제 bold face, 보통 글자, 명시적인 outline/stroke pass는 기존 경로를 유지한다.

장평은 glyph에 적용하고, 합성 stroke는 문자 크기 기준으로 정의한다. 같은 글자 원점을 유지하며 원래 outline을 검증한 프로그램으로 그린다. 대상 파일명이나 문서 ID, 절대 px 좌표 조건을 추가하지 않는다. 추후 fresh WASM에서도 실제 공급 face의 굵기와 같은 계약을 확인해야 하며 Native 개선만으로 전체 완료를 선언하지 않는다.

줄 나눔의 남은 직접 측정 분기 보정과 함께 Native를 한 번 빌드한 뒤 주거 계약서 전체 3쪽, 사회 시험지 제목, 국어·수학 대표 하락 페이지 및 기존 6쪽 공백 대조군을 먼저 대조한다. 독립 PDF의 원점·glyph 모양·굵기·쪽수·내용 순서를 함께 확인한다. 방향이 검증되기 전 전체 빌드·WASM·전쪽 sweep을 반복하지 않는다. 아직 새 보정의 실행 결과는 미검증이다.

실제 glyph·원점·폰트 프로그램 진단은 ignored 단계 1188·1189·1190·1191에 보존하며 글꼴 바이너리나 glyph outline은 저장소에 추가하지 않았다. 새 실물 회귀 검사 추가는 수정 후 Native/fresh WASM의 전쪽 90%와 확대 판독을 마친 뒤에만 수행한다.
