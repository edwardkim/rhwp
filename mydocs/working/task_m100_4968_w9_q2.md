## 1. 결론

Q2는 예상하지 못한 중요한 경계를 확인했다. HWP 2020 `11.0.0.9136`은 HWPX의 `useKerning`을 열기
단계에서 버리지 않는다. HWPML2X readback에서 공개 fixture 22개 context의 K0/K1, 장평, 자간, Noto face가
모두 원문과 일치했다. 그러나 같은 문서를 PDF로 내보내면 body의 9개 통제축에서 K0와 K1 glyph position이
전항 같았고 `AV`, `To`, `WA`, `HH` pair gap 차이도 모두 0이었다.

따라서 한컴 2020 PDF는 이번 fixture에서 kerning flag에 따른 layout differential을 만들지 않는다. 이 결과는
flag 유실이 아니라 “flag 보존 + PDF differential 없음”이다. 다만 양쪽에 항상 kerning을 적용했는지, 양쪽
모두 적용하지 않았는지는 이 비교만으로 결정할 수 없다. differential이 0이므로 장평·자간과 pair adjustment의
적용 순서도 한컴 출력에서 측정할 수 없다.

Q3의 의미를 명확히 바꿔야 한다. K0는 기존 rhwp 출력을 지키는 호환성 계약이고, K1은 공개 font의 OpenType
capability를 기능 탐지해 적용하는 명시적 기능 개선이다. HWP 2020 PDF byte parity를 K1의 정답으로 삼지
않는다. 이 수정 방향의 메인테이너 승인 전에는 제품 구현을 시작하지 않는다.

## 4. HWP 2020 readback 판정

Hyper-V 컨트롤러는 VM과 Standard checkpoint GUID를 호출자가 고정하고 automatic checkpoint가 꺼졌는지
검증한다. 로그인된 Explorer token이 정확히 하나일 때만 one-time Scheduled Task를 실행한다. 공개 Noto font는
`AddFontResourceEx`로 process/session에만 로드하며 시스템 font를 설치·삭제하지 않는다. 성공·실패와 무관하게
`finally`에서 같은 checkpoint를 복원하고 HWP process 0개와 guest staging 부재를 확인한다.

| 항목 | 최종 관측 |
| --- | --- |
| Hancom | `11, 0, 0, 9136` |
| document face 선택/readback | `Noto Sans KR`, exact |
| HWPML | Version 2.91, SubVersion 10.0.0.0 |
| fixture flag | 22/22 보존, K0 11·K1 11 |
| ratio·spacing·face | 22/22 보존 |
| PDF embedded subset | `INPILL+NotoSansKR-Regular` |
| controlled body | 9/9 K0/K1 position 동일 |
| 최대 K1-K0 position delta | 0 |
| 네 pair gap delta | 9축 × 4 pair 전부 0 |

첫 추출은 HWPML 문자열의 `UTF-16` 선언을 유지한 채 UTF-8 bytes로 저장하는 도구 결함이 있었다. VM은 정상
복원됐지만 그 추출물은 채택하지 않았다. 선언을 UTF-8로 정규화한 뒤 동일 checkpoint에서 다시 실행했고,
최종 HWPML은 표준 XML parser로 검증했다. 최종 local-only HWPML SHA-256은
`27e7aef7117ff601405a1631b788321eb55a93efa233c2de4aeeb7eded4cde4f`, PDF SHA-256은
`104ed4e91d3c5978fc0c0e47a4ec90d193bd64ecd97622c38aab7b5d73df5ad3`다.

복원 후 별도 PowerShell Direct session에서 HWP process 0개, guest staging 없음, Explorer 1개를 확인했다.
Windows host의 두 agent-created 임시 출력 경로는 WSL local-only 원장 hash 대사 뒤 제거했다.

## 5. 인과 판정과 한계

```text
HWPX useKerning K0/K1
  -> HWP 2020 open
  -> HWPML2X readback: K0/K1 보존
  -> PDF export: 9개 controlled axis의 glyph position 동일
```

확정할 수 있는 것은 “open에서 flag가 보존됐고 PDF 결과에는 on/off differential이 없다”까지다. 다음은
확정하지 않는다.

- 한컴이 K0/K1 모두에 독자 kerning을 적용했는지, 둘 다 적용하지 않았는지
- 다른 한컴 버전도 같은지
- table/text-box의 동일 결과가 LineSeg와 무관한지: 두 supplementary pair는 서로 다른 lane이라 causal gate가 아님
- differential이 0인 출력에서 장평·자간·pair adjustment의 정확한 적용 순서

따라서 한컴 결과의 역할은 `version-scoped-negative-compatibility-observation`이다. 공개 adjudication은
[`kerning_q2_hancom_adjudication.json`](../tech/investigations/issue-4968/kerning_q2_hancom_adjudication.json),
canonical SHA-256은 `8fce761f58c742a9a6d4fcf1cbfdf7a3037acd8f14f028e5f2c5cd41f64ff1ee`다.

## 6. Q3 수정 방향

1. `kerning=false`는 현행 measurement·position·줄바꿈·paint JSON·SVG를 그대로 유지한다.
2. `kerning=true`는 exact font source에서 GPOS/legacy capability를 기능 탐지한 경우에만 OpenType pair delta를
   적용한다.
3. K1은 한컴 2020 PDF 복제가 아니라 rhwp의 명시적 OpenType 기능 개선임을 trace와 문서에 남긴다.
4. 한컴에서 적용 순서를 관측하지 못했으므로 Q2의 candidate order는 Q3 controlled fixture에서 rhwp 계약으로
   먼저 고정하고 native·WASM에서 동일하게 검증한다.
5. source 없음·미지원·malformed·상한 초과·glyph/cluster 변화는 fail-closed하고 현행 advance를 유지한다.

이 변경은 기존 수행계획의 정답지 역할을 수정하므로 메인테이너의 방향 승인이 필요하다.
