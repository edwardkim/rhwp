## 1. 결론

Q3-4는 Q3-3에서 `eligible`로 판정한 run만 동일 exact face에서 `kern=0`과 `kern=1`로 두 번 shaping하고,
두 결과의 위치 차이를 layout 적용 전 후보로 만든다. 공개 Noto Sans KR의 `AV=-18`, `To=-76`이
`AV To WA HH` run에서 총 `-94` design units로 재현됐고, `HH`는 0이었다. synthetic legacy-only font의
`-70`도 재현했으며 GPOS와 legacy가 함께 있을 때는 GPOS의 `-18`만 사용됐다.

후보 상태는 `adjustment-candidate`, `no-adjustment-candidate`, `not-eligible`, `fail-closed`다.
`adjustment-candidate`는 실제 positions에 적용됐다는 뜻이 아니다. Q3-4는 measurement,
`compute_char_positions`, paint replay에 연결하지 않는다.

## 2. exact face 재사용 경계

초기 구현은 run마다 font SHA-256과 capability를 다시 계산했다. 입력 크기는 32 MiB로 bounded했지만 큰 font를
run 수만큼 반복 스캔할 수 있어 제품 연결 전 정정했다.

최종 구조는 `prepare_kerning_pair_engine`에서 다음 작업을 exact face마다 한 번 수행한다.

1. Q3-2 capability와 실제 source bytes·face index·byte 수·SHA-256·units-per-em 대사
2. `rustybuzz::Face` parse
3. 검증된 face와 capability를 `KerningPairEngine`으로 보존

각 run은 준비된 engine을 재사용하므로 per-run 경로에는 bounded text 확인과 두 번의 shaping만 남는다.
focused integration 전체 실행 시간은 정정 전 0.68초, 정정 후 0.32초였다. 이는 정밀 benchmark가 아니라
반복 hash·parse 제거를 확인한 동일 환경의 시험 시간이다.

## 3. glyph·cluster 보호 불변식

candidate를 만들기 위해 다음 조건을 모두 만족해야 한다.

- run gate가 `eligible`이고 code point·기존 glyph 수가 같은 1:1 nominal 경로
- 좌우 방향이 LTR
- `kern=0` glyph ID·cluster가 exact face의 nominal cmap 결과와 동일
- `kern=0`과 `kern=1`의 glyph 수·glyph ID·cluster가 동일
- shaped glyph 4,096, 인접 pair 4,095, trace record 4,096 이하
- gate와 prepared engine의 source provenance가 동일

조건이 깨지면 위치 delta를 반환하지 않는다. Noto의 `ffi`는 default GSUB ligature 때문에 nominal glyph
identity가 달라져 fail-closed했고, RTL 입력도 이번 W9 경계 밖이므로 fail-closed했다. GSUB·complex-script
shaping 전반은 후행 W10 범위다.

## 4. trace 계약

후보 trace에는 request 원문 대신 다음 bounded 정보만 들어간다.

- candidate status, capability, source SHA-256, face index, units-per-em
- glyph 수, 검사한 인접 pair 수, 조정된 position record 수
- 총 x-advance delta
- glyph index·ID·cluster와 x/y advance·offset delta가 있는 레코드만 최대 4,096건
- 구조화된 fallback reason

원문 text, 문서 경로, font bytes와 `applied=true` 같은 최종 적용 주장은 포함하지 않는다. delta는 design
units 그대로 보존한다. font size·장평·script scale과 결합해 layout units로 바꾸는 순서는 다음 절편에서
단일 함수로 고정한다.

## 5. dependency와 WASM 판정

`rustybuzz 0.20.1`은 기존 native dependency graph에는 `usvg`를 통해 이미 있었지만 WASM graph에는 없었다.
Q3-4는 이를 공통 직접 dependency로 명시했다. `Cargo.lock`에는 새 패키지나 버전 변경 없이 루트 `rhwp`
dependency 목록에 `rustybuzz` 한 줄만 추가됐다.

Docker WASM에서 `rustybuzz`와 관련 순수 Rust dependency가 실제 컴파일됐다. 최종 WASM은 8,978,378 bytes로
Q3-3과 같은 크기이고 SHA-256은
`a0081e2798b4dfc7f78134e65efa1c97b463b0f91a9568d2907eb006850d3aa3`다. 후보 API가 아직 제품 호출 경로에
연결되지 않아 optimizer가 제거할 수 있으므로, 같은 크기를 최종 적용 비용 0으로 해석하지 않는다. 실제
호출 경로 연결 뒤 크기와 run 성능을 다시 판정해야 한다.

## 8. 다음 절편의 진입 조건

메인테이너가 Q3-4 결과와 변경을 승인하면 현재 절편을 커밋한다. 다음 Q3-5는 design-unit candidate를
font size·장평·script scale과 결합하는 단일 순서 함수를 만들고, line measurement와
`compute_char_positions`가 동일 scaled adjustment map을 소비하도록 연결한다. 자간은 인접 문자 간 별도
항으로 유지하며 kerning delta와 중복 scaling하지 않는다.

이 연결부터 K1의 실제 positions와 line break가 달라질 수 있다. 따라서 Q2 controlled fixture의 기대값,
K0 byte/position 불변, native/Docker WASM parity, 실제 호출 경로의 WASM 크기·성능을 같은 절편의 승인
게이트로 둔다.
