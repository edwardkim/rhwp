# R91/R19 착수 게이트 실측 — autofix 봇의 첫 업스트림 PR 품질 확인

## 결론 (먼저)

**착수 게이트 미통과.** 트랙 J `R91`(및 트랙 B `R19`, 같은 기구)의 착수 게이트는
"첫 업스트림 PR 품질 확인"인데, **봇이 업스트림(edwardkim/rhwp)에 연 PR 은 0 건**이다 —
품질을 확인할 "첫 PR" 자체가 존재하지 않는다. DoD("봇이 낸 업스트림 PR 이 오탐 0 으로
머지되고, 열린 PR 캡이 사람 개입 없이 준수된다")의 앞절(오탐 0 머지)은 **분모가 0 이라
계산 불능**이고, 뒷절(캡 준수)만 자명하게 참(0 ≤ 4)이다. `[실측]` → `[완료]` 승격 근거
없음. 로드맵 본문("실패 재현이 초록으로 바뀌어야만 PR 이 열린다")은 **설계**로서는 사실이지만,
**운영 실적**으로는 아직 한 번도 그 지점에 도달하지 못했다는 차이를 명시해야 한다.

봇 자체는 실재하고 상시 가동 중이다 — 시크릿 설정 완료, 2026-07-27 신설 이후
334회 실행(성공 307 / 취소 24 / 실패 2), 30분 주기(체증 회피로 :13/:43)로 계속
돈다. 다만 "발견 루프"가 **기계적으로 결함을 확정(오라클)**하는 데까지는 307회 중
17회(≈5.5%) 도달했지만, 그 확정을 **red→green 수정으로 완결**해 PR 을 여는 데까지는
307회 중 **0회** 도달했다. 병목은 오탐 필터링이 아니라 자동 수정(aider + NVIDIA NIM)의
성공률이다.

## 조사 방법

1. `.github/workflows/rhwp-autofix.yml`(kevin9327/rhwp)을 읽어 봇 정체성과 판정 기구를
   확인 — `env.FORK`=`kevin9327/rhwp`, `env.UPSTREAM`=`edwardkim/rhwp`, 봇 브랜치
   패턴 `fix/issue-{이슈번호}`, PR 제목 `fix: {제목} (#{N})`, PR 작성 계정은
   `github.repository_owner`(=kevin9327, PAT `RHWP_BOT_PAT` 사용 — `github-actions[bot]`
   이 아니라 사람 계정으로 커밋/PR 이 남는다).
2. 업스트림에서 `head.ref` 가 `fix/issue-`로 시작하는 PR 을 전수 대조(REST API 페이지네이션,
   `state=all`) — 저자 필터로 `kevin9327` 매치 여부 확인.
3. 봇 PR 본문에만 나오는 고정 문구("red→green 은 CI 러너에서 기계적으로 검증했습니다")로
   업스트림 PR 전체(open+closed) 전문 검색.
4. kevin9327/rhwp 포크의 현재 브랜치 목록에서 `fix/issue-*` 잔존 여부 확인(봇이 성공하면
   fork 에 push 하는 브랜치 — 머지돼도 자동 삭제되지 않으므로 남아 있어야 정상).
5. `rhwp-autofix.yml` 워크플로의 **전체 실행 이력**(2026-07-27 신설 이후 334회) 각각에
   대해 `hunt` job 의 스텝별 결론(conclusion)을 GitHub Actions Jobs API 로 조회 —
   `upstream 에 PR 생성` 스텝이 `success` 인 실행 수, `이슈 등록`/`오라클 발견 이슈 등록`
   스텝이 `success` 인 실행 수를 각각 집계.
6. 시크릿 설정 여부(`NVIDIA_API_KEY`, `RHWP_BOT_PAT`)를 최근 실행 로그의 진단 스텝
   출력("has_key=true"/"has_pat=true")으로 확인 — 시크릿 미설정으로 인한 구조적 봉쇄가
   아님을 배제.
7. `MAX_OPEN_PRS` 캡(워크플로 `env` 선언값)과 `guard` job 이 매 실행마다 로그에 남기는
   "upstream 열린 봇 PR: N/CAP" 실측치를 대조.
8. 오탐률 계산이 불가능(분모 0)함을 확인한 대신, 오라클-only 폴백 17건 각각의 업스트림
   이슈 번호를 추출해 현재 상태(open/closed, `state_reason`)를 조회 — "왜 PR 로 완결되지
   못했는지"의 방증으로 삼음(PR 리뷰 코멘트가 아예 없으므로 대신 이슈 상태로 근사).

## 오탐률 계산

DoD 는 "머지된 것 / 전체 봇 PR"을 오탐률의 여집합으로 요구하지만, **전체 봇 PR 수가
0**이므로 이 비율은 정의되지 않는다(0/0). "오탐 0"이라는 문구는 참인 동시에 공허하다 —
분모가 없으면 분자도 의미가 없다. 이것이 이번 조사의 핵심 발견이다: **오탐이 통과해서
문제가 아니라, 정탐조차 PR 형태로 한 번도 나오지 않았다.**

대신 파이프라인의 각 단계 통과율을 실측했다:

| 단계 | 통과 실적 |
| --- | --- |
| 사이클 시작(guard 통과, 캡 미달) | 307/307 성공 실행 중 대다수(캡 도달로 쉰 사이클 존재, 로그 표본에서 확인) |
| 오라클이 기계적으로 결함 확정(회귀 테스트가 exit code 로 재현) | 17/307 (≈5.5%) |
| 그 결함의 수정이 red→green 게이트 + 회귀 0 + fmt/clippy/test 3종을 전부 통과 | **0/307 (0%)** |

즉 "탐지"는 산발적으로 동작하지만(약 3주에 17건, ~18시간당 1건꼴), "자동 수정"은
아이더(aider) + NVIDIA NIM 조합으로 **단 한 번도 게이트를 통과한 diff 를 만들지
못했다**. 오탐 차단 설계(red→green 계약)는 실제로 매우 엄격하게 작동하고 있다 —
다만 그 엄격함이 정탐도 걸러내고 있어, "차단 대상 오탐이 없다"가 아니라
"통과하는 무엇도 없다"에 가깝다.

## MAX_OPEN_PRS 캡 준수

캡은 `guard` job 이 매 사이클 `gh api repos/edwardkim/rhwp/pulls?state=open` 를 조회해
`head.ref` 가 `fix/issue-`로 시작하고 저자가 `kevin9327`인 PR 수를 세어 `MAX_OPEN_PRS`(=4)
이상이면 그 사이클을 조용히 쉰다 — 사람 개입 없는 자동 집행 코드가 실재한다(워크플로
94~104행). 다만 **캡이 한 번도 압박된 적이 없다**(열린 봇 PR 이 항상 0이므로 4라는
값이 실제로 시험된 적이 없음) — "캡이 준수된다"는 명제는 참이지만 "캡이 작동을
검증받았다"는 명제는 아직 성립하지 않는다. 로드맵 본문(트랙 J 24행)의 "10 내외"는
실물 워크플로 값(4)과 다르다 — 문서 드리프트로 별도 수정이 필요하다.

## DoD 재확인

> DoD — 봇이 낸 업스트림 PR 이 오탐 0 으로 머지되고, 열린 PR 캡이 사람 개입 없이
> 준수된다.

- **"오탐 0 으로 머지"**: 미충족. 머지된 봇 PR = 0건, 전체 봇 PR = 0건. 계산 불능.
- **"캡이 사람 개입 없이 준수"**: 형식적으로 참(0 ≤ 4)이지만 캡 로직이 압박 상황에서
  검증된 적이 없다.
- **착수 게이트("첫 업스트림 PR 품질 확인")**: **아직 평가 대상이 존재하지 않는다.**
  게이트를 통과시키려면 최소 1건의 봇 PR 이 실제로 열려야 한다.

## 권고

1. `[실측]` 라벨은 유지한다 — 봇 기구 자체(cron, 가드, red→green 게이트, 캡 집행 코드)는
   실재하고 실행 로그로 확인됐다. `[완료]` 승격은 **아직 근거 없음** — DoD 미충족.
2. 트랙 J `track_j_autonomy.md` 24행의 "`MAX_OPEN_PRS` 가드가 열린 PR 캡(10 내외)을"을
   실물 값 4로 정정하는 문서 수정이 필요하다(코드 변경 아님, 별도 후속 작업으로 분리
   가능).
3. 병목이 "오탐 필터링"이 아니라 "자동 수정 성공률 0%"라는 사실을 로드맵 본문에
   반영하면, 다음 착수 판단은 "PR 을 열지 판단"이 아니라 "aider/NVIDIA NIM 수정
   성공률을 어떻게 올릴지"로 재설정돼야 한다 — 예: 반복 시도 수 상향, 다른 모델
   선택, 수정 범위를 더 좁은 스코프(단일 함수)로 강제하는 프롬프트 조정 등. 이
   조사는 원인 진단까지는 포함하지 않는다(범위 밖).
4. 오라클-only 17건 중 duplicate 3건은 guard 의 `exclude` 목록이 제목 텍스트 매칭이라
   재발견을 완전히 막지 못한다는 신호다 — 봇이 향후 같은 근본원인을 다른 파일에서
   반복 보고할 위험이 있다. 별도 이슈로 분리해 트리아지할 가치가 있다.
