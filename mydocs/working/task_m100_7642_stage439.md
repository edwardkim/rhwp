## 실제 결함과 원인

Source437의 실제 Studio print 캡처에서 Canvas2D는 정상 숫자 0을 표시했으나,
CanvasKit compat/default software 경로는 기호 대체 face의 사선 0을 사용했다.
Haansoft Batang의 일반 숫자 경계를 사용하는 투영에 다른 face를 넣어 크기·기준선도
달라졌다. 하네스의 report-only parity 4건 통과는 이 결함을 면제하지 않는다.

입력은 `samples/issue6172/2599643_port_call_form.hwp`이며 SHA-256은
`94b705e86e3894c14d38ffa8469e662426e2ddc3b86aa2013f99a4999afd2f1e`다.
독립 기준은 앞 단계에 기록한 한컴 2020 Print PDF다. 현재 실제 Studio 대체 글꼴과
독립 PDF의 글꼴은 같지 않으므로 이 캡처를 한컴 전쪽 일치 완료로 판정하지 않는다.

## 수정과 소비 경로

`CanvasKitLayerRenderer`의 단자리 PUA fallback은 준비된 Haansoft Batang regular를
우선 사용한다. 없으면 본문 regular face와 기본 face를 기호 face보다 먼저 선택한다.
설치 face가 없는 경로는 실제 숫자 Font의 glyph bounds를 읽어
`singleDigitGeometry`에 전달한다. 공통 em 기준의 내부 잉크 경계로 투영한 결과를
같은 Font의 실제 drawText에 적용한다. 프레임 메트릭과 글자 전진은 변경하지 않는다.
측정 face가 준비된 경로와 다자리 PUA의 기존 경로도 유지한다.

이 수정은 문서·셀 좌표·고정 px 영역을 분기 조건으로 사용하지 않는다.
getter의 baseline 기준 좌표와 em 기준 목표를 같은 font size로 변환하며,
다른 face의 glyph bounds에 Haansoft Batang의 source 경계를 재사용하지 않는다.
