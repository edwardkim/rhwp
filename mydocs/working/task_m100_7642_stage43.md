# 이슈 #7642 — 상대 크기 그림의 저장 프레임 단위 보정

## 독립 근거와 범위

시작 생산 소스는 `3ba6bffa472c1a4d87b512f593d632dd952030ff`다.
원본 `samples/3-11월_실전_통합_2022.hwpx`의 한컴 2024 Print PDF는
`pdf/issue7642-failed-regression-print/3-11월_실전_통합_2022-hwpx-print-2024.pdf`다.
전 21쪽 Native TSV의 최저값 95.23834%와 별도로 4쪽의 그림 축소가 보인다.

원본 구역 0·문단 223·컨트롤 0의 그림은 `SQUARE`, `PARA` 상대 너비
3365(33.65%), 현재 너비 9014 HU, 절대 높이 9446 HU다. 실제 단 폭의
33.65%와 저장된 현재 너비는 같은 약 120의 표시 폭을 설명한다. 기존
helper가 3365를 HU로 바꾸어 약 44.9로 표시한다. 해당 숫자는 원인 진단
관측값이며 문서별 화면 위치나 회귀 기대 px 값으로 사용하지 않는다.

요청 목록의 HWPX 원본에서 상대 크기 그림은 9개 입력의 9개이며 모두
같은 그림의 유효한 현재 크기를 보유한다. 원본 XML과 직접 판독, 그림
소유를 보존한 render tree를 ignored output에 연결했다. 축소 원본·PDF를
새로 만들거나 기존 문서 내용을 바꾸지 않는다.

## 생산 결과와 소비 경로

- 절대 선언 크기의 HU와 상대 선언 크기의 비율을 구분한다. 저장 프레임을
  소비하는 흐름·배치 helper는 상대 축에 저장된 현재 HU 크기를 사용한다.
- 글자처럼 그림의 저장 줄 구성도 같은 단위 해석을 사용하므로 그 공통
  결과를 별도 모듈로 공유한다. 기존 절대 축의 측면 흐름 프레임과 그 밖의
  표시 크기 정책은 기존 계약과 반례로 대조한다.
- `원본 sz/curSz → 공통 저장 크기 → picture_flow_frame_size_hu →
  float exclusion/저장 앵커 측정 → layout_body_picture 원점/그림 bbox`
  경로를 실제 코드로 확인한다. 오른쪽 정렬의 원점과 그림 표시 너비는
  동일한 프레임을 소비해야 한다.
- 원본 속성 자체를 현재 출력에 맞게 수정하지 않는다. 현재 크기 메타데이터가
  없는 상대 축은 유효 저장 프레임과 구분하며, 측정 불가 범위를 완료로
  보고하지 않는다. 편집 후 기준 영역 변경은 저장 줄 재사용과 구분해 검토한다.

## 검증 순서

1. 공용 `target/pr-review`에서 Native를 빌드해 source/binary 해시를 고정한다.
2. 같은 원본 4쪽의 그림, 그래프 및 앞뒤 텍스트를 같은 Print와 비교한다.
   9개 해당 입력과 절대 크기 대조군도 확인한다.
3. 보정 코드의 전쪽 Native/fresh WASM TSV·쪽수와 대표 review를 직접 확인한다.
4. 해당 범위가 모두 90% 이상이고 확대 판독이 끝난 뒤 정식 관계형 검사를
   추가·변경한다. 원본 소유·단 내부 포함·앞뒤 순서와 독립 HU 크기 계약으로
   검사하며 수정 전 FAIL/후 PASS를 확인한다.
5. 최신 소스에서 전체 회귀와 필수 lint를 실행한다. 중단한 이전 nextest는
   통과 근거로 재사용하지 않는다. 전체 요청 범위와 PR/CI/merge는 계속 진행한다.

## 기존에 실행한 빌드와 선택 쪽 진단

저장 크기의 단위 해석을 `stored_picture_metrics::stored_picture_size_hu`에
공통화했다. 줄 구성의 `inline_picture_size_hu`와 측면 흐름 그림의
`picture_flow_frame_size_hu`가 같은 결과를 소비한다. 배제 영역, 저장
앵커, 본문 그림의 오른쪽 정렬과 표시 프레임도 이 크기를 사용한다.
문서 이름·그림 ID·특정 크기를 조건으로 추가하지 않았다.

새 Native 빌드는 exit 0(425.71초), Native Clippy는 exit 0(75.88초),
fmt check는 exit 0(20.09초)다. 실제 소스와 바이너리 해시는
`relative-picture-frame-native-provenance.json`에 고정했다.

| 원본과 독립 Print 대조 | 선택 쪽 | Native 결과 |
| --- | --- | --- |
| 2022년 11월 HWPX / 한컴 2024 | 4 | 95.23834 → 98.74440%, gate passed |
| 같은 HWP / 한컴 2020 | 4 | 98.70619%, gate passed |

새 review를 직접 열어 주머니 그림의 가로 크기와 오른쪽 단 경계 정렬이
Print와 맞는 것을 확인했다. 4쪽에 포함된 다른 그래프·본문의 큰 위치
차이는 보이지 않는다. 수식의 세부 장평·탭 간격 차이는 선택 쪽 점수만으로
면제하지 않는다. 선택 4쪽의 Native 확인이며 전 21쪽과 fresh WASM의
최종 검증, 정식 회귀의 수정 전 FAIL/후 PASS는 아직 미완료다.

## 남은 차이의 일괄 분석과 검증

작업지시자의 추가 지시에 따라 작은 수정마다 빌드와 전체 검증을 반복하지
않는다. 이미 실행한 위 빌드와 대조는 현재 상태의 진단으로 활용한다.
남은 원본 차이와 회귀 실패를 공통 원인·실제 소비 경로·영향 범위별로
정밀 분석하고 관련 수정을 묶은 뒤 Native/fresh WASM·회귀·lint를 일괄
실행한다. 필수 검증 범위나 90% 선행 조건을 축소하지 않는다.

이전 생산 소스의 요청 52개와 추가 3개 원본은 전체 쪽수를 확인했고,
50개는 독립 Print와 같으며 5개는 RHWP가 한 쪽씩 많다. 대표 원본의
마지막 미주 제목은 양쪽 모두 마지막 기준 쪽의 왼쪽 단에 있지만 Native가
큰 폭으로 아래에서 시작한다. 앞 내용의 점유 누적과 간격 소비를 추적하며
마지막 쪽 삭제나 기준 쪽수 증가로 수용하지 않는다. 이 관측과 이전
소스의 110개 실패를 묶은 분석은 최신 전체 회귀의 실패 수를 뜻하지 않는다.

로그·TSV·JSON·nextrun은 ignored output에 보존하며 Git에 커밋하지 않는다.
선택 쪽 진단과 코드 보정을 고정한 중간 단계다. 전체 요청 범위, 관계형
회귀 전환, PR·CI·merge·후속 처리는 계속 진행하며 완료로 판정하지 않는다.
