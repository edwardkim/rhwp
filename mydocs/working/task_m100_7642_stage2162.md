# #7642 WMF 내부 표본의 종횡비와 최종 배치 분리

## 독립 Print의 반례

정상 저장본 35쪽의 기존 geometry 관측(stage2158)에 이어 같은 512×512 WMF를
서로 뒤집힌 18000×9000 / 9000×18000 HWP 단위 사각형에 배치했다. WMF는
명시적 PS_NULL을 생성하는 별도 작성 대조군이다. 정상 입력을 수정하지 않았다.

stage2160은 한컴 2024 MCP `engine=2024`, PDF PrintMethod=0,
`frame_print_to_pdf_ex_one_up`, 실제 빌드 13.0.0.3901로 출력했다.
job `8992660f-903a-4f31-b4c7-2bf746937e0e`는 성공했다. PDF 자원 xref 12는
1500×1500이며 두 서로 다른 최종 배치에서 같은 자원을 재사용한다.
한 방향의 배율만 고르는 가정과 배치 종횡비대로 비균등 raster하는 가정을 모두
반박한다. `stage2161-wmf-aspect-independent-observation.json`에 실제 자원 크기·
변환·입력/PDF 해시를 기록했다. 명령·중간 자료는 ignored output에 보존한다.

공식 진단 입력·독립 PDF는 기존 palette 대조군과 같은 디렉터리에 추가했다.

- `pdf/issue7642-metafile-palette-visibility-20261017/metafile-aspect-explicit-pen.hwpx`
- `pdf/issue7642-metafile-palette-visibility-20261017/metafile-aspect-explicit-pen-2024.pdf`

입력 SHA-256은 `056e286366328fb7d891c306a0a73e46055203095d5f10338ef27053363b42fd`,
PDF는 `9bfe84ec99cea6acd193a0c1f19e76e5caf0ee3ef9bef57a20fe33564cc30ba6`다.

## 공통 원인 보정

`device_size`는 crop·fill·변환을 소비해 전체 표시 크기를 구한 뒤, 두 축의 요구
배율 중 큰 값 하나로 원본 viewport를 raster한다. 최종 ImageNode와 bbox·crop은
변경하지 않는다. 음수·무한대·NaN 입력은 배율을 고르기 전에 거절한다.
표시 위치를 clamp하거나 문서별 해상도를 지정하지 않는다. 기존 장치 상한과
원본 내용·자원 크기·실제 글꼴 source fingerprint 캐시도 유지한다.

## 이전 빌드와 새 검증의 구분

stage2151의 source `84fa650793b8a7677e77f970dc7f6d7ad956ec03` fresh WASM은
exit 0, 739.42초로 완료했다. 고정 package와 Studio SDK가 동기화되었으며 해당
생성 JS·타입도 함께 보존한다. 이 빌드에는 이번 종횡비 보정이 들어 있지 않다.
stage2154의 Native/fresh WASM queue는 그 이전 source의 실제 결과로만 남긴다.

이번 source에서 Native/fresh WASM을 순차 재빌드하고 같은 원본·독립 Print PDF·
Cairo 정책으로 정상 WMF 전체와 가로·세로 대조군을 검증한다. 새 대조군의
전체 페이지 양쪽 90%와 직접 판독 전에는 정식 회귀를 추가하지 않는다.
새 확대 판독·최신 devel 대비 하락·기존 Rust 실패의 보류도 아직 해소하지 않았다.

## 보정 후 실제 Native와 남은 표본 반올림

stage2168은 같은 Rust source 6b363c39ed의 실제 CLI를 306.04초, exit 0으로
빌드했다. stage2170은 93개 항목으로 새 Native/fresh WASM과 고정 devel
fe5725dc38의 재출력을 준비했다. Native의 정상 저장본 HWPX·HWP 전쪽 최저는
95.03221%이며 가로·세로 대조군은 100%다. 이 문서 작성 시 queue 전체와
fresh WASM 빌드는 아직 진행 중이다.

stage2176은 실제 출력 payload를 다시 열었다. 가로·세로 대조군은 서로 다른
240×120 / 120×240 배치에서 같은 1500×1500 PNG를 사용한다. 정상 35쪽의
최종 bbox는 그대로지만 내부 PNG는 **4560×2853**, PDF는 **4561×2853**이다.
첫 관측 코드가 추정한 4561을 실제 값과 같다고 assert해 실패한 기록은 기하
완료 근거로 세지 않는다. 실제 관측 JSON과 PNG 해시를 따로 보존했다.

단순 ceil로 바꾸지 않고 표본 경계를 독립 Print로 분리했다. stage2178·2179의
정사각형 원본은 긴 축을 18000에서 18001 HWP 단위로 바꿔도 PDF 자원이
1500×1500이었다. stage2180·2181은 원본 비율을 768:512로 바꾸고 긴 배치 축을
다음과 같이 출력했다. 두 실행 모두 실제 한컴 13.0.0.3901, PrintMethod=0이다.

|긴 배치 축(HWP 단위)|PDF 자원 너비×높이|
|---:|---:|
|18001|2250×1500|
|18005|2250×1500|
|18007|2251×1501|
|18011|2251×1501|

연속 배율로 두 축을 각각 round하거나 모두 ceil하는 가정으로는 이 표를
설명하지 못한다. 우선 긴 축을 장치 격자로 양자화하고 원본 비율을 소비하는
경계를 더 확인해야 한다. 아직 Rust에 추정 반올림이나 문서별 1px 보정을
추가하지 않았다. 정상 18쪽 raw 96.78116%, 35쪽 98.56538%도 이 남은 차이를
면제하지 않는다. 추가 대조군의 Print·원본·관측은 ignored output에 보존한다.

이 대조군들은 RHWP가 작성한 입력이며 version.xml의 제품 표기는 serializer의
2020 값이다. 2024 출력 장치 자체의 상호운용 계약을 비교하려고 명시적으로
engine 2024에서 Print한 진단이다. 정상 저장본 두 파일은 실제 저장 제품도
2024다. 진단 입력을 한컴의 정상 2024 저장본이라고 보고하지 않는다.
