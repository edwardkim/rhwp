# #7642 Stage 176 — 메타파일의 재생 상태와 한컴 그림 속성 대조

Issue: #7642

## 독립 근거와 확인 순서

Stage 175의 14쪽 진단은 Native에서 10쪽이 미달이다. 한컴 저장 HWP의
BinData 14개는 입력과 바이트가 같지만, Print의 EMF 도형 세 쪽은 그리기
항목이 없다. Native 원문 SVG의 타원은 검은 윤곽·fill none이며 검은 면이 아니다.
이 현상만으로 도형을 숨기거나 기존 golden을 갱신하지 않는다.

Windows `win10-ted`의 기본 작업공간 상태를 확인했다. 기존 작업 트리는
깨끗하며 Cargo/Rust 작업은 관측되지 않았다. 원문 메타파일을 화면 없는
bitmap DC에서 Windows GDI로 직접 재생하고, 기본 상태·명시적 stock pen/brush
대조군을 비교한다. 이 PNG는 한컴 Print 기준을 대신하지 않는 원인 진단이다.
사전 진단의 컴파일 산출물은 해당 host의 기본 작업공간 `target/pr-review`에 둔다.
입력 복사본·PNG·JSON·로그는 ignored `output/pr-review/issue7642/`에 둔다.

같은 HWP를 한컴에서 HWPX로 정상 저장해 그림의 원문 크기·crop·그리기 속성이
어떻게 기록되는지도 대조한다. 입력의 수동 메타데이터와 정상 저장본을 구분하고,
새 대조군의 통과를 최초 실패 입력의 일치로 보고하지 않는다.

구현 변경 전 `원문 기록 → 그림 viewport/crop → GDI/EMF 상태 → 최종 그림`
소비 위치를 연결한다. 실제 원인이 확인되면 적용·비적용 경계를 함께 보정한다.
관련 모든 페이지의 Native/fresh WASM 90% 이상과 확대 판독 이후에만 새 이름의
관계형 회귀를 추가하고, 기존 검사 대체 근거를 기록한다. 전체 회귀·lint·PR·CI와
merge 후속 처리는 이 진단으로 완료 처리하지 않는다.

## 실행 결과와 원인 계층

원문 EMF 4건은 Windows `PlayEnhMetaFile`에서 기본·명시 stock·null 호출 DC
세 상태 모두 성공했다. WMF 10건은 Windows GDI+ `DrawImage`에서 재생했다.
첫 확장 진단에서 WMF handle을 EMF API에 넘긴 실패는 호출 오류이며 원문
결함으로 세지 않았다. 컴파일은 Windows 기본 작업공간의 `target/pr-review`다.

한컴 정상 저장 HWPX는 그림 14개·원문 bytes·crop/imgDim을 보존한다. curSz는
0으로 저장되지만 WMF 그림도 같은 값을 가지므로 이를 근거로 EMF만 숨기지 않는다.
88/108바이트 헤더와 stock 선택을 조합한 12쪽에서 88바이트·stock 생략 조합의
세 도형만 Print에 없다. 나머지 아홉 도형은 출력됐다.
[EMR_HEADER 사양](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-emf/de081cd7-351f-4cc2-830b-d03fb55e89ab)에
따르면 88바이트도 정식 헤더다. 추가 대조군의 성공을 처음 세 입력의 Print 일치로
보고하지 않는다. 변경 전 Native 전체 12쪽은 최저 33.06477%이며 모두 미달이다.

[PlayEnhMetaFile 계약](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-playenhmetafile)은
물리 Frame을 출력 사각형에 대응시킨다. 현재 `Player::open_root_group`은 잉크
Bounds를 같은 크기로 늘리므로, Frame과 Bounds가 다른 입력에서 배율이 틀어진다.
`Header의 Frame·참조 장치 크기 → Player root matrix → page/world transform →
단독 SVG 및 Picture payload`의 연결에서 참조 장치 단위의 Frame을 공통으로 소비한다.
Frame·장치 크기가 유효하지 않은 입력의 기존 Bounds 폴백은 유지한다. 확장 헤더의
micrometers가 유효하면 반올림된 millimeters보다 먼저 사용한다. 고정 DPI·문서 ID로
원본 viewport를 대신하지 않는다.

WMF의 XOR→DPa→XOR에서는 중간 마스크 B가 바깥 XOR 영역 A를 넘을 수 있다.
독립 Print의 바깥 검은 픽셀을 확인했다. 검은 마스크에서 A와 B의 공통 영역은
원래 브러시 색, B 중 A 바깥은 검정이며 흰 마스크에서는 이전 바탕이 남는다.
기존 8×8·한 단위 허용 분기를 제거했다. 검은 B와 브러시색 A를 먼저 합성하고 B 전체의 역마스크를
한 번 적용한다. 보간된 alpha를 중복하지 않으며 같은 clip·요소 순서를 유지한다. 벡터 마스크와
미완성 XOR 순서의 처리는 별도로 유지한다. `BlitDestRect → 상태 기계의 A/B →
finish의 동일 역마스크·두 칠 → 최종 SVG`가 실제 소비 경로다.

원문의 장치 패턴 주기와 cosmetic pen 차이는 이 두 보정과 별도로 남는다.
새 회귀·golden 갱신과 전체 검증 완료를 선언하지 않는다. 두 원인 보정을 함께
Native 빌드하고 원문 전체 대조를 다시 실행한다.

## 보정 후 Native 묶음 및 헤더 경계 보완

생산 SHA `4b86e1c20`의 Native 빌드는 exit 0, 324.465초이며 공용
`target/pr-review`를 사용했다. 동일 빌드로 원문 14쪽·헤더 대조군 12쪽·정상
WMFC 15쪽을 순차 대조했다. 정상 WMFC는 최저 92.83091%, 미달·누락 없음을
유지했다. 진단 14쪽은 최저 13.16977%, 10쪽 미달이고 대조군 12쪽은 최저
32.16762%, 모두 미달이다. 소스 hash 유지 true다. Frame 위치 보정의 효과와
남은 cosmetic pen·장치 패턴 차이를 구분하며 시각 완료로 판정하지 않는다.

Frame 환산에 Micrometers를 사용하면서 기존 헤더 읽기의 위험도 확인했다.
Size에는 Description·PixelFormat 선택 버퍼도 포함되므로 Size만으로 확장
존재를 판단하면 텍스트·pixel format bytes를 장치 크기로 오인한다. 선택 버퍼
offset을 먼저 반영한 고정부 크기로 확장을 읽도록 보완했다. 실제 전체 parser
소스의 독립 사전 검사에서 수정 전 Description 경계 FAIL, 수정 후 Description·
PixelFormat·실제 extension2 대조군 3건 PASS를 확인했다. 실행 파일은 공용
`target/pr-review/release-test/stage176-header-boundary-{before,after}`이며,
소스 hash·입력·컴파일·실행 로그는 ignored output에 있다. 이 결과는 시각 검증이나
정식 렌더링 회귀를 대신하지 않는다. 보완 후 Native 빌드·시각 검증을 다시 수행한다.

최신 upstream/devel fetch 결과 base SHA는 `bfa28a77a2714482f647ee6a7b9aa7f7876d8404`
그대로다. 현재 브랜치에 포함돼 있으며 가져오지 않은 base commit은 없다. Windows
GDI 입력·PNG·로그를 로컬 ignored output에 보존하고 원격 전용 runtime 폴더가
없음을 확인했다. 공유 `target/pr-review`의 실행 파일·캐시는 유지했다.
