# #7642 저장 프레임 이월과 중첩 표의 종료 간격 보정 계획

Issue: #7642. 분석 기준 head는 `26ea4868ed`이다.

## 독립 근거와 관측

1. stage2930에서 기존 #5566 검사는 같은 실행 파일·원본 생성기·검사로
   수정 전 종료 코드 101, 수정 후 0이다. 첫 표 위끝 289.4px, 제목 247.2px,
   뒤 본문 509.1px는 stage2911 독립 Print의 같은 영역과 대응한다.
   그러나 stage2925는 후보 4쪽·PDF 3쪽으로 미달이다. 원본은 최저
   98.09909%이며 #7969 대조군 13개는 모두 90% 이상이다. 최저값은
   99.88926%다(`equation-lim-print2020`). 100%라는 종전 표기는 잘못이며,
   stage2926·stage2934의 실제 receipt를 기준으로 정정했다.
2. 정확한 입력의 문단10은 원래 문단9와 같은 저장 쪽에 속한다.
   문단9의 vpos는 47888, 문단10은 51068, 문단11은 60389HU다.
   현재 실제 첫 쪽이 문단9까지 소비하고 두 번째 쪽을 문단10부터 연다.
   문단12의 저장 vpos=0은 명시적 나누기가 아니다. 한컴 Print는 문단10·11·12를
   같은 두 번째 쪽에 둔다. 현재 코드는 문단12에서 다시 쪽을 열어 4쪽이 된다.
3. `36384689_결재문서본문_화재발생종합보고서(제2026-298호).hwpx`의
   바깥 셀2 문단0은 저장 줄 없는 8×3 TAC 표를 갖는다. 뒤 문단의 원본
   vpos=28760·30040HU와 2020/2024 독립 Print는 일치한다. Native는
   `붙임`을 표 위끝에서 408.5px 아래에 놓아 독립 기대 400.5px보다 8px
   아래다. stage2929 Native 전쪽 점수는 91.90514%이지만 직접 판독 결함이다.

## 원인과 변경할 공통 결과

- 저장 프레임 prefix의 실제 이전 쪽 소비 확인 함수가 텍스트 항목만 인정한다.
  완전한 TAC 표도 같은 저장 줄·소유 문단을 갖는다. 문단10의 실제 쪽 소유와
  문단9까지의 이전 쪽 소유를 같은 계약으로 읽는다. 명시적 나누기, 부분 표,
  dirty·합성 저장 줄은 이 근거로 사용하지 않는다. 실제 쪽 시작이 저장 쪽의
  중간이면 다음 자동 reset을 재배분한다. 정상 저장 쪽 시작은 보존한다.
- 중첩 TAC 호스트의 실제 줄 배치가 이미 소비한 종료 간격에 같은 600HU를
  다시 더한다. 배치된 줄·표의 물리 점유 끝에서 종료 간격을 한 번 확정한다.
  문단 뒤 간격을 버리거나 자식 높이를 줄이지 않으며, 마지막 셀 문단과
  중간 unit cut은 기존 종료 소유 판정을 유지한다. 측정·CellUnit의 동일
  종료 간격 소비와 실제 줄/표 끝을 대조한다.

## 생산·소비 연결과 검증

저장 원본 줄 → 실제 PageItem의 이전/현재 쪽 소유 → section의 자동 reset
판정 → fit·이월 순서다. TAC 쪽은 composed 줄/자식 표의 최종 배치 상자 →
호스트 종료 흐름 → 뒤 문단이다. 둘 다 독립 저장 위치·Print를 유지한다.

두 경계와 원본, #7969를 묶어 Native 검증한다. Native에서 개선을 확인한
코드로 fresh WASM도 검증하며, #7970 등 새 base 기능과 전체 회귀는 최종
후보에서 재검증한다. 기존 실패 기대값은 완화하지 않는다. Native/fresh
WASM 시각 선행 조건 충족 전 새 회귀·golden은 만들지 않는다.
