## 1. 결론

D5-B 최초 9-process 계측에서 나타난 큰 B 비용은 CanvasKit의 `drawGlyphs`가 아니라 Rust가 같은 immutable exact
font source를 layout·layer build마다 다시 해시·parse·복제한 것이 원인이었다. source 등록 시 준비한 identity와
원본 `Arc<[u8]>`를 vertical certificate까지 전달하도록 정정한 뒤 다음 결과를 얻었다.

| 64회 합계 | 정정 전 B p50 | 정정 후 B p50 | 개선 배수 |
|---|---:|---:|---:|
| warm render-tree/layout | 1,142,878,416 ns | 1,909,123 ns | 598.64× |
| layer build | 223,300,253 ns | 658,389 ns | 339.16× |

정정 후 호출당 p50은 layout 약 29.8 µs, layer build 약 10.3 µs다. 절대 SLA를 새로 만들지는 않았으며, 동일
하네스의 before/after effect size로만 기술한다.

## 2. 원인 계보

정정 전 vertical layout은 등록 때 이미 확정한 2,519,996-byte Noto source를 다시 `resolve_exact_font_source`로
SHA-256 대사한 뒤 일반 `shape_bounded_request`가 같은 SHA-256과 SFNT face parse를 반복했다. geometry도 face를
다시 parse했다.

layer publication은 한 단계 더 나아가 fresh `ResourceArena`마다 다음을 반복했다.

1. BLAKE3 resource digest 계산
2. FNV-1a lookup hash 계산
3. 16-byte fingerprint 생성
4. source 전체를 새 `Arc<[u8]>`로 복제
5. face parse와 glyph/weight/width/italic metadata 재추출

actual CanvasKit 9-process 결과에서 B draw p50 11,317,080 ns/64회는 A bracket 안이었고 9/9 pixel BLAKE3가
동일했다. 따라서 backend draw가 원인이라는 가설은 기각됐다.

## 3. 정정 구조

- `ExactFontSourceRegistry` entry가 immutable bytes와 함께 portable BLAKE3, FNV-1a, fingerprint를 등록 시 1회
  준비한다.
- 외부 `ExactFontSourceProvider`는 종전처럼 resolve마다 SHA-256을 다시 검증한다. registry-owned exact key에만
  무해시 accessor를 사용한다.
- vertical shaping은 등록 SHA-256, 한 번 parse한 `ttf_parser::Face`, verified canonicalization을 공유한다.
- certificate가 resource identity와 face metadata를 소유하며 paint는 이를 검증·복제한다.
- `ResourceArena`는 atomic preparation을 통과한 source만 원본 Arc로 intern한다. 일반 font blob API는 바뀌지
  않았다.

별도 장기 cache를 만들지 않았다. bytes와 prepared identity가 같은 registry entry에서 함께 생성·삭제되므로 stale
generation eviction 문제가 생기지 않는다.

## 4. 9-process 정정 후 결과

release profile, process 9개, process마다 warm-up 20회와 본 측정 64회를 사용했다. p95는 표본 9개의 nearest-rank
값이므로 최댓값이다.

| 축 | A1 p50 / p95 | B p50 / p95 | A2 p50 / p95 | B − A bracket p50 / p95 |
|---|---:|---:|---:|---:|
| cold layout | 173,556 / 192,950 | 125,903 / 135,695 | 41,663 / 71,141 | 22,182 / 28,974.5 |
| warm layout 64회 | 566,529 / 689,227 | 1,909,123 / 1,985,750 | 608,765 / 739,650 | 1,263,849.5 / 1,355,123.5 |
| layer build 64회 | 117,996 / 141,591 | 658,389 / 814,123 | 125,889 / 127,693 | 535,787.5 / 693,173.5 |
| JSON serialize 64회 | 2,558,253 / 2,880,207 | 85,535,657 / 100,907,135 | 2,760,206 / 2,825,317 | 82,840,201 / 98,269,577 |
| replay plan 64회 | 212,235 / 233,206 | 67,910,931 / 68,717,688 | 235,305 / 389,776 | 67,687,161 / 68,482,883.5 |

JSON과 replay-plan 비용은 남아 있다. B는 intentional portable payload 2.52 MiB를 JSON에 포함하므로 결과가
3,375,512 bytes이고, 각 serialization은 실제로 그 payload를 내보낸다. 이는 반복 source 준비 결함이 아니며
이번 정정에서 payload 계약을 바꾸거나 별도 schema를 열지 않는다.

## 5. 구조·회귀 gate

9/9 process에서 다음 값이 같았다.

- A1/A2 layer JSON BLAKE3 `b432af74…`, replay plan BLAKE3 `9837a3d0…`

## 6. 비용 이동과 판정

등록 시점에는 종전 SHA-256·byte copy 외에 BLAKE3와 FNV-1a 전수 pass가 1회 추가된다. source 등록은 D5 계약상
timed region 밖이지만 이 trade-off를 숨기지 않는다. 동일 source의 모든 후속 layout·layer build가 그 1회 준비를
공유하므로 반복 조판 환경에서는 비용 구조가 선형 재계산에서 source-entry 수에 묶인 준비로 바뀐다.

correctness·resource hard gate와 성능 정정 결과를 `qualified-performance-correction-result`로 판정하고 자동
승인한다.

## 7. causal WASM size 대조 결과

정정 checkpoint `e7f814330`을 B로 한 detached disposable worktree에서 계획에 고정한 여섯 제품 checkpoint를
최신 순서부터 `git revert --no-commit`으로 역적용했다. 첫 대상 `b1a33b6fc`에서 운영 문서·D4 증적·Studio E2E에
content 및 modify/delete 충돌이 발생했다.

수행계획은 reverse patch conflict를 강제로 풀거나 과거 절대 WASM size를 대체값으로 쓰는 것을 금지한다. 따라서
revert를 즉시 abort하고 disposable worktree를 제거했으며 A/B Docker build는 시작하지 않았다. 기계 판독 결과는
[`w10_q4_d5_b_causal_wasm.json`](../tech/investigations/issue-4969/w10_q4_d5_b_causal_wasm.json)에 고정했다.

성능 정정과 runtime correctness는 통과했지만 causal WASM size hard gate는 `causal-size-unavailable`이다. 이 결과를
자동 승인하고 D5-C correctness·regression 범위를 계속 닫되, 최종 Q4-D 분류는 계획상 `blocked`에서 벗어날 수 없다.
