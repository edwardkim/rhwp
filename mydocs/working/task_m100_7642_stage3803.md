# #7642 앞 호스트 글 조각의 표 바깥 상자 원점 보정

Issue: #7642

## 독립 기대값과 반례

[이전 진단](task_m100_7642_stage3796.md)에서 법령 네 표가 위쪽 바깥여백만큼
높이 놓이는 차이를 확인했다. 원본 HWP5의 네 CTRL_HEADER에서 위 바깥여백 두 바이트만
0·141·283·566 HWPUNIT로 바꾼 대조군을 만들었다. 압축 해제한 본문은 그 네 필드만
다르고 다른 모든 OLE stream은 byte-identical이다. 141 대조군은 본문 변경 없는
압축·CFB 재기록 대조다. 원본 파일을 덮어쓰지 않았다.

한컴 MCP engine 2020의 target PDF, PrintMethod 0으로 순차 출력했다. 구현 전 확인한
141·0·283 대조군은 각각 74쪽으로 완료됐다. 9쪽에서 위여백 141→0일 때 한컴 표 위끝은
199.301351→197.384033px로 바뀌지만, 같은 후보의 Native 표는 197.5px로 그대로다.
32·50·66쪽에도 같은 차이가 있다. Print 좌표는 HWPUNIT의 독립 기대값과 드라이버
좌표 반올림을 포함하므로 특정 px 수치를 구현에 넣지 않는다. 566 출력은 이 문서 작성 시
진행 중이며 완료한 것으로 쓰지 않는다.

74쪽의 다른 표들은 같은 차이가 없으므로 모든 문단 기준 표에 여백을 더하지 않는다.
호스트 글 조각이 선행해 확정한 문단 원점, 이미 확정된 표 계획, TAC·중첩 표·별도 저장
프레임을 구분한다. 정상 대조군과 여백 0 입력을 함께 검증한다.

## 생산과 소비

`layout.rs`의 `PageItem::Table` 진입은 바로 앞 같은 문단의 글 조각을 확인해
`para_start_y`에 그 글을 배치하기 전의 문단 상단을 저장하고 `table_push_floor`에
내용 바닥을 전달한다. 두 값은 가시 글자 유무를 추정해서 만드는 값이 아니다.
`compute_table_y_position`은 이 문단 원점의 오프셋을 바깥 상자로 해석해야 한다.
기존 코드는 저장 앵커를 재선택했을 때만 위여백을 더해, 앞 글 조각에서 이미 얻은
문단 원점에서는 여백이 누락됐다.

앞 호스트의 원점을 전달받은 최상위 비-TAC 문단 기준 TopAndBottom 경로에서 원본
위 바깥여백을 한 번 포함한다. `raw_y → max(push_floor) → 본문 제한 → 최종 원점`의
기존 소비 순서는 유지한다. 이미 확정한 `resolved_table_origin`은 이 함수를 거치지 않으며
중첩·TAC·용지 기준·overlay의 기존 경로도 유지한다. 문서 ID·오프셋 1624·여백 141·
픽셀 위치를 조건으로 넣지 않는다.

측정의 `typeset/table/host_spacing.rs::resolve`는 이 경로의 `outer_top`을 이미 계상한다.
측정에 새 여백을 더하는 대신 실제 배치가 같은 원본 바깥 상자를 소비하게 한다.
반영 지점은 기존 큰 `table_layout.rs`의 해당 조건과 설명만으로 제한했다.

## 검증 상태

구현 뒤 빌드·실행은 아직 미완료다. 새 source에서 Native와 fresh WASM을 각각 다시
빌드한 뒤 원본 74쪽·위여백 대조군·호스트 글/표·다른 앵커 경계를 묶어 검증한다.
이전 source의 점수·165개 차트 검사 통과를 새 코드의 통과라고 보고하지 않는다.
독립 Print 대조군과 Native의 구현 전 관측은 ignored 단계 3800·3801·3802에 보존했다.

전쪽 90%·devel 대비 0.1%p·직접 판독 전에는 새 실물 회귀나 px 핀을 추가하지 않고
기존 기대값도 바꾸지 않는다. 현재 원본 시험지 전체·수식·다른 실패·최종 전체 Rust·
lint·Studio·유입 PR 검증과 PR/CI/merge·옵션 2 기록 PR·후속 처리는 계속 남아 있다.
