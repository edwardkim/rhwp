# #7642 새 쪽 첫 저장 TAC 줄의 기준축 확정

Issue: #7642. 관측 대상 head는 `da5e8bbd1d`이다.

## 실제 결과와 남은 원인

stage2933에서 정확한 두 재현 입력은 PDF와 같은 3쪽이 됐다. 첫 쪽과 마지막
쪽은 90% 이상이나 두 번째 쪽은 26.97741%이므로 완료가 아니다. 원본 3쪽은
최저 98.09909%, 중첩 표 문서는 91.90514%에서 94.16906%로 개선됐다.

동일 immutable CLI의 `RHWP_DIAG_FLOW`·`RHWP_FLOW_DBG`·`RHWP_VPOS_DEBUG`
조회 결과를 stage2933-frame-ownership-diagnostics에 보존했다. 문단10을 새
쪽에 수용한 뒤 흐름 끝은 124.28px로 올바르다. 그러나 source 원점이 발행되지
않아 다음 문단의 HeightCursor가 lazy_base를 49688HU로 역산했다. 표의 원본
시작 51068HU보다 1380HU 낮다. 1380HU는 이미 소비한 뒤 줄간격 1080과
문단 뒤 간격 300의 합이다. 본문 문단11의 실제 잉크 원점은 맞지만 pagination
커서는 18.4px 더 전진하여 다음 표부터 독립 Print보다 아래로 밀린다.

## 공통 소유 규칙과 수정

완전한 저장 TAC 줄을 새 쪽 첫 항목으로 수용할 때, 바로 앞 원문 줄의 전체를
이전 실제 쪽이 소비했고 저장 축은 같은 프레임에서 연속한다면 이 원점은
쪽 가운데 있던 옛 절대 위치가 아니다. 현재 새 쪽 원점에 그 줄을 놓고 동일한
StoredColumnFrame을 fit·paint·뒤 본문에 발행한다. 뒤 간격으로 기준축을
다시 역산하지 않는다.

`TypesetState::stored_tac_page`가 이전 실제 쪽의 마지막 소유 문단·끝 줄을
읽고, `stored_tac::prepare`가 기존 source·실측 높이 검증과 함께 저장 축의
연속성을 확인한다. 반환 plan.source_frame은 기존 commit 경로가 원점과
paint metadata에 같이 기록한다. 부분 표, 명시적 쪽/단 시작, 잘못된 저장 줄,
다른 이전 소유, 원래부터 새 쪽에 있던 양수 앞 공간은 이 경로의 근거가 아니다.

## 검증

두 재현 입력·원본·중첩 표와 #7969를 같은 묶음으로 다시 확인한다. 직전
Native/fresh WASM 검증을 새 코드의 증거로 쓰지 않는다. 기존 Rust 집중
검사는 종료까지 유지하고 이후 같은 두 검사를 새 head로 재실행한다.
TSV·독립 Print·확대 판독의 선행 조건 전에 기대값·golden을 변경하지 않는다.
