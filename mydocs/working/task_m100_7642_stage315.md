# Stage 315 — 펼친 중첩 표의 바깥 프레임 소비 일치

Issue: #7642

## 추가 원인과 수정 범위

Stage 312의 저장 사다리 조건 보정만으로 사회 HWPX가 통과하지 않았다.
Source313의 전쪽 Native는 `exam_social-p1.hwpx` 80.49957%,
`exam_social.hwpx` 80.69494%였다. HWP·수학·과학 정상 대조군의 점수는 유지됐다.
기존 미달을 해결한 것으로 보고하지 않는다.

Source269/313의 실제 `RHWP_DIAG_TAC`·`RHWP_TABLE_DRIFT` 실행을 대조했다.
단순 표의 원점·흐름은 HWP 경로와 같아졌지만, 중첩 표를 담는 투명 wrapper는
HWPX에서 다른 끝점으로 수용되었다. 같은 저장 표를 펼치면 측정은 안쪽 6행을 소유한다.
그 6행 높이를 바깥 1셀 프레임의 전체 높이로 사용하면 padding·여백이 빠진다.
HWP5는 바깥 프레임을 복원하지만 HWPX는 복원하지 않아 닫힌 저장 줄을 거절하고,
paint가 복원한 표 본체의 뒤쪽으로 후속 내용이 되감긴다. 문서별 원점 조절로 해결하지 않는다.

## 생산과 소비 위치

- `height_measurer.rs::unwrapped_table_whole_height`는 안쪽 행 측정과 각 바깥 프레임을 합친다.
- `typeset/table.rs::format`의 effective_height는 두 원본 저장 형식 모두 이 결과를 소비한다.
- 같은 파일의 `fit_measured_for_host`는 wrapper의 높이에 맞춰 안쪽 행을 비례 확대하지 않는다.
- `controls/stored_tac.rs::prepare`의 measured_fits도 같은 복원 전체 높이로 저장 줄을 인증한다.
- 실제 paint는 wrapper 셀·안 여백·내부 표를 재귀 배치한다. fit이 성공한 원점/end는
  `commit_stored_tac_control`과 `layout.rs`의 advance_end 소비로 이어진다.

HWP5의 기존 조건에 원본 HWPX의 같은 저장 프레임 계약을 포함한다.
helper가 실제 투명 wrapper인지 검사하며, 다른 표를 wrapper라고 추정하지 않는다.
쪽수·baseline·golden을 변경하지 않는다. 수정 후 사회 HWP/HWPX 및 수학·과학 대조군의
Native/fresh WASM 전체 페이지를 비교한다. 시각 통과와 직접 판독 전에는 새 회귀를 추가하지 않는다.
