# Stage 109 — 첨자 경계의 미달 원인과 관계형 회귀 준비

Issue: #7642. 전체 55개 원본·853쪽 및 복원 회귀 292개, #1139 전체 범위를 유지한다.

## 독립 기준과 현재 관측

- Stage 108의 16개 구문 경계를 한컴 2020 11.0.0.9136에서 저장하고 Print 출력했다.
  PDF job은 PrintMethod=0, `hancom2020_pdf_driver_one_up`, 1쪽이다. 입력·저장본·
  PDF hash와 job은 `stage108-command-boundary-counterexamples/conversion-pipeline.json`에
  보존했다. 같은 폴더의 `hancom-normalized-equation-properties.json`에 한컴이 만든
  프레임과 기준선, `hancom-print-text-trace.json`에 PDF 원점을 연결했다.
- `a_n+1`의 n/+/1은 같은 작은 글자 크기의 첨자다. `a_{n}+1`의 +/1은
  본문 크기다. 기존 parser 검사의 unbraced n 단독 기대값은 독립 Print와 다르다.
- 고정 db43ff92e Native/fresh WASM의 전쪽 TSV는 둘 다 88.69690%, 한컴과
  같은 1쪽이다. `stage109-command-boundary-sweep/receipt.json`에서 두 실행의
  종료 코드 1과 미달을 확인했다. 이 상태에서 기대값·golden을 갱신하지 않는다.
  최신 점 표시 보정 ee6ee14e4의 빌드 결과로 보고하지 않는다.

## 원인 추적과 검증 순서

같은 원본의 네 표현식·네 크기를 비교하여 첨자 범위와 표시 프레임/기준선 차이를
구분한다. 생산된 LayoutBox → SVG/Canvas2D/Skia/CanvasKit 소비의 실제 경로를
확인하고 전체 회귀에서 수집한 원인과 함께 묶어 보정한다. 공통 수식 프레임을
문서 ID나 고정 px로 맞추지 않는다. 수정 후 Native/fresh WASM 전체 TSV 90%
이상과 직접 확대 판독을 먼저 확인한 다음 독립 관계로 필요한 검사만 변경한다.

전체 nextest는 detached 33c0082f4에서 실행 중이다. 출력 공백이나 중간 실패로
중단하지 않는다. 전체 원본의 고정 db43ff92e 검증도 진행 중이며 새로운 소스의
최종 통과 증거가 아니다. 새 head의 전체 검증·관계형 전환·PR/CI/후속은 미완료다.

## 큰 본체의 위첨자 기준선

직접 비교에서 `(1/6)^4`의 위첨자는 본체 축 근처에 내려오는 실제 결함이 확인됐다.
일반 공개 MATH의 `SuperscriptBaselineDropMax` 항도 현재 fallback에 없다.
[독립 조판 규칙](https://w3c.github.io/mathml-core/#base-with-superscript)은
본체의 잉크 상승부와 첨자 깊이·기준선 이동을 함께 고려한다. 공개 LMM의
MATH 상수는 UPM 1000에서 ShiftUp=363, BottomMin=108, BaselineDropMax=250이다.
한컴 font frame을 이 공개 값으로 임의 대체하지 않고 독립 Print와 구분한다.

9/11/16/22pt Print에서 `x^4`와 `(1/6)^4`의 위첨자 기준선은 각 수식 상단에
대해 같은 위치에 있다. 같은 글자 줄의 위첨자 프레임을 큰 본체에서도 공유해야
한다. 4개 크기만 적용하거나 .37em 등의 추정 상수를 범용 값으로 선언하지
않도록, 기존 font frame 범위의 15개 크기에서 짧은 본체·괄호 분수·보통 분수
세 구조 45개를 한컴에서 재생성해 비교한다. 새 기준 입력은 ignored output에
보존하며 정식 fixture 또는 통과한 새 회귀로 보고하지 않는다.

## 중첩 셀 계약의 잘못된 합성 입력

전체 회귀의 `set_char_shape_id_by_path_reflow_reaches_nested_inner_cell`에서
중첩 helper만 빈 `Document::default()`를 주입하고 글자 모양을 파생 기본값으로
추가했다. 그 기본값의 `base_size`는 0이어서 정상 글자 크기의 40자가 셀 폭으로
줄바꿈한다는 전제를 만족하지 않는다. 같은 모듈의 flat helper는 정식 빈 문서
생성 API의 DocInfo를 보존한다. 중첩 helper도 동일하게 정상 서식표를 보존하고
`set_document`로 캐시를 재설정한다. 기대 줄 수를 낮추거나 재래핑 검사를 제거하지
않는다. 이는 합성 입력의 편집/경로 계약이며 한컴 시각 일치 증거로 보고하지 않는다.

## 분수 위첨자 보정의 생산·소비 연결

- 45개 정상화 결과에서 괄호 분수와 보통 분수의 위첨자 높이·기준선은
  15개 크기마다 모두 같았다. `fraction_sup_frame.rs`에 이 font frame을
  HWPUNIT로 기록했다. prime·한글·중첩 분수/근호/다른 복합 본체는 같은
  일반 글자 분수로 수용하지 않으며 해당 경로를 이 자료로 검증했다고 보고하지 않는다.
- `logical_font_frame::superscript_shift`가 동일한 크기의 단일 글자 위첨자
  기준선과 분수 위첨자 프레임의 차이로 배치 shift를 생산한다.
  `layout_superscript`/`layout_subsup`는 그 값을 소비하며, Root의
  `logical_font_frame::frame_with_style`/`matrix_row_box`도 같은 프레임을
  사용한다. 생산 시 본체 기준선과 실제 자식 위치를 함께 유지한다.
- SVG/Canvas2D/Skia/CanvasKit은 LayoutBox 자식 원점을 사용한다. 마지막
  Equation 원점에서는 저장 frame의 기준선 정렬과 작은 frame의 세로 배율이
  적용되므로, helper만 통과한 것으로 완료하지 않고 새 산출의 이 경계까지 확인한다.
- source의 HWPUNIT frame과 em 비율은 문서의 절대 px 위치가 아니다.
  네 표현식의 전쪽 88.69690%와 내려온 큰 본체 위첨자는 수정 전 실패 증거이며,
  새 head의 빌드·fresh WASM·전쪽 TSV·확대 판독은 아직 실행 전이다.
  공개 MATH fallback의 ink 상승부 전체 처리는 이번 한컴 font frame 증거와
  구분한다. 미실행 분기와 새로운 기대값을 통과로 보고하지 않는다.
