# HWPX 저장의 중복 쪽번호 컨트롤이 한글을 멈춘다 (#6869 · #6871)

작업 브랜치: `fix/6874-master-page-table`
대상: `src/serializer/hwpx/section.rs` · `src/serializer/hwpx/context.rs`

## 한 줄

rhwp 가 한 문단에 `hp:pageNum` 을 여러 개 내보내고 그 슬롯이 문단 텍스트 축에 계상돼,
**한글이 그 문서에서 멈춘다.** 한컴은 같은 문단의 쪽번호 위치 컨트롤을 **하나로 접는다.**

## 이슈가 본 것과 실제

이슈는 "한글이 44쪽→12쪽으로 폐기" 로 기록했다. 정답지(한컴 2024 변환 서버)로 재니
**부분 폐기가 아니라 전면 중단**이다.

```text
  원본(HWP5, 44쪽)   → 44쪽 변환 성공
  rhwp h2x 산출      → status=failed · error=null · elapsed=1200  (20분 타임아웃)
```

12쪽은 한글이 중도 포기한 결과이고, 원인 지점이 아니다.

## 인과 사슬

```text
1. rhwp 가 한 문단에 hp:pageNum 을 중복 방출   pi=179: 9개 · pi=414: 3개 · pi=522: 9개 (총 23)
2. 그 슬롯이 문단 텍스트 축에 계상된다          lineseg textpos  한컴 68/128 → rhwp 132/192 (Δ+64 = 8×8)
3. 한글이 그 축에서 멈춘다
```

## 원인 귀속 — 정답지 이분법

한컴이 만든 같은 문서의 HWPX 를 공여체로 삼았다(양쪽 최상위 문단 정확히 610개, head 873B ·
tail 9B 동일이라 1:1 교체가 성립).

| 실험 | 판정 |
|---|---|
| 한컴 header 이식 | FAIL → header 무죄 |
| 한컴 section 이식 | **OK 44** → section 이 원인 |
| 문단 이분법 11회 | **k=179 OK / k=180 FAIL** |
| 문단 179 만 한컴 것으로 | **OK 44** |
| 중복 pageNum 만 제거(축 미보정) | FAIL ×2 |
| **중복 제거 + 축 보정** | **OK 45** |

문단 179 의 차이는 그것 하나뿐이다.

```text
  문단 179   rhwp 1,638B · 한컴 972B
  태그 차이   hp:ctrl 9 vs 1 · hp:pageNum 9 vs 1   (그 외 run·텍스트·속성 동일)
```

### 기각한 가설

| 가설 | 판정 |
|---|---|
| `textpos` 축 위반(#5943 원인) | 산출 내부 위반 0건 |
| 참조 무결성 | borderFill 546/549 · charPr 804/805 · paraPr 555/556 정상 |
| 이미지 데이터 팽창 | 압축 해제 총량 **1.00x 동일**(52,176,068 bytes) |
| 본문 문단 일반 | 초기 "문단 1개도 실패" 는 문단을 **잘라낸** 변형이라 잘린 참조 탓 — 거짓 신호 |

## 수정 — 접되, 축에서도 뺀다

`#5943`(PR #5960)이 만든 기계를 그대로 쓴다. `render_control_slot_tracked` 는 **XML 을 한
글자도 내지 않은 슬롯**을 세어 lineseg `textpos` 를 8씩 내린다. 그러므로 중복을 **아무것도
방출하지 않게** 만들면 축 보정이 자동으로 따라온다.

```rust
// SerializeContext
pub(crate) para_page_num_pos_emitted: bool,     // 문단 단위 상태

// render_runs 진입 시 초기화 → 문단당 하나
// 두 번째 이후 PageNumberPos 는 아무것도 내지 않는다
```

컨트롤만 지우고 `textpos` 를 그대로 두면 **오히려 더 어긋난다** — 실측으로 두 번 확인했다
(`p_dedup` FAIL ×2).

## `#5943` 픽스처 기대값 갱신 — 정답지 근거

이 수정으로 `issue_5943_hwpx_lineseg_axis_rebase` 의 합성 픽스처가 `32` → `8` 로 바뀐다.
그 픽스처는 구역 첫 문단에 `pgnp` 를 **넷** 두고 넷 모두 방출된다고 가정했다.

`#5943` 의 출처 문서 `02502`(156465025)를 한컴 2024 로 HWPX 저장해 확인했다.

```text
  한컴 산출        hp:pageNum 문서 전체 1개 · 문단0 textpos 0/8
  rhwp 수정 전     hp:pageNum 4개          · 문단0 textpos 0/8
  rhwp 수정 후     hp:pageNum 1개          · 문단0 textpos 0/8   ← 한컴과 일치
  수정본 재변환    OK 9쪽 (원본과 동일)
```

**실문서의 `textpos` 는 수정 전후 모두 `0/8` 로 바뀌지 않는다.** `#5943` 이 세운 "방출하지
않은 슬롯만큼 축을 내린다" 계약은 그대로이고, 접히는 슬롯이 셋 늘어 총 다섯이 된 것뿐이다.
바뀐 것은 합성 픽스처의 가정이므로 기대값만 옮기고 위 실측을 주석에 남겼다.

## `#6871` 도 같은 결함이다

`#6871`([조사] 한글이 정상 HWPX 원본을 1~2쪽으로 폐기하는데 rhwp 왕복본은 다 읽힌다)의
네 문서가 **전부 같은 문단에 쪽번호 중복**을 갖고 있다.

```text
  02482  전체 3 · 한 문단에 3개        02236  전체 7 · 두 문단에 3개씩
  02268  전체 3 · 한 문단에 3개        08833  전체 3 · 한 문단에 3개
```

그 이슈의 관찰이 그대로 설명된다 — **HWP5 는 중복을 허용하고 HWPX 는 아니다.** 그래서
한글이 원본 HWPX 는 버리고 rhwp 의 HWP5 산출(x2h)은 제대로 읽는다.

### x2x 에서는 축 보정이 꺼져 있었다

HWPX 출처면 `line_segs_on_hwpx_axis` 가 참이라 `#5943` 의 축 보정이 비활성이다. 그래서
1차 구현은 x2x 에서 **컨트롤만 접고 `textpos` 는 부푼 채** 남겼다 — 위에서 두 번 실패로
확인한 바로 그 조합이다.

원인은 "방출하지 않은 슬롯" 에 성격이 다른 둘이 섞여 있던 것이다.

| 슬롯 | HWPX 축에 | 처리 |
|---|---|---|
| `secd`·`cold` | **원래 없음** | HWPX 출처면 빼지 않는다(기존 게이트 유지) |
| **접은 `pageNum`** | **분명히 있었음** | **출처와 무관하게 항상 차감** |

`render_control_slot_tracked` 가 둘을 따로 모으고, 호출부가 전자만 게이트에 걸고 후자는
항상 더해 뺀다.

### 정답지 — 네 문서 전부 복구

| 문서 | 원본 HWPX | rhwp x2x(수정 후) | 이슈의 rhwp 판독 |
|---|---|---|---|
| 02482 (156730118) | FAIL | **OK 2쪽** | 2쪽 |
| 02268 (156603956) | FAIL | **OK 3쪽** | (3) |
| 02236 (156546895) | FAIL | **OK 5쪽** | 5쪽 |
| 08833 (36382475) | FAIL | **OK 3쪽** | (3) |

쪽수가 이슈에 적힌 rhwp 판독값과 정확히 일치한다. 손으로 "접기 + 축 −16" 만 한 원본도
`OK 2쪽` 이라 원인 귀속이 닫힌다.

### `#5943` 의 HWPX-출처 시험도 정밀화

`an_hwpx_source_keeps_its_own_axis` 는 같은 픽스처(`pgnp` 넷)를 채움재로 써서 두 범주를
뒤섞고 있었다. 의도(HWPX 출처에서 `secd`·`cold` 를 다시 빼지 않는다)를 정확히 인코딩하도록
`contains(&24)` + `!contains(&8)` 로 바꿨다 — 종전보다 강한 단언이다.
