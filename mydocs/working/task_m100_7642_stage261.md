# 점수 통과 뒤 확인한 수식 항 경계와 구분자 원점

Issue: #7642

## 독립 근거와 실패 원인

Source255 math8은 Native/fresh WASM 모두 90.14556%지만 확대 판독에서
첫 조건식 한글 원점이 Print보다 약 4.4px 왼쪽이다. 이 관측값을 위치 핀으로
사용하지 않는다. 실제 LayoutBox 조회에서 문서 항 파서가 `-3`, `=0`을
Row로 묶고 묶음 내부 첫 연산자의 앞 여백을 0으로 발행했다. 바깥 행이
앞 피연산자의 문맥을 전달하지 않아 이미 검증한 자동 연산자 여백이 빠진다.

64개 독립 입력을 한컴 MCP 2020으로 정상 저장·Print했다. 실제 제품은
11.0.0.9136, Print method 0, hancom2020_pdf_driver_one_up이다.
저장 job 975efdf9-e0b6-4c5e-a3e9-809c1e77252b, Print job
0c341b24-69cb-4062-8bbf-a17dce6fcedb 모두 download exit 0이다.
11pt `a _n -3`, `a _n - 3`, `a _n {-3}`는 저장 폭이 모두 2699HU다.
첨자 종료 뒤 이항 기호의 최소 0.2em과 관계 기호의 0.3em을 분리하면
원래 크기의 전진·연산자 폭·뒤 여백으로 정상 저장 폭을 설명할 수 있다.
첨자를 명시적으로 닫은 32개 관계/이항 대조군도 별도로 출력해 검증한다.

구분자 높이만 논리 프레임을 쓰고 Paren의 기준선은 본체의 자연 기준선으로
남겼다. CASES가 그 기준선 차이를 소비할 때 본문뿐 아니라 구분자 윤곽까지
내려간다. 동일한 논리 높이·기준선과 본체 원점 차이를 Paren이 한 번 발행해야 한다.
또한 사설 face의 E101 가로 bbox는 225..286/1024em이며 generic 선 굵기와
중앙 위치가 아니다. 폰트 윤곽·바이트를 복제하지 않고 숫자 메트릭과 단순
채움 사각형으로 논리 구분자 높이를 각 backend에 전달한다.

## 보정과 실제 소비

항 묶음의 양쪽 연산자 경계가 기존 before_operator_gap과 같은 규칙을
소비한다. 첨자·OVER 결합과 명시적 그룹을 평탄화하지 않는다. 관계 기호와
이항 기호의 첨자 여유를 의미 분류로 선택하며 문자열·문서 ID로 분기하지 않는다.
구분자와 본체가 동일한 logical frame을 소비하고 본체만 기준선 차이로 옮긴다.
기본 글리프 선택은 명목 1.2em 대신 확인한 글꼴의 일반 줄 프레임을 기준으로 한다.
미측정 글꼴 프레임은 기존 경로를 유지한다. 정상화 24/64/32개 대조군과
원본 math8·9월·10월 및 전체 문서를 한 빌드로 검증한다.

입력·원점·폭·MCP 실행은 ignored stage259-math8-*,
stage260-term-context-diagnostic, stage262-term-context-extra-diagnostic에 보존한다.
기존 Source255의 점수와 fresh WASM을 새 후보에 그대로 적용하지 않는다.
새 관계 회귀·최종 판정은 새 Native/fresh WASM과 직접 판독 이후다.
