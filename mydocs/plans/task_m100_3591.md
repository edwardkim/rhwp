# Task #3591 수행계획서 — 가로 팬 여백 정책 교정 + 줌 중앙 수렴

- Issue: [#3591](https://github.com/edwardkim/rhwp/issues/3591) (M100) / 브랜치 `local/task3591`
- 착수: 2026-07-30 (작업지시자 4K 환경 실측 제보 → CDP 계측으로 근인 확정 → 정책 승인)

## 1. 확정된 근인

`virtual-scroll.ts` `applyHorizontalPanSpace()`:

```
totalWidth = (maxPageWidth + 40) + viewportWidth × 2
pageLeft   = (baseWidth − pageWidth) / 2 + viewportWidth
```

편측 여백이 **창 폭 100%**라 스크롤 영역의 75%가 빈 공간이고(실측: 창 1229 → totalW
3291.7), 창 폭 비례라 4K 최대화 시 총 8500px 중 내용이 10% 미만이 된다. 화면 폭
(`screen.width`)은 수식에 개입하지 않는다 — 실측 역산으로 확인(3840 미개입).

파생 증상: 콘텐츠가 항상 창보다 넓어 브라우저 자연 중앙 정렬이 무력화되고, 수평 배치를
`scrollLeft` 가 전담하는데 줌 완료 후 중앙 수렴 규칙이 없어 앵커 잔류가 줌 비례로
증폭된다(복귀 구간 47.5→403.5px, 그리드 진입 −546px).

## 2. 승인된 정책 (작업지시자 결정, 2026-07-30)

```
pan = (콘텐츠폭 <= 창폭) ? 0 : clamp(창폭 × 0.25, 80, 240)
totalWidth = baseWidth + pan × 2
```

- **조건부**: 콘텐츠가 창보다 좁으면 팬 여백 0 → 일반 A4 문서는 가로 스크롤바 소멸,
  브라우저 자연 중앙 정렬 회복.
- **비율 25% + 하한 80 + 상한 240**: 광폭 문서에만 팬 여유 부여. 상한이 화면 크기
  증가를 끊어 4K 최대화에도 여백 불변(총 스크롤 영역 문서폭+480 로 수렴).

효과 예측(SO-SUEOP, base 833.7): 창 800 → 3234→1234 / 1229 → 3292→1314 /
1920 → 4674→1314 / 3840 → 8514→1314.

## 4. 검증 기준 (이슈 명시)

1. 첫 로드 수평 스크롤 영역이 내용 대비 합리적 비율, **4K 최대화에서도 유지**
2. 줌아웃/줌인 왕복 후 `scrollLeft` 중앙 수렴(`slError` ≈ 0), 그리드 모드 포함
3. 회귀: 광폭 문서 가로 팬 가능성 유지, #3377 좌표 동기화 무회귀
4. 최종: 작업지시자 4K 실기동 시각 판정

## 5. 위험과 제약

- `getCenteredScrollLeft`·`getPageLeftResolved`·`getZoomPageBox` 가 모두 `totalWidth`/
  `pageLefts` 에 의존 — 팬 수식 변경의 파급을 좌표 계약 테스트로 고정한다.
- 그리드 모드는 `layoutGrid` 가 자체 marginLeft 를 계산한 뒤 팬이 덧붙는 구조라 이중
  중앙 계산이 있다. Stage 1 에서 그리드 경로의 기대값도 함께 고정한다.
- #3377 수정(`repositionActivePages`)과 상호작용: 팬 변경 시 좌표계가 바뀌므로 기렌더
  페이지 재배치가 정상 동작하는지 CDP 로 확인한다.
- 계측 하니스는 실 Windows Chrome CDP(포트 19222) + 확장 압축해제 로드 상태에 의존.
  headless 는 오버레이 스크롤바/입력 주입 제약으로 보조 수단으로만 쓴다.
