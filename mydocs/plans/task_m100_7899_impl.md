# #7899 — 구역 끝 목록 소유·저장 계약 구현 계획

Issue: [#7899](https://github.com/edwardkim/rhwp/issues/7899)

상위 범위·승인·단계: [수행 계획](task_m100_7899.md). 2026-10-14 메인터너가 이 계획을 승인했다. 아래 내용은 승인된 구현 방향이며 제품 코드 변경 결과와 구분한다.

## 설계 원칙

구역 끝 목록은 마지막 본문 문단의 부수 레코드나 `is_extension` 렌더링 분류로 대체할 수 없다. 본문 구역의 원본 스트림이 무효화돼도 그 구역 끝 소유 범위는 살아 있어야 한다. 이미 모델로 투영한 목록과 원본 레코드를 동시에 내보내지 않는다.

새 보존 결과는 구역에 소유시킨다. 목록별로 원본 순서·레코드 범위·관련 모델 소유를 연결하고, 바탕쪽·메모·미해석 레코드를 구분해 파싱 결과와 저장 출력이 같은 소유 결과를 소비하게 한다. 최종 Rust 타입명·필드 구성은 기존 mutation·clone 경로를 대조한 뒤 확정한다.

원본에 모델로 표현하지 못하는 데이터가 있으면 이를 삭제해 자기 재파싱을 통과시키지 않는다. 본문 수정과 목록 자체 수정의 무효화 범위를 분리한다. 원본 전체를 반환해 입력한 글자가 사라지게 하거나, tail을 무조건 덧붙여 중복·낡은 모델을 남기는 방식도 허용하지 않는다.

## 입력 → 소유 결과 → 저장 소비

| 지점 | 계획하는 변경·확인 |

| clone·snapshot·undo·형식 변환 | 추가한 소유 정보가 깊은 복제·재편집에서 소실되거나 다른 구역으로 복사되지 않는지 실제 소비 위치를 확인한다. 소유 번호 remap이 필요하면 해당 경로에서 수행한다. |

구역 끝 목록 자체 편집 시 현재 모델 내용과 원본 보존 여부를 대조한다. 원본의 미해석 영역 때문에 재생성 계약을 확정하지 못하는 경우는 그 이유를 명시하고, 조용한 데이터 삭제로 성공을 보고하지 않는다. 신규 메모 UI나 전체 메모 편집 기능을 이번 구현의 필수 조건으로 확장하지 않는다.

## 실제 Native·WASM 및 한컴 검증

1. 작은 경계에서 Native 저장과 수정 전 실패 원문을 비교한다. 보정 방향이 확인되면 같은 입력의 최신 Docker WASM에서 `HwpDocument → insertText → exportHwp`를 다시 실행한다. 배포 0.8.7 조사 결과를 보정본 결과로 사용하지 않는다.
2. 저장본을 독립 한컴에서 열어 정상 열기·편집 글자·바탕쪽·메모의 보존을 확인한다. 열기 실패·timeout·worker 종료·미검증을 구분하고 필수 내용이 누락된 성공을 통과로 판정하지 않는다.
3. 저장본의 조판 소비 영향을 확인한다. 영향을 받는 문서는 **같이 편집해 저장된 HWP**를 버전에 맞는 독립 한컴 Print로 출력한 뒤 전체 Native/fresh WASM TSV를 산출하고 변경 영역을 직접 확대 판독한다. 원본 무편집 PDF를 편집본의 독립 정답지로 대체하지 않는다.
4. 코드 변경 뒤에는 새 head에서 영향 경계와 실제 저장·출력을 다시 확인한다. renderer를 직접 수정하지 않았다는 이유만으로 시각 영향을 비해당 처리하지 않는다.

Docker WASM은 worktree 루트에서 canonical locked wrapper를 사용하고 공용 target을 전달한다. 생성 `pkg/rhwp.js`·`rhwp_bg.wasm`과 Studio public의 hash 일치 및 실제 브라우저 수신을 확인한다. 공용 cache·다른 작업 서버는 임의 초기화하지 않는다.

## 제출 전과 완료 조건

2026-10-14 작업지시자는 한컴보다 큰 `{` 기호의 크기 차이를 이번 이슈의 예외로 수용하고 PR 등록·self-review 진행을 지시했다. 중괄호 크기 보정은 이번 제출의 필수 조건에서 제외한다. 이어 작업지시자는 “세로 위치 차이도 이번에 예외 수용하고 PR”로 명시해 약 2px 다중 행 세로 위치 차이도 현재 보정본의 제출 예외로 수용했다. 따라서 추가 수식 AST·행 배치 변경 없이 검증된 보정본으로 PR을 등록한다. Native/fresh WASM 자동 수치 통과나 Canvas2D의 수식 글리프 누락 해소로 확대 해석하지 않는다. 원격 push·PR 등록 승인은 확보했으며, 제출 전 필수 검증을 완료한 뒤 실행한다. 정확한 제출 head의 CI 성공 뒤 self-review·오늘할일을 추가하는 순서는 유지한다.

### 승인된 추가 범위: 편집 후 수식 줄 소속

2026-10-14 작업지시자는 남은 math_8 조판 차이의 보정을 승인했고, 원본은 정상이며 편집 저장본에서 문제가 발생한다고 확인했다. 기존 base CLI와 보정 CLI가 **같은 편집 저장본**에 같은 출력을 낸다는 관측은 #7899 tail 보정의 새 회귀가 아니라는 근거일 뿐, 원본도 잘못 조판된다는 근거가 아니다.

원본의 큰 글자취급 수식은 PARA_TEXT UTF-16 위치 41에서 시작하고 해당 LineSeg도 41에서 시작한다. A 삽입 뒤 수식 시작은 42이지만 재발행 LineSeg는 수식 뒤 개행인 50을 가리킨다. `char_offsets`는 제어문자 앞이 아닌 뒤 가시 문자를 가리키므로, 편집 재조판의 줄 구성 결과를 저장 UTF-16 범위로 변환할 때 실제 인라인 개체의 소유를 보존해야 한다. 입력은 일반 본문 편집으로 생성된 저장본이며 수동 LineSeg 입력이 아니다.

`reflow_line_segs_impl`/프레임 채움의 줄 경계 생산 → `Paragraph.line_segs` 저장 → composer의 줄 소속 → paragraph layout의 TAC 배치 → 미처리 Shape 배치까지 추적한다. 좌표 clamp나 샘플 전용 조건은 추가하지 않는다. 원본, 같은 A 편집본의 독립 한컴 Print, 보정 전후 Native/fresh Docker WASM을 구분해 확인하고, 시각 게이트 통과 뒤 관계형 회귀를 추가한다. 기존 구역 끝 목록·메모 보존 검사는 유지한다.

작업지시자는 원본이 한컴과 Studio 모두 정상이고, 한컴은 편집 저장본도 정상임을 확인했다. 기존 WASM API에서 같은 A 삽입을 실행한 결과 큰 수식은 원본의 `TextLine` 자식에서 편집 재조판 직후 `Column` 직속으로 바뀌었고, export 및 재열기에서도 유지됐다. 화면에서 저장 뒤에 관측된 증상의 생산 지점은 serializer의 원시 목록 보존이 아니라 편집 재조판의 줄 경계 발행이다. 이 API 관측을 사용자의 화면 관측과 구분한다.

별도로 문단 테두리의 `attr1 bit29`를 parser/model은 보존하지만 resolved style은 누락한다. 공식 [문단 배경 도움말](https://help.hancom.com/hoffice130/ko-KR/Hwp/format/paragraph/paragraph%28background%29.htm)의 문단 여백 무시 설명과 [자동화 ParameterSet의 BorderText](https://raw.githubusercontent.com/hancom-io/devcenter-archive/main/hwp-automation/ParameterSetObject.pdf)(0=단, 1=텍스트)를 근거로, 같은 속성을 스타일→문단 테두리 범위→연속 테두리 병합→각 backend 공통 Rect에 전달한다. 흐름 높이는 바꾸지 않으며 텍스트 기준 테두리와 기본 단 기준 테두리를 구분한다. 실제 한컴 편집본 Print와 대조해 적용 경계를 확인한다.

- 정책 base SHA를 고정하고 [로컬 검증 4.3](../manual/pr_review/local_validation.md#43-변경-범위별-기본-검증)의 fmt / Native·WASM32·workspace Clippy / workspace build / manifest 검사를 순차 수행한다.
- 필요한 전체 회귀·Native Skia는 focused·시각 결과 공유 후 승인된 범위에서 실행한다. 새 렌더링 fixture·기대값 변경에는 기존 90%·쪽수 일치 조건을 적용한다.
- #7867, #7694, #7671, #7668, #7675, #7682와 파일을 공유하므로 push 전에 최신 devel의 실제 충돌·호출 경로를 확인한다. 해당 PR의 병합을 #7899 해결로 간주하지 않는다.
- 완료는 본문 편집·목록 내용·번호·소속·순서가 보존되고 실제 한컴 열기·저장을 확인한 범위로 선언한다. 595개/16개 전수·한컴 2024 전체 문서 검증 등 미실행 범위를 조사 사실로 승격하지 않는다.
- 검증된 code candidate와 한국어 본문을 준비한 뒤 원격 push·PR 생성을 별도로 승인받는다. 자체 PR의 CI 성공 후 review·오늘할일을 포함하고 정확한 head의 merge·이슈 종료 확인으로 마무리한다.
