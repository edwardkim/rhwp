## 2. 문제 정의와 현재 근거

### 2.1 사용자 증상

115쪽 거대 셀 문서의 셀 내부에서 같은 줄의 짧은 텍스트를 마우스로 드래그해도 선택
하이라이트가 포인터를 따라오지 못하고 수초 동안 멈춘다. `requestAnimationFrame`으로
mousemove를 묶고 있지만 한 번의 선택 갱신 자체가 오래 걸리므로 사용자에게는 드래그가
불가능한 것처럼 보인다.

### 2.2 코드에서 확인된 병목 경로

```text
mousemove requestAnimationFrame
→ updateTextSelectionDragFromPointer
→ updateCaretDuringDrag
→ updateSelection
→ getSelectionRectsInCell
→ get_selection_rects_native
```

현재 `get_selection_rects_native()`는 셀 선택에서 셀 문단이 아니라 외부 표의 host
`parentParaIndex`로 `find_pages_for_paragraph()`를 호출한다. 재현 문서의 외부 표 문단은
115쪽 전체에 걸쳐 있어 후보 페이지가 115개가 된다.

코드 주석은 페이지별 로컬 캐시를 “최대 2페이지”로 설명하지만 실제 구현은 반환된 모든
후보 페이지에 대해 매 호출마다 uncached `build_page_tree()`를 실행한다. 이 함수 로컬의
트리는 다음 드래그 프레임에 재사용되지 않는다. 따라서 같은 페이지·같은 줄 선택도 다음
비용을 갖는 것이 직접 원인 후보로 확인된다.

```text
O(부모 표가 걸친 115쪽 page tree 구축 × 드래그 갱신 프레임)
```

이 경로에는 문서 mutation, pagination 또는 Canvas page refresh가 없다. #2214의 입력 표시
정확성 및 #2193의 일반 입력·pagination 비용과는 분리해 다룬다.

### 2.3 사실과 가설의 경계

| 분류 | 내용 |
|------|------|
| 확정 | 셀 선택의 후보 페이지 조회가 셀 문단이 아닌 115쪽 외부 표 host 문단을 사용한다. |
| 확정 | 조회된 후보마다 uncached `build_page_tree()`를 실행하고 함수 호출 간 트리를 재사용하지 않는다. |
| 확정 | Studio는 anchor/focus cursor 및 pointer hit에서 페이지 정보를 이미 관찰할 수 있다. |
| 확정 | selection rect 경로는 pagination과 Canvas page refresh를 직접 호출하지 않는다. |
| 미확정 | 같은 페이지 선택에 필요한 최소 인접 페이지 수와 경계 조건 |
| 미확정 | cross-page 선택에서 endpoint 사이 모든 페이지가 필요한지, rect가 존재하는 페이지만 좁힐 수 있는지 |
| 미확정 | 후보 범위 제한 뒤 남는 hit test·JSON 변환·overlay 렌더 비용의 비중 |
| 미확정 | page hint가 stale하거나 누락된 경우 정확성을 보장할 최소 fallback 계약 |

## 3. 목표

1. 같은 페이지의 짧은 셀 선택이 115개 page tree를 열거하거나 구축하지 않도록 한다.
2. anchor/focus page를 기준으로 선택 범위를 필요한 페이지로 제한하되 페이지 경계 선택,
   자동 스크롤, 잘못된 hint의 정확성을 유지한다.
3. 제한된 후보에서는 shared cached page tree를 사용해 드래그 프레임 사이의 중복 구축을
   제거한다.
4. 기존 positional API와 selection rect 기하 의미, 선택 문자열을 보존한다.
5. 문서화된 warm-up 조건에서 selection rAF callback p95 50ms 미만과 반복 long task 0건을
   달성한다.

## 4. 수행 원칙

1. 단순히 `build_page_tree_cached()`로 교체해 115쪽 순회를 유지하는 안은 완료안으로
   채택하지 않는다. 후보 페이지 수와 tree build 수를 함께 줄인다.
2. 이전 전체 탐색 결과를 정확성 oracle로 사용한다. 최적화 전후 rect와 복사 문자열을
   비교해 기하 의미를 바꾸지 않는다.
3. page hint는 성능 힌트로 취급한다. 누락·범위 밖·stale hint가 잘못된 선택 결과를 만들지
   않도록 명시적인 fallback을 유지한다.
4. HWP/HWPX, 문서 전반부·중간·후반부, same-page·cross-page를 분리해 측정한다.
5. 원인 제거 전후의 selection rect 호출, page 후보, tree build/cache hit, hit test 및 rAF
   시간을 분리해 기록한다.
6. pagination, Canvas refresh, 셀 간 선택 정책 또는 자동 스크롤 정책의 확장이 필요하면
   #2215 구현을 확대하지 않고 별도 범위로 재승인받는다.
7. split cross-page는 이전·다음 page 좌표를 섞지 않고 line segment의 양 cursor를 동일 page
   fragment에서 짝지어야 한다. 마지막 페이지 특례나 Studio clipping으로 숨기지 않는다.

## 5. 수행 범위

### Stage 1. 결정적 재현과 비용 기준선 고정

1. 최신 WASM과 Studio에서 HWP 재현 문서를 열고 동일한 짧은 셀 선택을 반복한다.
2. 첫 페이지·중간 페이지·후반 페이지에서 다음 시나리오를 각각 측정한다.
   - 같은 줄의 짧은 선택
   - 같은 셀의 여러 줄 선택
   - 페이지 경계를 넘는 선택
   - 드래그 자동 스크롤을 포함한 선택
3. cold/warm을 분리하고 다음 값을 한 호출 단위로 기록한다.
   - anchor/focus page 및 셀 문단/offset
   - `find_pages_for_paragraph()` 후보 수
   - page tree build 대상·횟수와 cache hit
   - `getSelectionRectsInCell` 총 시간과 반환 rect 수
   - pointer hit test, `updateSelection`, selection rAF callback 시간
   - pagination 및 Canvas page refresh 호출 수
4. HWPX는 native 동일성 기준선을 먼저 확보하고 Studio 업로드 재현 가능 여부를 확인한다.

### Stage 2. 최소 후보 범위와 정확성 계약 확정

1. 최적화 전 전체 탐색 결과를 same-page·cross-page별 rect JSON 및 복사 문자열 oracle로
   저장한다.
2. anchor/focus page를 기준으로 다음 후보 정책을 통제 실험한다.
   - same-page: endpoint page만
   - same-page 경계: endpoint page와 필요한 인접 페이지
   - cross-page: 두 endpoint 사이의 페이지 범위
3. 첫 페이지·중간·후반 페이지에서 후보 정책별 rect, cursor endpoint, highlight 및 복사
   문자열을 oracle과 비교한다.
4. hint 누락, 범위 밖, endpoint를 찾지 못한 경우의 fallback 비용과 정확성을 확인한다.
5. `build_page_tree_cached()` 사용 시 cache hit와 clone/순회 잔여 비용을 계측해 후보 제한과
   캐시 사용이 각각 필요한지 확정한다.
6. RAF 밖의 중복 cell hit test 또는 mousemove listener 중복이 지배 비용으로 남는 경우
   별도 finding으로 기록하고 구현 범위 확대 여부를 다시 승인받는다.

### Stage 3. 회귀 계약과 구현 경계 설계

1. native 표적 회귀는 다음 계약을 고정하도록 설계한다.
   - same-page 선택의 후보 및 tree 대상 수가 endpoint·필요 인접 페이지 수준임
   - cross-page 선택의 대상이 endpoint 사이의 필요한 페이지로 제한됨
   - HWP/HWPX rect 및 선택 문자열이 기존 전체 탐색 oracle과 동등함
   - hint 누락·오류 fallback이 정확한 결과를 반환함
   - 기존 `issue_658_text_selection_rects`가 유지됨
2. WASM/TypeScript 경계는 기존 positional API 호환성을 유지하면서 page hint/range를 전달할
   options 또는 명시적 확장 API를 비교한다.
3. Studio 회귀는 실제 mouse drag에서 focus offset, visible highlight, mouseup 후 선택 유지,
   복사 문자열과 자동 스크롤을 검증하도록 설계한다.
4. 테스트 전용 계측과 production API를 분리하고, 구현계획서에서 실제 변경 파일과 API
   형태를 확정한다.

### Stage 4. 구현 후 전체 검증과 결과 분리

1. 승인된 구현계획에 따라 page range 제한과 cached tree 사용을 최소 범위로 반영한다.
2. native, WASM, Studio 단위·E2E 및 브라우저 실사용 검증을 수행한다.
3. selection rAF p50/p95, 후보 페이지 수, tree build/cache hit, long task를 전후 표로 남긴다.
4. #2215 결과는 #2193에 상호 링크하되 일반 입력·pagination 최적화 완료로 간주하지 않는다.
5. revision 기반 derived state 전환(#2308)은 이 작업에 포함하지 않는다.

## 8. 완료 조건

- 같은 페이지 선택 한 번이 외부 표의 115개 page tree를 전부 열거하거나 구축하지 않는다.
- same-page 대상은 endpoint와 필요한 최소 인접 페이지 수준으로 제한되고 회귀 테스트에
  고정된다.
- cross-page 선택, 페이지 경계 선택 및 자동 스크롤이 계속 동작한다.
- 같은 cell paragraph가 분할된 cross-page 선택은 양쪽 page에 유효한 rect를 만들고 각 rect가
  해당 page 폭을 벗어나지 않는다.
