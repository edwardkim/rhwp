## 1. 결정과 목표

W7의 목적은 모든 backend가 같은 font face를 고르게 만드는 것이 아니다. 현재 Rust layout,
Canvas2D paint, webfont 공급과 CanvasKit SFNT 조달에 흩어진 유한 규칙의 **근거를 한 registry에서
관리하되**, 각 결정면에는 의미상 허용된 관계만 투영해 현재 결과를 그대로 보존하는 것이다.

이번 작업은 다음 질문에 답한다.

1. W1 조사 원장 1,507행 중 어떤 행이 runtime projection의 입력이고, 어떤 행은 관측·미확정 근거로만
   남아야 하는가?
2. style alias, metric surrogate, paint substitute와 supply source를 섞지 않고 한 schema에서 표현할
   수 있는가?
3. W6의 600개 metric 계보를 숫자 복제 없이 안정 `entryId`로 연결할 수 있는가?
4. 생성 전후 Rust·Canvas2D·webfont·CanvasKit lookup 결과와 순서를 전수 동일하게 유지할 수 있는가?
5. W2 Decision Trace의 `ruleId`가 실제 생성 항목까지 이어지고, 신규 규칙 하나가 필요한 backend
   산출물만 바꾸게 할 수 있는가?

## 2. Stage 0 원인 계보와 현 상태

### 2.1 중복이 생긴 흐름

```text
HWP/HWPX 문서 font name
  ├─ Rust style_resolver의 language/alt-type 이름 정규화
  ├─ Rust font_metrics_data의 layout metric alias와 600-entry lookup
  ├─ Rust renderer의 설치 face·successor·generic paint chain
  └─ Studio
       ├─ SUBST_TABLES와 document/system fallback → Canvas2D CSS family chain
       └─ FONT_LIST
            ├─ FontFace 등록·조건부 webfont supply
            └─ SFNT 가능 항목만 CanvasKit Typeface plan으로 변환

사건별 수정이 각 소비자 표에 직접 추가됨
  → 비슷한 source/target 쌍이 여러 파일에 중복
  → 관계 의미와 backend capability가 서로 다른데 겉모양은 같은 mapping
  → 한 곳만 고치거나 단일 resolver로 합치면 조판·paint·공급 drift 위험
```

W1은 30개 source boundary에서 1,507개 규칙을 판정했다. 관계별로는 metric entry 600,
supply source 361, paint substitute 269, style fallback 181, metric surrogate 24,
official successor 11과 그 밖의 capability·oracle·unknown 행이다. 그중 44개는 `unknown`이며,
SFNT/byte 근거 없는 이름 연결은 identity로 승격하지 않았다.

W6는 600 metric entry를 historical generated 595개와 measured overlay 5개로 분리하고 안정
`entryId`, current index와 semantic hash를 만들었다. 그러나 이 lineage manifest는 metric 값의
계보 정본이지 backend 선택 정책 정본이 아니다. W7은 이를 runtime JSON으로 직접 읽거나 600개
숫자를 registry에 복사하지 않고, 필요한 metric 관계에서 `entryId`를 참조한다.

W2 trace는 이미 W1 candidate identity로 `ruleId`를 계산해 조사 원장과 교차 검사한다. W7은 같은
ID를 생성 항목의 provenance로 보존하고 별도의 ID 체계를 만들지 않는다.

### 2.2 현재 소유 경계

| 결정면 | 현행 소유자 | W7 처리 |
| --- | --- | --- |
| Rust layout name | `src/renderer/style_resolver.rs`의 유한 alias/fallback mapping | registry의 `layout-name` projection |
| Rust layout metric | `src/renderer/font_metrics_data.rs::resolve_metric_alias` | `layout-metric` projection, W6 entry 참조 |
| Rust metric data | generated 595 + overlay 5와 기존 first-match index | 값·순서 유지, registry로 이동하지 않음 |
| Canvas2D paint | `rhwp-studio/src/core/font-substitution.ts`의 `SUBST_TABLES`와 유한 successor mapping | `paint/canvas2d` projection |
| webfont supply | `rhwp-studio/src/core/font-loader.ts::FONT_LIST` | `supply/canvas2d` projection |
| CanvasKit supply | 같은 `FONT_LIST`를 SFNT 조건으로 거르는 `resolveCanvasKitFontPlan` | `supply/canvaskit-sfnt` projection |
| 동적 알고리즘 | document substitution, local probe, generic fallback, glyph coverage와 capability 검사 | 코드를 유지하고 registry 항목을 입력으로만 사용 |

Rust paint chain, native Skia, SVG local alias와 local-font 탐지처럼 W1에 기록됐지만 이 이슈의 네
projection에 직접 속하지 않는 경계도 Stage W7-1 inventory에서 누락 없이 대응표에 남긴다. 유한 규칙을
옮길지 현행 알고리즘 소유권으로 남길지는 relation·decision plane·backend allowlist로 판정하며,
범위를 넓히기 위해 임의로 생성 대상으로 승격하지 않는다.

## 5. 목표 구조와 authority

구현 단계에서 module visibility와 build 경계를 확인해 정확한 파일명은 Stage W7-2에서 고정하되,
authority는 다음 네 층으로 분리한다.

```text
W1 investigation ledger + W6 metric lineage
  └─ migration/import audit의 근거(직접 runtime import 금지)

canonical font registry
  ├─ relation·plane·backend/profile·condition·order
  ├─ W1 ruleId·evidence status
  └─ 필요한 경우 W6 metric entryId 참조

deterministic generator + projection manifest
  ├─ Rust layout-name projection
  ├─ Rust layout-metric projection
  ├─ TypeScript Canvas2D paint projection
  ├─ TypeScript webfont supply projection
  └─ TypeScript CanvasKit SFNT projection

hand-written runtime algorithms
  └─ generated static table만 소비하고 기존 탐지·fallback·capability 순서를 유지
```

canonical registry는 font binary catalog나 metric DB의 복제품이 아니다. 한 행은 하나의 관계와 하나의
결정면을 가진다. 여러 backend가 같은 근거를 사용하더라도 `projections[]`에 명시된 backend/profile만
허용한다. Canvas2D CSS 공급과 CanvasKit SFNT 공급은 source URL이 같아도 별도 projection이다.

W1/W6 snapshot을 매 build 때 자동 import하지 않는다. Stage W7-1의 승인된 migration manifest가
대응 rule과 input digest를 고정하고, 이후 registry가 제품 정본이 된다. W1·W6는 provenance와 drift
감사의 입력으로 남는다.

## 6. schema와 projection 계약

registry 행은 최소 다음 의미를 가진다.

```text
ruleId
relationType
decisionPlane
sourceFace?
targetFaceOrPolicy
conditions
order?
projections[] { backend, profile, outputKey }
evidence { status, anchors[], limitations[] }
metricEntryId?
status
```

- `ruleId`는 W1 ID를 그대로 사용한다. 합성된 새 정책이 필요하면 source identity와 evidence를 먼저
  등록하고 임시 순번 ID를 만들지 않는다.
- `relationType × decisionPlane × backend/profile` allowlist를 schema 뒤의 semantic validator가
  검사한다. 예를 들어 `supply-source`는 `layout-metric`으로, `metric-surrogate`는 webfont로 투영할 수
  없다.
- ordered table은 source key가 중복될 수 있다. 중복 자체를 제거하지 않고 `(conditions, order)`의
  유일성과 연속성, 기존 first-match를 검사한다.
- 기존 active `unknown`은 현행 동작 보존을 위해 원래 decision plane의 legacy-preservation projection에만
  들어갈 수 있다. relation을 추정하거나 다른 backend로 확장하지 않는다. 신규 `unknown`, inactive와
  evidence anchor가 깨진 행은 실행 projection에서 제외하거나 오류로 거부하며 조용히 기본값으로 바꾸지
  않는다.
- URL·format·style·weight 같은 supply payload는 기존 `FONT_LIST` 의미를 보존하고 HTTPS, 허용 format,
  크기·항목 수 상한을 검사한다. generator는 네트워크를 호출하지 않는다.
- absolute path, timestamp, 사용자명과 객체 순서는 canonical hash 입력에 들어가지 않는다.

## 7. 기준선과 hash 계약

Stage W7-1은 기존 source를 없애기 전에 다음 projection을 canonical JSON으로 직렬화해 동결한다.

| hash | 기준선 내용 |
| --- | --- |
| `registryInputSha256` | 승인된 W1 rule·W6 entry anchor의 canonical 입력 |
| `rustStyleProjectionSha256` | 모든 유한 style mapping의 조건·source·target·order |
| `rustMetricProjectionSha256` | metric alias와 W6 entry 참조, 4-style lookup 결과 |
| `canvas2dPaintProjectionSha256` | language/alt-type별 ordered substitution과 display chain |
| `webfontSupplyProjectionSha256` | name·URL·format·weight·style·remote/offline 조건 |
| `canvasKitSfntProjectionSha256` | 문서 후보별 SFNT 조달 가능 여부와 계획 결과 |
| `projectionBundleSha256` | schema version과 위 backend hash의 canonical 조합 |

hash 비교만으로 의미 보존을 주장하지 않는다. 기준선 tuple과 exhaustive lookup 결과가 같고 그
직렬화 hash도 같을 때 통과한다. 같은 입력으로 generator를 두 번 실행해 byte-identical한지도 별도로
확인한다.

## 8. 단계별 수행

### Stage W7-1 — source inventory와 분리 전 기준선

- W1의 30개 boundary를 현재 source와 다시 대조하고 네 projection의 포함·참조·비대상 대응표를 만든다.
- Rust style/metric, `SUBST_TABLES`, `FONT_LIST`와 CanvasKit plan의 현행 유한 규칙을 추출한다.
- ordered duplicate와 first-match group, 조건부 supply, SFNT 불가 항목을 손실 없이 기록한다.
- 기존 lookup을 전수 실행하는 baseline과 mutation negative fixture를 만든다.
- `mydocs/working/task_m100_4966_w7_stage1.md`에 분모, source digest와 제외 사유를 기록한다.

**중지 조건**: 현재 source rule이 W1 행 또는 명시적 비대상 사유에 대응하지 않거나, 기준선 extractor가
중복·조건·순서를 보존하지 못하면 registry 설계로 넘어가지 않는다.

### Stage W7-2 — canonical schema와 migration manifest

- relation/plane/backend allowlist와 evidence 상태를 가진 registry schema·semantic validator를 만든다.
- W1 rule과 W6 `entryId`를 승인된 migration manifest로 연결한다.
- `unknown`, 깨진 anchor, 중복 `ruleId`, 상충 target/order, 불허 projection과 순환을 거부하는 negative
  contract를 만든다.
- registry와 migration input의 canonical serialization·digest를 고정한다.
- `mydocs/working/task_m100_4966_w7_stage2.md`에 projection 가능·참조 전용·비대상 수를 보고한다.

**중지 조건**: W1의 기존 active unknown이 삭제되거나 다른 relation·plane으로 추정 승격되고, 신규
unknown이 실행 규칙이 되거나, W6 metric 숫자가 registry에 복제되거나, relation 의미가 둘 이상의
plane에 암묵적으로 확장되면 중단한다.

### Stage W7-3 — 결정론적 generator와 backend 산출물

- registry를 한 번 읽어 backend별 정적 Rust/TypeScript projection을 생성한다.
- 생성 파일에는 schema version, input digest, projection digest와 각 항목의 `ruleId`를 보존한다.
- `--check`는 stale·부분 생성·수동 편집·불필요한 backend 변화와 marker 밖 overwrite를 거부한다.
- 같은 입력의 연속 생성, 항목 순서 교란과 단일 rule mutation으로 결정론·최소 영향 contract를 검증한다.
- `mydocs/working/task_m100_4966_w7_stage3.md`에 생성 ownership과 hash를 기록한다.

**중지 조건**: generator가 hand-written 알고리즘, metric data/overlay 또는 관련 없는 backend 파일을
덮어쓰거나 같은 입력에서 다른 bytes를 만들면 소비자 migration을 시작하지 않는다.

### Stage W7-4 — Rust layout-name·layout-metric 전환

- `style_resolver`의 유한 mapping과 `resolve_metric_alias`를 각 Rust projection 소비로 바꾼다.
- 동적 language 판정, metric index와 exact → bold-only → name-first 사다리는 hand-written code로
  유지한다.
- 모든 source mapping, alias/sentinel × 4 style과 W6 composition·width hash를 전환 전후 비교한다.
- W2 native/WASM trace의 `ruleId`, requested/resolved face와 metric entry가 같은지 확인한다.
- `mydocs/working/task_m100_4966_w7_stage4.md`에 전수 비교 결과를 기록한다.

**중지 조건**: mapping 결과뿐 아니라 entry index, match kind, bold fallback, width 또는 trace rule ID가
하나라도 달라지면 TypeScript 전환으로 넘어가지 않는다.

### Stage W7-5 — Canvas2D·webfont·CanvasKit 전환

- `SUBST_TABLES`와 유한 successor mapping을 Canvas2D paint projection 소비로 바꾼다.
- `FONT_LIST`의 공급 payload를 webfont와 CanvasKit projection으로 분리하되 현행 등록·선택 API를
  유지한다.
- document substitution, local enumeration/probe, offline filtering, glyph coverage와 SFNT capability
  판정은 기존 hand-written 알고리즘을 유지한다.
- 모든 table/lookup/plan tuple과 W2 Studio trace의 `ruleId`를 전환 전후 비교한다.
- `mydocs/working/task_m100_4966_w7_stage5.md`에 backend별 동등성과 capability 경계를 기록한다.

**중지 조건**: Canvas2D supply가 CanvasKit 가능으로 오인되거나, local/web/SFNT source 우선순위,
offline 동작, URL/format 또는 candidate chain이 달라지면 최종 통합으로 넘어가지 않는다.

### Stage W7-6 — 통합 검증·운영 인계와 최종 보고

- schema, generator, Rust·Studio focused test와 TypeScript typecheck를 실행한다.
- 전체 Rust test, Clippy, Studio production build, native와 Docker WASM build를 실행한다.
- 공개 대표 HWP/HWPX의 native/WASM SVG byte parity와 Canvas2D·CanvasKit 선택 결과를 확인한다.
- registry에 규칙 하나를 추가·수정·폐기하는 절차와 필요한 backend 산출물만 갱신하는 명령을 문서화한다.
- canonical font fallback 문서와 W2 trace 문서를 새 authority·`ruleId` 경계에 맞게 현행화한다.
- `mydocs/report/task_m100_4966_report.md`에 수량, hash, 불변식과 W8 인계 조건을 기록한다.

**중지 조건**: focused 동등성은 통과하지만 renderer output 또는 backend plan이 바뀌거나, 재현 명령이
clean checkout에서 registry drift를 탐지하지 못하면 완료로 판정하지 않는다.

각 Stage는 working 보고서와 local commit을 완료한 뒤 결과를 브리핑하고 메인테이너의 다음 단계
승인을 받는다. remote push, PR 생성과 merge는 각각 별도 승인을 받는다.

## 9. 검증 전략

계획 승인 뒤 Stage W7-1에서 실제 test target과 명령을 기준선에 고정한다. 최소 검증 축은 다음과 같다.

```bash
# W1·W2·W6 계보와 W7 schema/generator focused contract
node --test scripts/tests/font_rule_ledger.test.mjs
node --test scripts/tests/font_decision_trace_contract.test.mjs
node --test scripts/tests/font_metric_lineage.test.mjs

# Rust style·metric·trace focused contract
cargo test --profile release-test --lib style_resolver
cargo test --profile release-test --lib font_metrics
cargo test --profile release-test --lib font_decision

# Studio backend focused contract
cd rhwp-studio
npm test -- --runInBand
npx tsc --noEmit

# 모든 PR·push 직전
cargo fmt --all
cargo fmt --all -- --check
git diff --check
```

`npm test -- --runInBand`는 현재 package script와 test runner 옵션을 Stage W7-1에서 재확인해 실제
지원 명령으로 대체한다. 최종 full gate는
[로컬 검증 4.3](../manual/pr_review/local_validation.md#43-변경-범위별-기본-검증)의 변경 범위별 명령과
[개발 환경 가이드](../manual/dev_environment_guide.md)를 따른다. WASM은 프로젝트 규칙대로 Docker로
빌드한다.

시각 검증은 mapping을 바꾸는 작업이 아니므로 새 정답지를 만들지 않는다. 기존 공개 fixture의
byte/selection parity가 깨졌을 때만
[시각 검증 거버넌스](../manual/verification/visual_verification_governance.md)에 따라 원인 판정용으로
진입한다.

## 10. 보안·성능·저작권 경계

- registry와 generator는 항목·문자열·배열 길이 상한을 갖고 schema 외 필드를 거부한다.
- generator는 registry의 URL을 다운로드하지 않고, 허용 scheme·format과 canonical string만 검사한다.
- 입력과 출력은 checkout 내부 고정 경로만 허용하고 absolute path, `..`, symlink 탈출과 임의 target
  overwrite를 거부한다.
- canonicalization은 명시적 key/order 규칙을 쓰며 locale, filesystem enumeration과 wall-clock에
  의존하지 않는다.
- runtime은 JSON parse·schema validation·W1 ledger join을 수행하지 않는다. 빌드된 정적 projection의
  lookup 복잡도와 allocation 특성이 기존보다 나빠지지 않는지 focused benchmark 또는 구조 검사를 둔다.
- private corpus 원문·파일명·절대 경로와 로컬 font root는 산출물·hash·오류 메시지에 넣지 않는다.
- registry는 font 파일을 포함하지 않으며 기존 `assets/fonts/FONTS.md`와 라이선스 authority를 대체하지
  않는다. supply projection은 현재 승인된 URL·format을 그대로 보존한다.

## 11. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 비슷한 source/target을 identity로 합침 | relation·plane allowlist와 active-unknown legacy-preservation contract |
| W1 조사 snapshot이 곧 runtime truth가 됨 | 승인된 one-time migration manifest와 이후 registry authority 분리 |
| W6 metric 계보와 정책이 다시 섞임 | `entryId`만 참조하고 숫자·origin을 복제하지 않음 |
| ordered duplicate가 dedupe됨 | order를 schema 필드로 보존하고 first-match mutation test |
| webfont가 CanvasKit SFNT로 자동 승격됨 | backend/profile별 별도 supply projection과 format capability contract |
| generator가 큰 source 파일을 덮어씀 | 고정 출력 allowlist, paired commit과 marker 밖 변경 거부 |
| trace가 생성 규칙과 다른 ID를 보고함 | generated `ruleId`와 W1/W2 join 전수 검사 |
| registry가 startup 비용을 늘림 | runtime 정적 생성물, no JSON parse/ledger search 불변식 |
| full test·WASM 검증 비용 증가 | Stage별 focused gate 뒤 W7-6에서 한 번만 full gate 실행 |

## 12. 중단 조건과 잔여 위험

다음 중 하나가 발생하면 성공으로 기록하지 않고 해당 Stage에서 중단한다.

- relation 또는 decision plane이 다른 규칙을 하나의 target mapping으로 합침
- active unknown을 삭제하거나 unknown·inferred 근거를 verified identity 또는 다른 decision plane으로 승격함
- W6 metric 값·순서·width hash 또는 기존 first-match가 바뀜
- Rust·Canvas2D·webfont·CanvasKit 중 하나의 선택 결과가 기준선과 달라짐
- supply availability를 metric/paint 적합성으로 사용하거나 Canvas2D availability를 SFNT capability로 사용함
- generated output의 항목이 W1 `ruleId`와 연결되지 않거나 W2 trace가 다른 rule을 가리킴
- generator가 비결정적이거나 한 rule 변경이 무관한 backend projection을 바꿈
- runtime이 조사 원장·schema를 해석하거나 default render path에 추가 I/O를 만듦
- private corpus 식별 자료, host path 또는 허가되지 않은 font bytes가 diff에 포함됨
- 최신 `upstream/devel`과 충돌을 해결한 뒤 focused/full gate가 다시 통과하지 않음

W7 뒤에도 개별 mapping이 올바른지, unknown relation을 어떤 근거로 승격할지는 해결되지 않는다.
그 교정은 W8에서 한 face씩 Oracle·SFNT·metric evidence를 갖춘 별도 승인 작업으로 수행한다.

## 13. 완료 기준

- 네 projection의 모든 현행 유한 규칙이 registry row 또는 명시적 비대상 근거에 대응한다.
- schema·semantic validator가 relation/plane/backend 혼합, active-unknown 삭제와 의미 승격을 fail-closed한다.
- 생성 전후 table·lookup·condition·order·renderer 결과가 exhaustive comparison에서 동일하다.
- Rust와 TypeScript 생성 항목의 `ruleId`가 W1 원장 및 W2 trace와 이어진다.
- 동일 입력의 registry·backend별 projection hash와 생성 bytes가 결정론적이다.
- 단일 규칙 mutation에서 필요한 backend 산출물만 달라지고 나머지 hash는 동일하다.
- runtime 성능·startup 경계, private corpus와 font license 경계가 유지된다.
- 신규 규칙 변경 절차, Stage 보고서와 최종 보고서가 작성되고 메인테이너가 승인한다.

## 14. 계획 self-review

- **목적 검사**: 중복 제거 자체가 아니라 관계별 authority와 backend projection을 만들고 현재 조판을
  보존하는 목표로 한정했다.
- **계보 검사**: W1은 migration 근거, W6는 metric lineage, W2는 관측 ID로 소비하며 어느 snapshot도
  그대로 runtime policy로 오인하지 않는다.
- **의미 검사**: layout name·metric·paint·supply·capability를 분리하고 자동 승격을 금지했다.
- **행동 검사**: source table 비교뿐 아니라 lookup·condition·order·renderer 결과를 전수 비교한다.
- **생성 검사**: 출력 allowlist, paired write, stale check, deterministic hash와 단일 rule 최소 영향
  contract를 포함했다.
- **성능 검사**: runtime JSON 해석을 피하고 기존 정적 lookup의 복잡도·allocation을 보호한다.
- **보안·저작권 검사**: URL을 실행하지 않고 경로·크기 상한을 두며 private corpus와 font bytes를 제외했다.
- **운영 검사**: Stage별 보고·commit·승인과 remote push·PR·merge 별도 승인을 명시했다.
