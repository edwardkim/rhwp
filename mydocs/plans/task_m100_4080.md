## 1. 문제

[PR #3810](https://github.com/edwardkim/rhwp/pull/3810)이 고정한 Actions 캐시 기준선 4.73GB가 사흘 만에
스윕 직후 기준 8.84GB로 올랐다. 조사 시점 실제 총량은 53개 10.01GB로 **무료 한도 10GB의 100.1%**이며,
GitHub의 LRU 축출이 이미 도는 구간이다.

세대 상한은 정상 동작 중이었다. (ref, 그룹) 쌍 42개 중 2세대를 초과한 쌍은 3개뿐이었고 전부 마지막
스윕 이후 생성분이었다. 즉 #3684의 해법이 깨진 게 아니라 **전제가 바뀌었다.**

## 2. 원인

1. **쌍 수 증가로 하한이 올라감.** 세대 상한이 (ref, 그룹) 쌍마다 적용되므로 총량 하한이 쌍 수에
   비례한다. `refs/heads/devel` 한 ref만으로 19개 5.84GB로 기준선 전체를 넘는다.
2. **고아 ref 캐시.** 브랜치가 삭제되거나 PR이 닫혀도 그 ref의 최신 N개는 영구히 정리 대상이 아니다.
   GitHub의 7일 미사용 만료까지 자리를 차지한다.
3. **신호 부재.** 총량이 한도의 100%까지 오르는 동안 어떤 경고도 없었다.

## 3. 목표와 범위

| 항목 | 포함 여부 |
| --- | --- |
| 고아 ref 정리 | 포함 |
| 한도 경보 | 포함 |
| 스윕 판정 계약 테스트 | 포함 |
| `devel` 한정 KEEP=1 | **제외** — 4절 |
| 새 기준선 수치 확정 | **제외** — merge 뒤 실측으로 |

`devel` KEEP=1은 총량 기여가 가장 크지만, #3684가 KEEP=2를 택한 근거(진행 중 job이 방금 만든 캐시를
지울 위험, lock 변경 직후 PR cold)가 devel에도 적용되는지 미확인이다. devel 캐시의 실제 restore 주체와
빈도를 먼저 관측해야 판단할 수 있고, 고아 정리만으로 목표를 넘기므로 이번에 묶지 않는다.

## 4. 예상 단계

1. 실제 캐시 스냅샷으로 고아의 규모와 성격을 확인한다.
2. 스윕 워크플로에 고아 판정과 한도 경보를 넣는다.
3. 판정을 계약 테스트로 고정하고 뮤테이션으로 실효성을 확인한다.
4. 실제 스냅샷 시뮬레이션으로 정리 후 총량을 예측한다.
5. merge 뒤 실제 cron 스윕 1회로 예측을 검증하고 새 기준선을 정한다.

## 5. 안전 요구사항

이 워크플로는 삭제를 수행하므로 오작동의 비용이 비대칭이다. 다음을 필수 조건으로 둔다.

- checkout 금지 경계 유지. 권한은 최소로만 늘린다.
- 살아 있는 ref 목록을 못 믿는 상태에서는 삭제하지 않는다(fail-closed).
- dry-run으로 대상을 먼저 확인할 수 있어야 한다.
- 열린 PR의 캐시는 어떤 경우에도 지우지 않는다.

## 6. 구현 중 바뀐 판단

계획 시점에 없었고 구현·검토에서 드러난 것들이다. 사후에 계획서를 다듬지 않고 그대로 남긴다.

- **조회 순서가 안전 계약이라는 점을 처음엔 몰랐다.** 초안은 ref를 먼저 읽었고, 시뮬레이션 중에
  캐시를 먼저 읽어야 경합이 없다는 것을 깨달아 뒤집었다.
- **고아의 규모를 5배 과소평가했다.** 이슈에는 "약 0.53GB"로 적었는데 `refs/heads/*`만 센 값이었다.
  실제는 2.50GB이고 대부분이 닫힌 PR의 `refs/pull/<n>/merge`다.
- **`sweep_orphan_refs: false`가 동작하지 않았다.** boolean 입력에 `A && inputs.x || '<기본>'`
  관용구를 써서 끄려던 값이 켠 값이 됐다. 작업지시자 리뷰로 드러났고 dispatch 실측으로 확인했다.
- **새 계약 테스트가 CI에서 한 번도 돌지 않았다.** 같은 구멍이 #4071에도 있었다. 배선 자체를
  강제하는 테스트를 추가하는 것으로 범위를 넓혔다.
- **`refs/pull/<n>/head` 가정을 명시하지 않았다.** 고아 정리가 생기면서 이 ref의 캐시는 세대 상한이
  아니라 전량 삭제 대상이 됐다. 열린 PR의 `/head`도 보호하도록 고쳤다.

## 7. 완료 조건

- 계약 테스트가 고아 판정, fail-closed, 조회 순서, 한도 임계, boolean 입력 표현식, 배선을 모두
  뮤테이션으로 잡는다.
- merge 뒤 실제 cron 스윕이 예측치를 확인한다.
- 새 기준선을 #4080에 기록한 뒤 이슈를 닫는다.
