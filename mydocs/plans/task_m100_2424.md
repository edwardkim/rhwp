## 2. 최신 기준선과 유효성

최신 `upstream/devel@12f8a820`에서 #2424의 핵심 병목과 correctness 제약이 모두 남아 있다.

- `flushDeferredPagination()`은 page-tree cache를 무효화한 뒤 동기 `paginate()`를 호출한다.
- dirty section은 selective measurement를 일부 재사용하지만 `TypesetEngine`은 새 `TypesetState`로
  section 처음부터 다시 조판한다.
- `PageItem::matches_with_offset`의 `PartialTable` 비교는 para/control/row range만 보고
  continuation, start/end cut, block split을 비교하지 않는다.
- 최신 focused test에서 HWP/HWPX 모두 115 fragments와 full flush 뒤 113 changed cuts를 유지했다.

다만 #2430의 한양·휴먼 ASCII 메트릭 교정으로 숫자 입력의 flow boundary가 44번째에서 56번째로
이동했다. 이전 계측 브랜치의 44-input 하네스와 약 1.16초 수치는 현행 성능 기준선으로 재사용하지 않고,
56-input 기준으로 다시 측정한다.

## 3. 기존 로컬 프로토타입의 취급

`codex/issue-2424-pagination-subphase-profile`에는 2026-07-19 기준 7개 로컬 commit이 있다.

- Stage A subphase timer와 HWP/HWPX probe
- deferred pagination descriptor와 revision
- table structure fingerprint와 stale target guard
- continuation cursor와 owned context
- caller-controlled fragment budget step

이 브랜치는 현재 devel보다 383 commits 뒤이고 `typeset.rs`, rendering, text editing, WASM tests에 병합
충돌이 있다. 또한 pending job, WASM step API, Studio scheduler는 아직 구현하지 않아 UI long task를
줄이지 않는다.

따라서 브랜치 전체를 rebase/cherry-pick하지 않는다. 각 단계의 계약과 테스트 의도를 최신 코드에서
다시 구현하고, 기존 diff는 필요한 부분만 참고한다.

## 4. 단계

### Stage A — 최신 subphase 기준선 재확정

Native 전용 진단 게이트로 다음 시간을 분리한다.

- cache invalidation
- render normalization
- selective/full measurement
- `TypesetEngine` 전체와 target block-table continuation
- pagination 후처리와 dirty cleanup

HWP/HWPX 각 5회 이상 56-input boundary를 재현해 p50/min/max와 115쪽·113 changed cuts를 기록한다.
계측 코드는 후속 구현 방향을 결정한 뒤 production diff에서 제거할 수 있다.

### Stage B — descriptor와 stale guard

deferred cell edit가 revision, section/host/table/cell/cell paragraph, first affected page와 table structure
fingerprint를 보존한다. 새 edit, target 소실, 구조 변경을 구분하고 resumable job을 계속할 수 없는 경우
기존 full pagination으로 fallback한다.

### Stage C — synchronous resumable continuation

최신 `typeset_block_table`의 continuation loop를 owned cursor/context와 caller-controlled step으로 분리한다.
Native driver는 작은 fragment budget으로 동기 drain하며 one-shot full 결과와 모든 page의 row/cut/
continuation/block flag, geometry와 used height를 exact 비교한다.

### Stage D — pending job과 browser chunk/yield

shadow pagination result를 `DocumentCore`가 호출 사이에 보존한다. WASM begin/step/finish API와 Studio
scheduler를 연결해 한 task에서 제한된 fragment만 처리하고 다음 macrotask 또는 frame으로 yield한다.

- 새 edit는 이전 revision job을 취소·교체한다.
- 진행 중 공개 pagination은 완료 상태로 노출하지 않는다.
- save/save-as/print/manual full query는 동기 drain 또는 기존 full fallback을 보장한다.
- 완료 시 revision과 fingerprint를 다시 검증하고 shadow result를 원자적으로 commit한다.

### Stage E — 정확성·성능 수용 검증

- HWP/HWPX 115쪽과 page 0~114 fragment 연속성
- full pagination oracle과 model/tree/layout/cursor/caret exact 정합
- stable 입력의 full flush 0회
- pending job cancel/restart와 save/print completion/fallback
- 단일 blocking slice, 전체 completion, input-to-2-rAF p50/p95 before/after

## 5. 초기 fast-path

다음을 모두 증명할 수 있는 text-only cell edit로 제한한다.

- single-section, single-column
- row/column/span/control 구조 불변
- section/page/column definition 불변
- affected chain에 footnote/endnote 또는 pagination 종속 floating object 없음
- header/footer/master/new-page-number/page-hide 경계 없음
- fragment 연속성, page count와 global page offset 검증 가능
- edit revision과 pagination work revision 일치

하나라도 불확실하거나 fingerprint/state 검증이 실패하면 기존 full pagination으로 fallback한다.

## 7. Stage A 결과와 결정

최신 56-input 기준 HWP/HWPX 각 5회 incremental flush에서 전체 중앙값은 각각 1058.381ms,
1112.625ms였다. `TypesetEngine` 중앙값은 1044.644ms, 1099.749ms로 전체의 약 98.7%, 98.8%였고,
각 실행에서 `section=0/para=0/control=2/rows=3` block-table 하나가 114개 후속 페이지를 만들었다.

HWP run 3은 incremental total 3336.130ms의 outlier였으며 이때도 typeset이 3311.536ms를 차지했다.
measurement 중앙값은 HWP 13.079ms, HWPX 13.195ms이고 postprocess 중앙값은 0.033ms, 0.030ms다.

최신 #2214 exact-cut oracle도 HWP/HWPX 모두 115 fragments와 full flush 뒤 113 changed cuts를 유지했다.
따라서 측정·정규화·후처리 최적화가 아니라 table continuation loop를 resumable step으로 분리하고 browser
yield를 연결하는 기존 방향을 유지한다. 상세 raw 값과 환경은 Stage 1 보고서와 JSON 자산에 기록한다.

## 8. Stage B 결과

deferred cell edit마다 단조 revision과 target 좌표, 기존 pagination의 target 첫 global page, 누적
`cellFlowChanged`, table structure fingerprint를 기록한다. fingerprint는 row/column/span뿐 아니라 셀 문단
수와 문단 내 control 종류, 중첩 table 구조까지 포함한다.

각 resumable step이 사용할 stale guard는 다음 상태를 구분한다.

- 최신 descriptor와 구조가 일치하면 `Current`
- 새 deferred edit가 revision을 교체하면 `Superseded`
- section/paragraph/table/cell paragraph 좌표가 사라지면 `TargetMissing`
- 표 또는 셀 문단 control 구조가 달라지면 `StructureChanged`

동기 full pagination 성공 시 descriptor를 소비하는 수명 계약도 고정했다. focused 상태 전이 테스트,
#2214 library 9건, page-local repaint 3건과 `wasm32-unknown-unknown` library check가 통과했다. 상세 근거는
Stage 2 보고서에 기록한다.

## 9. Stage C 결과

최신 `typeset_block_table`의 row/cut 진행 상태를 `TableContinuationCursor`로 분리하고, 한번 계산한
split 입력과 shadow `TypesetState`를 `BlockTableContinuationContext`가 소유하도록 바꿨다. 각 iteration은
`Skipped`/`Emitted`/`Complete`를 반환하며 caller가 fragment budget 단위로 `step`을 호출한다. 현재 Native
경로는 step을 동기 drain하므로 공개 동작은 그대로다.

#2214 HWP/HWPX exact-cut oracle에서 budget 1은 115 fragments를 115 steps, budget 8은 15 steps,
무제한은 1 step으로 처리했다. 세 설정 모두 115쪽·113 changed cuts, adjacent cut 연속성, page 0
tree/cursor/cell bounds를 유지했다. #2214 library 9건, page-local repaint 3건과 wasm32 library check도
통과했다. 상세 근거는 Stage 3 보고서에 기록한다.

## 10. Stage D 결과

한 구역·한 문단·마지막 대형 RowBreak 표로 한정한 pending job을 `DocumentCore`에 추가했다. job은 최신
descriptor와 selective measurement, borrow-free continuation context를 소유하고, 각 step에서 target 구조와
revision을 다시 확인한다. 공개 pagination은 pending 114 steps 동안 유지되고 115번째 complete에서만
measurement·dirty flag·render cache와 함께 교체된다.

WASM begin/step/cancel/drain API와 Studio macrotask runner를 연결했다. 새 입력은 이전 job과 예약 task를
취소해 최신 revision으로 교체하고, save/save-as/print/manual flush는 동기 drain 또는 full fallback을
보장한다. 구버전 WASM과 fast-path 비대상 문서도 기존 동기 의미론을 유지한다.

HWP/HWPX #2214 fixture에서 budget 1은 각각 115 calls/115 fragments/115 pages를 만들었고, transient 대비
113 changed cuts와 모든 adjacent cut 연속성이 full oracle과 일치했다. release 계측은 begin 31.5~32.5ms,
step p50 10.16~10.18ms, p95 10.73~11.00ms, max 21.66~22.29ms였다. Studio 507 tests와 production build,
wasm-pack web binding, wasm32 check를 통과했다. 상세 근거는 Stage 4 보고서에 기록한다.
