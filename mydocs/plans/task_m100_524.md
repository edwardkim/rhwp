# Task #524 수행 계획서 — exam_science p2 우측 단 공백 + 쪽나누기 컬럼 인식 처리

## 1. 배경

`samples/exam_science.hwp` 페이지 2가 좌측 단에 표 2개(보기 + 답지, used=132.7px)만 표시되고 우측 단은 공백. 결과적으로 PDF에서 페이지 2에 있어야 할 8번 문제가 페이지 3 좌측 단으로 한 페이지 밀려 있다.

## 2. 증상 (이슈 #524)

```
페이지 2 단 0 (items=2, used=132.7px)
  Table  pi=30  3x3   407.4×107.1px   (보기, 문제 6 꼬리)
  Table  pi=31  1x10  411.9×19.1px    (답지)
페이지 2 단 1: (없음)

문단 0.32 [쪽나누기]  vpos=0  "7.-다음은 학생 가 수행한 탐구 활동이다."
```

## 3. 원인 분석 (가설)

### 가설 A — `[쪽나누기]` 처리의 컬럼 인식 누락 (1차 의심)

`src/renderer/pagination/engine.rs:139-148`에서 `page_break_before` 또는 `ColumnBreakType::Page`이면 `process_page_break()` → `force_new_page()` 호출. 다단(multi-column) 레이아웃에서 좌측 단에 있는 동안 page-break를 만나면 우측 단을 그대로 버리고 다음 페이지로 점프한다.

```rust
if (force_page_break || para_style_break) && !st.current_items.is_empty() {
    self.process_page_break(&mut st);   // → force_new_page()
}
```

비교: `process_column_break()`는 `advance_column_or_new_page()` 호출 (컬럼 인식). HWP의 동작이 진정한 "하드 페이지 브레이크"라면 현재 동작이 정합. 단, 한컴 PDF가 페이지 2 우측 단을 채우는 것으로 보인다는 사용자 보고와 모순. 한컴 동작 확인 필요.

### 가설 B — 페이지 1 우측 단 누적 높이 inflation (2차 의심)

페이지 1 단 1 used=1112.6px / 잔여 102.5px. 문제 6의 보기 표(107.1px) + 답지 표(19.1px) = 126.2px 필요하나 24px 차이로 페이지 2 좌측 단으로 spill. 가설 B가 참이면 보기/답지가 페이지 1에 들어가서 [쪽나누기]가 페이지 1 우측 단 끝에서 발동 → 자연스럽게 페이지 2 좌측으로. 그러면 우측 단도 채워질 가능성.

후보 누적 오차 원인:
- 줄간격 백분율(line=140%/Percent) 누적 계산
- 단락 후간격(spacing after=1000 HWPUNIT) 처리
- 표 outer_margin 또는 line_spacing 가산 중복

### 우선 가설

**B → A 순서**로 진단. B가 해결되면 A는 자동 해소되거나 영향이 사라질 가능성. 단 다른 페이지(p3 단 1: 135.4px만 사용, p4 단 1: 21.5px만 사용)에서도 우측 단 공백이 보이므로 A도 별도로 검증.
