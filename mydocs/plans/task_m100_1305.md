- 대상 마일스톤: M100 / v1.0.0
- 브랜치: `local/task1305` (base: `local/task1304` — #1304 시그마 수정 연속 검증)

## 2. 문제 요약

`(k+1)^2` 처럼 **괄호 그룹 뒤 위첨자**가 base 없는 orphan(`Superscript{base:Empty, sup:2}`)이 되어 지수 `2` 가 위첨자 높이로 올라가지 못하고 낮게 표시된다. 브레이스 표기 `(k+1) ^{2}` 에서도 동일.

`7^2`(숫자 base)는 정상 → **괄호/구분기호 그룹 한정** 문제.

## 3. 근본 원인

리터럴 `(...)` 가 `EqNode::Paren` 그룹이 아니라 **느슨한 `Symbol("(")` … `Symbol(")")`** 로 파싱된다 (`parse_element` 의 LParen/RParen 분기, parser.rs:199).
따라서 `)` 뒤의 `^2` 는 결합할 base 가 없어 `parse_element` 의 Subscript/Superscript 분기(203)에서 `try_parse_scripts(EqNode::Empty)` → orphan Superscript 가 된다.

`EqNode::Paren { left, right, body }` 노드는 LEFT-RIGHT 용으로 존재하며 #1226 으로 뒤따르는 첨자 결합을 이미 지원한다. 텍스트 높이 둥근 괄호는 layout/render 가 글리프(`(`,`)`)로 그려 느슨한 Symbol 과 동일하게 보인다.

## 4. 작업 범위

범위:
- 리터럴 `(...)` 가 **뒤에 `^`/`_` 가 올 때만** `EqNode::Paren` 그룹으로 묶여 첨자를 결합하도록 파서 보강.
- 첨자 없는 일반 괄호는 기존 느슨한 렌더 유지 (회귀 0 목표).
- `(k+1)^2`, `(k-1)^2` 등 대상 정상화.

비범위:
- 대괄호 `[...]^n` (텍스트 높이에서도 path 렌더라 외형 변화 위험 → 별도 검토).
- 괄호 layout/render 변경, stretch 괄호 로직.
- 첨자 위치/크기 파라미터 조정.

## 6. 구현 방향 후보

### 후보 A: 모든 `(...)` 를 Paren 그룹화

장점: 단순. 단점: 첨자 없는 수천 개 기존 괄호의 내부 패딩(layout_paren PAREN_PAD)이 느슨한 Symbol 렌더와 미세히 달라져 광범위 회귀 위험.

### 후보 B: trailing-script 가 있을 때만 그룹화 (기본안)

`(` 를 만나면 매칭 `)` 까지 스캔해 그 다음 토큰이 `^`/`_` 인 경우에만 Paren 그룹으로 파싱하고 `try_parse_scripts`. 아니면 기존 `Symbol("(")` 유지.

장점: 깨진 케이스(첨자 동반 괄호)만 그룹화 → 일반 괄호 렌더 무변경, 회귀 최소.
단점: 매칭 괄호 스캐너 필요.

## 7. 기본안

후보 B. 라운드 괄호 `(...)` 한정.

```text
1. parse_element LParen 분기에 "매칭 ) 다음이 ^/_ 인가" 스캔 추가.
2. 참이면 parse_paren_group() → EqNode::Paren{ "(",")", body } 후 try_parse_scripts.
3. 거짓이면 기존 Symbol("(") 유지.
4. (k+1)^2 → Superscript{ base: Paren, sup: 2 } AST 테스트.
5. 일반 괄호(첨자 없음) 회귀 가드 테스트.
```
