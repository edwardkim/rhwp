# #8153: 같은 런의 오른쪽 탭과 명시적 정지

## 원 해결과 독립 근거

PR #1021·Task #874의 보정과 공통 측정 통합 `b9075217cc`를 추적했다.
기존 분기는 같은 런의 RIGHT+leader를 항상 셀 우단으로 정렬한다.
HWP5 §4.2.7 표 36은 탭 위치·종류·채움을 구분하고 표 37은 자동 우측 탭을 별도로
정의한다. 채움이 있다는 이유로 명시적 탭 위치를 무시할 근거는 없다.

편람 280쪽의 두 실제 런은 자동 우측 탭이 꺼져 있고 명시적 정지는 38,272 HU다.
원본 저장 전진 폭은 각각 1,106·1,162 HU다. 실제 스타일에서 명시적 정지는
510.29333px, 현재 셀 우단은 520px이며 현재 문자 배치는 후자를 강제한다.
독립 Print의 두 쪽번호는 앞의 명시적 정지에 대응한다. 이 수치는 원인 증거이며
제품에 페이지·문서 ID·보정 좌표로 추가하지 않는다.

고정 source `c3b88a07df`의 실제 Native paint를 사용한 진단에서 수정 전 PNG는
정식 전쪽 출력과 RGB 전픽셀이 같았다. 원본에서 읽은 명시적 정지를 적용한 진단과
저장 전진 폭을 보존한 진단 모두 **미대응 164→0픽셀·raw 100%**다.
원본·PDF·글꼴·텍스트·소유·측정 기준을 바꾸지 않았다. 별도 source-free offset을
맞춘 결과가 아니며 제품 수정 뒤의 재검증을 대신하지 않는다.

## 공통 수정과 반례

`TabDef와 유효한 inline tab → 공통 정지 선택 → 측정 폭과 문자 위치 →
intrarun bbox·canonical TabLeader·Native/Canvas`의 실제 경로를 연결한다.
기존 `find_next_tab_stop`의 명시적 정지와 가용 프레임 계약을 재사용한다.
단 안의 정지는 보존하고, 더 좁은 셀 밖에 저장된 정지는 기존 프레임 계약을 유지한다.
명시적 RIGHT 정지가 없으면 유효한 저장 전진을 소비한다. 자동 우측 탭과
교차 런 정렬은 기존의 정렬 단위·문자 순서 계약을 함께 확인한다.
리더 채움만으로 셀 우단을 선택하는 잘못된 가정을 제거한다.

정식 두 원본의 `tests/cases/issue_8153_*` 검사에서 같은 런의 숫자 끝이 원본의
명시적 정지와 일치하는 관계·소유·순서를 보호한다. 같은 검사 원문으로 수정 전
실패와 수정 후 통과를 확인한다. 기존 intrarun bbox·자동 탭·교차 런·중간 탭·
명시적 LEFT·가용폭 밖의 정지 대조도 실행한다. 관련 매뉴얼의 과도한 일반화를
실제 검증 결과와 함께 정정한다.

새 Native 영향 페이지와 직접 판독을 먼저 확인하고 표준 최적화 fresh WASM 및
전쪽을 같은 원본/PDF로 검증한다. 현재 source의 전쪽 1,532조건은 모두 90% 이상이나
최종 목표인 전쪽 raw 100%·미대응 0과 필수 전체 테스트는 아직 완료되지 않았다.
작업 증적은 ignored `remaining-raw100-diagnostic/remaining-direct-current/`다.
upstream 동기화와 원격 GitHub 쓰기 없이 PR 준비까지만 진행한다.

## 후속: 저장 너비와 명시적 정지가 갈리는 실제 줄

원본 279쪽의 `10. 공문서 작성시…`와 `11. 공무직 등…`은 같은 paraPr61·tabPr10을
쓴다. 명시적 RIGHT 정지는 38,272HU이고 자동 우측 탭은 꺼져 있다. 실제 inline
너비는 각각 9,938HU·12,366HU다. 같은 저장 줄의 세로/가로 메트릭도 원본에서
읽었으며, 원본을 수정한 합성 입력이 아니다.

동결된 Native source `e5a1e3e04a`의 실제 paint에서 두 숫자의 x는 모두 586.56px다.
독립 Print의 첫 숫자는 583.04px, 다음 숫자는 586.56px다. 숫자 세 글자와 리더의
대응도 확인했으므로 다른 `279`를 찾은 결과와 구분한다. 현재 첫 탭 원점과 원본의
9,938HU를 더한 값은 583.01333px이며 Print의 장치 격자 위치와 대응한다.

280쪽만으로는 명시적 정지와 저장 전진의 우선순위를 구분하지 못했다. 이 실제
반례에서 원본 inline 너비·유효한 저장 줄과 편집 후 재조판의 계약을 구분하고,
공통 탭 측정 → 교차 런 pending → 숫자 블록 배치 → TabLeader/bbox를 추적한다.
원본 값의 직접 재생 진단과 정상 대조를 먼저 실행한 뒤 구현 근거를 판정한다.
현재 관측만으로 탭 종류나 전체 저장/재조판 규칙을 바꾼 것으로 기록하지 않는다.
원본 값·현재 실제 스타일·독립 glyph 원점은 ignored 작업 폴더의
`p279-source-paragraphs.json`, `p279-independent-digit-positions.json`,
`current-native-residual-text-attrs.json`, `residual-text-independent-origin-comparison.json`에 있다.

## 279쪽의 원본 전진 재생과 구현 경계

source `143f99b7aa`의 실제 Native paint 진단은 출력 전 RGB가 기존 PNG와 동일했다.
별도 탭 런의 원본 32비트 전진을 재생하면 279쪽은 미대응 17→0픽셀·raw 100%이고,
280쪽은 0픽셀을 유지한다. 4~8쪽은 이 진단이 적용되는 별도 탭 런이 없으므로
불변이며, 같은 런 내부 탭의 새 규칙을 입증한 결과로 사용하지 않는다.

실제 소비 경로는 `compose_paragraph`의 저장 줄 수용 → `tab_extended` →
`geometry_inline_tabs` → 교차 런 pending → 측정·배치 →
`resolve_trailing_tab_end`와 canonical TabLeader다. 원본·합성 줄 부재는
`para_has_no_stored_line_segs`가 구분하며, 그때 composition은 저장 탭을 전달하지 않는다.
현재 프레임에서 줄을 재구성하는 `StoredRowResolution::Reflowed` 역시 원본 탭 전진을
새 줄의 캐시로 넘기지 않아야 한다. 원본 모델·직렬화 바이트는 보존한다.

새 pending은 유효한 원본 RIGHT 전진의 **정렬 완료된 다음 블록 시작**과,
자동 우측/가운데/저장 정보 부재의 **아직 정렬할 정지**를 구분한다. 측정과 배치가
같은 시작점을 소비하며, 전자에서 뒤 블록 폭을 다시 빼지 않는다. 자동 우측 탭은
현재 프레임과 블록 폭으로 정렬하는 기존 계약을 유지한다. 채움은 정렬 여부를 바꾸지 않는다.
같은 런 내부 탭과 가운데 탭의 계약은 이 279쪽 보정으로 바꾸지 않는다.

실제 두 원본 279쪽의 서로 다른 저장 전진·문단 소유·숫자 순서·리더 끝을 검사하고,
280쪽과 목차 경계를 대조한다. 단위 계약은 원본 RIGHT·자동 탭·자리표·상위 16비트·
공백 carry-over와 재조판 후 저장 전진 폐기를 포함한다. 현재 진단은 제품 수정의
PASS 근거가 아니며, 보정 후 Native/fresh WASM과 전체 범위를 다시 확인한다.

## 제품 Native 검증과 검사 경로 정리

제품 source `bddd5d58e4`의 두 원본 279쪽은 각각 미대응 17→0픽셀·raw 100%다.
같은 source에서 두 문서 4~9·27·136·166·183·232·251·277·279·280쪽,
총 30조건을 비교했으며 다른 조건의 미대응 증가가 없다. 280쪽은 0픽셀을 유지한다.
이 결과는 전쪽 Native·WASM 1,532조건 완료를 뜻하지 않는다.

같은 실제 원본 검사에서 이전 source `143f99b7aa`는 두 문서 모두 첫 숫자
586.56px와 원본 전진의 시작 583.01333px가 달라 FAIL이며, `bddd5d58e4`는
두 검사 모두 PASS다. 처음 진단의 문단 검색은 표 셀 대신 구역 직접 문단을
조회하여 실패했으므로 결함 재현으로 세지 않고, 실제 표·셀·문단 소유를 찾는
검사로 수정한 뒤 같은 검사 원문으로 전후를 다시 실행했다. 정식 등록은 해당
새 source의 fresh WASM 확인 뒤에 진행한다.

source 내부 단위 검사 증가 금지 정책에 맞춰 기존 탭·재조판 검사를 보강하고,
그림자 검사는 `tests/cases/issue_8153_text_shadow_transport.rs`의 공개 문서 API →
실제 메모리 글꼴 공급 → 공통 Print 계획 → JSON/SVG·소유 clip 경로로 옮겼다.
동결된 `bddd5d58e4`의 라이브러리에서 3건 모두 PASS다. 합성 TTF는 저장소가
직접 만든 MIT fixture이며 읽기·메모리 등록만 한다. 한컴 시각 일치 증거로 사용하지 않는다.
외부 PUA 공급 계약이 이 합성 TTC에 적용된다고 가정했던 초기 검사 초안은 폐기하고,
실제 공개 경로가 지원하는 기존 ASCII 합성 face를 사용했다. 테스트를 위해 제품의
PUA 수용 규칙·폰트 파일·공개 API를 바꾸지 않았다.

부분 수식 재조판은 그대로 보존하는 앞행의 탭 순번·전진을 유지하고 새 줄의
저장 전진만 폐기하도록 추가 보완했다. 이 후속 source의 실제 단위·시각 재검증과
최종 최적화 WASM 및 전쪽 검증은 아직 남아 있다.

독립 Print로 출력했다. 원래 편람의 입력·기준 PDF는 바꾸지 않았다.
RIGHT 탭 뒤의 고정폭 공백과 `Z`가 별도 런으로 나뉘는 두 줄에서, Print의 `Z`는

Print 글리프 원점으로 확인했으며 폰트나 페이지 이름을 판정 조건으로 사용하지 않는다.

Task279의 기존 공백 carry-over를 유지한다. 생산자는 유효한 저장 탭이며, 소비자는
`resolve_last_tab_pending` → 측정/배치의 동일 pending → 실제 bbox·TabLeader다.
같은 런·별도 런의 공백과 자동 우측·가운데·자리표 대조를 검사하고, 실제 원본
279·280쪽 및 목차 경계의 Native/fresh WASM을 다시 확인한다.

진단과 독립 저장/Print 작업 영수증은 ignored
`continuous-text-shadow/leader-independent-controls-v2/`에 있다.
`source-span-vs-independent-cells.json`의 두 공백 줄은 현재 `Z`가 독립 Print보다
각각 약 4px 왼쪽임을 기록한다. 작은 입력의 Print 좌표계는 원래 편람의 쪽 크기와
다르므로 원점 비교 시 실제 Print 변환 행렬을 구분하며 제품에 보정 배율을 넣지 않는다.
점 리더의 실제 글리프·개수·간격은 별도 진단 중이며 아직 제품 규칙으로 채택하지 않았다.

## 점 리더의 실제 글리프와 셀 배분 진단

사양 표 36은 탭 채움 종류를 표 25로 연결하지만 특정 글꼴의 원·실선 윤곽을
지정하지 않는다. 독립 Print의 실제 점은 U+00B7 글리프이며, 해당 두 공급 글꼴의
원 프로그램과 Print 내장 글리프의 윤곽·hmtx가 같은 것을 메모리 안에서 확인했다.
현재 Native/SVG는 U+00B7 텍스트도 합성 원으로 바꾸므로, 문자열로 치환한 최초
진단은 실제 원 프로그램의 글리프를 검증한 결과가 아니다.

9·12·15pt, 두 글꼴, 짧은/긴 앞말, 고정폭 공백을 포함한 실제 한컴 저장·Print
8행에서는 1/4em 셀에 따른 점 개수와 마지막 셀 원점이 대응한다. 단순 고정 피치와
실제 글리프를 조합한 진단은 미대응이 증가하여 채택하지 않았다. 현재 리더 시작·끝
안에서 셀을 배분한 실제 윤곽 진단은 4쪽 1→0, 6쪽 10→1, 7쪽 6→3픽셀이고
279·280쪽은 0픽셀을 유지한다. 이는 공통 paint 구현이나 최종 WASM 검증이 아니며
제품 반영 전 실제 공급·소유·장식 경로와 정상 대조를 더 확인한다.

제품에 옮기지 않는다. 공통 측정/배치·소유·leader·각 backend와 대조군을 실제로

`continuous-text-shadow/toc-stored-and-outline-diagnostic/`에 있다.

## 점 리더 제품 단계의 공급·소비 연결

기존 bounded exact-font 슬롯 순회에 실제 탭 런 선택을 추가해 사용 중인 글자 모양·
언어만 수집한다. 기존 PUA·전체 슬롯 순회의 계약과 한도를 유지하며, 모든 미사용
글꼴을 선등록하는 방식으로 대신하지 않는다. 기존 텍스트 효과 공급 요청과 Native/
Studio/WASM의 같은 프로그램 등록·cache invalidation 경로를 재사용한다.

`원본 탭 슬롯 → 실제 supplied/embedded SFNT face → 공통 paint의 U+00B7 윤곽·
셀 원점 → 기존 Path paint → Native/Canvas/SVG`로 연결한다. 리더 장식만 Path로
내리고 원문 TextRun·소유·순서·저장 바이트는 유지한다. 다른 채움은 기존 TabLeader를
유지한다. 실제 face의 지원·외곽선과 자원 한도를 확인한 경우에만 원 장식을 대체하며,
부분 실패에서 리더를 소실시키지 않는다. 수평 본문과 기존 회전·세로 경로의 적용 경계를
구분하고 같은 서체의 실제 굵기·기울임도 확인한다.

수정 전 공개 core/실제 한컴 저장본의 탭 시작·공백 포함 관계와 실제 점 장식 경로에서
의도한 실패를 확보한다. 새 검사는 source 내부의 검사 수를 늘리지 않고 정식 cases
경로와 기존 계약 보강을 사용한다. 기존 단위 검사의 자동 우측 가정은 유효한 저장
전진과 재조판 후 동적 정렬을 구분한 독립 기대값으로 재검토한다.

## 장평 대조와 끝 탭 기하의 소비 보완

장평 80·100·120%의 추가 실제 한컴 저장·Print 8행에서도 셀 수의 기준은 장평을
곱한 폭이 아니라 명목 1/4em이다. 장평은 실제 점 윤곽에 적용한다. 원본·글꼴을
수정하거나 출력 점수로 계수를 구하지 않았다.

이 대조는 별도 fwSpace의 시작·전진과 기존 리더 끝이 갈리는 문제도 드러냈다.
예를 들어 120%의 공백은 원본 360HU·4.8px를 점유하지만 기존 리더는 공백 안에
그리기 끝을 남긴다. 초기 후보의 공통 Path만으로 이 오래된 끝을 정확하게 바꿀 수
없다. 숫자 시작·공백·TabLeader는 같은 확정 위치 배열을 소비해야 한다.

유효한 저장 pending은 공백 런을 방출하기 전에도 저장 시작점을 소비한다. 끝 탭
소비자는 뒤 공백의 원래 전진을 보존해 위치 배열을 완성하고, 기존 장식을 사후
늘이거나 임의로 clamp하지 않고 같은 배열에서 채움 기하를 다시 산출한다. 기존
일반/특수 탭과 #6800·#6801의 bbox/전진·장식 소비 경로도 대조한다.

## 실제 공급에서 확인한 바이트 상한 보완

첫 제품 후보에서 합성 공급·Path 전송·HWP 원본 검사는 통과했지만 HWPX의 실제 공급은
기존 64MiB 상한에 걸렸다. 점 하나를 요청하면서 fallback 사다리의 모든 프로그램을
등록한 것이 원인이다. 상한을 높이거나 파일을 복사해 해결하지 않는다.

요청이 정해진 글리프 집합을 가지면 실제 SFNT cmap가 그 집합을 공급하는 첫 후보만
등록한다. 이 판정을 Native·WASM·Studio가 같은 읽기 전용 프로그램 조회로 사용하게 한다.
전체 fallback이 필요한 연속 그림자와 WMF의 기존 요청은 유지한다. 같은 스타일의 요청이
합쳐지면 전체 요청을 축소하지 않으며, 빈 glyph 요청·등록 캐시·누락 후보를 각각 대조한다.

`e8122b1157`의 실제 HWP 목차 4·5·6·7·8·279·280쪽은 모두 raw 100%·미대응

검증 완료를 뜻하지 않는다.

### 브라우저 공급 face의 신원

기존 Visual Sweep catalogue의 `faceIndex`는 원 TTC의 출처 인덱스다. 실제 HTTP
응답과 기존 Canvas/paint 등록은 추출된 단독 SFNT의 0번 face를 사용한다. 현재 공급
목록의 바탕체도 원 인덱스 1과 단독 SFNT 헤더 `00010000`으로 이를 확인했다. 새 cmap
조회도 같은 공급 bytes의 0번 face를 읽어야 하며 원 출처 인덱스로 조회하지 않는다.
Native·Studio가 원 TTC bytes를 직접 받는 경로는 실제 인덱스를 유지한다. 이 구분을
공급 선택 검사에서 보호하며 프로그램·글꼴 이름·원본 파일은 변경하지 않는다.
