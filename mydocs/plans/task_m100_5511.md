## 1. 결정과 목표

#5511은 하나의 거대한 파일 이동 PR이 아니라 CLI 경계를 순차적으로 복원하는 마스터
이슈다. 각 단계는 독립적으로 검증·커밋·리뷰할 수 있어야 하며, 단계 종료 시 최신
`upstream/devel`과의 관계 및 지표를 다시 확인한 뒤 메인테이너 승인을 받아 다음 단계로
진입한다.

기존 복잡도 리팩토링 마스터 계획은 전역 지표 모집단에서 CLI dispatch인 `src/main.rs`를
제외했다. #5511은 그 전역 모집단을 소급 변경하지 않는다. 대신 비대해진 CLI 어댑터를
**태스크 로컬 평가 단위**로 정의하고, 사용자 계약을 고정한 상태에서 다음 목표를 달성한다.

1. 명령 메타데이터의 단일 원천을 마련한다.
2. 조회와 상태 변경의 물리적 경계를 복원한다.
3. CLI가 문서 내부 구현 대신 application/service 경계에 의존하도록 전환한다.
4. `src/main.rs`를 프로세스 조립과 최상위 dispatch에 집중하는 얇은 진입점으로 만든다.

## 2. 기준선

기준선은 위 커밋의 `src/main.rs`를 정적 계측한 값이다. Stage 0에서 동일한 산출 절차와
함께 재현 가능한 조사 문서로 고정한다.

| 파일 크기 | 1,792,248 bytes |
| 최상위 함수 | 351 |
| 편집 handler | 92 |

큰 함수의 대표 사례는 `mcp_tool_definitions` 약 4,178줄,

계약 테스트는 보호하고 확장해야 할 경계다.

## 3. 보호 불변식

모든 단계에서 다음 조건을 지킨다.

1. CLI 명령·옵션 이름, help 문구와 순서, 기본값, exit code, stdout/stderr 분리는 바꾸지 않는다.
2. JSON·NDJSON의 필드명·형식과 MCP tool 이름·schema·annotation은 바꾸지 않는다.
3. HWP/HWPX parser, serializer, renderer의 결과와 round-trip 동작을 바꾸지 않는다.
4. 읽기 전용 query와 상태 변경 command를 의미적으로 구분한다. 파일을 생성하는 export는
   문서를 변경하지 않더라도 부작용 경계를 명시한다.
5. crates.io 등 새 배포 채널이나 신규 기능을 추가하지 않는다.
6. Render Diff workflow와 classifier 개선은 #3789의 소유 범위다. #5511에서 그 workflow를
   우회하거나 중복 수정하지 않는다.
7. 생성된 snapshot을 갱신해 계약 차이를 감추지 않는다. 차이가 발생하면 먼저 원인을
   규명하고 해당 단계를 중단한다.

## 4. 수행 단계

### Stage 0 — CLI 계약과 의존 계보 동결

소스 이동 전에 현재 상태를 재현 가능한 증거로 만든다.

- `mydocs/tech/investigations/issue-5511/`에 명령 표면, handler, dispatch, help,
  capabilities, MCP tool, JSON/exit-code 계약과 기존 테스트의 대응표를 기록한다.
- `src/main.rs`, `src/mcp_serve.rs`, `src/bin/rhwp-agent/caps.rs`, application/service 및
  document-core 경계의 의존 방향을 기록한다.
- 미보호 계약을 식별하되 이 단계에서는 구현을 이동하지 않는다. 이동 전에 필요한 최소
  characterization test만 별도 변경 단위로 제안한다.
- 기준선 지표와 검증 명령, 결과를 Stage 0 작업 보고서에 남긴다.

완료 조건은 조사 문서·계약 대응표·실행 결과가 서로 일치하고, 다음 추출 단위가 근거를
갖고 선택된 상태다. Stage 0을 커밋한 뒤 메인테이너 승인을 받아 Stage 1로 진행한다.

### Stage 1 — 명령 catalog 단일 원천과 entrypoint 축소

동작 handler보다 중복된 명령 메타데이터를 먼저 분리한다.

- `src/bin/rhwp-agent/caps.rs`의 `CommandSpec`은 이미 동작하는 참고 사례로 검토하되,
  rhwp CLI 계약에 맞는 구조를 별도로 설계한다.
- `src/cli/catalog.rs`, `src/cli/help.rs`, `src/cli/mcp_catalog.rs` 등 책임별 모듈 후보를
  Stage 0 계보에 따라 확정한다. 파일명은 구현 시 Rust module 경계와 순환 의존을 검토해
  조정할 수 있다.
- help, capabilities, MCP schema·annotation의 동일 정보를 catalog에서 파생하도록 만든다.
  파생 결과는 기존 출력과 byte/semantic equivalence 검사를 모두 통과해야 한다.
- 실제 command handler와 dispatch 의미는 이 단계에서 바꾸지 않는다.

한 PR에 catalog 전체를 억지로 담지 않는다. 계약 characterization과 catalog 추출이 독립
리뷰 단위라면 각각 분리한다. 단계 종료 시 `main.rs` 크기뿐 아니라 중복 원천의 수와 계약
테스트의 보호 범위를 함께 보고한다.

### Stage 2 — CLI command/query 물리 분리

검증된 catalog를 기준으로 handler를 `src/cli/commands/`, `src/cli/queries/` 및 최소한의
공유 모듈로 이동한다.

- 먼저 의존이 작고 계약 테스트가 충분한 read-only query 한 계열을 수직 절편으로 이동해
  module API와 검증 절차를 확정한다.
- 이후 편집 command는 기능 계열별로 이동한다. 92개 handler를 한 번에 옮기지 않는다.
- `finish_edit_write`는 검증된 공통 seam으로 보존한다. move-only 기준선을 확보한 뒤에만
  `EditContext` 같은 명시적 의존성 묶음으로의 진화를 별도 변경 단위로 검토한다.
- command와 query가 공유하는 것은 타입·오류·입출력 어댑터 등 최소 요소로 제한한다.
  편의를 위한 양방향 참조나 새로운 God module을 만들지 않는다.

각 수직 절편 또는 기능 계열은 독립 PR 후보이며, 매 라운드 지표 재측정과 메인테이너
승인을 거친다.

#### Stage 2 실행 단위 재기준화 — 2026-08-19

24개 수직 절편 뒤 `src/main.rs`는 42,370줄에서 38,561줄로 줄었지만, 1,200줄 수용 기준에
필요한 감소량의 9.3%만 달성했다. 계약 보강과 단일 handler 이동마다 승인·전체 회귀·보고를
각각 반복하면 동일 속도에서 이동 절편만 약 190개가 더 필요한 구조다. 품질 관문은 유지하되
실행 단위를 응집된 기능군으로 확대한다.

- 메인테이너 승인은 개별 handler가 아니라 기능군 배치의 시작과 종료에서 받는다.
- 필요한 characterization test와 물리 이동은 같은 승인 배치 안의 분리 커밋으로 수행한다.
- focused test는 커밋마다, 전체 release-test와 정적·정책 검증은 배치 종료 시 한 번 수행한다.
- 원격·열린 PR 검사는 배치 시작과 종료에 수행하고, 도중 같은 경로의 원격 변경을 발견하면
  즉시 재검증한다.
- 배치는 한 도메인, 3~12개 handler, 대략 600~2,500 이동 줄을 기본 상한으로 삼는다. 새
  모듈은 각각 1,200줄 이하를 지킨다.
- 계약 차이, parser·serializer·renderer 동작 변경 필요, 순환 의존, CC>25 함수의 단순 이전,
  동시 PR 경로 중첩이 발견되면 배치 진행을 중단하고 메인테이너에게 보고한다.

상세 기능군, 순서, Stage 2 종료 조건은
[`task_m100_5511_stage2_batch_plan.md`](task_m100_5511_stage2_batch_plan.md)를 따른다. 이
재기준화는 보호 불변식이나 Stage 3·4의 수용 기준을 낮추지 않는다.

### Stage 3 — service layer와 DIP 전환

물리 분리만으로 감춰진 직접 의존을 application/service 경계로 옮긴다.

- 읽기·open 계열부터 application service를 통하도록 전환하고, 편집 command는 기능 계열
  하나씩 이전한다.
- CLI가 `wasm_api::HwpDocument`, parser, serializer, renderer 내부 타입을 직접 조립하는
  경로를 단계적으로 제거한다.
- `src/mcp_serve.rs`가 현재 binary helper인 `tables_json_value`, `info_json_value`,
  `fields_json_value`, `search_json_value`, `structure_json_value`,
  `extract_data_json_value`에 의존하는 경계를 재사용 가능한 application API로 이동한다.
- 전역·thread-local 상태는 마지막에 명시적 context 또는 service 의존성으로 바꾼다.
- 내부 오류는 typed error로 정리하되 사용자에게 보이는 메시지와 exit code는 보존한다.

공개 library API 변경이 필요하면 #5511의 내부 리팩토링으로 묵시적으로 처리하지 않고,
영향 분석과 별도 승인을 거친다.

### Stage 4 — 최종 수렴과 계보 보고

- `src/main.rs` 1,200줄 이하, 새 CLI 모듈 각각 1,200줄 이하를 확인한다.
- CLI 평가 단위에서 CC 25 초과 함수를 0으로 만들고, 목표 CC 15 이하에 도달하지 못한
  항목은 근거와 후속 이슈를 남긴다.
- `src/main.rs`의 `wasm_api::HwpDocument` 직접 참조가 0인지 확인한다.
- help·capabilities·MCP metadata가 단일 원천에서 파생되고 기존 계약과 동등한지 확인한다.
- 단계별 기준 SHA, 지표 변화, 검증 결과, 남은 위험과 후속 이슈를 최종 보고서에 기록한다.

## 6. 위험과 대응

| 위험 | 대응 |

- 관찰 가능한 CLI·MCP 계약 차이가 발생한 경우

- 추출에 parser·serializer·renderer 동작 변경이 필요해진 경우
- 기존 테스트가 이동 전 동작을 고정하지 못해 characterization test가 먼저 필요한 경우
