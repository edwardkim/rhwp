# #9164 Studio 최초 페이지 렌더링 경합 수정 계획

2026-11-18 · 담당 postmelee · 브랜치 `task/9164-studio-initial-page-render` · 기준 `fbf8081db5`

## 재현 근거

이슈에 보고된 Chromium 계측에서 최초 로드의 글꼴 준비 중에 loadingdone을 주입하면 완료 상태에서 페이지 캔버스가 0개였다. 주입 없는 대조군과 재열기는 각각 2개였다. 자연 발생 시점의 이벤트 순서는 확인되지 않았다.

v0.9.0과 기준 devel에서 CanvasView의 Git blob은 동일하다. 각 커밋의 실제 loadDocument, prepareRendererRevision, refreshPagesForRevision, selectNextDocumentRevision, refreshPages 메서드를 Node에서 실행하고 렌더러와 WASM을 합성 3쪽 입력으로 대체했다. 대조군은 두 버전 모두 페이지 목록 3개, 초기 그리기 호출 1회, document-view-loaded 통지 1회였다. 최초 metrics 준비 중 microtask에서 화면 갱신을 호출하면 양쪽 모두 0개, 0회, 0회였다. 이 검사는 브라우저의 글꼴 이벤트 전달과 실제 픽셀 출력을 측정하지 않는다.

## 구현 및 검증 범위

1. 독립 Chromium 세션에서 순정 v0.9.0과 기준 devel의 정상 열기와 loadingdone 주입을 대조한다. 합성 문서로 상태 표시줄, 연결된 페이지 캔버스, 첫 페이지의 내용과 완료 순서를 기록한다.
2. 최초 페이지 구성의 소유권을 현재 문서에 묶는다. 같은 문서의 글꼴 준비 갱신은 최신 준비 결과로 첫 화면을 완성하고, 교체된 문서의 비동기 작업은 새 화면과 상태 표시줄을 갱신할 수 없게 한다. 편집 중 렌더러 재선택과 기존 글꼴 준비 실패 복구 경로를 보존한다.
3. 브라우저 회귀에서 이벤트 없는 대조군, 최초 준비 중 loadingdone, 연속 갱신, 동일 문서 재열기, 구별되는 두 합성 문서의 빠른 교체, 준비 실패 후 복구를 확인한다. 제어 가능한 글꼴 응답 지연 및 호스트 글꼴 갱신의 영향을 구분한다. 실제 파일 열기와 성공 표시를 거치는 진입점으로 검사한다.
4. 수정 전 실패와 수정 후 통과를 같은 입력에서 확인하고 Studio 변경 범위의 로컬 검증을 실행한다. 공개 테스트와 기록에는 합성 자료만 사용한다.

이슈 담당자를 지정했고 번호로 검색한 열린 PR은 없었다. 원격 push와 PR 생성은 별도 승인 단계에서 진행한다.
