# Task M100-1329 수행계획서 — 글머리표 Enter 직후 빈 줄 caret 위치 보정

## 이슈

- GitHub Issue: #1329 `rhwp-studio: 글머리표 Enter 직후 빈 줄 caret이 글머리표 앞에 표시됨`
- 브랜치: `issue-1329-bullet-caret`
- 마일스톤: M100 / v1.0.0 편집 기반

## 배경

rhwp-studio에서 글머리표가 적용된 문단 끝에서 Enter를 누르면 새 문단에 같은 글머리표가 유지된다.
이때 실제 텍스트 입력은 글머리표 뒤 본문 위치에 정상 삽입되지만, 입력 전 깜박이는 caret은 글머리표
앞쪽 또는 글머리표 위치보다 왼쪽에 표시된다.

즉 문서 모델의 삽입 위치와 화면에 보이는 caret 위치가 어긋난다. 사용자는 입력 위치를 caret으로
판단하므로, 빈 글머리표 문단에서도 caret은 실제 입력 위치인 글머리표 뒤 본문 시작점에 표시되어야 한다.

한컴 직접 편집기 검증은 현재 로컬에 `Hancom Office HWP Viewer.app`만 있어 수행하지 못했다. 다만 한컴
도움말 기준으로 글머리표 문단에서 Enter를 누르면 같은 글머리표가 이어지고, 번호/글머리표 영역은 본문
입력 영역과 분리되어 취급된다. 따라서 caret은 번호/글머리표 marker가 아니라 본문 삽입 위치를 가리키는
것이 한컴 호환 방향이다.

참고:

- <https://help.hancom.com/hoffice/multi/ko_kr/hwp/format/numberbullet/numberbullet%28bullet%29.htm>
- <https://help.hancom.com/hoffice/multi/ko_kr/hwp/format/numberbullet/numberbullet%28position%29.htm>

## 목표

1. 글머리표 문단에서 Enter를 누른 직후 새 빈 글머리표 문단의 caret이 글머리표 뒤 본문 시작 위치에 표시된다.
2. 실제 텍스트 입력 위치와 입력 전 caret 위치가 일치한다.
3. 번호 문단에도 같은 구조적 결함이 있으면 같은 원칙으로 함께 보정할지 Stage 1에서 판정한다.
4. 기존 텍스트 입력, 글머리표 유지, 번호/글머리표 렌더링, 일반 빈 문단 caret 위치는 회귀하지 않는다.

## 비범위

- 글머리표/문단 번호 정의 UI 개편은 이번 범위가 아니다.
- 글머리표 marker 자체를 문서 문자 좌표에 포함시키는 구조 변경은 이번 범위가 아니다.
- 한컴의 모든 list continuation 규칙, list level 증감, 자동 번호 해제 규칙은 이번 범위가 아니다.
- 머리말/꼬리말, 각주/미주, 글상자, 중첩 표 내부 list 문단은 Stage 1에서 영향만 조사하고 필요하면 후속 분리한다.

## 현재 관찰

초기 조사 기준 코드 경로:

- `rhwp-studio/src/engine/input-handler-keyboard.ts`
  - plain Enter에서 `SplitParagraphCommand` 실행
- `rhwp-studio/src/engine/command.ts`
  - 문단 분할 성공 후 새 문단 `charOffset: 0`으로 cursor 이동
- `src/model/paragraph.rs`
  - `split_at()`이 새 문단에 기존 `para_shape_id`를 복사하므로 글머리표 ParaShape는 유지됨
- `src/renderer/layout/paragraph_layout.rs`
  - 번호/글머리표는 `char_start: None`인 별도 TextRun으로 렌더링됨
  - 문서 문자 좌표에는 포함되지 않음
- `src/document_core/queries/cursor_rect.rs`
  - cursor 탐색에서 `char_start: None`인 번호/글머리표 TextRun을 건너뜀
  - 빈 문단 fallback이 TextLine 시작 x를 반환할 수 있어 marker 폭 또는 본문 시작 x 보정이 누락될 수 있음

초기 가설:

```text
문서 위치: 새 문단 charOffset 0 → 정상
렌더링: 글머리표 marker는 별도 TextRun → 정상
caret 좌표: 빈 list 문단 fallback에서 numbering_text 폭을 반영하지 않음 → 결함 후보
```

## 접근 방향

Stage 1에서는 소스 수정 없이 다음 두 후보 중 실제 결함 지점을 확정한다.

1. 후보 A — cursor rect fallback 보정
   - 빈 번호/글머리표 문단에서 `charOffset: 0` caret을 TextLine 시작 x가 아니라 본문 시작 x로 반환한다.
   - `numbering_text` 폭 또는 렌더 트리의 list marker TextRun 폭을 반영한다.
   - 장점: 결함이 발생한 좌표 계산 경로에만 좁게 적용할 수 있다.
   - 위험: 본문 첫 TextRun이 없는 경우 스타일/폭 계산 기준을 새로 맞춰야 한다.

2. 후보 B — 빈 list 문단 렌더 트리에 zero-width 본문 anchor 생성
   - 글머리표 뒤 본문 시작 위치에 `char_start: Some(0)`인 zero-width TextRun 또는 anchor를 생성한다.
   - 기존 cursor 탐색 로직이 자연스럽게 정확한 hit을 찾게 한다.
   - 장점: cursor rect, hit-test, selection 계열에서 anchor 재사용 가능성이 있다.
   - 위험: 렌더 트리 구조 변경으로 selection/hit-test에 예상 밖 영향이 생길 수 있다.

권장 출발점은 후보 A다. 단, Stage 1에서 빈 list 문단 렌더 트리 구조와 selection 영향도를 확인한 뒤
후보 B가 더 안전하면 구현 계획서에서 조정한다.

## 성공 기준

1. 글머리표 Enter 직후 새 빈 글머리표 문단의 caret이 marker 뒤 본문 시작점에 표시된다.
2. 입력 전 caret x와 첫 입력 문자 x가 실질적으로 일치한다.
3. 글머리표 marker는 계속 문서 문자 좌표에 포함되지 않는다.
4. 번호 문단이 같은 구조라면 동일 원칙으로 처리하거나 후속 분리 근거를 남긴다.
5. 일반 빈 문단, 일반 텍스트 문단, 기존 글머리표 렌더링이 회귀하지 않는다.
6. 최소 한 개 이상의 자동 회귀 가드 또는 명확한 수동 재현 검증 절차가 남는다.

## 리스크

- `numbering_text` 폭 계산이 렌더 시점 스타일과 다르면 caret x가 marker 뒤 위치와 어긋날 수 있다.
- cursor rect 보정만 하면 hit-test나 selection 시작점과의 정책 차이가 남을 수 있다.
- 번호 문단은 numbering counter 상태가 개입되므로 글머리표보다 재현/테스트가 복잡할 수 있다.
- 셀/글상자/주석 문맥은 별도 cursor rect API를 사용하므로 한 번에 처리하면 범위가 커질 수 있다.
