## 1. 목표

혼합 글자색 범위에 형광펜을 적용해도 기존 색을 보존하고, Undo/Redo가 적용 전후의 구간별
글자 모양을 정확히 복원하도록 한다. 동일 경로의 굵기·글꼴 등 미지정 속성도 보존한다.

## 2. 확정된 기준선

사용자가 Firefox 확장 배포본에서 발견했다. 설치 버전·Firefox 버전은 미확인이다.
최신 devel 소스를 `scripts/wasm-pack-locked.sh --target nodejs --no-opt`로 빌드하고,
실제 Studio `ApplyCharFormatCommand`·`CommandHistory`를 연결하여 아래를 확인했다.
새 문서는 Studio와 동일하게 `createEmpty()` 뒤 `createBlankDocument()`로 초기화했다.

| 동작 | 결과 |
| --- | --- |
| `가나다라마바` 중 `다라`만 보라색 → 전체 노랑 형광펜 | 전체 글자색이 검정으로 바뀐다. |
| Undo → Redo | 형광펜은 제거·복구되지만 보라색은 돌아오지 않는다. |
| Undo 후 HWPX 저장·재적재 | 소실된 글자색 상태가 유지된다. |
| 보라색 `다라`만 형광펜 → Undo/Redo | 색상·선택 밖 모양 모두 유지된다. |
| 보라색에서 시작하는 `다라마바` 선택 | 뒤의 검정 글자까지 보라색으로 바뀐다. |
| 혼합 색상 전체에 굵게 적용 | 색상 소실과 Undo 미복원이 동일하게 발생한다. |
| 코어 호출만 기존 구간별로 나눈 분리 실험 | 적용 직후 색은 보존되나 실제 Studio Undo/Redo가 다시 소실시킨다. |

5개 재현·대조·분리 시나리오의 assertion이 예상과 일치했고 실행 종료 코드는 0이었다.
이는 수정 후 통과 증적이 아닌 **수정 전 결함 증적**이다. Firefox UI E2E는 아직 실행하지 않았다.
`v0.8.6` 태그에도 두 원인 코드가 있다. 원인과 재현 결과는 이슈 본문에도 게시했다.

원인:

1. [코어 적용](../../src/document_core/commands/formatting.rs)은 선택 시작 ID 하나를 기준으로
   새 모양 하나를 만들고 전체 범위에 덮어쓴다.
2. [Studio 명령](../../rhwp-studio/src/engine/command.ts)은 문단당 before/after ID 하나씩만
   저장하여, 서로 다른 모양 구간을 복원할 정보를 잃는다.

## 3. 범위와 불변식

범위 안:

- 본문, 일반·중첩 셀의 기존 글자 서식 적용 및 Undo/Redo.
- 머리말/꼬리말의 동일 원인 적용 경로와 기존 snapshot Undo/Redo의 보존 확인.
- F5 셀 블록의 적용 결과 및 기존 snapshot 복원 대조.
- 기존 서식 구간 보존을 위한 코어 공통 처리와 필요한 WASM/Studio 범위 API.
- 혼합 색상·굵기·글꼴, 부분 선택, 같은 구역의 여러 문단, UTF-16 경계, HWP/HWPX 저장 왕복.
- 실제 브라우저에서 형광펜 적용·Undo/Redo·저장·재열기 확인, Firefox 확장 빌드 경로 점검.

범위 밖:

- 미지원 각주 편집 등 새 편집 기능, 일반 renderer/layout 정책 개편.
- 색상 팔레트 디자인·키보드 접근성 #6635, 형광펜 sentinel 색 정책 변경.
- 구역 교차 선택 등 별개 원인의 범위 확장. 발견 시 영향과 분리 필요성을 보고한다.
- 원격 배포, 스토어 업로드, 승인 없는 push·PR·merge·close.

보호 불변식:

1. 명시하지 않은 속성은 각 기존 구간의 값을 유지한다. 선택 밖 구간은 변하지 않는다.
2. Undo/Redo는 위치·구간별 ID를 복원하며 UI 표시용 JSON을 재해석하지 않는다.
3. 문자 offset과 IR UTF-16 위치의 변환, 제어문자·문단 끝 경계를 보존한다.
4. `raw_stream` 무효화, 셀 dirty, reflow·pagination, paint-only 판정을 기존 계약대로 유지한다.
5. 문자마다 JS↔WASM을 왕복하지 않는다. 구간 수에 비례한 전달과 문단 단위 갱신을 사용한다.
6. 새 Rust integration 원본은 `tests/cases/`에만 둔다. 파생 suite·manifest는 제출하지 않는다.

## 5. 검증 계획과 승인 경계

단계별 focused 검증은 각 단계 승인 범위에 포함한다. 최종 광범위 검증은 2단계 결과를 공유하고
**3단계/PR 준비 승인**을 받은 뒤 실행한다. 기준은
[로컬 검증 4.3](../manual/pr_review/local_validation.md#43-변경-범위별-기본-검증)이다.

- Rust lint 전체: fmt, native Clippy, WASM32 Clippy, workspace build·all-target Clippy.
- 관련 Rust focused 계약과 `release-test` 전체 nextest 회귀.
- 새 WASM API를 사용하므로 fresh WASM build, TypeScript 검사, Studio npm test, 실제 browser 동작.
- WASM 영향 범위에 맞춰 Native Skia 3종도 최종 gate에 포함한다. 판정은 구현 후 실제 변경 범위와
  canonical 검증표를 대조하고, 축소가 필요하면 사유와 승인을 기록한다.
- HWP/HWPX 저장 후 재적재에서 구간별 색·모양 확인. 새 `samples/` 자료 추가 시 IR sweep과
  overflow-cell baseline 절차를 추가하며, 초기에는 코드로 생성하는 최소 문서를 사용한다.
- Firefox 확장 경로 검증은 실제 실행 여부와 버전을 기록한다. 일반 브라우저만 실행한 결과를
  Firefox 검증 완료로 대신하지 않는다. 불가 시 미검증 상태를 남기고 완료 판정을 요청한다.
- 시각 검증은 [시각 거버넌스](../manual/verification/visual_verification_governance.md)에 따라
  사용자-visible 글자색·형광펜 보존에 집중한다. renderer 정책 변경 시 별도 visual sweep 범위를 재판정한다.

Cargo·WASM 검증은 고정 `target/pr-review`를 재사용해 순차 실행한다. generated integration
준비·검사는 별도 review worktree에서만 실행한다. 계획 작성 단계에서는 Cargo/npm을 실행하지 않았고,
1단계 승인 후 코어 변경에 대한 focused Rust 검증을 수행했다.
