# #8153: Print 그림의 색과 투명도 마스크 분리

## 원본과 독립 관측

두 편람 원본 255쪽의 같은 PNG 그림은 768×401 RGBA다. 원본 투명도는 20개
수준이지만 독립 한컴 2024 Print의 색 자원은 JPEG이고 마스크는 1비트다.
현재 제품은 RGB555 PNG에 원본 8비트 투명도를 유지한다. 색 압축 전달은
`print_codec::encode`가 불투명 그림만 허용하며, 공통 면적 표본도 불투명만 소비한다.
원본의 알파를 PDF 마스크로 바꿔 읽거나 단순 PNG 재생으로 두 단계를 대신할 수 없다.

원본 JPEG 채움 보정 source `c3b88a07df`의 정식 Native 255쪽에는 미대응 265픽셀이
남는다. 261쪽의 전체 JPEG 채움과 다른 Picture 계약이므로 그 보정의 적용 조건을
PNG·투명 그림으로 넓히지 않는다. 원본·공식 효과/투명도 속성·원본 창은 입력 계약이며,
PDF 생성기의 이진 마스크·압축 정책을 HWP 사양에 명시된 수치라고 주장하지 않는다.

## 일반 규칙을 구분하는 독립 대조군

원본 255쪽의 알파만으로는 8×8과 16×16 순서 디더를 구분할 수 없었다.
이에 원본 HWPX의 같은 그림 소유 문단·자원 크기·창·그림 배치를 추출해 임시 1쪽
대조군을 만들었다. 그림만 직접 생성한 RGB와 256단계 알파로 바꾸었으며 원본은
바꾸지 않았다. 알파는 각 16×16 타일에서 `((x // 16) + 17 * (y // 16)) % 256`다.
프로그램으로 만든 합성 입력이며 원래 저장본의 독립 시각 증거와 구분한다.

이 신규 입력의 첫 독립 PDF를 job `dd2114a4-10f4-4325-b0b2-b5e944d61046`로 만들었다.
실제 한컴 2024 `13.0.0.3901`·PrintMethod 0·
`frame_print_to_pdf_ex_one_up`·입력 전처리 없음·1쪽을 확인했다.
입력 SHA-256은 `5f9e6c441534f1ba98011ec677764813864a2a52dc2956b6467c486fdb76b434`,
PDF SHA-256은 `93d1f9e9b8c2c93b54c73756c5ecc3fa5761f66866513ef47c6aa7b4c90c1071`다.
기존 편람 PDF를 재출력하거나 교체하지 않았다.

공개 재귀 Bayer 순위를 16×16까지 구성하고 원본 좌상단을 기준으로
`alpha > rank`를 적용하되 alpha 255의 완전 불투명을 유지하면, 원본과 신규 대조군의
독립 마스크 각각 **307,968픽셀 모두 정확히 같다**. 4×4·8×8과 행 반전은 신규
대조군에서 불일치한다. 이 규칙의 비교에는 PDF 화소를 입력으로 주입하지 않았다.
단일 사례에만 맞는 8×8 추정과 alpha 255를 낮추는 일반화는 채택하지 않는다.

## 아직 해결하지 않은 색과 표본 경계

원본의 RGB555 색·원본에서 계산한 마스크·마스크 밖 흰색·기존 품질 44의 JPEG를
조합하면 원본 255쪽의 독립 JPEG와 RGB가 전픽셀 같다. 그러나 같은 처리를 새 색
대조군에 적용하면 RGB가 다르다. 기존 정식 JPEG 인코더로도 같은 차이가 나므로
Pillow와 제품 인코더의 차이로 면제하지 않는다. premultiply/unpremultiply의
정수 연산 위치와 색 전달을 독립 대조군에서 더 구분해야 한다. 오차가 작은 후보를
정답으로 채택하거나 특정 문서에만 적용하지 않는다.

추가로 같은 RGB 패턴을 완전 불투명 RGBA와 RGB PNG로 각각 만들었다.
같은 그림 크기·창·소유 문단을 유지한 독립 Print job은 각각
`731c58a8-b042-428e-87f5-0481eac1c797`, `1df800f1-2e0c-4e5e-8077-522422c0a2aa`다.
두 출력 모두 2024 PrintMethod 0·1쪽·입력 전처리 없음을 확인했다.
두 자원의 JPEG RGB는 기존 bottom-up RGB555와 공통 품질 44에서
**307,968픽셀 모두 정확히 같다**. 알파 채널 유무 자체나 일반 RGB555가 원인이라는
가설은 기각하고, 실제 반투명 경로의 색 전달·정수 복원 위치를 구분한다.
비교 원문은 `opaque-color-independent-result.json`이다.

Windows GDI+의 실제 `LockBits`와 `GdipBitmapConvertFormat`도 같은 생성 PNG를
메모리에서 직접 읽어 측정했다. 일반 32비트 ARGB 읽기는 원본 RGBA를 전픽셀
보존했지만, 16비트 읽기와 Ordered4x4 변환만으로는 독립 Print의 색·마스크가
재현되지 않았다. 실제 GDI+ 결과라는 이유로 이 변환을 한컴 Print의 계약으로
동일시하지 않는다. 이 관측은 디더·색·마스크 생산 단계가 같다는 가정을 기각하며
반투명 처리 위치를 더 추적할 근거다. 원격 저장소·검증 파일을 만들지 않고
프로세스 메모리에서만 실행했으며 script·raw·비교 결과는 output에만 보존했다.

또한 원본에서 계산한 JPEG RGB와 이진 알파를 단순 RGBA PNG로 재생하는 실제 Native
진단은 미대응 **265→406픽셀**로 나빠졌다. 진단의 수정 전 PNG는 정식 현재 Native와
RGB 전픽셀이 같았다. 배치·텍스트·소유를 그대로 둔 자원 변경만으로 개선되지
않으므로 이 후보는 제품 코드에 반영하지 않았다. 색 압축·마스크 표본·최종 합성을
각각 추적하고 같은 공통 결과를 Native·Canvas가 소비하도록 검증해야 한다.

다음 구현은 독립 색 대조군과 원본 출력의 원인을 함께 설명한 뒤 진행한다.
관련 모든 쪽의 Native/fresh WASM·직접 판독 선행 조건을 확인한 후 정식
`tests/cases/issue_8153_*` 검사에 같은 마스크·색·투명/불투명 경계를 보호한다.
진단용 합성 원본·PDF·실행 결과는 ignored `remaining-raw100-diagnostic/alpha-print-contract/`에만
보존하며 아직 제출 fixture나 완료된 회귀 검사로 분류하지 않는다.

제품 코드·편람 원본·기존 PDF·글꼴·측정 기준은 이 조사에서 바꾸지 않았다.
SO 분석 자료는 output에만 둔다. 전쪽 100%와 필수 테스트 후 PR 준비까지만 진행하며
사용자 지시 전 upstream 동기화·원격 GitHub 쓰기를 하지 않는다.
