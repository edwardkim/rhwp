# #8153: Print 그림의 색과 투명도 마스크 분리

## 원본과 독립 관측

두 편람 원본 255쪽의 같은 PNG 그림은 768×401 RGBA다. 원본 투명도는 20개
수준이지만 독립 한컴 2024 Print의 색 자원은 JPEG이고 마스크는 1비트다.
현재 제품은 RGB555 PNG에 원본 8비트 투명도를 유지한다. 색 압축 전달은
`print_codec::encode`가 불투명 그림만 허용하며, 공통 면적 표본도 불투명만 소비한다.
원본의 알파를 PDF 마스크로 바꿔 읽거나 단순 PNG 재생으로 두 단계를 대신할 수 없다.

원본 JPEG 채움 보정 source `c3b88a07df`의 정식 Native 255쪽에는 미대응 265픽셀이
남는다. 261쪽의 전체 JPEG 채움과 다른 Picture 계약이므로 그 보정의 적용 조건을
PNG·투명 그림으로 넓히지 않는다. 원본·공식 효과/투명도 속성·원본 창은 입력 계약이며,
PDF 생성기의 이진 마스크·압축 정책을 HWP 사양에 명시된 수치라고 주장하지 않는다.

## 일반 규칙을 구분하는 독립 대조군

원본 255쪽의 알파만으로는 8×8과 16×16 순서 디더를 구분할 수 없었다.
이에 원본 HWPX의 같은 그림 소유 문단·자원 크기·창·그림 배치를 추출해 임시 1쪽
대조군을 만들었다. 그림만 직접 생성한 RGB와 256단계 알파로 바꾸었으며 원본은
바꾸지 않았다. 알파는 각 16×16 타일에서 `((x // 16) + 17 * (y // 16)) % 256`다.
프로그램으로 만든 합성 입력이며 원래 저장본의 독립 시각 증거와 구분한다.

이 신규 입력의 첫 독립 PDF를 job `dd2114a4-10f4-4325-b0b2-b5e944d61046`로 만들었다.
실제 한컴 2024 `13.0.0.3901`·PrintMethod 0·
`frame_print_to_pdf_ex_one_up`·입력 전처리 없음·1쪽을 확인했다.
입력 SHA-256은 `5f9e6c441534f1ba98011ec677764813864a2a52dc2956b6467c486fdb76b434`,
PDF SHA-256은 `93d1f9e9b8c2c93b54c73756c5ecc3fa5761f66866513ef47c6aa7b4c90c1071`다.
기존 편람 PDF를 재출력하거나 교체하지 않았다.

공개 재귀 Bayer 순위를 16×16까지 구성하고 원본 좌상단을 기준으로
`alpha > rank`를 적용하되 alpha 255의 완전 불투명을 유지하면, 원본과 신규 대조군의
독립 마스크 각각 **307,968픽셀 모두 정확히 같다**. 4×4·8×8과 행 반전은 신규
대조군에서 불일치한다. 이 규칙의 비교에는 PDF 화소를 입력으로 주입하지 않았다.
단일 사례에만 맞는 8×8 추정과 alpha 255를 낮추는 일반화는 채택하지 않는다.

## 아직 해결하지 않은 색과 표본 경계

원본의 RGB555 색·원본에서 계산한 마스크·마스크 밖 흰색·기존 품질 44의 JPEG를
조합하면 원본 255쪽의 독립 JPEG와 RGB가 전픽셀 같다. 그러나 같은 처리를 새 색
대조군에 적용하면 RGB가 다르다. 기존 정식 JPEG 인코더로도 같은 차이가 나므로
Pillow와 제품 인코더의 차이로 면제하지 않는다. premultiply/unpremultiply의
정수 연산 위치와 색 전달을 독립 대조군에서 더 구분해야 한다. 오차가 작은 후보를
정답으로 채택하거나 특정 문서에만 적용하지 않는다.

추가로 같은 RGB 패턴을 완전 불투명 RGBA와 RGB PNG로 각각 만들었다.
같은 그림 크기·창·소유 문단을 유지한 독립 Print job은 각각
`731c58a8-b042-428e-87f5-0481eac1c797`, `1df800f1-2e0c-4e5e-8077-522422c0a2aa`다.
두 출력 모두 2024 PrintMethod 0·1쪽·입력 전처리 없음을 확인했다.
두 자원의 JPEG RGB는 기존 bottom-up RGB555와 공통 품질 44에서
**307,968픽셀 모두 정확히 같다**. 알파 채널 유무 자체나 일반 RGB555가 원인이라는
가설은 기각하고, 실제 반투명 경로의 색 전달·정수 복원 위치를 구분한다.
비교 원문은 `opaque-color-independent-result.json`이다.

Windows GDI+의 실제 `LockBits`와 `GdipBitmapConvertFormat`도 같은 생성 PNG를
메모리에서 직접 읽어 측정했다. 일반 32비트 ARGB 읽기는 원본 RGBA를 전픽셀
보존했지만, 16비트 읽기와 Ordered4x4 변환만으로는 독립 Print의 색·마스크가
재현되지 않았다. 실제 GDI+ 결과라는 이유로 이 변환을 한컴 Print의 계약으로
동일시하지 않는다. 이 관측은 디더·색·마스크 생산 단계가 같다는 가정을 기각하며
반투명 처리 위치를 더 추적할 근거다. 원격 저장소·검증 파일을 만들지 않고
프로세스 메모리에서만 실행했으며 script·raw·비교 결과는 output에만 보존했다.

또한 원본에서 계산한 JPEG RGB와 이진 알파를 단순 RGBA PNG로 재생하는 실제 Native
진단은 미대응 **265→406픽셀**로 나빠졌다. 진단의 수정 전 PNG는 정식 현재 Native와
RGB 전픽셀이 같았다. 배치·텍스트·소유를 그대로 둔 자원 변경만으로 개선되지
않으므로 이 후보는 제품 코드에 반영하지 않았다. 색 압축·마스크 표본·최종 합성을
각각 추적하고 같은 공통 결과를 Native·Canvas가 소비하도록 검증해야 한다.

다음 구현은 독립 색 대조군과 원본 출력의 원인을 함께 설명한 뒤 진행한다.
관련 모든 쪽의 Native/fresh WASM·직접 판독 선행 조건을 확인한 후 정식
`tests/cases/issue_8153_*` 검사에 같은 마스크·색·투명/불투명 경계를 보호한다.
진단용 합성 원본·PDF·실행 결과는 ignored `remaining-raw100-diagnostic/alpha-print-contract/`에만
보존하며 아직 제출 fixture나 완료된 회귀 검사로 분류하지 않는다.

제품 코드·편람 원본·기존 PDF·글꼴·측정 기준은 이 조사에서 바꾸지 않았다.
SO 분석 자료는 output에만 둔다. 전쪽 100%와 필수 테스트 후 PR 준비까지만 진행하며
사용자 지시 전 upstream 동기화·원격 GitHub 쓰기를 하지 않는다.

## 2026-10-27: 색·마스크를 분리한 장치 표본의 원인 분리

제품 source 259의 원본 두 문서 255쪽을 같은 글꼴 환경으로 다시 재생했다.
진단의 수정 전 PNG는 각각 현재 제품의 Native PNG와 **RGB 전픽셀이 같다**.
현재 paint frame도 기존 실제 관측과 일치함을 확인해 임의 이동을 하지 않았다.

원본에서 이미 계산한 JPEG RGB와 이진 alpha를 그대로 사용하되,
색 평면과 마스크 평면을 실제 동결 WASM의 공통 면적 표본으로 각각 처리한 뒤
같은 장치 픽셀 격자에서 결합했다. 이진 alpha가 들어 있는 PNG를 먼저 합쳐
일반 RGBA 필터로 그렸던 265→406픽셀 진단과 구분한다. 그림의 원본 bbox,
본문·소유·순서·clip은 유지하고 paint leaf의 작업 사각형만 공통 sampler가
반환한 정수 장치 영역으로 재생했다. PDF 바이트를 그림 자원으로 주입하지 않았다.

새 실제 Native 원인 분리 진단은 두 원본 모두 **265→0픽셀, raw 100%**다.
이는 색 평면과 마스크의 표본 순서가 남은 차이를 설명한다는 근거이며 아직
제품 수정이나 fresh WASM 문서 출력 통과로 분류하지 않는다. 공통 불투명 sampler를
alpha를 가진 입력에 몰래 적용하지 않고, 두 opaque 평면을 각각 처리했음을 구분한다.

256단계 alpha 색 대조군의 색 전달은 여전히 설명이 필요하다. 같은 색과 alpha를
예측하는 일반 계약을 확인하고, 이미 표본화한 투명 결과에 두 번째 필터를 적용하지
않도록 Native/Canvas의 실제 소비까지 연결한 후 제품을 보정한다. 원본 하나의
색 불변 조건으로 수용 범위를 임의로 좁히지 않는다.

자료는 `alpha-print-contract/separate-device-planes/`의
`input.json`, `device-result.json`, `replay-results.json`, `comparison.json`,
각 원본의 actual-paint-frame과 before/after PNG다. 제품 src·원본·기준 PDF·폰트·
Visual Sweep의 내용 mask/2px 반경은 변경하지 않았다.

## 색 전달의 실제 API 경계와 관측된 정수 계약

기존 Windows LockBits의 실제 premultiplied ARGB 바이트를 원래 합성 RGBA와
대조했다. `round(channel × alpha / 255)`가 전체 픽셀의 실제 premultiplied
채널과 정확히 같다. 256 분모 근사 등은 같지 않으며 이 차이를 눈대중으로 조절하지 않는다.

새 실험은 실제 premultiplied 픽셀을 별도 32비트 PArgb 표면에 복사하고 ARGB로
읽었다. Graphics의 물리 DPI 변환이 섞인 초기 실험은 원본의 alpha를 바꿨으므로
제외했다. 픽셀을 직접 복사한 정상 실험은 원본과 합성 대조군 모두 alpha의
모든 바이트를 보존했다. 실제 한 번의 API 왕복은 다음 정수 연산과 RGBA 전 바이트가 같다.

- premultiplied 채널 = `(channel × alpha + 127) / 255`의 정수 몫
- 복원 계수 = `(255 × 65536) / alpha`의 정수 몫
- 복원 채널 = `(premultiplied × 복원 계수) >> 16`, alpha 0은 채널 0

한 번 왕복한 색의 RGB555·동일 JPEG 품질/인코더 조합은 원본 255쪽 색 자원과는
전픽셀 같지만, 256단계 alpha 대조군에는 RGB 63,799픽셀 차이가 남는다.
관찰된 비멱등성을 확인하려고 **같은 실제 연산을 한 번 더 적용한 진단**은
원본과 합성 대조군 모두 독립 JPEG의 RGB가 **전픽셀 정확히 같다**.
기준 source RGB555/JPEG 결과 208,685픽셀 차이도 먼저 재현했다.

이는 독립 출력과 동등한 관측 연산이며, 한컴 내부에서 API를 실제로 두 번 호출한다는
주장은 아니다. 반복 횟수를 제품에 넣은 상태가 아니다. 바닥 행 방향을 바꾸는
다른 후보는 RGB 차이를 247,905픽셀로 늘려 기각했다. 아직 저장본·색 처리 생산
경계 또는 다른 크기·alpha/색 패턴의 새 독립 Print로 일반성을 확인해야 한다.
기존 PDF를 같은 입력으로 다시 출력하거나 이 두 결과만으로 제품 완료를 선언하지 않는다.

실험과 첫 alpha 변경 실패의 기록은 ignored `alpha-print-contract/`의
`native-pargb-roundtrip/`, `native-pargb-pixel-roundtrip/`,
`native-premultiply-precision-contract.json`에 있다. 최종 진단은
`comparison.json`, `idempotence-comparison.json`, `handbook-idempotence-comparison.json`이며
API 결과와 정수식의 전 바이트 동일성, alpha·색 기대값과 실제 오차를 구분한다.
255쪽의 제품 보정은 아직 적용하지 않았다.

## 다른 크기·색·알파의 독립 Print와 공통 구현 계획

2026-10-27에는 기존 768×401 대조군과 다른 514×258 RGBA를 생성했다.
색은 `(29x+43y+71, 17x+31y+123, 53x+7y+19) mod 256`, alpha는
`(11x+19y+97) mod 256`이며 256단계다. 기존 단일 그림 문단의 표시 크기와
변환은 유지하고 PNG·전체 원본 창·imgDim만 일관되게 바꿨다. 이전 대조군의
HWPX 내부 PNG와 실험용 PNG가 바이트까지 같다는 선행 확인도 남겼다.

새 독립 Print job `50da39e1-5643-48b6-9a59-967ae99c6213`은 한컴
13.0.0.3901, PrintMethod 0, 1쪽, 입력 전처리 없음이다. PDF SHA-256은
`96077701185e57bb45d1b8bebd1197b171cabc7330da5b1a3f16d7960c026d3d`다.
마스크는 132,612픽셀 모두 표준 Bayer 16×16 계약과 같다. 색은 앞 절의
관측 연산과 원본 표시 폭에서 정한 품질 66, **현재 제품 JPEG 인코더**로
예측하면 독립 JPEG의 RGB가 전픽셀 같다. 기준 연산은 114,215픽셀,
단일 PArgb 왕복은 92,101픽셀 차이다. 새 입력의 실제 Windows 메모리 실험도
alpha를 전 바이트 보존했다. 내부 한컴 호출 횟수를 입증한 결과로 확대하지 않는다.

초기 진단은 오래된 별도 JPEG 인코더가 아래 3행에서 1,501픽셀 차이를 냈다.
현재 제품에는 `c2e298304c`의 색차 평균 후 하단 패딩 보정이 이미 있다.
동일 RGB를 현재 제품 라이브러리로 인코딩해 차이 0을 확인했으므로, 이미 고친
인코더를 다시 수정하거나 색 변환에 끝단 보정을 넣지 않는다.

구현은 원본·논리 배치와 분리된 Print 색/마스크 자원을 공통 resolver에서 만든다.
HWP5 표 32·107의 BinData·그림 속성, 원본 PNG alpha, 독립 Print를 구분하며
파일 사양이 정의하지 않는 codec 전달은 위 실제 출력 계약으로 설명한다.
두 PArgb 정수 연산의 합성은 확인된 색 전달식으로 구현하고 반복 횟수 탐색이나
한컴 내부 호출 횟수 주장은 넣지 않는다. 팔레트가 원래 고색수 bitmap 전달을
선택하고 효과·부분 창·회전이 없는 경로에서 원본 RGB·alpha를 소비한다.

생산·소비 연결은 `paint builder의 실제 frame → 공통 resolver의 RGB/마스크
payload → 공통 장치 격자·분리 표본 → Native/Canvas의 장치 좌표 재생`이다.
두 backend는 수학을 각각 구현하지 않는다. PNG를 Skia/Canvas에서 먼저
premultiply해 투명 픽셀 아래 RGB를 잃거나, 결합된 RGBA를 두 번째로 필터링하지 않는다.
같은 장치 사각형에서 색과 마스크를 각각 표본화한 뒤 결합한다. 기존 불투명
면적 표본과 Screen·다른 출력 세대의 경로는 보존한다.

먼저 두 원본 255쪽과 독립 대조군의 실제 Native/fresh WASM 출력을 비교한다.
투명 아래 RGB 보존·색/마스크 분리·불투명 대조·클립 경계를 검사하고, 실패 시

## 공통 제품 후보의 실제 Native 결과

제품 구현 `b2b33fda6027c03cbcfaa051ee1f5968fbb7930d`의 실제 Native 빌드는
target/pr-review·jobs 8에서 정상 종료했다. 빌드 시간은 약 13분 20초이며
동결 실행 파일과 라이브러리의 SHA-256을 `alpha-mask-native/producer/receipt.json`에
보존했다. 두 원본 각 40쪽, 80조건을 실제 출력해 source 259의 동일 페이지와
대조했으며 미대응 증가가 없다. 양쪽 255쪽은 **265→0픽셀, raw 100%**다.
실제 제품 전후와 독립 Print의 같은 영역을 확대해 세로 줄무늬 제거와 도형·연결선·
문자 보존도 확인했다. 진단의 자원 교체 결과만으로 제품 통과를 주장하지 않았다.

같은 라이브러리에 연결한 정식 원본 검사에서 TAC 2, 셀 clip 4, 낱말 간격 2,
한자 3건이 통과했다. TAC의 같은 정식 파일은 수정 전 source 9bab에서 2 FAIL이다.
Studio 타입 검사의 새 코드 null 처리 오류는 `2379bd13c5`에서 보정했으며 재검사는
exit 0, Studio 전체 단위 검사는 2,454 PASS·0 FAIL·0 skipped다.

서로 다른 크기의 단일 그림 대조군은 **색·마스크 자원의 독립 근거**로만 사용한다.
그림 문단을 분리한 기존 wrapper는 Native와 한컴 사이에 위치 차이가 있어
정식 배치 fixture의 선행 gate를 충족하지 않았다. 그 wrapper의 낮은 페이지 점수를
제품 전체 문서의 회귀나 허용된 fixture로 분류하지 않으며 임의 좌표로 맞추지 않는다.
제품의 실제 배치·표본 검증은 원본 두 편람 255쪽을 동일한 기존 PDF와 대조한다.

현재 Native 전쪽 766조건, fresh DEV WASM 브라우저 83조건과 실제 Cargo의
색/분리 평면 단위 검사는 진행 중이다. 최종 표준 최적화 WASM 전쪽·전체 Rust와
필수 검증, 모든 1,532조건 100%·미대응 0과 PR 준비 완료는 아직 입증하지 않았다.
중간 결과와 로그는 `continuous-text-shadow/alpha-mask-native*`,
`alpha-mask-wasm-dev*`, `alpha-mask-unit-*`에 구분한다.
