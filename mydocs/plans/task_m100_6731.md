# #6731 CodeQL alert #186 근거화·재발 방지 수행계획

## 1. 목적과 기준선

- **이슈**: [#6731](https://github.com/edwardkim/rhwp/issues/6731)
- **브랜치**: `task_m100_6731`
- **기준선**: `upstream/devel@9bf5bcfd061b491c89be1ea28ef1fff8a892b6d1`
- **운영 분류**: O3 CodeQL 보안 계약과 Studio 암호 문서 로딩 경계
- **메인테이너 최종 분류**: `dismissed` / `used in tests`

CodeQL alert #186(`js/insufficient-password-hash`)은 제품의 암호 저장·검증이 아니라 테스트·계측용
폰트 규칙 snapshot JSON의 SHA-256 무결성 digest를 sink로 지적한다. 단순 dismiss에 머물지 않고
실제 암호 값이 이 경로에 들어가지 않는다는 보호 불변식을 고정하며, 실제 password hashing 탐지
범위를 축소하지 않는 구조적 경계를 마련한다.

이슈 제목과 초기 본문의 `false positive` 표현은 이후 메인테이너가 확정한 `used in tests` 판정과
불일치한다. historical PR review 문서는 당시 판정 기록으로 유지하되, 이슈 제목·본문과 이번 조사
증적·최종 보고서는 최종 분류를 정본으로 사용한다.

## 2. 확인된 원인 계보

1. 최초 alert 분석은 `devel@5057a7fcaf055b928e76115cdee4bc20bf0936f9`의 JavaScript/TypeScript
   분석 `1659063897`이다. 2026-08-24 00:04:25 KST, CodeQL 2.26.3에서 등록됐다.
2. 현재 `devel@d1831146587b1ac2346f9ed1216a64c2943a02f9` 분석 `1725324233`의 CodeQL
   2.26.4도 같은 네 개 flow와 각 60~64개 location을 재현한다.
3. CodeQL `SensitiveCall` 휴리스틱은 이름이 민감정보를 뜻하는 함수 호출의 반환값을 민감정보로
   간주한다. 이 때문에 `loadDocumentWithPassword()`가 반환한 `DocumentInfo` 전체가 암호 유래
   값으로 시작된다.
4. `DocumentInfo.fontsUsed`는 Studio의 문서 폰트 상태 분석과 `font-substitution.ts`의 module-global
   `_resolveCache`를 지난다. 정적 분석은 브라우저 Studio와 별도 Node 계측 프로세스를 구분하지 않아
   `font_rule_runtime_snapshot.mjs`의 `resolvedFace`로 이어 붙인다.
5. snapshot rows의 canonical JSON이 `font_rule_ledger.mjs:104`의 SHA-256으로 들어가면서 CWE-916
   sink가 된다. 실제 암호는 `DocumentInfo` 필드, 폰트 cache, snapshot row 어디에도 없다.

## 3. 보호 불변식

1. 사용자가 입력한 raw password는 암호 문서 open 시도 지역 범위를 벗어나 반환·보관·로그·최근 문서·
   자동저장·폰트 상태·snapshot 입력으로 전달되지 않는다.
2. 암호 문서 open은 상태를 변경하는 command이고, `DocumentInfo` 취득은 별도의 query다. command의
   반환값을 문서 metadata 운반자로 사용하지 않는다.
3. `DocumentInfo`의 허용 필드는 문서 구조·암호화 상태·폰트 metadata뿐이며 raw password나 credential
   필드를 추가하지 않는다.
4. 폰트 snapshot SHA-256은 재현성·무결성 식별자다. password KDF로 교체하거나 암호 저장·검증 API로
   재사용하지 않는다.
5. CodeQL query, JavaScript/TypeScript 분석 경로와 실제 password source 탐지는 약화하지 않는다.
6. 암호 보호 HWP3·HWP5·HWPX의 열기, 오입력 재시도, 취소, 저장 보호 lifecycle은 유지한다.

## 4. 대안 비교와 채택 기준

| 대안 | 장점 | 위험 | 판정 |
| --- | --- | --- | --- |
| SHA-256을 KDF로 교체 | 경고 문구만 피할 가능성 | 무결성 digest 목적 훼손·불필요한 비용 | 제외 |
| JS/Node 경로 또는 query 제외 | 즉시 경고 억제 | 실제 취약점과 scripts 보안 범위까지 은폐 | 제외 |
| 광범위한 custom barrier/sanitizer | 특정 flow 차단 가능 | 베타 모델 API·다른 query까지 과잉 차단 가능 | 기본 제외 |
| 브라우저/Node 분석 job 분리 | 실제 runtime 경계 반영 | workflow·required check·비용 영향이 큼 | 후순위 |
| password open command와 metadata query 분리 | 실제 API 의미와 CQRS 일치·query 설정 불변 | CodeQL이 내부 side effect까지 추적하는지 실증 필요 | **우선 채택** |

우선 구현이 exact CodeQL 분석에서 실패하면 임의의 이름 변경이나 sanitizer를 연속 투입하지 않는다.
새 SARIF와 기존 flow의 차이를 기록하고 runtime-scoped cache 또는 분석 job 분리의 영향도를 다시
계획하여 메인테이너 승인을 받는다.

## 5. 단계별 수행

### Stage 1 — SARIF 기준선 보존

- 최초 분석 `1659063897`과 현재 분석 `1725324233`에서 alert #186 결과를 추출한다.
- 네 flow의 모든 location, source·sink, CodeQL 버전, 대상 SHA, 재수집 명령을
  `mydocs/tech/investigations/issue-6731/`에 보존한다.
- GitHub의 aggregate check 귀속과 실제 source 도입 시점을 구분한다.

### Stage 2 — RED 보호 계약

- `hwp-password-open.test.ts`에 command/query 분리와 `DocumentInfo` 허용 필드 계약을 먼저 추가한다.
- 브라우저 E2E에서 HWP3·HWP5·HWPX를 연 뒤 반환 metadata·storage·DOM·로그로 raw password가
  유출되지 않음을 검사한다.
- Node snapshot이 암호 로딩 모듈을 직접 import하지 않고 승인된 폰트 projection만 hash한다는 계약을
  고정한다.

### Stage 3 — 최소 구현

- password open API는 성공·실패만 나타내는 `void` command로 바꾼다.
- 성공 뒤 별도 `getDocumentInfo()` query로 metadata를 취득한다.
- 영향받는 Studio 단위·E2E 호출부만 갱신한다. CodeQL workflow·query·paths와 SHA-256 구현은 바꾸지
  않는다.

### Stage 4 — 로컬·CodeQL 검증

- Studio unit test, TypeScript build, 암호 문서 E2E와 영향받는 content-loss save E2E를 수행한다.
- `git diff --check`와 변경 범위별 로컬 검증을 수행한다.
- PR exact head의 JavaScript/TypeScript CodeQL SARIF에서 alert #186 flow가 사라졌는지 확인한다.
- query/config가 그대로이고 raw `password` 변수의 민감 source 계약이 유지되는지 확인해 실제
  password hashing 탐지 범위가 축소되지 않았음을 증명한다.

### Stage 5 — 운영 문서·최종 보고·통합

- `mydocs/manual/github_operations.md`에 alert source 도입·분석 등록·PR 귀속을 분리하는 triage와
  `used in tests` 근거 보존 절차를 추가한다.
- `mydocs/report/task_m100_6731_report.md`에 결과와 잔여 위험을 기록한다.
- push 전 최신 `upstream/devel`을 병합하고 동일 파일을 건드리는 열린 PR과 충돌을 재점검한다.
- PR merge 뒤 `devel` full CodeQL에서 alert가 재발하지 않음을 확인한 다음 이슈를 닫는다.

## 6. 검증 범위와 병렬 변경 위험

- 열린 PR #6725는 `rhwp-studio/src/core/wasm-bridge.ts`, #6637은 `rhwp-studio/src/main.ts`를 변경한다.
  현재 patch는 각각 다른 hunk지만 장기 작업 중 merge될 수 있으므로 push 직전 최신 base merge와
  재검증이 필수다.
- 로컬에는 CodeQL CLI가 설치되어 있지 않다. 제품 tree에 임시 취약 fixture를 커밋하지 않으며,
  CodeQL 최종 판정은 GitHub exact-head SARIF와 merge 뒤 `devel` full scan으로 고정한다.
- query/config를 바꾸지 않는 것이 실제 경고 탐지 보존의 1차 증거다. 구조 변경 뒤에도 flow가 남으면
  Stage 3을 완료로 판정하지 않는다.
