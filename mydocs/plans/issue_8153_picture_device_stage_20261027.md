# #8153: 그림 자원의 재표본화와 최종 배치 분리

두 편람의 전쪽 Native·표준 최적화 fresh WASM 1,532조건을 raw 100%·정수 미대응 0으로
만든 뒤 필수 검증과 PR 준비까지만 완료한다. upstream 동기화와 원격 쓰기는 하지 않는다.
현재 구현 소스는 `36bae7c0edab15dd27dd769e5b4e1a422dd2a282`이며, 이후 커밋은 WMF
회귀와 검증 문서다. 이 단계는 남은 33조건 중 두 원본 144쪽의 원인을 분리한다.

## 사양과 원본 계약

HWP 5.0 설명본의 표 107은 원본 그림 사각형·crop·안쪽 여백을 구분한다. HWPX의 대응
`orgSz`·`curSz`·`imgDim`·`imgClip`과 저장 배율도 함께 읽었다. 두 원본·기존 독립 Print PDF는
변경하지 않는다. 144쪽의 두 JPEG는 실제 paint에 회전이 없고 crop은 전체 원본이다.

| 자원 | 원본 픽셀 | 저장 현재 크기 HU | 독립 Print 자원 픽셀 |
| --- | --- | --- | --- |
| image389 | 860×769 | 17480×8738 | 1214×607 |
| image390 | 937×771 | 17010×8695 | 1181×604 |

사양은 파일의 그림 속성을 규정하며 이 Print 재표본화의 커널·출력 픽셀 수를 정하지 않는다.
독립 Print 관측을 공식 HWP 사양 수치로 표기하거나, 관측된 픽셀 수를 제품 상수로 넣지 않는다.
이전 [해상도 경계 대조](issue_8153_picture_resolution_20261026.md)의 높이8738/11070/11080HU
반례도 계속 유지한다. 소수 DPI가500을 넘는지만으로 재표본화하는 조건은 기각된 상태다.

## 수정 전에 추적한 생산·소비 연결

1. 원본은 `image_resolver::print_tone`에서 디코딩·색 전달을 받고 `print_codec`이 압축한다.
   144쪽의 실제 두 자원은 모두 `OutputDevice` JPEG이며 원본 픽셀 크기를 유지한다.
2. `paint`의 최종 image op은 기존 그림 사각형과 전체 crop을 전달한다.
3. Skia의 `draw_image`는 `print_area_sampling`이 선택한 공통 장치 표본을 소비한다.
   현재 경로에서는 원본 크기의 JPEG를 바로 최종 장치에 줄인다.
4. 독립 Print에는 그보다 앞서 달라진 이미지 자원과 별도 이진 마스크가 있다.
   자원 생성 단계의 차이를 본문 위치·표 높이·그림 좌표 이동으로 보상하지 않는다.

현재 두 그림의 최종 paint 사각형은 각각
`[133.1360691145,722.9696423552,232.8682505400,116.4686655531]`와
`[392.6954643629,723.2896112166,226.6349892009,115.9887122610]`다.
진단은 이 사각형과 부모 clip·원본 소유를 그대로 유지했다.

## 독립 재표본화 자원으로 원인 분리

기존에 확인한 공개 Windows GDI+ `HighQualityBicubic`·`PixelOffsetMode.Default`를
두 원본 JPEG에 메모리로 적용했다. 원격의 실제 JPEG SHA를 확인했으며 그림·글꼴 파일을
배포하지 않았다. 원본과 별도로 생성한 자원에는 기존 RGB555·이진 alpha·JPEG 전달을 적용했다.
관측한 독립 자원 크기는 커널을 분리하는 이 진단에서만 사용했다.

생성한 두 마스크는 독립 Print의 opacity 평면과 각각 전 픽셀이 같았다. Pixmap이 반환하는
opacity를 다시 반전하지 않았다. 색 RGB는 JPEG 픽셀 단위로 완전히 같지 않으므로 색 자원
완전 복원이라고 설명하지 않는다. 기존 96dpi·임계값232·반경2px로 실제 페이지 전체를 비교했다.

| 원본 | 진단 조건 | raw | 정수 미대응 픽셀 |
| --- | --- | ---: | ---: |
| HWP·HWPX 각각 | 현재 제품과 RGB 전체가 같은 identity | 99.67578% | 241 |
| HWP·HWPX 각각 | 원본 생성 image389만 교체 | 99.70892% | 216 |
| HWP·HWPX 각각 | 원본 생성 image390만 교체 | 99.96623% | 25 |
| HWP·HWPX 각각 | 원본 생성 두 자원 교체 | 100% | 0 |
| HWP·HWPX 각각 | 독립 PDF의 두 자원 교체, 원인 분리용 | 100% | 0 |

원본 생성 조건은 PDF 픽셀을 재생 입력으로 사용하지 않았다. 별도의 oracle 조건과 이름·
manifest를 구분했다. 두 원본의 identity가 현재 Native PNG와 RGB 전체가 같은 것도 확인했다.
따라서 이 범위의 241픽셀은 본문 조판을 움직이지 않고 그림의 생산·소비 연결로 해결할 수 있다.
이 사실은 아직 제품 구현·fresh WASM 완료 증거가 아니다.

같은 영역의 현재·원본 생성 자원·독립 Print 확대 PNG를 직접 읽었다. 아래쪽 가는 수평선의
잘못 남은 픽셀과 위쪽 선의 누락이 자원 교체 후 사라지고, 본문·두 그림의 순서와 외곽은 유지된다.
전체 페이지 review·overlay도 함께 생성했다.

## 공통 구현 전에 남은 입증

1. 최종 이미지 자원의 크기를 결정하는 일반 규칙을 확인한다. 저장된 크기·단위에서 계산하며,
   독립 PDF의 픽셀 수를 읽거나 문서·자원 ID별 수치를 제품에 넣지 않는다.
   관측 크기와 일치하는 정수 장치 크기 계산은 아직 후보이며 독립 경계·반례로 확인한다.
2. 공개 재표본화의 기하·필터·투명 경계 처리를 공통 Rust에서 설명한다. 원본 문서에 맞춰
   필터 계수를 탐색하거나, 임계값·alpha를 바꾸어 실루엣 차이를 숨기지 않는다.
   문서와 독립인32×32 상수장·가로/세로 선 자극을 서로 다른 확대·축소 축으로 실행한
   12조건을 `public-kernel-observed.json`에 보존했다. 일반 cubic의 표본 중심·경계 계약과
   대조하며 설명되지 않은 커널을 제품의 확정 규칙으로 채택하지 않는다.
3. 같은 producer 결과를 Native·Canvas2D·CanvasKit이 소비하게 한다. RGB와 마스크의 분리,
   RGB555·JPEG 순서와 최종 장치 표본까지 연결한다. API별로 같은 규칙을 따로 만들지 않는다.
4. 두 원본의 실제 영향 쪽·기존 정상 그림·해상도 경계 대조군을 먼저 실행하고, Native·표준
   최적화 fresh WASM 전쪽을 비교한다. 144쪽 진단의100%를 제품 수로 합산하지 않는다.
5. 실제 두 backend에서 페이지 조건과 직접 판독을 확인한 뒤 `tests/cases/issue_8153_*`에
   원본 속성·마스크·소유·포함·독립 ±2px 경계를 보호한다. 원래 전쪽1,532조건의100%와
   중요 위치 회귀·전체 검증·PR 준비 완료 조건은 유지한다.

현재 제품의 Native 전쪽 완료 수는 여전히733/766이며, 정수 미대응 합계는724개다.
현재 표준 최적화 WASM 전쪽과 최종 전체 검증은 미완료다. upstream을 동기화하지 않는다.
