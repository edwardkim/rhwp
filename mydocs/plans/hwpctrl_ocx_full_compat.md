## 0. 결론 먼저

1. **기존 `rhwp-studio/src/hwpctl/` 은 신규 층이 완성될 때까지 손대지 않는다.** 그 층은
   "studio 자동화 표면"이라는 **다른 계약**을 갖는다(예: `Undo` 를 정책상 미지원으로 판정 —
   `actions/clipboard.ts:60`). 100% 호환 층은 **별도 패키지**로 새로 세운다.
   **보존은 목적이 아니라 순서다** — 신규 층이 원장 100% 에 도달하면 P7 에서 **기존 층을 철거하고
   studio 를 신규 층으로 이관**한다(§6.2).
2. **먼저 짓는 것은 API 가 아니라 오라클이다.** 312개 액션·50종 ParameterSet 의 정확한 동작은
   문서가 아니라 **설치된 OCX 만** 안다. Phase 0 은 코드 변경 0 으로, 차등 테스트 하니스와
   기계 판독 가능한 **API 원장**을 만든다.
3. **"100%" 는 정의해야 측정된다.** §1 에서 4계층 계약으로 쪼개고, 물리적으로 불가능한 축
   (로컬 파일시스템 경로, 인쇄 드라이버, 프로세스/윈도우 객체)은 **명시적 대체 계약**으로 고정한다.
   여기를 흐리면 "100%" 가 영원히 판정 불가가 된다.
4. **진척은 원장 숫자로만 보고한다.** `api_ledger.json` 이 유일한 진실이고, 각 항목의 상태는
   사람 판단이 아니라 **오라클 대조 결과**가 채운다.

## 1. "100% 호환"의 정의 — 4계층 계약

| 계층 | 무엇을 맞추나 | 판정 방법 |
|---|---|---|
| **L1 표면** | 객체·메서드·속성의 **존재**, 인자 개수, 반환 타입 | OCX 타입 라이브러리 열거 ↔ 구현 열거 diff |
| **L2 반환값** | 같은 입력에 대한 **반환값** (Boolean/Integer/String/ParameterSet 아이템) | 시나리오 실행 로그 JSON diff |
| **L3 문서 상태** | 호출 뒤 **문서가 같아지는가** | 양쪽 저장본을 rhwp 로 파싱해 IR/레코드 대조 |
| **L4 시각** | 저장본을 조판했을 때 **같이 보이는가** | 한글 PDF ↔ rhwp `export-png` 픽셀 대조 |

**합격선**: L1·L2 는 전 항목 0 diff. L3 는 대상 API 가 건드리는 레코드에 한해 0 diff.
L4 는 기존 시각 게이트 기준선(`visual-sweep-oracle`, 정상 ~92-93%) 이하로 떨어지지 않을 것.

### 1.1 물리적으로 대체 불가한 축 — 명시적 계약

브라우저에는 없는 것들이다. **"미지원"이 아니라 "대체 계약"으로 문서화**하고, 원장에
`substituted` 상태로 기록한다.

> **갱신(P0)**: 아래 표의 대부분은 우리가 정할 일이 아니었다. 웹한글컨트롤 규격 v2.4 §2.2 가
> 이미 정해 놓았다(§4.4). 규격과 어긋나는 자체 계약을 만들지 말 것 — 규격이 먼저다.

| OCX 동작 | 브라우저 대체 계약 |
|---|---|
| `Open("C:\...\a.hwp")` 로컬 경로 | 경로 문자열을 **가상 FS 키/URL** 로 해석. 호스트가 등록한 리졸버 경유 |
| `SaveAs(path)` 로컬 저장 | 다운로드 트리거 또는 호스트 콜백(`onSave(bytes, path)`) |
| `PrintDocument` 프린터 드라이버 | PDF 생성 후 브라우저 인쇄 대화상자 (`rhwp-studio/src/ui/pdf-print-dialog.ts` 재사용) |
| `ShowToolBar`/`ShowRibbon` 등 UI 7종 | **no-op + `true` 반환** (OCX 도 반환값을 안 쓰는 호출) |
| `XHwpWindows`/프로세스 객체 | 단일 문서 인스턴스로 고정, 열거 시 1개짜리 컬렉션 |
| `RegisterModule`(보안 모듈) | no-op — 브라우저에는 파일 접근 승인 다이얼로그가 없다 |

이 표에 없는 API 가 "브라우저라 못 한다"는 이유로 미구현되면 **계획 위반**이다.

## 2. 현재 지점 (2026-08-07 실측)

정답지는 `mydocs/plans/archives/task_43_feature_def.md` §2 (Properties 18 / Methods 67 /
Action 312 / ParameterSet 50). 같은 문서 §3 의 매핑표는 낡았으므로 **현재 코드로 다시 셌다**.

| 축 | OCX 총수 | 기존 hwpctl 이름 호환 | 비고 |
|---|---|---|---|
| Properties | 18 | 1 (`PageCount()`) | 메서드 형태라 L1 부적합 |
| Methods | 67 | 17 (실동작 14) | `SetCurFieldName`·`RenameField` 는 stub (`index.ts:388,394`) |
| Actions | 312 | 30 등록 / 28 실행 | `Undo`/`Redo` 정책 미지원 |
| ParameterSet | 50종 | 0종 (범용 key-value 1개) | `parameter-set.ts` 73줄 |

**있는 자산**: rhwp WASM 366 함수(`src/wasm_api.rs`), studio 명령 156개(12 stub).
표·서식·검색치환·필드·페이지·머리말꼬리말은 **기능 등가가 이미 있다** — 새로 만들 것은
대부분 "능력"이 아니라 **OCX 모양의 배선**이다.

**등가물이 아예 없는 축** (신규 구현 필요): 맞춤법 검사, 음/양력 변환 4종, 하이퍼링크 삽입·수정,
개체 정렬 11종·캡션 부착, 쪽 배경 그림, 명령 잠금 3종, 스캔 커서(`InitScan`/`GetText`/`ReleaseScan`),
이벤트 발화.

## 3. 아키텍처 — 기존 보존 + 코어 공유

```
  기존 (건드리지 않음)                    신규
  ─────────────────────                  ──────────────────────────────
  rhwp-studio/src/hwpctl/                npm/hwpctrl-ocx/            ← 신규 패키지
    index.ts  (HwpCtrl, studio 계약)       src/hwpctrl.ts   (window.HwpCtrl, 67 methods/18 props)
    action.ts / action-registry.ts         src/actions/**   (312 action)
    actions/**  (30 action)                src/sets/**      (50 ParameterSet 스키마)
    parameter-set.ts                       src/objects/**   (Action/CtrlCode/ParameterSet/ParameterArray)
           │                                        │
           └──────────────┬─────────────────────────┘
                          ▼
              rhwp-studio/src/hwpctl-core/   ← 신규 공용 코어 (문서 상태기)
                cursor.ts · selection.ts · fields.ts · ctrl-walk.ts
                          ▼
                    WASM  HwpDocument  (src/wasm_api.rs)
```

**규칙**

1. 기존 `hwpctl/` 파일은 P0~P6 동안 **읽기 전용**으로 취급한다. 기존
   e2e(`rhwp-studio/e2e/hwpctl-basic.test.mjs`)는 그 기간 내내 녹색이어야 한다.
   **최종 상태는 단일 층이다** — P7 에서 기존 층은 삭제되고 studio 는 신규 층만 쓴다.
   따라서 신규 층은 처음부터 **studio 가 실제로 쓰는 호출**(§6.2 표)을 지원 범위에 포함시켜
   설계한다. 나중에 얹는 것이 아니다.
2. 신규 층은 `window.HwpCtrl` 전역을 심어 **기존 통합 스크립트를 무수정 실행**한다.
3. OCX 는 **동기** API 다. 신규 층도 동기로 만든다 — WASM 호출이 이미 동기다
   (`rhwp-studio/src/core/wasm-bridge.ts`). 비동기가 불가피한 축(URL 로딩)만 OCX 원래의
   `callback` 인자를 쓴다.
4. **코어에 없는 능력은 WASM 에 추가**한다(예: 하이퍼링크 삽입). 호환 층 안에서 임시 구현하지 않는다 —
   그러면 studio 와 동작이 갈라진다.

## 4. 오라클 하니스 — 이 계획의 심장

### 4.1 구조

```
scenario/*.json   ← 호출 시퀀스 (선언형 DSL)
      │
      ├── runner_ocx.py     설치된 한글 OCX (pyhwpx, 프로세스 격리)
      │       → returns.json · out.hwp · oracle.pdf
      │
      └── runner_rhwp.mjs   node + rhwp WASM (신규 호환 층)
              → returns.json · out.hwp · out/*.png
      ▼
compare.py  → L2 반환값 diff · L3 IR/레코드 diff · L4 픽셀 diff → verdict.tsv
```

시나리오 DSL 예 (한 파일 = 한 판정 단위):

```json
{ "id": "field-put-basic",
  "open": "samples/gian/기안문.hwp",
  "calls": [
    ["MoveToField", ["기안자", false, true, false]],
    ["PutFieldText", ["기안자", "홍길동"]],
    ["GetFieldText", ["기안자"]],
    ["GetPos", []]
  ],
  "saveAs": "out.hwp" }
```

### 4.2 재사용할 자산

- `tools/hwp_open_bisect/hangul_com.py` — 프로세스 격리 규약(문서당 프로세스 1개, 인스턴스
  재생성 금지)이 이미 문서화돼 있다. runner 의 뼈대로 쓴다.
- `tools/hangul_pdf_baseline.py`, 시각 스윕 자산 — L4 판정에 그대로 쓴다.

### 4.3 함정 목록 (하니스가 **먼저** 방어할 것)

과거 캠페인에서 실제로 오판을 만든 것들이다. 하니스 v1 에 전부 넣는다.

1. **COM hang** — stall-watchdog 필수. 시작 시 기존 한글 프로세스가 있으면 종료하지 않고
   `OCCUPIED`로 중단한다. `com.Quit()` 뒤 자연 종료를 최대 10초 기다린 뒤에도 남은 PID만
   `LEFTOVER`로 보고하고 자동 종료하지 않는다. 전용 Windows 계정에서만 `--cleanup-spawned`를
   명시해 새 PID를 정리할 수 있다.
2. **동시 실행 금지** — COM 판정은 직렬. 병렬은 서로의 인스턴스를 죽인다.
2.1. **반복은 `--skip-ocx` 로** (실측 **12초 대 13분**, 50시나리오). 게이트 시간의 거의 전부는
   한글 기동이다 — 시나리오마다 새 `Hwp.exe` 를 띄우고 그 13초 중 호출은 1초도 안 된다.
   그런데 오라클 답은 **(시나리오, 한글 버전, 표본)** 에만 달렸으므로 rhwp 쪽만 고쳤으면
   저장된 정답지가 그대로 유효하다. 라이브 전량 실행은 **시나리오나 표본이 바뀔 때만**.
   상함은 `--skip-ocx` 가 버전으로 검사한다(`STALE_ORACLE`).
   곁들여: JS 만 고쳤으면 **wasm 을 다시 안 만들어도 된다**(15~40초 절약).
3. **보안 다이얼로그** — `FilePathCheckerModule.dll` 을 `HKCU\Software\HNC\HwpAutomation\Modules`
   에 등록(`hwp_com_automation` 메모).
4. **버전 고정** — 한글2022. 2024 는 조판은 같아도 계측이 불안정하다.
5. **정착(settle)** — 조판 전 `PageCount`/좌표를 읽으면 비결정 값이 나온다. 읽기 전 정착 게이트.
6. **PDF producer 확인** — `producer=Hancom PDF` 만 정답지.
7. **바이너리·산출물 신선도** — 왕복본·PNG·덤프까지 재생성. stale 산출물이 닫힌 결함을 다시 연다.

### 4.4 스펙 추출 — 추측이 아니라 공식 문서에서

착수하며 확인한 사실: **한컴 공식 규격서 3종이 이미 저장소에 있다.**

| 문서 | 내용 |
|---|---|
| `samples/hwpctl_API_v2.4.hwp` | 웹한글컨트롤 API v2.4 — 이 계획의 **대상 규격 그 자체** |
| `samples/hwpctl_Action_Table__v1.1.hwp` | Action 312개 + 각자의 ParameterSet ID |
| `samples/hwpctl_ParameterSetID_Item_v1.2.hwp` | ParameterSet 50종 / Item 521개 |

따라서 §4.4 의 원안(왕복 판별로 Item 을 추정한다)은 **불필요해졌다**. `extract_spec.py` 가
rhwp CLI 로 세 문서를 읽어 기계 판독 스펙을 만든다. 왕복 판별은 문서가 모호한 항목
(서명과 `Parameters N` 이 어긋나는 18건)에만 쓴다.

> **대상 규격이 ActiveX 가 아니라 웹한글컨트롤이다.** v2.4 §2.2 가 이미 브라우저 제약에 대한
> 답을 정해 놓았다 — `Open`/`GetTextFile` 은 콜백, `SaveAs`/`CreatePageImage` 는 다운로드,
> `InsertPicture` 는 업로드된 File, 이벤트는 `addEventListener`. §1.1 의 대체 계약표는
> **우리가 정하는 것이 아니라 규격이 정한 것**으로 바뀐다. 그만큼 "100%"의 판정이 쉬워졌다.

### 4.5 P0 실행 결과 (2026-08-07)

만든 것 — `tools/hwpctrl_compat/` (`README.md` 가 사용법):

| 파일 | 역할 |
|---|---|
| `extract_spec.py` | 공식 문서 3종 → `spec/*.json`. 개수가 문서 약속과 다르면 **실패한다** |
| `build_ledger.py` | 스펙 → 원장 484항목. `--check` = CI 게이트, `--ingest` = 판정 반영 |
| `runner_ocx.py` | 설치된 한글 COM 에 시나리오 실행 → 정답지 |
| `runner_rhwp.mjs` | 같은 시나리오를 rhwp WASM 위에서 실행 (`--impl legacy` = 자체 검증) |
| `compare.py` | L2 반환값 + L3 문서 상태 대조 → `verdict.tsv`/`verdict.json` |
| `run_gate.py` | 직렬 오케스트레이터 — 시간 제한·안전한 잔류 PID 보고·정답지 버전 재검증 |

**P0 완료 판정("기존 층을 돌려 알려진 diff 를 재현")을 충족했다.** 한글2022 정답지 기준
시나리오 3건 28호출 중 12 일치, 16 불일치가 잡혔고 그 내역이 전부 설명된다.

| 잡힌 것 | 내용 |
|---|---|
| `MISSING_API` 9 | `IsEmpty`·`IsModified`·`Version`·`EditMode`·`SelectionMode`·`FieldExist`·`GetCurFieldName` 등 |
| `VALUE_DIFF` — 반환 규약 | `PutFieldText` 는 규격상 void(오라클 `null`)인데 기존 층은 `true` |
| `VALUE_DIFF` — 자료 형태 | `GetFieldList` 는 규격상 `0x02` 구분 **문자열**, 기존 층은 객체 배열 |
| `VALUE_DIFF` — 커서 모델 | `GetPos().list` 는 OCX 가 서브리스트 id(292·8)를 주는데 rhwp 는 늘 0 |
| **L3 문서 결함** | `PutFieldText` 가 **인접 필드를 오염**시킨다(§4.6) |

#### 4.5.1 오라클 버전 — **한글2022 로 고정 완료** (2026-08-07)

작업지시자가 관리자 권한으로 `Hwp.exe /regserver`(Office 2022)를 실행해 전환했다. 이후
`gen_py` 캐시를 지우고 정답지를 **전량 재수집**했다 — 현재 `output/poc/hwpctrl/ocx/` 는 전부
`12, 0, 0, 4547` 산이다. 게이트 기본값이 `--expect-version 12` 이므로 `12, 0, 0, 4547`과
`12.0.0.4547`을 같은 2022 오라클로 판정하고, 다른 major로는 **시나리오가 실행되지 않는다**.
재실행은 이전 `returns.json`과 저장본을 먼저 제거한 뒤 `<id>.rejected.json`만 남겨 stale 정답지가
비교에 섞이지 않게 한다. `--skip-ocx`도 저장된 oracle version을 다시 검사한다.

**2022 와 2024 의 답은 같았다.** 격리해 둔 2024 산출물과 대조한 결과 28호출 중 다른 것은
`Version` 값 하나뿐이다(`12, 0, 0, 4547` ↔ `13, 0, 0, 564`). 즉 **API 축은 두 버전에 둔감**하다
— 계획서가 2022 로 고정하는 이유는 정확성이 아니라 **저장소의 다른 오라클(10k 레이아웃
캠페인)과 재현 조건을 맞추기 위해서**다. 레이아웃 축은 여전히 버전에 민감하다.

아래는 전환 과정 기록이다(같은 상황이 재발할 때를 위해 남긴다).

#### 4.5.1.1 전환이 왜 레지스트리만으로 안 됐나

이 머신에는 한글2022(`Office 2022/HOffice120`, 12.0.0.4547)와 2024(`HOffice130`)가 함께 있다.
`HWPFrame.HwpObject` 의 CLSID·ProgID·TypeLib GUID 는 **두 버전이 공유**하고, 등록은 2024 가
전부 가져갔다(2022 를 가리키는 CLSID 는 레지스트리에 하나도 없다).

`HKCU\Software\Classes` 에 CLSID·TypeLib 을 우선 등록하면(관리자 불필요) 레지스트리는 바뀐다
— `HKCR…\LocalServer32` 가 2022 exe 를 가리킨다. **그런데 실제 기동 프로세스는 여전히
`HOffice130\Bin\Hwp.exe`(13,0,0,564)였다.** 2022 바이너리가 2024 로 넘겨준다. 버전 중재는 CLSID
등록이 아니라 한컴 내부(공유 설치 정보)에서 일어난다.

따라서 전환 경로는 **관리자 권한 `/regserver`** 뿐이다. CLSID 뿐 아니라 공유 설치 정보까지
갱신한다.

```powershell
# 관리자 PowerShell
& 'C:\Program Files (x86)\Hnc\Office 2022\HOffice120\Bin\Hwp.exe' /regserver
# 되돌리기
& 'C:\Program Files (x86)\Hnc\Office 2024\HOffice130\Bin\Hwp.exe' /regserver
```

전환한 뒤 반드시 두 가지를 한다(이번에 실제로 했다).

1. `%LOCALAPPDATA%\Temp\gen_py\3.12` 삭제 — `win32com` 이 옛 타입라이브러리로 만든
   조기 바인딩 래퍼가 남아 있으면 서버만 바뀌고 인터페이스는 옛것을 쓴다.
2. **정답지를 다시 만든다.** 이전 버전으로 모은 산출물은 폐기한다
   (`output/poc/hwpctrl/ocx-2024-quarantine/` 에 격리해 두었다 — 비교용이며 정답지가 아니다).

#### 4.5.2 시나리오 설계 규칙 — 반환값만 보면 통과한다

첫 판정에서 `MovePos` 가 `verified` 로 올라갔다. `true` 만 돌려주고 **커서를 옮기지 않아도**
반환값 대조를 통과했기 때문이다. 뒤따르는 `GetPos` 가 그것을 잡았다. 그래서 원장 반영을
**시나리오 단위**로 바꿨다 — 시나리오가 통째로 통과해야 그 시나리오가 선언한 항목이 올라간다.
시나리오는 **바꾼 뒤 반드시 읽어야** 한다.

### 4.6 P0 이 찾아낸 결함 — `PutFieldText` 필드 오염

`samples/issue-986-receipt.hwp` 에서 `PutFieldText("med_str_dt", "2026-08-07")` 한 번 호출 후
저장본을 대조한 결과다.

|---|---|---|
| `med_str_dt` | `2026-08-07` | `2026-08-07부터 ` |

같은 셀에 있는 **인접 필드까지 값이 번지고**, 기존 텍스트가 지워지지 않는다. 규격 §8.3.34 는

**절반은 좁혀 놓았다(P1 조사, 2026-08-07).**

| 관측 | 결론 |
|---|---|
| 하니스 rhwp 측 `GetFieldText` 가 쓰기 직후 `"2026-08-07"` 를 정확히 돌려준다 | **메모리 상태는 옳다** — 쓰기 경로 무혐의 |
| CLI `edit fill-fields` 로 저장한 뒤 다시 읽으면 오염 | 저장·재적재 경계의 문제 |
| HWP5 저장본과 HWPX 저장본에서 **동일하게** 재현 | 특정 직렬화기 결함이 아니다 — 공통 경로(필드 범위 ↔ 컨트롤 짝짓기) |
| 두 필드는 **같은 셀·같은 문단**(cell 7, para 0)에 있고 원래 둘 다 빈 값 | 빈 필드 두 개가 한 문단에 있을 때 재적재가 범위를 잘못 짝지음 |
| 재적재된 `med_str_dt` 값이 뒤 필드의 **안내문("진료 종료일")까지 삼킨다** | 범위 경계가 다음 필드 시작을 넘어간다 |

`Paragraph::insert_text_at`/`delete_text_at` 는 `field_ranges` 를 이미 시프트한다
(`src/model/paragraph.rs` §5-1) — 그래서 메모리가 맞는다.

#### 4.6.1 근인 — `rebuild_char_offsets` 가 필드 시작 위치를 **추정**한다

`src/document_core/queries/field_query.rs:1429`:

```rust
let ctrls_before_text = if !para.char_offsets.is_empty() {
    para.char_offsets[0] as usize / 8      // ← 첫 갭 크기로 "앞선 컨트롤 수"를 추정
} else { para.controls.len() }.min(para.controls.len());

for fr in &para.field_ranges {
    if fr.control_idx >= ctrls_before_text {   // ← 이 조건이 거짓이면
        field_begin_at[fr.start_char_idx.min(text_len)] += 1;   // 시작 위치 갭을 안 만든다
    }
}
```

문제의 셀은 텍스트가 `'부터 까지'` 이고 **빈 필드 두 개**가 그 안에 있다. 첫 갭이 커서
`ctrls_before_text` 가 2 로 추정되고, 두 필드의 `control_idx` 는 0·1 이라 **둘 다 조건에서
탈락**한다. 그러면 두 FIELD_BEGIN 이 모두 "텍스트 앞 선행 컨트롤"로 취급돼 **위치 0 에 붙어**
저장된다.

파서는 스택(LIFO)으로 짝짓는다(`src/parser/body_text.rs:328`). 위치 0 에 BEGIN 두 개가 붙은
스트림을 되읽으면:

```
BEGIN(a) BEGIN(b) … END@10 → b 에 [0,10)   … END@13 → a 에 [0,13)
```

즉 `med_end_dt`(b) = `'2026-08-07'`, `med_str_dt`(a) = `'2026-08-07부터 '` — **관측값과 정확히
일치한다.** 텍스트 자체는 온전하다(`export-tables` 로 `'2026-08-07부터 까지'` 확인).

#### 4.6.2 수정 시도 2회 — **둘 다 게이트가 되돌렸다** (2026-08-07)

| 시도 | 내용 | 결과 |
|---|---|---|
| ① `rebuild_char_offsets` 교정 | FIELD_BEGIN 을 `start_char_idx` 에 놓고, 선행 갭 상한을 **필드가 아닌** 컨트롤 수로 | 재현 케이스 해결. 그러나 `issue_2007_saved_frame_tail_nested_table…` **회귀** |
| ②  ① 을 좁힘 | 시작이 0 인 필드는 선행 갭에 유지, 중간 시작 필드만 자기 자리에 + 예산 차감 | 재현 케이스 해결. 그러나 같은 파일의 **다른** 테스트(`…intra_paragraph_saved_frame_break…`) 회귀 |
| ③ 직렬화기 차단 | 갭 채우기 루프가 필드 시작 전에 FIELD_BEGIN 을 방출하지 못하게 | 재현 케이스 해결 + `issue_2007` 4건 **전부 통과**. 그러나 **필드 소실**(165→164) |

**①·② 가 조판을 흔든 이유**: 적재 시 `clear_initial_field_texts` 가 필드 쓰기 경로를 타고
`rebuild_char_offsets` 를 부른다. 즉 이 함수는 저장 전용이 아니라 **적재 정규화 경로**이며,
`char_offsets` 는 `char_shapes`/`line_segs` 와 같은 좌표계를 공유하므로 값을 바꾸면 줄바꿈이
움직인다. "조판과 무관한 수정"이라는 초기 판단은 **틀렸다.**

**③ 이 필드를 잃은 이유**: 방출을 막기만 하면 그 FIELD_BEGIN 이 갈 자리를 못 찾는다. 갭
예산은 텍스트 편집 뒤 실제 구조보다 크게 남아 있고, 뒤쪽 위치에는 여유가 없다.

#### 4.6.3 다음 시도의 설계 (미착수)

③ 에 **강제 방출**을 더해야 한다. 위치 `i` 에서 방출 순서를 명시적으로 정한다.

1. `end == i` 이고 **BEGIN 이 이미 나간**(`start < i`) 필드의 FIELD_END
2. `start == i` 인 필드의 FIELD_BEGIN — 갭 예산과 무관하게 **강제 방출**
3. `start == i && end == i` 인 빈 필드의 FIELD_END

파서가 스택(LIFO)으로 짝지으므로 이 순서를 어기면 범위가 뒤엉킨다(1 과 2 의 순서가 특히
중요하다 — 한 필드가 끝나는 자리에서 다음 필드가 시작하는 경우). 현재 `field_ends` 는
인덱스별 마커 목록이라 범위와 연결돼 있지 않으므로, **`field_ranges` 를 직접 훑는 구조로
바꿔야 한다.**

검증 게이트(3중): `cargo nextest --no-fail-fast`(편집 계약) + `ir_field_sweep`(필드 IR 스윕)
+ 본 하니스 `field-put-save` L3 MATCH. 추가로 **필드 개수 보존**(165→165)을 회귀 검사에 넣는다
— ③ 의 소실을 잡은 것이 바로 이 확인이었다.

갈래를 한 계약으로 덮었다. 시나리오 `p1-field-rename` L2 15/15 · L3 MATCH → 원장 `verified`.

시나리오는 축별로 갈랐다. `p1-field-write` 가 이름 변경과 커서 위치 생성을 함께 들고 있어
`MovePos` 부재가 이미 증명된 이름 변경까지 막고 있었다(§4.5.2 규칙).

### 4.8 `GetFieldList` — 순회 순서와 option (2026-08-08)

이름 **집합**은 165개로 처음부터 같았다. 어긋난 것은 **순서**다.

#### 순서 — 컨테이너 단위로 셀 먼저, 누름틀 나중

OCX 목록을 rhwp 문서 순서에서 재구성해 규칙을 확정했다(165개 전수 일치).

```
컨테이너(표)가 처음 나온 순서대로 돌되,
  컨테이너 하나 안에서는  셀 구역 이름 전부(문서 순서) → 누름틀 전부(문서 순서)
```

이 서식에서는 `[셀 148] [누름틀 14] [셀 3]` 이 나온다. "셀을 먼저 다 낸다"가 아니라
**표 t2 의 셀 148 → t2 의 누름틀 12 → t3 의 누름틀 2 → t4 의 셀 2 → t6 의 셀 1** 이다.
rhwp 는 셀을 훑으며 둘을 섞어 내므로 그대로 쓰면 어긋난다.

이 순서는 **호환 층 안에만** 둔다(`ocxFieldOrder`). `collect_all_fields()` 의 문서 순서는
CLI `fields --json` 순번과 `set_field_value_by_name_at` 의 occurrence 계약이 딛고 서 있다.

셀 필드와 누름틀을 가르는 판별자가 없어서 코어가 `getFieldList` JSON 에 `cellField` 를 싣게
했다. `fieldType` 은 둘 다 `ClickHere` 라 못 가른다 — 셀 필드는 `ctrl_id == 0` 인 가상 필드다.

#### option — 낼 종류를 고르는 비트

| option | 오라클 | 뜻 |
|---|---|---|
| 0 | 165 | 전부 |
| 1 | 151 | 셀 필드만 |
| 2 | 14 | 누름틀만 |
| 3 | 165 | 둘 다 = 전부 |
| 4 | 0 | **빈 목록** |

비트 하나가 종류 하나를 켠다(0 은 전부라는 뜻의 특례). 이전 구현은 `option===2` 를
"안내문 있는 필드"로 근사했는데, 이 서식에서 우연히 같은 14개였을 뿐이다.

`number` 는 0/1 만 쓴다. **2 를 주면 오라클이 죽는다**(`com_error`, RPC 실패) — 시나리오에
넣지 말 것. 순번 `{{n}}` 은 돌려주는 목록 안에서 센다.

### 4.9 커서 좌표 — 리스트 아이디 체계 (2026-08-08)

규격은 `list` 를 "문서 내 리스트 아이디"라고만 적는다(§8.3.12). 번호 규칙은 실측으로 캤다.

#### 번호 매김

```
0        본문(루트 리스트)
1        문서마다 하나 비어 있다 — 무엇인지 미규명(바탕쪽으로 짐작만)
2 이상   서브리스트를 문서 순서 깊이 우선으로: 표 셀 · 글상자
         (셀에 번호를 준 **뒤** 그 셀 안으로 내려간다)
```

세 문서에서 재구성이 전수 일치했다.

| 문서 | 확인한 것 |
|---|---|
| `issue-986-receipt` (표 7개, 중첩 없음) | 셀 265+18+11+2+14+12+1 이 2..324 로 이어짐 |
| `issue2007_nested…42065` (3중 중첩) | 부모 셀 28 → 자식 표 11칸 → 부모 셀 29 순서 |
| `20250130-hongbo` (글상자 1개) | 글상자가 **자기 자리에서** 아이디 하나를 먹음(23), 뒤 표가 이어받음 |

범위를 벗어난 리스트를 `SetPos` 하면 **문서의 시작으로 떨어진다**(반환은 그대로 `true`).

#### 문서의 시작은 0 이 아니다

`MovePos(2)`(moveTopOfFile)가 가는 자리는 문단 앞머리의 **자리차지 컨트롤을 건너뛴 뒤**다.
영수증 서식(자리차지 표 7개 + 구역·단 정의)은 72, 보도자료 서식(인라인 표)은 16 이었다 —
컨트롤 하나가 8 코드 유닛이다. `pos` 는 글자 수가 아니라 코드 유닛이다.

#### 파일에 적힌 캐럿과 실행 중 번호가 1 만큼 다르다

문서를 열면 한글은 **저장된 캐럿 자리**에서 시작한다(영수증은 `list=292`, 마지막으로 편집한
셀). 그런데 파일의 `DOCUMENT_PROPERTIES` 에는 291 이 적혀 있다 — 파일은 서브리스트를 1부터,
실행 중 한글은 2부터 센다. 위의 "1번 자리"와 앞뒤가 맞는다.

`get_caret_position_native`(studio 의 캐럿 복원)는 이 값을 **구역 번호로 읽는다**. 리스트
아이디라서 표 안에서 저장한 문서는 범위 초과로 조용히 문서 처음을 돌려준다 — 별개 결함이다.

#### 판정과 남은 갭

`p2-cursor-lists` L2 29/29 MATCH. 곁가지로 `field-read`(8/8)·`p1-field-query`(5/5)·
`doc-basic`(9/9)·`p1-field-write`(10/10, L3 MATCH)가 통과로 돌아섰다 — **원장 9 → 16**.

`CreateField` 는 만든 누름틀 안으로 캐럿을 넣는다(오라클도 바로 뒤 `GetCurFieldName` 에서 새
이름을 답한다). 삽입 자리는 커서 좌표 그대로 코어에 넘긴다(`insertClickHereFieldAtCursor`) —
코드 유닛을 글자 번호로 옮기는 일이 `char_offsets` 를 가진 쪽에 있어야 한다.

남은 실패는 문서 속성 5종뿐이었고 `p2-doc-props` 로 격리했다 → §4.10 에서 닫았다.

**누름틀의 문단 내 `pos` 는 아직 고정하지 못한다.** `char_offsets` 가 문단마다 다르게 센다 —
필드 하나짜리 셀은 FIELD_BEGIN 8칸을 **빼먹고**(3 vs 오라클 11), 필드 둘짜리 셀은 두 개를
**앞에 몰아 세어**(16 vs 8) 어긋난다. §4.6.1 과 같은 뿌리이고 그 축은 수정 시도 3회가 모두
조판 회귀로 되돌아갔다. 그래서 시나리오는 이동이 옳은지를 `GetCurFieldName` 으로 읽어
확인하고, 누름틀의 정확한 `pos` 는 선언하지 않는다.

### 4.10 문서 속성 5종 — 오라클이 판정자가 아닌 자리 (2026-08-08)

`IsEmpty`·`EditMode`·`SelectionMode` 는 실측대로 맞췄다. 나머지 둘은 **COM 오라클이 계약을
말해 줄 수 없는 항목**이라 `substituted` 로 둔다 — 이 캠페인에서 처음 나온 종류다.

#### 실측으로 맞춘 셋

| 속성 | 계약 |
|---|---|
| `IsEmpty` | 새 문서 true, 내용 있으면 false. 구역·단 정의는 "내용"이 아니다 |
| `EditMode` | 1(일반 편집). 값만 지닌다 — **양식 모드 편집 제약은 아직 안 건다** |
| `SelectionMode` | `MoveToField(select=true)` 가 세 갈래로 갈린다 |

`SelectionMode` 의 세 갈래(한글2022 실측):

```
셀 필드            → 3 (표 셀 블록)   — 내용과 무관
누름틀 + 내용 있음 → 1 (일반 블록)
누름틀 + 빈 값     → 0                — 잡을 게 없다
커서 이동          → 0                — 규격 §8.3.30 "위치 이동시 셀렉션은 무조건 풀린다"
```

#### `Version` — 규격이 오라클을 부정한다

§8.2.14 가 못박는다: "기존 컨트롤에서의 Version 은 한글과 한글 OCX 의 버전 정보를 구한다.
그러나 **웹한글컨트롤은 한글 설치와 관계없이 사용되므로 웹한글의 버전을 리턴한다.**"

COM 오라클은 설치된 한글(`12, 0, 0, 4547`)을 답한다 — 다른 것을 재고 있다. 이 층은 자기
버전을 돌려주고 호스트가 `createHwpCtrl({ version })` 로 바꾼다.

#### `IsModified` — 한글의 값은 문서 상태가 아니다

커서를 옮긴 뒤의 **첫** `PutFieldText` 는 값이 분명히 들어갔는데도(바로 `GetFieldText` 하면 새
값이 나온다) `IsModified` 가 false 였고, **두 번째** 쓰기에서야 true 가 됐다. 커서를 안 옮기고
바로 쓰면 첫 쓰기에 true 다. 편집 엔진의 실행취소 경계를 따라가는 값이다.

그 시차는 계약이 아니라 남의 구현 사정이다. 이 층은 "문서를 바꾸는 호출이 성공하면 true" 로
두고 대조하지 않는다.

#### 판정

`p2-doc-props` 18/18 · `p2-doc-empty` 4/4 MATCH. **하니스 13개 시나리오 124/124 전량 통과** —
원장 16 → 21(verified 19 + substituted 2).

### 4.11 P3 서식 — 하니스가 먼저 눈을 떠야 했다 (2026-08-08)

서식은 값이 아니라 **ParameterSet 객체**로 온다. 러너는 객체를 `{__type: …}` 으로 줄이므로
그대로는 "아무것도 안 담은 구현"이 통과한다(§4.5.2 규칙의 정확한 재발). 그래서 러너 두 쪽에
**점 표기**를 넣었다 — `["CharShape.Item", ["Height"]]` 처럼 객체를 타고 들어가 값을 대조한다.

#### 읽기 축은 열렸다

코어가 한글 항목 이름·단위로 셋을 만든다(`getCharShapeSet`·`getParaShapeSet`, 커서 좌표로
addressing). 번역이 데이터 곁에 있어야 단위가 어긋나지 않는다 — `Height` 는 HWPUNIT,
`AlignType` 은 0~5 코드값이다.

| 자리 | 오라클 = rhwp |
|---|---|
| 셀 필드 `pt_nm` | `FaceNameHangul` Pretendard · `Height` 700 · `AlignType` 3 · `LineSpacing` 160 |
| 본문 문단 | `FaceNameHangul` 함초롬바탕 · `Height` 1000 · `AlignType` 0 |

못 채우는 항목(`FontType*`·`SmallCaps`·`BorderFill`)은 **담지 않는다**. 0 으로 채우면
"모른다"와 "0이다"가 뭉개져 서식이 틀린 것을 못 잡는다.

곁가지로 커서 계약 하나가 더 잡혔다: **범위 밖 문단 번호도 문서의 시작으로 떨어진다**
(`MovePos(0, 9, 0)` → `{0, 0, 72}`). 리스트 아이디 때와 같은 자리다.

판정: `p3-shape-read` 35/35 MATCH. **14개 시나리오 161/161 전량 통과** — 원장 21 → 26.

### 4.12 블록(선택 영역) 모델과 첫 쓰기 액션 (2026-08-08)

쓰기 축이 막혀 있던 이유는 하나였다 — **블록을 범위로 들고 있지 않았다**. `SelectionMode` 는
상태만 알았지 어디부터 어디까지인지 몰랐다.

#### 실측한 블록 계약

| 물음 | 오라클 |
|---|---|
| 셀 필드를 블록으로 | `SelectionMode` 3, **`GetSelectedPos` 는 실패**(`result:false`, 전부 0) |
| 누름틀(내용 있음)을 블록으로 | 모드 1, `slist/spos..epos` = 그 필드의 코드 유닛 범위 |
| `SelectText(spara,spos,epara,epos)` | **리스트 아이디 인자가 없다** — 블록은 한 리스트 안에서만 |
| `CharShapeBold` 를 두 번 | **토글이다** (0→1→0→1) |
| 셀 블록(모드 3)에 서식 | 걸린다 — 셀 글자 전체가 바뀐다 |
| 위치 이동 | 블록이 풀린다(규격 §8.3.30 명시) |

`GetSelectedPos` 는 규격 §8.3.14 의 속성 목록에 없는 `result` 를 함께 준다. 셀 블록이
"글자 범위가 아님"을 그 값으로만 구별할 수 있어서 그대로 싣는다.

#### 구현 범위

블록은 `{start, end}` 두 커서 좌표다. `Run` 은 글자 모양 토글 세 개
(`CharShapeBold`·`Italic`·`Underline`)를 다루고, 적용 자리는 글자 블록이면 그 범위,
셀 블록이면 그 셀의 모든 문단이다. 코어에 커서 좌표용 다리를 놓았다
(`applyCharFormatAtCursor` — 코드 유닛을 글자 번호로 옮기고 문단 끝을 넘으면 자른다).

**블록 없는 `Run` 은 하지 않는다.** 한글은 그때 "다음에 칠 글자"의 대기 서식을 바꾸는데
(실측: 블록 없이 `CharShapeBold` 를 걸면 `CharShape.Item("Bold")` 가 1 이 된다) 이 층은 그
캐럿 상태를 모델링하지 않는다. 경고를 남기고 아무 일도 하지 않는다.

#### 누름틀 블록은 아직 못 건다

`MoveToField("med_str_dt", …, select=true)` 의 범위가 오라클 8..18, rhwp 16..34 로 어긋난다 —
§4.11 과 같은 `char_offsets` 뿌리(§4.6.1)다. 그래서 시나리오는 셀 글자 블록만 고정한다.

### 4.15 커서 이동 액션 11개 (2026-08-08)

`Move*` 액션은 `MovePos` 표(§8.3.30)와 **1:1** 이다. 위치 기반이라 `GetPos` 로 정확히 대조된다.

| 액션 | 셀 안(list 8, "김철수")에서 | 본문 문단 1 에서 |
|---|---|---|
| `MoveDocBegin` / `MoveDocEnd` | `{0,0,72}` / `{0,2,0}` | 같음 |
| `MoveListBegin` / `MoveListEnd` | `{8,0,0}` / `{8,0,3}` | `{0,0,72}` / `{0,2,0}` |
| `MoveParaBegin` / `MoveParaEnd` | `{8,0,0}` / `{8,0,3}` | `{0,1,0}` / `{0,1,0}` |
| `MoveParentList`·`MoveRootList`·`MoveTopLevelList` | `{0,0,16}`(표 컨트롤 자리) | 제자리 |
| `MoveTopLevelBegin` / `MoveTopLevelEnd` | `{0,0,72}` / `{0,2,0}` | 같음 |

**최상위 리스트는 본문이다** — 셀 안에서 올라가도 표가 본문에 놓이므로 최상위는 루트다.
그래서 `MoveTopLevelBegin/End` 는 `MoveDocBegin/End` 와 같은 자리로 간다.

문단 경계는 코어가 준다(`getParaBounds`) — `start` 는 앞머리 자리차지 컨트롤을 건너뛴 자리라
본문 첫 문단은 0 이 아니고, `end` 는 문단 부호를 뺀 코드 유닛 길이다.

**글자·단어·줄 단위 이동은 넣지 않았다.** 문단 안에서 `pos` 를 한 칸씩 세는 축이라
`char_offsets` 결함(§4.6.1)에 그대로 물린다.

판정: `p3-action-move` 84/84 MATCH. **18개 시나리오 403/403 전량 통과** — 원장 67 → 78.

### 4.16 `char_offsets` 축 — 원본 바이트가 답했다 (2026-08-08)

§4.11·§4.12 를 막고 있던 축이다. 세 번의 수정 시도가 조판 회귀로 되돌아간 자리라
**손대기 전에 원본 스트림을 읽었다**(`olefile` 로 `BodyText/Section0` 을 풀어 PARA_TEXT 를
코드 유닛째로 출력).

#### 무엇이 진실이었나

파서는 **정확하다**. `parse_para_text` 는 `char_offsets` 에 진짜 코드 유닛 위치를 넣는다.
어긋남은 그 뒤에 생긴다 — 적재 때 `clear_initial_field_texts` 가 **빈 누름틀의 안내문 글자를
문단 텍스트에서 지우고**, `rebuild_char_offsets` 가 추정으로 대응표를 다시 쓴다.

원본 바이트(영수증 서식 list 9):

```
[  0] <FIELD_BEGIN × 8>
[  8] 진료 시작일      ← 안내문이 스트림에 들어 있다. 오라클의 med_str_dt pos = 8
[ 14] <FIELD_END × 8>
[ 22] 부터
[ 25] <FIELD_BEGIN × 8>
[ 33] 진료 종료일      ← 오라클의 med_end_dt pos = 33
```

그러니까 **rhwp 와 한글은 서로 다른 문서를 들고 있었다.** 좌표만 고쳐서 될 일이 아니었다.

#### 왕복 손실은 아니다

rhwp 저장본에는 안내문 글자가 없다(확인). 그러나 **한글은 파일을 열며 다시 채운다** — rhwp
저장본을 한글로 열어 리스트 길이를 재면 48 이 아니라 53 이다. 표시가 사라지지 않는다.

#### 고친 방법 — `char_offsets` 를 건드리지 않는다

호환 층 전용으로 스트림 좌표를 **직접 센다**(`field_query::stream_pos`·`field_content_start`).
세 규칙이면 끝이다.

```
글자 하나            → 1칸
확장 컨트롤          → 8칸 (누름틀은 시작·끝 두 개)
빈 누름틀의 안내문   → 안내문 글자 수
```

자기 필드의 내용 시작을 잴 때는 **자기 FIELD_END 와 자기 안내문을 세면 안 된다** — 그래서
`stream_pos` 와 `field_content_start` 를 갈랐다.

여섯 필드 전수 일치: `8 · 33 · 11 · 10 · 15 · 46`. 조판 경로는 손대지 않았으므로 §4.6.2 의
회귀 계열과 무관하다.

#### 남은 자리 하나

**편집 뒤에는 다른 필드의 안내문이 스트림에서 빠진다.** `PutFieldText` 로 한 필드를 채우면
같은 문단의 다른 빈 누름틀 안내문이 사라져(리스트 길이 53 → 47) 그 시점의 좌표가 달라진다.
언제 다시 채워지는지는 미규명이라, 시나리오는 **편집 전 상태에서만** 문단 길이를 고정한다.

판정: `p3-field-pos` 24/24 MATCH. **19개 시나리오 427/427 전량 통과.**

### 4.17 한 글자 이동 — 캐럿이 설 수 있는 자리 (2026-08-08)

§4.16 이 열어 준 축이다. 한 글자 이동은 "코드 유닛 +1" 이 아니라 **눈금 사이의 이동**이다.

영수증 서식 list 9(누름틀 둘 + 안내문)에서 오라클이 밟은 자리:

```
0 → 8 → 22 → 23 → 24 → 25 → 33 → …
```

규칙 셋으로 그 집합이 그대로 나온다(전수 일치).

| 눈금 | 자리 |
|---|---|
| 글자 | 글자마다 하나 |
| 누름틀 | **시작 코드 앞**과 **내용 시작**에 하나씩 — 끝 코드 앞에는 없다 |
| 문단 끝 | 하나 |

그래서 빈 누름틀에서 한 칸 가면 **안내문과 끝 코드를 한꺼번에 건너뛴다**(8 → 22).
안내문은 한글이 채워 넣은 표시용 글자라 캐럿이 그 안에 서지 못한다.

`MoveNextChar`·`MoveRight`·`MoveNextPos`·`MoveNextPosEx` 는 **문단 안에서 모두 같게** 움직인다
(실측). 다른 점은 리스트를 넘나드는지인데 그 경계 넘기는 아직 구현하지 않았다 — 문단 끝에서
멈춘다.

**단어·줄 이동은 아직이다.** 단어는 `0 → 8 → 25 → 49` 로 뛰어 경계 규칙이 더 필요하고,
줄 이동은 `line_segs` 를 코드 유닛으로 옮기는 일이 남았다.

판정: `p3-action-step` 53/53 MATCH. **20개 시나리오 480/480 전량 통과** — 원장 78 → 86.

### 4.19 단어 이동 — 공백으로 나뉜 덩어리, 누름틀이 경계 (2026-08-08)

평문 규칙은 단순하다. `가나 다라마 bc 12 !@ 하` 에서 단어 시작은 `0 · 3 · 7 · 10 · 13 · 16` 이고
문장부호(`!@`)나 문자 종류(한글/영문/숫자)는 단어를 **가르지 않는다** — 공백만 가른다.

누름틀이 끼면 이렇게 된다(list 9, 두 방향 자기정합):

```
0 → 8 → 25 → 33 → 49
```

| 자리 | 왜 |
|---|---|
| 0 | 문단 시작(FIELD_BEGIN 자리) |
| 8 | 누름틀 내용 시작 |
| 25 | 다음 FIELD_BEGIN 자리(앞이 공백이기도 하다) |
| 33 | 그 누름틀의 내용 시작 |
| 49 | 문단 끝 |

**끝 코드는 경계가 아니다** — 필드 바로 뒤 글자(list 9 의 47 '까')는 앞 단어에 붙는다. 그래서
"앞이 공백" 판정은 **스트림에서 바로 이웃일 때만** 성립한다(사이에 필드가 끼면 아니다).

`MoveWordEnd` 는 "다음 단어 시작 직전"이 아니라 **다음 공백 글자의 자리**다(4 → 6, 1 → 2).
마지막 단어에서는 문단 끝이다.

이 축을 열며 `leading_anchor_pos` 의 결함도 드러났다 — 누름틀 컨트롤을 자리차지로 세어
필드 있는 셀의 문단 시작이 0 대신 16 이었다. 누름틀은 캐럿이 서는 자리라 건너뛰면 안 된다.

판정: `p3-action-word` 53/53 MATCH. **21개 시나리오 533/533 전량 통과** — 원장 86 → 90.

### 4.21 문단 단위 이동과 선택 확장 이동 — 24종 (2026-08-08)

#### 문단 단위 이동 3종

문단 4개짜리 셀에서 전수 실측했다. 이름만 보면 셋 다 비슷한데 규칙이 다 다르다.

| 액션 | 규칙 | 실측 |
| --- | --- | --- |
| `MoveNextParaBegin` | 다음 문단의 처음. **마지막 문단에서는 아예 안 움직인다** | 2/1 → 3/0 · 3/1 → 3/1 |
| `MovePrevParaBegin` | 지금 문단의 처음, **이미 거기면** 앞 문단의 처음 | 2/1 → 2/0 → 1/0 |
| `MovePrevParaEnd` | 자리와 상관없이 앞 문단의 끝 | 2/1·2/0 → 1/1 |

마지막 문단에서 `MoveNextParaBegin` 을 "그 문단의 처음"으로 끌어내리면 틀린다(3/1 → 3/0 으로
갔다가 게이트에 걸렸다). 안 움직이는 것이 맞다.

#### 선택 확장 이동 21종

`MoveSel*` 은 같은 자리로 가되 **닻에서 여기까지**를 블록으로 잡는다.

- **닻**은 첫 확장 때의 캐럿이다. 보통 이동과 `SetPos` 가 놓는다.
- 되돌아와 닻과 겹치면 **블록이 풀린다**(`result:false`·모드 0). 그런데 **닻은 남는다** —
  더 가면 반대쪽으로 다시 잡힌다(3에서 6까지 잡았다가 3으로 돌아오면 풀리고, 2로 더 가면
  (2,3)이 잡힌다).
- 시작·끝은 언제나 정규화돼 나온다(캐럿이 앞이면 캐럿이 `start`).

**블록은 리스트를 넘지 못한다.** 그래서 문서 처음·끝으로 가는 확장이 보통 이동과 갈린다 —
셀 안에서 `MoveDocEnd` 는 본문 끝(0/2/0)으로 나가지만 `MoveSelDocEnd` 는 그 셀의 끝(262/0/59)에
멈춘다. `MoveSelDocBegin`·`MoveSelTopLevel*` 도 같아서, 넷 다 리스트의 처음·끝으로 옮겨 놓았다.

#### 곁들여 나온 코어 결함 — 시작이 끝보다 컸다

본문 첫 문단의 경계가 `{start:72, end:24}` 였다. `stream_len` 이 문단 텍스트만 세는데,
컨트롤 중에는 **텍스트에 자리표 글자를 안 남기는 것**이 있어서(구역·단 정의 같은 표식) 실제보다
짧게 나온 탓이다. 한글은 그 문단의 시작도 끝도 72 로 답한다. 앞머리 자리차지 자리를 바닥으로
깔아 고쳤다 — `stream_len` 은 이제 `leading_anchor_pos` 아래로 못 내려간다. 회귀 가드는
`para_bounds_never_start_past_end`.

### 4.22 글자 모양 나머지와 블록 잡기 — 9종 (2026-08-08)

#### 글자 모양 여섯

색 셋은 값만 재면 됐다(BGR 실측: 보라 6697881 = `#993366` · 흰색 16777215 · 노랑 65535).
장평 증감은 항목이 `RatioHangul` 이고 폭이 1 이다(100 → 101 → 102 → 101).

`CharShapeSuperSubscript` 는 이름과 달리 **토글이 아니라 순환**이다 — 없음 → 위 첨자 →
아래 첨자 → 없음. 따로 있는 `CharShapeSuperscript`·`CharShapeSubscript` 는 각각의 토글이라
서로 다른 액션이다.

**`CharShapeNextFaceName`·`PrevFaceName` 은 원장에 안 올렸다.** 글꼴을 **설치된 글꼴 목록**
순서로 옮긴다(실측: Pretendard → 가는안상수체 → 굴림). 목록이 머신마다 다르니 오라클이
판정자가 될 수 없다 — `Version` 과 같은 갈래인데, 그쪽은 계약이 분명해 `substituted` 로 뒀지만
이건 계약 자체가 환경이라 그냥 남겨 둔다.

#### 블록 잡기 셋

`SelectAll` 은 리스트 전체다. 그런데 시작이 **캐럿의 처음이 아니다** — 본문 첫 문단에서
캐럿은 72 인데 블록은 16 에서 시작한다. 캐럿은 앞머리 자리차지 개체를 전부 건너뛰지만
블록은 그 개체를 **담을 수 있어야** 하기 때문이다(표를 통째로 잡는 경우). 건너뛰는 것은
구역·단 정의 같은 표식뿐이라 코어에 `select_start_pos` 를 두고 `paraBounds` 에 실어 보냈다.

`Select`(F3)는 한 액션이 세 가지 일을 한다.

| 부를 때 상태 | 하는 일 |
| --- | --- |
| 모드 꺼짐 | 선택 모드를 켠다(`SelectionMode` 17). 블록은 없다 |
| 모드 켜짐 · 블록 없음 | 지금 **단어**를 잡는다(3 → (3,7)) |
| 모드 켜짐 · 블록 있음 | **리스트 전체**를 잡는다 |

모드가 켜진 동안에는 보통 이동뿐 아니라 **`SetPos` 도 블록을 늘린다**(평소 `SetPos` 는
블록을 푼다). `Cancel` 이 모드와 블록을 끄고 캐럿은 있던 자리에 남는다.

판정: `p3-action-char2` **28/28**, `p3-action-block` **78/78** — 둘 다 **첫 대조에서 전량

### 4.23 지우기 넷과, 이 표본이 판정하지 못하는 것 (2026-08-08)

#### 지우기 넷

셀마다 하나씩 걸어 서로 간섭하지 않게 재고, 문서 텍스트 길이(1820 → 1799)로 확인했다.

| 액션 | 지우는 범위 | 캐럿 |

| `DeleteBack` | 앞의 한 글자 | 지운 만큼 뒤로 |
| `DeleteWord` | 지금 낱말의 끝까지 | 제자리 |
| `DeleteWordBack` | 앞 낱말의 처음까지 | 그 처음 |

블록이 있으면 넷 다 블록을 지운다. **문단 끝에서 `Delete` 는 아무 일도 하지 않는다** —
다음 문단을 끌어올리지 않는다.

**`DeleteLine`·`DeleteLineEnd` 는 원장에 안 올렸다.** 실측은 됐지만 "줄"은 조판이 정하는
것이라 한 줄짜리 문단에서만 맞다 — §4.18(줄 이동)과 같은 이유다.

#### 곁들여 나온 결함 — `SetPos` 가 문단 끝을 안 잘랐다

4칸짜리 문단에 `SetPos(…, 5)` 를 주면 한글은 4로 자르는데 이 층은 5를 그대로 들고 있었다.
그 자리에서 `DeleteWordBack` 을 걸면 범위가 빈 채로 계산돼 아무 일도 일어나지 않는다.
`SetPos` 에서 문단 끝으로 자르게 고쳤다(`MoveListEnd` 가 답하는 값과 같은 자다).
전역 변경이라 전체 게이트를 다시 돌렸고 회귀는 없다.

#### 이 표본이 판정하지 못하는 것 — 구조 액션

`BreakPara`·`BreakLine`·`DeleteField`·`Table*` 열여덟 가지를 걸어 봤는데 **오라클이 아무 일도
하지 않는다.** 문서 텍스트도 문단 수도 리스트도 그대로다(1820자 → 1820자). 반면 같은 문서에서
글자 지우기는 멀쩡히 동작한다 — 즉 "읽기 전용"이라 막힌 것이 아니라 **구조를 바꾸는 액션만**
막혀 있다. 이 표본이 누름틀 서식 문서라 그런 것으로 보이나 확증은 못 했다.

관측 함정 하나: `EditMode` 를 문서를 연 **직후 첫 호출**로 물으면 0 이 나온다(`p2-doc-props`
에서는 1). 값이 정착하기 전에 물은 것이라 이 값으로 "읽기 전용"을 단정하면 안 된다.

**구조 액션은 다른 표본이 필요하다** — 이 캠페인에 표본을 하나 더 들이는 일이라 이 배치에
얹지 않고 따로 판다.

판정: `p3-action-delete` **33/33**. **26개 시나리오 896/896 전량 통과**(이번엔 한 번에 다 붙었다),

### 4.24 편집 액션이 띄엄띄엄 먹던 이유 — 읽기 전용으로 열려 있었다 (2026-08-08)

§4.23 이 "구조 액션은 이 표본이 판정 못 한다"고 적은 자리다. **표본 문제가 아니었고, 구조
액션만의 문제도 아니었다.**

**증상**: `BreakPara`·`Table*`(셀 이동·셀 블록) 같은 편집 액션이 오라클에서 대개 아무 일도
하지 않는다. 반환값은 `null`(정상)이고 캐럿도 문서도 그대로다. 그런데 **같은 파일에 같은
호출을 다시 돌리면 어떤 실행은 전부 먹는다.**

**원인**: 같은 파일이 **다른 한글 프로세스에 이미 열려 있으면** 한글은 그 문서를 **읽기
전용**으로 연다. 그 상태에서 편집 액션은 조용히 무시된다. `EditMode` 가 그것을 정확히 말해
준다 — 실측 짝:

| 남은 `Hwp.exe` | `EditMode` | `BreakPara` |
| --- | --- | --- |
| 없음 | 1 | 8/8 성공 |
| 같은 파일을 쥔 프로세스 있음 | 0 | 8/8 무동작 |

탐침이 프로세스를 남기고 끝나는 일이 잦아서(러너를 직접 부르면 `Quit` 뒤에도 남는다) 앞선
조사가 통째로 이 상태 위에서 이뤄졌다. "구조 액션만 막힌다"는 첫 진단은 **표본 추출의 착시**
였다 — 글자 지우기가 되던 실행은 마침 편집 가능하게 열린 실행이었다.

먼저 세웠다가 반증한 가설(다시 밟지 말 것): 표본이 누름틀 서식 문서라서 · 예열 부족
(`GetTextFile`) · 본문을 먼저 밟거나 편집을 한 번 해야 · 창이 숨겨져서(`HWPCTRL_VISIBLE=1`
로 띄워도 그대로) · `Run` 과 `HAction.Run` 이 다른 길이라서(둘 다 똑같이 먹고 똑같이 안 먹는다).

**막은 방법**: 러너가 `Open` 직후 `EditMode` 를 물어 1 이 아니면 **판정하지 않고** 종료한다
(`exit 4`, `<id>.rejected.json`). 게이트는 그것을 `READONLY` 로 보고한다. 버전 가드
(`--expect-version`)와 같은 자리다 — **못 믿을 정답지를 디스크에 남기지 않는 것**이 요점이다.

기존 원장은 오염되지 않았다. 읽기 전용에서 돌았다면 오라클만 무동작이고 rhwp 는 실제로 바꾸니
대조가 **깨졌을** 것이다. 통과한 시나리오는 그래서 편집 가능한 실행이었다.

**곁들여 확인한 것 둘**

- `EditMode` 는 문서를 연 **직후 첫 호출**에서도 참값을 준다. 앞서 "정착 전이라 0" 이라고 적은
  것은 틀렸다 — 그때는 정말 읽기 전용이었다.
- **문단 번호·글머리표 계열은 탐침에 넣지 말 것.** `PutBullet`·`PutParaNumber`·
  `PutOutlineNumber`·`ParaNumberBullet` 중 하나가 대화상자를 띄워 오라클이 멈춘다(10분 넘게
  응답 없음 → `Hwp.exe` 를 직접 죽여야 했다). `GetFieldList(number=2, …)` 와 같은 갈래다.

**열린 자리**: 편집 가능한 실행에서 `BreakPara` 도 `TableRightCell` 도 `TableCellBlock`(모드 3)도
정상 동작한다. **표 50종과 구조 액션 축이 열렸다** — 다음 배치가 여기다.

판정: 26개 시나리오 896/896 그대로(가드 추가로 인한 회귀 없음). 원장은 127/484 그대로다.

### 4.26 표 고치기 — 줄·열 끼움과 지움 6종 (2026-08-08)

이번엔 문서를 실제로 바꾸는 축이다. 구조가 바뀌면 좌표가 통째로 달라져서 **관측 방법부터**
정해야 했다 — 리스트 2‥14 의 문단 끝 자리를 늘어놓은 **지문**을 쓴다. 3열 표라 줄 하나가 셀
셋이니, 줄을 끼우면 그 뒤가 3씩 밀리고 열을 끼우면 줄마다 하나씩 늘어 지문이 통째로 달라진다.

액션은 **하나씩 새 문서에서** 쟀다. 누적으로 걸면 무엇이 어디에 들어갔는지 해석이 엉킨다
(한 번 그렇게 재다 헛짚었다).

#### 캐럿이 어디에 서는가

| 액션 | 캐럿 |
| --- | --- |
| `TableInsertUpperRow`·`TableInsertLeftColumn` | **자기 칸을 따라간다** — 8 → 11 |
| `TableInsertLowerRow`·`TableInsertRightColumn` | 자기 칸이 안 밀리면 제자리(8 → 8), 밀리면 따라감(8 → 10) |
| `TableDeleteRow` | 지운 줄 자리의 **첫 칸** — 8 에서 지워도 9 에서 지워도 8 |
| `TableDeleteColumn` | **첫 줄**의, 지운 열 자리 — 8 → 2, 12 → 3 |

지움 둘은 자기 칸이 사라지니 갈 곳이 따로 정해져 있고, 그 규칙이 서로 대칭이다(줄은 열 0 으로,
열은 줄 0 으로). 표 밖으로는 안 나가게 잘린다.

#### 코어에 더한 것

`table_edit_at_cursor(list_id, op)` — 리스트 아이디 하나를 구역·문단·컨트롤·행·열로 풀어
기존 표 편집 API(`insert_table_row_native` 따위)에 넘긴다. **캐럿을 어디로 옮길지는 코어가
정하지 않는다** — 표가 바뀐 뒤의 격자를 봐야 알 수 있어서 호환 층이 정한다. 표가 바뀌면
리스트 번호가 다시 매겨지므로 호환 층은 캐시한 리스트 표를 버리고 다시 읽는다.

**중첩 표는 아직이다.** 아래 표 편집 API 가 `(구역, 문단, 컨트롤)` 세 값만 받아 셀 안의 표를
짚지 못한다 — 그 경우 `{ok:false}` 로 돌려준다.

#### 시나리오 짜임

끼운 것은 **곧바로 되지운다.** 안 그러면 뒤 블록이 다른 표 위에서 돌아 지문이 어긋난다.
끼움 → 지움을 짝지어 표를 매번 원래대로 돌려놓는다.

판정: `p3-action-table-edit` **376/376 — 첫 대조에서 전량 일치.** 28개 시나리오 1339/1339,
원장 136 → **142/484**.

나눔 속성**을 얹는 것이라, 관측되는 좌표만 맞춰 흉내 내면 저장본이 달라진다 — 관측이 같다고
같은 일이 아니다. `BreakSection`·`BreakColDef` 도 같은 갈래다.

코어에 `split_para_at_cursor` 를 뒀다(좌표만 옮기고 본문·셀 경로의 기존 가르기 API 에 넘긴다).

판정: `p3-action-break` **31/31 — 첫 대조에서 전량 일치.** 32개 시나리오 1857/1857,
원장 153 → **155/484**.

### 4.31 개체 축은 열렸으나 순서를 못 굳혔다 — 미선언 (2026-08-08)

개체(Shape 41종)를 열려고 팠다. **표본은 있다** — `samples/2026_oss_rst.hwp`·

막힌 곳은 **어느 개체가 골라지는가**다.

- `ShapeObjNextObject`·`PrevObject` 는 **이미 고른 개체가 있어야** 움직인다. 아무것도 안 고른

- `SelectCtrlFront` 는 **캐럿과 무관하게** 돈다 — 0/0/0 에서도 0/1/0 에서도 0/0/24 에서도

같아 보이는 다른 동작"이 된다(§4.30 의 `BreakColumn` 과 같은 함정).

**남긴 것**: 코어에 `objects_json`(본문 개체 목록 — 문단·컨트롤 번호·종류·글 리스트), 호환 층에
`ShapeObjNextObject`·`PrevObject`·`ShapeObjTextBoxEdit` 와 개체 선택 모델. **원장에는 안 올렸다.**
다음 사람이 z-순서를 짚을 표본(개체 서너 개, 겹침 순서를 아는 문서)을 구하면 그대로 이어

### 4.33 `CellShape` 를 열어 봤다 — 표 크기 축은 더 깊다 (2026-08-08)

§4.32 가 꼽은 (1)번을 곧바로 팠다. **원장은 안 올랐다.** 무엇을 봤는지 남긴다.

**있는 항목은 셋뿐이다.** `CellShape.Item` 이 값을 주는 이름은 `Width`·`Height`·`VertAlign`
이고 나머지는 전부 `null` 이다(`CellWidth`·`MarginLeft`·`Protect`·`FieldName` … 이 컨트롤에
없다). 파라미터셋 64항목 중 셀 쪽은 이 셋이 전부라는 뜻이다.

**크기 조절 액션 여덟은 전부 무동작이다.** `TableResizeRight`·`Left`·`Up`·`Down`,
`TableResizeCell*`·`Line*`·`Ex*` 를 셀 블록이 있을 때와 없을 때 다 걸어 봤지만 `Width`·
`Height` 가 꿈쩍하지 않는다. UI 드래그로만 도는 것으로 보인다.

**`Width` 는 셀 폭이 아니다.** 오라클은 셀 8 과 셀 9 에 똑같이 47622 를 준다. 그런데 rhwp 의
셀 폭은 7384 와 2573 으로 서로 다르다 — 두 셀의 실제 너비가 다르다는 것은 문서를 보면 분명하다.
게다가 `TableSplitCellCol2` 로 칸을 반으로 갈라도 47622 그대로다. 표 폭 같은 상위 값으로
보이는데, 그 뜻을 못 굳힌 채 맞추면 또 "관측만 같은 다른 값"이 된다.

`TableDistributeCellWidth` 는 47622 → 47624 로 **아주 조금** 움직였다. 동작은 하지만 그 값의
뜻을 모르니 판정에 쓸 수 없다.

**남긴 것**: 코어 `cell_shape_set_json`(rhwp 기준 `Width`·`Height`·`VertAlign`)과 wasm
`getCellShapeSet`. 뜻을 굳히면 바로 얹을 수 있다. 그러려면 폭을 아는 표(예: 두 칸짜리, 한 칸이
다른 칸의 두 배)를 만들어 `Width` 가 무엇을 따라 움직이는지부터 봐야 한다.

### 4.34 개체 목록을 바로잡았다 — 그래도 순서는 아직 (2026-08-08)

§4.31 에서 접었던 개체 축을 한 걸음 더 밀었다. **원장은 안 올랐지만 목록이 틀렸던 것을 고쳤다.**

**표도 개체다.** `objects_json` 이 그림·그리기·수식만 세고 표를 뺐는데, 그러면 오라클이 고르는
자리와 안 맞는다 — `2026_oss_rst.hwp` 에서 rhwp 는 개체를 1개로 세는데 오라클은 `0/0/16`
말고 `0/1/0`·`0/4/0` 도 고른다. 그 둘이 표다. 표를 넣으니 5개가 되고 캐럿 자리가 전부 맞는다.
`anchored`(자리차지/글자처럼)도 함께 낸다.

**그래도 순서는 못 굳혔다.** 오라클이 만지는 것은 `{0/0/16, 0/1/0, 0/4/0}` 셋뿐이고
`0/2/0`·`0/7/0` 은 건드리지 않는다. 자리차지 여부로도 안 갈린다(만지는 셋 중 둘이 false,
안 만지는 둘도 하나는 false 하나는 true). 남은 가설은 **쪽 단위**(캐럿이 있는 쪽의 개체만)인데
확인하려면 쪽 정보를 붙여 재야 한다.

목록이 맞아졌으니 다음 사람은 "쪽으로 거르는가"만 확인하면 된다.

### 4.35 쪽 가설은 반증, 그러다 **다구역 좌표 결함**을 찾았다 (2026-08-08)

§4.34 가 남긴 "쪽 단위로 거르는가"를 쟀다. **아니다.**

`SelectCtrlFront` 는 쪽이 아니라 **캐럿 뒤로 나아간다** — 캐럿을 문단 0 에 두면 1 → 4 → 7 → 10,
문단 7 에 두면 10 → 13 → 14 → 14(끝에서 멈춤)다. `KeyIndicator` 로 본 쪽 번호는 내내 1 이었다.

그런데 그 값을 맞춰 보다 **더 큰 것**이 나왔다.

#### 본문 리스트는 구역을 가로지른다

오라클은 이 문서의 본문 문단을 **0‥14** 로 센다. rhwp 는 **8개**만 셌다. `KeyIndicator` 가
`secno: 2` 라 했고, 세어 보니 이 문서는 **두 구역**이다 — `2026_oss_rst.hwp` 만 두 구역이고
지금까지 쓴 다른 표본은 전부 한 구역이라 여태 안 드러났다.

**한글의 본문 리스트(0번)는 구역을 가로질러 하나로 이어진다.** rhwp 의 커서 모델은 첫 구역만
보고 있었다. 고친 자리:

- `root_para_location(core, 본문문단)` → `(구역, 그 구역 안 문단)` 을 새로 두고
- `cursor_paragraph`·`cursor_paragraph_ref`·`get_cursor_model_json`(문단 수·끝 문단·끝 자리)·
  `objects_json` 이 그것을 쓰게 했다
- 본문을 고치는 길들(`insert_text`·`split_paragraph`·`delete_text`·`apply_char_format`·
  `apply_para_format`)이 **구역 0 을 박아 쓰던 것**을 풀었다

고친 뒤 `paraCount` 가 15 로 한글과 같아졌고, 한 구역 표본들은 그대로다(5·3).

#### 곁들여 — `SetPos` 는 문단 **시작 아래로도** 자른다

다구역 시나리오를 돌리자 6행이 어긋났다. 앞머리 자리차지가 있는 문단에 `SetPos(…, 0)` 을 주면
한글은 그 뒤 자리로 민다(문단 0 → 24, 문단 7 → 8, 문단 8 → 16). §4.23 에서 끝만 자르게
고쳤던 것을 양쪽 다 자르도록 넓혔다.

#### 같은 뿌리의 잠복 결함 — 표를 구역으로 가르지 않았다

리스트 표의 `hostPara` 도 **구역 안 번호**다. 호환 층이 표를 `(hostListId, hostPara,
controlIndex)` 로만 갈랐으니, 구역이 다른 두 표가 같은 상대 문단 번호를 쓰면 **한 표로 뭉쳤다**.
셀 이동·셀 블록·표 편집이 전부 그 위에 서 있었다. 커서 모델이 `sectionIndex` 를 함께 내고
호환 층이 `#sameTable` 하나로 판정하게 고쳤다. 지금 표본으로는 안 드러나는 자리라 **터지기
전에** 막은 셈이다.

판정: `p2-multi-section` **50/50**. 33개 시나리오 1907/1907, 원장 155/484 그대로다 —
**새 항목이 아니라 이미 선언한 좌표 API 가 다구역 문서에서도 맞게 됐다.**

### 4.36 파라미터셋 좌표와 필드 상태 — 2종 (2026-08-08)

액션 말고 **컨트롤 본체**(`HwpCtrl` 88항목 중 62 남음)에서 값이 큰 것을 골랐다.

- `GetPosBySet` 은 `GetPos` 와 같은 값을 `List`·`Para`·`Pos` 로 준다. 파라미터셋 껍데기만
  씌우면 된다.
- `CurFieldState` 는 **갈래 + 필드 비트**다. 실측 넷으로 규칙을 세웠다:

| 자리 | 값 |
| --- | --- |
| 본문 | 0 |
| 표 셀 안(필드 아님) | 1 |
| 셀 필드 안 | 17 = 1 + `0x10` |
| 누름틀 안 | 18 = 2 + `0x10` |

처음엔 셋(0·17·18)만 보고 "0x10 이 필드 안"까지만 세웠다가, 셀 안 평문 자리에서 **1** 이
나와 갈래 비트를 갈랐다. 넷을 다 봐야 규칙이 섰다.

`SetPosBySet` 은 구현했지만 **원장에 못 올렸다** — 오라클에 넘길 파라미터셋을 시나리오가
만들 길이 없다(러너가 셋을 못 짓는다).

#### 하니스 구멍 둘

- **파이썬 러너의 점 표기가 메서드를 못 탔다.** `CharShape` 처럼 속성이면 됐지만
  `GetPosBySet` 은 메서드라 `GetPosBySet.Item` 이 죽었다. 중간이 호출 가능하면 불러서 그
  반환 객체를 타게 고쳤다(rhwp 러너는 이미 그랬다 — 두 러너의 규약을 맞췄다).
- **시나리오가 없는 원장 이름을 선언해도 게이트가 초록이었다.** 액션은 `Action.X` 인데
  컨트롤 본체는 `HwpCtrl.method.X`·`HwpCtrl.property.X` 다. `HwpCtrl.GetPosBySet` 이라 적은
  시나리오가 31/31 로 통과했는데 원장은 155 그대로였다 — 조용히 헛돈 것이다.
  `build_ledger.py --check` 가 시나리오의 선언을 전부 대조하게 했다(틀린 이름으로 물리는 것까지
  확인).

판정: `p2-pos-byset` **31/31**. 34개 시나리오 1938/1938, 원장 155 → **157/484**.

### 4.37 컨트롤 사슬 — 7종, 그리고 §4.34 가 풀렸다 (2026-08-08)

한글은 문서가 담은 컨트롤을 **하나의 사슬**로 준다. `HeadCtrl` 에서 `Next` 를 타면
`secd → cold → gso → tbl → … → secd` 처럼 문서 순서로 나온다. 마디마다 값 셋이 있다.

| 속성 | 값 |
| --- | --- |
| `CtrlID` | 네 글자 코드 — `secd`·`cold`·`gso`·`tbl` |
| `CtrlCh` | 스트림 글자 코드 — 구역·단 정의 같은 **표식은 2**, 표·그리기 같은 **개체는 11** |
| `UserDesc` | 사람이 읽는 이름 — "구역 정의"·"단 정의"·"표", 그리기는 갈래마다 다르다("사각형") |

`UserDesc` 는 rhwp 가 이미 같은 이름을 들고 있었다(`ShapeObject::shape_name`). 새로 짓지 않고
그대로 썼더니 오라클과 맞았다.

#### 사슬은 **셀 안까지** 든다 — §4.34 의 "표 하나 모자람"이 이것이었다

처음엔 본문 문단의 컨트롤만 걸어 `tbl` 이 넷이었는데 오라클은 다섯이었다. 이 표본에 **중첩
표**가 있다(셀 안의 표 — 리스트 16개가 셀을 호스트로 삼는다). 사슬을 깊이 우선으로 — 자기
다음에 자기 속을 — 걷게 하니 다섯으로 맞았다. 리스트 번호를 매기는 걸음(§4.9)과 같은 순서라
둘이 어긋나지 않는다.

### 4.38 명령 잠금 — 2종 (2026-08-08)

`LockCommand(액션, 참/거짓)` 으로 액션 하나를 잠그면 **`Run` 이 아무 일도 하지 않는다**

### 4.39 컨트롤 앵커 — 점 표기에 인자를 실었다 (2026-08-08)

### 4.40 `Lock` — §4.34 가 못 풀던 것의 답, 그리고 파서 결함 (2026-08-08)

앵커가 열리자 사슬 열다섯을 전부 앵커로 늘어놓고 `SelectCtrlFront` 가 고르는 여섯과 맞대 봤다.
자리로도 종류로도 안 갈렸다. 그래서 `Ctrl.Properties` 를 읽었더니 한 항목이 정확히 갈랐다.

**`Lock` 이다. 잠긴 개체는 `SelectCtrlFront` 가 건너뛴다.** 이 표본의 표 열둘 중 잠긴 셋
(`0/2/0`·`0/8/16`·`0/12/0`)만 정확히 빠진다. §4.31·§4.34 가 "z-순서 같다"고 짐작하던 자리의
답이다.

#### 곁들여 — rhwp 가 HWP5 잠금 비트를 안 읽고 있었다

`Properties` 를 만들어 대조하니 rhwp 의 `Lock` 이 **전부 0** 이었다. 모델에 `locked` 필드는
있는데 HWPX 경로에서만 채우고 HWP5 파서가 안 읽었다. 비트는 실측으로 뽑았다 — 잠긴 표의
`attr` 이 안 잠긴 표보다 정확히 `2^30` 만큼 크다(같은 문서 열둘로 대조). **비트 30** 을
배선하니 오라클과 전량 일치한다.

이건 호환 층만의 일이 아니다. 잠긴 개체가 저장·변환에서 **풀려 나가고 있었다**.

`Properties` 는 `Lock`·`TreatAsChar`·`AllowOverlap`·`Width`·`Height` 만 낸다. `TextWrap`·
`VertRelTo` 같은 항목은 `attr` 비트 해석이 더 필요해 **넣지 않았다**(`CharShape` 와 같은 규칙 —
짐작으로 채우면 "모른다"가 사라진다).

#### 다른 표본으로 교차 확인 — 규칙이 더 좁아졌다

`20250130-hongbo.hwp` 에서 `SelectCtrlFront` 를 돌리니 **본문 개체 일곱을 전부** 돈다
(`0/0/16 → 0/2/0 → 0/5/0 → 0/24/0 → 0/25/0 → 0/26/0 → 0/29/0`). 여기서 앞선 짐작 둘이
반증됐다:

- "캐럿이 있는 문단의 개체는 건너뛴다" — 아니다. `0/0/16` 을 첫 누름에 고른다.
- "그리기는 안 고른다"·"자리차지가 아니면 안 고른다" — 아니다. `0/25/0`(그리기)도
  `0/29/0`(`TreatAsChar=0`)도 고른다.

그래서 지금 선 규칙은 **본문 층 + 잠기지 않음**이다. 이 규칙은 hongbo 를 7/7 로 맞추고
oss_rst 를 8 중 6 으로 맞춘다 — 남는 예외가 **하나**다: oss_rst 의 그리기 `0/0/16`.

> **뒤에 밝혀짐(§4.44)**: 그 예외는 `TextWrap` 이 아니라 **캐럿 자리**였다. 아래 절이 답이다 —
> 여기 적은 `TextWrap=3` 후보는 **틀린 짐작**이다.

판정: `p2-ctrl-chain` **90/90**(사슬 30 + 앵커 24 + 속성 36). **36개 시나리오 2040/2040**,
원장 167 → **168/484**.

### 4.41 하니스가 객체를 인자로 넘길 수 있게 됐다 — 2종 (2026-08-08)

§4.32 가 "시나리오는 JSON 값만 줄 수 있어 못 부른다"고 접어 둔 갈래를 열었다.

시나리오 인자에 `{"$obj": "경로"}` 를 쓰면 러너가 **자기 쪽에서 그 자리의 객체를 만들어**
넘긴다(두 러너 같은 규약). `SetPosBySet({"$obj": "GetPosBySet()"})` 처럼 쓴다.

- `SetPosBySet` — 파라미터셋으로 캐럿을 옮긴다. `SetPos` 와 같은 자다.
- `CreateSet` — **아는 이름이면 그 이름을, 모르면 빈 이름을** 단 셋을 준다. 확인한 이름 열

  `Style`·`CellBorderFill`·`ShapeObject`)은 전부 그대로 돌려주고 없는 이름은 `""` 다.
  **이 목록은 실측한 것만** 담는다 — 규격 전체가 아니므로 여기 없는 이름을 한글이 받아 줄 수
  있다(확인하면 그때 넣는다).

#### `KeyIndicator` 어댑터를 고쳤다 (항목은 아직)

값이 **아홉**인데 러너가 여덟로 읽어 `secno` 부터 이름이 한 칸씩 밀려 있었다 — `result` 다음에
`seccnt`(구역 수)가 하나 더 온다. 마지막 값이 숫자가 아니라 `"(A43): 문자 입력"` 같은
**문자열**이라 밀림이 눈에 띄었다. 고치고 나니 `ctrlname` 이 **셀 주소를 담는다**는 것도 보였다.

그래도 원장에는 못 올린다 — `prnpageno`·`line`·`pos` 가 조판을 타고, 반환이 한 덩어리라
일부만 맞출 수 없다.

#### 여전히 못 부르는 것

`GetCtrlHorizontalOffset`·`GetCtrlVerticalOffset`·`GetViewStatus`·`ScrollPosInfo`·
`ReadOnlyMode`·`GetTableCellAddr` 은 **이 COM 개체에 아예 없다**(`AttributeError`).
`$obj` 로도 못 부른다 — 오라클이 판정자가 아니다.

### 4.44 개체 고르기가 열렸다 — 내 짐작이 틀렸다 (2026-08-09)

§4.40 이 "예외 하나는 `TextWrap=3` 인 것 같다"고 남긴 자리다. **아니었다.**

`TextWrap` 을 실측으로 뽑아(그 자체가 `attr` **비트 21‥22** 라는 성과다 — 값 `0`·`1`·`3` 여섯
짝을 두 문서에서 모아 구간을 찾았다) 규칙에 넣고 돌렸더니, 이번엔 **다른 표본이 어긋났다**.
hongbo 의 첫 표를 통째로 건너뛴 것이다.

원인은 내 쪽이었다. `SetPos(0, 0, 0)` 은 **문단 시작으로 밀린다**(§4.35 — 앞머리 자리차지가
있으면 그 뒤로). oss_rst 의 본문 첫 문단은 시작이 **24** 이고 문제의 그리기는 **16** 에 있다.
즉 그 개체는 **캐럿보다 앞**이라 앞으로 가는 고르기에 안 걸린 것뿐이었다. `TextWrap` 은 아무
상관이 없었다.

바로 선 규칙:

- 고른 개체가 없으면 **캐럿 자리부터**(같은 자리 포함) 첫 개체
- 고른 개체가 있으면 그 **다음** 개체
- 더 없으면 **고르기를 푼다**(모드 0), 캐럿은 그대로
- 대상은 본문 층의 개체 중 **잠기지 않은 것**

두 표본으로 못박았다 — oss_rst 는 잠긴 셋을 건너뛰고 여섯을 돌며, hongbo 는 일곱을 다 돈다.

> 두 번째 교훈이다. §4.39 에서 `stream_pos` 를 "고쳤다가" 게이트에 잡혔고, 여기서는 `TextWrap`
> 을 규칙에 넣었다가 **다른 표본**에 잡혔다. 한 표본에서 세운 규칙은 다른 표본이 재판한다.

`TextWrap` 은 그대로 `Properties` 에 남긴다 — 규칙에는 안 쓰지만 값 자체는 실측이고 맞는다.

판정: `p2-obj-select` **26/26** · `p2-obj-select2` **29/29**. **39개 시나리오 2143/2143**,
원장 173 → **174/484**.

### 4.45 나누기 넷과 탭 — 자를 빈 곳에 대면 눈금이 안 보인다 (2026-08-09)

`BreakPage`·`BreakColumn`·`BreakColDef`·`BreakSection`, 그리고 `InsertTab` 다섯을 올렸다.
셋 다 처음 재려던 자리에서는 **아무 일도 안 하는 것처럼 보였다.**

#### 자를 빈 곳에 댔다

처음 잰 자리는 문단 3, 글자 없는 빈 문단이었다. `BreakPage` 와 `BreakColumn` 은 문단 수도 안
늘리고 문단 길이도 안 바꿨다. "표식만 얹고 마는 액션"으로 접을 뻔했다. 글자 한가운데(문단 6,
글자 7 개 중 3)에서 다시 재니 넷 다 문단을 가른다.

자는 `SetPos(list, para, 10**7)` 의 **클램프**다 — 그 뒤 `GetPos` 가 그 문단의 끝 자리를 준다.
문단 여섯의 끝을 액션 앞뒤로 늘어놓으면 무엇이 얼마나 늘었는지 한눈에 보인다. 한글을 두 번
열 필요도 없다.

#### 규칙 — 가르는 것은 한가운데일 때뿐

| 캐럿 | 하는 일 | 표식이 앉는 문단 |
| --- | --- | --- |
| 문단 끝 | 안 가름 | 다음 문단 |
| 문단 처음 | 안 가름 | 그 문단 |
| 한가운데 | 가름 | 뒤쪽 문단 |

표식 크기는 갈래마다 다르다: 쪽·단은 문단 속성이라 **0칸**, `BreakColDef` 는 `ColumnDef` 하나로
**8칸**, `BreakSection` 은 `SectionDef`+`ColumnDef` 로 **16칸**이다. 캐럿은
`max(표식칸, 대상 문단의 원래 시작)` 에 선다 — 이것은 **맞춘 식**이지 밝힌 기전이 아니라고
적어 둔다. 액션 넷 × 자리 셋에 판별 자리 셋, 열다섯 관측에 전부 맞는다.

조건이 둘 더 있고, 둘 다 게이트가 잡아 줬다:

1. **대상이 이미 표식을 지고 있으면 겹쳐 얹지 않고 빈 문단을 새로 끼운다.** 쪽 나눔이 앉은
   문단에 단 나눔을 걸면 문단이 하나 는다.
2. **시작과 끝이 같은 문단은 `end > 0` 으로 갈린다.** 자리차지가 하나라도 있으면 끝으로 치고,
   아무것도 없는 빈 문단은 자기가 표식을 진다. 쪽 나눔은 0칸이라 문단 자에는 자국이 안 남고
   **캐럿으로만** 보이는 갈림이다.

#### 덤으로 나온 좌표 결함 — 탭은 8칸이다

`InsertTab` 뒤 캐럿이 3 → **11** 로 갔다. 탭은 스트림에서 8칸인데
(`parse_para_text` 의 탭 가지가 `pos += 16` 으로 넘어간다 — 16바이트 = 8 코드 유닛),
파서는 그것을 **글자 하나** `'\t'` 로 담는다. 그래서 탭이 든 문단은 그 뒤 자리가 탭 하나당
7칸씩 앞당겨져 보였다. 누름틀 좌표가 어긋나는 결함이라 `stream_pos` 와 `field_content_start`
에서 메웠다(`tab_padding`).

### 4.46 구역 이동 — 앞 구역인가 이 구역인가 (2026-08-09)

`MoveSectionUp`·`MoveSectionDown` 은 **앞뒤 구역의 첫 문단 처음**으로 간다. 끝 구역에서 아래로,
첫 구역에서 위로는 제자리가 아니라 **그 구역의 처음**으로 물린다.

표본에 구역이 둘뿐이라 "앞 구역"과 "첫 구역"이 안 갈렸다. 그래서 방금 검증한
`BreakSection` 으로 시나리오 안에서 **구역을 하나 더 만들고** 가운데 구역에서 걸었다 —
마지막 구역 한가운데에서 위로 가면 그 구역 처음이 아니라 **앞 구역 처음**이 나온다.
검증한 액션이 다음 액션의 자가 된 셈이다.

두 가지가 게이트에 잡혔다:

- **구역 경계를 `document.sections` 칸막이로 세면 안 된다.** `BreakSection` 은 문단에
  `SectionDef` 를 얹을 뿐 `sections` 를 안 가르는데, 한글은 그 문단부터 새 구역으로 본다.
  칸막이로 세면 방금 만든 구역이 안 보인다 — **문단이 진 표식**으로 세야 한다.
- **셀 안에서 걸면 본문으로 나간다.** 어느 구역에 있었는지는 그 리스트를 담은 본문 문단으로
  친다.

판정: `p3-action-section` **68/68**.

### 4.48 쪽 번호 셋 — 자리표 글자를 두 번 세고 있었다 (2026-08-09)

`InsertPageNum`·`InsertCpNo`·`InsertTpNo`. 셋 다 사슬에 `atno` 하나를 더하고 스트림에서

### 4.50 `Action` 객체 — 반환 갈래가 메서드마다 다르다 (2026-08-09)

`CreateAction` 이 주는 객체로 일곱을 올렸다: `ActID`·`SetID`·`CreateSet`·`GetDefault`·
`Run`·`Execute`, 그리고 `CreateAction` 자신.

값이 아니라 **갈래**가 다르다는 것이 이 축의 함정이다. 실측:

| | 돌려주는 것 |
| --- | --- |
| `Run` | `1` |
| `Execute` | `true` |
| `GetDefault(셋)` | `1` |
| `SetID`(셋 안 쓰는 액션) | `""` |

하나로 뭉개면 시나리오는 통과하는데 호출 측이 `=== true` 로 재는 순간 어긋난다.

두 가지가 더 잡혔다. **`Execute` 는 셋이 필수다** — 없이 부르면 한글이 "필수 매개 변수입니다"
로 죽는다. 그리고 액션이 아닌 이름(`MovePos` 는 메서드다)에는 **객체를 안 준다**. 뒤엣것은
양쪽 다 실패하지만 오류 문구가 달라 하니스가 대조하지 못하므로 시나리오에서 뺐다 — 구현에는
남긴다(`ACTIONS` 에도 셋 이름에도 없으면 `null`).

판정: `p3-action-object` **17/17**. 원장 186 → **193/484**.

덤: `run_gate.py` 의 `--impl` **기본값을 새 호환 층으로** 바꿨다. 예전 기본값은 `legacy`(구
studio `hwpctl` 층)라 플래그를 빼먹으면 옛 층을 재고 전량 실패했는데, 로그 접두어가
`[hwpctl]` 로 다를 뿐이라 원인이 안 보였다. 옛 층은 이제 `--impl legacy` 로만 잰다.

같은 걸음으로 찾기 넷(`RepeatFind`·`ForwardFind`·`BackwardFind`·`ReverseFind`)도 쟀는데
**검색어가 없으면 넷 다 무동작**이다(캐럿·모드 불변, 반환 없음). 무동작을 근거로 올리면
아무 일도 안 하는 구현이 통과하므로 안 올린다 — 검색어를 심는 길(`FindDlg` 는 대화상자,
파라미터셋 항목 이름 미규명)이 먼저다.

### 4.51 줄 계열과 `InsertLine` — 잰 것과 안 올린 이유 (2026-08-09) — **미제출**

열 개를 하나씩 짧은 시한으로 걸어 봤다(멈추면 대화상자로 보고 곧바로 죽이는 방식). 대화상자에
걸린 것은 없었고, 관측은 이렇다:

| 액션 | 관측 |
| --- | --- |
| `DeleteLineEnd` | 캐럿부터 줄 끝까지 지움(문단 끝 7 → 3) |
| `DeleteLine` | 줄을 통째로 지우고 **문단이 하나 줄음**(14 → 13) |
| `InsertLine` | 8칸 컨트롤 하나를 끼움(문단 끝 7 → 15, 캐럿 +8) |
| `MoveLineBegin`·`MoveLineEnd` | 줄의 처음·끝으로 |
| `ToggleOverwrite`·`ViewZoom*`·`ReturnPrevPos` | 관측 없음 |

앞의 넷은 **줄 단위**라 §4.18 과 같은 벽이다 — 한 줄짜리 문단에서는 문단 연산과 구별되지 않고,
여러 줄에서는 한글이 파일을 열며 다시 나눈 줄을 따라간다. 한 줄 문단만 보고 올리면 "관측만 같은
다른 동작"이 된다.

`InsertLine` 은 다른 이유로 접었다. 끼우는 것이 **그리기 사각형**(`gso`·"사각형")인데, 그
기하(테두리·채우기·자리)를 지금 API 로는 관측할 수 없다. 좌표만 맞춰 8칸을 채우면 게이트는
초록인데 **저장본이 다른 문서**가 된다.

### 4.52 리스트 번호가 밀리던 뿌리는 **캡션**이었다 (2026-08-09)

§4.49 가 남긴 "사슬은 표본 의존" 을 파다가 리스트 번호 자체가 어긋난다는 것을 먼저 봤다.
각주 든 표본에서 리스트 **2번부터** 한글과 rhwp 가 다른 것을 가리킨다.

#### 큰 문서로는 못 푼다

그 표본은 사슬이 470개다. 거기서 규칙을 세우려다 두 번 헛짚었다. 그래서 **묶음이 들어 있으면서
사슬이 가장 짧은 표본**을 찾아 `samples/draw-group.hwp`(사슬 3개)로 옮겼다. 거기서는 차이가
여덟 개뿐이고 하나씩 읽힌다.

#### 첫 짐작은 틀렸다 — 그룹 자식이 아니다

한글 사슬에 rhwp 에 없는 `atno` 가 list 2 에 앉아 있길래 "한글은 묶음 **속으로** 들어가
자식 글상자에 리스트를 준다"고 보고 그렇게 구현했다. 그런데 그 문서의 묶음 자식 17개는
**전부 그림**이라 글상자가 하나도 없다 — 구현해도 list 2 가 안 생겼다.

부모를 직접 물었다(`SetPos(2,0,0)` → `MoveParentList`). 답은 **그 묶음 컨트롤 자신**(0/0/16)
이었고, 그 리스트는 가운데 정렬 한 문단에 자동 번호가 든 것이었다. **캡션**이다.

> 짐작한 기전(그룹 자식)과 실제 기전(캡션)이 관측 하나에 똑같이 들어맞았다. 부모를 물어보지
> 않았으면 틀린 규칙을 심은 채 초록을 봤을 것이다. 그룹 하강은 근거가 없으므로 **되돌렸다.**

#### 캡션은 세 곳에서 빠져 있었다

1. **리스트 표**가 캡션에 번호를 안 줬다 — 그래서 그 뒤 번호가 전부 밀린다.
2. **경로 만들기**(`cell_path_to_list`)가 `is_cell` 이 아니면 곧바로 포기했다 — 글상자
   리스트도 여태 못 닿고 있었다는 뜻이다.
3. **경로 풀기**(`cell_paragraph_at_path`)가 표만 알았다 — 그래서 캡션 문단에 닿아도 끝이 0.

셋을 고치니 `draw-group.hwp` 가 **37/37** 이 됐다. 덤으로 이름 둘도 실측으로 맞췄다:
묶음의 `UserDesc` 는 rhwp 가 "묶음" 이라 하는데 한글은 **"그리기"**, 자동 번호는
**"번호 넣기"** 이고 `CtrlCh` 는 **18**(`0x12`, 스트림 글자 코드)이다.

아직 못 잰 것: 글상자와 캡션을 **둘 다** 가진 개체의 앞뒤 순서, 그리고 **표 캡션**. 표본을
만나면 그때 잰다.

### 4.53 남은 속성 넷, 그리고 빈 문서도 구역 정의를 진다 (2026-08-09)

액션이 아닌 남은 항목(291 중 비-액션 110)을 훑어 **관측 가능한 것부터** 골랐다:
`CellShape`·`ParentCtrl`·`CurSelectedCtrl`·`Clear` 넷.

- **`ParentCtrl`** — 캐럿이 든 리스트를 **담고 있는** 컨트롤. 셀 안에서는 그 표, 본문에서는

- **`Clear`** 가 결함을 하나 드러냈다. 한글은 비운 문서에서 캐럿을 **16** 에 세우는데 rhwp 는
  0 이었다. 원인은 `createEmpty` 가 주는 빈 문서에 **구역 정의·단 정의가 없다**는 것 — 실제
  HWP 문서는 예외 없이 그 둘을 첫 문단에 진다.

  처음엔 `create_empty` 를 고쳤는데 **단위 시험 둘이 깨졌다**(`issue_1470_*`): `char_shapes`

  기준으로는 더 맞지만, 그 기대값을 내 변경에 맞춰 고쳐 쓰면 회귀를 덮는 짓이다. 되돌리고
  **`Clear` 만 번들 템플릿**(`createBlankDocument`)을 쓰게 했다 — 그 문서는 실물이라 둘을
  제대로 진다. 캐럿은 덤으로 **문단 경계 클램프**를 붙여 풀었다(`SetPos` 와 같은 규칙).

  > 남는 사실 하나: `createEmpty` 의 빈 문서는 실물 HWP 와 다르다. 이 캠페인 밖의 결함이라
  > 여기서 고치지 않고 적어만 둔다.

> 널을 돌려주는 자리는 시나리오에서 뺐다. 점 표기로 `null.CtrlID` 를 물으면 양쪽 다 실패하되
> **오류 문구가 달라** 하니스가 대조하지 못한다. 값이 서는 자리로만 증명한다.

(개요 없는 문단에서 `""` 뿐이라 판별력 없음), `SetCurFieldName`(필드 밖에서는 무동작).

판정: `p2-ctrl-props` **27/27**.

### 4.54 스캔 계열이 열렸다 — 규약은 잡았고 구현은 안 했다 (2026-08-09) — **미제출**

§4.32 가 "`InitScan` 인자 모양 미규명"으로 미뤄 둔 자리다. 실제로는 **인자 없이도 열린다.**

```
InitScan()            → true
GetText()             → [상태, 글]      ← 문서 끝까지 되풀이해 부른다
ReleaseScan()         → (반환 없음)
GetText()             → [101, ""]      ← 스캔을 닫은 뒤
```

`2026_oss_rst.hwp` 를 끝까지 돌린 실측(60회):

- 글은 **문단 단위**로 나오고 줄 끝이 `\r\n` 이다. **표 셀도 흐름에 든다**(표를 만나면 셀
  글이 차례로 나온다).
- 상태 코드는 `0`·`2`·`3`·`4`·`5`·`101` 이 나왔다. `101` 은 "스캔 안 열림"이 분명하다.
- `InitScan(0x0007, 0x0000)` 은 다른 범위를 잡는다 — 이 문서에서는 `[2, "\r\n"]` 하나만 주고
  곧바로 `[0, ""]` 로 마른다(블록이 없어서로 보인다).

#### 작은 문서로 다시 재서 굳힌 것 (2026-08-09 추가)

큰 문서에서 "본문을 다 훑고 셀로 간다"고 볼 뻔했다. 표 **둘**이 한 문단에 달린 작은 표본

 5 상태=2  "A12\r\n"  …

  "문단이 끝났는가"로 읽히다가 `table-001.hwp` 에서 어긋난다.

  스캔의 글이 항목마다 같다(줄 끝 표기만 `\n` 대 `\r\n`).

### 4.55 `GetTextFile` — 규칙 셋을 다 갈라 올렸다 (2026-08-09)

스캔이 열렸으니 같은 뿌리인 글 계열을 쟀다. 실측:

- **`GetTextFile("TEXT","")` 은 훑기와 같은 뿌리다** — 훑기가 주는 조각에서 **표식 항목**
  (구역·단 정의)만 빼고 각 조각이 줄 끝으로 끝나게 이어 붙이면 된다. 다만 **마지막 문단 뒤에는
  줄 끝을 안 붙인다**(오라클이 정확히 두 글자 짧다).
- `"saveblock"` 은 블록이 없으면 아무것도 안 준다.
- **`GetTextBySet`·`SaveDocument` 는 이 COM 개체에 없다**(`AttributeError`).
- `GetPageText(쪽, 0)` 는 답한다 — 쪽 단위라 조판 합의가 먼저다.

처음엔 표본 넷 중 셋만 맞았다. 어긋난 것을 파서 규칙 셋을 더 찾았다.

**① CP949 밖 글자는 `&#N;` 수치 참조가 된다.** `◦`(U+25E6)는 바뀌고 `€`·`①`·`㈜` 는 그대로다.
글자를 통제해서(빈 필드에 시험 문자열을 넣고 재기) `ḁ`·`Ǆ`·`ↀ`·`⿰`·`◦` 는 escape,
`€`·`①`·`가` 는 그대로임을 확인했다 — **여덟 글자 예측 전수 적중**. 판정은 표를 손으로 적지
말고 `encoding_rs::EUC_KR` 로 **실제 인코딩해 본다**(CP949 는 EUC-KR + 마이크로소프트 확장이라
"없을 것 같은데 있는" 글자가 많다). 훑기(`GetText`)는 escape 하지 **않는다** — 이 형식만의 규칙이다.

**② 인라인 개체 앞 조각은 줄을 안 만든다.** 표·글상자처럼 **리스트를 여는** 개체 앞 조각은
줄이 되고, 수식처럼 줄 안에 있는 개체 앞 조각은 안 된다.

**③ 빈 누름틀은 안내문을 글로 낸다.** 한글은 파일을 열며 빈 필드에 안내문을 채우고 그 글이
스트림에도 든다(좌표 셈의 `guide_units` 가 이미 세던 것이다). 안 넣으면 서식 문서의 글이
통째로 짧아진다 — 영수증 서식에서 1756 대 1844 였다.

셋을 넣으니 표본 여섯이 전량 일치한다. 판정: **56시나리오 2822/2822**, 원장 200 → **201/484**.

**2026-08-10 코드페이지 독립 재검증.** Windows ACP 65001에서는 한컴 COM 자체가
`GetTextFile("TEXT","")`의 한글을 U+FFFD와 깨진 문자열로 반환했다. 같은 문서의
`GetTextFile("UNICODE","")`는 원문 4,030자를 손실 없이 반환했다. 따라서 코어는 공통 문서
순서를 한 번만 조립한 뒤 `TEXT`에는 위 CP949 수치 참조를, `UNICODE`에는 원문을 내보낸다.
live Oracle의 본문 완전일치는 `UNICODE`로 고정하고, `TEXT` escape 규칙은 Rust와 npm
계약 테스트로 계속 보호한다. 이는 기존 `TEXT` 계약을 폐기한 것이 아니라 환경에 따라 달라지는
ANSI 전송층을 Oracle 판정에서 분리한 것이다.

### 4.56 파라미터셋 축 — 이름 49종과 멤버 7종 (2026-08-09)

원장에서 가장 큰 미개척 덩이가 `ParameterSet` 이었다. 파 보니 **두 갈래가 섞여** 있었다 —
셋 **이름**(`BorderFill`·`CharShape`·`PageDef` …)과 셋 객체의 **멤버**(`Count`·`IsSet` …).

**이름은 한글에게 하나씩 물었다.** `CreateSet(이름).SetID` 가 아는 이름이면 그 이름을, 모르면

### 4.57 글자 모양 액션은 대화상자다, 그리고 액션 전수 스윕 (2026-08-09)

`CharShapeHeight`·`CharShapeWidth`·`CharShapeSpacing` 은 **대화상자를 띄운다** — 한꺼번에

#### 창을 열거해 보니 절반은 진짜 대화상자였다 — 두 번 틀렸다 (2026-08-09)

작업지시자가 "**HANG 69개도 화면 찍어 확인해봐**" 라고 해서 전수로 돌렸다. 69장을 눈으로
읽는 대신 **Win32 로 창을 열거**해 기계로 판정했다(`hang_windows.ps1`).

1차 답은 "**추가 창 0**" 이었다. 그런데 창 **개수**를 보니 1 개인 것이 78, **19~42 개**인 것이
31 이었다. 개수가 뛰는데 "추가 창 0" 이라는 것은 앞뒤가 안 맞는다 — **내 필터가 틀린 것**이다.

한글의 창 클래스는 `HwndWrapper[Hwp.exe;;<GUID>]` 라 **클래스 이름으로는 문서 창과 대화상자를
못 가른다.** 제목으로 갈라야 한다. 고쳐서 31개를 다시 돌리니 **전부 제목이 잡혔다**:

| 액션 | 대화상자 |
| --- | --- |
| `CharShape`·`CharShapeHeight`·`Width`·`Spacing` | 글자 모양 |
| `ParagraphShape` | 문단 모양 |
| `PageSetup` | 편집 용지 |
| `TableCreate` | 표 만들기 |
| `InsertFile` | 문서 끼워 넣기 |
| `InputCodeTable` | 문자표 |
| `PageNumPos` | 쪽 번호 매기기 |
| `PageHiding` | 감추기 |
| `HeaderFooter` | 머리말/꼬리말 |
| `Hyperlink`·`InsertHyperlink` | 하이퍼링크 |
| `InsertFieldTemplate` | 필드 입력 |
| `DocSummaryInfo` | 문서 정보 |
| `PictureInsertDialog` | 그림 넣기 |
| `ParaNumberBullet` | 글머리표 및 문단 번호 |
| `Print` | 인쇄 |
| 나머지 11(각주·미주·줄 지우기·문단 번호 계열) | 제목이 `한글` — 이름 없는 대화상자 |

**그래서 갈래가 둘로 갈린다.** 대화상자를 띄우는 **31**, 대화상자 없이 호출만 안 끝나는 **78**.
둘 다 이 하니스로는 판정 못 하지만 이유가 다르다 — 앞엣것은 사람이 눌러야 끝나고, 뒤엣것은
누를 것조차 없다.

> **같은 실수를 세 번 했다.** 빈 문단에 자를 댄 것(§4.45), 맥락 없이 액션을 건 것(§4.57),
> 그리고 클래스로 창을 거른 것. 전부 **관측 도구가 못 보는 것을 "없다"로 읽은 것**이다.
> 관측이 0 을 줄 때는 "정말 없는가"보다 **"내 잣대가 볼 수 있는 것인가"** 를 먼저 물어야 한다.
> 이번에는 창 **개수**가 그 모순을 드러냈다 — 0 이라면서 22 개가 있을 수는 없다.

#### 화면을 찍어 보니 "대화상자"가 아니었다 (작업지시자 제안)

멈춘 액션을 **대화상자**라고 적어 왔는데, 작업지시자가 "COM 을 보이게 띄우고 화면을 확인하며
진행할 수 없느냐"고 물어 그렇게 해 봤다. `HWPCTRL_VISIBLE=1` 로 창을 띄우고
`tools/hwpctrl_compat/screenshot.ps1` 로 화면을 찍어 읽었다.

화면에는 **대화상자가 안 보였다.** 창은 문서를 그대로 보여 주고 한글 프로세스는
`Responding=True` 인데 호출만 안 끝난다. 그래서 갈래 이름을 `HANG` 으로 바꿨다 — 관측한
사실은 "시한 안에 안 끝난다" 뿐인데 보지도 않고 "대화상자"라고 적었기 때문이다.

> 이 절의 결론은 위 §에서 **다시 갈렸다.** 화면에 안 보였을 뿐 창은 만들어져 있었고, 창을
> 열거하니 31개는 진짜 대화상자였다. 화면을 보는 것만으로는 부족했고 **창을 세어야** 했다.

실무적 차이가 있다: 대화상자라면 "닫아 주면 된다"는 우회를 떠올리지만, 대화상자가 없으면
그 길이 아예 없다. 틀린 이름은 틀린 우회를 부른다.

    # 멈춘 자리를 눈으로 보는 법
    $env:HWPCTRL_VISIBLE=1
    Start-Process python -ArgumentList "tools\hwpctrl_compat\runner_ocx.py","<시나리오>",...
    powershell -File tools/hwpctrl_compat/screenshot.ps1 -Out output/poc/hwpctrl/shot.png

> 이 표를 만들다 **스윕 결과를 스스로 덮은 사고**가 있었다. `--limit 4` 스모크 테스트가 같은
> 기본 출력 경로에 써서 151행이 4행이 됐다. 로그에 줄마다 남아 있어 복원했지만, 그 전까지
> 분류기는 "대화상자 0" 이라는 **거짓 그림**을 그렸다. 산출물 경로를 공유하는 도구는 스모크
> 테스트에도 `--out` 을 따로 줘야 한다.

#### 개체를 골랐다고 다 같은 개체가 아니다 — 크기 조절 넷 (2026-08-09)

무동작으로 남은 63 중 **33이 `ShapeObj`** 였다. 개체 맥락으로 이미 돌렸는데도 그랬다. 이유는
그 맥락이 고르는 첫 개체가 hongbo 의 **표**라서다 — 옮기기·크기·뒤집기는 **그리기에만** 먹는다.
`drawing` 맥락(그리기 개체를 고른 상태)을 더해 다시 돌리니 여섯이 살아났다.

관측창도 좁았다. 오라클의 개체 `Properties` 는 **32항목**인데 이쪽은 넷만 읽고 있었다. 위치는
`VertOffset`·`HorzOffset`·`VertRelTo`·`HorzRelTo`·`VertAlign`·`HorzAlign` 로 따로 있다.

**`ShapeObjResize*` 넷을 올렸다.** 걸음은 **283 HWPUNIT**(≈1mm)로 일정하고, 무엇보다
**결정적이다** — 같은 값을 두 번 읽어도 같고 되돌리면 그대로 되짚는다(25704 → 25987 → 26270
→ 25987). §4.47 의 표 크기 조절이 읽을 때마다 달라 판정 불가였던 것과 정반대다. 방향 이름은
**가장자리를 미는 쪽**이라 `Left`·`Up` 이 줄인다.

#### 앞머리 셈을 고쳤다 — 자리차지 개체 사이엔 공백이 한 칸씩 있다

아래 §4.57 에서 못 올린 옮기기의 뿌리를 잡았다. 자를 대기 전에 **캐럿이 어디 서는지**부터
쟀더니 규칙이 드러났다(`mix-shape-01`, 자리차지 그리기 셋):

| 잰 것 | 값 |
|---|---|
| 앵커(`GetAnchorPos`) | **16 · 25 · 34** — 8 이 아니라 **9** 씩 |
| 캐럿이 서는 자리(`SetPos` 스냅) | **24 · 33 · 42** |
| 본문(`GetTextFile`) | **`"  "`** (공백 둘) |
| `SelectText(0,24,0,25)` | 진짜로 한 글자를 잡는다 |

즉 스트림은 `[secd 0-7][cold 8-15][선 16-23][공백 24][사각형 25-32][공백 33][타원 34-41]` 이다 —
**개체 사이의 한 칸은 실재하는 공백 글자**다. rhwp 도 그 공백을 들고 있다(`cc=43, text_len=2`).
틀린 것은 `leading_anchor_pos` 뿐이었다: **컨트롤 개수 × 8** 로만 셈해 40 을 주고, 그래서
`SetPos(0,0,0)` 이 문단 끝으로 밀려 `SelectCtrlFront` 가 아무것도 못 골랐다.

고침은 스트림을 믿는 것이다 — 앞머리 컨트롤이 있으면 **첫 글자의 스트림 자리**를 쓰되, 개수
셈이 그보다 앞서 나갈 때만 갈아끼운다. 맞붙은 문단에서는 두 값이 같아 아무것도 안 바뀐다.

**0 은 안 믿는다**는 단서가 하나 필요했다. 구역 나누기로 **새로 생긴 문단**은 `char_offsets` 가
0 부터 다시 매겨져 앞머리 컨트롤을 안 담는다 — 그대로 두면 `p3-action-break2`·`p3-action-section`
이 6건 어긋난다(실제로 어긋났고, 그 신호를 보고 조건을 좁혔다). 그 문단에서는 개수 셈이 맞다.

판정: `p3-objmove` **24/24**(오라클 실측). 65개 시나리오 3018/3018 · `cargo test --lib
document_core` 454 통과. 원장 275 → **279/484**.

#### 조판 의존 축을 다시 열었다 — §4.18 의 벽은 **안내문 문서에 한정**이었다

§4.18 은 줄 이동을 "조판 엔진의 일"이라며 접었다. 그 근거는 영수증 서식 하나였다 — 한글이 빈
누름틀에 **안내문을 채워** 조판 입력 자체가 rhwp 와 달랐던 문서다. 안내문이 없는 맑은 문서로
다시 재니 결론이 뒤집힌다.

`para-001` 의 여덟 줄에서 한글이 답한 줄 시작·끝이 **저장된 `LineSeg::text_start` 와 전부
같다**: 66 · 116 · 166 · 216 · 264 · 313 · 366. 조판을 다시 할 필요가 없다. 두 자리만 다른데
규칙이 있다 — 첫 줄의 시작은 `text_start` 0 이 아니라 **앞머리 자리차지 뒤**(16)이고, 마지막
줄의 끝은 **문단 끝**이다.

rhwp 에는 이미 `getLineStarts` 경로가 있었고 **첫 줄만 안 잘라서** 0 을 주고 있었다. 한 줄
고쳐 `MoveLineBegin`·`MoveLineEnd`·`MoveSelLineBegin`·`MoveSelLineEnd` 넷이 통과했다(65/65).
같은 눈금으로 `DeleteLineEnd`·`DeleteLine` 둘도 열렸다(19/19) — 캐럿에서 줄 끝까지 46자를
지우고 `Undo` 로 되돌아온다.

**한계는 그대로 안고 간다.** 이 눈금은 저장값이라 문단을 고치면 낡는다. 한글은 열면서 다시
나누므로 고친 문단에서는 갈릴 수 있다. 지금 재는 것이 연 그대로의 문서라 맞는 것이지, 조판을
맞춘 것이 아니다.

#### 대화상자 계열 여섯 — 맥락을 맞춰 갈래를 확정한다

§4.70 에서 "짐작으로 넣었던 여섯"을 `무동작(맥락 더 필요)` 으로 미뤄 뒀다. 그 맥락을 만들어
마저 쟀다. **셋으로 갈린다.**

**둘은 맥락에서 그대로 멈춘다.** 글만 있는 문단에서는 몇 초에 끝나 "안 멈춘다"고 볼 뻔했다:

| 건 것 | 글만 있는 문단 | 맞는 맥락 |
|---|---|---|
| `ShapeObjDialog` | 무동작 | 개체를 고르면 **STALL** |
| `TablePropertyDialog` | 무동작 | 칸 블록을 잡으면 **STALL** |

(표 컨트롤을 고른 상태에서는 `TablePropertyDialog` 가 2.5초에 끝난다 — 칸 맥락이라야 뜬다.)

**셋은 창조차 안 뜬다.** `FindDlg`·`ReplaceDlg`·`SpellingCheck` 는 몇 초에 끝나고, 한글을
**보이게 띄워 창을 세어도 문서 창 하나뿐**이다(대화상자를 여는 액션들이 19~42개를 보이던 것과
대조된다). COM 으로 걸면 조용히 아무 일도 안 한다 — `관측창 없음` 이다.

**마지막 하나도 쟀다.** `ModifyHyperlink` 는 캐럿이 **하이퍼링크 글자 위에 있을 때만** 대화상자를
연다. 표본은 이미 있었다 — `KTX.hwp` 의 문단 205 에 `%hlk` 필드가 든다
(`cmd="http\://www.nipa.kr);1;0;0;"`). 그 문단 안에서 자리를 옮겨 가며 걸었더니 이렇게 갈린다:

| 자리 | 결과 |
|---|---|
| 10 · 50 · 70 | 2.5초에 끝난다(무동작) |
| **30 · 40** | **STALL** — 두 번 걸어 두 번 다 |

링크 글자(`www.nipa.kr`)가 그 언저리다. **한 문단 안에서 자리 하나 차이로 갈린다** — 문단만
맞추고 "무동작"이라 적었으면 또 틀릴 뻔했다.

곁들여: 하이퍼링크는 **필드 API 로 안 잡힌다.** `GetCurFieldName` 이 링크 위에서도 `""` 이고
`GetFieldList` 도 비어 있다(이름 없는 `%hlk` 라서다). 그래서 "캐럿이 링크 위인가"를 API 로는
확인할 수 없고, **멈추는 자리를 찾는 것**이 유일한 판별이었다.

곁들여 창 조사 도구를 고쳤다. `--names` 가 **HANG 으로 알려진 이름만** 걸러 보고 있어서, "안
끝나는 줄 알았지만 아니었던" 이름의 창을 볼 수가 없었다 — 갈래를 다시 매기려면 바로 그 이름을
봐야 한다. 이제 준 이름을 그대로 본다.

상한 318 → **312**. 이번에도 늘린 것은 점수가 아니라 **지도의 정확도**다.

이로써 **도달 가능한 것 중 음·양력 넷만 남는다**(308/312).

#### 쪽 그림 만들기를 올린다 — 픽셀은 **호스트가 만든다**

`CreatePageImage` 의 계약을 끝까지 쟀다(`20250130-hongbo`, 4쪽):

| 건 것 | 답 |
|---|---|
| 인자 **정확히 둘**, 쪽 번호 0~3 | `true` — 파일이 실제로 생긴다 |
| 쪽 번호 4·9(쪽수 밖) | `false` |
| 쪽 번호 **음수** | **예외** |
| 없는 폴더·빈 경로 | `false` |
| 인자 하나·셋 | `false` |

쪽 번호는 **0부터**다. 한글은 확장자를 **`.bmp` 로 강제**하고(`.png` 를 줘도 `.bmp` 로 쓴다)
**33×47 4bpp 미리보기**를 앉힌다. 쪽마다 내용이 다르니(md5 가 갈린다) 빈 그림이 아니다.

**픽셀은 이 층이 만들지 않는다.** 래스터라이저(`resvg`·skia)는 네이티브 전용이고, 그것을 WASM
쪽에 끌어들이면 studio 가 함께 무거워진다 — 한 항목 때문에 공용 산출물을 부풀릴 일이 아니다.
그리고 rhwp 는 원래 그렇게 생겼다: **코어가 쪽을 그려 주면 호스트가 화면·파일로 옮긴다**
(studio 는 CanvasKit 으로 한다). 그래서 고리를 하나 더 뒀다 — 코어에서 그 쪽의 SVG 를 받아
`onCreatePageImage({path, pageNo, svg})` 로 넘기고, 파일로 어떻게 앉힐지는 호스트가 정한다.
고리가 없으면 `false` 다(못 한 것을 했다고 하지 않는다).

**그래서 픽셀과 파일 갈래는 약속하지 않는다** — 대조하는 것은 위 표의 반환값이다. 하니스의
호스트는 래스터라이저가 없어 그 SVG 를 그대로 쓴다. 그 경계를 코드 주석과 여기에 적어 둔다.

판정: `pG-pageimage` **10/10**. 파일도 오라클과 똑같이 **둘만** 생겼다. 원장 307 → **308/484**.

#### 쪽 배경 그림은 **성공하는 길이 없다** — 없는 파일과 같은 값을 준다

`InsertPicture` 가 절대 경로로 풀렸으니 옆에 있는 `InsertBackgroundPicture` 도 그럴 줄 알았다.
아니다. 다 걸어 봤다.

- **인자 꼴 열넷**(경로만, 경로+플래그 1~5개, 앞에 `true`/`false`/`0`/`1` 을 붙인 꼴) — 하나면
  `필수 매개 변수` 로 죽고 **둘 이상이면 전부 `false`**.
- **맥락**: 본문, 셀 안, 칸 블록(모드 3), 블록 넓히기, 표 고른 상태 — 전부 `false`.
- **그림 갈래**: jpg, png — 전부 `false`.
- **한글이 스스로 만든 bmp**(`CreatePageImage` 로 뽑은 1058바이트 파일) — 그것도 `false`.

마지막이 결정적이다. 파일이 분명히 있고 한글이 방금 쓴 것인데도 실패한다. 그리고 **없는 파일도
같은 `false`** 라 실패 이유조차 안 준다 — 무엇을 고쳐야 할지 알려 주는 신호가 없다.

곁들여 `CreatePageImage` 는 **정말 파일을 쓴다**(1058바이트 bmp 가 생겼다). `true` 가 빈말이
아니라는 뜻이라, "아직 안 이은 것" 딱지가 더 단단해졌다 — 호스트 파일 **쓰기** 고리를 하나 더
놓으면 열린다.

#### 글자 블록 서식이 끝 글자를 빠뜨리던 것 — 그리고 내가 적어 둔 원인이 또 틀렸다

`Undo` 를 재면서 "rhwp 는 블록 위에서도 `CharShapeBold` 가 안 먹는다"고 적고 시나리오를 탭
기준으로 옮겼다. 다시 재 보니 **틀렸다. 서식은 제대로 먹는다** — 자리 16~20 이 `Bold` 1 이다.

어긋난 것은 **끝 한 글자**였다. `SelectText(0,16,0,21)` 뒤 굵게를 걸면

| | 굵어진 자리 |
|---|---|
| 한글 | 16 ~ **21** (캐럿 22 에서 0 으로 떨어진다) |
| rhwp | 16 ~ 20 |

블록 자체(`GetSelectedPos`)는 양쪽이 `16~21` 로 같다. 갈린 곳은 **서식이 덮는 범위**이고,
한글은 블록의 **끝 글자도 포함**한다. 한 줄 고쳤다.

"안 먹는다"는 관측은 캐럿이 블록 끝(21)에 서 있어서 나온 것이었다 — 그 자리는 rhwp 기준으로
굵어지지 않은 첫 글자다. **한 자리만 보고 "안 먹는다"고 적으면 이렇게 된다.** 이번에는 자리를
여섯 개 훑어 갈랐고, 그 훑기를 게이트 시나리오(`pI-charshape-block`)로 남겼다.

#### 삽입이 좌표 자취를 안 남기던 것 — 이슈 #4347 로 올리고 고쳤다

`InsertPicture` 를 올리며 "앞머리 컨트롤이 있는 문단에서는 앵커가 문단 끝(406)으로 나온다"고
적고 시나리오를 다른 문단으로 옮겨 뒀다. 그 자리를 파 보니 **rhwp 코어 결함**이었다.

먼저 앞서 적은 원인이 틀렸다. `char_offsets` 가 0 에서 시작한다고 썼는데 **아니다** — 재 보니
`para-001` 문단 0 은 스트림 16 → 글자 0 으로 **정확하다**. 짐작을 원인이라 적었던 것이다.

진짜 원인은 삽입 쪽이다. 파서는 확장 컨트롤을 만나면 8 코드 유닛을 건너뛰고 **보이는 글자를
안 남긴다.** 그래서 컨트롤의 자리는 `control_text_positions()` 가 `char_offsets` 의 **갭**으로
되짚는다. 삽입이 그 갭을 안 만들면 그 컨트롤은 자리를 잃고 **문단 끝 폴백**으로 떨어진다.

```
insertPicture(0, 0, char_offset=4, …)
  넣기 전  스트림 16→글자 0, 20→4, 24→8      글자 수 4030
  넣은 뒤  스트림 16→글자 0, 20→4, 24→8      글자 수 4030   ← 그대로다
  사슬     secd 0 · cold 8 · gso(그림) 406                  ← 한글은 20 이다
```

그러라고 만든 헬퍼(`shift_for_inline_control_insert`)가 이미 있고 **수식·각주·새 번호는
쓰는데 그림·표·도형만 안 썼다.** 빠진 자리를 채우는 일이지 새 규약이 아니다.

**고친 범위를 좁혔고, 그 뒤 나머지를 실측으로 갈랐다.** 처음에는 "본문만 고치고 셀·표는 이슈에
남긴다"였는데, 재 보니 **나머지 셋은 애초에 맞았다**:

| 경로 | 사슬이 답한 자리 | 판정 |
|---|---|---|
| 그림 · 본문 문단 | ~~406(문단 끝)~~ → **20** | 결함이었고 고쳤다 |
| 그림 · 셀(표 sibling) | `표@0 그림@8` | 맞다 |
| 표 · `createTableEx` 인라인 | `표@20` | 맞다 |
| 도형 · `createShapeControl` | `사각형@20` | 맞다 |

`control_text_positions()` 의 폴백 셈(`앞선 맨 글자 수 + 8 × 앞선 컨트롤 수`)이 **글자 없는 표
문단**에서는 정답과 같아진다 — 컨트롤이 맞붙어 있으니 `ci × 8` 이 곧 그 자리다. 이슈에
"셋 다 헬퍼를 안 쓴다"고 적었는데, **헬퍼를 안 쓰는 것과 좌표가 틀린 것은 다른 문제**였다.

관측되는 결함이 없는 자리를 "일관성"을 위해 건드릴 이유가 없어 되돌렸다. 셋 다 고쳤을 때
실제로 글자처럼 그림 둘의 줄 넘김 테스트가 깨졌다.

**남겨 뒀던 글상자 경로는 표본을 만들어 재니 진짜 결함이었다.** 글상자는 표 문단과 달리
**글자를 담아서** 폴백 셈이 정답이 안 된다. 글자 일곱짜리 글상자의 자리 3 에 그림을 넣어 보면:

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 반환 `logicalOffset` | 8(문단 끝) | **4** |
| 사슬 자리 | `그림@7` | **`그림@3`** |
| 스트림 대응 | 4→글자 4 (갭 없음) | 3→3 · **11→3** · 12→4 (갭 8칸) |

표본은 코어로 만들었다 — `createShapeControl(shapeType:"textbox")` 로 글상자를 세우고
`insertTextInCell` 로 글자를 넣으면 그 경로가 그대로 선다. 회귀 테스트
(`inserted_picture_in_a_textbox_keeps_its_place_too`)도 그 꼴로 세웠고, 고침을 빼면 정확히
붉다(3 이어야 할 자리가 11).

회귀는 두 겹이다 — 단위 테스트(`issue_4347_…`, 고치기 전 코드에서 정확히 붉다)와, 시나리오를
**결함이 있던 문단 0 으로 되돌린** `pF-insertpicture` 다. 우회로 피해 가던 자리를 다시 밟는다.

#### 그림 넣기를 올린다 — 호스트 파일 읽기 고리를 하나 놓았다

규격이 **경로**를 받는 API 는 이 층에서 곤란하다. OCX 는 바탕화면에서 돌아 경로가 곧 파일이지만
이 층은 브라우저에서도 돌기 때문이다. 그래서 호스트 고리를 하나 더 뒀다 —
`createHwpCtrl({ wasm, onSave, onReadFile })`. 고리가 없으면 그 API 는 **아무 일도 안 한다**
(있는 척하지 않는다). 하니스는 node 의 파일 읽기를 그대로 준다.

잰 계약을 그대로 옮겼다. 컨트롤은 `gso`/`그림`, 속성 셋은 `ShapeObject`(항목 33), 크기는
**1픽셀 = 75 HWPUNIT**(96 DPI — 164×152 인 jpg 이 12300×11400), 배치는 **글자처럼**, 캐럿은
**8** 밀린다.

옮기면서 걸린 것 셋:

- **속성 셋 이름이 컨트롤마다 다르다.** 표는 `Table`, 그리기·그림은 `ShapeObject` 인데 이 층은
  늘 `Ctrl` 을 줬다. 두 갈래만 실측했으므로 그 둘만 고치고 나머지는 그대로 뒀다.
- **코어는 그림을 자리차지로 넣는다.** studio 는 끌어다 놓으므로 그쪽이 맞다 — 코어 기본값을
  건드리지 않고, 이 API 가 넣은 그 컨트롤만 `treatAsChar` 로 되돌린다.
- **그림 크기를 스스로 재야 한다.** 코어의 `insertPicture` 는 크기를 받기만 한다. JPEG·PNG·
  GIF·BMP 머리말만 읽는 작은 함수를 뒀다.

**한 자리는 못 맞췄고 그 이유를 적어 둔다.** 앞머리에 구역·단 정의가 있는 문단(`para-001` 의
문단 0)에 넣으면 앵커가 20 이어야 하는데 406(문단 끝)이 나온다. 그 문단의 `char_offsets` 가
**0 에서 시작해** 앞머리 컨트롤을 안 담고 있어서, 갭으로 컨트롤 자리를 배정하는
`control_text_positions` 가 어긋난다 — `leading_anchor_pos` 에 "0 은 안 믿는다" 단서를 달게 한
그 약점과 **같은 뿌리**다. 앞머리 컨트롤이 없는 문단에서는 앵커까지 맞으므로 시나리오를 그쪽에
두고, 이 한계를 여기 적는다.

판정: `pF-insertpicture` **14/14**. 원장 306 → **307/484**.

#### `관측창 없음 38` — 큰 둘은 **버텼고**, 하나는 내 잘못이었다

이번에는 반증할 새 창을 들고 갔다. §4.66 에서 **개체 돌기가 z 순서로 돈다**는 것을 알았으니,
앞뒤 순서를 바꾸면 **돌기 차례가 달라져야** 한다. 그것이 z 순서의 관측창이다.

걸어 보니 안 달라진다. `타원` 을 맨 앞으로 보내도, 맨 뒤로 보내도 돌기 차례는 `선 → 사각형 →
타원` 그대로다. **앞뒤 순서 여섯은 그대로 닫힌다** — 이번에는 창을 새로 들고 가서 확인한 것이라
전보다 단단하다.

표 크기 조절 열여섯도 다시 봤다. 전에는 `CellShape`(실은 **표**의 셋)만 봤으니, 이번에는 표
**컨트롤의 `Properties`** 로 봤다. `TableResizeCellRight` 를 세 번, `TableResizeDown` 을 한 번
걸어도 `Width` 47622 · `Height` 62181 이 꿈쩍도 안 한다. **그대로 닫힌다.**

**하나는 내가 틀렸다.** `InsertPicture` 를 "멀쩡한 파일을 줘도 무동작"이라고 적었는데, 그때 준
것이 **상대 경로**였다. 절대 경로를 주면 된다 — 컨트롤을 돌려주고 사슬에 `그림` 이 생기며
캐럿이 **8** 밀린다(20 → 28 → 36 → 44). `Open` 이 상대 경로로 되니까 다 될 줄 알았던 것이
화근이다.

rhwp 에도 `insertPicture` 가 있는데 **경로가 아니라 바이트**를 받는다. 호스트 파일 읽기 고리가
하나 필요하니 막힌 것이 아니라 **아직 안 이은 것**이라 갈래를 옮긴다. `InsertBackgroundPicture`
는 절대 경로를 줘도 `false` 라 그대로 둔다.

상한 317 → **318**. 이 갈래는 앞의 둘과 달리 **대체로 버텼다** — 얻은 것은 하나다.

#### `안 끝남 39` — 뿌리는 맞았는데 **내 결론이 성급했다**

같은 의심으로 가장 큰 갈래를 팠다. 분류기가 쓰는 `sweep_kinds()` 에 이런 줄이 있었다:

```python
kinds = {name: "HANG" for name in FORBIDDEN}
```

금지 목록에는 실제로 멈추는 것뿐 아니라 **이름만 보고 대화상자겠지 싶어 넣은 것들**
(`FindDlg`·`ReplaceDlg`·`ShapeObjDialog`·`TablePropertyDialog`·`SpellingCheck`·`ModifyHyperlink`)
이 섞여 있었다. 그 여섯이 **한 번도 안 재인 채** "안 끝남"으로 세어졌다. 짐작을 목록에 넣으면
그 짐작이 지도가 된다 — 뿌리는 여기다.

39 을 하나씩 걸어 보니 **전부 몇 초 만에 끝났다.** 그래서 "이 갈래가 통째로 틀렸다"고 적었는데,
**그것이 성급했다.** 걸어 본 자리가 글만 있는 문단이라 표·개체 액션이 **아무 데도 안 닿았던**
것이다. 맥락을 맞춰 다시 거니 그대로 멈춘다:

| 맥락을 맞춰 다시 건 것 | 결과 |
|---|---|
| `TableSplitCell`(칸 블록) | **STALL** |
| `CellFill`(칸 블록) | **STALL** |
| `TableInsertRowColumn`(칸 블록) | **STALL** |
| `ModifyCtrl`(개체 고름) | **STALL** |
| `SpellingCheck`(글만) | OK 2.8초 |

이 캠페인이 세 번 적어 둔 그 함정을 **내가 또 밟았다** — 빈 곳에 자를 대면 눈금이 안 보인다.
다행히 판정 전에 맥락을 맞춰 봤다.

남는 결론은 둘이다.

1. **뿌리 고침은 유효하다.** 안 잰 것을 `HANG` 으로 채우지 않는다 — 실측으로 확인된 것만
   `HANG`, 한글을 죽이는 셋은 `KILLS` 로 따로 센다.
2. **짐작으로 넣었던 여섯만 갈래가 바뀐다.** 제대로 스윕하니 글만 있는 문단에서 **전부
   무동작**이라 `무동작(맥락 더 필요)` 으로 간다. TSV 에 실측 시한 초과가 남아 있는 33 은
   그대로다.

상한 311 → **317**. 앞의 두 갈래와 달리 여기서는 **큰 것을 뒤집지 못했다** — 얻은 것은 뿌리
하나와 여섯이다.

#### `UI 전용 16` 도 딱지가 틀렸다 — 아홉은 **아예 없는 API** 였다

음·양력에서 딱지 하나가 틀린 것을 보고 같은 의심으로 `UI 전용` 을 팠다. 열여섯 중 **아홉이
`AttributeError`** 다 — 이 COM 개체에 아예 없다: `ShowCaret`·`ShowRibbon`·`ShowStatusBar`·
`ShowToolBar`·`ShowHorizontalScroll`·`ShowVerticalScroll`·`SetToolBar`·`IsSpellCheckCompleted`·
`CreatePageImageEx`. "반환 말고 볼 것이 없다"가 아니라 **부를 수가 없다**.

나머지에는 실측 이유를 붙였다.

- **`GetMousePos(x, y)`** 는 `MousePos` 셋(항목 5)을 주는데 `X`·`Y` 가 **물리 마우스 자리**다
  (1743332 · 1539150). 부를 때마다 다르고 이 층에는 마우스가 없다.
- **`ViewZoom*`** 은 관측창이 있다 — `ViewProperties.ZoomRatio` 가 보통 **100**, 쪽 맞춤
  **37**, 폭 맞춤 **139** 으로 움직인다. 그런데 뒤 둘은 **창 크기·DPI 가 정하는 값**이다.
  `ViewZoomNormal` 만 상수라 그것 하나로는 셋을 가를 수 없다.
- **`ToggleOverwrite`** 는 진짜로 먹는다 — `KeyIndicator` 의 `over` 가 **1 ↔ 0** 으로 뒤집힌다.
  그런데 그 값을 보는 창이 `KeyIndicator` 뿐인데 그 API 는 `pos` 때문에 통째로 못 올린다(§4.67).
  **한 값 때문에 다른 항목까지 막히는** 꼴이다.
- **`CreatePageImage`** 는 인자 **둘**이고 `true` 를 준다(셋 이상이면 false). rhwp 는 쪽을 그릴
  수 있으니 이것도 막힌 것이 아니라 **아직 안 이은 것**이라 `자료 없음(막힌 것 아님)` 으로 옮겼다.

상한이 다시 310 → **311** 로 올라간다. 두 갈래를 파서 얻은 것이 항목이 아니라 **지도의 정확도**
였다 — 막혔다고 적어 둔 것 중 열넷이 사실은 다른 이유였다.

#### 음·양력 넷은 **머신 의존이 아니었다** — 딱지가 틀렸고 상한이 거짓이었다

메인테이너 재검토를 기다리는 동안 남은 갈래 중 근거가 가장 얇아 보이는 것을 다시 팠다.
음·양력 넷을 `머신 의존` 으로 세고 있었는데, 그 딱지의 근거는 "설치된 자료에 달렸다"는
**짐작**이었다. 재 보니 아니다 — **결정적인 표 조회**다.

잰 계약을 그대로 적어 둔다(다음 사람이 구현할 수 있게):

| | `SolarToLunar(y, m, d)` | `LunarToSolar(y, m, d, leap)` |
|---|---|---|
| 반환 | `[ok, 음년, 음월, 음일, 윤달인가]` | `[ok, 양년, 양월, 양일]` |
| 인자 | 셋이면 된다(넷째부터는 무시) | **넷을 다 줘야** 한다(셋이면 `필수 매개 변수`) |
| 범위 밖 | `[true, 0, 0, 0, false]` — **`ok` 가 참인 채** 0 | `[false, 0, 0, 0]` — `ok` 가 거짓 |

**둘이 범위 밖을 알리는 방식이 다르다.** `SolarToLunar` 는 성공이라고 말하면서 0 을 준다 —
`ok` 만 보고 믿으면 안 된다.

표가 덮는 범위는 **음력 1841 ~ 2043** 이다. 양력 1841-01-01 은 0 을 주고 1841-02-01 은
답한다(그 사이가 음력 1841 년 초하루다). 위쪽은 양력 2043-12-31 까지 답하고 2044-01-01 부터
0 이다. 윤달도 제대로 갈린다 — 2025 년 음력 6월 6일이 평달이면 양력 6/30, 윤달이면 7/30 이다
(2025 년에 실제로 윤6월이 있다).

없는 날짜는 **거르지 않고 넘긴다**: 2026-02-29(없는 날)에도 답을 준다.

그래서 이 넷은 **막힌 것이 아니라 rhwp 에 음력 표가 없을 뿐**이다. 구조적으로 막힌 것으로 세면
상한이 거짓이 된다 — 갈래를 `자료 없음(막힌 것 아님)` 으로 옮기고 **상한을 306 → 310 으로
되돌린다**. 지금 306, 남은 4.

**다만 표를 오라클에서 뽑아 만들면 검증이 순환이 된다** — 한글로 만든 표를 한글로 검증하는
꼴이라 초록의 뜻이 없다. 표는 한국천문연구원 같은 독립된 출처에서 와야 하고, 그때 이 넷이
열린다. 그래서 이번에는 **재고 적기까지만** 하고 구현은 안 했다.

#### `KeyIndicator` 의 `pos` 는 글자 수가 아니라 **x** 다 — 상한을 채우고 닫는다

`KeyIndicator` 는 네 값 중 셋이 이미 재현된다. `prnpageno` 는 쪽 시작 목록으로, `line` 은 쪽
시작부터 lineseg 를 세어(실측 세 곳에서 16 · 10 · 4 정확히 일치), `ctrlname` 은 캐럿의 컨트롤로
나온다. 남은 것이 `pos` 인데, 처음엔 **고정 표**처럼 보였다 — 한글 3 · 공백 1 로 놓으면 초기
세 점이 정확히 맞는다(0 → 1, 5 → 12, 41 → 4, 42 → 5).

그래서 한 글자씩 밟아 보니 무너진다:

```
'전' +3   '사' +3   '각' +3   '지' +3   '대' +2   '를' +3
' '  +1   ' '  +2   ' '  +1   ' '  +2
',' +1    '‘' +1    '’' +1
```

**같은 글자가 3이었다 2였다 하고 공백도 1이었다 2였다 한다.** 고정 표라면 있을 수 없다 —
이것은 **캐럿의 x 를 어떤 단위로 나눠 반올림한 값**의 무늬다(단위는 한글 글자 폭의 약 1/3).
작은 구간에서 정수로 딱 떨어져 보였던 것은 반올림이 아직 안 쌓였기 때문이다.

그래서 `KeyIndicator` 는 **글자 폭(advance)이 한글과 같아야** 재현된다. `pos` 하나 때문에 넷을
다 못 올린다 — 이 API 는 값을 한 덩이로 주기 때문이다. 캐럿 들여쓰기
(`ParagraphShapeIndentAtCaret`, 캐럿 x 에서 나오는 −23648)도 같은 부류라 둘을 `글자 폭 정밀도`
갈래로 따로 센다. 조판 정밀도를 올려서 열리는 것이 **아니다** — 글꼴 계측의 일이다.

이로써 **도달 가능한 상한 306 을 채웠다(306/306).** 남은 178 은 전부 이유가 붙은 갈래다.

#### 개체 사이 돌기 — "일곱 중 셋만 돈다"의 정체는 **쪽**이었다

`ShapeObjNextObject`·`ShapeObjPrevObject` 는 오래 "세 개만 돌고 차례를 모르겠다"로 남아 있었다.
개체가 셋뿐인 표본(`mix-shape-01`)에서 재니 깨끗하다 — 사각형 → 타원 → 선 → 사각형 으로 돌고
`Prev` 는 그대로 되짚는다. 그런데 표가 섞인 문서(`20250130-hongbo`, 개체 일곱)에서는 문단
**0 → 5 → 2 → 0** 만 돌았다.

캐럿을 다른 쪽에 두고 다시 걸어 보니 답이 나왔다:

| 걸기 시작한 곳 | 도는 것 |
|---|---|
| 1쪽(문단 0) | 0 → 5 → 2 → 0 |
| 2쪽(문단 24) | 24 ↔ 25 |
| 3쪽(문단 26) | 26 ↔ 29 |

**쪽 안에서만 돈다.** 문서 전체를 도는 것이 아니다 — "일곱 중 셋"은 그 쪽에 놓인 개체가 셋이라
그랬던 것이다. 쪽 안의 차례는 문단 순서가 아니라 **z 순서**다(0 → 5 → 2 가 그 증거다).

`mix-shape-01` 이 깨끗해 보였던 것은 개체 셋이 **한 쪽에 있고 z 순서와 사슬 순서가 같아서**였다.
쉬운 표본만 보면 규칙을 못 본다 — 어려운 표본이 규칙을 드러낸다.

쪽을 조판기에 물으므로 **조판 정밀도를 물려받는다**(쪽 이동과 같다).

판정: `p9-nextobj` **41/41**(첫 시도). 원장 303 → **305/484**.

#### `아직 안 잼` 15 를 전부 재고 넷을 올린다

한 번도 안 재 본 채로 남아 있던 15 를 훑었다. 넷이 올라가고 여섯이 **아예 없는 API** 로,
다섯이 **관측창 없음**으로 갔다.

**올린 넷.**

- `SetTextFile` — 이름과 달리 **캐럿 자리에 안 넣는다. 문서 맨 앞에 붙인다.** 캐럿을 20 에 두고
  `가나다` 를 넣으면 본문이 `가나다오호라…` 가 되고, 다시 30 에서 `라마` 를 넣으면
  `라마가나다오호라…` 다. 캐럿은 제자리를 지키므로 **넣은 글자 수만큼 밀린다**(20 → 23,
  30 → 32). 반환은 성공 여부가 아니라 **1** 이다. 처음 구현에서 `insertText` 의 셋째 인자를
  스트림 자리로 착각해 글 한가운데(16)에 꽂혔다 — 그 인자는 **글자 번호**다. 이 좌표 계약은
  `UNICODE` 형식에서 코드페이지와 무관하게 재현됐다. ACP 65001의 한컴 `TEXT` 형식은 한글
  세 글자를 6만큼 옮기므로 host 간 기준으로 사용하지 않는다.
- `InsertCtrl` — 빈 `Table` 셋을 주면 한글은 **5행 5열**을 넣는다(칸 리스트 2~26 으로 25 개,
  `TableColEnd` 가 6 · `TableColPageDown` 이 22 라 5×5). 캐럿은 8 만큼 밀린다. 표의 기본
  크기(30610 × 6410)는 표 만들기 쪽 규칙이라 이 API 의 계약이 아니어서 대조하지 않는다.
  반환 객체의 **형 이름**까지 봐야 맞는다 — 규격은 `CtrlCode` 라 부르는데 실물은
  **`IDHwpCtrlCode`** 다. 형 이름도 관측되는 표면이라 그쪽에 맞췄다.
- `ViewProperties` — `SetID`·`Count`(12)·`IsSet` 과 정규화 가능한 항목 둘
  (`ZoomType` 5 · `ZoomRatio` 100). 한컴에서 `ViewZoomNormal`을 먼저 실행해 확대율을
  고정한다. `OptionFlag`는 버전·사용자 상태에 따라 0과 8192가 모두 관측돼 알려진 값에서
  제외한다.
- `EngineProperties` — `SetID` 와 `Count`(12) 뿐이다.

**여기서 정직하게 적어 둘 것.** 두 속성은 `Count` 가 12 인데 환경과 무관하게 이름·값이
밝혀진 항목은 `ViewProperties` 둘, `EngineProperties` 는 **하나도 없다.** 후보 이름 70여 개를 훑어도 더 안
나왔고 이 컨트롤에는 **항목을 열거하는 길이 없다.** 아는 것만 담고 개수는 실측값을 그대로
주기로 했다 — 모르는 이름을 지어내 채우는 것보다 낫다고 봤다.

**없는 API 여섯** — `AddEventListener`·이벤트 셋(`OnMouseLButtonDown`·`OnMouseLButtonUp`·
`OnScroll`)·`PopupDialog`·`InsertDocument` 는 전부 `AttributeError` 다. 웹 규격에는 있어도
이 COM 개체에는 없다.

**관측창 없는 다섯** — `InsertPicture` 는 멀쩡한 그림 파일을 줘도 아무 일도 안 하고(사슬 그대로),
`InsertBackgroundPicture` 는 멀쩡한 파일에도 **false** 다. `ReplaceAction` 은 `true` 를 주면서
바꾼 대로 안 돈다(`MoveDocEnd` 를 `MoveDocBegin` 으로 바꿔도 문서 끝으로 간다). `Insert` 는
문자열도 셋도 조용한 무동작, `GetHeadingString` 은 문서 셋에서 전부 빈 문자열이다.

곁가지로 **`SetPos` 는 없는 리스트를 주면 문서 처음(0/16)으로 되돌린다**는 것을 확인했다 —
칸 수를 세는 잣대로 썼다.

#### 무동작으로 남아 있던 여섯을 전부 닫는다 — 그리고 앞선 판단 하나를 바로잡는다

**`CellShape` 은 칸의 셋이 아니라 표의 셋이다.** `SetID` 가 **`Table`** 이고, 폭이 제각각인
표(4717 · 6010 · 6576)에서 어느 칸에서 읽어도 `Width` 가 **44778** 로 같다. 항목 수도 37 로
어디서나 같다.

이것이 §4.60 의 판단을 바로잡는다. 거기서 "칸이 전부 같은 폭이라 나눌 것이 없다"고 적었는데,
같았던 것은 칸이 아니라 **표**였다 — 애초에 칸 폭을 읽은 적이 없다. 결론(나눔은 못 올린다)은
같지만 **이유가 달랐다.**

폭이 다른 표(`2010-01-06`)를 찾아 다시 재니 진짜 이유가 나온다. 나눔을 걸면 표 값이 움직이긴
하는데(높이 30352 → 31679), **같은 표를 연달아 읽어도 값이 다르다**(31679 → 33171). §4.47 이
본 "한 박자 늦게 답한다"가 여기서도 그대로다. 정답지가 안 서니 못 올린다.

나머지 넷은 두 갈래다.

- **`CellBorder`·`CellBorderFill` 은 한글을 죽인다.** 걸고 나면 COM 서버가 사라져 그 뒤 호출이
  전부 RPC 오류다. 탐침이 10분을 넘겨 한글을 죽여 풀었다 — `TableStringToTable` 과 같은 부류라
  스윕 금지 목록에 함께 넣었다. **죽이는 이름을 적어 두는 것이 이 목록의 값이다.**
- **`AllReplace`·`BackwardFind` 는 숨은 상태에 매달려 있다.** 찾을 말이 **대화상자에 남은
  상태**인데 API 로는 정할 길이 없다. 상태가 없으면 `AllReplace` 는 예외로 죽고
  `BackwardFind` 는 조용히 아무 일도 안 한다(캐럿 그대로, 글자 그대로). 세로 이동의 x 닻과
  같은 계열이라 `숨은 상태` 로 묶는다.

이로써 **`무동작(맥락 더 필요)` 갈래가 0 이 됐다.** 남은 것은 전부 이유가 적힌 갈래다.

#### `TableColPage*` 는 이름이 거짓말이다 — 쪽과 무관하다

이름에 `Page` 가 붙어 있어 쪽 계열로 묶어 두었는데, 재 보니 **쪽과 아무 상관이 없다.**
147행 3열 표에서:

| 시작 칸 | `TableColPageDown` | `TableColPageUp` |
|---|---|---|
| 0행 1열(list 3) | **146행 1열**(441) | 0행 1열(3, 제자리) |
| 2행 2열(list 10) | **146행 2열**(442) | **0행 2열**(4) |
| 6행 0열(list 20) | **146행 0열**(440) | **0행 0열**(2) |

**같은 열의 마지막 칸·첫 칸**이다. 두 번째로 걸어도 안 움직인다(끝에서 제자리). 표가 네 쪽에
걸쳐 있는데도 한 번에 마지막 행으로 가니, 쪽 단위가 아니라 **열 단위**다.

조판이 필요 없다 — 격자만 있으면 된다. 표 밖에서는 아무 일도 하지 않는다.

판정: `p7-tablecolpage` **47/47**(첫 시도). 원장 297 → **299/484**.

이름만 보고 갈래를 정하면 안 된다는 사례를 하나 더 얻었다. 스윕이 이것을 `MOVED`(리스트 3 →
441)로 잡아 두고도 "쪽 이동"으로 분류해 두었는데, **그 큰 뜀이 오히려 쪽이 아니라는 신호**였다.

#### 쪽 이동 6종 — 조판기가 답한다

줄과 달리 **쪽 경계는 파일이 안 알려 준다.** 저장 vpos 되돌아감으로 `20250130-hongbo` 의 네 쪽
중 둘(15/122 · 26/0)은 짚히는데 넷째(30/0)는 안 짚힌다 — 표가 쪽을 넘는 자리이고 **셀 안
`vpos` 는 셀 기준**이라 되돌아감이 안 남는다. 그래서 rhwp 조판기에 물었고, WASM 조판이 CLI 와
같은 답(4쪽)을 낸다는 것을 먼저 확인했다.

항목 갈래를 가려야 한글과 같아진다:

| 쪽의 첫 항목 | 캐럿이 서는 자리 |
|---|---|
| 문단이 이어짐(`PartialParagraph`) | **그 줄의 시작**(15/122) |
| 표가 이어짐(`PartialTable` 이어짐) | 본문에 자리가 없다 — **그 쪽에 보이는 첫 칸 안** |
| 그 밖 | 그 문단의 시작(첫 쪽은 앞머리 자리차지 뒤) |

이동 규칙도 전부 실측이다 — `End` 는 **다음 쪽 시작 바로 앞**(같은 문단이면 −1, 문단이 바뀌면
앞 문단의 끝)이고, `Up` 은 **지금 쪽의 시작에 서 있을 때만** 앞 쪽으로 간다. 다음 쪽의 첫 자리가
본문이 아니면 `Down` 은 그 **칸 안으로 들어가고** `End` 는 **제자리**다. 둘이 다르다.

판정: `p6-pagemove` **129/129**(오라클 실측, 4쪽·표 이어짐 포함). 원장 291 → **297/484**.

**이 여섯은 조판 정밀도를 물려받는다.** 둘째 문서(`2026_oss_rst`, 6쪽)로 교차검증하니 61 중
59 가 맞고, 남은 둘은 이어지는 표 쪽에서 한글이 칸 **(9행, 1열)** 로 들어가고 rhwp 가
**(9행, 0열)** 로 들어가는 자리다. 그 문서는 게이트가 아니라 **탐침**으로 남겨
(`probes/p6-pagemove2.json`) 어디서 갈리는지 짚어 둔다.

> **정정(#4359).** 이 차이를 "rhwp 는 행 경계로 자르고 한글은 행 안에서 자른다"로 읽고 이슈를
> 열었는데 **틀렸다.** 한글에 직접 물으니 9행의 **두 칸이 모두 3쪽**이다(`KeyIndicator` 의
> `prnpageno`) — 한글도 행 경계에서 자른다. 게다가 이 표는 `쪽나눔 = RowBreak`(행 경계에서만
> 나눔)로 **선언돼** 있어 rhwp 가 선언대로 하고 있었다.
>
> 같은 문서 6쪽에서는 **한글도 (7행, 0열)을 골라 rhwp 와 일치**한다. 한 문서 안에서 한 번은
> 같고 한 번은 다르니 "자르는 낟알"로는 둘을 함께 설명할 수 없다. 남은 것은 **그 쪽의 첫
> 캐럿을 어느 칸으로 치느냐**는 훨씬 작은 규칙이고, 아직 못 밝혔다. 이슈는 반증을 적고 닫았다.
>
> `startCut` 이 비었다는 것을 근거로 삼은 것이 화근이다 — **그 값은 "행 안에서 안 잘랐다"는
> 뜻이지 "한글은 잘랐다"는 뜻이 아니다.** 한쪽만 보고 상대의 행동을 지어냈다.

#### 세로 이동 — 막는 것이 둘이다(숨은 x 닻 + 글자 폭)

앞에서 "x 기하라 못 연다"고 적었는데, 더 파 보니 **그 앞에 벽이 하나 더 있다.** 같은 입력을
반복해 봤더니 시작 자리를 아무리 바꿔도 **늘 같은 곳으로 간다**:

```
시작  60 MoveLineDown -> 0/109      시작  20 MoveLineDown -> 0/109
시작  20 MoveLineDown -> 0/109      시작  30 MoveLineDown -> 0/109
시작  45 MoveLineDown -> 0/109      시작  16 MoveLineDown -> 0/109
```

**`SetPos` 는 세로 이동이 딛는 x 를 안 바꾼다.** 그 x 는 문서를 연 뒤 **첫 자리 지정**이 정하고
그 뒤로는 `SetPos` 로 안 움직인다 — 첫 자리를 20 으로 잡고 열면 그 세션의 답이 전부 **69**,
60 으로 잡고 열면 전부 **109** 다(따로 확인).

그래서 §4.62 에서 "오프셋이 아니라 x 를 지킨다"고 본 것도 실은 **앞선 세로 이동이 남긴 x** 를
보고 있었던 것이다. 관측이 흔들린 것이 아니라 **잣대가 숨은 상태를 안 보고 있었다**.

막는 것을 정리하면 둘이고, 둘 다 넘어야 한다:

1. **숨은 x 닻** — API 로는 한 번(첫 자리)밖에 못 정하고 읽을 수도 없다.
2. **글자 폭** — 닻을 맞춰도 x → 글자 번호가 폰트 advance 로 갈린다(첫 자리 20 → 줄 1 의 **3**,
   60 → **43** 으로 한 칸씩 어긋난다). 이 저장소가 재 온 글자 폭 발산(HY 계열 ASCII 25% 과대
   따위)을 생각하면 정확히 맞출 수 있는 자리가 아니다.

`관측창 없음` 이 아니라 **`숨은 상태 + 정밀도`** 라 따로 적는다. 조판 정밀도만 올려서는 안
열린다 — 닻을 읽거나 정하는 길이 API 에 없기 때문이다.



같은 자료로 위아래 이동도 될 줄 알았는데 아니다. 처음엔 맞아 보였다 — 120 → 170 → 220 처럼
줄 안 오프셋(4칸)을 지키며 내려간다. 그런데 경계를 재니 무너진다:

| 건 것 | 갔어야(오프셋 유지) | 실제 |
|---|---|---|
| 60 에서 `MoveLineDown` | 110 | **98** |
| 66 에서 `MoveLineUp` | 16 | **48** |
| 120 에서 `MoveSelLineDown` | 170 | **198** |

오프셋이 아니라 **가로 x 를 지킨다.** 글자 폭이 줄마다 달라(한자·괄호·라틴) 같은 x 가 다른
글자 번호로 떨어진다. 맞추려면 글리프 advance 까지 한글과 같아야 하는데, 이 저장소가 재 온
픽셀 일치율은 94% 대다 — 캐럿 자리를 정확히 맞출 수 있는 정밀도가 아니다.

곁가지로 확인한 것: 마지막 줄에서 `MoveLineDown` 은 **다음 문단으로 넘어간다**(문단 1 자리 0 →
문단 2 자리 1). 문단 안 좌표가 아니라 문서 기하 위를 걷는다 — §4.18 이 셀에서 본 것과 같다.

**남은 조판 의존 29건의 갈래**: 세로 이동 12(x 기하) · 쪽 이동 8(쪽 나눔) · 화면·스크롤 8
(OCX 뷰포트, rhwp 에 없음) · `KeyIndicator`·`GetPageText`(쪽 기하). 앞의 둘은 조판 정밀도를
올리면 언젠가 열리고, 화면·스크롤은 이 층에 뷰포트가 없어 구조적으로 막힌다.

#### 표 둘은 잴 수 없다 — 하나는 자취가 없고 하나는 한글을 죽인다

`TableStringToTable` 은 **한글을 죽인다.** 걸고 나면 COM 서버가 사라져 그 뒤 호출이 전부 RPC

정답지를 만들 수 없으니 못 올린다 — 그리고 **다시 걸지 않는다**. 위험한 이름은 이렇게 적어

#### 뒤집기는 창이 없고, 칸 나눔은 **잴 표본이 없다**

뒤집기 넷은 개체 속성 **36항목** 어디에도 안 적힌다 — `HorzFlip`·`VertFlip`·`Flip` 어느 이름도
값이 없고 폭·높이·자리도 그대로다(뒤집기는 크기를 안 바꾸니 당연하다). 앞뒤 순서와 같은 판정
으로 `관측창 없음` 에 넣는다.

칸 나눔은 사정이 다르다. 표본 둘(`별표2`·`table-001`)의 칸이 **전부 같은 폭**이라(47622 / 42168)
나눌 것이 없다. 같은 폭 위에서 걸면 42168 → **42169** 로 1 만 움직이는데, 이것은 나눔이 아니라
반올림 흔적이다. 그 1 을 맞추려면 한글의 나눗셈·반올림까지 맞춰야 하고, 그것은 이 표본으로는
확인할 수 없다. **칸 폭이 다른 표본이 있어야 재는 축**이라 그렇게 적어 둔다 — "무동작"이 아니다.

#### 글상자는 빈 채로 생긴다 — 그리고 자식 리스트 안의 고르기 규칙이 드러났다

글상자 붙이기·떼기는 캡션과 같은 창으로 보인다. 다만 **빈 채로** 생긴다(붙이면 캐럿이

본문으로 되돌아간다 — 그 되돌아감이 뗐다는 판별자다.

여기서 규칙 하나가 새로 나왔다. **자식 리스트 안에서 `SelectCtrlFront` 를 부르면 그 리스트를
담은 개체가 잡힌다.** rhwp 는 본문 자리로 되짚어 엉뚱한 개체(직선)를 골랐다 — 캐럿의 문단·자리가
본문 것이 아닌데 본문 좌표로 읽었기 때문이다. 이것을 고치자 그 뒤 셋(고른 개체·뗀 뒤 캐럿·
리스트가 사라졌는가)이 한꺼번에 맞았다.

#### 되돌리기는 **액션으로 고친 것만** 담는다

`Undo` 가 스윕에서 무동작으로 나온 이유는 단순하다 — **고치기 전에 걸었다.** 고친 뒤에 걸면
또렷하게 보인다: `InsertTab` 으로 20 → 28 로 간 캐럿이 `Undo` 뒤 **20** 으로 돌아오고, 세 번
끼운 뒤 네 번 되돌리면 세 번째에서 멈춘다(더 되돌릴 것이 없다).

한 가지 갈렸다. **API 로 고친 것은 안 담긴다.** `SetCurFieldName` 으로 이름을 바꾼 뒤 `Undo` 를
걸어도 이름이 그대로다(`FieldExist` 도 그대로). 되돌리기 목록에 들어가는 것은 `Run` 으로 건
액션뿐이다.

코어에 되돌리기가 없어 호환 층이 **문서를 통째로 찍어** 쌓는다. 찍는 매체는 **HWPX** 다 —
HWP5 저장은 무손실이 아닌 것으로 밝혀져 있고(그림 스트림이 빠진다) HWPX 왕복은 10k 표본에서
IR 차이 0 으로 닫힌 축이라, 되돌리기가 문서를 조용히 깎지 않으려면 이쪽이어야 한다. 캐럿과
고르기도 함께 찍는다 — 글자만 되돌리고 캐럿을 두면 실측(`InsertTab` 되돌리기)과 어긋난다.

여기서 **별개 틈** 하나가 드러났다. 처음엔 굵게로 재려 했는데 rhwp 는 블록 위에서도
`CharShapeBold` 가 안 먹는다(`블록이 없다 — 대기 서식은 아직 다루지 않는다`). 검증된 토글은
셀 블록 쪽이었다. 되돌리기와 무관한 축이라 시나리오를 탭 기준으로 옮기고 그 틈은 남겨 둔다.

#### 캡션은 빈 채로 생기지 않는다 — 붙이는 순간 `그림 ` + 번호가 들어 있다

앞머리 셈을 고치니 캡션 두 종도 잴 수 있게 됐다. 붙이면 캐럿이 **캡션 리스트 안**으로 들어간다
(list 2, pos **12**). 그 12 가 무엇인지 자리 지도를 떠서 알아냈다 — `SetPos` 를 0~13 으로 훑으면
0·1·2·3 은 그대로 서고 **4~10 이 전부 11 로** 간 뒤 11·12 가 다시 선다:

| 자리 | 무엇 |
|---|---|
| 0–2 | 글자 `그`·`림`·공백 |
| 3–10 | 번호 컨트롤 **8칸** |
| 11 | 공백 하나 |

**한글은 빈 캡션을 만들지 않는다.** 개체 갈래와 무관하게 말머리는 `그림` 이다(사각형에 붙여도
그렇다). 떼기는 고르기를 **안 푼다**(모드 4 그대로) — 잠그기가 푸는 것과 반대다.

**못 옮긴 규칙 하나를 남긴다.** 컨트롤 한가운데를 찍었을 때 한글은 다음 글자 자리로 미는데,

자리표 글자가 있는 문단에서는 한글이 다르게 민다. 아직 안 밝힌 규칙이라 흉내내지 않고, 그

#### 옮기기는 규칙까지 알아냈지만 못 올렸다 — 앞머리 자리차지 셈이 갈린다

옮기기(`ShapeObjMove*`)는 그리기 맥락에서도 무동작이었다. 그 개체가 **글자처럼** 배치라 자유롭게
못 움직이기 때문이다. 자리차지 개체(`samples/mix-shape-01.hwp`)로 옮겨 재니 규칙이 나왔다:

- 걸음은 **56 HWPUNIT**(≈0.2mm)로 일정하고 **결정적**이다(23040 → 23096 → 23152, 되돌리면
  그대로 되짚는다). **크기 조절의 283 과 다르다** — 같은 개체 액션이라고 같은 걸음일 것이라
  넘겨짚으면 틀린다.
- 관측창은 `Properties` 의 `HorzOffset`·`VertOffset` 뿐이다. 옮기기는 **`CurSelectedCtrl` 을
  놓으므로**(잠금과 같은 꼴) 사슬로 읽어야 한다. 그리고 사슬 번호를 박아 읽으면 **다른 개체**를
  보게 된다 — 이 표본에서 고른 것은 사슬 3(사각형)인데 2(선)를 읽고 있었다.

그런데 **rhwp 는 이 표본에서 아무 개체도 못 고른다.** `SetPos(0,0,0)` 도 `SetPos(0,0,24)` 도

세어 40 까지 민다. 한글은 24 에 세운다(그래서 사각형@24 를 고른다).

**앞머리 자리차지를 세는 규칙이 한글과 다르다** — 좌표 축의 별개 결함이고 `leading_anchor_pos`
는 곳곳이 딛고 선 함수라 이 자리에서 손대지 않는다. 구현(`move_control_at`, 걸음 56)과 탐침

#### 파라미터셋 고치기 멤버 — 되읽을 자리가 없어 부름 규약만 잰다

`아직 안 잼 26` 중 셋·배열 멤버 9종은 **문서가 필요 없어** 먼저 팠다. 그런데 관측이 반쪽이다.

**`CreateSet` 은 부를 때마다 새 빈 셋을 준다.** `SetItem("Height",1000)` 한 다음 줄에서
`Item("Height")` 를 읽으면 `null` 이고 `Count` 는 0 이다. 상태가 남는 셋(`HParameterSet`)이
있나 뒤졌지만 이 OCX 에는 **없다**(전 마디 `AttributeError`). 그래서 **고친 결과를 되읽을 창이
없다** — 잴 수 있는 것은 반환값과 부름 규약뿐이다. 그 한계를 알고 올린다.

그래도 규약 쪽에서 세 가지가 나왔다.

- **`RemoveAll` 은 인자를 하나 받는다.** 규격에는 없는데 인자 없이 부르면 `필수 매개
  변수입니다` 로 **죽는다**. 값이 무엇인지는 못 가렸다(0 이든 1 이든 같다). 그래도 *없으면
  죽는다*는 판별되므로 그대로 옮겼다.
- **`IsEquivalent` 는 셋 ID 만 본다.** 둘 다 빈 CharShape 끼리는 `true`, CharShape ↔ ParaShape
  는 `false`. 담긴 항목은 안 본다.
- **`Merge` 는 늘 `true`** 다. 셋 ID 가 달라도 `true` — 성공 여부를 가리는 값이 아니다.
- **배열의 `Clone` 은 죽는다**(서버에서 예외 오류). 셋 쪽 `Clone` 은 멀쩡한데 배열만 그렇다.
  규격이 아니라 실물을 옮기는 자리라 **죽는 것까지** 옮겼다.

오류 대조는 **한 방향으로만** 판별한다는 점도 적어 둔다 — 판정자가 "양쪽 모두 예외"를 일치로
보기 때문에, 오라클이 죽는 자리에서 rhwp 가 안 죽으면 걸리지만 그 반대는 안 걸린다.

판정: `p4-setmutate` **20/20**. 원장 263 → **272/484**.

#### 이름 바꾸기와 블록 위치 — 인자 수가 규격과 다르다

`SetCurFieldName` 은 **인자 넷을 다 줘야 한다.** 하나·둘·셋으로 부르면 `필수 매개 변수입니다`
로 죽는다. 규격에는 뒤 셋이 선택으로 적혀 있는데 실물은 아니다. 넷을 주면 `true` 를 주고
이름이 실제로 바뀐다 — `GetCurFieldName`·`GetFieldList`·`FieldExist` 셋 다 따라온다. 되읽을 창이
있는 몇 안 되는 고치기 API 라 왕복(`pt_nm` → `새이름` → `pt_nm`)까지 넣었다. **17/17**.

`GetSelectedPosBySet` 은 셋 둘에 담아 주고 **블록이 있는가**를 돌려준다. 담긴 값은 못 읽는다
(위와 같은 이유) — 판별되는 것은 반환값뿐이라 그것만 대조한다. **10/10**.

그 자리에서 블록 잡는 법 둘을 배웠다.

- **`SelectText(0,0,0,5)` 는 `true` 를 주면서 아무것도 안 잡는다.** 이 문서의 글자는 **16**
  부터라(앞은 구역·단 정의) 0–5 는 글자가 없는 구간이다. `true` 만 보고 잡혔다고 여기면
  또 빈 곳에 자를 대는 것이다. 글자 범위(16–21)를 주면 잡힌다.
- **`Cancel` 은 COM 에 없다**(`AttributeError`). 블록을 푸는 것은 액션(`Run`)이다.

`Insert` 는 문자열을 줘도 셋을 줘도 **조용한 무동작**이다(캐럿도 글자도 안 변한다). 죽지도
않아서 판별자가 없다 — 못 올린다. `GetHeadingString` 은 문서 셋에서 전부 `""` 라 양성 사례를
못 찾았다. 빈 값끼리 맞춰 올리는 것은 안 한다.

- **나눔은 진짜 무동작이었다.** 잰 칸 둘이 이미 **같은 폭**(47622/47622)이라 `Distribute*` 가
  할 일이 없다. 또 빈 곳에 자를 댄 것이다 — 이번엔 재기 전에 알아챘다.
- **조절 16종은 `CellShape` 에 안 비친다.** 블록을 풀고 다시 들어가 읽어도 47622 그대로다.
  §4.47 의 "한 박자 늦는다"보다 나쁘다 — 늦는 게 아니라 **안 온다**.

**앞뒤 순서 6종은 어떤 창에도 안 비친다.** 사슬이 안 바뀐다(`선`·`사각형`·`타원` 순서가

`ZOrder`·`ZOrderType`·`Order` 어느 이름으로도 값이 없다. **관측창 부재**로 닫는다 — 파일에는
분명 적히겠지만, 이 층이 대조하는 것은 API 반환이라 파일로 가르는 것은 이 게이트의 잣대가

**글꼴 돌리기 2종은 머신 의존이다.** `CharShapeNextFaceName` 은 잘 돌아간다 — Pretendard →

순서다. 다른 컴퓨터에서는 다른 답이 나온다. 여기서 초록을 만들 수는 있지만 그 초록은

`DeleteField` 는 캐럿이 누름틀 안(`GetCurFieldName` = `pt_nm`)인데도 지워지지 않는다
(`FieldExist` 그대로). 판별자가 없어 못 올린다.

#### 시나리오가 Windows 한 대를 전제로 적혀 있었다 (2026-08-09, #4274 리뷰 2차)

Linux 공식 게이트가 붉었다. 79개 3,458호출 중 **3개 시나리오 13호출**이 오류였다. 갈래는
셋인데 뿌리는 하나다 — **시나리오가 실행 기계를 하나로 가정했다.**

**1. 경로.** Linux 에서 `C:\Users\...\s1.jpg` 는 "못 여는 경로"가 아니라 **그냥 그런 이름의 상대
경로**다. `InsertPicture` 가 조용히 실패하고 뒤따르는 여덟 호출이 `MissingApi` 로 무너졌다.
`pG-pageimage` 는 더 나쁘다. "없는 폴더"를 재려던 `C:\없는폴더xyz\a.bmp` 가 Linux 에서는 **멀쩡한
파일 이름**이라 `false` 여야 할 자리가 `true` 였는데, 자체 검사가 반환값을 안 보니 그대로 `OK` 로
셌다. 저장소 작업본에 그 이름의 쓰레기 파일까지 남았다.

시나리오가 경로를 **이름으로** 적고 러너가 제 플랫폼 값으로 풀게 했다(`paths` + `{"$path": …}`,
`{repo}`·`{out}` 토큰). Windows 갈래는 오라클이 지금까지 쓴 경로 **그대로** 둬서 정답지가 안
흔들린다. 산출은 `{out}` 아래로 내려 작업본을 안 더럽힌다.

**2. 일부러 죽는 호출.** `SetCurFieldName` 인자 부족 셋, `RemoveAll()`·배열 `Clone()` 둘.
검사를 무르게 하는 것은 답이 아니다 — 그러면 진짜 오류도 함께 통과한다. 시나리오가 **미리
선언**하게 했다(`expectError`). 선언은 면제가 아니라 계약이다: 안 죽어도 실패, 딴 문구로 죽어도
실패, `MissingApi` 로 죽으면 선언했든 말든 실패다. 선언 없이 양쪽이 죽은 자리는 이제 `MATCH` 가
아니라 `ERROR_UNDECLARED` 다 — 1차 리뷰에서 `MissingApi` 를 막은 것과 **같은 모양의 구멍**이었다.

오라클 쪽 오류 **문구는 안 쟀다.** 안 잰 것을 적어 두는 대신 `"ocx": null` 로 남겼다 — 그러면
"죽었는가"까지만 보고, 뒷사람이 Windows 에서 재서 그 자리에 넣으면 그때부터 문구까지 대조된다.

**3. 반환값을 보는 자리.** 경로가 플랫폼마다 갈리면 인자는 더 이상 공통 닻이 아니다. 그래서
시나리오가 **기대 반환값**(`expect`)을 적고, Linux 자체 검사와 Windows 오라클 대조가 **같은 한
값**을 보게 했다.

판정: 80개 시나리오 3,478호출, Linux 게이트 **초록**. 원장 308/484 그대로다(새 시나리오는 이미
올린 항목을 다시 밟는다).

### 4.19 "관측창 없음" 의 전제가 절반 무너졌다 — 저장본을 안 열어 봤다 (2026-08-10)

`관측창 없음` 갈래에 이렇게 적어 두었다: *"파일에는 적히지만 이 게이트가 대조하는 것은 API

#### 왜 여태 안 보였나 — `ir-diff` 가 그 필드를 안 본다

손으로 쌓은 화이트리스트라 그 필드들을 아예 안 볼 뿐이었다(간접 지표를 관측으로 착각하는 함정).

`diagnostics::ir_field_sweep` 은 `Debug` 파생 기반 **전수** 비교기라 이 사각지대가 없다.
라이브러리에만 있고 부를 길이 없어 `rhwp ir-sweep <A> <B> [--json]` 으로 냈다.

#### 차분끼리 견준다 — 바탕이 다른 것을 상쇄한다

**잡음 바닥은 0 이다** — 액션 없이 두 번 저장하면 차이가 하나도 없고, `SelectCtrlFront`

### 4.20 뒤집기는 재기만 하고 접었다 — 표시 비트 규칙이 안 선다 (2026-08-10)

§4.19 로 열린 축의 두 번째 후보였다. 앞뒤 순서(여섯)는 올렸고 뒤집기(넷)는 **구현했다가
되돌렸다.** 왜 되돌렸는지 남긴다.

밝힌 것은 있다. 뒤집기는 그 축 비트를 토글하고 `0x0003_0000` 두 비트를 함께 세운다. 행렬은
그 축의 배율이 −1 이 되고 이동량이 붙는데, 이동량은 **그 변의 길이를 짝수로 내린 값**이다 —
8475→8474 · 8250→8250 · 6750→6750 · 7425→7424 로 배율 없는 개체 네 관측이 모두 맞는다.
홀수일 때만 1 이 빠지는 것이라 "폭−1" 로 넘겨짚으면 짝수 개체에서 틀린다.

못 밝힌 것이 둘이다.

1. **표시 비트가 언제 지워지는가.** 한 축만 뒤집었다 되돌리면 남는데(`pM2-vv`:
   720898 → 720896), 두 축을 뒤집고 차례로 되돌리면 마지막에 지워진다(`pM-flip` 넷째 자취:
   720898 → **524288**). 축마다 따로 세는 것인지, 둘이 모두 한 번씩 돌았는지를 보는 것인지
   두 관측만으로는 안 갈린다.
2. **배율이 걸린 개체의 이동량.** 크기를 바꾼 뒤 뒤집으면 배율과 얽히는데 같은 개체가
   8756 이었다 8758 이었다 한다(`pM5-resized`). 어느 식도 두 값을 함께 못 낸다.

앞쪽 관측에만 맞는 규칙을 호환 층에 심으면 **틀린 기하를 조용히 쓰게 된다.** 원장에 넷을
얹는 것보다 안 얹는 쪽이 낫다. 잰 것은 탐침으로 전부 남겼다(`probes/pM*.json`).

### 4.18 줄 이동은 좌표 문제가 아니라 조판 문제다 (2026-08-08) — **미제출**

§4.17 다음 순서로 잡았다가 **원장에 올리지 않고 접었다.** 이유를 남긴다.

줄 시작 자리는 파일이 코드 유닛으로 들고 있다(`LineSeg::text_start`) — 좌표 변환이 필요 없다.
그래서 쉬워 보였는데, 값이 어긋난다. 영수증 서식 list 10(누름틀 둘 + 안내문, 두 줄):

| | 줄 2 시작 |
|---|---|
| 파일에 저장된 값(rhwp 가 읽는 값) | **42** |
| 한글이 열어서 답한 값 | **35** |

42 는 안내문 글자 한가운데(35..44)다. 즉 **한글은 파일을 열며 다시 줄을 나눈다** — 저장 당시의
줄 나눔과 지금의 줄 나눔이 다르다. §4.16 에서 본 대로 한글은 빈 누름틀에 안내문을 채워 넣으므로
**조판 입력 자체가 rhwp 와 다르다**.

맞추려면 안내문을 채운 텍스트로 한글의 줄 나눔을 재현해야 한다 — 좌표 층이 아니라 조판 엔진의
일이고, 이 캠페인의 범위를 넘는다. `MoveLineBegin`/`MoveLineEnd` 구현은 코드에 남겨 두되
(한 줄짜리 문단에서는 맞다) **원장에는 선언하지 않는다.** 한 줄 문단만 담은 시나리오로 통과
도장을 받는 것은 과대 주장이다.

곁가지로 확인한 것: 줄을 **위아래로** 옮기는 이동(`MoveLineUp`·`MoveDown` 등)은 리스트를
넘나든다(실측: 셀 10 → 15 → 20). 문단 안 좌표가 아니라 쪽 위 기하 탐색이라 또 다른 축이다.

## 5. API 원장과 게이트

`npm/hwpctrl-ocx/spec/api_ledger.json` — 항목당:

```json
{ "kind": "method", "name": "PutFieldText", "arity": 2, "returns": "void",
  "status": "verified",            // unimplemented | implemented | verified | substituted | by-design-noop
  "oracle": { "scenarios": ["field-put-basic", "field-put-multi"], "lastRun": "r1", "diff": 0 } }
```

- `status: verified` 는 **오라클 대조 0 diff 로만** 올라간다. 사람이 손으로 못 올린다.
- CI 게이트 ①: 원장에 없는 API 가 코드에 있거나, 코드에 없는 API 가 원장에 `implemented` 면 실패.
- CI 게이트 ②: 원장 커버리지가 직전 커밋보다 **줄면** 실패(래칫).
- `GetActionSupport` 를 신규 층에도 두되 원장에서 생성한다 — 손으로 관리하지 않는다.
- 진척 보고는 항상 `verified / 447` (18+67+312+50) 형태의 한 숫자로 한다.

### 6.1 Phase 내부 작업 루프

1. 대상 API 의 시나리오를 **먼저** 쓴다 (OCX 만으로 돌려 정답지 확보).
2. OCX 반환값을 보고 계약을 확정한다 — 문서가 아니라 실측이 계약이다.
3. 구현 → 하니스 재실행 → diff 0 → 원장 `verified`.
4. PR 단위: 축 하나(예: "필드 10종"), fmt+clippy, studio e2e, 하니스 리포트 첨부.

### 6.2 P7 — 기존 층 철거와 studio 이관

최종 상태는 **단일 층**이다. 두 층을 영구히 병존시키면 같은 결함을 두 번 고치게 된다.

#### 6.2.1 실측한 이관 범위 (2026-08-07)

착수 전에 실제 소비자를 셌다. **`rhwp-studio` 본 편집기(`main.ts`)는 `src/hwpctl/` 을 쓰지 않는다.**
`grep -rn "hwpctl" rhwp-studio/src --include=*.ts` 결과에서 `src/hwpctl/` 자신을 빼면 남는 것은
주석 1건(`view/flow-image-url-cache.ts:87`)과 무관한 legacy 메시지 별칭
(`embed/runtime.ts:99` — `hwpctl-load` 는 `loadFile` 의 옛 이름일 뿐 `HwpCtrl` 클래스와 무관)뿐이다.

| 소비자 | 성격 | P7 처리 |
|---|---|---|
| `rhwp-studio/hwpctl-test.html` | 데모·수동 시험 페이지 (`./src/hwpctl/index.ts` 동적 import) | 신규 층 import 로 교체 |
| `rhwp-studio/e2e/hwpctl-basic.test.mjs` | e2e 회귀 | 신규 층 기준으로 재작성(§6.2.3) |
| `embed/runtime.ts:99` `hwpctl-load` | 이름만 같은 별칭 | **무관 — 건드리지 않는다** |
| studio 편집기 UI 156 명령 | `HwpCtrl` 경유 아님, WASM 직접 호출 | **무관 — 이관 대상 아님** |

즉 이관 비용은 **파일 2개**다. 이 사실이 "기존 층을 P6 까지 동결"하는 결정을 싸게 만든다 —
동결 비용이 거의 0 이므로 신규 층을 서두를 이유가 없다.

> 이 절은 계획 초안의 "studio 가 main.ts 경유로 실사용 중"이라는 서술을 실측으로 대체한 것이다.

#### 6.2.2 철거 순서

1. **동결 확인** — P6 종료 시점에 §6.2.1 표를 다시 실측한다(그 사이 새 소비자가 생겼을 수 있다).
2. **계약 차이 목록화** — 신규 층이 기존 층과 **다르게 답하는 지점**을 전수로 뽑는다. 알려진 것:
   - `Undo`/`Redo`: 기존 = `notSupportedByDesign`, 신규 = **OCX 와 동일하게 동작해야 함**.
     studio 이관 시 신규 층의 undo 가 studio 히스토리(`engine/history.ts`)와 **이중 관리**가 되지
     않도록, 신규 층 undo 를 studio 히스토리에 위임할지 여기서 결정한다.
   - 비표준 확장 3종(`SetCellText`/`GetCellText`/`EvaluateFormula`)과 `GetActionSupport`:
     OCX 에 없는 API 다. **신규 층에 같은 이름으로 남긴다**(OCX 표면 + rhwp 확장 표면 분리 문서화).
   - `MovePos(2)` 결함: 기존 층은 "문서 끝"에서 커서를 `(0,0)` 으로 놓는다(`index.ts:365-371`).
     신규 층은 OCX 대조로 올바르게 구현되므로 **동작이 바뀐다** — 이관 노트에 명시.
3. **교체** — `hwpctl-test.html` 의 import 를 신규 패키지로 돌리고, e2e 를 재작성한다.
4. **삭제** — `rhwp-studio/src/hwpctl/` 12 파일 제거. 같은 PR 에서 지운다(호환 shim 을 남기지 않는다).
5. **문서 갱신** — `mydocs/tech/` 및 studio 문서에서 기존 층을 가리키는 서술을 신규 층으로 옮긴다.

#### 6.2.3 완료 판정

- `grep -rn "src/hwpctl" rhwp-studio` **0건**
- 재작성한 e2e 가 기존 e2e 의 **모든 단언을 포함**하고 녹색
  (등록 액션 수 ≥ 30 → **≥ 312**, `GetActionSupport` 3상태, ParameterSet 왕복)
- 하니스 전 시나리오 0 diff 유지(철거 PR 이 회귀를 만들지 않았음)
- studio 수동 시험: 문서 열기 → 편집 → 저장 정상

#### 6.2.4 되돌리기

철거 PR 은 **단일 커밋 revert 로 복구 가능**해야 한다. 삭제와 이관을 한 커밋에 담고, 그 커밋
메시지에 §6.2.1 실측 결과를 남긴다.
