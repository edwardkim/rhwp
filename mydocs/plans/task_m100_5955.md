## 1. 목적

W7은 W1·W6의 역사 증거와 현재 runtime 규칙을 830개 active rule의 schema 1.0 registry로 일회 이행했다.
이 판은 현재 제품 선택을 재현하는 봉인 snapshot이므로 rule 수, status, W1/W6 anchor와 backend별 population을
고정한다. 이 제약을 단순히 풀면 다음 mapping 수정이 과거 evidence를 현재 정책으로 위장하거나 여러 backend의
변화를 한 번에 숨길 수 있다.

#5955의 목적은 schema 1.0을 수정 가능한 파일로 바꾸는 것이 아니다. 다음 세 층을 분리해 W8의 실제 face
교정이 감사 가능한 command로만 들어오게 하는 것이다.

```text
sealed v1 registry + approved append-only change sets
                         │
                         ▼
              schema 2.0 lifecycle registry
                         │
                         ▼
       active rules only → five backend projections

all rules + evidence + change sets → migration/delta audit
```

초기 v1→v2 이행 자체는 제품 규칙을 바꾸지 않는다. 830개 rule의 selection tuple과 active 순서, 다섯
projection의 semantic hash, native/WASM renderer 결과가 기존과 같아야 한다.

## 2. 현재 구조와 이 문제가 생긴 이유

### 2.1 schema 1.0은 의도적으로 변경을 표현하지 못한다

현재 `scripts/font_rule_registry.mjs`는 다음 세 역사 입력에서 registry 전체를 다시 만든다.

- W7 pre-migration projection baseline
- W1 ledger·candidate
- W6 metric lineage

validator는 830개 전부 `active`, projection별 171/67/281/153/158, legacy unknown 43개와 W1/W6 anchor를
고정한다. 이는 W7 당시에는 올바른 보호 장치였지만 다음 rule의 추가·교정·retirement를 표현할 command
source가 없다.

### 2.2 현재 evidence는 역사 anchor만 소유한다

각 rule의 `evidence`는 W1 rule/candidate, source boundary, W6 metric entry와 pre-migration projection
hash를 설명한다. W5 Oracle Profile이나 이후 공개 fixture·source discovery가 어느 rule 변경을 정당화했는지,
그 evidence의 parent와 digest가 무엇인지 표현할 일반 계보는 없다.

### 2.3 배열 행 삭제·제자리 수정은 audit를 파괴한다

현재 배열 순서는 generated projection의 순서다. 행을 삭제하면 과거 trace가 가리킨 `ruleId`를 잃고,
target이나 decision plane을 같은 ID에서 바꾸면 같은 `ruleId`가 시점별로 다른 의미를 갖는다. schema 2.0은
행 삭제나 in-place semantic mutation을 허용하지 않고 lifecycle event로만 표현해야 한다.

### 2.4 backend projection과 registry provenance가 결합돼 있다

projection generator, `font_metric_lineage.mjs`, public projection integration test와 generated source의
sentinel이 현재 v1 경로를 직접 참조한다. 새 판을 추가할 때 consumer inventory를 함께 이행하지 않으면 v1과
v2가 동시에 authority가 되는 이중 정본이 생긴다.

## 4. 핵심 설계 결정

### 4.1 schema 2.0을 별도 판으로 추가한다

`status`, lifecycle, evidence graph와 change-set command가 추가돼 v1 validator와 호환되지 않으므로 다음 판은
`1.1`이 아니라 `2.0`으로 한다. v1 registry·schema·W7 migration은 현재 경로와 byte를 그대로 보존한다.

신규 정본 후보는 versioned path를 사용한다.

```text
assets/font-rules/font_rule_registry_v2.schema.json
assets/font-rules/font_rule_change_set.schema.json
assets/font-rules/font_rule_registry_v2.json
assets/font-rules/font_rule_change_sets/*.json
mydocs/tech/investigations/issue-5955/
  font_rule_registry_v1_to_v2_migration.schema.json
  font_rule_registry_v1_to_v2_migration.json
```

v2 통합 뒤 projection generator와 현재 consumer가 v2만 읽도록 전환한다. v1은 역사 입력·audit anchor로만
남기며 두 판을 제품 선택에 동시에 사용하지 않는다.

### 4.2 change set은 command, registry와 projection은 query model이다

W8 이후 제품 규칙 변경은 generated registry JSON을 직접 편집하지 않고 승인된 append-only change set을
추가한다. reducer는 봉인 v1과 순서가 고정된 change set을 읽어 v2 registry를 결정론적으로 만든다.

각 change set은 최소한 다음을 가진다.

- `changeSetId`, issue, parent registry SHA-256과 sequence
- 정확히 한 `decisionPlane`
- `add-rule`, `augment-evidence`, `retire-rule`, `retire-and-replace` operation
- evidence record와 parent evidence ID·artifact digest
- 예상 pre/post selection tuple, active projection delta와 비대상 projection 무변화 선언

parent digest가 현재 reducer head와 다르면 stale change set으로 fail-closed한다. 병렬 W8 PR은 같은 parent에서
갈라진 두 event를 자동 병합하지 않고 최신 registry 위에서 뒤 change set을 다시 계산한다.

### 4.3 semantic tuple이 바뀌면 같은 ruleId를 재사용하지 않는다

selection tuple은 다음 필드의 canonical JSON으로 정의한다.

```text
relationType, decisionPlane, sourceFace, targetFaceOrPolicy,
conditions, decision-group order, projection id/mode,
metricEntryIds, supply payload
```

- tuple이 동일하고 evidence·설명만 보강되면 기존 `ruleId`를 유지한다.
- tuple 중 하나라도 바뀌면 기존 rule을 `retired`로 남기고 새 `ruleId`를 만든다.
- generator 직렬화나 주석 정정은 registry change set이 아니며 같은 semantic hash를 유지한다.

이 규칙으로 한 `ruleId`가 시점에 따라 다른 선택 의미를 갖는 것을 막는다.

### 4.4 retired rule은 보존하지만 runtime에서 제외한다

v2 rule은 `active|retired` 상태와 lifecycle을 가진다.

- active: `introducedBy`, optional `lastEvidenceChangeBy`
- retired: `retiredBy`, reason, successor rule ID 목록과 retirement evidence
- 모든 상태: immutable selection tuple hash와 projection sequence

retired rule은 registry·migration·offline trace audit에는 남지만 다섯 runtime projection에서는 제외한다.
active rule의 projection sequence만 유일·연속이어야 하며, replacement가 retirement된 rule의 active slot을
명시적으로 승계할 수 있다. 기존 decision-group `order`는 이 sequence와 혼합하지 않는다.

### 4.5 W2 trace는 runtime schema를 불필요하게 늘리지 않는다

현재 trace가 내보내는 active `ruleId`는 그대로 유지한다. 별도 lifecycle resolver가 trace `ruleId`를 v2
registry에 join해 다음을 설명한다.

- carried-forward active
- 새 active rule과 도입 change set
- retired rule, retirement reason과 successor

초기 이행에서 active trace JSON이나 renderer output 필드를 늘리지 않는다. future W8에서 public trace
schema 변경이 실제로 필요하면 그 face 이슈에서 별도 승인한다.

## 5. schema·보안 상한

schema와 수기 validator는 같은 제한을 가져야 하며 mutation test로 둘의 불일치를 막는다.

| 항목 | 상한·규칙 |
| --- | --- |
| 전체 rule | 최대 4,096, `ruleId` 전 상태 전역 유일 |
| 한 change set operation | 최대 64, #4967의 face·decision-plane 단위 PR 원칙 우선 |
| evidence record | change set당 최대 128 |
| rule당 evidence/successor 참조 | 각각 최대 16 / 8 |
| 문자열 | 기존 계약과 같은 최대 2,048자 |
| metric entry 참조 | rule당 기존 최대 600 유지 |
| evidence graph | cycle·self-parent·dangling parent 거부 |
| path | checkout 상대경로만, `..`, symlink escape, host absolute와 `file://` 거부 |
| 외부 자료 | HTTPS와 digest·license/provenance 분류가 있는 경우만 허용 |
| unknown field | 전 계층 거부 |

private corpus 원본·본문·식별 파일 목록·host path·font bytes는 change set과 evidence에 넣지 않는다. 필요한
경우 기존처럼 aggregate·비식별 결과나 공개 controlled fixture의 repository path와 digest만 기록한다.

통과시키지 않는다.

### Stage W7.5-1 — executable contract red

### Stage W7.5-5 — future W8 mutation rehearsal

실제 제품 mapping을 바꾸지 않는 임시 fixture에서 다음 네 흐름을 실행한다.

1. evidence-only: 같은 ruleId·tuple 유지
2. add: 새 ruleId와 한 decision plane의 active projection 추가
3. retire: 역사 row 보존·runtime 제외

각 fixture는 pre/post tuple, projection delta, 비대상 backend 무변화와 rollback을 검증한다. fixture 결과를
canonical product registry에는 적용하지 않는다.

**종료 게이트**: 네 lifecycle path와 모든 negative mutation이 결정론적으로 통과.

## 9. 검증 사다리

### 9.1 schema·reducer

- JSON schema와 semantic validator의 positive/negative fixture 일치
- canonical serialization·hash 결정성
- stale parent·fork·sequence gap·중복 changeSetId 거부
- unknown field, size cap, unsafe path·symlink escape 거부
- 실패 시 canonical/generated set 전체 rollback

### 9.2 lifecycle·evidence

- same ID는 tuple hash 불변일 때만 허용
- semantic change는 retire-and-replace 강제
- retired row 삭제 금지, successor·predecessor 양방향 대사
- evidence artifact digest·parent graph·issue scope 검증
- W1/W6 historical anchor를 current change evidence로 다시 쓰지 않음

### 9.3 projection·runtime

- active rule만 다섯 allowlisted output으로 1회 projection
- one rule/one decision plane/one projection
- initial v2의 active ruleId·order·semantic hash가 v1과 동일
- Canvas2D availability, webfont plan, CanvasKit SFNT capability·load success 분리
- layout metric과 paint face 분리
- native/WASM public output byte parity

### 9.4 제출 경계

- generated Rust·TypeScript는 generator 결과만 stage
- integration은 `tests/cases/` 원본만 stage
- generated suite·manifest·unit-tier inventory는 stage 금지
- font binary, private sample, host path·identifying corpus evidence 0
- 모든 PR·push 직전 `cargo fmt --all`, `cargo fmt --all -- --check`

## 10. 보호 불변식

- v1 registry·schema·W7 migration·pre-migration baseline의 byte와 historical hash를 다시 쓰지 않는다.
