## 구현 전 확인한 원인과 소비 경로

- 8쪽의 원문과 render tree에는 정상 한글이 있다. Native 글꼴 추적은 본문 문단 349의
  `한컴돋움`을 실제 설치된 시스템 face로 선택했지만, 최종 그림에서는 다른 글자가 표시됐다.
- 현재 Mac의 `HDOTUM.TTF` 두 버전은 Unicode→glyph ID가 서로 다르다. 두 프로그램을 각각
  직접 열거나 시스템 face에서 얻은 바이트를 다시 열면 정상 한글이며, 시스템 face를 그대로
  그릴 때만 다른 글자가 나온다. Unicode cmap 자체의 오매핑 가설은 독립 CoreText/Skia
  대조에서 재현되지 않았다. 개인 글꼴 파일·설치를 수정하지 않는다.
- 공통 경로는 Native 후보 선택 → `text_replay::fonts::for_text` → 실제 Font 생성 →
  nominal/shaping/합성 굵기·윤곽 paint다. 시스템 조회의 논리적 face를 실제 OpenType 프로그램
  바이트에 묶인 face로 준비한 뒤 같은 Font를 소비하도록 보정한다. family·문서·쪽 번호로
  분기하지 않으며 기존 후보 우선순위·명시 공급·줄 폭·기준선·페이지 예산을 바꾸지 않는다.
- 개인 폰트에 의존하지 않는 프로그램·스타일·glyph 소유 관계 검사를 보강하고 실제 결함의
  수정 전/후 출력도 따로 남긴다. 캐시와 프로그램 준비의 크기·개수 상한, collection index와
  variation 좌표를 보존하며 준비할 수 없는 face의 기존 fallback을 유지한다.
- 미주의 단·쪽 내용 차이는 별도로 남아 있다. 첫 종료 컷·저장 줄·TAC 수식 상자·실제 점유를
  독립 Print와 대조한다. 글자 표시 한 곳을 고친 사실로 전쪽 완료를 주장하지 않는다.

## 저장 줄과 현재 수식 프레임의 수용 계약 후보

- 독립 Print 11쪽의 마지막 `g(x)`·적분식은 두 입력 모두 왼쪽 단에 있다. 공개 렌더 트리에서
  원본 미주 주소 `s0:p99:ci0:note8`과 실제 단 소속을 확인하는 새 관계 검사는 원본 통과,
  재저장본 `[1,1]` 대 기대 `[0,0]`으로 실제 실패했다. 절대 px 위치를 고정하지 않았다.
- 후보는 기존 단순 수식의 논리 프레임 질의를 공유한다. 수식 상자와 기준선이 이미 그 프레임과
  같은데, 온전한 저장 줄의 LH=TH가 모든 현재 텍스트/수식보다 큰 경우에는 소유자가 사라진
  과거 예약 높이를 유지하지 않고 현재 기준선 합집합을 재발행한다. 문서·쪽 번호 분기는 없다.
- 모든 소유 수식이 이 계약을 만족해야 한다. 크기 보호·별도 선언 프레임·legacy 원본 프레임·
  미지원 복합 구조, 양식/그림/표와 저장 문자 분할이 달라진 줄은 이 수용 계약으로 넓히지 않는다.
  기존 참여 줄 간격과 보호된 프레임, 완료된 수식 문서는 별도 정상 대조군으로 검사한다.
- 현재는 새 관계 검사와 실제 전쪽 출력으로 후보의 수용 범위를 확인하는 단계이며,
  11쪽 단 소속 복구만으로 21쪽 전체 완료를 판정하지 않는다.

## 장식 프레임 단위 보존의 다음 보정

- 현재 윗줄 프레임 생산식은 `장식 높이 + 본체 높이 - 일반 줄 높이`다. 본체와 일반 줄이
  같을 때도 중간 합의 반올림으로 한 ULP가 사라져, 1080HU인 현재 프레임을 1079HU로
  전달한다. 현재 수식 프레임 인증이 실패해 저장 TH1305가 남고 19쪽 끝 적분식이 20쪽으로
  넘어간다. 공개 렌더 트리·원본 저장값·독립 Print의 실제 단 소속으로 확인한다.
- 수식의 본체가 달라지는 프레임 증분과 장식 높이를 구분해 생산한다. 전역 단위 변환을
  반올림하거나 허용오차를 넓히지 않고 같은 본체의 차가 0임을 보존한다. 측정의 현재 프레임
  질의와 실제 수식 bbox가 이 공통 결과를 사용한다.
- 현재 저장 프레임의 단위 보존 및 19쪽 끝 적분식의 단 소속 관계 검사를 먼저 실행한다.
