## 1. 목표

이 이슈는 전체 font 개선 로드맵을 구현하지 않는다. 선행 보고서의 단일 임계 경로 가운데 W0와 W1만
수행한다.

1. **W0 — 기준선 고정**: 현재 font 선택 결과, lookup 순서, 입력 source와 기존 backend test를
   재현 가능한 manifest로 고정한다.
2. **W1 — Font Rule Ledger**: Rust와 Studio에 흩어진 finite mapping, ordered fallback,
   algorithmic classification, font supply와 capability detection 규칙을 전수 inventory하고 각 규칙의
   관계 유형·근거·적용 plane·backend를 기록한다.

완료 시점에도 layout metric, paint face, webfont supply, local-font detection과 CanvasKit Typeface
선택 결과는 현재와 같아야 한다. 이 작업의 산출물은 후속 W2 Font Decision Trace의 **조사 입력**이지
제품 runtime의 새 canonical registry가 아니다.

## 2. 왜 이 순서가 필요한가

현재 같은 형태의 `source → target` mapping 안에 서로 다른 의미가 섞여 있다.

- 같은 face의 한국어·영문 이름을 연결하는 identity alias
- HWP/HWPX가 제공한 문서 `substFont`
- 정부상징 legacy face에서 ROKG로 가는 official successor
- 원본 metric이 없을 때만 쓰는 metric surrogate
- layout을 바꾸지 않고 glyph만 바꾸는 paint substitute
- URL·파일 bytes를 제공하는 webfont supply
- serif/sans/mono 분류와 weight suffix 같은 algorithmic fallback
- 열거·probe·SFNT blob 여부를 판단하는 backend capability rule

이를 구분하지 않고 table을 먼저 합치면 #2279·#2430·#4701에서 철회한 잘못된 alias와 PDF profile
혼합을 반복할 수 있다. 반대로 문서만 수기로 작성하면 후속 source 변경 때 누락을 자동 검출할 수 없다.
따라서 다음 세 층을 분리한다.

```text
현재 source에서 자동 수집한 candidate
  → 사람이 evidence와 relationType을 판정한 investigation ledger
  → source candidate와 ledger의 전수 대응을 검사하는 validator
```

## 5. W0 baseline manifest 계약

### 5.1 결정론적 봉투

`font_rule_baseline.json`에는 다음 필드를 둔다.

```text
schemaVersion
sourceCommit
generatorVersion
inputs[] { path, sha256, owner, extractionMode }
fontMetrics { entryCount, uniqueNameCount, styleCounts, duplicateKeys, tableSha256 }
lookupContract { exactOrder, fallbackOrder, knownInputCount, projectionSha256 }
ruleCandidates { countsByOwner, countsByKind, projectionSha256 }
fixtures[] { id, path, sha256, purpose, backend }
gates[] { id, command, status, evidence }
```

- wall-clock, elapsed time, 절대 workspace path, 사용자명과 private corpus filename은 넣지 않는다.
- JSON key와 array order를 고정하고 pretty-print newline까지 deterministic output으로 만든다.
- 같은 source commit에서 두 번 생성한 파일의 SHA-256이 같아야 한다.
- `generatedAt`처럼 재실행마다 바뀌는 값은 machine baseline에 넣지 않고 Markdown manifest에만 기록한다.

### 5.2 lookup 기준선

- `FONT_METRICS`의 물리 순서를 보존한다.
- `(name, bold, italic)` 4개 style 요청에서 선택되는 metric entry와 `bold_fallback`을 projection한다.
- metric alias의 모든 좌변·우변, metric table의 모든 이름과 미등록 sentinel을 입력 집합에 포함한다.
- 기존 `legacy_find_metric` 전수 등가 test를 실행해 projection이 runtime 계약과 어긋나지 않는지 확인한다.
- private static을 노출하기 위한 새 public API는 만들지 않는다. 필요한 경우 test-only helper나 source
  candidate projection을 사용하고 production visibility는 바꾸지 않는다.

### 5.3 backend 기준선

W0은 새로운 golden을 대량 생성하지 않고 기존 공개 fixture와 test contract를 연결한다.

- native/WASM: #4046의 public 대표 fixture set에서 SVG byte parity
- Canvas2D: `font-substitution`, `local-fonts`, renderer baseline font loading test
- CanvasKit: font plan, SFNT face, document preflight test
- font asset: `scripts/frontend-font-assets.test.mjs`와 `assets/fonts/FONTS.md`

과거 #4046 10k 전수 결과는 역사 evidence로 연결하되 이번 이슈에서 private corpus 전수를 다시 실행해
hard gate로 만들지 않는다.

## 6. W1 Font Rule Ledger 계약

### 6.1 행의 단위

규칙 종류에 따라 행의 granularity를 고정한다.

| source 형태 | ledger 행 |
| --- | --- |
| finite `A | B → X` mapping | `A → X`, `B → X`를 각각 한 행으로 확장 |
| ordered fallback chain | 후보 edge마다 한 행, `order`로 우선순위 보존 |
| style·language 조건 mapping | 조건 조합마다 별도 행 |
| algorithmic classifier | 무한 입력을 열거하지 않고 predicate·owner·대표 test를 한 행으로 기록 |
| font asset supply | family·style·file/URL 조합마다 한 행 |
| capability detection | 열거·probe·blob·backend 상태 전환마다 한 행 |
| exact metric table | face·bold·italic entry마다 한 행 또는 baseline entry ID 참조 |

주석만 있고 실행되지 않는 역사 설명은 rule 행으로 세지 않고 evidence로 연결한다. 반대로 코드가
실행하는데 근거가 없는 규칙은 반드시 `evidenceStatus: unknown` 행으로 남긴다.

### 6.2 필수 필드

각 ledger 행은 최소한 다음 필드를 가진다.

```text
ruleId
sourceOwner
sourceLocation { path, symbol, selector }
decisionPlane
relationType
sourceFace
targetFaceOrPolicy
conditions { languageSlot, altType, bold, italic, weight, availability, profile }
backends[]
order
evidence[] { kind, issue, commit, document, fontDigest }
evidenceStatus
licenseOrDistribution
tests[]
knownLimitations[]
status
```

- `ruleId`는 사람이 정한 의미 ID이며 source line number를 ID에 넣지 않는다.
- `sourceLocation`의 line은 summary에 표시할 수 있지만 안정 selector는 symbol·case/predicate를 사용한다.
- digest가 필요한데 공개·보존할 수 없는 font는 bytes 대신 허용된 SHA-256과 외부 asset 역할만 기록한다.
- evidence가 여러 profile에서 충돌하면 하나를 덮지 않고 행을 profile별로 분리한다.

### 6.3 enum

`decisionPlane`:

- `layout-name`, `layout-metric`, `paint`, `supply`, `detection`, `backend-resource`, `oracle`

`relationType`:

- `metric-entry`
- `identity-alias`
- `document-substitution`
- `official-successor`
- `metric-surrogate`
- `measured-overlay`
- `paint-substitute`
- `style-fallback`
- `generic-fallback`
- `supply-source`
- `capability-detection`
- `oracle-observation`
- `unknown`

`evidenceStatus`:

- `verified-by-bytes`, `verified-by-oracle`, `verified-by-test`, `historical`, `inferred`, `unknown`

`unknown`은 허용 상태이지만 빈칸은 허용하지 않는다. `identity-alias`는 SFNT naming record나 byte
identity 같은 근거 없이는 선택할 수 없다. `official-successor`와 `metric-surrogate`도 identity로
자동 승격하지 않는다.

## 8. 수행 단계와 승인 게이트

각 Stage의 변경은 다음 Stage 전에 별도 commit과 working 보고서로 고정한다. 다음 Stage로의 전환은
메인테이너 승인 뒤 수행한다.

### Stage 1 — schema와 source boundary RED

1. issue-4939 조사 README와 schema 초안을 만든다.
2. owner/symbol selector manifest를 작성한다.
3. fixture source snippet으로 grouped mapping expansion, ordered chain, predicate row를 고정한다.
4. 누락 owner, 사라진 symbol, 중복 `ruleId`, 허용되지 않은 enum, 빈 evidence 상태가 실패하는 RED를 만든다.
5. production renderer·Studio source는 변경하지 않는다.

**종료 게이트:** schema invalid case가 모두 실패하고, source selector 하나를 의도적으로 제거했을 때
collector가 0건 성공이 아니라 명시적 오류를 낸다.

### Stage 2 — W0 deterministic baseline

1. candidate collector와 canonical JSON writer를 구현한다.
2. source digest·metric entry·lookup contract·fixture contract를 수집한다.
3. 같은 HEAD에서 두 번 생성해 normalized SHA-256 일치를 확인한다.
4. focused Rust·Studio·asset test와 public native/WASM parity를 실행한다.
5. baseline JSON과 Markdown manifest, Stage 2 보고서를 작성한다.

**종료 게이트:** `sourceCommit`·input digest·count·projection hash가 폐합하고 모든 선택 결과가 current
baseline과 같으며, private corpus 정보가 산출물에 없다.

### Stage 3 — W1 candidate 전수 수집

1. 7절 owner의 finite mapping을 행 단위 candidate로 확장한다.
2. ordered chain과 algorithmic predicate를 별도 kind로 수집한다.
3. source candidate마다 안정 selector와 source digest를 붙인다.
4. asset supply와 backend capability candidate를 runtime mapping과 분리한다.
5. candidate count를 owner·kind·decision plane별로 summary한다.

**종료 게이트:** 선언된 모든 owner가 1개 이상의 candidate 또는 명시적 `not-applicable` disposition을
가지며, collector가 인식하지 못한 실행 mapping block이 0개다.

### Stage 4 — evidence 판정과 Font Rule Ledger 완성

1. candidate마다 relation type과 evidence status를 판정한다.
2. 관련 issue·commit·계획·보고서·font digest·test를 연결한다.
3. exact/missing oracle, layout/paint, Canvas2D/CanvasKit profile을 분리한다.
4. 근거 미확정은 `unknown`으로 보존하고 후속 조사 질문을 기록한다.
5. 동일 source/condition의 상충 target, 순환 chain, order 중복과 orphan evidence를 검사한다.

**종료 게이트:** source candidate 전부가 ledger의 정확히 한 행 또는 허용된 profile 분할 행들에 대응하고,
설명 없는 누락·중복·identity 승격이 0개다.

### Stage 5 — 행동 불변·최종 감사

1. baseline을 재생성해 Stage 2 snapshot과 byte 비교한다.
2. `src/renderer`, `src/paint`, `rhwp-studio/src`의 제품 동작 변경이 없는지 diff를 확인한다.
3. focused test와 native/WASM public parity를 재실행한다.
4. ledger summary에 owner별 count, relation별 count, `unknown` 목록, 후속 W2 입력 계약을 기록한다.
5. final report와 Issue #4939 완료 조건의 전항 disposition을 작성한다.

**종료 게이트:** baseline 0-delta, 모든 ledger validator 통과, FI-01~FI-14 전항 판정, W2가 ledger를
읽을 수 있지만 runtime이 ledger에 의존하지 않는 경계가 확인된다.

사전 build와 public fixture 실행법을 따른다. W0 자체가 현재 HEAD의 기준선을 수집하는 단계이므로
동일 commit의 release binary와 fresh WASM을 사용한다. 10k private corpus 전수는 실행하지 않는다.

다음 조건이면 성공으로 판정하지 않고 중단한다.

- selector가 사라졌는데 candidate count가 조용히 감소
- 같은 source commit에서 JSON hash가 달라짐
- `identity-alias`에 bytes/name-table evidence가 없음
- exact-font와 missing-font evidence가 같은 profile 행에 혼합됨
- source candidate와 ledger 사이 orphan 또는 설명 없는 중복이 존재
- baseline을 만들기 위해 production font selection visibility/API를 확대해야 함
- 제품 source나 backend 출력이 예상과 다르게 변경됨
