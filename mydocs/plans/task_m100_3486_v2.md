## 재설계 결정

#3529가 해결한 HWP3 암호 문서의 Square-wrap 도형·쪽 배경·A4 Canvas 물리 경계·확인된
문단/인라인 위치 계약을 다시 넓게 흔들지 않는다. 다음 목표는 "24쪽 완전 일치"라는 큰 문구가
아니라, **한컴 PDF에서 보이는 하나의 재현 가능한 구조 또는 paint 결함을 source → IR → layout
→ paint → Studio Canvas 경로에서 증명하고 최소 범위로 고치는 것**이다.

작업지시자가 제공한 `task_m100_3486_stage11.md`의 결론도 이 계획의 고정 전제다. 제목의
`ᄒᆞᆫ글`은 HWP3만의 decode 오류가 아니고, Studio CanvasKit도 공개 옛한글 글꼴로 하나의 cluster를
shape한다. 한컴 PDF의 독점 legacy glyph/metric과 다르다는 사실만으로 `ᄒᆞᆫ → 한`을 전역 치환하거나
HWP3 parser를 고치지 않는다.

### #3486 절차 우선순위

이 이슈는 기준 PDF에서 실제 사용자-visible 차이가 확인됐지만 원인과 수정 범위가 미확정이므로
[bug-hunter](../manual/bug_hunting_playbook.md)가 지배 절차다. Stage 12 visual sweep은 페이지·glyph
후보와 수정 전후 무회귀를 제공하는 하위 도구이며, `legacy_glyph_visual_mismatch` 하나만으로 전역 치환,
font 교체 또는 renderer 보정을 결정하지 않는다. source→IR→layout→paint 원인 경로와 PDF/Studio
사람 판정이 연결된 뒤에만 코드 변경을 시작한다.

## 다음 결함 후보와 선택 규칙

첫 조사 대상은 서로 섞지 않는 두 가지다. 첫째는 **HWP3 p3 표 오른쪽 셀의 bullet/목록 표기와 폭**이다.
Stage 10의 실제 Studio Canvas(왼쪽)와 PDF(오른쪽)에서는 PDF 셀의 반복 bullet이 Canvas에서 보이지
않는다. 둘째는 **문서 전반의 제품명 `ᄒᆞᆫ글` 표시**다. 최신 SVG/PDF p10 대조에서 같은 문구가
rhwp에는 표준 옛자모로, PDF에는 현대 제품명 `한글`로 실제 보인다. Stage 7의 p10·p24 목록 차이도
이 둘과 같은 원인인지 아직 확정하지 않았다.

p3을 주 대상, p10·p24를 공통성 확인용 보조 대상으로 둔다. 다음 중 하나가 확인되기 전에는
parser·renderer·font 중 어느 곳도 수정하지 않는다.

| 판별 | 필요한 증거 | 다음 행동 |
| --- | --- | --- |
| HWP3 raw/IR에서 marker·번호 설정이 사라짐 | 같은 논리 HWP5의 대응 문단과 raw code, control, `ParaShape`/번호·bullet 속성을 문단 단위로 비교 | 실제 HWP3 fixture에 한정한 parser/IR 보정 후보 |
| IR에는 있으나 layout/render tree의 PaintOp가 없음 | 같은 page/paragraph의 render tree에서 text·marker·cell bbox와 flow 순서를 대조 | layout 또는 paint 경계의 최소 보정 후보 |
| PaintOp는 있는데 Studio Canvas에만 없음 | 동일 WASM document의 `renderPageToCanvas()`와 SVG를 같은 page에서 따로 대조 | Canvas/CanvasKit 전달·clip·font 등록 경로 조사 |
| 제품명 `ᄒᆞᆫ글`만 PDF의 `한글`과 다름 | 24쪽의 모든 출현을 raw code·CharShape·문단 context로 분류하고 PDF raster에서 제품명 convention을 확인 | 원문 IR은 유지한 문서/context 한정 paint-time projection 후보. 일반 옛한글·다른 문서는 명시적 negative regression으로 보호 |
| marker의 위치는 맞고 일반 옛한글 glyph 외관만 다름 | glyph·advance와 cell/line bbox가 PDF와 구조적으로 대응하고 제품명 convention도 아님 | font capability 잔여로 분류하고 코드 변경하지 않음 |
| p3의 cell width/flow 자체가 다름 | cell bbox·line break·다음 문단 anchor가 PDF/HWP5 비교와 함께 어긋남 | table layout 계약을 별도 단일 원인으로 재설계 |

HWP5는 24쪽이므로 HWP3의 page-flow/IR 비교에 쓴다. HWPX는 23쪽이라 문단·문자 의미 비교까지만
허용한다. 어느 비교도 한컴 PDF와의 시각 오라클을 대체하지 않는다.

## Stage 12-A — 중단 가능한 시각 sweep의 증적 보존

`scripts/task1274_visual_sweep.py`에는 이미 `--page`/`--pages`가 있다. 하지만 현재
`render_target()`은 시작할 때 SVG·PNG·overlay·analysis 디렉터리를 모두 비우고, target 전체가 끝난
뒤에야 `manifest.json`과 최상위 `summary.json`을 쓴다. 따라서 page raster/overlay 단계가 단일 실행
한도를 넘으면 완료 페이지가 있어도 재개 가능한 summary가 남지 않는다.

다음 보강을 **별도 작은 도구 변경**으로 먼저 수행한다.

1. 기본 실행은 기존처럼 새 output을 만들고, 명시적 `--resume`에서만 기존 output을 유지한다.
2. 각 페이지가 SVG raster·PDF raster·compare·overlay·review·해당 page metrics까지 모두 성공한 뒤,
   `pages/page-XXX.json`을 원자적으로 기록한다. 실패·중단 페이지는 완료로 기록하지 않는다.
3. resume 시작 시 입력 HWP/PDF SHA-256, git HEAD, `rhwp` 실행 파일 식별값, DPI, diff threshold,
   선택 페이지를 run manifest와 대조한다. 하나라도 다르면 이전 artifact를 섞지 않고 명시적으로
   거부한다.
4. 완료 page manifest만 합쳐 summary/contact sheet를 재생성하고, `requested`·`completed`·`missing`
   page 목록과 run 상태(`complete`/`incomplete`)를 남긴다. 누락 페이지가 있으면 전체 sweep 완료나
   정상 summary로 표현하지 않는다.
5. `--pages 1-4`, `--pages 5-8`처럼 shard 실행해도 같은 provenance의 완성 run으로 합칠 수 있게 한다.
   기존 `--page` 선택, singleton fallback, 깨끗한 새 output 동작은 유지한다.

이 도구는 Rust SVG/render-tree 후보 탐지용이다. **Stage 10의 Studio Canvas/PDF 대조를 대체하지
않는다.** Studio 최종 증적도 같은 방식으로 page별 완료 상태와 capture provenance를 남겨야 한다.

## Stage 12-B — p3 source-to-canvas 원인 판별

도구 보강 뒤, 코드 변경 없이 다음 순서로 p3을 조사한다.

1. 현 `upstream/devel` 기준의 HWP3 password 입력에서 p3 Studio Canvas와 Hancom PDF를 새로 capture한다.
   Canvas/PDF 크기, fixture/PDF hash, commit, capture API를 기록하고 좌우 review·overlay를 남긴다.
2. p3의 두 표와 그 다음 문단을 raw HWP3 → IR → render tree 순으로 추출한다. 셀별
   text, control, bullet/numbering, CharShape, ParaShape, cell bbox, line bbox, PaintOp를 기록한다.
3. `ᄒᆞᆫ글`의 24쪽 모든 출현을 code point, CharShape, heading/body/product-name context로
   분류하고, 대표 PDF crop과 대조한다. p10 `가. ᄒᆞᆫ글 드라이버 사용`은 반드시 포함한다.
   HWP3/HWP5/HWPX에 같은 raw text가 있음을 HWP3 parser 결함의 부재로만 사용하며, 공통
   display projection의 필요성을 배제하는 근거로 사용하지 않는다.
4. 같은 의미의 HWP5 문단과 비교해 HWP3 변환 손실인지 공통 layout/paint인지 분리한다. HWPX는
   페이지가 아닌 대응 문단의 문자·속성 확인에만 쓴다.
5. 같은 방법으로 p10·p24의 목록 marker를 표본 확인한다. 공통 raw/IR/paint 패턴이 있을 때만 하나의
   공통 결함으로 승격하고, 그렇지 않으면 p3만의 table 결함으로 좁힌다.
6. 위 판별표의 한 행이 재현 가능한 증거로 채워지면 그 행만 구현 계획으로 바꾼다. 제품명 convention이
   증명되지 않은 일반 옛한글만 font capability로 남기고, p10처럼 PDF와 다른 제품명 표시는 이
   분류를 근거로 방치하지 않는다.

## 구현 및 검증 게이트

원인이 확정된 뒤에만 한 원인·한 계약의 code/test/working report를 같은 커밋에 넣는다.

1. 실제 암호 HWP3 fixture의 focused 회귀가 raw/IR 또는 page-item/paint 계약을 고정한다. password,
   token, 환경 값은 명령 출력·문서·asset 메타데이터에 기록하지 않는다.
2. p3은 한컴 PDF↔Studio Canvas before/after/overlay로 다시 확인한다. 공통 원인으로 증명된 경우에만
   p10·p24도 같은 방식으로 확인한다. p1은 Stage 11의 제품명 glyph를 현대화하지 않았다는 회귀
   guard로 남긴다.
3. 새 checkpoint sweep으로 24쪽 전체를 shard 실행·resume 한다. 모든 requested page가 `complete`일
   때만 24/24 수치와 contact sheet를 보고하며, SVG 결과와 Studio Canvas 결과를 별도 표로 기록한다.
4. focused 검증과 시각 증적을 먼저 공유한다. 전체 release-test, clippy, PR 생성·push는 작업지시자의
   별도 승인을 받은 뒤에만 실행한다.

## 완료 기준과 비목표

이번 재설계의 첫 완료는 전체 fidelity 선언이 아니라 다음을 모두 만족하는 것이다.

- 중단된 sweep이 완료된 페이지를 숨기거나 전체 완료로 가장하지 않고 재개 가능하다.
- p3의 PDF 차이가 source/IR/layout/paint/font 중 정확히 한 계층 또는 명시적 capability 한계로
  분류된다.
- p10을 포함한 제품명 `ᄒᆞᆫ글`의 PDF 표시 차이는 전역 치환 없이 context 한정 projection 후보인지,
  아니면 일반 옛한글 glyph 한계인지 전수 근거로 분류된다.
- 코드 변경이 필요한 경우에만 최소 focused regression과 실제 Studio Canvas/PDF 증적이 같은 커밋에
  있다.
- 독점 한컴/HY glyph 자산을 저장소에 넣지 않으며, 실제 옛한글의 원문 의미를 전역 치환으로 바꾸지
  않는다.

이 단계에서는 암호 알고리즘·암호 UI/저장 정책, HWPX 23쪽 문서의 HWP3-PDF 직접 page 대조,
문서별 font-size 상수, 과거에만 보였고 최신 Studio에서 재현되지 않은 검은 셀을 범위에 포함하지
않는다.
