## 1. 목표와 현재 판단

최신 원격 `devel`의 검증된 기능을 v0.8.6으로 릴리스한다. 버전만 올리는 작업이 아니라 기여 계보, 사용자
변경 기록, 빌드·배포물, 공식 채널을 하나의 release candidate로 고정해 제3자가 대사할 수 있게 한다.

현재 `main..devel`은 2,214커밋, 17,373파일 차이다. `git shortlog`만으로 기여자를 세면 maintainer가
provenance를 보존해 cherry-pick·통합한 외부 PR author가 빠질 수 있다. 따라서 이번 릴리스는 수작업 명단을
정답으로 삼지 않고 Git 계보, GitHub PR 메타데이터와 PR review 기록을 교차 대사한 기여자 원장을 먼저 만든다.

### 1.1 현재 버전·게시 상태

| 표면 | 저장소 버전 | 2026-09-02 공개 상태 | v0.8.6 처리 |
|---|---:|---:|---|
| `Cargo.toml` / `@rhwp/core` | 0.8.4 | npm 0.8.4, 0.8.6 없음 | 0.8.6으로 갱신 |
| `npm/editor/package.json` | 0.8.5 | npm 0.8.4, 0.8.6 없음 | 0.8.6으로 갱신 |
| VS Code·Studio | 0.8.4 | 저장소 기준 0.8.4 | 0.8.6으로 갱신 |
| Chrome/Edge·Firefox·Safari | 0.8.4 | 저장소 기준 0.8.4 | 0.8.6으로 갱신 |

저장소의 editor 개발 버전이 이미 0.8.5이므로 메인테이너 결정에 따라 모든 공식 표면을 0.8.6으로 단조
증가시킨다. npm publish workflow는 이미 존재하는 동일 버전을 조회해 생략하지만, 이번 기준에서는 core와
editor 모두 0.8.6이 아직 없으므로 정상 신규 게시 대상이다.

### 1.2 동결 범위

- 기준은 `063041a2ced54085b5cf94c2e646ac7aa0e1960d`다.
- 열린 Draft PR #5953, #6458과 stacked #6467은 자동 포함하지 않는다.

  메인테이너가 base 갱신을 승인하기 전에는 병합·릴리스 후보에 자동 포함하지 않는다.
- 신규 기능, 신규 공식 배포 채널, #6243만의 main cherry-pick은 범위 밖이다.

## 2. 보호 불변식

1. `devel`과 `main`에 직접 push하지 않고 release-prep PR과 `devel -> main` release PR을 사용한다.
2. release base 이후 변경을 조용히 포함하지 않는다. base SHA 변경은 영향도·기여자·검증 계획과 함께 기록한다.
3. 기여자 목록은 Git author만으로 확정하지 않는다. GitHub PR author, co-author, cherry-pick·통합 provenance와
   보안 제보자 credit을 함께 대사한다.
4. 사람 기여자 집합은 기여자 원장, `CHANGELOG.md`, `CHANGELOG_EN.md`, GitHub 릴리스 노트에서 같아야 한다.
5. bot은 사람 기여자 수와 분리하고, 익명 요청이 있는 보안 제보자는 공개 명단에서 제외하되 disposition을 남긴다.
6. `Unreleased`의 항목을 무조건 전부 v0.8.6으로 이동하지 않는다. release base 포함 여부를 항목별로 확인한다.
7. `pkg/package.json` 같은 파생 파일을 직접 편집하지 않는다. 정본 버전에서 빌드가 생성하게 한다.
8. 최종 exact head에서 Rust·Docker WASM·Studio/E2E·배포물 검사와 5플랫폼 dry-run이 끝나기 전에는
   release PR을 merge-ready로 판정하지 않는다.
9. 태그는 승인된 `main` merge commit 하나에만 생성한다. 실패 복구를 위해 태그를 덮어쓰거나 재사용하지 않는다.
10. GitHub issue/comment, push, PR, merge, tag, release와 publish 재시도는 단계별 메인테이너 승인을 받는다.
11. #5949는 실제 v0.8.6 Linux AArch64 asset 검증 뒤 닫고, #6243은 별도 post-release canary 성공 전까지
    OPEN으로 유지한다.

## 4. 단계별 수행

### Stage R0 — 기준선·절차 고정

1. #6584, assignee, label, milestone과 중복 이슈 부재를 확인한다.
2. release base, `main`, v0.8.4 tag, 공개 npm 버전과 열린 PR을 snapshot한다.
3. 배포 정본은 `mydocs/manual/publish_guide.md`, GitHub 운영은
   `mydocs/manual/github_operations.md`, 검증은 PR review local validation 정본을 따른다.
4. 이 수행계획을 검토·승인하고 commit한 뒤에만 계측·구현으로 진입한다.

**종료 게이트**: release base와 비범위, 기여자·CHANGELOG·릴리스 노트 보호 불변식을 메인테이너가 승인한다.

### Stage R1 — 기여자 계보 계측과 원장

1. `v0.8.4..release base`의 commit author, `Co-authored-by`, commit message의 PR 참조와 merge parent를
   수집한다.
2. `gh`로 PR 번호, author, state, source branch와 merge·close 정보를 페이지네이션해 공개 JSON으로 수집한다.
3. 범위에서 추가·수정된 `mydocs/pr/archives/`와 commit의 cherry-pick·통합 기록을 대사한다. GitHub가
   원 PR 연결을 반환하지 않는 경우 release commit에 보존된 author·co-author를 정본 provenance로 사용한다.
4. 반복 실행과 집합 대사가 가능하도록 최소 contributor audit 도구와 fixture test를 만든다. 도구는 GitHub
   네트워크를 직접 신뢰하지 않고 미리 수집한 JSON과 로컬 Git 출력을 입력으로 받아 ledger를 만든다.
5. ledger 각 행에 공개 credit key, PR 목록, Git identity hash, evidence source, human/bot/anonymous,
   disposition을 기록한다. GitHub 계정이 확인되지 않은 직접 author는 다른 사람에게 임의 병합하지 않는다.
6. unresolved PR ref, 이름만 있고 handle이 없는 human, 근거 없는 handle이 0이 될 때까지 수동 대사한다.

**종료 게이트**: 공개 사람 기여자마다 범위 안 PR 또는 직접 Git provenance가 있고, 같은 입력의 재실행 결과가
결정론적이며 미해결 번호·정체성이 0이다.

### Stage R2 — 변경 목록·호환성·알려진 문제

1. Git 계보와 PR 원장에서 사용자 영향 변경을 parser/save, layout/render, editing/studio, CLI/agent, security,
   performance, packaging/operations로 분류한다.
2. `CHANGELOG.md`의 `Unreleased` 각 항목이 release base에 실제 포함됐는지 SHA·이슈로 확인한다.
3. 회귀가 해결되지 않았거나 배포 후 관찰이 필요한 항목은 알려진 문제와 후속 이슈로 분리한다.
4. 17,373파일 전체를 나열하지 않고 사용자 영향과 배포 위험을 대표하는 근거 PR·이슈를 고정한다.

**종료 게이트**: CHANGELOG 후보 항목마다 포함 SHA 또는 다음 사이클 이월 disposition이 존재한다.

### Stage R3 — 버전·CHANGELOG·릴리스 노트 구현

1. `Cargo.toml`을 0.8.6 정본으로 올리고 Cargo lock의 root package 버전을 정합시킨다.
2. VS Code, Studio, Chrome/Edge, Firefox, Safari의 정본 manifest를 0.8.6으로 맞춘다.
3. `npm/editor/package.json`은 개발 버전 0.8.5에서 0.8.6으로 올리고 게시 전 레지스트리 부재를 다시
   확인한다.
4. `CHANGELOG.md`와 `CHANGELOG_EN.md`의 v0.8.6 절, 날짜, 주요 변경, 호환성·알려진 문제와 기여자 절을
   같은 의미로 작성한다.
5. GitHub 릴리스 노트 초안을 별도 작성하고 기여자 원장의 사람 handle 집합과 두 CHANGELOG의 집합을
   기계적으로 비교한다.
6. README, THIRD_PARTY_LICENSES, store 제출 문서는 실제 변경 필요 여부를 대사하고 변경 없음도 근거와 함께
   기록한다.

**종료 게이트**: 모든 정본 버전이 0.8.6이고, 세 공개 기록의 사람 기여자 집합과 총 인원이 ledger와 일치한다.

### Stage R4 — 로컬 release candidate 검증

장시간·고비용 검증은 Stage R3 결과와 예상 시간을 보고한 뒤 별도 승인을 받아 실행한다.

1. release channel·version 계약, Markdown 링크와 packaging contract를 실행한다.
2. 파생 integration suite를 준비하고 fmt, native/WASM/workspace Clippy와 workspace build를 순차 통과한다.
3. `cargo nextest run --cargo-profile release-test --target-dir target/pr-review --tests --no-fail-fast`를
   현재 환경의 기본 동시성으로 실행한다.
4. Docker 정본으로 WASM을 빌드하고 생성된 npm core/editor package를 검사한다.
5. Studio·확장을 빌드하고 호스트 Chrome CDP E2E를 실행한다.
6. 공식 archive·store zip에 `.env`, token, 개인 폰트, `node_modules/`, `target/`, 불필요한 `dist/`가
   들어가지 않았는지 allowlist와 denylist로 검사한다.
7. 저작권 폰트, 라이선스, source zip 크기와 필수 파일을 확인한다.

**종료 게이트**: 실패 0건, 정책상 skip은 사유가 기록되고 배포물 비밀·개인 자산 검사 위반이 0건이다.

### Stage R5 — release-prep PR과 5플랫폼 dry-run

1. 단계별 문서·도구·버전·기록 변경을 commit하고 최신 release base drift를 확인한다.
2. push와 `devel` 대상 PR은 각각 별도 승인 뒤 수행한다.
3. Full CI·CodeQL·필수 workflow와 self-review를 통과한다.
4. exact PR head에서 승인 기반 `Release Binary(tag=test)`를 실행한다.
5. 다섯 build job, release job skip, Linux AArch64 `ubuntu-24.04-arm`, archive 4파일, 실행권한, ELF AArch64,
   `rhwp v0.8.6`을 독립 검증한다.
6. 최신 `devel`에 승인되지 않은 추가 commit이 있으면 병합하지 않고 R1~R4 영향도를 갱신한다.

**종료 게이트**: `MERGEABLE / CLEAN`, 모든 check 성공, exact-head dry-run과 기록 self-review 승인.

### Stage R6 — `devel -> main` release PR

1. release-prep PR 병합 뒤 로컬 `devel`을 원격과 동기화하고 후보 SHA를 다시 고정한다.
2. `main`과의 merge-tree, 2,214커밋 이상 누적 범위, workflow·permission·branch protection 영향을 대사한다.
3. 승인된 릴리스 노트와 contributor/change inventory를 본문 근거로 `main` 대상 release PR을 연다.
4. Full CI, CodeQL, Pages, review와 일반 merge commit 승인을 거친다.
5. merge 뒤 `main`의 trusted controller SHA·event·최소 권한을 live 확인하되 release PR을 #6243 canary로
   오인하지 않는다.

**종료 게이트**: 승인된 exact merge commit이 `main`에 포함되고 Pages와 필수 post-merge check가 성공한다.

### Stage R7 — 태그·GitHub Release·자동 게시

1. 태그·Release 생성 직전 `main` exact SHA, 버전, 미게시 npm 0.8.6과 draft notes를 재확인한다.
2. 별도 승인 뒤 정본 절차로 v0.8.6 tag와 GitHub Release를 생성한다.
3. Release Binary의 다섯 archive와 `SHA256SUMS.txt`를 다운로드해 이름·해시·내부 구조·버전을 검증한다.
4. Linux AArch64는 ELF machine, 실행권한과 native runner log를 다시 확인한다.
5. `Publish All Packages`의 `@rhwp/core`, `@rhwp/editor`, VS Code/Open VSX 결과를 확인한다. 이미 게시된
   immutable 버전은 workflow의 skip guard만 허용하고 덮어쓰지 않는다.

**종료 게이트**: GitHub Release와 자동 게시 채널의 exact v0.8.6 결과가 모두 확인된다.

**완료 조건**: 기록·코드·asset·공식 채널의 v0.8.6 정합이 확인되고 #5949/#6243 경계가 보존된다.

## 6. rollback과 실패 처리

- `devel` 병합 전: 작업 branch에서 수정하고 실패 산출물은 게시하지 않는다.
- `devel` 병합 후·`main` 전: revert PR 또는 release-prep 정정 PR로 복구하며 admin push하지 않는다.
- `main` 병합 후·태그 전: 영향과 rollback 후보를 보고하고 승인된 PR로만 정정한다.
- 태그·Release 후: immutable npm·store 버전을 덮어쓰지 않는다. workflow 재시도와 후속 PATCH 여부를 분리한다.
- contributor 누락 발견: 공개 전에는 기록 gate 실패로 중단한다. 공개 후에는 CHANGELOG·릴리스 노트를 즉시
  정정하되 이미 게시된 package bytes를 바꾸지 않고 후속 기록 PR로 계보를 남긴다.
- #6243 Full fallback은 안전한 성능 회귀다. 잘못된 fast-pass나 권한 확대가 아니면 v0.8.6 rollback 사유로
  과장하지 않는다.
