# #9154 Ubuntu runner 기준과 Native ABI 보완 계획

Issue: [#9154](https://github.com/edwardkim/rhwp/issues/9154)

## 작업 지시와 기준

사용자는 Ubuntu 전환 영향 브리핑 뒤 “이슈로 등록해서 진행합니다.”라고 지시했습니다.
이 지시와 브리핑의 권고 범위에 따라 이슈 등록·계획·로컬 구현·검증을 진행합니다.
원격 push·PR·merge·새 workflow dispatch와 main 적용은 실제 후보·검증 결과를 갖춰
별도 승인 범위를 확인합니다.

- 기준 devel: `1e2488ebd432deb7c326be532f8a91945f260231`.
- 현재 main: `7213ed1f96266b95e22cd5645a07851c9c18298e`.
- branch: `task/9154-ubuntu-runner-baseline`.
- 중복 검색: 열린 동일 범위 issue/PR 없음. #536은 멀티 렌더러 부모 로드맵으로 보존합니다.
- 운영 분류: job runner/matrix·cache와 ABI 검사 명령의 O3. 제품 Rust/JS·조판·허용치는 변경하지 않습니다.

## 근거와 한계

[GitHub 공지](https://github.com/actions/runner-images/issues/14748)는 `ubuntu-latest`의
24.04→26.04 전환을 예고합니다. 양 branch의 25개 workflow 중 24개, matrix 확장 전
45개 job 정의가 이 label을 사용하지만 metadata/control과 제품 빌드 작업은 구분합니다.

표준 CLI는 앞선 GLIBC_2.43/Ubuntu 24.04 실행 실패를 보정해 Linux x86_64/ARM을
각각 24.04/24.04-arm으로 고정했습니다. [선행 보정과 독립 실행 근거](../working/release_0_9_0_ci_runtime_corrections.md)를
보존합니다. 현재 Native host `.so`의 ABI 실패를 이미 검출한 것은 아니며 실제 산출물로 확인합니다.

Fuzz 실패·재실행 성공은 모두 26.04, 같은 code/nightly였지만 image build와 runner가 달랐습니다.
재실행은 HML 61초·240,550입력과 전체 6타깃을 통과했습니다. 종료 신호의 근본 계기는 미확정이며
이 변경을 그 원인의 입증 또는 영구 제거로 설명하지 않습니다.

## 구현 범위

1. Native host Linux package를 `ubuntu-24.04`로 고정합니다. 실제 ELF의 요구 GLIBC 버전을
   검사하는 별도 도구를 기존 packaging job에 연결하고 2.39 초과·불명확한 ABI 요구는 실패 처리합니다.
   기존 capability probe·headless 편집/저장 재열기·세 플랫폼 artifact 계약은 유지합니다.
2. 주요 실제 실행 job을 24.04로 고정합니다. 대상은 CI의 lint/Native/frontend/WASM,
   nextest archive build/worker, CodeQL analyze, Render Diff worker, Adapter/Proptest worker,
   Pages build와 npm의 WASM/VSIX build입니다. metadata/preflight/집계·게시 전용 job은 구분합니다.
   표준 CLI의 기존 Linux/ARM runner와 macOS/Windows는 보존합니다.
3. 기존 수동 Fuzz·Full Renderer Sweep에 `runner_image` 선택(24.04 기본, 26.04 명시)을 추가합니다.
   schedule은 24.04를 사용하고, 임의 runner 입력은 거부합니다. 기존 시간·matrix·검사 명령·
   권한·PR 자동 실행 경계는 유지하며 새 무거운 workflow나 중복 CI 호출을 만들지 않습니다.
4. 영향받은 직접 작성 Cargo cache key/restore prefix와 Native build shared key를 OS 기준별로
   구분합니다. 수동 26.04 결과가 24.04 key로 저장·복원되지 않게 검사합니다.
5. 기존에 CI가 호출하는 `test_release_channel_policy_workflow.py`를 확장해 runner·수동 선택·
   cache 격리·Linux ABI gate를 검증합니다. ABI helper의 독립 입력 계약도 같은 기존 테스트
   실행 경로에 둡니다. 새 테스트라는 이유만으로 CI 개별 호출을 추가하지 않습니다.
6. 운영 매뉴얼·Native 패키징 안내에 baseline, 26.04 대조법, cache와 main 적용 경계를 기록합니다.

## 실제 검증과 완료 gate

Oracle·layout advisory도 실제 제품 CLI를 빌드·실행하므로 같은 기준에 포함합니다.
별도 Gym benchmark와 skill-router 도구 실행은 이번 제품 baseline 범위에 넣지 않습니다.

- workflow YAML·기존 workflow/CI 영향/승격/재사용 계약과 actionlint를 실행합니다.
- ABI helper는 정상·상한 초과·숫자 버전 순서·정의/요구 구분·잘못된 ELF·도구 실패를 확인합니다.
- 최종 source의 Native FFI를 Ubuntu 24.04/Rust 1.93.1에서 실제 빌드합니다. Cargo는 기본
  작업공간 `/home/edward/mygithub/rhwp/target/pr-review` 하나를 사용하며 다른 Cargo와 겹치지 않습니다.
- 실제 `.so`의 요구 버전·해시·동적 의존성을 확인하고 package/capability/headless IME 편집·저장·
  재열기를 실행합니다. 사용 가능한 Docker의 Ubuntu 24.04와 26.04에서도 같은 package를 소비합니다.
  GPU·Qt 실기기 검증이나 새로운 독립 한컴 조판 정확도 검증으로 확대 해석하지 않습니다.
- 소스/테스트/기준값을 바꾸지 않은 제품 전체 Rust 회귀·Visual Sweep은 의례적으로 반복하지 않습니다.
  변경한 실행·도구·package의 실제 경로와 정책 검증을 완료합니다.
- 최신 base·본인 열린 PR·병합 시뮬레이션을 확인한 뒤 검증된 후보의 원격 처리안을 제시합니다.
  새 head의 필수 CI와 별도 승인된 Native/Fuzz/Renderer 실행 증거가 필요합니다.
- CI 실행 정의 변경이므로 후속 기록은 옵션 2입니다. devel 수용 뒤 main workflow 적용과
  실제 schedule/수동 선택·cache hit/save·Native artifact 동작 관찰은 별도 gate입니다.

## 복구와 제외 범위

설정 보정은 이전 workflow label·cache prefix와 수동 선택 추가를 되돌릴 수 있게 분리합니다.
새 cache를 이전 OS key에 합치지 않으며 cache 전량 삭제·보호 설정·token·release 재게시를 하지 않습니다.
기존 다른 작업과 사용자 글꼴·Studio/CDP를 보존합니다. 검증과 후속 처리가 종료된 뒤에만
작업 전용 worktree/branch와 기본 작업공간 output/debug를 정리합니다.

## 수동 Fuzz 시간 초과 후 승인된 보정

24.04 수동 실행 44072235493에서 HML·OOXML Chart는 성공했으나 WMF·HWP·HWPX·HWP3는
GitHub annotation의 45분 job 상한 초과로 취소됐다. 종료 로그는 BlobNotFound였고 단일
Smoke-run 단계에 컴파일·퍼징이 함께 있어 어느 구간이 길었는지는 확정하지 못했다.
별도로 캐시의 configured budget 도달·read-only 경고를 관측했으며 인과를 단정하지 않는다.

사용자는 60분·단계 분리·추가 검증안을 승인했다. Fuzz job 예산을 45→60분으로 조정하고
`cargo +nightly fuzz build`와 기존 run을 분리한다. 기본 60초·입력별 30초·RSS 2GiB·6개 타깃·
nightly·OS 선택·cache namespace는 유지한다. 단계별 새 상한으로 수동 실행 시간을 제한하지 않는다.

workflow 계약 263건·정책 339건·actionlint와 실제 최소 대조군의 build→run을 검증했다.
최소 대조군은 로컬 Rust 1.100.0-nightly / cargo-fuzz 0.13.2에서 build 13.273초·run 2.33초였고
두 번째 컴파일은 없었다. 이는 CLI 단계 분리 검증이며 실제 rhwp 6개 타깃의 60분 완료는
새 head의 원격 실행으로 확인한다.

적용 승인 범위는 commit·push·새 head CI, 기존 26.04 실행이 남아 있으면 그 실행만 일반 취소,
새 source의 24.04/26.04 Fuzz 각 1회다. 기존 Native·Renderer 실행은 해당 workflow·제품 source의
동일성을 기록해 유지한다. source·한도·검사 범위가 달라지는 재사용을 임의로 적용하지 않는다.
한 ref의 Fuzz concurrency에서 pending이 교체되지 않도록 첫 실행 시작을 확인한 뒤 두 번째를 접수한다.
기존 self-review·merge·옵션 2 후속 기록 승인은 유지하며 main·cache 삭제·budget 설정은 제외한다.


push 직전 devel의 #9156 추가 병합(`22da83586a`)을 확인했다. 작업 branch의 제품 source를
고정한 채 충돌 없는 실제 병합 tree를 만들었고, 그 제품 code가 최신 devel과 같음을 확인했다.
실제 병합 결과에서 탭·직선 개체 흐름·진단의 새 회귀 7건을 파일 시스템 격리 최소 글꼴 환경으로
실행해 모두 통과했다. PR CI는 기본 checkout의 GitHub merge ref에서 이 병합 결과를 검증한다.
수동 Native·Renderer의 실제 source와 PR의 실제 병합 결과를 구분해 기록하며 동일 source라고
잘못 표기하지 않는다.

## Fuzz 컴파일 메모리의 추가 보정안

새 head `b931460f9c`의 24.04 HWP3는 빌드 중 60분 job 상한을 초과했다. 두 OS의 HWP는
각각 27분 2초·25분 40초의 runner shutdown·exit 143이므로 원인을 구분한다. 사용 중단 경고를
컴파일 오류로 보지 않으며, 원격 OOM이나 종료 신호의 기원은 아직 확정하지 않았다.

같은 source·Rust 1.102.0-nightly·cargo-fuzz 0.13.2·Ubuntu 24.04의 실제 로컬 빌드는
24분 14초에 성공했지만 GNU time의 최대 RSS는 16.64 GiB였다. 기본 단일 codegen unit을
16개로 나눈 실제 target 재빌드는 8분 46초·13.18 GiB로 성공했다. host/proc-macro 캐시를
재사용했고 호스트 CPU 수가 다르므로 시간 차이를 원격 성능 보장으로 일반화하지 않는다.

양 구성에서 실제 HWP·HWP3 60초 퍼징과 같은 느린 생성 입력의 30초 이내 재실행이 통과했다.
ASan·coverage·trace-compares·debug assertions·최적화 설정을 실제 rustc 명령으로 대조했다.
[측정 원문·명령·입력 해시](../working/assets/issue9154/fuzz-codegen-memory.json),
[기본 RSS 원문](../working/assets/issue9154/fuzz-cgu1-build-resources.txt),
[분할 RSS 원문](../working/assets/issue9154/fuzz-cgu16-build-resources.txt)를 보존한다.

제안은 build와 run 모두 `--codegen-units 16`을 사용하게 하는 한정 실행 정의 보완이다.
job 60분·퍼징 60초·입력별 30초·RSS 2 GiB와 6타깃·nightly·OS 선택·cache 정책은 유지한다.
실제 GitHub 두 OS의 새 source 검증과 새 head 필수 CI를 완료해야 수용할 수 있다.
이 추가 보정의 commit·push 및 현재 미완료 Fuzz 복구를 새 source 각 OS 1회로 대체하는 범위는
구체적인 patch와 검사 결과를 준비한 뒤 사용자 승인을 확인한다. 기존 Native·Renderer 실행과
self-review·merge·옵션 2 후속 기록 범위는 보존하며 main과 cache budget은 변경하지 않는다.
