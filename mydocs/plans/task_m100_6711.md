## 2. 거버넌스 결정

### 2.1 정본과 안내 문서

1. `mydocs/manual/codex/docs_and_git_workflow.md`가 월별 아카이빙의 canonical 정본이다.
2. `mydocs/README.md`는 정보구조 변경과 작업 증적의 월별 아카이빙을 구분하고 정본을 연결한다.
3. `mydocs/manual/hyper_waterfall_docs_guide.md`는 누적 기록을 보존하면서 현재 탐색 비용을
   줄여야 하는 이유를 설명하되 세부 규칙을 복제하지 않는다.
4. `AGENTS.md`는 이미 모든 문서·Git 작업이 정본을 읽도록 지시하므로 별도 중복 규칙을 넣지 않는다.

### 2.2 경로와 상태의 분리

- 다섯 폴더의 직접 하위는 **당월에 최초 생성된 Markdown의 작업 집합**이다.
- `archives/`는 완료·폐기 상태가 아니라 **생성 월에 따른 보관 위치**다.
- 열린 이슈나 PR에 속한 이전 달 문서도 이동한다. 이동만으로 이슈·PR을 닫거나 문서의 의미를
  historical로 바꾸지 않는다.
- 이전 달 문서를 계속 갱신해야 하면 archive 경로를 정본 경로로 사용한다.
- 현재 월 작업을 훑을 때는 root를 우선하고, 특정 이슈·PR·원인 계보를 조사할 때는 root와
  `archives/`를 함께 검색한다.

### 2.3 반복 시점과 판정 기준

1. 매월 첫 유지보수 구간에 전월까지 생성된 직접 하위 `*.md`를 이동한다.
2. 기준은 `Asia/Seoul` 당월 1일 00:00 미만이다.
3. filesystem mtime은 clone·checkout으로 바뀌므로 사용하지 않는다.
4. Git 최초 도입 commit의 author timestamp를 사용한다. `--diff-filter=A`로 추가 commit을 찾지
   못한 merge 유입 경로는 전체 이력에서 그 경로가 처음 존재한 commit을 근거로 삼는다.
5. 아직 Git에 들어오지 않은 파일이나 최초 시점을 결정할 수 없는 파일은 자동 추정하지 않고
   예외 원장에 남겨 메인테이너 판단을 받는다.
6. 직접 하위 Markdown만 대상으로 하며 assets·evidence·주제별 중첩 디렉터리는 건드리지 않는다.

### 2.4 충돌과 링크

- 목적지 파일이 없으면 basename을 유지해 `archives/`로 옮긴다.
- 목적지와 SHA-256이 같으면 기존 archive를 유지하고 root의 byte-identical 중복만 제거한다.
- 목적지와 내용이 다르면 덮어쓰지 않는다. root 문서는
  `<stem>_archived_<YYYYMMDD>_<blob7>.md`로 보존하고 충돌 원장에 두 경로와 hash를 기록한다.
- repository-relative·문서 상대 Markdown 링크는 원래 해석 대상을 기준으로 새 상대 경로를 계산해
  같은 commit에서 갱신한다.
- root를 다시 채우는 redirect stub은 만들지 않는다. 외부 이력에서 현재 branch 경로가 필요한
  예외가 발견되면 일괄 stub 대신 별도 canonical index나 해당 외부 링크를 정정한다.

기준선 충돌 16건 중 다음 12건은 byte-identical 중복이다.

- `plans/task_m100_1363.md`, `plans/task_m100_1363_v2.md`
- `pr/pr_2331_maintainer_review.md`
- `report/task_m100_1363_report.md`
- `working/task_m100_1363_stage1.md`부터 `stage5.md`
- `working/task_m100_1363_v2_stage1.md`부터 `stage3.md`

다음 4건은 내용이 다르므로 suffix 이름으로 양쪽을 보존한다.

- `plans/task_m100_1880.md`
- `plans/task_m100_2214.md`
- `pr/pr_1844_review.md`
- `pr/pr_2370_review.md`

## 3. 보호 불변식

1. 이동 전후 문서의 byte 내용과 Git 계보를 보존한다. 링크 정정은 별도 내용 변화로 원장에 구분한다.
2. 서로 다른 문서를 덮어쓰거나 임의 삭제하지 않는다.
3. archive 이동을 이슈·PR 생명주기 변경으로 해석하지 않는다.
4. 2026년 9월 생성 문서는 root에 유지한다.
5. 완료 시 cutoff 이전 생성 direct Markdown은 대상 root에 남지 않는다.
6. canonical 기본 링크 검사 0건을 유지하고 historical 전수 기준선에 신규 오류를 추가하지 않는다.
7. 문서 metadata 검사에서 신규 오류를 만들지 않는다.
8. redirect stub으로 root 문서 수를 다시 증가시키지 않는다.
9. 사용자·다른 contributor의 미커밋 작업을 변경하지 않는다.
10. 문서 전용 변경을 이유로 Rust·Cargo·WASM 검증을 실행하지 않는다.

4. divergent 충돌 2건을 suffix 경로로 보존한다.

한도를 넘었다. 따라서 승인된 fail-closed 분할 규칙을 적용해 다음 batch를 분리한다.

2. `pr`, `report`의 832개 후보와 관련 링크·canonical metadata를 이동 경로로 갱신한다.
3. 동일 중복 2건과 divergent 충돌 2건을 같은 규칙으로 처리한다.

**종료 게이트**: 보수적 변경 파일 수가 3,000개 미만이고, `pr/report` root에는 cutoff 이전

### Stage 3 — 최신 devel 동기화와 working batch

1. PR 1 merge 뒤 새 continuation branch를 최신 `upstream/devel`에서 만든다.
2. `working`의 2,239개 후보와 관련 링크를 같은 원칙으로 이동한다.

**종료 게이트**: working root에는 9월 생성 문서만 남고 신규 링크 오류가 없다.

### Stage 4 — 전수 감사와 최종 보고

1. 다섯 root의 잔여 문서를 Git 최초 생성일로 전수 재검사한다.
2. 이동 전후 수량·SHA-256·충돌·링크 집합을 대조한다.
3. canonical 링크·metadata·diff 검사를 실행한다.
4. 실제 root 감소율, PR별 변경 파일 수, 예외와 다음 월 실행 순서를 최종 보고서에 기록한다.
5. `mydocs/report/task_m100_6711_report.md`를 메인테이너가 승인한 뒤 이슈 완료를 판단한다.

**종료 게이트**: 3,844개 후보가 손실 없이 처리되고, 기준선의 9월 문서 72개와 #6711 수행 중
새로 생성된 9월 문서만 root에 남는다.

## 5. PR 크기 방어

[GitHub REST의 pull request file 목록](https://docs.github.com/en/rest/pulls/pulls?apiVersion=2022-11-28#list-pull-requests-files)은
최대 3,000개다. CI impact classifier가 이 목록을 사용하므로 대량 문서 이동을 단일 PR로 보내면
분류 입력이 잘릴 수 있다.

- 기본은 Stage 1 실측으로 확정한 `orders/plans`, `pr/report`, `working` 순차 PR이다.
- 각 push 전 `git diff --name-status --find-renames upstream/devel`과 rename 판정에 기대지 않는
  old/new path 합계를 모두 기록한다.
- GitHub가 rename을 일부 add/delete로 판단해도 3,000개를 넘지 않는 보수적 batch를 사용한다.
- 추가 분할이 필요해도 #6711 안에서 처리하며 자식 이슈를 만들지 않는다.
- 후속 PR은 반드시 앞 PR이 반영된 최신 `upstream/devel`에서 시작한다.

## 6. 검증

각 PR에서 다음을 실행한다.

```bash
git diff --check
python3 scripts/check_markdown_links.py
python3 scripts/check_document_metadata.py
```

추가 감사 항목:

- cutoff 이전 direct Markdown 잔여 0건
- 계획된 후보 수와 실제 rename·dedupe·collision-preserve 합계 일치
- 이동 전후 source/destination SHA-256 대조
- 기존에 유효했던 내부 링크가 이동 뒤 깨진 경우 0건
- historical 전수 링크 오류 집합에 신규 항목 0건
- 이동 파일은 합의한 `mydocs/**` 범위인지 확인하고, 범위 밖 변경은 이동 문서로 들어오는
  Markdown 링크의 새 경로 갱신에만 한정
- Rust source, Cargo manifest/lockfile, WASM, workflow 변경 0건

`check_document_metadata.py`와 historical 전수 링크 검사에는 기존 오류가 있으므로 단순 exit code만으로
판정하지 않는다. 기준선과 결과 집합의 차이를 비교해 **신규 오류 0건**을 증명한다.

### Stage 3-A CI 피드백 반영

첫 PR head `f73a68590d`에서 Gym 계약 테스트가 이동 전 `mydocs/working/gym_*.md`를 실행 경로로
하드코딩한 사실이 드러났다. 승인된 수정 계획에 따라 Markdown 링크뿐 아니라 test·tool·generator의
실제 경로 소비자를 archive 위치로 갱신하고, 역사적 `canonical`과 과거 증적 문자열은 보존한다.
Rust integration source를 포함한 경로 계약이 바뀌므로 Stage 3-A의 검증 범위는 문서 기본 검사에서
해당 Python 계약 테스트와 Rust 필수 lint/build 묶음까지 확대한다.

첫 정정 head `03417efe2d`의 Archive C 실행에서는 완성된 경로 문자열 검색으로 잡히지 않은
`tests/cases/agent_surface_skill_contract.rs`의 분할 `.join(...)` 경로 1건이 추가로 드러났다.
따라서 같은 실행 소비자 감사에서 완성 문자열과 경로 조각 조립을 별도 검색하고, 발견한 계약의
focused nextest와 Rust 필수 lint/build 묶음을 다시 실행한다.

## 8. 비범위와 rollback

- `feedback`, `manual`, `tech`, `troubleshootings`의 월별 이동은 비범위다.
- 중첩된 assets·evidence·주제 디렉터리를 재분류하지 않는다.
- GitHub Actions 자동 아카이빙과 새로운 CI gate를 만들지 않는다.
- 이 작업에서 이슈·PR을 일괄 close하지 않는다.
- 과거 Git history를 재작성하지 않는다.
- merge 전 rollback은 해당 task branch 폐기다. merge 뒤에는 PR 단위 revert로 이전 경로와 링크를
  함께 복원한다.
