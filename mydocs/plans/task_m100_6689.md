## 3. 왜 기존 절차가 놓쳤는가

1. PR #5366 검토 기록은 “nightly runner는 원격 workflow에서 확인 필요”라고 정확히 적었지만, 그것을
   merge 종료 조건이나 별도 증적 필드로 바꾸지 않았다.
2. 통합 PR #5425의 CI·CodeQL·Render·Proptest가 모두 성공했어도 새 `Fuzz smoke` workflow 자체는 check
   목록에 없었다. 일반 CI 성공을 신규 workflow 성공으로 잘못 대체할 수 있는 구조였다.
3. `workflow_dispatch` 선언을 실행 가능성으로 간주했다. 그러나 GitHub의 수동 dispatch는 workflow 파일이
   기본 브랜치에 있어야 하며, API의 `ref`도 branch 또는 tag다. 따라서 신규 workflow에는 별도
   pre-main 경로가 필요하고, 기존 workflow도 실행 뒤 실제 `head_sha`를 다시 확인해야 한다.
4. 릴리즈 준비는 제품·패키지 검증은 상세했지만 `main` tree와 최종 `devel` tree 사이 workflow
   add/modify/delete, trigger·permission·matrix 차이를 독립 inventory로 만들지 않았다.
5. 실행 증적을 candidate commit에 다시 커밋하면 commit SHA가 바뀌는 자기참조 문제가 생긴다. 그러므로
   exact-SHA run 영수증은 Actions run·artifact·PR check 같은 Git 외부 증적으로 보존해야 한다.

GitHub 공식 계약상 workflow run은 event에 연결된 ref의 workflow 버전을 사용하고,
`workflow_dispatch`는 기본 브랜치 등록이 필요하다. reusable workflow는 고정 SHA로 호출할 수 있지만
`uses`에 동적 expression을 넣을 수 없으므로, 임의의 신규 candidate YAML을 특권 controller가 동적으로
실행하는 해법으로 사용하지 않는다.

- [Triggering a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)
- [REST workflow dispatch](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)
- [Reuse workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)
- [Workflow·ref 실행 모델](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows)

## 4. 채택 구조

### 4.1 결정적 inventory

표준 라이브러리만 쓰는 도구를 `scripts/`에 두고 두 Git tree의 `.github/workflows/*.yml`과
`.github/actions/**`를 Git blob으로 비교한다. 결과는 JSON과 사람용 Markdown으로 같은 정렬 순서에서
생성한다.

- add, modify, delete, rename과 before/after Git blob·SHA-256을 기록한다.
- YAML 전체 parser를 흉내 내지 않는다. block scalar 본문은 그대로 보존하고, YAML scalar 밖의 주석과
  빈 줄만 제거하는 보수적 fingerprint가 같을 때만 `comment-only`로 판정한다.
- 재정렬·들여쓰기·인용부호 변경처럼 의미 동등성을 확정할 수 없는 변화는 실행 변경으로 fail-closed 한다.
- trigger, permission, secret 참조, matrix, `uses`, cache, artifact, timeout, concurrency, 배포 명령의
  before/after 신호를 별도 위험 축으로 보고한다.
- main 고유 commit이 있는 현재 상태를 숨기지 않도록 base SHA, candidate SHA, merge-base와 예상 merge
  tree를 함께 기록한다.

### 4.2 증적 봉투와 검증기

실행 증적은 다음 최소 필드를 가진다.

- base SHA, candidate head SHA, 필요 시 PR merge SHA
- workflow path, Git blob, content SHA-256
- run ID·URL, event, head branch, head SHA, workflow identity
- 기대 job 집합과 실제 conclusion
- inventory hash와 생성 시각
- 직접 실행인지 동등 실행 adapter인지 구분하는 `executionMode`

검증기는 GitHub API snapshot을 입력으로 받아 같은 결과를 재현한다. candidate SHA 불일치, workflow hash
불일치, missing/pending/failed/cancelled/skipped 필수 job, pagination 누락, 허용하지 않은 actor·event는
모두 실패다. `continue-on-error` workflow는 run의 녹색만 보지 않고 해당 도구의 verdict·artifact 존재까지
확인한다.

### 4.3 신규 workflow의 pre-main 실행 계약

기본 브랜치에 없는 신규 workflow를 generic controller가 임의로 실행하지 않는다. 신규·고위험 workflow는
다음 중 하나를 명시해야 한다.

1. candidate PR 또는 신뢰 `devel` push에서 secret·write 없이 실제 job을 실행하는 lane
2. production workflow와 동일한 repository script/composite action을 exact candidate checkout에서
   실행하는 동등 adapter
3. 실행 불가 사유가 있는 승인 waiver

동등 adapter는 YAML event orchestration 전체가 실행됐다고 주장하지 않는다. 공유 실행 로직과 정적
trigger·permission 검사까지 각각 무엇을 증명했는지 봉투에 분리한다. 이번에 새로 추가하는 promotion
검사 자체가 task PR의 `pull_request`에서 실행되는 것을 첫 pre-main bootstrap 실증으로 삼는다.

### 4.4 기존 required context에 fail-closed 연결

새 required check 이름을 즉시 branch protection에 추가하지 않는다. canonical `devel -> main` release PR인
경우에만 `ci.yml`의 promotion job이 inventory와 증적을 검증하고, 기존 `Build & Test` aggregate가 그
결과를 요구하게 한다.

- 일반 devel PR은 정책 unit test와 자기 bootstrap만 수행한다.
- fork head를 privileged event나 write token으로 checkout하지 않는다.
- Actions 조회는 `actions: read`, source는 `contents: read`, PR 조회가 필요하면 `pull-requests: read`만 쓴다.
- workflow 실행을 gate가 자동 재귀 dispatch하지 않는다. 실행은 승인된 preflight 단계에서 만들고 gate는
  증적을 읽어 검증한다.
- `main`과 `devel`이 갈라진 상태에서는 base/head/merge tree가 일치하지 않으면 중립 통과하지 않고
  원격 동기화 또는 명시적 merge 결과를 요구한다.

### 4.5 waiver

waiver는 검증 실패를 지우는 flag가 아니다. maintainer가 작성한 GitHub sideband record에 candidate SHA,
workflow hash, 적용 job·위험 축, 사유, 승인자, 만료 시각, 후속 검증을 기록한다. 검증기는 작성자 권한,
exact scope와 만료를 확인하고, secret 노출·권한 상승·실패 테스트 은폐에는 waiver를 허용하지 않는다.

## 5. 보호 불변식

1. fork 또는 신뢰하지 않는 PR head를 `pull_request_target`, write token, release/package secret으로 실행하지 않는다.
2. candidate exact SHA와 workflow content hash가 함께 맞지 않으면 과거 녹색 run을 재사용하지 않는다.
3. main-only commit과 synthetic merge tree를 candidate head와 같은 것으로 간주하지 않는다.
4. 신규 workflow 실행 불가를 `success`로 바꾸지 않고 adapter와 waiver의 증명 범위를 명시한다.
5. `continue-on-error`, trigger 삭제, 짧은 matrix, `continue-on-error` 추가로 실제 실패를 숨기지 않는다.
6. 모든 scheduled workflow를 일반 PR required check로 바꾸지 않는다.
7. controller는 다른 workflow를 자동 재귀 dispatch하지 않고 runner 비용·timeout·concurrency 상한을 둔다.
8. Pages·package·release write job은 verify-only 실행에서 절대 동작하지 않는다.
9. evidence에 secret 값, private corpus, 개인 폰트, 인증 URL을 넣지 않는다.
10. #6634의 publish chaining과 #6689의 workflow preflight 판정을 하나의 성공 조건으로 합쳐 원인을 흐리지 않는다.

## 6. 단계별 수행

### Stage 1 — 기준선·RED 계약

1. 위 8개 workflow의 before/after blob, 실행 의미 변화와 live run 유무를 조사 문서에 고정한다.
2. comment-only, block scalar 내부 변경, trigger·permission·secret·matrix·artifact·action ref 변경,
   add/delete/rename fixture를 먼저 만든다.
3. exact SHA 불일치, stale run, missing job, failed/skipped job, 만료·범위초과 waiver가 실패하는 RED test를 작성한다.

**종료 게이트**: 현재 8개 workflow 위험도가 수작업 판정과 같고, 과거 #5366/#5425 증적을 넣으면
`Fuzz smoke evidence missing`으로 실패한다.

### Stage 2 — inventory·evidence verifier 구현

1. Git blob 기반 inventory와 보수적 comment fingerprint를 구현한다.
2. 고위험 축과 external action SHA pin 위반을 구조화한다.
3. GitHub run/job snapshot과 waiver를 검증하는 offline verifier를 구현한다.
4. JSON 출력 순서·hash·exit code를 반복 실행으로 고정한다.

**종료 게이트**: Stage 1 RED 전건이 GREEN이며 API 장애·분류 불명은 모두 fail-closed 한다.

### Stage 3 — 실제 실행 경로와 배포 안전 경계

1. 현재 8개 workflow를 direct run, contracts-only, verify-only adapter로 분류한다.
2. `deploy-pages.yml`은 수동·preflight 실행에서 build만 하고 Pages write/deploy는 `main` push에서만
   가능하도록 실제 job 조건을 분리한다.
3. Gym은 contracts lane만 release workflow 변경 증적으로 인정하며 전건 benchmark를 제품 release gate로
   되돌리지 않는다.
4. Oracle advisory는 run success와 별도로 비교 verdict/artifact를 증적에 포함한다.
5. 새 promotion 경로 자체가 default branch 반영 전 task PR exact head에서 실행되는지 실증한다.

**종료 게이트**: 신규 workflow pre-main 경로, write job 미실행, exact content hash를 실제 GitHub run으로
보인다. remote push·PR·workflow 실행은 각각 별도 승인을 받는다.

### Stage 4 — release gate·문서 연결

1. canonical `devel -> main` PR에서만 inventory와 증적을 검사하는 CI job을 추가한다.
2. 기존 `Build & Test` aggregate가 해당 job의 성공을 요구하도록 하고 일반 PR·fork·push의 run/no-run을
   계약 테스트로 고정한다.
3. `github_operations.md`에 workflow 승격 절차·waiver·복구를 추가한다.
4. `publish_guide.md`에 main 대비 inventory, candidate evidence, #6634 독립 상태를 release checklist로 연결한다.

**종료 게이트**: 증적 누락 fixture에서는 release promotion이 실패하고, 완전한 봉투만 통과한다.

### Stage 5 — Fuzz smoke 6-matrix dogfood

1. 실행 직전 `upstream/devel` exact SHA가 움직이지 않았는지 확인한다.
2. 별도 승인 뒤 `Fuzz smoke`를 `devel` ref에서 6개 matrix로 한 번 dispatch한다.
3. 반환 run의 `head_sha`, workflow path/hash와 6개 job conclusion을 증적 봉투로 고정한다.
4. 알려진 `parse_wmf` failure가 재현되면 숨기지 않고 제품 결함으로 분리 기록한다. 이 이슈의 preflight
   장치 성공과 Fuzz 제품 성공을 같은 판정으로 쓰지 않는다.

**종료 게이트**: `devel` exact candidate에서 6개 job이 실제 생성됐고, 성공·실패 결과가 빠짐없이 보존된다.

### Stage 6 — 최종 검증·보고·PR

1. workflow 정책 unit test, 변경된 job command의 focused test, `git diff --check`, Markdown link·metadata를 실행한다.
2. 최신 `upstream/devel`과 main 고유 commit의 drift, 열린 workflow PR 충돌을 다시 확인한다.
3. `mydocs/report/task_m100_6689_report.md`에 run URL·SHA·hash·job 결론·비용·rollback을 기록한다.
4. push와 PR 생성은 각각 승인 뒤 수행하고, PR exact head에서 release promotion의 positive/negative 계약을
   self-review한다.

workflow 변경이라는 이유로 무관한 renderer·WASM 전체를 의례적으로 실행하지 않는다. 다만 실제

## 8. rollback과 승인 게이트

- 로컬 단계: task branch commit을 정정하며 사용자 WIP와 다른 worktree를 건드리지 않는다.
- PR 전: latest devel과 merge-tree를 재계산하고 충돌이나 main-only 의미 손실이 있으면 push를 멈춘다.
- merge 전: gate가 required context를 사라지게 하거나 fork에 권한을 넓히면 merge하지 않는다.
- merge 후: 예상 devel push run/no-run과 비용을 관찰하고 오작동 시 일반 revert PR로 복구한다.
- branch protection, workflow dispatch, push, PR, comment, merge, close는 각각 메인테이너의 명시 승인을 받는다.
