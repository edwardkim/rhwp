- 관련 문서: [수행 계획](crates_io_preparation_20261023.md), [구현 계획](task_m100_8174_impl.md),
  [1단계 조사](../working/task_m100_8174_stage1.md), [보안 제한 현황](../manual/security_feature_limits.md).
- 검토 기준: `f69fda8219996449caad21be955675befb351c83`. 제품 source 기준은 `def947c2149df5bc812d801e6e79be19a403b4d1`이다.
- 상태: **MD01–MD09는 미결정. 정책 의존 구현 범위 v1은 미확정이며, C01–C04의 공통 선행 절편은 완료했다.**

## 이미 정해진 사항과 이번 문서의 역할

| 항목 | 기록된 결정 |
| --- | --- |
| 다음 제품 버전 | 사용자 지시에 따라 0.9.0. 이 버전을 다시 선택할 필요는 없다. |
| 준비 작업 | #8174로 crates.io 배포 준비와 1단계 조사를 진행한다. 실제 게시 승인은 별도다. |
| 결정 방식 | 2026-10-23 사용자 지시에 따라 메인테이너의 결정을 문서에 기록하고 그 결과로 구현 범위를 확정한다. |

아래의 **권고안은 검토용 제안**이다. 메인테이너가 선택하기 전에는 승인·확정으로 표시하지 않는다.
기존 8개 패키지 구성과 보안 제한 유지도 조사에서 제시한 안이며, 결정 대장에 채택 여부를 기록한다.
실측·코드 근거는 위 연결 문서에 두고 여기에는 선택과 구현 영향만 기록한다.

## 결정을 기다리지 않고 수행하는 공통 선행 작업

2026-10-23 사용자는 MD01을 결정 사안으로 구분하고, 메인테이너 결정과 무관하게 해야 하는
처리부터 착수하도록 지시했다. 이 지시를 MD01의 A/B 선택이나 다른 권고안의 승인으로 바꾸지 않는다.
모든 준비 작업을 MD 결정 뒤로 묶지 않고, 다음 공통 기반을 먼저 구현·검증한다.

| ID | 지금 수행할 처리 | 정책 결정과의 경계 |
| --- | --- | --- |
| C01 | Git source와 패키지 후보의 파일 목록·해시·압축 크기를 재현 가능한 정식 도구로 검사 | 후보 graph를 입력으로 검사하며 게시 구성·이름·버전을 확정하지 않는다. |
| C02 | 라이선스·고지·원본 추적 자료와 필수 내장 파일의 포함, 사유/검증 자료의 제외 검사 | 기계적 누락을 확인하며 법적 검토나 공개 API 안정성의 완료로 확대하지 않는다. |
| C03 | manifest의 path 버전 누락·root patch 의존·게시 제한을 source와 연결해 보고 | 문제를 수집하되 `publish`·version·feature를 임의로 바꾸지 않는다. |
| C04 | 도구의 실패 경계·재현성 검사와 실제 저장소 실행 결과 기록 | source 후보 검증과 실제 Cargo/registry 소비·게시 준비를 구분한다. |

이번 착수 범위는 C01–C04다. 선택이 필요한 구현은 결정 대장과 범위 v1에 기록한 뒤 수행한다.
[2단계 공통 결과](../working/task_m100_8174_stage2.md)에 정식 도구·실제 누락 보정·실행 결과를 기록했다.

### MD01 — 제품 릴리즈와 crates.io 게시 시점

- **A (권고):** 0.9.0을 crates.io 초회 게시 후보로 준비한다. 필수 검증과 보안 조건을 충족하지
  못하면 crates.io 게시는 보류하고, 기존 제품 릴리즈와의 결합 여부를 별도로 판단한다.
- **B:** 이번에는 준비·소비 검증까지 완료하고 실제 게시는 v1.0.0 이후로 둔다.
- **기록할 조건:** 목표 시점, crates.io 미준비가 제품 0.9.0 릴리즈도 보류시키는지.
- **구현 영향:** A는 게시 가능한 인계 자료까지, B는 준비 결과와 다음 게시 조건까지 완료한다.
  둘 다 지금 원격 게시·태그·토큰 설정을 실행하라는 승인은 아니다.
- **선행 결정:** [#5446의 신규 채널 보류 결정](https://github.com/edwardkim/rhwp/issues/5446#issuecomment-5327810241).
  A를 채택하면 이 정책 중 crates.io의 시점만 재검토한 것으로 기록한다.

### MD02 — 게시 graph와 버전

- **A (권고):** [1단계의 8개 별도 패키지](../working/task_m100_8174_stage1.md#게시-구조-선택)와
  [이름·버전 제안](../../packaging/crates-io/source-policy.json)을 채택한다. 본체 0.9.0,
  내부 3개 0.1.0, fork는 upstream 기반 보정 버전으로 구분한다.
- **B:** 일부 내부 crate를 본체에 흡수한다. 흡수할 대상과 유지할 공개 re-export를 지정한다.
- **기록할 조건:** 실제 게시할 이름·버전, fork의 소유 범위, 이름을 사용할 수 없을 때 재결정할 대상.
- **구현 영향:** A는 registry 버전 병기·별도 fork 연결·의존 순서 검증, B는 모듈/소비자 경계 보정과
  해당 회귀 검증이 추가된다. 어느 쪽도 보안 patch·출처·라이선스를 제거하는 안은 아니다.

### MD03 — 공식 API와 호환성

- **A (권고):** 1단계의 핵심 여정인 HWP/HWPX 파싱·Document IR·DocumentCore·저장 왕복,
  지원 범위의 PDF 입력과 기존 re-export를 우선 공식 소비 계약으로 문서화한다.
  나머지 공개 표면의 지원 상태도 구분해 표시한다.
- **B:** 현재 공개된 전체 `pub` 표면을 공식 지원 대상으로 삼고 예제·호환성 검증을 확대한다.
- **기록할 조건:** 지원 API 목록, 실험적 API 표시, 0.9.x의 소스 호환성·feature 기본값 변경 정책.
- **구현 영향:** 선택한 API의 저장소 밖 소비 예제·문서·컴파일/왕복 검사를 작성한다.
  A를 고르더라도 기존 공개 API를 임의로 삭제하거나 비호환 변경을 숨기지 않는다.

### MD04 — Rust 버전·feature·target

- **A (권고):** 고정 툴체인 Rust 1.93.1에서 먼저 검증하고, 확인하지 않은 하위 MSRV는 약속하지 않는다.
  현재 기본 feature, default 해제, `pdf-import`, `wasm-api`, `native-skia` 조합을 소비 경로별로 정한다.
- **B:** 더 낮은 Rust 버전을 지원한다. 후보 버전과 반드시 지원할 feature/target을 지정한다.
- **기록할 조건:** 최소 Rust 버전, Rust 라이브러리·CLI·WASM별 target/feature 표, docs.rs 구성.
  기존 제품의 CLI 5개 배포 target과 이번 Rust 소비 앱에서 실측한 target을 구분한다.
- **구현 영향:** manifest의 `rust-version`·docs.rs metadata와 소비 검사를 연결한다. B는 dependency
  제약 보정이 추가될 수 있다. 실제 통과 전에는 선택한 MSRV를 검증 완료라고 선언하지 않는다.
- **의존 관계:** PDF 기본값 변경은 MD05의 결정과 일치해야 한다. 기존 #7488·#7474·#7981의
  WASM 빌드·산출물·start/export 계약은 유지한다.

### MD05 — PDF 입력의 신뢰 범위와 보안 조건

현재 PDF는 기본 포함이지만 `parserAllocationBoundsProven=false`이고,
backend에는 요청 예산을 받지 않는 legacy API도 있다. `trusted input` 표시는
전체 메모리 제한이나 안전성 보증을 대신하지 않는다.

| 선택 | 지원 주장과 필요한 작업 |
| --- | --- |
| A (권고) | 기존 PDF 기본 포함을 유지하되 초기 지원은 출처·처리 권한을 확인한 입력의 실험적 가져오기로 한정한다. 비신뢰 업로드 서비스의 안전성을 보장하지 않는다. 해당 여정의 필수 자원·오류·격리 경계를 정하고 실제 검증한다. |
| B | 비신뢰 PDF 업로드도 공식 지원한다. #7911의 남은 할당·font·cache·제품 경계 감사를 주장 범위에 맞게 완료하고, 필요한 host 격리·종료·요청 간 분리를 실제 검증한다. 별도 보안 구현의 범위와 일정을 잡는다. |
| C | registry 초기 기본 구성에서 PDF를 제외하는 안을 검토한다. 지금과 다른 feature 기본값과 opt-in 소비 계약을 승인하고 검증해야 한다. 단순 manifest 변경으로 보안 문제가 해결됐다고 판정하지 않는다. |

- **기록할 조건:** 지원 입력·실행 환경, backend 직접 소비의 지원 여부,
  [#7911 B01–B05·B07](task_m100_7911_backlog.md) 중 게시 전에 완료할 항목과 후속 감사 항목,
  그 구분의 기술 근거·담당·완료 조건.
- **구현 영향:** A는 제한된 지원 문구와 그 범위의 실제 소비 검증, B는 보안 구현·실행 증거,
  C는 기능 계약 변경과 기존 소비자의 기능 보존 검증이 추가된다.
- **공통 조건:** 선택으로 확인된 결함이나 이미 필수로 정한 검증을 면제하지 않는다. 후속으로
  분류한 미검증을 PASS로 기록하지 않으며, 선택한 지원 범위의 필수 검증이 남으면 게시를 보류한다.

미지원은 자동 추가하지 않는다. 상세 현황과 구현 근거는 [보안 제한 목록](../manual/security_feature_limits.md)을 따른다.

### MD07 — 자원 정책과 host의 책임

- **A (권고):** 현재 PDF·HWP5·HWPX의 유한한 기본 한도와 초과 시 실패 계약을 유지한다.
  PDF host 정책은 기존 API 범위에서만 다루고 새 CLI/UI 조정 옵션은 추가하지 않는다.
- **B:** 배포 환경별로 더 작은 profile 또는 조정 옵션을 제공한다. 적용 환경·변경할 한도·상한을 지정한다.
- **기록할 조건:** 제품별 입력/쪽/픽셀/압축 해제/중첩 한도의 변경 여부,
  프로세스·Worker 격리와 시간·메모리 제한 중 host가 보장해야 하는 항목.
- **구현 영향:** A는 현재 값과 오류 경계의 소비 검증, B는 옵션 검증·누적 예산·정확한 한도 반례와
  정상 대조군을 추가한다. 기존 카운터를 전체 heap·CPU 시간의 상한으로 설명하지 않는다.

### MD08 — 패키지 소유와 유지보수 책임

- **A (권고):** 메인테이너가 확정한 패키지들의 게시·보안 업데이트·부분 실패 복구 책임을 일원화한다.
  실제 owner 계정과 보조 책임자는 결정 대장에 명시한다.
- **B:** 내부 crate/fork별 owner와 업데이트 책임을 분담한다. package별 담당과 인계 조건을 정한다.
- **기록할 조건:** owner 계정, 보안 신고 경로·대응 기준, upstream 보안 변경 추적,
  fork 갱신·yank·정정 버전·게시 도중 실패의 판단/수행 책임.
- **구현 영향:** README·고지·운영 인계와 부분 복구 절차에 같은 책임표를 사용한다.
  계정 추가·권한 변경·토큰 설정은 문서 작성과 구분해 승인된 때 수행한다.

### MD09 — 초회 게시와 자동화

- **A (권고):** 초회는 검증한 source와 순서를 고정해 수동으로 게시할 절차를 준비한다.
  이후 OIDC 자동화는 별도 단계로 준비하며 이번 릴리즈에 자동 활성화하지 않는다.
- **B:** 초회부터 GitHub Actions 기반 게시까지 준비한다. 초회 인증과 owner/권한 연결,
  실패 복구·재실행·verify-only 계약을 실제 적용 전에 검증한다.
- **기록할 조건:** 이번 작업에서 작성할 workflow/script 범위, 기존 release 집계와의 연동 여부,
  인증 방식과 실제 적용 시점. 지원되는 최신 registry 인증 절차는 구현 시 공식 문서로 확인한다.
- **구현 영향:** A는 수동 명령·preflight·단계별 확인과 실패 복구, B는 workflow·권한·집계 검사가
  추가된다. 모두 exact SHA/version/digest와 자식→부모 등록 확인을 보존한다.

## 결정 뒤 구현 범위 확정 방법

1. 사용자 답변을 결정 대장의 선택·조건·결정자·날짜에 기록한다. 권고안과 다른 선택도 그대로 기록한다.
   `MD06=A`는 F01–F08 전부의 제한 유지로 기록할 수 있고, 일부 변경이면 세부 ID와 나머지의 처리도 적는다.
2. 선택 간 모순을 확인한다. 예: MD05=C인데 MD04가 PDF 기본 포함이면 두 계약을 맞춘다.
   MD06에서 새 codec을 요구하면 MD05·MD07의 감사/자원 범위도 함께 확정한다.
3. 아래 표에 포함·제외·보류 작업과 검증을 채우고 수행/구현 계획에 연결한다. 새 구현에 필요한
   선행 결정이 모두 기록되고 해당 단계의 진행 승인이 있으면 실행한다.
4. 결정 후 변경은 이전 기록을 지우지 않고 변경 이력에 남긴다. 영향받은 구현·문서·검증만 다시 산정한다.

| 범위 버전 | 상태 | 포함 작업·결정 근거 | 제외/보류 작업·이유 | 필수 검증·완료 조건 | 진행 승인 근거 |
| --- | --- | --- | --- | --- | --- |
| v1 | 미확정 | 결정 후 기입 | 결정 후 기입 | 결정 후 기입 | — |

결정은 **무엇을 구현할지**, 검증 결과는 **실제로 충족했는지**를 기록한다. 미해결 필수 항목을
범위 밖으로 다시 붙여 완료를 대신하지 않는다. 라이선스/원본 고지·사유 자료 제외·보안 patch 보존과
변경 범위별 필수 검증은 공통 전제다. 정책 선택이 이 전제를 면제하지 않는다.

결정 대장을 채웠다는 사실은 remote push·PR 생성·실제 게시·태그·인증 설정의 포괄 승인이 아니다.
각 원격 작업은 세션에서 실제 승인된 범위와 [문서·Git 절차](../manual/codex/docs_and_git_workflow.md)를 따른다.
