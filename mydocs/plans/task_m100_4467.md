## 1. 목표

루트 README에 압축되어 있는 초기 제품 로드맵을 별도 `ROADMAP.md`로 분리한다. 초기
`0.5 → 1.0 → 2.0 → 3.0` 방향은 보존하되, #2659·#3608·#3880·#3907에서 발전한
증거 기반 관리 형식을 프로젝트 전체 범위에 적용한다.

README는 비전·현재 단계·상세 로드맵 진입점만 제공하고, 장기 단계의 현재 상태·착수 조건·완료 판정은
`ROADMAP.md` 한 곳에서 관리한다.

## 2. 권위 구조

```text
README.md / README_EN.md
        │ 공개 요약과 진입점
        ▼
ROADMAP.md
        │ 프로젝트 전체 제품 방향과 버전 단계의 canonical
        ├─ GitHub milestone v1.0.0 — 현재 릴리즈 추적
        ├─ mydocs/tech/* — 기술 계약과 설계의 canonical
        └─ agent_roadmap/README.md — AI 에이전트 자동화 하위 트랙
```

- 상위 `ROADMAP.md`는 제품의 `무엇/왜/완료 조건`을 관리한다.
- GitHub milestone과 issue/PR은 현재 실행 상태와 실제 착지 증거를 관리한다.
- #3907 R1~R100은 프로젝트 전체 로드맵이 아니라 AI 에이전트 자동화의 상세 기술 지도다.
- 하위 기술 문서가 상위 로드맵에 없는 기능을 적었다고 해서 구현 권한이나 우선순위를 자동 획득하지 않는다.

## 3. 새 로드맵 형식

### 운영 규칙

1. 로드맵은 일정 약속이 아니라 방향과 의존성 지도다.
2. 착수는 단계 번호가 아니라 현재 milestone, 사용자 가치, 실측 근거와 메인테이너 판단이 결정한다.
3. 완료 표기는 merge·release·실측 링크 같은 검증 가능한 근거와 함께만 한다.
4. 새로운 하위 로드맵은 상위 제품 단계를 명시하고, 같은 축의 기존 문서와 중복되지 않아야 한다.
5. 장기 가설은 현재 v1.0.0 작업을 선점하거나 열린 PR 큐를 늘리는 근거가 아니다.

### 증거 등급

`[완료]`, `[실측]`, `[문서]`, `[이슈]`, `[가설]`을 사용한다. 기술 세부의 현재 상태는 해당
canonical 문서와 GitHub 실물을 우선하고 상위 문서에서 손으로 중복 집계하지 않는다.

### 제품 단계

각 단계는 다음 여섯 항목으로 기록한다.

- **한 줄** — 사용자와 프로젝트에 무엇이 달라지는가
- **지금** — 현재 버전과 검증 가능한 증거
- **범위** — 이 단계에 포함되는 제품 축과 명시적 비범위
- **착수 게이트** — 다음 단계로 넘어가기 전에 필요한 판단·실측
- **DoD** — 관측 가능한 완료 판정
- **의존** — 선행 단계와 하위 canonical 문서

단계 축은 초기 비전을 보존한다.

| 단계 | 제품 방향 | 초기 로드맵과의 관계 |
| --- | --- | --- |
| v0.5 기반 | 파싱·공통 IR·읽기/쓰기·기본 렌더 기반 | 뼈대 공개 |
| v1.0 조판 | 한컴 동일 조판을 지향하는 조판 엔진 체계화 | 현재 milestone |
| v2.0 협업 | 안정된 조판·편집 위에 기여·확장·AI 자동화 개방 | 커뮤니티가 살을 붙이는 단계 |
| v3.0 공공 자산 | 전체 기능·접근성·플랫폼·실무 도입의 검증 | 한컴 대등 수준과 공공 자산화 |

## 4. 변경 파일

- `ROADMAP.md` 신설 — 프로젝트 제품 로드맵 canonical
- `README.md` — 중복 표를 현재 단계와 canonical 링크로 축약
- `README_EN.md` — 별도 영문 로드맵을 만들지 않고 같은 canonical을 가리키는 영문 진입점
- `mydocs/README.md` — canonical manifest에 프로젝트 로드맵 등록
- `llms.txt` — 에이전트가 프로젝트 전체 로드맵과 하위 에이전트 로드맵을 구분하도록 진입점 추가
- `mydocs/tech/README.md` — #3907 상세 지도의 상위 제품 로드맵 연결
- `mydocs/tech/agent_roadmap/README.md` — 프로젝트 전체 범위가 아닌 하위 트랙임을 명시

기존 `mydocs/tech/archive/`의 초기 로드맵은 historical 근거로 보존하며 이동·복원하지 않는다.

## 8. 조판과 협업의 병행 진행 보정

작업지시자는 v1.0 이전에 이미 40명이 넘는 외부 기여자와 두 명의 콜레보레이터가 참여하고 있으므로,
v2.0 협업을 “다음 단계”로만 설명하는 것은 현재 프로젝트와 맞지 않는다고 판정했다.

이에 따라 버전 번호는 작업 착수의 엄격한 순서가 아니라 목표의 성숙도와 완료 기준으로 설명한다.
현재 상태는 v1.0 조판 집중 진행과 v2.0 협업 기반 병행 진행으로 고치고, v2.0의 남은 과제는 협업의
시작이 아니라 지속 가능한 역할 분담, 호환성, 실패 복구와 유지 책임으로 다시 정의한다.

## 9. 업스트림과 다운스트림의 경계

작업지시자는 공식 업스트림 배포 대상과 활발히 성장하는 다운스트림 제품을 구분하고, 기여자가 구현
위치를 판단할 기준을 공개 로드맵에 추가하도록 지시했다.

- 업스트림: 공통 문서 엔진, Web/WASM 기반, Chrome·Edge·Firefox·VS Code 확장, npm 패키지,
  CLI 릴리스·설치 패키지, GHCR 이미지, GitHub Action, 재사용 가능한 CLI·MCP·공개 API 계약
- 다운스트림: 데스크톱·macOS·iOS·Android 앱, 사내 뷰어, Google Docs 연계, 조직별 인증·배포·
  업무 화면과 서비스별 백엔드
- 혼합 변경: 제품 코드는 다운스트림에 유지하고 범용 결함 수정·확장점만 작은 이슈와 PR로 분리
- 새 공식 대상: 코드보다 먼저 유지 담당자, 배포 권한, 보안 대응, CI와 장기 지원 책임을 합의

README는 경계의 존재를 안내하고, CONTRIBUTING은 PR을 만들기 전 판단할 수 있도록 로드맵의 해당
절로 연결한다. PR #4322의 개별 판정은 이 일반 기준과 정합하는 선례로 기록한다.
