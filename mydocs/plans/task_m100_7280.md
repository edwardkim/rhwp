## 1. 목적과 경계

기여자가 조판 기능을 구현·수정할 때 담당 모듈, 보존할 계약, 검증할 규칙을 명확히
찾을 수 있도록 구조를 정비한다. 파일 크기나 복잡도 수치 감소만으로 완료하지 않는다.

설계 지침은 **SOLID 원칙과 CQRS**다. 기존 프로젝트의 역할별 책임 분리와
Command/Query 분리 방향을 계승하며, 복잡도는 그 구조 개선을 확인하는 보조 지표로 사용한다.

`typeset.rs`를 중심으로 규칙 판단과 상태 변경을 분리하고, 측정·페이지 분할·배치가
소비하는 공통 결과의 소유권을 명시한다. 실제 호출 관계를 조사한 뒤 추출 경계를 확정한다.
우선은 동작 보존 리팩토링이며, 발견한 규칙 오류 수정은 구조 이동과 분리한다.

**설계의 출발점은 문단 중심의 문서 구조다.** 기존 함수들을 종류별 파일로 이동하는 데서
출발하지 않고, 구역의 문단 흐름과 문단에 속한 텍스트·컨트롤의 논리적 관계가 공통 IR에서
조판 결과까지 유지되는지를 먼저 확인한다. IR의 표현·참조·유효성 계약도 조사·설계 범위다.
IR 전면 교체를 선결 조건으로 삼지는 않으며 실제 스키마·파서·저장 변경은 영향 분석과
구현계획 승인을 거친다.

관련 #7090·#7195의 증거와 승인 이력은 참고하되, #7195와 PR #7222의 미병합 코드를
기준으로 삼거나 자동 이식하지 않는다. #6976의 넘침 불변식 제안과도 범위를 구분한다.
전체 엔진 재작성이나 범용 동적 rule engine 도입은 목표가 아니다.

## 4. 설계 원칙

### SOLID의 적용 기준

| 원칙 | #7280 설계에서 확인할 사항 |
| --- | --- |
| SRP | 문단·표·각주의 규칙 판단과 페이지 상태 전이를 변경 이유별로 분리한다. 하나의 거대 상태를 여러 파일의 `impl`에서 계속 임의 수정하는 것으로 끝내지 않는다. |
| OCP | 규칙별 명시적인 입력·결과와 확장 경계를 마련한다. 새 규칙 때문에 관계없는 문단·표·각주 분기를 동시에 고치지 않도록 한다. 문서별 예외나 범용 rule engine은 만들지 않는다. |
| LSP | 같은 계약을 구현하는 계산·배치 경로는 좌표계, 단위, 소유 범위, 실패·미지원 의미를 동일하게 지킨다. native/WASM별 측정값 차이와 계약 의미의 차이를 구분한다. |
| ISP | 규칙 계산에는 필요한 불변 입력만, 상태 적용에는 필요한 변경 권한만 제공한다. 전체 `TypesetState`나 엔진을 모든 helper에 전달하지 않는다. |
| DIP | 조판 정책은 안정적인 도메인 결과·필요한 측정 계약에 의존한다. 브라우저나 SVG/Canvas backend의 구현 세부를 규칙 판단에 끌어들이지 않는다. 기존 추상화를 우선 재사용하고 교체 경계가 필요한 곳에만 trait을 도입한다. |

### CQRS의 적용 경계

기존 `document_core/commands`·`queries`의 방향을 조판 내부의 읽기·쓰기 책임에 적용한다.
문서 편집 Command와 조판 세션의 상태 전이는 서로 다른 책임이므로 같은 계층으로 합치지 않는다.

- **Query / 계산**: 불변 문서·스타일·측정 결과와 현재 페이지 예산의 읽기 전용 관측값으로
  줄 구성, 점유 영역, 수용 가능 여부, 분할 후보를 반환한다. 원본 IR, 소비 컷, 페이지 커서를
  이 경로에서 전진시키지 않는다.
- **Command / 적용**: 확정된 계산 결과를 받아 페이지 항목 추가, 커서 전진, 각주 예약,
  continuation 소유권 이전을 담당한다. 결과를 적용하면서 별도 규칙으로 재측정·재판정하지 않는다.
- **조정 계층**: 후보 계산 → 수용 또는 이월 결정 → 상태 적용의 순서를 관리한다.
  후보가 기각됐을 때 부분 상태 변경이 남지 않는 계약과, 상태가 바뀐 뒤 낡은 후보를
  그대로 적용하지 않는 계약을 설계한다. 구체 타입·함수명은 구현계획에서 확정한다.
- 측정 캐시의 내부 가변성과 의미상 조판 상태 변경은 구별한다. `&self`라는 서명이나
  `queries/`라는 폴더 이름만으로 Query라고 판단하지 않고 `Cell`/`RefCell`을 포함한 실제
  부수효과를 추적한다. 캐시가 결과나 호출 순서에 영향을 주는지 별도로 확인한다.
- 여기서 CQRS는 읽기·쓰기 책임과 계약 분리다. 별도 데이터베이스, 이벤트 소싱, 비동기
  메시지 버스 또는 편집 undo Command로의 전환을 요구하지 않는다.

초기 전략 문서의 488개 테스트·과거 점수·파일 크기와 당시 `cargo test` 절차는 역사 자료다.
설계 방향은 계승하되 현재 검증은 §7의 현행 CI 정책을 따른다. 과거의 source-side 테스트
분할 예시를 그대로 적용해 신규 테스트 모듈 금지 정책을 우회하지 않는다.

### 조판 계약과 변경 관리

- 문단 중심 IR 및 조판 계층은 아래 §9를 설계의 우선 기준으로 삼는다.
- 규칙 판단은 명시적 입력과 결과를 갖고, 페이지 커서·소비 상태의 변경과 구분한다.
- 측정과 배치는 같은 줄 구성·메트릭·분할 결과를 소비한다. 기존 공통 결과를 우선 재사용한다.
- 문서 ID나 우연한 수치 조합으로 예외를 만들지 않는다. 불명확한 기존 예외는 확인 필요로 기록한다.
- `typeset.rs`의 역할은 실행 순서 조정으로 좁히되, 파일 이동만으로 책임 분리가 되었다고 보지 않는다.
- 기존 기술 문서를 정본으로 유지하고 기여자 안내에서 연결한다. 중복 규칙 정본을 만들지 않는다.
- 기존 결함을 보존하는 구조 이동과 올바른 동작으로 승인하는 판정은 구분한다.

## 5. 검증 계약

1. 동일한 입력·설정·환경에서 고정 baseline과 변경본을 비교한다. 서로 다른 브랜치의 테스트를
   교차 실행한 결과는 별도 진단으로 표기하며 기본 CI 결과와 섞지 않는다.
2. 기존 실패, 검출 강화로 발견한 기존 결함, 변경으로 생긴 실제 회귀를 구분한다.
3. 줄 구성·점유 높이·여백·분할 경계·잔여 내용 소유권에 대한 계약을 보호한다. 영향을 받는
   규칙의 적용 사례와 반례를 확인하고 합성 테스트를 실제 한컴 증거로 격상하지 않는다.
4. 구조 이동은 출력 보존이 기본이다. 페이지 수 외에도 표 외곽, 빈 줄, 후속 문단 위치,
   누락·중복·겹침과 줄바꿈을 확인한다. 애매한 한컴 차이는 메인테이너 시각 판정에 맡긴다.
5. 실패 은폐 목적의 baseline/golden/ignore 완화는 하지 않는다. 필요한 계약 수정은 별도 근거와 승인을 남긴다.
6. 소스 변경 후 적용 범위에 따라 native·WASM·workspace lint 및 회귀를 수행한다.
   최신 WASM과 native/SVG 증거를 구분하고, 과거 빌드의 판정을 새 SHA의 판정으로 재사용하지 않는다.

### 테스트 배치와 모듈 추출

- 새 공개 API 회귀·계약 테스트는 `tests/cases/`에 둔다. 새 최상위 `tests/*.rs`나
  integration binary를 임의로 추가하지 않는다. suite 번호를 고정하지 않고
  `scripts/run-rust-test.mjs`로 원본 이름을 선택한다.
- 기존 source-side 테스트는 `integration_ready / test_support / white_box`를 구분한다.
  단순히 코드와 함께 새로운 `#[cfg(test)]` 모듈로 옮기는 계획을 세우지 않는다.
  `rust-unit-test-tiers.mjs::previousEntry`는 기존 모듈 ID 또는 Git rename으로 대응되는
  파일과 동일한 모듈 suffix를 비교한다. 파일 일부 추출은 자동으로 순수 이동으로 인정되지 않는다.
- 추출 단위마다 기존 테스트의 유지 위치·이전 방식·가시성 영향을 먼저 설계한다.
  공개 계약은 integration 이전을 검토하고 private 계약은 기존 접근 경계를 우선 보존한다.
  정책에 걸리면 테스트 삭제, 무분별한 public API 노출, `--accept-baseline`이나 정책 상향으로
  우회하지 않고 분리 방식을 재검토한다.
- 검사 시 module·support item·테스트 총량 및 모듈별 최대값을 실제 PR base와 비교한다.
  `--check` 단독 통과를 PR base 대비 정책 통과로 보고하지 않는다.

### 생성·실행·제출 경계

- 원본 commit → 같은 SHA의 별도 검증 worktree → `--prepare` → 적용 검사 → 같은 SHA 제출 순서다.

## 9. 문단 중심 구조와 IR 경계

2026-09-20 작업지시자의 추가 요구: HWP/HWPX의 문단과 그 안에 선언된 컨트롤 관계를
출발점으로 논리적 조판 흐름을 설계한다. 필요할 때마다 분기를 추가하는 구조를 재생산하지 않는다.

### 논리 구조와 물리 배치의 구분

```text
Document / Section의 문단 목록
  └─ Paragraph: 문단 서식 + 순서 있는 텍스트·컨트롤 앵커
       ├─ 텍스트·명시적 개행·인라인 개체
       ├─ 부동 개체: 문단에 소속되지만 위치 기준·어울림 규칙에 따라 배치
       └─ 컨트롤의 하위 문단 목록
            └─ 예: 표 → 셀 → 문단 → 중첩 컨트롤
```

이는 논리적 소속 관계이며 paint 순서나 세로 적층 순서를 뜻하지 않는다.
`treat_as_char` 컨트롤은 글줄 구성에 참여하고 부동 개체는 앵커·위치 기준·어울림·겹침 정책을
따른다. 문단에 속한다는 이유로 모든 컨트롤을 문단 기준 좌표나 인라인으로 취급하지 않는다.
용지·쪽·단·문단 좌표와 소유 문단은 별도 정보다. 각주·머리말 등은 소속과 배치 영역도 구분한다.

### 계층별 책임

1. **파서 → 공통 IR**: HWP 레코드/HWPX XML 차이를 정규화하여 문단 경계, 텍스트와 컨트롤의
   순서·참조 위치, 서식, 하위 문단 소유 관계를 보존한다. 원본 왕복 보존 정보와 조판 의미를 구분한다.
2. **문단 해석·줄 구성(Query)**: 유효한 저장 줄 정보를 재사용할지, 재조판할지를 명시적으로
   판단한다. 문단 내용 순서·개행·가용 폭·글자모양·문단모양·개체 점유 영역에서 줄 구성 결과를 만든다.
3. **페이지/단 흐름(Query)**: 동일한 구성 결과와 현재 영역 예산으로 배치·분할·이월 후보를 계산한다.
   표 셀·글상자·각주 등의 하위 흐름은 공통 문단 규칙을 사용하되 컨테이너별 제약을 명시한다.
4. **상태 적용(Command)**: 수용된 결과와 잔여 내용의 소유권을 확정한다. 문단·컨트롤의 논리 순서를
   복원하려고 paint 단계에서 재추측하지 않는다.
5. **출력 backend**: 확정된 배치 결과를 그린다. backend별 독자적인 페이지 분할·원본 해석을 하지 않는다.

### 현재 IR에서 우선 확인할 계약

- `Paragraph`에는 `text`, `char_offsets`, `char_shapes`, `controls`, `line_segs` 등이 나뉘어 있다.
  `controls` 배열 순서만을 문단 내 삽입 위치로 해석하지 않고, 기존 `control_text_positions()` 등
  위치 접근자의 계약과 소비자를 추적한다. UTF-16 위치, Rust 문자열 위치, 컨트롤 슬롯을 혼동하지 않는다.
- HWPX의 `hwpx_axis_shift`와 `line_seg_text_start()`처럼 이미 있는 정규화 접근자를 우선 확인한다.
  새 정렬된 내용 표현이 필요하면 기존 IR에서 파생되는 읽기 전용 view로 충분한지 먼저 검토한다.
- 논리 문서 내용, 저장 LineSeg의 출처·유효성, 재조판 결과, 진행 중인 페이지 상태를 구분한다.
  저장 원본·편집 후 무효화·조판 전용 보강 줄을 한 필드의 같은 의미로 소비하지 않는다.
- 빈 문단·빈 줄도 서식에 따른 점유 영역을 가질 수 있다. 가시 텍스트 없음과 흐름 공간 없음은
  별개다. 표나 그림을 가진 문단도 텍스트가 비었다는 이유만으로 소속·앵커·간격을 지우지 않는다.
- 분할 조각은 원본 문단/컨트롤과 내용 범위에 연결되고 앞뒤 조각 사이에서 내용이 누락·중복되지
  않아야 한다. 논리 컨트롤을 여러 물리 조각으로 그리는 것과 IR 컨트롤 복제는 구분한다.

근거 문서는 [파서/공통 IR 경계](../tech/parser_architecture.md),
[LineSeg 계약](../tech/document_ir_lineseg_standard.md)다. 기존 참고 문서 사이에서 좌표 원점이나
HWPX 저장 정보에 대한 설명이 충돌하면, 현재 코드·정상 입력·독립 사양으로 확인할 항목으로
기록하고 문서의 오래된 단정으로 새 분기를 만들지 않는다.

### 설계 및 검증 산출물 보강

- 1단계에서 `원본 표현 → Paragraph IR/접근자 → 줄 구성 → 분할 → 실제 배치` 추적 지도를 작성한다.
  IR가 이미 표현하는 정보를 소비자가 잃는 문제와 IR 자체의 표현 부족을 구분한다.
- 구현계획의 모듈 경계는 위 논리 구조·Query/Command 역할·컨테이너 제약으로 정하고,
  기존 함수명이나 파일 크기만으로 결정하지 않는다.
- 문단 내 앞뒤 텍스트와 컨트롤 혼재, 같은 문단의 여러 컨트롤, 명시적 개행, 빈 문단,
  TAC/부동 개체, 중첩 문단 및 페이지 이월을 관련 계약의 적용·반례로 선정한다.
- IR/파서/직렬화를 실제 변경하는 절편은 저장·재열기·왕복 보존과 편집 후 무효화 검증을
  추가한다. IR 조사만 했다는 이유로 포맷 호환성 검증이 완료되었다고 보고하지 않는다.
