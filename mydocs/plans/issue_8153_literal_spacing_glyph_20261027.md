# #8153: 빈칸 제어와 실제 문자 글리프의 표시 계약 구분

편람 두 형식 79쪽에 각각 남은 2픽셀은 원본 `U+3000` 두 글자의 실제 글꼴 윤곽이다.
Unicode 공백 속성으로 잉크가 없다고 판정하지 않고, 빈칸 제어와 일반 문자를 구분해
공통 paint 경로를 보정한다. 줄 점유·저장 전진·본문 흐름은 바꾸지 않는다.

## 선행 해결과 반례

원 PR [#7534](https://github.com/edwardkim/rhwp/pull/7534)의 본문·댓글,
통합 PR #7575·merge `1e488ac370ec715a5b97c765542e16fc9bf65714`, 메인터너 보정
`80aa36e947`과 [개별 검토 기록](../pr/archives/pr_7534_review.md)을 먼저 대조했다.
그 보정은 HY신명조의 NBSP가 잘못된 `uni0080` 윤곽으로 그려지는 문제를 해결했다.
NBSP의 전진·장식은 남기고 잉크를 생략한 수용 범위는 유지해야 한다.
뒤의 `98ba0afbd95`는 개체 마커 U+FFFC의 별도 비표시 계약을 추가했다. 이것도 유지한다.

HWP5 revision 1.3의 표 7에서 코드 30은 묶음 빈칸, 31은 고정폭 빈칸이다.
`parser/body_text.rs`와 HWPX `nbSpace`·`fwSpace` parser는 이를 각각 U+00A0·U+2007로
투영한다. 탭·줄 제어·일반 ASCII 빈칸·no-break 빈칸의 기존 비표시 계약을 유지한다.
반면 원본 U+3000은 글꼴에서 표시하는 일반 문자다. Unicode `is_whitespace()`를
모든 공백의 잉크 부재 증거로 확장한 조건은 이 반례를 숨긴다.

79쪽의 KoPub돋움체 Light `uni3000`은 900/1000 전진과 작은 실제 사각 윤곽을
갖는다. 독립 Print subset gid 647과 원본 설치 프로그램의 윤곽·힌트·hmtx가 모두 같다.
두 잔여 좌표 482/493,284px는 그 윤곽과 대응한다. 원본·글꼴 파일을 수정하거나
복사하지 않았다. 프로그램 hash와 대조는 ignored
`remaining-raw100-diagnostic/small-residuals/p079-original-spacing-glyph-proof.json`에 있다.

## 공통 생산·소비와 보정

`원본 문자/빈칸 제어 → 저장 위치·전진 → TextRun의 표시 문자열 →
공통 비표시 제어 판정 → 실제 공급 font cmap → Native/SVG/Canvas paint`를 확인한다.
측정에서 이미 정한 전진·layout_positions·밑줄·배경은 유지한다. 실제 빈칸 제어만
비표시로 소비하고, 나머지 문자는 공급한 글꼴 프로그램에 따라 그린다. 글꼴·쪽·문서 이름이나
잔여 픽셀 좌표로 분기하지 않는다. U+FFFC의 개체 소유와 complex span 경계도 유지한다.

Native의 글꼴 선택도 같은 비표시 계약으로 문자를 선택한다. U+3000만 있는 클러스터를
이유 없이 첫 fallback face로 보내거나, 실제 glyph가 없는 face의 `.notdef`를 그리지 않는다.
연속 그림자의 glyph 공급·포함 영역에서도 같은 기준을 사용한다. 빈칸의 폭과 잉크 후보는
별개이며, 문자 후보가 된다는 사실이 글꼴의 빈 glyph를 가시 잉크로 바꾸지는 않는다.

## 검증과 완료 조건

두 편람의 79쪽·주변 78/80쪽과 기존 보정 경계부터 Native로 직접 비교한다. 79쪽은
독립 Print와 현재 양쪽 backend가 98% 이상이며, 새 기대값은 실제 문자·폰트·PDF에 근거한다.
NBSP·고정폭 빈칸·ASCII 공백·개체 마커의 비표시와 전진 보존은 기존 계약 검사와
해당 출력에서 함께 확인한다. 다른 실물 문서를 새 보정 대상으로 넓히지 않는다.
Native/fresh WASM 시각 검증 뒤 source·소유·내용 보존과 실제 backend 출력을
정식 회귀로 보호한다. 현재 1,532조건 전쪽 100%·미대응 0과 최종 검증은 유지한다.

직전 HNC 후보의 집중 Native 42조건·독립 원 기호 3쪽·공급 프로토콜 제안 9건은
통과했으며 전쪽과 fresh WASM은 별도 진행한다. upstream 동기화와 원격 쓰기 없이
PR 준비까지만 수행한다.
