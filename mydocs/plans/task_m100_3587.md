## 1. 목표

**AI agent·스크립트·API가 템플릿과 구조화된 데이터로 정형 문서를 결정적으로 생성하고,

템플릿의 기존 칸을 채우는 것뿐 아니라 원형 표·문단·글상자·컨트롤 묶음을 복제하고,
데이터 건수에 맞춰 반복 영역을 구성하는 흐름을 포함한다. 업무마다 별도 빈 문단 정리나

새로 들어갈 반복 항목 수가 달라져도 기존 앞뒤 문단의 내용·순서·속성·컨트롤 소유 관계가
뜻하지 않게 바뀌어서는 안 된다.

구조 보존은 화면 좌표 고정을 의미하지 않는다. 내용 증가에 따른 정상적인 뒤쪽 문단의 이동과
페이지 증가는 허용하되, 문단 합쳐짐·불필요한 빈 문단 생성·기존 Enter 삭제·구역 정의 유실은
구별해 검증한다. 렌더러의 자동 문단 삭제나 임의 높이 보정으로 편집 경계 오류를 숨기지 않는다.

## 3. 설계 출발점과 범위 — 승인 전 확정하지 않을 것

### 3.0 전체 사용 흐름과 책임 경계

포크 사전 검토에서 기반 및 현행 `paste_control_native`의 후속 빈 문단 생성, 포크의 동일
행·열·너비 기반 raw INSTANCE_ID 계산, 2pt 압축의 반복 스타일 추가, 문단 전체를 복제하는
목차 분할을 확인했다. Stage 1은 이 관찰을 출발점으로 **붙여넣기 경계 → 개체/참조 정합성 →
반복 생성·채우기 → 필요한 후처리** 순서로 기존 계약을 검증한다. 최종 저장 ID나 한컴 증상은
아직 실행하지 않았으므로 코드 관찰과 실제 재현을 구분한다.

설계 대상 흐름은 `템플릿/원형 선택 → 대상 식별 → 생성·복제 계획 → 데이터 채우기 →
구조·참조 검증 → 재조판 → 저장·재열기`다. 특정 포맷의 XML/바이너리를 호출자가 직접
수정해야만 하는 방식을 공통 자동화 API의 정상 사용법으로 삼지 않는다.

| 기능 축 | 설계에서 답할 질문 | 검증할 대표 사용 |
| --- | --- | --- |
| 템플릿·원형 | 기존 문서의 어느 부분을 원형으로 삼으며 원본과 생성 결과를 어떻게 분리하는가 | 기존 서식 유지, 표·문단·글상자 묶음을 원형으로 새 결과 문서 구성 |
| 대상 지정 | 필드·이름·개체 참조·명시적 범위 중 기존 API로 무엇이 가능한가 | 같은 이름의 여러 필드, 다중 반복 영역, 삽입으로 인덱스가 달라지는 경우 |
| 생성·반복 | 단일 칸 채우기, 행 반복, 표/문단/복합 블록 반복은 어떤 연산을 공유하는가 | 0·1·복수 데이터, 제목+표+설명 블록, 반복 블록 안 중첩 개체 |
| 데이터 연결 | 누락·빈 값·추가 데이터·자료형 불일치를 어떻게 구별하는가 | 텍스트·수치·그림 입력, 선택 항목의 보존/생략 정책 |
| 복제 정합성 | 개체 ID·스타일·이미지 참조를 어느 계층에서 복제·공유·재매핑하는가 | 동일 문서 반복 복제와 다른 템플릿 문서에서 가져오기 |
| 실행 계약 | 계획 확인, 적용 범위, 부분 실패, 재시도, undo를 어떻게 설명하는가 | 동일 요청 재시도와 의도적 추가를 구별, 실패 시 비대상 영역 보존 |
| 출력·진단 | 무엇을 어디에 몇 개 만들었고 무엇이 실패했는지 어떻게 확인하는가 | 기계 판독 가능한 결과, 생성 개체 대응, HWP/HWPX 저장 후 검증 |

위 표는 모든 기능의 신규 구현 약속이 아니라 **전체 설계의 조사·결정 범위**다.
Stage 1에서 각 항목을 `기존 기능 재사용 / 기존 결함 보정 / 신규 공통 기능 / 이번 구현 제외`로
분류하고 실제 코드·테스트 근거를 붙인다. 같은 문서와 문서 간 복제를 모두 설계상 검토하되,
구현 지원 범위는 명시한다. 기여자의 원래 호출에 없다는 이유만으로 범용 요구를 제외하지 않는다.

- 호출자는 업무 데이터·반복 건수·선택 항목 정책을 정한다. 엔진이 빈 문단 모양을 보고 업무 의도를 추측하지 않는다.
- 공통 엔진은 문단/컨트롤 구조, 복제 참조와 편집 무결성을 책임진다.
- HWP/HWPX 파서·저장기는 포맷별 식별자와 참조를 공통 계약에 맞게 변환·보존한다.
- native·WASM·CLI·agent/MCP 표면은 동일 계약을 소비해야 한다. 기존 호출 경로를 조사해
  실제 자동화에 필요한 최소 연결을 선택하며, 표면마다 별도 복제 로직을 만들지 않는다.
- 기존 필드 채우기·batch·계획 실행·clipboard 경로부터 조사한다. 코드 위치 후보는
  `src/document_core/commands/clipboard.rs`, `foreign_paste.rs`,
  `src/cli/commands/batch_fill.rs`, `src/cli/commands/edit/fields.rs`,
  `src/cli/protocol/plan/`이다. 이름/파일 존재를 확인했을 뿐 정합성·재사용 가능성은 아직 검증 전이다.
  [서식 채우기 가이드](../manual/form_filling_guide.md)와
  [소비자 편집 API](../manual/consumer_edit_api_guide.md)를 조사 진입점으로 삼는다.

서식 생성에 필요한 엔진/API 설계가 범위다. 새로운 템플릿 문법·전용 스크립트 언어·웹 템플릿
디자이너·LLM 서비스·별도 배포 제품을 선결하지 않는다. 필요성이 입증되면 구현 전에 제안·승인받는다.

### 3.1 템플릿 자동화의 편집 계약부터 조사

1. 기여자의 사례와 다른 구조의 대표 템플릿을 함께 선정하고, 기존 `copyControl`/`pasteControl`·문단 삽입·내용 채우기 호출 순서를 확인한다.
   기존 API 조합으로 충분한 부분과 엔진에서 보완해야 하는 부분을 나눈다.
2. 대상 범위와 앞뒤 보존 문단을 어떤 기존 식별자·참조로 지정할 수 있는지 확인한다.
   삽입 중 인덱스가 변해 다른 문단을 수정하는 위험을 검토한다. 새 범위 타입이나 대규모 API를
   먼저 만들지 않고, 구역 인덱스 하나만으로 목적을 안전하게 충족하는지부터 판정한다.
3. 복제 원본, 새 반복 항목, 기존 경계 문단, 자동화 과정에서 새로 만든 임시 문단을 구별한다.
   빈 문자열이나 표와의 인접성만으로 기존 문단을 임시 문단으로 추정하지 않는다.
4. 앞쪽·뒤쪽 문단의 불변 구조를 편집 전 캡처하고, 채우기 후와 HWP/HWPX 저장 재열기 후에
   대조한다. 형식 변환으로 달라지는 내부 번호는 참조 관계로 비교하며 물리 인덱스 동일성을
   구조 보존으로 잘못 정의하지 않는다.
5. 정리 연산이 실제로 필요한지, 기존 삽입·복제의 경계 처리를 바로잡아 해결되는지 판단한다.
   실패 원인이 기존 API에 있으면 해당 경로와 근거를 구현계획에 명시해 승인받는다.

### 3.1.1 컨트롤 복제와 ID·참조 보존

메인테이너는 표·글상자 등 템플릿 컨트롤의 복사·붙여넣기가 주요 사용 방식임을 강조했다.
기존 표에 텍스트만 쓰는 경우로 검증을 제한하지 않는다. 다음은 확정 구현이 아닌 조사·설계 요구다.

- **ID의 의미와 범위:** 컨트롤 종류를 나타내는 식별자와 개별 개체의 인스턴스 식별자,
  문단 식별자, 스타일 테이블 참조 번호를 구별한다. HWP/HWPX 원본 → IR → clipboard →
  paste → serializer 경로별로 각 필드의 유일성 범위와 생성·보존·재매핑 책임을 표로 정리한다.
  모든 ID를 일괄 재발급하거나 원본 번호를 그대로 복사하는 방법을 선결하지 않는다.
- **개체 복제:** 복제본이 독립적으로 식별·선택·편집되어야 한다. 루트 표/글상자뿐 아니라
  내부 문단·중첩 컨트롤도 조사하고, 원본·다른 복제본을 잘못 가리키는 참조를 방지한다.
  복제본 내부 참조와 의도적으로 외부를 참조하는 항목은 구별한다.
- **스타일 참조:** 글자모양·문단모양·스타일·테두리/배경·번호 매기기 등 실제 사용 참조를
  추적한다. 동일 문서의 유효한 스타일 공유는 유지할 수 있지만, 복제본만의 서식 편집이
  공유 테이블 변경을 통해 원본이나 다른 문단까지 바꾸지 않는지 확인한다.
- **리소스 참조:** 글상자 안 그림이나 배경 이미지 등 복제에 딸린 BinData 참조도 확인한다.
  불필요한 리소스 복제와 존재하지 않는 대상 참조를 구분한다.
- **문서 간 경계:** 같은 템플릿 문서 안 반복 복제와 별도 원본에서 목적 문서로 가져오기를
  구분해 조사한다. 후자는 목적 문서의 스타일·리소스 번호 재매핑과 충돌 처리 계약을 검토한다.
  Stage 1에서 기존 지원과 누락을 확인하고 구현 범위를 승인받는다. 문서 간 붙여넣기를 확인 없이
  지원 완료로 보고하거나 별도의 범용 clipboard 재설계를 시작하지 않는다.
- **저장 일관성:** IR에서 바꾼 식별자·참조가 원본 raw 데이터 재사용으로 되돌아가지 않는지,
  HWP/HWPX 각각 저장 후 재열기에서 의도한 개체와 스타일로 연결되는지 검증한다.

필수 시나리오는 같은 표/글상자를 여러 번 붙여넣기 → 각 복제본에 서로 다른 내용 채우기 →
한 복제본만 내용·서식 수정 또는 삭제 → 원본·나머지 복제본·앞뒤 문단 보존 확인 → 저장 재열기다.
식별자 충돌·참조 해소 검사와 렌더링 비교를 함께 수행한다. 화면이 같다는 사실만으로
식별자·참조 정합성 통과를 선언하지 않는다.

### 3.2 전체 설계에 대한 원 제안 4종의 대응

| 연산 | 이번 계획의 제안 | Stage 1에서 확정할 계약 |
| --- | --- | --- |
| `removeOrphanParasBeforePageBreaks` | 자동화로 생긴 잉여 문단 정리가 필요한 경우의 후보 | 기존 빈 문단과 신규 생성분 구분, 대상 영역 밖의 쪽나눔·문단 보호 |
| `trimTrailingParasAfterLastTable` | 반복 채우기 끝부분의 잔여 문단 정리가 필요한 경우의 후보 | 구역의 마지막 표와 이번 채우기 영역의 끝을 혼동하지 않고 뒤쪽 기존 문단을 보존 |
| `compactLeadingParasBeforeTables` | 표 앞 문단 훼손·밀림이 생기는 원인부터 조사 | 기존 앞쪽 문단을 2pt로 바꾸는 것은 경계 보존 목표에 맞지 않음. 원본 훼손 없이 해결할 경로와 손상 보고 확인 |
| `mergeSectionIntoPrevious` | 반복 블록 삽입 방식에 실제 필요한지 조사 | 병합으로 기존 앞뒤 구역 속성이 변하지 않는 계약이 가능한지, 단순 정리와 구조 변경 구분 |

3·4번의 제외 또는 보류를 이미 결정된 것으로 간주하지 않는다. Stage 1 보고와 구현계획에서
각 연산의 수용·제외·보류 사유를 한 표로 제시해 승인받는다. 별도 이슈나 자식 이슈를 자동 생성하지 않는다.
네 이름을 그대로 이식하는 것을 목표로 삼지 않는다. 목표를 만족하는 최소 연산 조합과 원 제안의
요구 충족 여부를 매핑해 보고한다. API 신설·기존 API 보정 범위는 조사 후 승인받는다.

원 제안 함수의 개수로 구현량이나 완료 여부를 결정하지 않는다. §3.0의 공통 계약을 기준으로
기존 API 재사용·보정·추가를 정하고, 원 제안 4종은 그 결과에 대응시킨다.
네 함수의 상태만 정리하고 범용 자동화의 실행 경로를 제시하지 못하면 설계 완료가 아니다.

## 4. 안전 계약과 반례

1. **명시적 실행과 대상 경계:** 열기·렌더링·저장 과정에서 자동으로 정리하지 않는다.
   호출자가 지정한 채우기 영역만 편집하며 같은 구역의 다른 문단도 보호한다.
2. **삭제 적격성:** 텍스트의 `trim()` 결과만으로 삭제하지 않는다. 수식·필드·책갈피·각주·구역/단 정의 등
   모든 컨트롤, 범위 표식·참조와 문단 나눔 속성을 조사한다. 안전을 증명할 수 없는 문단은 보존한다.
   공백뿐인 문단을 빈 문단에 포함할지도 계약에서 명시한다.
3. **앞뒤 구조 보존:** 기존 문단의 텍스트·공백·Enter·스타일·나눔 속성·컨트롤·참조 관계를
   유지한다. 표 내부 문단과 본문 문단을 혼동하지 않고, 경계 문단에 붙은 구역 정의를 보존한다.
4. **범위와 원자성:** 잘못된 구역 인덱스는 변경 전에 오류로 반환한다. 삭제 후보를 먼저 결정하고
   뒤에서 삭제하는 순서, 중간 실패의 부분 변경 방지, 조판 갱신 횟수와 기존 undo 연동을 검토한다.
5. **멱등성:** 1·2번은 재호출 시 변경 0건을 기대한다. 반대로 인덱스 기반 구역 병합은 재호출 시
   다음 구역을 병합할 수 있으므로 같은 계약을 적용하지 않는다. 첫 구역·범위 초과 오류도 별도다.
6. **무변경 보존:** 대상이 없으면 문서 구조·스타일·raw 보존 상태를 불필요하게 갱신하지 않는다.
   저장 바이트 동등성과 IR 동등성은 별도 검사하며, serializer의 기존 정규화를 새 회귀와 구분한다.
7. **원본·출처:** fork 코드를 가져올 경우 실제 commit·라이선스·기여 출처를 확인한다. 기존 소스의
   오류 수정인지 신규 API 미구현인지, 앱이 만든 불필요 문단인지 구분해 보고한다.
8. **복제 정합성:** 인스턴스 식별자는 해당 형식의 유일성 계약을 만족하고, 종류 식별자와
   공유 가능한 스타일 참조는 의미를 보존한다. 중첩 개체·스타일·리소스 참조가 유효한 대상으로
   연결되며 한 복제본의 편집이 원본·다른 복제본·앞뒤 영역을 의도치 않게 변경하지 않는다.
9. **자동화 입력과 자원:** 대상이 모호하거나 데이터·참조가 유효하지 않으면 정해진 오류 정책을
   적용한다. 반복 건수·중첩 깊이·이미지 크기 등 자원 한도와 사전 검증을 기존 정책에 맞춰 검토하고,
   일부만 적용한 결과를 전체 성공으로 반환하지 않는다. 한도 값은 근거 없이 임의로 정하지 않는다.

### 4.1 대표 시나리오와 판정

실제 fixture를 선정한 뒤 다음 대표 흐름을 대응시킨다. 모든 조합의 전수 코퍼스 검사를 먼저
시작하지 않고, 정상 사용과 계약 경계에 필요한 최소 대표군을 정한다.

| 시나리오 | 확인할 의미 |
| --- | --- |
| 고정 서식의 필드·셀 채우기 | 기존 채우기 기능을 보존하고 비대상 영역이 변경되지 않음 |
| 데이터별 표·행·문단 반복 | 원형 서식과 항목 순서 유지, 데이터와 생성 대상의 정확한 대응 |
| 제목+표+글상자/그림 복합 블록 복제 | 내부 순서·중첩 구조·ID·스타일·리소스 참조 및 앞뒤 경계 보존 |
| 여러 생성 영역과 선택 항목 | 한 영역의 삽입이 다음 영역의 대상을 잘못 바꾸지 않음 |
| 원형 문서에서 별도 결과 문서 생성 | 원형 불변, 목적 문서 참조 충돌 처리. 지원 여부·제외 이유를 명시 |
| 생성 후 개별 편집·실패·재시도 | 원본/다른 항목 독립성, 오류 상태와 재실행 의미가 계약과 일치 |

완료 판정은 승인된 대표 시나리오별 `사용 API / 입력 / 기대 구조 / 저장·재열기 / 시각 결과 /
실패·제외 / 증적` 표로 한다. 지원하지 않는 조합은 명시적 오류 또는 문서화된 범위로 구분한다.

주 검증은 동일 템플릿의 대상 영역에 반복 항목 0·1·복수를 채워 앞뒤 기존 문단 구조가
보존되는지 확인하는 것이다. 본문·표 내부·표 앵커 문단의 차이, 빈 기존 경계 문단,
쪽나눔·구역 정의, 긴 내용에 따른 정상적인 페이지 증가를 포함한다.
0건이 삭제와 무변경 중 무엇을 뜻하는지는 계약에서 먼저 확정한다.
동일 요청의 재시도와 새 항목 추가 요청을 구별하고, 모든 추가 연산에 멱등성을 요구하지 않는다.
대상 없음·잘못된 범위·중간 실패·저장 왕복도 검사한다. 하위 정리 연산은 적격 1개/복수와
삭제하면 안 되는 반례를 검증한다.
합성 IR은 API 계약 검사에만 쓰며 한컴의 유효 문서·시각 정답지를 대신하지 않는다.

  review worktree에서 준비한 generated suite·manifest는 커밋하지 않는다.
- source/test 변경의 PR 전에는 AGENTS.md의 fmt·native Clippy·WASM lib Clippy·workspace build와
  all-target Clippy 묶음을 순차 통과한다. 긴 전체 회귀는 단계 승인 후 실행한다.
- WASM은 Docker로 빌드한다. 기존 7700 dev 서버·공유 target·다른 PR worktree는 보존한다.
- 동일 입력에 대한 편집 전·후·저장 재열기 결과를 분리한다. 기존 한컴 PDF가 있으면 재사용한다.
  유효한 한컴 출력·메인테이너 판정 없이 페이지 수 감소만을 성공으로 삼지 않는다.
- AI agent·스크립트가 사용할 수 있는 기존 또는 승인된 공개 API 경로로 정형 표·문단 반복 채우기가
  실행되고, 기존 앞뒤 문단 구조가 편집 직후와 저장 재열기 후 모두 보존되어야 한다.
  한 사례만이 아니라 승인된 대표 템플릿들에서 동일한 공통 계약을 재사용해야 한다.
- 표·글상자의 반복 복제본을 각각 식별·편집할 수 있고, 스타일·중첩 컨트롤·리소스 참조가
  HWP/HWPX 저장 재열기 후에도 유효해야 한다. 원본과 다른 복제본의 비의도적 변경이 없어야 한다.
- 네 제안 각각의 필요성·구현 또는 대체 경로·제외/보류 결정이 남아야 한다.
  경계 보존이 검증되지 않았는데 정리 함수 테스트나 페이지 수 감소만으로 완료하지 않는다.
- API 이용자가 재현할 수 있도록 템플릿·입력 데이터·호출 순서·출력·오류 동작을 문서화한다.
  신규 함수 수가 아니라 실제 자동화 경로의 완결성과 승인된 지원 범위로 판정한다.
- 이번 수행계획 작성은 구현·시각 검증·PR 준비 완료를 의미하지 않는다.
