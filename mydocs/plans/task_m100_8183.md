## 목표와 확정한 방향

추가 코덱은 설치·빌드 때 필요한 것만 선택한다. PDF 기본 가져오기는 현재대로 유지하며,
JBIG2와 JPEG 2000은 각각 기본 비활성 feature로 제공한다. 두 코덱이 서로를 활성화하거나
backend의 전체 renderer·시스템 글꼴을 끌어오지 않도록 한다.

사용자 여정은 다음과 같다.

1. PDF 열기의 진단과 사용 중인 빌드의 기능 정보에서 필요한 코덱을 식별한다.
2. Native CLI 설치, Rust 의존 선언 또는 WASM 빌드 중 자기 경로의 가이드를 선택한다.
3. 해당 코덱만 추가한 빌드로 PDF를 가져온다. 포함하지 않은 코덱·잘못된 입력·한도 초과는
   구별 가능한 진단을 받으며 실패 뒤 다음 정상 문서를 처리할 수 있다.

런타임에 내려받는 플러그인 구조를 새로 만들지 않는다. Cargo feature로 코드를 포함하는
방식이며, 배포된 CLI·Studio WASM의 지원 범위는 그 산출물에 실제 포함한 feature로 결정된다.

## 범위와 기존 계약

| 구분 | 이번 범위 |
| --- | --- |
| 코덱 | JBIG2, JPEG 2000 (`JPXDecode`)를 개별 opt-in으로 설계·구현 |
| 소비자 | Native CLI, Rust 라이브러리, fresh WASM·Studio PDF 가져오기 |
| 자원 | 기존 요청 budget의 사전 제한·중단·누적 계상을 새 codec의 실제 내부 예약·작업에 연결 |
| 출력 | 일반 그림, 사양상 허용되는 공유 자원·마스크·색 공간 조합에서 실제 픽셀·소유·배치 보존 |
| 문서 | 개발 빌드, CLI 설치·사용, Rust 소비, WASM 재빌드·배포 산출물 확인, 보안 제한 안내 |
| 기존 기본값 | `pdf-import`, `wasm-api`, Native Skia 선택과 기존 HWP/HWPX 동작 유지 |
| 별도 정책 | 0.9.0 포함 시점·실제 게시·하위 MSRV·비신뢰 업로드의 전체 안전성 보증은 자동 확정하지 않음 |

ICC CMM·OCR·암호 PDF 지원은 이번 코덱 추가와 구분한다. 기존 자원 상수·거부 조건을
완화하거나 legacy 무제한 경로로 우회하지 않는다. 기존 `parserAllocationBoundsProven=false`는
코덱 일부의 검증만으로 바꾸지 않는다.

## 선행 해결과 현재 base

JBIG2/JPEG 2000/codec/코덱으로 열린·닫힌 이슈를 검색했다.
같은 opt-in 구조와 가이드 작업을 맡은 열린 이슈는 확인하지 못했다.

[#7959](https://github.com/edwardkim/rhwp/issues/7959)의 원본은 간접 stream·mask·색 공간 전달의
호환 문제였다. [PR #7970](https://github.com/edwardkim/rhwp/pull/7970)의 실제 통합
`515bd72dcde0eecdeece333666b675354b7fa91d`와
[정식 review](../pr/archives/pr_7970_review.md)의 독립 출력·자원 경계 결과를 확인했다.
그 commit이 현재 base에 포함됨을 `git merge-base --is-ancestor`로 확인했다.
이 검증은 새 코덱 활성 경로의 실행 근거로 재사용하지 않는다.
실제 구현 중 기존 회귀가 실패하면 해당 실패의 원 이슈·통합·독립 기대값을 각각 추적한다.

## 단계와 완료 조건

### 1단계 — 설계와 소비 경로 조사

- 이슈 등록·담당 지정·최신 base의 작업 브랜치를 준비한다.
- 기존 feature·실제 이미지 handle·코덱·mask·PNG 소비 경로를 연결한다.

### 3단계 — 실제 소비와 가이드 완성
