## 1. 목표

다음과 같은 canonical review 계보에서 이미 성공한 Full Canvas visual diff를 안전하게 재사용한다.

```text
녹색 code candidate
  -> 현재 devel을 정확히 병합한 current-base merge bridge 1개
  -> mydocs 등 허용된 review-only single-parent tail
```

PR #6214에서는 code candidate `9c568b40a`, merge bridge `469ac96fd`, review tail `ba060deca` 순서였으나
Render Diff가 candidate의 과거 base identity를 거부해 Canvas worker를 5분 24초 다시 실행했다. 이번 작업은
merge-tree 보호를 유지하면서 이 비대칭만 해소한다.

### 1.1 최신 devel 병합 뒤 재검토

- 이전 기준 `6415047a4` 뒤 21개 commit은 CI·CodeQL·nextest 정책을 바꿨지만
  `.github/workflows/render-diff.yml`과 `test_review_only_fast_pass_workflows.py`의 해당 경로는 바꾸지 않았다.
- run `33071270488`의 실제 preflight는 code candidate `9c568b40a`에 대해 여전히
  `fast_pass=false reason=canvas-visual-diff-identity-mismatch`를 기록한다.
- 현행 Python 계약 18건은 모두 통과하지만 prior-base 경계는 호출 문자열을 확인하는 정적 계약뿐이다.
  Render Diff의 workflow run·jobs·identity step을 실행하는 fixture가 없어 이 비대칭을 직접 재현하지 못한다.
- PR #6270의 review tail fast-pass는 registry 보정 뒤 새 Full code candidate `a271733ba`를 재사용했다. bridge 이전
  base identity를 읽는 #6243 계보가 아니므로 이 결함의 canary나 반증으로 사용하지 않는다.
- 기본 브랜치 `main`에는 controller workflow가 없고, `devel`에만 `ci-impact-policy.yml`이 있다. `devel`의
  required context는 `Build & Test`이며 #6243 assignee와 열린 PR은 없다.

따라서 원인·수정 경계는 유효하다. 범위를 넓히지 않고 O2-1에 실행 가능한 Render Diff red 계약을 보강한다.

## 2. 원인과 최소 수정 경계

`.github/workflows/render-diff.yml`의 직접 merge-head 경로는
`renderDiffResult(sourceParent.sha, pr, true)`를 호출해 bridge 이전 Full run의 base identity를 읽을 수 있다.
반면 merge bridge 뒤 review tail이 있는 일반 candidate loop는 `renderDiffResult(candidateSha, pr)`로 호출해
같은 bridge를 발견했어도 `allowPriorPrBase=false`가 된다.

최소 수정은 일반 candidate loop에서도 **검증 대상 current-base merge bridge를 정확히 한 개 발견한 경우에만**
prior-base identity lookup을 허용하는 것이다. 이 허용은 candidate 채택을 확정하지 않는다. 기존
`pending-base-merge-tree` 상태와 후속 `git merge-tree` 또는 `mydocs/` 한정 충돌 해소 검증이 성공해야만 최종
fast-pass가 된다.

## 3. 범위

### 범위 안

- `.github/workflows/render-diff.yml`의 trailing review candidate lookup 조건 정정
- `scripts/tests/test_review_only_fast_pass_workflows.py`의 실행 가능한 회귀 계약 추가
- direct bridge와 trailing review bridge의 prior-base identity 허용 조건 대칭화
- 복수 merge, 잘못된 base, source/test/workflow 충돌, 다른 PR·branch·repository, failed candidate의 Full fallback 보존
- 적용 후 실제 PR에서 preflight reason, Canvas worker skip, required check를 관찰할 기준 명시

### 범위 밖

- Canvas visual diff 검사 축소 또는 threshold 변경
- CI·CodeQL·Proptest·Adapter의 별도 정책 변경
- required check, branch protection, permission, controller 배포 변경
- #6215 generator path 분류와 #4969 제품 font/shaping 구현
- `main` 직접 반영 또는 `devel` admin push

## 4. 보호 불변식

1. prior-base identity는 같은 PR 번호, head branch, source repository, PR 생성 이후의 성공한 Full Render Diff
   run에만 허용한다.
2. current base와 정확히 연결되는 2-parent merge bridge가 하나뿐일 때만 예외를 연다.
3. merge tree가 자동 계산과 같거나 수동 충돌 해소 경로가 전부 `mydocs/`일 때만 최종 fast-pass한다.
4. bridge 없는 review tail은 현재 base identity의 성공 run만 재사용한다.
5. 복수 bridge, 일반 merge, 실행 정책 변경의 trusted controller 부재, missing·pending·failed 최신 완료 후보는
   기존대로 Full 실행으로 닫힌다.
6. required `Render Diff / Canvas visual diff` check 이름과 생성 주체를 바꾸지 않는다.
7. privileged event·permission을 추가하지 않고 PR head script를 write token으로 실행하지 않는다.

## 5. 단계별 수행

### Stage O2-1 — 재현 계약 고정

1. #6214의 세 SHA와 run `33071270488` preflight 로그를 기준 증적으로 기록한다.
2. workflow inline JavaScript를 현재 Python harness에서 실행할 수 있도록 Render Diff의
   `listWorkflowRuns`·`listJobsForWorkflowRun`·identity step fixture를 보완한다.
3. `code -> current-base bridge -> review tail`과 bridge 이전 base identity를 입력하고, 기대값을
   `pending-base-merge-tree`로 둔 red 계약이 수정 전 `canvas-visual-diff-identity-mismatch`로 실패함을 고정한다.
4. bridge 없음, 복수 bridge, wrong PR·branch·repository, PR 생성 전 run, missing·pending·failed run,
   identity step 실패는 계속 Full fallback인지 같은 실행 harness로 확인한다.

**종료 게이트**: 실제 장애 계보를 재현하는 테스트가 수정 전 실패하고, bridge 없는 동일 입력은 허용되지 않음을
함께 증명한다.

### Stage O2-2 — 최소 workflow 정정

1. candidate loop만 `renderDiffResult(candidateSha, pr, Boolean(baseMergeBridge))` 형태로 검증 대상
   `baseMergeBridge` 존재 여부를 전달한다.
2. identity lookup 이후의 `setPendingBaseMergeResult`와 merge-tree 검증 흐름은 변경하지 않는다.
3. 직접 bridge, 일반 review tail, 복수 bridge, failed newer candidate 계약을 그대로 유지한다.

**종료 게이트**: 새 재현 테스트는 통과하고 fail-closed 음성 조합은 모두 기존 결과를 유지한다.

### Stage O2-3 — 비례 검증과 제출 준비

다음을 실행한다.

```bash
python3 -m unittest scripts.tests.test_review_only_fast_pass_workflows
python3 -m unittest scripts.tests.test_ci_impact_workflow
node --test scripts/tests/ci-impact-policy.test.cjs
cargo fmt --all
cargo fmt --all -- --check
git diff --check
```

workflow YAML의 inline JavaScript syntax, event·permission·required check 이름, 변경 파일 범위를 함께 대사한다.
제품 명령이나 renderer 구현을 바꾸지 않으므로 Cargo 전체 회귀, Native Skia, WASM, Studio, 시각 검증은 수행하지
않는다. 재검토 기준선은 Python 계약 18/18 통과다.

**종료 게이트**: 집중 계약과 형식 검증이 모두 통과하고 rollback이 해당 workflow·test commit revert 한 번으로
가능하다.

### Stage O2-4 — 승인 기반 적용과 live 관찰

1. 계획 승인 뒤 #6243을 메인테이너에게 할당한다.
2. 구현·검증 결과를 commit하고, 별도 승인 뒤 remote push와 PR 생성을 수행한다.
3. workflow 실행 정책 변경 PR이므로 Full CI·Render Diff를 통과한 code candidate를 확보한다. 기본 브랜치에
   controller가 아직 없으므로 #6243 PR의 후행 review 기록도 Full fallback하는 것이 이 단계의 정상 결과다.
4. 최신 head의 required checks와 fail-closed를 확인한 뒤 승인에 따라 `devel`에 정상 병합한다. 이때 #6243은
   post-release canary가 남아 있으므로 자동 close하지 않는다.

**종료 게이트**: 수정 workflow와 계약 테스트가 `devel`에 포함되고 모든 required check가 성공한다.

### Stage O2-5 — 정상 릴리즈와 post-release canary

1. 릴리즈 절차의 전체 검증과 별도 승인을 거쳐 `devel -> main` release PR을 처리한다. #6243만 `main`에 직접
   cherry-pick하거나 admin push하지 않는다.
2. `main` 병합 뒤 `CI Impact Policy Controller`의 `pull_request_target`·`workflow_run` 등록과 최소 권한을
   live 조회한다.
3. 후행 #6215 workflow 변경 PR을 실제 canary로 사용한다. Full code candidate가 성공한 뒤 review-only tail을
   추가하고, 필요하면 그 사이 발생한 current-base bridge까지 포함해 trusted status와 Render Diff를 관찰한다.
4. `current-base-update-merge-tree-green:*` 또는 `current-base-update-merge-resolution-mydocs-only-green:*`,
   Canvas worker skip, required check success를 실제 run에서 확인한다.
5. canary가 성공하면 #6243에 run URL과 SHA를 기록하고 close한다. 실패하면 #6215를 Full fallback 상태로 두고
   #6243을 다시 열어 둔 채 원인 수정 또는 release commit revert를 판단한다.

**완료 조건**: `main`의 trusted controller와 수정 Render Diff가 함께 활성화되고, 실제 후행 workflow PR에서
중복 Canvas가 억제되며 모든 required check가 성공한다.

## 6. 예상 변경과 rollback

- 예상 변경: workflow 조건 1곳, Render Diff preflight 계약 test와 이 계획·운영 기록
- 비용 효과: 해당 계보마다 Canvas worker 약 5분대 중복 실행 제거(PR #6214 관측 기준이며 보장값 아님)
- rollback 조건: merge bridge가 없는데 prior base를 허용하거나 merge-tree 검증 전 fast-pass가 확정되는 경우
- devel rollback: 수정 commit revert 후 모든 입력을 기존 Full fallback으로 복원
- main rollback: release PR의 실제 merge commit과 배포 영향을 확인한 뒤 승인된 revert PR로 복구
