## 3. 원인 계보와 확정 판정

### 3.1 성공했던 릴리스

v0.8.0~v0.8.3은 Release가 게시된 직후 `Publish All Packages`의 `release` run이 생성됐다. 이때
Release 게시 시각은 `Release Binary`의 자산 첨부 job 완료보다 앞선다.

| 릴리스 | Release 게시 | Release Binary 시작·완료 | package run |
| --- | --- | --- | --- |
| v0.8.0 | 2026-07-25 22:29:06 UTC | 22:29:08–22:41:16 | 22:29:08 `release`, 성공 |
| v0.8.1 | 2026-07-26 12:59:16 UTC | 12:58:51–13:10:27 | 12:59:18 `release`, 성공 |
| v0.8.2 | 2026-07-26 15:57:18 UTC | 15:57:04–16:08:37 | 15:57:20 `release`, 성공 |
| v0.8.3 | 2026-08-11 20:36:50 UTC | 20:36:40–20:51:13 | 20:36:52 `release`, 성공 |

즉, 이 구간은 사람이 먼저 Release를 게시했고, 뒤이어 `Release Binary`가 자산을 첨부했다. package
workflow는 binary 5종의 성공을 기다린 것이 아니므로 현재 보호 불변식도 실제로 보장하지 않았다.

### 3.2 누락된 릴리스

v0.8.4와 v0.8.6은 draft Release가 먼저 생성됐고, `Release Binary`의 `Attach to GitHub Release`
job이 자산을 올리면서 `draft: false`로 바꿨다.

| 릴리스 | draft 생성 | 자산·Release 게시 | 자동 package run | 복구 |
| --- | --- | --- | --- | --- |
| v0.8.4 | 2026-08-12 01:17:59 UTC | bot 자산 01:33:50, 게시 01:33:52 | 없음 | 수동 run #31556367061 |
| v0.8.6 | 2026-09-02 02:41:42 UTC | bot 자산 03:00:30, 게시 03:00:31 | 없음 | 수동 run #33623579151 |

`release-binary.yml`이 고정한 `softprops/action-gh-release` commit의 `token` 입력은 생략 시
`${{ github.token }}`을 사용한다. 실제 workflow는 별도 token을 넘기지 않는다. GitHub 공식 계약은
repository `GITHUB_TOKEN`으로 발생한 event가 `workflow_dispatch`와 `repository_dispatch` 등 명시된
예외를 제외하면 새 workflow run을 만들지 않는다고 규정한다.

- [GitHub: GITHUB_TOKEN이 workflow run을 만드는 조건](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs)
- [GitHub: reusable workflow 호출](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)

따라서 직접 원인은 **draft를 게시한 인증 주체가 사람에서 `GITHUB_TOKEN`으로 바뀌었는데도
`release.published` 간접 연쇄를 계속 배포 계약으로 사용한 것**이다. API의 Release `author`는 draft
작성자를 보여 주므로 게시 인증 주체의 반증 자료가 아니다. 자산 uploader, action 입력, job·게시 시각,
공식 token 계약을 함께 봐야 한다.

## 4. 채택 구현 방향

### 4.1 Release Binary가 package workflow를 직접 호출

`npm-publish.yml`을 reusable workflow로 만들고 `release-binary.yml`의 release 완료 뒤 로컬 경로로
호출한다.

- `uses: ./.github/workflows/npm-publish.yml`은 GitHub 공식 계약상 caller와 **같은 commit**의 workflow를
  사용한다.
- 정식 publish는 `push` event의 `refs/tags/v*`에서만 허용한다.
- 다섯 binary build와 Release 자산 첨부가 성공한 뒤에만 package 호출 job이 시작된다.
- called workflow 실패는 caller run 실패로 전파한다. package 누락을 녹색 Release Binary로 남기지 않는다.
- 불확정적인 `release: published` trigger는 제거해 사람 게시와 bot 게시의 동작 차이 및 이중 실행을 없앤다.

개인 PAT 또는 별도 GitHub App token으로 기존 event 연쇄를 살리는 방안은 채택하지 않는다. 새 장기
credential의 발급·회전·감사 비용을 만들면서도 exact-SHA와 부분 재시도 문제를 별도로 풀어야 하기 때문이다.
`workflow_dispatch`/`repository_dispatch` API를 caller에서 호출하고 새 run을 polling하는 방안도 비동기
run 탐색과 실패 전파가 추가되므로 기본안보다 복잡하다.

### 4.2 production과 비게시 검증을 분리

`npm-publish.yml`은 두 진입점을 둔다.

1. `workflow_call`: Release Binary가 정식 태그에서 `publish=true`로 호출한다.
2. `workflow_dispatch`: 기본값은 `publish=false`인 비게시 검증이다. 운영 복구에서 실제 publish하려면
   메인테이너가 release tag ref와 `publish=true`를 명시해야 한다.

production mode는 실행 전에 다음을 실패-폐쇄로 검증한다.

- ref가 `v*` tag이며 checkout HEAD와 `github.sha`가 같다.
- tag가 가리키는 commit과 checkout commit이 같다.
- Cargo/package의 공개 버전이 tag 버전과 같다.
- 같은 tag의 GitHub Release가 존재하고 draft가 아니며 대상 commit이 같다.

비게시 mode는 같은 WASM·npm package·VSIX 생성 경로를 실행하되 npm·Marketplace·Open VSX publish job과
secret 사용을 건너뛴다. `devel` exact head의 실제 Actions run으로 reusable 호출 배선과 산출물 생성까지
검증한다.

### 4.3 채널별 재실행 안전성

- npm 두 패키지는 현재의 exact-version 존재 확인과 skip 계약을 유지한다.
- VS Code Marketplace와 Open VSX를 하나의 직렬 job에서 분리한다.
- VSIX는 한 번 만들고 artifact로 전달하며, 각 채널은 공개 상태에서 exact version 존재를 독립 확인한다.
- 이미 존재하면 성공으로 skip하고, 없을 때만 해당 채널 secret으로 publish한다.
- 상태 API가 timeout·인증 오류·해석 불능이면 “미게시”로 추정하지 않고 실패한다.
- 한 채널 성공·다른 채널 실패 뒤 재실행하면 성공 채널은 skip되고 실패 채널만 다시 게시된다.

채널 상태 확인은 secret을 사용하지 않는 작은 repository script와 offline fixture test로 고정한다. 로그와
artifact에는 token이나 인증 URL을 넣지 않고 tag, exact SHA, package/version, 채널별
`already-present | published | verify-only | failed` 판정만 남긴다.

### 4.4 workflow promotion과 관찰

이번 변경은 `release-binary.yml`과 `npm-publish.yml`의 실행 의미를 바꾸므로 #6689 promotion policy에
두 workflow의 비게시 실행 계약을 추가한다. 다음 release 전에 main을 devel에 먼저 동기화하고, 새 exact
devel SHA에서 두 workflow를 포함한 promotion inventory·필수 dispatch를 다시 만들어야 한다.

정식 tag run에서는 `Release Binary`가 다음 순서로 보일 때만 성공이다.

`5-platform build → Release asset attach/publish → reusable package validation/build/publish → aggregate success`

## 5. 보호 불변식

1. Release Binary 다섯 플랫폼이 모두 성공하기 전에 외부 package·extension을 게시하지 않는다.
2. production publish 입력은 승인된 `v*` tag의 exact commit이며 움직이는 `main`을 checkout하지 않는다.
3. npm Trusted Publishing의 OIDC와 `environment: NPM_TOKEN`을 장기 token으로 대체하지 않는다.
4. `VSCE_PAT`, `OVSX_PAT`를 호출 입력·로그·artifact·문서에 노출하지 않는다.
5. reusable workflow의 token 권한은 caller에서 확대할 수 없게 `contents: read`, `id-token: write`의 필요한
   job 경계로 제한하고 Release write 권한과 분리한다.
6. 수동 dispatch 기본값으로 실제 publish하지 않는다.
7. 이미 게시된 immutable version을 덮어쓰거나 부분 성공 채널 때문에 미게시 채널을 영구 차단하지 않는다.
8. 상태 확인 실패를 “없음”으로 바꾸지 않는다.
9. 테스트를 위해 가짜 release tag나 외부 package version을 게시하지 않는다.
10. #6689 workflow promotion 성공을 #6634 production publish 성공으로 대신하지 않는다.

## 6. 단계별 수행

### Stage 1 — 원인 계보·RED 계약

1. v0.8.0~v0.8.6 Release·binary·package run 시각과 actor 표면을 정규화한 조사 기록으로 보존한다.
2. 사람 게시 성공군과 action 게시 누락군의 차이를 계약 fixture로 만든다.
3. 간접 `release.published`, release 전 조기 publish, branch ref production, tag/SHA/version 불일치,
   extension 직렬 publish, 모호한 상태 조회를 검출하는 RED test를 작성한다.

**종료 게이트**: 기존 workflow가 자동 기동·exact SHA·부분 재시도 보호 계약에서 의도대로 실패하고,
원인이 단순 네트워크 지연이나 Actions 등록 누락이 아님을 증적과 test가 함께 설명한다.

### Stage 2 — reusable 호출·exact release guard

1. `npm-publish.yml`에 `workflow_call`과 안전 기본값의 `workflow_dispatch`를 구성한다.
2. `release-binary.yml`의 binary/release/package 순서를 직접 dependency로 연결한다.
3. job별 `contents`·`id-token` 권한과 secret 전달 경계를 최소화한다.
4. tag, checkout SHA, release, package version을 검증하는 fail-closed preflight를 구현한다.

**종료 게이트**: Stage 1의 호출·순서·권한·exact-source RED가 GREEN이고, branch ref에서 production을
요청하는 negative fixture가 모두 실패한다.

### Stage 3 — channel idempotency·부분 재시도

1. package/extension build와 외부 publish를 분리하고 VSIX를 한 번만 생성한다.
2. npm core/editor, VS Code Marketplace, Open VSX의 exact-version 상태 판정을 독립시킨다.
3. 전체 미게시, 전체 기게시, VS Code만 성공, Open VSX만 성공, 조회 실패 fixture를 검증한다.
4. 모든 채널 결과를 하나의 비민감 publish evidence와 job summary로 집계한다.

**종료 게이트**: 부분 성공 재실행에서 기게시 채널은 성공 skip, 미게시 채널만 publish 대상으로 판정되며
한 채널 실패가 다른 채널의 재시도를 구조적으로 막지 않는다.

### Stage 4 — promotion policy·매뉴얼 현행화

1. `scripts/workflow_promotion_policy.json`에 Release Binary와 Publish All Packages의 비게시 실행 계약을
   추가하고 verifier fixture를 갱신한다.
2. `github_operations.md`와 `publish_guide.md`를 직접 호출, 수동 복구, 관찰·rollback 절차와 일치시킨다.
3. 기존 문서에서 “Release 생성만 하면 자동 실행”이라고 단정한 활성 설명을 새 순서로 정정한다.

**종료 게이트**: main..devel inventory에 두 workflow가 미등록 executable로 남지 않고, 문서와 workflow
trigger·job·permission mirror test가 일치한다.

### Stage 5 — 로컬 회귀·비게시 원격 실증

1. workflow 정책·release channel·promotion verifier test, YAML/actionlint, `git diff --check`, Markdown
   link·metadata 검사를 실행한다.
2. package별 lockfile install/build/pack과 VSIX 생성을 실제로 검증한다. Rust source를 바꾸지 않으므로
   무관한 renderer·시각 회귀는 실행하지 않는다.
3. 별도 승인 뒤 exact task/devel head에서 Release Binary manual `tag=test`를 실행해 5-platform build,
   reusable package build와 외부 publish job skip을 확인한다.
4. run의 head SHA, workflow blob, job·step run/skip, artifact와 외부 채널 무변경을 기록한다.

**종료 게이트**: 비게시 run이 전체 직접 호출 경로를 통과하고 npm·VS Code·Open VSX version이 실행 전후
같다. remote workflow dispatch는 메인테이너 승인 전 실행하지 않는다.

### Stage 6 — 최종 보고·PR·다음 release canary

1. 최신 `upstream/devel`과 열린 workflow PR을 다시 확인하고 merge tree를 검증한다.
2. 최종 보고서에 원인, 변경, test, 비게시 run, 보안·비용, rollback과 다음 release canary를 기록한다.
3. push와 PR 생성은 각각 별도 승인 뒤 수행하고 exact PR head CI와 self-review를 확인한다.
4. 다음 정식 release에서 package 호출이 같은 tag SHA로 정확히 한 번 실행되고 네 채널이 성공했는지
   post-release 증적으로 추가한다.

npm package, VSIX build만 영향 범위에 맞게 검증한다.

## 8. rollback과 승인 게이트

- 로컬 구현 실패: task branch commit만 정정하며 사용자 WIP와 review worktree를 건드리지 않는다.
- remote 검증 실패: 외부 publish가 없는 verify mode이므로 workflow·artifact만 보존하고 원인을 수정한다.
- PR merge 전: latest devel과 workflow promotion policy 불일치가 있으면 push·merge를 멈춘다.
- merge 후: 잘못된 자동 publish 가능성이 발견되면 다음 tag 전 일반 revert PR로 caller를 제거하고 수동
  tag-ref dispatch만 임시 복구 경로로 사용한다.
- publish 뒤에는 npm·Marketplace version을 삭제·덮어쓰지 않는다. 채널별 skip 후 미완료 채널만 재시도한다.
- workflow dispatch, push, PR 생성, comment, merge, Issue close는 각각 메인테이너의 명시 승인을 받는다.

이 수행계획 승인 전에는 Stage 1 RED test와 workflow 구현에 진입하지 않는다.
