## 1. 목표와 성공 기준

메인테이너가 Controller 실행 요약에서 실패 유형, 대상 PR/head, 원본 실패 workflow/job/step,

현재 메시지는 `workflow-not-success:CI:failure`이며 실제 실패는

이 결과만으로 신규 회귀를 단정하지 않는다. renderer 문제 해결은 본 작업에 포함하지 않는다.

## 2. 확인된 출발점과 남은 조사

- `scripts/ci-impact-policy.cjs::auditPolicyRuns`는 workflow conclusion이 success가 아니면
  job 상세 검증 이전에 일반 reason으로 반환한다. 실패 판정 자체가 잘못됐다는 뜻은 아니다.
- `.github/workflows/ci-impact-policy.yml`의 `Summarize trusted policy`에는 정책/집계 사유는 있지만
  원본 실패 job·step·오류를 연결하는 보고가 없다.
- #6819는 취소 충돌 문제로 범위가 다르다. 유사 이슈·열린 Controller PR 검색 후 #6899를 등록했다.
- Stage 1에서 현재/최초 도입 이력, 이미 수집하는 run/job 필드, run attempt 선택,
  main/devel 실행 코드 차이와 초기 단계 실패 시 summary 누락을 조사한다.

## 3. 구현 범위와 보호 불변식

1. 선행 검증 실패 / Controller 내부 실패 / 증적 미확인을 구분한다.
2. PR 및 head/base, run ID·attempt, 실패 job·step, 원본 링크를 연결한다.
3. 실패한 검증 job을 집계 job과 구분한다. 다중 실패를 제한된 목록으로 표시하며
   시간순서만으로 근본 원인을 단정하지 않는다.
4. 메타데이터 우선, 실패 시에만 필요한 annotation/로그를 제한적으로 조회한다.
   추출 불가·권한 오류·로그 부재는 미확인 사유와 링크로 표현한다.
5. 진단 실패는 기존 policy verdict를 바꾸지 않는다. 성공을 실패로 만들거나 실패를 성공으로 완화하지 않는다.
6. exact identity, stale 및 fail-closed, required context, fast-pass, concurrency, 최소 권한을 보존한다.
7. PR 코드·artifact 실행 금지. 로그는 비신뢰 데이터이며 escape·민감정보 필터·길이·조회량·시간 상한을 둔다.
8. 자동 댓글·재실행·baseline 변경·제품 코드 수정·child issue 생성은 제외한다.

## 4. 단계와 승인 지점

| 단계 | 작업 및 산출물 | 다음 gate |
| --- | --- | --- |
| Stage 1 | 원인 계보·수집 필드·main/devel 배선 조사, 진단 데이터 계약 및 구현계획 | 구현계획 승인 |
| Stage 2 | 보고 helper/배선과 집중 테스트를 한 구현 묶음으로 작성 | 구현 결과 승인 |
| Stage 3 | 기존 정책 계약 회귀, 악성/과대 입력 및 오류 경계, 호출량·시간 비용 측정, PR 준비 | 결과 및 push·PR 승인 |
| Stage 4 | 원격 CI 확인·self-review·승인 후 병합, 운영 적용 여부 구분 | 병합 및 별도 배포 승인 |

단계 전환 전에 해당 단계 변경을 커밋한다. 불필요한 세분화나 증적만을 위한 추가 이슈는 만들지 않는다.
수행계획 승인 전 구현을 시작하지 않는다. 오늘할일/PR 문서는 PR 준비·채번 시점에 역할별 절차로 작성한다.

## 6. 운영 적용·완료·복구

Controller YAML은 default branch 등록형이다. trusted-base script 변경은 선택된 PR base의
코드에 따라 달라지므로 YAML과 helper 각각의 실제 소비 경로를 Stage 1에서 확정한다.
devel 병합만으로 main의 workflow 배선이 바뀌었다고 보고하지 않는다.

정상적인 main 승격 또는 별도 승인된 운영 적용 이후 exact run에서 summary·원본 링크·판정 보존을
확인해야 운영 적용 완료다. main 직접 push, dispatch, 재실행, 권한 확대는 본 계획 승인에 포함하지 않는다.
devel 구현 완료와 live 적용 대기를 구분하여 보고하며, 미적용 상태에서 이슈를 해결 완료로 닫지 않는다.

복구는 보고 helper/배선 변경만 되돌리는 방식으로 설계한다. 기존 policy 판정 및 required check는 유지한다.
