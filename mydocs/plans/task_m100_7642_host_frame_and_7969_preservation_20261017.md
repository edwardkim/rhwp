# #7642 호스트 줄의 공통 배치와 #7969 기능 보존

Issue: #7642. 기준 devel은 `04f8c2bd1617f0dbec6f10543913391ff088c4a7`이다.
현재 보정 문서 전체와 [#7969](https://github.com/edwardkim/rhwp/pull/7969)의
기능을 함께 충족해야 제출한다. 한쪽의 통과로 다른 쪽을 대신하지 않는다.

## 독립 근거와 소비 경로

- #1440의 원본 및 호스트 102의 저장 줄만 제거한 진단 입력을 각각 한컴 Print와
  대조했다. 진단 입력의 첫 줄은 138.08px, 다음 줄은 124.8px에서 시작한다.
  기존 Native의 첫 줄 124.7px는 들여쓰기 1000 HU를 잃었다. 물리 프레임의
  구간은 문단 여백·배제 영역을 포함하지만 줄 채움이 별도로 소비하는 들여쓰기와
  목록 마커는 포함하지 않는다. 줄 채움 → 실제 RowSegment → LineSeg 투영 →
  paragraph_layout의 글줄 원점·가용 폭까지 같은 소유 정보를 전달한다.
  같은 물리 행의 두 번째 구간에는 들여쓰기·마커를 다시 적용하지 않는다.
- 같은 실행에서 호스트 측정 전진은 96px지만 실제 배치 전진은 106.6667px다.
  layout_table_item이 호스트 배치 전에 간격 소비 상태를 복사하고,
  layout_table_control_block이 layout_inline_flow_plan을 통해 그 상태를 갱신해도
  표 뒤 간격 분기가 이전 값을 읽는다. 앞 간격 판단은 배치 전 상태를 유지하고,
  뒤·마지막 줄간격 판단은 실제 배치가 반환한 소비 상태를 사용한다.
- #7969의 image_conv는 흑백·디더링을 원본 픽셀에서 처리한 뒤 nearest를 선택한다.
  ReplayPolicy의 fastPreview·PreferRaster도 nearest를 요청한다. 현재 브랜치의
  전체 이미지 축소용 mipmap 준비가 이 최종 선택을 덮어쓴다. 최종 sampling이
  nearest이면 축소용 선형 보간을 만들지 않는다. 일반 선형 그림의 저역 통과,
  자른 원본의 strict 경계, 색조·캐시·실패 fallback은 유지한다.

문서 ID·특정 좌표에 대한 분기, 빈 페이지 삭제, 출력 은폐를 추가하지 않는다.
원본의 쪽수 47 대 Print 46 문제는 위 간격과 별도로 남아 있으며, 앞 문단의
줄 수용 경계를 분석한다. 빈 문단 삭제로 쪽수만 맞추지 않는다.

## 검증 범위

1. 현재 보정 범위 102문서 1704쪽은 유지한다. 새 head와 고정 devel을 같은 원본·
   Print PDF·글꼴·DPI·PDFium으로 Native/fresh WASM 비교한다.
2. #7969의 13개 입력·26개 backend-page를 추가 대조한다. 본문·혼합 글자·그림
   crop·그룹·극한·두 형식의 폼·Native IME 저장본과 색조 대조군 5개를 포함한다.
   극한 PDF는 통합 단계 8의 SHA가 같은 영구 경로를 사용한다.
3. #7969의 Native host·실제 C ABI feature-on/off·집중 Rust 검사·Studio 단위·
   fresh 브라우저 geometry·글꼴·색조·crop을 다시 확인한다. 소스 동일성만으로
   실행 통과를 주장하지 않는다. 현재까지 Studio 단위는 2316 PASS/0 FAIL/2 skip다.
4. 물리 행은 양수 들여쓰기·음수 내어쓰기·다중 구간·목록 마커·첫/후속 줄을
   대조한다. 실제 문서의 새 회귀는 전쪽 raw 90%와 직접 판독 뒤 새 이름으로
   추가한다. 완료 페이지의 좌표 검사는 양쪽 raw 98%와 독립 기대값이 필요하다.
5. 전체 Rust·lint·fresh WASM·실제 판독을 완료하고, PR 직전 devel head를 다시
   확인한다. 90% 미만·쪽수 차이·0.01%p 이상 하락·눈에 보이는 결함은 제출을 보류한다.
   이후 승인된 PR·CI·옵션 2 기록 PR·merge 후속 처리를 계속한다.

진행 중인 b3795a7a73 빌드는 고정 worktree에서 계속한다. 이번 보정 뒤의 실행과
구분하며 해당 결과를 새 head의 최종 검증으로 재사용하지 않는다.
