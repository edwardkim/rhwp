## 1. 목표

직전 릴리즈 `v0.8.2` 이후 `devel`에 통합된 변경을 `v0.8.3`으로 배포한다. 코드와 문서만
태그로 묶는 데서 끝내지 않고, 태그가 새로 가동하는 패키지·바이너리·설치 프로그램·컨테이너
워크플로까지 검증하고 실제 배포 상태를 확인한다.

## 2. 기준선과 범위

| 항목 | 값 |

| 직전 릴리즈 | `v0.8.2` = `9b16aa9e23f476e2b335d7c029fc9f24a199d63c` |
| 릴리즈 준비 기준 | `upstream/devel` = `572786d0246915e435ab1cd94be8c72f49304bb5` |

이번 버전은 작업지시자가 `0.8.3`으로 확정했다. 스키마와 semver 연동은 현재 canonical 문서에서
아직 제안 상태이므로, 본 릴리즈 번호를 재판정하는 게이트로 사용하지 않는다.

## 3. main 계보 동기화

`main`에는 기본 브랜치에서만 등록되는 CI workflow를 조기 가동하기 위해 직접 병합한 이력이 있다.
그 변경들은 당시 `devel`의 동일 파일을 복사한 것이고, 현재 차이는 `devel`에서 후속 발전한
`cache-generation-sweep.yml`, `codeql.yml`, `render-diff.yml` 세 파일이다.

릴리즈 작업 브랜치에서 `upstream/main`을 merge commit으로 흡수한다. 충돌 시 현재 `devel`
내용을 유지한다. 병합 직전과 직후의 트리 해시를 비교해 **계보만 합쳐지고 파일 내용은 바뀌지
않았음**을 확인한다. 이 merge commit은 이후 `devel → main` 통합에서 ancestry를 보존하기 위한
것이며 squash하지 않는다.

## 5. 버전·문서 갱신 대상

기본 동기화 대상은 다음과 같다.

- Rust·공식 소비자: `Cargo.toml`, `Cargo.lock`, `rhwp-vscode/package.json`,
  `npm/editor/package.json`, `rhwp-studio/package.json`
- 브라우저 확장: Chrome·Firefox의 manifest/package와 Safari manifest
- lockfile: 각 npm 작업공간에서 package version 정합이 필요한 경우 함께 갱신
- 릴리즈 노트: `CHANGELOG.md`, `CHANGELOG_EN.md`, `rhwp-vscode/CHANGELOG.md`
- 현행 표지: README 한국어·영어, `THIRD_PARTY_LICENSES.md`
- 스토어 문서: Chrome 한국어·영어, Edge reviewer note, Firefox AMO note

`pkg/package.json`은 직접 편집하지 않는다. `@rhwp/core`는 `Cargo.toml`에서 생성한다. Node/Python
바인딩은 태그 빌드에서 `tools/set_package_version.py`가 태그와 일시 정렬하므로, 저장소 개발
버전을 무조건 릴리즈 번호로 고정하지 않고 workflow 계약과 테스트로 검증한다.

Scoop·Homebrew·Winget 해시는 릴리즈 바이너리의 `SHA256SUMS.txt`가 생성된 뒤에만 확정할 수 있다.
따라서 `tools/update_channel_manifests.py`를 사용한 채널 매니페스트 갱신은 태그 후 후속 PR로
분리한다. AUR은 자동 갱신 대상이 아니므로 별도 확인한다.

## 6. 검증 계획

- Rust: build, fmt, clippy, release-test 전체 테스트와 계약·스키마 집중 테스트
- WASM: 프로젝트 공식 Docker 절차로 빌드하고 Studio 사용 위치에 반영
- Studio·확장: build/test, E2E, 확장 build와 필수 산출물 확인
- 바인딩: Node generated type drift·테스트, Python 테스트·패키지 빌드
- 릴리즈 패키지: 태그/Cargo 버전 게이트, 바이너리·휠·sdist·npm wrapper·deb/rpm/MSI·Docker
  workflow의 트리거와 비밀정보 게이트 확인
- 위생: `git diff --check`, 버전 문자열 검색, 배포 zip의 민감 파일·개인 폰트·대형 로컬 자산 제외

PR 직전의 전체 CI 성격 검증, 원격 push, PR 생성, merge, 태그와 GitHub Release 생성은 프로젝트
승인 게이트에 따라 진행한다.

## 7. 위험과 대응

- **main 계보 분기**: 먼저 release branch에서 흡수하고 tree hash 동일성으로 내용 무변경을 증명한다.
- **2주간 대규모 변경**: 커밋 제목만으로 CHANGELOG를 만들지 않고 PR·경로·계약 diff를 교차 확인한다.
- **새 배포 채널의 첫 태그 실행**: secret이 없는 채널은 명시적 skip이 정상인지 구분하고, 게시 성공과
  레지스트리 반영 완료를 동일시하지 않는다.
- **배포 중 기준선 이동**: 각 원격 변경 단계 전 fetch하고 `devel`이 이동하면 범위와 검증을 다시 판단한다.
- **릴리즈 이슈 조기 종료**: PR 본문에 `Closes #4601`을 쓰지 않고 배포 후 수동으로 닫는다.
