## 2. 1차 조사 결과 (코드/SVG 무수정)

### 2.1 본질 결함 위치 — `tokenizer.rs::read_command` (L101-124)

```rust
fn read_command(&mut self) -> Token {
    for kw in ["bold", "it", "rm"] {       // ← prefix-split 대상이 3개 뿐
        if self.matches_at(kw) {
            let after = self.peek(kw.len());
            if matches!(after, Some(c) if c.is_ascii_alphanumeric()) {
                self.pos += kw.len();
                return Token::new(TokenType::Command, kw, start);
            }
        }
    }
    // 그 외: 연속 alphanumeric 을 단일 토큰으로 — 결함 발현
    while let Some(ch) = self.current() { ... }
}
```

`"timesm"` 입력 → 단일 Command 토큰 `"timesm"` (기대: `"times"` + `"m"`).

### 2.2 정답 keyword 목록은 `symbols.rs::lookup_symbol` 에 등록됨

`symbols.rs` 에 그리스 문자 (alpha/beta/...), 특수 기호 (times, sim, cdot, ...), 함수 (sqrt, sin, cos, ...) 등 수십 개 keyword 가 등록. 단 토크나이저가 이 목록과 sync 되지 않음.

## 6. 위험 요소

### 6.1 Keyword prefix 충돌
짧은 keyword (alpha, beta, pi, mu, ...) 가 더 긴 식별자의 prefix 일 수 있음. 예: `"alphabet"` → `"alpha"` + `"bet"` (잘못). HWP 수식 script 컨벤션 확인 필요 — 식별자가 그리스 문자 + 라틴 문자 결합으로 시작하는 케이스가 있는지.

→ Stage 1 에서 광범위 sweep 으로 충돌 가능성 측정.

### 6.2 메모리 정합
- `feedback_rule_not_heuristic`: 토크나이저 분리 룰은 HWP 수식 script 표준 룰이어야 함. 휴리스틱 (안 C) 도입 회피.
- `feedback_essential_fix_regression_risk`: 토크나이저는 모든 수식 처리의 기반. 광범위 sweep 필수.
- `feedback_pdf_not_authoritative`: PDF 비교는 보조 ref.

### 6.3 longest-prefix match 의 비용
모든 keyword 와 매번 비교 → 토크나이저 성능 저하 가능. HashMap/Trie 구조로 최적화 가능 (Stage 2 에서 결정).
