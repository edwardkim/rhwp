## 1. 목표

정상적인 필드 값 편집 뒤 메모리 문서와 저장·재적재 문서가 같은 조판 파생 상태를 갖도록 한다.
`batch fill --verify`의 diff를 무시하거나 종료 코드를 완화하지 않고, 편집된 문단을 실제 소유 상자의
폭과 흐름 안에서 즉시 재조판해 원인을 제거한다.

완료 범위는 본문 ClickHere 필드 하나에 한정하지 않는다. 공개 setter가 도달할 수 있는 본문·표 셀·
글상자 필드를 입력 방식별로 분류하고, 지원하는 모든 경로가 동일한 저장 왕복 불변식을 지키게 한다.

## 2. Stage 0 감사 기준선

### 2.1 확인된 재현과 원인 계보

1. `set_field_text_at`은 문자열·문자 모양·범위·offset을 갱신한 뒤 기존 `LineSeg`를 비운다.
2. 종전 setter는 그 뒤 section compose만 갱신하고, 편집 문단의 소유 상자 폭으로 `LineSeg`를
   다시 만들지 않았다.
3. HWP5 저장기는 메모리에 남은 빈 줄 배열을 기록할 수 있고, 재적재 경로는 최소 줄을 다시 합성한다.
4. 따라서 같은 편집 결과가 메모리에서는 0줄, 저장·재적재 뒤에는 1줄 이상이 되어 `--verify`가
   exit 3, `identical=false`, `diffCount>0`을 반환했다.
5. #6628 Stage 4의 정상 입력 전수 1,035건 중 `batch-ops/BO05`, `BO15`만 이 제품 결함으로 실패했다.

보존 WIP를 격리 빌드한 바이너리로 두 task만 다시 실행했을 때 두 건 모두 통과했다. 이는 WIP가
발견 증상의 원인 축을 실제로 건드린다는 증거이지, #6641 전체 범위의 완료 증거는 아니다.

### 2.2 보존 WIP 감사

WIP는 다음 두 파일만 바꾼다.

- `src/document_core/queries/field_query.rs`: 편집 전 본문 흐름 끝 보존, 편집 후 본문 또는 중첩
  경로 reflow·vpos 재계산, 표 dirty 처리
- `tests/batch_fill_contract.rs`: 정상 `samples/field-01.hwp` 채움이 exit 0,
  `verify.identical=true`, `verify.diffCount=0`임을 요구

현재 WIP의 방향은 맞지만 그대로 완료로 판정할 수 없는 공백이 있다.

- 기존 통합 계약은 본문 HWP5 한 경로만 직접 고정한다.
- 표 셀 가상 필드와 표 셀 안 ClickHere 필드는 다른 mutation 경로이므로 각각 확인해야 한다.
- 글상자 안 ClickHere와 깊이 2 이상 중첩 경로의 소유 폭·문단 번호 해석이 직접 검증되지 않았다.
- 중첩 reflow helper가 경로 또는 폭 해석 실패 시 조용히 반환하므로, mutation 성공 뒤 stale
  `LineSeg`가 남는 silent success 가능성을 제거하거나 불가능함을 계약으로 증명해야 한다.
- `set_field_value_by_id`와 `set_field_value_by_name_at`의 실제 지원 행렬을 먼저 고정해야 한다.
  특히 가상 셀 필드의 합성 ID를 by-id setter가 지원한다고 가정하지 않는다.

### 2.3 최신 devel 차이

WIP 부모 이후 `upstream/devel`은 16커밋 전진했다. `field_query.rs`와
`batch_fill_contract.rs`의 직접 충돌은 없고 `git merge-tree --write-tree`도 성공했지만,
renderer·table cell layout·paragraph layout이 크게 바뀌었다. 따라서 텍스트 충돌 부재를
조판 호환성으로 간주하지 않고, 계획 승인 뒤 최신 devel을 정상 merge한 head에서 focused 계약부터
다시 실행한다.

## 3. 보호 불변식

1. `--verify`의 diff 무시, 허용 목록, 종료 코드 완화로 결함을 숨기지 않는다.
2. 편집된 본문은 본문 frame, 표 셀은 셀 내용 폭과 padding, 글상자는 글상자 폭과 margin으로 reflow한다.
3. reflow 뒤 해당 컨테이너의 문단 vpos 사다리를 잇고, 본문 후속 흐름과 표 dirty·pagination cache를
   기존 편집 계약과 일치시킨다.
4. `raw_stream` 무효화, 필드 범위, `char_count`, `char_offsets`, 채움 완료 비트 등 #838·#3380
   기존 직렬화 계약을 보존한다.
5. 지원 경로에서 소유자 또는 폭을 해석하지 못한 상태를 정상 성공으로 반환하지 않는다.
6. HWP5 정상 저장 왕복은 메모리와 재적재 문서의 줄 수·줄 시작·vpos가 일치해야 한다.
   HWPX의 새 reflow 합성 LineSeg는 bit 31 표식과 함께 파일에서 생략하는 기존 안전 규약을 지키고,
   대신 저장 왕복 문자모양 경계와 재계산 가능한 텍스트 축이 일치해야 한다.
7. 실제 mutation 실패와 미지정 필드의 기존 exit 1/부분 성공 계약은 약화하지 않는다.
8. Gym task·reference·oracle은 이 제품 PR에서 변경하지 않는다.
9. 새 integration source와 파생 suite·manifest를 source diff에 추가하지 않는다.

### Stage 2 — 소유자 인식 재조판 정정

1. 본문 경로는 편집 전 흐름 끝을 보존하고 해당 문단을 reflow한 뒤 section vpos를 잇는다.
2. 중첩 경로는 `NestedEntry` 의미를 보존해 최내곽 표 셀 또는 글상자의 폭·padding/margin으로
   대상 문단을 reflow하고 그 컨테이너의 vpos를 잇는다.
3. 표 안 변경은 필요한 table tree와 section pagination/render cache를 기존 cell edit 계약대로
   무효화한다. 글상자는 별도 table dirty가 없음을 명시하고 section invalidation을 확인한다.
4. 경로·소유 폭 해석 실패가 silent success가 되지 않도록 사전 검증, `Result` 전달 또는 안전한
   보수적 재조판 중 가장 좁은 방식을 적용한다.
5. 같은 section을 필드 여러 개가 연속 편집해도 이전 편집의 새 흐름을 다음 편집이 기준으로 삼게 한다.

**종료 게이트**: Stage 1의 지원 경로가 모두 메모리 안에서 유효한 `LineSeg`와 연속 vpos를 가지며,

## 6. 검증 명령 기준

focused 명령은 Stage 1에서 실제 target 배치를 확인한 뒤 확정한다. PR 준비 전 최소 묶음은 다음과 같다.

```bash
node scripts/rust-test-suite-manifest.mjs --prepare
cargo fmt --all
cargo fmt --all -- --check
cargo clippy --locked --target-dir target/pr-review -- -D warnings
cargo clippy --locked -p rhwp --lib --target wasm32-unknown-unknown \
  --target-dir target/pr-review -- -D warnings
cargo build --locked --workspace --target-dir target/pr-review
cargo clippy --locked --workspace --all-targets --target-dir target/pr-review -- -D warnings
cargo nextest run --locked --cargo-profile release-test \
  --target-dir target/pr-review --tests --no-fail-fast
node scripts/rust-test-suite-manifest.mjs --check
```

`target/pr-review`은 기존 고정 경로를 재사용한다. 현재 약 90GB인 이 디렉터리를 이 이슈가 소유한
임시 산출물로 간주해 삭제하거나 이름을 바꾸지 않으며, 별도 대형 target을 새로 만들지 않는다.
