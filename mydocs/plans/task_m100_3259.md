# 수행계획서 — macOS Finder 드롭 문서의 최근 문서 재열기 핸들 보존 (M100 #3259)

- **이슈**: [edwardkim/rhwp#3259](https://github.com/edwardkim/rhwp/issues/3259)
- **브랜치**: `task/3259-recent-document-reopen-macos` (`upstream/devel@4b5514457` 기준)
- **작성일**: 2026-07-24

## 1. 목표

macOS Finder에서 HWP/HWPX/HML 파일을 rhwp-studio로 드롭해 연 문서도 최근 문서에
`FileSystemFileHandle`을 함께 저장한다. 다른 문서를 연 뒤 해당 최근 항목을 선택했을 때
파일 선택기를 다시 띄우지 않고, 권한 확인을 거친 뒤 같은 문서를 재연다.

## 2. 확인된 원인

현재 흐름은 다음과 같다.

```text
Finder drop → dataTransfer.files[0] → loadFile(file) → loadBytes(bytes, file.name, null)
          → addRecentDoc(handle: null) → openRecentEntry(): needs-pick → file picker
```

- `rhwp-studio/src/main.ts`의 drop handler는 `File`만 넘긴다.
- `loadFile()`은 `loadBytes(..., null)`로 호출하므로 `wasm.currentFileHandle`도 null이 된다.
- `recent-open.ts`는 의도대로 handle 없는 항목을 삭제하지 않고 `needs-pick`과 재선택 안내를
  반환한다. 이 정책(바이트 스냅샷 폴백 금지)은 유지해야 한다.

`DataTransferItem.getAsFileSystemHandle()`은 drop handler의 **같은 tick**에서 호출해야
유효한 Promise를 얻는다. 파일이면 `FileSystemFileHandle`, 디렉터리면 directory handle을 줄 수
있으므로 `kind === 'file'` 확인이 필수다. API는 지원 범위가 제한적이므로 feature detection과
기존 fallback이 필요하다. [MDN API 문서](https://developer.mozilla.org/en-US/docs/Web/API/DataTransferItem/getAsFileSystemHandle),
[Chrome drag-and-drop 안내](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access?hl=en)를 따른다.

## 3. 범위와 안전 조건

| 포함 | 제외 |
|---|---|
| Chromium이 제공한 드롭 파일 handle을 최근 문서·현재 문서에 전달 | 절대경로 수집·표시, 바이트 스냅샷 저장, 권한 우회 |
| 확인 대화상자 이전에는 handle Promise만 동기적으로 capture | 확인 취소 뒤 파일 bytes 읽기 또는 recent entry 저장 |
| 미지원·오류·디렉터리이면 현재 meta-only 재선택 fallback 유지 | Safari/Firefox에 비표준 API 강제 또는 picker 동작 변경 |
| macOS Chrome 실 시나리오 및 TypeScript unit test | 최근 문서 저장소/권한 정책의 재설계 |

## 4. 구현 설계

1. `file-system-access.ts`에 DOM 표준 타입 의존을 최소화한 `DroppedFileSystemHandle`/item
   narrow type과 `captureDroppedFileHandle()` helper를 둔다.
   - `DataTransferItem.getAsFileSystemHandle()`이 있을 때, helper를 호출한 동일 stack에서
     Promise를 시작한다. Promise 거부·null·directory·선택 `File`과 맞지 않는 항목은 null로
     정규화한다.
   - handle을 얻는 것만으로 bytes를 읽거나 IndexedDB에 기록하지 않는다.
2. drop handler에서 `await showDropConfirmDialog()` **전에** 위 Promise를 확보한다.
   승인 뒤에만 Promise 결과를 await하고 `loadFile(file, { fileHandle })`에 전달한다.
   취소하면 handle은 사용하지 않고 현재처럼 종료한다.
3. `loadFile` 옵션에 선택적 `fileHandle`을 추가해 `loadBytes`로 전달한다. 이후의
   `wasm.currentFileHandle` 설정과 `addRecentDoc`은 기존 단일 수렴점을 그대로 사용한다.
4. native API가 없거나 handle 취득에 실패하면 null을 전달한다. 따라서 기존 recent 항목의
   `needs-pick` 안내와 파일 선택기 fallback은 변하지 않는다.

## 5. 검증 계획

1. `file-system-access` 단위 테스트
   - 지원 item은 same-tick에 handle Promise를 시작하고 파일 handle을 반환한다.
   - API 없음, Promise reject, null, directory, 선택 파일 불일치는 null fallback이다.
   - helper 호출 직후 handle API 호출 횟수를 확인해 `await` 전 capture 규칙을 고정한다.
2. Studio focused 검증: TypeScript build와 관련 Node tests(`file-system-access`, `recent-open`,
   `recent-store`)를 실행한다.
3. macOS Chrome 수동 검증
   - Finder로 문서 A를 드롭해 열고, 문서 B를 연 뒤, 최근 문서에서 A를 선택한다.
   - A가 picker/toast 없이 다시 열리는지, 새로고침 후에도 recent handle로 열리는지 확인한다.
   - API를 제공하지 않는 환경에서는 기존 재선택 안내가 유지되는지 확인한다.
