## 1. 목표

편람 HWP/HWPX의 KoPub 글꼴을 Canvas2D에서 처음부터 정확한 face로 그리되, 글꼴 설치 상태와
한글·PDF 생성기 버전이 다른 결과를 하나의 보편 정답지로 섞지 않는다.

완료 계약을 다음 두 층으로 분리한다.

1. **paint 계약**: 저장된 local-font snapshot과 정확한 style face를 첫 Canvas2D paint 전에
   준비하고, 새 감지 결과는 문서 전체 재로드 없이 한 번의 결정적 repaint로 반영한다.
2. **layout 계약**: KoPub 설치 환경의 실제 hmtx와 KoPub 미설치 한컴 환경의 대체 글꼴 메트릭을
   구분한다. 어느 한쪽을 전역 상수로 덮어 다른 환경의 정답을 가장하지 않는다.

#3931의 표 fragment·페이지 소유권 로직은 이 작업에서 변경하지 않는다. KoPub 폰트 파일은
`/home/edward/mygithub/ttfs/kopub`의 외부 검증 자산으로만 사용하며 저장소·PR에 포함하지 않는다.

## 2. Stage 0 조사 결과

### 2.1 오늘 추가된 PDF의 provenance

| PDF | 생성기 | 글꼴 환경 | 쪽수 | 본문 내장 글꼴 |
| --- | --- | --- | ---: | --- |
| `...-2010-no-ttf.pdf` | Hancom PDF `1.3.0.404` | KoPub 미설치 | 389 | `Haansoft Batang` |
| `...-2010-kopub.pdf` | Hancom PDF `1.3.0.404` | KoPub 설치 | 388 | KoPub 6종 + `Haansoft Batang` |
| `...-2020-kopub.pdf` | Hwp 2020 `11.0.0.9136`, Hancom PDF `1.3.0.550` | KoPub 설치 | 383 | KoPub 6종 + `Haansoft Batang` |

동일 한글 2010에서도 설치 여부만으로 389쪽과 388쪽이 갈리고, 같은 KoPub 설치 상태에서도
한글 2010과 2020이 388쪽과 383쪽으로 갈린다. 따라서 PDF 정답지는 최소한 입력 형식, 한글 버전,
PDF producer 버전, 설치 글꼴 목록과 파일 해시를 provenance로 가져야 한다.

### 2.2 한컴 2010 미설치 글꼴의 실제 글립

- KoPub 설치 PDF의 6개 embedded subset을 제공 원본 TTF와 Unicode→CID→glyph outline으로
  대조했다. KoPubBatang Bold/Light/Medium과 KoPubDotum Bold/Light/Medium의 대조 가능 글립
  **2,603/2,603**이 윤곽과 advance 모두 일치했다.
- 미설치 PDF의 `Haansoft Batang` subset을 KoPub 6종과 대조한 결과, 대조 가능 Unicode 933개에서
  non-empty glyph 윤곽 일치는 0개이고 advance 일치는 0개였다. 빈 space 윤곽 한 건만 형식상
  일치했다.
- 설치 PDF 안의 `Haansoft Batang` subset과 미설치 PDF subset 사이 공통 Unicode 26개는
  윤곽과 advance가 **26/26** 일치했다.
- 물리 11쪽 text layer의 SHA-256은 두 한글 2010 PDF가 동일하지만, 설치 PDF는 KoPub 4개 face를
  본문에 사용하고 미설치 PDF의 text span은 전부 `Haansoft Batang`이다.

결론: 이 환경의 한글 2010은 누락된 KoPub 이름을 보존한 채 다른 모양을 그린 것이 아니라,
**KoPub바탕·KoPub돋움 본문 모두 실제 `Haansoft Batang` TrueType 글립과 폭으로 치환해 PDF에
subset embed**했다. 이는 한글 2010 + 해당 설치 상태의 관측이며 모든 한글 버전의 보편 규칙으로
확장하지 않는다.

### 2.3 현재 devel의 재현과 기존 전제 정정

- `fontFamilyChainForDisplay("KoPub바탕체 Light")`는 현재
  `"GulimChe", "D2Coding", "Noto Sans Mono", monospace`를 반환한다. `/바탕체/` 검사가
  serif 검사보다 먼저여서 생기는 확정 결함이다.
- `initializeDocument()`는 `canvasView.loadDocument()` 뒤에
  `promptLocalFontsIfNeeded()`/`loadStoredLocalFonts()`를 실행한다. `local-fonts-changed`는
  toolbar만 갱신하므로 첫 Canvas2D paint와 후속 paint의 local face 적용이 보장되지 않는다.
- 호스트 Chrome 150은 Local Font Access `granted`이고 현재 KoPub 6개 face를 모두 반환한다.
- 현재 native/WASM layout은 #4046 이후 공통 `EmbeddedTextMeasurer`를 사용한다. 브라우저
  `measureTextWidth`와 local-font snapshot이 Rust 페이지네이션을 바꾸는 구조가 아니다. 따라서
  snapshot 반영 뒤 무조건 WASM 문서를 다시 여는 것은 근거 없는 비용과 중복 초기화다.
- Rust `kopub_char_width()`는 과거 KoPub 미설치 PDF 관측을 근거로 KoPub돋움 한글을 `1.0em`으로
  고정한다. 제공 원본 TTF의 11,172개 현대 한글 advance는 Dotum 3종 모두 `0.872em`, Batang 3종
  모두 `0.936em`이다. Batang의 현행 `0.94em`은 근사하지만 Dotum `1.0em`은 설치 KoPub과 다른
  **미설치 Haansoft 대체 프로필**이다.

## 3. 범위와 비범위

### 포함

1. KoPub바탕/KoPubBatang weight suffix를 비례폭 serif로 분류하고 KoPub돋움/KoPubDotum은
   sans-serif로 유지한다.
2. 저장된 local-font snapshot을 첫 Canvas2D paint의 family 해소보다 먼저 로드한다.
3. family 하나로 Light/Medium/Bold를 뭉개지 않도록 Local Font Access의 full name 또는
   동등한 정확 face 선택 계약을 사용한다.
4. 새로 감지한 local face를 한 번의 repaint에 반영하고 중복 `loadDocument()`를 막는다.
5. 설치 KoPub과 미설치 Haansoft의 layout metric을 A/B로 계측하고, 전역 Dotum `1.0em` 유지 여부를
   별도 판정 게이트로 올린다.
6. PDF 비교 보고에 provenance tuple을 기록한다.

### 제외

- KoPub 바이너리의 저장소 추가, 변환 또는 재배포
- #3931의 표 분할·페이지 소유권 변경
- 한글 2010 미설치 결과를 한글 2020 또는 모든 OS의 보편 fallback으로 선언
- #4741의 불완전 `queryLocalFonts()` 보완을 근거 없이 중복 구현. 같은 접합면을 공유하므로
  #4739 구현 뒤 남는 재현만 #4741에서 처리한다.

## 4. 단계

### Stage 1 — RED 계약과 oracle profile 고정

1. KoPub바탕체 Light/Medium/Bold가 monospace로 분류되는 현재 실패를 단위 테스트로 고정한다.
2. 저장 snapshot 로드가 첫 Canvas2D view load보다 뒤인 현재 순서를 RED로 고정한다.
3. local-font 갱신이 toolbar만 바꾸고 repaint를 보장하지 않는 현재 실패를 고정한다.
4. `KoPubBatang Light`처럼 family에 여러 style이 있는 경우 정확 face를 선택하지 못하는 경계를
   Local Font Access mock으로 고정한다.
5. 위 PDF·TTF 대조값과 provenance를 Stage 1 보고서에 남긴다.

### Stage 2 — Canvas2D 첫 paint와 face 선택 정정

1. 앱 시작 시 저장 snapshot을 읽되 새 권한 요청은 하지 않는다.
2. 문서 첫 view load 전에 snapshot cache가 준비됐음을 보장한다.
3. 고정폭 분류를 정확한 legacy fixed-pitch 이름으로 좁히고 KoPub바탕 변형은 serif로 우선
   분류한다.
4. alias 해소 결과가 style별 face이면 canonical family만이 아니라 정확한 full face를 CSS chain의
   첫 항목으로 둔다.
5. Rust가 전달한 family chain을 JS가 불필요하게 폐기하는 범위를 줄이되, 기존 웹폰트 fallback과
   CanvasKit 경로는 보존한다.

### Stage 3 — 감지 직후 단일 repaint

1. `local-fonts-changed`에서 toolbar와 Canvas2D view를 같은 snapshot 세대로 갱신한다.
2. Rust layout이 local snapshot과 독립인 현재 구조에서는 WASM 재파싱·재페이지네이션을 하지 않고
   visible view repaint만 수행한다.
3. 같은 감지 세대의 중복 이벤트가 전체 reload나 반복 repaint를 만들지 않게 회귀 테스트를 둔다.

### Stage 4 — layout metric 판정 게이트

Stage 2·3의 paint 수정과 섞어 Dotum 전역 상수를 즉시 바꾸지 않는다. 다음 A/B를 먼저 만든다.

1. 현행 portable/missing-font 프로필: Dotum `1.0em`, 과거 Haansoft 치환 PDF 근거.
2. exact-KoPub 프로필: 제공 원본의 Dotum `0.872em`, Batang `0.936em`.
3. 편람 HWP/HWPX의 쪽수, 11쪽 glyph 위치, 첫 divergence, #3931 대표 fragment 소유권을 두
   프로필로 비교한다.
4. 기존 KoPub 관련 회귀가 어느 PDF provenance를 정답으로 삼았는지 전수 분류한다.

이 결과를 메인테이너에게 보고한 뒤 다음 중 하나를 별도 승인받는다.

- exact local font가 준비된 실행에서만 exact-KoPub metric profile을 선택하는 명시적 계약
- 결정적 portable layout을 유지하고 paint fidelity만 #4739에서 완료하며 metric profile은 별도 이슈

암묵적으로 전역 `1.0em`을 `0.872em`으로 바꾸는 선택은 하지 않는다.

### Stage 5 — 검증과 시각 판정

- TypeScript focused tests와 `npm test`
- `npm run build`
- Chrome 150 CDP host E2E: 저장 snapshot이 있는 첫 열기와 새로고침, KoPub 6종 exact face,
  물리 11쪽의 effective family와 대표 glyph/폭
- CanvasKit local Typeface와 SVG fallback focused 회귀
- layout metric 변경이 승인된 경우에만 Rust focused/전체 회귀, Native Skia, 공식 Docker WASM,
  HWP/HWPX 및 PDF profile별 시각 비교를 추가한다.
- 최종 시각 합격 판정은 메인테이너가 내린다.

## 5. 완료 기준

- KoPub바탕체가 monospace chain으로 가지 않는다.
- 저장 snapshot이 첫 Canvas2D paint 전에 사용된다.
- Light/Medium/Bold가 정확 face로 구분된다.
- 새 감지 결과가 중복 전체 문서 reload 없이 한 번 반영된다.
- 설치 KoPub PDF와 미설치 Haansoft PDF를 같은 정답지로 섞지 않으며, 결과마다 provenance가 남는다.
- layout metric 선택은 Stage 4 증거와 메인테이너의 별도 승인으로 확정된다.
