## 1. 목표와 문제의 출처

외부 기여자가 공개 기여 안내만으로 변경 범위에 필요한 검증을 고르고, source 제출 checkout과 별도
review worktree를 구분해 검사한 원본 commit을 제출할 수 있도록 한다. 기존 검증 계약을 실행 가능한
순서로 설명하는 문서 작업이며 CI 정책이나 테스트 생성기는 바꾸지 않는다.

문제 제기의 직접 출처는 첫 외부 기여자 baba9811의 [PR #6786](https://github.com/edwardkim/rhwp/pull/6786)
본문 「외부 기여자 검증 절차 확인」이다. 2026-09-06 조회 결과:

- head: `d0179dd0410757aea8d116ba4be7b38438e406e9`
- base: `51ad998e33ef7f5191b0e1b0b656dc44cef33a1c`
- 변경: Studio 파일 5개. Rust source·Cargo.toml 변경 없음.
- source checkout의 전체 fmt는 generated suite 28개 누락으로 실패했다고 보고했으며 PASS로 집계하지 않았다.
- 해당 head의 `Frontend package gates`, `Build & Test`는 success, Rust `Lint (fmt, clippy, WASM check)`는 skipped.
- 현재 `.github/workflows/ci.yml`의 frontend package gate는 fresh WASM build를 선행한다. Rust lint skip은
  WASM을 전혀 빌드하지 않는다는 뜻이 아니다.

원 PR의 기능 검토는 별도 작업이다. 이 작업에서는 #6786의 head·본문·review·comment·merge를 변경하지 않는다.

## 3. 채택한 절차와 승인 경계

읽은 부트스트랩은 `AGENTS.md`, `CLAUDE.md`, [Codex MEMORY](../manual/codex/MEMORY.md),
[문서 지도](../README.md), [manual 지도](../manual/README.md)다. 구체 절차는
[문서·Git 워크플로우](../manual/codex/docs_and_git_workflow.md)와
[하이퍼 워터폴 문서 가이드](../manual/hyper_waterfall_docs_guide.md)를 적용한다.

PR 준비 역할은 현재 계정의 저장소 `push=true`, `admin=false`, `maintain=false`를 확인해 collaborator로
판정했다. [PR 라우터](../manual/pr_review_workflow.md)와 [선택표](../manual/pr_review/README.md)를 읽고,
후속 기본 경로는 [collaborator self-merge](../manual/pr_review/collaborator_self_merge.md), 현재 보조 경로는
[로컬 검증](../manual/pr_review/local_validation.md)으로 정했다. 아직 PR 번호·정식 review는 없다.

1. 중복 조사 → 이슈 실제 등록·본인 assignee 지정: 완료. 사용자 지시로 승인된 범위다.
2. 최신 upstream/devel에서 별도 세션 worktree의 작업 브랜치 생성: 완료.
3. 수행계획 작성·링크 확인·로컬 commit → 작업지시자 승인.
4. 승인된 수행계획으로 파일별 구현계획 작성·commit → 구현 착수 승인.
5. 아래 3단계의 문서 수정·focused 검증·단계 보고서·commit → 각 단계 결과 승인.
6. 최종 보고서와 검증 증적, PR 본문 초안·생성 명령 준비 → 결과 승인.
7. remote push와 PR 생성은 별도 승인 뒤 수행. PR 번호가 생긴 뒤 정식 review 기록과 필요한 오늘할일을
   같은 브랜치에 추가한다. 최신 CI와 merge·이슈 close는 각각 후속 승인 경계다.

`collaborator_self_merge.md` 8.2.1에 따라 조사·계획·구현 중에는 오늘할일을 만들거나 갱신하지 않는다.
PR 번호를 예측한 파일도 만들지 않는다. 수행계획 승인 전에 공개 문서를 편집하지 않으며, 기존 구현을
사후 계획으로 기록하지 않는다. 현재 기준선 실험은 수행계획을 위한 원인·실행 가능성 조사다.

## 4. 최소 변경 범위와 문구 충돌

| 대상 | 확인한 공백 | 개선 방향 |
| --- | --- | --- |
| CONTRIBUTING 상단·PR 체크리스트 | Rust lint를 모든 PR에 요구하는 문구와 source checkout 생성 금지가 함께 있음 | 변경 범위 표를 단일 진입점으로 두고 해당 검증 실패 시 차단한다고 명시 |
| CONTRIBUTING 처음 참여·Fork 흐름 | clean clone에서 곧바로 전체 cargo test, 원본 commit·검증·push 순서 생략 | 같은 공개 준비 절차로 연결해 우회 진입에서도 suite 준비를 놓치지 않게 함 |
| CONTRIBUTING frontend 검증 | Rust 검증과 별도라고만 설명해 Studio 단독도 Rust 전체 검증이 필요한 것처럼 읽힘 | Studio 단독과 혼합 변경을 구분하고 fresh WASM → 타입·단위·build·관련 E2E 순서 명시 |
| CONTRIBUTING 회귀·포맷 정책 | 별도 worktree 허용이 뒤쪽에만 있음. 전체 fmt 적용 요구와 포맷 전용 브랜치 규칙 충돌 | 기여자 본인의 review worktree 생성·검증을 공개 명령으로 연결하고 원본 보정·재검증 순서 명시 |
| PR 템플릿 | 무조건 fmt·cargo test·native Clippy 체크, 준비 금지 설명 | 범위 선택·실행 결과·해당 없음 사유를 구분하고 공개 절차와 같은 Rust lint·회귀 명칭 사용 |

장기 안내의 기본 수정 대상은 [CONTRIBUTING.md](../../CONTRIBUTING.md)와
[PR 템플릿](../../.github/pull_request_template.md) 두 파일이다. 계획·단계·최종 보고서는 별도 증적이다.
내부 문서와 CI는 기존 계약 확인 근거로 사용하며, 외부 기여자가 이를 해석해야만 검증할 수 있도록
떠넘기지 않는다. 실제 충돌이 추가 파일 수정을 요구하면 파일·근거·필요성을 보고한 뒤 범위를 조정한다.

## 5. 예상 구현 단계

### Stage 1 — 공개 검증 범위 정렬

- Rust source·test/baseline helper·Cargo/toolchain 등 Rust 검증 입력, Studio 단독, 혼합, 문서 변경을 구분한다.
- Rust 변경의 lint·focused 회귀·전체 integration 및 renderer/WASM 추가 검증 계약을 유지한다.
- Studio 단독의 TypeScript·단위·build·관련 E2E/실제 브라우저 확인과 fresh WASM 준비를 설명한다.
- 상단 차단 안내·frontend 절·체크리스트가 같은 범위 표를 따르는지 확인한다.

### Stage 2 — 검증 worktree와 제출 순서 정렬

- source 변경을 commit한 뒤 정확한 commit에서 별도 review worktree를 만든다.
- 그곳에서 `--prepare` → 전체 fmt check → native/WASM/workspace Clippy와 필요한 build·회귀 → manifest
  `--check`를 순차 실행하도록 공개한다. 실행 전 도구 준비와 명령 실행 디렉터리를 적는다.
- fmt 실패 시 원본 보정 commit을 제출 branch에 반영하고 그 commit을 다시 검증한다. 검증 worktree의
  수정만 통과시키고 기존 source commit을 push하는 오류를 방지한다.
- generated 파일은 검증 공간에서 생성 가능하지만 PR에 포함하지 않는다. 기본 prepare와 maintainer 전용
  `--sync-cargo-targets`·rebalance를 구분한다.
- 포맷 정책·회귀 안내·처음 참여 흐름과 PR 템플릿을 같은 절차로 연결한다.
- suite 누락 실패, 실제 포맷 위반, 범위상 미실행을 구분한다. 실패를 PASS로 기록하지 않는다.

### Stage 3 — 공개 명령 검증과 PR 준비

- 최종 문서 commit으로 만든 새 clean review worktree에서 공개된 준비·fmt·manifest 순서를 그대로 실행한다.
- 전후 tracked Rust 원본·Cargo.toml·Cargo.lock hash와 git status로 원본 불변·생성물 미제출을 증명한다.
- 링크 검사와 내부 anchor·명령 순서·적용 범위의 수동 정합 검토, `git diff --check`를 완료한다.
- 단계 보고서, 최종 보고서, 실제 검증 SHA와 결과를 담은 PR 본문 초안·push/생성 명령을 준비한다.

각 단계의 변경과 `mydocs/working/task_m100_6791_stageN.md`를 함께 commit하고 다음 단계 문서를 시작한다.
최종 보고서는 `mydocs/report/task_m100_6791_report.md`에 작성한다.

## 6. 수행계획 전 기준선 실험

사용자·다른 작업의 worktree를 재사용하지 않고 `/private/tmp/rhwp-6791-validation-baseline`을
기준 SHA의 detached worktree로 새로 만들었다. 시작 시 tracked/untracked 변경이 없고 파생 suite도 없었다.
환경: macOS, Node `v24.15.0`, Cargo/Rust toolchain `1.93.1`.

| 순서 | 명령·확인 | 실제 결과 |
| --- | --- | --- |
| 1 | `cargo fmt --all -- --check` | exit 1. generated suite 001~028 누락으로 검사 실패. PASS로 집계하지 않음 |
| 2 | `node scripts/rust-test-suite-manifest.mjs --prepare` | exit 0 |
| 3 | `cargo fmt --all -- --check` | exit 0. 포맷 수정 명령 없이 동일 검사 통과 |
| 4 | `node scripts/rust-test-suite-manifest.mjs --check` | exit 0. 1169 sources, 28 suites + 20 exceptions, 48/48 integration targets |
| 5 | tracked `.rs` 전체와 루트 Cargo.toml·Cargo.lock의 SHA-256 비교 | 2,206개 파일 모두 불변 |
| 6 | 검증 worktree `git status --porcelain` | 출력 없음. 파생 파일은 ignored 상태 |

`summary.json`이다. 임시 파일 경로는 세션 조사 증적이며 공개 제출 절차의 환경 전제가 아니다.
이 실험은 최종 문서의 copy/paste 검증을 대신하지 않는다. 최종 명령을 작성한 뒤 Stage 3에서 확인한다.

## 7. 검증 범위와 완료 기준

- 이 문서 변경 때문에 전체 Rust build·Clippy·nextest·frontend build를 실행하지 않는다. 실제 실행은
  공개 준비·포맷·manifest 순서와 문서 검사에 한정한다. 문서에 안내할 나머지 명령은 기존 권위 문서·CI와
  대조하며 실행하지 않은 명령을 통과했다고 기록하지 않는다.
- `python3 scripts/check_markdown_links.py`에 변경 Markdown 경로를 명시해 검사한다. 이 검사기는 내부
  anchor·외부 URL을 검사하지 않으므로 새 anchor는 제목과 직접 대조한다.
- 외부 기여자는 내부 review 문서 없이 Rust/Studio/혼합의 해당 검증과 원본 commit → 검증 → push 관계를
  판단할 수 있어야 한다.
- 생성기·CI·Cargo·Rust/Studio 코드 diff가 없어야 하며 generated suite·manifest를 stage하지 않는다.
- #6786 및 이전 계약의 출처는 이 이슈·계획·결과 기록에 남긴다. #6786 자체의 기능 리뷰로 확장하지 않는다.

구현계획을 작성하고 구현 착수 승인을 요청한다. remote push·PR 생성·merge·이슈 close는 수행하지 않았다.
