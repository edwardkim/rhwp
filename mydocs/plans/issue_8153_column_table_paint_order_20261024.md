# #8153: 본문 흐름과 문단 앵커 표의 paint 순서

## 원인과 독립 기준

편람 284쪽의 이미지 원본 `image351.jpg`와 독립 Print의 해당 영상은 디코딩 픽셀이 같다.
최종 LayerTree의 그림 원점·확장 영역도 Print와 대응한다. 처음 확인한 의미 tree의
반올림된 bbox만 보고 새로운 좌표 오프셋이 필요하다고 판단하지 않는다.

원본 HWPX section10의 문단 12·13·14를 직접 확인했다.

| 문단 | 원본 table ID | `treatAsChar` | 배치 | 원본 z-order |
| ---: | --- | ---: | --- | ---: |
| 12 | 1998419061 | 0 | 문단 기준 TOP_AND_BOTTOM | 389 |
| 13 | 1998419064 | 1 | 글줄 흐름 참여 | 390 |
| 14 | 1998419068 | 0 | 문단 기준 TOP_AND_BOTTOM | 391 |

원본 독립 Print 284쪽은 가운데 인라인 표 배경을 먼저(sequence 8), 위 앵커 표를
그 다음(180), 아래 앵커 표를 마지막(485)에 그린다. Native의 Column 자식은 현재
문단 순서로만 소비된다. 따라서 먼저 그린 위 표의 배경 마지막 줄이 가운데 표의
흰 셀 채움에 가려진다. 사각형 반올림·이미지 원본·레이아웃 좌표를 먼저 바꾸지 않는다.

HWP 5.0 revision 1.3의 표 69는 독립된 INT32 z-order를, 표 70 bit 0은 글자처럼
취급 여부를 정의한다. 공식 표가 Print의 모든 paint 단계를 명시한다고 주장하지 않는다.
실제 순서는 아래 독립 출력으로 구분했다.

## 원본 속성만 바꾼 독립 대조군

원본 문단 12·13·14와 구역·단 설정, 스타일·리소스를 보존한 진단 입력에서 표의
z-order만 원래 값·역순·동률로 바꿨다. 실제 한컴 2024 13.0.0.3901 PrintMethod 0은
세 입력 모두 2쪽이다. 원본 383쪽의 쪽수 검증과 구분한다. 세 출력의 페이지별 영상
위치·크기와 위치로 정렬한 본문은 모두 같다.

| 대조군 | 첫 쪽의 배경 paint 순서 |
| --- | --- |
| 원래 z 389·390·391 | 인라인 문단 13 → 앵커 문단 12 → 앵커 문단 14 |
| 역순 z 391·390·389 | 인라인 문단 13 → 앵커 문단 14 → 앵커 문단 12 |
| 동률 z 0·0·0 | 인라인 문단 13 → 앵커 문단 12 → 앵커 문단 14 |

즉 표·문단을 무조건 역순으로 그리는 규칙이 아니다. 흐름 내용과 앵커 개체를 나누고,
앵커끼리는 원본 z-order와 문서 순서를 따른다. 자료와 원본/입력/PDF/생성 코드 SHA,
실제 engine·Print 영수증은 ignored 작업 루트의 `inline-table-order-controls/`에 있다.
`paint-order-result.json`에 geometry·본문 보존과 실제 paint sequence를 함께 기록했다.
이 파생 입력을 원본의 pagination 완료 증거나 정식 회귀 fixture로 등록하지 않았다.

## 공통 소비 경로와 반례

먼저 고정 Native `dd8ea4e054`의 원본 실제 LayerTree에서 원본 속성으로만 Column의
paint 순서를 대응하는 진단을 실행한다. 정상 재생이 같은 CLI PNG와 RGB 전체에서 같은지
먼저 확인하고, 그 뒤 순서만 바꾼 결과를 독립 Print와 비교한다. 문서 ID·위치·픽셀로
선택하지 않고 원본 `treat_as_char`·wrap·z-order와 소유 Column을 사용한다.

제품 수정은 다음 연결을 공통 결과로 만든다.

1. whole/partial 표 생성 시 원본 비인라인 layer와 문단·control 소유 정보를 보존한다.
2. 같은 Column의 흐름 내용과 앵커 개체를 공통 paint 순서로 소비한다. 소유 clip이나 다른
   Column으로 이동하지 않고 실제 bbox·줄·높이·예약 공간·원본 내용 순서는 보존한다.
3. LayerBuilder와 SVG가 같은 Column 순서를 소비해 Native·Canvas2D·CanvasKit·벡터
   경로가 다른 정렬을 추측하지 않게 한다. 원본 tree/IR의 문서 순서와 paint 순서는 구분한다.

원본 284·296·300·149쪽과 정상 288·307쪽을 먼저 비교한다. 인라인 표는 흐름 자리를
유지하고, 앵커의 z-order 역순·동률, 셀의 흰 잔재/BehindText 계약과 부분 표 소유를
검증한다. 사양·Print와 다른 기존 검사는 원 해결 근거부터 추적하며 통과를 위해 약화하지 않는다.
시각 선행 조건 후 `tests/cases/`에서 실제 최종 소비의 순서와 내용·소유 보존을 보호한다.
전쪽 Native/fresh WASM·PR8148 corpus·새 base 기능·회귀/lint/Skia/Studio는 최종 source에서
완료하며, 이번 진단을 최종 1532개 raw100·페이지별 중요 경계 ±2px의 완료로 대신하지 않는다.

## 실제 소비자 진단에서 분리한 두 원인

고정 `dd8ea4e054` 라이브러리의 실제 Native 재생을 원본 두 형식 각 6쪽에서 실행했다.
정상 재생은 현재 CLI PNG와 RGB 전체가 같았다. 앵커 순서만 바꿨을 때 284쪽의 RGB는
일부 달라졌지만 큰 회색 경계 잔여는 남았다. 따라서 순서 오류만 고쳤다고 완료하지 않는다.

위 표 마지막 흰 셀 채움은 조판 y=407.693333…부터 444.333333…까지다. 독립 Print는
약 407.640부터 444.277px까지다. 현재 bitmap 채움은 이미 600dpi 장치와 물리 종이를
대응하지만, 본문의 단색 사각형은 논리 좌표 그대로였다. 두 끝점을 같은 600dpi 장치에
양자화한 뒤 물리 종이에 대응하면 407.636749…부터 444.272862…가 된다. 이 작은 차이가
기존 정수 채움에서 마지막 행을 포함할지 바꾼다. RGB 임계값이나 2px 대응 반경은 바꾸지 않는다.

캐시를 끈 새 renderer로 정상·순서만·단색 프레임만·둘 다의 네 경우를 실제 재생했다.
원본 284·296쪽은 두 수정이 함께 있을 때만 양쪽 형식 모두 미대응 0픽셀이다.

| 원본 쪽 | 정상 미대응 | 순서만 | 프레임만 | 순서+프레임 |
| ---: | ---: | ---: | ---: | ---: |
| 284 | 504 | 504 | 504 | 0 |
| 296 | 482 | 482 | 482 | 0 |
| 300 | 688 | 688 | 688 | 688 |
| 288·307 | 0 | 0 | 0 | 0 |
| 161 | 1 | 1 | 1 | 1 |

이는 소비자 진단이며 아직 새 제품 source의 Native/fresh WASM 통과가 아니다. 자료는
ignored 작업 루트의 `table-fill-physical-order-dd8ea4e054/`와
`table-fill-physical-probe-fresh-process-audit.json`에 있다. 300쪽의 별도 잔여를 숨기지 않는다.

구현은 Column 순서의 공통 iterator를 LayerBuilder와 SVG가 소비하도록 하고 원본 tree는
재배열하지 않는다. whole/partial 표 생성에서 같은 원본 layer를 전달한다. 기존 셀의
앵커/BehindText 후처리는 유지한다. 단색 채움의 프레임 변환은 NORMAL 채움 중첩 뒤,
최종 paint op를 만들 때 한 번 적용한다. 바탕쪽의 이미 변환한 가로 축과 그림 테두리의
공유 frame은 다시 변환하지 않는다. 회전/아핀 하위나 stroke·gradient·pattern·shadow·alpha의
별도 paint 계약은 이 단색 채움 실험으로 확장하지 않는다. 이러한 적용·비적용 범위와
72/96/144/192dpi·정상 대조군은 실제 새 source에서 검증한다.

## 2026-10-25: 원본 용지에서 공통 EMF 참조 프레임 생산

### 독립 근거와 반례

원본 HU를 바로 PDF point로 내린 현재 viewport는 참조 DC의 물리 크기와 EMF frame을
생략한다. `source-paper-print-reference-units-audit.json`의 별도 한컴 Print 4개는
원본 용지 → DEVMODE 0.1mm → 참조 장치 픽셀·정수 mm → EMF 0.01mm → PDF 정수 point
계산으로 용지 크기가 모두 일치했다. HU 높이 75420의 독립 PDF는 753pt이므로
단순 `floor(HU / 100)`의 754pt가 반례다. 장치 정수 원점 12개의 최대 오차는
PDF의 0.001pt 표기 정밀도 이내인 0.000419pt다.

`so-analysis-20261025-paper-units/{,width/}printer-extent-result.json`의 공개 GDI 호출은
0.5mm 경계 12조건을 확인했다. 정수 mm는 DEVMODE에서 반올림해야 하며, 이미 반올림한
장치 픽셀에서 mm를 역산하면 266.5mm·196.5mm 경계에서 다르다. DEVMODE는 메모리에서만
검증했고 프린터 설정을 바꾸지 않았다. 600dpi는 확인한 Print 장치 계약이며 raster 출력 DPI와
구분한다. 이는 HWP 사양 오류가 아니라 사양 밖 인쇄 장치의 단위 변환 누락이다.

### 소비 경로와 보정 범위

`print_paper`에서 용지별 출력 크기·장치 한 픽셀의 CSS 길이를 한 번 생산하고

`hangul2024_print` 계약에서만 선택한다. Screen·2022 경로와 논리 조판 소속·높이는 보존한다.
도형 끝점·그림 원점의 반올림 규칙은 별도 반례가 있으므로 이 변경으로 바꾸지 않는다.
문서 ID·쪽 번호·관측 배율을 조건이나 상수로 넣지 않는다.

먼저 단위 산술·유효성 및 독립 용지 4개를 확인하고, 편람의 그림·채움 영향 페이지를
고정 4319 Native 및 5cf7 optimized WASM과 대조한다. 방향 확인 뒤 새 source의 전쪽
Native/fresh WASM과 필수 게이트를 완료한다. 현재 이 절은 구현 전 계획이며 통과 기록이 아니다.

단색 채움 변환은 논리 종이를 바로 최근접 장치 크기로 나눈다. 그러나 EMF의 물리
프레임은 정수 0.01mm이고 참조 장치의 pixel/mm와 별개다. 공개 `GetDeviceCaps`로 확인한
참조 DC는 가로 4,630pixel/196mm, 세로 6,283pixel/266mm다. 원본 종이의 출력용 장치
영역 4,630×6,284pixel을 이 DC에서 정수 물리 프레임으로 변환하면 19,600×26,604가 된다.

기존 `754 / 6284`pt와 같지 않다. 측정한 PDF 끝점을 이 수식의 입력으로 사용하지 않았다.

독립 편람 PDF의 첫 종이 clip을 두 형식 모두 검사했다. 해당 clip이 실제로 있는
