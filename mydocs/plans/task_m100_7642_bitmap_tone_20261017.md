# #7642 한컴 2024 Print의 원본색 bitmap 전달 경로 보정

Issue: #7642

## 근거와 적용 범위

독립 Print와 입력 변형 진단은
[stage2025](../working/task_m100_7642_stage2025.md)에 보존했다.
추가 stage2028/2029에서 16비트 BMP·32비트 BMP·16비트 PNG·알파·그림 효과를 한 번에
출력했다. 원본색 bitmap은 픽셀 성분 확장과 같은 방향이며, 그레이스케일·흑백은
같은 처리를 하지 않는다. 밝기·대비를 지정한 경로에서는 효과 뒤 색 변환 순서와
기존 대비식 차이가 남는다. 이를 원본색 경로의 통과로 완료 처리하지 않는다.

우선 시험지의 현재 공통 미달에 해당하는 **밝기·대비 보정 없는 원본색 그림**을 고친다.
문서명·쪽·좌표·그림 크기로 분기하지 않는다. 한컴 2024 Print, BMP/PNG,
원본 RGB 색이 8비트 팔레트 용량인 256개를 초과하는 경우를 사용한다.
2020·화면 프로필·JPEG·팔레트 범위·그레이스케일·흑백·지정한 밝기/대비는 반례로 보존한다.
미검증 경로를 해결했다고 주장하지 않으며, 전체 범위의 미달과 기존 회귀 실패는 계속 보정한다.

## 생산과 소비의 연결

1. `DocumentCore::build_canvas_page_layer_tree_with_profile`의 실제 `hangul2024_compat`와 Print
   프로필을 LayerBuilder에 전달한다. 장치 픽셀 값의 존재로 제품 세대를 추정하지 않는다.
2. LayerBuilder가 ImageNode의 출력 전용 표지를 설정한다. 원본 IR, 그림 크기·crop·좌표·
   줄 구성은 바꾸지 않는다. 표·각주·그룹의 그림도 같은 Image leaf 하위화 경로를 소비한다.
3. image_resolver의 한 변환에서 제한된 디코드·색 수 확인·RGB 성분 확장·PNG를 만든다.
   같은 변환을 Native Skia, Canvas/SVG의 resolved payload가 사용한다.
4. `SourceImageVariant`에 별도 출력 신원을 두고, inline JSON·바이트 생략 후 재조회가
   같은 변환을 사용하도록 연결한다. 2020/2024 및 화면/Print의 캐시를 섞지 않는다.
5. 직접 구성한 `PaintOp::Image { resolved: None }`의 fallback도 같은 결과를 사용한다.
   이미 변환된 payload를 재생할 때 표지를 지워 성분 확장을 중복 적용하지 않는다.

## 검증 순서와 완료 조건

새 Native/fresh WASM으로 같은 원본의 전쪽 TSV를 산출한다. 11월 공통 실패 문서와
10월 입력, 원본·정상 저장 sample16 및 독립 색 수/형식 대조군을 묶어 확인한다.
현재 제품 원본과 입력 변형 진단을 구분하고, review와 standalone overlay를 함께 직접 연다.
새 회귀는 해당 원본·관련 모든 페이지의 양쪽 90%와 확대 판독 이후에만 추가한다.
기존 golden과 허용치는 바꾸지 않는다. source SHA·새 빌드·로그·입력·Print 해시를 기록한다.
최신 devel 대비 하락, 원래 12개 회귀 실패와 전체 Rust/lint는 별도 필수 gate로 남는다.

## 후속 조사: 메타파일 색과 축소 필터의 분리

stage2040의 원본 11월 HWP/HWPX는 각각 전 21쪽 Native 최소 96.09167%,
fresh WASM 최소 96.23178%다. 10월 원본은 1·6쪽 미달이 그대로다.
원본 BinData와 실제 SVG image를 추적한 결과 10월 그래프는 WMF가 아니라
1126×1094·983×868 PNG이며 약 1/6 크기로 배치된다. Native는 mipmap 없는
선형 표본, CanvasKit은 기본 drawImageRect를 소비한다. 독립 PDF는 같은 크기의
bitmap 자원을 보존하며 얇은 축이 보인다. 같은 원본 그림을 면적으로 축소한
입력 변형 진단(stage2051)은 1쪽 raw가 88.52370%에서 90.27979%로 변했다.
이 값은 제품 통과 증거가 아니며 좌표·기준 PDF·마스크를 바꾸지 않는다.

따라서 원본 전체를 그리는 bitmap의 축소에서는 Native와 CanvasKit 모두
실제 장치 변환에 맞는 mipmap 저역 통과를 사용한다. 1:1·확대는 기존 경로,
잘린 source rect는 기존 strict crop 경로를 유지한다. 새 그림 크기나 문서별
예외를 넣지 않는다. 원본 크기의 데이터·배치·색 효과·출력 DPI는 유지한다.
Native의 실제 canvas matrix와 CanvasKit의 getTotalMatrix가 축소 여부의 근거다.
새 mipmapped Image는 그리기 호출이 끝나면 해제하고 기존 cache 신원을 바꾸지 않는다.
새 회귀는 원본 전쪽 Native/fresh WASM 90%와 직접 판독 후에만 추가한다.

한편 stage2044~2049의 독립 WMF 대조군은 256색 vector/DIB와 257색 vector/DIB를
구분한다. 2024 Print에서 눈에 보이는 257번째 색을 가진 vector도 RGB 성분이
확장되므로 원본 BMP만의 동작이 아니다. 하지만 전체 WMF에 무조건 적용하면
256색 대조군과 모순된다. 전체 그림의 합성 후 색 전달 조건과 2020 반례를
더 확인하기 전에는 WMF에 임의 전역 밝기 보정을 넣지 않는다.

Visual Sweep의 fresh WASM producer는 Studio CanvasKit이 아니라 Rust Web Canvas2D를
직접 호출한다. 이 소비 경로도 함께 수정한다. 실제 context 변환과 원본 픽셀 크기로
축소를 판단해 imageSmoothingQuality를 High로 선택하고, 반환·조기 반환 시 원래 값을
복원한다. source rect를 자르는 함수에는 적용하지 않는다. CanvasKit만의 통과를
fresh WASM 통과로 대신하지 않는다.

## 8쪽 문단 원점의 덮어쓰기 보정

새 Native의 1쪽은 90.69311%지만 6쪽 89.06661%, 8쪽 89.97725%로 미달이다.
8쪽은 단순 선 품질이 아니라 그림 원점이 한컴보다 약 141px 내려가는 배치 차이가 있다.
원본 pi384/ci1의 vertical_offset은 0이다. 저장 줄의 첫 원점은 4236HU,
그림 소유 줄은 10629HU이며 공통 stored_picture_anchor_delta는 85.24px를 반환한다.
실행 trace는 layout_shape_item이 para_start_y를 288.5px로 덮은 뒤 delta를 더해
373.7px에 그렸음을 보인다. 첫 본문 줄은 147.2px이며 PDF 그림의 상단은 약232.23px다.

선행 TAC 개체가 있다는 이유로 떠 있는 후속 그림까지 현재 흐름의 끝을 문단 원점에
저장하는 가정을 제거한다. 현재 개체도 TAC일 때만 기존 여러 TAC 줄의 진행을 사용한다.
문서·쪽·좌표·offset으로 분기하지 않는다. 측정은 transition의 ObjectPlacementFrame →
picture_exclusion → stored_picture_anchor_delta, 실제 배치는 shape_item의 문단 원점 →
같은 delta → 수용한 ParagraphFloatPlacement 우선 적용 → layout_body_picture 순서다.
뒤의 수용 frame을 제거하지 않는다. 선행 inline box + 후속 floating 그림,
여러 줄 TAC, 수용 frame, 저장 정보가 무효인 편집 재조판을 반례로 확인해야 한다.
새 source 재출력 전에는 수정 완료·새 회귀 자격을 주장하지 않는다.

## PDF raster의 균일색 보존 계약

stage2061의 같은 PDF 6쪽은 canonical Poppler 89.06661%, MuPDF 98.15071%,
PDFium 98.21221%였다. 이를 즉시 통과 근거로 바꾸지 않았다. stage2067~2071에서
독립적인 Flate RGB 상수 면 PDF를 만들어 원인을 분리했다. 1:1·확대는 세 renderer가
모두 같은 값을 유지한다. 1201×657 균일색 원본을 실제 그림과 같은 153.038×83.668pt로
축소하면 Poppler는 64→63, 128→127, 192→191, 231→230, 232→231,
233→232, 255→254로 바꾼다. MuPDF·PDFium은 모두 원래 균일색을 유지한다.
JPEG를 쓰지 않은 독립 PDF에서도 재현되므로 원본 그림의 색을 바꾸어 해결하지 않는다.
stage2070의 Poppler 자체 원본 자원 디코드도 232를 보존해 축소 단계의 차이로 좁혀졌다.

검증기의 PDF raster 경로를 고칠 때는 이 균일색 보존·분수 좌표 축소 계약과 실제 Print의
선을 독립적으로 확인한다. raw 수식·내용 이진화·90%·98%·0.01%p 기준은 바꾸지 않는다.
교체한 renderer·버전·DPI·PDF SHA를 provenance에 기록하고 동일 base/head의
Native/fresh WASM 전쪽을 같은 PDF raster로 다시 계산한다. 기존 RHWP PNG의 producer
SHA와 바이트가 확인되면 재렌더링과 분리해 재사용하되 새 source 출력이라고 쓰지 않는다.
검증기 수정과 전체 재산출 전에는 새 renderer의 진단 수치로 gate 통과를 선언하지 않는다.

## Cairo 기준 raster 구현과 CI 계약

기존 poppler-utils 안의 `pdftocairo`도 위 상수 면의 모든 RGB를 보존했다.
새 Python PDF dependency 대신 이 공통 backend를 모든 문서에 일괄 사용한다.
전체·선택 쪽수 명령, renderer 버전·실행 파일 해시·정책 신원을 기록하고,
이전 Splash/shape/none의 PDF PNG·TSV와 새 결과를 섞지 않는다.
raw 판정식·마스크·DPI·90%·98%·0.01%p는 변경하지 않는다.
분수 축소의 상수 RGB 계약을 순수 DeviceRGB/Flate PDF로 작성한 실제 실행 검사와
기존 한컴 Print의 파랑 그라데이션 검사를 실행한다. 이 테스트는 HWP 조판 회귀가
아닌 PDF 검증기의 독립 수학·파일 프로토콜 계약이다.

기존 full/selected command 검사는 새 renderer의 동일 쪽 선택 계약으로 갱신한다.
CI Lint의 기존 Visual Sweep 검사가 실제 PDF 도구로 이 계약을 실행하도록
poppler-utils를 명시 설치한다. job command만 추가하는 O3 변경이며 trigger·job 의존성·
permissions·fork 신뢰·required context는 유지한다. 실제 명령 로컬 실행,
YAML·관련 CI 정책 검사와 최종 PR head Actions를 확인해야 한다.

## 흑백 예약색을 포함한 팔레트 경계 보완

stage2091~2099의 독립 Print에서 기존의 원본 색 수만 세는 가정을 반증했다.
흑백을 포함한 256색은 보존되지만, 둘 중 하나가 빠진 256색과 둘 다 빠진 255색은
full-color 전달로 바뀐다. 둘 중 하나만 빠진 255색은 보존된다. 같은 실제 픽셀의
24비트 BMP·RGB PNG·indexed PNG·indexed BMP가 모두 같은 결과다.
따라서 공통 bitmap resolver의 색 집합을 흑백 두 예약색으로 시작한다.
원본 데이터·alpha·형식/세대/Print/effect 조건·채널 전달식·캐시 신원은 유지한다.
일반 화면·2020·JPEG와 팔레트에 수용되는 대조군은 기존 경로를 사용한다.

이는 전체 WMF의 해결이 아니다. WMF는 clip·겹침·StretchDIB 후의 합성 결과를
같은 팔레트 계약과 연결해야 한다. 가려진 source RGB를 세어 적용하거나 모든 WMF를
일괄 밝게 만들지 않는다. 실제 재생 surface·색·글꼴 보존을 입증하기 전에는 미해결이다.
