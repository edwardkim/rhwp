## 1. 목표와 범위

`src/bin`·`src/agent`·`src/cli`를 리팩토링하기 전에 무엇이 같은 기능이고 무엇이 다른 계약인지,
Gym과 어떤 관계이며 제품 배포에 어떤 역할을 갖는지 근거로 분류한다. 이번 산출물은 분석과
우선순위 제안이다. 코드 이동·삭제·병합, 새 공개 API, Cargo/CI/배포 변경은 실행하지 않는다.

세 폴더 외의 `src/main.rs`, `src/lib.rs`, `document_core`, MCP/WASM/Native,
scripts·tests·Cargo·릴리즈 설정은 실제 호출과 소유 관계를 확인하는 범위에서 읽는다.
`src/tools/font_metric_gen.rs`는 같은 패키지의 개발용 실행 타깃이므로 배포 분류에 포함한다.

## 2. 사전 조사 단서

- src/bin 실행 타깃 24개, 루트 패키지 실행 타깃 26개. 사전 목록과 현 기준에서 해당 소스 차이는 없다.
- 본 CLI catalog 102개와 rhwp-agent 등록부 80개에 같은 이름 15개. 이름 일치와 의미 중복은 별도다.
- scan·verify 승격 후 별도 구현 잔존, structure의 공통 코어/개별 어댑터, explore의 입력 구성 차이,
  search의 범위·주소·상한 차이, q-more/q-pack의 봉투 코드 복제를 확인했다.
- src/agent의 현재 DSEL 공개 모듈과 전체 커널 설명을 구분해야 한다. 저장소 소비자 미검출은
  외부 사용자 부재 또는 안전한 삭제의 증거가 아니다.
- 현재 릴리즈 설정과 v0.8.6 Linux x86_64 압축파일은 rhwp 실행 파일만 제공한다.
  이 확인을 모든 배포 채널·모든 버전의 검사로 확대하지 않는다.

이 단서는 시작점이며 전수 분석 결과가 아니다. 이전 #5511·#3918·#4875와 #6916의 보고 및
실측 자료를 먼저 재사용하고 필요한 부분만 현재 코드와 대조한다.

## 3. 분류 기준

### 중복 판정

각 명령·모듈에 목적, 옵션, JSON/출처 표지, 주소 단위, 종료 코드, 암호/오류/자원 제한,
읽기·쓰기 효과, 공통 코어, 호출자와 테스트를 기록한다. 판정은 다음과 같다.

1. 실제 처리 코드 복제 — 공통화 후보.
2. 같은 코어를 쓰는 다른 어댑터 — 외부 계약 비교가 먼저다.
3. 부분 중복 또는 의미 분기 — 차이를 보존할지 결정해야 한다.
4. 독립 기능 — 이름 유사만으로 합치지 않는다.
5. 소비자/계약 미확정 — 추가 증거가 필요하며 삭제 대상으로 확정하지 않는다.

### Gym 관련성

역할 축과 의존 축을 따로 기재한다.

| 축 | 분류 |
| --- | --- |
| 기능 역할 | 제품 / 개발·진단 / 실험 / Gym 평가 전용 / 미확정 |
| 현재 연결 | Gym→제품 소비 / 제품→Gym 의존 / 테스트·문서 참조 / 역사적 계기만 / 확인된 연결 없음 |

증거는 파일·심벌·호출 방향과 관련 이슈/PR로 연결한다. gym/agent 문자열이나 도입 계기만으로
Gym 전용이라고 판단하지 않는다. #6916의 제품 독립성과 Gym→rhwp 방향을 유지하며,
#6684 온보딩·채점기·과제·리더보드 수정은 이번 범위에 포함하지 않는다.

## 4. 수행 순서

| 단계 | 할 일 | 산출물·판정 |
| --- | --- | --- |
| Stage 1 — 전수 목록·관계 조사 | Cargo 타깃·명령·모듈·소비자를 목록화하고 Gym 역할/의존을 분류한다. 기존 증적과 도입·승격 이력을 연결한다. | `working/task_m100_7001_stage1.md`: 목록, Gym 분류, 근거 및 미확정 항목 |
| Stage 2 — 계약 대조·위험 분석 | 우선 후보의 실제 처리와 입출력 계약을 비교한다. 정적으로 확정할 수 없는 쌍만 제한적 실행 대조한다. 공통화·호환 유지·독립 보존 후보를 구분한다. | `working/task_m100_7001_stage2.md`: 명령 대응표, 보호 불변식, 배포/검증 영향 |
| Stage 3 — 방향·우선순위 보고 | 소유 계층·제품/선택적 도구 경계 대안을 비교하고 최소 리팩토링 단위와 검증 전략을 제안한다. | `report/task_m100_7001_report.md`: 메인테이너의 구현 범위 결정 요청 |

단계 전환은 현 단계 증적 커밋 후 메인테이너 승인 절차를 따른다. 분석 단계마다 자식 이슈를
만들지 않는다. 실제 리팩토링은 최종 분석 결과와 별도 수행계획 승인 후 시작한다.

## 5. 분석 검증과 증거 관리

- 정적 목록 수와 Cargo metadata·명령 등록부를 대조한다. 주석·문서와 실제 dispatch의 차이를 표시한다.
- 공통 코어 사용과 복제 구현을 구별하고, 중요한 분류는 호출자 및 테스트 양쪽에서 교차 확인한다.
- 필요 시 기존 바이너리의 출처/소스 일치를 먼저 확인하고, 공개 샘플에 대한 읽기 전용 대조만 한다.
  불일치한 바이너리 결과는 현 소스의 실행 증거로 쓰지 않는다. 추가 빌드 필요성은 사유와 범위를 보고한다.
- Gym 내부 자료 본조사 전 `gym/AGENTS.md`와 관련 운영 지침을 읽는다. 해답·비공개 코퍼스·폰트·
  credential 원문을 보고서에 복제하지 않는다. 공개 가능한 집계·코드 근거 위주로 남긴다.
- 전체 코퍼스 재계측, Gym 전건 평가, Cargo 전체 회귀, Docker WASM 빌드, 원격 CI dispatch는
  분석의 기본 게이트가 아니다. 실제 비용을 계측하지 않으면 절감률을 제시하지 않는다.
- 일반 Markdown 증적 변경은 diff 공백·링크를 확인한다. 산출물을 보존하기 위한 push/PR은
  별도 승인 후 진행하며 이슈 등록 승인으로 추정하지 않는다.

## 6. 완료 조건

1. 기준 SHA, 대상 전수 목록과 조사 방법이 재현 가능하다.
2. 중복/차이/소비자 및 Gym 분류마다 근거가 있고 미확정 항목을 숨기지 않는다.
3. 도입 계보와 공개 계약을 근거로 보존·공통화·이동 후보의 우선순위를 설명한다.
4. 빌드 대상, 설치 대상, 배포 파일, 검증 대상의 경계를 따로 제시한다.
5. 메인테이너가 실제 구현 범위를 선택할 수 있는 최종 보고서를 검토한다.

분석 이슈의 완료는 제품 리팩토링 완료를 뜻하지 않는다. 현 제품 코드와 동작은 그대로 유지한다.
