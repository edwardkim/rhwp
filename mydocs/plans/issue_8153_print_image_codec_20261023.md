## 근거와 원인 계층

### 확대 표본의 공통 소비 보정 계획

92쪽의 463×538 원본과 최종 491×576 장치 영역은 확대 관계다. 실제 Native·Canvas의
`print_image_sampling::rasterize`는 `weights`가 확대를 거부해 다른 재생 경로로 돌아간다.
즉 JSON의 `printArea` 표식만으로 공통 계산을 실제 소비했다고 판정할 수 없다.
원점만 바꾼 앞의 진단은 이 보간 경로를 유지한 결과이며 좌표 원인만을 입증하지 않는다.

공개 PDFium chromium/7999 `CStretchEngine::WeightTable::CalculateWeights`는 확대 축에서
표본 중심의 두 이웃과 16.16 가중치를 사용하며, 충분히 큰 확대에서는 같은 공개
`UseInterpolateBilinear` 조건에 따라 최근접 표본을 선택한다. 축소 축의 면적 가중치와
축별 채널 절삭은 유지한다. 한컴 비공개 구현이나 PDF에서 추정한 보정 수치를 옮기지 않는다.

독립 원본 PDF의 그림 객체만 메모리에서 분리하고 정확한 96dpi 행렬로 출력한 92쪽은
491×575픽셀이다. 공개 확대 가중치의 결과와 RGB 전체가 같다. 원본 PDF SHA를 전후
확인했고 파일을 다시 저장하지 않았다. 자료는 `handbook-pdfium-upscale-independent/`다.
이 결과는 제품 프레임의 576픽셀 높이까지 맞았다는 증거가 아니며 두 차이를 구분한다.

공통 경로는 `최종 장치 변환 → 정수 외접 영역 → 공개 확대/축소 표본 → 동일 RGBA →
Native·Canvas2D·CanvasKit 소비`다. 부분 창·alpha·아핀의 미입증 계약을 이 변경으로
넓히지 않는다. 확대 시 출력 크기·할당 한계도 확인하고, 92·95·163쪽과 기존 정상 그림을
실제 출력해 먼저 확인한다. Native/fresh WASM 집중 확인과 이후 전쪽 검증 전에는
이 구현 계획을 해결·제출 완료로 표시하지 않는다.

후보는 공통 표본 함수에서 확대 축을 거부하던 조건을 제거하고, 공개 표본 중심 가중치와
기존 축소 가중치를 함께 소비하게 했다. 원본·중간·출력 bitmap의 크기와 할당 한계를

고정 `04437c268a` 실제 LayerTree에서 새 공통 함수만 소비하는 진단도 준비했으며,

### Canvas의 실제 원본 표본 소비 순서

같은 고정 source `04437c268a`에서 Native와 WASM의 273쪽 의미 tree의 그림·그룹·본문
위치는 같다. 실제 브라우저의 `getImageData`·`drawImage` 인자만 관측한 캡처는 앞선
WASM PNG와 SHA까지 같다. Print 원본 JPEG는 877×510·777×522인데 공통 표본
함수가 읽은 canvas는 이미 499×282·523×326이다. 디코더나 글꼴 문제로 먼저 추측하지
않고 실제 소비 전에 실행된 `bitmap_raster::prepare_bitmap`을 원인으로 구분한다.

Native의 실제 호출은 `원본 decode → 공통 Print 표본 → 비대상일 때 일반 bitmap 준비`다.
Canvas는 `일반 bitmap 준비와 종이 투영 → 준비한 PNG decode → 공통 Print 표본`으로
달랐다. 같은 helper 이름을 사용해도 같은 원본·격자를 소비한 상태가 아니었다.

Canvas도 원본 decode 캐시를 공통으로 사용하고, 원본에서 Print 표본을 먼저 시도한다.
미지원 계약에서만 기존 일반 준비·재생으로 돌아간다. crop 전체 원본의 기존 위임과
부분 crop·alpha·아핀의 비적용 계약은 유지한다. backend별 보간 수학·문서 ID 분기나
새 좌표 오프셋을 추가하지 않는다. 앞선 후보의 Native 산출물은 동결한 뒤 수정한다.

새 최적화 fresh WASM에서 같은 쪽의 실제 표본 입력 크기·PNG·source와 공급 프로그램을
다시 확인하고, 90·92·95·161·163·273쪽과 정상 쪽 및 기존 bitmap 대조군을 실행한다.
이후 원본 전쪽 및 필수 게이트를 완료한다. 자료는
`handbook-palette-04437c268a/canvas-observation-p273/`에 있다. 관측 driver의 외부
exit code는 보존하지 못했으므로 이를 정식 회귀 검사 통과로 쓰지 않으며, 실제
PNG 동일성·읽기/그리기 인자·원본 payload 진단으로만 사용한다.

아래 초기 진단의 코드 기준은 `c6fbb92d3b71d5aaac55807ce5758e6926ddc29a`다. 기존 편람의 입력과
383쪽 독립 Print PDF는 그대로 재사용한다. 273쪽의 877×510 / 777×522 원본 BMP는
PDF 안에서 각각 JPEG로 전달되지만 현재 paint는 무손실 PNG를 사용한다. 페이지의 좌표와
원본 픽셀 전달, 손실 압축을 서로 다른 계약으로 검증한다.

독립적인 작은 크기 대조군의 JPEG 양자화 표는 같은 원본도 출력 크기에 따라 달라진다.
원본 369의 별도 문서별 너비 7200/14400/21600/28800/32400/34300 HU에서는 품질
35/35/46/62/69/51에 해당한다. 이미지 객체를 재사용한 여러 쪽의 같은 양자화 표를
독립 크기 실험으로 세지 않는다. 기존 Print 26개에서 대응 치수가 확인된 31개 자원을
대조했다. 원본 433의 RGB를 재압축한 자원은 독립 PDF의 계수·RGB와 일치하는 것을
별도 진단으로 확인했으며, 이를 제품 출력의 완료 증거로 쓰지 않는다.

HWP/HWPX 사양은 원본 그림·효과·잘라내기·좌표 계약의 근거다. PDF 생성기의 압축 정책은
해당 사양이 명시한 수치라고 주장하지 않는다. 측정 임계값이나 문서 ID별 분기를 추가하지 않는다.
상단 그림의 색 전달 차이와 나머지 페이지의 미대응은 계속 해결해야 할 범위다.

## 공통 소비 경로와 구현

`ImageNode 원본/효과 → 기존 공통 resolver → 실제 Print frame → 공통 출력 payload →
Native/Canvas/SVG`를 연결한다. 장치·배치에 따라 달라진 압축 바이트는 원본 bin 키로
재조회하지 않고 `OutputDevice` payload로 전달한다. 최종 frame을 별도로 추정하거나
좌표를 다시 보정하지 않는다. 문단·개체 소속과 논리 bbox는 유지한다.

불투명 raster와 투명도 합성, 전체 원본과 부분 잘라내기는 각각의 전달 계약이다. 첫 구현에서
입증한 계약을 연결한 뒤 남은 계약도 계속 구현·검증하며, 부분 성공을 전쪽 목표의 완료로
바꾸지 않는다. 일반 화면과 다른 호환 모드는 기존 계약을 유지한다.

Native/fresh WASM의 인코더는 같은 스칼라 정수 연산을 소비한다. 공개 `jpeg-encoder` 0.7.1의
출처와 원래 라이선스를 보존한 내부 패키지를 사용하며, 역수 근사로 양자화 경계가 바뀌지 않도록
반올림 정수 나눗셈을 사용한다. 공개 코드의 변경 목록과 원본 SHA를 vendor에 남긴다.
한컴 바이너리·디스어셈블리·호출 기록은 Git에 포함하지 않는다.

## 검증 순서

1. 원본 RGB에서 인코딩한 자원의 계수·RGB를 독립 Print와 비교한다. 정답 픽셀을 입력이나
   제품 payload에 복사하지 않는다.
2. 현재 원본 273쪽과 관련 그림 페이지를 실제 Native로 재출력해 기존 PNG·독립 PDF와
   비교한다. 개선·하락·불변과 정확한 미대응 수, 내용·쪽수·관측 글꼴을 구분한다.
3. 정상 대조군과 최적화 fresh WASM을 같은 조건으로 검증한다. 실제 review·overlay를 열어
   그림 내부 선·문자와 바깥 경계를 확인한다.
4. 영향을 받는 경로를 보정한 뒤 최종 전 1,532개 결과·페이지별 ±2px 검사·전체 회귀 등
   #8153의 나머지 완료 조건을 충족한다. 273쪽의 개선만으로 PR을 제출하지 않는다.

이 문서는 구현 전 계획이다. 새 코드의 실제 결과와 미해결 범위는 실행 후 연결한다.

## 첫 Native 후보 결과와 다음 공통 소비 단계

코드 `f9e31456eb7794073ab74ce0746e5497f9a3f927`의 Native 빌드는 성공했다.
선정 52쪽에서 미대응 합계는 56,081 → 50,583개로 줄었으며 내용 구조와 관측 글꼴은
유지됐다. HWPX 273쪽은 raw 98.65734 → 99.08806%, 미대응 2,437 → 1,672개다.
그러나 두 형식 모두 67쪽 −0.00133%p, 260쪽 −0.05627%p의 하락이 남았다.
대조군의 기존 호환(2022) 모드 12쪽은 RGB가 같았으나, 2024 모드에는 하락도 있어 완료로 판정하지 않는다.
2024 모드를 기존 2020 PDF와 비교한 진단과 같은 버전 출력의 승인 근거를 구분한다.

압축과 화면 축소는 별개다. 공개 PDFium chromium/7999의 `CStretchEngine` 계산을
독립적으로 구현하고, 기존 Print의 260·273쪽 그림 14개를 각각 메모리 안에서 분리해
같은 PDFium으로 렌더했다. 16.16 면적 가중치, 축별 채널 절삭, 실제 bitmap/paper 변환을
따른 Rust 계산 결과는 14개 모두 RGB 바이트 단위로 같았다. 원본 PDF는 수정하지 않았다.
이 진단은 PDF 안의 JPEG 디코딩 RGB를 사용하므로 제품 입력의 검증을 대신하지 않는다.

공통 소비는 `최종 그림 frame → 실제 장치 변환과 페이지 viewport → 정수 외접 경계 →
공통 16.16 면적 표본 → Native/Canvas2D/CanvasKit 재생`으로 연결한다. 배율·페이지 크기를
별도 예측하거나 96dpi를 고정하지 않는다. 처음 입증한 불투명 JPEG의 전체 원본 축소부터
연결하고, 부분 자르기·alpha·회전 등 다른 계약은 승인 근거를 확보해 계속 처리한다.
Native·WASM의 수학을 따로 구현하지 않는다. 좌표·쪽·소유·순서는 바꾸지 않고 출력의 장치
표본만 다룬다. 영향을 받는 본문·대조군을 재출력한 뒤 하락과 실제 확대 출력을 확인한다.

공개 계산 근거: [PDFium chromium/7999 cstretchengine.cpp](https://pdfium.googlesource.com/pdfium/+/refs/heads/chromium/7999/core/fxge/dib/cstretchengine.cpp),
[고정소수점 정의](https://pdfium.googlesource.com/pdfium/+/refs/heads/chromium/7999/core/fxge/dib/cstretchengine.h).
한컴 바이너리 분석 자료는 이 문서에 옮기지 않고 ignored `output/`에만 보존한다.

## 다음 공개 JPEG 경계 계약: 하단 색차 패딩

공개 libjpeg-turbo `jcprepct.c`의 no-context 경로는 원본의 마지막 행 그룹을 먼저
채워 표본화한 뒤, 마지막 **출력** 행을 iMCU 끝까지 반복한다. 현재 스칼라 인코더는
원본 마지막 행을 iMCU 전체에 먼저 반복한 뒤 평균을 내므로, 세로 평균 그룹의 끝과
원본 끝이 일치하지 않는 경우 서로 다른 색차를 만든다. 가로 경계는 `jcsample.c`가
원본을 먼저 확장하므로 이번 세로 계약과 구분한다. 한컴 비공개 코드를 옮기지 않는다.

공통 평균 블록 계산은 유효 원본 높이를 받아 마지막 유효 그룹의 평균을 반복하도록
수정한다. interleaved와 최적화 Huffman의 블록 수집 경로가 같은 결과를 소비하게 한다.
원본 RGB·양자화 표·DCT·가로 bias는 유지한다. 공개 libjpeg/Pillow의 독립 계수와
짝수·홀수 높이, 완전/불완전 iMCU 경계로 검증한 뒤 실제 Native/fresh WASM을 재검증한다.

근거: [공개 전처리 controller](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/main/src/jcprepct.c),
[공개 표본화 경로](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/main/src/jcsample.c).

세로 경계 후보의 실제 vendored 인코더를 별도 실행해 공개 Pillow/libjpeg의 계수와
74건 대조했다. 16/17/19 너비와 1/2/3/14/15/16/17/18/30/31/32/33 높이의 YCbCr,
877×510 RGB 원본 색 확장 입력에 대해 일반/최적화 Huffman 두 경로를 확인했다.
기존 후보는 26건 불일치, 수정 후보는 74건 모두 계수가 같았다. 공개 코드만 수정했으며
이 진단은 실제 문서 Native/fresh WASM·정식 회귀의 완료 증거를 대신하지 않는다.
후속 Native 집중·정상 대조군과 최적화 fresh WASM을 같은 새 source로 재검증한다.


## 실제 Canvas2D 소비자의 JPEG 스캔 계약

`4d7ffc79d8`의 최적화 WASM 빌드는 성공했지만 원본 HWPX 집중 검증은 실패했다.
273쪽 raw가 56.98405%이고, 면적 표본 이전의 JPEG 디코딩 RGBA가 이미 녹색 줄무늬다.
동일 ImageData를 JS 소유 배열로 복사해도 결과가 같아 버퍼 소유 가설은 제외했다.

공통 Print payload를 baseline interleaved JPEG로 전달해 Native/Canvas/CanvasKit이
동일 바이트를 소비하게 한다. backend별 색 보정·그림 ID 분기·점수 보정은 하지 않는다.
양자화·DCT·원본 RGB는 유지한다. 코드 변경 뒤 원본 입력의 Native/fresh WASM 집중 쪽과
정상 대조군을 재출력한다. 압축 크기 변화는 별도 전달 비용이며 픽셀 차이로 취급하지 않는다.

## 공통 장치 색 변환 구현

Print bitmap의 연속적인 채널 밝기 확장을 표준 RGB555 양자화로 교체한다.
4×4 Bayer 순서 디더링은 원본 raster의 좌표와 bottom-up 행 순서를 소비하며,
5비트 채널을 비트 복제로 8비트에 전달한다. 알파와 원본 소유·논리 배치는 유지한다.
팔레트 수용 판정과 다른 호환 모드의 선택 규칙은 같은 공통 resolver에서 소비한다.
이 계산은 HWP 사양에 명시된 색 보정값이라고 주장하지 않는다.

값 추적은 `원본 RGB → 공통 Print 색 변환 → 기존 PNG payload/재조회 → 공통 JPEG →
Native·Canvas·CanvasKit의 실제 재생`이다. 문서·그림 ID별 수치나 backend별 색식을
추가하지 않는다. 부분 자르기의 색 변환 순서·창 신원·압축은 별도 미완료 소비 경계이며,
전체 원본 경로의 통과로 대신하지 않고 계속 검증·구현한다.

공개 형식 근거: [BITMAPINFOHEADER의 RGB555와 bottom-up 계약](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-bitmapinfoheader),
[CreateDIBitmap의 장치 형식 변환](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createdibitmap).
바이너리 분석 자료·함수 주소·호출 기록은 Git에 옮기지 않는다. 새 색 변환의 실제 원본
Native/fresh WASM 출력과 독립 Print를 먼저 검증하고, 잘못된 기존 평탄색 픽셀 assertion은
해당 입력의 시각 선행 조건을 확인한 뒤 독립적인 채널 계약에 맞게 정리한다.

## 가시 원본 창의 공통 전달

HWP5 그림 개체의 crop 사각형과 원본 크기는 별도 값이다. 기존 source 좌표 해소와
같은 원본 창을 정수 픽셀로 확정하고, 팔레트 판정·RGB555·압축이 그 창을 소비하게 한다.
crop 창의 좌표와 높이는 자른 뒤 raster를 기준으로 하며 원본 전체의 디더 위상을
재사용하지 않는다. 원본 HWP/HWPX·문서 모델·render tree의 소유와 개체 frame은 보존한다.

`원본/crop → 공통 가시 창 → 그 창의 색 변환 → 실제 frame/창 너비의 압축 →
창을 이미 포함한 payload → PaintOp 생성 시 crop 소비 완료 → Native/Canvas/SVG 재생`으로
연결한다. 원본 bin key는 창·장치별 바이트를 재현하지 못하므로 해당 payload는 inline으로
전달한다. JPEG도 같은 디코딩 RGB·팔레트 계약을 소비한다. codec별 픽셀 오프셋은 넣지 않는다.

기존 fit 그림 경로에서 먼저 적용하고, 자연 크기·반복 채움이나 원본 밖의 빈 영역을 갖는
경로는 해당 좌표 계약을 확인해 처리한다. 전체 원본을 압축한 뒤 부분 창을 다시 자르거나
각 backend에서 crop 값을 따로 지우는 방식으로 대신하지 않는다. 소수점 경계의 증거가
부족하면 임의 epsilon·문서별 반올림 상수를 추가하지 않는다.

90쪽과 기존 전체 그림·가시 팔레트 대조군의 실제 Native/fresh WASM·확대 판독을 먼저
진행하고, 잘못된 기존 평탄색·해상도·재조회 전제도 해당 검증 후 정리한다. 최종 1,532개
raw100·정확한 미대응 0개와 전체 페이지 ±2px 검사를 이 단계의 부분 통과로 대신하지 않는다.
