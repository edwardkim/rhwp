# #8153 Print 그림의 공통 압축 전달

## 근거와 원인 계층

현재 코드 기준은 `c6fbb92d3b71d5aaac55807ce5758e6926ddc29a`다. 기존 편람의 입력과
383쪽 독립 Print PDF는 그대로 재사용한다. 273쪽의 877×510 / 777×522 원본 BMP는
PDF 안에서 각각 JPEG로 전달되지만 현재 paint는 무손실 PNG를 사용한다. 페이지의 좌표와
원본 픽셀 전달, 손실 압축을 서로 다른 계약으로 검증한다.

독립적인 작은 크기 대조군의 JPEG 양자화 표는 같은 원본도 출력 크기에 따라 달라진다.
원본 369의 별도 문서별 너비 7200/14400/21600/28800/32400/34300 HU에서는 품질
35/35/46/62/69/51에 해당한다. 이미지 객체를 재사용한 여러 쪽의 같은 양자화 표를
독립 크기 실험으로 세지 않는다. 기존 Print 26개에서 대응 치수가 확인된 31개 자원을
대조했다. 원본 433의 RGB를 재압축한 자원은 독립 PDF의 계수·RGB와 일치하는 것을
별도 진단으로 확인했으며, 이를 제품 출력의 완료 증거로 쓰지 않는다.

HWP/HWPX 사양은 원본 그림·효과·잘라내기·좌표 계약의 근거다. PDF 생성기의 압축 정책은
해당 사양이 명시한 수치라고 주장하지 않는다. 측정 임계값이나 문서 ID별 분기를 추가하지 않는다.
상단 그림의 색 전달 차이와 나머지 페이지의 미대응은 계속 해결해야 할 범위다.

## 공통 소비 경로와 구현

`ImageNode 원본/효과 → 기존 공통 resolver → 실제 Print frame → 공통 출력 payload →
Native/Canvas/SVG`를 연결한다. 장치·배치에 따라 달라진 압축 바이트는 원본 bin 키로
재조회하지 않고 `OutputDevice` payload로 전달한다. 최종 frame을 별도로 추정하거나
좌표를 다시 보정하지 않는다. 문단·개체 소속과 논리 bbox는 유지한다.

불투명 raster와 투명도 합성, 전체 원본과 부분 잘라내기는 각각의 전달 계약이다. 첫 구현에서
입증한 계약을 연결한 뒤 남은 계약도 계속 구현·검증하며, 부분 성공을 전쪽 목표의 완료로
바꾸지 않는다. 일반 화면과 다른 호환 모드는 기존 계약을 유지한다.

Native/fresh WASM의 인코더는 같은 스칼라 정수 연산을 소비한다. 공개 `jpeg-encoder` 0.7.1의
출처와 원래 라이선스를 보존한 내부 패키지를 사용하며, 역수 근사로 양자화 경계가 바뀌지 않도록
반올림 정수 나눗셈을 사용한다. 공개 코드의 변경 목록과 원본 SHA를 vendor에 남긴다.
한컴 바이너리·디스어셈블리·호출 기록은 Git에 포함하지 않는다.

## 검증 순서

1. 원본 RGB에서 인코딩한 자원의 계수·RGB를 독립 Print와 비교한다. 정답 픽셀을 입력이나
   제품 payload에 복사하지 않는다.
2. 현재 원본 273쪽과 관련 그림 페이지를 실제 Native로 재출력해 기존 PNG·독립 PDF와
   비교한다. 개선·하락·불변과 정확한 미대응 수, 내용·쪽수·관측 글꼴을 구분한다.
3. 정상 대조군과 최적화 fresh WASM을 같은 조건으로 검증한다. 실제 review·overlay를 열어
   그림 내부 선·문자와 바깥 경계를 확인한다.
4. 영향을 받는 경로를 보정한 뒤 최종 전 1,532개 결과·페이지별 ±2px 검사·전체 회귀 등
   #8153의 나머지 완료 조건을 충족한다. 273쪽의 개선만으로 PR을 제출하지 않는다.

이 문서는 구현 전 계획이다. 새 코드의 실제 결과와 미해결 범위는 실행 후 연결한다.

## 첫 Native 후보 결과와 다음 공통 소비 단계

코드 `f9e31456eb7794073ab74ce0746e5497f9a3f927`의 Native 빌드는 성공했다.
선정 52쪽에서 미대응 합계는 56,081 → 50,583개로 줄었으며 내용 구조와 관측 글꼴은
유지됐다. HWPX 273쪽은 raw 98.65734 → 99.08806%, 미대응 2,437 → 1,672개다.
그러나 두 형식 모두 67쪽 −0.00133%p, 260쪽 −0.05627%p의 하락이 남았다.
대조군 2020 모드 12쪽은 RGB가 같았으나, 2024 모드에는 하락도 있어 완료로 판정하지 않는다.
2024 모드를 기존 2020 PDF와 비교한 진단과 같은 버전 출력의 승인 근거를 구분한다.

압축과 화면 축소는 별개다. 공개 PDFium chromium/7999의 `CStretchEngine` 계산을
독립적으로 구현하고, 기존 Print의 260·273쪽 그림 14개를 각각 메모리 안에서 분리해
같은 PDFium으로 렌더했다. 16.16 면적 가중치, 축별 채널 절삭, 실제 bitmap/paper 변환을
따른 Rust 계산 결과는 14개 모두 RGB 바이트 단위로 같았다. 원본 PDF는 수정하지 않았다.
이 진단은 PDF 안의 JPEG 디코딩 RGB를 사용하므로 제품 입력의 검증을 대신하지 않는다.

공통 소비는 `최종 그림 frame → 실제 장치 변환과 페이지 viewport → 정수 외접 경계 →
공통 16.16 면적 표본 → Native/Canvas2D/CanvasKit 재생`으로 연결한다. 배율·페이지 크기를
별도 예측하거나 96dpi를 고정하지 않는다. 처음 입증한 불투명 JPEG의 전체 원본 축소부터
연결하고, 부분 자르기·alpha·회전 등 다른 계약은 승인 근거를 확보해 계속 처리한다.
Native·WASM의 수학을 따로 구현하지 않는다. 좌표·쪽·소유·순서는 바꾸지 않고 출력의 장치
표본만 다룬다. 영향을 받는 본문·대조군을 재출력한 뒤 하락과 실제 확대 출력을 확인한다.

공개 계산 근거: [PDFium chromium/7999 cstretchengine.cpp](https://pdfium.googlesource.com/pdfium/+/refs/heads/chromium/7999/core/fxge/dib/cstretchengine.cpp),
[고정소수점 정의](https://pdfium.googlesource.com/pdfium/+/refs/heads/chromium/7999/core/fxge/dib/cstretchengine.h).
한컴 바이너리 분석 자료는 이 문서에 옮기지 않고 ignored `output/`에만 보존한다.
