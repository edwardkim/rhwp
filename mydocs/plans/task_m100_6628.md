# #6628 Gym 라이브 오라클 계보·정답지·전수 계약 정상화 수행계획

## 1. 목적과 비목적

Gym은 AI 에이전트가 rhwp CLI/API를 조합해 과제를 수행하는 기술을 학습·평가하는
벤치마크다. 이 작업은 Gym 내부의 정답 권위, 기준풀이, 음성 대조, trajectory와
실행 계약을 정직하게 만든다.

Gym 결과만으로 한컴 조판 동등성이나 제품 릴리스 적합성을 주장하지 않는다. 일반
PR/devel/main CI, 태그, Release Binary, npm·extension 게시를 Gym 전건 평가에 의존시키는
것도 비목적이다.

커밋은 Gym을 제품 릴리스 인증으로 결합하려던 잘못된 경로도 포함하며, 마지막 WIP

3. profile 구현 문자열을 그대로 찾는 낡은 source snapshot 2건

5. pack-health 196건과 tutorial 날짜 정문 snapshot 각 1건

## 3. 보호 불변식

1. **제품 릴리스 비의존**: Gym 실패가 제품 CI·main 승격·릴리스·게시를 차단하지 않는다.
2. **정답 권위 정직성**: 같은 현재 rhwp로 계산한 기대값은 `self-live`이지 외부 정답이
   아니다. 독립 fixture·명세·한컴 근거와 같은 이름으로 접지 않는다.
3. **양·음·경로 삼각형**: 각 과제는 기준풀이 통과만 보지 않는다. 적용 가능한 음성
   대조가 거부되고, 다단계 의미 step이 실제로 load-bearing인지 함께 확인한다.
4. **오류 봉투 불통과**: 정상 결과를 요구하는 과제가 exit 오류 봉투, 빈 파일, 존재·크기만
   맞는 파일을 정답으로 허용하지 않는다.
5. **예외는 데이터**: 전수 계약의 승인 예외는 이유·적용 범위·근거·재검토 조건을 가진
   기계 판독 자료로 남긴다. 깨진 시험을 단순 skip하거나 기대값을 느슨하게 하지 않는다.
6. **제품 수정 분리**: Gym이 발견한 Rust 제품 결함은 별도 이슈·브랜치·제품 검증으로
   처리한다. #6628 PR에 `src/**`나 Rust integration source를 섞지 않는다.
7. **비밀·사설 코퍼스 비의존**: 공개 Gym 재현은 저장소 추적 자산만 사용한다.
8. **외부 변경 승인**: issue comment, push, PR 생성과 merge는 단계별 승인 뒤 수행한다.

## 4. 단계별 수행

### Stage 0 — WIP 계보 감사와 제출 구조 정상화

1. 일곱 커밋의 최종 트리와 `upstream/devel` 차이를 범위별로 분류한다.
2. 최종 트리에서 이미 철회된 release certification producer/consumer가 남지 않았는지
   기계 검사한다.
3. `src/document_core/queries/field_query.rs`와 `tests/batch_fill_contract.rs`의 제품 수정은
   재현 근거와 함께 별도 이슈 후보로 분리한다.
4. 메인테이너 승인 뒤 로컬 전용 safety ref를 만들고, WIP를 최신 devel 위에 논리
   커밋으로 replay한다. 새 트리와 WIP tree가 의도한 경계에서만 다른지 대사한 뒤 safety
   ref를 삭제해 고아 브랜치를 남기지 않는다.

**종료 게이트**: #6628 최종 diff에 과도기 release 결합과 제품 Rust 수정이 없고, WIP
변경의 disposition 표가 존재한다.

### Stage 1 — 정답 권위 분류 모델과 전수 원장

1. task/reference의 `run`, `answer`, artifact, 상수 기대값과 외부 근거를 읽어 권위를
   다음 최소 계층으로 분류한다.
   - `self-live`: 채점 대상과 같은 rhwp 실행으로 계산
   - `contract-constant`: 작성자가 고정한 내부 계약값
   - `independent-fixture`: rhwp 실행과 독립된 공개 fixture/명세 근거
   - `external-oracle`: 한컴 또는 독립 구현에서 획득한 외부 증적
2. 1,035개 task를 한 번씩 포함하는 기계 판독 원장 또는 결정론적 생성 보고서를 만든다.
3. 미분류·다중 분류·근거 경로 부재를 감사 실패로 만든다.
4. 집계 수치가 개별 행에서 재계산되는 시험을 추가한다.

**종료 게이트**: task 1,035개가 중복·누락 없이 분류되고 `self-live`를 제품 정답으로
승격하는 문장이나 판정이 없다.

### Stage 2 — 전수 Python 계약 정상화

1. subprocess 시험은 환경의 `python` 별칭 대신 `sys.executable`을 사용한다.
2. profile 시험은 소스 문자열이 아니라 구조화 예외와 실제 pack 선택 동작을 검증한다.
3. `CHECK_FIELD_HINTS`를 현행 `REGISTRY`와 완전히 대사한다.
4. tutorial front matter 시험은 과거 날짜 문자열이 아니라 필드 형식·정본 관계를 검증한다.
5. pack-health 196건을 유형별로 정산한다. 실제 spoiler·누락은 자료를 고치고, 의도된
   교육용 힌트는 기계 판독 예외 원장에 근거와 재검토 조건을 남긴다.

**종료 게이트**: `test_gym_*.py` 전수 실행이 failure/error 0이거나, 승인된 예외만 별도
구조화 결과로 보고되고 unittest 자체는 성공한다.

### Stage 3 — 약한 answer/artifact 오라클 정산

1. 기존 WIP가 바꾼 task/reference를 task별로 대사해 live-only answer, 파일 존재·크기,
   동일 해시, 오류 봉투 허용 문제를 분류한다.
2. 제출물 전체 의미를 검증하는 최소 연산자를 사용하고, untrusted 텍스트는 크기 상한과
   digest 보고를 적용한다.
3. 새 연산자마다 정상·변조·과대 입력·인코딩 실패 음성 시험을 둔다.
4. reference command와 결과 좌표가 현재 CLI capabilities와 일치하는지 확인한다.

**종료 게이트**: 알려진 19 task/28 false-pass뿐 아니라 전수 discrimination에서
false-pass 0이며, 검사를 약화해 얻은 통과가 없다.

### Stage 4 — positive baseline·discrimination·trajectory 전수 감사

1. 공개 저장소 자산으로 positive baseline을 21 pack 전건 실행한다.
2. 적용 가능한 모든 음성 대조를 실행한다.
3. 다단계 reference의 마지막 의미 step 제거 실험으로 load-bearing 여부를 확인한다.
4. 실패 시 task id, authority class, tool exit, artifact 상태를 같은 봉투에 남긴다.

**종료 게이트**: baseline 1,035/1,035, discrimination false-pass 0, trajectory의 theater와
도구 오류 0. 예외가 있으면 Stage 2 형식의 승인 원장으로만 남는다.

### Stage 5 — Gym 전용 실행 경계

1. 기존 workflow 파일 경로는 보존하고 표시 이름을 `Gym Benchmark Validation`으로 바꾼다.
2. Gym 관련 PR에서만 빠른 구조·단위 계약을 실행한다.
3. 전건 baseline/discrimination/trajectory/oracle probe는 메인테이너 수동 실행으로만 둔다.
4. devel/main push, v* tag, Release Binary, npm/extension workflow가 Gym artifact를 생산·소비하지
   않는 계약 시험을 둔다.
5. 수동 artifact에는 exact SHA, 권위 집계, 각 도구 exit와 30일 보존 정보를 남긴다.

**종료 게이트**: 제품 변경 PR은 Gym 때문에 추가 runner 비용을 부담하지 않고, Gym 변경
PR과 수동 전건 실행은 벤치마크 결함을 fail-closed로 드러낸다.

### Stage 6 — 검증·보고·PR 준비

1. 변경 Python·workflow 계약과 전수 Gym 계약을 실행한다.
2. 문서 링크·front matter를 검사한다.
3. Rust source가 최종 diff에서 제거됐음을 확인한다. 남아 있다면 Rust 필수 lint 묶음과
   integration manifest 규칙을 적용하되, 원칙적으로 별도 제품 이슈에서 처리한다.
4. 비용, 권위 분포, 수정 task, 승인 예외, 독립 oracle 공백과 재현 명령을 최종 보고서에
   기록한다.
5. 최신 `upstream/devel`을 다시 fetch하고 충돌·영향도를 재검증한다.

**종료 게이트**: clean tree에서 재현 명령이 성공하고 메인테이너가 보고서와 PR 범위를
승인한다.

분리 이슈에서는 `AGENTS.md`와 local validation 4.3의 Rust 필수 묶음을 모두 적용한다.
