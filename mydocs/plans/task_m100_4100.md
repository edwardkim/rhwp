## 1. 배경

rhwp 는 차트를 **그릴** 수 있지만 **고칠** 수 없다. 이 작업은 기존 차트의 숫자 값을 바꾸고 그
편집이 한컴에서 보이게 한다. 범위는 엔진 축(코어 + CLI)이고 WASM 바인딩·rhwp-studio UI 는 다음
서브이슈(B1-UI) 몫이다.

#4055 스파이크가 확정한 전제 — 값 하나가 3~4중으로 저장돼 있다.

| | 표현 | 위치 | 한컴이 읽나 |
|---|---|---|---|
| ① | `Chart/chartN.xml` | HWPX zip 파트 | **예** |
| ② | `OOXMLChartContents` | 중첩 CFB (`BinData/*.ole`) | **예** (HWP5 에선 이것만) |
| ③ | 레거시 `Contents` | 같은 중첩 CFB | 아니오 (음성 대조군 확정) |
| ④ | `\x02OlePres000` EMF | 같은 중첩 CFB | 아니오 |

①==② 는 코퍼스 28종 전건 SHA-256 일치다. **①만 편집하면 HWP 변환에서 사라진다** → ①②를 함께
쓴다. ③은 쓰지 않고(한컴이 안 읽는다, 파서 결함은 #4098), ④는 재생성하지 않는다.

## 3. 코퍼스 실측 — 설계를 바꾼 발견 4건

`samples/chart` 28종 HWPX 의 `Chart/*.xml`·`Contents/section0.xml` 을 직접 열어 셌다.

```text
파일 28 / 차트 파트 28(파일당 1) / BinData ole 28(파일당 1)
①↔② 조인 가능(<hp:switch> 안 <hp:chart> + <hp:default><hp:ole>)  = 28/28
계열 합계 68 · ptCount↔실제 c:pt 불일치 0 · c:pt idx 비순차 0 · 톱니 계열 0 · cat수≠val수 0
계열 3개=16파일 · 1개=6 · 2개=5(분산형) · 4개=1(시가고가저가종가)
값 4개=22파일 · 3개=5(분산형) · 1개=1(특이케이스)
extLst · hncChartStyle = 28/28 보유
```

**M1 — `c:f` 를 레이아웃 근거로 쓸 수 없다.** 분산형 5건 **전부** ser 0 의 yVal 참조가
`Sheet1!$B$2:$A$4` 다 — 시작 열 B, 끝 열 A 의 비대칭 범위(한컴이 그렇게 쓴다). 이슈 본문은
"행=카테고리·열=계열"의 근거로 `c:f` 모양을 들었는데 결론은 맞고 근거는 못 쓴다.
**레이아웃은 요소 구조(`c:cat`/`c:xVal`/`c:val`/`c:yVal`)에서 유도한다.** B1 은 `c:f` 를 읽지도
쓰지도 않으므로 무해하지만, 근거를 여기서 바로잡아 다음 사람이 `c:f` 파싱을 시도하지 않게 한다.

**M2 — 분산형의 X 공유는 코퍼스 성질이지 포맷 보장이 아니다.** 5건 모두 두 계열의 xVal 이
`0.7/1.8/2.6` 로 동일해 이슈가 제안한 `X,계열1,계열2` 한 장 레이아웃이 성립한다. 그러나 OOXML 은
계열마다 다른 X 를 허용한다 → §4-3 의 거부 규칙.

**M3 — `numLit`/`strLit` 1건은 `c:f`·`c:cat` 자체가 없다.**
`특이케이스/가로막대형_하나만있을떄_단일시리즈제목` — 계열 1, 값 1, 카테고리는 `strLit` 리터럴.
스캐너가 `numCache`/`numLit` 을 같은 경로로 잡아야 한다는 이슈 지시는 맞고, **수용 기준 2
(무편집 왕복 바이트 동일)의 최난도 케이스가 이 파일이다.**

**M4 — 실패 경로는 코퍼스 커버리지 0 이다.** 28/28 이 조인 가능하므로
`nestedCopyNotFound`/`ambiguousNestedCopy` 는 합성으로만 덮인다. #4099 가 같은 문제를 만나
만든 선례를 그대로 쓴다 — `synth_chart_without_fallback`
(`tests/issue_4099_hwpx_chart_to_hwp.rs`, `<hp:switch>` 를 벗겨 `chart_switch_fallback = None` 을 만든다).
#4499 머지 전에는 그 파일이 없으므로 **같은 조립을 이 작업의 테스트 안에 자체 구현**하고,
머지 후 중복이 확인되면 공통화 여부를 별도로 판단한다.

## 4. 설계

### 4-1. 편집은 최소 diff 바이트 수술이다

`src/ooxml_chart/` 에 writer 가 없고, 파서(`parser.rs:62 parse_chart_xml`)가
`c:pt idx`·`c:f`·`c:externalData`·`extLst` 를 **읽지 않는다**(확인함). 파싱→재방출로 왕복시키면
모델에 없는 것이 전부 사라진다 — 코퍼스 28/28 이 `c:extLst`·`ho:hncChartStyle` 을 갖고 있다.

`c:v` 텍스트만 바꾸는 치환을 한다. 구조 스캐너는 문자열 검색이 아니라 `quick_xml` +
`buffer_position()` 오프셋 추적으로 만든다 — 접두어(`c:`)를 고정하지 않고, `c:numLit`(M3)도 같은
경로로 잡기 위해서다. **선례가 in-tree 에 있다**: `src/parser/hwpx/header.rs:2067`(와 `:1980`)이
이벤트 직전 `buffer_position()` 을 스냅숏해 원본 바이트를 정확히 잘라낸다.
**`Reader::from_str`** 이어야 오프셋이 바이트 위치가 된다(현 `ooxml_chart/parser.rs:63` 은
`from_reader` 라 그대로 못 쓴다).

스캐너 산출은 "각 계열의 각 값이 원본 바이트의 어느 구간인가"의 목록이다. 패처는 그 구간만
치환하고 나머지 바이트는 손대지 않는다. 값 개수·계열 개수·라벨은 바꾸지 않는다(B2).

### 4-2. 슬롯 해석 — ①과 ②

주소 `(section, para, control)` → `Control::Shape(ShapeObject::Ole(ole))` 에서

- **①** = `ole.bin_data_id >= 60001` 인 `bin_data_content` 항목(`extension == "ooxml_chart"`,
  href `Chart/chart{id-60000}.xml`)
- **②** = `ole.chart_switch_fallback`(`src/model/shape.rs:858`)이 가리키는 `BinData/*.ole` 슬롯의
  중첩 CFB 안 `/OOXMLChartContents`

조인 키는 HWPX 파서가 `<hp:switch>` 안에 chart 와 ole 이 **둘 다** 있을 때만 매단다
(`src/parser/hwpx/section.rs:6143-6155`). 해소 실패 시 **아무것도 쓰지 않고**
`nestedCopyNotFound`/`ambiguousNestedCopy` 로 보고한다. 반쪽만 새 값인 파일이 나가는 것이 최악이라
`wrote[]` 를 봉투에 실어 어느 표현에 썼는지 항상 드러낸다.

**HWP5 입력엔 ①이 없다.** `Chart/*.xml` 파트가 없고 차트는 평범한 `OleShape` 다
(`chart_id_ref`·`chart_switch_fallback` 모두 `None`). "①② 동시 기록"은 HWP5 에서 **②만**으로
자연 축약된다. 차트 판별은 렌더러와 같은 방법을 쓴다 —
`parse_ole_container`(`src/parser/ole_container.rs:63`)로 `/OOXMLChartContents` 유무를 본다
(`src/renderer/layout/shape_layout.rs:1972-1974`).

#### 주소 축은 둘이고, **정본은 문서 순번**이다

| 축 | 닿는 범위 | 위치 |
|---|---|---|
| 문서 순번 0-based (**정본**) | 컨테이너 안까지 전부 | `collect_charts` · CLI `--chart N` · `get/set_chart_data_by_index_native` |
| `(section, paragraph, control)` 3인자 | **본문 직속만** | `get/set_chart_data_native` — 그림 API 와 동형인 편의 경로 |

3인자를 정본으로 삼지 않는 이유: 글상자 안 차트를 표현하지 못하는데 rhwp-studio 는 그것도
선택할 수 있다(B1-UI). 편집이 컨트롤이 아니라 **슬롯 바이트**만 건드리므로 순번 축으로는
컨테이너 안 차트도 그대로 편집된다 — 3인자는 그림 API 와의 대칭을 위해 남기는 편의 경로다.

#### 열거 범위 — 명시적으로 좁힌다

`collect_charts` 가 재귀하는 컨테이너는 **글상자·표 셀·머리말·꼬리말·각주·미주**다.
`SectionDef.master_pages`·`Field.memo_paragraphs`·개체 캡션 안의 차트는 **범위 밖**이고
열거되지 않는다.

이 저장소는 *"한 워커가 컨테이너 하나를 놓쳤다"* 가 반복 결함이고(#4099 보고서 §7-2, 워커
다섯의 커버리지 표), 검증할 합성 문서 없이 재귀 가지를 늘리는 것이 바로 그 결함을 만드는
방식이다. 그래서 **가지를 늘리는 대신 범위를 문서로 못박고** 덮은 컨테이너만 테스트로
고정한다. 워커 통합은 #4099 가 이미 후속으로 지목한 별개 작업이다.

**② 재포장** — `all_ole_streams` 로 전 스트림을 뜬 뒤 `/OOXMLChartContents` 만 갈고
`build_cfb_with_root_clsid`(`src/serializer/mini_cfb.rs:101`)로 되짓는다. 원본 CLSID 는
`ole_root_clsid`(`src/parser/ole_container.rs:184`)로 읽는다. **`build_cfb`(`:89`)를 쓰면 안 된다** —
CLSID 0 을 넣고, 그러면 한컴이 개체를 못 알아봐 내용을 비워 그린다(#4097 의 증상이고,
그 함수 주석이 중첩 OLE 재포장에 쓰지 말라고 못박고 있다).

직렬화기는 손대지 않는다. `src/serializer/hwpx/mod.rs:178` 이 슬롯 바이트를 `Chart/chartN.xml` 로
무가공 방출하고, `src/serializer/cfb_writer.rs:281-291` 이 `.ole` 에 4바이트 LE 크기 접두어를 다시
붙여 내보낸다(**IR 은 접두어 없는 맨 중첩 CFB 를 들고 있다**). 따라서 편집하지 않은 차트는 슬롯이
원본 그대로라 바이트 원형이 유지되고, 수용 기준 3 이 자료구조로 충족된다 — 플래그가 필요 없다.

### 4-3. CSV 레이아웃 계약

행=카테고리, 열=계열. 인용·파싱은 `document_core::queries::table_csv` 를 그대로 쓴다 —
`quote_field:53` · `matrix_to_csv:90` · `parse_csv:115`(RFC 4180, CRLF, BOM 상수 포함).

```text
,계열 1,계열 2,계열 3          분산형:  X,계열 1,계열 2
항목 1,4.3,2.4,2                       0.7,2.7,1
항목 2,2.5,4.4,2                       1.8,3.2,2
```

거부 규칙 — 하나라도 어기면 **한 칸도 쓰지 않고** `invalid[]` + exit 2 (`csv-to-table` 규약 그대로):

| 코드 | 조건 |
|---|---|
| `rowCountMismatch` / `colCountMismatch` | 행·열 수가 원본과 다름 |
| `seriesNameMismatch` / `categoryMismatch` | 계열명·라벨이 다름 (B1 은 라벨을 안 바꾼다) |
| `notANumber` | 값이 실수로 파싱되지 않음 |
| `sharedXRequired` | **분산형에서 계열별 xVal 이 서로 다름 (M2)** — X 한 열로는 표현할 수 없다 |

`sharedXRequired` 는 코퍼스에 0건이지만 반드시 넣는다. 없으면 X 한 열이 한 계열의 xVal 만 조용히
바꾼다 — 이 작업이 가장 피해야 할 실패 모드다.

`c:formatCode` 는 동기화하지 않는다. 계열의 서식이 `General` 이 아니면(예: `0`) 한컴은 새 값을
그 서식대로 **표시**한다 — 파일이 틀린 것이 아니라 표시 규약이다. 코퍼스는 전건 `General` 이라
현재 무영향이지만, `chart-to-csv` 는 캐시 텍스트를 그대로 내보내므로 화면 표시와 CSV 값이 다를
수 있다. 보고서 "알려진 한계"에 적는다.

### 4-4. 코어 표면

기존 개체 API 와 동형이다(`object_ops/picture.rs:113` get / `:454` set — 주소 3인자 `usize`,
JSON `String` 반환).

```text
get_chart_data_native(section_idx, parent_para_idx, control_idx) -> Result<String, HwpError>
set_chart_data_native(section_idx, parent_para_idx, control_idx, edits_json) -> Result<String, HwpError>
```

주소·타입 오류만 `Err`. 데이터 검증 실패는 `Ok` + `{"ok":false,"invalid":[…]}` — 검증기가 코어와
CLI 두 곳으로 갈리면 안 된다(`agent_surface_playbook` 규칙 2).

**이건 새 선례다.** 코어의 기존 부정 응답은 `{"ok":false, …}` 까지이고
(`src/document_core/queries/field_query.rs:684`), `invalid[]` 는 지금 CLI 봉투 관례다
(`src/main.rs` 안에서만 등장). 검증기 단일화를 위해 `invalid[]` 를 코어로 올리는 판단을 여기 명시해
리뷰에서 다투지 않게 한다.

wasm 은 `Deref`(`src/wasm_api.rs:348`)로 자동 노출되지만 **바인딩은 이 작업에서 쓰지 않는다**(B1-UI).

### 4-5. CLI 표면과 배선

`table-to-csv`/`csv-to-table` 선례를 따르는 최상위 서브커맨드 2개.

```text
rhwp chart-to-csv <파일> [--chart N] [-o <경로>] [--bom] [--json]
rhwp csv-to-chart <파일> --csv <경로> --chart N [-o out] [--dry-run] [--verify] [--json]
```

`--chart N` 은 **문서 순서 1-based**다 — `Chart/chartN.xml` 번호가 아니다. HWP5 엔 그 번호가
없고, 파서가 차트를 64개·연속으로만 훑기 때문이다(`src/parser/hwpx/mod.rs:519`, 첫 결번에서 `break`).
`--table N` 의 선례와 같은 규칙이다.

핸들러는 `table_to_csv`(`src/main.rs:5357`)·`csv_to_table`(`:5553`)을 베낀다. 디스패치는
clap 이 아니라 `match args.get(1)`(`:271-272`). exit 코드는 0/1/2 가 상수(`:14-22`), **3·4 는 날
