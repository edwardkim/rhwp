# #9165 Canvas2D 셀 입력 시 호스트 글꼴 요청 수집 개선 계획

작업 브랜치는 `task/9165-host-font-input`이며 기준은 `upstream/devel`의 `fbf8081db57c0c6abc9bad418290c5018193e24f`이다.

## 재현 근거

기존 WKWebView 실측에서 표 셀 입력 20회에 글꼴 준비 20회, 페이지 트리 조회 60회, 활성 상태 변경 0회를 확인했다. 두 번째 프레임까지 걸린 시간의 중앙값은 공급자가 없을 때 22.5ms, 빈 공급자를 연결했을 때 39.0ms였다.

Studio 기준 커밋 `c9095c5f67`과 최신 devel에서 실제 `prepareCanvasMetrics` 메서드를 각각 추출해 합성 3쪽 문서로 20회 호출했다. 두 버전 모두 공급자 없음은 0회, 빈 공급자 연결은 60회 조회했다. 이 검사는 메서드의 호출 수를 측정하며 브라우저 입력 지연은 별도의 실행으로 측정한다.

## 수정과 검증 범위

1. 합성 다쪽 문서에서 같은 표 셀을 편집하는 Studio 기준선을 먼저 측정한다. 공급자 미연결, 빈 목록, 실제로 준비할 face가 있는 목록에서 호출 수와 프레임 시간을 구분한다.
2. 카탈로그 준비 이후 빈 목록의 페이지 조회를 생략한다. 일반 글꼴 대체와 PUA의 독립 준비 경로를 보존한다. 목록이 있는 경우에는 편집에서 실제로 무효화된 범위를 확인하고, 범위를 확정할 수 없을 때는 전체를 다시 수집한다. 같은 수집 안에서 같은 family·weight·slant의 후보 탐색을 재사용한다.
3. 문서 교체, 공급자 교체와 세대 변경, 스타일 적용, 붙여넣기, 새 문자·PUA, 한글 조합, 실행 취소·다시 실행에서 필요한 face와 커서·페이지 배치를 확인한다. 회귀 검사는 공개 가능한 합성 fixture로 작성한다.
4. 수정 전후 동일 조건의 호출 횟수와 프레임 시간을 기록한다. Studio 변경 범위의 필수 로컬 검증을 수행하고 브라우저·실제 IME별 실행 결과를 구분한다.

## 수정 및 검증 결과

2026-11-18 계획 승인 후 #7405에서 도입된 전체 페이지 수집과 이후 추가된 PUA·글꼴 등록 경로를 대조했다. 준비를 마친 호스트 카탈로그가 비어 있으면 페이지 조회를 생략한다. 카탈로그에 face가 있고 단일 쪽의 텍스트 편집이면 해당 쪽의 요청을 새로 수집한다. 문서·글꼴 세대, 쪽수, metrics 종류, 이전 편집의 준비 완료 여부를 확인하며 전체 갱신이나 조판 전환 뒤에는 다시 수집한다. 캐시에 보관하는 값은 페이지별 face 요청이다. 동일 페이지의 같은 글꼴·스타일 후보는 한 번만 해소한다.

빈 문서에 3쪽과 표를 만들고 첫 셀에 같은 글자를 20회 입력했다. 공급자 미연결·빈 카탈로그·실제 글꼴을 반환하는 카탈로그를 각각 측정했다. 아래는 변경 전후의 페이지 트리 조회 수와 입력 이벤트부터 두 번째 프레임 콜백까지 걸린 시간의 중앙값이다. 맨 처음 준비용 입력 1회는 제외했다. 양쪽 Studio는 같은 release WASM을 사용했다.

| 환경 | 공급자 | 조회 수 전 → 후 | 중앙값 전 → 후 |
| --- | --- | ---: | ---: |
| Chrome | 미연결 | 0 → 0 | 33.3 → 33.3 ms |
| Chrome | 빈 카탈로그 | 60 → 0 | 66.7 → 33.3 ms |
| Chrome | 글꼴 공급 | 60 → 20 | 66.6 → 33.3 ms |
| Firefox | 미연결 | 0 → 0 | 17 → 16 ms |
| Firefox | 빈 카탈로그 | 60 → 0 | 33 → 17 ms |
| Firefox | 글꼴 공급 | 60 → 20 | 33 → 17 ms |
| WKWebView | 미연결 | 0 → 0 | 33 → 33 ms |
| WKWebView | 빈 카탈로그 | 60 → 0 | 67 → 33 ms |
| WKWebView | 글꼴 공급 | 60 → 20 | 67 → 33 ms |

조판 전환 시에는 전체 수집이 발생할 수 있다. 최종 측정에 앞선 WKWebView 반복 실행에서는 글꼴 공급 시 처음 두 입력에서 각각 세 쪽, 이후 18회에서 각각 한 쪽을 조회해 총 24회였다. 회귀 검사는 안정화된 후반부의 실제 조회 페이지를 확인한다. 프레임 시간은 성능 관측값이며 고정 임계값으로 사용하지 않는다.

- 세 브라우저의 공급자 세 조건 각각에서 합성 한글 조합·PUA 붙여넣기·실행 취소·다시 실행 후 셀 내용과 커서 위치를 확인했다. 모든 조건에서 전후의 전쪽 layer tree·셀 글자 속성·커서 기하를 합친 SHA-256이 일치했다. 다른 쪽에 새 스타일을 적용하면 추가 face를 읽었다.
- macOS 두벌식의 물리 키에 대응하는 키코드를 격리 WKWebView 프로세스에 전달했다. 같은 키로 일반 textarea에는 `한 `이 들어갔고 Studio 셀에는 기존 devel과 수정본 모두 `ㅎㅏㄴ `이 들어갔다. 두 Studio의 쪽수는 3, 초기 문자 하나를 포함한 최종 커서 오프셋은 5였다. 이 입력 경로의 기존 자모 분리 현상은 남아 있다. 설치된 알한글 프로세스는 이 검사의 대상에 포함되지 않았다.
- fresh release web WASM의 SHA-256은 `aa692061e1bc527eeeef803bce17e3b00fb31e4261e05c9c09b3b6afe04bfeef`다. Chrome이 양쪽에서 실제 수신한 바이트와 production 번들의 공개 WASM을 확인했다. TypeScript 검사, Studio 단위 검사 2,808건, production build, 기존 #7403 Canvas2D E2E와 신규 #9165 E2E를 통과했다. 기존 #7403은 공급자 교체·해제·지연 응답 폐기와 실제 글꼴 측정·paint를 포함한다.
