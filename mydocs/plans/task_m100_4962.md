## 1. 목표

실제 renderer가 사용한 각 문자를 기준으로 font metric coverage를 다시 측정한다. 선언된 font family의
존재 여부가 아니라 다음 질문에 재현 가능한 수치로 답해야 한다.

1. 실제 사용 문자는 exact metric, 검증된 identity alias, measured overlay, metric surrogate 중 무엇을
   거쳐 advance를 얻었는가?
2. metric face는 있으나 해당 문자가 없는 `char-miss`, face 자체가 없는 `face-miss`, 그리고 최종
   heuristic은 각각 얼마인가?
3. 이 결과가 HWP/HWPX, 언어 slot, bold·italic, 장평·자간, 고정 frame과 stored/fresh LineSeg
   cohort에서 어떻게 달라지는가?

W3의 결과는 기존 `metric mapped 91.16%`를 문자별 renderer decision으로 보강한 coverage 기준선이다.
기존 POC의 유효한 편집 습관·실사용 aggregate는 폐기하거나 다시 만들지 않는다. 이 단계에서는 조판
위험 순위를 확정하거나 metric·fallback·font asset을 바꾸지 않는다.

### 2.5 추가 전수 계측의 정당성 경계

현재 v2 aggregate만으로 7개 coverage 분류를 역산할 수 없다. 결정적인 결손은 다음과 같다.

1. usage row에 code point 분포가 없어 face가 존재해도 특정 문자가 없는 `char-miss`를 계산할 수 없다.
2. `metricFace`는 원시 font 이름에 `layout_metric_face_name()`을 직접 호출한 결과라 `altType`, 언어별
   `substFont`, style normalization과 W2 resolver 계보를 거치지 않는다.
3. space·구두점·KoPub 등 문자별 `widthSource`가 없어 exact hit와 measured overlay를 분리할 수 없다.
4. W1 relation이 없어 identity alias와 metric surrogate를 일반 alias·fallback에서 분리할 수 없다.
5. stored LineSeg는 존재 여부 boolean뿐이며 유효성이나 fresh layout과의 경계 차이가 없다.
6. POC 기준 commit `44125461187c158073daf5b6b317b08042e7332a` 이후 현재 `devel`까지 642개
   commit이 있으며, model·parser·style resolver·metric·text measurement 관련 commit도 51개다.

따라서 **문자별 coverage를 얻기 위한 corpus 1회 delta read는 필요하다.** 그러나 다음 작업은 정당화되지
않으며 기본 계획에서 제외한다.

- 이미 확보된 장평·자간·문맥·font 사용 통계를 처음부터 다시 설계하거나 새 기준선으로 덮어쓰기
- 모든 page의 raw W2 trace 저장
- 10k 전체에 native·브라우저 paint snapshot과 fresh layout을 무조건 실행
- 기존 POC와 같은 face-level 91.16%를 다시 계산하는 것만으로 W3 완료 주장

새 delta pass는 기존 usage key를 유지하면서 character decision 분류만 추가하고, 기존 합계와의 차이를
parser·model drift audit로 보고한다. Stage 3 pilot에서 비용과 정확성이 입증되지 않으면 10k 전수 실행을
승인 요청하지 않는다.

## 3. 착수 조사에서 확인한 결손

### 3.1 W2 trace 상한

W2 공개 query는 page 한 개, 기본 1,024문자, hard maximum 4,096문자만 지원하고 offset·pagination이
없다. 현재 `rhwp-q-font-trace`도 기본 상한으로 한 page를 조회한다. 따라서 이를 그대로 반복 호출하면 긴
page의 뒤쪽 문자가 누락된다.

W3는 W2의 공개 진단 상한을 무제한으로 올리지 않는다. 동일한 내부 문자 결정 walker를 사용하는
streaming aggregate collector를 두어 전체 문자를 일정한 메모리로 한 번씩만 집계한다. 원시 문자 trace를
전수 보존하지 않는다.

### 3.2 source와 조판 문맥 join

W2 record는 장평·자간 transform을 제공하지만 고정 frame, stored LineSeg 유효성, fresh layout cohort를
완성된 W3 축으로 제공하지 않는다. 공개 fixture pilot에서도 `sourceMappingMismatch`가 관찰됐다.

W3는 source 좌표를 추정으로 보충하지 않는다. 다음 상태를 구분한다.

- `joined`: 문단·run·문자와 조판 문맥을 유일하게 연결함
- `layout-only`: metric 결정은 유효하지만 frame·LineSeg 문맥 join은 불완전함
- `excluded`: 문자 결정 자체를 만들 수 없거나 파싱에 실패함

coverage 분모와 조판 교차축 분모를 분리하고 각 상태의 수를 함께 대사한다.

### 3.3 backend observation

독립 `DocumentCore`·CLI 조회는 준비된 native/Studio renderer snapshot이 없으면 native Skia,
Canvas2D와 CanvasKit을 `unsupported`로 끝낸다. portable layout coverage에 이 상태를 metric miss로
섞지 않는다.

- corpus 전수: native/WASM 공통 portable layout metric decision
- backend 불일치: 준비된 native renderer 또는 Studio snapshot을 사용하는 별도 관찰 cohort

W3 보고서에는 두 분모를 분리한다. browser가 actual Canvas2D glyph face를 공개하지 않으면
`notObserved`를 face 선택 성공으로 승격하지 않는다.

### 3.4 ledger source drift

W2 trace는 W1 source digest가 trace-only refactor 이전이라는 `ledgerSourceDrift`를 이미 명시한다.
Stage 1에서 W1 collector·validator를 현재 source에 재실행하되 기존 artifact를 즉시 덮어쓰지 않는다.
candidate identity·relation·선택 순서가 달라졌는지 먼저 비교하고, digest만 달라진 경우와 의미 변경을
구분해 보고한다. 의미 변경이 발견되면 W3 구현을 중단하고 계획 변경 승인을 받는다.

## 4. 보호 불변식

[폰트 메트릭·fallback 원인 계보 보고서](../report/font_metrics_fallback_causal_lineage_20260816.md)의
FI-01~FI-14를 적용하며 다음 항목을 W3 hard gate로 둔다.

- metric 값, lookup 순서, fallback target, paint face, font asset과 기본 renderer output을 바꾸지 않는다.
- W2 trace와 W3 collector는 같은 실제 `CharWidthDecision`을 사용한다.
- layout metric face와 paint face를 같은 것으로 강제하지 않는다.
- HWP/HWPX 또는 producer build 번호로 정책을 분기하지 않고 현재 LineSeg 유효성과 객체 상태를
  feature detection한다.
- stored LineSeg와 fresh layout 결과를 같은 cohort나 hash에 섞지 않는다.
- `identity-alias`, document substitution, style fallback, official successor, metric surrogate,
  measured overlay, paint substitute와 heuristic을 서로 대체 가능한 이름으로 축약하지 않는다.
- 모든 성공 분류는 상호배타적이며 분류 합이 해당 분모와 정확히 일치해야 한다.
- parse 실패, page truncation, source join 실패와 backend 미관찰을 0이나 성공으로 가장하지 않는다.
- private corpus 원문·본문·식별 파일 목록·절대 경로·raw trace·재배포 불가 font bytes를 저장소,
  GitHub Issue, PR과 CI artifact에 넣지 않는다.
- default render 경로에는 collector·hash·파일 I/O 비용을 추가하지 않는다.

## 5. W3 분류 계약 후보

분류는 한 record가 둘 이상에 들어가지 않도록 아래 순서로 판정한다. Stage 1 RED test에서 실제 W1
relation과 W2 `widthSource` 조합을 전수 대조한 뒤 확정한다.

| 순서 | 분류 | 판정 후보 |
| ---: | --- | --- |
| 1 | `measured-overlay` | 검증된 overlay relation 또는 `metricSpaceOverlay`·구두점 overlay 등 measured/manual 폭 산출 |
| 2 | `identity-alias-hit` | `identity-alias` 근거가 verified이고 최종 metric character가 hit |
| 3 | `metric-surrogate` | 선택에 참여한 metric relation이 `metric-surrogate`이고 character가 hit |
| 4 | `exact-hit` | metric entry가 존재하고 character가 hit이며 위 관계에 해당하지 않음 |
| 5 | `char-miss` | metric entry는 있으나 `characterMatch=miss` |
| 6 | `face-miss` | 실제 해소된 layout face에 metric entry가 없음 |
| 7 | `heuristic` | 최종 advance의 폭 산출원이 heuristic 또는 metric 외 정책임 |

특수문자, cluster continuation, inline object, tab advance처럼 font metric coverage의 대상이 아닌 문자는
억지로 `heuristic`에 넣지 않는다. Stage 1에서 `not-applicable` 분모를 별도로 둘지, 전체 실제 사용 문자
분모 안의 명시적 하위 상태로 둘지 결정한다. 이 결정을 하지 않고 7개 분류 합계 완료 조건을 주장하지
않는다.

`matchKind=boldOnly` 또는 `nameFirst`는 곧바로 face miss가 아니다. 실제 선택된 metric entry와 style
fallback provenance를 함께 보고 exact hit의 하위 교차축으로 집계한다.

## 6. aggregate와 개인정보 계약

### 6.1 저장소에 남길 값

- 입력 형식별 문서·page·문단·문자 수
- parse·layout·join·backend 상태별 aggregate count
- 7개 coverage 분류와 확정된 non-applicable count
- language slot, bold·italic, 장평 bucket, 자간 bucket, 고정 frame, LineSeg 상태별 교차표
- 분류별 layout face aggregate와 W4 후보를 만들 수 있는 비식별 통계
- 도구·schema version, 기준 source commit, 결정론적 aggregate hash
- 반복 실행 간 count·hash 비교와 성능 요약

### 6.2 저장소에 남기지 않을 값

- 문서 원문과 추출 본문
- 파일명·상대/절대 경로·문서별 hash 목록
- 문서별 raw trace 또는 문자 위치 목록
- corpus directory 구조와 기관별 식별 가능한 실패 목록
- host 사용자명, 재배포 불가 font bytes와 로컬 font 경로

collector는 raw record를 메모리상에서 집계한 뒤 폐기한다. 실행 로그도 문서 경로나 원문을 포함하지 않는
요약 모드만 정식 증적으로 사용한다. 원인 진단에 식별 자료가 필요하면 로컬 임시 조사로만 사용하고
커밋 대상과 명시적으로 분리한다.

### 6.3 hash

aggregate hash는 정렬된 schema와 수치만 포함한다. 다음 값은 제외한다.

- 입력 경로와 파일 순회 순서
- timestamp, elapsed time, host·OS·사용자명
- 오류 stack과 원문 파생 문자열
- hash 필드 자체

face·format·language slot·style·조판 bucket의 key ordering을 고정하고 UTF-8 JSON canonical projection에
SHA-256을 적용한다. 같은 corpus와 source commit을 두 번 실행한 aggregate hash가 같아야 한다.

## 8. 수행 단계와 승인 게이트

### Stage 1 — 기존 자산 동결과 분류·분모·privacy 계약 RED

1. 기존 POC v2 schema·totals·usage key와 생성 source를 재사용 기준선으로 동결하고 무결성 검사를
   자동화한다.
2. W1 collector와 validator를 현재 source에서 재실행해 candidate identity, relation, source digest drift를
   비교한다.
3. W2 `widthSource`, `characterMatch`, `matchKind`, provenance relation의 가능한 조합을 inventory한다.
4. 7개 분류 우선순위와 non-applicable 처리, 전체·coverage·join·backend 분모를 machine-readable schema로
   고정한다.
5. 긴 page, source join 실패, parser 실패, unsupported backend와 raw path 유출을 실패시키는 RED test를
   만든다.
6. aggregate canonicalization과 반복 hash golden을 고정한다.

**종료 게이트:** 기존 POC에서 그대로 재사용할 필드와 새로 측정할 delta가 schema로 분리되고, 분류의
중복·누락이 test로 검출되며, W1 의미 drift 여부와 전수 계측 구현 경계가 설명된다. 결과를
`task_m100_4962_stage1.md`에 기록하고 메인테이너 승인 전 Stage 2로 가지 않는다.

**결과:** [Stage 1 기록](../working/task_m100_4962_stage1.md)에 기존 POC 비식별 projection,
W1 digest-only drift, 7개 분류·독립 분모·privacy·hash 계약과 focused 검증을 기록했다. Stage 2는
메인테이너 승인 전 시작하지 않는다.

### Stage 2 — 기존 POC walker를 확장한 decision delta collector

1. commit `631287d47`의 재귀 문단·context walker와 v2 usage key를 기준선으로 재사용한다.
2. W2와 같은 실제 문자 decision을 결합하고 lookup 사다리를 별도로 복제하지 않는다.
3. page 상한 없이 문자를 한 번씩만 streaming 집계하되 raw record를 저장하지 않는다.
4. 기존 usage aggregate에는 decision category와 필요한 provenance 차원만 추가한다.
5. 문단·frame·LineSeg source join을 추가하고 `joined`·`layout-only`·`excluded`를 구분한다.
6. parse·layout·join·분류 count reconciliation과 bounded memory를 검증한다.

**종료 게이트:** 공개 long-page fixture에서 truncation 없이 모든 문자가 한 번만 집계되고, 기존 v2
usage key의 projection이 POC와 일치하며, default renderer와 W2 trace 결과가 변하지 않는다. Stage 2
보고와 승인 뒤 pilot으로 간다.

**결과:** [Stage 2 기록](../working/task_m100_4962_stage2.md)에 기존 POC 재귀 walker·usage key·정렬을
유지한 decision delta collector, 분모 대사, 5,000자 공개 long-page와 W2 무변경 검증을 기록했다.
이후 보안 감사에서 무제한 성공 집계와 무제한 자원 사용을 분리해야 하는 결함을 발견해

코퍼스 실행은 수행하지 않았으며 Stage 3는 메인테이너 승인 전 시작하지 않는다.

### Stage 2-S — 무제한 성공 집계의 자원 고갈 방어

1. CharShape 경계마다 문단 전체를 재검색하는 경로를 단일 UTF-16 위치 병합 순회로 바꾼다.
2. work unit, deadline, cancellation, 중첩 깊이, aggregate row, 출력 byte 예산을 명시한다.
3. 자원 초과와 취소는 partial aggregate 없이 `resource-limit`·`cancelled` 문서 실패로 분리한다.
4. 긴 정상 문서는 상한으로 자른 성공이 아니라, 승인된 예산에서 전수 성공하거나 문서 전체가 실패한다.
5. corpus runner는 문서별 별도 process와 OS timeout·RSS 제한 없이는 실행할 수 없도록 Stage 3 선행
   조건으로 둔다.
6. 긴 문단, 다수 CharShape 경계, 낮은 work·row·output 예산과 사전 취소를 공격형 fixture로 검증한다.

**종료 게이트:** 정상 long-page는 truncation 없이 대사되고, 공격 입력은 전체 process를 고갈시키기 전에
명시적 오류로 종료되며, 부분 결과가 coverage 성공 분모에 섞이지 않는다. corpus worker 격리가 없는
상태에서는 private pilot을 시작하지 않는다.

**결과:** [Stage 2-S 기록](../working/task_m100_4962_stage2_security.md)에 `O(N+R)` 병합 walker,
결정적·시간·취소·중첩·row·output 예산, 실패 상태 확장과 공격형 integration 5건을 기록했다. corpus
worker isolation은 계약상 `required`이며 Stage 3 runner 구현·실행의 첫 번째 hard gate다.

### Stage 3 — 공개 fixture와 private 소규모 pilot

1. 문서별 별도 process, OS timeout·RSS 제한과 비식별 실패 봉투를 가진 corpus supervisor를 먼저
   구현하고 공개 fixture로 강제 종료·고립을 검증한다.
2. 공개 HWP/HWPX fixture로 exact, alias, overlay, surrogate, char miss, face miss, heuristic과

3. 비공개 POC의 local risk ranking과 format·usage aggregate를 이용해 결정론적 소규모 cohort를
   재수집 없이 선정하고 로컬에서만 실행한다.
4. pilot의 기존 projection을 v2 usage·totals와 대조하고 새 decision delta만 별도 비교한다.
5. 두 번 실행해 delta aggregate hash와 모든 count가 일치하는지 확인한다.
6. 처리량, peak memory, parse/layout/join 실패율과 full 10k delta pass 예상 시간을 측정한다.
7. 로그와 산출물에 경로·원문·식별 목록이 없는지 검사한다.

**첫 번째 hard gate 결과:** [Stage 3-I 격리 기록](../working/task_m100_4962_stage3_isolation.md)에

사용했으며 private corpus와 pilot은 실행하지 않았다.

**종료 게이트:** 기존 자료로 답할 수 없는 항목만 새 collector가 채운다는 사실, 전수 delta pass 비용과

뒤 별도 승인을 받아 Stage 4를 실행한다. 정당성이 입증되지 않으면 Stage 4는 취소한다.

### Stage 4 — 승인된 private 10k decision delta pass

1. 동일 source commit·도구·schema로 corpus 전체의 문자별 decision delta를 읽기 전용 실행한다.

5. 첫 실행 비용을 보고한 뒤 승인된 경우에만 동일 delta pass를 한 번 더 실행해 canonical aggregate
   hash를 검증한다.
6. raw trace와 식별 로그가 남지 않았음을 확인하고 비식별 delta aggregate만 저장소 보고서로 옮긴다.

**종료 게이트:** 기존 POC 기준선과 새 decision delta의 책임이 분리되고, 분류 합과 분모가 일치하며,

coverage 비율을 게시하지 않는다.
