# #8153 위·아래 첨자의 실제 Print 글꼴 계약

## 원본·사양·기존 해결 이력

대상은 기존 두 편람이다. HWPX 272쪽의 `charPr 444`는 height 1200HU,
전 언어 장평 98%, 상대 크기 100%, 글자 위치 0과 `supscript`를 저장한다.
해당 HWPX 전체에 실제 사용하는 위·아래 첨자는 이 모양의 `＊` 한 곳뿐이다.
HWP5 사양 설명본 표 35는 bit 15/16의 위·아래 첨자 여부를 정의한다.
첨자의 글꼴 크기·baseline 배율을 수치로 규정하지 않으므로 미확인 배율을
공식 사양의 수치로 부르거나 사양 오류로 정정하지 않는다.

기존 해결은 PR #2771의 통합 커밋 `0a1e6bb294`다. 흩어져 있던 크기 0.7,
상향 0.3em·하향 0.15em과 SVG/Canvas 폭 중복 확대를 공통 함수로 모았고
Native의 누락된 첨자 재생을 연결했다. 기존 문제와 독립 기대값을 보존하면서,
이 상수가 현재 실제 프로그램의 Print 결과와 맞는지 다시 검증한다.

## 확인된 차이와 해석의 한계

현재 표시 함수는 위첨자를 16×0.7=11.2px로 그리고 본문 baseline에서 4.8px
올린다. 독립 PDF의 해당 실제 연산은 600dpi CTM 아래 `Tf 64`, `Tz 98.305084`,
baseline 장치 좌표 (3041,2071)이다. 같은 줄 본문은 `Tf 100`, baseline y=2115다.
PDF texttrace의 `size`만 보고 Tf나 세로 크기를 추측하지 않고 실제 연산을 확인했다.

Windows 공개 GDI를 설치 글꼴 그대로 읽어 3개 face·6개 높이 18조건을 실행했다.
KoPub의 양수 cell 높이 70은 문자 높이 64, 음수 em 높이 -70은 문자 높이 70이다.
한컴바탕은 같은 양수 70에서도 문자 높이가 70이다. 이는 프로그램의 cell/em 차이를
구분해야 한다는 독립 증거지만, 한컴이 실제로 그 API·계산 순서를 썼다는 입증은 아니다.
일치하는 한 수치를 근거로 0.64나 baseline 0.44를 구현 상수로 추가하지 않는다.

## 다음 검증과 구현 경계

원본 두 문서와 기존 PDF는 다시 변환하지 않는다. 원본에는 첨자 반례가 부족하므로
같은 속성의 소형 합성 입력에서 글꼴·크기를 나누고 본문·위첨자·아래첨자를 함께 만든다.
수동 LineSeg를 넣지 않고 실제 한컴 저장 정규화와 독립 Print를 거쳐 각 Tf·Tz·baseline,
글꼴 프로그램과 원본 속성을 대조한다. 자료는 ignored `output/`에만 생성한다.

검증된 값의 생산·측정·배치·최종 paint 소비 지점을 추적한 뒤 공통 첨자 결과를 연결한다.
가시 문자와 관계없는 문서·쪽·글꼴 이름 분기나 수치 맞춤은 추가하지 않는다.
원본·정상 대조군, Native·표준 최적화 fresh WASM, 중요한 경계 회귀를 함께 검증한다.
목표인 두 편람 1,532조건 전쪽 raw 100%·미대응 0과 최종 필수 검증은 그대로 유지한다.
upstream 동기화와 원격 GitHub 쓰기는 하지 않으며 PR 준비까지만 완료한다.

## 실제 정규화·Print의 추가 대조

소형 입력 두 개를 각각 실제 한컴 HWP 저장본으로 정규화하고 `PrintMethod=0`으로
인쇄했다. 첫 입력은 3개 글꼴×900/1200/1800HU의 9쪽, 둘째는 같은 3개 글꼴×
장평 90/100/110%의 9쪽이다. 첫 입력의 장평은 원본과 같은 98%다.
정규화 전 HWPX와 정규화한 HWP 모두 기준 크기·상대 크기 100%·글자 위치 0·
위/아래 첨자 flag를 보존했다. 저장 시 첨자를 작은 일반 글자로 풀어쓴 결과가 아니다.

18조건의 실제 PDF 연산에서 글리프 크기/본문 크기는 0.64, 위첨자 baseline 상향은
본문 대비 0.44, 아래첨자 하향은 0.12였다. 장평을 바꾼 대조에서도 같은 값이며,
예를 들어 본문 Tf 75/100/150에 첨자 Tf 48/64/96이 대응한다. 이 결과는 해당 한컴
2024 실제 Print의 계약이며, 공식 HWP5 문서가 이 숫자를 정의한다는 뜻은 아니다.

GDI 양수 cell 높이 70이 문자 높이 64가 되는 관측은 KoPub의 한 경우와 맞았지만,
한컴바탕의 같은 공개 API 결과는 70인 반면 실제 Print는 64다. 따라서 이 우연한
일치를 일반 첨자 계산식으로 채택하지 않는다. 구현 전에는 기존 공통 첨자 함수의
측정·전진 폭과 실제 paint 소비, 버전·출력 profile 경계 및 뒤의 별도 보정을 추적한다.

자료는 `output/pr-review/issue8153-handbook-raw100-20261022/remaining-raw100-diagnostic/`
아래 `small-residuals/literal-spacing-glyph/native-print-precision/`의
`independent-script-contract-summary.json`, 각 `script-cell-*-controls/`와
`script-cell-controls/`에 있다. 원본 두 편람과 기존 기준 PDF는 변경·재출력하지 않았다.
이 진단 자료는 아직 정식 회귀 fixture나 최종 완료 증거로 등록하지 않았다.

## 공통 결과의 실제 소비와 버전 경계

12pt 대조의 첨자 뒤 본문은 현재 Native에서 PDF보다 첨자 하나당 약 0.7~1.1px
오른쪽으로 전진한다. 끝 본문에서는 누적 약 1.6~2.0px 차이가 난다. glyph 크기만
바꾸면 이 잘못된 전진이 남으므로 다음 연결을 함께 보정한다.

- 생산: `resolve_styles_with_environment`가 문서의 실제 조판 호환 profile을 선택한다.
- 전파: `ResolvedStyleSet → resolved_to_text_style → TextStyle`에 첨자 계약을 전달한다.
- 측정: `text_measurement::style_params`, 문단의 kerning/shaping 경로와 composer의
  scalar style이 같은 `TextStyle`의 첨자 크기를 사용한다.
- 배치·paint: `script_draw_metrics`의 크기·baseline을 Native, Canvas, SVG, HTML,
  paint bounds와 JSON의 장식이 소비한다. 장평·기존 glyph fit은 그 뒤 적용되므로
  Native 집중/전쪽 및 독립 장평 대조에서 중복 배율이 없는지 확인한다.
- CanvasKit의 기존 별도 0.7/0.3/0.15 계산은 Rust가 확정한 크기·baseline 이동을
  JSON으로 받아 소비하게 한다. 브라우저에 새 2024 배율 사본을 추가하지 않는다.

기존 PR #5756의 `156732409` 저장 줄에는 전진 0.7의 독립 근거가 있다. 이 계약을
전역으로 덮어쓰지 않는다. 새 계약은 명시된 2024 호환 profile의 HWP5/HWPX에
한정하며, HWP3 계보와 기존 기본 모드는 종전 계약을 유지한다. 해당 차이는 문서·쪽·
글꼴 이름에 따른 예외가 아닌 실제 버전/원본 조판 계약의 경계다.

호환 모드가 첨자 계약을 바꿀 때에는 이전 조합 결과를 그대로 두지 않고 재조합한다.
기존 큰 source 파일에는 계약 선택·전파·공통 helper 호출만 최소로 연결한다. 수치와
계산은 새 작은 모듈로 모으며, 관련 없는 대규모 파일 분할로 범위를 넓히지 않는다.
