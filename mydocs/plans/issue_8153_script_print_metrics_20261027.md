# #8153 위·아래 첨자의 실제 Print 글꼴 계약

## 원본·사양·기존 해결 이력

대상은 기존 두 편람이다. HWPX 272쪽의 `charPr 444`는 height 1200HU,
전 언어 장평 98%, 상대 크기 100%, 글자 위치 0과 `supscript`를 저장한다.
해당 HWPX 전체에 실제 사용하는 위·아래 첨자는 이 모양의 `＊` 한 곳뿐이다.
HWP5 사양 설명본 표 35는 bit 15/16의 위·아래 첨자 여부를 정의한다.
첨자의 글꼴 크기·baseline 배율을 수치로 규정하지 않으므로 미확인 배율을
공식 사양의 수치로 부르거나 사양 오류로 정정하지 않는다.

기존 해결은 PR #2771의 통합 커밋 `0a1e6bb294`다. 흩어져 있던 크기 0.7,
상향 0.3em·하향 0.15em과 SVG/Canvas 폭 중복 확대를 공통 함수로 모았고
Native의 누락된 첨자 재생을 연결했다. 기존 문제와 독립 기대값을 보존하면서,
이 상수가 현재 실제 프로그램의 Print 결과와 맞는지 다시 검증한다.

## 확인된 차이와 해석의 한계

현재 표시 함수는 위첨자를 16×0.7=11.2px로 그리고 본문 baseline에서 4.8px
올린다. 독립 PDF의 해당 실제 연산은 600dpi CTM 아래 `Tf 64`, `Tz 98.305084`,
baseline 장치 좌표 (3041,2071)이다. 같은 줄 본문은 `Tf 100`, baseline y=2115다.
PDF texttrace의 `size`만 보고 Tf나 세로 크기를 추측하지 않고 실제 연산을 확인했다.

Windows 공개 GDI를 설치 글꼴 그대로 읽어 3개 face·6개 높이 18조건을 실행했다.
KoPub의 양수 cell 높이 70은 문자 높이 64, 음수 em 높이 -70은 문자 높이 70이다.
한컴바탕은 같은 양수 70에서도 문자 높이가 70이다. 이는 프로그램의 cell/em 차이를
구분해야 한다는 독립 증거지만, 한컴이 실제로 그 API·계산 순서를 썼다는 입증은 아니다.
일치하는 한 수치를 근거로 0.64나 baseline 0.44를 구현 상수로 추가하지 않는다.

## 다음 검증과 구현 경계

원본 두 문서와 기존 PDF는 다시 변환하지 않는다. 원본에는 첨자 반례가 부족하므로
같은 속성의 소형 합성 입력에서 글꼴·크기를 나누고 본문·위첨자·아래첨자를 함께 만든다.
수동 LineSeg를 넣지 않고 실제 한컴 저장 정규화와 독립 Print를 거쳐 각 Tf·Tz·baseline,
글꼴 프로그램과 원본 속성을 대조한다. 자료는 ignored `output/`에만 생성한다.

검증된 값의 생산·측정·배치·최종 paint 소비 지점을 추적한 뒤 공통 첨자 결과를 연결한다.
가시 문자와 관계없는 문서·쪽·글꼴 이름 분기나 수치 맞춤은 추가하지 않는다.
원본·정상 대조군, Native·표준 최적화 fresh WASM, 중요한 경계 회귀를 함께 검증한다.
목표인 두 편람 1,532조건 전쪽 raw 100%·미대응 0과 최종 필수 검증은 그대로 유지한다.
upstream 동기화와 원격 GitHub 쓰기는 하지 않으며 PR 준비까지만 완료한다.
