# 문서 확대/축소 앵커와 대칭성 설계

- 대상: `rhwp-studio`
- 승인: 하이브리드 앵커 정책

## 문제

`ViewportManager`의 확대/축소 목표값은 대칭이다. 실제 6쪽 문서에서 쪽 맞춤 배율
`0.5728285077951002`부터 같은 횟수로 확대하고 축소하면 배율은 정확히 원래 값으로
돌아왔다.

그러나 `CanvasView.onZoomChanged`는 세로 스크롤만 보정한다. 확대 중 스크롤 콘텐츠
폭이 `883px`에서 `971px`로 늘어도 `scrollLeft`가 `0`에 남아 페이지 중심이 약
`44px` 오른쪽으로 이동했다. 세로 방향도 쪽 맞춤 여백과 가상 스크롤 간격이 달라
왕복 후 `scrollTop`에 `1px` 오차가 남았다. 사용자가 느낀 비대칭은 배율 목표값이
아니라 이 레이아웃 이동에서 발생한다.

## 목표

- Ctrl/Cmd+휠 확대/축소는 포인터 아래의 문서 지점을 유지한다.
- 상태 표시줄 버튼과 키보드 확대/축소는 뷰포트 중심 아래의 문서 지점을 유지한다.
- 쪽 맞춤 상태에서 확대를 시작해도 페이지가 가로 중심에서 밀리지 않는다.
- 반대 방향의 같은 입력은 배율과 스크롤 위치를 허용 오차 안에서 복원한다.
- 기존 `22ms` 완화 시간, `0.0042` 휠 민감도, 애니메이션 중 CSS 미리보기와
  정착 후 재렌더링 구조를 유지한다.

## 선택한 설계

### 명시적 확대/축소 앵커

`ViewportManager`에 뷰포트 기준 정규화 좌표를 나타내는 확대/축소 앵커를 둔다.
`smoothZoomTo`와 `smoothZoomBy`는 선택적으로 앵커를 받고, 각
`zoom-changed` 이벤트에 현재 앵커를 함께 전달한다.

- Ctrl/Cmd+휠: 컨테이너 경계 안의 포인터 좌표를 `0..1`로 정규화해 전달한다.
- 버튼·키보드·메뉴: 앵커를 생략해 기본값 `(0.5, 0.5)`를 사용한다.
- 연속 휠 입력: 가장 최근 입력의 포인터 앵커를 같은 애니메이션 흐름에 반영한다.
- 즉시 배율 변경: 기본 중심 앵커를 사용한다.

암묵적인 마지막 포인터 전역 상태는 두지 않는다. 버튼 입력이 오래된 포인터 위치를
재사용하지 않도록 확대/축소 요청 자체가 앵커를 소유한다.
이 문서에서 버튼·키보드의 “보이는 페이지 중심”은 페이지 사각형의 기하학적 중심이
아니라 현재 뷰포트 중심 아래에 놓인 문서 지점을 뜻한다.

### 두 축의 문서 지점 보존

`CanvasView.onZoomChanged`는 레이아웃 재계산 전에 앵커 아래의 쪽과 쪽 내부 비율을
X/Y 양쪽에서 구한다. 레이아웃 재계산 뒤 같은 쪽 내부 비율이 같은 뷰포트 좌표에
오도록 `scrollLeft`와 `scrollTop`을 함께 보정한다.

단일 열에서 페이지가 뷰포트보다 좁으면 CSS 자동 여백을 포함한 실제 레이아웃 폭을
사용한다. 페이지가 뷰포트보다 넓어지는 경계를 통과해도 페이지 중심이 튀지 않도록
계산 폭은 `max(viewportWidth, totalContentWidth)`로 통일한다. 그리드 모드는 기존
명시적 페이지 `left` 좌표를 사용한다.

브라우저가 문서 가장자리에서 스크롤 값을 제한하는 동작은 유지한다. 제한되지 않은
구간에서는 같은 확대/축소 입력의 왕복 오차를 `1px` 이하로 제한한다.

### 쪽 맞춤 여백 정합

현재 쪽 맞춤은 세로에서 `40px`을 빼지만 `VirtualScroll`의 첫 페이지 위·아래
간격 합은 `20px`이다. 세로 쪽 맞춤 계산을 실제 간격 합과 맞춰 세로 중심이
뷰포트 중심과 일치하게 한다. 가로 계산은 `scrollContent`가 사용하는 좌우
`20px`씩의 총 `40px` 여백을 유지한다.

상태 표시줄 경로와 보기 메뉴 command 경로가 같은 계산을 사용하도록 두 진입점을
동일한 계약으로 갱신한다.

## 데이터 흐름

1. 입력 계층이 목표 배율과 정규화 앵커를 `ViewportManager`에 전달한다.
2. `ViewportManager`가 기존 지수 완화로 배율을 계산하고
   `zoom-changed(zoom, anchor)`를 발생시킨다.
3. `CanvasView`가 이전 레이아웃에서 앵커의 쪽 내부 X/Y 비율을 구한다.
4. `VirtualScroll`이 새 배율로 페이지 폭, 높이, 오프셋을 계산한다.
5. `CanvasView`가 새 레이아웃의 같은 문서 지점으로 두 스크롤 축을 보정한다.
6. 애니메이션 중에는 기존 canvas를 CSS로 확대/축소하고, 정착 프레임에서 한 번
   다시 렌더링한다.

## 범위와 오류 처리

- 최소·최대 배율, 휠 delta 정규화와 제한값은 변경하지 않는다.
- 페이지가 없으면 기존처럼 확대/축소 레이아웃 처리를 생략한다.
- 잘못된 앵커 좌표는 `0..1`로 제한하고 숫자가 아니면 뷰포트 중심으로 대체한다.
- 브라우저 스크롤 제한 때문에 문서 가장자리에서 완전한 앵커 보존이 불가능하면
  유효한 스크롤 범위로 제한한다.
- 관련 없는 toolbar, Subsecond, 입력 지연 작업은 수정하거나 커밋하지 않는다.

## 검증

1. `ViewportManager` 집중 테스트에서 휠 포인터 앵커 전달, 기본 중심 앵커,
   같은 휠 delta의 왕복 배율 대칭성을 검증한다.
2. `CanvasView` 회귀 테스트에서 가로·세로 스크롤 보정과 두 축 앵커 전달 계약을
   검증한다.
3. 쪽 맞춤 계산이 세로 실제 간격 합 `20px`을 사용하고 두 명령 경로가 일치하는지
   검증한다.
4. 집중 테스트, TypeScript/Vite production build와 `git diff --check`를 실행한다.
5. 실제 `biz_plan.hwp`에서 다음을 측정한다.
   - 쪽 맞춤 페이지 중심과 뷰포트 중심의 오차
   - 쪽 맞춤에서 가로 overflow 경계를 넘는 확대 시 페이지 중심 이동량
   - 뷰포트 중심이 아닌 임의 지점에서 휠 확대/축소할 때 앵커 이동량
   - 같은 확대/축소 입력 왕복 뒤 배율과 `scrollLeft`/`scrollTop` 오차
   - 애니메이션 중 재렌더링 없음과 정착 후 최종 렌더링
