# 뷰포트 경계와 무관한 확대/축소 의미 설계

- 대상: `rhwp-studio`
- 승인: 추가 질문 없이 빠르게 구현하라는 작업지시자 위임

## 목표

문서가 뷰포트보다 좁은 상태와 넓은 상태 사이를 오가더라도 확대/축소의 기준점 의미를
바꾸지 않는다. Ctrl/Cmd+휠은 포인터 아래의 문서 좌표를 계속 보존하고, 도구 모음과
키보드는 뷰포트 중심 아래의 문서 좌표를 계속 보존한다.

동시에 승인된 반응성 조정값을 적용한다.

- 휠 민감도: `0.0042`에서 `0.00525`
- 완화 시간: `22ms`에서 `16ms`

## 원인

현재 포인터 anchor 자체는 확대/축소 전 과정에서 유지된다. 문제는 가로 스크롤이 표현할
수 있는 좌표 범위가 레이아웃 경계에서 달라지는 것이다.

- 문서가 뷰포트보다 좁으면 `scroll-content`와 canvas를 CSS로 가운데 정렬한다.
- 포인터 아래 문서 좌표를 보존하려면 음수 `scrollLeft`가 필요한 경우가 있다.
- 브라우저는 그 값을 `0`으로 clamp하므로 가로 포인터 anchor가 소실된다.
- 문서가 뷰포트보다 넓어지면 같은 계산 결과가 양수 스크롤 범위에 들어오고 포인터
  anchor가 갑자기 적용된다.

실제 `biz_plan.hwp` 측정에서도 fit 상태에서는 포인터 X의 페이지 상대 좌표가
`0.190526`에서 `0.227233`으로 이동하고 `scrollLeft`는 `0`에 고정되었다. 반면 가로
overflow 상태에서는 같은 측정값이 `0.346520`에서 `0.345857`로 유지되며
`scrollLeft`가 `10`에서 `49.5`로 이동했다.

## 검토한 접근

### 모든 휠 확대/축소를 가운데 기준으로 변경

구현은 가장 작지만 사용자가 선택한 hybrid 정책을 없앤다. overflow 상태에서도
포인터 아래 문서 좌표를 보존하지 못하므로 채택하지 않는다.

### 경계에서 anchor를 혼합하거나 방향별 민감도를 다르게 적용

경계 근처의 이동은 완화할 수 있지만 입력량과 문서 위치에 따라 의미가 계속 달라진다.
동일한 반대 입력의 roundtrip 계약도 복잡해지므로 채택하지 않는다.

### 안정된 가로 pan 좌표계

선택한 접근이다. 실제 페이지 레이아웃의 양쪽에 각각 한 뷰포트 너비의 논리적 pan
공간을 둔다. DOM `scrollLeft`가 항상 음수가 아닌 값으로 동일한 포인터 anchor를
표현할 수 있으므로 underflow와 overflow가 같은 계산 경로를 사용한다.

## 설계

### VirtualScroll 가로 좌표

단일 열과 그리드 레이아웃을 계산한 뒤 다음 pan 공간을 공통 적용한다.

- 기존 레이아웃 너비를 `baseWidth`라고 한다.
- 각 페이지의 명시적 `left`에 `viewportWidth`를 더한다.
- 전체 너비는 `baseWidth + 2 * viewportWidth`로 만든다.
- 가운데 정렬 위치는 `(totalWidth - viewportWidth) / 2`다.

단일 열에서 쓰던 `-1` sentinel과 CSS `left: 50%` fallback은 실제 뷰포트 레이아웃에서
명시적 페이지 좌표로 정규화한다. 그리드 페이지 좌표에도 같은 inset을 적용한다.

이 좌표계에서는 페이지의 어느 지점을 뷰포트의 어느 X 위치에 놓더라도 필요한
`scrollLeft`가 논리적 스크롤 범위 안에 남는다. 따라서 기존
`calculateAnchoredScroll` 공식을 변경하지 않는다.

### CanvasView 수명주기

- 첫 문서 레이아웃 뒤에는 VirtualScroll이 제공하는 가운데 `scrollLeft`를 적용한다.
- 확대/축소 중에는 기존 순서대로 old page box를 읽고, 레이아웃을 다시 계산하고,
  new page box로 anchored scroll을 계산한다.
- 뷰포트 너비 변경 시에는 이전 중심 아래 문서 좌표를 새 중심에 다시 배치한다.
- animation frame 동안 기존 canvas CSS preview를 유지하고, 정착 뒤에만 다시 렌더링한다.

### 좌표 소비자

canvas, overlay, caret, field marker, hit testing은 VirtualScroll의 명시적 페이지 X를
공통 사용한다. 가로 눈금자도 별도의 `margin: auto` 추정식을 사용하지 않고 같은
페이지 X에서 `scrollLeft`를 빼서 화면 좌표를 얻는다.

### 입력 반응성

`ViewportManager`의 지수형 배율 계산과 방향 대칭은 유지한다.

- `WHEEL_ZOOM_SENSITIVITY = 0.00525`
- `ZOOM_SMOOTHING_TIME_MS = 16`
- 버튼과 키보드의 `0.1` 목표 단계는 유지
- 최소 `0.25`, 최대 `4.0`, wheel delta clamp `120px` 유지

`deltaY = -30`인 확대 입력은 100%에서 약 117.1%를 목표로 한다. `deltaY = 1`인
입력 8회는 100%에서 약 95.89%를 목표로 한다.

## 데이터 흐름

```text
휠 입력(pointer anchor)
-> ViewportManager(대칭 지수 배율과 16ms 완화)
-> CanvasView(old page-local anchor 계산)
-> VirtualScroll(동일한 pan 좌표계로 새 레이아웃 계산)
-> calculateAnchoredScroll
-> 유효한 양수 scrollLeft
-> 같은 page-local anchor로 CSS preview와 최종 렌더
```

도구 모음과 키보드는 같은 흐름에 viewport-center anchor를 넣는다.

## 검증

1. VirtualScroll 단위 테스트에서 underflow와 overflow 모두 페이지가 초기 중앙에
   배치되고 양쪽 pan 범위가 존재하는지 확인한다.
2. 포인터 anchor가 underflow에서 overflow를 가로질러도 계산된 `scrollLeft`가
   유효 범위 안에 있고 반대 입력으로 복원되는지 확인한다.
3. CanvasView가 첫 레이아웃과 viewport resize에서 같은 중심 문서 좌표를 유지하는지
   회귀 테스트로 고정한다.
4. 가로 눈금자가 VirtualScroll 페이지 X를 사용하는지 확인한다.
5. 민감도 테스트에서 8픽셀 입력의 최종 배율이 `0.96`보다 작고 16ms 완화가 목표에
   더 빨리 정착하는지 확인한다.
6. 전체 Node 테스트, production build, `git diff --check`를 통과시킨다.
7. 실제 브라우저의 `biz_plan.hwp`에서 포인터 `(0.25, 0.75)`로 fit 이하에서 overflow
   이상까지 확대하고 다시 축소한다.
   - 모든 중간 frame의 page-local anchor drift: 문서 좌표 기준 `1px` 이하
   - 최종 zoom 오차: `1e-12` 이하
   - 최종 scroll 오차: `1px` 이하
   - animation 중 page render: `0`
   - 정착 뒤 보이는 페이지 다시 렌더
