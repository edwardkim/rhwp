## 1. 배경과 사용자 관찰

몇몇 공공기관 웹사이트에서 XLSX를 다운로드했는데도 `rhwp-chrome`이 HWP 후보로 오인해
rhwp 뷰어 탭을 자동으로 여는 현상이 보고되었다. 다운로드 파일 자체는 `.xlsx`로 남지만,
사용자가 요청하지 않은 탭과 원본 URL 재요청, 뒤이은 HWPX 파싱 오류가 발생할 수 있다.

현재 기준선에서 다음 두 원인을 재현했다.

1. `shouldInterceptDownload()`이 `filename`, `url`, `finalUrl`, `mime`의 양성 신호를 무조건
   OR로 결합한다. 확정 파일명과 MIME이 XLSX여도 URL 하나가 `.hwp`이면 자동 열기를 승인한다.
2. XLSX와 HWPX가 모두 ZIP인 상황에서 Studio와 Rust 포맷 감지가 ZIP 매직만으로 HWPX 후보를
   수용한다. XLSX는 원격 바이트 게이트를 통과한 뒤 `Contents/content.hpf` 누락으로 늦게 실패한다.

격리 packaged Chrome 실험에서는 XLSX 파일명·MIME을 가진 같은 ZIP 계열 응답에 대해 URL이
`normal.xlsx`이면 뷰어 탭 0개, `misleading.hwp`이면 뷰어 탭 1개가 생성되었다.

## 2. 작업의 본연 목적

이 작업의 1차 목적은 **공공기관의 불완전하거나 상충하는 다운로드 메타데이터 때문에 XLSX가
rhwp 자동 열기 대상으로 승격되지 않게 하는 것**이다. 사이트별 블랙리스트를 늘리거나 XLSX를
rhwp에서 지원하는 것이 목적이 아니다.

2차 목적은 자동 열기 오탐이 뷰어까지 도달하더라도 일반 OOXML ZIP을 HWPX로 확정하지 않는
방어 계층을 마련하는 것이다. 두 목적은 각각 다운로드 의도 판정과 실제 바이트 형식 판정이므로
한 함수에 합치지 않는다.

## 3. 범위

### 포함

- Chrome/Firefox 공유 다운로드 판정을 단순 boolean에서 근거가 있는 결정으로 정리
- 확정 HWP 파일명, 확정 비-HWP 파일명, 구체 MIME, URL/finalUrl 힌트의 우선순위 확정
- `onCreated`의 저신뢰 후보 보류와 `onChanged` 확정 메타데이터 재판정
- XLSX/OOXML ZIP과 HWPX 패키지의 구조적 구별
- 공유 판정 단위 테스트, Chrome 상태 머신 테스트, packaged extension E2E
- 추적된 HWPX 표본에 대한 구조 게이트 호환성 감사
- 실제 공공기관 응답을 확보할 수 있을 때 비식별 메타데이터 증적 추가

### 제외

- XLS/XLSX 열기·변환·미리보기 기능
- 공공기관별 URL 블랙리스트의 무분별한 추가
- 인증·POST·세션 의존 다운로드를 GET으로 완전히 재현하는 기능
- 브라우저 스토어 버전 증가와 배포
- Safari `downloads` API 경로 추가 — Safari에는 해당 API가 없다
- 사용자 다운로드 파일 내용이나 세션 토큰의 공개 저장

## 4. 판정 정책 초안

구체 구현은 별도 구현계획서에서 확정하되, 정책 우선순위는 다음과 같이 둔다.

1. `NON_REFETCHABLE_PATTERNS` 일치: **무조건 무시**
2. 확정 파일명이 `.hwp/.hwpx/.hml`: **HWP 후보 확정**
3. 확정 파일명이 `.xlsx/.xls/.docx/.pptx/.pdf/.zip` 등 알려진 비-HWP 형식:
   **자동 열기 거부**
4. 파일명이 확정되지 않았고 구체적인 비-HWP MIME이 있음: **자동 열기 거부 또는 확정 시점까지 보류**
5. HWP MIME 또는 HWP URL/finalUrl만 있음: `onCreated`에서는 **보류**, filename이나 terminal
   상태가 확인된 `onChanged`에서 다시 판정
6. 끝까지 확장자 없는 파일이지만 HWP MIME/URL 증거가 유지됨: #198 호환 범위에서 **HWP 후보 확정**

확정 `.hwp` 파일명은 공공기관의 부정확한 generic MIME 때문에 거부하지 않는다. 반대로 확정
`.xlsx` 파일명은 URL에 남은 `.hwp` 문자열이나 잘못된 HWP MIME보다 우선한다. 자동 열기는
보수적으로 거부해도 브라우저의 정상 다운로드는 계속되므로 데이터 접근을 막지 않는다.

## 5. 보호 불변식

1. **일반 다운로드 무간섭**: `onDeterminingFilename`을 다시 등록하거나 `suggest()`에 참여하지 않는다.
2. **확정 HWP 보존**: `.hwp/.hwpx/.hml` 파일명 다운로드의 기본 자동 열기는 유지한다.
3. **확장자 없는 HWP 보존**: #198에서 도입한 URL/MIME 보조 감지를 삭제하지 않는다.
4. **과거 항목 차단**: #1498/#1515의 신선도 상태 머신과 `onCreated` 관측 전제는 유지한다.
5. **중복 탭 차단**: download id당 탭 1개와 in-flight 선점 계약을 유지한다.
6. **설정 fail-closed**: `autoOpen=false`, sync read 실패, 근거 없는 partial sync에서는 탭을 열지 않는다.
7. **로컬 파일 계약**: 진짜 `file://` HWP의 open + cancel/erase best-effort만 유지하고 XLSX에는 적용하지 않는다.
8. **DEXT5 계약**: 재요청 불가 핸들러 블랙리스트는 자동 열기보다 우선한다.
9. **브라우저 공통성**: 공유 판정 정책은 Chrome과 Firefox에서 동일하고 이벤트 adapter만 분리한다.
10. **형식 정직성**: ZIP 컨테이너라는 이유만으로 공개적으로 HWPX라고 확정하지 않는다.

## 6. 단계별 수행 계획

### Stage 1 — 증적 고정과 red 계약

- 현재 boolean 판정의 신호 조합을 결정표로 고정한다.
- 정상 XLSX, HWP URL + XLSX filename/MIME, HWP MIME + XLSX filename, redirect 충돌,
  filename 지연 확정 시나리오를 failing test로 만든다.
- packaged Chrome에서 정상 XLSX는 탭 0개, 충돌 XLSX도 탭 0개가 되어야 하는 E2E 계약을 설계한다.
- 실제 공공기관 응답을 제공받거나 공개적으로 재현할 수 있으면 도메인·토큰을 제거한
  `filename/url path shape/finalUrl path shape/mime/event order`만 집계한다.
- 이 단계에서는 제품 코드를 바꾸지 않는다.

### Stage 2 — 다운로드 근거 판정과 이벤트 adapter 정정

- 공유 모듈에 `intercept/defer/ignore`와 판정 근거를 반환하는 순수 결정 표면을 둔다.
- 기존 `shouldInterceptDownload()` 호환 표면의 유지 또는 제거 범위를 구현계획서에서 결정한다.
- Chrome/Firefox adapter가 `onCreated` 저신뢰 후보를 추적만 하고, `onChanged` 확정 시점에 재판정하게 한다.
- 확정 비-HWP 파일명이 URL/MIME 단독 HWP 힌트를 이기는 규칙을 적용한다.
- 기존 상태 저장·terminal cleanup·동시 이벤트 방어를 변경 전후 같은 테스트로 교차검증한다.

### Stage 3 — HWPX 구조 판정 방어

- 추적된 실제 HWPX 표본의 필수 ZIP 엔트리 분포를 먼저 감사한다.
- 평문·비밀번호 보호 HWPX와 rhwp 산출 HWPX가 제공하는 안정적인 구조 신호를 확정한다.
- XLSX의 `[Content_Types].xml`, `xl/workbook.xml`과 HWPX의 `Contents/content.hpf`,
  `Contents/header.xml`을 구별하는 최소 bounded 검사를 설계한다.
- Studio 원격 바이트 게이트와 Rust `detect_format()` 중 어느 계층이 후보/확정을 소유하는지
  구현계획서에서 단일 책임으로 정한다.
- 일반 ZIP/XLSX는 HWPX 내부 파서의 `MissingFile`까지 들어가기 전에 명확한 비지원 형식으로 거부한다.

### Stage 4 — 집중 회귀와 실제 브라우저 교차검증

- 공유 모듈, observer state, Chrome/Firefox interceptor 테스트를 실행한다.
- Chrome/Firefox 확장 빌드와 dist 계약을 확인한다.
- 격리 Chrome 프로필에서 정상 XLSX, 충돌 XLSX, 확정 HWP, 확장자 없는 HWP를 실제 다운로드한다.
- 탭 수, 다운로드 보존, 재요청 횟수, 오류 메시지와 download id당 1회 불변식을 확인한다.
- HWPX 구조 판정을 바꾸면 Rust native/WASM lint와 관련 파서 테스트를 추가로 통과시킨다.

### Stage 5 — 결과 정산과 PR 준비

- 계획 대비 결과, 실사이트 증적 확보 여부, 잔여 위험을 최종 보고서에 기록한다.
- 브라우저 확장 개발 가이드의 매직=HWPX 단정이 바뀌면 canonical 설명을 함께 정정한다.
- 변경 범위별 전체 로컬 검증은 별도 승인 후 수행한다.
- 커밋, push, PR 생성은 각각 프로젝트 승인 게이트를 따른다.

## 9. 위험과 완화

| 위험 | 완화 |
| --- | --- |
| XLSX 거부가 확장자 없는 진짜 HWP 감지율을 낮춤 | 확정 비-HWP와 미확정 filename을 구별하고 terminal fallback을 별도 테스트 |
| `onCreated` 보류로 HWP 탭 생성이 늦어짐 | 확정 HWP filename은 즉시 처리하고 저신뢰 URL/MIME 후보만 보류 |
| 잘못된 MIME 때문에 진짜 HWP를 거부 | 확정 HWP filename을 구체 MIME보다 우선하는 비대칭 정책 유지 |
| generic ZIP 판정 강화가 오래된 HWPX를 거부 | tracked HWPX 전수 구조 감사 후 필수 신호를 정하고 암호 HWPX 포함 |
| ZIP 구조 검사가 비용을 늘림 | central directory의 제한된 entry-name 검사만 수행하고 payload 전체 압축 해제 금지 |
| 공공기관 실제 URL이 세션 의존이라 재현 불가 | 공개 가능한 메타데이터 shape만 보존하고 synthetic E2E를 결정론적 계약으로 사용 |
| Chrome/Firefox event 순서 차이 | 순수 결정 표와 브라우저 adapter 테스트를 분리 |

## 10. 완료 조건

- #6534 본문의 XLSX 충돌 조합이 자동 열기 탭 0개로 고정된다.

- Chrome과 Firefox의 공유 정책·adapter 테스트 및 packaged Chrome E2E가 통과한다.
- 수행 결과와 실사이트 증적 한계를 최종 보고서에 명시한다.
