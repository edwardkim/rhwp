## 문제와 관측

기존 `hash:m/8` default-feature test는 실행 건수가 비슷해도 `overflow_cell_lines_do_not_grow` 등
장기 테스트가 한 shard에 몰려 10.331~168.457초의 큰 편차를 보였다. slow target을 전용 archive로
분리한 뒤에는 full archive 반복 전송도 binary-affine archive로 해소했다.

최신 실행에서는 worker별 archive download가 약 4초로 충분히 작았다. 그러나 builder A가
`slow`·`1`~`3`, builder B가 `4`~`7`을 만든 뒤 실행 worker를 네 개만 쓰도록 바꾸려면, `4`~`7`은
실행되지 않는 target compile과 upload만 남긴다. 기준 실행의 builder B는 7분 33초, slow worker는
2분 42초였고 slow worker가 B까지 기다린 구조도 임계 경로를 길게 만들었다.

## 최종 구현 계획

1. `cargo metadata --no-deps` planner는 `slow`, `1`, `2`, `3` 네 archive만 만든다. slow target은
   `overflow_cell_baseline` 하나이고, 나머지 test-enabled Cargo target은 일반 세 archive에 독점 배정한다.
2. builder job은 slow+`2`, regular `1`, regular `3`의 세 개다. 각 job은 자신의 selector만 compile하고
   자기 archive만 upload한다. regular target은 세 archive에 직접 source-balanced 배정해 build load를
   균형화한다.
3. test worker는 slow, `1/3`, `2/3`, `3/3`의 네 개다. 각각 자신의 archive 한 개만 download한다.
   slow와 `2/3`은 slow+`2` builder와 Native Skia만 기다리고, `1/3`·`3/3`은 각자 builder 완료와
   독립적으로 시작한다.
4. `Build & Test`는 archive expected count 4개와 worker run count 4개의 합계를 대조하고, 세 builder와
   네 worker의 성공을 각각 확인한다.
5. 네 worker는 독립 job이며 다른 worker 실패를 기다리지 않고 자신의 결과를 집계 job에 전달한다.

## 수용 기준

- `test-archive-slow`, `test-archive-1`, `test-archive-2`, `test-archive-3` 외 archive를 만들거나
  download하지 않는다.
- target selector에 중복·누락이 없고 각 일반 archive target 수 차이는 최대 1이다. regular builder별
  target 수는 약 150개다.
- expected/run count artifact가 각각 네 개이며 합계가 일치한다.
- Native Skia 실패 시 네 test worker 모두 실행되지 않는다.
- 최신 PR CI가 성공하고, builder/worker 시간과 전체 임계 경로를 기준 실행 14분 52초와 비교해 기록한다.
