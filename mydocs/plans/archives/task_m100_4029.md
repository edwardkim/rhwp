- **연계 이슈**: [#3790](https://github.com/edwardkim/rhwp/issues/3790), [#4080](https://github.com/edwardkim/rhwp/issues/4080)

## 1. 문제와 재현 경계

다음 조합에서 default-feature nextest archive builder가 30분 상한에 도달해 취소된다.

- `release` profile의 LTO·단일 codegen unit
- `test-archive` Rust cache miss
- 전체 default-feature test target compile/link
- builder `timeout-minutes: 30`

기존 수동 full run `30904172203`과 실제 main push run `30863866920`이 같은 증상을 보였다.
#3790 Stage 5B canary의 같은 SHA 수동 full run `31474843602`에서도 archive builder 세 개가
모두 cache miss 뒤 약 30분에 취소됐다. timeout 전에 cache 저장 단계에 도달하지 못하므로 실제
main cold run은 다음 실행도 cold 상태로 반복될 수 있다.

## 2. 목표

1. 일반 PR·`devel`·비릴리즈 수동 full은 `release-test`로 빠른 전체 회귀를 수행한다.
2. `main`·tag·명시적 release-grade 수동 full은 `release` 의미를 유지하면서 cold build를 완주한다.
3. required check `Build & Test`와 archive builder/worker 이름을 유지한다.
4. event, ref, 선택 profile, timeout, cache exact-hit 여부를 job summary에서 확인할 수 있게 한다.
5. 실제 배포 artifact의 `cargo build --release`와 WASM release 계약은 변경하지 않는다.
6. cache miss 뒤 main push가 완주해 기존 save 정책으로 cache를 다시 만들 수 있게 한다.

## 3. 실행 정책

| 실행 경로 | CI test profile | archive builder timeout | 의미 |
| --- | --- | ---: | --- |
| pull request | `release-test` | 30분 | 빠른 전체 회귀 |
| `devel` push | `release-test` | 30분 | merge 후 전체 회귀·cache writer |
| 일반 `workflow_dispatch` | `release-test` | 30분 | same-SHA full 비교의 기본값 |
| `main` push | `release` | 60분 | release-grade 회귀·cache writer |
| `v*` tag push | `release` | 60분 | release-grade 회귀 |
| `workflow_dispatch`, `release_grade=true` | `release` | 60분 | 명시적 release-grade 검증 |
| 알 수 없는 경로 | `release` | 60분 | 검증 강도를 낮추지 않는 fail-closed |

60분은 정상 경로의 실행 시간을 늘리는 값이 아니라 hang 판정 상한이다. PR·`devel`·일반 수동
경로는 기존 30분을 유지한다. tag cache는 다른 tag에서 재사용 가치가 낮고 #4080의 ref별 cache
증가를 악화시킬 수 있으므로 cache 저장 범위는 기존 `devel/main push`로 유지한다.

## 4. 범위

### 포함

- `ci.yml`의 수동 `release_grade` 입력과 단일 test profile/archive timeout 라우터
- Native Skia test가 archive builder와 같은 test profile을 소비하는 배선
- 재사용 archive workflow의 명시적 profile/timeout 입력과 허용 조합 검증
- Rust cache exact-hit 및 선택 정책 job summary
- 장기 workflow 계약 테스트와 CI 배선
- focused 검증, PR 후 cold-cache canary 측정

### 제외

- Cargo profile 자체 변경
- 실제 release binary, Node, Python, WASM artifact 생성 방식 변경
- nextest target 배정이나 worker shard topology 변경
- cache 보존량·고아 ref 정리 정책 변경 — #4080에서 계속 추적
- #3790 Stage 5B 선택 실행 성능 판정 변경

## 5. 단계와 게이트

1. **계획 고정**: 이슈 결정 코멘트, 수행·구현 계획, 오늘할일을 같은 브랜치에 기록한다.
2. **RED 계약**: profile 진리표, reusable input, timeout, summary, artifact 불변 계약을 먼저 실패시킨다.
3. **구현**: `ci.yml`이 정책을 한 번 계산하고 세 builder와 Native Skia test에 같은 profile을 전달하게 한다.
4. **focused 검증**: 새 계약, 전체 workflow 계약 배선, `actionlint`, `git diff --check`를 통과한다.
5. **PR canary**: PR 기본 경로가 `release-test/30`인지 확인한다.
6. **수동 canary**: 같은 SHA에서 일반 dispatch `release-test/30`과 `release_grade=true`
   `release/60`을 각각 실행한다. cache miss 여부와 builder/archive/worker 완주 시간을 기록한다.
7. **main 후속**: merge 후 실제 main/tag-equivalent 결과와 main cache 재생성 여부를 확인하고 이슈를 닫는다.

긴 원격 canary와 PR 생성·Draft 해제는 저장소 승인 게이트를 별도로 따른다.

## 6. 완료 조건

- 정책 진리표와 허용 profile/timeout 조합이 계약 테스트로 고정된다.
- cold-cache release-grade canary에서 세 builder와 네 worker가 모두 완료된다.
- 일반 수동 full이 의도치 않게 `release` 비용을 발생시키지 않는다.
- `Build & Test` aggregate/check identity가 유지된다.
- release binary와 WASM release artifact 명령이 그대로다.
- 실행 요약만으로 event/ref/profile/timeout/cache exact-hit를 판독할 수 있다.

## 7. 위험과 롤백

| 위험 | 억제 |
| --- | --- |
| 일반 수동 실행 의미가 불명확해짐 | 기본값을 `release-test`로 명시하고 release-grade는 boolean 입력으로만 선택 |
| main/tag 검증 강도 저하 | 두 경로는 계속 `release`; 실제 artifact 계약도 불변 |
| hang 비용이 60분으로 증가 | release-grade builder에만 적용; 빠른 경로 30분 유지 |
| profile/timeout 전달 불일치 | reusable workflow에서 `release-test:30`, `release:60` 두 조합만 허용 |
| tag cache 누적 | save 정책을 `devel/main push`로 유지 |
| required check pending | job과 aggregate 이름·topology를 변경하지 않음 |

롤백은 `release_grade` 입력과 archive policy output/inputs를 제거하고 기존 event/ref 기반 profile 선택 및
builder 30분 상한으로 되돌린다. release artifact workflow에는 롤백 대상 변경이 없다.
