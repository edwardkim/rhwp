# 구현계획서 — Task M100 #3137

## 1. 목표와 기준선

115쪽 거대 표 셀 fixture의 매 입력에서 exact cursor rect 조회가 stable operation 대부분을
차지한다. #3412의 idle 전체 pagination flush 회귀는 #3462/#3467로 `devel`에서 해소됐으므로,
이 작업은 회귀가 제거된 최신 `upstream/devel`에서 공통 cursor lookup 비용을 독립적으로
측정하고 frame budget에 가깝게 줄이는 것을 목표로 한다.

2026-07-27 fresh fetch 기준 SHA는
`7995786bf466bb9ce444ca2b31a1d933d13ec61b`다. 이 SHA의 production WASM 재계측은 다음과 같다.

| 항목 | HWP p95 | HWPX p95 |
| --- | ---: | ---: |
| stable operation | 48.0ms | 49.2ms |
| cursor query | 47.3ms | 48.6ms |

## 2. Stage 1 — 전용 성능 하네스

기존 `issue-2214-page-local-repaint.test.mjs`는 56번째 셀 flow 경계, resumable pagination,
시각 crop, 삭제·IME·저장·인쇄 barrier의 상시 회귀 게이트로 유지한다. #3137 시간 계측은
별도 진단 하네스로 분리해 #2214의 correctness 계약과 성능 실험을 섞지 않는다.

측정 매트릭스:

- 포맷: HWP, HWPX
- 입력: 영문 `a`, 숫자 `1`, 한글 IME `ㅎ → 하 → 한`
- 요청 입력 간격: 0ms, 80ms, 150ms, 250ms
- 기본 반복: 시나리오별 warm-up 2회, 논리 입력 20회
- 브라우저: Puppeteer가 새 임시 프로필로 실행한 headless Chrome
- 엔진: 최신 checkout에서 새로 빌드한 production WASM

측정 항목:

- deferred mutation
- exact cursor query
- 일반 입력의 `InputHandler.executeOperation`
- raw mutation을 쓰는 IME의 동기 `input` dispatch 전체 시간
- input dispatch부터 두 번째 `requestAnimationFrame`까지
- Long Tasks API entry
- 실제 input start interval
- `flush` / `begin` / `step` 호출 수

산출물:

- 시나리오별 원시 event/sample JSON
- 전체 p50/p95/max와 계약 결과 JSON
- 비교용 TSV

시간 절대값은 머신 의존이므로 기본 실행에서 16.7ms를 hard fail로 만들지 않는다. 대신
frame-budget 충족 여부를 결과에 기록하고, 최적화 뒤 선택적으로 강제할 수 있는 실행 옵션을 둔다.
다음 correctness 계약은 기본 실행에서도 단언한다.

- 원본 포맷과 115쪽 유지
- 입력 종류별 최종 본문·cursor offset 일치
- 측정 sample마다 mutation과 operation 존재
- 대형 문서 동기 pagination flush 0회
- browser page error 없음

완료 결과(2026-07-27):

- `probe-input-perf-issue3137.mjs`와 npm/MANIFEST 배선을 추가했다.
- production WASM과 새 headless Chrome에서 기본 24개 시나리오, 800/800 stable sample을 완주했다.
- `flush/begin/step/getCursorRectInCell`은 전 시나리오 0회였다.
- cursor query p95는 0~80ms cadence에서 약 43~46ms, 150ms에서 약 52~53ms,
  250ms에서 약 63~66ms였다. 역순 실행에서도 같은 관계를 확인했다.
- 상세 결과는 `mydocs/working/task_m100_3137_stage1.md`에 기록했다.

## 3. Stage 2 — Rust 내부 구간 계측

Stage 1 기준선을 고정한 뒤 다음 구간을 분리한다.

1. `find_pages_for_paragraph`
2. page-tree cache hit/miss
3. `build_page_tree_cached`
4. tree traversal
5. `compute_char_positions`

셀 편집 뒤 `invalidate_page_tree_cache_from(0)`와 직후 exact query의 page-tree rebuild가 지배
항이라는 가설을 하위 계측으로 확인한다. Stage 1에는 Rust 공개 API나 제품 동작 변경을 포함하지 않는다.

완료 결과(2026-07-27):

> 아래 Rust breakdown API와 하네스 옵션은 원인 확인을 위한 일회성 연구 계측이다.
> 측정 근거는 보존하되 정리 PR의 런타임·공개 API에서는 제거한다.

- normal API와 분리된 `getCursorRectByPathNearDiagnostic` 및 하네스
  `--cursor-breakdown` 모드를 추가했다.
- 24개 시나리오의 800개 profile에서 page-tree cache miss가 800회, hit가 0회였다.
- 전체 Rust query 누적 시간의 99.86%가 `build_page_tree(0)`이었고,
  traversal exclusive p95는 0.0ms, `compute_char_positions` p95는 0.1ms였다.
- cadence별 build p95는 0/80/150/250ms에서 44.5/44.7/52.7/65.5ms로 증가해
  cursor query 증가를 그대로 설명했다.
- 상세 결과는 `mydocs/working/task_m100_3137_stage2.md`에 기록했다.

## 4. Stage 3 — focused geometry 재사용

내부 계측으로 지배 구간을 확정하면 focused cell/line geometry를 edit revision에 묶어 유지하고,
로컬 reflow가 이미 계산한 줄 위치와 cell/page 원점을 조합한 exact rect를 mutation 결과에서
재사용하는 방향을 우선 검토한다.

다음 경우에는 전체 exact query로 fallback한다.

- 줄 또는 flow 경계 변경
- shadow pagination commit
- 동기 flush
- 편집 대상·서식·셀 경로 변경
- revision 불일치

기존 `getCursorRectByPathNear()`를 mutation 내부에서 그대로 호출하거나 다음 frame으로 옮기는
방식은 47~49ms 비용 또는 long task를 이동할 뿐이므로 우선 구현 후보에서 제외한다.

완료 결과(2026-07-28, PR #3745 review 보완 2026-08-02):

- 최신 `upstream/devel` `6c18949bb39c1fa5026b556ef7308ae99cdcf489` 기준으로 구현했다.
- deferred mutation이 보수적으로 검증한 same-line local x delta와 revision/source/target을 반환하고,
  Studio cursor가 직전 exact rect의 absolute 원점에 one-shot으로 적용한다.
- path·target·revision 불일치, flow 경계, vertical cell, overflow, 동기 flush,
  shadow pagination commit은 기존 exact query로 fallback한다.
- 최종 production WASM의 24개 시나리오, 800개 sample에서 geometry 제공·적용 800/800,
  exact cursor query 0회, stable operation p95 0.7~2.3ms를 확인했다.
- 첫 입력은 원본 `LineSeg` 정규화 때문에 exact fallback하며, 이후 연속 입력부터 fast path를 사용한다.
- #2214의 `flush=0`, boundary `begin=1`, `step=115`, 삭제·IME·저장·인쇄 계약을 HWP/HWPX에서 유지했다.
- 상세 결과는 `mydocs/working/task_m100_3137_stage3.md`에 기록했다.

## 5. Stage 4 — page repaint 잔여 지연

Stage 3 뒤 동기 cursor hot path는 frame budget 안으로 들어왔지만,
`document-page-invalidated` 뒤 첫 animation frame의 page repaint가 전체 page tree를 다시 만든다.
최종 행렬의 `input → 2-rAF` p95는 67.8~85.2ms였다.

다음 단계는 stable same-flow edit의 focused page에서 local render patch 또는 reusable page layer를
검토한다. flow 경계와 shadow pagination commit은 기존 full repaint를 유지하고, 첫 입력의
line-metric 정규화도 별도 안전성 항목으로 다룬다.

완료 결과(2026-07-28):

- 최신 `upstream/devel` `ad16eb45799645ea96f3ef533b24fd07320ec476` 기준으로 구현했다.
- stable horizontal tail edit가 캐시된 focused `TextLine`의 `TextRun`만 교체하고, mutation 결과에
  3px padding을 둔 page-space dirty rect를 반환한다. 조건을 증명하지 못하면 기존 cache
  invalidation과 full repaint를 그대로 사용한다.
- cached page tree를 유지한 중간 행렬에서도 full Canvas replay p95가 17.9~26.1ms,
  `input → 2-rAF` p95가 20.5~31.3ms여서 24개 시나리오 모두 frame budget을 넘었다.
  반면 `PageRenderTree → PageLayerTree` lowering 자체는 평균 HWP 0.183ms, HWPX 0.174ms여서
  남은 지배 항은 브라우저의 전체 Canvas replay로 확정했다.
- 기존 Canvas 크기와 픽셀을 유지한 채 dirty rect만 clip/clear/replay하는 WASM API와 Studio
  one-shot repaint 전달 경로를 추가했다. 같은 frame의 같은 page rect는 합친다. plain
  `TextRun`/`FootnoteMarker`는 `2 × max(line height, font size)`로 확장한 replay envelope가
  clip 밖일 때만 건너뛰고, 독립적인 잉크 범위를 갖는 효과와 editor mark는 fail-closed로
  모두 replay한다.
- production WASM의 24개 시나리오, 800개 sample에서 geometry/page-tree patch/dirty payload
  800/800을 확인했다. frame coalescing 뒤 실제 repaint 713회는 모두 partial이었고 full repaint,
  exact cursor query, long task, `flush/begin/step`은 모두 0회였다.
- PR #3745 review 보정 뒤 page repaint p95는 1.4~1.6ms, `input → 2-rAF` p95는
  8.4~15.6ms로 유지되어
  24/24 시나리오가 16.7ms frame-budget gate를 통과했다.
- 이미지/RawSvg page, 첫 line-metric 정규화, non-tail·복합 text, flow 경계, shadow commit,
  동기 flush, invalid rect·canvas extent·API 실패는 기존 full repaint로 보수적으로 fallback한다.
- #2214의 HWP/HWPX visual crop, raw IME/iOS, boundary `begin=1`, `step=115`, `flush=0`,
  Backspace/Delete, 저장·인쇄 barrier를 유지했다.
- 상세 결과는 `mydocs/working/task_m100_3137_stage4.md`에 기록했다.
