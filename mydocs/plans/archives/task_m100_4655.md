# #4655 수행계획서 — v0.8.4 배포 채널을 v0.8.2 범위로 복원

- **Issue**: [#4655](https://github.com/edwardkim/rhwp/issues/4655)
- **브랜치**: `task_m100_4655`
- **기준 커밋**: `upstream/devel` `193e26b7ffb0`
- **통합 방식**: 작업지시자의 명시적 결정에 따라 PR 없이 메인테이너 권한으로 `devel`에 직접 반영

## 1. 결정

v0.8.4의 배포 채널은 v0.8.2에서 실제 운영하던 범위와 동일하게 유지한다. 신규 배포 채널은
워크플로가 존재하거나 태그가 생성됐다는 이유만으로 활성화하지 않는다. 개발·빌드·설치·업데이트·롤백을
안전하게 검증하고 사용자 영향이 없다는 근거를 확보한 뒤 메인테이너가 명시적으로 채택해야 한다.

## 2. 보존 범위

- GitHub Pages 데모
- GitHub Release 네이티브 CLI 바이너리
- npm `@rhwp/core`, `@rhwp/editor`
- VS Code Marketplace와 Open VSX
- Chrome Web Store, Microsoft Edge Add-ons, Firefox AMO 수동 배포
- 기존 WASM Docker 빌드 환경

## 3. 제거 범위

- GHCR Docker CLI 이미지와 전용 Dockerfile·workflow·테스트
- Python 바인딩과 PyPI wheel/sdist 개발·테스트·게시 경로
- Node 바인딩과 `@rhwp/node` 개발·테스트·게시 경로
- deb/rpm/MSI, cargo-binstall, install.sh/install.ps1, AUR, MCP registry `server.json`
- Scoop/Homebrew/Winget 매니페스트와 갱신 도구
- 릴리스 바이너리를 설치하는 저장소 루트 GitHub Action과 self-test
- 위 경로를 실행하거나 현재 기능으로 안내하는 CI·활성 문서·테스트·버전 정렬 코드

과거 이슈·PR·작업 보고서와 v0.8.3 CHANGELOG는 당시 사실을 보존하는 historical evidence이므로
일괄 삭제하지 않는다. 현재 사용 가능한 경로로 오인하게 만드는 링크와 현재형 서술만 정리한다.

## 4. 단계

| 단계 | 내용 | 게이트 |
| --- | --- | --- |
| 1 | v0.8.2와 현재 devel의 배포 표면·도입 이력 비교 | 보존·제거 목록 확정 |
| 2 | 신규 workflow·패키지·바인딩·설치 자산 제거 | 태그 자동 게시 경로 0 |
| 3 | CI·Cargo metadata·버전 도구·현재 문서 정리 | 실행 가능한 잔존 참조 0 |
| 4 | workflow 계약, 문서 링크, Rust·기존 npm 채널 focused 검증 | 기존 채널 회귀 0 |
| 5 | 결과 기록과 커밋, 로컬 devel 통합 | 작업지시자 확인 뒤 원격 devel push |

## 5. 검증 원칙

- `v*` 태그를 받는 workflow 목록에서 신규 채널이 사라졌는지 기계 검사한다.
- 기존 `npm-publish.yml`, `release-binary.yml`, `deploy-pages.yml`은 삭제하거나 v0.8.2로
  되돌리지 않고 현재의 보안·재실행 보완을 유지한다.
- 삭제된 경로를 참조하는 현재 CI와 active/canonical 문서가 없는지 검사한다.
- Python/Node 바인딩 테스트를 억지로 통과시키는 보정은 하지 않는다. 해당 표면 전체를 제거한다.
- 전체 CI 성격의 장시간 검증은 focused 결과를 먼저 보고한 뒤 작업지시자 승인 게이트를 따른다.

## 6. 원격 산출물 경계

v0.8.3에 이미 게시된 GHCR 이미지와 GitHub Release의 deb/rpm 자산을 이 코드 변경에서 자동 삭제하지
않는다. 원격 패키지 삭제는 복구 가능성과 사용자 영향을 별도로 판단해야 하는 운영 작업이다.
