# Task #3891 수행계획서 — C 표면 계약 가드 (툴체인 없는 범위)

- Issue: [#3891](https://github.com/edwardkim/rhwp/issues/3891) (M100) — [#3664](https://github.com/edwardkim/rhwp/issues/3664) 후속
- 브랜치: `local/task3891` / 착수: 2026-08-03

## 1. 환경 제약이 범위를 정한다

**현재 개발 환경(Linux)에 Swift·.NET 툴체인이 없다**(작업지시자 확인). 이슈가 제시한
3단계 중 검증 가능한 것은 최소 단계뿐이다.

| 단계 | 이 환경에서 |
|---|---|
| **최소 — 소스 가드**(선언 대조) | **가능** ← 채택 |
| 중간 — `swift build`·`dotnet build` | 불가(툴체인 부재) |
| 완전 — 실제 링크 E2E | 불가 |

검증할 수 없는 것을 CI 에 넣지 않는다. 넣어도 "동작한다"고 말할 근거가 없고, 러너에서
처음 도는 것을 확인 없이 배포하는 셈이 된다.

## 2. 착수 실측 — 이미 불일치가 있다

Rust `pub extern "C"` 선언을 권위로 삼아 세 소비자를 대조했다.

| 함수 | Rust | C 헤더 | **C# 래퍼** | Swift |
|---|---|---|---|---|
| `rhwp_export_text` | ✓ | ✓ | ✓ | ✓ |
| `rhwp_export_markdown` | ✓ | ✓ | ✓ | ✓ |
| **`rhwp_read_text`** | ✓ | ✓ | **없음** | ✓ |
| `rhwp_string_free` | ✓ | ✓ | ✓ | ✓ |

**C# 래퍼만 3개를 선언해 `rhwp_read_text` 가 빠져 있다.** 가드가 있었다면 잡혔을
표류이며, 이 이슈가 필요한 이유의 실증이다.

### 대조 대상 위치

- 권위: `bindings/Native/src/lib.rs` — `pub [unsafe] extern "C" fn`
- C 헤더: `bindings/swift/Sources/CRhwpNative/rhwp_native_ffi.h`
- C#: `bindings/csharp/RhwpNative.cs` — `[DllImport]` + `private static extern`
- Swift: `bindings/swift/Sources/Rhwp/*.swift` — C 헤더를 `import CRhwpNative` 로 참조
  (직접 선언하지 않으므로 **헤더 대조로 커버**된다)

## 3. 구현 설계

`tests/ffi_c_surface_contract.rs` — 순수 Rust 테스트(외부 툴체인 불요).

1. `lib.rs` 에서 `pub [unsafe] extern "C" fn` 이름·인자수·반환형을 파싱해 **권위 집합**을 만든다.
2. **C 헤더**의 선언과 대조 — 이름 누락·추가, 인자 개수 불일치를 잡는다.
3. **C# 래퍼**의 `extern` 선언과 대조 — 같은 축.
4. 불일치가 있으면 **어느 소비자에서 무엇이 어긋났는지** 메시지로 지목한다.

### 타입 매핑 규칙 (문서화)

| Rust | C | C# |
|---|---|---|
| `*const c_char` | `const char *` | `byte[]` |
| `*mut c_char` | `char *` | `IntPtr` |
| `i32` | `int` | `int` |
| `()` | `void` | `void` |

정확한 타입 문자열 비교가 아니라 **이 매핑표를 통과한 정규화 형태**로 비교한다.
문자열을 그대로 맞추면 공백·별표 위치 차이로 오탐이 난다.

## 4. 단계 계획

| 단계 | 내용 | 산출물 |
|---|---|---|
| Stage 1 | 가드 테스트 구현 + **현재 불일치(`rhwp_read_text`) 검출 확인** → C# 래퍼 정정 | 구현 + stage1 보고 |
| Stage 2 | red-check — 각 소비자에서 선언을 지우거나 인자를 바꾸면 실패하는지 3축 확인 | stage2 보고 |
| Stage 3 | 검증 — release-test 전체·clippy·fmt | stage3 보고 |
| Stage 4 | 최종 보고 → PR(별도 승인) | 보고서 + PR |

## 5. 검증 기준

1. 가드가 **현재 불일치를 검출**한다(구현 직후 실패 → C# 정정 후 통과).
2. red-check 3축 — 헤더/C#/Rust 어느 쪽을 흔들어도 잡힌다.
3. release-test 전체·clippy·fmt 통과.
4. 외부 툴체인 없이 실행된다(`cargo test` 만으로).

## 6. 위험과 제약

- **소스 가드의 한계를 명시한다.** 선언이 일치해도 **런타임 동작·ABI 호환은 보장하지
  않는다.** 실제 링크·호출 검증은 Swift·.NET 툴체인이 있는 환경(맥북)에서 별도로
  해야 하며, 그 필요성을 보고서와 이슈에 남긴다.
- **파싱 기반이라 형식 변화에 취약하다.** 선언 스타일이 바뀌면 오탐/미탐이 생길 수
  있다. 파싱 실패 시 **조용히 통과하지 말고 실패**시켜, 가드가 죽은 채 통과하는
  #3664 형 함정을 피한다.
- C# 에 `rhwp_read_text` 를 추가하는 것이 맞는지 확인이 필요하다 — 의도적으로 뺀
  것일 수도 있다. Stage 1 에서 판단하고, 의도적 미구현이면 **가드에 명시적 예외**로
  등재하되 사유를 적는다(#3648 의 "미지원 명문화"와 같은 방식).
