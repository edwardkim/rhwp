## 1. 결정과 목표

W6의 목적은 font metric 값을 고치는 것이 아니다. 현재 하나의 46,000여 줄 Rust 파일에 섞인
역사적 생성 데이터, 한컴 실측 overlay와 lookup 코드를 **행동 변화 없이** 분리하고, 600개 항목의
출처와 불확실성을 기계가 검사할 수 있는 계보로 만드는 것이다.

이번 작업은 다음 질문에 답한다.

1. 600개 항목 가운데 어떤 것이 SFNT 생성 경로에 속하고, 어떤 것이 실측·수동 overlay인가?
2. 원본 font bytes가 없는 항목을 exact로 과장하지 않고 `unknown`으로 보존할 수 있는가?
3. 파일을 분리해도 이름·물리 순서·style fallback·모든 저장 폭이 이전과 완전히 같은가?
4. 생성기를 다시 실행해도 core lookup과 overlay를 덮어쓰지 않고 같은 manifest/hash를 얻는가?
5. 후행 W7이 계보가 분리된 입력만 사용해 backend projection을 만들 수 있는가?

## 2. Stage 0 원인 계보와 현 상태

### 2.1 데이터가 섞인 흐름

```text
원본 SFNT/TTC
  → font-metric-gen의 name/cmap/hmtx/head 분석과 Hangul 압축
  → 역사적 FONT_METRICS 생성 스냅샷
  → Windows·오픈소스 font의 사건별 추가
  → #2430 한컴 COM 실측 ASCII 5종을 같은 파일 끝에 수동 합성
  → #4149/#4168 lookup index·관측 계약을 같은 파일 앞부분에 추가
  → 현재: 생성기를 전체 출력하면 뒤의 계보·lookup·overlay를 잃을 수 있는 구조
```

현재 `src/renderer/font_metrics_data.rs`의 선언은 600개 항목이며 W1 기준선은 401개 unique name,
style 분포 regular 383·bold 89·italic 79·bold-italic 49를 기록한다. Git 계보상 항목 수는
582 → 584 → 590 → 595 → 600으로 증가했다.

마지막 5개는 #2430에서 추가한 다음 measured overlay다.

- `HanyangSinMyeongJo`
- `HanyangJungGothic`
- `HanyangKyunMyeongJo`
- `HanyangKyunGothic`
- `HumanMyeongJo`

이 overlay들은 `tools/task2430/measured/ladder_*.tsv`의 한컴 COM 실측 ASCII와 median-ratio
보간을 사용하고, 나머지 Latin 범위와 Hangul 압축 데이터는 대응 HY 항목을 공유한다.
`tools/task2430/gen_metrics.py --verify`가 현재 배열과 측정 자료의 동일성을 검사한다.

### 2.2 `generated`와 `exact`를 분리하는 이유

앞의 595개가 역사적으로 생성기 영역에 있었다는 사실은 확인되지만, 저장소에는 대부분의 원본 font
bytes와 당시 실행 manifest가 없다. 따라서 다음 두 명제는 서로 다르다.

- **생성 경로가 확인됨**: 기존 생성 스냅샷 또는 해당 변경 commit으로 계보를 설명할 수 있다.
- **source-exact가 검증됨**: source digest·face index·name record와 생성 결과를 현재 재검산할 수 있다.

W6는 첫 번째를 두 번째로 자동 승격하지 않는다. 항목은 물리적으로 generated 영역에 있더라도
manifest의 provenance 상태가 `unknown`일 수 있다. 확인할 수 없는 source digest, face index,
license, naming record와 compression error는 빈칸이나 추정값 대신 상태와 사유를 가진 `unknown`으로
남긴다.

### 2.3 현재 생성기의 위험

`src/tools/font_metric_gen.rs`는 현재 다음 한계가 있다.

- 디렉터리 입력을 파일명으로 정렬하고 `(family, bold, italic)`을 dedupe한 뒤 다시 순서를 구성한다.
- TTC face를 순회하지만 선택된 face index를 산출물에 기록하지 않는다.
- Hangul 압축 오차를 계산하지만 manifest로 내보내지 않는다.
- source digest, 전체 naming record, license/provenance를 기록하지 않는다.
- 데이터 조각만이 아니라 `font_metrics_data.rs` 전체와 과거형 lookup까지 다시 쓴다.

따라서 W6에서 기존 600개를 원본 font 디렉터리로 재생성하지 않는다. 먼저 기존 행동을 동결하고,
생성기의 출력 소유권을 generated 영역으로 제한한 뒤 확인 가능한 source만 별도 검산한다.

포함한다.

## 5. 목표 구조

구현 단계에서 최종 경로는 Rust module 가시성과 기존 소비자 정합성을 확인해 확정하되, 역할은 다음
세 영역으로 고정한다.

```text
font_metrics_data.rs                 core type·get_width·alias·lookup/index
font metric generated data          기존 0..594 생성 스냅샷과 생성기 소유 영역
font metric overlay data            기존 595..599 measured/manual 합성 영역
font metric lineage manifest        0..599 composition·provenance·evidence 정본
```

Rust runtime은 `generated → overlay` 순서의 단일 논리 iterator를 사용한다. 분리 과정에서 원소를
복사해 새 정렬 배열을 만들거나 name/style key로 dedupe하지 않는다. `entry_index`는 이 iterator의
순번이며 기존 index와 같아야 한다.

W1 수집기는 더 이상 `static FONT_METRICS:`라는 한 파일의 우연한 source shape에 의존하지 않는다.
W6의 deterministic composition reader 또는 manifest를 통해 같은 600행을 읽고, manifest와 Rust
fragment가 불일치하면 fail-closed한다. W7 전까지 lineage manifest를 runtime policy registry로
사용하지는 않는다.

## 6. lineage manifest 계약

각 항목은 최소 다음 정보를 가진다.

```text
entryId, currentIndex
metricIdentity { name, bold, italic, emSize }
storageRegion { kind, sourcePath, symbol }
origin { kind, status, reason }
fontSource { sha256, faceIndex, namingRecords[], license, provenance }
measurementSource { method, inputDigests[], interpolation, evidence[] }
composition { latinRangeSources[], hangulSource }
compression { algorithm, maxAbsoluteError, averageAbsoluteError, status, reason }
relations[] { w1RuleId, relationType, evidence[] }
oracleProfiles[] { issue, profileId, digest, relation }
semanticHashes { metric, widths }
```

필드에 값이 없을 수는 있지만 이유 없는 `null`이나 빈 문자열은 허용하지 않는다. 각 optional evidence는
`verified`, `historical`, `inferred`, `unknown`, `not-applicable` 중 하나의 상태와 근거를 가진다.
W5 profile은 해당 metric이 exact라는 증명으로 자동 사용하지 않고, profile이 실제로 관찰한 relation만
연결한다.

안정 ID는 현재 index를 의미에 포함하지 않는다. `currentIndex`는 W6에서 동결한 composition 좌표이고,
이름·style·source evidence가 같은지를 별도 검사한다. 같은 이름의 중복 항목도 삭제하거나 합치지 않는다.

## 7. 결정론적 hash 계약

machine-readable 산출물은 정렬 규칙, UTF-8, 줄바꿈과 마지막 newline을 고정하고 wall-clock,
절대 경로, 사용자명 같은 실행 변수를 제외한다.

| hash | 입력 |
| --- | --- |
| `manifestSha256` | canonical 600행 lineage manifest |
| `compositionSha256` | index·name·style·em·range symbol·Hangul source 순서 |
| `metricDataSha256` | 모든 range table·Hangul group/map/width raw data |
| `widthProjectionSha256` | 600개 항목의 모든 data-bearing codepoint별 `Option<u16>` |
| `lookupProjectionSha256` | 모든 metric 이름·alias 이름·미등록 sentinel × 4 style의 선택 index와 fallback |

도구는 `--check`에서 저장된 hash를 재계산하며, `--generate`는 의도한 manifest 갱신 단계에서만 쓴다.
연속 두 번 생성한 결과의 파일 hash가 같지 않으면 다음 단계로 넘어가지 않는다.

## 8. 단계별 수행

### Stage W6-1 — 분리 전 행동 기준선 동결

- 현재 600개 source projection과 W1 baseline을 교차 검사한다.
- 모든 data-bearing 문자 폭, lookup selection, bold fallback의 deterministic projection/hash를 만든다.
- #2430 `gen_metrics.py --verify`로 5개 overlay의 측정 원문 정합성을 다시 확인한다.
- 기준선 도구와 negative fixture가 순서 변경·누락·폭 1단위 변경을 실제로 거부하는지 검증한다.
- `mydocs/working/task_m100_4964_w6_stage1.md`에 입력 digest와 결과를 기록한다.

**중지 조건**: W1의 600행/401명 통계나 #2430 실측 배열이 현재 source와 다르면 분리하지 않고 원인을
먼저 보고한다.

### Stage W6-2 — manifest schema·계보 inventory

- 600개 모두에 안정 entry ID와 provenance 상태를 부여한다.
- Git commit 계보, tracked font, #2430 측정 evidence, W1 ledger, W5 profile을 연결한다.
- source-exact를 재현할 수 없는 generated 항목은 `unknown`으로 남긴다.
- font digest와 measurement input digest를 혼동하지 않고 별도 필드로 둔다.
- schema와 validator의 누락·잘못된 exact 승격·깨진 evidence anchor negative test를 만든다.
- `mydocs/working/task_m100_4964_w6_stage2.md`에 확인/미확인 분모를 모두 보고한다.

**중지 조건**: 600개 가운데 manifest에 대응하지 않는 항목이 하나라도 있으면 물리 분리를 시작하지
않는다.

### Stage W6-3 — data-only 물리 분리

- core type·alias·lookup/index와 metric data를 분리한다.
- 기존 0..594 generated snapshot과 595..599 overlay를 별도 source 영역으로 옮긴다.
- overlay가 공유하는 HY Latin/Hangul source edge를 명시하되 숫자는 바꾸지 않는다.
- 논리 composition iterator가 기존 index를 그대로 내도록 구현한다.
- W1 collector를 새 composition 경계에 맞추고 기존 ledger projection이 동일한지 검사한다.
- Stage W6-1의 composition·metric·width·lookup hash가 모두 그대로인지 확인한다.
- `mydocs/working/task_m100_4964_w6_stage3.md`에 이동 전후 hash를 기록한다.

**중지 조건**: fmt를 제외한 대규모 숫자 diff, sort/dedupe, entry index 또는 hash 변화가 있으면 해당
절편을 폐기하고 원인을 분리한다.

### Stage W6-4 — 생성기 소유권·metadata 보강

- `font-metric-gen`의 출력 대상을 generated data와 provenance metadata로 제한한다.
- digest, TTC face index, 필요한 naming record와 Hangul compression error를 산출할 수 있게 한다.
- 입력 순서를 명시적으로 고정하고 암묵적 sort/dedupe가 기존 DB를 재구성하지 못하게 fail-closed한다.
- source가 확인되는 공개/tracked canary만 재현하고, 원본 없는 595개 전체를 재생성하지 않는다.
- 생성기가 overlay와 core 파일을 수정하지 않는 ownership test를 둔다.
- 같은 canary 입력의 연속 생성 hash가 동일한지 확인한다.
- `mydocs/working/task_m100_4964_w6_stage4.md`에 생성 가능/불가능 경계를 기록한다.

### Stage W6-5 — 통합 불변식·renderer 검증

- Rust font metric unit test와 exhaustive legacy lookup equivalence를 실행한다.
- W1 ledger/candidate, W6 lineage/manifest, #2430 verify test를 함께 실행한다.
- 기존 W0 공개 대표 7개 fixture의 native/WASM SVG byte parity를 확인한다.
- 변경 범위에 해당하는 renderer fixture와 native release build를 실행한다.
- WASM은 프로젝트 표준 Docker 경로로 빌드한다.
- `cargo fmt --all`과 `cargo fmt --all -- --check`를 마지막 push 전 다시 실행한다.
- `mydocs/working/task_m100_4964_w6_stage5.md`와 최종 보고서에 gate·잔여 unknown을 기록한다.

## 9. 재계측·보안·라이선스 경계

이번 작업은 이미 존재하는 W0/W1/W5와 #2430 측정 evidence를 우선 재사용한다. 구조 분리의 정당성을
확인하기 위해 private 10k corpus나 Hyper-V 한컴 ladder를 다시 전수 실행하지 않는다. 다음 입력 identity가
실제로 달라지고 별도 승인을 받은 경우에만 제한 재계측을 검토한다.

- metric 또는 measurement source digest
- 한컴/OS/font environment identity
- Oracle fixture bytes 또는 export route
- compression/manifest schema의 의미

저장소 밖 local font는 read-only 검산 입력으로만 사용할 수 있으며 font bytes를 stage하지 않는다.
digest와 공개 가능한 name/license 정보만 기록하고, 재배포 권한이 불명확하면 `unknown` 또는
`local-only` 상태로 둔다.

## 11. 완료 조건과 승인 게이트

W6 완료는 파일이 나뉘었다는 사실만으로 판정하지 않는다. 다음을 모두 충족해야 한다.

1. 600개 항목이 generated, measured/manual overlay 또는 명시적 unknown provenance에 전부 대응한다.
2. 순서·이름·style·em·range/Hangul data·문자 폭·lookup/fallback hash가 분리 전과 같다.
3. W1 collector와 ledger가 새 source 경계에서도 같은 600개를 인식한다.
4. 생성기가 core/overlay를 덮어쓰지 않고, 확인 가능한 입력에서 manifest/hash가 결정론적이다.
5. native/WASM 공개 fixture SVG parity와 대표 renderer gate가 통과한다.
6. 잔여 unknown을 숨기지 않고 후행 조사 입력으로 목록화한다.
7. 신규 font bytes와 private corpus 식별 자료가 Git 변경에 포함되지 않는다.

본 수행계획 승인 뒤에만 Stage W6-1을 시작한다. 각 Stage 결과는 보고서와 변경 범위를 브리핑하고
메인테이너 승인 후 다음 Stage로 진행한다. remote push, PR 생성, self-review, merge와 이슈 종료는 각각
프로젝트 승인 절차를 따른다.
