## 1. 문제

`build_cfb`(`src/serializer/mini_cfb.rs:71`)가 CFB **디렉터리 엔트리**의 CLSID(오프셋 +80, 16바이트)를
항상 0 으로 고정한다. `DirEntry`(`:32-43`)에 CLSID 필드 자체가 없고 `write_dir_entry`(`:513`)은 주석만
남긴다.

OLE 개체는 루트 스토리지 엔트리의 CLSID 로 서버를 식별한다. 중첩 OLE CFB 를 재포장하면
`{4C3DA137-DC90-47B9-9BED-59DAE352A280}` 가 사라지고 **한컴이 개체를 통째로 비워 그린다** — 틀과 선택
핸들만 보이고 내용이 없다(2026-08-05 실측, CLSID 를 되박자 정상 렌더).

> 같은 파일 `:422` 는 CFB **파일 헤더**의 CLSID 필드로 MS-CFB 스펙상 0 이 맞다 — 이쪽은 결함이 아니다.

rhwp 는 `parse_ole_container`(`src/parser/ole_container.rs:63-165`)가 스트림 **이름**으로만 개체를
판별해 CLSID 를 아예 읽지 않는다. 그래서 왕복 검증·조립 검증이 전부 통과했고 한컴에서만 드러났다.
[#3546](https://github.com/edwardkim/rhwp/issues/3546) 과 같은 계열의 "자기정합은 유지되고 한컴 호환만
조용히 깨지는" 결함이다.

**함께 고칠 것** — `build_entries`(`:330`)가 `path.trim_start_matches('/').split('/')` 로 `/` 로만 경로를
쪼갠다. Windows 에서 `cfb` 크레이트는 `/BinData\BIN0001.OLE` 처럼 구분자를 섞어 돌려주므로, 정규화 없이
넘기면 스토리지가 사라지고 이름에 역슬래시가 든 루트 스트림 하나로 뭉개진다.

## 3. 설계 결정

### (a) 루트 CLSID 만 받는다

```rust
pub fn build_cfb(named_streams: &[(&str, &[u8])]) -> Result<Vec<u8>, String>   // 시그니처 불변, [0u8;16] 위임
pub fn build_cfb_with_root_clsid(
    named_streams: &[(&str, &[u8])],
    root_clsid: [u8; 16],
) -> Result<Vec<u8>, String>
```

CLSID 를 실을 수 있는 엔트리는 Root(5)와 Storage(1) 둘뿐인데 **코퍼스 56건 전부 서브 스토리지가
0개**다(Stage 1 실측). HWP3 축도 서브 스토리지를 **루트로 승격**하므로 출력에 스토리지가 없다. B1 편집
대상도 같은 평탄 구조다. → per-path CLSID 는 현재도 향후도 소비자가 0 인 speculative generality.

단, `DirEntry` 에 `clsid: [u8;16]` **필드**를 두고 `write_dir_entry` 가 그 필드를 쓰게 한다(루트 값을
특별 취급해 직접 쓰지 않는다). 나중에 스토리지별 CLSID 가 필요하면 `build_entries` 에 조회 한 줄만
추가하면 되고 `write_dir_entry` 는 무변경이다.

### (b) 리더는 `cfb_reader.rs` 에 유일 구현, `ole_container.rs` 는 위임

```rust
// src/parser/cfb_reader.rs
pub fn root_clsid(cfb: &[u8]) -> Option<[u8; 16]>
// src/parser/ole_container.rs — 이슈가 지정한 이름, 위임 래퍼
pub fn ole_root_clsid(cfb: &[u8]) -> Option<[u8; 16]>
```

`cfb_reader.rs` 가 CFB 바이트 레이아웃 지식의 단일 소유자다 — 이미 `0x1E` 섹터 지수(`:359`)·`0x30`
first_dir_sector(`:376`)를 읽고, **`9..=12` 범위 검증**을 wasm32 shift overflow 근거 주석(`:350-364`)과
함께 갖고 있다. 오프셋 지식을 복제하면 다음에 한쪽만 고쳐진다.

`LenientCfbReader::list_entries` 튜플 확장은 **기각**: (1) 엄격 파서 실패 시에만 쓰이는 폴백이라 정상
CFB 는 이 경로를 안 탄다, (2) `open()` 이 파일 전체를 `to_vec()` 복사하고 FAT/DIFAT 를 다 만든다,
(3) `(String,u32,u64,u8)` 를 늘리면 전 소비자의 패턴 매칭이 바뀐다.

`OleContainer` 구조체 필드 추가는 **이번 범위 제외** — `parse_ole_container` 의 `Some` 게이트가 렌더러
분기(`renderer/layout/shape_layout.rs:1964`)를 좌우한다. B1 이 실제로 필요해질 때 추가한다.

### (c) HWP3 축 포함

`cfb` 가 CLSID 를 노출하므로 raw 파싱이 불필요하다. `extract_ole_payloads`(`src/parser/hwp3/ole.rs:166-225`)는
이미 `walk()` 로 서브 스토리지 `Entry` 를 쥐고 있다(`:174-179`). 되박아야 할 CLSID 는 원본 CFB 의 루트가
아니라 **승격되는 서브 스토리지 엔트리**의 것이다.

### (d) `build_entries` 부수 결함 2건 동시 수정 (이슈 미기재, 작업지시자 승인)

1. dedup 탐색이 `entries[0]`(Root, `parent==0`)를 최상위 후보에 포함 → `/Root Entry` 스트림이 루트를
   덮어쓴다. `.skip(1)` 로 해소.
2. 같은 이름이 스토리지·스트림으로 겹치면 스토리지에 `.data` 만 채우고 `write_dir_entry:533-537` 이
   type 1 에 size 0 을 써 **데이터가 조용히 소실**된다. `Err` 로 승격한다 — `build_cfb` 는 이미
   `Result` 인데 현재 `Err` 를 한 번도 안 낸다.
