# Subsecond WASM 라이브 렌더러 계획

- 기준: `upstream/devel` @ `1ddfc7da`
- 작성일: 2026-07-24

## 1. 목표

열려 있는 rhwp-studio의 문서와 편집 상태를 유지한 채 Rust 렌더러 함수 본문을
Subsecond로 교체하고, 패치가 적용되면 현재 보이는 페이지를 자동으로 다시 그린다.

이 계획은 rhwp-studio를 Dioxus UI로 마이그레이션하지 않는다. Vite/TypeScript UI,
`WasmBridge`, `CanvasView`, 기존 `HwpDocument` 인스턴스와 이벤트 버스는 그대로
유지한다.

## 2. 현재 실행 경로와 훅 경계

문서 로드는 다음 경로이며 Subsecond 훅으로 사용하지 않는다.

```text
CanvasView.loadDocument()
  -> WasmBridge.loadDocument()
  -> HwpDocument / DocumentCore::from_bytes()
```

이 경로는 문서를 열 때 한 번 실행되므로 렌더러 수정 후 열린 편집기를 즉시 다시
그리는 반복 진입점이 될 수 없다.

Canvas2D의 반복 렌더 경로는 다음과 같다.

```text
CanvasView.refreshPagesForRevision()
  -> PageRenderer
  -> WasmBridge.renderPageToCanvasFiltered()
  -> HwpDocument::render_page_to_canvas_filtered_with_profile()
```

따라서 첫 번째 실제 Subsecond 훅은
`src/wasm_api.rs`의
`HwpDocument::render_page_to_canvas_filtered_with_profile`로 한다.

CanvasKit은 Rust가 만든 `PageLayerTree` JSON을 재생하므로 두 번째 훅은
`src/wasm_api.rs`의
`HwpDocument::get_page_layer_tree_with_profile`로 한다.

`DocumentCore::render_page_svg_native`는 네이티브/CLI SVG 경로의 중심 함수이지만,
열린 WASM 편집기 자동 갱신의 첫 범위에는 포함하지 않는다.

## 3. 채택 구조

### 3.1 안정된 wasm-bindgen 외피와 패치 가능한 함수 본문 분리

기존 wasm-bindgen export 이름과 인자·반환 ABI는 유지한다. export 함수는 얇은
외피가 되고, 실제 렌더링은 별도 Rust 함수로 이동한다.

```text
render_page_to_canvas_filtered_with_profile()  // 안정된 wasm-bindgen 외피
  -> Subsecond HotFn
  -> render_page_to_canvas_filtered_impl()     // 패치 대상

get_page_layer_tree_with_profile()             // 안정된 wasm-bindgen 외피
  -> Subsecond HotFn
  -> get_page_layer_tree_with_profile_impl()   // 패치 대상
```

브라우저 WASM은 Rust stack unwinding을 지원하지 않으므로 단순히
`subsecond::call`에 의존하지 않는다. Subsecond 0.7의 WASM 지침에 따라
`subsecond::HotFn::current`와 `HotFn::call`을 사용해 명시적인 패치 경계를
만든다.

Subsecond 의존성과 런타임 코드는 개발용 feature로 격리한다. 일반 debug,
release 및 배포용 `wasm-pack` 산출물의 기존 ABI와 실행 경로는 바꾸지 않는다.

### 3.2 패치 revision 감지

패치 적용만으로 브라우저가 렌더 함수를 다시 호출하지는 않는다. 개발용 WASM
export가 두 렌더 `HotFn::ptr_address()`에서 계산한 revision을 문자열 또는 두
개의 `u32`로 노출한다. JavaScript의 `requestAnimationFrame` 기반 개발용 감시기는
직전 revision과 비교하며, 값이 바뀐 경우에만 다음 작업을 수행한다.

1. WASM의 렌더·레이아웃 캐시 전체 무효화
2. `document-view-changed` 이벤트 발행
3. 현재 visible page 재렌더

revision 감시는 문서 mutation을 만들지 않으며 dirty/undo 상태를 변경하지 않는다.
감시기는 문서가 열린 동안만 동작하고 `CanvasView.dispose()`에서 해제한다.

### 3.3 캐시 무효화

현재 `DocumentCore::invalidate_page_tree_cache()`는 다음 상태를 함께 비운다.

- `page_tree_cache`
- `layer_tree_json_cache`
- `layout_engine`의 레이아웃 캐시

Subsecond revision 변경 시 이 함수를 호출하는 개발용 WASM API를 추가한다. 캐시를
비우지 않으면 새 함수가 호출되어도 이전 `PageLayerTree` 또는 직렬화 JSON이 그대로
재사용될 수 있다.

UI 쪽 재렌더는 이미 존재하는 `document-view-changed`를 사용한다.
`CanvasView`는 이 이벤트를 `refreshPagesForRevision()`으로 연결하므로 별도 문서
로드나 mutation 이벤트를 만들지 않는다.

## 4. 개발 서버와 빌드 경계

Subsecond 0.7의 patch compiler와 ThinLink는 독립 실행 crate가 아니라 Dioxus CLI에
통합되어 있다. 따라서 Rust/WASM patch lane은 같은 protocol type 버전을 쓰는
`dioxus-cli 0.7.9`와 `subsecond 0.7.9` 조합을 우선 사용하고
`dx serve --hotpatch`로 구동한다.

Vite는 기존 HTML/TypeScript 개발 서버 역할을 유지한다. Dioxus component,
Virtual DOM, router 또는 Dioxus UI runtime은 도입하지 않는다. `dx serve`가 만든
초기 WASM과 patch transport를 Vite 페이지가 소비하는 연결만 추가한다.

첫 구현 단계는 다음 두 사실을 작은 spike로 증명해야 한다.

1. 현재 `rhwp` cdylib가 `dx serve --hotpatch`의 WebAssembly tip crate로
   인식되고 `src/renderer/` 변경이 thin patch에 포함된다.
2. dx가 만든 wasm-bindgen 산출물과 patch websocket을 Vite가 연
   rhwp-studio에서 소비할 수 있다.

둘 중 하나라도 실패하면 Dioxus UI 마이그레이션이나 대규모 crate 이동으로
우회하지 않는다. 실패 근거와 필요한 최소 build-adapter 범위를 기록한 뒤 다음
설계를 승인받는다.

## 5. 패치 시 데이터 흐름

```text
Rust renderer 함수 본문 수정
  -> dx/ThinLink가 변경 object를 thin patch로 생성
  -> Dioxus devtools websocket이 열린 WASM instance에 jump table 적용
  -> JS revision 감시기가 HotFn pointer 변경 감지
  -> DocumentCore 렌더 캐시 무효화
  -> eventBus.emit("document-view-changed")
  -> CanvasView.refreshPagesForRevision()
  -> 기존 HwpDocument로 visible page 재렌더
  -> HotFn이 새 render implementation 호출
```

문서 bytes 재파싱, `CanvasView.loadDocument()`, 새 `HwpDocument` 생성 또는 전체
브라우저 reload는 이 흐름에 포함하지 않는다.

## 6. 유지되는 상태와 재시작 경계

### 패치 대상으로 허용

- 기존 타입과 함수 signature를 유지한 렌더 알고리즘 변경
- 상수, 조건문, PaintOp 처리 및 Canvas2D/CanvasKit replay 로직 변경
- 기존 IR을 읽는 레이아웃·페인트 계산 변경

### 문서만 다시 열어야 함

- parser가 채우는 값 또는 IR 생성 규칙 변경
- 타입 layout은 같지만 이미 로드된 `Document` 내용을 다시 만들어야 하는 변경

### dx/browser session을 다시 시작해야 함

- struct/enum field, `repr`, 크기 또는 alignment 변경
- wasm-bindgen export 이름, 인자 또는 반환 ABI 변경
- Cargo dependency, feature 또는 build/link 설정 변경
- static initializer 또는 thread-local 동작에 의존하는 변경

기존 state와 새 코드가 서로 다른 type layout을 해석하게 두지 않는다. Subsecond는
기존 `HwpDocument` 내부 IR을 자동 migration하지 않는다.

## 7. 구현 단계

### Stage 0 — WebAssembly patch 가능성 spike

- `dioxus-cli 0.7.9`/`subsecond 0.7.9` 조합을 고정한다.
- 최소 개발 feature와 한 개의 `HotFn` probe를 만든다.
- `dx serve --hotpatch`에서 함수 상수 하나를 바꾸고 같은 브라우저 WASM instance가
  새 값을 반환하는지 확인한다.
- full rebuild, page reload, document reload 여부와 patch 시간을 기록한다.

### Stage 1 — Canvas2D 반복 훅

- `render_page_to_canvas_filtered_with_profile`의 ABI 외피를 유지한다.
- 실제 본문을 patch 대상 함수로 분리하고 `HotFn`을 통해 호출한다.
- revision이 바뀌어도 기존 `HwpDocument`가 유지되는지 확인한다.

### Stage 2 — 자동 repaint와 캐시 계약

- 개발용 revision/cache WASM API를 추가한다.
- `WasmBridge`에 해당 API의 optional capability detection을 추가한다.
- `CanvasView`가 patch revision 변경 시 캐시 무효화 후
  `document-view-changed`를 한 번만 발행하도록 한다.
- dispose, 문서 미로드, background tab 및 연속 patch에서 감시기가 누적되지
  않는지 검증한다.

### Stage 3 — CanvasKit 경로

- `get_page_layer_tree_with_profile`도 동일한 방식으로 patchable body로 분리한다.
- JSON cache가 patch 이후 비워지고 CanvasKit visible page가 새 tree를 재생하는지
  확인한다.

### Stage 4 — 회귀 및 속도 검증

- Subsecond feature를 끈 기존 `wasm-pack` build와 studio test가 그대로 통과하는지
  확인한다.
- Canvas2D와 CanvasKit에서 문서를 한 번만 연 뒤 renderer body를 수정한다.
- 브라우저 reload 없이 화면이 바뀌고 selection, scroll, zoom, undo stack,
  unsaved 상태가 유지되는지 확인한다.
- source save부터 visible repaint까지 시간을 기록하고 full WASM rebuild/reload
  기준선과 비교한다.

## 8. 수용 기준

1. rhwp-studio를 Dioxus UI로 마이그레이션하지 않는다.
2. 문서를 다시 열지 않고 Canvas2D renderer 함수 수정이 visible page에 반영된다.
3. CanvasKit에서도 layer-tree 생성 변경이 같은 방식으로 반영된다.
4. patch 직후 이전 render/layout/JSON cache가 재사용되지 않는다.
5. selection, scroll, zoom, undo stack과 unsaved 편집 상태가 유지된다.
6. type/ABI/IR 변경은 정해진 reload 또는 restart 경계를 따른다.
7. Subsecond feature를 끈 일반 개발·배포 build에는 동작 변화가 없다.

## 9. 범위 밖

- 실제 브라우저 설치·설정 또는 실제 브라우저 사용 계획
- rhwp-studio의 Dioxus component/Virtual DOM 마이그레이션
- `from_bytes()` 또는 `loadDocument()`를 hot loop로 만드는 작업
- type layout 또는 기존 IR instance의 자동 migration
- 네이티브 CLI/SVG renderer hotpatch 지원
