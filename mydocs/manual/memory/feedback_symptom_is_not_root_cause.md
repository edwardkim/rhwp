**테스트가 실패한 지점과 결함의 원인은 다르다.** 관측 지점을 근인처럼 서술하면 후속 조사가
엉뚱한 곳을 파게 된다.

2026-07-27 #3412 사례. v0.8.2 릴리즈 1단계에서 내가 이렇게 보고했다.

> `hwp run 1 after-56-sync` 체크포인트에서 누적 `wasmFlush` 가 기대값 0 대신 2

이건 **단언이 깨진 위치**일 뿐이다. planet6897 이 호출 시각·소요시간을 계측한 결과 실패는
56번째 입력 경계에서 일어나지 않았다. 55번째 입력 뒤 `afterPageLocalEdit` 이 pending 이라
**120ms idle 타이머를 재무장**했고, 그 타이머 발화가 `flushDeferredPagination` 을 호출했다.
입력 순번이 아니라 **타이머 타이밍**이 원인이었다.

**Why:** "56번째" 라는 숫자가 원인처럼 읽히면 조사자가 경계 조건·off-by-one 을 뒤지게 된다.
실제로는 비동기 타이머 수명 문제라 그 방향으로는 영원히 안 나온다.

**How to apply:**

- 실패 보고에는 **관측한 것**(어느 단언이 어떤 값으로 깨졌는지)과 **추정**(왜 그런지)을
  분리해 적는다. 진단하지 않았으면 "근인 미진단" 이라고 명시한다.
- 비동기 코드에서는 이벤트 순번보다 **타이머·스케줄러 수명**을 먼저 의심한다. "N번째에서
  터진다" 는 관측은 N 과 무관한 주기적 트리거일 수 있다.
- 근인 확정에는 계측(호출 시각·소요시간·호출자)이 필요하다. 로그 위치만으로 단정하지 않는다.

이번 건에서 릴리즈를 막지 않고 별도 이슈로 분리하면서 **"회귀 여부 미확정" 을 확정 서술로
바꾸지 않은 판단은 옳았다.** 다만 실패 지점을 근인처럼 제목에 넣은 것은 정확하지 않았다.
[[feedback_diagnosis_layer_attribution]](결함 귀속 layer 정확화)과 같은 계열이다.
