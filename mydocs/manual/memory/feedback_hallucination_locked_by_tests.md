2026-07-26, #3363에서 작업지시자가 지적한 교훈. HWP3 글맵시(내장 OLE)를 처음 마주쳤을
때 "00000000.OOO"라는 파일명처럼 생긴 **내부 참조명**을 외부 이미지 파일로 오인 →
사이드카 로딩 경로(populate_external_images_from_dir, #3313 주입 UX)를 증축 →
수동 추출된 워크어라운드 파일(samples/00000000.OOO)이 이 이론을 "실측 green"으로
만들어 자기강화 → **issue_1692 테스트가 오분류를 단언으로 고정**해 회귀 보호까지
받는 공식 동작이 됨. 올바른 수정(#3363)을 넣자 이 테스트가 저항했다.

**Why:** 표면적으로 그럴듯한 증거(파일명 모양 문자열)에서 출발한 해석이, 워크어라운드
와 스냅샷 테스트를 거치며 검증된 사실처럼 굳는다. 테스트 코드는 권위가 아니라 **과거
믿음의 스냅샷**일 수 있다 — green이 정답을 보증하지 않는다([[feedback-self-verification-not-hancom]]
의 파서 구조 해석판). 중간에 작업지시자가 "내부에 포함된 것 아닌가"라고 확인하지
않았다면 존재할 필요 없는 기능(사이드카 공급 UX)을 계층째 양산할 뻔했다.

**How to apply:**
- 파서에 외부 자원 의존(사이드카/링크/경로)을 새로 도입·확장할 때는 스펙 해당 절
  정독 + 원시 바이트 + 한컴 실동작(UI/변환본)의 3중 교차검증을 선행한다. "파일명이
  보인다"는 증거가 아니다 (HWP3 스펙 표 44 "그림 파일 이름"은 pic_type=1/2에서 내부
  참조명 — 12.1절).
- 동작을 고정하는 테스트에는 근거(스펙 절/한컴 실측)를 주석으로 남기고, 워크어라운드
  를 단언하는 테스트는 워크어라운드임을 명시한다. 기존 테스트가 수정에 저항하면
  "테스트가 정답인가, 과거 믿음인가"를 먼저 물을 것.
- samples/에 놓인 정체불명 보조 파일(수동 추출본 등)은 이론의 증거로 삼지 말고
  출처를 먼저 추적한다.
