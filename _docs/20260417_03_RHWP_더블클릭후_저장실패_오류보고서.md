# RHWP 더블클릭 후 저장 실패 오류 보고서

## 발단: 사용자 요청

사용자는 로컬 `.hwp` 파일을 Explorer에서 더블클릭했을 때 `rhwp`로 열리게 하고 싶다고 요청했다. 이후 Open With 등록, `RHWPLauncher.exe` 도입, preview server 교체, 저장 bridge 보강까지 진행한 뒤에도 특정 실제 문서에서 `Ctrl+S`와 `메뉴 > 저장`이 동작하지 않는다고 보고했다.

사용자가 최종으로 보고한 실제 증상은 다음과 같다.

- 대상 파일: `D:\vibe-coding\리딩북스_문제자동화\references\20260413_고등교과서 어법에서 주로 물어보는 문법포인트 (선생님 제작).hwp`
- 재현 절차: 파일 더블클릭으로 RHWP 실행 → 내용 수정 → `Ctrl+S` 또는 `메뉴 > 저장`
- 실제 결과: 저장이 반응하지 않거나, 반응하더라도 원본 파일에 수정 내용이 반영되지 않음
- 현재 보고 범위: Explorer 더블클릭으로 연 문서의 저장 실패. 파일 picker로 연 동일 문서 경로는 이번 보고서 범위에서 확정하지 않음.

이 문서는 해당 문제를 별도 세션에서 이어서 조사하기 위한 오류 보고서였고, 아래 후속 조사로 root cause와 수정 내역까지 반영한 상태다.

## 작업 상세내역

이번 세션에서 저장 관련 경로는 아래 순서로 변경되었다.

1. `RHWPLauncher.exe` 기반 Open With 등록을 만들었다.
2. `.hwp` 더블클릭 시 파일을 `rhwp-studio/dist/__opened/` 아래 staged copy로 복사하고, Chrome app window를 `?url=...&filename=...`로 여는 경로를 구현했다.
3. 기존 `vite preview`가 런타임 생성 파일을 정적으로 서빙하지 못해 초기 페이지만 뜨는 문제가 확인됐다.
4. 이를 해결하기 위해 `rhwp-studio/scripts/preview-server.mjs`를 추가하고, 런타임 staged file을 직접 서빙하도록 교체했다.
5. 더블클릭으로 연 문서에서 `Ctrl+S`가 원본 파일로 저장되도록, 브라우저 내부에서 `saveUrl`로 `PUT` 요청을 보내는 pseudo file handle(`createHttpFileHandle`)를 추가했다.
6. `preview server`는 `__rhwp_save/<token>` endpoint를 통해 원본 파일과 staged file을 함께 갱신하도록 보강했다.
7. 기존 7701 서버와 충돌 가능성을 줄이기 위해 새 저장 bridge는 7702 포트를 사용하도록 조정했다.

실제 조사 과정에서 확보한 사실은 다음과 같다.

- 대상 실제 파일은 `Read-only`가 아니었다. `Attributes=Archive`였고 ACL 기준 `Authenticated Users: Modify`가 허용되어 있었다.
- 동일한 폴더에 만든 테스트 사본 `20260417_저장테스트_고등교과서 어법에서 주로 물어보는 문법포인트 (선생님 제작).hwp`에서는 저장이 성공했다.
- 위 테스트 사본에 대해 브라우저 자동화로 문자열 입력 후 `Ctrl+S`를 실행했을 때 파일 해시와 수정 시각이 실제로 변경됐다.
- 사용자가 보고한 실제 원본 파일에서는 여전히 실패한다고 진술했다.
- 사용자가 실패를 재보고한 뒤, 이 문제는 별도 세션에서 다루기로 결정하고 현 세션에서는 오류 보고서 작성으로 전환했다.

문제는 현재 두 개의 사실이 동시에 성립하는 상태다.

- 코드와 자동 검증 기준으로는 저장 경로가 동작한다.
- 사용자의 실제 사용 맥락에서는 저장이 실패한다.

따라서 현재 단계에서는 저장 구현 전체가 실패한다고 단정할 수 없고, `사용자 실제 창/세션 조건에서만 발생하는 저장 실패`로 분리해 다뤄야 한다.

## 후속 조사 결과

후속 세션(`codex:019d9a20-7c77-7513-978d-506539b5103d`)에서 저장 실패를 다시 재현했을 때, 기존의 "저장이 안 된다" 대신 아래 오류가 UI에 명시적으로 노출됐다.

- 오류 메시지: `파일 저장에 실패했습니다: HTTP 500: Internal Server Error`
- 실패 지점: `__rhwp_save/<token>` endpoint
- 실제 대상 파일: `D:\vibe-coding\리딩북스_문제자동화\references\20260413_고등교과서 어법에서 주로 물어보는 문법포인트 (선생님 제작).hwp`

추가 조사로 확보한 직접 증거는 다음과 같다.

- 실제 launch manifest 파일 `rhwp-studio/dist/__opened/a679b89a5a4e4d42bba493eb3745b866.json` 앞부분에 UTF-8 BOM 바이트 `EF BB BF`가 들어 있었다.
- Node로 위 manifest를 직접 파싱했을 때 `SyntaxError: Unexpected token '﻿'`가 재현됐다.
- `preview-server.mjs`의 `readLaunchManifest()`는 `JSON.parse(raw)`로 manifest를 그대로 읽고 있었고, 이 지점에서 500이 발생하는 구조였다.
- PowerShell 런처 `Publish-RhwpLaunchFile()`는 `Set-Content -Encoding UTF8`로 manifest를 쓰고 있었고, 실제 `powershell.exe` 환경 기준으로 BOM이 포함됐다.

즉, 이번 저장 실패의 root cause는 `launcher가 BOM 포함 JSON manifest를 생성하고, preview server가 이를 그대로 JSON.parse하면서 save endpoint가 500을 반환한 것`으로 확정됐다.

## 수정 및 해결 내역

확정된 원인에 대해 아래 수정이 반영됐다.

1. `tools/rhwp_launcher.lib.ps1`
   - launch manifest를 `UTF-8 without BOM`으로 쓰도록 `Write-Utf8NoBomFile` 헬퍼를 추가했다.
2. `rhwp-studio/scripts/preview-server.mjs`
   - 과거에 생성된 BOM 포함 manifest도 읽을 수 있도록 `JSON.parse(raw.replace(/^\uFEFF/, ''))`로 보강했다.
3. `rhwp-studio/src/command/commands/file.ts`
   - 기존 문서 저장 실패 시 브라우저 다운로드로 silent fallback하지 않고, 상태바와 alert에 실패를 즉시 노출하도록 변경했다.
4. `rhwp-studio/src/command/file-system-access.ts`, `src/main.ts`
   - save trace와 health metadata를 추가해 다음 장애 시 경계를 바로 좁힐 수 있게 했다.

수정 반영 후 사용자가 같은 실제 파일을 다시 열어 수정 후 `Ctrl+S`를 실행했을 때, "이제, 수정이 반영된다."고 확인했다.

## 의사결정 기록

- 결정: 이 문제는 별도 세션에서 재현 중심으로 다시 조사한다.
- 근거: 자동 검증과 로컬 재현 일부는 이미 성공했고, 현재 남은 문제는 `사용자 실제 실패 세션`과 `로컬 성공 세션` 사이의 차이를 추적하는 작업이기 때문이다.
- 근거: 이 상태에서 추가 구현을 계속 쌓으면 저장 경로 자체보다 세션 재사용, 포커스, 메뉴 이벤트, save endpoint hit 여부 같은 관측 문제를 가릴 위험이 있다.
- 트레이드오프: 지금 바로 기능 추가를 멈추는 대신, 별도 세션에서 더 정교한 로깅과 현장 재현에 집중해야 한다.
- 후속 결정: 원인 확정 후에는 기능 추가보다 `manifest 인코딩 수정 + BOM 호환 읽기`처럼 root cause만 정확히 제거하는 최소 수정으로 마무리했다.

## 리스크 및 미해결 이슈

- 이번 보고서 범위의 저장 실패 root cause는 해결됐다.
- 다만 이미 떠 있는 오래된 RHWP 창이나 오래된 preview server 세션은 새 코드 반영 전 상태를 유지할 수 있으므로, 실사용 재검증은 새로 파일을 다시 열어 수행하는 것이 안전하다.
- save trace와 health metadata는 남겨 두었으므로, 같은 증상이 다시 나오면 `__rhwp_health`와 `[save-trace]` 로그 기준으로 즉시 재분류할 수 있다.

## 다음 액션

1. 현재 코드 변경을 별도 커밋으로 정리한다.
2. 동일 증상이 다시 발생하면 `__rhwp_health`의 `lastSave`와 브라우저 콘솔 `[save-trace]`를 먼저 확보한다.
3. 별도 후속 작업이 없다면, save trace와 health metadata는 유지하되 불필요한 임시 로그는 추후 정리 여부를 검토한다.
