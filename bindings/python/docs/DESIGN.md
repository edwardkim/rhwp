# 설계 결정 기록

바인딩을 만들며 내린 판단과 **버린 대안**을 남긴다. 왜 그랬는지 모르면 다음 사람이
같은 논쟁을 다시 하거나, 좋은 이유로 세운 제약을 무심코 걷어낸다.

---

## D1. 서브프로세스 래퍼 — C ABI 가 아니라

**결정**: rhwp 실행 파일을 프로세스로 띄우고 stdout 봉투를 읽는다.

**버린 대안**: `cdylib` + `ctypes`/PyO3 로 인프로세스 호출.

**이유**: C ABI 는 성능이 가장 좋지만 ABI 안정성·메모리 규약·플랫폼별 빌드를 새로
떠안는다. 서브프로세스는 이미 검증된 CLI 계약(#2707 종료 코드, 봉투 스키마)을
**그대로 재사용**하므로 바인딩이 지는 책임이 봉투 파서 하나로 줄어든다.

호출당 수십 ms 의 프로세스 기동 비용은 세션(2층)이 상쇄한다 — 같은 문서를 반복해서
만지는 경우가 성능이 문제 되는 유일한 경우다.

**되돌릴 조건**: 인프로세스 성능이 실제 병목으로 실증되면 승격한다
(`bindings_foundation.md` §2 의 "수요 실증 후 승격").

---

## D2. 판정(exit 3/4)을 예외로 만들지 않는다

**결정**: 검증 단언 실패는 반환값의 판정 필드다. `raise_on_verdict=True` 로만 예외.

**버린 대안**: 모든 0 아닌 종료 코드를 예외로.

**이유**: `--verify` 불일치는 **도구가 정상 동작한 결과**다. 예외로 올리면 호출자가
`try/except` 로 "고장"처럼 다루고, 정작 봉투에 담긴 판정 근거(`diffCount`)를 읽지
않는다. 파이썬 관례(예외 우선)를 따르는 것보다 **rhwp 계약의 의미론을 보존**하는
쪽이 옳다고 판단했다.

**대가**: 파이썬 개발자에게 처음엔 낯설다. README·가이드·요리책 세 곳에서 이 규약을
반복해 설명하는 이유다.

---

## D3. 봉투를 dataclass 로 정적 매핑하지 않는다

**결정**: `Envelope` 하나가 봉투를 감싸고, 키를 snake_case 속성으로 노출한다.

**버린 대안**: 명령마다 `InfoResult`·`SearchResult` dataclass 를 손으로 정의.

**이유**: 봉투는 **필드 추가 허용** 계약이다. 수기 dataclass 는 rhwp 가 필드를 더할
때마다 뒤처지고, 뒤처졌다는 사실조차 드러나지 않는다(그냥 값이 안 보일 뿐).
`Envelope` 는 봉투에 있는 것을 전부 노출하므로 구조적으로 뒤처질 수 없다.

**대가**: IDE 자동완성이 약하다. 이를 보완하려고 IR 쪽은 스키마 기반 코드 생성
(`tools/gen_models.py`)을 두었다 — 거기는 스키마가 단일 출처라 생성이 안전하다.

---

## D4. 없는 필드는 `None` 이 아니라 예외

**결정**: `Envelope` 는 없는 키에 `AttributeError`/`KeyError` 를 낸다.

**버린 대안**: `dict.get` 처럼 `None` 반환.

**이유**: 조용한 `None` 은 오타를 "값 없음"으로 둔갑시킨다. 그 코드는 실패하지 않고
잘못된 결과를 낸다 — 가장 찾기 어려운 종류의 버그다. 예외 메시지에 **있는 필드를
함께** 실어 즉시 고칠 수 있게 했다.

**예외의 예외**: `verify`·`changed_pages` 처럼 **계약상 null 이 유효한** 필드는
프로퍼티로 감싸 `None` 을 돌려준다. "없어도 되는 것"과 "이름이 틀린 것"은 다르다.

---

## D5. 이름 변환은 기계로, 개명은 금지

**결정**: camelCase ↔ snake_case 를 규칙 함수로 잇고, 원문 키 접근도 함께 지원한다.

**버린 대안**: 파이썬스러운 이름으로 손수 다시 명명(`pageCount` → `pages`).

**이유**: 사람이 이름을 붙이기 시작하면 매핑 표를 유지해야 하고, 그 표는 반드시
뒤처진다. 규칙이면 새 필드가 자동으로 따라온다. 원문 키를 계속 받는 이유는, 봉투
문서를 보고 코드를 쓰는 사람이 변환 규칙을 몰라도 되게 하기 위함이다.

---

## D6. 런타임 의존성 0

**결정**: 표준 라이브러리만 쓴다.

**버린 대안**: `pydantic`(검증), `httpx`(향후 원격), `rich`(출력).

**이유**: 바인딩이 무거우면 "재포장"이 아니라 새 표면이다. 의존성이 하나 늘 때마다
버전 충돌 가능성과 설치 실패 지점이 는다. 문서 처리 도구는 다른 스택 한가운데
들어가는 경우가 많아 가벼움이 곧 채택률이다.

---

## D7. 계획의 `dryRun` 을 CLI 플래그가 아니라 계획서 필드로

**결정**: `plan.dryRun` 이 진실이고, `--dry-run` 은 그것을 덮어쓰는 편의 입구다.

**이유**: 계획서가 필드를 실으면 MCP `hwp_run_plan{plan}` 이 **인자 추가도
cmdTemplate 변경도 없이** 같은 계약을 얻는다. 의도의 단일 출처가 계획서 하나로
유지된다.

(이 결정은 rhwp 본체 #3759 에서 내렸고, 바인딩은 그것을 그대로 따른다.)

---

## D8. 선검증 위반은 예외가 아니라 결과

**결정**: `Plan.check()`/`run()` 은 위반이 있어도 `PlanResult` 를 돌려준다.

**버린 대안**: exit 2 규약대로 `UsageError`.

**이유**: 계획 실행에서 위반은 **설계된 흐름의 일부**다 — 검사하고, 고치고, 다시
검사한다. 예외로 만들면 `try/except` 안에서 계획을 고치는 어색한 코드가 된다.
단, `invalid` 가 없는 exit 2 는 진짜 호출 조립 버그이므로 그대로 올린다.

---

## D9. IR 스키마를 손으로 쓴다

**결정**: `src/ir_schema.rs` 에 공개 IR 을 명시적으로 서술한다.

**버린 대안**: serde 파생에서 자동 추출(`schemars` 등).

**이유**: 자동 추출은 **직렬화 표현**을 공개한다. 라운드트립 보존용 원본 바이트
(`raw_stream`·`extra_streams`)나 내부 shim(`is_hwp3_variant`)처럼 바인딩이 알 필요도
없고 알아서도 안 되는 필드까지 계약이 되고, 한번 나간 필드는 되돌리기 어렵다.

명시 목록은 유지 비용이 들지만, 그 비용이 곧 "무엇을 약속할지 의식적으로 고르는"
과정이다.

---

## D10. 단위 테스트는 바이너리 없이 돈다

**결정**: 탐색·변환·예외 매핑·계획 직렬화는 순수 로직으로 분리해 rhwp 빌드 없이
검증한다. 실물이 필요한 것만 `@pytest.mark.integration`.

**이유**: CI 대부분이 Rust 빌드(수 분) 없이 수 초에 끝난다. 바인딩 기여의 문턱이
낮아지고, 로직 회귀를 빠르게 잡는다.

**함정**: 가짜 픽스처는 플랫폼 기본 인코딩을 따르므로 UTF-8 을 명시해야 한다.
실물 rhwp(Rust)는 콘솔 코드페이지와 무관하게 항상 UTF-8 이다. 이 불일치로 테스트가
두 번 실패했고, 원인은 바인딩이 아니라 픽스처였다.

---

## D11. 계약 패리티 가드를 통합 테스트에 둔다

**결정**: `capabilities` 선언과 파이썬 API 를 대조하는 테스트를 CI 에 둔다.

**이유**: 바인딩이 뒤처지는 것은 **조용히** 일어난다. rhwp 에 명령이 늘어도 파이썬은
아무 오류 없이 잘 돈다 — 그 명령을 못 쓸 뿐이다. 가드가 없으면 사용자가 발견할
때까지 아무도 모른다.

실제로 이 가드가 개발 중 `export-doclang` 누락을 잡았다.

---

## 열린 질문

- **휠에 바이너리 동봉**: 플랫폼별 CI 매트릭스가 필요하다. 지금은 `RHWP_BIN`·`PATH`
  경로만 검증한다.
- **비동기 API**: `asyncio` 지원을 요구하는 소비자가 나오면 `run_json` 의 비동기
  쌍둥이를 둘지 판단한다. 지금은 수요가 없어 미룬다.
- **세션 풀링**: 여러 문서를 다룰 때 서버 하나를 재사용하는 것은 이미 가능하지만
  (`session=` 인자), 자동 풀링은 두지 않았다 — 수명 관리를 암묵적으로 만들면
  프로세스 누수의 원인이 된다.
