# 설계 결정 기록

바인딩을 만들며 내린 판단과 **버린 대안**을 남긴다. 왜 그랬는지 모르면 다음 사람이
같은 논쟁을 다시 하거나, 좋은 이유로 세운 제약을 무심코 걷어낸다.

권위 문서는 [`bindings_foundation.md`](../../../mydocs/tech/bindings_foundation.md)(§2 표면 판단
매트릭스·§4 착수 조건)이고, 파이썬 1호(M18, #3762)의 결정을 승계한 항목은 그 사실을 밝힌다.

---

## D1. 서브프로세스 래퍼 — napi 도 WASM 단독도 아니다

**결정**: rhwp 실행 파일을 프로세스로 띄우고 stdout 봉투를 읽는다.

**버린 대안 ①**: `napi-rs` 로 네이티브 애드온을 만들어 인프로세스 호출.

**버린 대안 ②**: WASM 만으로 Node 까지 덮기.

**이유**: M19 의 착수 조건은 `bindings_foundation.md` §4 가 정한 대로 "M18 의 봉투 매핑
규약 재사용 판정 + napi vs WASM 비교표 갱신"이다. 그 판정의 근거는 이렇다.

| 표면 | 성능 | 배포 | 새로 지는 책임 | 판단 |
|---|---|---|---|---|
| CLI 서브프로세스 | 호출당 기동(수십 ms) + 재파싱 | 바이너리 하나 | 봉투 파서뿐 | **채택** |
| mcp-serve 세션 | 재파싱 회피 | 동일 | 세션 도구 계약 재사용 | **병용(2층)** |
| napi 네이티브 애드온 | 최고 | Node ABI × OS × arch 프리빌드 | ABI 안정성·메모리 규약·릴리스 매트릭스 | 수요 실증 후 |
| WASM | 중간 | JS 생태계 한정 | 파일 시스템 없음 | **브라우저 전용 병용** |

M18(#3762)이 정확히 이 경로로 **CI 에서 251건을 통과**시켰다. "얇은 재포장"이 실제로
성립한다는 것이 실증됐으므로, 언어가 하나 늘었다고 표면 종류를 바꿀 이유가 없다.

napi 는 성능이 가장 좋지만 **Node ABI × OS × arch 매트릭스**를 새로 떠안는다. 그 비용은
인프로세스 성능이 **실제 병목으로 실증된 뒤**에 치르는 것이 맞다. 지금 치르면, 병목이
아니었다는 사실을 알게 됐을 때 되돌릴 수 없는 배포 표면만 남는다.

WASM 단독은 안 되는 이유가 따로 있다 — 파일 시스템이 없다. `export-pdf -o` 처럼 디스크에
쓰는 명령이 성립하지 않으므로 Node 사용자의 절반이 못 쓰는 바인딩이 된다.

**되돌릴 조건**: 인프로세스 성능이 실제 병목으로 실증되면 승격한다(§2 의 "수요 실증 후 승격").
그때도 서브프로세스 경로를 지우지 않는다 — 같은 계약의 두 번째 구현일 뿐이다.

## D2. 판정(exit 3/4)을 예외로 만들지 않는다

**결정**: 검증 단언 실패는 반환값의 판정 필드다. `throwOnVerdict: true` 로만 예외.

**버린 대안**: 0 아닌 종료 코드를 전부 `throw`.

**이유**: `--verify` 불일치는 **도구가 정상 동작한 결과**다. 예외로 올리면 호출자가
`try/catch` 로 "고장"처럼 다루고, 정작 봉투에 담긴 판정 근거(`diffCount`)를 읽지 않는다.
그러면 "표 하나가 달라졌다"와 "파일을 못 읽었다"가 같은 경로로 처리된다 — 대응이 전혀
다른데도.

**버린 이유(추가)**: JavaScript 는 `throw` 가 값 반환보다 편한 언어가 아니다. `Promise`
거절은 타입에 나타나지 않아서, 예외로 만들면 **타입 시스템이 판정의 존재를 잊는다.**
반환값에 두면 `result.verify` 가 시그니처에 남는다.

**대가**: 처음엔 낯설다. README·가이드·요리책·문제 해결 네 곳에서 이 규약을 반복해
설명하는 이유다. (M18 D2 승계.)

## D3. 봉투 타입을 생성한다 — 파이썬과 갈리는 지점

**결정**: `capabilities` 의 명령별 `recordFields` 와 `export-ir-schema` 의 IR 정의 41개,
**두 출처**에서 타입을 생성한다(`tools/gen-types.ts` → `src/envelopes.ts`·`src/ir.ts`).

**버린 대안 ①**: 파이썬처럼 동적 `Envelope` 하나로 끝내기.

**버린 대안 ②**: 명령마다 인터페이스를 손으로 쓰기.

**이유**: 파이썬은 `Envelope` 가 봉투에 있는 것을 전부 노출하므로 구조적으로 뒤처질 수
없었고, 동적 언어에서는 그것으로 충분했다. **TypeScript 는 다르다.** 사용자가 이 언어를
고른 이유의 상당 부분이 "필드 이름을 컴파일러가 확인해 준다"인데, 봉투를
`Record<string, unknown>` 으로만 주면 바인딩이 그 값어치를 통째로 버린다.

그렇다고 손으로 쓰면 rhwp 가 필드를 더할 때마다 뒤처지고, **뒤처졌다는 사실조차 드러나지
않는다**(그냥 값이 안 보일 뿐). 그래서 생성으로 간다. 수기 목록은 없다.

**왜 출처가 둘인가**: IR 스키마는 **문서 모델**을 서술하고, `capabilities` 는 **명령별
봉투**를 서술한다. 봉투 필드에 정적 타입을 붙이려면 둘 다 필요하다. 어느 한쪽을 IR 로
흉내 내면 그 순간 수기 매핑이 부활한다.

**대가**: 생성물이 저장소에 커밋된다. `--check` 로 CI 가 뒤처짐을 잡고, 생성물을 손으로
고치면 다음 재생성에서 사라진다는 것을 문서 세 곳에 적었다.

## D4. 없는 필드는 `undefined` 가 아니라 예외

**결정**: `Envelope.get()` 은 없는 키에 예외를 낸다. 메시지에 **있는 필드를 함께** 싣는다.

**버린 대안**: `obj[key]` 처럼 `undefined` 반환.

**이유**: 조용한 `undefined` 는 오타를 "값 없음"으로 둔갑시킨다. 그 코드는 실패하지 않고
**잘못된 결과**를 낸다 — 가장 찾기 어려운 종류의 버그다. JavaScript 는 `?.` 와 `??` 가
관용구인 언어라 그 오독이 더 깊이 숨는다. `result.verify ?? {}` 한 줄이면 "검증 안 함"과
"검증 실패"가 영원히 구분되지 않는다.

**예외의 예외**: `verify`·`changedPages` 처럼 **계약상 null 이 유효한** 필드는 프로퍼티로
감싸 `null` 을 돌려준다. "없어도 되는 것"과 "이름이 틀린 것"은 다르다. (M18 D4 승계.)

## D5. 이름 변환은 기계로, 개명은 금지

**결정**: `toSnake`/`toCamel`/`snakeKeys`/`camelKeys` 규칙 함수만 두고, 봉투 키는 원문
그대로 노출한다.

**버린 대안**: JS 스럽게 다시 명명(`pageCount` → `pages`).

**이유**: 사람이 이름을 붙이기 시작하면 매핑 표를 유지해야 하고, 그 표는 반드시 뒤처진다.
규칙이면 새 필드가 자동으로 따라온다.

TypeScript 에서는 봉투 키가 이미 camelCase 라 **변환할 일이 파이썬보다 적다.** 그래도
변환기를 두는 이유는 (1) 파이썬 바인딩·snake_case 를 쓰는 외부 시스템과 데이터를 주고받을
때 필요하고, (2) 규칙을 코드로 고정해 두면 사람이 임의로 개명할 유혹이 줄기 때문이다.

```
pageCount ↔ page_count · sourceA ↔ source_a · irSchemaVersion ↔ ir_schema_version
```

## D6. 런타임 의존성 0

**결정**: Node 표준 모듈만 쓴다. `dependencies` 는 비어 있다.

**버린 대안**: `zod`(검증), `execa`(프로세스), `undici`(향후 원격), `chalk`(출력).

**이유**: 바인딩이 무거우면 "재포장"이 아니라 새 표면이다. npm 생태계에서 의존성 하나는
전이 의존성 수십 개이고, 그만큼 버전 충돌·감사 경고·공급망 위험 지점이 는다. 문서 처리
도구는 다른 스택 한가운데 들어가는 경우가 많아 **가벼움이 곧 채택률**이다.

`execa` 를 안 쓴 것이 특히 의도적이다 — 이 바인딩이 프로세스에 요구하는 것(타임아웃,
stdin 주입, 중단 시 정리)은 `node:child_process` 로 충분하고, 그 얇은 층이 곧 우리가
책임지려는 범위다. (M18 D6 승계.)

## D7. ESM + CJS 듀얼

**결정**: 같은 소스에서 ESM·CJS 두 산출물과 각각의 타입 선언을 낸다.

**버린 대안 ①**: ESM 만 낸다("이제 2026년이다").

**버린 대안 ②**: CJS 만 낸다("가장 넓게 호환된다").

**이유**: Node 생태계가 아직 둘로 갈려 있다. 한쪽만 내면 다른 쪽 사용자는 **바인딩을 쓰기
위해 앱 구조를 바꿔야 한다** — 재포장 도구가 요구할 일이 아니다. 이 패키지의 존재 이유는
"이미 있는 계약을 쓰기 쉽게 하는 것"이지 소비자에게 마이그레이션을 시키는 것이 아니다.

**대가**: 듀얼 패키지의 알려진 함정을 우리가 떠안는다.

| 함정 | 대응 |
|---|---|
| `__dirname` 이 ESM 에 없음 | 두 경우를 모두 처리해 동봉 바이너리 경로를 잡는다 |
| 이중 로드로 `instanceof` 깨짐 | 클래스 실체가 둘이 될 수 있음을 문제 해결에 명시 |
| `exports` 서브 경로 타입 해석 | `moduleResolution: node16`/`bundler` 요구를 문서화 |

## D8. 브라우저 어댑터를 같은 인터페이스로 둔다

**결정**: `createBrowserClient(wasm)` 이 Node 경로와 **같은 `RhwpClient` 인터페이스**를
구현한다. 진입점만 다르다(`@rhwp/node` vs `@rhwp/node/browser`).

**버린 대안 ①**: 브라우저용 별도 패키지에 별도 API.

**버린 대안 ②**: 런타임 감지로 하나의 진입점이 알아서 갈라지기.

**이유**: 서브프로세스가 불가능한 환경에서 전혀 다른 API 를 쓰게 하면, 같은 업무 로직을
**두 벌 유지**해야 한다. 문서 검사·서식 채우기 로직은 서버와 브라우저에서 같은 코드여야
할 이유가 충분하다.

런타임 감지를 버린 이유는 번들러다. 하나의 진입점이 조건 분기로 `node:child_process` 를
참조하면, 브라우저 번들에 Node 내장 모듈이 딸려 오거나 폴리필 경고가 뜬다. **진입점을
쪼개면 정적으로 갈라진다** — 번들러가 추론하게 두지 않고 우리가 선언한다.

**대가**: 브라우저 경로는 파일 쓰기 명령을 지원하지 못한다. 인터페이스가 같아도 **환경별
가능 범위는 다르다**는 것을 문서에 표로 못 박았다. 인터페이스 통일이 능력 통일이라고
읽히면 그것대로 거짓말이다.

## D9. 선검증 위반은 예외가 아니라 결과

**결정**: `Plan.check()`/`run()` 은 위반이 있어도 `PlanResult` 를 돌려준다.

**버린 대안**: exit 2 규약대로 `UsageError`.

**이유**: 계획 실행에서 위반은 **설계된 흐름의 일부**다 — 검사하고, 고치고, 다시 검사한다.
예외로 만들면 `try/catch` 안에서 계획을 고치는 어색한 코드가 된다. `describeViolations()`
가 사람이 읽을 형태를 주는 것도 같은 이유다 — 위반은 읽고 대응하라고 있는 것이지
스택 트레이스로 올려 보낼 것이 아니다.

단, `invalid` 가 없는 exit 2 는 진짜 호출 조립 버그이므로 그대로 올린다.

**빌더는 문법만 검사한다**: 셀 값의 줄바꿈 금지, 좌표는 0 이상 정수, step 0개 금지.
실행 가능성(그 필드가 존재하는가, 그 좌표가 병합으로 덮였는가)은 rhwp 의 선검증이
판정한다. 판정자를 두 곳에 두면 반드시 어긋나고, 그때 어느 쪽이 맞는지 아무도 모른다.
(M18 D8 승계.)

## D10. 단위 테스트는 바이너리 없이 돈다

**결정**: 탐색·이름 변환·예외 매핑·계획 직렬화는 순수 로직으로 분리해 rhwp 빌드 없이
검증한다. 실물이 필요한 것만 통합으로 격리한다.

**이유**: CI 대부분이 Rust 빌드(수 분) 없이 수 초에 끝난다. 바인딩 기여의 문턱이 낮아지고,
로직 회귀를 빠르게 잡는다. 바인딩 PR 을 내려고 Rust 툴체인을 갖춰야 한다면 기여자가
줄고, 줄어든 기여는 곧 뒤처짐이다.

**함정 — 인코딩**: 실물 rhwp(Rust)는 콘솔 코드페이지와 무관하게 **항상 UTF-8** 을
주고받는다. 가짜 픽스처는 플랫폼 기본을 따르므로 stdout·stdin 에 UTF-8 을 **명시**해야
한다. 안 그러면 윈도우(cp949)에서만 깨져 "바인딩 버그"로 오인된다. M18 에서 이 불일치로
테스트가 두 번 실패했고, 원인은 바인딩이 아니라 픽스처였다. 같은 비용을 두 번 치르지
않으려고 이 항목을 설계 기록에 남긴다.

## D11. 계약 패리티 가드

**결정**: `capabilities` 선언과 TypeScript API 를 대조하는 테스트를 CI 에 둔다.
생성 타입은 `gen:check` 가 별도로 감시한다.

**이유**: 바인딩이 뒤처지는 것은 **조용히** 일어난다. rhwp 에 명령이 늘어도 TypeScript 는
아무 오류 없이 잘 돈다 — 그 명령을 못 쓸 뿐이다. 가드가 없으면 사용자가 발견할 때까지
아무도 모른다.

M18 에서 이 가드가 개발 중 실제 결함 5건을 잡았다(`export-doclang` 래퍼 누락, 세션
`output` 필수 인자 누락, MCP 도구 누락, `inputSchema.required` 누락, 선언만 하고 배선
안 된 속성). **설계대로 작동한 사례가 이미 있다**는 것이 이 가드를 두는 가장 강한 근거다.

M19 에서는 같은 가드가 **양방향으로** 작동한 사례가 나왔다. `render-diff` 는

1. 처음엔 `--json` 이 없는데 바인딩이 감싸고 있었다 — **없는 계약을 감쌈**.
   통합 테스트 실물 실행에서 `알 수 없는 옵션: --json`(exit 2)으로 드러나 제거했다.
2. 그 뒤 `--json` 이 본체에 들어오자(#3719 §6-2) 이번엔 바인딩에 함수가 없었다 —
   **있는 계약을 빠뜨림**. 같은 패리티 테스트가 잡았다.

두 결함은 정반대인데 **테스트 하나에 걸린다.** 노출 기준을 손으로 고른 목록이 아니라
자기서술에 둔 설계의 값어치가 여기서 나온다. 목록이었다면 1 은 잡히지 않고(목록에 있으니
"의도된 것"이다) 2 는 목록을 고치는 사람이 잊는 순간 영구히 숨는다.

## D13. `Plan.check()` 는 미지원 rhwp 에서 던진다 — 실행으로 대체하지 않는다

**결정**: `check()` 는 계획서를 보내기 **전에** `capabilities` 로 rhwp 의 `run` 이
`--dry-run` 을 선언하는지 확인하고, 선언하지 않으면 `RhwpError` 를 던진다.

**버린 대안 ①**: 미지원이면 그냥 실행으로 내려보낸다("어차피 결과는 나온다").

**버린 대안 ②**: 계획서에 `dryRun: true` 만 실어 보내고 rhwp 를 믿는다.

**이유**: `--dry-run` 을 모르는 rhwp 는 계획서의 `dryRun` 필드를 **그냥 무시하고 편집을
수행하고 저장한다.** 실측으로 재현했다.

```
$ rhwp run --plan-json '{…,"dryRun":true,"steps":[{"action":"replace_text",…}]}' --json
{"changedPages":[0],"output":"…/plan_out.hwp",…,"verify":null}
exit=0

$ ls -l plan_out.hwp
-rw-r--r-- 1 … 473600 … plan_out.hwp
```

exit 0, 경고 없음, 봉투에 `dryRun` 필드 없음 — 그리고 **473,600바이트짜리 편집본이
생겼다.** 호출자는 "검사만 했다"고 믿고 있다. 실패도 예외도 없이 문서가 바뀌므로,
사람이 파일을 열어보기 전까지 아무도 모른다. **조용한 데이터 사고**의 교과서적 형태다.

버린 대안 ②가 특히 위험한 이유는 이것이 **무응답이 아니라 오응답**이라는 점이다.
rhwp 가 "그런 필드 모른다"고 실패해 줬다면 아무 문제가 없었다. 모르는 필드를 조용히
무시하는 것은 JSON 계약에서 흔하고 대개 옳지만, **그 필드가 안전 스위치일 때는 아니다.**

**왜 바인딩이 판단하나**: 판정자를 두 곳에 두지 않는다는 이 바인딩의 원칙(D9)과 얼핏
충돌해 보인다. 하지만 여기서 바인딩이 판정하는 것은 *문서*가 아니라 **도구의 능력**이고,
그 능력은 `capabilities` 자기서술이라는 단일 출처가 이미 답한다. 바인딩은 새 판정을
만드는 것이 아니라 **자기서술을 읽고 계약이 성립하는지만 확인**한다.

**대가 ①**: `run --dry-run`(#3759)이 머지되기 전 rhwp 에서는 `check()` 가 **항상 던진다.**
3층을 쓰려는 사용자에게는 그때까지 `run()` 만 남는다. 이것이 설계대로의 동작이라는 사실을
README·API·요리책·문제 해결에 적었다.

**대가 ②**: `capabilities` 호출이 한 번 더 붙는다. 프로세스 수명 동안 캐시하고
(`clearPlanCapabilityCache()` 로 비운다) — 계획 하나 부를 때마다 다시 띄울 이유가 없다.

**되돌리지 않을 조건**: "미지원이면 그냥 실행"이 편의처럼 보일 때마다, 그 편의의 대가가
**호출자가 안전하다고 믿는 경로에서 파일이 바뀌는 것**임을 기억한다. 바인딩이 지불해도
되는 대가가 아니다.

## D14. 명령은 자기서술로 열되, 플래그는 계약으로 가른다

**결정**: 어떤 명령을 감쌀지는 `capabilities` 의 `json` 선언이 정한다(D11). 그러나
**그 명령의 플래그를 전부 옵션으로 여는 것은 아니다.** `--json` 봉투 계약을 깨거나
아무 일도 하지 않는 플래그는 닫는다.

**버린 대안**: `capabilities` 의 `flags` 를 기계적으로 옵션에 매핑한다.

| 닫은 것 | 실측 동작 | 닫은 이유 |
|---|---|---|
| `exportText` · `exportStructure` 의 `-o` | `--json` 모드에서 **조용히 무시**(디렉터리조차 안 생긴다) | 받아 주면 "저장했다"는 거짓말이 된다. 아무 일도 하지 않는 옵션은 없느니만 못하다 |
| `exportTables` 의 `-o` | stdout 이 사람용 문장으로 **바뀐다** | 봉투 계약이 깨져 `runJson` 이 `ProtocolError` 를 던진다 |
| `renderDiff` 의 `--batch` | 한 줄 봉투가 아니라 **NDJSON 스트림** | 한 함수의 반환 타입은 하나여야 한다 |

**왜 기계적 매핑을 버렸나**: `capabilities` 의 `flags` 는 "이 명령이 이 플래그를 파싱한다"
는 사실만 말한다. **그 플래그가 `--json` 모드에서 무엇을 하는지는 말하지 않는다.**
위 세 자리가 정확히 그 간극이고, 셋 다 실물 실행으로만 드러났다.

**가른 기준은 봉투 계약이다.** 같은 `-o` 라도 `exportCapabilitiesSchema` 는 **열어 뒀다** —
저장해도 stdout 이 봉투를 유지하기 때문이다(`output`·`bytes` 가 담긴다). 플래그 이름이
아니라 **계약을 지키는가**로 가른다.

**`exportTables` 는 우리 문제가 아니다**: 앞의 둘은 "쓸모없는 옵션을 안 여는" 정리지만,
`exportTables -o` 는 **`--json` 을 준 호출에서 출력 형식이 바뀌는** 것이다. 그것은 명령
하나의 사정이 아니라 봉투 계약 전체의 예외이고, 바인딩이 옵션을 닫은 것은 회피일 뿐
수정이 아니다. **본체 쪽 별도 업스트림 이슈감**으로 남긴다.

**`--batch` 를 뺀 것은 성격이 다르다.** 계약이 깨져서가 아니라 **반환 타입이 달라서**다.
단건은 `Envelope`, 배치는 레코드 배열이다. 한 함수가 둘 다 처리하면 호출자가 받은 값이
봉투인지 배열인지 타입으로 알 수 없게 되고, 그러면 TypeScript 를 쓰는 이유가 사라진다
(D3 와 같은 근거다). 폴더 일괄은 `runNdjson` 이라는 이미 있는 문을 쓴다.

**대가**: "자기서술이 노출을 결정한다"는 문장에 각주가 붙었다. 각주 없이 기계 매핑으로
가면 문서가 더 단순해지지만, **항상 실패하는 옵션**이나 **봉투를 깨는 옵션**을 API 에
싣게 된다. 각주를 지는 편이 싸다.

## D12. 정리는 `close()` 가 계약, `await using` 은 축약

**결정**: `Document`·`Session` 은 멱등 `close()` 를 계약으로 두고, `Symbol.asyncDispose`
를 추가로 구현한다. 폴리필은 넣지 않는다.

**버린 대안 ①**: `await using` 전용으로 설계하고 `close()` 를 감춘다.

**버린 대안 ②**: 진입점에서 `Symbol.asyncDispose` 를 폴리필한다.

**이유**: `await using` 은 TypeScript 5.2+ 문법이면서 **런타임에 심볼이 실제로 있어야**
동작한다(Node 20+). 지원 환경만 대상으로 설계하면 Node 18 사용자는 자원 정리 수단을
잃는다 — 그리고 정리 실패는 "서버가 남아 파일이 잠긴다"는 형태로 나타나 원인을 찾기 어렵다.

폴리필을 안 넣는 이유는 부작용이다. `sideEffects: false` 를 선언한 패키지가 전역을
오염시키면 번들러의 가정이 깨진다. 전역을 건드릴지는 앱이 정할 일이다.

## 열린 질문

- **패키지에 바이너리 동봉**: `dist/_bin/` 경로는 계약으로 열어 뒀지만 채우지 않았다.
  OS × arch 릴리스 매트릭스와 `optionalDependencies` 분할(플랫폼별 서브패키지) 중 무엇을
  고를지 정하지 않았다. 지금은 `RHWP_BIN`·`PATH` 경로만 검증한다.
- **npm 배포**: 스코프(`@rhwp`)와 버전 정책(rhwp 본체 버전과 연동할지 독립할지)이 미정이다.
- **napi 승격 기준**: "실제 병목으로 실증"의 기준선을 숫자로 정하지 않았다. 세션(2층)이
  상쇄하지 못하는 사용 패턴이 보고되면 그때 정한다.
- **스트리밍 표면**: `iterNdjson` 은 있지만 Web Streams(`ReadableStream`) 어댑터는 없다.
  요구하는 소비자가 나오면 판단한다.
- **세션 풀링**: 여러 문서를 다룰 때 서버 하나를 재사용하는 것은 이미 가능하지만
  (`session` 옵션), 자동 풀링은 두지 않았다 — 수명 관리를 암묵적으로 만들면 프로세스
  누수의 원인이 된다.
- **브라우저 어댑터의 계약 검증**: Node 경로는 `capabilities` 대조로 뒤처짐을 잡지만,
  WASM 경로가 같은 인터페이스를 계속 만족하는지는 아직 타입 수준에서만 보장된다.
