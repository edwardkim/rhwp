# 커진 표 다음 저장 줄의 흐름

## 공개 PDF 검증 입력

`native-8-0.hwpx`는 공개 합성 문서의 텍스트·표를 한컴 2020(11.0.0.9136)에서
HWP→HWPX로 정상 재저장한 파일이다. 사용자 양식이나 비공개 내용은 포함하지 않는다.
파일명은 기존 경로를 유지했지만 현재 내용은 HWP5-origin 마커가 없는 한컴 HWPX다.
SHA256: `3aa0379ab1b4d158800d33c73ae26eed909e5f08e3614dca228044780c8c5e64`.

원 제출 파일에는 표 앞 15개, 뒤 70개 공백과 Footer가 있었으나 수동 저장한 호스트
LineSeg는 3개뿐이었다. 실제 네 번째 줄(textpos 83)과 셀의 8줄 메트릭이 누락되었고,
선언 표 높이도 실제 내용과 달랐다. 한컴은 표 높이 6000→12872 HU, 호스트 3→4줄,
셀 줄 메트릭을 다시 저장했다. 정상 재저장본을 기존 경로에 적용하고 별도
`hancom-resaved.hwpx`는 중복 보관하지 않는다.

교체 전 파일은 commit `086078148db2a9f66b21c98a2f3d356c40365fec`의 같은 경로에 보존되어 있다.
이전 실패 PNG와 변환 job은 [검토 기록](../../mydocs/pr/archives/pr_7242_review.md)에 남긴다.
잘못된 저장 정보를 엔진이 자동 복구했다는 의미가 아니다.

기준은 [한컴 PDF](../../pdf/pr7242/native-8-0-2020.pdf)다. 교체 전후 입력의 한컴 PDF raster가
동일함을 확인했으므로 PDF를 중복 추가하지 않는다. 정식 회귀 검사
`hancom_saved_tail_preserves_pdf_baseline_after_the_table`는 **이 공개 파일 자체**를 읽어
4줄의 텍스트 소속, 한 쪽, 표 외곽과 Footer 기준선을 검사한다. 독립 기대값은 PDF의
Footer 기준선 354.4891px와 표 외곽 y=140.77..312.42px(96dpi)다. 허용 오차는 0.5px다.

## 메모리에서 생성하는 기하 계약 입력

`tests/cases/stored_table_text_tail.rs`는 위 정상 파일에서 별도의 수동 경계 입력을 만든다.
공개 파일의 메트릭을 그대로 검사하는 PDF 테스트와 구분한다. 셀 LineSeg를 제거하고
선언 표 높이를 6000 HU, 호스트 줄을 0/1000/7000+gap HU의 3줄로 명시적으로 구성한다.
공개 파일의 70개 공백은 바꾸지 않고, 메모리 경계 입력에서만 표 뒤 공백을 2개로 줄인다.
표 앞 15자 + 표 제어 8단위 + 공백 2자 = textpos 25이므로 Footer 자체가 세 번째 줄의
시작이며 추가 네 번째 줄이 필요하지 않다. 테스트는 Footer의 가로 시작점과 셀 폭 안의
수용도 검사한다. 이 파생 입력을 한컴이 저장한 문서나 PDF 일치 증거로 취급하지 않는다.

- 셀 문단 2/8개: 2개는 선언 높이 6000 HU에 들어가고, 8개는 실제 표가 커지는 경계를 검사한다.
- 저장 줄 사이 gap 0/600 HU: 96dpi에서 Footer 위치 차이가 8px인지 검사한다.
- native/pure: 파싱 전에 메모리 ZIP에 HWP5-origin 마커를 추가하거나 없는 상태로 둔다.
- 문단 뒤 간격 0/600/1200 HU: 같은 문단의 Footer는 움직이지 않아야 한다.
- 같은 문단에 도형을 추가하고 다음 문단을 검사한다. 표·도형·부분 문단이 실제 페이지 항목에
  존재하며, 뒤 간격을 늘리면 다음 문단만 8/16px 내려가야 한다.

작은 표의 독립 간격은 `(7000 + gap) - 1000 - 6000 = gap`이다.
앞 빈 줄의 1000 HU를 표 뒤 간격에 다시 더하지 않는다. 생성 방식·수치 가정과
실제 정상 저장 파일의 검증 결과는 위 검토 기록에서 각각 보고한다.
