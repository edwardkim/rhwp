## 형상

4쪽 목차. 각 줄은 제목 · 점 리더 · 쪽번호로 끝난다. 한컴은 대부분의 줄을
**탭으로 끝나는 런 + 쪽번호 런**(교차-run)으로 저장하지만, 넷째 줄만
**탭과 쪽번호를 한 런**(`"\t8"`)에 담았다.

```text
런 "\t8"   x=595.4   charX [0.0, 88.5, 98.3]
  수정 전  w=78.0  → 상자는 673.4 에서 끝나는데 글자는 693.7 까지 간다
  수정 후  w=98.3  → 상자와 글자가 693.7 에서 함께 끝난다

형제 줄(교차-run 경로)  "1" · "2" · "8" · "12" · "15" · "18"  모두 오른쪽 끝 693.7
```

`pending_right_tab_render` 는 런이 탭으로 **끝날 때**만 서므로 이 런은 그 경로를 타지
않는다. `charX` 는 이미 오른쪽 정렬된 자리를 담고 있었고, **bbox 폭만**
`estimate_text_width` 가 낸 "탭 스톱까지" 값으로 남아 있었다.

## 회귀 계약

탭 뒤가 가시문자로 끝나는 런은 **마지막 문자 경계가 곧 잉크의 끝**이다. bbox 폭을
거기에 맞춰 `bbox·장식·리더·문자 위치`가 하나의 값을 공유하게 한다.

⚠ **출력은 불변이다** — 글리프 위치는 이미 옳았고 상자만 짧았다. 이 문서 4쪽 SVG 는
수정 전후 바이트가 같다. `#6800` 과 같은 **렌더 트리 계약** 결함이라, hit-test·선택·클립
처럼 상자를 쓰는 소비자만 영향을 받는다. 기준 PDF 는 형상 확인용이고 이 축의 판정을
주지 않는다.

## 코퍼스 실측 (10,000건)

```text
  런 안 중간 탭                                   9,923건
    ├ inline_tabs 가 LEFT 명시                    7,180건  (대상 아님 — 좌측 전진이 옳다)
    ├ TabDef 가 LEFT                                 48건  (대상 아님)
    └ 우/가운데 스톱                              2,695건
        └ 런의 마지막 탭 + 줄의 마지막 런          2,574건  ← 이 수정의 대상 형상
  대상 형상 중 **글리프가 상자 밖**                  998건  (최대 571.7px)
  layout-anomaly 다섯 지표 변화                        0건
```

⚠ **문자 위치 자체는 옮기지 않는다.** 교차-run 경로의 `effective_pos` 변환을 그대로
가져와 재정렬해 봤더니 34건이 움직였고, 그중 `3142535`(별지 5 징수결정액통지서)의 글자가
`x=671.4 → 1000.1` 로 **용지(793.7) 밖**으로 나갔다. 그 런들의 위치는 기존 기계가 정하고
있고 그 계약은 이 이슈의 범위가 아니다 — 기각했다.

새 sample이 기존 코퍼스 래칫에 주는 영향은 통합 검증에서 실측한다. 알려지지 않은
회귀를 숨기려고 기존 문서 기준선을 올리거나 보안 탐지 신호를 포괄적으로 무시하지 않는다.
