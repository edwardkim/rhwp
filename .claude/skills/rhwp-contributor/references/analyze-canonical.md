# 분석: 원인과 독립적인 기대 결과

기여 구현은 [CONTRIBUTING.md](../../../../CONTRIBUTING.md)를,
메인터너 검토는 [PR review workflow](../../../../mydocs/manual/pr_review_workflow.md)의 역할별 경로를 따른다.
[문서 지도](../../../../mydocs/README.md)에서 해당 영역의 현재 canonical 문서를 찾는다.

## 구현 전에 남길 판단

- 실제 입력, 재현 조건과 사용자에게 보이는 실패를 특정한다.
- 기대 결과는 사양, 입력과 대응하는 기준 출력 또는 독립적인 기존 계약으로 정한다.
  현재 구현의 출력을 그대로 테스트 기대값으로 옮기지 않는다.
- 원인이 있는 파일/함수와 파서, IR, 측정, 레이아웃, paint, 저장 중 책임 계층을 설명한다.
- 정상 사례와 적용되면 안 되는 반례, 변경에 필요한 경계/혼재 사례를 선정한다.
- 검증 범위와 남기는 증거, 이번에 해결하지 않는 문제를 기록한다.

비슷한 코드나 과거 PR의 성공 판정만으로 현재 사례의 원인을 추정하지 않는다.
입력과 기준 출력의 페이지 번호가 다르면 내용으로 대응 영역을 먼저 찾는다.
DocumentCore나 CLI 변경의 허용 여부는 실제 이슈 범위와 해당 아키텍처 계약으로 판단한다.
